# _shared

> **Role.** The cross-adapter shared-infrastructure package. Logic recurring across three or more harness adapters is hoisted here so each adapter holds only its harness-specific identity and scope. The underscore prefix keeps this package out of the `apothem.harnesses` entry-point namespace — it is shared machinery, not a registrable adapter.

## What lives here

`install_driver.py` is the shared propagation driver every adapter's `install.py` delegates to. It carries the install recipe once: load a harness's rules from `lib/propagation-manifest.yaml`, sweep stale top-level paths from earlier layouts, then apply each install entry in declaration order. The driver supplies:

- The structured materialization-result surface (`MaterializationResult` / `MaterializationRun`) with deterministic per-outcome counts.
- The safe-write primitives: path validation against an allowed root, backup-before-replace, atomic swap, no-op detection, and backup retention (`BACKUP_KEEP`: the newest 10 install records per root and backup sets per harness are kept, plus anything a kept record references).
- The directory-replace and stale-sweep primitives.
- The operator-owned merge path: sentinel-block merge for Markdown anchors, key-preserving merge for JSON and YAML. An operator file that parses only as JSONC, JSON5 or commented YAML is left byte-identical when the merge changes no value and refused with `config.unparseable` when it would, so a rewrite never drops the operator's comments. Each structured merge records in the install ledger exactly which keys and list items Apothem added; the next install replaces only those and uninstall removes only those, so operator entries (permission rules, MCP servers, hook handlers) survive.
- The destructive-authorization gate.
- The no-write previews (`install_driver_preview.py`) for the writes an install makes beyond the manifest list (data stores, native config, instruction anchor, profile document), so `install --dry-run` and `diff` list every path the install writes.
- Rollback of a recorded install (`install_driver_reversal.py`): each recorded backup is restored to its recorded path, every file and directory the install created is removed, and the directories it created (captured before the install writes anything) are removed once empty.
- Retention of the install ledger and backup sets (`install_driver_retention.py`): after every install, uninstall and rollback, and on demand through `apothem backups prune`, it keeps the newest N backup sets per harness and install records per install root, and never removes a backup set a kept record, or a root's latest install record, references.
- The installed corpus layout (`install_driver_layout.py`): where an install places the directories Apothem bodies cite (`rules/`, `templates/`, `schemas/`, `hooks/`, `conformity/`), derived from the manifest, for the note each command-as-skill carries and for the "Apothem support files" section each install adds to its instruction anchor (a `sentinel_merge` anchor, Claude Code's `CLAUDE.md`, or the profile document of an adapter with no anchor). When the install places `rules/apothem-rule-index.md`, the section also carries one sentence that points at it, so a harness that loads no rule file at launch still reaches every rule.
- The per-mode entry appliers (`write_text`, `replace_tree`, `merge_tree_entries`, `command_skills`, and the per-harness agent/command converters).
- User-level folders shared by several installs (`install_driver_shared.py`): a manifest target spelled `${USER_HOME}/...` (the skills folders such as `~/.agents/skills/`, and the rules and templates corpus under `~/.config/apothem/`) is written by every install that names it, with the same bytes whichever harness writes it (one skill emission, one reference note). The install ledger is the reference counter: an uninstall or rollback removes a target only when no other install's current record still lists it, and an unreadable ledger of a harness that writes such a folder stops the uninstall or rollback before it changes anything (the install stays recorded; `install_driver_sharedlock.py` also holds the lock and says which harnesses write user-level folders). A rollback also removes a folder its install only found in place when an install that has let go of it created it, so rolling back every holder strands nothing. A skill folder that no record lists and that differs from what would be written is left alone with a `skill_conflict` warning (`install_driver_skillguard.py`). Each user-level skill folder is written to a hidden `.<name>.apothem-staging` sibling and renamed into place, so an interrupted write leaves no half-written folder that would read as foreign. A symlink at or above a closed user-level folder is followed when it stays inside the home. In a project-scope block these entries come first, so a failure writing the home aborts the install before the project changes. One lock under the ledger state root spans the first write through the ledger record, and a backup taken from the home during a project-scope install is keyed under `__home__/`.

The driver's implementation is decomposed into single-responsibility sibling modules — `install_driver_agent_apply.py`, `install_driver_agent_comma_tools.py`, `install_driver_agent_copilot_cursor.py`, `install_driver_agent_emitters.py`, `install_driver_agent_kimi_devin.py` and `install_driver_agent_kiro.py` (the agent emissions, below), `install_driver_apply.py`, `install_driver_backup.py`, `install_driver_converters.py`, `install_driver_datahome.py` (where an install's shared data stores live, as recorded on its ledger record), `install_driver_hookfile.py` (the `native_hooks` mode, below), `install_driver_jsonmerge.py`, `install_driver_layout.py`, `install_driver_lifecycle.py`, `install_driver_materialize.py`, `install_driver_merge.py`, `install_driver_ownership.py`, `install_driver_pathsafety.py`, `install_driver_planvalidation.py`, `install_driver_preview.py`, `install_driver_removal.py`, `install_driver_retention.py`, `install_driver_reversal.py`, `install_driver_shared.py` (the user-level folders above), `install_driver_sharedlock.py` (their lock), `install_driver_skillguard.py` (foreign skill folders), `install_driver_treeops.py`, and `install_driver_types.py` — which `install_driver.py` composes into the public driver surface. `wrapper_factories.py` builds the shared adapter classes (the user-scope and project-scope adapter factories) so each adapter's `__init__.py` declares only its harness identity and scope. A project-scope install can be given a `content_tokens` resolver (`python_bin_tokens` for the hook interpreter, `python_call_tokens` for the interpreter plus the `& ` call operator that a PowerShell command line needs on a Windows host); the factory runs it before anything is written, preview included, and renders the tokens it returns into the templates the install writes.

The `native_hooks` mode writes the hook-registration JSON file of a harness whose hooks are flat entries rather than Claude-shaped handler groups, implemented in `install_driver_hookfile.py`: the one file Apothem owns in a hooks folder (Kiro's `.kiro/hooks/apothem.json`, GitHub Copilot's `.github/hooks/apothem.json`) or an entry in the operator's own project hook file (Cursor's `.cursor/hooks.json`). The vendors' files do not nest handlers under a matcher the way Claude Code's settings do, so the Claude-shaped merge in `install_driver_jsonmerge.py` does not apply: the mode reads a hook list (`hooks: [...]`, the command at `action.command`) or an event map (`hooks: {event: [...]}`, the command in `bash`, `powershell` or `command`). A hook is Apothem's when its command runs `.../hooks/dispatch.py` under the project, which holds without an install record and without the interpreter token the install rendered. An install writes the rendered template as the whole file, keeps any hook the operator added ahead of Apothem's, and backs up a file it replaces; an uninstall removes Apothem's hooks, deletes a file left with none, and leaves a file it cannot read as it is. The manifest entry's ownership class sets what happens to a file the merge cannot enter without damage: an `apothem-owned` file is replaced after the backup, and an `operator-owned` one (Cursor's) is refused with `config.unparseable` and left untouched.

The agent emissions are one registry. Each mode that renders the source `agents/` cohort into a harness's native subagent files is a row of `AGENT_EMITTERS` in `install_driver_agent_emitters.py`: its renderer, the extension of the file it writes (`None` keeps the source name, `toml`, or a double extension such as `agent.md`), whether an earlier `.md` copy is retired first, and the source agents the harness is not given (`exclude`). `install_driver_agent_apply.py` installs a row through one applier, and the install dispatcher, the plan, the dry-run preview and the uninstall enumeration all read the same row, so a new agent emission is one row and its renderer. `install_driver_agent_comma_tools.py` holds the CodeBuddy and Trae renderers, which share one shape: a fresh frontmatter of `name`, `description`, and `tools` and `disallowedTools` as comma-separated strings limited to each vendor's tool names (CodeBuddy also keeps `maxTurns`). `install_driver_agent_copilot_cursor.py` holds the GitHub Copilot and Cursor renderers: Copilot writes `name`, `description` and a `tools` allowlist of Copilot aliases into `<name>.agent.md` (no deny key, so `disallowedTools` is folded into the allowlist), and Cursor writes `name`, `description` and `readonly: true` only for an agent that is read-only and holds no shell. `install_driver_agent_kimi_devin.py` holds the Kimi Code and Devin Local (Windsurf) renderers, which translate the tool names into each vendor's own list: Kimi Code writes `name`, `description`, `tools` and `disallowedTools` as lists of Kimi tool names (`WebFetch` is `FetchURL`, `TodoWrite` is `TodoList`), and Devin writes `name`, `description` and one `allowed-tools` list of lowercase Devin tool names, with the source denials folded in because Devin has no deny key. `install_driver_agent_kiro.py` holds the Kiro renderer: it writes `name`, `description` and one `tools` list of Kiro category tags (`read`, `write`, `shell`, `web`, `subagent`) into `<name>.md`, folding `disallowedTools` into the list and dropping a tag the source denies any tool of. The `devin_agents` row is the one that sets `exclude`: it holds back the three agents that need web tools, whose `allowed-tools` names Devin does not document. `_INSTALL_ENTRY_MODES` and `OPERATION_LABELS` in `install_driver_types.py` stay literal tables; a row without an entry in both fails `tests/unit/test_install_driver_agent_emitters.py`.

Scope is expressed by which root the caller supplies — a user-scope harness root or a project-scope project root.

## Conventions

- Writes go through the safe-write primitives — never bypass them with a raw `Path.write_*`.
- Targets whose ownership class is vendor-reserved or immutable are refused outright; operator-owned non-additive overwrites route through the authorization gate with a unified diff.
- The hoist threshold is structural similarity across **three or more** adapters, not mere topical overlap; genuinely per-harness logic stays in the adapter subpackage.
- The package name stays underscore-prefixed; nothing here registers as an adapter or joins the `apothem.harnesses` entry-point group.
- This package is in `mypy --strict` scope.

## Operating in this folder

Add or change a primitive here only when the behavior is shared by three or more adapters; a one-adapter need belongs in that adapter's own module. Preserve the structured result/run surface — callers depend on the outcome vocabulary (`created` / `updated` / `unchanged` / `skipped` / `warning` / `error`) and the dry-run contract — so extend it additively rather than redefining existing outcomes. Validate with `python -m ruff check`, `python -m mypy src/apothem/harnesses/`, the conformity gate (`python -m apothem.conformity.gate --all .`), and `python -m pytest` (the adapter round-trip integration suite exercises this driver through every adapter).
