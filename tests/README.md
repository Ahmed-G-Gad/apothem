# Tests

The `apothem` test suite. `pytest` is the sole test framework; the configuration lives in the root `pyproject.toml` under `[tool.pytest.ini_options]`.

## Configuration

| Setting | Value |
|---------|-------|
| `testpaths` | `tests` |
| `addopts` | `-ra --strict-markers --import-mode=importlib -n auto` |

`--import-mode=importlib` avoids basename collisions between sibling `test_*.py` files across subtrees; `-n auto` runs the suite in parallel via `pytest-xdist`.

## Layout

| Subtree | Holds |
|---------|-------|
| `unit/` | Per-module unit tests — the harness adapters (one per registered harness in the 17-harness cohort), the CLI surface, the harness materializer, the conformity-gate scope, the parallel sweep, the propagation manifest — **plus a repo-coherence-guard class**: cross-surface drift guards (`test_harness_registry.py` against `site/app/page.tsx` + `pyproject.toml`, `test_citation_cff.py`, `test_example_settings_sync.py`, `test_example_cursor_rules_sync.py`, `test_assets_manifest_coverage.py`, `test_guard_wiring_coherence.py`, `test_crlf_set_sync.py` against `.gitattributes` + `.editorconfig` + `.pre-commit-config.yaml`) and the `unit/docs/` subtree, which validates the docs-site frontmatter examples against the conformity contract. |
| `integration/` | Cross-component integration tests — multi-harness parity, the hermetic clean-machine installer gate, installer tag-verification aborts, clean-slate install, the rollback CLI, the install-ledger acceptance matrix, memory portability / isolation, the self-contained vendored runtime, and the byte-golden behavior-diff walls (CLI + install-driver), with a guard that their oracles capture the same bytes on Windows and Linux. |
| `conformity/` | Per-validator self-tests. Most matchers own a directory named for the matcher's kebab module (`hedging-grep`, `secret-leak-grep`, `magic-number-grep`, `bare-except-grep`, `binding-reciprocity-grep`, `unpinned-action-grep`, and more) carrying `pass` / `fail` fixtures or scenario tests; a set of top-level `test_*.py` files hold cross-matcher infrastructure and scope-contract tests (the corpus per-write runner, the matcher-coverage loop, the standalone-grep in-process sweep). See [Conformity corpus layout](#conformity-corpus-layout) for the directory-name resolution rules. |
| `hooks/` | Hook-infrastructure tests — the dispatcher, hook-context emission, the session-start bootstrap, the interpreter locator, the header-inject guard, and the plan-write guard. |
| `scripts/` | Tests for the executables under [`scripts/`](../scripts/) — the header injector, the installer invocation model, the release-notes extractor, the SBOM recipe, script-pair parity, the behavior-diff golden regenerator, and the validation tooling. |
| `packaging/` | Release-artifact packaging tests — sdist + wheel payload contract, runtime tarball/zip build, examples validity. |
| `commands/` | Slash-command behavior tests (e.g., `plan-spec-quick`). |
| `property/` | Property-based tests (Hypothesis) over the invariants — frontmatter parsing, materialize round-trip, profile merge, path-safety, and operator settings entries surviving install, update, uninstall and rollback. |
| `fuzz/` | Atheris fuzz targets for the operator-file parsers (the JSONC / JSON5 reader, the hook-file merge, the profile loader, the install ledger, the frontmatter probe), their seed inputs, and `test_fuzz_seed_replay.py`, which replays every seed in the ordinary run. ClusterFuzzLite fuzzes them in CI (`.github/workflows/fuzzing.yml`); see [`fuzz/README.md`](fuzz/README.md). |
| `conformity-scenarios/` | End-to-end multi-mandate fixture scenarios (`F-*`) driven by `verify.py` and gated in CI by `.github/workflows/conformity.yml` — not collected by the default `pytest` run (see Running). |
| `fixtures/` | Shared cross-suite fixtures — the multi-surface-claims schema, the plans-discipline fixture, and the byte-golden `behavior-diff/` corpus — each with a paired schema/fixture test. |
| `_shared/` | Cross-subtree test helpers imported as `tests._shared`, not collected as tests. `bash_resolver.py` locates a usable POSIX `bash` (and refuses the Windows WSL launcher, which is not one), so the installer tests skip honestly on a host without it instead of failing. `git_env.py` builds the environment for a test's git subprocesses with the host's global, system and environment-carried git config switched off, so a developer's `gpg.format ssh`, `commit.gpgsign` or global hooks path cannot change a fixture repository. `python_shim.py` writes a `python3` shim that execs the interpreter running the test, so a script or hook command that names `python3` does not run the host's, which can lack the test's dependencies or be the Windows Store alias. `claude_rule_scope.py` restates two Claude Code rule behaviors for the rule tests: a `paths` list that scopes nothing (empty after a trailing `/**` is stripped, or `**` alone) loads the rule at launch, and a rule glob matches a path with `.gitignore` semantics. |

The `unit/` repo-coherence guards also include `test_no_hidden_bidi_controls.py`: it lists the tracked files with `git ls-files`, skips binary ones, and fails on any text file that holds a hidden bidirectional control (U+202A to U+202E, U+2066 to U+2069), naming its file, line, column and code point. The marks LRM, RLM and ALM stay allowed; a file that needs a control goes on the test's allowlist with its reason.

## Running

```sh
pytest
```

The configured `-n auto` parallelism is the default. On Python 3.14, the `pytest-xdist` worker capture interacts poorly with some output-capturing tests; run those with `pytest -n0 -s` to disable parallel workers and output capture when a 3.14 capture quirk surfaces.

The `conformity-scenarios/` subtree is **not** collected by `pytest` (it carries no `test_*.py` — only a `verify.py` runner plus `F-*` fixtures). It is gated in CI by `.github/workflows/conformity.yml`; run it locally with `python tests/conformity-scenarios/verify.py`.

## Conventions

- Test files mirror their source: `tests/<subtree>/test_<unit>.py` for the unit under test.
- Conformity self-tests follow the `pass` / `fail` fixture pattern where the matcher is fixture-driven.
- Markers are strict (`--strict-markers`) — every marker used is declared, or collection fails.
- Tests assert behavior over implementation, name the behavior in the test name, and never depend on test ordering (the suite runs in parallel).
- A test that builds a fixture git repository (init, config, commit, tag), or runs a script that does git work on one, SHOULD take the subprocess environment from `hermetic_git_env()` in `_shared/git_env.py`, so the host's git config cannot change the outcome.
- A test that runs a script or command naming `python3` SHOULD put a `write_python_shim()` shim from `_shared/python_shim.py` first on the subprocess PATH, so the host's `python3` cannot change the outcome.
- The root `tests/conftest.py` owns the suite-wide bootstrap: two `sys.path` inserts (`src/`, so `apothem` imports from a plain checkout with no editable install; and the repo root, so the helpers under `_shared/` resolve as `tests._shared` however pytest is invoked) plus the isolation of what an install or a hook writes outside the test's temporary folders: the user home itself (`HOME` and `USERPROFILE`), the install ledger (`install_ledger.STATE_ROOT`), the backup root (`install_driver.BACKUP_ROOT`), the Codex root (`CODEX_HOME`, cleared), the Claude Code folder (`CLAUDE_CONFIG_DIR`, cleared), the hook state folder (`APOTHEM_HOOK_STATE_DIR`, pointed at a temporary folder) and the XDG base directories (`XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `XDG_DATA_HOME`, `XDG_CACHE_HOME`, cleared, so the code and the tools a test launches, such as `pwsh`, fall back to the temporary home). The ledger and backup roots are bound from `Path.home()` when their modules are imported, before any fixture runs, so redirecting `HOME` does not move them; the three variables place a write or a read whatever `HOME` says. Each of these is therefore redirected twice: for the whole session, which covers module-, class- and package-scoped fixtures that run an install (pytest builds higher-scoped fixtures first), and again for every test. A session-scoped fixture that runs an install MUST request `_isolate_session_home` as a parameter, because pytest sets up session-scoped autouse fixtures in the order they were registered (a plugin's first, then a conftest's by name), not by intent. `unit/test_suite_state_isolation.py` pins the session-level redirect and fails on any other module-level path that still names the real home. The writes no fixture can catch (collection-time code, a plugin's session-scoped fixture) are audited by running pytest with `HOME` and `USERPROFILE` set to an empty folder and checking that nothing appears in it; the `home-isolation` job in `.github/workflows/ci.yml` does that for the whole suite whenever that workflow runs, with the XDG base directories on empty folders too. Per-subtree conftests carry only subtree-specific fixtures.

## Real-home guard

A test must never run Apothem against your real home folder. The isolation fixtures in `tests/conftest.py` move the home and Apothem's state folders into temporary folders, and their names start with `_`. A probe folder whose conftest star-imported `tests/conftest.py`, at a time when a star import skipped those names, once ran an install and an uninstall against a developer's real home: it deleted a real install ledger and overwrote a file in `~/.config/apothem`.

Two things in `tests/conftest.py` now stop that:

- **`__all__`.** It lists the isolation fixtures, `_report_real_home_refusals`, the guard's names and the other public names, so `from tests.conftest import *` brings the isolation with it, and the fixture that fails a test after which an absorbed refusal was found (see **Report** below). Without that fixture the guard still fails such a test, but says the refusal came while a fixture was torn down.
- **The guard, `real_home_guard`.** Importing `tests/conftest.py` inside a pytest session registers this plugin object with that session, however the import is written: pytest loading the file as a conftest, `-p tests.conftest`, a star import, or a conftest that imports single names, such as two isolation fixtures and no guard name. It is registered once per session, as `apothem-real-home-guard`, and pytest calls its hooks on the object, so deleting or rebinding a name in a conftest does not remove it. If the file was imported before the session started, the `pytest_configure` hook `pytest_register_real_home_guard`, which a star import carries, registers it instead. Its hooks:
  - **Setup.** It runs first when pytest sets up a test, before any fixture, and fails the test when `_isolate_session_home`, `_isolate_user_home`, `_isolate_install_ledger` or `_isolate_backup_root` does not apply to it, whichever import brought the others in. It also fails the test when `_isolate_session_home` is a fixture of the same name from somewhere else, and when a session-scoped fixture would be set up before `_isolate_session_home` without requesting it: pytest sets up session-scoped autouse fixtures in the order they were registered (a `-p` plugin's, then a parent conftest's, then a conftest's own by name), so a fixture named `_install_x` would run first, against the real home. The test's own fixtures then never run, so they cannot write to the real home while they are set up, and the same holds under `--setup-only`. The message names the missing fixtures or the fixture that would run too early. Fixtures of a plugin installed as a package are not checked for their order.
  - **Call.** It runs after every fixture of the test is set up, after every `pytest_runtest_call` hook and every `pytest_pyfunc_call` wrapper has started, including those of a conftest that imported the file and of a plugin registered before it, right before pytest calls the test function. A `unittest` case or a doctest is checked in `pytest_runtest_call` instead, right before pytest runs it. It fails the test before the body starts if any of these points at the real home or at a real folder in it:
    - the `HOME` and `USERPROFILE` variables and `Path.home()`;
    - the user home the install manifest uses (`propagation.user_home()`);
    - the data home (`~/.apothem`) and the profile and support folder (`~/.config/apothem`);
    - the install ledger root (`install_ledger.STATE_ROOT`) and the backup root (`install_driver.BACKUP_ROOT`);
    - `CODEX_HOME`, `CLAUDE_CONFIG_DIR` and `XDG_CONFIG_HOME`, which move the Codex home, the Claude Code folder and the OpenCode folder;
    - the hook state folder, which falls back to `LOCALAPPDATA` on Windows when `APOTHEM_HOOK_STATE_DIR` is unset, and `CLAUDE_PLUGIN_DATA` or `XDG_STATE_HOME` when it builds that folder.
  - **Report.** A test the guard stopped stays failed when it is marked `xfail`, and so does a test after which an absorbed refusal was found (see the product-side refusal below). Without this, pytest would report it as XFAIL and the run would pass. The guard knows its failure by a mark on the failure's class, not by the class, so this holds also when pytest imported `tests/conftest.py` as two modules, `conftest` and `tests.conftest`, as when `python -m pytest` runs from `tests/` with a conftest there that imports from `tests.conftest`, or with `-p tests.conftest` and the repository root on `PYTHONPATH`: the fixture of one copy then raises its own class.
  - **Collection.** A collect report fails when a refusal was logged while pytest collected that node (a test module's module-level code, or a conftest that pytest imports then), instead of the first test after it. A refusal logged between two collect reports (in a `pytest_itemcollected` or `pytest_collectreport` hook for the node before, or a `pytest_collectstart` hook) is held instead, as below, named `during collection, before pytest collected <node>` for the node pytest collects next: failing that node would blame it and stop the run before any test.
  - **Before the first test.** Any refusal absorbed outside any test before the first test runs, other than one logged while pytest collected a node (see **Collection** above), is held and reported when the session finishes, and the tests still run: failing the session's collection would drop all of them, and failing the first test would blame it. It is named `at the session start, before collection` when it came from a conftest's import, `pytest_configure`, `pytest_sessionstart` or a `pytest_collection` hook (the guard reads the log once every plain `pytest_sessionstart` hook has run, and again right before the session's own collect report), `during collection, before pytest collected <node>` when it came from a hook between two collect reports (the guard reads the log right before each collect report), and `after collection, before the first test` when it came from `pytest_collection_modifyitems`, a collection-finish hook, a `pytest_runtestloop` wrapper or the last node's `pytest_collectreport` (it reads the log once every plain `pytest_collection_finish` hook has run, again once every `pytest_runtestloop` wrapper has started, and again when the first test's setup starts, which covers a plain `pytest_runtestloop` hook of a conftest: pytest calls that one before its own). When the test loop runs no test (`--co`, every test deselected, or a collection error that stops the run), what such a plain `pytest_runtestloop` hook logged is held when the loop ends instead, named `after collection, in a test loop that ran no test`.
  - **Between tests.** A refusal absorbed outside any test between two tests (in a `pytest_runtest_logreport` hook for the teardown report, a `pytest_runtest_logfinish` or `pytest_runtest_logstart` hook, or a `pytest_runtest_protocol` wrapper) is held the same way when the next test's setup starts, before its fixtures, and named `between two tests, before <test>`, instead of failing that test as made during it.
  - **Session finish.** After every plain `pytest_sessionfinish` hook, whenever it was registered (a `trylast` one of a conftest that pytest finds during collection included), the guard writes what it holds, and a refusal one of those hooks absorbed (`after the last test`), to the terminal above the summary, and changes the exit code to 1 (tests failed) when it was 0 (passed) or 5 (no tests collected). It does the same after pytest has written the summary and called every `pytest_terminal_summary` hook, and again after the plain `pytest_unconfigure` hooks (`after the session finished`, or `while pytest ran no test session` when no session started: a `pytest_configure` hook ended the run with `pytest.exit`, or `--markers` or `--help` ran), because pytest returns the session's exit code after that hook; a session pytest made but never started counts too. There it also changes the exit code back to 1 once it has reported a refusal in the session: a plain `pytest_sessionfinish` hook that calls `pytest.exit(returncode=0)` sets the code after every session-finish wrapper has finished, the guard's included. A code other than 0 or 5 stays. pytest catches no `SystemExit` around `pytest_sessionfinish` or `pytest_unconfigure`, so a hook there that calls `sys.exit(0)` would end the process with 0: once the guard has reported a refusal, its `tryfirst` session-finish wrapper and its `pytest_unconfigure` wrapper raise `SystemExit(1)` in place of a `SystemExit` with the code 0, 5 or `None` that leaves a hook they wrap (a `pytest_terminal_summary` hook included), as `pytest.exit` with 0 or 5 gets 1. Its `tryfirst` `pytest_cmdline_main` wrapper, around all of those hooks and the cleanups registered with `config.add_cleanup`, does the same for such an exit from a hook they do not wrap: a `tryfirst` session-finish or `pytest_unconfigure` wrapper that pytest registered after the guard (a conftest's), a cleanup, or an xdist controller's plain session-finish hook before the controller read its workers' files; it first reads those files and reports what was logged since the guard's other hooks (`after the session finished`). Any other `SystemExit` code stays, and so does the code of one that left the session finish when the only refusal comes in `pytest_unconfigure` after it, which pytest then runs after `pytest_cmdline_main`. A refusal absorbed later still, after the `yield` of a `tryfirst` `pytest_unconfigure` wrapper that pytest registered after the guard or in a cleanup registered with `config.add_cleanup`, shows only on `stderr` unless such a passing exit follows it (see **How you see it** below).
  - **xdist.** A worker cannot fail the run itself: its terminal output is discarded, and the controller does not use its exit code. At its own session finish, once every plain `pytest_sessionfinish` hook has run, it hands what it holds to the controller in `config.workeroutput`, which xdist then sends; the controller's `pytest_testnodedown` hook holds it under the worker's name (`in xdist worker gw0, ...`), once also for a worker that stopped on Ctrl-C, which xdist reports down twice, and the controller reports it when its session finishes and fails the run. A worker also appends each refusal, as soon as it holds it, to a file of its own, which the controller's `pytest_configure_node` hook names in the worker's `workerinput`: one held at the session start, during collection, between two tests or when its session finish starts (what it logged after its last test, in a `pytest_runtest_logfinish` hook, say), and one it finds after the hand-off. There is one file per worker, in a folder the controller makes for the session in the temporary folder with `tempfile.mkdtemp`, so a folder an earlier run left is never read, also with the same `--basetemp`; the controller makes none when Python finds no usable temporary folder or when Apothem would refuse a write into it. The folder is not in pytest's basetemp: without `--basetemp`, pytest's own session finish removes the basetemp under `tmp_path_retention_policy` `none`, or `failed` in a passing run, and under `all` removes its lock, after which another pytest run may remove it, all before the controller reads the files. Until the hand-off the file holds a copy of what the worker hands over; the controller reports the copy only when its `pytest_testnodedown` did not take that hand-off from the worker's output: when a hook of the controller ended its test loop with `pytest.exit`, when a session-finish wrapper that encloses the guard's (a conftest's, which pytest registers in the worker before xdist's own) raised or called `pytest.exit` before its `yield`, so xdist sent the output without the hand-off, or when the worker crashed or was stopped before its session finish handed anything over (a crash or `os._exit` in its session finish, before the hand-off, which xdist reports as a worker down without failing any test). What a worker finds after the hand-off (after another session-finish wrapper's `yield`, or in its `pytest_terminal_summary` or `pytest_unconfigure`) reaches the controller through the file alone. xdist's own `pytest_sessionfinish` in the controller tells each worker to exit and waits for its process to end, so the controller reads the files in its `pytest_unconfigure`, after every worker's `pytest_unconfigure`; when a plain `pytest_sessionfinish` hook that pytest calls before xdist's ends the run with `pytest.exit`, xdist's does not run, and the guard tells the workers to exit and waits for them itself before it reads the files. It names a refusal the worker wrote after the hand-off `in xdist worker gw0, after it handed its refusals to the controller, ...`, and one it wrote before the hand-off `in xdist worker gw0, ...`, fails the run and removes the folder. A worker creates its file only to write a refusal, so a file the controller cannot read, or one a worker left empty (it was stopped while it wrote, say), fails the run too, named for the worker. A worker whose session stopped before its session finish (`pytest.exit` in its `pytest_sessionstart`, say) handed nothing over: what it held is in its file already, and the controller names it `in xdist worker gw0, ...` without the hand-off. A worker still running Python code 5 seconds after it was told to exit is interrupted (on Windows, not one blocked in a sleep or another call), and one still running after 10 seconds is stopped: a refusal it had neither handed over nor written to its file by then, or before it ended itself (one absorbed in a plain `pytest_sessionfinish` hook that then calls `os._exit`, say), shows only on `stderr`, and so does every refusal a worker finds after the hand-off when it has no file or cannot write to it (see **How you see it** below). The controller runs no test itself: a refusal one of its own hooks absorbs while the workers run the tests (a reporting plugin's `pytest_runtest_logreport`, say) is held when its session finish starts and named `in the xdist controller, during the test run`.

The guard reads the real home once, when pytest imports `tests/conftest.py` and before any fixture changes it: `HOME`, `USERPROFILE`, `HOMEDRIVE` with `HOMEPATH`, `~` and, on Linux and macOS, the account's home. If a job points `HOME` at a temporary folder for the whole run, that folder is the real home. The real folders are the home's `.apothem`, `.config/apothem`, `.local/state/apothem`, `.codex`, `.claude` and `.config` folders, the folders that `CODEX_HOME`, `CLAUDE_CONFIG_DIR` and `XDG_CONFIG_HOME` named at that moment, and the `apothem` folder in `XDG_STATE_HOME` and in `LOCALAPPDATA`. Other folders below the real home are allowed, because the Windows temporary folder, where every test's temporary home lives, is one of them. `LOCALAPPDATA` itself is allowed for the same reason: every test inherits it, and the temporary folder is inside it. The failure message names each variable or path and the real location it reaches.

The isolation clears `CODEX_HOME` and `CLAUDE_CONFIG_DIR` for every test, so a developer's own setting does not stop the suite.

The guard does not catch:

- writes made outside a test's setup and call: while a conftest is imported, during collection, in a setup hook of a conftest's own that runs before the guard's or between it and the fixtures, in a session-scoped fixture of a plugin installed as a package, and in a fixture's teardown after it undoes the isolation;
- what a test body changes after it starts, including a fixture it requests with `request.getfixturevalue`, and the environment it builds for a child process; and a conftest's own plain `pytest_pyfunc_call` that calls the test itself;
- a fixture that a conftest defines under `_isolate_user_home`, `_isolate_install_ledger` or `_isolate_backup_root` (one suite test replaces `_isolate_backup_root` on purpose): the setup check sees the name and passes, and the call check sees only what that fixture left;
- a run with `--noconftest`, which loads neither the isolation nor the guard; a run with `-p no:apothem-real-home-guard`, which turns the guard off; and a conftest that imports single names from `tests/conftest.py` after an earlier import in the same process, in an earlier pytest session (a script that calls `pytest.main` twice) or outside pytest, which registers nothing;
- the folders it does not compare: harness folders in a home other than `.codex`, `.claude` and `.config` (such as `.cursor`, `.gemini` or `.agents`), whether a test passes one as its own install root or `CODEX_HOME` or `XDG_CONFIG_HOME` points at one; `XDG_DATA_HOME` and `XDG_CACHE_HOME`, which Apothem does not read but the tools a test launches do; `OPENCODE_CONFIG_DIR` and `OPENCODE_CONFIG`, which only add or take away an OpenCode note; and `APOTHEM_HOOK_STATE_DIR`, which counts only through the hook state folder it names;
- a script that imports Apothem outside pytest.

So:

- An agent or a probe must never run Apothem's installers or adapters against the real home. The guard and the refusal below cover pytest runs only; a script or an agent's probe that runs an install is covered by nothing but this rule.
- Never star-import a conftest.
- Put probes and experiments under `tests/`, so `tests/conftest.py` applies to them.
- Outside pytest, point `HOME` and `USERPROFILE` at a temporary folder before you import Apothem. Apothem sets its ledger and backup roots from the home when it is imported, so changing the home later does not move them.

`unit/test_real_home_guard.py` checks the guard. Its in-suite tests confirm that the import registered one guard object, that its setup hook runs before pytest's, that its call hooks run before pytest's own (`pytest_pyfunc_call` right before the function is called), that its report hook wraps the `skipping` plugin's, that its session hooks read the refusal log late enough (after the plain `pytest_sessionstart` and `pytest_collection_finish` hooks, before and after each collect report, right before the test loop, after every plain `pytest_sessionfinish` hook as the innermost wrapper, after the terminal summary and after the plain `pytest_unconfigure` hooks, and around them all as a `tryfirst` `pytest_cmdline_main` wrapper), that its two xdist hooks, `pytest_testnodedown` and `pytest_configure_node`, are optional, since only xdist defines them, that `tests/conftest.py` itself holds none of the guard's hooks (read from the guard object, not from a list; it defines none of them at module level and pytest registered it under none of them), so a star import registers none of them twice, that `__all__` carries the isolation, `_report_real_home_refusals` and the guard, and no other name that starts with `_`, and that the call check finds nothing for a suite test. It also runs a separate pytest session with the `pytester` plugin, in which each case writes a probe folder, points the home and `LOCALAPPDATA` at fresh folders that the probe session takes as the real ones, and runs two probe tests, one with no fixture and one with `tmp_path`. A probe conftest that star-imports `tests/conftest.py` runs both tests. A probe conftest that imports one plain name, or two isolation fixtures by name, is stopped at setup, with or without `--setup-only` and with or without `xfail`, and neither its own fixtures nor the test bodies write the file each writes first; so is a star-importing one with a session-scoped fixture named to run before `_isolate_session_home` (one that requests it runs), or with a fixture of its own named `_isolate_session_home`. A fixture that puts the real home, the ledger and backup roots, `CODEX_HOME`, `CLAUDE_CONFIG_DIR`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME` or `CLAUDE_PLUGIN_DATA` for the hook state, or, on Windows, `LOCALAPPDATA` for the hook state back on a real location gets both tests stopped before their bodies, and so do a conftest that deletes the guard's names, a later `pytest_runtest_call` or `pytest_pyfunc_call` wrapper that puts the real home back, an `xfail` mark (reported as failed), and a session that imported the file before it started. Two more cases protect the fake home with `also_protect_home` and absorb a refusal of a write into it, in the test body, in a fixture's teardown, in a fixture's teardown beside another fixture whose teardown fails (pytest raises the two together as an exception group) and in a module fixture's teardown: each test errors at teardown, with or without an `xfail` mark, and nothing lands in the fake home. A third gives the probe conftest the `_report_real_home_refusals` of a second copy of `tests/conftest.py`, loaded under another module name, so that fixture raises a class of its own while the guard stays the first copy's (the probe conftest checks both): the `xfail` tests still error, and the run exits 1. The other cases absorb such a refusal outside any test. One absorbed while a test module is imported fails that module's collection. One absorbed in a probe conftest's hook leaves the tests to run and pass and fails the run, named for where it happened: at the session start (also in a run that collects no test, whose exit code becomes 1, not 5), in a `pytest_collection` or `pytest_collection_modifyitems` hook, in a `pytest_collection_finish` hook while a path that does not exist stops the collection (named after collection, before the first test, with the exit code 4 kept), between two collect reports (in a `pytest_itemcollected` hook, and in the `pytest_collectreport` hook of the session's own report), in a `pytest_runtestloop` wrapper before it yields and in a plain `pytest_runtestloop` hook (also with `--co` and with every test deselected, named for a test loop that ran no test), between two tests (in a `pytest_runtest_logreport` hook for the first test's teardown report), in a `pytest_sessionfinish` hook (also one that then calls `pytest.exit(returncode=0)`, which still exits 1, while `pytest.exit(returncode=4)` keeps 4, and one that then calls `sys.exit(0)`, with and without `-n 2`, which exits 1, as `sys.exit(5)` there, a bare `sys.exit()` in a `pytest_terminal_summary` hook and `sys.exit(0)` in a `pytest_unconfigure` hook do, while `sys.exit(3)` keeps 3, and a `sys.exit(0)` after the guard's other hooks exits 1 too: in a `tryfirst` session-finish or `pytest_unconfigure` wrapper that pytest registered after the guard, in a cleanup registered with `config.add_cleanup` (where `sys.exit(3)` keeps 3), and in an xdist controller's plain session-finish hook before it read the files its workers wrote after the hand-off; those probe sessions run in a child process, because pytester's in-process run cannot report a `SystemExit` that leaves `pytest.main`) or after a session-finish wrapper yields, in `pytest_terminal_summary`, in `pytest_unconfigure` (with `-p no:xdist`), and with `-n 2` at the session start (named once by the controller and once by each worker) and in a worker's session finish, also in a `trylast` hook of a conftest that pytest finds during collection, which runs after the guard's, and in a worker after it handed its refusals to the controller: in its `pytest_terminal_summary`, in its `pytest_unconfigure` and after the `yield` of a `tryfirst` session-finish wrapper that pytest registered after the guard, which the worker writes to the file the controller reads and removes (a second run with the same `--basetemp` and no refusal passes; with the temporary folder inside a protected folder the controller makes no folder there, and the run passes); a worker that ends with `os._exit(0)` in its session finish before it handed anything over, after it absorbed a refusal between two tests and one after its last test (`--dist loadfile` runs both probe tests in it), still fails the run with both, named for that worker, and when the same worker hands them over each is reported once; a worker whose session-finish wrapper raises or calls `pytest.exit` before its `yield`, so that the output xdist sends holds no hand-off, fails the run with both too; a worker that stops on Ctrl-C has its refusal reported once, and one the controller absorbs in its own `pytest_runtest_logreport` hook is named for the test run, not after the last test. A session that absorbs nothing exits 0, with and without `-n 2`.

## Product-side refusal

Apothem also refuses these writes itself, so a test run that skips `tests/conftest.py` (a test file copied out of `tests/` and run with `-c`, `-o addopts=` or `--rootdir` elsewhere) still cannot reach the real home through Apothem.

- **What is refused.** `apothem.lib.home_write_guard` raises `RealHomeWriteError`, an `OSError`, for a write, a new folder, a copy destination, a removal, a rename or a lock file at or inside one of these folders of the account's home: `.apothem`, `.config/apothem`, and the tool folders that the harness registry names there (`.agents`, `.claude`, `.codebuddy`, `.codex`, `.config/opencode`, `.gemini`, `.hermes`, `.kiro`, `.openclaw`, `.qwen`, `.trae`); and each path outside those folders that an install or a stale sweep in the propagation manifest changes in the home, by itself, which today is one file an earlier release wrote, `.antigravity/profile.yaml` (the rest of `~/.antigravity` belongs to the Antigravity editor and stays writable). The set is derived from the registry and the manifest, a stale-sweep entry joined to the folder of its harness's first registry target, and `FALLBACK_ROOTS` holds the same list for when either cannot be loaded; `unit/test_home_write_guard.py` pins the two equal. Removing or moving a folder that holds one of them, such as the home or `~/.config`, is refused too. Nothing is changed before the error.
- **A project root at the home.** A project-scope install, update, uninstall or rollback whose project root is the account home itself (any spelling the write checks accept, a link to the home included) is refused with the same error before the pass writes anything, so the project's `AGENTS.md`, `GEMINI.md` and tool folders never land in the home. The check runs in the driver (`run_install`, `run_uninstall`, `rollback_install`) and in the project-scope uninstall adapters before their first step. A project folder inside the home stays allowed.
- **A data home right in the home.** A profile with the `user-home` workspace scope puts the data home at `~/<directory_name>`, and the name is the profile's to choose, so no protected folder covers it unless it is `.apothem`. While pytest runs, a data home whose folder is the account home (any spelling the project-root check accepts) is refused before it is created and before its stores are removed (`DataHome.ensure`, `_remove_data_home`), whatever its name. The data home itself is resolved as well, as the project-root check resolves a root, so a data home that is a link (a junction on Windows) to a folder right in the home is refused too, and so is one that leads to the home itself, directly or through a chain of links, whose stores would land right in the home. A data home written as the home itself sits right in no home and stays allowed. One that does not exist yet is judged by its folder alone. A data home in a project or a tool folder is left to the write checks. The check runs late in a pass: an install or update has written the project's files by then and undoes them, recording a rollback (a fresh install leaves the folders it created there, empty), and an uninstall has removed them by then and records itself unfinished.
- **When.** Only while pytest runs: while `PYTEST_CURRENT_TEST` is set and not empty, which pytest does, to the test's id and phase, during each test's setup, call and teardown, or while `PYTEST_VERSION` holds the version of the pytest that runs in the process, which pytest 8.2 and later sets, to its own version, for the whole session, so writes during collection, in module-level code and in session hooks are refused too. That version is the `__version__` of the running `_pytest` package, the string pytest puts in the variable, so a stale `pytest-*.dist-info` earlier on `sys.path`, or a pytest run from a source tree that names itself `unknown`, changes nothing. In a process that has not imported pytest (a child process a session started, say), the variable counts when it holds the version of the pytest installed for the Python that runs Apothem, read from the package metadata (`importlib.metadata.version("pytest")`) only while `PYTEST_VERSION` is set, never at import; the answer is kept for the process, and a failed lookup (no pytest installed), also kept, means the variable does not count there. A `PYTEST_VERSION` with any other value, such as an empty one or a version pin like `8.2` that a shell profile or a CI job exports, does not count, and neither does an empty `PYTEST_CURRENT_TEST`, which pytest never sets: an empty one comes from a shell, a container image or a CI template. A refusal outside any test names `PYTEST_VERSION` and the version it holds in place of a test. Reads, dry runs and previews still work, and outside pytest nothing is refused, unless the environment carries a `PYTEST_CURRENT_TEST` that is not empty, or a `PYTEST_VERSION` equal to the installed pytest's version. One status check is a write: when it finds an uninstall that stopped partway, it records the finished uninstall in the ledger. Against the real home that write is refused quietly and reported.
- **What a check costs.** Measured on one Windows host (Python 3.14, pytest 9.1, a local disk; the mean or median of 200 checks, 2000 when the guard is off; another test run was loading the host, so expect about 30 percent either way). Outside pytest a check is two environment lookups, about 3 µs, the data home check included. A `PYTEST_VERSION` that does not count costs about 3 µs a check. In a process that has not imported pytest the first such check takes about 0.15 to 0.2 s, because it imports `importlib.metadata` and reads pytest's version, or about 0.14 s where the Python running Apothem has no pytest installed; the answer, a failed lookup included, is kept, so later checks cost about 3 µs there too. In a process that has imported pytest no metadata is read. While pytest runs, with the home folders settled: a path that names a protected folder as written, about 0.15 to 0.3 ms; a local path outside the protected folders, about 0.55 to 0.95 ms (an existing file about 0.55 to 0.65 ms, a new file several folders deep about 0.8 to 0.95 ms); the project-root check, about 1 ms; the data home check, about 1.2 to 1.5 ms. The first check after a home or its `.config` changed, and every check while one changed less than 0.1 s ago, takes about 11 to 15 ms, because every protected folder is resolved again. A share path outside the protected folders: a loopback admin share (`\\localhost\C$\...`) about 2.3 to 2.6 ms, since resolving it goes through the share; a share reached by one of the machine's own addresses, placed by file identity, about 0.1 to 0.12 s for the first check and 10 to 14 ms for each later one. A share whose host cannot be reached waits on the network (about 21 s for a first check, measured once, and close to nothing for a repeat).
- **Which home.** The account's home as the operating system records it (the profile folder on Windows, the `passwd` entry elsewhere), never `HOME` or `USERPROFILE`, which name a temporary folder during a test. The system functions that lookup calls are bound when the guard is imported, so a test that later fakes `pwd.getpwuid`, `ctypes` or `winreg` does not change the home the guard protects. The temporary folder, the checkout and the rest of the home stay writable.
- **Which spellings.** A path is compared as written and as resolved through links, afresh on every check, so a link or junction into a protected folder counts, and so does a folder swapped for a link during a test, before or after the first check. On Windows letter case and short (8.3) names do not matter, also in the last part of the path, and a `\\?\`, `\\.\` or `\??\` prefix (with either slash), a loopback admin share (`\\localhost\C$`, `\\127.0.0.1\C$`, `\\--1.ipv6-literal.net\C$`, the machine's own name) and an alternate data stream (`.apothem:name`) read as the plain path. A device path behind any of those prefixes (`GLOBALROOT\Device\HarddiskVolume2`, `Volume{GUID}`, `GLOBALROOT\GLOBAL??\C:`) is resolved to the plain path it names. Any other share path, such as one reached by one of the machine's own addresses or the share a mapped drive resolves to, is matched by file identity with the protected folders and the folders above them, folder by folder up to the share, so a path below a protected folder counts too. Only the string rules make no network contact. Resolving a share path (a path on a mapped drive included) asks the share's host, and so does matching it by identity, which reads each share folder at most once in a check and stops at the first error that says the host or the share cannot be reached. On macOS letter case and Unicode normalization (`é` as one character or as two) are ignored too, and `/System/Volumes/Data/<path>`, the data volume that `/Users` is firmlinked from, reads as `/<path>`; Linux compares names as they are.
- **Where it is checked.** The atomic write, append and lock helpers in `apothem.lib.atomic_io`; the install driver's target check `_validate_target_path` (a caller that only previews passes `mutating=False`); backup copies and backup pruning; the stale sweep, which checks every stale path before it removes the first; a rollback, which checks every path its install record names, the data stores it would remove and the user-level folders in the home it would tidy last (`~/.agents/skills`, `~/.agents`) before the first change; the install root; the OpenClaw uninstall, which checks `openclaw.json` and every workspace rules file before it takes Apothem's block out of the first (a workspace the operator moved out of `~/.openclaw` included); the backup root and the ledger, which a rollback and an uninstall check before their first change, because a refusal at a backup copy or at the record would leave what they had changed unrecorded; the data home and the store folders; clean-slate; workspace migration; and the profile write.
- **How you see it.** The error names the path, the protected folder, the variable that turned the refusal on with its value, and the fix. In a test it says `PYTEST_CURRENT_TEST is set: <test id>`. Outside any test it says `PYTEST_VERSION holds the version of the pytest imported in this process, <version>, outside any test`, which does not claim that a pytest session runs, since a process can import pytest without running one; in a process that has not imported pytest it says `PYTEST_VERSION holds the installed pytest's version, <version>, though no pytest runs in this process`. A refusal checked just before pytest takes the test id out of the environment at the end of a teardown names `PYTEST_VERSION`, as outside any test, or, when `PYTEST_VERSION` does not count either, the pytest session alone. Each refusal is also written to `stderr` with the same text, once per protected folder in each test (outside any test, once per protected folder until a test logs a refusal and once more after each test that does; the guard sees a test only through a refusal made in it, so a test that refuses nothing does not count), and logged in the process, because a few callers absorb the error (a best-effort ledger line, for one). The autouse fixture `_report_real_home_refusals` in `tests/conftest.py` fails a test after which a refusal was logged, also when the test is marked `xfail` (it fails with the guard's own failure type, which the report hook keeps failed), and the guard's report hook fails the teardown of a test when a fixture torn down after that fixture logged one. A refusal absorbed outside any test while pytest collects a node (a test module's module-level code, or a conftest that pytest imports then) fails that node's collection, not the next test. Any other refusal absorbed outside any test is written to the terminal when the session finishes, named for where it happened (`at the session start, before collection`, `during collection, before pytest collected <node>`, `after collection, before the first test`, `after collection, in a test loop that ran no test`, `between two tests, before <test>`, `in the xdist controller, during the test run`, `after the last test`, `after the session finished` or `while pytest ran no test session`), and changes the exit code to 1 when it was 0 or 5, also when a hook then ends the run with `pytest.exit(returncode=0)` or `sys.exit(0)` after the guard reported the refusal (a `pytest_sessionfinish` or `pytest_unconfigure` hook or wrapper, or a cleanup), or with `sys.exit(0)` before the guard reported it, except when the exit leaves the session finish and the only refusal comes in `pytest_unconfigure` after it; the tests still run. pytest's last line counts tests only, so it can still read `2 passed` in green: the refusal written in red above the summary, and the exit code, say that the run failed. That covers a conftest's import, `pytest_configure`, `pytest_sessionstart`, `pytest_collection`, `pytest_collectstart`, `pytest_itemcollected`, `pytest_collectreport` and `pytest_collection_modifyitems` hooks, `pytest_runtestloop` hooks and wrappers, the `pytest_runtest_logstart`, `pytest_runtest_logreport` and `pytest_runtest_logfinish` hooks and `pytest_runtest_protocol` wrappers between two tests, `pytest_sessionfinish` hooks and wrappers, `pytest_terminal_summary` and `pytest_unconfigure`. Under xdist a worker sends what it found up to the end of its own plain `pytest_sessionfinish` hooks to the controller, which reports it as `in xdist worker gw0, ...` and fails the run; what the worker finds after that hand-off (after another session-finish wrapper's `yield`, or in its `pytest_terminal_summary` or `pytest_unconfigure`) it writes to a file that the controller reads once the worker has ended, and the controller reports it as `in xdist worker gw0, after it handed its refusals to the controller, ...` and fails the run too. The worker writes each refusal to that file as soon as it holds it, so one it held before it crashed or was stopped short of the hand-off, or before a session-finish wrapper stopped its session finish short of it, still reaches the controller, named `in xdist worker gw0, ...`. Three cases still show only on `stderr` and leave the exit code as it is: one absorbed after the `yield` of a `tryfirst` `pytest_unconfigure` wrapper that pytest registered after the guard (a conftest's, say), which finishes after the guard's own; one absorbed after every `pytest_unconfigure` hook, in a cleanup registered with `config.add_cleanup` (each unless a passing `sys.exit` then ends the run); and one an xdist worker absorbs but neither hands over nor writes to the controller's file, because the worker ended or was stopped first (one absorbed in a plain `pytest_sessionfinish` hook that then calls `os._exit` or crashes the worker, say; when the controller's session finishes, xdist tells each worker to exit; one still running Python code 5 seconds later is interrupted, though on Windows not one blocked in a sleep or another call, and any worker still running after 10 seconds is stopped) or because that file could not be made or written. The first two, in any process, and a refusal a worker had neither handed over nor written when it ended or was stopped show only as the guard's own `stderr` line; a worker that has no file, or cannot write to it, writes the refusal to `stderr` with a note that says why (the controller named no file, or writing the file failed, with the system's reason) and that the run does not fail on it. The guard's `tryfirst` wrappers finish after every other wrapper except a `tryfirst` one registered after the guard, so a refusal absorbed after such a `pytest_sessionfinish` wrapper's `yield` is caught only at `pytest_unconfigure` and named `after the session finished`, not `after the last test`. Every other caller, the CLI included, raises the error as it is instead of turning it into an error row. An uninstall that is refused records no unfinished uninstall in the ledger, unless it had already changed files outside the protected folders, in a step before the shared removal too (the first step of a native-config uninstall, say): then it records one, so the backups of those files stay referenced. A stale sweep, a rollback and an OpenClaw uninstall are refused before they change anything. The log is kept per process, so a refusal absorbed in a child process reaches the test only as the child's `stderr` line.
- **The test seam.** `home_write_guard.also_protect_home(path)` makes the guard treat a test folder as one more account home, and `clear_extra_homes()` forgets those folders. It only adds a home: it cannot replace or remove the real one, and no environment variable, setting or flag reaches it.
- **A real install on purpose.** A test that must run a real install starts Apothem without `PYTEST_CURRENT_TEST` and `PYTEST_VERSION` in the child's environment. No test in the suite or in CI does this today.

Known gaps:

- folders that `CODEX_HOME`, `CLAUDE_CONFIG_DIR` or `XDG_CONFIG_HOME` move away from their default names, outside the home or inside it: a copied test that inherits `XDG_CONFIG_HOME=~/xdg` writes OpenCode's folder `~/xdg/opencode` with no refusal;
- the hook state folder (`~/.local/state/apothem`, `%LOCALAPPDATA%\apothem`, `CLAUDE_PLUGIN_DATA`);
- programs that are not Python (`pwsh`, the shell installers, `git`), and the developer tools (`plugin_tree`, the audit writers);
- a checkout that itself sits inside a protected folder (under `~/.claude`, say): its Apothem writes are refused during tests;
- on Linux and macOS, a second path to a protected folder that is not a link: no file identity is compared there, so a bind mount of the home (a container that mounts it at `/workspace/home`, say) and a case-insensitive Linux mount (an ext4 folder with `casefold` on, a CIFS share), where a name in other letter case is the same folder, are judged by their spelling;
- on Linux and macOS, a path that climbs out of a link with `..` (`<link>/../.claude/x`): it is judged by its spelling, not by where the system would put it;
- a hard link outside the home to a file in a protected folder: an append or a lock file opened through it changes that file (an atomic write replaces the link and is not affected), and no system call lists a file's other names on Linux and macOS;
- a link changed during a test run above a home (a linked `C:\Users`, say), or a protected folder's own link retargeted in place: the protected folders are resolved again only when a home or its `.config` changes, or, when one of those is a link, the folder it leads to;
- a share path whose host cannot be reached, or that reports no file numbers: it is judged by its spelling;
- the network contact of a share path's check: resolving the path and matching it by identity wait on the share's host, so a host that is slow to answer or to fail slows every check of a path on it;
- a refusal absorbed in a child process (a test that runs `python -m apothem` in a subprocess with `PYTEST_CURRENT_TEST`, or the installed pytest's version in `PYTEST_VERSION`, in its environment): the child refuses and writes the refusal to its `stderr`, but the refusal log is per process, so the test is not failed for it unless it reads that `stderr` or the exit code;
- a child process started outside any test (by a conftest, a session hook or collection) inherits `PYTEST_VERSION` but not `PYTEST_CURRENT_TEST`, and it compares the variable with the package metadata of the pytest installed for its Python: when that names a different version (another pytest installed, a stale `pytest-*.dist-info` first on `sys.path`, a pytest run from a source tree), or there is none, the variable does not count there and the child is not guarded;
- the time between the check and the write: the check resolves the path, then the write opens it by path, so a folder swapped for a link into a protected folder in between (by another thread or process) is followed;
- under `sudo -E pytest`, the home of the account the process runs as (`root`) is protected, not the home of the developer who ran `sudo`;
- removing an empty folder whose path holds a protected folder (an empty `~/.config` after an uninstall): it holds nothing to protect, so it is allowed;
- a system with no record of the account's home (a container user with no `passwd` entry): then only the homes added with `also_protect_home` are protected;
- `pytest --fixtures`, `--fixtures-per-test`, `--markers` and `--help`: the guard prints a refusal it holds, but pytest returns 0 in these modes whatever the session's exit status, so the command still exits 0. `--markers` and `--help` start no session, so a refusal from a conftest's import or a `pytest_configure` hook is named `while pytest ran no test session`.

`unit/test_home_write_guard.py` checks the decision against a fake home (when `PYTEST_VERSION` counts, in a pytest process by the running pytest's version whatever its package metadata says and, in a child Python that has not imported pytest, by the installed one's, how often that is looked up and that importing the guard looks nothing up, that an empty `PYTEST_CURRENT_TEST` does not count, a data home that is a link into the home or to the home itself, the variable each refusal names, also in a Python that imports pytest without running it, and that no check does any path work outside pytest), `unit/test_home_write_guard_spellings.py` checks the spellings of one folder (a folder swapped for a link before or after the first check, or inside a linked `.config`, the Windows prefixes and the device paths behind each of them, short names, admin shares, shares reached by the machine's own addresses or through a mapped drive, a share path below a protected folder, how often a share's host is asked, data streams, the macOS data volume, letter case and Unicode normalization), `unit/test_home_write_guard_driver.py` checks the install driver, the stores and the profile write, `unit/test_home_write_guard_passes.py` runs a whole CLI uninstall for every harness that writes into a protected folder, an Antigravity uninstall whose stale sweep would remove `~/.antigravity/profile.yaml` and the plugin folder in `~/.gemini/antigravity-cli` (refused before either moves), an OpenClaw uninstall with a workspace outside `~/.openclaw` (refused before its rules file changes) and one with a rules file in a protected folder, an install and an uninstall with a data home named `apothem-data` right in the home, an uninstall refused after it removed project files, a native-config uninstall stopped after its first step removed a file elsewhere, by a refusal, an ordinary error or an interrupt (recorded unfinished with that backup; the ordinary error is raised as a stopped uninstall that carries that removal, and `unit/test_wrapper_factory_uninstall.py` checks that the CLI then exits 2 and says the uninstall stopped after removing files), a stale sweep whose second path is protected, a Cursor rollback with the project outside the home and a rollback whose data stores sit right in the home (both refused before any change), and an install, update, uninstall and rollback with the home as project root, with the ledger outside the home, and `unit/test_home_write_guard_incidents.py` rebuilds three ways of running a copied test file without `tests/conftest.py` in child pytest sessions whose home is a fake one, plus a session whose conftest, session-start hook and module-level code each try a write outside any test, and a control run without the guard's fake home that shows the probe does reach the writers. Each of those sessions has its own temporary folder and `--confcutdir` on its own folder, so it never lists the shared temporary folder while other processes change it.

## Conformity corpus layout

The `conformity/` subtree holds two kinds of module. Per-matcher tests live in a
directory named for the matcher; top-level `test_*.py` files hold cross-matcher
infrastructure and scope-contract tests.

**Directory-name resolution.** The matcher-coverage loop
(`conformity/matcher-coverage/test_matcher_coverage_loop.py`) maps each matcher's
underscore module name to kebab-case and resolves its corpus directory by trying,
in order: the bare kebab form (`bare-except-grep`), the `<kebab>-grep` form, and —
for a name already ending in `-grep` — the suffix-stripped form. Most directories
carry the module's full kebab name; a few historical directories drop the `-grep`
suffix or diverge (`file-header`, `link-check`, `copilot-instructions-presence`),
which is why the resolver probes more than one candidate. Prefer the exact
`<module-kebab>` directory name for any new matcher so the mapping stays one-to-one.

**Fixture forms.** A matcher directory satisfies coverage with any one of three
equivalent fixture forms:

- a `test_*.py` scenario/contract test;
- a `pass.*` + `fail.*` content-file pair (a single conformant / non-conformant file each); or
- a `pass` + `fail` corpus-directory pair (a whole conformant / non-conformant tree, used by the standalone root-walking greps).

## Working in this folder

Add or modify a test in the subtree that mirrors the changed source, then run
`python -m pytest`. When a behavioral or public-surface change lands in the
package, the covering test ships in the **same change-set**. Conformity matcher
fixtures are also swept by the conformity gate itself:

```bash
python -m pytest
python -m apothem.conformity.gate --all .
```
