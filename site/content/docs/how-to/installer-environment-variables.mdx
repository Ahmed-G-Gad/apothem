Goal: drive `install.sh` / `install.ps1` without editing the script by setting
environment variables before you run it.

## Prerequisites

- A POSIX shell (`bash`) or PowerShell 5.1+. The PowerShell examples below run
  `pwsh` (PowerShell 7+). Under Windows PowerShell 5.1, run
  `powershell -NoProfile -ExecutionPolicy Bypass -File install.ps1` instead.
- The variables are read once at the top of the installer, so set them in the
  same command (or export them first), then run the installer.

## The installer variables

| Variable | Controls | Default |
| --- | --- | --- |
| `APOTHEM_HOME` | Install destination for the source tree | `$HOME/.apothem` |
| `APOTHEM_REPO` | Git remote to clone; a value that starts with `-` is refused | `https://github.com/ahmed-g-gad/apothem` |
| `APOTHEM_REF` | Git ref to check out; unset resolves the latest signed `vMAJOR.MINOR.PATCH` tag, a tag value pins it, `main` selects the moving branch. A non-tag ref such as `main` aborts unless `APOTHEM_ALLOW_UNVERIFIED=1`. | unset (latest signed tag) |
| `APOTHEM_ALLOW_UNVERIFIED` | Downgrade a failed tag check on the clone path from a fatal abort to a warning when set to `1`, and allow `APOTHEM_VERIFY=checksum`; the `release` path never downgrades, and no setting skips the check that the signed tag is the one named for the release, but since it lets an unsigned tag, or one signed by another key, through, that check protects only tags that carry the maintainer key's signature | `0` (verify, fail-closed) |
| `APOTHEM_VERIFY` | `auto` uses `release` when `cosign` is on `PATH` and `APOTHEM_HOME` is not a git clone, and `signature` otherwise; `release` installs the platform archive after the tag carries the maintainer key's signature, cosign confirms the release workflow signed `SHA256SUMS` in a run on the tag's commit, and the archive's SHA-256 matches it; `signature` checks the release tag's GPG signature against the pinned maintainer key; `checksum` installs the archive after the SHA-256 check alone and needs `APOTHEM_ALLOW_UNVERIFIED=1`. Checksum mode does not verify the release. SHA256SUMS comes from the same release as the archive, so a match only shows the download isn't damaged; anyone who can change the release's files can change both. | `auto` |
| `APOTHEM_RELEASE_BASE` | Download base for the `release` and `checksum` modes | `<APOTHEM_REPO>/releases/download` |
| `APOTHEM_SOURCE` | Explicit local source tree to use instead of cloning | unset (clone) |
| `APOTHEM_HARNESS` | User-scope harness to install (`antigravity`, `claude-code`, `codex`, `hermes`, `open-claw`, `opencode`, `qwen-code`). The installer does not pass `--project`, so a project-scope harness fails with `project.required`; install those afterward with `apothem install --harness NAME --project PATH`. | `claude-code` |
| `APOTHEM_PROFILE` | Path to the shared profile YAML | `$HOME/.config/apothem/profile.yaml` |
| `APOTHEM_SKIP_VERIFY` | Skip the post-install verify step when set to `1` | `0` (verify runs) |
| `APOTHEM_AUTO_INSTALL_DEPS` | Install the missing `click` / `rich` prerequisites automatically, without prompting, when set to `1` | `0` (prompt, or decline in a non-interactive pipe) |
| `APOTHEM_BIN_DIR` | Directory for the placed `apothem` command shim | `$HOME/.local/bin` (POSIX); `%LOCALAPPDATA%\Microsoft\WindowsApps` (Windows) |
| `NO_COLOR` | Turn off coloured output when set to any value ([no-color.org](https://no-color.org/)); colour is also off whenever the output is not a terminal (a pipe, a file, a CI log) | unset (colour on an interactive terminal only) |

`APOTHEM_SOURCE` takes precedence over a clone: when set to a checkout that
contains `src/apothem`, the installer uses it directly, never touches
`APOTHEM_REPO` / `APOTHEM_REF`, and skips tag resolution and signature
verification (nothing is fetched to verify).

`APOTHEM_SOURCE` and running a checkout's own installer script by its path (from
any folder) are the only two ways to use a local tree. A piped one-liner (`curl
... | sh`, `irm ... | iex`) never uses one: it ignores the current folder and
its parent folders, and fetches and verifies the release. The installers,
updaters and uninstallers, the `apothem` shims, the npm launcher, the hooks and
the conformity gate's validator processes keep the current folder off Python's
module search path. A `python -m apothem` command you type yourself does not:
`-m` reads modules from the current folder first.

Empty and relative entries in your own `PYTHONPATH` are not passed on to the
engine by any launcher (the installers, updaters, uninstallers, the POSIX and
Windows `apothem` shims, and the npm launcher). A kept entry must be a full
path: on Windows a drive path such as `C:\lib` or a network path, elsewhere a
path that starts with `/`. A rooted `\lib` or a drive-relative `C:lib` is
dropped. The sh scripts ask the Python they run which form it reads, and the
`apothem` shim they write keeps that form. A Windows Python (the usual one
under Git Bash) gets the engine paths in Windows form, joined with `;`, and
keeps only the drive and network paths of your `PYTHONPATH`. A POSIX Python,
including Cygwin's and MSYS2's own `python3`, gets POSIX paths joined with `:`
and keeps only entries that start with `/`. The installers' `git` commands
that do not work on a clone do not read a repository in the current folder.

Those `git` commands run from an empty temporary folder that the installer
creates for the run, so a relative path in a git environment variable
(`GIT_SSH`, `GIT_ASKPASS` and similar) no longer points where it did
before. Use an absolute path in those variables. A relative `APOTHEM_REPO` that
names a folder or a file (such as a git bundle) is still resolved from the
folder you started in.

The installers ignore the git environment variables that redirect git
(`GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE` and similar), and they stop
when `APOTHEM_REPO` starts with `-`, so a value cannot be read as a git
option.

The installers and updaters also clear `GIT_CONFIG`, `GIT_CONFIG_GLOBAL` and
`GIT_CONFIG_SYSTEM`, so a value inherited from your environment cannot point
git at another config file. If you set one of them, the installer ignores it;
the PowerShell scripts put it back when the run ends, so an `irm ... | iex`
run leaves your session as it was. `GIT_CONFIG_NOSYSTEM` stays as you set it:
it only stops git reading the system config. git still reads your own global
config (`~/.gitconfig` or `$XDG_CONFIG_HOME/git/config`) and the system config
from the places it always looks, and `git`, `gpg` and `cosign` are the
programs your `PATH` finds. The installers trust them as found, and so they
trust that config.

Each run of the install, update and uninstall scripts holds a lock,
`<APOTHEM_HOME>.lock`, for the whole run; a second run on the same
`APOTHEM_HOME` stops. When `APOTHEM_HOME` is a symbolic link (or, on Windows,
a junction), the POSIX and the PowerShell scripts both take the lock beside
the folder it leads to. A forced kill or a power loss can leave folders
beside `APOTHEM_HOME`, and the next fetched install names them and stops
before changing anything; see
[Troubleshooting](/docs/install/troubleshooting).

When `APOTHEM_HOME` points at an existing directory, what happens depends on
what it holds.

- A git clone is fetched in `auto` or `signature` mode; the new tag is checked
  first, and only then is the clone checked out. A failed check leaves the clone
  unchanged, and changes to tracked files stop the update, with a message to
  commit or stash them, instead of being lost. With a non-release ref such as
  `main`, the clone follows origin's copy of that branch. A `.git` file (a
  linked worktree) counts as a clone. `release` and `checksum` refuse a clone
  without `--yes`, and with `--yes` they still refuse while the clone holds
  local work (changes, stashes, unpushed commits, or untracked files in its
  source tree), also in a dry run. When `--yes` does replace a clone, the
  clone's own tree moves into a new folder,
  `<APOTHEM_HOME>.before-apothem-<time>`, under its own name, rather than being
  deleted. Before the fetch, an update in place stops when files are marked
  assume-unchanged or skip-worktree, when the clone's work tree is not
  `APOTHEM_HOME`, when the clone holds a submodule, when `.git/info/attributes`
  sets a `filter=`, or when the clone's `.git/config` or `.git/config.worktree`
  holds a setting other than the ones `git clone` and `git init` write there,
  branch settings, `user.name`, `user.email`, `maintenance.auto`,
  `maintenance.strategy`, `pull.rebase` and `pull.ff`
  ([Troubleshooting](/docs/install/troubleshooting#the-installer-stops-the-existing-clone-is-set-up-in-a-way-the-update-would-trust)
  lists them); the clone's git hooks never run during the update. Only a clone
  of an Apothem source counts: a clone of anything else is handled as a folder
  that holds no Apothem install.
- An earlier release-archive install is updated by a re-run in `auto` mode
  with cosign (or `release`, or `checksum`).
- A folder that holds no Apothem install is refused: move it aside, point
  `APOTHEM_HOME` elsewhere, or pass `--yes` (`-Yes` on Windows). With `--yes`,
  the installer moves the whole folder, unchanged, into a new folder,
  `<APOTHEM_HOME>.before-apothem-<time>`, and installs fresh.
- A stale empty directory, or one that holds only the engine's own data
  (`backups`, `state`, `plans`, `memory`, `contexts`, `learning`,
  `providers`), is updated without the flag, and that data is kept.
- A symbolic link (on Windows, a symbolic link or a junction) is refused
  whenever the install would replace it: point `APOTHEM_HOME` at the folder
  the link leads to. An existing git clone behind a link is updated in place.
- On Linux and macOS, a file or folder to carry over whose name has a space or
  another special character stops the install: move it out of `APOTHEM_HOME`
  first.

For an Apothem install that is replaced, the new source is checked in a staging
folder beside `APOTHEM_HOME` and swapped in only after every check passes.
Everything in the old install that is not part of its source tree, including the
engine's backups, install ledgers, plans and memory, is kept. If a step fails or
the run is stopped by Ctrl+C or a termination signal, the earlier install is put
back unchanged; a forced kill or a power loss can leave folders beside
`APOTHEM_HOME` that the next fetched install reports. `--dry-run` (`-DryRun` on
Windows) does its checks in a temporary folder and leaves `APOTHEM_HOME`
unchanged. It makes the same checks as a real run, except that it does not
fetch into an existing clone, and so does not check it for changes to tracked
files, which a real update does after its fetch.

## Trust model

With no `APOTHEM_REF` set, the installer resolves the latest release and
checks it before materializing any configuration. It always verifies the
release tag with `git verify-tag` and requires the signature to come from the
maintainer key published in SECURITY.md; an unsigned or tampered tag, or one
signed by any other key, aborts the install, and so does a signed tag object
that is not the one named for the release (a signed tag for another release,
re-pointed at this name). With `cosign` on `PATH`, it then
installs the release archive once cosign confirms the release workflow signed
`SHA256SUMS` and, through its `--certificate-github-workflow-sha` check, that
the certificate it verified was issued to a run on the tag's commit, and the
archive's SHA-256 matches it. That path needs `gpg` and cosign. For an
existing git clone, the installer fetches and checks the tag before it checks
the clone out, so a failed check leaves the clone as it was. A signed tag
whose maintainer public key is missing from the local keyring aborts with
key-import guidance instead - import the key and check its fingerprint
against the value published in
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md).
Pin a known
release with `APOTHEM_REF=<tag>`, taking the tag from the
[releases page](https://github.com/ahmed-g-gad/apothem/releases); a pinned tag
is verified the same way. Select the moving branch with `APOTHEM_REF=main` plus
`APOTHEM_ALLOW_UNVERIFIED=1`; that install is unverified, and `main` alone
aborts because a branch is not a signed tag. Set `APOTHEM_ALLOW_UNVERIFIED=1` to proceed past a failed tag check with a
warning (air-gapped, local, or pre-signed-release use). It applies to the
clone path only, never to the cosign path, so on a host with cosign set
`APOTHEM_VERIFY=signature` with it.

```bash title="Pinned, verified install"
APOTHEM_REF=vMAJOR.MINOR.PATCH bash install.sh
```

```bash title="Require the tag check and the cosign check"
APOTHEM_VERIFY=release bash install.sh
```

Checksum mode does not verify the release. SHA256SUMS comes from the same
release as the archive, so a match only shows the download isn't damaged;
anyone who can change the release's files can change both. The installer runs
it only with `APOTHEM_ALLOW_UNVERIFIED=1` set as well.

```bash title="Check the archive digest alone (no cosign, no gpg; does not verify the release)"
APOTHEM_VERIFY=checksum APOTHEM_ALLOW_UNVERIFIED=1 bash install.sh
```

```bash title="Proceed past a failed tag check (interim / air-gapped)"
APOTHEM_VERIFY=signature APOTHEM_ALLOW_UNVERIFIED=1 bash install.sh
```

## Steps (POSIX bash)

1. Install a non-default user-scope harness:

   ```bash
   APOTHEM_HARNESS=codex bash install.sh
   ```

2. Pin the install destination and select the moving `main` branch. A branch is
   not a signed tag, so the installer also needs `APOTHEM_ALLOW_UNVERIFIED=1`:

   ```bash
   APOTHEM_REF=main APOTHEM_ALLOW_UNVERIFIED=1 APOTHEM_HOME=/opt/apothem bash install.sh
   ```

3. Use a local checkout and a custom profile, skipping verify:

   ```bash
   APOTHEM_SOURCE=/work/apothem \
   APOTHEM_PROFILE=/work/profile.yaml \
   APOTHEM_SKIP_VERIFY=1 \
   bash install.sh
   ```

## Steps (PowerShell)

Set each variable on `$env:` before running the installer:

```powershell
$env:APOTHEM_HARNESS = 'codex'
pwsh -NoProfile -File install.ps1
```

```powershell
$env:APOTHEM_ALLOW_UNVERIFIED = '1'
$env:APOTHEM_REF = 'main'
$env:APOTHEM_HOME = 'C:\opt\apothem'
pwsh -NoProfile -File install.ps1
```

```powershell
$env:APOTHEM_SOURCE = 'C:\work\apothem'
$env:APOTHEM_PROFILE = 'C:\work\profile.yaml'
$env:APOTHEM_SKIP_VERIFY = '1'
pwsh -NoProfile -File install.ps1
```

## Verify

The installer prints `✓ Harness <name> installed`, then (unless
`APOTHEM_SKIP_VERIFY=1`) `✓ verify passed`. Confirm independently:

```bash
apothem verify --harness codex
```

For a project-scope harness such as Cursor, run the install and the verify
yourself after the installer, with `--project`:

```bash
apothem install --harness cursor --project /path/to/project
apothem verify --harness cursor --project /path/to/project
```

When the profile did not yet exist, the installer creates one from the example
and carries on to install and verify in the same run. The example's identity
fields are placeholders, so the install prints a note; edit `$APOTHEM_PROFILE`,
then run `apothem update --harness <name>` to apply your identity. A `--dry-run`
with no profile previews with the example in place and writes nothing.
