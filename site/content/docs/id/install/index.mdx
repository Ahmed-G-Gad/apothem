Apothem terpasang dalam waktu kurang dari dua menit dan bekerja berdampingan
dengan konfigurasi harness Anda yang sudah ada. Setiap jalur menjalankan mesin
mandiri yang sama — pohon sumber membawa dependensinya yang di-vendor dan
berjalan dari checkout pada Python sistem 3.10 atau yang lebih baru (lihat
[runtime mandiri](/docs/architecture/self-contained-runtime)).

**Dua prasyarat berlaku untuk setiap jalur:** **Python 3.10 atau lebih baru**
milik sistem pada `PATH`, dengan paket `click` dan `rich` yang dapat diimpor di
bawahnya. Shim npm (kanal 2), ekstensi keluarga VS Code (kanal 4), dan bootstrap
baris perintah (kanal 5–7) juga membutuhkan **Node.js 18 atau lebih baru** untuk
menjalankan `npx`. Python 3.10 serta Node.js 18 dan 20 telah melewati akhir masa
pakai (end of life) di upstream; ketiganya tetap didukung dan diuji, tetapi
versi yang lebih baru lebih disarankan (lihat
[Prasyarat sekilas](#prasyarat-sekilas)). Bagian masing-masing kanal di bawah
ini mengulang prasyarat persisnya, satu perintah siap-salin, dan langkah
verifikasi.

## Pilih kanal

Delapan kanal instalasi tersedia. Pilih berdasarkan cara Anda sudah bekerja.

| # | Kanal | Menghadirkan | Prasyarat |

| 2 | [Shim npm (`npx`)](#2-shim-npm-npx) | Harness lengkap, alat apa pun | Node 18+ · Python 3.10+ |
| 3 | [Pemasang satu langkah](#3-pemasang-satu-langkah) | Harness lengkap + perintah `apothem` | Python 3.10+ (`git` untuk instalasi jaringan) |
| 4 | [Ekstensi keluarga VS Code](#4-ekstensi-keluarga-vs-code) | Harness lengkap dari editor | VS Code · Node 18+ · Python 3.10+ |
| 5 | [Bootstrap baris perintah (host ekstensi)](#5-bootstrap-baris-perintah-host-ekstensi) | Bootstrap yang menjalankan mesin | Alat host-nya · Node 18+ · Python 3.10+ |
| 6 | [Bootstrap baris perintah (host `qwen-code`)](#6-bootstrap-baris-perintah-host-qwen-code) | Bootstrap yang menjalankan mesin | Alat host-nya · Node 18+ · Python 3.10+ |

<Callout title="Kanal mana yang menghadirkan harness lengkap">
  Shim npm (2), pemasang satu langkah (3), dan mesin langsung (8)
  mematerialisasikan seluruh unit tersinkron untuk harness apa pun dengan
  sendirinya. Tiga ekstensi baris perintah (5–7) memasang **bootstrap** kecil
  yang memanggil mesin melalui shell (`npx @ahmed-g-gad/apothem install`) untuk
  mematerialisasikan harness lengkap — ketiganya adalah titik masuk, bukan
  penghantaran penuh dengan sendirinya. Plugin Claude Code (1) membawa mesin dan
  menjalankannya secara langsung. Ekstensi keluarga VS Code (4) tidak membawa
  mesin sendiri: perintahnya menjalankan mesin melalui shim npm secara default.
</Callout>

Setiap jalur bersifat idempoten: menjalankan ulang aman dan konvergen ke
keadaan yang sama.

## 1. Plugin Claude Code

**Prasyarat:** Claude Code, dan Python sistem 3.10+ pada `PATH`.

Jalur plugin berjalan sepenuhnya di dalam Claude Code. Jalur ini membundel
mesin Apothem bersama perintah slash, pekerja terdelegasi, skill, aturan, dan
hook-nya, yang semuanya dapat dijalankan dari pohon plugin mandiri:

```text title="Inside Claude Code"
/plugin marketplace add ahmed-g-gad/apothem
/plugin install apothem@apothem
```

Setelah instalasi, set perintah Apothem, pekerja terdelegasi yang disertakan,
skill, dan empat [output-style](/docs/reference/output-styles) (pilih salah
satu dengan `/output-style` atau dari `/config`) tersedia di setiap sesi Claude
Code. Plugin mengirim setiap perintah sebagai skill, yaitu sebuah `SKILL.md`
dengan detail yang dimuatnya sesuai kebutuhan di folder `references/` di
sebelahnya, sehingga Claude Code memanggilnya dengan awalan plugin:
`/apothem:plan-spec`, `/apothem:security-audit`, dan seterusnya. Dua nama sudah
dipakai oleh Claude Code sendiri: `/plan` masuk ke mode rencana dan
`/code-review` menjalankan tinjauan bawaan, jadi ketik `/apothem:plan` dan
`/apothem:code-review` untuk perintah Apothem. Ketika mesin Apothem dipasang ke
Claude Code alih-alih plugin, skill yang sama ditulis ke `~/.claude/skills/`
tanpa awalan, dan skill pribadi `code-review` menggantikan `/code-review`
bawaan (aliasnya, `/review`, tetap menjalankan yang bawaan). Dua nama,
`projectify` dan `workflow`, juga merupakan skill native; skill native itulah
yang dikirim oleh plugin dan instalasi mesin, bukan skill yang diturunkan dari
perintah. Lihat
[Claude Code](/docs/harnesses/claude-code#command-skills-and-reference-files)
untuk cara perintah dipecah, dan [Perintah slash](/docs/reference/commands)
untuk katalog perintah lengkap.

**Verifikasi:** jalankan `/plugin` di dalam Claude Code dan konfirmasikan bahwa
**apothem** tercantum sebagai terpasang, atau periksa laporan penyimpangan dari
terminal:

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 2. Shim npm (`npx`)

**Prasyarat:** Node.js 18+ (untuk `npx`) dan Python sistem 3.10+ pada `PATH`.
Shim menemukan interpreter dan meneruskan setiap perintah CLI ke mesin yang
disertakan — tidak ada yang ditempatkan secara permanen di sistem Anda. Shim
mencoba `python3`, `python`, lalu `py -3` dalam urutan itu; setel
**`APOTHEM_PYTHON`** ke jalur interpreter agar interpreter itu dicoba lebih
dahulu, yang Anda perlukan ketika Python terpasang tetapi tidak ada di `PATH`,
atau ketika beberapa versi terpasang dan Anda menginginkan versi tertentu.
Interpreter yang Anda sebutkan tetap harus lolos pemeriksaan Python 3.10+;
jika tidak lolos, shim kembali ke `python3`, `python`, lalu `py -3`.

```bash title="npx"
npx @ahmed-g-gad/apothem install --harness claude-code
```

Pada komputer tanpa profil, `install` pertama ini membuat profil awal di
`~/.config/apothem/profile.yaml` dan memberitahukannya. Bidang identitasnya
berupa placeholder: personalisasikan bidang tersebut
(`npx @ahmed-g-gad/apothem profile edit`), lalu jalankan ulang perintah dengan
`update` sebagai pengganti `install` untuk menerapkannya.

Shim ini juga berjalan langsung dari repositori:

```bash title="npx from the repository"
npx github:ahmed-g-gad/apothem install --harness claude-code
```

Setiap perintah dalam [referensi CLI](/docs/cli-reference) berfungsi dalam
bentuk ini; gunakan `npx @ahmed-g-gad/apothem` sebagai pengganti `apothem`. Ini
juga jalur instalasi untuk OpenCode dan setiap alat lain yang tidak mengekspos
registri plugin atau ekstensi terpisah — Apothem menyinkronkan alat-alat
tersebut langsung ke direktori konfigurasi native-nya
(`npx @ahmed-g-gad/apothem install --harness opencode`).

**Verifikasi:**

```bash title="Verify"
npx @ahmed-g-gad/apothem --version
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 3. Pemasang satu langkah

**Prasyarat:** Python sistem 3.10+ pada `PATH` (pemasang menawarkan untuk
menambahkan prasyarat `click` / `rich` untuk Anda). Untuk instalasi jaringan:
`git`, untuk menemukan rilis terbaru, dan `gpg`, untuk memeriksa tag rilis yang
ditandatangani (Git for Windows menyertakan keduanya).
[cosign](https://docs.sigstore.dev/cosign/system_config/installation/) bersifat
opsional: dengan cosign, pemasang juga memeriksa arsip rilis yang ditandatangani.

Skrip pemasang me-resolve rilis terbaru, memeriksanya (lihat
[Model kepercayaan](#model-kepercayaan)), menempatkan pohon sumber Apothem di
`~/.apothem`, membuat profil awal bila belum ada, mematerialisasikan harness
pertama Anda, dan memverifikasi hasilnya, semuanya dalam satu kali jalan.
Profil awal membawa bidang identitas placeholder: sunting profil itu, lalu
jalankan `apothem update --harness <name>` untuk menerapkan nilai milik Anda.
Menjalankan ulang bersifat idempoten: klon git di-fetch, tag barunya diperiksa,
dan baru setelah itu klon di-checkout ke tag yang di-resolve; instalasi dari
arsip rilis diperbarui di tempat; dan harness dimaterialisasikan ulang. Bila
mesin berakhir sebagai parsial (kode keluar `2`), pemasang mencetak baris
peringatan, tetap memverifikasi, menempatkan perintah `apothem` dan mencetak
banner-nya, lalu berakhir dengan kode keluar `2`. Mesin berakhir sebagai
parsial bila ia membiarkan sebuah file apa adanya karena baris penanda
Apothem-nya, atau bila ia berhenti setelah menulis sesuatu (lihat
[Saat mesin membiarkan file apa adanya](/docs/install/updating#when-the-engine-leaves-a-file-as-it-is)).
Instalasi terverifikasi adalah jalur default dan yang direkomendasikan.

Impor kunci penandatanganan pemelihara sekali terlebih dahulu. Setiap instalasi
jaringan memeriksa tag rilis terhadap kunci itu, dengan atau tanpa cosign, dan
berhenti ketika kunci itu tidak ada di keyring Anda. Periksa bahwa sidik jari menunjukkan
`5C89 98F9 F241 7204 45D3  F28B 7039 6FED 9C63 4163`, nilai yang dipublikasikan di [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md#maintainer-signing-key). Di Windows, `git verify-tag` membaca keyring dari `gpg` yang
disertakan dengan Git for Windows, sehingga impor dijalankan melalui `bash` milik Git:

```bash title="macOS · Linux · WSL2 · BSD — import the key once"
curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import
gpg --fingerprint 70396FED9C634163
```

```powershell title="Windows · PowerShell — import the key once"
& "$env:ProgramFiles\Git\bin\bash.exe" -c 'curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import && gpg --fingerprint 70396FED9C634163'
```

```bash title="macOS · Linux · WSL2 · BSD — latest signed tag, verified"
curl -fsSL https://apothem.ahmedgad.com/install.sh | bash
```

```powershell title="Windows · PowerShell — latest signed tag, verified"
irm https://apothem.ahmedgad.com/install.ps1 | iex
```

Skrip yang sama disertakan dalam checkout di bawah `scripts/installer/` —
`install`, `uninstall`, dan `update` dalam bentuk `.sh`, `.ps1`, dan `.bat` —
sehingga Anda dapat menjalankannya langsung setelah mengkloning:

```bash title="From a checkout"
APOTHEM_HARNESS=claude-code sh scripts/installer/install.sh                                 # POSIX
$env:APOTHEM_HARNESS = 'claude-code'; pwsh -NoProfile -File scripts/installer/install.ps1   # Windows
```

One-liner yang disalurkan lewat pipa tidak pernah memakai pohon lokal:
`curl ... | sh` dan `irm ... | iex` mengabaikan folder tempat Anda
menjalankannya beserta folder induknya, lalu mengambil dan memverifikasi rilis.
Pemasang memakai pohon lokal hanya bila Anda menjalankan
`scripts/installer/install.sh` (atau `install.ps1`) milik checkout itu sendiri
melalui path-nya, dari folder mana pun (misalnya
`sh ~/src/apothem/scripts/installer/install.sh`), atau bila `APOTHEM_SOURCE`
menunjuk pohon tersebut. Pemasang, pembaru, dan penghapus instalasi, shim
`apothem`, peluncur npm, hook, serta proses validator gerbang konformitas
menjauhkan folder saat ini dari jalur pencarian modul Python. Perintah
`python -m apothem` yang Anda ketik sendiri tidak melakukannya: `-m` membaca
modul dari folder saat ini terlebih dahulu.

Entri kosong dan relatif dalam `PYTHONPATH` milik Anda tidak diteruskan ke
mesin oleh peluncur mana pun (pemasang, pembaru, penghapus instalasi, shim
`apothem` POSIX dan Windows, serta peluncur npm). Entri yang dipertahankan harus
berupa path lengkap: di Windows, path drive seperti `C:\lib` atau path jaringan;
di tempat lain, path yang diawali `/`. `\lib` yang berakar atau `C:lib` yang
relatif terhadap drive dibuang. Skrip sh menanyakan kepada Python yang
dijalankannya bentuk mana yang dibacanya, dan shim `apothem` yang ditulisnya
mempertahankan bentuk itu. Python Windows (yang biasa dipakai di Git Bash)
menerima path mesin dalam bentuk Windows, digabung dengan `;`, dan hanya
mempertahankan path drive dan path jaringan dari `PYTHONPATH` Anda. Python
POSIX, termasuk `python3` milik Cygwin dan MSYS2 sendiri, menerima path POSIX
yang digabung dengan `:` dan hanya mempertahankan entri yang diawali `/`.
Perintah `git` pemasang yang tidak bekerja pada sebuah klon tidak membaca
repositori di folder saat ini.

### Model kepercayaan

Bila `APOTHEM_REF` tidak disetel, pemasang me-resolve rilis
`vMAJOR.MINOR.PATCH` tertinggi dan memasang *rilis itu* — tidak pernah branch
`main` yang terus bergerak. Pemasang memeriksa rilis sebelum konfigurasi apa pun
dimaterialisasikan, dan pemeriksaannya bergantung pada apakah `cosign` ada di
`PATH` Anda:

- **Dengan cosign**, dua pemeriksaan harus sama-sama lolos. Pertama, tag rilis
  harus membawa tanda tangan yang sah dari kunci pemelihara, diperiksa seperti
  pada butir berikutnya, dan tag bertanda tangan itu harus tag yang dinamai
  untuk rilis tersebut: tag bertanda tangan untuk rilis lain yang diarahkan
  ulang ke nama ini ditolak. Lalu pemasang mengunduh arsip platform rilis,
  file `SHA256SUMS`-nya, dan `SHA256SUMS.cosign.bundle`. cosign harus
  memastikan bahwa workflow rilis Apothem menandatangani `SHA256SUMS` untuk tag
  persis itu dan, melalui pemeriksaan `--certificate-github-workflow-sha`-nya,
  bahwa sertifikat yang diverifikasinya diterbitkan untuk sebuah run pada
  commit yang ditunjuk tag bertanda tangan itu. Pemasang tidak membaca
  sertifikat itu sendiri. SHA-256 arsip kemudian harus cocok dengan digest
  yang tercantum. Workflow itu berjalan untuk tag apa pun yang di-push,
  sehingga tanda tangannya saja tidak cukup; tanda tangan tag menunjukkan bahwa
  pemelihara merilis commit tersebut.
- **Tanpa cosign**, atau bila `APOTHEM_HOME` sudah berisi klon git, pemasang
  mengkloning atau memperbarui repositori dan memeriksa tag saja dengan
  `git verify-tag`. Tanda tangan harus sah *dan* dibuat oleh kunci pemelihara
  yang dipublikasikan di [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md), dan tag bertanda tangan itu harus tag yang dinamai untuk
  rilis tersebut. Tag yang ditandatangani kunci lain mana pun ditolak,
  bahkan bila keyring Anda memercayai kunci itu. Tag git bertanda tangan
  menyebut commit-nya dengan ID SHA-1; dengan cosign, pemasang juga memeriksa
  SHA-256 arsip. Klon yang sudah ada di-fetch dan tag barunya diperiksa
  *sebelum* klon itu di-checkout. Pemeriksaan yang gagal membiarkan klon
  seperti semula, dan klon dengan perubahan pada file yang dilacak
  menghentikan pembaruan dengan pesan untuk meng-commit atau men-stash
  perubahan itu, alih-alih menghilangkannya. Dengan ref non-rilis seperti
  `main`, klon yang sudah ada mengikuti salinan branch itu milik origin.

Pemasang mengabaikan variabel lingkungan git yang mengalihkan git
(`GIT_DIR`, `GIT_WORK_TREE` dan sejenisnya) serta yang mengarahkan git ke file
konfigurasi lain (`GIT_CONFIG`, `GIT_CONFIG_GLOBAL` dan `GIT_CONFIG_SYSTEM`) atau
membuatnya membaca atribut dari pohon lain (`GIT_ATTR_SOURCE`; `attr.tree` di
konfigurasi Anda sendiri dikosongkan pada setiap perintah git yang dijalankan
pada klon), dan berhenti bila `APOTHEM_REPO` diawali `-`. `GIT_CONFIG_NOSYSTEM`
tetap seperti yang Anda setel; variabel itu hanya menghentikan git membaca
konfigurasi sistem. git tetap membaca konfigurasi global Anda sendiri dan,
kecuali Anda menyetel `GIT_CONFIG_NOSYSTEM`, konfigurasi sistem dari tempat yang
selalu dicarinya, dan `git`, `gpg` serta `cosign` adalah program yang ditemukan
`PATH` Anda: pemasang memercayainya sebagaimana ditemukan. Selama seluruh
jalannya, pemasang menyetel `GIT_NO_REPLACE_OBJECTS=1`, sehingga git tidak
pernah menukar objek melalui replace ref, `GIT_NO_LAZY_FETCH=1`, sehingga git
tidak pernah mengambil sendiri objek yang hilang dari remote,
`GIT_ALLOW_PROTOCOL` ke transport file, git, http, https dan ssh, sehingga nilai
di lingkungan Anda tidak dapat memperluas daftar itu, dan `GIT_ATTR_NOSYSTEM=1`;
dengan `core.attributesFile` dikosongkan pada setiap perintah git yang
dijalankan pada klon, git lalu tidak membaca file atribut apa pun di luar klon,
sehingga makro yang didefinisikan di file Anda tidak dapat menyebut filter di
sana. Skrip PowerShell mengembalikan keempatnya saat jalannya berakhir. Pemasang
membaca tag rilis satu kali, mencatat commit yang disebutnya, memverifikasi tag,
melakukan checkout commit itu berdasarkan ID, dan mewajibkan `HEAD` adalah
commit itu, sehingga tag yang dipindahkan setelah pemeriksaan tidak mengubah
apa pun. Di Windows PowerShell 5.1 dan 7, unduhan yang dialihkan ke alamat yang
bukan https ditolak, seperti yang dilakukan `curl` pada pemasang POSIX.

`APOTHEM_HOME` harus berupa folder yang hanya dapat ditulis oleh Anda, karena
siapa pun yang dapat menulis ke folder itu dapat mengubah kode yang dijalankan
perintah `apothem`. Di Windows, folder yang dibuat di akar sebuah drive, seperti
`C:\apothem`, dapat diubah oleh setiap pengguna yang masuk ke komputer itu, di
bawah izin default Windows. Default-nya, `~/.apothem`, berada di folder
pengguna Anda sendiri. Setiap instalasi, pembaruan, dan dry run yang mengambil
dari jaringan memperingatkan, tanpa berhenti, bila hal itu tidak terpenuhi,
atau bila folder itu atau folder yang menampungnya dimiliki orang lain, dengan
menyebut folder itu, siapa yang dapat menulis ke atau memilikinya, dan
perbaikannya; instalasi dari checkout lokal, dan pembaruan dengan
`APOTHEM_SOURCE` disetel, melewati pemeriksaan itu. Di Windows
peringatan itu berasal dari
`install.ps1` dan `update.ps1`: `install.sh` dan `update.sh` tidak memeriksa
di bawah Git Bash, MSYS2, atau Cygwin (lihat
[Pemecahan masalah](/docs/install/troubleshooting#the-installer-warns-other-users-can-change-apothem_home)).

Pemeriksaan yang gagal membatalkan instalasi sebelum konfigurasi apa pun ditulis
dan sebelum pemasang mengganti `APOTHEM_HOME`. Tag
bertanda tangan yang kunci publik pemeliharanya belum ada di keyring lokal
justru membatalkan instalasi dengan panduan impor kunci: impor kunci seperti
yang ditunjukkan di atas, periksa sidik jarinya terhadap nilai yang
dipublikasikan di [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md), lalu jalankan ulang.

Menjalankan ulang dengan cosign memperbarui instalasi arsip rilis sebelumnya.
Sumber baru diperiksa dan dibongkar terlebih dahulu di folder di samping
`~/.apothem`, lalu ditukar masuk. Semua yang ada di `~/.apothem` yang bukan
bagian dari pohon sumber terbawa ke instalasi baru: backup rollback mesin
(`backups/`), ledger instalasi (`state/`), rencana, memori, dan data lainnya.
Bila sebuah langkah gagal atau Anda menghentikan jalannya dengan Ctrl+C atau
sinyal terminasi, instalasi sebelumnya dikembalikan tanpa perubahan; bila itu
pun gagal, pesannya menyebut di mana file sebelumnya berada. Kill paksa atau
listrik padam selama penukaran tidak dapat ditangkap: hal itu dapat
meninggalkan folder di samping `~/.apothem`, dan instalasi berikutnya yang
mengambil dari jaringan melaporkannya (lihat di bawah). Aturan berikut berlaku
saat pemasang mengganti `~/.apothem`:

- Klon git tidak diganti oleh arsip rilis tanpa `--yes`. File yang tidak
  dilacak klon pindah ke instalasi baru, dan pohon klon itu sendiri (riwayat
  dan sumbernya) pindah ke folder baru,
  `~/.apothem.before-apothem-<time>`, dengan namanya sendiri (`.apothem`);
  pemasang menyebutkan lokasinya, dan Anda menghapusnya setelah tidak lagi
  membutuhkannya. Bahkan dengan `--yes`, pemasang menolak selama klon itu
  menyimpan pekerjaan lokal yang akan hilang: perubahan, stash, commit yang
  belum di-push, atau file yang tidak dilacak di pohon sumbernya. Commit dan
  push pekerjaan itu, atau pindahkan ke tempat lain, lalu jalankan ulang.
  Pemeriksaan ini juga berjalan dengan `--dry-run`. File `.git` (worktree
  tertaut) dihitung sebagai klon, begitu juga folder `.git`.
- Klon git dari apa pun selain Apothem diperlakukan seperti folder apa pun yang
  tidak berisi instalasi Apothem (lihat di bawah), tidak pernah diperbarui atau
  diganti sebagai klon.
- Klon yang sudah ada diperbarui di tempat hanya bila git dapat melihat setiap
  perubahan di dalamnya dan tidak ada apa pun dalam penyiapannya sendiri yang
  menjalankan kode selama pembaruan. Sebelum fetch, pemasang berhenti bila ada
  file yang ditandai assume-unchanged atau skip-worktree, bila git tidak
  menemukan work tree di `APOTHEM_HOME` (seperti bila konfigurasi klon
  menyetel `core.bare` ke `true`), bila klon berisi submodule (tercatat di
  index-nya, atau disimpan di `.git/modules`), bila `.git/info/attributes`
  menyebut filter atau diff driver (`filter=` atau `diff=`), bila file itu atau
  sebuah file konfigurasi bukan file biasa, atau bila klon meminjam objek dari
  repositori lain (`objects/info/alternates`). Pemasang juga berhenti pada
  setelan apa pun di `.git/config` atau `.git/config.worktree` milik klon itu
  sendiri selain yang ditulis `git clone` dan `git init` di sana untuk klon
  penuh, setelan branch (`remote` dan `pushremote` sebuah branch harus
  `origin`), `user.name`, `user.email`, `maintenance.auto`,
  `maintenance.strategy`, `pull.rebase` dan `pull.ff`, sehingga klon parsial
  yang dibuat dengan `--filter` juga berhenti;
  [Pemecahan masalah](/docs/install/troubleshooting#the-installer-stops-the-existing-clone-is-set-up-in-a-way-the-update-would-trust)
  mencantumkannya. Pesannya menyebut setelan itu dan file tempatnya berada.
  Pemeriksaan setelan, atribut, dan objek berjalan sebelum perintah git apa pun
  yang membaca index atau objek klon, dan juga, bersama pemeriksaan submodule,
  saat `--yes` akan mengganti klon.
  Sebelum perintah git apa pun yang menerapkan file `.gitattributes` milik work
  tree, pemasang berhenti pada file yang tidak dilacak git, yang berbeda dari
  salinan yang di-commit, atau yang salinan ter-commit-nya tidak dapat dibaca
  git atau menyebut filter atau diff driver (salinan di work tree juga dibaca),
  dan pada repositori git di dalam klon yang tidak dilacak git, yang file
  `.gitattributes`-nya juga akan dibaca git. Folder data milik mesin sendiri,
  seperti `backups`, tempat tidak ada rilis yang menulis, tidak dibaca untuk
  hal-hal ini. Sebelum fetch, pemasang berhenti
  pada file di bawah `src` (dieja dengan huruf besar atau kecil apa pun) yang
  tidak dilacak git, karena mesin dapat memuatnya. Setelah checkout, pemasang
  menghapus folder cache Python (`__pycache__`) di bawah `src` sebelum mesin
  berjalan dari klon. Hook git milik klon
  tidak pernah berjalan selama pembaruan, dan setiap perintah git pada klon
  berjalan tanpa pager, tanpa pemeliharaan otomatis, dengan monitor sistem
  file dimatikan, hanya transport file, git, http, https dan ssh yang
  diizinkan (sehingga alamat di konfigurasi klon tidak dapat membuat git
  menjalankan program pembantu seperti `ext::`) dan tanpa rekursi submodule;
  `git diff` dan `git status` melewati submodule. Klon yang dimiliki pengguna
  lain menghentikan jalannya dengan penjelasan (lihat
  Pemecahan masalah).
- Folder yang hanya berisi data milik mesin sendiri (`backups`, `state`, `plans`,
  `memory`, `contexts`, `learning`, `providers`) diperbarui tanpa `--yes`,
  dan data itu dipertahankan.
- Folder yang tidak berisi instalasi Apothem tidak disentuh tanpa `--yes`.
  Dengan `--yes`, pemasang memindahkan seluruh folder, tanpa perubahan, ke
  folder baru, `~/.apothem.before-apothem-<time>` (namanya sendiri tetap
  dipertahankan di dalamnya), menyebutkan lokasinya, lalu memasang dari awal.
- Tautan simbolik di `APOTHEM_HOME` (di Windows, tautan simbolik atau
  junction) ditolak, karena menggantinya akan mengganti tautan itu, bukan
  folder yang ditujunya. Arahkan `APOTHEM_HOME` ke folder itu lalu jalankan
  ulang. Pengecualiannya adalah klon git yang sudah ada, yang diperbarui di
  tempat.
- Di Linux dan macOS, file atau folder yang akan dibawa yang namanya memuat
  spasi atau karakter khusus lain menghentikan instalasi. Pindahkan dulu keluar
  dari `APOTHEM_HOME`.

**Satu jalan pada satu waktu, dan jalan yang dihentikan.** Setiap jalannya
skrip instalasi, pembaruan, dan penghapusan instalasi mengambil kunci di
samping `APOTHEM_HOME`, `~/.apothem.lock` secara default, selama seluruh
jalannya, dan melepaskannya saat jalannya berakhir karena berhasil, gagal,
Ctrl+C, atau sinyal terminasi. Perintah `apothem` sendiri tidak mengambilnya.
Jalan kedua berhenti dengan "Another Apothem install, update or uninstall is
running". Di POSIX, kunci itu berupa folder yang menyimpan ID proses jalannya.
Kunci yang ditinggalkan jalan yang di-kill dilaporkan beserta cara
menghapusnya dan tidak pernah diambil alih, dan kunci yang dibuat di lingkungan
lain (misalnya WSL dan Git Bash di satu komputer) dilaporkan sebagai kunci yang
prosesnya tidak dapat diperiksa dari sana. Di Windows PowerShell, kunci itu
berupa file yang ditutup dan dihapus Windows saat prosesnya berakhir. Bila
`APOTHEM_HOME` berupa tautan, setiap skrip mengambil kunci di samping folder
yang ditujunya. Dry run juga mengambil kunci, kecuali folder yang menampung
`APOTHEM_HOME` belum ada. Jadi setiap jalan, termasuk pembaruan di tempat,
penghapusan instalasi, dan dry run, membutuhkan akses tulis ke folder yang
menampung `APOTHEM_HOME`; tanpanya, jalannya berhenti sebelum mengubah apa pun.

Kill paksa atau listrik padam selama penukaran dapat meninggalkan instalasi
sebelumnya atau entri lain dari `APOTHEM_HOME` di `.apothem-old.<name>.*`,
`.apothem-extract.<name>.*` atau `.apothem-clone.<name>.*` di sampingnya, dengan
`<name>` adalah bagian terakhir dari `APOTHEM_HOME`, atau di folder
`APOTHEM_HOME.before-apothem-<time>`. Instalasi berikutnya yang mengambil dari
jaringan untuk `APOTHEM_HOME` itu, termasuk dry run, berhenti sebelum mengubah
apa pun, menyebut setiap folder dan entri yang dipindahkan ke dalamnya, dan
menjelaskan cara memindahkannya kembali. Untuk folder yang dibuat pemasang
versi sebelumnya, yang tidak menyebut home mana pemiliknya, barisnya mungkin
hanya menyebut data mesin: periksa isinya. Pemasang tidak menghapus apa pun.
Lihat
[Pemecahan masalah](/docs/install/troubleshooting#the-installer-stops-an-earlier-run-left-folders-beside-apothem_home).

`--dry-run` (`-DryRun` di Windows) mengambil dan memeriksa rilis di folder
sementara dan membiarkan `~/.apothem` tidak berubah. Opsi ini melakukan
pemeriksaan yang sama seperti jalan sungguhan, dengan satu pengecualian untuk
klon yang sudah ada: opsi ini memeriksa penyiapan klon itu sendiri, seperti
tercantum di atas, tetapi tidak melakukan fetch ke dalam klon, sehingga tidak
memeriksanya untuk perubahan pada file yang dilacak, yang dilakukan pembaruan
sungguhan setelah fetch-nya. Patok rilis tertentu dengan `APOTHEM_REF`:

```bash title="Pinned, verified install"
APOTHEM_REF=vMAJOR.MINOR.PATCH sh -c "$(curl -fsSL https://apothem.ahmedgad.com/install.sh)"
```

Ganti `vMAJOR.MINOR.PATCH` dengan tag dari
[halaman rilis](https://github.com/ahmed-g-gad/apothem/releases). Tag rilis
tertua adalah tag ringan (lightweight) tanpa tanda tangannya sendiri, sehingga
pemeriksaan tag membatalkan instalasi pada tag itu meskipun commit-nya
bertanda tangan; setiap tag rilis setelahnya beranotasi dan bertanda tangan.
Bagian penandatanganan rilis di
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md)
mencantumkan setiap tag dan cara memverifikasinya.

Penggantian eksplisit melonggarkan perilaku default. `APOTHEM_ALLOW_UNVERIFIED=1` menurunkan pemeriksaan tag yang gagal pada jalur klon menjadi peringatan lalu melanjutkan proses, untuk penggunaan air-gapped atau lokal, atau untuk memasang rilis yang terbit sebelum penandatanganan tag diterapkan. Variabel ini tidak pernah melonggarkan jalur cosign, jadi setel `APOTHEM_VERIFY=signature` bersamanya pada host yang memiliki cosign. Variabel ini juga tidak pernah melonggarkan pemeriksaan bahwa tag bertanda tangan adalah tag yang dinamai untuk rilis itu. Karena penggantian ini meloloskan tag yang tidak bertanda tangan, atau yang ditandatangani kunci lain, pemeriksaan itu hanya melindungi tag yang membawa tanda tangan kunci pemelihara. `APOTHEM_REF=main` melakukan checkout branch yang bergerak tanpa verifikasi hanya bersama `APOTHEM_ALLOW_UNVERIFIED=1`. Dengan `APOTHEM_REF=main` saja, pemasang mengambil `main` ke dalam folder staging (ke dalam klon yang sudah ada, bila `APOTHEM_HOME` adalah klon), lalu membatalkan proses sebelum melakukan checkout apa pun, mengganti `APOTHEM_HOME`, atau mematerialisasikan konfigurasi apa pun, karena branch bukan tag rilis yang bertanda tangan. Checkout lokal melalui `APOTHEM_SOURCE` tidak mengambil apa pun dan melewati verifikasi.

Setel `APOTHEM_VERIFY` untuk memilih pemeriksaannya sendiri. Default-nya adalah `auto`:

| Nilai | Apa yang diperiksa pemasang |
| --- | --- |
| `auto` (default) | `release` bila `cosign` ada di `PATH` dan `APOTHEM_HOME` bukan klon git, selain itu `signature` |
| `release` | Tanda tangan tag rilis dari kunci pemelihara dan bahwa tag bertanda tangan adalah tag yang dinamai untuk rilis itu, lalu pemeriksaan cosign bahwa workflow rilis menandatangani `SHA256SUMS` dalam sebuah run pada commit tag tersebut, lalu SHA-256 arsip. Berhenti bila cosign atau `gpg` tidak ada |
| `signature` | Tanda tangan GPG tag rilis, yang harus berasal dari kunci pemelihara, dan bahwa tag bertanda tangan adalah tag yang dinamai untuk rilis itu |
| `checksum` | SHA-256 arsip terhadap `SHA256SUMS` saja. Membutuhkan `APOTHEM_ALLOW_UNVERIFIED=1`, dan memperingatkan sebelum mengunduh. Mode checksum tidak memverifikasi rilis. SHA256SUMS berasal dari rilis yang sama dengan arsipnya, sehingga kecocokan hanya menunjukkan bahwa unduhan tidak rusak; siapa pun yang dapat mengubah file rilis dapat mengubah keduanya. Gunakan hanya pada host yang tidak memiliki cosign maupun `gpg`, dan hanya bila Anda menerima hal itu |

Setiap mode arsip membatalkan instalasi bila digest tidak cocok sebelum
mengekstrak apa pun. Rilis awal menamai bundle-nya `SHA256SUMS.sig`, dan
pemasang membaca nama itu bila `SHA256SUMS.cosign.bundle` tidak ada.

Mesin kemudian berjalan langsung dari pohon yang ditempatkan. Setiap
dependensi pihak ketiga kecuali `click` dan `rich` di-vendor di dalam pohon
sumber, dan entry point sendiri yang menaruh direktori vendor tersebut di
`sys.path`. Pemasang mencetak path lengkap shim `apothem` yang ditulisnya. Bila
tidak menulis shim, pemasang mencetak perintah yang menjalankan mesin dengan
folder saat ini dijauhkan dari `sys.path`; salin perintah itu dari banner.

Kedua skrip membaca variabel lingkungan konfigurasi yang sama
(`APOTHEM_HOME`, `APOTHEM_REPO`, `APOTHEM_REF`, `APOTHEM_ALLOW_UNVERIFIED`,
`APOTHEM_VERIFY`, `APOTHEM_RELEASE_BASE`, `APOTHEM_SOURCE`, `APOTHEM_HARNESS`, `APOTHEM_PROFILE`,
`APOTHEM_SKIP_VERIFY`, `APOTHEM_AUTO_INSTALL_DEPS`, `APOTHEM_BIN_DIR`); lihat
[Variabel lingkungan pemasang](/docs/how-to/installer-environment-variables)
untuk tabel lengkapnya dan
[Runtime mandiri](/docs/architecture/self-contained-runtime) untuk cara kerja
model pemanggilan `python -m`.

**Perintah `apothem`.** Setelah instalasi berhasil, pemasang menulis shim
`apothem` yang meneruskan ke mesin yang disertakan — di POSIX ke dalam
`$HOME/.local/bin`, di Windows ke dalam `%LOCALAPPDATA%\Microsoft\WindowsApps`
(direktori pengguna yang sudah ada pada `PATH` default Windows). Pemasang tidak
pernah menyunting `PATH` Anda. Setelah direktori tersebut ada di `PATH`, Anda
menjalankan `apothem <command>` secara langsung, tanpa `PYTHONPATH` manual.

**Verifikasi:**

```bash title="Verify"
apothem verify --harness claude-code

# or, before the shim is on PATH, by the shim's full path:
~/.local/bin/apothem verify --harness claude-code
```

## 4. Ekstensi keluarga VS Code

**Prasyarat:** VS Code, Node.js 18+, dan Python sistem 3.10+ pada `PATH`.

Ekstensi **Apothem for VS Code** tersedia di
[Visual Studio Marketplace](https://marketplace.visualstudio.com/items?itemName=ahmed-g-gad.apothem-vscode)
sebagai `ahmed-g-gad.apothem-vscode`: pasang dari tampilan Extensions atau dengan
`code --install-extension ahmed-g-gad.apothem-vscode`. Ekstensi ini juga dapat dipasang dari paket
`apothem.vsix`: `code --install-extension apothem.vsix`, atau perintah *Install from VSIX…*
milik editor. Alur kerja rilis menandatangani paket tersebut dan
melampirkannya ke setiap GitHub Release. Rilis yang dipublikasikan sebelum alur
kerja mengemas ekstensi tidak menyertakan `.vsix`; jika rilis terbaru tidak
memilikinya, bangun paket dari checkout dengan rilis vsce yang dikunci di
`tools/vsce/` (rilis vsce itu memerlukan Node.js 22 atau lebih baru):
jalankan `npm ci --prefix tools/vsce --ignore-scripts`, lalu
`cd vscode-extension && ../tools/vsce/node_modules/.bin/vsce package --no-dependencies --out apothem.vsix`.
Salinan yang dipasang dari `apothem.vsix` versi sebelumnya membawa pengenal
`ahmed-g-gad.apothem`; hapus salinan tersebut (`code --uninstall-extension ahmed-g-gad.apothem`)
agar kedua salinan tidak sama-sama mendaftarkan perintah yang sama. Satu ekstensi
mencakup editor-editor dalam keluarga VS Code. Perintah paletnya (`Apothem: Install`, `Verify`,
`Update`, `Uninstall`, `Doctor`) menjalankan mesin yang sama melalui runner
yang dikonfigurasi (`npx @ahmed-g-gad/apothem@<extension version>` secara
default, sehingga ekstensi menjalankan versi mesin yang dikirim bersamanya;
arahkan pengaturan pengguna `apothem.runner` ke checkout lokal untuk
menjalankan dari sumber). Install, Verify, Update, dan Uninstall menanyakan
harness mana yang akan ditangani, dengan menawarkan harness milik editor itu
sendiri terlebih dahulu; `all` adalah salah satu pilihan, tidak pernah menjadi
default. Pengaturan `apothem.runner` berlingkup komputer (machine-scoped),
sehingga workspace tidak dapat mengubahnya, dan ekstensi hanya berjalan di
workspace tepercaya.

**Verifikasi:** jalankan perintah **Apothem: Verify** dari palet perintah
editor, atau dari terminal:

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 8. Mesin langsung (`python -m apothem`)

**Prasyarat:** Python sistem 3.10+ dengan paket `click` dan `rich` yang dapat
diimpor, ditambah checkout repositori. Node.js tidak diperlukan.

Jalankan mesin langsung dari klon. Entry point menaruh dependensi yang
di-vendor (`src/apothem/_vendor`) di `sys.path`, sehingga dengan `click` dan
`rich` yang dapat diimpor, `PYTHONPATH=src` adalah seluruh penyiapannya:

```bash title="Direct engine"
git clone https://github.com/ahmed-g-gad/apothem
cd apothem
PYTHONPATH=src python -m apothem install --harness claude-code
```

`python -m` menaruh folder saat ini di urutan pertama jalur pencarian modul
Python, sehingga file di sana seperti `click.py`, atau folder bernama `apothem`,
akan berjalan menggantikan modul yang sebenarnya. Jalankan perintah ini dari
akar checkout, atau dari folder lain yang Anda percayai. Perintah `apothem` yang
terpasang tidak membaca folder saat ini.

Seperti pada shim npm, `install` pertama pada komputer tanpa profil membuat
profil awal di `~/.config/apothem/profile.yaml` lalu melanjutkan.

**Verifikasi:**

```bash title="Verify"
PYTHONPATH=src python -m apothem verify --harness claude-code
```

## Prasyarat sekilas

- **Python 3.10 atau lebih baru** — jalur yang menemukannya melakukannya
  berdasarkan nama, dan namanya berbeda per jalur. Shim npm mencoba `python3`,
  `python`, lalu `py -3`. Pemasang mencoba `python3`, `python`, dan nama
  berversi `python3.14` turun hingga `python3.10`.
- **`click` dan `rich` dapat diimpor** di bawah interpreter itu — dua
  dependensi yang berhadapan dengan terminal yang tidak di-vendor oleh mesin.
  Pemasang memeriksa keduanya, menyebutkan apa pun yang hilang, dan menawarkan
  untuk memasangnya untuk Anda — dengan konfirmasi Anda, atau secara otomatis
  dengan `--yes` (`-Yes` di PowerShell) atau `APOTHEM_AUTO_INSTALL_DEPS=1`. Di
  setiap kanal lainnya, paket yang hilang menghentikan mesin dengan galat
  (kode keluar 1) yang menyebutkan perintah persis untuk interpreter yang
  ditemukannya, dengan batasan versi yang diuji oleh Apothem
  (`<interpreter> -m pip install "click==…" "rich>=…"`); dengan `--json`, galat
  yang sama tiba sebagai amplop JSON dengan kode `runtime.dependency_missing`.
- **Node.js 18 atau lebih baru** — hanya jalur yang menjalankan `npx`: shim npm
  (2), ekstensi keluarga VS Code (4), dan bootstrap baris perintah (5–7).
- **Runtime yang telah mencapai akhir masa pakai.** Python 3.10 mencapai akhir
  masa pakai di upstream pada 2026-10-01, dan Node.js 18 dan 20 pada 2025-04-30
  dan 2026-04-30. Apothem masih mendukung ketiganya sebagai batas bawah yang
  dideklarasikannya dan menguji masing-masing di CI, tetapi ketiganya tidak
  lagi menerima perbaikan keamanan dari upstream, jadi utamakan Python 3.11
  atau lebih baru dan Node.js 22 atau lebih baru.
  [Kebijakan batas bawah runtime](/docs/governance/release-engineering-policy#runtime-floors)
  menjelaskan cara batas bawah dinaikkan.
- **Git dan GnuPG** — hanya jalur pemasang, dan hanya untuk bentuk jaringan
  (skrip memakai keduanya untuk menemukan rilis terbaru dan memeriksa tag
  bertanda tangannya, dan, tanpa cosign, mengkloning sumber; checkout lokal
  tidak memerlukan keduanya).
- **Claude Code** — hanya jalur plugin. **VS Code** dan alat host milik setiap
  bootstrap baris perintah hanya dibutuhkan untuk kanalnya masing-masing (4–7).
