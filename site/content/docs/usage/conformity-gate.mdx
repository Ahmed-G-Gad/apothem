The conformity gate at `src/apothem/conformity/gate.py` runs the
mechanical fraction of the fifteen-bar pre-emission gate (M1-M15)
against every artifact the operator authors.

The commands on this page assume an Apothem checkout, so prefix each one you run
with `PYTHONPATH=src`. After a script install, use `PYTHONPATH="$HOME/.apothem/src"`
in place of `PYTHONPATH=src`.

## Running the gate

The gate is **advisory by default**: it reports findings and exits `0`, so a
local run never blocks you. Add `--strict` (or set
`APOTHEM_CONFORMITY_STRICT=1`) to exit non-zero on a blocking finding — the mode
CI and pre-commit use to fail a violating change.

```bash
# Advisory: report every validator's findings across the repo, exit 0
PYTHONPATH=src python -m apothem.conformity.gate --all .

# Strict: exit non-zero (code 2) when a blocking finding is present
PYTHONPATH=src python -m apothem.conformity.gate --all --strict .
```

These commands run the gate from an Apothem checkout. `python -m` reads
modules from the current folder first, so run them from the checkout root
or another folder you trust. To check a project whose files you do not
trust, run the gate by its script path with `-E -s` instead:
`python3 -E -s src/apothem/conformity/gate.py --all .` in a checkout, or
`python3 -E -s ~/.apothem/src/apothem/conformity/gate.py --all .` after a
script install. On Windows, use `python` in place of `python3` and the full
path, since Windows PowerShell and cmd do not expand `~`:
`$HOME\.apothem\src\apothem\conformity\gate.py` in PowerShell, or
`%USERPROFILE%\.apothem\src\apothem\conformity\gate.py` in cmd. A script start
keeps the current folder out of the first entry of Python's module search
path; `-E` also keeps out `PYTHONPATH`, where an empty or relative entry
names the current folder too, and `-s` keeps out your user site-packages.
This keeps the project's files out of the gate's own Python code only;
the `git` the gate runs is covered next.

Three standalone validators run `git` in the project they check, and so do
`--all`, which runs them, and `--all-perwrite`, which lists the tracked files
with `git ls-files`:

```text
agents-md-coverage-grep
conventional-commit-grep
no-global-plans-grep
```

That repository's own settings, in `.git/config`, the files it includes and
`.git/config.worktree`, can name a program for git to start while it only
reads. The gate turns off each such setting it knows of with options on git's
command line, which win over every file git reads and also reach any git that
git starts in a submodule:

- no file-system monitor (`core.fsmonitor`);
- no signature program (`gpg.program`, `gpg.ssh.program` and
  `gpg.x509.program` point at a path where nothing can exist, and
  `log.showSignature` is off);
- no hooks, no pager, and no automatic maintenance;
- no external diff or text-conversion program, and submodule changes shown as
  commit ids only, so git starts no second git inside a submodule;
- file contents read with `git cat-file blob`, which refuses a submodule entry
  where `git show` would show it as a commit.

Three settings name a file for git to read, not a program, and that file can
sit on a network path. The gate's command line keeps git from reading them
too: the diff order file (`diff.orderFile`), the excludes file
(`core.excludesFile`) and the mailmap file.

It also sets `GIT_NO_LAZY_FETCH=1` and an empty `GIT_ALLOW_PROTOCOL`, so git
never fetches a missing object of a partial clone through an address the
repository names. The gate starts git only from a full-path entry of your
`PATH`. It never takes git from the current folder: it skips empty and relative
`PATH` entries, which name that folder, and it does not look there first, as
Windows does for a bare program name. git gets only those full-path entries for
the programs it starts by name.

So you can run these commands on a project that came with its `.git` folder
from someone else, in an archive or a shared folder: none of the settings
above can make the gate start a program. Two limits remain. The repository can
still make git read a path somewhere else through any setting or file that
names one, for example `include.path` or `includeIf`, `core.worktree`, the
`gitdir:` line of a `.git` file, or `.git/objects/info/alternates`; on
Windows, a network path there (`\\server\share`) makes Windows connect to that
server and sign you in. One case is narrower: Git for Windows 2.55 refuses a
network path in a `gitdir:` line before it connects, unless your own
`safe.directory` setting allows that path. And the list covers the settings
known today; a later git release can add a new one. Your own global and system
git settings still apply, except the ones above, which the gate's command line
overrides. This covers git only: `python -m` reads Python modules from the
current folder first, so start the gate from a folder you trust.

Exit codes: `0` clean (or advisory), `2` a strict findings-block, `3` a
usage error: an unknown flag or validator name, a file that does not exist, or a
root directory that does not exist. `--help` prints the full usage and exits
`0`. Every standalone validator accepts the same `--help` and exits `3` on an
unknown flag or a missing root.

A relative root such as `.` is resolved to an absolute path before any
validator runs, so `--all .` and `--all "$PWD"` inspect the same tree. Each
validator reports `inspected` — how many targets it examined — and `--all`
copies that count into every result entry. A validator that inspected nothing
reports `passed: false`, so a wrong working directory cannot pass silently. The
two plan-suite validators are one exception: plan suites live in the gitignored
`.apothem/plans/` tree, so they report `empty_scope_expected: true` on a clean
checkout and still pass. The workflow validators do the same when the project
has no `.github/workflows/` directory yet, and the commit-subject validator does
when the root has no commit history.

A project can come with files someone else made, in an archive or a shared
folder, so every `--all` validator opens and lists only regular files and real
folders that it reaches through real folders below the root. It never follows
a symbolic link or, on Windows, a junction, and at any level below the root it
treats each of these as missing:

- a link, even one that points inside the root. A walk or a folder listing
  skips it, so what it points to is checked only where the validator reaches
  it under its own path;
- a named pipe, a device or a socket, where a read would wait or never end;
- on Windows, a name that ends in a dot or a space, because Windows would
  open a different entry under that name.

A few checks still use a link without entering it:

- for a fixed file that is a symbolic link, such as a `CLAUDE.md` that points
  at another file, the gate reads the link's own text and opens the file it
  names only when that is a regular file inside the project, reached through
  real folders. A per-folder `README.md` link counts the same way. An absolute
  link counts when it is written through the project folder as it resolves,
  or on Windows through the same path in another letter case; a validator
  run on its own also accepts the folder as you
  typed it, unless that path contains `..`, while the gate resolves the
  folder before it starts each validator. A linked
  `.gitattributes` still counts as missing, because git does not read it;
- the stray-plans check in `no-global-plans-grep` reports a plans folder or an
  `.apothem` folder that is a link, by its name, wherever the link leads;
- `no-toplevel-docs-grep` reports a `docs` link at the root by its name;
- `naming-grep` checks a link's own name.

Each validator's report lists the links and special files it left out under
`skipped_links`, so a link never hides a file without a trace. It also lists
there a folder it could not list (no access, a path too long, a read error),
and the `.git` entry of a folder it skipped as a nested checkout when that
entry is a link or a special file. A validator
that passes when its folder is missing, such as the workflow validators, does
not pass when that folder is a link: the files may be behind it, so the run
fails like one that checked nothing. A hard link is a regular file and is read
like one. The `--all` validators look at each level when they reach it and
then open the file by name, so a second user who can write to the project
while the gate runs can swap a checked file or folder for a link or a named
pipe before it is opened, or make a read wait until the time limit; the gate
does not guard against that. `--all-perwrite` opens the last level without
following it, but its folders can still be swapped. In `--all` and
`--all-perwrite`, the gate itself opens only regular files inside the root,
checking each folder on the way with `lstat`, including every path git lists,
and never reads inside a `.git` entry. Before they run git, the three `--all`
validators that run git, and the two `--staged` checks, look with `lstat` at
the `.git` entry of the root and of every folder above it that git searches,
as the tree is at that moment; if any of them is a link, or cannot be looked
at, they do not run git. This also refuses projects git would handle safely,
such as every project below a home folder whose `.git` is a link, even one
with its own repository: that is the deliberate cost of a simple rule. The
three `--all` validators run git without `GIT_DIR` and the other variables
that name the repository, its stores or its index; the `--staged` checks keep
a hook's `GIT_DIR`. Which repository git then reads is not checked: a
`gitdir:` line, `commondir`, alternates, `core.worktree`, an include, or a
link inside the git folder can name another one, and git follows them, so git
can reach a network path or wait until its time limit. The gate uses git's
output only as names, modes, status letters, the subject of the last commit,
commit times and a few settings, and never opens a path git prints without
checking each level inside the root. When a link is found, each of the three
`--all` validators lists it under `skipped_links` (relative to the root inside
it, by its full path above it). `conventional-commit-grep` then reports
`not-a-git-repo`, as it does outside a checkout, but it does not pass: it
gives a `check_error` that names the link.
`no-global-plans-grep` reports the link as a finding and fails, and the
companion coverage check skips its freshness test, as it does with no history.
`--all-perwrite` does not list the tracked files either: it fails with a
`check_error` that names the link, and so do the two `--staged` checks, which
name a link only in `check_error`: they read the repository a hook's
`GIT_DIR` names but still refuse a link on the search path from the folder
they run in. A `.git` entry the gate cannot look at (a path too long, a share
it cannot reach, no access) is not a link and is not listed under
`skipped_links`: `conventional-commit-grep` fails with the status
`git-failed` and a `check_error`, the companion coverage check,
`--all-perwrite` and the two `--staged` checks fail with a `check_error` that
says the entry could not be looked at, and `no-global-plans-grep` reports it as
a finding.

Each standalone validator runs as a program of its own, and the gate gives it
10 minutes, in `--all` and in `--check`. The slowest one takes about a minute on
Apothem's own repository. A validator still running at the limit is stopped,
together with every program it started, such as a `git` command still waiting,
and reported with `passed: false` and a `check_error` that says it did not
finish. On Linux and macOS each validator runs in a session of its own, and a
`SIGTERM` or `SIGHUP` to the gate, such as from `timeout` or a closed terminal,
stops the validator's programs before the gate exits with code 128 plus the
signal's number. That holds too for one that arrives while the gate starts or
stops a validator: it waits until that step is done, and the exit code stays
128 plus its number even when a Ctrl+C follows during that step. A `SIGKILL`,
which no program can catch, ends only the gate there: a validator it started
runs on
until it finishes, and a `git` command that validator waits on still stops at
its own limit. On Windows each validator runs in a job object, which also ends
its programs when the gate itself ends.
Each program the gate starts there waits, suspended, until it is in the job
object. A program it cannot resume is stopped, and the error says whether it
is in the job object. A program that something else told to end before it was
resumed never ran, and fails the same way, whatever its exit code, with two
exceptions. One ended with exit code 259, the code Windows also gives a
running program, reads as running while Windows is still ending it. One ended
just before the resume is caught only when the gate reads its exit code within
1 ms of the resume; a later read, for example on a busy machine or while other
threads in the calling process are busy, takes its exit code as the program's
own. On the machine it was
measured on, the smallest program Windows can run lived at least 3 ms past
its resume, and `git` 27 ms, so a program that ran is not taken for one that
was ended. One ended just after
the resume cannot be told apart from one that ran either. On
every platform, in the gate's own run, a Ctrl+C that arrives during the start
waits until the program runs (on Windows, until the gate has tried to resume
it), so no program is left suspended or running past its limit. A second
Ctrl+C that arrives while the gate stops a program waits until the stop is
done. One that arrives just before the stop begins makes the gate try the
stop again, up to three times. When those tries fail, or a Ctrl+C lands
between two of them, the gate stops the program without holding signals
back, again up to three times, so one more Ctrl+C does not skip the stop. It
takes several Ctrl+C presses, each within microseconds of one of these
points, to leave the program running. After a stop the gate waits up to half
a second for the stopped program to end, so on Linux and macOS it does not
linger as a defunct process, and a Ctrl+C during that wait does not replace a
termination already under way. A handler the calling process set for another
signal can still leave the program running (on Windows, suspended), when its
error lands in the few microseconds after the program starts, before the gate
records it. When the gate changes
its own signal handlers, a signal that
arrives mid-change does not leave a handler changed. On Linux and macOS the
gate blocks Ctrl+C, `SIGTERM` and `SIGHUP`, and no other signal, for the few
microseconds the change takes, so such a signal waits until the change is
done and meets the handlers that are then in place. The gate then unblocks
only the signals it blocked. For any other signal, on Windows, and for a
signal that arrived just before the block, a change the signal stopped is
made again, up to three times. When putting its handlers back fails at
every try, the gate makes one last try for each handler left. A handler stays
changed when an error stops that last try too, such as a `TimeoutError` from
a timer the calling process set that fires each time, and in rare cases when
several signals whose handlers raise arrive back to back, within
microseconds, and skip the last try. An error that
comes back at every try, such as a `RecursionError` near Python's recursion
limit, ends the change within two tries and goes on. The gate puts its
handlers back with calls no deeper than the ones that changed them, so near
that limit it does not leave Ctrl+C ignored. A `SIGTERM` handler that the
calling process sets during a run stays in place. On Linux and macOS, in a
Python subinterpreter, where no signal handler may be set, the gate runs its
programs without changing handlers; on Windows, Python cannot read a
program's output from an isolated subinterpreter, which allows no daemon
threads. Ctrl+C prints one line and exits
`130`. The limits add up: a run in
which several validators wait takes the sum of their limits.

Five validators also give each `git` command they run a time limit of its own.
The limits hold on every platform, including on Windows when `git` on `PATH`
is the launcher that Git for Windows installs, which starts the real git:

```text
conventional-commit-grep            git log -1, git rev-parse           1 minute
                                    git ls-files, git config            1 minute
agents-md-coverage-grep             git rev-parse, git config           1 minute
                                    git log over the whole history      5 minutes
no-global-plans-grep                git ls-files                        1 minute
production-ready-pr-grep --staged   git diff --cached                   1 minute
semver-stability-grep --staged      git diff --cached, git cat-file     1 minute
```

These commands take a fraction of a second on most projects, so a limit is
reached only when `git` waits for something that never comes. A project's own
git settings can make it wait for ever, for example an `include.path` in its
`.git/config` that names a named pipe. A `git` command that runs past its limit
does not pass: the validator reports `passed: false` with a `check_error` that
names the command. Neither does a `git` that refuses a checkout it found, for
example one another user owns or one with a bad line in its `.git/config`; the
`check_error` then gives git's exit code, and exit code 128 is the one git uses
when it cannot open or read a repository. A folder whose `.git` entry git
cannot open counts as such a checkout, because the history the checks need may
be there unread: an empty `.git` folder outside any other checkout, or a
`.git` file that names a folder that no longer exists, as an unpacked worktree
or a copied submodule leaves behind. Remove that entry, or run the gate on a
full checkout. That holds for the stale-companion check too, although its
findings are otherwise advisory, and the commit-subject check then also
reports `inspected: 0` with `empty_scope_expected: false`. On Windows, a `git`
that the gate started but could not resume is a failed `git` too: the
`check_error` gives exit code 128, and it never counts as a missing `git`. The
stale-companion check reads the whole history once, and that read gets 5
minutes, so a large history is slow rather than a failure; a history that
takes longer to read fails the check. A plain folder that is not inside any
git checkout, a repository with no commit yet, or a machine without `git`
still passes these checks as before. So does a partial clone, one made with
`git clone --filter`: the gate does not let `git` fetch what the clone left
out, and git gives no answer that tells an object the clone left out from one
that was lost. So in a partial clone the stale-companion check counts any
failed history read as history that is not available: it skips its freshness
test and passes, as it does with no history. These exemptions, and the
`check_error` for a checkout git refuses, are for the other four validators:
`no-global-plans-grep` needs a checkout git can read, so outside one, on a
machine without `git`, or in a checkout git refuses, it fails as before, with
the reason on standard error: git's exit code, not git's own text. As with any result that does not pass, the
advisory default reports it and exits `0`, and `--strict` exits `2`.

For the two `--staged` checks, a value git cannot read for a diff setting,
such as `diff.renameLimit = abc`, is one such bad line: `git diff` fails, and a
change set that was not read is not an empty one. These two checks, the
commit-subject check and the stale-companion check look for the checkout in
the folder they run in and in the folders above it, so the same holds in a
subfolder of the checkout. They stop looking where git stops: at a folder
named in `GIT_CEILING_DIRECTORIES` and, outside Windows, at a folder on
another file system, unless `GIT_DISCOVERY_ACROSS_FILESYSTEM` is set. A
folder with no repository of its own, mounted below one, therefore still
passes. The commit-subject check run on a subfolder of a checkout checks the
checkout's latest commit when the checkout tracks a file in that subfolder,
or has one staged there. Where the checkout ignores case, as on Windows and
macOS, that holds for a subfolder whose name was changed on disk only in upper
or lower case too. A folder the checkout does not track, untracked or
ignored, has no history of its own and passes, such as a new project inside a
home-folder dotfiles repository. An empty `.git` folder above the folder it
runs in, with no repository further up, makes git fail, and the check reports
`git-failed`.

Both `--staged` checks read the staged names from the top of the work tree,
whatever your own `diff.relative` setting is, so a subfolder setting never
hides a staged file.

`semver-stability-grep --staged` looks for the package in the folder it runs
in and then in the folders above it, up to the nearest folder that holds a
repository or where git stops looking, and runs git in the folder that holds
the package, so a run from a subfolder checks the same change set. It reads
the version file from that folder too, so a package below the top of the
repository is checked. When a `.git` file that git refuses lies between the
folder it runs in and the package, git runs in the folder it runs in
instead, stops at that file, and the check reports a `check_error`. git
refuses a `.git` file that names no repository, that is larger than 1 MiB, or
that does not hold `gitdir:`, one space and a path, with only line endings
after it. On Windows the check also refuses a `.git` file that names a network,
device or NT path (`\\host\share`, `\\?\`, `\??\`), and it does not look that
path up itself. It also refuses a path Git for Windows refuses: a name that
ends in a dot or a space or is a device name such as `aux.d`, `lpt0` or
`CONIN$` (but not `com0`, which Git for Windows accepts), or a `:` after the
drive. It reads a byte in the path that is not UTF-8 as Git for
Windows does: from `0xA0` up as that character and below it as two hex digits,
so `0x9F` reads `9f`. The nearest folder that holds `src/apothem/__init__.py`
is the one checked; it does not read `GIT_WORK_TREE`. A project without the
package has nothing to check there: it passes without running git, whatever
state its repository is in.

The gate reads each list of path names from git byte for byte, so a name that
holds a line break, a carriage return or a byte that is not UTF-8 names the
same file to every check. One case cannot be read: Windows cannot hand git a
name that is not UTF-8, which only an index made on another system can hold.
`semver-stability-grep --staged` then reports a `check_error` for the change
set; it does not skip that file. The history read of the stale-companion check
is the exception to the first sentence: there git prints a name with a control
character in its quoted form, and a byte that is not UTF-8 reads as the
replacement character, so that check cannot match a folder with such a name.

The stale-companion check treats only the `AGENTS.md` at the top of the
repository as the canon. When you run it on a subfolder that has a README of
its own, that subfolder's `AGENTS.md` is a per-folder companion. When the
subfolder is the top of a repository of its own, such as a submodule or a
nested clone, its `AGENTS.md` is that repository's canon instead. A run on the
whole repository skips some subfolders, such as test fixtures and nested
repositories, that a run on the subfolder itself checks. A subfolder without a
README is not checked as a folder of its own this way; run the check on a
folder above it. A companion that was deleted in a commit and written again
counts as new until you commit it.

Six validators start at the repository root and search the whole tree for the
files they check:

```text
agents-md-coverage-grep
agnosticism-grep
dynamism-grep
freshness-token-grep
plain-language-grep
reference-token-grep
```

These skip nested git checkouts, such as worktrees, submodules and nested
clones (a folder whose `.git` file or folder holds or names a repository; a
plain `.git` file or an empty `.git` folder does not hide its folder), never
enter a linked folder, and skip directories that hold
dependencies, virtual environments, caches or build output, such as
`node_modules`, `venv` and `dist`. The
stray-plans check in `no-global-plans-grep` also stops at a nested checkout. A
run of any of these reports on the checkout it was pointed at and on nothing
else. A validator that reads one fixed folder, such as `naming-grep` under
`src/apothem/`, reads everything below that folder.

`--all-perwrite` checks the files that `git ls-files` lists under the root.
git lists each entry exactly as the repository's index holds it, and a project
can come with an index and files someone else made, so the gate reads a listed
path only when it is a regular file inside the root, of at most 64 MiB,
holding UTF-8 text. It counts every other listed path under `files_skipped`,
by reason:

- `outside_project`: an entry with an empty, `.` or `..` part, such as
  `../notes.md`, `a//b.md` or a name starting with `/`, or a part that names
  `.git` on Windows: `.git` in any case, also with dots, spaces or a colon
  after it, and `GIT~1`. git refuses each of these by default on every
  system, so the run does not pass;
- `unsupported_name`: on Windows, a name the system cannot hold as written:
  one with a colon (as in `a:b.md`, whose `a:` reads as a drive), a backslash,
  one of `<>"|?*` or a control character, or a part that ends in a dot or a
  space; and a name Windows reads as something else: a device name standing
  alone, such as `CON`, `NUL` or `COM1`, or a short name such as `GIT~2`.
  git on Linux or macOS can track such a name, so it is counted without
  failing the run. A hand-written entry such as `C:/x` or `..\..\x` lands
  here on Windows too;
- `link`: a symbolic link, or on Windows a junction, at any level below the
  root, even one that points inside it, or an entry the index marks as a link
  (in any stage of a merge conflict, so such a file is not read until the
  conflict is resolved).
  git stores a link as the path it points to, and a tracked file that a link
  points to is checked under its own path;
- `submodule`: the entry of a submodule;
- `not_regular_file`: anything else that is not a regular file, such as a
  folder, a named pipe or a device, where a read would wait or never end;
- `missing`: a tracked file that is not in the working tree; on Windows this
  includes a name git listed in bytes that are not UTF-8, which only an index
  made on another system holds (Git for Windows writes such a file under
  another name, so its content is not checked), and a path longer than the
  system allows when long paths are not turned on;
- `unreadable`: a file, or a folder on the way to it, that the system will not
  let the gate look at, open or read: for lack of permission, because another
  program holds the file or part of it, or because the system cannot open it,
  such as an online-only file whose sync program is stopped. When another
  program holds the whole file, the gate waits 0.2 seconds and tries once more:
  on Windows, a program that has it open without sharing it; elsewhere, a write
  lease being broken, such as a Samba oplock or an NFS delegation. The run does
  not pass, since a finding in it would go unseen. A few cases fail the run this
  way though nothing is wrong with the file: a lease break that takes longer
  than 0.2 seconds, a file waiting to be deleted, and a named pipe in a project
  on a `\\wsl$` share, where each read first waits about 10 seconds;
- `too_large`: a file over 64 MiB whose first 64 MiB are UTF-8 text, or a
  file that grows past 64 MiB while the gate reads it. The run does not
  pass, for the same reason;
- `not_utf8_text`: a file whose bytes are not UTF-8 text, such as a UTF-16
  file with a byte-order mark. Over 64 MiB, the first 64 MiB decide, and a
  file is binary when a quarter or more of its first 8000 bytes are NUL,
  such as a large zero-filled image or a UTF-16 file of mostly Latin text
  without a byte-order mark, so it does not fail the run; a few NUL bytes in
  text do not count;
- `exempt`: a file the checks leave out by design: one whose suffix marks it
  as binary, such as an image or an archive, and anything under a
  `.apothem/plans`, `tests/conformity`, `tests/fixtures`, `_vendor` or
  `node_modules` folder at any depth inside the root. The checks for
  `outside_project` and `unsupported_name` come first, so no exemption hides
  them.

When a run does not pass for `outside_project`, `unreadable` or `too_large`,
`files_not_passed` names the entries behind each of those reasons, as git
lists them, sorted, up to 10 per reason; `files_skipped` has the full count.
A line on stderr names those reasons and their counts too, so a CI log that
shows only stderr says why the run failed.

Each file's levels are checked right before it is read, and the file opened must
be the one that check found. A file another program swaps in between, for
another file, a link or a named pipe, is looked up once more, and counted as
`unreadable` if it is swapped again; on Windows a junction swapped in is
`unreadable` at once, and a symbolic link is found as a `link` on the second
look. The gate never waits on a named pipe or reads through a link that took the
file's place. On Windows, a file that Data Deduplication or a cloud sync program
keeps behind a reparse point is read through that program as usual; when the
program is stopped, the file is `unreadable`.

Three things these checks do not see. A hard link reads as an ordinary file, so
a hard link to a file elsewhere is read; git does not create one. A folder above
the file that another program swaps for a link between the check and the open is
followed. And on Windows, a network file system that gives neither a file's
reparse tag nor its file ID, but does hold symbolic links, could have a file
swapped for a link between the check and the open without the gate seeing it.

In this run the `link-check` matcher looks up a link target only inside the
root: a relative link that leaves the root counts as external, and the search
for a `site/content/docs` folder stops at the root. In every mode, it never
looks up a link that names a place by itself, such as a network share
(`\\host\share`), a drive (`C:/notes.md`) or a `file:` address. On Windows,
looking up a share sends your sign-in to that host. On Windows it also leaves
unchecked a `/docs/` route segment holding a colon, which Windows reads as a
drive, and a link it finds only through a part that ends in a dot or a
space: Windows can drop that ending (`ci.yml.` finds `ci.yml`), so the find
proves nothing. Such a link that finds nothing is reported dead as usual.
On every system, a `/docs/` route with a `.` or `..` segment, such as
`/docs/../x`, counts as external and is not looked up.

Each `git ls-files` call gets 60 seconds: the one this run makes, and the one
in `no-global-plans-grep`, whose report then carries the same `check_error`
and fails; when git itself fails there, its message gives git's exit code,
not git's own text. A repository whose own settings make git wait, such as
an `include.path` that points at a named pipe, holds up each of these calls
for that long at most, on Windows too, where the limit also stops the git
that Git's launcher started. A
`--all-perwrite` run that read no file does not pass: it reports
`files_scanned: 0` with `empty_scope_expected: false`. When the list of tracked
files cannot be read, `check_error` gives a fixed reason: git did not start,
`git ls-files` failed with a given exit code, or it did not finish in
time. To see git's own message, for example when the root is not inside a git
work tree, run `git ls-files` in the root; the report leaves it out, because it
can name files outside the project. With `--strict`, a run that did not pass
exits `2`.

## Targeted checks

```bash
# List every registered validator
PYTHONPATH=src python -m apothem.conformity.gate --list

# Run one per-write validator against one file
PYTHONPATH=src python -m apothem.conformity.gate --check multi-surface-coherence src/apothem/rules/my-rule.md

# Run one standalone validator over a root directory
PYTHONPATH=src python -m apothem.conformity.gate --check naming-grep .

# Run every per-write validator against one file
PYTHONPATH=src python -m apothem.conformity.gate src/apothem/rules/my-rule.md
```

A per-write validator takes the file to check, or `--stdin` to read the content
from standard input; with neither it waits for input on standard input, so pass
the file when you run it from a terminal. A standalone validator takes a root
directory (the current directory when omitted). `--list` shows which group each
validator belongs to.

`--hook` mode (`<python> -E -s .../conformity/gate.py --hook`, where
`<python>` is the interpreter the install found) is the harness-dispatched
entry point: it reads a tool-input JSON payload from stdin and runs the
per-write matcher chain against the pending write. This is the form the
deployed `PreToolUse` hook invokes; you rarely call it by hand.

Hook mode is **scoped to a set of directories**. It runs the matcher chain
only on writes whose target falls under one of them; a write outside every
scope short-circuits to a silent pass. The defaults are two roots:

```text
~/.claude      Claude Code
$CODEX_HOME    Codex (~/.codex when CODEX_HOME is not set)
```

Set `APOTHEM_CONFORMITY_SCOPE` to a directory to replace them:

```bash
# Run the per-write matcher chain against one project tree instead
export APOTHEM_CONFORMITY_SCOPE=/path/to/project
```

A hook that appears to do nothing is usually a scope miss rather than a
failure — check the write's target against the scopes above first.

## CI integration

The quality job in `.github/workflows/ci.yml` runs the gate in strict mode
(`python -m apothem.conformity.gate --all . --strict`) on pushes to `main` and
on pull requests to `main` that touch the paths that job watches. The separate
`.github/workflows/conformity.yml` workflow runs the fixture sweep
(`tests/conformity-scenarios/verify.py --strict`).
