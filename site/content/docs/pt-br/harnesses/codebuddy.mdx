**Fornecedor:** Tencent
**Nome de instalação:** `codebuddy`
**Status:** GA
**Configuração nativa:** `<project>/.codebuddy/rules/apothem-rules.md`

## Instalação

```bash
apothem install --harness codebuddy --project /path/to/project
```

O adaptador grava um único arquivo de regras com escopo de projeto a partir das
regras compartilhadas do Apothem e da superfície de governança.

**Arquivos gravados:** `<project>/.codebuddy/rules/apothem-rules.md`

## Mapeamento do perfil para a configuração nativa

O adaptador lê o perfil compartilhado do Apothem e renderiza o arquivo de regras
do projeto a cada execução de `apothem install` ou `apothem update`. O CodeBuddy
lê cada arquivo `*.md` sob `.codebuddy/rules/` como Markdown com frontmatter
YAML opcional (`alwaysApply`, `paths`, `enabled`), conforme a
[documentação de regras do CodeBuddy](https://www.codebuddy.ai/docs/ide/Rules);
o arquivo do Apothem carrega `alwaysApply: true` para que a superfície de
governança se aplique a cada interação. O frontmatter é o primeiro conteúdo do
arquivo e o bloco gerenciado pelo Apothem vem depois dele; o texto que você
adiciona após o bloco é mantido a cada sincronização. O perfil compartilhado é a
fonte da verdade; as edições locais do projeto no arquivo gerado recebem backup
antes que a próxima sincronização substitua o conteúdo gerenciado pelo Apothem.

## Notas de compatibilidade

A superfície de regras do CodeBuddy tem escopo de projeto sob
`.codebuddy/rules/`. O adaptador grava um arquivo dedicado `apothem-rules.md`
que coexiste com quaisquer arquivos de regras que o operador crie no mesmo
diretório. O arquivo de memória de projeto `CODEBUDDY.md`, o
`.codebuddy/settings.json` e o `.mcp.json` do projeto (servidores MCP) são de
propriedade do operador; o Apothem não os grava. O CodeBuddy também documenta
skills, comandos, subagentes e hooks; o adaptador não grava nenhum deles e, em
vez disso, referencia as disciplinas dentro do arquivo de regras. Quando um
projeto não tem `CODEBUDDY.md`, o CodeBuddy Code lê `AGENTS.md` como memória de
projeto, de modo que um `AGENTS.md` gravado por outro adaptador também chega ao CodeBuddy. As convenções da superfície do fornecedor das quais o
adaptador depende estão fixadas em
`src/apothem/harnesses/codebuddy/STANDARD-CONVENTION-PIN.md`, com snapshot feito
contra a documentação ao vivo do CodeBuddy.

## Verificação

```bash
apothem verify --harness codebuddy --project /path/to/project
```

O comando verify confirma que:

1. A configuração nativa existe no caminho esperado.
2. O arquivo de regras gerenciado está presente e não está vazio.
3. A rotina de verificação específica do adaptador relata sucesso.

## Atualização

```bash
apothem update --harness codebuddy --project /path/to/project
```

Deriva novamente o arquivo de regras do projeto a partir do estado atual do
perfil compartilhado. `install` e `update` são idempotentes — executá-los
novamente sobrescreve o arquivo gerenciado com o conteúdo renderizado mais
recente.

## Desinstalação

```bash
apothem uninstall --harness codebuddy --project /path/to/project
```

Remove o bloco do Apothem de `apothem-rules.md` e mantém qualquer outro texto que haja nele. O arquivo só é excluído quando nada mais permanece nele. Antes da mudança, uma cópia com carimbo de data e hora do arquivo é salva em `~/.apothem/backups/`; nenhum arquivo de backup fica no projeto. O YAML do perfil compartilhado e o motor do Apothem não são afetados.

```bash
python -m apothem.conformity.gate --all .
```

## Solução de problemas

| Sintoma | Correção |
|---------|-----|
| Arquivo de configuração não encontrado | Execute novamente `apothem install --harness codebuddy --project /path/to/project` |
| Falha na verificação | Execute `apothem update --harness codebuddy --project /path/to/project` e depois verifique novamente |
| Conteúdo de configuração inesperado | Verifique `~/.config/apothem/profile.yaml` ou `--profile PATH` e depois execute novamente `apothem update --harness codebuddy --project /path/to/project` |
