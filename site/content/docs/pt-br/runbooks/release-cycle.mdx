Este runbook conduz um lançamento `vX.Y.Z` do `apothem` de uma árvore de
trabalho limpa até superfícies de distribuição verificadas. O procedimento é
escrito para o mantenedor que maneja `gh`, `git` e o shell de nível de
lançamento; ele termina com uma página de Release verificada, um CHANGELOG
registrado e um teste de fumaça da rota de instalação que confirma que cada
superfície voltada ao usuário responde ao comando de instalação canônico.

O modelo de lançamento é **aditivo**. Cada lançamento adiciona um commit em
`main` e uma tag `vX.Y.Z` assinada e anotada; nada recebe force-push e nenhuma
tag, GitHub Release ou versão do npm anterior é removida. O projeto tem três
lançamentos, cada um com sua tag, seu GitHub Release e sua versão do npm, e
todos permanecem publicados: as versões do npm são imutáveis (um `name@version`
publicado nunca pode ser substituído), e as instalações fixadas dependem das
tags.

O push da tag inicia dois fluxos de trabalho. `.github/workflows/release.yml`
compila, assina, atesta e publica o GitHub Release com seu conjunto completo de
artefatos: sdist, wheel, SBOM CycloneDX, bundles cosign do Sigstore, procedência
SLSA-3 e os arquivos de runtime de cada plataforma. `publish-npm.yml` publica
`@ahmed-g-gad/apothem` no npmjs.com por meio da publicação confiável do npm. A
seção versionada do CHANGELOG entra no commit de lançamento; o operador executa
o teste de fumaça da rota de instalação depois que ambos os fluxos de trabalho
terminam.

## 1. Pré-requisitos

O mantenedor confirma o seguinte antes de marcar a tag:

- **Árvore de trabalho.** Limpa (`git status` não mostra nada pendente). Todo o
  trabalho de funcionalidades do lançamento está em `main`.
- **CI em verde.** No `main` mais recente, `gh run list --branch=main --limit=1
  --json conclusion --jq '.[0].conclusion'` retorna `success`.
- **Ferramentas.** `gh` (GitHub CLI) versão 2.40 ou posterior autenticado em
  `ahmed-g-gad`; `git` 2.40 ou posterior com a subchave de assinatura GPG
  carregada; o vínculo de publicador confiável do npm para `@ahmed-g-gad/apothem`
  está ativo (verificado conforme o
  [runbook de configuração da conta de publicador](/docs/runbooks/publisher-account-setup)).
- **Âncoras de versão alinhadas.** A string de versão declarada em
  `pyproject.toml` corresponde à tag planejada sem o prefixo `v`
  (a §2.1 a define, junto com todas as outras âncoras). Verifique:

  ```bash
  grep '^version' pyproject.toml
  ```

  Saída esperada (para um lançamento `vX.Y.Z`; os marcadores de posição representam a tag do lançamento em andamento):

  ```text
  version = "X.Y.Z"
  ```

- **Entradas do CHANGELOG preparadas.** Os itens do lançamento ficam em
  `## [Unreleased]`, nos cabeçalhos do Keep-a-Changelog; a §2.1 os transforma na
  seção de versão datada no commit em que a tag é aplicada.

## 2. Marcar a tag e disparar

### 2.1 Redigir o commit de lançamento

A versão fica em mais de uma dúzia de arquivos, então não os edite à mão. Um
único comando altera todos eles:

```bash
git checkout main
git pull --ff-only origin main
python scripts/release/bump_version.py X.Y.Z
```

`bump_version.py` atualiza todas as âncoras de versão juntas:

- Todos os manifestos de empacotamento, extensão, plugin e marketplace, além do
  arquivo de citação (versão e data de lançamento). A lista completa:

  ```text
  pyproject.toml
  package.json
  site/package.json
  site/package-lock.json            (the project entries only)
  vscode-extension/package.json
  gemini-extension.json
  qwen-extension.json
  .claude-plugin/marketplace.json   (top level and metadata)
  plugins/apothem/.codex-plugin/plugin.json
  src/apothem/harnesses/antigravity/templates/plugin.json
  CITATION.cff
  ```

- `CHANGELOG.md`: as entradas de `[Unreleased]` se tornam uma seção
  `## [X.Y.Z]` datada, `[Unreleased]` passa a comparar a partir de `vX.Y.Z`, e
  um link `[X.Y.Z]` é adicionado.
- `SECURITY.md`: uma nova versão menor ganha uma linha `X.Y.x` suportada. Se as
  versões menores mais antigas continuam listadas é decisão sua; o script exibe
  um lembrete.

Em seguida, ele regenera as árvores derivadas: o pacote do plugin do Claude
Code, os goldens de diff de comportamento e as páginas de referência e de
changelog da documentação. Passe `--dry-run` para listar as mudanças primeiro,
`--date
YYYY-MM-DD` para definir a data de lançamento (padrão: hoje em UTC), ou
`--no-regen` para pular a regeneração. O script recusa uma versão malformada ou
um downgrade, e executá-lo novamente com a versão atual apenas realinha âncoras
dispersas.

Revise o diff e depois faça o commit:

```bash
git add -A
git commit -S -m "chore(release): cut vX.Y.Z"
git push origin main
```

O sinalizador `-S` assina o commit com a chave GPG. O push dispara a matriz de
CI padrão (lint, test, build); aguarde o verde antes de marcar a tag.

### 2.2 Assinar e enviar a tag

```bash
git tag -a -s vX.Y.Z -m "vX.Y.Z"
git push origin vX.Y.Z
```

A combinação `-a -s` produz uma tag anotada e assinada com GPG. O push dispara
`.github/workflows/release.yml`, que compila, assina, atesta e publica.

### 2.3 Confirmar que o fluxo de trabalho de lançamento foi concluído

```bash
gh run watch $(gh run list --workflow=release.yml --limit=1 --json databaseId --jq '.[0].databaseId')
```

O fluxo de trabalho executa a compilação (sdist + wheel, depois um SBOM
CycloneDX dessas distribuições gravado ao lado delas), a assinatura cosign sem
chave, a geração e a verificação da procedência SLSA-3, as compilações dos
arquivos de plataforma (darwin / linux / windows), a assinatura dos arquivos com
um manifesto `SHA256SUMS` agregado e a publicação final do GitHub Release. O
mantenedor examina o log do job `publish GitHub Release` em busca das
confirmações de upload dos ativos.

### 2.4 Confirmar a publicação no npm

O push da tag também executa `publish-npm.yml`. Aprove a implantação do ambiente
`release` quando solicitado. O fluxo de trabalho publica
`@ahmed-g-gad/apothem@X.Y.Z` no npmjs.com por meio da publicação confiável do
npm (OIDC); nenhum token de registro é armazenado no repositório. Em seguida,
confirme a prontidão:

```bash
bash scripts/release/check-release-ready.sh vX.Y.Z
```

Para publicar novamente após uma execução com falha, despache o fluxo de
trabalho para a mesma tag (`gh workflow run publish-npm.yml --field tag=vX.Y.Z`).
Ele pula a publicação quando a versão já está no registro, porque as versões do
npm são imutáveis.

## 3. Superfícies de distribuição

Cada superfície tem um comando de verificação que responde "o lançamento
aterrissou aqui?":

| # | Superfície | Artefato | Verificação |
|---|---|---|---|
| 1 | GitHub Release (distribuições Python) | `apothem-X.Y.Z.tar.gz` (sdist) + `apothem-X.Y.Z-py3-none-any.whl` | `gh release view vX.Y.Z --json assets --jq '.assets[].name'` inclui ambos os nomes de arquivo |
| 2 | GitHub Release (SBOM) | `sbom.cdx.json` + `sbom.cdx.json.cosign.bundle` | a lista de ativos inclui ambos; o `metadata.component.purl` do SBOM é `pkg:pypi/apothem@X.Y.Z` e seus componentes incluem todos os pacotes de `src/apothem/_vendor/vendor.txt` |
| 3 | GitHub Release (assinaturas) | um `<asset>.cosign.bundle` por sdist, wheel, SBOM, extensão do VS Code, arquivo de plataforma e `SHA256SUMS` (os lançamentos anteriores nomeiam os bundles dos arquivos e de `SHA256SUMS` como `<asset>.sig`) | `cosign verify-blob` com a identidade exata da §5.5 sai com 0 |
| 4 | GitHub Release (procedência) | `provenance.intoto.jsonl` | `bash scripts/release/verify-provenance.sh <download-dir>` sai com 0 (§5.5) |
| 5 | GitHub Release (arquivos de plataforma) | `apothem-vX.Y.Z-darwin.tar.gz`, `apothem-vX.Y.Z-linux.tar.gz`, `apothem-vX.Y.Z-windows.zip` | a lista de ativos inclui cada arquivo mais `SHA256SUMS`. Os arquivos darwin e linux são os mesmos bytes sob dois nomes (o runtime é neutro em relação à plataforma; `--platform` apenas escolhe entre tar.gz e zip), de modo que suas linhas em `SHA256SUMS` mostram o mesmo digest duas vezes |
| 6 | GitHub Release (extensão do VS Code) | `apothem.vsix` + `apothem.vsix.cosign.bundle` | a lista de ativos inclui ambos; `code --install-extension apothem.vsix` a instala. Os lançamentos anteriores ao empacotamento da extensão pelo fluxo de trabalho de lançamento não trazem nenhum dos dois |
| 7 | npmjs.com | `@ahmed-g-gad/apothem@X.Y.Z` | `npm view @ahmed-g-gad/apothem version` retorna `X.Y.Z`; `npx @ahmed-g-gad/apothem@X.Y.Z --version` imprime `Apothem, version X.Y.Z` |
| 8 | Pages (instaladores de script) | `install.sh` / `install.ps1` no site de documentação | `curl -fsSL https://apothem.ahmedgad.com/install.sh \| head -n 1` retorna o cabeçalho do script |

O GitHub Release é a superfície canônica de artefatos; o pacote do npm e os
instaladores de script são as rotas de instalação sobrepostas a ele. A
publicação no npm é executada ao lado do fluxo de trabalho de lançamento, no
mesmo push da tag.

## 4. Disciplina do CHANGELOG

O `CHANGELOG.md` carrega uma seção por lançamento sob a convenção
Keep-a-Changelog. A edição do CHANGELOG no commit de lançamento:

- Confirma que a seção de versão usa o cabeçalho `## [X.Y.Z] - YYYY-MM-DD`
  (um hífen; `bump_version.py` o escreve, e `extract_release_notes.py`
  corresponde ao prefixo `## [X.Y.Z]`).
- Confirma que os cabeçalhos padrão — Added, Changed, Deprecated, Removed,
  Fixed, Security — são usados onde aplicável. Cabeçalhos vazios são removidos
  do arquivo renderizado.
- Captura **capacidades**, não implementação. Apenas linguagem de domínio; sem
  referências internas ao plano; sem hashes de commit; sem identificadores de
  plano ou de fase.

Uma seção do CHANGELOG que passou pela revisão do mantenedor serve como âncora
das notas de lançamento para a narrativa do anúncio.

## 5. Teste de fumaça da rota de instalação

Depois que ambos os estágios forem concluídos, o mantenedor executa o teste de
fumaça. O teste de fumaça é a verificação canônica de que os comandos de
instalação voltados ao usuário respondem.

### 5.1 Plugin do Claude Code

```text
/plugin marketplace add ahmed-g-gad/apothem
/plugin install apothem@apothem
```

Esperado: o plugin é instalado e os comandos `apothem` ficam disponíveis dentro
do Claude Code.

### 5.2 Node.js (npx)

```bash
npx @ahmed-g-gad/apothem@X.Y.Z --version
```

Saída esperada: `Apothem, version X.Y.Z`.

### 5.3 Instalador de script de um único passo (POSIX)

```bash
curl -fsSL https://apothem.ahmedgad.com/install.sh | sh
apothem --version
```

Saída esperada: `Apothem, version X.Y.Z`.

### 5.4 Instalador de script de um único passo (Windows)

```powershell
irm https://apothem.ahmedgad.com/install.ps1 | iex
apothem --version
```

Saída esperada: `Apothem, version X.Y.Z`.

### 5.5 Verificação de artefatos (evidência da cadeia de suprimentos)

Baixe todos os ativos para um diretório vazio e depois verifique. A identidade
do certificado é o fluxo de trabalho de lançamento nesta tag exata. As
verificações de identidade diferenciam maiúsculas de minúsculas, e os
certificados trazem o proprietário como o GitHub o informa, `Ahmed-G-Gad`, de
modo que um proprietário em minúsculas falha.

```bash
mkdir release-vX.Y.Z && cd release-vX.Y.Z
gh release download vX.Y.Z --repo ahmed-g-gad/apothem
cosign verify-blob \
  --bundle apothem-X.Y.Z-py3-none-any.whl.cosign.bundle \
  --certificate-identity https://github.com/Ahmed-G-Gad/apothem/.github/workflows/release.yml@refs/tags/vX.Y.Z \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  apothem-X.Y.Z-py3-none-any.whl
slsa-verifier verify-artifact \
  --provenance-path provenance.intoto.jsonl \
  --source-uri github.com/Ahmed-G-Gad/apothem \
  --source-tag vX.Y.Z \
  apothem-X.Y.Z-py3-none-any.whl apothem-X.Y.Z.tar.gz
bash ../scripts/release/verify-provenance.sh .
```

Esperado: `Verified OK`, `PASSED: SLSA verification passed` e
`verify-provenance: chain OK (3 of 3 layers verified)`. O script verifica
`SHA256SUMS`, cada bundle de assinatura e a procedência em uma única execução;
ele deriva a tag do nome do wheel (`--tag vX.Y.Z` a substitui).

O teste de fumaça produz uma linha de PASS / FAIL por superfície; registre as
linhas no log de lançamento do mantenedor.

## 6. Recuperação de falhas

O fluxo de trabalho de lançamento tem modos de falha documentados para o motor
de lançamento e o publicador do npm:

| Falha | Diagnóstico | Recuperação |
|---|---|---|
| Push da tag rejeitado (falha de assinatura) | `git push origin vX.Y.Z` retorna `error: failed to push some refs` com uma mensagem relacionada a GPG | Verifique se a subchave GPG está carregada (`gpg --list-secret-keys --keyid-format=long`); marque a tag novamente, localmente, com `-s` depois de corrigir o chaveiro; envie novamente |
| A compilação do lançamento para em `Check the plugin version changed with the plugin` | O log do job de compilação nomeia o plugin e a tag anterior; nenhum ativo foi compilado ou publicado | O pacote do plugin mudou desde o lançamento anterior, mas sua versão não. Exclua a tag (`git push --delete origin vX.Y.Z`, `git tag -d vX.Y.Z`), execute `python scripts/release/bump_version.py X.Y.Z`, faça o commit e então assine e envie a tag novamente (§2.2). A mesma verificação é executada em todo pull request como uma anotação de aviso, então isso normalmente aparece antes de marcar a tag |
| Um job de `release.yml` falha em um único estágio | `gh run view <run-id> --log` nomeia o job que falhou (build, que também grava o SBOM / sign / provenance / archive / publish) | Execute novamente apenas o job que falhou via `gh run rerun <run-id> --failed`; se a falha se repetir, corrija a entrada do job na origem antes de marcar a tag novamente |
| A verificação da procedência SLSA falha | O job `verify SLSA provenance artifact` sai com código diferente de zero | Inspecione o artefato de procedência em busca de incompatibilidade de digest do sujeito; recompile a partir da mesma tag — a procedência se vincula aos digests exatos dos artefatos, então qualquer regeneração de artefatos exige uma reexecução completa do fluxo de trabalho |
| Publicação no npmjs.com rejeitada | O job do npm sai com código diferente de zero durante `npm publish`; um `404` do registro durante `PUT` é uma incompatibilidade de autorização / publicador confiável, não prova de que o código do pacote está ausente | Verifique se o npm Trusted Publishing para `@ahmed-g-gad/apothem` nomeia o proprietário `ahmed-g-gad`, o repositório `apothem`, o fluxo de trabalho `publish-npm.yml` e a ação permitida `npm publish`; confirme que o job é executado com a versão do Node e o piso OIDC da CLI do npm fixados no fluxo de trabalho |
| Tag visível, mas ativos ausentes | `gh release view vX.Y.Z` retorna um lançamento vazio | Execute novamente o job de publicação do fluxo de trabalho de lançamento; ele edita o lançamento existente e reenvia todos os ativos. Exclua a tag e marque-a novamente somente quando nada da tag tiver chegado aos usuários (nenhum ativo, nenhuma versão do npm); caso contrário, corrija para frente com o próximo lançamento de patch ([runbook de recuperação de lançamento](/docs/runbooks/release-recovery) §2) |

Se um ciclo de recuperação não conseguir aterrissar uma superfície em um único
passe de diagnóstico, a superfície é registrada como uma falha conhecida nas
notas de lançamento, com um link para a issue aberta; os usuários a jusante são
direcionados às superfícies que funcionam enquanto a quebrada é corrigida em um
lançamento de patch.

## 7. Referências cruzadas

- **Configuração do publicador.** O
  [runbook de configuração da conta de publicador](/docs/runbooks/publisher-account-setup)
  estabelece o vínculo de publicador confiável do npm e os pré-requisitos do
  lado do GitHub que este runbook pressupõe.
- **Fluxo de recuperação.** O [runbook de recuperação de lançamento](/docs/runbooks/release-recovery)
  segue o mesmo modelo aditivo: ele recupera uma tag ou um estágio de publicador
  com falha, estágio por estágio, e faz a reversão lançando a correção como uma
  nova versão de patch, nunca excluindo ou redirecionando uma tag, um lançamento
  ou uma versão do npm publicados.
- **Habilitação do Pages.** O fluxo de trabalho `publish-static-site.yml`
  valida e implanta o site do projeto no domínio personalizado; o runbook de
  habilitação do Pages (`site/content/docs/runbooks/pages-enablement.mdx`)
  é o procedimento anterior que estabeleceu o domínio personalizado em
  primeiro lugar.
- **Política de versionamento.** `site/content/docs/governance/release-engineering-policy.mdx`
  contém a política de SemVer + assinatura + descontinuação que este runbook
  respeita.
