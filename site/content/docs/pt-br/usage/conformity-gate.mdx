O conformity gate em `src/apothem/conformity/gate.py` executa a
fração mecânica do portão de pré-emissão de quinze barras (M1-M15)
contra cada artefato que o operador redige.

Os comandos desta página pressupõem um checkout do Apothem, então prefixe com
`PYTHONPATH=src` cada um que você executar. Após uma instalação por script, use
`PYTHONPATH="$HOME/.apothem/src"` no lugar de `PYTHONPATH=src`.

## Executar o portão

O portão é **consultivo por padrão**: ele relata os achados e sai com `0`, de
modo que uma execução local nunca bloqueia você. Adicione `--strict` (ou defina
`APOTHEM_CONFORMITY_STRICT=1`) para sair com código diferente de zero diante de
um achado bloqueante — o modo que o CI e o pre-commit usam para fazer falhar uma
mudança que viola as regras.

```bash
# Advisory: report every validator's findings across the repo, exit 0
PYTHONPATH=src python -m apothem.conformity.gate --all .

# Strict: exit non-zero (code 2) when a blocking finding is present
PYTHONPATH=src python -m apothem.conformity.gate --all --strict .
```

Códigos de saída: `0` limpo (ou consultivo), `2` um bloqueio por achados no modo
estrito, `3` um erro de uso: um sinalizador ou nome de validador desconhecido,
um arquivo que não existe ou um diretório raiz que não existe. `--help` imprime
o uso completo e sai com `0`. Todo validador independente aceita o mesmo
`--help` e sai com `3` diante de um sinalizador desconhecido ou de uma raiz
ausente.

Uma raiz relativa como `.` é resolvida para um caminho absoluto antes que
qualquer validador seja executado, de modo que `--all .` e `--all "$PWD"`
inspecionam a mesma árvore. Cada validador relata `inspected` — quantos alvos
ele examinou — e `--all` copia essa contagem para cada entrada de resultado. Um
validador que não inspecionou nada relata `passed: false`, de modo que um
diretório de trabalho errado não pode passar silenciosamente. Os dois
validadores de suíte de planejamento são uma exceção: as suítes de planejamento
ficam na árvore `.apothem/plans/`, ignorada pelo git, então eles relatam
`empty_scope_expected: true` em um checkout limpo e ainda assim passam. Os
validadores de fluxo de trabalho fazem o mesmo quando o projeto ainda não tem um
diretório `.github/workflows/`, e o validador de assunto de commit faz o mesmo
quando a raiz não tem histórico de commits.

Um projeto pode chegar com arquivos que outra pessoa criou, em um arquivo
compactado ou em uma pasta compartilhada, então cada validador do `--all` abre
e lista apenas arquivos comuns e pastas reais que alcança por meio de pastas
reais abaixo da raiz. Ele nunca segue um link simbólico nem, no Windows, uma
junção (junction), e em qualquer nível abaixo da raiz trata cada um destes
itens como ausente:

- um link, mesmo um que aponta para dentro da raiz. Uma varredura ou uma
  listagem de pasta o ignora, então o destino só é verificado onde o validador
  o alcança pelo próprio caminho;
- um pipe nomeado, um dispositivo ou um socket, em que uma leitura esperaria ou
  nunca terminaria;
- no Windows, um nome que termina em ponto ou espaço, porque o Windows abriria
  outra entrada com esse nome.

Algumas verificações ainda usam um link sem entrar nele:

- para um arquivo fixo que é um link simbólico, como um `CLAUDE.md` que aponta
  para outro arquivo, o gate lê o texto do próprio link e abre o arquivo
  indicado apenas quando ele é um arquivo comum dentro do projeto, alcançado
  por pastas reais. Um link `README.md` por pasta conta da mesma forma. Um link
  absoluto conta quando é escrito através da pasta do projeto como ela se
  resolve, ou no Windows através do mesmo caminho com outra combinação de
  maiúsculas e minúsculas; um validador executado sozinho também aceita a
  pasta como você a digitou, a menos que esse caminho contenha `..`, enquanto o
  gate resolve a pasta antes de iniciar cada validador. Um `.gitattributes`
  vinculado ainda conta como ausente, porque o git não o lê;
- a verificação de planos soltos do `no-global-plans-grep` relata pelo nome uma
  pasta de planos ou uma pasta `.apothem` que é um link, para onde quer que o
  link leve;
- `no-toplevel-docs-grep` relata pelo nome um link `docs` na raiz;
- `naming-grep` verifica o próprio nome de um link.

O relatório de cada validador lista em `skipped_links` os links e arquivos
especiais que deixou de fora, então um link nunca esconde um arquivo sem deixar
rastro. Ele também lista ali uma pasta que não conseguiu listar (sem acesso, um
caminho longo demais, um erro de leitura) e a entrada `.git` de uma pasta que
ignorou como checkout aninhado quando essa entrada é um link ou um arquivo
especial; a própria pasta é listada em `skipped_checkouts`, descrito abaixo.
Um validador que passa quando sua pasta está ausente, como os
validadores de workflows, não passa quando essa pasta é um link: os arquivos
podem estar atrás dele, então a execução falha como uma que não verificou nada.
Um link físico é um arquivo comum e é lido como tal. Os validadores do `--all` e
o `--all-perwrite` olham cada nível quando o alcançam e depois abrem o arquivo
nível por nível a partir da raiz, cada pasta dentro da que foi aberta antes,
nunca através de um link. Então, quando alguém que pode escrever no projeto
troca um arquivo já verificado, ou uma pasta acima dele, por um link ou um pipe
nomeado enquanto o gate roda, o gate não lê através do link nem espera no pipe:
o arquivo não é lido. Um validador do `--all` o conta como ausente ou ilegível,
como conta um link, e lista a entrada trocada em `skipped_links`; o
`--all-perwrite` o conta como `link`, ou como `unreadable` quando é trocado de
novo, como descrito abaixo. No Windows resta uma espera, como já acontecia ao
abrir o arquivo do jeito comum: um programa que pode escrever no projeto pode
manter um bloqueio oportunista (oplock) sobre um arquivo e não soltá-lo quando o
gate o abre. Nenhuma forma de abrir o arquivo evita essa espera, então um
validador do `--all` espera até seu limite de 10 minutos, e o `--all-perwrite`,
que não tem esse limite, até que esse programa o solte.
No `--all` e no `--all-perwrite`, o próprio
gate abre apenas arquivos comuns dentro da raiz, verifica cada pasta no caminho
com `lstat`, incluindo cada caminho que o git lista, e nunca lê dentro de uma
entrada `.git`. Antes de executar o git, os três validadores do `--all` que
executam o git, e as duas verificações `--staged`, olham com `lstat` a entrada
`.git` da raiz e de cada pasta acima dela em que o git procura, como a árvore
está naquele momento; se alguma delas for um link, ou não puder ser olhada, eles
não executam o git. Isso também recusa projetos que o git trataria com
segurança, como todo projeto abaixo de uma pasta pessoal cujo `.git` é um link,
mesmo um com repositório próprio: esse é o custo deliberado de uma regra
simples. Os três validadores do `--all` executam o git sem `GIT_DIR` e as outras
variáveis que nomeiam o repositório, seus armazenamentos ou seu índice; as
verificações `--staged` mantêm o `GIT_DIR` de um hook. Qual repositório o git lê
depois não é verificado: uma linha `gitdir:`, `commondir`, alternates,
`core.worktree`, um include ou um link dentro da pasta do git podem nomear
outro, e o git os segue, então o git pode alcançar um caminho de rede ou esperar
até o seu limite de tempo. O gate usa a saída do git apenas como nomes, modos,
letras de status, o assunto do último commit, horários de commit e algumas
configurações, e nunca abre um caminho que o git imprime sem verificar cada
nível dentro da raiz. Quando um link é encontrado, cada um dos três validadores
do `--all` o lista em `skipped_links` (relativo à raiz quando está dentro dela,
pelo caminho completo quando está acima). O `conventional-commit-grep` então
relata `not-a-git-repo`, como fora de um checkout, mas não passa: ele dá um
`check_error` que nomeia o link. O `no-global-plans-grep` relata o link como
achado e falha, e a verificação de arquivos companheiros pula seu teste de
atualidade, como faz sem histórico. O `--all-perwrite` também não lista os
arquivos rastreados: ele falha com um `check_error` que nomeia o link, assim
como as duas verificações `--staged`, que nomeiam um link apenas no
`check_error`, ou dizem ali que a entrada `.git` da pasta em que rodam é um
link: elas leem o repositório que o `GIT_DIR` de um hook nomeia, mas ainda
recusam um link no caminho de busca a partir da pasta em que rodam. Uma entrada
`.git` que o gate não consegue olhar (um caminho longo demais, um
compartilhamento inalcançável, sem acesso) não é um link e não aparece em
`skipped_links`: o `conventional-commit-grep` falha com o status `git-failed` e
um `check_error`; a verificação de arquivos companheiros, o `--all-perwrite` e
as duas verificações `--staged` falham com um `check_error` que diz que a
entrada não pôde ser olhada, e o `no-global-plans-grep` a relata como achado.

Seis validadores partem da raiz do repositório e buscam em toda a árvore os
arquivos que verificam:

```text
agents-md-coverage-grep
agnosticism-grep
dynamism-grep
freshness-token-grep
plain-language-grep
reference-token-grep
```

Eles ignoram checkouts git aninhados, como worktrees, submódulos e clones
aninhados (uma pasta cujo arquivo ou pasta `.git` contém ou nomeia um
repositório; um arquivo `.git` simples ou uma pasta `.git` vazia não oculta sua
pasta), e ignoram diretórios que guardam dependências, ambientes virtuais,
caches ou saída de build, como `node_modules`, `venv` e `dist`. A verificação de
planos perdidos em `no-global-plans-grep` também para em um checkout aninhado.
Toda pasta ignorada como checkout aninhado é listada no relatório em
`skipped_checkouts`, seja o que for que sua entrada `.git` nomeie, já que uma
única linha `gitdir:` pode fazer o git ignorar qualquer pasta. A lista nunca
muda o veredito, e uma pasta ignorada assim não é verificada; pastas ignoradas
pelo nome, como `node_modules`, não são listadas. Uma execução de qualquer um deles relata sobre o checkout para o
qual foi apontada e sobre nada mais. Um validador que lê uma pasta fixa, como
`naming-grep` sob `src/apothem/`, lê tudo abaixo dessa pasta.

## Verificações direcionadas

```bash
# List every registered validator
PYTHONPATH=src python -m apothem.conformity.gate --list

# Run one per-write validator against one file
PYTHONPATH=src python -m apothem.conformity.gate --check multi-surface-coherence src/apothem/rules/my-rule.md

# Run one standalone validator over a root directory
PYTHONPATH=src python -m apothem.conformity.gate --check naming-grep .

# Run every per-write validator against one file
PYTHONPATH=src python -m apothem.conformity.gate src/apothem/rules/my-rule.md
```

Um validador por gravação recebe o arquivo a verificar, ou `--stdin` para ler o
conteúdo da entrada padrão; sem nenhum dos dois, ele espera por entrada na
entrada padrão, então passe o arquivo ao executá-lo a partir de um terminal. Um
validador independente recebe um diretório raiz (o diretório atual, quando
omitido). `--list` mostra a qual grupo cada validador pertence.

O modo `--hook` (`python -m apothem.conformity.gate --hook`) é o ponto de
entrada despachado pelo harness: ele lê um payload JSON de entrada de
ferramenta da stdin e executa a cadeia de matchers por gravação contra a
gravação pendente. Essa é a forma que o hook `PreToolUse` implantado invoca;
raramente você o chama manualmente.

O modo hook tem **escopo limitado a um conjunto de diretórios**. Ele executa a
cadeia de matchers apenas em gravações cujo alvo esteja sob um deles; uma
gravação fora de todos os escopos é encerrada antecipadamente com uma aprovação
silenciosa. Os padrões são duas raízes:

```text
~/.claude      Claude Code
$CODEX_HOME    Codex (~/.codex when CODEX_HOME is not set)
```

Defina `APOTHEM_CONFORMITY_SCOPE` como um diretório para substituí-las:

```bash
# Run the per-write matcher chain against one project tree instead
export APOTHEM_CONFORMITY_SCOPE=/path/to/project
```

Um hook que parece não fazer nada geralmente é um caso de alvo fora do escopo, e
não uma falha — verifique primeiro o alvo da gravação em relação aos escopos
acima.

## Integração com CI

O job de qualidade em `.github/workflows/ci.yml` executa o portão em modo
estrito (`python -m apothem.conformity.gate --all . --strict`) em pushes para
`main` e em pull requests para `main` que alterem os caminhos que esse job
monitora. O fluxo de trabalho separado `.github/workflows/conformity.yml`
executa a varredura de fixtures (`tests/conformity-scenarios/verify.py --strict`).
