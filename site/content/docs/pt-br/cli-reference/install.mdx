Instala a configuração de um adaptador de harness a partir do perfil compartilhado.

## Sinopse

```
apothem install --harness NAME|all [--profile PATH] [--dry-run]
                 [--clean|--fresh] [--yes] [--project PATH]
                 [--quiet|-q] [--verbose|-v]
                 [--format plain|json] [--json] [--no-color]
```

Carrega e valida o perfil compartilhado, seleciona um adaptador nomeado ou o
conjunto `all` de todo o registro, valida o plano de materialização e grava a
configuração nativa do harness mais os cohorts de suporte. Os adaptadores com
escopo de projeto exigem `--project PATH`. A pasta é lida com seus links seguidos
e `~` expandido, e o registro de instalação a nomeia dessa forma. Uma instalação
registrada sob outra grafia da pasta, como um link que um código Python ou um
lançamento anterior manteve, é movida para essa grafia assim que a instalação
passa nas suas verificações (consulte [`uninstall`](/docs/cli-reference/uninstall)).

O alias na forma contínua `apothem installing` (também aceito como
`apothem Installing`) resolve para o mesmo manipulador.

## Primeira execução sem um perfil

Quando `--profile` é omitido e não existe nenhum perfil no caminho padrão
(`~/.config/apothem/profile.yaml`), `install` primeiro grava ali o perfil
inicial, imprime `Created a starter profile at <path>` e continua. O perfil
inicial carrega campos de identidade com marcadores de posição, então a
instalação também imprime a nota sobre a identidade com marcadores de posição;
personalize o perfil e depois execute [`update`](/docs/cli-reference/update)
para aplicá-lo. Com `--json`, a criação é relatada como uma entrada de
`warnings` com `"operation": "profile_created"`.

- `--dry-run` nunca grava o perfil: a prévia usa o perfil inicial em memória e
  relata `"operation": "profile_scaffold_preview"`.
- Um `--profile PATH` explícito que não existe nunca é criado; o comando sai com
  o código 1 e `profile.not_found`.

## Prévia do raio de impacto

`install --harness all` se ramifica em escopos mistos: os adaptadores com escopo
de projeto gravam sob a raiz informada em `--project`, enquanto os adaptadores com
escopo de usuário gravam sob o seu diretório pessoal — fora dessa raiz. Antes que
a instalação grave qualquer arquivo, o comando imprime os destinos concretos
agrupados sob dois títulos: os que ficam dentro da raiz do projeto e os que ficam
sob o seu diretório pessoal. Um terceiro título lista as pastas compartilhadas
no seu diretório pessoal que os adaptadores com escopo de projeto gravam, fora de
`--project`: a pasta de skills e `~/.config/apothem/` (consulte
[Pastas no seu diretório pessoal](#pastas-no-seu-diretório-pessoal)). A única
exceção é `--clean`: a etapa de limpeza completa roda antes desta prévia e grava
um backup e remove os destinos anteriores, como descrito abaixo.

Quando a seleção grava fora da raiz do projeto, seja na pasta de um adaptador
com raiz no diretório pessoal ou em uma pasta compartilhada, uma confirmação
interativa protege as gravações com raiz no diretório pessoal. `--yes`, um shell não
interativo (sem TTY), `--dry-run` e `--format json` prosseguem, cada um, sem
perguntar. Somente `--dry-run` não grava nada; `--format json` pula a prévia e o
prompt de confirmação, mas ainda realiza as gravações. Recusar o prompt do
diretório pessoal aborta a operação antes que a instalação grave. Com
`--clean`, a etapa de recomeço limpo é executada primeiro, sob uma confirmação
própria para cada destino: ela grava um backup em `~/.apothem/backups` e remove
os destinos que confirma. Essas remoções e o backup permanecem no lugar quando o
prompt de instalação é recusado.
Os destinos são as pastas de ferramentas no seu diretório pessoal que o prompt
lista, entre elas `~/.agents` e `~/.config/apothem`.
Um destino que é ele próprio um link, incluindo uma junção do Windows, perde
apenas o link, e um link dentro de um destino é removido sem que se entre nele.
Quando `~/.config` é um link que leva para fora do seu diretório pessoal, a etapa
de recomeço limpo para com `Clean-slate removal was refused` antes de fazer backup
ou remover qualquer coisa, já que remover `~/.config/apothem` excluiria a pasta
na outra ponta desse link. O erro nomeia o link: substitua-o por uma pasta real ou
faça-o levar a uma pasta dentro do seu diretório pessoal. A etapa também para
antes de alterar qualquer coisa, e antes de criar o perfil inicial, quando o seu
diretório pessoal não é um caminho completo, é a raiz de uma unidade ou de um
sistema de arquivos, é um link ou uma junção que leva a uma delas, ou é alcançado
através de um link que forma um ciclo.

A etapa de recomeço limpo remove o perfil padrão,
`~/.config/apothem/profile.yaml`, junto com `~/.config/apothem`, e o grava de
volta depois. Um perfil que ela não removeu, como um que você passa com
`--profile PATH` a partir de outra pasta, não é gravado. A gravação de volta segue
a mesma regra de todas as outras gravações de perfil: ela é recusada quando um
link a levaria para fora do seu diretório pessoal. Quando o perfil não pode ser
gravado de volta, o comando sai com 1 e o erro nomeia a cópia de backup que o
contém. O código de erro é `clean_slate.profile_restore_refused` quando um link
recusou a gravação, e `clean_slate.profile_restore_failed` quando a própria
gravação falhou. Quando uma remoção para no meio do caminho, por exemplo em um
arquivo que outro programa mantém aberto, o perfil é gravado de volta primeiro. O
comando então sai com 1 com o código de erro `clean_slate.removal_failed`, e o
erro nomeia a pasta de backup. Se o perfil não puder ser gravado de volta, o erro
é, em vez disso, um dos dois códigos de perfil acima.

## Pastas no seu diretório pessoal

Sete adaptadores com escopo de projeto gravam as skills do Apothem, e as regras e
os templates que as skills citam, em pastas no seu diretório pessoal:

```text
cursor, github-copilot, windsurf, zed  ->  ~/.agents/skills/ (codex writes it too)
codebuddy                               ->  ~/.codebuddy/skills/
kiro                                    ->  ~/.kiro/skills/
trae                                    ->  ~/.trae/skills/
all seven                               ->  ~/.config/apothem/rules/ and templates/ (codex uses them too)
```

- `--project` seleciona o arquivo de regras e o projeto ao qual a instalação
  pertence. Ele não altera para onde vão as skills: uma instalação com
  `--project A` e outra com `--project B` gravam as mesmas pastas.
- Toda instalação que nomeia uma pasta grava os mesmos arquivos. Uma segunda
  instalação os encontra e relata `unchanged`, e a ordem em que você instala não
  importa.
- As pastas do diretório pessoal são gravadas antes de qualquer coisa no projeto.
  Se uma gravação ali falhar, a instalação do adaptador para com o erro e o
  projeto permanece inalterado. O erro nomeia o caminho que está obstruindo, por
  exemplo um arquivo chamado `~/.agents` onde a pasta deveria estar.
- Cada pasta de skill é gravada em uma pasta oculta `.<name>.apothem-staging` ao
  lado dela e renomeada para o lugar quando concluída, de modo que uma gravação
  com falha ou interrompida nunca deixa uma pasta de skill gravada pela metade
  sob o seu nome final. Execute a instalação novamente para concluir; ela
  substitui uma pasta de staging que tenha sobrado.
- Um link em uma dessas pastas ou acima dela, como os que os gerenciadores de
  dotfiles criam para `~/.config` ou `~/.agents`, é seguido quando leva a algum
  lugar dentro do seu diretório pessoal. No Windows, uma junção conta como um
  link. Um link que sai do seu diretório pessoal interrompe a instalação com
  `target escapes the
  allowed materialization root`, seguido do link, da pasta para a qual ele leva
  e da correção: substituir o link por uma pasta real. Uma pasta de skill que é
  ela própria um link nunca é gravada através dele: a instalação a ignora com um
  aviso, ou para quando o Apothem já gravou essa skill ali antes. Um link dentro
  de uma pasta de skill que o Apothem gravou é substituído por uma pasta na
  próxima vez que a instalação grava essa skill.
- Uma pasta de harness abaixo de `~/.config`, como `~/.config/opencode/` do
  OpenCode ou um `CODEX_HOME` ali, também segue um link em `~/.config` que leva a
  algum lugar dentro do seu diretório pessoal. Um link em `~/.config` que sai do
  seu diretório pessoal interrompe a instalação antes que ela grave qualquer
  arquivo, assim como um link em um caminho que a instalação grava dentro da
  pasta do harness. Em uma primeira execução, o perfil inicial, também abaixo de
  `~/.config`, também não é gravado através de um link que sai do seu diretório
  pessoal: a execução para com `Apothem could
  not create the starter profile`, como fazem `apothem quickstart`, `apothem profile
  init`, `apothem profile set` e `apothem profile edit`. Para manter o perfil fora
  do seu diretório pessoal, crie-o lá primeiro com `apothem
  profile init --profile PATH`, escrevendo PATH como o próprio caminho dele fora
  do seu diretório pessoal, e passe o mesmo `--profile PATH` a cada comando. Isso
  só faz passar da etapa do perfil: uma instalação que grava abaixo de
  `~/.config` ainda para no link. Para o OpenCode, defina também
  `XDG_CONFIG_HOME` (consulte [OpenCode](/docs/harnesses/opencode)). Um harness
  cuja instalação sempre grava `~/.config/apothem/` precisa que o link leve para
  dentro do seu diretório pessoal; a página do harness diz isso.
- Uma pasta pessoal que é ela própria um link, como um perfil de usuário do
  Windows movido para outra unidade por trás de uma junção, é seguida: toda
  gravação permanece dentro da pasta para a qual ela leva.
- A instalação não adiciona nenhum arquivo de skill ou de regra ao seu
  repositório. O projeto recebe o arquivo de regras do adaptador, mais a pasta de
  dados `.apothem/` que toda instalação de projeto cria.
- Uma pasta de skill que tem o nome de uma skill do Apothem e que o Apothem não
  gravou é ignorada. A instalação imprime uma linha `Warning:` e o envelope
  `--format json` carrega uma entrada de `warnings` com `"outcome": "warning"` e
  `"operation": "skill_conflict"` que nomeia a pasta. Renomeie ou mova a pasta e
  depois execute [`update`](/docs/cli-reference/update).
- Esta regra cobre todas as pastas de skills compartilhadas da tabela acima:
  `~/.agents/skills/`, `~/.codebuddy/skills/`, `~/.kiro/skills/` e
  `~/.trae/skills/`. Um registro de instalação mostra que uma pasta de skill ali é
  do Apothem enquanto a pasta de instalação dele (um projeto ou um `CODEX_HOME`)
  estiver ativa: ela existe e ainda contém um dos arquivos que essa instalação
  registrou nela, com o conteúdo do Apothem. Um arquivo que pertence ao Apothem
  conta enquanto existir. Um arquivo que é seu, como um arquivo de instruções ao
  qual o Apothem adicionou o bloco dele, conta apenas enquanto ainda contiver esse
  bloco ou, para um arquivo sem bloco, o conteúdo que o Apothem registrou, de modo
  que um projeto clonado novamente que mantém apenas a sua própria cópia do
  arquivo não está ativo. Os arquivos de suporte que uma instalação grava sob
  `.apothem/support/` contam; os armazenamentos de dados sob `.apothem/`
  (memória, contextos, planos) não contam, nem um arquivo alcançado através de um
  link dentro da pasta de instalação.
- Qualquer outro registro, cuja pasta de instalação não existe mais, não contém
  arquivos do Apothem ou não pode ser lida (uma unidade ou um compartilhamento de
  rede que não responde, um erro de permissão), mostra que uma pasta de skill é
  do Apothem apenas enquanto essa pasta contiver exatamente os arquivos que essa
  instalação registrou, inalterados, sem nenhum arquivo adicionado e nenhum link
  dentro. Uma pasta que já contém o que este lançamento grava é mantida como
  está, de modo que uma pasta não editada gravada por um lançamento anterior não
  é afetada enquanto ainda corresponder ao que este lançamento grava.
- As próprias pastas compartilhadas nunca contam como arquivos de uma pasta de
  instalação, de modo que um projeto instalado na pasta pessoal não está ativo
  só porque `~/.agents/skills/` ou `~/.config/apothem/` existe.
- Assim, quando apenas registros desse tipo listam uma pasta de skill, a
  instalação a ignora e a deixa intacta em três casos: você colocou sua própria
  skill ali, você a editou (alterou, adicionou ou removeu um arquivo), ou um
  lançamento anterior que não registrava seus arquivos a gravou e este lançamento
  grava algo diferente. O mesmo vale quando apenas uma instalação anterior na
  mesma pasta a listou: uma instalação que ignorou a pasta não a lista, e ela
  continua não comprovada a menos que contenha exatamente os arquivos que essa
  instalação anterior registrou.
  O aviso da instalação, da atualização e da simulação dá a causa e os dois
  caminhos a seguir, com as mesmas palavras que o [`verify`](/docs/cli-reference/verify),
  que relata o harness como não
  verificado e nomeia essas pastas. Para manter sua skill, deixe-a ali. Para usar
  a versão do Apothem, mova a pasta para fora da pasta de skills e depois execute
  [`update`](/docs/cli-reference/update) para esse harness (com `--project`
  para um com escopo de projeto).
- Toda instalação, atualização e simulação desse tipo imprime uma `Note:` que
  nomeia as pastas que grava fora de `--project`. No envelope JSON, ela é uma
  entrada de `warnings` com `"operation": "user_level_write"` e uma lista `paths`.

## Notas sobre capacidades

Cada adaptador projeta apenas as capacidades que o seu harness suporta
nativamente; as capacidades sem superfície nativa são relatadas, e não
descartadas silenciosamente. No modo plain, isso é uma única nota agrupada por
harness (por exemplo,
`Note: <harness> - 9 capabilities not projected; pass --verbose for detail`);
com `--verbose`, cada capacidade imprime sua própria linha de justificativa.
Qualquer outro aviso de adaptador também é impresso em sua própria linha
`Warning:` no modo plain, por exemplo o aviso do Zed que nomeia um arquivo de
instruções que o novo `.rules` oculta, e o aviso que nomeia um arquivo que contém
um marcador BEGIN do Apothem sem END depois dele: a instalação mantém o texto
depois desse marcador e grava o bloco do Apothem separado dele, então o aviso
nomeia a linha do marcador, dá passos numerados que alteram essa linha e todas as
outras linhas de marcador BEGIN, exceto a que abre o bloco do Apothem (incluindo
um marcador BEGIN que você cita em código), e diz para não adicionar de volta o
marcador END, o que
deixaria então dois blocos do Apothem (consulte
[Resolução de problemas](/docs/install/troubleshooting#a-file-has-an-apothem-begin-marker-with-no-end-marker)).
O mesmo fazem o aviso para um arquivo que contém dois ou mais blocos inteiros
entre os marcadores do Apothem, que nomeia cada bloco pelas suas linhas (consulte
[Um arquivo contém dois blocos entre os marcadores do Apothem](/docs/install/troubleshooting#a-file-holds-two-blocks-between-apothems-markers)),
e o aviso para um arquivo em que o Apothem não consegue distinguir o bloco dele do
seu texto, que nomeia cada par de marcadores e como corrigi-lo (consulte
[O Apothem não consegue distinguir o bloco dele do seu texto](/docs/install/troubleshooting#apothem-cannot-tell-its-block-from-your-text)):
a instalação deixa esse arquivo como está (para pares de marcadores, enquanto um
registro de instalação listar o arquivo; consulte [`update`](/docs/cli-reference/update)).
Uma instalação que deixa esse arquivo como está termina como parcial, já que a
ferramenta não recebe nenhum bloco atual do Apothem desse arquivo: no lugar da
linha `✓`, ela imprime uma linha `✗` no erro padrão que nomeia o arquivo (de modo
que `--quiet` a mantém), o `status` do envelope `--format json` é `"partial"` e o
aviso desse arquivo carrega `"detail": {"left_as_is": "1"}`, e o código de saída
é `2`. Toda instalação e atualização termina dessa forma até que você corrija as
linhas de marcador que o aviso nomeia. Sem `--quiet`, uma instalação desse tipo
com `--harness all` termina com uma linha de resumo que começa com `!` no lugar
de `✓` e conta os arquivos deixados como estão:
`! Installed <n> harnesses (<m> files written); <k> file(s) left as they are, named above.`
Com `--clean`, uma instalação desse tipo não imprime sua próxima etapa,
`apothem verify`, que falha até que você corrija o arquivo. Em uma simulação, o
aviso para um arquivo deixado como está diz que o Apothem
"would leave the file as it is", e a execução ainda termina com `status`
`"dry_run"` e código de saída `0`. Uma regra no seu perfil que abre um bloco de
código e nunca o fecha não oculta o marcador END do bloco que a instalação grava:
a instalação fecha esse bloco de código no fim do bloco. Um bloco que um
lançamento anterior gravou a partir de uma regra desse tipo não tem essa linha de
fechamento. Um bloco de código seu que abre acima do bloco do Apothem e nunca
fecha é um caso diferente: uma linha de fechamento no bloco o fecha, de modo que
o bloco é lido como código. A instalação avisa sobre um bloco desse tipo assim
que o grava, e o aviso nomeia o bloco de código a fechar acima do marcador BEGIN
(consulte
[O Apothem não consegue distinguir o bloco dele do seu texto](/docs/install/troubleshooting#apothem-cannot-tell-its-block-from-your-text)).
Uma simulação lê o arquivo antes que qualquer coisa seja gravada, então ela não
mostra que o bloco seria lido como código depois de gravado.
O envelope `--format json` sempre carrega o array `warnings` completo,
independentemente do nível de detalhe.

A instalação e a atualização também imprimem avisos consultivos como linhas
`Note:`. Um aviso consultivo nunca altera o que a instalação grava. Quando uma
instalação grava em uma raiz compartilhada, um caminho que outras ferramentas
também carregam (por exemplo, a pasta de skills `~/.agents/skills/`), a nota
nomeia essas ferramentas e coloca entre parênteses uma ferramenta que só carrega
o caminho sob uma condição, por exemplo `Open-Claw (only under its default state
directory)`. Uma instalação que grava uma pasta que outras instalações também
gravam (o papel `holder`) informa que a pasta permanece até que a última
instalação do Apothem que a usa seja desinstalada e nomeia as instalações que a
usam agora. Quando uma instalação tem como alvo uma ferramenta que já carrega
conteúdo do Apothem a partir da raiz compartilhada de outra instalação, a nota
nomeia a instalação que o colocou ali: o proprietário registrado enquanto ele
ainda usa a pasta, caso contrário a instalação mais antiga que a usa. No
envelope `--format json`, cada aviso consultivo é uma entrada de `warnings` com
`"outcome": "advisory"` e `"operation": "shared_root"`; o seu `role` é `owner`,
`holder` ou `reader`, `holders` lista as instalações que usam a pasta e
`owner_of_record` nomeia o proprietário registrado.

Uma instalação que registra hooks também imprime notas sobre o arquivo de hooks.
Um aviso consultivo `hook_review` nomeia a etapa de que a ferramenta precisa
antes de executar os hooks (uma reinicialização e uma revisão, ou confiar no
workspace), ou o risco de um arquivo de hooks que um repositório versiona e que
nomeia o interpretador desta máquina. Um aviso consultivo `hook_import` aparece
para uma ferramenta que também executa os hooks dos arquivos de configuração do
Claude Code, como os que a instalação do Apothem para o Claude Code grava, e
nomeia o próprio interruptor da ferramenta para desativar essa importação e o
que o interruptor também interrompe. Cada um é uma entrada de `warnings` com
`"outcome": "advisory"`, o `harness`, o `path` do arquivo de hooks e uma
`message`.

Um comando de hook mantém o caminho do projeto e o caminho do interpretador
entre aspas duplas, que `sh`, o Git Bash e o PowerShell leem. Um caminho que
contém `$`, um acento grave, uma aspa dupla ou uma barra invertida faria o
comando executar um arquivo diferente, então a instalação (e `--dry-run`) para
com um erro que nomeia o caminho e não grava nada; mova ou renomeie o projeto e
execute novamente. Um espaço ou um apóstrofo em um caminho não causa problema.

Algumas ferramentas carregam apenas o primeiro arquivo com texto de uma lista
fixa em uma pasta, então um arquivo seu à frente daquele que o Apothem grava
impede que a ferramenta carregue o bloco do Apothem. Por exemplo,
[uma ferramenta suportada](/docs/harnesses/codex#compatibility-notes) lê um
`AGENTS.override.md` que tem texto em vez do `AGENTS.md` que o Apothem grava ao
lado dele na pasta pessoal dessa ferramenta. A instalação e a atualização então
imprimem uma nota que nomeia esse arquivo, incluindo nas simulações. Um override
vazio é ignorado, assim como um link simbólico para `AGENTS.md`; um hard link ou
uma cópia recebe a nota, porque uma instalação que regrava `AGENTS.md` o deixa
como um arquivo separado. O OpenCode 1 funciona de outra forma: uma lista
`instructions` em um `opencode.jsonc`, mesmo vazia, substitui a lista que o
Apothem grava em `opencode.json` na mesma pasta. Um `config.json`,
`opencode.json` ou `opencode.jsonc` ali que ele não consegue ler ou analisar,
cujo nível superior não é um objeto, cujo valor `instructions` não é uma lista de
texto, ou com um `{file:path}` que nomeia um arquivo que ele não consegue ler o
impede de carregar qualquer parte da sua configuração, assim como uma pasta com
um desses nomes. A instalação e a atualização imprimem uma nota
`instruction_override` também para cada um desses arquivos, exceto um
`opencode.json` que não conseguem analisar nem como JSON5, que recusam com um
erro `config.unparseable`
([notas do OpenCode](/docs/harnesses/opencode#compatibility-notes)). A nota é uma
entrada de `warnings` com `"outcome": "advisory"` e `"operation": "instruction_override"`,
o `harness`, o `path` do arquivo de que a nota trata, o `target` que a
instalação grava e uma `message`.

Os servidores MCP do perfil recebem três avisos consultivos, cada um nomeando o
campo do perfil:

| Operação | Condição | Correção |
| --- | --- | --- |
| `mcp_deprecated_transport` | `transport: sse` (a especificação MCP descontinua o HTTP+SSE) | Use `streamable-http` quando o servidor oferecer suporte a ele. |
| `mcp_plain_http` | uma URL `http://` para um host que não é loopback | Use uma URL `https://`. |
| `mcp_literal_credential` | um valor de `headers` ou `env` com formato de token (`ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_`, `sk-`, `xoxa-`, `xoxb-`, `xoxo-`, `xoxp-`, `xoxr-`, `xoxs-`, ou `Bearer` com um token longo) | Mantenha o segredo em uma variável de ambiente e escreva referências no estilo `${GITHUB_TOKEN}`. |

O aviso consultivo de credencial nunca imprime o valor que encontrou. Um valor
que contém uma referência `${...}` nunca é sinalizado.

## Configurações do operador com comentários

Algumas configurações de harness são arquivos que você também edita, como
`settings.json`, `opencode.json` (que pode ser JSONC), `openclaw.json` (JSON5) e
`config.yaml`. A instalação mescla as próprias chaves nesses arquivos e mantém
todas as chaves que você adicionou.

Uma mesclagem reescreve o arquivo como JSON ou YAML simples, o que descartaria
comentários, vírgulas finais e a sintaxe JSON5. Por isso:

- Quando a mesclagem não alteraria nenhum valor (por exemplo, você mesmo já
  adicionou as chaves do Apothem), o arquivo é mantido byte a byte como está.
- Quando a mesclagem precisa alterar um valor em um arquivo que carrega
  comentários ou sintaxe JSON5, ou em um arquivo que nem sequer pode ser
  analisado, a instalação não grava nada para esse harness e sai com o código 1
  e o código de erro `config.unparseable`. O campo `fix` nomeia as chaves que a
  instalação adicionaria, para que você possa converter o arquivo para JSON ou
  YAML simples, ou adicionar essas chaves à mão e executar novamente.
- Quando uma chave que a instalação preenche com um mapeamento ou uma lista (por
  exemplo, `skills.external_dirs` em `config.yaml`) contém um valor escalar, ou o
  outro formato de contêiner, no seu arquivo, a instalação não grava nada para
  esse harness e sai com o código 1 e o mesmo código de erro, porque preencher a
  chave descartaria o seu valor. O erro nomeia a chave; altere-a para o formato
  que ele nomeia, ou remova-a, e execute novamente. Uma chave que você deixou
  vazia (`skills:` sem nada abaixo dela) é preenchida.

## Opções

| Opção | Descrição |
|---|---|
| `--harness NAME` | Adaptador de harness a instalar, ou `all` para o conjunto de todo o registro (obrigatório). Com `all`, os harnesses listados em `exclude_harnesses` do perfil são ignorados, mas um harness nomeado explicitamente é instalado mesmo quando listado. Execute `apothem harnesses list` para ver os nomes registrados. |
| `--profile PATH` | Caminho para o YAML do perfil compartilhado. O padrão é `~/.config/apothem/profile.yaml`. |
| `--dry-run` | Mostra uma prévia da instalação sem gravar arquivos. |
| `--clean`, `--fresh` | Recomeço limpo, ativado explicitamente: faz backup e remove o estado de instalação anterior de cada harness antes de instalar. |
| `--yes` | Pula a confirmação por destino durante uma remoção de recomeço limpo (obrigatório em execuções não interativas de `--clean`). |
| `--project PATH` | Raiz do projeto para os harnesses com escopo de projeto. |
| `--quiet`, `-q` | Suprime a saída informativa; apenas os erros são emitidos. |
| `--verbose`, `-v` | Imprime a justificativa de cada capacidade não projetada, em vez da nota agrupada por harness. |
| `--format plain\|json` | Formato de saída (padrão: `plain`). |
| `--json` | Abreviação de `--format json`. |
| `--no-color` | Desativa os códigos de cor ANSI na saída. |
| `-h`, `--help` | Mostra a ajuda e sai. |

## Saída JSON

Quando `--json` (ou `--format json`) é fornecido, um único documento JSON é
gravado em stdout:

```json
{
  "schema_version": 1,
  "status": "success",
  "command": "install",
  "action": "installed",
  "harness": "claude-code",
  "profile_path": "C:\\Users\\Example\\.config\\apothem\\profile.yaml",
  "project": null,
  "files_written": ["C:\\Users\\Example\\.claude\\settings.json"],
  "results": [],
  "warnings": [],
  "error": null,
  "output_path": "C:\\Users\\Example\\.claude\\settings.json"
}
```

Uma instalação que deixou um arquivo como está por causa das suas linhas de
marcador do Apothem tem `status` `"partial"` e sai com código `2` (consulte
[Notas sobre capacidades](#notas-sobre-capacidades)).

Com `--dry-run`, nada é gravado e `results` lista cada caminho que a instalação
gravaria, cada um com o resultado que teria (`created`, `updated` ou
`unchanged`) e, para um arquivo que você também edita, o diff unificado em
`detail.diff` — o mesmo plano que [`apothem diff`](/docs/cli-reference/diff)
mostra:

```json
{
  "schema_version": 1,
  "status": "dry_run",
  "command": "install",
  "action": "dry_run",
  "harness": "claude-code",
  "files_written": [],
  "results": [
    {
      "harness": "claude-code",
      "outcome": "created",
      "operation": "write_text",
      "path": "C:\\Users\\Example\\.claude\\settings.json",
      "message": "dry run: no filesystem changes made"
    }
  ],
  "warnings": [],
  "error": null
}
```

Um resultado recusado em um link nomeia o link em `detail.symlink` e o caminho
para o qual ele leva em `detail.leads_to`. Um resultado recusado porque um link
leva a pasta de uma ferramenta para fora do seu diretório pessoal também carrega
a correção em `detail.fix`.

Quando `--clean` é fornecido, o envelope carrega adicionalmente um objeto
`clean` que descreve a fase de remoção — a lista de disposições por destino, se
a execução foi uma prévia e o diretório de backup com carimbo de data e hora
(`null` em uma execução de simulação):

```json
{
  "clean": {
    "dry_run": true,
    "backup_dir": null,
    "targets": [
      {
        "path": "C:\\Users\\Example\\.claude",
        "present": true,
        "removed": false,
        "skipped_reason": null
      }
    ]
  }
}
```

Uma execução de simulação com limpeza mostra uma prévia das duas fases em um
único documento: a prévia da remoção em `clean` e a prévia da nova gravação em
`results`.

Os erros de validação esperados usam o mesmo envelope e incluem um objeto de
erro:

```json
{
  "schema_version": 1,
  "status": "error",
  "command": "install",
  "harness": "all",
  "files_written": [],
  "error": {
    "code": "project.required",
    "field": "project",
    "reason": "project-scope harnesses require --project: cursor, gemini-cli, github-copilot, kimi-code, windsurf, codebuddy, kiro, trae, zed, glm.",
    "fix": "Pass --project PATH or select only user-scope harnesses."
  }
}
```

## Exemplos

```bash
apothem install --harness claude-code
apothem install --harness claude-code --dry-run
apothem install --harness cursor --project . --profile ~/profile.yaml --json
apothem install --harness all --project . --dry-run --json
apothem installing --harness claude-code   # continuous-form alias
apothem Installing --harness claude-code   # capitalized variant
```

## Códigos de saída

| Código | Significado |
|---|---|
| 0 | Adaptador instalado com sucesso ou execução de simulação planejada sem erros |
| 1 | Erro esperado de validação, de perfil, de harness, de projeto ou de adaptador |
| 2 | Parcial: um lote parou após pelo menos uma gravação, ou a instalação deixou como está um arquivo em que o Apothem mantém o bloco dele por causa das suas linhas de marcador do Apothem (consulte [Notas sobre capacidades](#notas-sobre-capacidades)); `status` é `"partial"` |
| 64 | Erro de uso: uma opção ou um comando desconhecido, ou um valor de opção ausente ou inválido. Com `--json`, o erro é um envelope JSON com o código `cli.usage`. |
