O Apothem é instalado em menos de dois minutos e funciona junto da sua
configuração de harness existente. Cada via executa o mesmo motor
autocontido — a árvore de código-fonte carrega suas dependências incorporadas
e é executada a partir de um checkout no Python 3.10 ou mais recente do sistema
(consulte
[o runtime autocontido](/docs/architecture/self-contained-runtime)).

**Dois pré-requisitos são compartilhados por todas as vias:** o **Python 3.10
ou mais recente** do sistema no `PATH`, com os pacotes `click` e `rich`
importáveis sob ele. O shim do npm (canal 2), a extensão da família VS Code
(canal 4) e os bootstraps de linha de comando (canais 5–7) precisam
adicionalmente do **Node.js 18 ou mais recente** para executar o `npx`. O
Python 3.10 e o Node.js 18 e 20 já passaram do fim de vida upstream; eles
continuam suportados e testados, mas versões mais recentes são preferíveis
(consulte [Pré-requisitos de relance](#pré-requisitos-de-relance)). A seção
própria de cada canal abaixo repete seus pré-requisitos exatos, um comando
pronto para copiar e uma etapa de verificação.

## Escolha um canal

Oito canais de instalação estão disponíveis. Escolha pela forma como você já
trabalha.

| # | Canal | Entrega | Pré-requisitos |
|---|---------|----------|---------------|
| 1 | [Plugin do Claude Code](#1-plugin-do-claude-code) | Harness completo no Claude Code | Claude Code · Python 3.10+ |
| 2 | [Shim do npm (`npx`)](#2-shim-do-npm-npx) | Harness completo, qualquer ferramenta | Node 18+ · Python 3.10+ |
| 3 | [Instaladores de uma única etapa](#3-instaladores-de-uma-única-etapa) | Harness completo + um comando `apothem` | Python 3.10+ (`git` para uma instalação pela rede) |
| 4 | [Extensão da família VS Code](#4-extensão-da-família-vs-code) | Harness completo a partir do editor | VS Code · Node 18+ · Python 3.10+ |
| 5 | [Bootstrap de linha de comando (host de extensão)](#5-bootstrap-de-linha-de-comando-host-de-extensão) | Bootstrap que executa o motor | Sua ferramenta host · Node 18+ · Python 3.10+ |
| 6 | [Bootstrap de linha de comando (host `qwen-code`)](#6-bootstrap-de-linha-de-comando-host-qwen-code) | Bootstrap que executa o motor | Sua ferramenta host · Node 18+ · Python 3.10+ |
| 7 | [Bootstrap de linha de comando (host de plugin)](#7-bootstrap-de-linha-de-comando-host-de-plugin) | Bootstrap que executa o motor | Sua ferramenta host · Node 18+ · Python 3.10+ |
| 8 | [Motor direto (`python -m apothem`)](#8-motor-direto-python--m-apothem) | Harness completo a partir de um checkout | Python 3.10+ (`click`, `rich`) |

<Callout title="Quais canais entregam o harness completo">
  O shim do npm (2), os instaladores de uma única etapa (3) e o motor direto
  (8) materializam por conta própria toda a unidade sincronizada para qualquer
  harness. As três extensões de linha de comando (5–7) instalam um pequeno
  **bootstrap** que invoca o motor pelo shell (`npx @ahmed-g-gad/apothem install`)
  para materializar o harness completo — elas são o ponto de entrada, não a
  entrega completa por si só. O plugin do Claude Code (1) carrega o motor e o
  executa diretamente. A extensão da família VS Code (4) não carrega um motor
  próprio: por padrão, seus comandos executam o motor por meio do shim do npm.
</Callout>

Cada via é idempotente: executar novamente é seguro e converge para o mesmo
estado.

## 1. Plugin do Claude Code

**Pré-requisitos:** Claude Code e o Python 3.10+ do sistema no `PATH`.

A via do plugin é executada inteiramente dentro do Claude Code. Ela empacota o
motor do Apothem com seus comandos de barra, trabalhadores delegados, skills,
regras e hooks, todos executáveis a partir da árvore autocontida do plugin:

```text title="Inside Claude Code"
/plugin marketplace add ahmed-g-gad/apothem
/plugin install apothem@apothem
```

Após a instalação, o conjunto de comandos do Apothem, os trabalhadores
delegados incluídos, as skills e os quatro
[output-styles](/docs/reference/output-styles) (escolha um com
`/output-style` ou a partir de `/config`) ficam disponíveis em cada sessão do
Claude Code. O plugin distribui cada comando como uma skill, um `SKILL.md` com
o detalhe que carrega sob demanda em uma pasta `references/` ao lado dele, então
o Claude Code o invoca com o prefixo do plugin: `/apothem:plan-spec`,
`/apothem:security-audit` e os demais. Dois nomes são ocupados pelo próprio
Claude Code: `/plan` entra no modo de planejamento e `/code-review` executa a
revisão integrada, então digite `/apothem:plan` e `/apothem:code-review` para os
comandos do Apothem. Quando o motor do Apothem é instalado no Claude Code em vez
do plugin, as mesmas skills são gravadas em `~/.claude/skills/` sem prefixo, e
uma skill pessoal `code-review` substitui o `/code-review` integrado (seu alias
`/review` ainda executa o integrado). Dois nomes, `projectify` e `workflow`,
também são skills nativas; a skill nativa é a que o plugin e a instalação do
motor distribuem, e não uma skill derivada do comando. Consulte
[Claude Code](/docs/harnesses/claude-code#command-skills-and-reference-files)
para ver como os comandos são divididos, e [Comandos de barra](/docs/reference/commands)
para o catálogo completo de comandos.

**Verifique:** execute `/plugin` dentro do Claude Code e confirme que
**apothem** aparece listado como instalado, ou consulte o relatório de desvio
a partir de um terminal:

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 2. Shim do npm (`npx`)

**Pré-requisitos:** Node.js 18+ (para o `npx`) e o Python 3.10+ do sistema no
`PATH`. O shim localiza o interpretador e encaminha cada comando da CLI para o
motor incluído — nada é colocado permanentemente no seu sistema. Ele tenta
`python3`, `python` e depois `py -3`, nessa ordem; defina **`APOTHEM_PYTHON`**
como o caminho de um interpretador para tentá-lo primeiro, que é o que você
precisa quando o Python está instalado mas não está no `PATH`, ou quando há
várias versões e você quer uma específica. O interpretador que você indicar
ainda precisa passar na verificação do Python 3.10+; quando não passa, o shim
recorre a `python3`, `python` e depois `py -3`.

```bash title="npx"
npx @ahmed-g-gad/apothem install --harness claude-code
```

Em uma máquina sem perfil, este primeiro `install` cria o perfil inicial em
`~/.config/apothem/profile.yaml` e informa isso. Seus campos de identidade são
marcadores de posição: personalize-os (`npx @ahmed-g-gad/apothem profile edit`)
e depois execute o comando novamente com `update` no lugar de `install` para
aplicá-los.

Ele também é executado diretamente a partir do repositório:

```bash title="npx from the repository"
npx github:ahmed-g-gad/apothem install --harness claude-code
```

Cada comando da [referência da CLI](/docs/cli-reference) funciona nesta forma;
use `npx @ahmed-g-gad/apothem` no lugar de `apothem`. Esta também é a via de
instalação para o OpenCode e para todas as outras ferramentas que não expõem um
registro separado de plugins ou extensões — o Apothem as sincroniza diretamente
no diretório de configuração nativo delas
(`npx @ahmed-g-gad/apothem install --harness opencode`).

**Verifique:**

```bash title="Verify"
npx @ahmed-g-gad/apothem --version
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 3. Instaladores de uma única etapa

**Pré-requisitos:** o Python 3.10+ do sistema no `PATH` (o instalador se oferece para adicionar os pré-requisitos `click` / `rich` para você). Para uma instalação pela rede: `git`, para encontrar o lançamento mais recente, e `gpg`, para verificar a tag de lançamento assinada (o Git for Windows traz ambos). O [cosign](https://docs.sigstore.dev/cosign/system_config/installation/)
é opcional: com ele, o instalador também verifica o arquivo de lançamento assinado.

Os scripts de instalação resolvem o lançamento mais recente, verificam-no (consulte
[Modelo de confiança](#trust-model)), colocam a árvore de código-fonte do Apothem em `~/.apothem`,
criam um perfil inicial quando nenhum existe, materializam seu primeiro harness e
verificam o resultado, tudo em uma única execução. O perfil inicial traz campos
de identidade com marcadores de posição: edite-o e depois execute
`apothem update --harness <name>` para aplicar os seus. Executar novamente é
idempotente: um clone git é atualizado com fetch, sua nova tag é verificada e só
então o clone recebe o checkout da tag resolvida; uma instalação a partir do
arquivo de lançamento é atualizada no lugar; e o harness é materializado
novamente. Quando o motor termina como parcial (código de saída `2`), o
instalador imprime uma linha de aviso, ainda verifica, coloca o comando
`apothem` e imprime seu banner, e então termina com o código de saída `2`. O
motor termina como parcial quando deixa um arquivo como está por causa das suas
linhas de marcação do Apothem, ou quando para depois de já ter gravado algo
(consulte
[Quando o motor deixa um arquivo como está](/docs/install/updating#when-the-engine-leaves-a-file-as-it-is)).
A instalação verificada é a via padrão e recomendada.

Importe primeiro, uma vez, a chave de assinatura do mantenedor. Toda instalação pela rede verifica a tag de lançamento com ela, com ou sem cosign, e para quando a chave não está no seu chaveiro. Confira se a impressão digital é `5C89 98F9 F241 7204 45D3  F28B 7039 6FED 9C63 4163`, valor publicado em [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md#maintainer-signing-key). No Windows, o `git verify-tag` lê o chaveiro do `gpg` que vem com o Git for Windows, por isso a importação roda pelo `bash` do próprio Git:

```bash title="macOS · Linux · WSL2 · BSD — import the key once"
curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import
gpg --fingerprint 70396FED9C634163
```

```powershell title="Windows · PowerShell — import the key once"
& "$env:ProgramFiles\Git\bin\bash.exe" -c 'curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import && gpg --fingerprint 70396FED9C634163'
```

```bash title="macOS · Linux · WSL2 · BSD — latest signed tag, verified"
curl -fsSL https://apothem.ahmedgad.com/install.sh | bash
```

```powershell title="Windows · PowerShell — latest signed tag, verified"
irm https://apothem.ahmedgad.com/install.ps1 | iex
```

Os mesmos scripts vêm em um checkout sob `scripts/installer/` — `install`,
`uninstall` e `update` nas formas `.sh`, `.ps1` e `.bat` — de modo que você pode
executá-los diretamente após clonar:

```bash title="From a checkout"
APOTHEM_HARNESS=claude-code sh scripts/installer/install.sh                                 # POSIX
$env:APOTHEM_HARNESS = 'claude-code'; pwsh -NoProfile -File scripts/installer/install.ps1   # Windows
```

Um comando de uma linha com pipe nunca usa uma árvore local: `curl ... | sh` e `irm ... | iex`
ignoram a pasta a partir da qual você os executa e as pastas acima dela, e buscam e
verificam o lançamento. O instalador usa uma árvore local apenas quando você executa
o próprio `scripts/installer/install.sh` (ou `install.ps1`) do checkout pelo seu caminho,
a partir de qualquer pasta (por exemplo `sh ~/src/apothem/scripts/installer/install.sh`),
ou quando `APOTHEM_SOURCE` aponta para essa árvore. Os instaladores, atualizadores e
desinstaladores, os shims `apothem`, o inicializador do npm, os hooks e os
processos de validação do conformity gate mantêm a pasta atual fora do caminho de
busca de módulos do Python. Um comando `python -m apothem` que você mesmo digita não faz isso:
`-m` lê módulos da pasta atual primeiro.

Entradas vazias e relativas no seu próprio `PYTHONPATH` não são repassadas ao
motor por nenhum inicializador (os instaladores, atualizadores, desinstaladores, os shims
`apothem` de POSIX e Windows e o inicializador do npm). Uma entrada mantida precisa ser um caminho
completo: no Windows, um caminho com unidade, como `C:\lib`, ou um caminho de rede; nos demais sistemas, um
caminho que começa com `/`. Um `\lib` com raiz ou um `C:lib` relativo à unidade é
descartado. Os scripts sh perguntam ao Python que executam qual forma ele lê, e o
shim `apothem` que eles gravam mantém essa forma. Um Python do Windows (o habitual
no Git Bash) recebe os caminhos do motor na forma do Windows, unidos com `;`, e
mantém apenas os caminhos com unidade e de rede do seu `PYTHONPATH`. Um Python POSIX,
incluindo o próprio `python3` do Cygwin e do MSYS2, recebe caminhos POSIX unidos com `:`
e mantém apenas as entradas que começam com `/`. Os comandos `git` dos instaladores
que não atuam sobre um clone não leem um repositório na pasta atual.

### Modelo de confiança [#trust-model]

Sem `APOTHEM_REF` definido, o instalador resolve o lançamento
`vMAJOR.MINOR.PATCH` mais alto e instala *esse* — nunca a branch `main` em
movimento. Ele verifica o lançamento antes que qualquer configuração seja
materializada, e a verificação depende de o `cosign` estar ou não no seu `PATH`:

- **Com cosign**, duas verificações precisam passar. Primeiro, a tag de lançamento precisa
  ter uma assinatura válida da chave do mantenedor, verificada como no próximo
  item, e a tag assinada precisa ser a que tem o nome desse lançamento: uma tag
  assinada de outro lançamento, reapontada para esse nome, é recusada. Em seguida, o
  instalador baixa o arquivo de plataforma do lançamento, seu arquivo `SHA256SUMS`
  e o `SHA256SUMS.cosign.bundle`. O cosign precisa confirmar que o workflow de
  lançamento do Apothem assinou o `SHA256SUMS` para exatamente essa tag e, por meio da sua
  verificação `--certificate-github-workflow-sha`, que o certificado verificado
  foi emitido para uma execução no commit para o qual a tag assinada aponta. O instalador
  não lê o certificado ele mesmo. O SHA-256 do arquivo precisa então corresponder ao
  digest listado. O workflow é executado para qualquer tag enviada, então sua
  assinatura sozinha não basta; a assinatura da tag mostra que o mantenedor
  lançou esse commit.
- **Sem cosign**, ou quando `APOTHEM_HOME` já contém um clone git, o
  instalador clona ou atualiza o repositório e verifica apenas a tag com
  `git verify-tag`. A assinatura precisa ser válida *e* feita pela
  chave do mantenedor publicada em [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md), e a tag assinada precisa ser a que tem o nome do
  lançamento. Uma tag assinada por qualquer outra chave é recusada,
  mesmo quando seu chaveiro confia nessa chave. Uma tag git assinada identifica seu commit por
  um ID SHA-1; com cosign, o instalador também verifica o SHA-256 do arquivo.
  Um clone existente é atualizado com fetch e sua nova tag é verificada *antes* de o clone
  receber o checkout. Uma verificação que falha deixa o clone como estava, e um clone com
  alterações em arquivos rastreados interrompe a atualização com uma mensagem para fazer commit ou stash
  delas, em vez de perdê-las. Com uma ref que não é de lançamento, como `main`, um
  clone existente acompanha a cópia dessa branch em origin.

O instalador ignora as variáveis de ambiente do git que redirecionam o git
(`GIT_DIR`, `GIT_WORK_TREE` e semelhantes) e as que apontam o git para outro
arquivo de configuração (`GIT_CONFIG`, `GIT_CONFIG_GLOBAL` e `GIT_CONFIG_SYSTEM`) ou o fazem
ler atributos de outra árvore (`GIT_ATTR_SOURCE`; um `attr.tree` na sua
própria configuração é esvaziado em todo comando git executado sobre um clone), e para quando
`APOTHEM_REPO` começa com `-`. `GIT_CONFIG_NOSYSTEM` permanece como você
o definiu; ele apenas impede o git de ler a configuração do sistema. O git ainda lê sua própria
configuração global e, a menos que você defina `GIT_CONFIG_NOSYSTEM`, a configuração do sistema
nos lugares onde sempre procura, e `git`, `gpg` e `cosign` são os
programas que seu `PATH` encontra: o instalador confia neles como encontrados. Durante toda a
execução, o instalador define `GIT_NO_REPLACE_OBJECTS=1`, para que o git nunca troque um
objeto por meio de replace refs, `GIT_NO_LAZY_FETCH=1`, para que o git nunca busque por conta própria um
objeto ausente no remoto, `GIT_ALLOW_PROTOCOL` com os transportes file,
git, http, https e ssh, para que um valor no seu ambiente não possa
ampliar essa lista, e `GIT_ATTR_NOSYSTEM=1`; com `core.attributesFile` esvaziado
em todo comando git executado sobre um clone, o git então não lê nenhum arquivo de atributos fora
do clone, de modo que uma macro definida no seu não pode nomear um filtro ali. O
script do PowerShell restaura as quatro quando a execução termina. O instalador
lê a tag de lançamento uma vez, registra o commit que ela nomeia, verifica a tag,
faz o checkout desse commit pelo ID e exige que `HEAD` seja esse commit, de modo que uma tag
movida depois da verificação não muda nada. No Windows PowerShell 5.1 e 7, um
download que redireciona para um endereço que não é https é recusado, como faz o
`curl` dos instaladores POSIX.

`APOTHEM_HOME` precisa ser uma pasta em que só você pode gravar, pois qualquer pessoa que possa
gravar nela pode alterar o código que o comando `apothem` executa. No Windows, uma
pasta criada na raiz de uma unidade, como `C:\apothem`, pode ser alterada por
qualquer usuário que entre no computador, com as permissões padrão do Windows.
O padrão, `~/.apothem`, fica na sua própria pasta de usuário. Cada instalação, atualização
e simulação obtida pela rede avisa, sem parar, quando isso não acontece, ou quando a
pasta ou a que a contém pertence a outra pessoa, nomeando a pasta,
quem pode gravar nela ou é seu dono, e a correção; uma instalação a partir de um checkout
local, e uma atualização com `APOTHEM_SOURCE` definido, pulam a verificação. No Windows,
o aviso vem de
`install.ps1` e `update.ps1`: `install.sh` e `update.sh` não fazem a verificação
no Git Bash, MSYS2 ou Cygwin (consulte
[Resolução de problemas](/docs/install/troubleshooting#the-installer-warns-other-users-can-change-apothem_home)).

Uma verificação que falha aborta a instalação antes que qualquer configuração seja gravada e
antes que o instalador substitua `APOTHEM_HOME`. Uma
tag assinada cuja chave pública do mantenedor ainda não está no chaveiro local aborta,
em vez disso, com orientações para importar a chave: importe a chave como mostrado acima, confira a
impressão digital com o valor publicado em [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md) e execute novamente.

Uma nova execução com cosign atualiza uma instalação anterior feita a partir do arquivo de lançamento. O novo
código-fonte é verificado e descompactado primeiro em uma pasta ao lado de `~/.apothem` e
depois trocado. Tudo em `~/.apothem` que não faz parte da árvore de código-fonte
é levado para a nova instalação: os backups de rollback do motor (`backups/`),
os registros de instalação (`state/`), planos, memória e seus outros dados. Se uma etapa falhar
ou você interromper a execução com Ctrl+C ou um sinal de término, a instalação anterior é
restaurada sem alterações; se até isso falhar, a mensagem indica onde estão os arquivos
anteriores. Um encerramento forçado ou uma queda de energia durante a troca não pode ser capturado:
pode deixar pastas ao lado de `~/.apothem`, e a próxima instalação obtida pela rede as relata
(veja abaixo). Estas regras se aplicam quando o instalador substitui `~/.apothem`:

- Um clone git não é substituído por um arquivo de lançamento sem `--yes`. Os arquivos
  que o clone não rastreia vão para a nova instalação, e a própria árvore do clone
  (seu histórico e código-fonte) vai para uma nova pasta,
  `~/.apothem.before-apothem-<time>`, com seu próprio nome (`.apothem`); o
  instalador informa onde, e você a exclui quando não precisar mais dela. Mesmo com
  `--yes`, o instalador recusa enquanto o clone contém trabalho local que seria perdido:
  alterações, stashes, commits não enviados ou arquivos não rastreados na sua árvore de código-fonte.
  Faça commit e push desse trabalho, ou mova-o para outro lugar, e execute novamente. Essa verificação também
  roda com `--dry-run`. Um arquivo `.git` (uma worktree vinculada) conta como clone,
  assim como uma pasta `.git`.
- Um clone git de qualquer coisa que não seja o Apothem é tratado como qualquer pasta que
  não contém uma instalação do Apothem (veja abaixo), nunca atualizado ou substituído como clone.
- Um clone existente é atualizado no lugar apenas quando o git consegue ver todas as alterações nele
  e nada na sua própria configuração executa código durante a atualização. Antes do fetch,
  o instalador para quando há arquivos marcados como assume-unchanged ou skip-worktree,
  quando o git não encontra uma work tree em `APOTHEM_HOME` (como quando a configuração do clone
  define `core.bare` como `true`), quando o clone contém um submódulo (registrado no seu
  índice, ou mantido em `.git/modules`), quando `.git/info/attributes` nomeia um
  filtro ou driver de diff (`filter=` ou `diff=`), quando ele ou um arquivo de configuração não é
  um arquivo comum, ou quando o clone toma objetos emprestados de outro repositório
  (`objects/info/alternates`). Ele também para em qualquer configuração no próprio
  `.git/config` ou `.git/config.worktree` do clone além das que `git clone` e
  `git init` gravam ali para um clone completo, configurações de branch (o `remote`
  e o `pushremote` de uma branch precisam ser `origin`), `user.name`, `user.email`,
  `maintenance.auto`, `maintenance.strategy`, `pull.rebase` e `pull.ff`, de modo que um
  clone parcial feito com `--filter` também para;
  [Resolução de problemas](/docs/install/troubleshooting#the-installer-stops-the-existing-clone-is-set-up-in-a-way-the-update-would-trust)
  as lista. A mensagem nomeia a configuração e o arquivo em que ela está. As verificações de configurações,
  atributos e objetos rodam antes de qualquer comando git que leia o
  índice ou os objetos do clone e também, com a verificação de submódulos, quando `--yes` está
  prestes a substituir o clone.
  Antes de qualquer comando git que aplique os arquivos `.gitattributes` da work tree,
  o instalador para em um que o git não rastreia, que difere da
  cópia em commit, ou cuja cópia em commit o git não consegue ler ou nomeia um filtro ou
  driver de diff (a cópia na work tree também é lida), e em um repositório git
  no clone que o git não rastreia, cujos arquivos `.gitattributes` o git também
  leria. As próprias pastas de dados do motor, como `backups`, onde nenhum lançamento
  grava, não são lidas para isso. Antes do fetch, ele para
  em arquivos sob `src` (escrito com qualquer combinação de maiúsculas e minúsculas) que o git não rastreia, pois
  o motor poderia carregá-los. Depois do checkout, ele
  remove as pastas de cache do Python (`__pycache__`) sob `src` antes de o motor
  ser executado a partir do clone. Os git hooks do clone
  nunca rodam durante a atualização, e todo comando git sobre o clone roda sem
  pager, sem manutenção automática, com seu monitor de sistema de arquivos desligado, apenas com os transportes file,
  git, http, https e ssh permitidos (de modo que um endereço na configuração do clone
  não possa fazer o git executar um programa auxiliar como `ext::`) e sem
  recursão de submódulos; `git diff` e `git status` ignoram submódulos. Um clone
  que pertence a outro usuário interrompe a execução com uma explicação (consulte
  Resolução de problemas).
- Uma pasta que contém apenas os próprios dados do motor (`backups`, `state`, `plans`,
  `memory`, `contexts`, `learning`, `providers`) é atualizada sem `--yes`,
  e esses dados são mantidos.
- Uma pasta que não contém uma instalação do Apothem não é tocada sem `--yes`. Com
  `--yes`, o instalador move a pasta inteira, sem alterações, para uma nova pasta,
  `~/.apothem.before-apothem-<time>` (ela mantém seu próprio nome lá dentro), informa
  onde e instala do zero.
- Um link simbólico em `APOTHEM_HOME` (no Windows, um link simbólico ou uma
  junção) é recusado, porque substituí-lo substituiria o link e não
  a pasta para a qual ele leva. Aponte `APOTHEM_HOME` para essa pasta e execute novamente. A
  exceção é um clone git existente, que é atualizado no lugar.
- No Linux e no macOS, um arquivo ou pasta a ser levado cujo nome tem um espaço ou
  outro caractere especial interrompe a instalação. Mova-o para fora de `APOTHEM_HOME`
  primeiro.

**Uma execução por vez, e execuções que foram interrompidas.** Cada execução dos scripts de instalação,
atualização e desinstalação obtém um bloqueio ao lado de `APOTHEM_HOME`,
`~/.apothem.lock` por padrão, durante toda a execução, e o libera quando a execução
termina por sucesso, falha, Ctrl+C ou um sinal de término. Os próprios comandos
`apothem` não o obtêm. Uma segunda execução para com "Another Apothem
install, update or uninstall is running". Em POSIX, o bloqueio é uma pasta que
contém o ID de processo da execução. Um bloqueio deixado por uma execução que foi encerrada à força é
relatado com instruções de como removê-lo e nunca é assumido, e um bloqueio criado em
outro ambiente (WSL e Git Bash na mesma máquina, por exemplo) é relatado como um
cujo processo não pode ser verificado dali. No Windows PowerShell, o bloqueio é
um arquivo que o Windows fecha e exclui quando o processo termina. Quando
`APOTHEM_HOME` é um link, todo script obtém o bloqueio ao lado da pasta para a qual ele
leva. Uma simulação também obtém o bloqueio, a menos que a pasta que contém
`APOTHEM_HOME` ainda não exista. Assim, toda execução, incluindo uma atualização no lugar, uma
desinstalação e uma simulação, precisa de acesso de gravação à pasta que contém
`APOTHEM_HOME`; sem ele, a execução para antes de alterar qualquer coisa.

Um encerramento forçado ou uma queda de energia durante uma troca pode deixar a instalação anterior ou
outras entradas de `APOTHEM_HOME` em `.apothem-old.<name>.*`,
`.apothem-extract.<name>.*` ou `.apothem-clone.<name>.*` ao lado dela, onde
`<name>` é a última parte de `APOTHEM_HOME`, ou em uma pasta
`APOTHEM_HOME.before-apothem-<time>`. A próxima instalação obtida pela rede para esse
`APOTHEM_HOME`, incluindo uma simulação, para antes de alterar qualquer coisa, nomeia
cada pasta e as entradas que foram movidas para ela, e explica como movê-las
de volta. Para uma pasta criada por um instalador anterior, que não indica a qual home ela
pertence, a linha pode nomear apenas os dados do motor: verifique o conteúdo dela. Ele
não exclui nada. Consulte
[Resolução de problemas](/docs/install/troubleshooting#the-installer-stops-an-earlier-run-left-folders-beside-apothem_home).

`--dry-run` (`-DryRun` no Windows) busca e verifica o lançamento em uma
pasta temporária e deixa `~/.apothem` inalterado. Ele faz as mesmas verificações
de uma execução real, com uma exceção para um clone existente: verifica a
própria configuração do clone, como listado acima, mas não faz fetch no clone, e por isso não
o verifica quanto a alterações em arquivos rastreados, o que uma atualização real faz depois do seu
fetch. Fixe um lançamento específico com `APOTHEM_REF`:

```bash title="Pinned, verified install"
APOTHEM_REF=vMAJOR.MINOR.PATCH sh -c "$(curl -fsSL https://apothem.ahmedgad.com/install.sh)"
```

Substitua `vMAJOR.MINOR.PATCH` por uma tag da
[página de lançamentos](https://github.com/ahmed-g-gad/apothem/releases). A tag
de lançamento mais antiga é uma tag leve, sem assinatura própria, de modo que a
verificação de tag aborta nela mesmo que seu commit seja assinado; todas as
tags de lançamento posteriores são anotadas e assinadas. A seção de assinatura
de lançamentos do
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md)
lista cada tag e como verificá-la.

Substituições explícitas relaxam o padrão. `APOTHEM_ALLOW_UNVERIFIED=1` rebaixa uma
verificação de tag que falhou no caminho do clone para um aviso e prossegue, para uso air-gapped ou
local, ou para instalar um lançamento anterior à assinatura de tags. Ele nunca relaxa
o caminho do cosign, então defina `APOTHEM_VERIFY=signature` junto com ele em um host que tenha
cosign. Ele também nunca relaxa a verificação de que a tag assinada é a que tem o nome
do lançamento. Como a substituição deixa passar uma tag não assinada, ou assinada por
outra chave, essa verificação protege apenas as tags que carregam a assinatura da
chave do mantenedor. `APOTHEM_REF=main` faz o checkout da branch em movimento sem
verificação somente junto com `APOTHEM_ALLOW_UNVERIFIED=1`. Com
`APOTHEM_REF=main` sozinho, o instalador busca `main` em uma pasta de preparação
(no clone existente, quando `APOTHEM_HOME` é um), e então aborta antes de
fazer checkout de qualquer coisa, substituir `APOTHEM_HOME` ou materializar qualquer
configuração, porque uma branch não é uma tag de lançamento assinada. Um checkout local via `APOTHEM_SOURCE` não busca nada e
pula a verificação.

Defina `APOTHEM_VERIFY` para escolher você mesmo a verificação. O padrão é `auto`:

| Valor | O que o instalador verifica |
| --- | --- |
| `auto` (padrão) | `release` quando o `cosign` está no `PATH` e `APOTHEM_HOME` não é um clone git; caso contrário, `signature` |
| `release` | A assinatura da tag de lançamento feita pela chave do mantenedor e que a tag assinada é a que tem o nome do lançamento; depois, a verificação do cosign de que o workflow de lançamento assinou o `SHA256SUMS` em uma execução no commit da tag; depois, o SHA-256 do arquivo. Para se o cosign ou o `gpg` estiver ausente |
| `signature` | A assinatura GPG da tag de lançamento, que precisa vir da chave do mantenedor, e que a tag assinada é a que tem o nome do lançamento |
| `checksum` | Apenas o SHA-256 do arquivo comparado ao `SHA256SUMS`. Exige `APOTHEM_ALLOW_UNVERIFIED=1` e avisa antes de baixar. O modo checksum não verifica o lançamento. O SHA256SUMS vem do mesmo lançamento que o arquivo, então uma correspondência mostra apenas que o download não está danificado; qualquer pessoa que possa alterar os arquivos do lançamento pode alterar ambos. Use-o apenas em um host sem cosign e sem `gpg`, e somente quando você aceitar isso |

Todo modo de arquivo aborta em caso de divergência de digest antes de extrair qualquer coisa.
Os primeiros lançamentos nomeiam o bundle como `SHA256SUMS.sig`, e o instalador lê esse
nome quando `SHA256SUMS.cosign.bundle` está ausente.

O motor então é executado diretamente a partir da árvore colocada. Todas as
dependências de terceiros, exceto `click` e `rich`, estão incorporadas dentro da
árvore de código-fonte, e o próprio ponto de entrada coloca esse diretório de
dependências incorporadas no `sys.path`. O instalador
imprime o caminho completo do shim `apothem` que gravou. Quando não grava nenhum shim, ele
imprime um comando que inicia o motor mantendo a pasta atual fora do
`sys.path`; copie esse comando do banner.

Ambos os scripts leem as mesmas variáveis de ambiente de configuração
(`APOTHEM_HOME`, `APOTHEM_REPO`, `APOTHEM_REF`, `APOTHEM_ALLOW_UNVERIFIED`,
`APOTHEM_VERIFY`, `APOTHEM_RELEASE_BASE`, `APOTHEM_SOURCE`, `APOTHEM_HARNESS`, `APOTHEM_PROFILE`,
`APOTHEM_SKIP_VERIFY`, `APOTHEM_AUTO_INSTALL_DEPS`, `APOTHEM_BIN_DIR`); consulte
[Variáveis de ambiente do instalador](/docs/how-to/installer-environment-variables)
para a tabela completa e
[Runtime autocontido](/docs/architecture/self-contained-runtime) para entender
como funciona o modelo de invocação `python -m`.

**O comando `apothem`.** Após uma instalação bem-sucedida, o instalador grava um
shim `apothem` que encaminha para o motor incluído — no POSIX em
`$HOME/.local/bin`, no Windows em `%LOCALAPPDATA%\Microsoft\WindowsApps` (um
diretório de usuário que já está no `PATH` padrão do Windows). O instalador
nunca edita seu `PATH`. Assim que o diretório estiver no `PATH`, você executa
`apothem <command>` diretamente, sem `PYTHONPATH` manual.

**Verifique:**

```bash title="Verify"
apothem verify --harness claude-code

# or, before the shim is on PATH, by the shim's full path:
~/.local/bin/apothem verify --harness claude-code
```

## 4. Extensão da família VS Code

**Pré-requisitos:** VS Code, Node.js 18+ e o Python 3.10+ do sistema no `PATH`.

A extensão **Apothem for VS Code** está disponível no
[Visual Studio Marketplace](https://marketplace.visualstudio.com/items?itemName=ahmed-g-gad.apothem-vscode)
como `ahmed-g-gad.apothem-vscode`: instale-a pela visualização Extensões ou com
`code --install-extension ahmed-g-gad.apothem-vscode`. Ela também é instalada a
partir de um pacote `apothem.vsix`: `code --install-extension apothem.vsix`, ou o
comando *Install from VSIX…* do editor. O fluxo de trabalho de lançamento assina
o pacote e o anexa a cada GitHub Release. Os lançamentos publicados antes de o fluxo de trabalho
empacotar a extensão não trazem nenhum `.vsix`; quando o lançamento mais recente
não o traz, gere o pacote a partir de um checkout com a versão do vsce travada
em `tools/vsce/` (essa versão do vsce exige Node.js 22 ou posterior): execute
`npm ci --prefix tools/vsce --ignore-scripts` e depois
`cd vscode-extension && ../tools/vsce/node_modules/.bin/vsce package --no-dependencies --out apothem.vsix`.
Uma cópia instalada a partir de um `apothem.vsix` anterior tem o identificador
`ahmed-g-gad.apothem`; desinstale-a (`code --uninstall-extension ahmed-g-gad.apothem`)
para que as duas cópias não registrem os mesmos comandos. Uma única extensão
cobre os editores da família VS
Code. Seus comandos de paleta (`Apothem: Install`,
`Verify`, `Update`, `Uninstall`, `Doctor`) executam o mesmo motor por meio do
executor configurado (`npx @ahmed-g-gad/apothem@<extension version>` por padrão,
de modo que a extensão executa a versão do motor com a qual foi distribuída;
aponte a configuração de usuário `apothem.runner` para um checkout local para
executar a partir do código-fonte). Install, Verify, Update e Uninstall
perguntam sobre qual harness agir, oferecendo primeiro o harness do próprio
editor; `all` é uma opção, nunca o padrão. A configuração `apothem.runner` tem
escopo de máquina, de modo que um workspace não pode alterá-la, e a extensão é
executada somente em um workspace confiável.

**Verifique:** execute o comando **Apothem: Verify** a partir da paleta de
comandos do editor, ou a partir de um terminal:

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 5. Bootstrap de linha de comando (host de extensão)

comando traz o host e o slug de harness exatos:

Esta extensão é um **bootstrap**, não a instalação completa por si só: ela

npx @ahmed-g-gad/apothem verify --harness gemini-cli --project .

## 7. Bootstrap de linha de comando (host de plugin)

**Pré-requisitos:** sua ferramenta host de linha de comando, Node.js 18+ e o
Python 3.10+ do sistema no `PATH`.

Adicione o repositório como um marketplace de plugins e depois instale o
plugin — o comando traz o host e o slug de harness exatos:

```bash title="Install the plugin"
codex plugin marketplace add ahmed-g-gad/apothem --sparse .agents/plugins --sparse plugins/apothem
codex plugin add apothem@apothem
```

Os dois caminhos `--sparse` buscam apenas a listagem do marketplace e o plugin,
não o repositório inteiro; um clone completo pode ultrapassar o limite de clone
de 30 segundos do host em um disco lento, como uma unidade do Windows sob o WSL.

Como as extensões dos canais 5 e 6, este é um **bootstrap** que invoca o motor
pelo shell. O plugin inclui uma skill de entrada; seu manifesto é um
`plugin.json` na raiz, e a
[página de harness do host do plugin](/docs/harnesses/codex#codex-plugin) descreve o
layout e o que o plugin deixa para o motor. Materialize o harness completo
executando a instalação por meio dele:

```bash title="Materialize the full harness"
npx @ahmed-g-gad/apothem install --harness codex
```

**Verifique:**

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness codex
```

## 8. Motor direto (`python -m apothem`)

**Pré-requisitos:** o Python 3.10+ do sistema com os pacotes `click` e `rich`
importáveis, além de um checkout do repositório. Node.js não é necessário.

Execute o motor diretamente a partir de um clone. O ponto de entrada coloca as
dependências incorporadas (`src/apothem/_vendor`) no `sys.path`, de modo que,
com `click` e `rich` importáveis, `PYTHONPATH=src` é toda a configuração
necessária:

```bash title="Direct engine"
git clone https://github.com/ahmed-g-gad/apothem
cd apothem
PYTHONPATH=src python -m apothem install --harness claude-code
```

`python -m` coloca a pasta atual em primeiro lugar no caminho de busca de módulos
do Python, de modo que um arquivo ali, como `click.py`, ou uma pasta chamada
`apothem`, seria executado no lugar do módulo real. Execute estes comandos a
partir da raiz do checkout ou de outra pasta em que você confie. O comando
`apothem` instalado não lê a pasta atual.

Assim como no shim do npm, um primeiro `install` em uma máquina sem perfil cria
o perfil inicial em `~/.config/apothem/profile.yaml` e continua.

**Verifique:**

```bash title="Verify"
PYTHONPATH=src python -m apothem verify --harness claude-code
```

## Verifique qualquer instalação

Cada canal acima indica seu próprio comando de verificação. As duas formas
gerais são:

```bash title="Installer path"
apothem verify --harness claude-code
```

```bash title="npx path"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

Substitua o nome do harness pelo adaptador que você instalou; consulte a
[lista de harnesses](/docs/harnesses) para todos os nomes suportados. Para
verificar de uma só vez cada adaptador instalado (sua verificação e seus
comandos de hook), execute `doctor` no lugar de `verify --harness NAME`, na
mesma forma que você usou acima: `apothem doctor` (ou o caminho completo do
shim, ou o comando que o instalador imprimiu, quando a pasta dele não está no
`PATH`) ou
`npx @ahmed-g-gad/apothem doctor`. Para a via do plugin, execute
`/plugin` dentro do Claude Code e confirme que **apothem** aparece listado como
instalado.

## Pré-requisitos de relance

- **Python 3.10 ou posterior** — as vias que o localizam fazem isso pelo nome, e
  os nomes diferem de uma via para outra. O shim do npm tenta `python3`,
  `python` e depois `py -3`. Os instaladores tentam `python3`, `python` e os
  nomes com versão, de `python3.14` até `python3.10`.
- **`click` e `rich` importáveis** sob esse interpretador — as duas
  dependências voltadas ao terminal que o motor não incorpora. Os instaladores
  verificam ambas, indicam o que estiver faltando e se oferecem para instalá-lo
  para você — com sua confirmação, ou automaticamente com `--yes` (`-Yes` no
  PowerShell) ou `APOTHEM_AUTO_INSTALL_DEPS=1`. Em todos os outros canais, um
  pacote ausente interrompe o motor com um erro (código de saída 1) que indica o
  comando exato para o interpretador que ele encontrou, com as restrições de
  versão contra as quais o Apothem é testado
  (`<interpreter> -m pip install "click==…" "rich>=…"`); com `--json`, o mesmo
  erro chega como um envelope JSON com o código `runtime.dependency_missing`.
- **Node.js 18 ou posterior** — apenas as vias que executam `npx`: o shim do npm
  (2), a extensão da família VS Code (4) e os bootstraps de linha de comando
  (5–7).
- **Runtimes em fim de vida.** O Python 3.10 chegou ao fim de vida upstream em
  2026-10-01, e o Node.js 18 e o 20, em 2025-04-30 e 2026-04-30. O Apothem
  ainda os suporta como seus pisos declarados e testa cada um deles no CI, mas
  eles não recebem mais correções de segurança upstream, então prefira o
  Python 3.11 ou mais recente e o Node.js 22 ou mais recente. A
  [política de pisos de runtime](/docs/governance/release-engineering-policy#runtime-floors)
  explica como um piso é elevado.
- **Git e GnuPG** — apenas a via do instalador, e somente para a forma pela rede
  (o script encontra o lançamento mais recente e verifica sua tag assinada com
  eles e, sem cosign, clona o código-fonte; um checkout local não precisa de
  nenhum dos dois).
- **Claude Code** — apenas a via do plugin. O **VS Code** e a ferramenta host
  própria de cada bootstrap de linha de comando são necessários apenas para o
  seu próprio canal (4–7).
