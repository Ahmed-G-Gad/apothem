O registro de harnesses é o inventário de adaptadores que serve como fonte de
verdade para a CLI, a documentação, os testes de fixtures e a validação dos pins
de convenção. A fonte em tempo de execução é
`src/apothem/lib/harness_registry.py`; cada linha abaixo é rastreável até esse
registro, até o `capabilities.yml` de cada adaptador e até o
`STANDARD-CONVENTION-PIN.md` de cada adaptador.

## Suporte a cohorts de payload

Os valores de status são `native`, `converted`, `support-tree`,
`profile-projected`, `unsupported`, `not-applicable` e
`discovery-pending`.

Um cohort `converted` é reescrito no formato próprio do harness, e alguns campos
de origem não têm lugar nele. Para cada cohort convertido de comandos, agentes ou
regras, o `capabilities.yml` do adaptador carrega um mapa `conversion_losses`
que informa o que acontece com cada campo de frontmatter de origem:

| Valor | Significado |
| --- | --- |
| `native:<field>` | O harness o lê sob esse campo. |
| `sidecar:<path>` | Ele é gravado em um arquivo separado ao lado do arquivo convertido, como o `agents/openai.yaml` do Codex. |
| `filename` | O nome do arquivo ou da pasta o carrega. |
| `inlined` | Ele passa para o texto do prompt ou do corpo. |
| `ignored` | Ele permanece no arquivo, mas o harness não o lê. |
| `dropped` | Ele é omitido. |

Um teste renderiza cada arquivo convertido e confere os mapas contra a saída.

| Harness | Payloads nativos ou convertidos | Payloads na árvore de suporte | Avisos de não suportado ou pendente |
| --- | --- | --- | --- |
| Antigravity | comandos, agentes e regras convertidos; skills, despacho de subagentes e templates de prompt de sistema nativos; restrições de ferramentas projetadas do perfil | hooks, templates | statuslines, output styles; descoberta de MCP e de memória pendente |
| Claude Code | comandos convertidos; skills, hooks, agentes, regras, statuslines, output styles, despacho de subagentes, restrições de ferramentas e memória nativos | templates | `CLAUDE.md` continua sendo de propriedade do operador; nenhum template de prompt de sistema gravado pelo adaptador; descoberta de MCP pendente |

## Raízes compartilhadas

Alguns alvos de instalação são carregados por harnesses diferentes daquele que
os grava. O registro anota cada um desses caminhos em `SHARED_ROOTS` com um
proprietário (o único adaptador que o grava) e os leitores cuja documentação do
fornecedor o carrega por padrão, além das páginas do fornecedor que o mostram e
da data em que foram obtidas. Instalar o proprietário coloca o conteúdo do
Apothem diante de cada leitor, e desinstalar o proprietário o remove de cada
leitor.

| Caminho | Proprietário | Leitores |
| --- | --- | --- |
| `~/.agents/skills/` | Codex | Cursor, Gemini CLI, GitHub Copilot, Kimi Code, Open-Claw, OpenCode, Windsurf, Zed |
| `~/.claude/skills/` | Claude Code | Cursor, OpenCode |
| `~/.claude/CLAUDE.md` | Claude Code | OpenCode |
| `<project>/AGENTS.md` | Kimi Code | Antigravity, CodeBuddy, Codex, Cursor, GitHub Copilot, Hermes, Kiro, OpenCode, Windsurf, Zed |
| `<project>/GEMINI.md` | Gemini CLI | Antigravity, GitHub Copilot, Zed |
| `~/.gemini/GEMINI.md` | Antigravity | Gemini CLI |
| `<project>/.github/copilot-instructions.md` | GitHub Copilot | Zed |

O bloco do Apothem que um proprietário grava em um arquivo de instruções
compartilhado não nomeia nenhuma ferramenta específica como sua leitora.
`tests/unit/test_shared_roots.py` falha quando dois adaptadores gravam o mesmo
alvo do registro, e quando um alvo do registro cujo nome é o de um arquivo de
instruções entre ferramentas (`AGENTS.md`, `CLAUDE.md`, `GEMINI.md`,
`copilot-instructions.md`) não tem um proprietário declarado. A única exceção é
`~/.codex/AGENTS.md`, cujo carregamento nenhum outro harness registrado
documenta.

## Hooks de validação

O registro permanece sincronizado por meio destas verificações:

| Verificação | Propósito |
| --- | --- |
| `python scripts/dev/validate_harness_convention_pins.py --today YYYY-MM-DD` | Confirma que cada adaptador tem um pin de convenção que não tem mais de 90 dias de idade, cita pelo menos uma URL do fornecedor e não tem nenhum alvo de descoberta vencido. A CI o executa em cada pull request, semanalmente e antes de um lançamento. |
| `python scripts/dev/check_vendor_urls.py` | Busca cada URL de fornecedor que os pins e os templates de harness citam e falha diante de uma página movida ou inativa, incluindo um nome de host que não resolve mais ou um certificado que falha na verificação; um tempo limite esgotado, uma conexão recusada ou redefinida, ou um erro de servidor 5xx é relatado como inacessível e não o faz falhar. O monitor semanal de convenções o executa. |
| `python -m apothem.conformity.gate --all .` | Executa as verificações de conformidade de documentação e de implementação. |
| `python -m pytest` | Exercita os testes de fixtures do registro e os testes de contrato dos adaptadores. |
