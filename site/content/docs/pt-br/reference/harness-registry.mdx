O registro de harnesses é o inventário de adaptadores que serve como fonte de
verdade para a CLI, a documentação, os testes de fixtures e a validação dos pins
de convenção. A fonte em tempo de execução é
`src/apothem/lib/harness_registry.py`; cada linha abaixo é rastreável até esse
registro, até o `capabilities.yml` de cada adaptador e até o
`STANDARD-CONVENTION-PIN.md` de cada adaptador.

## Suporte a cohorts de payload

Os valores de status são `native`, `converted`, `support-tree`,
`profile-projected`, `unsupported`, `not-applicable` e
`discovery-pending`.

Um cohort `converted` é reescrito no formato próprio do harness, e alguns campos
de origem não têm lugar nele. Para cada cohort convertido de comandos, agentes ou
regras, o `capabilities.yml` do adaptador carrega um mapa `conversion_losses`
que informa o que acontece com cada campo de frontmatter de origem:

| Valor | Significado |
| --- | --- |
| `native:<field>` | O harness o lê sob esse campo. |
| `sidecar:<path>` | Ele é gravado em um arquivo separado ao lado do arquivo convertido, como o `agents/openai.yaml` do Codex. |
| `filename` | O nome do arquivo ou da pasta o carrega. |
| `inlined` | Ele passa para o texto do prompt ou do corpo. |
| `ignored` | Ele permanece no arquivo, mas o harness não o lê. |
| `dropped` | Ele é omitido. |

Um teste renderiza cada arquivo convertido e confere os mapas contra a saída.

| Harness | Payloads nativos ou convertidos | Payloads na árvore de suporte | Avisos de não suportado ou pendente |
| --- | --- | --- | --- |
| Antigravity | comandos, agentes e regras convertidos; skills, despacho de subagentes e templates de prompt de sistema nativos | hooks, templates | statuslines, output-styles; descoberta de MCP e de memória pendente |
| Claude Code | comandos convertidos; skills, hooks, agentes, regras, statuslines, output-styles e despacho de subagentes nativos | templates | `CLAUDE.md` continua sendo de propriedade do operador, exceto pelo único bloco do Apothem; nenhum template de prompt de sistema gravado pelo adaptador; descoberta de MCP pendente |
| CodeBuddy | comandos e agentes convertidos; skills, hooks, regras, despacho de subagentes e templates de prompt de sistema nativos | templates | statuslines, output-styles; descoberta de MCP pendente |
| Codex | comandos e agentes convertidos; skills, hooks, despacho de subagentes e templates de prompt de sistema nativos | regras, templates | statuslines, output-styles; descoberta de MCP pendente porque o Apothem não sobrescreve `config.toml` |
| Cursor | comandos e agentes convertidos; skills, hooks, regras, despacho de subagentes e templates de prompt de sistema nativos | templates | statuslines, output-styles, memória; descoberta de MCP pendente |

`Hermes`, `Kiro`, `Open-Claw`, `OpenCode` e `Qwen Code`.

## Raízes compartilhadas

Alguns alvos de instalação são carregados por harnesses diferentes daquele que
os grava. O registro anota cada um desses caminhos em `SHARED_ROOTS` com um
proprietário registrado (o adaptador para o qual o fornecedor documenta o caminho),
os coinstaladores que gravam os mesmos arquivos nele e os leitores cuja documentação do
fornecedor o carrega por padrão, além das páginas do fornecedor que o mostram e
da data em que foram obtidas.

Um caminho com coinstaladores é uma pasta de nível de usuário no diretório pessoal que
várias instalações gravam com os mesmos bytes. Uma máquina com apenas o `Cursor`
instalado não tem um `Codex` para gravar `~/.agents/skills/`, de modo que cada instalação que
nomeia a pasta a grava, e o livro-razão de instalação conta as instalações que a
usam. O proprietário de referência é o proprietário registrado enquanto ele usa a pasta e,
caso contrário, a instalação mais antiga que a usa; nada muda quando o proprietário registrado
é desinstalado. Uma desinstalação remove a pasta somente quando nenhuma outra instalação ainda
a usa (veja [`uninstall`](/docs/cli-reference/uninstall#shared-folders-in-your-home-directory)).
Instalar um leitor não coloca nenhum arquivo na pasta; instalar o proprietário ou um
coinstalador coloca o conteúdo do Apothem diante de cada leitor.

| Caminho | Proprietário | Coinstaladores | Leitores |
| --- | --- | --- | --- |
| `~/.agents/skills/` | Codex | Cursor, GitHub Copilot, Windsurf, Zed | Gemini CLI, Kimi Code, Open-Claw, OpenCode, Qwen Code |
| `~/.config/apothem/rules/` | Codex | CodeBuddy, Cursor, GitHub Copilot, Kiro, Trae, Windsurf, Zed | nenhum |
| `~/.config/apothem/templates/` | Codex | CodeBuddy, Cursor, GitHub Copilot, Kiro, Trae, Windsurf, Zed | nenhum |
| `~/.claude/skills/` | Claude Code | nenhum | Cursor, OpenCode |
| `~/.claude/agents/` | Claude Code | nenhum | Cursor |
| `~/.codex/agents/` | Codex | nenhum | Cursor |
| `~/.claude/CLAUDE.md` | Claude Code | nenhum | OpenCode, Windsurf |
| `<project>/AGENTS.md` | Kimi Code | nenhum | Antigravity, Claude Code, CodeBuddy, Codex, Cursor, GitHub Copilot, Hermes, Kiro, OpenCode, Windsurf, Zed |
| `<project>/GEMINI.md` | Gemini CLI | nenhum | Antigravity, GitHub Copilot, Zed |
| `~/.gemini/GEMINI.md` | Antigravity | nenhum | Gemini CLI |
| `<project>/.github/copilot-instructions.md` | GitHub Copilot | nenhum | Zed |
| `<project>/.cursor/rules/apothem-rules.mdc` | Cursor | nenhum | Hermes, Windsurf |

`~/.config/apothem/rules/` e `~/.config/apothem/templates/` contêm os arquivos
que as skills e os arquivos de instruções do próprio Apothem citam. Nenhuma outra ferramenta os carrega, então
eles não têm leitores nem páginas do fornecedor. `CodeBuddy`, `Kiro` e `Trae` também
gravam uma pasta de skills própria (`~/.codebuddy/skills/`, `~/.kiro/skills/`
e `~/.trae/skills/`); somente essa ferramenta a carrega, então ela não é uma raiz compartilhada.

Um leitor só é listado onde a documentação do seu fornecedor mostra um carregamento padrão desse
caminho exato. Quando um leitor carrega um caminho apenas em alguns casos, o
registro anota a condição, e a nota de instalação a repete. `Open-Claw` indexa
`~/.agents/skills/` somente sob o seu diretório de
estado padrão (ele ignora a pasta quando `OPENCLAW_STATE_DIR` aponta para outro
lugar). O `OpenCode` 1 carrega `~/.claude/CLAUDE.md` somente quando a sua pasta
de configuração (`~/.config/opencode/` por padrão) não contém nenhum
`AGENTS.md`, e ignora esse arquivo quando
`OPENCODE_DISABLE_CLAUDE_CODE_PROMPT=1` ou `OPENCODE_DISABLE_CLAUDE_CODE=1`
estiver definido. O `OpenCode` 2 lê a mesma configuração de
`~/.config/opencode/`, mas não usa `CLAUDE.md` como alternativa, então não
carrega `~/.claude/CLAUDE.md`. O `Codex` usa o primeiro entre
`AGENTS.override.md` e `AGENTS.md` em cada pasta, então carrega
`<project>/AGENTS.md` somente quando o projeto não tem `AGENTS.override.md` ao
lado desse arquivo. O `CodeBuddy` usa `<project>/AGENTS.md` como memória de
projeto somente quando o projeto não tem `CODEBUDDY.md`. O `Claude Code` lê `AGENTS.md` nas versões
que a sua [página de memória](https://code.claude.com/docs/en/memory#agents-md) nomeia, e
a nota de instalação informa a primeira delas. Com a configuração padrão **Project
instructions**, ele carrega todos os `AGENTS.md` e `.claude/AGENTS.md` da
pasta de trabalho e das pastas acima dela quando uma sessão começa, mas somente
quando nenhuma dessas pastas contém um `CLAUDE.md`, `.claude/CLAUDE.md` ou
`CLAUDE.local.md`. Ele carrega o `AGENTS.md` de uma pasta abaixo da pasta de
trabalho, como um projeto aberto a partir de uma pasta pai, quando a sua ferramenta Read
abre um arquivo ali e essa pasta também não tem nenhum desses três arquivos.
`~/.claude/CLAUDE.md` não conta, então o bloco do Apothem ali continua sendo carregado
junto com `<project>/AGENTS.md`. A configuração `claude-md-and-agents-md` carrega
os dois tipos de arquivo, e `claude-md` e `managed-only` não carregam nenhum `AGENTS.md`.
Algumas sessões não leem nenhum `AGENTS.md` em nenhuma configuração; a página de memória
as lista. O `Zed` carrega apenas
o primeiro arquivo de instruções do projeto da sua lista: `.rules`,
`.cursorrules`, `.windsurfrules`, `.clinerules`,
`.github/copilot-instructions.md`, `AGENT.md`, `AGENTS.md`, `CLAUDE.md` e depois
`GEMINI.md`. Assim, ele carrega `<project>/.github/copilot-instructions.md`,
`<project>/AGENTS.md` e `<project>/GEMINI.md` somente quando o projeto não tem
nenhum dos arquivos que vêm antes desse arquivo na lista. A instalação do `Zed`
grava `<project>/.rules`, o primeiro arquivo da lista, então o `Zed` não carrega
nenhum dos três em um projeto em que foi instalado.

O `Hermes` carrega um tipo de contexto do projeto por sessão: o primeiro tipo com
um arquivo não vazio, na ordem `.hermes.md` ou `HERMES.md`, a cadeia de
`AGENTS.md` (em cada pasta, um `AGENTS.override.md` não vazio substitui o
`AGENTS.md` ao lado dele), `CLAUDE.md` e depois as regras do `Cursor`. Assim, ele
carrega `<project>/AGENTS.md` somente quando o projeto não tem `.hermes.md` nem
`HERMES.md` e não tem `AGENTS.override.md` ao lado desse arquivo, e
`<project>/.cursor/rules/apothem-rules.mdc` somente quando o projeto não tem
`.hermes.md`, `HERMES.md`, `AGENTS.override.md`, `AGENTS.md` nem `CLAUDE.md`. O
`Hermes` procura `.hermes.md` e `HERMES.md` a partir da pasta em que inicia,
subindo até a raiz do repositório, e lê a cadeia de `AGENTS.md` da raiz do
repositório para baixo, então um arquivo desses em uma pasta acima do projeto
também conta. Um arquivo vazio não conta. Um `.hermes.md` vazio também oculta um
`HERMES.md` ao lado dele, então o `Hermes` passa para a cadeia de `AGENTS.md`
mesmo quando esse `HERMES.md` tem texto. Essas condições valem para uma sessão
iniciada no projeto. Uma sessão iniciada em uma pasta acima dele ainda pode
carregar `<project>/AGENTS.md`, ou um `AGENTS.override.md` não vazio ao lado
dele, na primeira vez em que ela trabalha em um arquivo do projeto,
independentemente do `.hermes.md` ou `HERMES.md` que o projeto tenha. O `Hermes`
ignora isso em um diretório pessoal e em algumas pastas contêiner.

A documentação do `Cursor`
lista `~/.codex/agents/` como uma pasta de compatibilidade com o `Codex`, mas não diz
quais formatos de arquivo o `Cursor` interpreta ali, e uma instalação do `Codex` grava arquivos
TOML, então não está confirmado se o `Cursor` lê esses auxiliares. A instalação do `Cursor`
também grava sua própria cópia `<project>/.cursor/agents/` dos auxiliares,
que a precedência do fornecedor classifica acima das pastas que ele importa, de modo que, em um
projeto instalado, a cópia nativa prevalece sobre a de `~/.claude/agents/`.

O `Windsurf` lê os arquivos de regras de outras ferramentas por meio da
importação de configuração do Devin, que vem ativada por padrão, e o agente
Local do Devin Desktop encontra seus arquivos do mesmo jeito que a Devin CLI.
Assim, ele carrega o bloco de `~/.claude/CLAUDE.md` que a instalação do
`Claude Code` grava e o arquivo da instalação do `Cursor`,
`<project>/.cursor/rules/apothem-rules.mdc`, cujo frontmatter
`alwaysApply: true` o mantém ativo em todas as sessões. A importação também lê
um `CLAUDE.md` do projeto, que nenhuma instalação do Apothem grava.

Algumas ferramentas deliberadamente não são leitoras de `~/.agents/skills/`: a documentação do
`Antigravity`, do `CodeBuddy`, do `Kiro` e do `Trae` não diz que elas a carregam por
padrão (o `Trae` carrega a pasta `.agents/skills/` do projeto somente depois que uma configuração
é ativada), e é por isso que `CodeBuddy`, `Kiro` e `Trae` recebem uma pasta de skills
própria. A documentação do `Hermes` a nomeia apenas como um valor de exemplo para
`skills.external_dirs`. O `GitHub Copilot` não é leitor de `~/.claude/agents/`:
a documentação do VS Code lista essa pasta para o agente Anthropic Claude, não para o
agente que o `GitHub Copilot` executa.

O bloco do Apothem que um proprietário grava em um arquivo de instruções
compartilhado não nomeia nenhuma ferramenta específica como sua leitora.
`tests/unit/test_shared_roots.py` falha quando os adaptadores que gravam um
alvo do registro não são exatamente o seu proprietário e os seus coinstaladores, e quando um alvo do registro cujo nome é o de um arquivo de
instruções entre ferramentas (`AGENTS.md`, `CLAUDE.md`, `GEMINI.md`,
`copilot-instructions.md`) não tem um proprietário declarado, salvo
`~/.codex/AGENTS.md`, cujo carregamento nenhum outro harness registrado
documenta.

## Hooks de validação

O registro permanece sincronizado por meio destas verificações:

| Verificação | Propósito |
| --- | --- |
| `python scripts/dev/validate_harness_convention_pins.py --today YYYY-MM-DD` | Confirma que cada adaptador tem um pin de convenção que não tem mais de 90 dias de idade, cita pelo menos uma URL do fornecedor e não tem nenhum alvo de descoberta vencido. A CI o executa em cada pull request, semanalmente e antes de um lançamento. |
| `python scripts/dev/check_vendor_urls.py` | Busca cada URL de fornecedor que os pins e os templates de harness citam e falha diante de uma página movida ou inativa, incluindo um nome de host que não resolve mais ou um certificado que falha na verificação; um tempo limite esgotado, uma conexão recusada ou redefinida, ou um erro de servidor 5xx é relatado como inacessível e não o faz falhar. Um nome de host que resolve apenas para um endereço de espaço reservado que nenhum servidor pode ter (os servidores de nomes de um fornecedor podem devolver esse endereço para a região de onde a verificação é executada) não recebe nenhuma requisição: ele é relatado como não roteável, não faz a verificação falhar, e suas páginas precisam de uma verificação manual. O monitor semanal de convenções o executa, emite um aviso para cada host desse tipo a cada execução e lista as páginas desses hosts na issue que ele abre. |
| `python scripts/dev/check_vendor_releases.py` | Consulta cada canal de lançamento em `scripts/dev/vendor-release-channels.json` sobre a sua versão atual: a dist-tag de um pacote npm, o lançamento mais recente de um repositório GitHub (ou, para um canal com um padrão de tag, o seu lançamento estável mais novo com uma tag correspondente entre os 100 mais novos), ou um projeto PyPI. Para um endereço de instalador, pergunta para onde o endereço redireciona. Compara a resposta com o que foi revisado por último. Uma nova versão major, um lançamento que passa de um gatilho que o arquivo nomeia, um endereço de instalador que redireciona para outro lugar, ou um pacote, dist-tag, lançamento ou endereço que não existe mais o faz falhar, assim como um padrão de tag ao qual nenhum lançamento estável entre os 100 mais novos corresponde. Uma versão minor ou patch mais nova é relatada e não o faz falhar, a menos que o nível `watch` do canal nomeie esse nível. Um registro que não responde, ou cuja resposta é interrompida no meio, é relatado como inacessível e também não o faz falhar. Cada tentativa de requisição tem 30 segundos no total e, após 20 minutos, a verificação não consulta mais nenhum canal, de modo que sempre grava o seu relatório. Antes de qualquer requisição, verifica se cada pasta de harness tem uma entrada e se a frase de evidência de cada canal está no seu pin, e sai com 1 quando uma não está; o relatório e a issue então dizem o que está errado. O monitor semanal de convenções o executa com um token somente leitura, lista cada canal no resumo da execução e abre uma issue quando ele falha. `--list` imprime os canais sem consultar nenhum registro. |
| `python3 -E -s src/apothem/conformity/gate.py --all .` | Executa as verificações de conformidade de documentação e de implementação. |
| `python -m pytest` | Exercita os testes de fixtures do registro e os testes de contrato dos adaptadores. |

## Canais de lançamento

`scripts/dev/vendor-release-channels.json` tem uma entrada para cada pasta de
harness. Um harness monitorado lista os seus canais de lançamento. Cada canal registra a
versão revisada por último, com a data. Essa é a versão que o seu pin nomeia ou,
quando o pin não nomeia nenhuma, a versão que o registro servia quando o canal
foi registrado. Um registro também pode conter apenas uma versão major. Cada canal cita
a frase do pin que o nomeia. O primeiro número de uma versão é a sua
versão major, incluindo 0, então uma linha 0.x que passa de 0.26 para 0.27 relata
uma versão minor mais nova e não falha. Um canal com versões de calendário,
como os números ano.mês.lançamento do OpenClaw, relata cada lançamento mais novo
sem falhar e não aceita nível `watch`. Codex, Gemini CLI, Hermes, Qwen
Code e GLM estão em linhas 0.x, então uma nova versão de um deles é listada no
resumo da execução e não abre nenhuma issue até chegar a 1.0, a menos que o seu canal
defina um nível `watch`.

O OpenCode tem quatro canais. `opencode-ai` traz o OpenCode 1, e
`@opencode/cli` traz o OpenCode 2. Os lançamentos no GitHub de `anomalyco/opencode`
mostram uma nova linha major qualquer que seja o pacote npm em que ela é distribuída. O
quarto canal pergunta para onde `opencode.ai/install` redireciona. Em 2026-11-03, ele
redirecionava para o script de instalação do OpenCode 1. Esse script instala a versão que a
dist-tag `latest` de `opencode-ai` nomeia quando ela é uma versão do OpenCode 1,
e nunca instala o OpenCode 2. A decisão sobre o OpenCode de 2026-11-03 passa a
gravar os formatos próprios do OpenCode 2 onde o OpenCode 2 é executado quando surgir um
de dois sinais: o OpenCode 2 anuncia uma data para remover a sua tradução dos
formatos do OpenCode 1, ou `opencode.ai/install` ou `opencode-ai` passa para o
OpenCode 2. A verificação monitora o segundo sinal. O canal `opencode-ai` e
o canal do instalador têm cada um um gatilho: a verificação falha quando a
versão `latest` de `opencode-ai` passa da versão major 1, ou quando
`opencode.ai/install` deixa de redirecionar para o script do OpenCode 1. Uma alteração
dentro desse script não altera o redirecionamento, então a verificação não a
vê. Nenhum registro responde ao primeiro sinal, então ele continua sendo uma verificação
manual, com prazo até 2027-02-01, junto com a próxima revisão do pin do OpenCode.

Antigravity, Cursor, Kiro, Trae e Windsurf não são monitorados. Cada um é um
aplicativo de desktop, ou uma ferramenta de linha de comando que se instala com um script,
e o seu pin não nomeia nenhum canal de lançamento que um script possa consultar sem
credenciais. O arquivo informa o motivo de cada um.

Depois de verificar novamente um pin em relação a um novo lançamento ou destino de
redirecionamento, atualize os campos `reviewed`, `reviewed_on` e `reviewed_from` desse
canal. Um gatilho em um canal de versão faz a verificação falhar toda semana até que você o
remova ou altere. Um gatilho em um endereço de instalador para assim que `reviewed`
registra o novo destino, então registre esse destino somente depois que a ação do gatilho
estiver concluída.
