O registro de harnesses é o inventário de adaptadores que serve como fonte de
verdade para a CLI, a documentação, os testes de fixtures e a validação dos pins
de convenção. A fonte em tempo de execução é
`src/apothem/lib/harness_registry.py`; cada linha abaixo é rastreável até esse
registro, até o `capabilities.yml` de cada adaptador e até o
`STANDARD-CONVENTION-PIN.md` de cada adaptador.

## Suporte a cohorts de payload

Os valores de status são `native`, `converted`, `support-tree`,
`profile-projected`, `unsupported`, `not-applicable` e
`discovery-pending`.

Um cohort `converted` é reescrito no formato próprio do harness, e alguns campos
de origem não têm lugar nele. Para cada cohort convertido de comandos, agentes ou
regras, o `capabilities.yml` do adaptador carrega um mapa `conversion_losses`
que informa o que acontece com cada campo de frontmatter de origem:

| Valor | Significado |
| --- | --- |
| `native:<field>` | O harness o lê sob esse campo. |
| `sidecar:<path>` | Ele é gravado em um arquivo separado ao lado do arquivo convertido, como o `agents/openai.yaml` do Codex. |
| `filename` | O nome do arquivo ou da pasta o carrega. |
| `inlined` | Ele passa para o texto do prompt ou do corpo. |
| `ignored` | Ele permanece no arquivo, mas o harness não o lê. |
| `dropped` | Ele é omitido. |

Um teste renderiza cada arquivo convertido e confere os mapas contra a saída.

| Harness | Payloads nativos ou convertidos | Payloads na árvore de suporte | Avisos de não suportado ou pendente |
| --- | --- | --- | --- |
| Antigravity | comandos, agentes e regras convertidos; skills, despacho de subagentes e templates de prompt de sistema nativos | hooks, templates | statuslines, output-styles; descoberta de MCP e de memória pendente |
| Claude Code | comandos convertidos; skills, hooks, agentes, regras, statuslines, output-styles e despacho de subagentes nativos | templates | `CLAUDE.md` continua sendo de propriedade do operador, exceto pelo único bloco do Apothem; nenhum template de prompt de sistema gravado pelo adaptador; descoberta de MCP pendente |
| CodeBuddy | comandos e agentes convertidos; skills, hooks, regras, despacho de subagentes e templates de prompt de sistema nativos | templates | statuslines, output-styles; descoberta de MCP pendente |
| Codex | comandos e agentes convertidos; skills, hooks, despacho de subagentes e templates de prompt de sistema nativos | regras, templates | statuslines, output-styles; descoberta de MCP pendente porque o Apothem não sobrescreve `config.toml` |
| Cursor | comandos e agentes convertidos; skills, hooks, regras, despacho de subagentes e templates de prompt de sistema nativos | templates | statuslines, output-styles, memória; descoberta de MCP pendente |

`Hermes`, `Kiro`, `Open-Claw`, `OpenCode` e `Qwen Code`.

## Raízes compartilhadas

Alguns alvos de instalação são carregados por harnesses diferentes daquele que
os grava. O registro anota cada um desses caminhos em `SHARED_ROOTS` com um
proprietário registrado (o adaptador para o qual o fornecedor documenta o caminho),
os coinstaladores que gravam os mesmos arquivos nele e os leitores cuja documentação do
fornecedor o carrega por padrão, além das páginas do fornecedor que o mostram e
da data em que foram obtidas.

Um caminho com coinstaladores é uma pasta de nível de usuário no diretório pessoal que
várias instalações gravam com os mesmos bytes. Uma máquina com apenas o `Cursor`
instalado não tem um `Codex` para gravar `~/.agents/skills/`, de modo que cada instalação que
nomeia a pasta a grava, e o livro-razão de instalação conta as instalações que a
usam. O proprietário de referência é o proprietário registrado enquanto ele usa a pasta e,
caso contrário, a instalação mais antiga que a usa; nada muda quando o proprietário registrado
é desinstalado. Uma desinstalação remove a pasta somente quando nenhuma outra instalação ainda
a usa (veja [`uninstall`](/docs/cli-reference/uninstall#pastas-compartilhadas-no-seu-diretório-pessoal)).
Instalar um leitor não coloca nenhum arquivo na pasta; instalar o proprietário ou um
coinstalador coloca o conteúdo do Apothem diante de cada leitor.

| Caminho | Proprietário | Coinstaladores | Leitores |
| --- | --- | --- | --- |
| `~/.agents/skills/` | Codex | Cursor, GitHub Copilot, Windsurf, Zed | Gemini CLI, Kimi Code, Open-Claw, OpenCode, Qwen Code |
| `~/.config/apothem/rules/` | Codex | CodeBuddy, Cursor, GitHub Copilot, Kiro, Trae, Windsurf, Zed | nenhum |
| `~/.config/apothem/templates/` | Codex | CodeBuddy, Cursor, GitHub Copilot, Kiro, Trae, Windsurf, Zed | nenhum |
| `~/.claude/skills/` | Claude Code | nenhum | Cursor, OpenCode |
| `~/.claude/agents/` | Claude Code | nenhum | Cursor |
| `~/.codex/agents/` | Codex | nenhum | Cursor |
| `~/.claude/CLAUDE.md` | Claude Code | nenhum | OpenCode |
| `<project>/AGENTS.md` | Kimi Code | nenhum | Antigravity, CodeBuddy, Codex, Cursor, GitHub Copilot, Hermes, Kiro, OpenCode, Windsurf, Zed |
| `<project>/GEMINI.md` | Gemini CLI | nenhum | Antigravity, GitHub Copilot, Zed |
| `~/.gemini/GEMINI.md` | Antigravity | nenhum | Gemini CLI |
| `<project>/.github/copilot-instructions.md` | GitHub Copilot | nenhum | Zed |

`~/.config/apothem/rules/` e `~/.config/apothem/templates/` contêm os arquivos
que as skills e os arquivos de instruções do próprio Apothem citam. Nenhuma outra ferramenta os carrega, então
eles não têm leitores nem páginas do fornecedor. `CodeBuddy`, `Kiro` e `Trae` também
gravam uma pasta de skills própria (`~/.codebuddy/skills/`, `~/.kiro/skills/`
e `~/.trae/skills/`); somente essa ferramenta a carrega, então ela não é uma raiz compartilhada.

Um leitor só é listado onde a documentação do seu fornecedor mostra um carregamento padrão desse
caminho exato. Um leitor traz uma condição, e a nota de instalação a repete:
`Open-Claw` indexa `~/.agents/skills/` somente sob o seu diretório de estado padrão
(ele ignora a pasta quando `OPENCLAW_STATE_DIR` aponta para outro lugar). A documentação do `Cursor`
lista `~/.codex/agents/` como uma pasta de compatibilidade com o `Codex`, mas não diz
quais formatos de arquivo o `Cursor` interpreta ali, e uma instalação do `Codex` grava arquivos
TOML, então não está confirmado se o `Cursor` lê esses auxiliares. A instalação do `Cursor`
também grava sua própria cópia `<project>/.cursor/agents/` dos auxiliares,
que a precedência do fornecedor classifica acima das pastas que ele importa, de modo que, em um
projeto instalado, a cópia nativa prevalece sobre a de `~/.claude/agents/`.

Algumas ferramentas deliberadamente não são leitoras de `~/.agents/skills/`: a documentação do
`Antigravity`, do `CodeBuddy`, do `Kiro` e do `Trae` não diz que elas a carregam por
padrão (o `Trae` carrega a pasta `.agents/skills/` do projeto somente depois que uma configuração
é ativada), e é por isso que `CodeBuddy`, `Kiro` e `Trae` recebem uma pasta de skills
própria. A documentação do `Hermes` a nomeia apenas como um valor de exemplo para
`skills.external_dirs`. O `GitHub Copilot` não é leitor de `~/.claude/agents/`:
a documentação do VS Code lista essa pasta para o agente Anthropic Claude, não para o
agente que o `GitHub Copilot` executa.

O bloco do Apothem que um proprietário grava em um arquivo de instruções
compartilhado não nomeia nenhuma ferramenta específica como sua leitora.
`tests/unit/test_shared_roots.py` falha quando os adaptadores que gravam um
alvo do registro não são exatamente o seu proprietário e os seus coinstaladores, e quando um alvo do registro cujo nome é o de um arquivo de
instruções entre ferramentas (`AGENTS.md`, `CLAUDE.md`, `GEMINI.md`,
`copilot-instructions.md`) não tem um proprietário declarado. A única exceção é
`~/.codex/AGENTS.md`, cujo carregamento nenhum outro harness registrado
documenta.

## Hooks de validação

O registro permanece sincronizado por meio destas verificações:

| Verificação | Propósito |
| --- | --- |
| `python scripts/dev/validate_harness_convention_pins.py --today YYYY-MM-DD` | Confirma que cada adaptador tem um pin de convenção que não tem mais de 90 dias de idade, cita pelo menos uma URL do fornecedor e não tem nenhum alvo de descoberta vencido. A CI o executa em cada pull request, semanalmente e antes de um lançamento. |
| `python scripts/dev/check_vendor_urls.py` | Busca cada URL de fornecedor que os pins e os templates de harness citam e falha diante de uma página movida ou inativa, incluindo um nome de host que não resolve mais ou um certificado que falha na verificação; um tempo limite esgotado, uma conexão recusada ou redefinida, ou um erro de servidor 5xx é relatado como inacessível e não o faz falhar. O monitor semanal de convenções o executa. |
| `python -m apothem.conformity.gate --all .` | Executa as verificações de conformidade de documentação e de implementação. |
| `python -m pytest` | Exercita os testes de fixtures do registro e os testes de contrato dos adaptadores. |
