**Vendor:** OpenCode
**Install name:** `opencode`
**Status:** Beta
**Native config:** `~/.config/opencode/` (or `$XDG_CONFIG_HOME/opencode/`)

## Installation

```bash
apothem install --harness opencode
```

The adapter writes OpenCode's JSON config, installs Apothem skills into the
OpenCode skills surface, converts command prompts to OpenCode Markdown command
files, and normalizes Apothem helper definitions as OpenCode subhelpers.

**Files written:**

```text
~/.config/opencode/opencode.json
~/.config/opencode/apothem/rules/00-apothem-profile.md
~/.config/opencode/commands/
~/.config/opencode/skills/
~/.config/opencode/agents/
~/.config/opencode/.apothem/support/{rules,templates,hooks}/
```

These are the default paths. When `XDG_CONFIG_HOME` is set to an absolute
folder, the adapter writes to `$XDG_CONFIG_HOME/opencode/` instead, the folder
both OpenCode 1 and OpenCode 2 read. A relative value or a filesystem root is
not used, and the install says so. `OPENCODE_CONFIG_DIR` is not followed:
OpenCode 1 reads that folder as well as the default one, but OpenCode 2 reads it
instead, so when it names another folder the install warns that OpenCode 2 does
not load the install.

A `~/.config` that is a link into your home directory, as dotfile managers
make it, is followed. On Windows a junction counts as a link. When that link
leads outside your home directory, the install stops with `target path crosses
a symlink` before it writes any file. On a first run, with no profile yet, it
stops one step earlier, before the starter profile is written, with `Apothem
could not create the starter profile`. To keep the profile outside your home
directory, create it there with `apothem profile init --profile PATH` and pass
the same `--profile PATH` to the install; the install then still needs
`XDG_CONFIG_HOME`, as described below. An `XDG_CONFIG_HOME` spelled inside
your home directory that a link leads out of it, such as `~/xdg` linked to
another drive, stops the install, the uninstall and `apothem rollback` too. A
link on a path the install writes inside `~/.config/opencode/` stops it as
well, with `target path crosses a symlink`, or with `target escapes the
allowed materialization root` when that link leads out of `~/.config`.

To install through a `~/.config` link that leaves your home directory, set
`XDG_CONFIG_HOME` to the folder the link leads to, spelled as that folder's own
path, outside your home directory. Only the path as you spell it counts: a
path outside your home directory is followed wherever its links lead. The
install then writes there, and the `instructions` entries an install made
earlier in `~/.config/opencode` wrote are replaced, so the config lists each
file once. An uninstall with the same setting removes that earlier install as
well, also when nothing was installed with the setting first: its
`opencode.json`, once only Apothem's entries were in it, is copied into the
Apothem backup root (`~/.apothem/backups/`) before it goes, and the empty
folders that install created go too. When `XDG_CONFIG_HOME` names `~/.config`
by another spelling inside your home directory (`$HOME/.config` through a
link, another case, or a short name), the install keeps using
`~/.config/opencode`, so it stays one install.

## Profile-to-native-config mapping

The adapter renders `opencode.json` with an `instructions` file list naming
your profile document, the four core rules, and the rule index, then propagates
each shared Apothem cohort into either a native OpenCode surface or an
Apothem-owned support subtree. Existing matching Apothem-managed children are
backed up before replacement.

## Compatibility notes

The install works with OpenCode 1 and OpenCode 2. It writes one
configuration, which OpenCode 1 reads as it is and OpenCode 2 translates:
both read the same configuration folder, and OpenCode 2 converts the OpenCode
1 forms the install writes in memory, without rewriting the file. The helper
`permission` lists and the `mcp` server entries load in OpenCode 2 through
that translation. OpenCode 1 also loads the
block a Claude Code install writes to `~/.claude/CLAUDE.md` when its
configuration folder holds no `AGENTS.md` and neither
`OPENCODE_DISABLE_CLAUDE_CODE` nor `OPENCODE_DISABLE_CLAUDE_CODE_PROMPT` is
set; OpenCode 2 has no `CLAUDE.md` fallback, so it does not load that file.

Helper definitions carry only `deny` rules, for the tools a helper must not
use. OpenCode allows every tool by default and asks before it reads a `.env` or
`.env.*` file. An `allow` rule in a helper would turn that question off and
would override a stricter rule in your own OpenCode config, so a helper follows
your `permission` settings.

When the shared profile lists MCP servers, the install writes them to the `mcp`
block of `opencode.json`. OpenCode substitutes `{env:NAME}`, not `${NAME}`, so
each `${NAME}` in a server's environment, headers or URL is written as
`{env:NAME}`. Command arguments are copied as written: a reference there is
left for the server, or a shell it runs, to expand. The install warns about
two kinds of `$` reference OpenCode does not expand, which the server then
receives as written: a `$NAME` in an environment or header value, and any
other `${...}` form, a plain `${NAME}` in a command argument included. The
warning names where the reference sits, such as `environment.TOKEN`, and never
prints the value.

OpenCode inserts an `{env:NAME}` value into the config text it reads without
escaping it; OpenCode 2 escapes it only when that text would not parse
otherwise. So a value with a backslash (such as a Windows path), a double
quote or a control character can stop OpenCode 1 from reading the file, and
in both lines a `\t` or `\n` in it reaches the server as a control character.
The install checks each such variable when it runs and warns about one that
holds those characters. Restate that whole server under
`harnesses.opencode.mcp_servers.<name>`, since an override replaces the whole
server, and write the value there as `{file:path}`; the other tools keep the
`${NAME}` reference.

OpenCode combines every file the `instructions` list names into every session
([OpenCode rules](https://opencode.ai/docs/rules/)). The list therefore names
your profile document first, then only the rules whose `alwaysApply` is
`true`, one explicit path each, `~/.config/opencode/.apothem/support/rules/<name>.md`
by default. OpenCode expands a leading `~/` against your home directory; the
path is absolute when the configuration folder is outside it, and the
support tree always sits under the configuration folder. Those rules are
`agnostic-posture`, `authority-inquiry`, `context-management`,
`session-closure`, and the rule index, `apothem-rule-index`. OpenCode scopes no
rule by path, so every other rule is read on demand. It stays installed as
reference material under `~/.config/opencode/.apothem/support/`, and the index
names each rule and the situation that calls for it. A rule, skill, or command
that cites a rule, template, or hook prompt reads it from there. Commands,
skills, and helper definitions use native discovery locations.

Every install and update deletes every file in
`~/.config/opencode/apothem/rules/` that Apothem did not put there, after
saving it in a backup set under `~/.apothem/backups/`. That backup is deleted
once 10 newer backup sets of the harness exist, so keep your own files
elsewhere.

The profile document `~/.config/opencode/apothem/rules/00-apothem-profile.md`
carries your identity and preferences from the shared profile, and ends with
an Apothem support files section that names the absolute directory under
`~/.config/opencode/.apothem/support/` each repository-style citation
(`rules/<name>.md`, `templates/...`, `hooks/...`) resolves against. It is the
first `instructions` entry, so OpenCode loads it in every session.

An `opencode.json` written by an earlier release lists the single glob
`~/.config/opencode/.apothem/support/rules/*.md`, which loads every rule, or an
explicit path for each of the 28 rules that were then always-on. `apothem
install` and `apothem update` replace either form with the list above, which
drops the 24 paths that no longer load at launch, and `apothem uninstall`
removes all of them. Your own `instructions` entries are kept in every case.

## Verification

```bash
apothem verify --harness opencode
```

The verify command confirms that:

1. The native config exists at the expected path.
2. Each managed target exists; managed files are non-empty, and JSON or YAML
   configs parse. Add `--profile PATH` to also confirm that the installed files
   match that profile.
3. The adapter-specific verification routine reports success.

## Updating

```bash
apothem update --harness opencode
```

Refreshes `opencode.json`, native commands, skills, helper definitions, and the
Apothem support tree. An MCP server the install wrote that you converted to
OpenCode 2's `mcp.servers` shape, without changing it, is written back under
`mcp`, where both OpenCode lines read it. A server under `mcp.servers` counts
as that conversion only when its `mcp` entry is gone and it matches what the
install wrote as a whole; your own server of the same name, a conversion you
edited and one you disabled are left as they are. Beside such a conversion,
the update writes the server under `mcp` again, so OpenCode 1 uses that copy
and OpenCode 2 the converted one; to keep the server off in both lines,
remove it from the profile. This needs an install record that lists the
entries the install wrote; a record from before Apothem kept that list is not
covered.

## Uninstalling

```bash
apothem uninstall --harness opencode
```

Removes the entries the adapter added to `~/.config/opencode/opencode.json`
(your own keys, MCP servers, and `instructions` entries stay, and the file is
deleted only when Apothem created it and nothing of yours is left). An MCP
server the install wrote that you converted to OpenCode 2's `mcp.servers` shape
without changing it is removed too, as a whole; other servers under
`mcp.servers` stay. A server of your own under `mcp.servers` that matches one
the install wrote, after you removed the install's `mcp` entry, cannot be told
from a converted copy and is removed with it; the file is backed up first.
Removes the
Apothem block from the profile document
`~/.config/opencode/apothem/rules/00-apothem-profile.md` and keeps any other
text in it; that file is deleted only when nothing else remains in it. Also
removes the Apothem files in `~/.config/opencode/commands/`,
`~/.config/opencode/skills/`, `~/.config/opencode/agents/`, and
`~/.config/opencode/.apothem/support/`; other files in those folders stay.
Each file is backed up under `~/.apothem/backups/` before it is changed or
removed. The shared profile YAML and Apothem engine are unaffected.

An install made by an earlier release in `~/.config/opencode/` while
`XDG_CONFIG_HOME` named another folder stays there, and OpenCode never read it.
The next install says so while its files are there; to remove it, run the
uninstall with `XDG_CONFIG_HOME` unset. When `~/.config` has since become a
link that leads out of your home directory, that uninstall is refused with
`target path crosses a symlink`, and the note names the folder the link leads
to instead: run the uninstall with `XDG_CONFIG_HOME` set to that folder.

## Troubleshooting

| Symptom | Fix |
|---------|-----|
| Config file not found | Re-run `apothem install --harness opencode` |
| Verification failed | Run `apothem update --harness opencode`, then verify again |
| Unexpected config content | Check `~/.config/apothem/profile.yaml` or `--profile PATH`, then re-run `apothem update --harness opencode` |
