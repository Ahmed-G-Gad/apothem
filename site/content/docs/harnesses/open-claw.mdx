**Vendor:** Open-Claw
**Install name:** `open-claw`
**Status:** Preview
**Native config:** `~/.openclaw/openclaw.json`

## Installation

```bash
apothem install --harness open-claw
```

The adapter writes OpenClaw's user-global config file, projects the shared
profile into a profile document, writes an Apothem rules file into each
OpenClaw workspace, and installs Apothem support cohorts under the harness root.
OpenClaw's native config is JSON; the materializer renders two entries,
`skills.load.extraDirs` and the `bootstrap-extra-files` hook entry, and an
existing file keeps its other keys.

**Files written:** `~/.openclaw/openclaw.json`, the profile document
`~/.openclaw/apothem/rules/00-apothem-profile.md`, the rules file
`<workspace>/apothem/AGENTS.md` in each workspace, and support files under
`~/.openclaw/.apothem/support/`

Every install and update deletes every file in `~/.openclaw/apothem/rules/`
that Apothem did not put there, after saving it in a backup set under
`~/.apothem/backups/`. That backup is deleted once 10 newer backup sets of the
harness exist, so keep your own files elsewhere.

The profile document ends with an Apothem support files section that names
the absolute directory under `~/.openclaw/.apothem/support/` each
repository-style citation (`rules/<name>.md`, `templates/...`, `hooks/...`)
resolves against.

## Profile-to-native-config mapping

The adapter authors two config entries:

- It adds `~/.openclaw/.apothem/support/skills` to `skills.load.extraDirs`, the
  list of extra skill directories OpenClaw reads, which is how OpenClaw finds
  the installed skills. The entry goes after any entries you already list.
- It adds `apothem/AGENTS.md` to the path list of the
  `hooks.internal.entries.bootstrap-extra-files` entry, which is how OpenClaw
  loads the Apothem rules file (see [Rules in each workspace](#rules-in-each-workspace)).

Your other keys stay as they are, and Apothem never writes
`hooks.internal.enabled`. The profile's identity, preferences, and rules go into
the profile document and into each workspace's rules file. Shared commands,
skills, rules, templates, and hook prompts are installed as support material
under `~/.openclaw/.apothem/support/`.

## Compatibility notes

Preview adapter. OpenClaw loads the Apothem skills through
`skills.load.extraDirs` and the Apothem rules through the rules file in each
workspace. It does not load MCP servers from Apothem.

### Rules in each workspace

OpenClaw puts six files from a workspace into its system prompt: `AGENTS.md`,
`SOUL.md`, `IDENTITY.md`, `USER.md`, `BOOTSTRAP.md`, and `MEMORY.md`. Its
bundled `bootstrap-extra-files` hook adds more files that carry one of those
names, with paths read relative to the workspace of each session. Apothem
writes `apothem/AGENTS.md` into each workspace and lists that path in the
hook's entry:

```json
{
  "hooks": {
    "internal": {
      "entries": {
        "bootstrap-extra-files": {
          "enabled": true,
          "paths": ["apothem/AGENTS.md"]
        }
      }
    }
  }
}
```

The file holds the profile's managed block and a pointer to the rule index
under `~/.openclaw/.apothem/support/`, through which the whole rule set is
reached. Because the file is named `AGENTS.md`, OpenClaw also loads it in cron
sessions and in the helper sessions another session starts, which get only
some of the six files. Apothem never
edits the workspace's own `AGENTS.md`: OpenClaw creates it from a template and
the assistant working in that workspace edits it. A folder named `apothem` does
not count as setup work, so a workspace that OpenClaw has not set up yet still
gets its first-run files.

Apothem writes the file into every workspace that exists in your home
directory: `agents.defaults.workspace` (else `OPENCLAW_WORKSPACE_DIR`, else
`~/.openclaw/workspace`), the `workspace` of each `agents.entries` entry, and
for an entry without one, `<agents.defaults.workspace>/<id>` or
`~/.openclaw/workspace-<id>`. A workspace that does not exist yet is skipped:
once OpenClaw creates it, `apothem verify --harness open-claw` fails until you
run `apothem update --harness open-claw`. A workspace outside your home directory is skipped.

If your config already has a `bootstrap-extra-files` entry, Apothem adds its
path to the list the hook reads: the first non-empty one of `paths`,
`patterns`, and `files`. It never starts a second list that would hide yours.

**When Apothem leaves the hook alone.** In three cases the install writes the
rules file but does not change the hook settings, and prints a warning:

- `hooks.internal.enabled` is `false`: you turned internal hooks off.
- The `bootstrap-extra-files` entry has `enabled: false`.
- `hooks.internal.enabled` is `true` and no hook is named under
  `hooks.internal.entries` (and `hooks.internal.load.extraDirs` is empty).
  OpenClaw then loads every eligible hook, and naming a first hook would switch
  the others off. Name the hooks you use, then run the update.

**Size limits.** OpenClaw injects at most 20,000 characters per file and 60,000
in total (`agents.defaults.bootstrapMaxChars` and `bootstrapTotalMaxChars`).
With the default profile the rules file is a few thousand characters. A rules
file over the per-file limit is not written, because OpenClaw would cut its
middle out; the install says so. Extra files come after the six workspace
files, so when those already use most of the total, the install warns that
OpenClaw shortens or skips the rules file. (OpenClaw behavior per its
[hooks configuration](https://docs.openclaw.ai/automation/hooks/configuration)
and [bundled hooks](https://docs.openclaw.ai/automation/hooks/bundled-hooks)
docs, read 2026-11-08.)

### Skills

**Name clashes.** OpenClaw reads skills from these sources, highest precedence
first, and when the same skill name appears in more than one place the highest
source wins: the workspace `skills/` folder, the workspace `.agents/skills/`
folder, `~/.agents/skills` (default state directory only), the state
directory's `skills/` folder (`~/.openclaw/skills` by default), workshop
skills, bundled and custodian skills, and then the folders listed under
`skills.load.extraDirs` together with plugin skills. A session that runs in a
separate execution workspace, a folder other than its own workspace, also reads
that folder's `skills/` and `.agents/skills/` folders after all of these, so an
Apothem skill wins over a skill of the same name kept there. The Apothem directory is an
`extraDirs` entry, so a skill of the same name that you keep in any of the
earlier sources is the one OpenClaw uses, and the Apothem copy of that skill
stays unused on disk. Apothem writes only to `openclaw.json` and under
`~/.openclaw/.apothem/support/`, never into those earlier folders, so install,
update, and uninstall do not replace a skill you keep there.

`agents.defaults.skills` is the allowlist of skill names, and an
`agents.entries.<id>.skills` list replaces it for the entry it belongs to.
Apothem edits neither list, so if you keep one, check that it names the Apothem
skills you want.
`apothem update` keeps keys you add to `openclaw.json`. MCP servers live in
the `mcp.servers` block of the OpenClaw config, which you manage with
`openclaw mcp add` and the related subcommands; the adapter writes no entries
there. (OpenClaw behavior per its [skills](https://docs.openclaw.ai/tools/skills),
[skills config](https://docs.openclaw.ai/tools/skills-config),
[config extensions](https://docs.openclaw.ai/gateway/config-extensions), and
[MCP CLI](https://docs.openclaw.ai/cli/mcp) docs, read 2026-11-03.)

**Comments in `openclaw.json`.** OpenClaw reads its config as JSON5, and Apothem
rewrites the file as plain JSON. When the file carries comments or other JSON5
syntax and an entry is missing, Apothem leaves the file untouched and install
stops with a message that names the key. Merge these entries into your file
yourself, or convert the file to plain JSON, then run the install again:

```json
{
  "skills": {
    "load": {
      "extraDirs": ["~/.openclaw/.apothem/support/skills"]
    }
  },
  "hooks": {
    "internal": {
      "entries": {
        "bootstrap-extra-files": {
          "enabled": true,
          "paths": ["apothem/AGENTS.md"]
        }
      }
    }
  }
}
```

An entry you add yourself counts as yours: uninstall leaves it in place.

## Verification

```bash
apothem verify --harness open-claw
```

The verify command confirms that:

1. The native config exists at the expected path.
2. Each managed target exists; managed files are non-empty, and JSON or YAML
   configs parse. Add `--profile PATH` to also confirm that the installed files
   match that profile.
3. `skills.load.extraDirs` in the native config lists
   `~/.openclaw/.apothem/support/skills`. Without that entry OpenClaw does not
   load the installed skills; `apothem update` adds it back.
4. The `bootstrap-extra-files` entry lists `apothem/AGENTS.md` in the list the
   hook reads, unless your own settings keep Apothem from registering it (see
   [Rules in each workspace](#rules-in-each-workspace)).
5. Every workspace Apothem finds holds `apothem/AGENTS.md` with its managed
   block. A workspace created after the install fails this check until
   `apothem update` writes the file. `apothem status` reports a rules file whose
   block was edited.

## Updating

```bash
apothem update --harness open-claw
```

Re-derives the profile document and each workspace's rules file from the
current shared profile state and refreshes the support files; `openclaw.json`
keeps the keys it already has, and the Apothem entries in
`skills.load.extraDirs` and the hook entry stay listed once however often you
update. Text you add to a rules file outside its managed block stays. Run after editing `~/.config/apothem/profile.yaml` or upgrading the
installed Apothem package.

## Uninstalling

```bash
apothem uninstall --harness open-claw
```

Removes what the adapter added: its entry in `skills.load.extraDirs`, its path
in the hook entry (and the entry itself when Apothem created it), the managed
block in each workspace's `apothem/AGENTS.md` (the file and folder go when
nothing else is left in them), the profile document, and the support tree. Your
own keys in `openclaw.json` stay, including your own `extraDirs` entries and
hook settings, the workspace's own files stay as they are, and `openclaw.json`
is deleted only when Apothem created it and nothing of yours is left. The shared profile YAML and
Apothem engine are unaffected.

## Troubleshooting

| Symptom | Fix |
|---------|-----|
| Config file not found | Re-run `apothem install --harness open-claw` |
| Verification failed | Run `apothem update --harness open-claw`, then verify again |
| Unexpected config content | Apothem authors only the `skills.load.extraDirs` entry and the `bootstrap-extra-files` hook entry in `openclaw.json` and keeps the keys already in it, so profile content does not land there. Profile content lands in `~/.openclaw/apothem/rules/00-apothem-profile.md`: check `~/.config/apothem/profile.yaml` or `--profile PATH`, then re-run the command under [Updating](#updating) |
| Install stops with a message about comments or JSON5 syntax in `openclaw.json` | Apothem does not rewrite a file it would have to strip comments from. Add the `skills.load.extraDirs` entry shown under [Compatibility notes](#compatibility-notes) yourself, or convert the file to plain JSON, then run the install again |
| OpenClaw does not follow the Apothem rules | Run `apothem verify --harness open-claw` and check the install warnings: a workspace that did not exist at install time, internal hooks turned off, or open hook discovery leave the rules unloaded (see [Rules in each workspace](#rules-in-each-workspace)). Then run `apothem update --harness open-claw` |
| An Apothem skill does not appear in OpenClaw | A skill of the same name in the workspace, `~/.agents/skills`, `~/.openclaw/skills`, or among OpenClaw's workshop or bundled skills takes precedence over the Apothem copy (see [Compatibility notes](#compatibility-notes)). Also run `apothem verify --harness open-claw`, and check that any `agents.defaults.skills` or `agents.entries.<id>.skills` allowlist you keep names the skill |
