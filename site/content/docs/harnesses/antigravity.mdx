**Vendor:** Antigravity
**Install name:** `antigravity`
**Status:** Preview
**Native config:** `~/.gemini/GEMINI.md` plus
`~/.gemini/config/plugins/apothem/`

## Installation

```bash
apothem install --harness antigravity
```

The adapter renders the shared profile to `~/.gemini/GEMINI.md` and installs
Apothem support cohorts as an Antigravity plugin. The plugin folder is shared by
the Antigravity CLI, App, and IDE, so all three load the plugin.

**Files written:** `~/.gemini/GEMINI.md`,
`~/.gemini/config/plugins/apothem/plugin.json`,
`~/.gemini/config/plugins/apothem/skills/`,
`~/.gemini/config/plugins/apothem/rules/`,
converted local helper definitions inside the plugin,
`~/.gemini/config/plugins/apothem/.apothem/support/templates/`, and
`~/.gemini/config/plugins/apothem/.apothem/support/hooks/`.

The Apothem block in `~/.gemini/GEMINI.md` ends with an Apothem support files
section that names the absolute directory each repository-style citation
resolves against: `rules/<name>.md` under the plugin's `rules/`, and
`templates/...` and `hooks/...` under the plugin's `.apothem/support/`.

**Plugin folder.** Antigravity loads a plugin from
`~/.gemini/config/plugins/<name>/` without a registration step
([Antigravity plugins documentation](https://antigravity.google/docs/plugins)),
and the adapter writes the Apothem plugin there. Current CLI releases load
plugins from this folder; the CLI updates itself, so if you turned updates off
with `AGY_CLI_DISABLE_AUTO_UPDATE=true`, update it before relying on the
plugin. The Antigravity App and IDE load the same folder, so the Apothem
plugin, with its always-on rules, skills, and helper definitions, applies in
all three. Antigravity documents no per-tool switch for a plugin: `plugin.json`
has no field that limits a plugin to one of them. An earlier Apothem release
wrote the plugin to `~/.gemini/antigravity-cli/plugins/apothem/`, in the CLI's
own data folder; an install or update over such an install backs that folder up
and removes it (see [Uninstalling](#uninstalling)).

**Plugin rules.** Antigravity discards any file in a plugin's `rules/`
directory that does not open with a valid `trigger`
([Antigravity rules documentation](https://antigravity.google/docs/rules)), so
each Apothem rule is converted on install. A rule that always applies gets
`trigger: always_on`; a rule scoped to paths gets `trigger: glob` with the same
patterns in `globs`; any other rule gets `trigger: model_decision`. Every rule
keeps its `description`. Five rules always apply: `agnostic-posture`,
`authority-inquiry`, `session-closure`, `context-management`, and the rule index
`apothem-rule-index`, which names every other rule and when to read it. The other
rules carry `trigger: glob`. Antigravity shares a 20,000-token budget across
always-on rules and turns the largest into on-demand pointers past it; the five
rules come to about 11,000 tokens, so none is turned into a pointer.

**Plugin manifest.** `plugin.json` carries only `name` and `description`. The
plugin schema published on Antigravity's
[Build plugins page](https://antigravity.google/docs/build-plugins) requires
`name`, also lists keys such as `displayName`, `version`, and `author`, and
admits no other key, so `agy plugin validate` reports a key it does not list.

**Plugin helpers.** Helper definitions in the plugin's `agents/` directory
carry `name` and `description`. Antigravity's `tools` list uses its own tool
names, and the docs warn that an unknown name can hang the subagent, so no tool
list is emitted and helpers inherit the parent's tools. Because nothing on
Antigravity enforces a read-only limit, those helpers' descriptions drop the
"read-only" label.

**Shared user anchor.** `~/.gemini/GEMINI.md` is also the user-scope anchor for
Gemini-family tooling. The Antigravity adapter keeps its extra Apothem material
inside the `apothem` plugin under `~/.gemini/config/plugins/` so it does not
claim generic Gemini CLI project directories. Because more than one
tool loads `~/.gemini/GEMINI.md`, the Apothem block there is written as global
guidance that names no single tool as its reader.

## Profile-to-native-config mapping

The adapter reads Apothem's shared profile and renders the instruction anchor
plus support cohorts on every `apothem install` or `apothem update` run.

## Compatibility notes

Preview adapter. The `GEMINI.md` anchor is active instruction content; the
Antigravity plugin preserves converted command skills, reusable skills, local
helper definitions, rules, templates, and hook support material in a clear
Apothem-owned namespace.
Hook files are not registered as active Antigravity hook events until the
adapter owns a schema translation layer for Antigravity `hooks.json`.

## Verification

```bash
apothem verify --harness antigravity
```

The verify command confirms that:

1. The native context file exists at the expected path.
2. The plugin manifest `plugin.json` exists, is non-empty, and parses as JSON.
   Verify does not check the plugin name; inspect that field yourself after
   changing it.

## Updating

```bash
apothem update --harness antigravity
```

Re-derives the native config from the current shared profile state. Run after
editing `~/.config/apothem/profile.yaml` or upgrading the installed Apothem
package.

## Uninstalling

```bash
apothem uninstall --harness antigravity
```

Removes the Apothem block from `~/.gemini/GEMINI.md` and keeps any other text
in it. The file is deleted only when nothing else remains in it. Also removes
Apothem's keys from `plugin.json` in the plugin folder
`~/.gemini/config/plugins/apothem/` and keeps yours, and removes the Apothem
files in that folder's `skills/`, `rules/`, `agents/`, and `.apothem/support/`
subfolders; other files there stay. Each file is backed up under
`~/.apothem/backups/` before it is changed or removed. The shared profile YAML
and Apothem engine are unaffected.

An install made by an earlier release holds the plugin in
`~/.gemini/antigravity-cli/plugins/apothem/`, in the CLI's own data folder. An
install, an update, or an uninstall over such an install backs that folder up
under `~/.apothem/backups/` and removes it, files of yours in it included. A
symbolic link or a Windows junction at that path, above it or inside the folder
is left in place, with a warning that names it, and nothing it points to is changed or
backed up. A link at that path that points to the current plugin folder is left
in place on every run, with a warning: it stays after an uninstall, so delete
it yourself once nothing uses the old path. An uninstall therefore removes the
earlier folder and, from the current one, only the Apothem files described
above. It prints each warning, and it reports a failure rather than success
when removing the earlier folder fails.

Install, update and uninstall never touch `~/.gemini/antigravity/`, the data
folder of the Antigravity App. (The CLI's is `~/.gemini/antigravity-cli/` and
the IDE's is `~/.gemini/antigravity-ide/`.) The App's folder holds its sign-in
tokens for MCP servers (`mcp_oauth_tokens.json`), its session transcripts
(`brain/`), the legacy global skills folder (`skills/`), and `sidecar_data/`.
Earlier releases treated that folder as a layout Apothem used before its first
release: they backed it up under `~/.apothem/backups/` and removed it on every
install and update. The CLI's own settings and session history, in
`~/.gemini/antigravity-cli/`, were not affected.

If an App sign-in, a session transcript, or a skill of yours went missing, the
copies are in
`~/.apothem/backups/<timestamp>/antigravity/.gemini/antigravity/`: one set for
each earlier install or update that found the folder, each holding the folder as
it stood then. Apothem keeps only the newest 10 Antigravity backup sets, so
copies from older installs may already be gone, and the next install, update,
uninstall, or rollback prunes again. Copy the sets you need out of
`~/.apothem/backups/` first.

## Conformity gate

```bash
python ~/.apothem/src/apothem/conformity/gate.py --all .
```

Run it from your project folder. The path is where the installer puts the engine;
[Conformity gate](/docs/conformity-gate) explains the script path and the other installs.

## Troubleshooting

| Symptom | Fix |
|---------|-----|
| Config file not found | Re-run `apothem install --harness antigravity` |
| Verification failed | Run `apothem update --harness antigravity`, then verify again |
| Unexpected config content | Check `~/.config/apothem/profile.yaml` or `--profile PATH`, then re-run `apothem update --harness antigravity` |
