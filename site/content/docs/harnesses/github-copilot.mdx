**Vendor:** GitHub / Microsoft
**Install name:** `github-copilot`
**Status:** GA
**Native config:** `<project>/.github/copilot-instructions.md`

## Installation

```bash
apothem install --harness github-copilot --project /path/to/project
```

The adapter derives the project instructions file from your shared profile and
the shared Apothem rules and governance surface.

It also writes Apothem's skills, and the rules and templates they cite, to
your user home, before it touches the project (see
[Files outside the project](#files-outside-the-project)).

**Files written:**

- `<project>/.github/copilot-instructions.md`, the instructions file.
- `~/.agents/skills/<name>/SKILL.md` for each Apothem skill and command, in your user home.
- `~/.config/apothem/rules/` and `~/.config/apothem/templates/`, in your user home.

## Files outside the project

The install also writes Apothem's skills to your user home, before it changes
anything in the project:

| Folder | What Apothem writes there |
| --- | --- |
| `~/.agents/skills/` | One folder with a `SKILL.md` for each Apothem skill, and one for each Apothem command (a command becomes a skill of the same name). |
| `~/.config/apothem/rules/`, `~/.config/apothem/templates/` | The rules and templates that the skills and the instructions file refer to. |

These folders are shared. They are not private to the project:

- Every project you install `github-copilot` into, and every other Apothem install that names the folder, uses the same copy and writes the same files, so the order you install in does not matter. Several other tools read `~/.agents/skills/` too; the [harness registry](/docs/reference/harness-registry#shared-roots) lists them.
- `--project` chooses the instructions file to write and which project the
  install belongs to. It does not change where the skills go.
- The install adds no skill or rule file to your repository. The project
  gets the instructions file, plus the `.apothem/` data folder every project install
  creates.
- The home folders are written first. If that fails, for example because a
  folder in the path is a link that leaves your home directory (a link that
  stays inside it is followed) or cannot be written, the install stops
  with the error before anything in the project changes.
- A skill folder with an Apothem skill's name that Apothem did not write is
  left alone, and the install prints a warning that names it. Rename or move
  it, then run `apothem update`. `apothem verify` fails while that name is held.
- The files add up to a few megabytes.

The install prints a note that names the folders it writes outside `--project`,
and `--dry-run` lists them.

## Profile-to-native-config mapping

The adapter reads Apothem's shared profile and renders the repo-wide Copilot
instructions file on every `apothem install` or `apothem update` run. The
shared profile is the source of truth; project-local edits to the generated
file are backed up before the next sync replaces the Apothem-managed content.

Inside the Apothem block, the section rendered from your profile (operator,
preferences, custom rules, opted-in behaviors, MCP server names) comes first,
ahead of the shared governance text. GitHub notes that shorter instruction
files are more likely to be processed in full by code review
([Customizing code review](https://docs.github.com/en/copilot/tutorials/customize-code-review)),
so the part that is specific to you leads the file.

## Compatibility notes

GitHub Copilot does not expose a file-based user-global instructions path for
this adapter to manage. Apothem targets the documented project-scope
instructions file and leaves IDE-level user settings operator-owned.

Within the Apothem repository, `.github/copilot-instructions.md` is one voice
among that repository's assistant instruction surfaces. In a checkout of that
repository, the conformity gate's multi-surface coherence check compares the
shared claims in `AGENTS.md`, `CLAUDE.md`, and `.github/copilot-instructions.md`.
It reports a shared claim that one of the three files leaves out, and a file that
contradicts a claim `AGENTS.md` makes. The check does not read the
instructions file Apothem writes into your project. The gate is advisory by
default: it reports findings and exits `0`.

GitHub Copilot lists `~/.agents/skills/` among its personal skill locations,
so the skills the install writes are on your machine for Copilot to load.
Surfaces that run on GitHub, the cloud coding service and code review, run
elsewhere and do not see your home folder, which is why the instructions file carries the
disciplines itself. Apothem has not confirmed how Copilot treats a `SKILL.md`
header key it does not list; the skills carry `user-invocable`,
`disable-model-invocation`, `allowed-tools`, `argument-hint`, and a `metadata`
map.

## Verification

```bash
apothem verify --harness github-copilot --project /path/to/project
```

The verify command confirms that:

1. The native config exists at the expected path.
2. Each managed target exists; managed files are non-empty, and JSON or YAML
   configs parse. Add `--profile PATH` to also confirm that the installed files
   match that profile.
3. Every Apothem skill folder is in place with a `SKILL.md`, whichever
   install wrote it, and no skill folder with an Apothem name belongs to
   something Apothem did not write. A failed check names the missing or
   foreign folders.
4. The adapter-specific verification routine reports success.

## Updating

```bash
apothem update --harness github-copilot --project /path/to/project
```

Re-derives the project instructions file from the current shared profile state.

The update also rewrites any skill folder whose files differ from the current ones.
If you installed with an earlier release that wrote no skills, the update adds them.

## Uninstalling

```bash
apothem uninstall --harness github-copilot --project /path/to/project
```

Removes the Apothem block from `<project>/.github/copilot-instructions.md` and
keeps any text outside it. The file is deleted only when nothing else remains in
it. Before the change, a timestamped copy of the file is saved under
`~/.apothem/backups/`. The shared profile YAML and Apothem engine are
unaffected.

The uninstall also removes the skill folders it wrote in `~/.agents/skills/` and the
rules and templates in `~/.config/apothem/`, but only when no other Apothem
install still uses them. Another project, or another tool that shares the
folder, may. In that case the uninstall keeps the folders, prints which install
uses them, and the last uninstall removes them. Files you added to those
folders stay, and a folder left empty is removed. Each
folder is backed up under `~/.apothem/backups/` before it is removed.

## Conformity gate

```bash
python -m apothem.conformity.gate --all .
```

The `--all` run covers the standalone validators. It does not run the
multi-surface coherence check described under Compatibility notes. To run that
check by name in a checkout:

```bash
python -m apothem.conformity.gate --check multi-surface-coherence-grep AGENTS.md
```

## Troubleshooting

| Symptom | Fix |
|---------|-----|
| Config file not found | Re-run `apothem install --harness github-copilot --project /path/to/project` |
| Verification failed | Run `apothem update --harness github-copilot --project /path/to/project`, then verify again |
| `apothem verify` names a missing skill folder | Run `apothem install --harness github-copilot --project /path/to/project`; it restores the folder |
| An install or update warns that it skipped a skill folder | A folder with an Apothem skill's name already exists in the skills folder and Apothem did not write it. Rename or move it, then run `apothem update` |
| An install stops before it changes the project | A write in your home failed. Read the error, fix the folder it names (a link that leaves your home directory, a file where a folder belongs, or a read-only folder), and install again |
| Unexpected config content | Check `~/.config/apothem/profile.yaml` or `--profile PATH`, then re-run `apothem update --harness github-copilot --project /path/to/project` |
