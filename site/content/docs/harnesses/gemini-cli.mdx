**Vendor:** Google
**Install name:** `gemini-cli`
**Status:** GA
**Native config:** project-local `GEMINI.md` and `.gemini/`

## Installation

```bash
apothem install --harness gemini-cli --project /path/to/project
```

The adapter is project-scoped. It installs the project `GEMINI.md`, converts
Apothem commands to Gemini TOML slash commands, normalizes local helper
definitions, and places non-native support cohorts under `.gemini/.apothem/support/`.
Other coding tools also read a project `GEMINI.md`, so the Apothem block in it
is written as project-wide guidance that names no single tool as its reader.

**Files written:**

```text
GEMINI.md
.gemini/commands/*.toml
.gemini/agents/*.md
.gemini/skills/
.gemini/.apothem/support/
```

## Profile-to-native-config mapping

The adapter reads Apothem's shared cohorts and routes each one through a
Gemini-compatible surface. Markdown rules, templates, and hook material remain
under `.gemini/.apothem/support/` because they are support material, not a Gemini-native
rules directory.

Each converted command in `.gemini/commands/` holds a `description` and a
`prompt`. The prompt is the command's instructions only; the Apothem metadata
at the top of the source file (version, tool list, and similar fields) is left
out, so the model never reads it as instructions. Gemini runs a custom command
only when you type it.

Helper definitions in `.gemini/agents/` keep their tool limits and turn limit:
the source `tools` grant, minus `disallowedTools`, becomes a Gemini `tools`
allowlist of Gemini tool names, and `maxTurns` becomes `max_turns`. A read-only
helper therefore gets no `write_file` or `replace` tool. No model is set, so
each helper inherits the session model.

## Compatibility notes

`~/.gemini/` remains user-scope territory for tools that use a global Gemini
profile. The Gemini CLI adapter writes only to the project passed through
`--project`.

## Verification

```bash
apothem verify --harness gemini-cli --project /path/to/project
```

The verify command confirms that:

1. The native config exists at the expected path.
2. All mandatory fields from the shared profile are present.
3. The adapter-specific verification routine reports success.

## Updating

```bash
apothem update --harness gemini-cli --project /path/to/project
```

Refreshes `GEMINI.md`, converted commands, local helper definitions, installed
skills, and the `.gemini/.apothem/support/` support tree.

## Uninstalling

```bash
apothem uninstall --harness gemini-cli --project /path/to/project
```

Removes the native config files written by the adapter.
The shared profile YAML and Apothem engine are unaffected.

## Conformity gate

```bash
python -m apothem.conformity.gate --all .
```

## Troubleshooting

| Symptom | Fix |
|---------|-----|
| Config file not found | Re-run `apothem install --harness gemini-cli --project /path/to/project` |
| Verification failed | Run `apothem update --harness gemini-cli --project /path/to/project`, then verify again |
| Unexpected config content | Check `~/.config/apothem/profile.yaml` or `--profile PATH`, then re-run `apothem update --harness gemini-cli --project /path/to/project` |
