Slash-Befehlsdefinitionen liegen als flache `.md`-Dateien unter `src/apothem/commands/`. Der
kanonische Satz wird von der architekturbewussten Plansuite-Pipeline angeführt, die
als sieben erstklassige Befehle ausgeliefert wird — einer pro Stufe, jeder direkt aufrufbar als
`/plan-<stage>`. Es gibt keinen monolithischen Dispatcher; jede Stufe ist ihre eigene
registrierte Befehlsdatei unter `src/apothem/commands/plan-<stage>.md`.

| Aufruf | Befehlsdatei | Beschreibung |
|------------|--------------|-------------|
| `/plan-spec` | `src/apothem/commands/plan-spec.md` | Unstrukturierten Inhalt zu spezifikationsreifer Prosa verfeinern |
| `/plan-generate` | `src/apothem/commands/plan-generate.md` | Eine Plansuite aus Prosa / Anforderungen materialisieren |
| `/plan-review` | `src/apothem/commands/plan-review.md` | Forensisches Audit mit Scorecards |
| `/plan-design` | `src/apothem/commands/plan-design.md` | `_inputs/design.md` für architekturtragende Suiten ausgeben |
| `/plan-execute` | `src/apothem/commands/plan-execute.md` | Eine Phase mit Qualitätsschranken ausführen |
| `/plan-status` | `src/apothem/commands/plan-status.md` | Schreibgeschützter Fortschrittsbericht |
| `/plan-amend` | `src/apothem/commands/plan-amend.md` | Eine bestehende Suite ergänzen, erweitern, verfeinern oder zurücksetzen, ohne aufgelöste Entscheidungen zu verlieren |
| `/plan-audit` | `src/apothem/commands/plan-audit.md` | Geschlossene Schleife von spec → generate → review mit aktiver Behebung (orthogonal, vor execute) |

Neben der Plan-Pipeline werden projektweite Harness-Befehle mitgeliefert —
`/freshify`, `/github-deploy-fresh`, `/github-deploy-next` und `/elevate` zum
Auffrischen und Veröffentlichen; `/audit`, `/fortress` und `/workflow` für
Mehragenten-Review und -Orchestrierung; `/projectify` zur Veredelung von
Chat-App-Projekten — sowie die elf Audit-/Review-Durchläufe und die
`/research`-Pipeline:

| Aufruf | Befehlsdatei | Beschreibung |
|------------|--------------|-------------|
| `/freshify` | `src/apothem/commands/freshify.md` | Ein Projekt frisch, spurenfrei und produktionsreif machen; jeder destruktive Schritt bestätigungsgesteuert |
| `/github-deploy-fresh` | `src/apothem/commands/github-deploy-fresh.md` | GitHub-Spezialisierung von `/freshify`, die ein einzelnes frisches Erstversions-Release erzeugt |
| `/github-deploy-next` | `src/apothem/commands/github-deploy-next.md` | Einen vollständigen Folge-Release-Zyklus auf der GitHub-Release-Oberfläche ausführen |
| `/elevate` | `src/apothem/commands/elevate.md` | Jede Projektoberfläche über unabhängige Kritik-Worker auf den aktuellen SOTA-Stand heben, dann an `/freshify` übergeben |

Der vollständige, maßgebliche Befehlssatz — einschließlich der Audit-Review-Sequenz —
ist das generierte Inventar am Fuß dieser Seite.

## Frontmatter-Vertrag

Jede Befehlsdatei trägt das kanonische Frontmatter mit acht Schlüsseln. Der
maschinenlesbare Vertrag ist [`command.schema.json`](https://github.com/ahmed-g-gad/apothem/blob/main/src/apothem/schemas/command.schema.json)
(`additionalProperties: false`); dieser Block spiegelt ihn wider:

```yaml
---
name: <slash-command name without leading slash>
version: <semver>
updated: <YYYY-MM-DD>
description: <one-line role>
argument-hint: <placeholder for the slash-command argument>
disable-model-invocation: <true | false>
portability: <portability classification, e.g. universal>
allowed-tools: <comma-separated tool list, or "*">
---
```

Die `frontmatter-cohort`-Prüfung des Validators (Command-Zweig) verifiziert den
Vertrag bei jeder Befehlsdatei.

## Autorendisziplin

- **Eigenständiger Workflow.** Der Body jedes Befehls führt den Workflow als
  nummerierte Schritte auf, sodass der Assistent aus einem Kaltstart heraus ausführen kann.
- **Bindings-Block.** Jeder Befehl endet mit dem kanonischen
  Fünf-Richtungen-Bindings-Block.
- **Nur Domänensprache.** Keine plan-internen Verweise in den Bodys.
