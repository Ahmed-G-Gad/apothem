> **Kanonische Registry der Artefakt-Kohorten.** Dieses Dokument trägt die vollständigen Aufzählungen von Commands, Regeln, delegierten Workern, Hooks, Skills, Output-Styles, der Disziplin der Artefaktevolution und den Deklarationen leerer Artefaktklassen; die substanziellen Tabellen leben hier. Das Quell-Layout des Projekts liefert die verdichtete, stets geladene Ansicht.

## 1. Commands

Fünfundvierzig Commands werden aus `src/apothem/commands/*.md` registriert (nicht rekursiv) — die vollständige, stets aktuelle Referenz pro Command ist die generierte [Commands-Referenz](https://apothem.ahmedgad.com/docs/reference/commands/), und die dreizehnstufige `/research`-Pipeline (`/research-ideate` bis `/research-disseminate`) sowie die Orchestratoren für umhüllte Workflows `/audit` und `/fortress` sind dort vollständig aufgezählt. Jeder Command ist eine erstklassige registrierte Datei; der `/plan`-Orchestrator verkettet nur die bereits erstklassigen Plan-Stages und trägt keine eigene Stage-Logik, sodass es weiterhin keinen monolithischen Dispatcher und keine Subcommand-Gruppierung gibt.

Fünfunddreißig Commands sind vom Modell aufrufbar (`disable-model-invocation: false`): Das Modell darf einen davon ausführen, wenn eine Anfrage zu seiner Beschreibung passt. Zehn werden nur vom Operator aufgerufen: `/freshify`, `/github-deploy-fresh`, `/github-deploy-next`, `/release-readiness`, `/elevate`, `/fortress`, `/workflow`, `/plan-execute`, `/research-experiment` und `/research-publish`. Das Flag pro Command ist in `src/apothem/commands/README.md` verzeichnet.

### Plan-Pipeline-Commands

Die Plan-Pipeline wird als acht erstklassige Commands ausgeliefert — einer pro Stage, jeder direkt als `/plan-<stage>` aus seiner eigenen registrierten Datei unter `src/apothem/commands/plan-<stage>.md` aufrufbar.

| Command | Datei | Verhalten |
| ------- | ---- | -------- |
| `/plan-spec` | `src/apothem/commands/plan-spec.md` | Verfeinert freie Prosa zu einer spezifikationsreifen `_spec/spec.md`; jede offene Frage läuft über den Strukturierte-Inquiry-Kanal statt durch stilles Standardisieren; `--quick` schreibt eine einzelne leichtgewichtige Plan-Datei unter `<project-root>/.apothem/plans/` |
| `/plan-generate` | `src/apothem/commands/plan-generate.md` | Generiert eine vollständige Master-Plan-Suite aus verfasster Prosa/Anforderungen |
| `/plan-review` | `src/apothem/commands/plan-review.md` | Forensisches Audit einer bestehenden Suite — Prosatreue, interne Konsistenz, Lückenanalyse — verfeinert über interaktive Q&A |
| `/plan-design` | `src/apothem/commands/plan-design.md` | Erzeugt ein Architektur-Design-Artefakt unter `_inputs/design.md` der Suite, validiert durch das fünfzehnbalkige Pre-Emission-Gate vor der Promotion |
| `/plan-audit` | `src/apothem/commands/plan-audit.md` | Audit und Remediation im geschlossenen Kreislauf über den vollständigen Zyklus Spec → Generate → Review, in Schleife bis null Befunde verbleiben oder eine Iterationsobergrenze mit definiertem Rückzug erreicht ist |
| `/plan-execute` | `src/apothem/commands/plan-execute.md` | Führt eine Phase mit Konformitätsprüfung und Qualitätstoren aus — Standard-Aufwand `medium`, pro Phase überschreibbar über ein `effort:`-Feld in der `PHASE.md`-Frontmatter; hält standardmäßig an jeder Phasengrenze an, wobei `--no-pause` (oder das Profil-Flag `enforcement.continuous_execution`) das kontinuierliche Vorrücken von Phase zu Phase aktiviert |
| `/plan-status` | `src/apothem/commands/plan-status.md` | Schreibgeschützter Fortschrittsbericht gegen die Dimensionen Aufgabe, Phase und Artefakt |
| `/plan-amend` | `src/apothem/commands/plan-amend.md` | Ergänzt, erweitert, verfeinert oder revidiert eine bestehende Suite, ohne zuvor getroffene Entscheidungen zu zerstören; leitet nur die betroffenen nachgelagerten Artefakte neu ab |

### Operator-Workflow- & Orchestrator-Commands

Drei Commands treten in eine tiefe Prozedur ein, statt eigene Stage-Logik zu tragen: zwei Operator-Workflow-Einstiegspunkte (jeweils gestützt durch einen gleichnamigen Begleit-Skill) plus den schlanken Plan-Pipeline-Orchestrator.

| Command | Datei | Beschreibung |
| ------- | ---- | ----------- |
| `/workflow` | `src/apothem/commands/workflow.md` | Allzweck-Einstiegspunkt zur Workflow-Steuerung (`/goal <<mission>>`): treibt genuin unabhängige, dynamische Multi-Agenten-Workflows unter benannten Return-Verträgen, Verifikation per Widerlegung-by-Default vor dem Überleben eines Befunds, über die Mission hinausgehende Remediation, offengelegt im Änderungs-Ledger, und deterministische Ausgabe; Multi-Worker-Dispatch und Auto-Ausführung sind opt-in / bestätigungsgesteuert. Gestützt durch den `workflow`-Skill |
| `/projectify` | `src/apothem/commands/projectify.md` | Elevation eines Chat-App-Projekts: verfasst die Deliverables Description / Instruction / knowledge-Files für ein Claude Project, Custom GPT oder Gem zu aktuellen SOTA-Konventionen, innerhalb eines messbaren Kontextbudgets pro Plattform; deterministische Ausgabe, opt-in Autonomie. Gestützt durch den `projectify`-Skill |
| `/plan` | `src/apothem/commands/plan.md` | Schlanker Orchestrator, der die erstklassigen Plan-Stages verkettet (`plan-spec → plan-generate → plan-review → plan-design (bedingt) → plan-execute`) und jede aus dem Übergabe-Manifest der vorherigen Stage fortsetzt; trägt keine Stage-Logik — die Verkettung ist opt-in / bestätigungsgesteuert (`--auto` verkettet kontinuierlich) |

## 2. Regeln

Verhaltensregeln leben unter `src/apothem/rules/` — ein kleiner, stets geladener Kern plus ein größerer, pfadgefilterter Satz (bei passenden Artefaktberührungen bedarfsgeladen). Die vollständige Aufzählung pro Regel — mit den Spalten Scope (stets geladen / pfadgefiltert) und Implements — ist die quellgenerierte `reference/rules.mdx`, aktualisiert aus `src/apothem/rules/*.md` durch den Reference-Inventory-Generator; konsultiere sie für die maßgebliche aktuelle Liste.

> **CM-21-Facettenabgrenzung** (drei Regeln implementieren CM-21 gemeinsam mit verschiedenen, nicht überlappenden Facetten): **kreative Filter & kognitive Identität** → `cognitive-identity.md`; **Generierungsmethodik (Schreib- & Umschreib-Protokolle)** → `clean-room-generation.md`; **Planungs-/Review-Techniken** → `planning-techniques.md`. Jede Regel besitzt ihre Facette; die anderen verweisen darauf.

> **Verweis auf das Interactive-Questions-Schema.** Das kanonische Invocation-Schema der strukturierten Inquiry — Pflichtfelder, Feldübersichtstabelle, zwei ausführbare durchgearbeitete Beispiele (Single-Select bei §2.1 und Multi-Select bei §2.2) — lebt unter `src/apothem/rules/interactive-questions.md` §2 „Structured-Inquiry Shape". Nachgelagerte Artefakte dürfen §2.1 oder §2.2 als Invocation-Vorlagen kopieren; das dreiteilige Option-Annotation-Schema, das der `description`-Body jeder Option trägt, ist im §3 derselben Datei spezifiziert.

## 4. Hooks

Installierte Hook-Einträge von Claude Code verwenden die Exec-Form: `command` ist `${PYTHON_BIN}`, und `args` enthält einen Skriptpfad unter `${HARNESS_ROOT}/.apothem/support/` (zum Beispiel `hooks/dispatch.py` und `conformity/gate.py`). Die Form `-m apothem.hooks.dispatch` ist für die Entwicklung aus einem Quell-Checkout mit `PYTHONPATH=src` gedacht. Der Dispatcher importiert `src/apothem/hooks/lib/resolve_root.py` für die Auflösung der Ökosystem-Wurzel und delegiert an zwei Helfer, die daneben direkt unter `src/apothem/hooks/` liegen: `src/apothem/hooks/emit_hook_context.py` formatiert Event-Payloads für den Assistenten, und `src/apothem/hooks/session_start_bootstrap.py` übernimmt die SessionStart-Vorbereitung, die der Dispatcher übergibt, wenn er dieses Event weiterleitet. Die Hook-Nachrichten, die dem Assistenten angezeigt werden, wenn die unterstützten Events auslösen, liegen als Markdown-Kontextdateien unter `src/apothem/hooks/messages/`, eine pro Event-Variante: `postcompact.md`, `precompact.md`, `posttooluse-proactive-compaction.md`, `pretooluse-askuserquestion-recommended.md`, `pretooluse-bash.md`, `pretooluse-bash-plan-guard.md`, `pretooluse-conformity.md`, `pretooluse-dependency-guard.md`, `pretooluse-edit.md`, `pretooluse-edit-header-guard.md`, `pretooluse-eval-guard.md`, `pretooluse-notebookedit.md`, `pretooluse-write.md`, `pretooluse-write-header-guard.md`, `pretooluse-write-plan-guard.md`, `sessionstart.md`, `skill-index.md`, `stop.md`. Jede geroutete Kontextdatei lädt der Dispatcher, wenn ihr Event auslöst und ihr Kontextargument in `settings.json` registriert ist. `pretooluse-conformity.md` wird als verfügbare Variante ausgeliefert, hat aber keinen aktuellen Routing-Eintrag in `settings.json`. `skill-index.md` wird aus dem Skill- und Command-Katalog generiert und vom Session-Start-Bootstrap gelesen, nicht über `settings.json` geroutet. `pretooluse-dependency-guard.md` ist für die Matcher Write und Edit geroutet, und `pretooluse-eval-guard.md` für die Matcher Write, Edit und `Bash|PowerShell`.

```text
Event             Automates                Timeout  Purpose
----------------- ------------------------ -------- --------------------------------------------------
SessionStart      CM-14                    30s      Read memory, check plan state, report readiness
PreCompact        CM-24                    30s      Verify state externalized before compaction. Codex and Qwen Code register it; the Claude Code settings.json template does not
PostCompact       CM-24                    30s      Restore working state after compaction. Codex and Qwen Code register it; the Claude Code settings.json template does not
Stop              CM-14/CM-22/CM-24/CM-26  60s      Session-end externalization
PreToolUse        CM-7/CM-22               10s      Write/Edit/NotebookEdit validation — codebase-isolation, frontmatter, license-header, and plans-locality checks plus the conformity gate. Bash validation — git artifact isolation and plans-locality
PostToolUse       Proactive compaction     10s      Proactive-compaction advisory on every tool call; the Claude Code settings.json template routes it on the all-tools matcher
UserPromptSubmit  —                        10s      Accepted by src/apothem/hooks/dispatch.py whitelist for forward compatibility; no settings.json entry currently routes this event
Notification      —                        10s      Accepted by src/apothem/hooks/dispatch.py whitelist for forward compatibility; no settings.json entry currently routes this event
```

> **Konvention.** Zeilen, in denen **Automates** `—` ist, werden von `dispatch.py` akzeptiert, aber nicht in `settings.json` verdrahtet; die Spalte **Timeout** zeigt den Dispatch-Level-Standard, der gilt, falls und wenn das Event später verdrahtet wird.
>
> **Kanonischer Block der Timeout-Werte.** Die Spalte **Timeout** dieser Tabelle ist die einzige Quelle der Wahrheit für Hook-Timeout-Werte im gesamten Ökosystem. Die `timeout`-Felder pro Hook in `settings.json`, die Spiegeltabellen in `site/content/docs/reference/settings-reference.mdx` § Hook Events und `site/content/docs/reference/artifact-schema.mdx` § Hooks Pipeline sowie die Regelanleitung in `src/apothem/rules/persistent-conventions-vigilance.md` § Convention Awareness leiten sich alle aus dieser Spalte ab. Künftige Timeout-Revisionen landen hier und die Konsumenten leiten beim nächsten Verweis neu ab.

### Review-Kadenz der Settings-Vorlage

`settings.json` ist die einzige Claude Code Vorlage. Jeder Hook-Command verwendet
Exec-Form statt eines shell-spezifischen Wrappers, sodass plattformübergreifendes Verhalten
innerhalb einer Datei überprüft wird statt durch das Vergleichen gepaarter Vorlagen. Neue Permission-Einträge,
Hook-Events, Timeouts und Statusmeldungen landen atomar in dieser Datei.

## 7. Artefaktevolution

**Verpflichtend.** Wenn ein wiederverwendbares Muster, eine Korrektur oder eine Technik wiederkehrt (2+ Instanzen in einer Session oder im Gedächtnis als wiederkehrend vermerkt), muss das Ökosystem sich weiterentwickeln. Der Zyklus hat vier Schritte: **Detect** des Musters während jeder Interaktion; **Search** bestehender Skills, Regeln, Commands, Hooks und Gedächtnis nach Überlappung; **Act** durch In-Place-Weiterentwicklung des passenden Artefakts (Aktualisierung von Prozedur, Anti-Mustern, Scope) oder Erstellung eines neuen, wenn das Anliegen genuin orthogonal ist; **Validate**, dass Querverweise weiterhin auflösen und abhängige Artefakte konsistent bleiben. Bevorzuge Verfeinerung gegenüber Erstellung — neue Artefakte vergrößern die Wartungsoberfläche. Siehe `src/apothem/rules/persistent-conventions-vigilance.md` §2+§4 für das vollständige Protokoll einschließlich des geschlossenen Katalogs von Lückenerkennungs-Triggern über jede Artefaktklasse.

## 8. Leere Artefaktklassen

Oberflächen, die in der Ökosystem-Registry deklariert, aber absichtlich leer sind, bis ein Aktivierungs-Trigger auslöst. Jede Zeile verzeichnet die reservierte Oberfläche, die Datei oder das Verzeichnis, das die Klasse gerüstet, und den Trigger, der die Zeile von Leer-Attestierung zu Befüllt befördert.

| Klasse | Gerüst | Status | Aktivierungs-Trigger |
| ----- | -------- | ------ | ------------------ |
| MCP-Server | (noch kein Gerüst) | leer-attestiert | Erste MCP-Server-Installation unter der User-Config-Wurzel |

Leer-Attestierung ist eine positive Deklaration, keine Lücke. Das Gerüst der Klasse (sofern eines existiert) ist das kanonische No-op-Artefakt, das den Aktivierungsmoment verfolgt. Promotionen von Leer-Attestierung zu Befüllt landen atomar mit dem ersten nicht-leeren Wert des Gerüsts im relevanten Registry-Abschnitt.
