Installiert eine Harness-Adapterkonfiguration aus dem gemeinsamen Profil.

## Übersicht

```
apothem install --harness NAME|all [--profile PATH] [--dry-run]
                 [--clean|--fresh] [--yes] [--project PATH]
                 [--quiet|-q] [--verbose|-v]
                 [--format plain|json] [--json] [--no-color]
```

Lädt und validiert das gemeinsame Profil, wählt einen benannten Adapter oder die
registry-weite Menge `all` aus, validiert den Materialisierungsplan und schreibt
die harness-native Konfiguration sowie die Unterstützungskohorten. Adapter mit
Projekt-Geltungsbereich erfordern `--project PATH`. Der Ordner wird mit
verfolgten Links und erweitertem `~` gelesen, und der Installationsdatensatz
benennt ihn auf diese Weise. Eine Installation, die unter einer anderen
Schreibweise des Ordners aufgezeichnet ist, etwa einem Link, den Python-Code
oder ein früheres Release beibehalten hat, wird auf diese Schreibweise
umgestellt, sobald die Installation ihre Prüfungen besteht (siehe
[`uninstall`](/docs/cli-reference/uninstall)).

Der Alias in Verlaufsform `apothem installing` (auch als `apothem Installing`
akzeptiert) wird auf denselben Handler aufgelöst.

## Erster Lauf ohne Profil

Wenn `--profile` weggelassen wird und am Standardpfad
(`~/.config/apothem/profile.yaml`) kein Profil existiert, schreibt `install`
zuerst das Starterprofil dorthin, gibt `Created a starter profile at <path>` aus
und fährt fort. Das Starterprofil trägt Platzhalter-Identitätsfelder, daher gibt
die Installation auch den Hinweis zur Platzhalter-Identität aus; passen Sie das
Profil an und führen Sie dann [`update`](/docs/cli-reference/update) aus, um es
anzuwenden. Unter `--json` wird das Anlegen als `warnings`-Eintrag mit
`"operation": "profile_created"` gemeldet.

- `--dry-run` schreibt das Profil niemals: Die Vorschau verwendet das
  Starterprofil im Speicher und meldet `"operation": "profile_scaffold_preview"`.
- Ein explizit angegebener `--profile PATH`, der nicht existiert, wird niemals
  angelegt; der Befehl endet mit Exit-Code 1 und `profile.not_found`.

## Wirkungsradius-Vorschau

`install --harness all` fächert sich in gemischte Geltungsbereiche auf: Adapter mit Projekt-Geltungsbereich schreiben unter die angegebene `--project`-Wurzel, während Adapter mit Benutzer-Geltungsbereich unter Ihr Home-Verzeichnis schreiben — außerhalb dieser Wurzel. Bevor die Installation eine Datei schreibt, gibt der Befehl die konkreten Ziele aus, gruppiert unter zwei Überschriften: die Ziele innerhalb der Projektwurzel und die Ziele unter Ihrem Home-Verzeichnis. Eine dritte Überschrift listet die gemeinsamen Ordner in Ihrem Home-Verzeichnis auf, die die Adapter mit Projekt-Geltungsbereich außerhalb von `--project` schreiben: den Skills-Ordner und `~/.config/apothem/` (siehe [Ordner in Ihrem Home-Verzeichnis](#ordner-in-ihrem-home-verzeichnis)). Die einzige Ausnahme ist `--clean`: Sein Schritt für einen sauberen Neuanfang läuft vor dieser Vorschau, schreibt eine Sicherung und entfernt vorherige Ziele, wie unten beschrieben.

Wenn die Auswahl außerhalb der Projektwurzel schreibt, sei es in den Ordner eines
Adapters im Home-Verzeichnis oder in einen gemeinsamen Ordner, schützt eine
interaktive Bestätigung die Schreibvorgänge im Home-Verzeichnis. `--yes`, eine nicht
interaktive Shell (kein TTY), `--dry-run` und `--format json` fahren jeweils ohne
Nachfrage fort. Nur `--dry-run` schreibt nichts; `--format json` überspringt die
Vorschau und die Bestätigungsabfrage, führt die Schreibvorgänge aber dennoch aus.
Lehnen Sie die Abfrage zum Home-Verzeichnis ab, bricht die Installation ab, bevor
sie schreibt. Mit `--clean` läuft der Schritt für den sauberen Neuanfang zuerst,
mit einer eigenen Bestätigung pro Ziel: Er schreibt eine Sicherung unter
`~/.apothem/backups` und entfernt die Ziele, die Sie bestätigen. Diese
Entfernungen und die Sicherung bleiben bestehen, wenn die Installationsabfrage
abgelehnt wird.
Die Ziele sind immer dieselben vier Ordner in Ihrem Home-Verzeichnis, gleich
welchen Harness `--harness` nennt:

```text
~/.claude
~/.codex
~/.agents
~/.config/apothem
```

Kein anderer Ordner wird entfernt, und der Rest von `~/.config` bleibt erhalten.
Bei einem Ziel, das selbst ein Link ist, eine Windows-Junction eingeschlossen,
wird nur der Link entfernt, und ein Link innerhalb eines Ziels wird entfernt,
ohne betreten zu werden. Ist `~/.config` ein Link, der aus Ihrem
Home-Verzeichnis herausführt, hält der Schritt für den sauberen Neuanfang mit
`Clean-slate removal was refused` an, bevor er etwas sichert oder entfernt, da
das Entfernen von `~/.config/apothem` den Ordner am anderen Ende dieses Links
löschen würde. Der Fehler nennt den Link: Ersetzen Sie ihn durch einen echten
Ordner, oder lassen Sie ihn auf einen Ordner innerhalb Ihres
Home-Verzeichnisses führen. Der Schritt hält auch an, bevor er etwas ändert und
bevor er das Startprofil anlegt, wenn Ihr Home-Verzeichnis kein vollständiger
Pfad ist, die Wurzel eines Laufwerks oder Dateisystems ist, ein Link oder eine
Junction ist, die zu einer solchen führt, oder über einen Link erreicht wird,
der eine Schleife bildet.

Der Schritt für den sauberen Neuanfang entfernt das Standardprofil,
`~/.config/apothem/profile.yaml`, zusammen mit `~/.config/apothem` und schreibt
es danach zurück. Ein Profil, das er nicht entfernt hat, etwa eines, das Sie mit
`--profile PATH` aus einem anderen Ordner übergeben, wird überhaupt nicht
geschrieben. Das Zurückschreiben folgt derselben Regel wie jeder andere
Profil-Schreibvorgang: Es wird abgelehnt, wenn ein Link es aus Ihrem
Home-Verzeichnis herausführen würde. Kann das Profil nicht zurückgeschrieben
werden, beendet sich der Befehl mit 1, und der Fehler nennt die
Sicherungskopie, die es enthält. Der Fehlercode ist
`clean_slate.profile_restore_refused`, wenn ein Link den Schreibvorgang
abgelehnt hat, und `clean_slate.profile_restore_failed`, wenn der
Schreibvorgang selbst fehlgeschlagen ist. Bricht eine Entfernung mittendrin ab,
etwa bei einer Datei, die ein anderes Programm geöffnet hält, wird zuerst das
Profil zurückgeschrieben. Der Befehl beendet sich dann mit 1 und dem Fehlercode
`clean_slate.removal_failed`, und der Fehler nennt den Sicherungsordner. Kann
das Profil nicht zurückgeschrieben werden, ist der Fehler stattdessen einer der
beiden Profilcodes oben.

## Ordner in Ihrem Home-Verzeichnis

Sieben Adapter mit Projekt-Geltungsbereich schreiben Apothems Skills sowie die
Regeln und Vorlagen, auf die sich die Skills beziehen, in Ordner in Ihrem
Benutzer-Home:

```text
cursor, github-copilot, windsurf, zed  ->  ~/.agents/skills/ (codex writes it too)
codebuddy                               ->  ~/.codebuddy/skills/
kiro                                    ->  ~/.kiro/skills/
trae                                    ->  ~/.trae/skills/
all seven                               ->  ~/.config/apothem/rules/ and templates/ (codex uses them too)
```

- `--project` wählt die Regeldatei und das Projekt aus, zu dem die Installation
  gehört. Es ändert nicht, wohin die Skills gehen: Eine Installation mit
  `--project A` und eine mit `--project B` schreiben dieselben Ordner.
- Jede Installation, die einen Ordner benennt, schreibt dieselben Dateien. Eine
  zweite Installation findet sie vor und meldet `unchanged`, und die Reihenfolge,
  in der Sie installieren, spielt keine Rolle.
- Die Home-Ordner werden vor allem anderen im Projekt geschrieben. Schlägt dort
  ein Schreibvorgang fehl, bricht die Installation des Adapters mit dem Fehler ab,
  und das Projekt bleibt unverändert. Der Fehler benennt den Pfad, der im Weg
  ist, zum Beispiel eine Datei namens `~/.agents` dort, wo der Ordner hingehört.
- Jeder Skill-Ordner wird in einen versteckten Ordner `.<name>.apothem-staging`
  daneben geschrieben und nach Abschluss an seinen Platz umbenannt, sodass ein
  fehlgeschlagener oder unterbrochener Schreibvorgang niemals einen halb
  geschriebenen Skill-Ordner unter seinem endgültigen Namen hinterlässt. Führen
  Sie die Installation erneut aus, um sie abzuschließen; sie ersetzt einen
  übrig gebliebenen Staging-Ordner.
- Ein Link auf oder oberhalb eines dieser Ordner, wie ihn Dotfile-Manager für
  `~/.config` oder `~/.agents` anlegen, wird verfolgt, wenn er an eine Stelle
  innerhalb Ihres Home-Verzeichnisses führt. Unter Windows zählt eine Junction
  als Link. Ein Link, der Ihr Home-Verzeichnis verlässt, bricht die Installation
  mit `target escapes the
  allowed materialization root` ab, gefolgt vom Link, dem Ordner, zu dem er
  führt, und der Korrektur: Ersetzen Sie den Link durch einen echten Ordner. In
  einen Skill-Ordner, der selbst ein Link ist, wird nie geschrieben: Die
  Installation überspringt ihn mit einer Warnung oder hält an, wenn Apothem
  diesen Skill zuvor dort geschrieben hat. Ein Link innerhalb eines
  Skill-Ordners, den Apothem geschrieben hat, wird durch einen Ordner ersetzt,
  wenn die Installation diesen Skill das nächste Mal schreibt.
- Ein Harness-Ordner unterhalb von `~/.config`, etwa `~/.config/opencode/` von
  OpenCode oder ein `CODEX_HOME` dort, folgt ebenfalls einem Link bei
  `~/.config`, der an eine Stelle innerhalb Ihres Home-Verzeichnisses führt.
  Ein Link bei `~/.config`, der Ihr Home-Verzeichnis verlässt, bricht die
  Installation ab, bevor sie eine Datei schreibt, ebenso ein Link auf einem
  Pfad, den die Installation innerhalb des Harness-Ordners schreibt. Beim
  ersten Lauf wird auch das Startprofil, ebenfalls unterhalb von `~/.config`,
  nicht über einen Link geschrieben, der Ihr Home-Verzeichnis verlässt: Der
  Lauf hält mit `Apothem could
  not create the starter profile` an, wie es `apothem quickstart`, `apothem profile
  init`, `apothem profile set` und `apothem profile edit` tun. Um das Profil
  außerhalb Ihres Home-Verzeichnisses zu halten, legen Sie es zuerst dort mit
  `apothem
  profile init --profile PATH` an, wobei PATH sein eigener Pfad außerhalb Ihres
  Home-Verzeichnisses ist, und übergeben Sie jedem Befehl dasselbe
  `--profile PATH`. Das bringt nur über den Profilschritt hinweg: Eine
  Installation, die unterhalb von `~/.config` schreibt, hält weiterhin am Link
  an. Für OpenCode setzen Sie außerdem `XDG_CONFIG_HOME` (siehe
  [OpenCode](/docs/harnesses/opencode)). Ein Harness, dessen Installation immer
  `~/.config/apothem/` schreibt, braucht stattdessen einen Link, der innerhalb
  Ihres Home-Verzeichnisses bleibt; seine Harness-Seite sagt das.
- Ein Home-Ordner, der selbst ein Link ist, etwa ein Windows-Benutzerprofil,
  das hinter einer Junction auf ein anderes Laufwerk verschoben wurde, wird
  verfolgt: Jeder Schreibvorgang bleibt innerhalb des Ordners, zu dem er führt.
- Die Installation fügt Ihrem Repository keine Skill- oder Regeldatei hinzu. Das
  Projekt erhält die Regeldatei des Adapters sowie den Datenordner `.apothem/`,
  den jede Projektinstallation anlegt.
- Ein Skill-Ordner, der den Namen eines Apothem-Skills trägt und den Apothem
  nicht geschrieben hat, wird übersprungen. Die Installation gibt eine
  `Warning:`-Zeile aus, und der `--format json`-Umschlag trägt einen
  `warnings`-Eintrag mit `"outcome": "warning"` und
  `"operation": "skill_conflict"`, der den Ordner benennt. Benennen Sie den
  Ordner um oder verschieben Sie ihn und führen Sie dann
  [`update`](/docs/cli-reference/update) aus.
- Diese Regel gilt für jeden gemeinsamen Skills-Ordner in der Tabelle oben:
  `~/.agents/skills/`, `~/.codebuddy/skills/`, `~/.kiro/skills/` und
  `~/.trae/skills/`. Ein Installationsdatensatz zeigt, dass ein Skill-Ordner
  dort Apothem gehört, solange sein Installationsordner (ein Projekt oder ein
  `CODEX_HOME`) aktiv ist: Er ist vorhanden und enthält noch eine der Dateien,
  die diese Installation darin aufgezeichnet hat, mit dem Inhalt von Apothem.
  Eine Datei, die Apothem gehört, zählt, solange sie vorhanden ist. Eine Datei,
  die Ihnen gehört, etwa eine Anweisungsdatei, der Apothem seinen Block
  hinzugefügt hat, zählt nur, solange sie diesen Block noch enthält oder, bei
  einer Datei ohne Block, den Inhalt, den Apothem aufgezeichnet hat; ein neu
  geklontes Projekt, das nur seine eigene Kopie der Datei behält, ist daher
  nicht aktiv. Die Unterstützungsdateien, die eine Installation unter
  `.apothem/support/` schreibt, zählen; die Datenspeicher unter `.apothem/`
  (Memory, Kontexte, Pläne) zählen nicht, ebenso wenig eine Datei, die über
  einen Link innerhalb des Installationsordners erreicht wird.
- Jeder andere Datensatz, dessen Installationsordner nicht mehr existiert,
  keine Apothem-Dateien enthält oder nicht gelesen werden kann (ein Laufwerk
  oder eine Netzwerkfreigabe, die nicht antwortet, ein Berechtigungsfehler),
  zeigt nur dann, dass ein Skill-Ordner Apothem gehört, wenn dieser Ordner
  genau die Dateien enthält, die diese Installation aufgezeichnet hat,
  unverändert, ohne hinzugefügte Datei und ohne Link darin. Ein Ordner, der
  bereits enthält, was dieses Release schreibt, bleibt unverändert, sodass ein
  unbearbeiteter Ordner, den ein früheres Release geschrieben hat, nicht
  betroffen ist, solange er noch dem entspricht, was dieses Release schreibt.
- Die gemeinsamen Ordner selbst zählen nie als Dateien eines
  Installationsordners, sodass ein im Home-Ordner installiertes Projekt nicht
  allein deshalb aktiv ist, weil `~/.agents/skills/` oder `~/.config/apothem/`
  vorhanden ist.
- Wenn also nur solche Datensätze einen Skill-Ordner auflisten, überspringt die
  Installation ihn und lässt ihn in drei Fällen unberührt: Sie haben dort Ihren
  eigenen Skill abgelegt, Sie haben ihn bearbeitet (eine Datei geändert,
  hinzugefügt oder entfernt), oder ein früheres Release, das seine Dateien nicht
  aufgezeichnet hat, hat ihn geschrieben, und dieses Release schreibt etwas
  anderes. Dasselbe gilt, wenn nur eine frühere Installation im selben Ordner
  ihn aufgelistet hat: Eine Installation, die den Ordner übersprungen hat,
  listet ihn nicht auf, und er ist weiterhin nicht belegt, sofern er nicht
  genau die Dateien enthält, die diese frühere Installation aufgezeichnet hat.
  Die Warnung von Installation, Aktualisierung und Dry-Run nennt die Ursache und
  die zwei Wege weiter, mit denselben Worten wie
  [`verify`](/docs/cli-reference/verify), das den Harness als nicht
  verifiziert meldet und diese Ordner nennt. Um Ihren Skill zu behalten, lassen
  Sie ihn dort. Um die Version von Apothem zu verwenden, verschieben Sie den
  Ordner aus dem Skills-Ordner und führen Sie dann
  [`update`](/docs/cli-reference/update) für diesen Harness aus (mit
  `--project` für einen Harness mit Projekt-Geltungsbereich).
- Jede solche Installation, Aktualisierung und jeder solche Dry-Run gibt einen
  `Note:` aus, der die Ordner benennt, die außerhalb von `--project` geschrieben
  werden. Im JSON-Umschlag ist er ein `warnings`-Eintrag mit
  `"operation": "user_level_write"` und einer `paths`-Liste.

## Hinweise zu Fähigkeiten

Jeder Adapter projiziert nur die Fähigkeiten, die sein Harness nativ
unterstützt; Fähigkeiten ohne native Oberfläche werden gemeldet, nicht still
verworfen. Im Plain-Modus ist dies ein einzelner gruppierter Hinweis je Harness
(zum Beispiel
`Note: <harness> - 9 capabilities not projected; pass --verbose for detail`);
unter `--verbose` gibt jede Fähigkeit ihre eigene Begründungszeile aus. Jede
andere Adapterwarnung wird auch im Plain-Modus in einer eigenen `Warning:`-Zeile
ausgegeben, zum Beispiel die Zed-Warnung, die eine Anweisungsdatei benennt, die
von der neuen `.rules`-Datei verdeckt wird, und die Warnung, die eine Datei
benennt, die einen Apothem-BEGIN-Marker ohne nachfolgendes END enthält: Die
Installation behält den Text nach diesem Marker und schreibt den Block von
Apothem getrennt davon, daher nennt die Warnung die Zeile des Markers, gibt
nummerierte Schritte, die diese Zeile und jede andere BEGIN-Markerzeile außer
der, die den Block von Apothem öffnet, ändern (auch einen BEGIN-Marker, den Sie
in Code zitieren), und sagt, den END-Marker nicht stattdessen wieder
hinzuzufügen, was
dann zwei Apothem-Blöcke hinterließe (siehe
[Fehlerbehebung](/docs/install/troubleshooting#a-file-has-an-apothem-begin-marker-with-no-end-marker)).
Ebenso die Warnung für eine Datei, die zwei oder mehr vollständige Blöcke
zwischen den Markern von Apothem enthält und jeden Block mit seinen Zeilen
nennt (siehe
[Eine Datei enthält zwei Blöcke zwischen den Markern von Apothem](/docs/install/troubleshooting#a-file-holds-two-blocks-between-apothems-markers)),
und die Warnung für eine Datei, in der Apothem seinen Block nicht von Ihrem
Text unterscheiden kann und die jedes Markerpaar und dessen Behebung nennt (siehe
[Apothem kann seinen Block nicht von Ihrem Text unterscheiden](/docs/install/troubleshooting#apothem-cannot-tell-its-block-from-your-text)):
Die Installation lässt eine solche Datei unverändert (bei Markerpaaren,
solange ein Installationsdatensatz die Datei auflistet; siehe
[`update`](/docs/cli-reference/update)). Eine Installation, die eine solche
Datei unverändert lässt, endet als teilweise, da das Werkzeug aus dieser Datei
keinen aktuellen Apothem-Block erhält: Statt der `✓`-Zeile gibt sie auf der
Standardfehlerausgabe eine `✗`-Zeile aus, die die Datei nennt (sodass
`--quiet` sie behält), der `status` des `--format json`-Umschlags ist
`"partial"`, die Warnung zu dieser Datei trägt
`"detail": {"left_as_is": "1"}`, und der Exit-Code ist `2`. Jede Installation
und Aktualisierung endet so, bis Sie die Markerzeilen korrigieren, die die
Warnung nennt. Ohne `--quiet` endet eine solche Installation mit
`--harness all` mit einer Zusammenfassungszeile, die statt mit `✓` mit `!`
beginnt und die unverändert gelassenen Dateien zählt:
`! Installed <n> harnesses (<m> files written); <k> file(s) left as they are, named above.`
Mit `--clean` gibt eine solche Installation ihren nächsten Schritt,
`apothem verify`, nicht aus, da er fehlschlägt, bis Sie die Datei korrigieren.
In einem Dry-Run sagt die Warnung für eine unverändert gelassene Datei, dass
Apothem
"would leave the file as it is", und der Lauf endet weiterhin mit `status`
`"dry_run"` und Exit-Code `0`. Eine Regel in Ihrem Profil, die einen Codeblock
öffnet und nie schließt, verdeckt nicht den END-Marker des Blocks, den die
Installation schreibt: Die Installation schließt diesen Codeblock am Ende des
Blocks. Ein Block, den ein früheres Release aus einer solchen Regel geschrieben
hat, hat keine solche schließende Zeile. Ein Codeblock von Ihnen, der oberhalb
des Blocks von Apothem öffnet und nie schließt, ist ein anderer Fall: Eine
schließende Zeile im Block schließt ihn, sodass der Block als Code gelesen
wird. Die Installation warnt vor einem solchen Block, sobald sie ihn schreibt,
und die Warnung nennt den Codeblock, der oberhalb des BEGIN-Markers zu
schließen ist (siehe
[Apothem kann seinen Block nicht von Ihrem Text unterscheiden](/docs/install/troubleshooting#apothem-cannot-tell-its-block-from-your-text)).
Ein Dry-Run liest die Datei, bevor etwas geschrieben wird, und zeigt daher
nicht, dass der Block nach dem Schreiben als Code gelesen würde.
Der `--format json`-Umschlag trägt unabhängig von der Ausführlichkeit immer das
vollständige `warnings`-Array.

Installation und Aktualisierung geben außerdem Empfehlungshinweise als
`Note:`-Zeilen aus. Ein Empfehlungshinweis ändert niemals, was die Installation
schreibt. Wenn eine Installation in ein gemeinsames Wurzelverzeichnis schreibt,
also einen Pfad, den auch andere Werkzeuge laden (zum Beispiel den Skills-Ordner
`~/.agents/skills/`), benennt der Hinweis diese Werkzeuge und setzt ein Werkzeug,
das den Pfad nur unter einer Bedingung lädt, in Klammern, zum Beispiel
`Open-Claw (only under its default state
directory)`. Eine Installation, die einen Ordner schreibt, den auch andere
Installationen schreiben (die Rolle `holder`), teilt mit, dass der Ordner
bestehen bleibt, bis die letzte Apothem-Installation, die ihn verwendet,
deinstalliert wird, und benennt die Installationen, die ihn derzeit verwenden.
Wenn eine Installation auf ein Werkzeug zielt, das bereits Apothem-Inhalte aus dem
gemeinsamen Wurzelverzeichnis einer anderen Installation lädt, benennt der
Hinweis die Installation, die sie dort abgelegt hat: den registrierten Eigentümer,
solange er den Ordner noch verwendet, andernfalls die älteste Installation, die
ihn verwendet. Im `--format json`-Umschlag ist jeder Empfehlungshinweis ein
`warnings`-Eintrag mit `"outcome": "advisory"` und `"operation": "shared_root"`;
seine `role` ist `owner`, `holder` oder `reader`, `holders` listet die
Installationen auf, die den Ordner verwenden, und `owner_of_record` benennt den
eingetragenen Eigentümer.

Eine Installation, die Hooks registriert, gibt außerdem Hinweise zur Hook-Datei
aus. Ein `hook_review`-Empfehlungshinweis benennt den Schritt, den das Werkzeug
benötigt, bevor es die Hooks ausführt (einen Neustart und eine Überprüfung oder
das Vertrauen in den Arbeitsbereich), oder die Gefahr einer Hook-Datei, die ein
Repository eincheckt und die den Interpreter dieses Rechners benennt. Ein
`hook_import`-Empfehlungshinweis erscheint für ein Werkzeug, das auch die Hooks in
den Einstellungsdateien von Claude Code ausführt, etwa denen, die die
Apothem-Installation für Claude Code schreibt, und benennt den eigenen Schalter
des Werkzeugs, mit dem sich dieser Import abschalten lässt, sowie das, was der
Schalter außerdem unterbindet. Jeder ist ein `warnings`-Eintrag mit
`"outcome": "advisory"`, dem `harness`, dem `path` der Hook-Datei und einer
`message`.

Ein Hook-Befehl setzt den Projektpfad und den Interpreterpfad in doppelte
Anführungszeichen, die `sh`, Git Bash und PowerShell jeweils lesen. Ein Pfad, der
`$`, einen Backtick, ein doppeltes Anführungszeichen oder einen Backslash enthält,
würde den Befehl eine andere Datei ausführen lassen; daher bricht die Installation
(und `--dry-run`) mit einem Fehler ab, der den Pfad benennt, und schreibt nichts;
verschieben oder benennen Sie das Projekt um und führen Sie den Befehl erneut aus.
Ein Leerzeichen oder ein Apostroph in einem Pfad ist unproblematisch.

Manche Werkzeuge laden aus einer festen Liste in einem Ordner nur die erste
Datei mit Text, sodass eine Datei von Ihnen vor der, die Apothem schreibt, das
Werkzeug daran hindert, den Apothem-Block zu laden. Zum Beispiel liest
[ein unterstütztes Werkzeug](/docs/harnesses/codex#compatibility-notes) eine
`AGENTS.override.md` mit Text statt der `AGENTS.md`, die Apothem daneben in den
Home-Ordner dieses Werkzeugs schreibt. Installation und Aktualisierung geben
dann einen Hinweis aus, der diese Datei nennt, Dry-Runs eingeschlossen. Eine
leere Override-Datei wird übersprungen, ebenso ein symbolischer Link auf
`AGENTS.md`; ein Hardlink oder eine Kopie erhält den Hinweis, weil eine
Installation, die `AGENTS.md` neu schreibt, sie als separate Datei
zurücklässt. OpenCode 1 funktioniert anders: Eine `instructions`-Liste in einer
`opencode.jsonc`, selbst eine leere, ersetzt die Liste, die Apothem in
`opencode.json` im selben Ordner schreibt. Eine
`config.json`, `opencode.json` oder `opencode.jsonc` dort, die es nicht lesen
oder parsen kann, deren oberste Ebene kein Objekt ist, deren
`instructions`-Wert keine Liste von Text ist oder die ein `{file:path}` mit
einer Datei enthält, die es nicht lesen kann, hindert es daran, irgendeinen
Teil seiner Konfiguration zu laden, ebenso ein Ordner mit einem dieser Namen.
Installation und Aktualisierung geben auch für jede solche Datei einen
`instruction_override`-Hinweis aus, außer für eine `opencode.json`, die sie
nicht einmal als JSON5 parsen können und die sie mit einem
`config.unparseable`-Fehler ablehnen
([OpenCode-Hinweise](/docs/harnesses/opencode#compatibility-notes)). Der
Hinweis ist ein `warnings`-Eintrag mit `"outcome": "advisory"` und
`"operation": "instruction_override"`, dem `harness`, dem `path` der Datei, um
die es im Hinweis geht, dem `target`, das die Installation schreibt, und einer
`message`.

Die MCP-Server des Profils erhalten drei Empfehlungshinweise, die jeweils das
Profilfeld benennen:

| Operation | Bedingung | Behebung |
| --- | --- | --- |
| `mcp_deprecated_transport` | `transport: sse` (die MCP-Spezifikation erklärt HTTP+SSE für veraltet) | Verwenden Sie `streamable-http`, wenn der Server es unterstützt. |
| `mcp_plain_http` | eine `http://`-URL zu einem Host, der keine Loopback-Adresse ist | Verwenden Sie eine `https://`-URL. |
| `mcp_literal_credential` | ein `headers`- oder `env`-Wert, der wie ein Token geformt ist (`ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_`, `sk-`, `xoxa-`, `xoxb-`, `xoxo-`, `xoxp-`, `xoxr-`, `xoxs-` oder `Bearer` mit einem langen Token) | Bewahren Sie das Geheimnis in einer Umgebungsvariable auf und schreiben Sie Referenzen im Stil von `${GITHUB_TOKEN}`. |

Der Empfehlungshinweis zu Anmeldedaten gibt niemals den gefundenen Wert aus. Ein
Wert, der eine `${...}`-Referenz enthält, wird niemals markiert.

## Operator-Konfigurationen mit Kommentaren

Manche Harness-Konfigurationen sind Dateien, die Sie ebenfalls bearbeiten, etwa
`settings.json`, `opencode.json` (das JSONC sein kann), `openclaw.json` (JSON5)
und `config.yaml`. Die Installation führt ihre Schlüssel in diese Dateien
zusammen und behält jeden Schlüssel bei, den Sie hinzugefügt haben.

Eine Zusammenführung schreibt die Datei als reines JSON oder YAML neu, wodurch
Kommentare, nachgestellte Kommas und JSON5-Syntax verloren gingen. Daher gilt:

- Wenn die Zusammenführung keinen Wert ändern würde (zum Beispiel, weil Sie
  Apothems Schlüssel bereits selbst hinzugefügt haben), bleibt die Datei Byte für
  Byte unverändert.
- Wenn die Zusammenführung einen Wert in einer Datei ändern muss, die Kommentare
  oder JSON5-Syntax enthält, oder in einer Datei, die sich überhaupt nicht parsen
  lässt, schreibt die Installation für diesen Harness nichts und endet mit
  Exit-Code 1 und dem Fehlercode `config.unparseable`. Das Feld `fix` benennt die
  Schlüssel, die die Installation hinzufügen würde, sodass Sie die Datei in
  reines JSON oder YAML umwandeln oder diese Schlüssel von Hand hinzufügen und den
  Befehl erneut ausführen können.
- Wenn ein Schlüssel, den die Installation mit einer Zuordnung oder einer Liste
  füllt (zum Beispiel `skills.external_dirs` in `config.yaml`), in Ihrer Datei
  einen skalaren Wert oder die jeweils andere Containerform enthält, schreibt die
  Installation für diesen Harness nichts und endet mit Exit-Code 1 und demselben
  Fehlercode, weil das Füllen des Schlüssels Ihren Wert verwerfen würde. Der
  Fehler benennt den Schlüssel; ändern Sie ihn in die genannte Form oder entfernen
  Sie ihn und führen Sie den Befehl erneut aus. Ein Schlüssel, den Sie leer
  gelassen haben (`skills:` ohne etwas darunter), wird gefüllt.

## Optionen

| Option | Beschreibung |
|---|---|
| `--harness NAME` | Zu installierender Harness-Adapter oder `all` für die registry-weite Menge (erforderlich). Bei `all` werden Harnesses übersprungen, die in `exclude_harnesses` des Profils aufgeführt sind; ein ausdrücklich benannter Harness wird dagegen auch dann installiert, wenn er aufgeführt ist. Führen Sie `apothem harnesses list` aus, um die registrierten Namen zu sehen. |
| `--profile PATH` | Pfad zur YAML-Datei des gemeinsamen Profils. Standard: `~/.config/apothem/profile.yaml`. |
| `--dry-run` | Vorschau der Installation, ohne Dateien zu schreiben. |
| `--clean`, `--fresh` | Optionaler sauberer Neuanfang: Die vier unter [Wirkungsradius-Vorschau](#wirkungsradius-vorschau) aufgeführten Ordner werden vor der Installation gesichert und entfernt, gleich welchen Harness `--harness` nennt. |
| `--yes` | Überspringt die Bestätigung je Ziel während einer Entfernung für den sauberen Neuanfang (erforderlich für nicht interaktive `--clean`-Läufe). |
| `--project PATH` | Projektwurzel für Harnesses mit Projekt-Geltungsbereich. |
| `--quiet`, `-q` | Unterdrückt informative Ausgaben; nur Fehler werden ausgegeben. |
| `--verbose`, `-v` | Gibt die Begründung jeder nicht projizierten Fähigkeit aus statt des gruppierten Hinweises je Harness. |
| `--format plain\|json` | Ausgabeformat (Standard: `plain`). |
| `--json` | Kurzform für `--format json`. |
| `--no-color` | Deaktiviert ANSI-Farbcodes in der Ausgabe. |
| `-h`, `--help` | Zeigt die Hilfe an und beendet den Befehl. |

## JSON-Ausgabe

Wenn `--json` (oder `--format json`) angegeben wird, wird ein einzelnes
JSON-Dokument nach stdout geschrieben:

```json
{
  "schema_version": 1,
  "status": "success",
  "command": "install",
  "action": "installed",
  "harness": "claude-code",
  "profile_path": "C:\\Users\\Example\\.config\\apothem\\profile.yaml",
  "project": null,
  "files_written": ["C:\\Users\\Example\\.claude\\settings.json"],
  "results": [],
  "warnings": [],
  "error": null,
  "output_path": "C:\\Users\\Example\\.claude\\settings.json"
}
```

Eine Installation, die eine Datei wegen ihrer Apothem-Markerzeilen unverändert
gelassen hat, hat `status` `"partial"` und beendet sich mit Code `2` (siehe
[Hinweise zu Fähigkeiten](#hinweise-zu-fähigkeiten)).

Bei `--dry-run` wird nichts geschrieben, und `results` listet jeden Pfad auf, den
die Installation schreiben würde, jeweils mit dem Ergebnis, das sie hätte
(`created`, `updated` oder `unchanged`), und, für eine Datei, die Sie ebenfalls
bearbeiten, mit dem Unified Diff in `detail.diff` — derselbe Plan, den
[`apothem diff`](/docs/cli-reference/diff) anzeigt:

```json
{
  "schema_version": 1,
  "status": "dry_run",
  "command": "install",
  "action": "dry_run",
  "harness": "claude-code",
  "files_written": [],
  "results": [
    {
      "harness": "claude-code",
      "outcome": "created",
      "operation": "write_text",
      "path": "C:\\Users\\Example\\.claude\\settings.json",
      "message": "dry run: no filesystem changes made"
    }
  ],
  "warnings": [],
  "error": null
}
```

Ein an einem Link abgelehntes Ergebnis nennt den Link in `detail.symlink` und
den Pfad, zu dem er führt, in `detail.leads_to`. Ein Ergebnis, das abgelehnt
wurde, weil ein Link den Ordner eines Werkzeugs aus Ihrem Home-Verzeichnis
herausführt, trägt außerdem die Korrektur in `detail.fix`.

Wenn `--clean` angegeben wird, trägt der Umschlag zusätzlich ein `clean`-Objekt,
das die Entfernungsphase beschreibt — die Liste der Dispositionen je Ziel, ob der
Lauf eine Vorschau war, und das mit Zeitstempel versehene Sicherungsverzeichnis
(`null` bei einem Dry-Run):

```json
{
  "clean": {
    "dry_run": true,
    "backup_dir": null,
    "targets": [
      {
        "path": "C:\\Users\\Example\\.claude",
        "present": true,
        "removed": false,
        "skipped_reason": null
      }
    ]
  }
}
```

Ein Dry-Run mit sauberem Neuanfang zeigt beide Phasen in einem Dokument in der
Vorschau: die Entfernungsvorschau unter `clean` und die Vorschau der neuen
Schreibvorgänge unter `results`.

Erwartete Validierungsfehler verwenden denselben Umschlag und enthalten ein
Fehlerobjekt:

```json
{
  "schema_version": 1,
  "status": "error",
  "command": "install",
  "harness": "all",
  "files_written": [],
  "error": {
    "code": "project.required",
    "field": "project",
    "reason": "project-scope harnesses require --project: cursor, gemini-cli, github-copilot, kimi-code, windsurf, codebuddy, kiro, trae, zed, glm.",
    "fix": "Pass --project PATH or select only user-scope harnesses."
  }
}
```

## Beispiele

```bash
apothem install --harness claude-code
apothem install --harness claude-code --dry-run
apothem install --harness cursor --project . --profile ~/profile.yaml --json
apothem install --harness all --project . --dry-run --json
apothem installing --harness claude-code   # continuous-form alias
apothem Installing --harness claude-code   # capitalized variant
```

## Exit-Codes

| Code | Bedeutung |
|---|---|
| 0 | Adapter erfolgreich installiert oder Dry-Run sauber geplant |
| 1 | Erwarteter Validierungs-, Profil-, Harness-, Projekt- oder Adapterfehler |
| 2 | Teilweise: Ein Batch hat nach mindestens einem Schreibvorgang angehalten, oder die Installation hat eine Datei, in der Apothem seinen Block hält, wegen ihrer Apothem-Markerzeilen unverändert gelassen (siehe [Hinweise zu Fähigkeiten](#hinweise-zu-fähigkeiten)); `status` ist `"partial"` |
| 64 | Verwendungsfehler: eine unbekannte Option oder ein unbekannter Befehl oder ein fehlender oder ungültiger Optionswert. Unter `--json` ist der Fehler ein JSON-Umschlag mit dem Code `cli.usage`. |
