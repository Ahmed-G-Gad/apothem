Apothem liefert eine architekturbewusste `/plan`-Pipeline, eine dreizehnstufige
`/research`-Pipeline sowie eine Audit-Review-Sequenz aus elf Befehlen aus — und gibt
damit jedem Projekt einen strukturierten Weg von roher Prosa zu Code in
Produktionsqualität, der entlang mehrerer Achsen geprüft wurde, und von einer
rohen Idee zu einem verbreiteten, begutachteten (peer-reviewed) Paper.

## Pipeline-Überblick

```mermaid
flowchart LR
    accTitle: Plan pipeline command flow
    accDescr: Left-to-right flowchart of the apothem plan pipeline from the spec stage through the generate and review stages, then through a conditional architecture-bearing decision that either runs the design stage or skips directly to the execute stage. The orthogonal audit stage wraps the spec-through-review span as a closed remediation loop, and the re-entrant amend stage revises an existing suite and returns it to review.
    A[/plan-spec] --> B[/plan-generate]
    B --> C[/plan-review]
    AUD[/plan-audit<br/>orthogonal: wraps spec → review] -.->|closed-loop remediation| A
    AM[/plan-amend<br/>re-entrant: revises an existing suite] -.->|re-review| C
    C --> Q{Architecture-bearing suite?}
    Q -->|yes| F[/plan-design<br/>emit _inputs/design.md]
    Q -->|no| D[/plan-execute]
    F --> D
    D --> E[/plan-status]
    D --> G[Audit review sequence]
    G --> H[Completion milestone]
```

## Die Planungsstufen

Die Pipeline wird als acht vollwertige Slash-Befehle ausgeliefert, einer je
Stufe — jeder einzeln als `/plan-<stage>` aufrufbar. Der Orchestrator
[/plan](/docs/pipeline/plan) führt sie von einer Mission bis zu einer
ausgeführten Suite.

| Stufe | Rolle | Position |
|-------|------|----------|
| [/plan-spec](/docs/pipeline/plan-spec) | Schmiede — von der Prosa zur Spezifikation | Anfang |
| [/plan-generate](/docs/pipeline/plan-generate) | Generator — von der Spezifikation zur Plan-Suite | Kettenmitte |
| [/plan-review](/docs/pipeline/plan-review) | Prüfer — forensisches Audit des Plans | Kettenmitte |
| [/plan-design](/docs/pipeline/plan-design) | Architekt — `_inputs/design.md` für architekturtragende Suiten | Bedingtes Gate |
| [/plan-execute](/docs/pipeline/plan-execute) | Ausführender — Ausführung der Phasen | Ende |
| [/plan-status](/docs/pipeline/plan-status) | Berichterstatter — Status, nur lesend | Nur lesend |
| [/plan-audit](/docs/pipeline/plan-audit) | Wächter — geschlossene Schleife um spec → generate → review | Orthogonal (vor execute) |
| [/plan-amend](/docs/pipeline/plan-amend) | Verwalter — wiedereintretende Änderung einer bestehenden Suite | Wiedereintretend |

`/plan-audit` ist orthogonal zum linearen Ablauf, keine Stufe darin. Es umschließt
`/plan-spec → /plan-generate → /plan-review` als eine einzige geschlossene
Schleife, führt nur die fehlenden vorgelagerten Stufen aus, behebt Befunde aktiv
und hinterlässt die Suite bereit für `/plan-execute`. Es unterscheidet sich von
der Audit-Review-Sequenz weiter unten, die eine ausgeführte Codebasis statt
einer Plan-Suite auditiert.

`/plan-design` ist keine universelle Zeremonie. `/plan-review` stuft ein, ob die
Suite architekturtragende Oberflächen ändert. Falls ja, gibt `/plan-design` die
Design-Spur aus, die `/plan-execute` und `/architecture-review` verarbeiten.
Falls nein, geht die geprüfte Suite direkt in die Ausführung über.

## Die Forschungs-Pipeline

Die Forschungs-Pipeline wird als dreizehn vollwertige Slash-Befehle
ausgeliefert, einer je Stufe — jeder einzeln als `/research-<stage>` aufrufbar,
verkettet durch ein Sequenz-Gate und ein Übergabe-Manifest, unter zehn
Strenge-Mandaten (maßgebliche Quellen, Reproduzierbarkeit, Falsifizierbarkeit,
Zitationsintegrität, Präregistrierung, Ethik / Interessenkonflikte, statistische
Strenge, Open Science / FAIR, Konformität mit Berichtsrichtlinien, theoretische
Fundierung / Wirkung).

```mermaid
flowchart LR
    accTitle: Research pipeline command flow
    accDescr: Left-to-right flowchart of the apothem research pipeline from the ideate stage through spec, theory, sources, synthesis, proposal, study design, experiment, analysis, paper, and peer review to publish and disseminate, with a revision loop from review back to paper.
    RI[/research-ideate] --> RS[/research-spec]
    RS --> RT[/research-theory]
    RT --> RSO[/research-sources]
    RSO --> RSY[/research-synthesis]
    RSY --> RPR[/research-proposal]
    RPR --> RD[/research-design]
    RD --> RE[/research-experiment]
    RE --> RA[/research-analysis]
    RA --> RP[/research-paper]
    RP --> RR[/research-review]
    RR --> RPU[/research-publish]
    RPU --> RDI[/research-disseminate]
    RR -.->|revision loop| RP
```

| Stufe | Rolle | Position |
|-------|------|----------|
| [/research-ideate](/docs/pipeline/research-ideate) | Das Problem formulieren — Kandidatenfragen aus einem Domänen-Ausgangspunkt | Anfang |
| [/research-spec](/docs/pipeline/research-spec) | Die Frage rahmen — falsifizierbare Hypothesen + Umfang | Kettenmitte |
| [/research-theory](/docs/pipeline/research-theory) | Konzeptueller Rahmen + Wirkungstheorie (Theory of Change) | Kettenmitte |
| [/research-sources](/docs/pipeline/research-sources) | Systematische Quellensammlung mit einem wiederholbaren Suchprotokoll | Kettenmitte |
| [/research-synthesis](/docs/pipeline/research-synthesis) | Karte des Stands der Technik (SOTA) + Lückenanalyse | Kettenmitte |
| [/research-proposal](/docs/pipeline/research-proposal) | Ziele + Machbarkeit + Notfallpläne + Wirkung + Datenplan + Präregistrierungsplan; Matrix zur Förderausschreibung oder Antwort auf eine Wiedereinreichung | Kettenmitte |
| [/research-design](/docs/pipeline/research-design) | Studiendesign + Präregistrierung | Kettenmitte |
| [/research-experiment](/docs/pipeline/research-experiment) | Durchführen + aufzeichnen, reproduzierbar | Kettenmitte |
| [/research-analysis](/docs/pipeline/research-analysis) | Ergebnisse + Statistik | Kettenmitte |
| [/research-paper](/docs/pipeline/research-paper) | Paper-Entwurf auf Spitzenniveau | Kettenmitte |
| [/research-review](/docs/pipeline/research-review) | Kritik auf Peer-Review-Niveau | Kettenmitte |
| [/research-publish](/docs/pipeline/research-publish) | Paket für den Publikationsort + Einreichung | Kettenmitte |
| [/research-disseminate](/docs/pipeline/research-disseminate) | Verbreitung + Wirkung + FAIR-Archivierung | Ende |

Der Orchestrator für den gekapselten Workflow [/research](/docs/pipeline/research)
führt diese Stufen von der rohen Frage bis zum veröffentlichten Paper (er selbst
ist keine Stufe) und prüft die Ausgabe jeder Stufe unabhängig, bevor die nächste
Stufe darauf aufbaut; `--quick` führt nur `/research-sources` +
`/research-synthesis` aus, für einen zitierten Bericht in einem einzigen
Durchgang.

Die empirischen Stufen (sources, design, experiment, analysis) und die
Schreibstufen (paper, review, publish, disseminate) stützen sich zusätzlich auf
Oberflächen, die die Strenge operationalisieren — fairer Vergleich mehrerer
Methoden, Provenienz der Vergleichsverfahren, ein Gerüst für das
Experimentprogramm, ein Plan zur Rechenauslastung, eine optionale (Opt-in)
autonome Experimentschleife, ein Fortschritts-Gate nach Definition of Done,
Verblindung mit gestufter Offenlegung, ein Suchprotokoll, Zuteilung und
Teststärkeplanung der Studie, Analysedisziplin, Notfallpläne für den Plan,
Integrität der Abbildungen sowie die Planung von Vorträgen und Postern —, die
den zehn Mandaten operative Details hinzufügen, ohne sie zu erweitern.

## Audit-Review-Sequenz

Der Orchestrator für den gekapselten Workflow [/audit](/docs/pipeline/audit) durchläuft alle elf nachstehenden Dimensionen in einem einzigen parallelen Durchgang — das Gegenstück der Audit-Festung zu `/plan` und `/research` — und fasst die Ergebnisse zu einem einzigen deduplizierten, nach Schweregrad priorisierten Befundbericht zusammen (nur Bericht; die Behebung wird an `/elevate` weitergeleitet). Jede Dimension ist auch einzeln aufrufbar.

Der Orchestrator für den gekapselten Workflow [/fortress](/docs/pipeline/fortress) schließt die Schleife, über die `/audit` berichtet: Er erkennt Befunde über `/audit`, verifiziert jeden Befund, behebt jeden verbleibenden Befund an der Oberfläche, der er gehört, auditiert in einer begrenzten Schleife erneut und führt das Ergebnis durch das Gate [/release-readiness](/docs/pipeline/release-readiness) — das Gegenstück für die Produktionshärtung zu `/plan` und `/research`.
