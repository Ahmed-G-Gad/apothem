Apothem ist ein host-agnostischer Konfigurationsmanager für KI-Harnesses. Ein
gemeinsames Profil unter `~/.config/apothem/profile.yaml` wird in siebzehn
harness-native Konfigurationsoberflächen materialisiert. Dieser Abschnitt legt
dar, wie Sie Apothem gegenüber den Alternativen bewerten, die Sie bereits
verwenden.

## Wie Apothem im Vergleich abschneidet

Die Angaben zu vergleichbaren Projekten auf dieser Seite haben den Stand
**2026-10-02** und stammen aus der eigenen README oder Dokumentation des
jeweiligen Projekts (siehe [Quellen](#quellen)); prüfen Sie sie bei jedem
Minor-Release erneut.

Andere Werkzeuge lösen angrenzende Teile dieses Problems. Dateibasierte
Konfigurationsmanager wie **chezmoi** und **GNU Stow** legen Dateien ab,
verlinken sie oder erzeugen sie aus Templates, übersetzen aber niemals eine
Quelle in das *native* Konfigurationsschema jedes Harness.
Werkzeugübergreifende Sync-CLIs erzeugen aus einer Quelle Dateien je Werkzeug:
**rulesync** erzeugt native Konfiguration für 60 Coding-Werkzeuge und zwei
offene Standards, über eine breitere synchronisierte Einheit als die von
Apothem; **ruler** verteilt ein `.ruler/`-Verzeichnis auf 33 Ziele, verkettet
dabei Regeln in die Anweisungsdatei jedes Werkzeugs und übersetzt MCP-Server,
Skills und Subagenten in native Konfiguration. Das Unterscheidungsmerkmal von
Apothem ist die **Governance- und Lebenszyklus-Disziplin, die rund um die
Synchronisierung ausgeliefert wird**: ein mechanisiertes Konformitäts-Gate,
deterministische Pipelines, eine Audit-Festung und ein reversibler,
verifizierter Lebenszyklus.

| Fähigkeit | Apothem | Dateibasierte Konfigurationsmanager (chezmoi, Stow) | rulesync | ruler |
| ---------- | :-----: | :----------------------------------: | :------: | :---: |
| Eine Quelle für die nativen Schemata vieler Werkzeuge | Ja — siebzehn Harness-Adapter | Nein — Kopie, Symlink oder Template, keine Übersetzung | Ja — 60 Werkzeuge plus die Standards AGENTS.md und Agent Skills | Teilweise — Regeln werden in die Anweisungsdatei jedes Werkzeugs verkettet; MCP, Skills und Subagenten werden in nativer Form geschrieben |
| Synchronisierte Einheit | Regeln, Skills, Hooks, Slash-Befehle, MCP | beliebige Dateien | Regeln, Ignore, MCP, Befehle, Subagenten, Skills, Hooks, Berechtigungen, Checks (Anweisungen für Code-Review-Checks) | Regeln, MCP, Skills, Subagenten |
| Governance-Korpus (Verhaltensregeln plus ein mechanisches Konformitäts-Gate) | Ja — `python -m apothem.conformity.gate` | Nein | Nein — seine Funktion `checks` synchronisiert Code-Review-Checks in die Werkzeuge; kein Konformitäts-Gate über den Regeln | Nein |
| Deterministische Planungs- und Recherche-Pipelines | Ja — von `/plan-spec` bis `/plan-execute`, `/research` in dreizehn Stufen | Nein | Nein | Nein |
| Audit-Festung, die erkennt und behebt | Ja — Durchlauf mit elf Befehlen, `/fortress`-Re-Audit-Schleife | Nein | Nein | Nein |
| Lieferketten-gehärtete Releases | Ja — SBOM, Sigstore, SLSA, Scorecard-Ziel | Nicht verglichen | In seiner README nicht angegeben | In seiner README nicht angegeben |
| Reversibler, verifizierter Lebenszyklus | Ja — Sicherung, `apothem verify --json`, Deinstallation ohne Waisen | chezmoi: `chezmoi verify` prüft jedes Ziel; Stow: nur Symlinks | In seiner README nicht angegeben | `.bak`-Sicherungen und `ruler revert`; kein Verify-Befehl in seiner README |

Wo ein vergleichbares Projekt stärker ist, wird es benannt: **rulesync**
erreicht mehr als dreimal so viele Werkzeuge und synchronisiert eine breitere
Einheit (einschließlich Berechtigungen und Review-Checks), und **ruler**
erreicht fast doppelt so viele Werkzeuge und hat einen eigenen
Revert-Befehl. Apothem tauscht die reine Werkzeuganzahl gegen die Governance-,
Audit- und Lebenszyklus-Disziplin, die rund um die Synchronisierung
ausgeliefert wird — ein Konformitäts-Gate, deterministische Planungs- und
Recherche-Pipelines, eine Audit-Festung mit elf Befehlen, dauerhaftes
Gedächtnis und ein reversibler, verifizierter Lebenszyklus —, die keines der
beiden Sync-Werkzeuge mitbringt.

## Wie Sie vergleichen

Vergleichen Sie entlang dreier Achsen:

1. **Quelle der Wahrheit.** Wo liegen Ihre Regeln, Agents, Befehle und
   Einstellungen? Apothem hält ein einziges gemeinsames Korpus und rendert
   daraus das native Format jedes Harness. Handgepflegte Konfiguration hält
   eine Kopie pro Werkzeug.
2. **Drift-Kosten.** Was passiert, wenn Sie eine Regel ändern? Apothem
   überträgt die Änderung bei `apothem update` an jeden installierten Harness.
   Handgepflegte Konfiguration verlangt, dass Sie die native Datei jedes
   Werkzeugs einzeln bearbeiten und sie aus dem Gedächtnis aufeinander
   abgestimmt halten.
3. **Verifizierung.** Woher wissen Sie, dass jeder Harness korrekt konfiguriert
   ist? Apothem liefert `apothem verify --harness <name>` und `apothem doctor`.
   Handgepflegte Konfiguration hat keine eingebaute Verifizierung.

## Funktionsmatrix

Die Matrix stellt Apothem den beiden Alternativen gegenüber, zu denen Operatoren
zuerst greifen: die native Konfiguration jedes Harness von Hand zu pflegen und
diese Dateien über einen universellen Dotfile-Manager zu verwalten.

| Fähigkeit | Handgepflegte Konfiguration | Dotfile-Manager | Apothem |
| ---------- | ---------------------- | --------------- | ------- |
| Eine einzige gemeinsame Quelle der Wahrheit | Nein (eine Kopie pro Werkzeug) | Nein (verfolgt Dateien, kein Profil) | Ja (ein Profil) |
| Rendert harness-native Formate | Manuell | Nein | Ja (Materializer je Adapter) |
| Drift-Vermeidung zwischen Harnesses | Manueller Abgleich | Nur Datei-Sync | Ja (`apothem update`) |
| Installation/Deinstallation je Harness | Manuell | Teilweise (Symlink/Kopie) | Ja (`install` / `uninstall`) |
| Eingebaute Verifizierung | Keine | Keine | Ja (`verify` / `doctor`) |
| Formatübersetzung je Werkzeug | Keine | Keine | Ja (`.mdc`, `.toml`, eingebettetes `.md`) |
| Siebzehn Harnesses aus einer einzigen Eingabe | Nein | Nein | Ja |
