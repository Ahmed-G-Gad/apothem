**Anbieter:** Moonshot
**Installationsname:** `kimi-code`
**Status:** GA
**Native Konfiguration:** `<project>/AGENTS.md` sowie `<project>/.kimi-code/.apothem/support/`

## Installation

```bash
apothem install --harness kimi-code --project /path/to/project
```

Der Adapter schreibt die gemeinsame Governance-Oberfläche von Apothem als durch
Sentinels begrenzten verwalteten Block in die `AGENTS.md` im
Projektstammverzeichnis (vom Operator verfasste Prosa außerhalb der Sentinels
bleibt erhalten) und hält die nicht nativen Markdown-Kohorten im Apothem-eigenen
Unterstützungs-Teilbaum unter `<project>/.kimi-code/.apothem/support/`.
Eine Projekt-`AGENTS.md` wird außer von Kimi Code von vielen weiteren
Coding-Werkzeugen gelesen, daher wird der Block als projektweite Anleitung
geschrieben, die kein einzelnes Werkzeug als ihren Leser nennt.

Kimi Code liest die Anweisungsdatei `AGENTS.md` im Projektstammverzeichnis gemäß
der universellen AGENTS.md-Konvention, und die Projektkonfiguration liegt unter
`<project>/.kimi-code/`. Die Oberfläche `<project>/.kimi-code/mcp.json` gehört
dem Operator; Apothem benennt sie, verfasst aber keine Einträge.

**Geschriebene Dateien:** `<project>/AGENTS.md` (verwalteter Block) sowie die
Kohorten Commands, Skills, Hooks, Agenten, Regeln und Templates unter
`<project>/.kimi-code/.apothem/support/`.

## Zuordnung von Profil zu nativer Konfiguration

Der Adapter liest Apothems gemeinsames Profil und rendert die Anweisungsoberfläche
`AGENTS.md` im Projektstammverzeichnis bei jedem Lauf von `apothem install` oder
`apothem update`. Die Verhaltensregeln und der Governance-Korpus landen im
verwalteten Block der `AGENTS.md`; die Kohorten Commands, Skills, Hooks, Agenten,
Regeln und Templates werden unter `.kimi-code/.apothem/support/` abgelegt und von
der Anweisungsoberfläche referenziert. Dies ist das vom Adapter gewählte Layout,
keine Lücke in Kimi Code: Kimi Code lädt Skills aus `.kimi-code/skills/` und
`.agents/skills/`, benutzerdefinierte Agenten aus `.kimi-code/agents/` und
`.agents/agents/` sowie Hooks aus dem `[[hooks]]`-Array in
`~/.kimi-code/config.toml`, lädt sie aber nicht aus dem Unterstützungs-Teilbaum; die
dortigen Apothem-Kopien sind daher Referenzmaterial, auf das der
`AGENTS.md`-Block verweist. Der Block endet mit einem Abschnitt zu den
Apothem-Unterstützungsdateien, der relativ zum Projektstammverzeichnis das
Verzeichnis unter `.kimi-code/.apothem/support/` nennt, gegen das jeder Verweis im
Repository-Stil (`rules/<name>.md`, `templates/...`, `hooks/...`) aufgelöst wird,
sodass eine committete `AGENTS.md` keinen maschinenspezifischen Pfad enthält.
(Verhalten von Kimi Code gemäß seinen Anpassungsseiten zu
[Skills](https://moonshotai.github.io/kimi-code/en/customization/skills),
[Subagenten](https://moonshotai.github.io/kimi-code/en/customization/agents) und
[Hooks](https://moonshotai.github.io/kimi-code/en/customization/hooks), gelesen
am 2026-10-02.)

## Kompatibilitätshinweise

Kimi Code liest Projektanweisungen aus `AGENTS.md` oder
`.kimi-code/AGENTS.md` und erkennt `.kimi-code/mcp.json` als die dem Operator
gehörende MCP-Oberfläche; Apothem benennt diese Oberfläche, verfasst aber keine
Einträge darin. Von den beiden Anweisungsdateien schreibt der Adapter nur die
`AGENTS.md` im Projektstammverzeichnis, die Kimi Code als Projektanweisungen
liest; die Kimi-Code-Dokumentation sagt nicht, welche der beiden Dateien Vorrang
hat, wenn beide existieren. Kimi Code stellt keine Dateioberfläche für
Statuszeilen oder Output-Styles bereit, daher werden diese Kohorten nicht
materialisiert.

Kimi Code läuft auf der Kimi-Modellfamilie von Moonshot; das aktuelle Modell und
die aktuelle Konfigurationsoberfläche finden Sie in der
[Konfigurationsreferenz des Anbieters](https://moonshotai.github.io/kimi-code/en/configuration/config-files).

## Verifizierung

```bash
apothem verify --harness kimi-code --project /path/to/project
```

Der Befehl verify bestätigt Folgendes:

1. Die native Konfiguration existiert am erwarteten Pfad.
2. Jedes verwaltete Ziel existiert; verwaltete Dateien sind nicht leer, und
   JSON- oder YAML-Konfigurationen lassen sich parsen. Fügen Sie `--profile PATH`
   hinzu, um außerdem zu bestätigen, dass die installierten Dateien zu diesem
   Profil passen.
3. Die adapterspezifische Verifizierungsroutine meldet Erfolg.

## Aktualisierung

```bash
apothem update --harness kimi-code --project /path/to/project
```

Leitet den verwalteten Block der `AGENTS.md` im Projektstammverzeichnis und die
Unterstützungskohorten aus dem aktuellen Zustand des gemeinsamen Profils neu ab.

## Deinstallation

```bash
apothem uninstall --harness kimi-code --project /path/to/project
```

Entfernt den Apothem-Block aus der `AGENTS.md` im Projektstammverzeichnis und
behält jeden Text außerhalb der Sentinels. Die Datei wird nur gelöscht, wenn
darin nichts anderes übrig bleibt. Entfernt außerdem die Unterstützungsdateien,
die Apothem unter `<project>/.kimi-code/.apothem/support/` abgelegt hat. Vor der
Änderung wird von jeder Datei eine mit Zeitstempel versehene Kopie unter
`~/.apothem/backups/` gespeichert; im Projekt bleibt keine Sicherungsdatei
zurück. Die YAML-Datei des gemeinsamen Profils und die Apothem-Engine bleiben
unberührt.

python -m apothem.conformity.gate --all .

## Fehlerbehebung

| Symptom | Behebung |
|---------|-----|
| Konfigurationsdatei nicht gefunden | Führen Sie `apothem install --harness kimi-code --project /path/to/project` erneut aus |
| Verifizierung fehlgeschlagen | Führen Sie `apothem update --harness kimi-code --project /path/to/project` aus und verifizieren Sie dann erneut |
| Unerwarteter Konfigurationsinhalt | Prüfen Sie `~/.config/apothem/profile.yaml` oder `--profile PATH` und führen Sie dann `apothem update --harness kimi-code --project /path/to/project` erneut aus |

## Konfigurationsschalter

| Flag | Standard | Beschreibung |
|------|---------|-------------|
| `--dry-run` | `false` | Vorschau der Installation, ohne Dateien zu schreiben. |
