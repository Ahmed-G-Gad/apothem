**Anbieter:** Hermes
**Installationsname:** `hermes`
**Status:** Vorschau
**Native Konfiguration:** `~/.hermes/config.yaml`

## Installation

```bash
apothem install --harness hermes
```

Der Adapter übersetzt das gemeinsame Profil in die benutzerweite globale
Konfigurationsdatei von Hermes Agent und installiert die
Apothem-Unterstützungskohorten unter dem Harness-Wurzelverzeichnis.

**Geschriebene Dateien:** `~/.hermes/config.yaml`, das Profildokument
`~/.hermes/apothem/rules/00-apothem-profile.md` und Unterstützungsdateien unter
`~/.hermes/.apothem/support/`

Das Profildokument endet mit einem Abschnitt zu den
Apothem-Unterstützungsdateien, der das absolute Verzeichnis unter
`~/.hermes/.apothem/support/` nennt, gegen das jeder Verweis im
Repository-Stil (`rules/<name>.md`, `templates/...`, `hooks/...`) aufgelöst
wird.

## Zuordnung von Profil zu nativer Konfiguration

Der Adapter liest das gemeinsame Profil von Apothem und rendert die native
YAML-Konfiguration einschließlich des MCP-Inventars des Profils. Die MCP-Server
stammen aus dem Abschnitt `mcp_servers` des Profils. Sie werden bei jeder
Installation und jedem Update in `config.yaml` gerendert, nicht als Dateien
kopiert. Identität, Präferenzen und Regeln des Profils gehen in das Profildokument.
Gemeinsame Commands, Skills, Helfer-Definitionen, Regeln, Templates und
Hook-Prompts landen als Unterstützungsmaterial unter `~/.hermes/.apothem/support/`.

## Kompatibilitätshinweise

Vorschau-Adapter. Hermes lädt weder den Unterstützungs-Teilbaum noch das
Profildokument von selbst: Nichts in `config.yaml` und keine der
Kontextdateien, die Hermes liest, verweist dorthin, daher läuft Hermes nach der
Installation ohne die Regeln, Skills oder Hooks von Apothem. Hermes liest
Skills aus `~/.hermes/skills/` und aus jedem Ordner, der in `config.yaml` unter
`skills.external_dirs` aufgeführt ist; um die Apothem-Skills zu verwenden,
fügen Sie `~/.hermes/.apothem/support/skills` selbst zu dieser Liste hinzu;
`apothem update` behält Schlüssel bei, die Sie zu `config.yaml` hinzufügen. Der
Adapter schreibt das MCP-Inventar des Profils unter den Top-Level-Schlüssel
`mcp_servers`, wo Hermes MCP-Server liest.
Frühere Apothem-Releases schrieben es unter `auxiliary.mcp`, das Hermes als
Hilfsmodell für den Dispatch von MCP-Werkzeugen liest; sowohl `apothem update`
als auch `apothem uninstall` entfernen diesen Block, wenn er noch dem
entspricht, was ein solches Release aus Ihrem aktuellen gemeinsamen Profil
schreiben würde (siehe [Deinstallation](#deinstallation), wann er stehen
bleibt). (Verhalten von Hermes gemäß den Seiten seines Benutzerhandbuchs zu
[Skills](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/skills.md)
und [MCP](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/mcp.md),
gelesen am 2026-10-02.)

## Verifizierung

```bash
apothem verify --harness hermes
```

Der Befehl verify bestätigt Folgendes:

1. Die native Konfiguration existiert am erwarteten Pfad.
2. Jedes verwaltete Ziel existiert; verwaltete Dateien sind nicht leer, und
   JSON- oder YAML-Konfigurationen lassen sich parsen. Fügen Sie `--profile PATH`
   hinzu, um außerdem zu bestätigen, dass die installierten Dateien zu diesem
   Profil passen.
3. Die adapterspezifische Verifizierungsroutine meldet Erfolg.

## Aktualisierung

```bash
apothem update --harness hermes
```

Leitet die native Konfiguration aus dem aktuellen Zustand des gemeinsamen
Profils neu ab.
Führen Sie den Befehl aus, nachdem Sie `~/.config/apothem/profile.yaml`
bearbeitet oder das installierte Apothem-Paket aktualisiert haben.

## Deinstallation

```bash
apothem uninstall --harness hermes
```

Entfernt, was der Adapter hinzugefügt hat: die `mcp_servers`-Einträge, die
seine Installation in `config.yaml` festgehalten hat (Ihre eigenen Schlüssel
bleiben erhalten, und die Datei wird nur gelöscht, wenn Apothem sie erstellt
hat und nichts von Ihnen übrig ist), das Profildokument und den
Unterstützungs-Teilbaum. Die YAML-Datei des gemeinsamen Profils und die
Apothem-Engine bleiben unberührt.

Bei einer Installation durch ein früheres Release, das die Server des Profils
unter `auxiliary.mcp` schrieb, wird dieser Block ebenfalls entfernt, wenn er
noch dem entspricht, was dieses Release aus Ihrem aktuellen gemeinsamen Profil
unter `~/.config/apothem/profile.yaml` schreiben würde. Dies ist dieselbe
Regel, die `apothem update` anwendet, sodass eine Deinstallation ohne
vorheriges Update keinen veralteten Block hinterlässt, solange die MCP-Server
des Profils unverändert sind. Ein Block, den Sie bearbeitet haben, einer, der
nicht mehr zu den MCP-Servern Ihres aktuellen Profils passt, oder einer, für
den kein lesbares gemeinsames Profil zum Vergleich vorliegt, bleibt an Ort und
Stelle, und der Rest Ihrer `auxiliary`-Einstellungen bleibt immer erhalten.

## Fehlerbehebung

| Symptom | Behebung |
|---------|-----|
| Konfigurationsdatei nicht gefunden | Führen Sie `apothem install --harness hermes` erneut aus |
| Verifizierung fehlgeschlagen | Führen Sie `apothem update --harness hermes` aus und verifizieren Sie dann erneut |
| Unerwarteter Konfigurationsinhalt | Prüfen Sie `~/.config/apothem/profile.yaml` oder `--profile PATH` und führen Sie dann `apothem update --harness hermes` erneut aus |

## Konfigurationsschalter

| Flag | Standard | Beschreibung |
|------|---------|-------------|
| `--dry-run` | `false` | Vorschau der Installation, ohne Dateien zu schreiben. |
