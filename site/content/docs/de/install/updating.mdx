## Das Claude Code-Plugin aktualisieren

Aktualisieren Sie den Marketplace-Eintrag und aktualisieren Sie anschließend das Plugin über das `/plugin`-
Menü innerhalb von Claude Code:

```text title="Inside Claude Code"
/plugin marketplace update apothem
```

Öffnen Sie `/plugin`, wählen Sie **apothem** aus und wählen Sie die Aktualisierungsaktion, wenn eine neuere
Plugin-Version aufgeführt ist.

## npx führt immer das aktuelle Release aus

`npx @ahmed-g-gad/apothem` löst bei jeder Ausführung das aktuell veröffentlichte Paket
auf, sodass es nichts zu aktualisieren gibt. Wenn ein veralteter npx-Cache eine ältere
Kopie ausliefert, fixieren Sie den dist-Tag explizit:

```bash
npx @ahmed-g-gad/apothem@latest --version
```

## Eine installerbasierte Einrichtung aktualisieren

Führen Sie den Installer erneut aus — er ist idempotent und checkt in einem vorhandenen Baum das Release-Tag aus —
oder führen Sie das dedizierte Update-Skript aus:

```bash title="macOS · Linux · WSL2 · BSD"
bash scripts/installer/update.sh
```

```powershell title="Windows · PowerShell"
pwsh -NoProfile -File scripts/installer/update.ps1
```

Das Update-Skript checkt den Quellbaum unter `APOTHEM_HOME` (Standard `~/.apothem`) erneut auf `APOTHEM_REF` aus. Ist `APOTHEM_REF` ungesetzt, wird das neueste signierte Release-Tag `vMAJOR.MINOR.PATCH` aufgelöst; ein Tag-Wert fixiert `APOTHEM_REF`, und `main` wählt den beweglichen Branch nur dann, wenn zusätzlich `APOTHEM_ALLOW_UNVERIFIED=1` gesetzt ist. Ohne diese Überschreibung checkt das Update die Ref aus und bricht dann ab, bevor es erneut materialisiert, weil ein Branch kein signiertes Release-Tag ist. Vor dem erneuten Materialisieren prüft es die Signatur des Tags mit `git verify-tag`; ein unsigniertes oder manipuliertes Tag bricht den Vorgang ab, sofern nicht `APOTHEM_ALLOW_UNVERIFIED=1` den Abbruch zu einer Warnung herabstuft. Ein signiertes Tag, dessen öffentlicher Schlüssel des Maintainers im lokalen Schlüsselbund fehlt, bricht mit einer Anleitung zum Schlüsselimport ab, die auf den Fingerprint verweist, der in [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md) veröffentlicht ist. Danach materialisiert es den durch `APOTHEM_HARNESS` benannten Harness neu, indem es `apothem update` aus dem aktualisierten Baum ausführt (Standardwerte für den Harness gemäß der Tabelle [Installer-Umgebungsvariablen](/docs/how-to/installer-environment-variables)). Es setzt eine vorherige Installation voraus: Existiert unter `APOTHEM_HOME` kein Baum und ist `APOTHEM_SOURCE` nicht gesetzt, beendet es sich mit einer Meldung, die Sie zunächst auf den Installer verweist.

## Harness-Ausgabe neu materialisieren

Nach dem Aktualisieren der Engine oder dem Bearbeiten von `~/.config/apothem/profile.yaml`
leiten Sie die installierte Harness-Konfiguration neu ab. Adapter mit Benutzerbereich benötigen kein
`--project`; Adapter mit Projektbereich schon.

```bash
apothem update --harness claude-code
apothem update --harness cursor --project /path/to/project
apothem update --harness all --project /path/to/project
```

Führen Sie denselben Befehl mit `--dry-run --json` aus, wenn Sie eine maschinenlesbare
Vorschau ohne Dateisystem-Schreibvorgänge benötigen.

## Aktuelle Befehlsgrenze

`apothem update` aktualisiert nur die Harness-Ausgabe. Die CLI implementiert
`update --self`, `update --check` oder `update --apply` nicht; aktualisieren Sie die Engine
selbst über den Kanal, mit dem Sie sie installiert haben — den `/plugin`-Ablauf, eine frische
`npx`-Ausführung oder die oben genannten Installer-/Update-Skripte.
