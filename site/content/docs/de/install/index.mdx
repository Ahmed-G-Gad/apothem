Apothem ist in unter zwei Minuten installiert und arbeitet neben Ihrer
bestehenden Harness-Konfiguration. Jeder Weg führt dieselbe eigenständige
Engine aus — der Quellbaum trägt seine vendorten Abhängigkeiten mit und läuft
aus einem Checkout unter System-Python 3.10 oder neuer (siehe
[die eigenständige Laufzeit](/docs/architecture/self-contained-runtime)).

**Zwei Voraussetzungen gelten für jeden Weg:** System-**Python 3.10 oder neuer**
im `PATH`, unter dem die Pakete `click` und `rich` importierbar sind. Der npm-Shim
(Kanal 2), die Erweiterung für die VS Code-Familie (Kanal 4) und die
Kommandozeilen-Bootstraps (Kanäle 5–7) benötigen zusätzlich **Node.js 18 oder
neuer**, um `npx` auszuführen. Python 3.10 sowie Node.js 18 und 20 haben ihr
Upstream-Lebensende überschritten; sie bleiben unterstützt und getestet, neuere
Versionen werden jedoch bevorzugt (siehe
[Voraussetzungen auf einen Blick](#voraussetzungen-auf-einen-blick)). Der
eigene Abschnitt jedes Kanals unten wiederholt seine exakten Voraussetzungen,
einen kopierbereiten Befehl und einen Verifizierungsschritt.

## Einen Kanal wählen

Acht Installationskanäle stehen zur Verfügung. Wählen Sie danach, wie Sie
bereits arbeiten.

| # | Kanal | Liefert | Voraussetzungen |
|---|---------|----------|---------------|
| 1 | [Claude Code-Plugin](#1-claude-code-plugin) | Vollständiger Harness in Claude Code | Claude Code · Python 3.10+ |
| 2 | [npm-Shim (`npx`)](#2-npm-shim-npx) | Vollständiger Harness, jedes Werkzeug | Node 18+ · Python 3.10+ |
| 3 | [Ein-Schritt-Installer](#3-ein-schritt-installer) | Vollständiger Harness + ein `apothem`-Befehl | Python 3.10+ (`git` für eine Netzwerkinstallation) |
| 4 | [Erweiterung für die VS Code-Familie](#4-erweiterung-für-die-vs-code-familie) | Vollständiger Harness aus dem Editor | VS Code · Node 18+ · Python 3.10+ |
| 5 | [Kommandozeilen-Bootstrap (Erweiterungs-Host)](#5-kommandozeilen-bootstrap-erweiterungs-host) | Bootstrap, der die Engine ausführt | Das zugehörige Host-Werkzeug · Node 18+ · Python 3.10+ |
| 6 | [Kommandozeilen-Bootstrap (`qwen-code`-Host)](#6-kommandozeilen-bootstrap-qwen-code-host) | Bootstrap, der die Engine ausführt | Das zugehörige Host-Werkzeug · Node 18+ · Python 3.10+ |
| 7 | [Kommandozeilen-Bootstrap (Plugin-Host)](#7-kommandozeilen-bootstrap-plugin-host) | Bootstrap, der die Engine ausführt | Das zugehörige Host-Werkzeug · Node 18+ · Python 3.10+ |
| 8 | [Direkte Engine (`python -m apothem`)](#8-direkte-engine-python--m-apothem) | Vollständiger Harness aus einem Checkout | Python 3.10+ (`click`, `rich`) |

<Callout title="Welche Kanäle den vollständigen Harness liefern">
  Der npm-Shim (2), die Ein-Schritt-Installer (3) und die direkte Engine (8)
  materialisieren für sich allein die gesamte synchronisierte Einheit für jeden
  Harness. Die drei Kommandozeilen-Erweiterungen (5–7) installieren einen
  kleinen **Bootstrap**, der die Engine per Shell aufruft
  (`npx @ahmed-g-gad/apothem install`), um den vollständigen Harness zu
  materialisieren — sie sind der Einstiegspunkt, nicht für sich allein die
  vollständige Lieferung. Das Claude Code-Plugin (1) trägt die Engine mit und
  führt sie direkt aus. Die Erweiterung für die VS Code-Familie (4) trägt keine
  eigene Engine mit: Ihre Befehle führen die Engine standardmäßig über den
  npm-Shim aus.
</Callout>

Jeder Weg ist idempotent: Ein erneuter Aufruf ist sicher und konvergiert zum
selben Zustand.

## 1. Claude Code-Plugin

**Voraussetzungen:** Claude Code und System-Python 3.10+ im `PATH`.

Der Plugin-Weg läuft vollständig innerhalb von Claude Code. Er bündelt die
Apothem-Engine mit ihren Slash-Befehlen, delegierten Workern, Skills, Regeln
und Hooks, alle aus dem eigenständigen Plugin-Baum ausführbar:

```text title="Inside Claude Code"
/plugin marketplace add ahmed-g-gad/apothem
/plugin install apothem@apothem
```

Nach der Installation stehen der Apothem-Befehlssatz, die mitgelieferten
delegierten Worker, die Skills und die vier
[Ausgabestile](/docs/reference/output-styles) (wählen Sie einen mit
`/output-style` oder über `/config`) in jeder Claude Code-Sitzung zur
Verfügung. Das Plugin liefert jeden Befehl als Skill aus, eine `SKILL.md`,
deren bei Bedarf geladene Details in einem `references/`-Ordner daneben liegen;
daher ruft Claude Code ihn mit dem Präfix des Plugins auf: `/apothem:plan-spec`,
`/apothem:security-audit` und die übrigen. Zwei Namen belegt Claude Code
selbst: `/plan` wechselt in den Plan-Modus, und `/code-review` führt das
mitgelieferte Review aus; geben Sie daher `/apothem:plan` und
`/apothem:code-review` für die Apothem-Befehle ein. Wenn statt des Plugins die
Apothem-Engine die Installation in Claude Code vornimmt, werden dieselben
Skills ohne Präfix nach `~/.claude/skills/` geschrieben, und ein persönlicher
`code-review`-Skill ersetzt das mitgelieferte `/code-review` (sein Alias
`/review` führt weiterhin das mitgelieferte aus). Zwei Namen, `projectify` und
`workflow`, sind außerdem native Skills; das Plugin und die Engine-Installation
liefern den nativen Skill aus, nicht einen aus dem Befehl abgeleiteten Skill.
Siehe [Claude Code](/docs/harnesses/claude-code#command-skills-and-reference-files)
dazu, wie die Befehle aufgeteilt sind, und [Slash-Befehle](/docs/reference/commands) für
den vollständigen Befehlskatalog.

**Verifizieren:** Führen Sie `/plugin` innerhalb von Claude Code aus und
bestätigen Sie, dass **apothem** als installiert aufgeführt ist, oder prüfen
Sie den Drift-Bericht in einem Terminal:

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 2. npm-Shim (`npx`)

**Voraussetzungen:** Node.js 18+ (für `npx`) und System-Python 3.10+ im `PATH`.
Der Shim ermittelt den Interpreter und leitet jeden CLI-Befehl an die
mitgelieferte Engine weiter — nichts wird dauerhaft auf Ihrem System abgelegt.
Er versucht `python3`, `python` und dann `py -3`, in dieser Reihenfolge; setzen
Sie **`APOTHEM_PYTHON`** auf einen Interpreterpfad, damit dieser zuerst
versucht wird. Das benötigen Sie, wenn Python installiert ist, aber nicht im
`PATH` liegt, oder wenn mehrere Versionen installiert sind und Sie eine
bestimmte verwenden wollen. Der von Ihnen benannte Interpreter muss die Prüfung
auf Python 3.10+ dennoch bestehen; besteht er sie nicht, greift der Shim auf
`python3`, `python` und dann `py -3` zurück.

```bash title="npx"
npx @ahmed-g-gad/apothem install --harness claude-code
```

Auf einem Rechner ohne Profil erstellt dieses erste `install` das Startprofil
unter `~/.config/apothem/profile.yaml` und meldet dies. Seine Identitätsfelder
sind Platzhalter: Personalisieren Sie sie
(`npx @ahmed-g-gad/apothem profile edit`) und führen Sie den Befehl dann mit
`update` anstelle von `install` erneut aus, um sie anzuwenden.

Er läuft auch direkt aus dem Repository:

```bash title="npx from the repository"
npx github:ahmed-g-gad/apothem install --harness claude-code
```

Jeder Befehl in der [CLI-Referenz](/docs/cli-reference) funktioniert in dieser
Form; setzen Sie `npx @ahmed-g-gad/apothem` anstelle von `apothem` ein. Dies ist
auch der Installationsweg für OpenCode und jedes andere Werkzeug, das keine
separate Plugin- oder Erweiterungs-Registry bereitstellt — Apothem
synchronisiert diese direkt in ihr natives Konfigurationsverzeichnis
(`npx @ahmed-g-gad/apothem install --harness opencode`).

**Verifizieren:**

```bash title="Verify"
npx @ahmed-g-gad/apothem --version
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 3. Ein-Schritt-Installer

**Voraussetzungen:** System-Python 3.10+ im `PATH` (der Installer bietet an, die
Voraussetzungen `click` / `rich` für Sie hinzuzufügen). Für eine
Netzwerkinstallation: `git`, um das neueste Release zu finden, und `gpg`, um das
signierte Release-Tag zu prüfen (Git for Windows liefert beide mit).
[cosign](https://docs.sigstore.dev/cosign/system_config/installation/) ist
optional: Damit prüft der Installer zusätzlich das signierte Release-Archiv.

Die Installationsskripte ermitteln das neueste Release, prüfen es (siehe
[Vertrauensmodell](#vertrauensmodell)), legen den Apothem-Quellbaum unter
`~/.apothem` ab, erstellen ein Startprofil, wenn keines existiert, materialisieren
Ihren ersten Harness und verifizieren das Ergebnis, alles in einem Durchlauf. Das
Startprofil enthält Platzhalter-Identitätsfelder: Bearbeiten Sie es und führen Sie
dann `apothem update --harness <name>` aus, um Ihre eigenen anzuwenden. Ein
erneuter Aufruf ist idempotent: Ein Git-Klon wird per Fetch aktualisiert, sein
neues Tag wird geprüft, und erst dann wird der Klon auf das ermittelte Tag
ausgecheckt; eine Installation aus einem Release-Archiv wird an Ort und Stelle
aktualisiert; und der Harness wird neu materialisiert. Endet die Engine als
teilweise (Exit-Code `2`), gibt der Installer eine Warnzeile aus, verifiziert
trotzdem, legt den `apothem`-Befehl ab, gibt sein Banner aus und endet dann mit
Exit-Code `2`. Die Engine endet als teilweise, wenn sie eine Datei wegen ihrer
Apothem-Markierungszeilen unverändert lässt oder wenn sie anhält, nachdem sie
bereits etwas geschrieben hat (siehe
[Wenn die Engine eine Datei unverändert lässt](/docs/install/updating#when-the-engine-leaves-a-file-as-it-is)).
Die verifizierte Installation ist der Standardweg und der empfohlene Weg.

Importieren Sie den Maintainer-Signaturschlüssel vorab einmalig. Jede Netzwerkinstallation prüft das Release-Tag dagegen, mit oder ohne cosign, und bricht ab, wenn der Schlüssel nicht in Ihrem Schlüsselbund liegt. Prüfen Sie, dass der Fingerabdruck `5C89 98F9 F241 7204 45D3  F28B 7039 6FED 9C63 4163` lautet, also der Wert, den [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md#maintainer-signing-key) veröffentlicht. Unter Windows liest `git verify-tag` den Schlüsselbund des `gpg`, der mit Git for Windows ausgeliefert wird; daher läuft der Import über Gits eigene `bash`:

```bash title="macOS · Linux · WSL2 · BSD — import the key once"
curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import
gpg --fingerprint 70396FED9C634163
```

```powershell title="Windows · PowerShell — import the key once"
& "$env:ProgramFiles\Git\bin\bash.exe" -c 'curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import && gpg --fingerprint 70396FED9C634163'
```

```bash title="macOS · Linux · WSL2 · BSD — latest signed tag, verified"
curl -fsSL https://apothem.ahmedgad.com/install.sh | bash
```

```powershell title="Windows · PowerShell — latest signed tag, verified"
irm https://apothem.ahmedgad.com/install.ps1 | iex
```

Dieselben Skripte liegen in einem Checkout unter `scripts/installer/` —
`install`, `uninstall` und `update` in den Formen `.sh`, `.ps1` und `.bat` —,
sodass Sie sie nach dem Klonen direkt ausführen können:

```bash title="From a checkout"
APOTHEM_HARNESS=claude-code sh scripts/installer/install.sh                                 # POSIX
$env:APOTHEM_HARNESS = 'claude-code'; pwsh -NoProfile -File scripts/installer/install.ps1   # Windows
```

Ein per Pipe ausgeführter Einzeiler verwendet nie einen lokalen Baum: `curl ... | sh` und `irm ... | iex`
ignorieren den Ordner, aus dem Sie sie ausführen, und dessen übergeordnete Ordner
und rufen das Release ab und verifizieren es. Der Installer verwendet einen lokalen
Baum nur, wenn Sie das eigene `scripts/installer/install.sh` (oder `install.ps1`)
des Checkouts über seinen Pfad ausführen, aus einem beliebigen Ordner (zum Beispiel
`sh ~/src/apothem/scripts/installer/install.sh`), oder wenn `APOTHEM_SOURCE` diesen
Baum benennt. Die Installer, Updater und Uninstaller, die `apothem`-Shims, der
npm-Launcher, die Hooks und die Validator-Prozesse des Konformitäts-Gates halten
den aktuellen Ordner aus dem Modul-Suchpfad von Python heraus. Ein
`python -m apothem`-Befehl, den Sie selbst eingeben, tut das nicht: `-m` liest
Module zuerst aus dem aktuellen Ordner.

Leere und relative Einträge in Ihrem eigenen `PYTHONPATH` gibt kein Launcher an die
Engine weiter (die Installer, Updater, Uninstaller, die POSIX- und
Windows-`apothem`-Shims und der npm-Launcher). Ein beibehaltener Eintrag muss ein
vollständiger Pfad sein: unter Windows ein Laufwerkspfad wie `C:\lib` oder ein
Netzwerkpfad, anderswo ein Pfad, der mit `/` beginnt. Ein wurzelbezogenes `\lib`
oder ein laufwerksrelatives `C:lib` wird verworfen. Die sh-Skripte fragen das
Python, das sie ausführen, welche Form es liest, und der `apothem`-Shim, den sie
schreiben, behält diese Form bei. Ein Windows-Python (das übliche unter Git Bash)
erhält die Engine-Pfade in Windows-Form, mit `;` verbunden, und behält nur die
Laufwerks- und Netzwerkpfade Ihres `PYTHONPATH`. Ein POSIX-Python, einschließlich
des eigenen `python3` von Cygwin und MSYS2, erhält POSIX-Pfade, mit `:` verbunden,
und behält nur Einträge, die mit `/` beginnen. Die `git`-Befehle der Installer, die
nicht auf einem Klon arbeiten, lesen kein Repository im aktuellen Ordner.

### Installer-Optionen

`install.sh` nimmt die folgenden Optionen an, `install.ps1` dieselben Schalter als
PowerShell-Parameter. `install.bat` akzeptiert die `install.sh`-Schreibweise der
ersten drei Zeilen und gibt jede an `install.ps1` weiter. Ein über eine Pipe
ausgeführter Einzeiler kann keinen PowerShell-Parameter übergeben; laden Sie
`install.ps1` daher zuerst herunter, um einen zu verwenden:

```bash title="Pass a flag"
curl -fsSL https://apothem.ahmedgad.com/install.sh | sh -s -- --dry-run    # POSIX
irm https://apothem.ahmedgad.com/install.ps1 -OutFile install.ps1; pwsh -NoProfile -File install.ps1 -DryRun   # Windows
```

| `install.sh` | `install.ps1` | Wirkung |
|---|---|---|
| `--clean`, `--fresh` | `-Clean`, `-Fresh` | Vor der Installation werden die vier Ordner in Ihrem Home-Verzeichnis, die [`apothem install`](/docs/cli-reference/install#blast-radius-preview) aufführt, darunter `~/.claude` und `~/.agents`, gesichert und entfernt, gleich welchen Harness Sie installieren; dann wird frisch installiert. Der Installer gibt die Option als `apothem install --clean` an die Engine weiter, die vor jeder Entfernung fragt, die Sicherung unter `~/.apothem/backups` ablegt und Ihr Profil zurückschreibt. |
| `--dry-run` | `-DryRun` | Holt und prüft das Release in einem temporären Ordner und zeigt, was die Installation ändern würde, ohne etwas zu ändern (siehe [Vertrauensmodell](#vertrauensmodell)). |
| `--yes` | `-Yes` | Fragt nicht vor jeder Entfernung durch `--clean`. Erlaubt außerdem die Ersetzungen dessen, was unter `APOTHEM_HOME` liegt, für die das [Vertrauensmodell](#vertrauensmodell) `--yes` verlangt. |
| `-h`, `--help` | keine | Gibt die Optionen und das Vertrauensmodell aus und beendet sich. |

### Vertrauensmodell

Ist `APOTHEM_REF` nicht gesetzt, ermittelt der Installer das höchste
`vMAJOR.MINOR.PATCH`-Release und installiert *dieses* — niemals den beweglichen
`main`-Branch. Er prüft das Release, bevor irgendeine Konfiguration materialisiert
wird, und die Prüfung hängt davon ab, ob `cosign` in Ihrem `PATH` liegt:

- **Mit cosign** müssen zwei Prüfungen beide bestehen. Zuerst muss das Release-Tag
  eine gültige Signatur des Maintainer-Schlüssels tragen, geprüft wie im nächsten
  Punkt, und das signierte Tag muss dasjenige sein, das für dieses Release benannt
  ist: Ein signiertes Tag eines anderen Releases, das auf diesen Namen umgehängt
  wurde, wird abgelehnt. Dann lädt der Installer das Plattform-Archiv des Releases,
  seine Datei `SHA256SUMS` und `SHA256SUMS.cosign.bundle` herunter. cosign muss
  bestätigen, dass der Release-Workflow von Apothem `SHA256SUMS` für genau dieses
  Tag signiert hat und – über seine Prüfung
  `--certificate-github-workflow-sha` – dass das verifizierte Zertifikat für einen
  Lauf auf dem Commit ausgestellt wurde, auf den das signierte Tag zeigt. Der
  Installer liest das Zertifikat nicht selbst. Danach muss der SHA-256 des Archivs
  mit dem aufgeführten Digest übereinstimmen. Der Workflow läuft für jedes Tag, das
  gepusht wird, daher genügt seine Signatur allein nicht; die Tag-Signatur zeigt,
  dass der Maintainer diesen Commit veröffentlicht hat.
- **Ohne cosign**, oder wenn `APOTHEM_HOME` bereits einen Git-Klon enthält, klont
  oder aktualisiert der Installer das Repository und prüft allein das Tag mit
  `git verify-tag`. Die Signatur muss gültig *und* mit dem in [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md) veröffentlichten Maintainer-Schlüssel erstellt sein, und das signierte Tag muss dasjenige
  sein, das für das Release benannt ist. Ein mit einem anderen Schlüssel
  signiertes Tag wird abgelehnt, selbst wenn Ihr Schlüsselbund diesem Schlüssel
  vertraut. Ein signiertes Git-Tag benennt seinen Commit über eine SHA-1-ID; mit
  cosign prüft der Installer zusätzlich den SHA-256 des Archivs. Ein vorhandener
  Klon wird per Fetch aktualisiert, und sein neues Tag wird geprüft, *bevor* der
  Klon ausgecheckt wird. Eine fehlgeschlagene Prüfung lässt den Klon unverändert,
  und ein Klon mit Änderungen an nachverfolgten Dateien stoppt das Update mit der
  Meldung, sie zu committen oder zu stashen, statt sie zu verlieren. Mit einer Ref,
  die kein Release ist, etwa `main`, folgt ein vorhandener Klon der Kopie dieses
  Branches auf origin.

Der Installer ignoriert die Git-Umgebungsvariablen, die Git umleiten
(`GIT_DIR`, `GIT_WORK_TREE` und ähnliche), sowie diejenigen, die Git auf eine
andere Konfigurationsdatei richten (`GIT_CONFIG`, `GIT_CONFIG_GLOBAL` und
`GIT_CONFIG_SYSTEM`) oder Attribute aus einem anderen Baum lesen lassen
(`GIT_ATTR_SOURCE`; ein `attr.tree` in Ihrer eigenen Konfiguration wird bei jedem
Git-Befehl auf einem Klon geleert), und hält an, wenn `APOTHEM_REPO` mit `-`
beginnt. `GIT_CONFIG_NOSYSTEM` bleibt so, wie Sie es gesetzt haben; es verhindert
nur, dass Git die Systemkonfiguration liest. Git liest weiterhin Ihre eigene
globale Konfiguration und, sofern Sie nicht `GIT_CONFIG_NOSYSTEM` setzen, die
Systemkonfiguration an den Orten, an denen es immer sucht, und `git`, `gpg` und
`cosign` sind die Programme, die Ihr `PATH` findet: Der Installer vertraut ihnen
so, wie sie gefunden werden. Für den gesamten Lauf setzt der Installer
`GIT_NO_REPLACE_OBJECTS=1`, damit Git nie ein Objekt über Replace-Refs austauscht,
`GIT_NO_LAZY_FETCH=1`, damit Git nie von sich aus ein fehlendes Objekt vom Remote
abruft, `GIT_ALLOW_PROTOCOL` auf die Transportwege file, git, http, https und ssh,
damit ein Wert in Ihrer Umgebung diese Liste nicht erweitern kann, und
`GIT_ATTR_NOSYSTEM=1`; da `core.attributesFile` bei jedem Git-Befehl auf einem Klon
geleert wird, liest Git dann keine Attributdatei außerhalb des Klons, sodass ein in
Ihrer Datei definiertes Makro dort keinen Filter benennen kann. Das
PowerShell-Skript stellt alle vier am Ende des Laufs wieder her. Der Installer liest
das Release-Tag einmal, hält den Commit fest, den es benennt, verifiziert das Tag,
checkt diesen Commit über seine ID aus und verlangt, dass `HEAD` dieser Commit ist,
sodass ein nach der Prüfung verschobenes Tag nichts ändert. Unter Windows
PowerShell 5.1 und 7 wird ein Download abgelehnt, der auf eine Adresse umleitet,
die nicht https ist, so wie es `curl` in den POSIX-Installern tut.

`APOTHEM_HOME` muss ein Ordner sein, in den nur Sie schreiben können, denn wer
hineinschreiben kann, kann den Code ändern, den der `apothem`-Befehl ausführt.
Unter Windows kann ein im Stammverzeichnis eines Laufwerks angelegter Ordner wie
`C:\apothem` unter den Standardberechtigungen von Windows von jedem Benutzer
geändert werden, der sich am Computer anmeldet. Der Standard, `~/.apothem`, liegt
in Ihrem eigenen Benutzerordner. Jede abgerufene Installation, jedes Update und
jeder Probelauf warnt, ohne anzuhalten, wenn das nicht so ist oder wenn der Ordner
oder der Ordner, der ihn enthält, jemand anderem gehört, und nennt den Ordner, wer
hineinschreiben kann oder ihn besitzt, und die Abhilfe; eine Installation aus einem
lokalen Checkout und ein Update mit gesetztem `APOTHEM_SOURCE` überspringen die
Prüfung. Unter Windows kommt die Warnung von
`install.ps1` und `update.ps1`: `install.sh` und `update.sh` prüfen unter Git
Bash, MSYS2 oder Cygwin nicht (siehe
[Fehlerbehebung](/docs/install/troubleshooting#the-installer-warns-other-users-can-change-apothem_home)).

Eine fehlgeschlagene Prüfung bricht die Installation ab, bevor irgendeine
Konfiguration geschrieben wird und bevor der Installer `APOTHEM_HOME` ersetzt. Ein
signiertes Tag, dessen öffentlicher Maintainer-Schlüssel noch nicht im lokalen
Schlüsselbund liegt, bricht stattdessen mit einer Anleitung zum Schlüsselimport ab:
Importieren Sie den Schlüssel wie oben gezeigt, prüfen Sie seinen Fingerabdruck
gegen den in [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md) veröffentlichten Wert und führen Sie den Vorgang erneut aus.

Ein erneuter Lauf mit cosign aktualisiert eine frühere Installation aus einem
Release-Archiv. Die neue Quelle wird zuerst in einem Ordner neben `~/.apothem`
geprüft und entpackt und dann eingewechselt. Alles in `~/.apothem`, das nicht zum
Quellbaum gehört, wird in die neue Installation übernommen: die Rollback-Backups
der Engine (`backups/`), die Installations-Ledger (`state/`), Pläne, Gedächtnis und
ihre übrigen Daten. Schlägt ein Schritt fehl oder stoppen Sie den Lauf mit Ctrl+C
oder einem Beendigungssignal, wird die frühere Installation unverändert
wiederhergestellt; schlägt selbst das fehl, nennt die Meldung, wo die früheren
Dateien liegen. Ein erzwungenes Beenden oder ein Stromausfall während des Wechsels
lässt sich nicht abfangen: Es kann Ordner neben `~/.apothem` zurücklassen, und die
nächste abgerufene Installation meldet sie (siehe unten). Diese Regeln gelten, wenn
der Installer `~/.apothem` ersetzt:

- Ein Git-Klon wird ohne `--yes` nicht durch ein Release-Archiv ersetzt. Die
  Dateien, die der Klon nicht nachverfolgt, werden in die neue Installation
  verschoben, und der eigene Baum des Klons (seine Historie und sein Quellcode)
  wird in einen neuen Ordner,
  `~/.apothem.before-apothem-<time>`, unter seinem eigenen Namen (`.apothem`)
  verschoben; der Installer sagt, wohin, und Sie löschen ihn, sobald Sie ihn nicht
  mehr brauchen. Selbst mit `--yes` lehnt der Installer ab, solange der Klon lokale
  Arbeit enthält, die er verlieren würde: Änderungen, Stashes, nicht gepushte
  Commits oder nicht nachverfolgte Dateien in seinem Quellbaum. Committen und
  pushen Sie diese Arbeit oder verschieben Sie sie an einen anderen Ort und führen
  Sie den Vorgang dann erneut aus. Diese Prüfung läuft auch mit `--dry-run`. Eine
  `.git`-Datei (ein verknüpfter Worktree) zählt als Klon, ebenso ein
  `.git`-Ordner.
- Ein Git-Klon von etwas anderem als Apothem wird wie jeder Ordner behandelt, der
  keine Apothem-Installation enthält (siehe unten), und nie als Klon aktualisiert
  oder ersetzt.
- Ein vorhandener Klon wird nur dann an Ort und Stelle aktualisiert, wenn Git jede
  Änderung darin sehen kann und nichts in seiner eigenen Einrichtung während des
  Updates Code ausführt. Vor dem Fetch hält der Installer an, wenn Dateien als
  assume-unchanged oder skip-worktree markiert sind, wenn Git in `APOTHEM_HOME`
  keinen Arbeitsbaum findet (etwa wenn die Konfiguration des Klons `core.bare` auf
  `true` setzt), wenn der Klon ein Submodul enthält (in seinem Index
  festgehalten oder in `.git/modules` abgelegt), wenn `.git/info/attributes` einen
  Filter- oder Diff-Treiber benennt (`filter=` oder `diff=`), wenn diese Datei oder
  eine Konfigurationsdatei keine einfache Datei ist, oder wenn der Klon Objekte aus
  einem anderen Repository entleiht (`objects/info/alternates`). Er hält außerdem
  bei jeder Einstellung in der eigenen `.git/config` oder `.git/config.worktree` des
  Klons an, die nicht zu denen gehört, die `git clone` und `git init` dort für einen
  vollständigen Klon schreiben, Branch-Einstellungen (`remote` und `pushremote`
  eines Branches müssen `origin` sein), `user.name`, `user.email`,
  `maintenance.auto`, `maintenance.strategy`, `pull.rebase` und `pull.ff`, sodass
  auch ein mit `--filter` erstellter partieller Klon anhält;
  [Fehlerbehebung](/docs/install/troubleshooting#the-installer-stops-the-existing-clone-is-set-up-in-a-way-the-update-would-trust)
  führt sie auf. Die Meldung nennt die Einstellung und die Datei, in der sie steht.
  Die Prüfungen der Einstellungen, Attribute und Objekte laufen vor jedem
  Git-Befehl, der den Index oder die Objekte des Klons liest, und zusammen mit der
  Submodul-Prüfung auch dann, wenn `--yes` im Begriff ist, den Klon zu ersetzen.
  Vor jedem Git-Befehl, der die `.gitattributes`-Dateien des Arbeitsbaums anwendet,
  hält der Installer bei einer solchen Datei an, die Git nicht nachverfolgt, die von
  der committeten Kopie abweicht oder deren committete Kopie Git nicht lesen kann
  oder einen Filter- oder Diff-Treiber benennt (die Kopie im Arbeitsbaum wird
  ebenfalls gelesen), sowie bei einem Git-Repository im Klon, das Git nicht
  nachverfolgt und dessen `.gitattributes`-Dateien Git ebenfalls lesen würde. Die
  eigenen Datenordner der Engine, etwa `backups`, in die kein Release schreibt,
  werden dafür nicht gelesen. Vor dem Fetch hält er
  bei Dateien unter `src` (in beliebiger Schreibweise) an, die Git nicht
  nachverfolgt, da die Engine sie laden könnte. Nach dem Checkout entfernt er
  die Python-Cache-Ordner (`__pycache__`) unter `src`, bevor die Engine aus dem Klon
  läuft. Die Git-Hooks des Klons
  laufen während des Updates nie, und jeder Git-Befehl auf dem Klon läuft ohne
  Pager, ohne automatische Wartung, mit abgeschaltetem Dateisystem-Monitor, nur mit
  den erlaubten Transportwegen file, git, http, https und ssh (sodass eine Adresse
  in der Konfiguration des Klons Git kein Hilfsprogramm wie `ext::` ausführen lassen
  kann) und ohne Submodul-Rekursion; `git diff` und `git status` überspringen
  Submodule. Ein Klon, der einem anderen Benutzer gehört, stoppt den Lauf mit einer
  Erklärung (siehe Fehlerbehebung).
- Ein Ordner, der nur die eigenen Daten der Engine enthält (`backups`, `state`,
  `plans`, `memory`, `contexts`, `learning`, `providers`), wird ohne `--yes`
  aktualisiert, und diese Daten bleiben erhalten.
- Ein Ordner, der keine Apothem-Installation enthält, wird ohne `--yes` nicht
  angerührt. Mit `--yes` verschiebt der Installer den gesamten Ordner unverändert in
  einen neuen Ordner, `~/.apothem.before-apothem-<time>` (darin behält er seinen
  eigenen Namen), sagt, wohin, und installiert neu.
- Ein symbolischer Link bei `APOTHEM_HOME` (unter Windows ein symbolischer Link oder
  eine Junction) wird abgelehnt, weil das Ersetzen den Link ersetzen würde und nicht
  den Ordner, auf den er führt. Richten Sie `APOTHEM_HOME` auf diesen Ordner und
  führen Sie den Vorgang erneut aus. Die Ausnahme ist ein vorhandener Git-Klon, der
  an Ort und Stelle aktualisiert wird.
- Unter Linux und macOS hält eine zu übernehmende Datei oder ein zu übernehmender
  Ordner, dessen Name ein Leerzeichen oder ein anderes Sonderzeichen enthält, die
  Installation an. Verschieben Sie sie zuerst aus `APOTHEM_HOME` heraus.

**Ein Lauf zur Zeit, und gestoppte Läufe.** Jeder Lauf der Installations-, Update-
und Deinstallationsskripte nimmt für den gesamten Lauf eine Sperre neben
`APOTHEM_HOME`, standardmäßig `~/.apothem.lock`, und gibt sie frei, wenn der Lauf
durch Erfolg, Fehlschlag, Ctrl+C oder ein Beendigungssignal endet. Die
`apothem`-Befehle selbst nehmen sie nicht. Ein zweiter Lauf hält mit „Another
Apothem install, update or uninstall is running“ an. Unter POSIX ist die Sperre ein
Ordner, der die Prozess-ID des Laufs enthält. Eine Sperre, die ein abgebrochener
Lauf hinterlassen hat, wird mit einer Anleitung zum Entfernen gemeldet und nie
übernommen, und eine in einer anderen Umgebung angelegte Sperre (etwa WSL und Git
Bash auf einem Rechner) wird als eine gemeldet, deren Prozess von dort aus nicht
geprüft werden kann. Unter Windows PowerShell ist die Sperre eine Datei, die
Windows schließt und löscht, wenn der Prozess endet. Ist `APOTHEM_HOME` ein Link,
nimmt jedes Skript die Sperre neben dem Ordner, auf den er führt. Auch ein
Probelauf nimmt die Sperre, es sei denn, der Ordner, der `APOTHEM_HOME` enthält,
existiert noch nicht. Daher braucht jeder Lauf, einschließlich eines Updates an Ort
und Stelle, einer Deinstallation und eines Probelaufs, Schreibzugriff auf den
Ordner, der `APOTHEM_HOME` enthält; ohne ihn hält der Lauf an, bevor er etwas
ändert.

Ein erzwungenes Beenden oder ein Stromausfall während eines Wechsels kann die
frühere Installation oder andere Einträge von `APOTHEM_HOME` in
`.apothem-old.<name>.*`, `.apothem-extract.<name>.*` oder
`.apothem-clone.<name>.*` daneben zurücklassen, wobei `<name>` der letzte Teil von
`APOTHEM_HOME` ist, oder in einem Ordner `APOTHEM_HOME.before-apothem-<time>`. Die
nächste abgerufene Installation für dieses `APOTHEM_HOME`, einschließlich eines
Probelaufs, hält an, bevor sie etwas ändert, nennt jeden Ordner und die Einträge,
die hineinverschoben wurden, und sagt, wie Sie sie zurückverschieben. Bei einem
Ordner, den ein früherer Installer angelegt hat und der nicht angibt, zu welchem
Home er gehört, nennt die Zeile möglicherweise nur die Engine-Daten: Sehen Sie
hinein. Sie löscht nichts. Siehe
[Fehlerbehebung](/docs/install/troubleshooting#the-installer-stops-an-earlier-run-left-folders-beside-apothem_home).

`--dry-run` (`-DryRun` unter Windows) ruft das Release in einem temporären Ordner
ab, prüft es dort und lässt `~/.apothem` unverändert. Er macht dieselben Prüfungen
wie ein echter Lauf, mit einer Ausnahme für einen vorhandenen Klon: Er prüft die
eigene Einrichtung des Klons, wie oben aufgeführt, ruft aber nicht in den Klon ab
und prüft ihn daher nicht auf Änderungen an nachverfolgten Dateien, was ein echtes
Update nach seinem Fetch tut. Pinnen Sie ein bestimmtes Release mit `APOTHEM_REF`:

```bash title="Pinned, verified install"
APOTHEM_REF=vMAJOR.MINOR.PATCH sh -c "$(curl -fsSL https://apothem.ahmedgad.com/install.sh)"
```

Ersetzen Sie `vMAJOR.MINOR.PATCH` durch ein Tag von der
[Release-Seite](https://github.com/ahmed-g-gad/apothem/releases). Das älteste
Release-Tag ist ein leichtgewichtiges Tag ohne eigene Signatur, daher bricht
die Tag-Prüfung bei ihm ab, obwohl sein Commit signiert ist; jedes spätere
Release-Tag ist annotiert und signiert. Der Abschnitt zur Release-Signierung in
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md)
listet jedes Tag auf und beschreibt, wie es verifiziert wird.

Ausdrückliche Überschreibungen lockern den Standard. `APOTHEM_ALLOW_UNVERIFIED=1` stuft eine fehlgeschlagene Tag-Prüfung auf dem Klon-Weg zu einer Warnung herab und fährt fort; das ist für Air-Gapped-Umgebungen oder den lokalen Einsatz gedacht oder um ein Release zu installieren, das vor der Signatur von Tags erschienen ist. Den cosign-Weg lockert es nie; setzen Sie daher auf einem Host mit cosign zusätzlich `APOTHEM_VERIFY=signature`. Es lockert auch nie die Prüfung, dass das signierte Tag dasjenige ist, das für das Release benannt ist. Da die Überschreibung ein unsigniertes oder mit einem anderen Schlüssel signiertes Tag durchlässt, schützt diese Prüfung nur Tags, die die Signatur des Maintainer-Schlüssels tragen. `APOTHEM_REF=main` checkt den beweglichen Branch ohne Verifizierung nur zusammen mit `APOTHEM_ALLOW_UNVERIFIED=1` aus. Mit `APOTHEM_REF=main` allein holt der Installer `main` in einen Staging-Ordner (in den vorhandenen Klon, wenn `APOTHEM_HOME` einer ist) und bricht dann ab, bevor er etwas auscheckt, `APOTHEM_HOME` ersetzt oder eine Konfiguration materialisiert, weil ein Branch kein signiertes Release-Tag ist. Ein lokaler Checkout über `APOTHEM_SOURCE` ruft nichts ab und überspringt die Verifizierung.

Setzen Sie `APOTHEM_VERIFY`, um die Prüfung selbst zu wählen. Der Standard ist `auto`:

| Wert | Was der Installer prüft |
| --- | --- |
| `auto` (Standard) | `release`, wenn `cosign` im `PATH` liegt und `APOTHEM_HOME` kein Git-Klon ist, sonst `signature` |
| `release` | Die Signatur des Release-Tags durch den Maintainer-Schlüssel und dass das signierte Tag dasjenige ist, das für das Release benannt ist, dann die Prüfung von cosign, dass der Release-Workflow `SHA256SUMS` in einem Lauf auf dem Commit des Tags signiert hat, dann den SHA-256 des Archivs. Hält an, wenn cosign oder `gpg` fehlt |
| `signature` | Die GPG-Signatur des Release-Tags, die vom Maintainer-Schlüssel stammen muss, und dass das signierte Tag dasjenige ist, das für das Release benannt ist |
| `checksum` | Allein den SHA-256 des Archivs gegen `SHA256SUMS`. Braucht `APOTHEM_ALLOW_UNVERIFIED=1` und warnt vor dem Download. Der Prüfsummenmodus verifiziert das Release nicht. SHA256SUMS stammt aus demselben Release wie das Archiv, daher zeigt eine Übereinstimmung nur, dass der Download nicht beschädigt ist; wer die Dateien des Releases ändern kann, kann beide ändern. Verwenden Sie ihn nur auf einem Host ohne cosign und ohne `gpg`, und nur, wenn Sie das in Kauf nehmen |

Jeder Archivmodus bricht bei einer Abweichung des Digests ab, bevor er irgendetwas
entpackt. Frühe Releases nennen das Bundle `SHA256SUMS.sig`, und der Installer
liest diesen Namen, wenn `SHA256SUMS.cosign.bundle` fehlt.

Die Engine läuft dann direkt aus dem abgelegten Baum. Jede
Drittanbieter-Abhängigkeit außer `click` und `rich` ist innerhalb des
Quellbaums vendort, und der Einstiegspunkt setzt dieses Vendor-Verzeichnis
selbst auf `sys.path`. Der Installer gibt den vollständigen Pfad des
`apothem`-Shims aus, den er geschrieben hat. Hat er keinen Shim geschrieben, gibt
er einen Befehl aus, der die Engine startet und dabei den aktuellen Ordner aus
`sys.path` heraushält; kopieren Sie diesen Befehl aus dem Banner.

Beide Skripte lesen dieselben Konfigurations-Umgebungsvariablen
(`APOTHEM_HOME`, `APOTHEM_REPO`, `APOTHEM_REF`, `APOTHEM_ALLOW_UNVERIFIED`,
`APOTHEM_VERIFY`, `APOTHEM_RELEASE_BASE`, `APOTHEM_SOURCE`, `APOTHEM_HARNESS`, `APOTHEM_PROFILE`,
`APOTHEM_SKIP_VERIFY`, `APOTHEM_AUTO_INSTALL_DEPS`, `APOTHEM_BIN_DIR`); siehe
[Umgebungsvariablen des Installers](/docs/how-to/installer-environment-variables)
für die vollständige Tabelle und
[Eigenständige Laufzeit](/docs/architecture/self-contained-runtime) dafür, wie
das `python -m`-Aufrufmodell funktioniert.

**Der Befehl `apothem`.** Nach einer erfolgreichen Installation schreibt der
Installer einen `apothem`-Shim, der an die mitgelieferte Engine weiterleitet —
unter POSIX nach `$HOME/.local/bin`, unter Windows nach
`%LOCALAPPDATA%\Microsoft\WindowsApps` (ein Benutzerverzeichnis, das bereits im
standardmäßigen Windows-`PATH` liegt). Der Installer bearbeitet niemals Ihren
`PATH`. Sobald das Verzeichnis im `PATH` liegt, führen Sie `apothem <command>`
direkt aus, ohne manuelles `PYTHONPATH`.

**Verifizieren:**

```bash title="Verify"
apothem verify --harness claude-code

# or, before the shim is on PATH, by the shim's full path:
~/.local/bin/apothem verify --harness claude-code
```

## 4. Erweiterung für die VS Code-Familie

**Voraussetzungen:** VS Code, Node.js 18+ und System-Python 3.10+ im `PATH`.

Die Erweiterung **Apothem for VS Code** ist im
[Visual Studio Marketplace](https://marketplace.visualstudio.com/items?itemName=ahmed-g-gad.apothem-vscode)
als `ahmed-g-gad.apothem-vscode` verfügbar: Installieren Sie sie über die
Erweiterungsansicht oder mit `code --install-extension ahmed-g-gad.apothem-vscode`.
Sie lässt sich außerdem aus einem `apothem.vsix`-Paket installieren:
`code --install-extension apothem.vsix` oder der Befehl *Install from VSIX…*
des Editors. Der Release-Workflow signiert das Paket und hängt es an jedes
GitHub Release an. Releases, die veröffentlicht wurden, bevor der Workflow die
Erweiterung paketierte, enthalten keine `.vsix`-Datei; fehlt sie im neuesten
Release, bauen Sie das Paket aus einem Checkout mit dem in `tools/vsce/`
festgeschriebenen vsce-Release (dieses vsce-Release benötigt Node.js 22 oder
neuer): Führen Sie
`npm ci --prefix tools/vsce --ignore-scripts` aus, dann
`cd vscode-extension && ../tools/vsce/node_modules/.bin/vsce package --no-dependencies --out apothem.vsix`.
Eine Kopie, die aus einem früheren `apothem.vsix` installiert wurde, trägt den
Bezeichner `ahmed-g-gad.apothem`; deinstallieren Sie sie
(`code --uninstall-extension ahmed-g-gad.apothem`), damit die beiden Kopien nicht
dieselben Befehle registrieren. Eine Erweiterung deckt die Editoren der
VS Code-Familie ab. Ihre
Palettenbefehle (`Apothem: Install`, `Verify`, `Update`, `Uninstall`, `Doctor`)
führen dieselbe Engine über den konfigurierten Runner aus (standardmäßig
`npx @ahmed-g-gad/apothem@<extension version>`, sodass die Erweiterung die
Engine-Version ausführt, mit der sie ausgeliefert wurde; richten Sie die
Benutzereinstellung `apothem.runner` auf einen lokalen Checkout, um aus dem
Quellcode auszuführen). Install, Verify, Update und Uninstall fragen, auf
welchen Harness sie wirken sollen, und bieten den eigenen Harness des Editors
zuerst an; `all` ist eine Auswahlmöglichkeit, niemals die Vorgabe. Die
Einstellung `apothem.runner` gilt maschinenweit, sodass ein Workspace sie nicht
ändern kann, und die Erweiterung läuft nur in einem vertrauenswürdigen
Workspace.

**Verifizieren:** Führen Sie den Befehl **Apothem: Verify** über die
Befehlspalette des Editors aus oder in einem Terminal:

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 8. Direkte Engine (`python -m apothem`)

**Voraussetzungen:** System-Python 3.10+, unter dem die Pakete `click` und
`rich` importierbar sind, sowie ein Checkout des Repositorys. Kein Node.js
erforderlich.

Führen Sie die Engine direkt aus einem Klon aus. Der Einstiegspunkt setzt die
vendorten Abhängigkeiten (`src/apothem/_vendor`) auf `sys.path`; sind `click`
und `rich` importierbar, ist `PYTHONPATH=src` die gesamte Einrichtung:

```bash title="Direct engine"
git clone https://github.com/ahmed-g-gad/apothem
cd apothem
PYTHONPATH=src python -m apothem install --harness claude-code
```

`python -m` setzt den aktuellen Ordner an den Anfang des Modul-Suchpfads von
Python, sodass dort eine Datei wie `click.py` oder ein Ordner namens `apothem`
anstelle des echten Moduls laufen würde. Führen Sie diese Befehle aus dem
Stammverzeichnis des Checkouts aus oder aus einem anderen Ordner, dem Sie
vertrauen. Der installierte `apothem`-Befehl liest den aktuellen Ordner nicht.

Wie beim npm-Shim erstellt ein erstes `install` auf einem Rechner ohne Profil
das Startprofil unter `~/.config/apothem/profile.yaml` und fährt fort.

**Verifizieren:**

```bash title="Verify"
PYTHONPATH=src python -m apothem verify --harness claude-code
```

## Voraussetzungen auf einen Blick

- **Python 3.10 oder neuer** — die Wege, die es ermitteln, tun dies über den
  Namen, und die Namen unterscheiden sich je nach Weg. Der npm-Shim versucht
  `python3`, `python` und dann `py -3`. Die Installer versuchen `python3`,
  `python` und die versionierten Namen von `python3.14` bis hinunter zu
  `python3.10`.
- **`click` und `rich` importierbar** unter diesem Interpreter — die beiden
  terminalseitigen Abhängigkeiten, die die Engine nicht vendort. Die Installer
  prüfen beide, benennen alles Fehlende und bieten an, es für Sie zu
  installieren — mit Ihrer Bestätigung oder automatisch mit `--yes` (`-Yes`
  unter PowerShell) oder `APOTHEM_AUTO_INSTALL_DEPS=1`. Auf jedem anderen Kanal
  stoppt ein fehlendes Paket die Engine mit einem Fehler (Exit-Code 1), der den
  exakten Befehl für den gefundenen Interpreter nennt, mit den
  Versionsbeschränkungen, gegen die Apothem getestet wird
  (`<interpreter> -m pip install "click==…" "rich>=…"`); mit `--json` kommt
  derselbe Fehler als JSON-Envelope mit dem Code `runtime.dependency_missing`
  an.
- **Node.js 18 oder neuer** — nur die Wege, die `npx` ausführen: der npm-Shim
  (2), die Erweiterung für die VS Code-Familie (4) und die
  Kommandozeilen-Bootstraps (5–7).
- **Laufzeiten am Lebensende.** Python 3.10 erreichte sein Upstream-Lebensende
  am 2026-10-01, Node.js 18 und 20 am 2025-04-30 bzw. 2026-04-30. Apothem
  unterstützt sie weiterhin als seine deklarierten Mindestversionen und testet
  jede davon in der CI, sie erhalten jedoch keine Upstream-Sicherheitskorrekturen
  mehr; bevorzugen Sie daher Python 3.11 oder neuer und Node.js 22 oder neuer.
  Die
  [Richtlinie zu Laufzeit-Mindestversionen](/docs/governance/release-engineering-policy#runtime-floors)
  erklärt, wie eine Mindestversion angehoben wird.
- **Git und GnuPG** — nur der Installer-Weg und nur für die Netzwerkform (das
  Skript findet damit das neueste Release und prüft dessen signiertes Tag und
  klont ohne cosign den Quellcode; ein lokaler Checkout benötigt keines von
  beiden).
- **Claude Code** — nur der Plugin-Weg. **VS Code** und das eigene Host-Werkzeug
  jedes Kommandozeilen-Bootstraps werden nur für ihren eigenen Kanal (4–7)
  benötigt.
