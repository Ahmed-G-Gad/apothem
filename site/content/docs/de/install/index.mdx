Apothem ist in unter zwei Minuten installiert und arbeitet neben Ihrer
bestehenden Harness-Konfiguration. Jeder Weg führt dieselbe eigenständige
Engine aus — der Quellbaum trägt seine vendorten Abhängigkeiten mit und läuft
aus einem Checkout unter System-Python 3.10 oder neuer (siehe
[die eigenständige Laufzeit](/docs/architecture/self-contained-runtime)).

**Zwei Voraussetzungen gelten für jeden Weg:** System-**Python 3.10 oder neuer**
im `PATH`, unter dem die Pakete `click` und `rich` importierbar sind. Die Wege
über den npm-Shim und die Werkzeug-Plugins benötigen zusätzlich **Node.js 18
oder neuer**, um `npx` auszuführen. Python 3.10 sowie Node.js 18 und 20 haben
ihr Upstream-Lebensende überschritten; sie bleiben unterstützt und getestet,
neuere Versionen werden jedoch bevorzugt (siehe
[Voraussetzungen auf einen Blick](#voraussetzungen-auf-einen-blick)). Der
eigene Abschnitt jedes Kanals unten wiederholt seine exakten Voraussetzungen,
einen kopierbereiten Befehl und einen Verifizierungsschritt.

## Einen Kanal wählen

Acht Installationskanäle stehen zur Verfügung. Wählen Sie danach, wie Sie
bereits arbeiten.

| # | Kanal | Liefert | Voraussetzungen |
|---|---------|----------|---------------|
| 1 | [Claude Code-Plugin](#1-claude-code-plugin) | Vollständiger Harness in Claude Code | Claude Code · Python 3.10+ |
| 2 | [npm-Shim (`npx`)](#2-npm-shim-npx) | Vollständiger Harness, jedes Werkzeug | Node 18+ · Python 3.10+ |
| 3 | [Ein-Schritt-Installer](#3-ein-schritt-installer) | Vollständiger Harness + ein `apothem`-Befehl | Python 3.10+ (`git` für eine Netzwerkinstallation) |
| 4 | [Erweiterung für die VS Code-Familie](#4-erweiterung-für-die-vs-code-familie) | Vollständiger Harness aus dem Editor | VS Code · Node 18+ · Python 3.10+ |
| 5 | [Kommandozeilen-Bootstrap (Erweiterungs-Host)](#5-kommandozeilen-bootstrap-erweiterungs-host) | Bootstrap, der die Engine ausführt | Das zugehörige Host-Werkzeug · Node 18+ · Python 3.10+ |
| 6 | [Kommandozeilen-Bootstrap (`qwen-code`-Host)](#6-kommandozeilen-bootstrap-qwen-code-host) | Bootstrap, der die Engine ausführt | Das zugehörige Host-Werkzeug · Node 18+ · Python 3.10+ |
| 7 | [Kommandozeilen-Bootstrap (Plugin-Host)](#7-kommandozeilen-bootstrap-plugin-host) | Bootstrap, der die Engine ausführt | Das zugehörige Host-Werkzeug · Node 18+ · Python 3.10+ |
| 8 | [Direkte Engine (`python -m apothem`)](#8-direkte-engine-python--m-apothem) | Vollständiger Harness aus einem Checkout | Python 3.10+ (`click`, `rich`) |

<Callout title="Welche Kanäle den vollständigen Harness liefern">
  Der npm-Shim (2), die Ein-Schritt-Installer (3) und die direkte Engine (8)
  materialisieren für sich allein die gesamte synchronisierte Einheit für jeden
  Harness. Die drei Kommandozeilen-Erweiterungen (5–7) installieren einen
  kleinen **Bootstrap**, der die Engine per Shell aufruft
  (`npx @ahmed-g-gad/apothem install`), um den vollständigen Harness zu
  materialisieren — sie sind der Einstiegspunkt, nicht für sich allein die
  vollständige Lieferung. Das Claude Code-Plugin (1) trägt die Engine mit und
  führt sie direkt aus. Die Erweiterung für die VS Code-Familie (4) trägt keine
  eigene Engine mit: Ihre Befehle führen die Engine standardmäßig über den
  npm-Shim aus.
</Callout>

Jeder Weg ist idempotent: Ein erneuter Aufruf ist sicher und konvergiert zum
selben Zustand.

## 1. Claude Code-Plugin

**Voraussetzungen:** Claude Code und System-Python 3.10+ im `PATH`.

Der Plugin-Weg läuft vollständig innerhalb von Claude Code. Er bündelt die
Apothem-Engine mit ihren Slash-Befehlen, delegierten Workern, Skills, Regeln
und Hooks, alle aus dem eigenständigen Plugin-Baum ausführbar:

```text title="Inside Claude Code"
/plugin marketplace add ahmed-g-gad/apothem
/plugin install apothem@apothem
```

Nach der Installation stehen der Apothem-Befehlssatz, die mitgelieferten
delegierten Worker, die Skills und die vier
[Ausgabestile](/docs/reference/output-styles) (wählen Sie einen mit
`/output-style` oder über `/config`) in jeder Claude Code-Sitzung zur
Verfügung. Plugin-Befehle tragen das Präfix des Plugins: `/apothem:plan-spec`,
`/apothem:security-audit` und die übrigen. Claude Code akzeptiert auch die
Kurzform (`/plan-spec`), solange kein anderer Befehl diesen Namen verwendet.
Zwei Namen belegt Claude Code selbst: `/plan` wechselt in den Plan-Modus, und
`/code-review` führt das mitgelieferte Review aus; geben Sie daher
`/apothem:plan` und `/apothem:code-review` für die Apothem-Befehle ein. Wenn
statt des Plugins die Apothem-Engine die Installation in Claude Code vornimmt,
werden Befehle zu persönlichen Skills unter `~/.claude/skills/` ohne Präfix,
und ein persönlicher `code-review`-Skill ersetzt das mitgelieferte
`/code-review` (sein Alias `/review` führt weiterhin das mitgelieferte aus).
Zwei Namen, `projectify` und `workflow`, werden sowohl als Befehl als auch als
Skill ausgeliefert; Claude Code führt den Skill aus, wenn beides existiert,
daher führt das Plugin den Skill aus, und die Engine-Installation schreibt den
Skill in diesen Platz. Siehe [Slash-Befehle](/docs/reference/commands) für den
vollständigen Befehlskatalog.

**Verifizieren:** Führen Sie `/plugin` innerhalb von Claude Code aus und
bestätigen Sie, dass **apothem** als installiert aufgeführt ist, oder prüfen
Sie den Drift-Bericht in einem Terminal:

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 2. npm-Shim (`npx`)

**Voraussetzungen:** Node.js 18+ (für `npx`) und System-Python 3.10+ im `PATH`.
Der Shim ermittelt den Interpreter und leitet jeden CLI-Befehl an die
mitgelieferte Engine weiter — nichts wird dauerhaft auf Ihrem System abgelegt.
Er versucht `python3`, `python` und dann `py -3`, in dieser Reihenfolge; setzen
Sie **`APOTHEM_PYTHON`** auf einen Interpreterpfad, damit dieser zuerst
versucht wird. Das benötigen Sie, wenn Python installiert ist, aber nicht im
`PATH` liegt, oder wenn mehrere Versionen installiert sind und Sie eine
bestimmte verwenden wollen. Der von Ihnen benannte Interpreter muss die Prüfung
auf Python 3.10+ dennoch bestehen; besteht er sie nicht, greift der Shim auf
`python3`, `python` und dann `py -3` zurück.

```bash title="npx"
npx @ahmed-g-gad/apothem install --harness claude-code
```

Auf einem Rechner ohne Profil erstellt dieses erste `install` das Startprofil
unter `~/.config/apothem/profile.yaml` und meldet dies. Seine Identitätsfelder
sind Platzhalter: Personalisieren Sie sie
(`npx @ahmed-g-gad/apothem profile edit`) und führen Sie den Befehl dann mit
`update` anstelle von `install` erneut aus, um sie anzuwenden.

Er läuft auch direkt aus dem Repository:

```bash title="npx from the repository"
npx github:ahmed-g-gad/apothem install --harness claude-code
```

Jeder Befehl in der [CLI-Referenz](/docs/cli-reference) funktioniert in dieser
Form; setzen Sie `npx @ahmed-g-gad/apothem` anstelle von `apothem` ein. Dies ist
auch der Installationsweg für OpenCode und jedes andere Werkzeug, das keine
separate Plugin- oder Erweiterungs-Registry bereitstellt — Apothem
synchronisiert diese direkt in ihr natives Konfigurationsverzeichnis
(`npx @ahmed-g-gad/apothem install --harness opencode`).

**Verifizieren:**

```bash title="Verify"
npx @ahmed-g-gad/apothem --version
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 3. Ein-Schritt-Installer

**Voraussetzungen:** System-Python 3.10+ im `PATH` (der Installer bietet an,
die Voraussetzungen `click` / `rich` für Sie hinzuzufügen); `git` wird nur für
eine Netzwerkinstallation benötigt, die den Quellcode klont.

Die Installationsskripte ermitteln das neueste signierte Release-Tag,
verifizieren seine Signatur, legen den Apothem-Quellbaum auf dem Stand dieses
Tags unter `~/.apothem` ab, erstellen ein Startprofil, wenn keines existiert,
materialisieren Ihren ersten Harness und verifizieren das Ergebnis, alles in
einem Durchlauf. Das Startprofil enthält Platzhalter-Identitätsfelder:
Bearbeiten Sie es und führen Sie dann `apothem update --harness <name>` aus, um
Ihre eigenen anzuwenden. Ein erneuter Aufruf ist idempotent: Ein bestehender
Baum wird erneut auf das ermittelte Tag ausgecheckt, und der Harness wird neu
materialisiert. Die an ein Tag gepinnte, verifizierte Installation ist der
Standardweg und der empfohlene Weg.

```bash title="macOS · Linux · WSL2 · BSD — latest signed tag, verified"
curl -fsSL https://apothem.ahmedgad.com/install.sh | bash
```

```powershell title="Windows · PowerShell — latest signed tag, verified"
irm https://apothem.ahmedgad.com/install.ps1 | iex
```

Dieselben Skripte liegen in einem Checkout unter `scripts/installer/` —
`install`, `uninstall` und `update` in den Formen `.sh`, `.ps1` und `.bat` —,
sodass Sie sie nach dem Klonen direkt ausführen können:

```bash title="From a checkout"
APOTHEM_HARNESS=claude-code sh scripts/installer/install.sh                                 # POSIX
$env:APOTHEM_HARNESS = 'claude-code'; pwsh -NoProfile -File scripts/installer/install.ps1   # Windows
```

### Vertrauensmodell

Ist `APOTHEM_REF` nicht gesetzt, ermittelt der Installer das höchste
`vMAJOR.MINOR.PATCH`-Release-Tag und checkt *dieses* aus — niemals den
beweglichen `main`-Branch. Bevor irgendeine Konfiguration materialisiert wird,
wird die Signatur des abgerufenen Tags mit `git verify-tag` verifiziert; ein
unsigniertes, manipuliertes oder nicht verifizierbares Tag bricht die
Installation ab, bevor irgendetwas geschrieben wird. Ein signiertes Tag, dessen
öffentlicher Maintainer-Schlüssel noch nicht im lokalen Schlüsselbund liegt,
bricht stattdessen mit einer Anleitung zum Schlüsselimport ab: Importieren Sie
den Schlüssel, prüfen Sie seinen Fingerabdruck gegen den in
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md)
veröffentlichten Wert und führen Sie den Vorgang erneut aus. Pinnen Sie ein
bestimmtes Release mit `APOTHEM_REF`:

```bash title="Pinned, verified install"
APOTHEM_REF=vMAJOR.MINOR.PATCH sh -c "$(curl -fsSL https://apothem.ahmedgad.com/install.sh)"
```

Ersetzen Sie `vMAJOR.MINOR.PATCH` durch ein Tag von der
[Release-Seite](https://github.com/ahmed-g-gad/apothem/releases). Das älteste
Release-Tag ist ein leichtgewichtiges Tag ohne eigene Signatur, daher bricht
die Tag-Prüfung bei ihm ab, obwohl sein Commit signiert ist; jedes spätere
Release-Tag ist annotiert und signiert. Der Abschnitt zur Release-Signierung in
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md)
listet jedes Tag auf und beschreibt, wie es verifiziert wird.

Ausdrückliche Überschreibungen lockern den Standard. `APOTHEM_ALLOW_UNVERIFIED=1`
stuft einen Verifizierungsfehler zu einer Warnung herab und fährt fort; das ist
für den Einsatz in Air-Gapped-Umgebungen, lokal oder vor signierten Releases
gedacht. `APOTHEM_REF=main` checkt den beweglichen Branch ohne Verifizierung nur
zusammen mit `APOTHEM_ALLOW_UNVERIFIED=1` aus. Mit `APOTHEM_REF=main` allein
holt der Installer `main` nach `APOTHEM_HOME` und bricht dann ab, bevor eine
Konfiguration materialisiert wird, weil ein Branch kein signiertes Release-Tag
ist. Ein lokaler Checkout über `APOTHEM_SOURCE` ruft nichts ab und überspringt
die Verifizierung.

`APOTHEM_VERIFY=checksum` ist der Mittelweg für einen Host, der den
öffentlichen Schlüssel des Maintainers noch nicht besitzt: Statt zu klonen,
lädt der Installer das Plattform-Archiv des Releases und dessen `SHA256SUMS`
herunter, bricht bei einer Abweichung des Digests ab, bevor er irgendetwas
entpackt, und warnt, dass ein übereinstimmender Digest belegt, dass das Archiv
dasjenige ist, das das Release auflistet, nicht aber, wer es veröffentlicht hat.

Die Engine läuft dann direkt aus dem abgelegten Baum. Jede
Drittanbieter-Abhängigkeit außer `click` und `rich` ist innerhalb des
Quellbaums vendort, und der Einstiegspunkt setzt dieses Vendor-Verzeichnis
selbst auf `sys.path`:

```bash
PYTHONPATH="$HOME/.apothem/src" python -m apothem <command>
```

Beide Skripte lesen dieselben Konfigurations-Umgebungsvariablen
(`APOTHEM_HOME`, `APOTHEM_REPO`, `APOTHEM_REF`, `APOTHEM_ALLOW_UNVERIFIED`,
`APOTHEM_VERIFY`, `APOTHEM_RELEASE_BASE`, `APOTHEM_SOURCE`, `APOTHEM_HARNESS`, `APOTHEM_PROFILE`,
`APOTHEM_SKIP_VERIFY`, `APOTHEM_AUTO_INSTALL_DEPS`, `APOTHEM_BIN_DIR`); siehe
[Umgebungsvariablen des Installers](/docs/how-to/installer-environment-variables)
für die vollständige Tabelle und
[Eigenständige Laufzeit](/docs/architecture/self-contained-runtime) dafür, wie
das `python -m`-Aufrufmodell funktioniert.

**Der Befehl `apothem`.** Nach einer erfolgreichen Installation schreibt der
Installer einen `apothem`-Shim, der an die mitgelieferte Engine weiterleitet —
unter POSIX nach `$HOME/.local/bin`, unter Windows nach
`%LOCALAPPDATA%\Microsoft\WindowsApps` (ein Benutzerverzeichnis, das bereits im
standardmäßigen Windows-`PATH` liegt). Der Installer bearbeitet niemals Ihren
`PATH`. Sobald das Verzeichnis im `PATH` liegt, führen Sie `apothem <command>`
direkt aus, ohne manuelles `PYTHONPATH`.

**Verifizieren:**

```bash title="Verify"
apothem verify --harness claude-code

# or, before the shim is on PATH, from the bundled source:
PYTHONPATH="$HOME/.apothem/src" python -m apothem verify --harness claude-code
```

## 4. Erweiterung für die VS Code-Familie

**Voraussetzungen:** VS Code, Node.js 18+ und System-Python 3.10+ im `PATH`.

Die **Apothem**-Erweiterung wird aus einem `apothem.vsix`-Paket installiert:
`code --install-extension apothem.vsix` oder der Befehl *Install from VSIX…*
des Editors. Der Release-Workflow signiert das Paket und hängt es an jedes
GitHub Release an. Releases, die veröffentlicht wurden, bevor der Workflow die
Erweiterung paketierte, enthalten keines; fehlt es im neuesten Release, bauen
Sie das Paket aus einem Checkout mit dem in `.github/vsce/` festgeschriebenen
vsce-Release, das Node.js 22 oder neuer benötigt: Führen Sie
`npm ci --prefix .github/vsce --ignore-scripts` aus, dann
`cd vscode-extension && ../.github/vsce/node_modules/.bin/vsce package --no-dependencies --out apothem.vsix`.
Ein Eintrag im [Visual Studio Marketplace](https://marketplace.visualstudio.com/)
ist noch nicht veröffentlicht. Eine Erweiterung deckt VS Code und seine im
Editor integrierte Oberfläche für den begleitenden Assistenten ab. Ihre
Palettenbefehle (`Apothem: Install`, `Verify`, `Update`, `Uninstall`, `Doctor`)
führen dieselbe Engine über den konfigurierten Runner aus (standardmäßig
`npx @ahmed-g-gad/apothem@<extension version>`, sodass die Erweiterung die
Engine-Version ausführt, mit der sie ausgeliefert wurde; richten Sie die
Benutzereinstellung `apothem.runner` auf einen lokalen Checkout, um aus dem
Quellcode auszuführen). Install, Verify, Update und Uninstall fragen, auf
welchen Harness sie wirken sollen, und bieten den eigenen Harness des Editors
zuerst an; `all` ist eine Auswahlmöglichkeit, niemals die Vorgabe. Die
Einstellung `apothem.runner` gilt maschinenweit, sodass ein Workspace sie nicht
ändern kann, und die Erweiterung läuft nur in einem vertrauenswürdigen
Workspace.

**Verifizieren:** Führen Sie den Befehl **Apothem: Verify** über die
Befehlspalette des Editors aus oder in einem Terminal:

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 5. Kommandozeilen-Bootstrap (Erweiterungs-Host)

**Voraussetzungen:** das zugehörige Host-Kommandozeilenwerkzeug, Node.js 18+ und
System-Python 3.10+ im `PATH`.

Installieren Sie Apothem als Erweiterung direkt aus dem Repository — der Befehl
enthält den exakten Host- und Harness-Slug:

```bash title="Install the extension"
gemini extensions install https://github.com/ahmed-g-gad/apothem
```

Diese Erweiterung ist ein **Bootstrap**, nicht für sich allein die vollständige
Installation: Sie lädt eine Apothem-Kontextdatei und fügt einen
`/apothem`-Befehl hinzu, der die Engine per Shell aufruft
(`npx @ahmed-g-gad/apothem`). Materialisieren Sie den vollständigen Harness,
indem Sie die Installation darüber ausführen:

```bash title="Materialize the full harness"
npx @ahmed-g-gad/apothem install --harness gemini-cli --project .
```

**Verifizieren:**

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness gemini-cli --project .
```

**Voraussetzungen:** das zugehörige Host-Kommandozeilenwerkzeug, Node.js 18+ und

Installieren Sie Apothem als `--harness qwen-code`-Erweiterung direkt aus dem


Apothem-Kontextdatei und ruft die Engine per Shell auf. Materialisieren Sie den
vollständigen Harness, indem Sie die Installation darüber ausführen:

```bash title="Materialize the full harness"
npx @ahmed-g-gad/apothem install --harness qwen-code
```

**Verifizieren:**

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness qwen-code
```

## 7. Kommandozeilen-Bootstrap (Plugin-Host)

**Voraussetzungen:** das zugehörige Host-Kommandozeilenwerkzeug, Node.js 18+ und
System-Python 3.10+ im `PATH`.

Fügen Sie das Repository als Plugin-Marketplace hinzu und installieren Sie dann
das Plugin — der Befehl enthält den exakten Host- und Harness-Slug:

```bash title="Install the plugin"
codex plugin marketplace add ahmed-g-gad/apothem
codex plugin add apothem@apothem
```

Wie die Erweiterungen aus Kanal 5 und Kanal 6 ist dies ein **Bootstrap**, der
die Engine per Shell aufruft. Materialisieren Sie den vollständigen Harness,
indem Sie die Installation darüber ausführen:

```bash title="Materialize the full harness"
npx @ahmed-g-gad/apothem install --harness codex
```

**Verifizieren:**

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness codex
```

## 8. Direkte Engine (`python -m apothem`)

**Voraussetzungen:** System-Python 3.10+, unter dem die Pakete `click` und
`rich` importierbar sind, sowie ein Checkout des Repositorys. Kein Node.js
erforderlich.

Führen Sie die Engine direkt aus einem Klon aus. Der Einstiegspunkt setzt die
vendorten Abhängigkeiten (`src/apothem/_vendor`) auf `sys.path`; sind `click`
und `rich` importierbar, ist `PYTHONPATH=src` die gesamte Einrichtung:

```bash title="Direct engine"
git clone https://github.com/ahmed-g-gad/apothem
cd apothem
PYTHONPATH=src python -m apothem install --harness claude-code
```

Wie beim npm-Shim erstellt ein erstes `install` auf einem Rechner ohne Profil
das Startprofil unter `~/.config/apothem/profile.yaml` und fährt fort.

**Verifizieren:**

```bash title="Verify"
PYTHONPATH=src python -m apothem verify --harness claude-code
```

## Jede Installation verifizieren

Jeder Kanal oben nennt seinen eigenen Verifizierungsbefehl. Die zwei
allgemeinen Formen sind:

```bash title="Installer path"
PYTHONPATH="$HOME/.apothem/src" python -m apothem verify --harness claude-code
```

```bash title="npx path"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

Ersetzen Sie den Harness-Namen durch den Adapter, den Sie installiert haben;
alle unterstützten Namen finden Sie in der [Harness-Liste](/docs/harnesses). Um
jeden installierten Adapter auf einmal zu prüfen (seine Verifizierung und seine
Hook-Befehle), führen Sie `apothem doctor` (oder
`npx @ahmed-g-gad/apothem doctor`) in derselben Form aus. Für den Plugin-Weg
führen Sie `/plugin` innerhalb von Claude Code aus und bestätigen, dass
**apothem** als installiert aufgeführt ist.

## Voraussetzungen auf einen Blick

- **Python 3.10 oder neuer** — jeder Weg, der die Engine ausführt, sucht danach
  (`python3`, `python`, die versionierten Namen und `py -3` unter Windows).
- **`click` und `rich` importierbar** unter diesem Interpreter — die beiden
  terminalseitigen Abhängigkeiten, die die Engine nicht vendort. Die Installer
  prüfen beide, benennen alles Fehlende und bieten an, es für Sie zu
  installieren — mit Ihrer Bestätigung oder automatisch mit `--yes` (`-Yes`
  unter PowerShell) oder `APOTHEM_AUTO_INSTALL_DEPS=1`. Auf jedem anderen Kanal
  stoppt ein fehlendes Paket die Engine mit einem Fehler (Exit-Code 1), der den
  exakten Befehl für den gefundenen Interpreter nennt, mit den
  Versionsbeschränkungen, gegen die Apothem getestet wird
  (`<interpreter> -m pip install "click==…" "rich>=…"`); mit `--json` kommt
  derselbe Fehler als JSON-Envelope mit dem Code `runtime.dependency_missing`
  an.
- **Node.js 18 oder neuer** — nur die Wege über den npm-Shim und die
  Werkzeug-Plugins.
- **Laufzeiten am Lebensende.** Python 3.10 erreichte sein Upstream-Lebensende
  am 2026-10-01, Node.js 18 und 20 am 2025-04-30 bzw. 2026-04-30. Apothem
  unterstützt sie weiterhin als seine deklarierten Mindestversionen und testet
  jede davon in der CI, sie erhalten jedoch keine Upstream-Sicherheitskorrekturen
  mehr; bevorzugen Sie daher Python 3.11 oder neuer und Node.js 22 oder neuer.
  Die
  [Richtlinie zu Laufzeit-Mindestversionen](/docs/governance/release-engineering-policy#laufzeit-mindestversionen)
  erklärt, wie eine Mindestversion angehoben wird.
- **Git** — nur der Installer-Weg und nur für die Netzwerkform (das Skript
  klont den Quellcode; ein lokaler Checkout benötigt keinen Klon).
- **Claude Code** — nur der Plugin-Weg. **VS Code** und das eigene Host-Werkzeug
  jedes Kommandozeilen-Bootstraps werden nur für ihren eigenen Kanal (4–7)
  benötigt.
