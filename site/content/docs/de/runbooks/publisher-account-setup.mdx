Dieses Runbook konfiguriert die Publisher-Seite der Release-Oberfläche. Die
Distributionsgeschichte hat eine einzige Registry: das Scoped-npm-Paket
`@ahmed-g-gad/apothem` auf npmjs.com, veröffentlicht vom manuell ausgelösten
Workflow `publish-npm.yml`, nachdem die Workflows für GitHub Release, Pages, CI,
Konformität und Harness grün sind. Jedes andere Artefakt wird auf der
GitHub-Release-Seite selbst ausgeliefert und benötigt kein externes
Publisher-Konto.

## Identitätszuordnung

| Oberfläche | Konto | Paketidentität |
|---|---|---|
| GitHub | `ahmed-g-gad` | `ahmed-g-gad/apothem` |
| npm (npmjs.com) | `ahmed-g-gad` | `@ahmed-g-gad/apothem` |

Der GitHub-Eigentümer darf sich künftig ändern. Die Workflow- und
Installer-Logik liest `github.repository`, `github.repository_owner` oder
`APOTHEM_GITHUB_REPOSITORY`, wo eine Plattform dynamische Auflösung zulässt.
Der Paketbezeichner in der Registry bleibt stabil, weil Benutzer den Paketnamen
installieren, nicht den Kontonamen des Maintainers.

## npm (npmjs.com)

1. Melden Sie sich bei `https://www.npmjs.com/` als `ahmed-g-gad` an.
2. Aktivieren Sie die Zwei-Faktor-Authentifizierung für das Konto.
3. Bestätigen Sie den Scoped-Paketnamen:

   ```bash
   npm view @ahmed-g-gad/apothem name
   ```

   Ein `404` bedeutet, dass das Scoped-Paket noch nicht veröffentlicht wurde.
   Jede andere Paketantwort muss vor der Veröffentlichung mit diesem Repository
   und diesem Konto übereinstimmen.
4. Erstellen Sie das Paket auf npm, falls die Benutzeroberfläche einen ersten
   Paketeintrag verlangt. Behalten Sie den Namen mit Scope bei:
   `@ahmed-g-gad/apothem`.
5. Konfigurieren Sie Trusted Publishing für `@ahmed-g-gad/apothem` aus GitHub Actions:
   - GitHub-Eigentümer: `ahmed-g-gad`
   - Repository: `apothem`
   - Workflow-Dateiname: `publish-npm.yml`
   - Umgebung: `release` (das `environment:` des Publish-Jobs in
     `publish-npm.yml`; beide müssen übereinstimmen)
   - Erlaubte Aktion: `npm publish`.
6. Verifizieren Sie in GitHub, dass die Umgebung `release` in
   `ahmed-g-gad/apothem` existiert und eine manuelle Genehmigung für das
   Deployment verlangt.
7. Beschränken Sie die npm-Oberfläche auf ein öffentliches Registry-Paket:
   `@ahmed-g-gad/apothem` auf npmjs.com.
8. Bestätigen Sie die Release-Bereitschaft:

   ```bash title="Release readiness"
   bash scripts/release/check-release-ready.sh <release-tag>
   ```

9. Führen Sie `Publish — npm` (`publish-npm.yml`) über den Tab GitHub Actions
   mit `tag=<release-tag>` aus und genehmigen Sie das Deployment der Umgebung
   `release`.
10. Verifizieren Sie das Live-Paket:

    ```bash title="npm verification"
    npm view @ahmed-g-gad/apothem version
    npx @ahmed-g-gad/apothem@<version> --version
    ```

Es ist kein `NPM_TOKEN`-, Benutzernamen- oder Passwort-Secret erforderlich. Der
Workflow veröffentlicht über npm Trusted Publishing (OIDC), wobei die
Node-Version und der OIDC-Mindeststand der npm-CLI in
`.github/workflows/publish-npm.yml` gepinnt sind. Er führt
`npm publish --access public` gegen npmjs.com aus; npm erzeugt automatisch
Provenance für öffentliche Pakete, die aus einem öffentlichen
GitHub-Actions-Workflow veröffentlicht werden. Ein Registry-`404` während `PUT`
bedeutet, dass der vertrauenswürdige Publisher auf npm-Seite, der Paket-Scope
oder die Kontoautorisierung noch nicht abgestimmt ist; korrigieren Sie die
npm-Paketeinstellungen, bevor Sie den Workflow erneut versuchen.

Sobald eine vertrauenswürdige Veröffentlichung gelungen ist, schließen Sie den
Token-Pfad endgültig: Wählen Sie in den **Settings → Publishing access** des
Pakets auf npmjs.com die Option **Require two-factor authentication and
disallow tokens**, und löschen Sie jedes npm-Token-Secret, das noch im
Repository liegt. Der Workflow liest keines mehr.

Referenzen: [npm Trusted Publishers](https://docs.npmjs.com/trusted-publishers/), [npm-Provenance](https://docs.npmjs.com/generating-provenance-statements/) und [npm-Scopes](https://docs.npmjs.com/about-scopes/).

## GitHub-seitige Release-Voraussetzungen

Die übrigen Release-Oberflächen sind GitHub-nativ und authentifizieren sich mit
dem auf das Repository beschränkten `GITHUB_TOKEN`; es ist kein externes Konto
beteiligt.

1. **GitHub Release.** `.github/workflows/release.yml` läuft auf dem
   Versions-Tag und benötigt nur seine job-lokale Berechtigung
   `contents: write`. Bestätigen Sie vor dem Taggen, dass die Workflow-Datei
   auf `main` vorhanden ist.
2. **Benutzerdefinierte Pages-Domain.** Die Dokumentationsseite wird über
   `publish-static-site.yml` auf die benutzerdefinierte Domain
   `apothem.ahmedgad.com` bereitgestellt. Die Domain, das DNS und die
   HTTPS-Erzwingung werden durch das
   [Pages-Aktivierungs-Runbook](/docs/runbooks/pages-enablement) eingerichtet;
   verifizieren Sie:

   ```bash title="Pages verification"
   gh api repos/ahmed-g-gad/apothem/pages --jq '.cname, .https_enforced'
   curl -sSI https://apothem.ahmedgad.com/ | head -n 1
   ```

3. **Skript-Installer.** `install.sh` und `install.ps1` werden von der
   Pages-Website ausgeliefert (`https://apothem.ahmedgad.com/install.sh` und
   `https://apothem.ahmedgad.com/install.ps1`). Sie werden durch dasselbe
   Pages-Deployment veröffentlicht; es ist kein separates Konto und kein Token
   erforderlich.

## Verifizierungsmatrix

Nach der Einrichtung beantwortet jede Publisher-Oberfläche ihre kanonische
Prüfung:

| Oberfläche | Prüfung |
|---|---|
| npmjs.com | `npm view @ahmed-g-gad/apothem version` gibt die veröffentlichte Version zurück |
| GitHub Release | `gh release view <release-tag> --json assets --jq '.assets[].name'` listet sdist, Wheel, SBOM, cosign-Bundles, Provenance und Plattformarchive auf |
| Pages | `curl -sSI https://apothem.ahmedgad.com/` gibt `200` auf der benutzerdefinierten Domain zurück |
