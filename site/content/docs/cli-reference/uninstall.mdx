Remove a harness adapter configuration.

## Synopsis

```
apothem uninstall --harness NAME|all [--yes] [--project PATH]
                   [--quiet|-q] [--verbose|-v]
                   [--format plain|json] [--json] [--no-color]
```

Removes adapter-managed harness targets, then the directories the install
created once they are empty (a directory holding anything of yours stays).

## What an uninstall removes

An install records the SHA-256 of every file it copies into place (skills,
commands, rules and the like)
in the install ledger (`~/.apothem/state/<harness>/ledger.jsonl`). An
uninstall removes such a file only while it still has that content, then each
folder left holding nothing, an empty folder you made inside an Apothem
folder included. Everything else stays and gets a `Warning:` line: a file you
added to an Apothem folder, an Apothem file you edited, a file of your own that
has an Apothem name, and a path the install record does not list. A file you
keep keeps its folder.

An install recorded by an earlier release does not say which files Apothem
wrote. For it, the uninstall compares each file with what this release writes
at that path and removes the ones with the same bytes. Two spots hold the
Python interpreter the install found: the statusline's command and a comment
in the conformity gate. Such a spot compares as the same only when it holds
`py -3`, the one launcher an earlier release wrote there, or the full path of
an interpreter file on this machine, and nothing else. A path there that holds
`&`, `#` or `$` (a Windows user name such as `R&D`), or that names no file
here, never compares as the same, so that file is kept. A path to an
interpreter you have since upgraded or removed names no file here either, so
that file is kept too: run `apothem update`, then uninstall again. Apothem's
hook entries in a settings or hooks file are not compared this way: they are
recognized by the dispatcher script they run, whatever interpreter comes
before it, and removed after the file is backed up.

A file at a name Apothem writes that differs (written by that earlier
release, or edited by you) stays, and the uninstall does not finish: it
prints `✗ <harness> uninstall did not finish:` with the number of such paths
(a folder counts once, and its files are listed under its `Warning:` line)
and exits `2`. So does a path that release recorded and this release no
longer writes, since there is nothing to compare it with. An install with no
record at all (its ledger was deleted) ends the same way, because nothing
shows which of its files Apothem wrote; every path it keeps outside a link is
listed under one `Warning:` line, the files you added included, since nothing
tells them apart.
`apothem update` writes this release's files and records them, so running it
and then `apothem uninstall` again finishes the job. Before you do, copy any
listed file you edited or added: the update overwrites the paths it writes
and replaces each Apothem folder entry it writes whole (it backs both up
first, under `~/.apothem/backups/`, but nothing puts them back). Fix any file
a warning names for an Apothem marker first too (see
[An uninstall that did not finish](#an-uninstall-that-did-not-finish)). For an
install an earlier release recorded, a file in an Apothem folder at a name
Apothem never writes is yours: it is listed under the `Warning:` line for
files that are changed or yours, it stays, and the uninstall still finishes.

When the latest record at that location is an uninstall that finished (and
an install after it stopped before it could record itself, say), the
uninstall compares each path with what this release writes, apart from the
shared folders in your home directory: those stay as they are, as when there
is no record (see
[Shared folders in your home directory](#shared-folders-in-your-home-directory)).
It removes a file only when the file has exactly the same bytes, and it
removes a folder that holds no file. Nothing there shows which interpreter
that install found, so a file that holds an interpreter's path (the
statusline's command, the comment in the conformity gate) never compares as
the same and stays. While the gate stays, the harness still reads as
installed, so check that file and remove it by hand. Everything else stays
too (a file of yours, an Apothem file you edited, a cache another program
wrote) and gets a `Warning:` line, and the uninstall finishes. A file left in
a folder whose other files were removed is listed under the line for files
that are changed or yours; any other path is listed under a line saying that
no install record lists it, that it does not match what this release writes,
and that you can remove it by hand if you no longer want it. A
file with exactly the same bytes behind a link stops the uninstall, as
Apothem's own files behind a link do for a recorded install (see below). If
such an uninstall does not finish (a file it could not remove, say), the
harness still reads as installed, and running the uninstall again works the
same way, also after an install that failed and undid its own changes. After
a rollback, or only uninstalls that did not finish, such a path stops the
uninstall as it does when there is no record.

When no install is recorded at that location, as in the cases above, the
uninstall also leaves Apothem's managed block where it is: in
`~/.claude/CLAUDE.md` for Claude Code, and in the profile document
`apothem/rules/00-apothem-profile.md` in the folder of a tool configured
through one settings file, such as Open-Claw, OpenCode or Qwen Code. Nothing
shows which install wrote that block, so the file stays as it is, and a
`Warning:` line names it; the warning does not stop the uninstall. If you no
longer want the block (Claude Code still reads `CLAUDE.md`), delete the lines
from `<!-- BEGIN APOTHEM MANAGED BLOCK -->` to
`<!-- END APOTHEM MANAGED BLOCK -->` by hand.

The shared working directory's memory, contexts, and learning stores are
backed up and removed only when this is the last harness installed at that
directory. Uninstall removes them at the location the install recorded, so it
finds them wherever the install wrote them (see the `workspace` profile
fields). The `plans/` directory is never removed. Here an install whose
folder no longer exists (a deleted project) still counts as using the stores,
unlike for the shared folders below, and the uninstall says so (see below).

Prompts for confirmation unless
`--yes` is supplied. When no prompt is possible — `--format json` (prompt
text would corrupt the single JSON document) or a non-interactive shell (no
TTY) — the command refuses up front with a structured
`uninstall.confirmation_required` error (exit 1) unless `--yes` is supplied.
If a selected harness is not installed, the command succeeds (exit 0) and, in
plain output, prints `NAME is not installed; nothing to remove.`, where `NAME`
is the harness id.

The uninstall stops before it removes anything when a link leads a tool's
folder in your home directory out of it, such as `~/work/tool` with `~/work`
linked to another drive. On Windows a junction counts as a link. In an
interactive run the command does not ask for confirmation first. A run that
cannot ask (JSON output, or no terminal) still stops first and asks for
`--yes`; the link error shows once you pass it. The error contains `uninstall
refused: target path crosses a link`, names the link and the folder it
leads to, and says what to do; the command exits 1. Make the link lead to a
folder inside your home directory, or replace it with the folder itself, and
run the uninstall again. A folder you spell as a path outside your home
directory is followed.

The shared data stores under `.apothem/` at the install root (`memory/`,
`contexts/`, `learning/`) stay while another installed harness at the same
root still uses them. When the harness you remove is the last one at that
root, the command copies each store into the Apothem backup root
(`~/.apothem/backups/`) first, then removes it with everything in it.
Anything you keep in `plans/` is never removed.

When the only installs that keep the stores sit in folders that no longer
exist, the command keeps the stores and prints a `Warning:` line that names
one such install and the steps that release it. An uninstall in an empty
recreated folder finds nothing installed, so the steps install the tool there
again first, with the same `--profile` that install used. The stores sit
outside that folder, so that install's profile put them where they are. An
install without it writes stores of its own, and the uninstall after it leaves
these with no install that uses them. Apothem does not record which profile
an install used, so the warning prints `--profile <the profile it used>` for
you to fill in. For a tool installed in a project, the steps are:

```bash
mkdir -p /path/to/old-project
apothem install --harness cursor --project /path/to/old-project --profile /path/to/that-profile.yaml
apothem uninstall --harness cursor --project /path/to/old-project --yes
```

The warning puts the folder in double quotes on Windows and in single quotes
elsewhere. When those quotes cannot carry the folder, the warning gives the
same steps in words and names the folder as it is. On Windows that happens
when the folder holds `$`, a backquote, `%`, `!`, a straight or curly double
quote or a control character, which a Windows shell would change inside
double quotes, or two backslashes in a row, as at the start of a network
share (`\\server\share`), which Git Bash reads as one. Elsewhere it happens
when the folder holds a straight or curly single quote (a shell can end
single quotes at a curly one too) or a control character.

For a tool installed in your home directory, the warning gives the same steps
in words: the folder it installed into may have come from an environment
variable (`XDG_CONFIG_HOME`, say) that a printed command would not repeat. The
stores go with that uninstall when no other install still uses them. You can
also remove the stores by hand.

## Shared folders in your home directory

Several installs can use one folder in your home directory: the skills folder
(`~/.agents/skills/`, or `~/.codebuddy/skills/`, `~/.kiro/skills/`, or
`~/.trae/skills/`) and `~/.config/apothem/rules/` and
`~/.config/apothem/templates/`. The [install](/docs/cli-reference/install#folders-in-your-home-directory)
page lists which adapter writes which. Apothem records which installs use each folder,
and an uninstall follows one rule: it removes a folder only when no other
Apothem install still uses it.

- Uninstalling one tool keeps the skills while another install still uses
  them, and says so. One tool installed in two projects counts as two installs,
  so uninstalling it from project A keeps the folders while project B still
  uses them. The last uninstall removes them (see the second example below).
- Only what the install's own record lists is removed. An install made before
  the folders were managed has no such record, so uninstalling it removes
  nothing in your home. Files you added to the folders stay, and so does a
  folder that has an Apothem skill's name and that Apothem did not write.
- An install whose project folder no longer exists is ignored, so a deleted
  project does not keep the folders for good. The note names it.
- If the record of an install that could use the folders cannot be read, the
  uninstall stops with an error before it removes anything, and the install
  stays recorded. Repair or move the unreadable record, then run the command
  again. A damaged record of a tool that never writes these folders is ignored.
- When the last use goes, the folders left empty are removed
  too. Each folder is backed up under `~/.apothem/backups/` before it is
  removed.

Each uninstall prints one `Note:` per folder, for example `Note: <harness> -
~/.agents/skills/ was kept: still used by <harness> (/path/to/project)`, or
`was removed: no other Apothem install uses it`. In the `--format json` envelope each
note is a `warnings` entry with `"outcome": "advisory"`,
`"operation": "shared_root"`, and `"role"` set to `retained` or `released`. It
carries `path`, `holders` (the installs that keep the folder), `stale` (ignored
installs), and `kept` and `total` (the recorded entries kept and the entries the
install listed).

An uninstall also prints a `Warning:` line for each thing it left in place on
purpose. Apothem does not remove anything through a symbolic link or a Windows
junction, so a link in a folder it removes stays, and so does a leftover folder
from an earlier release that is reached through a link. Paths kept for the same
link, or for the same reason (not what Apothem wrote, not in the install
record), print as one line with their count. Under a line for kept paths,
each file it kept is listed, the files inside a kept folder included (a kept
folder that holds nothing is listed itself). A file Apothem wrote that it
could not remove is listed under the `✗` line that reports it, not as a kept
file. With `--quiet` these lines print only
when the uninstall does not finish, and then on standard error with the `✗`
line, so the paths its advice is about stay in view. A line that names an
Apothem marker left in a file prints on standard error under `--quiet` even
when the uninstall finishes: a later install keeps that marker, and `verify`
fails until you delete it. In the `--format json`
envelope each such line is one `warnings` entry with `"outcome": "warning"`,
the line's `message`, `count` (how many paths it covers), `paths` (each of
them) and, for kept paths, `files` (each file kept). These warnings do not
stop the uninstall. Three kinds do: files of an install an earlier release
recorded that differ from what this release writes, the files of an
install with no record at all (see
[What an uninstall removes](#what-an-uninstall-removes)), and a file that
holds two different blocks between Apothem's markers (see
[An uninstall that did not finish](#an-uninstall-that-did-not-finish)).

Apothem's own files reached through a link are different: most tools still
load them, so the uninstall is not finished. (OpenClaw no longer loads its
rules file once the uninstall has taken Apothem's path out of its hook entry,
so for OpenClaw the `✗` line says so only while it still does; see
[OpenClaw](/docs/harnesses/open-claw#uninstalling).) Say `~/.claude/rules` is a
junction to a dotfiles folder that still holds the rules Apothem wrote: the
command prints `✗ <harness> uninstall did not finish:` with the link and the
number of paths it left, keeps the install recorded, and exits `2`. Replace
the link with a real folder that holds the same files, then run the command
again. For an install whose record lists the files it wrote, a linked folder
that holds only your own files, or Apothem files you have edited, does not
stop the uninstall: the link stays with a warning and the uninstall finishes.
For an install an earlier release recorded, any file behind the link at a
name this release writes stops the uninstall, edited or not, because nothing
tells it apart from what that release wrote. Replace the link with a real
folder that holds the same files, then follow the steps for such an install
above: copy any file you edited, fix any file a warning names for an Apothem
marker, run `apothem update`, then uninstall again.

When a removal step reports an error (an installed file whose path leads out
of your home folder, say), the command prints `✗ <harness> uninstall did not
finish: <reason>` instead of `Uninstalled`, once per reason with the number of
paths it applies to. The install stays recorded, so running the command again
removes what the first run left. The retention notes are not printed, because
the folders they describe were not released. In JSON output the harness gets a
`results` row with `"outcome": "error"` and `"operation": "uninstall"`,
followed by one row for each failed step. A step's row lists the files it
kept as `files` and the files Apothem wrote that it could not remove as
`stuck`. The envelope's `status` is
`"partial"` and the exit code `2` when the uninstall removed files before the
step failed, or when another harness was removed; otherwise `status` is
`"error"` and the exit code `1`. The top-level `error` stays `null`: the
reasons are in `results`. An uninstall that stops with an exception (a backup
that cannot be written, say) prints `✗ <harness> uninstall stopped after
removing files:` (or `failed:` when it removed nothing) with the message, and
gets a `results` row with its message, followed by one row for each step that
failed before it. It exits `2` with `status` `"partial"` when it removed files
first, otherwise `1`. A refused uninstall (a link that leads the folder out of
your home directory, say) removes nothing and exits `1`.

### An uninstall that did not finish

When an uninstall does not finish, it appends an `uninstall-incomplete` record
to the install ledger instead of an `uninstall` record. That happens when a
step failed, when it stopped with an exception, when Apothem's own files stay
behind a link, when a file holds two different blocks between Apothem's
markers (see below), when files of an install an earlier release recorded
differ from what this release writes, and when the install has no record. The
last four exit `2` with `status` `"partial"` even when nothing was removed,
including a second run before you fix what they name. The last two finish only after
`apothem update` (see
[What an uninstall removes](#what-an-uninstall-removes)). The
install stays recorded, so `apothem status`, `verify` and
`rollback` still see it, and the harness reads as installed while something
the install wrote is still there as it wrote it (see below), so running
`uninstall` again finishes the job. An install with no record has none to
keep: only its files on disk make the harness read as installed, and
`rollback` has nothing to roll back.
An `install`, `update`, `rollback` or finished `uninstall` of that
harness at that location replaces the state, and so does removing the
remaining files by hand: with none of Apothem's files left as it wrote them
and nothing left in its `.apothem` folder, the harness reads as not
installed, whatever else is in the folder. The first
command that checks whether the harness is installed (`status`, `verify`,
`uninstall`) then appends an `uninstall` record that closes the install. After
an uninstall that finished, though, no record lists the files an install
wrote, so there only an install, an update or an uninstall that finishes
replaces the state.
`backups prune` keeps the record, and the backups it references, while the
install it belongs to is kept. After an uninstall that finished, it keeps the
record together with that uninstall's record, so running the uninstall again
still works the same way.

What still counts: a whole file the install wrote, while it is unchanged (for
an install an earlier release recorded, while it is there); anything in the
folders Apothem installs into under `.apothem`; and a file where Apothem keeps
a managed block beside your own text, while the block is still in it,
whatever you have written around it. Those files are `CLAUDE.md`, the profile
document the shared profile is projected into, the rules file in each
OpenClaw workspace, and `AGENTS.md` and the other instruction files the
install adds a block to.

A managed block runs from a `<!-- BEGIN APOTHEM MANAGED BLOCK -->` marker to
the next `<!-- END APOTHEM MANAGED BLOCK -->` marker, each on a line of its own;
Apothem reads a marker only that way and outside code, as a Markdown viewer
would: a fenced code block (closed by a fence of the same character, at least
as long, with nothing after it) or a block indented four spaces. So a marker
you quote in a sentence or a code example is your text. A fence in Apothem's own
block does not hide its END marker, a fence you leave open anywhere is read
as text, and a byte order mark at the start of the file (as some Windows
editors save it) does not hide a marker on the first line. If the END marker is
gone, nothing shows where Apothem's text stops and yours starts, so the
uninstall leaves the file as it is, names it in a warning and finishes; so
does a retry after an uninstall that did not finish. If a BEGIN marker of
yours is left with no END after it once Apothem's block is out, the uninstall
names that file too. Delete such a BEGIN marker, or the rest of the block, by
hand, keeping your own lines. An `install` or `update` keeps the text after it
as it is, writes Apothem's block apart from it and names the file, and
`verify` fails until the marker is gone (see
[A file has an Apothem BEGIN marker with no END marker](/docs/install/troubleshooting#a-file-has-an-apothem-begin-marker-with-no-end-marker)).

A file that holds two different blocks between the markers (a marker pair you
quote outside a code block, or a block you pasted in a second time) is left as
it is and named, and the uninstall stays unfinished until you remove or
reword the marker lines you added, or move them inside a code block. Do not
delete Apothem's block instead: the next uninstall would then take out the one
block left, your own. Fix such a file before you run `apothem update`, too: an
update writes over the first whole block in the file, which can be yours.

When the uninstall's next step is to run `apothem update` and a warning names
a file for an Apothem marker (in the `--format json` envelope, its `detail`
has `marker_left`), the `✗` line, and the warning of each path it keeps for
an earlier release or for a missing record, tell you to fix that file first,
with the advice for its kind of marker.

If the ledger cannot take the `uninstall-incomplete` record (a full disk,
say), the ledger stays as it was, and a `Warning:` line names the ledger and
the folders of the backups the uninstall took: no record keeps those backups
from `backups prune`, so copy any you need. With no record of that unfinished
pass, running the command again may find the harness not installed and
remove nothing; then remove the files the `✗` and `Warning:` lines listed by
hand. While the harness still reads as installed, running the command again
works as before: against the install record, or, after an uninstall that
finished with no install recorded since, the same way as that pass (see
[What an uninstall removes](#what-an-uninstall-removes)). When the
`uninstall` record of a finished uninstall cannot be saved to
disk, the uninstall removes it from the ledger again and ends as unfinished.
It finishes, with the same kind of warning, when the ledger still ends in a
finished uninstall: the record stayed in the ledger all the same, or the
uninstall followed one that finished. An interrupt (`Ctrl+C`) after the
record is saved leaves the uninstall finished.

If a folder stays because of an install you cannot find, the note names it.
When the project folder was deleted, the install is ignored and the folder goes
with the next uninstall. When the project exists but you removed the Apothem
block from its rules file by hand, `uninstall` reports the harness as not
installed and does not release its claim; run `install` for that harness and
project, then `uninstall`, to release it. `apothem verify` shows whether a
folder is still complete.

A `--harness all` removal is deliberately exhaustive: it covers every
registered harness, including any the profile's `exclude_harnesses` skips
during install — cleanup reaches state a previously broader install may have
left behind. Harnesses that were never installed get the same notice.

The continuous-form alias `apothem uninstalling` (also accepted as
`apothem Uninstalling`) resolves to the same handler.

## Options

| Option | Description |
|---|---|
| `--harness NAME` | Harness adapter to remove, or `all` for the registry-wide set (required). |
| `--yes` | Skip confirmation prompt. |
| `--project PATH` | Project root for project-scope harnesses. |
| `--quiet`, `-q` | Suppress informational output; only errors are emitted. An uninstall that does not finish still prints its `Warning:` lines, which list what it kept, on standard error, and any uninstall prints there a `Warning:` line that names an Apothem marker left in a file. |
| `--verbose`, `-v` | Accepted for consistency with other commands; this command prints no extra output. |
| `--format plain\|json` | Output format (default: `plain`). |
| `--json` | Shorthand for `--format json`. |
| `--no-color` | Disable ANSI color codes in output. |
| `-h`, `--help` | Show help and exit. |

## JSON output

When the adapter is installed and successfully removed:

```json
{
  "schema_version": 1,
  "status": "success",
  "command": "uninstall",
  "action": "uninstalled",
  "harness": "claude-code",
  "profile_path": null,
  "project": null,
  "files_written": [],
  "results": [
    {
      "harness": "claude-code",
      "outcome": "updated",
      "operation": "uninstall",
      "path": "C:\\Users\\Example\\.claude\\settings.json",
      "message": "managed files removed"
    }
  ],
  "warnings": [],
  "error": null,
  "output_path": "C:\\Users\\Example\\.claude\\settings.json"
}
```

When the adapter was not installed, the command exits `0`. In JSON output the
envelope has `"status": "success"` and `"action": "uninstalled"`, and the results
row has `"outcome": "skipped"` with the message `"not installed; no files
removed"`. The `status` field is never `"not_installed"`.

A result refused at a link names the link in `detail.symlink` and the folder
it leads to in `detail.leads_to`, as in
[`apothem install`](/docs/cli-reference/install#json-output).

## Examples

```bash
apothem uninstall --harness claude-code
apothem uninstall --harness claude-code --yes
apothem uninstall --harness cursor --project . --yes
apothem uninstall --harness all --project . --yes
apothem uninstalling --harness cursor --project . --yes   # continuous-form alias
```

A shared skills folder stays until the last install that uses it goes:

```bash
apothem install --harness codex
apothem install --harness cursor --project A
apothem uninstall --harness codex --yes                  # keeps ~/.agents/skills/, the cursor install uses it
apothem uninstall --harness cursor --project A --yes     # removes it: no install uses it now
```

## Exit codes

| Code | Meaning |
|---|---|
| 0 | Adapter uninstalled, or was not installed |
| 1 | Harness not found, confirmation declined or unavailable (non-interactive or JSON mode without `--yes`), or nothing was removed because each installed harness failed before removing anything |
| 2 | Partial removal — an uninstall failed or stopped after removing files, at least one harness was removed and another failed, an uninstall left Apothem's own files in place because a link leads to them, a file holds two different blocks between Apothem's markers, files of an install an earlier release recorded differ from what this release writes, or an install has no record to show which files Apothem wrote |
| 64 | Usage error: an unknown option or command, or a missing or invalid option value. Under `--json` the error is a JSON envelope with code `cli.usage`. |
