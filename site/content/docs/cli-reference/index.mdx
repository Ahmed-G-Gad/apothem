The `apothem` command-line interface manages harness adapter configurations
from the shared profile. Each page below documents one subcommand: its
synopsis, options, behavior, and exit codes.

Each of `install`, `update`, and `uninstall` also accepts a continuous-form
alias (`installing`, `updating`, `uninstalling`) that is identical in flags and
behavior to the base command. Updating and uninstalling through the install
channels — the Claude Code plugin, `npx`, and the one-shot installer
scripts — are documented in the [Updating](/docs/install/updating) and
[Uninstalling](/docs/install/uninstalling) install guides, not by the aliases
themselves.

## Commands

| Command | Description |
|---------|-------------|
| [quickstart](/docs/cli-reference/quickstart) | Guided first run: ensure a profile, preview the writes, then install. |
| [install](/docs/cli-reference/install) | Install a harness adapter configuration from the shared profile (alias: `installing`). |
| [update](/docs/cli-reference/update) | Re-install a harness adapter configuration from the current shared profile (alias: `updating`). |
| [uninstall](/docs/cli-reference/uninstall) | Remove a harness adapter configuration (alias: `uninstalling`). |
| [rollback](/docs/cli-reference/rollback) | Restore a harness to the state before its recorded install. |
| [verify](/docs/cli-reference/verify) | Verify a harness adapter installation. |
| [status](/docs/cli-reference/status) | Report install, verify, and drift state for every registered harness. |
| [diff](/docs/cli-reference/diff) | Preview the pending configuration changes for a single harness. |
| [harnesses](/docs/cli-reference/harnesses) | List and inspect registered harness adapters. |
| [profile](/docs/cli-reference/profile) | Manage the shared Apothem profile. |
| [migrate-workspace](/docs/cli-reference/migrate-workspace) | Migrate a legacy per-harness workspace into the shared `.apothem` layout. |
| [doctor](/docs/cli-reference/doctor) | Run system diagnostics for the Apothem installation. |
| [completion](/docs/cli-reference/completion) | Emit a sourceable shell-completion script (bash, zsh, fish, powershell). |

## JSON output contract

Every command accepts `--json` (shorthand for `--format json`) and then writes
exactly one JSON document to stdout. Each document starts with a top-level
`schema_version` key, an integer that is `1` today:

```json
{"schema_version": 1, "status": "success", "command": "verify", "...": "..."}
```

- **Stability.** Within one `schema_version`, changes are additive: a new key
  can appear, but no key is renamed or removed and no value changes type.
  Anything else increases `schema_version`.
- **Versioned artifacts.** `profile show --json` emits the profile itself, so
  its `schema_version` is the profile schema version (also `1` today).
- **One exception.** `harnesses list --json` emits a JSON array (one object
  per harness), as it always has, so it has no top-level key to carry the
  version. Wrapping it in an object would break existing parsers; until a
  version bump does that, treat its shape as `schema_version` `1`.
- **Errors.** Expected failures use the same document shape with
  `"status": "error"` and an `error` object carrying `code`, `field`,
  `reason`, and `fix`.
