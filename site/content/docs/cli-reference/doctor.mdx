Check the health of what is installed. Where
[`apothem verify`](/docs/cli-reference/verify) checks the harnesses you select,
`doctor` checks every installed harness and the shared profile in one pass.

## Synopsis

```
apothem doctor [--project PATH] [--quiet|-q] [--verbose|-v]
               [--format plain|json] [--json] [--no-color]
```

## What it checks

- **Shared profile.** A present profile is validated against the packaged
  schema; a malformed one fails with its diagnostic code. A missing profile is
  reported, not failed (`install` creates one).
- **Installed harnesses only.** A harness that is not installed is reported as
  `not_installed` and is not a failure, so a machine with one healthy harness
  passes. Project-scope harnesses are checked when `--project` names their root;
  without it they are reported as `needs_project`. A file with marker lines
  Apothem cannot tell from your text counts as an install while the install
  ledger cannot be read, so such a harness is checked, and its
  `ledger.unreadable` check names the damaged ledger, rather than being
  reported as `not_installed`.
- **Verify.** Each installed harness must pass the same check as
  [`verify`](/docs/cli-reference/verify). When a file holds an Apothem BEGIN
  marker with no END marker, the failed check is `harness.stray_begin`, and its
  fix names each such file and says to delete the marker line and the old
  Apothem text below it, and not to add the END marker back with a line of
  yours between the two markers, which the next run would replace or take out,
  nor at all once an install or update has written Apothem's block apart from
  it, which would leave two Apothem blocks: an update alone does not clear it
  (see
  [Troubleshooting](/docs/install/troubleshooting#a-file-has-an-apothem-begin-marker-with-no-end-marker)).
  A file that holds two or more whole blocks between Apothem's markers, or
  whose marker pairs Apothem cannot tell from your text, such as its block
  inside a code block of yours, fails the same check: its message says the
  file holds "Apothem markers to fix by hand", and its fix names each block
  by its lines (see
  [A file holds two blocks between Apothem's markers](/docs/install/troubleshooting#a-file-holds-two-blocks-between-apothems-markers)),
  or each marker pair, where its lines read and how to fix it, along with each
  BEGIN marker that starts no marker pair (see
  [Apothem cannot tell its block from your text](/docs/install/troubleshooting#apothem-cannot-tell-its-block-from-your-text)).
- **Hook runtime.** For each verified harness, and for each one that such a
  marker fails, doctor reads the files that the
  install it checks wrote: the install in the harness's own folder (a
  `CODEX_HOME` set where doctor runs is that folder), or, for a project-scope
  harness, in the `--project` folder. An install in another folder, such as a
  `CODEX_HOME` doctor is not pointed at or a project you have since deleted,
  is not used in its place. doctor finds the hook commands Apothem registered
  in the JSON files among them, and starts each interpreter and hook script
  once with a no-op payload (the registered arguments plus `--help`, `{}` on
  stdin, a scratch working directory, and `PYTHONPATH` removed). Nothing is
  written. A missing interpreter, a missing script, or a crash at import time
  fails the check. When a hook has a separate command line for each system,
  doctor starts the one the tool runs on this machine: the `powershell` line
  on Windows and the `bash` line on macOS and Linux. Doctor starts the program
  itself, without a shell, so on Windows it leaves out the `&` that a line
  written for PowerShell starts with. A hook registered outside a JSON file is
  not started and is not counted in `N started`. The install record is found
  under any spelling of that folder, such as another letter case on Windows.
  When the install ledger has no record for that folder, the check is not
  run: the report shows `not checked`, its last line names the harnesses whose
  hook commands were not checked instead of `All checks passed`, and the JSON
  output carries a `hook.unchecked` check.
- **Project hook files.** Anyone who can commit to a project can change its
  files, so for a project-scope harness doctor starts a hook command only when
  everything it runs is known. It reads the install record of the project
  that `--project` names, takes hook commands only from the places the tool
  reads them, and starts a command only when its interpreter is the one that
  install recorded (unless it is inside the project, where others can change
  it) or the Python that Apothem itself runs under, the options
  before the script run no code (such as `-E` and `-s`), the script is the
  hook script that install wrote, in a folder whose files still match the
  SHA-256 checksums the install recorded and that holds no other Python file
  and no link, and the arguments after it are the ones Apothem writes. Doctor
  then starts those known paths rather than the text it read, and it looks up
  no other path a hook command names. A recorded interpreter or hook script
  that is gone fails the check without anything being started. Doctor starts
  no other project hook command, and reports each one, with the reason, as
  `hook.unchecked` (info, not a failure, marked `!` in the plain output).
  Hooks installed by an earlier release, which recorded no interpreter or no
  checksums, stay unchecked until you run `update` with the same options you
  installed with.

Every failed check names a fix. A fix that runs `update` ends with the
command, after a colon. For a project-scope harness the command names
`--project` with the folder quoted for the shell, as
[`uninstall`](/docs/cli-reference/uninstall) quotes its steps. When those
quotes cannot carry the folder, the fix gives `--project` in words and ends
with the folder as it is. Exits 0 when no check fails and 1 otherwise.

## JSON output

`--json` keeps the earlier fields (`version`, `python`, `platform`,
`profile_path`, `profile_exists`, `profile_valid`, `harnesses`, `all_ok`,
and `profile_error` when the profile is invalid) and adds:

- `profile_error_code` — the profile diagnostic code, when the profile is
  invalid.
- `project` — the resolved `--project` root, or `null`.
- `harnesses[].status` — `ok`, `not_installed`, `needs_project`,
  `verify_failed`, `hook_failed`, or `error`; plus `verified` and `hooks`
  (`{"probed": N, "failed": [...]}`, or `null` when the checked folder has no
  install record or the install ledger cannot be read).
- `checks` — one record per check: `code` (for example `harness.verify_failed`,
  `harness.stray_begin`, `hook.start_failed`, `hook.unchecked`,
  `ledger.unreadable`, or a `profile.*` code), `status`
  (`pass`, `fail`, or `info`), `harness`, `message`, and `fix`.

```json
{
  "schema_version": 1,
  "all_ok": false,
  "checks": [
    {
      "code": "hook.start_failed",
      "status": "fail",
      "harness": "claude-code",
      "message": "claude-code: a registered hook command cannot start: …",
      "fix": "Check that the interpreter in the hook command exists and runs, then …"
    }
  ]
}
```

## Options

| Option | Description |
|---|---|
| `--project PATH` | Project root for project-scope harnesses; without it they are reported as `needs_project`. |
| `--quiet`, `-q` | Suppress informational output; only errors are emitted. |
| `--verbose`, `-v` | Accepted for consistency with other commands; this command prints no extra output. |
| `--format plain\|json` | Output format (default: `plain`). |
| `--json` | Shorthand for `--format json`. |
| `--no-color` | Disable ANSI color codes in output. |
| `-h`, `--help` | Show help and exit. |

## Examples

```bash
apothem doctor
apothem doctor --project .
apothem doctor --json
```

The default `plain` format prints human-readable diagnostics; `--json`
(equivalent to `--format json`) emits a machine-readable document on stdout,
suitable for piping into other tooling.

## Exit codes

| Code | Meaning |
|---|---|
| 0 | All checks passed (also when no harness is installed yet) |
| 1 | An installed harness does not verify, a registered hook command cannot start, an adapter could not be loaded or probed, or a present profile failed schema validation |
| 64 | Usage error: an unknown option or command, or a missing or invalid option value. Under `--json` the error is a JSON envelope with code `cli.usage`. |
