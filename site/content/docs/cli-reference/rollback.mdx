Restore a harness to the state before its recorded install.

## Synopsis

```
apothem rollback --harness NAME|all [--install-id ULID | --last] [--yes]
                 [--project PATH]
                 [--quiet|-q] [--verbose|-v]
                 [--format plain|json] [--json] [--no-color]
```

`rollback` returns each selected harness to the state it was in before the
recorded install pass — by default the newest install still in place, or the
one named by `--install-id`. A second `rollback` therefore undoes the install
before the one the first undid. An `--install-id` naming an install that a
rollback or uninstall already reversed is refused with
`rollback.already_reversed` (exit 1), and nothing changes. Working through
that install's ledger record, newest change first, it:

- restores every file and directory the install overwrote from the backup the
  install captured, at its recorded path (a directory the install replaced is
  restored exactly, without the files the install added to it);
- removes every file and directory the install created, as long as it still
  has the content that install wrote: a file you made at that path since, or
  one you edited, stays with a `Warning:` line (a `warnings` entry under `--json`), and so does a folder holding
  it. The line lists each file it kept, the files inside a kept folder
  included, and the `warnings` entry lists them as `files`. An install
  recorded by an earlier release does not say what it wrote,
  so what it created stays. It also puts back any
  legacy-layout path the install swept away. A path the current release no
  longer sweeps (a folder that may hold your own files) is restored only where
  files are missing: every file there now is kept, and the output names the
  backup used. A file it cannot write is listed for you to copy by hand, and
  the rollback then exits 2 (partial) when it wrote any other file. A path
  that is now a link (a symlink or a Windows junction), or a file where the
  backup has a folder or the other way round, is never written through.
  Nothing is restored there, and nothing is restored either when the path's
  backup is gone. The rollback still exits 0 and prints a `Warning:` line (a
  `warnings` entry under `--json`) that names the backup to copy from by
  hand. Rollback reaches that install only while its record is among the
  newest 10 kept (below). `apothem backups prune --keep N` prunes to `N` once;
  the next install, update, uninstall or rollback prunes to 10 again. The
  backup set itself stays even after the record goes, so copying the files
  out of it by hand is the dependable way back;
- removes the shared data stores (`memory`, `contexts`, `learning`) the
  install created, unless another installed harness still uses them;
- removes the directories the install created, once they are empty.

A file or folder in your home directory that other installs also use (a skills
folder, or `~/.config/apothem/`) is treated like the shared data stores:
rollback keeps it while another install still lists it, and restores or removes
it only for the last install that uses it. A folder this install found already
in place (a second tool installed after the first) goes with the last install
that uses it when an install that has since let go of it created it, so rolling
back every tool leaves nothing behind. When an install's record that could use
the folder cannot be read, rollback stops with an error before it changes
anything and writes no `rollback` record; repair the record and run it again.

A rollback also stops before it changes anything, and writes no `rollback`
record, when a link leads the tool's folder out of your home directory: a
`CODEX_HOME` or `XDG_CONFIG_HOME` spelled inside your home directory, such as
`~/work/tool`, where `~/work` became a link to another drive after the
install. On Windows a junction counts as a link. The error reads `rollback
refused: target path crosses a symlink` and names the link, and the command
exits 1 without asking for confirmation first. Make the link lead to a folder inside your home directory, or replace
it with the folder itself, and run the rollback again. A folder you spell as a
path outside your home directory is followed.

Everything rollback removes or replaces is first copied into the Apothem backup
root (`~/.apothem/backups/`), so a rollback can itself be undone by hand.
Rollback then appends a `rollback` record to the harness ledger. Rolling back an
older install restores or removes only the targets that older install recorded,
and drops every install after it from the ledger's active installs at the same
root. Files a later install added outside those targets stay in place.

The ledger keeps the newest 10 install records per install root (with the
backups they reference); an older install can no longer be rolled back by id
and reports `rollback.no_record`. [`apothem backups prune`](/docs/cli-reference/backups)
lowers that bound on demand, and never removes the backup the latest install
restores from.

Records written by an Apothem release before this behaviour was added do not
list which files the install created; rolling back such a record restores the
overwritten files only.

Confirmation is prompted per harness unless `--yes` is supplied. When no
prompt is possible — `--format json` (prompt text would corrupt the single
JSON document) or a non-interactive shell (no TTY) — the command refuses up
front with a structured `rollback.confirmation_required` error (exit 1)
unless `--yes` is supplied. `--install-id` and `--last` select the install
pass and are mutually exclusive.

A `--harness all` rollback is deliberately exhaustive: it covers every
registered harness, including any the profile's `exclude_harnesses` skips
during install — restoring pre-install state is a cleanup operation, so it
reaches records a previously broader install may have left. A harness with no
recorded install fails as an `"outcome": "error"` row in `results` (see JSON
output), and the run continues with the remaining harnesses. The command then
exits 1 when nothing was rolled back, or 2 (partial result) when at least one
target was rolled back and a failure was also recorded.

## Options

| Option | Description |
|---|---|
| `--harness NAME` | Harness adapter to roll back, or `all` for the registry-wide set (required). |
| `--install-id ULID` | Roll back the named install pass, if it is still in place. Defaults to the newest install still in place. |
| `--last` | Roll back the newest install still in place (the default; the explicit form). Mutually exclusive with `--install-id`. |
| `--yes` | Skip the per-harness confirmation prompt. |
| `--project PATH` | Project root for project-scope harnesses. Required when the selected set includes project-scope adapters. |
| `--quiet`, `-q` | Suppress informational output; only errors are emitted. |
| `--verbose`, `-v` | Emit additional diagnostic output. |
| `--format plain\|json` | Output format (default: `plain`). |
| `--json` | Shorthand for `--format json`. |
| `--no-color` | Disable ANSI color codes in output. |
| `-h`, `--help` | Show help and exit. |

## JSON output

The example is the envelope for a single named harness. Under `--harness all`,
`harness` is `all`, `output_path` is `null`, and `results` carries the rows of
every selected harness.

```json
{
  "schema_version": 1,
  "status": "success",
  "command": "rollback",
  "action": "rolled_back",
  "harness": "claude-code",
  "profile_path": null,
  "project": null,
  "files_written": [],
  "results": [],
  "warnings": [],
  "error": null,
  "output_path": "C:\\Users\\Example\\.claude\\settings.json"
}
```

Each restored or removed target appears in `results` with
`"operation": "rollback"` and an `outcome` of `created` or `updated` (and in
`files_written`); the `message` says whether the path was restored or removed.
A failed restore (for example, a backup that was deleted) is
`"outcome": "error"`. An install that recorded no changes is reported with
`"outcome": "skipped"`. A swept path where nothing was restored (it is now a
link, a file stands where the backup has a folder or the other way round, or
its backup is gone) is a `skipped` row in `results` and also an entry in
`warnings`, and the rollback still exits 0:

```json
{
  "harness": "claude-code",
  "outcome": "advisory",
  "operation": "rollback",
  "path": "C:\\Users\\Example\\.claude\\commands",
  "message": "left in place: C:\\Users\\Example\\.claude\\commands is now a link, so nothing was restored there; copy what you need from C:\\Users\\Example\\.apothem\\backups\\20261001T000000Z\\claude_code\\.claude\\commands"
}
```

When no matching install record exists for a single
named harness, the command reports a `rollback.no_record` error with
`"status": "error"`, and an `--install-id` of an install already rolled back
or uninstalled reports `rollback.already_reversed`. Once the ledger has
trimmed that record (see above), such an id reports `rollback.no_record`
instead. Under `--harness all`, a harness with no matching record
is an `"outcome": "error"` row in `results` instead.

## Examples

```bash
apothem rollback --harness claude-code --last
apothem rollback --harness claude-code --install-id 01J9Z… --yes
apothem rollback --harness cursor --project . --last --json
```

## Exit codes

| Code | Meaning |
|---|---|
| 0 | Rolled back successfully, or nothing to roll back (the install recorded no changes); also when a swept path was left in place with a `Warning:` line (a `warnings` entry under `--json`) |
| 1 | Expected error — no install record, conflicting selectors, unknown harness, missing project root, or confirmation declined or unavailable (non-interactive or JSON mode without `--yes`) |
| 2 | Partial result — at least one target was rolled back and a failure was also recorded (a failed restore or, under `--harness all`, a harness with no install record) |
| 64 | Usage error: an unknown option or command, or a missing or invalid option value. Under `--json` the error is a JSON envelope with code `cli.usage`. |
