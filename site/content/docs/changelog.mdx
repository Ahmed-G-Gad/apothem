# Changelog — Apothem

All notable changes to this project are documented in this file.

This changelog follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/)
and the project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Data loss in earlier releases: recover your files

- **Releases 1.0.1 to 1.5.0 deleted folders that hold your own files.** Every
  `apothem install` and `apothem update` of these adapters removed the whole
  folder, with everything you had placed in it:
  - Claude Code: `~/.claude/commands/` (your slash commands), `~/.claude/hooks/`
    (your hook scripts; a `settings.json` entry that runs one now points at
    nothing), and `scripts/`, `templates/`, `tools/`, `lib/`, `docs/`,
    `config/`, `src/`, `tests/`, `schemas/`, `conformity/`, `packaging/`,
    `mcp/`, `examples/`, `assets/`, `site/` and `public/` under `~/.claude/`,
    plus the `AGENTS.md` files in `~/.claude/{agents,rules,skills,statuslines,output-styles}/`.
  - Codex: `~/.codex/rules/` (Codex's own `.rules` execution policies) and
    `~/.codex/commands/`, plus `~/.config/apothem/hooks/` and
    `~/.agents/skills/AGENTS.md`.
  - Gemini CLI: a project's own `skills/AGENTS.md`.
  - Hermes: `~/.hermes/cli-config.yaml` and `~/.hermes/profile.yaml`. Open-Claw:
    `~/.open-claw/config.yaml`.
  - Antigravity: `~/.gemini/antigravity/`, the Antigravity App's own data folder
    (MCP sign-in tokens, session transcripts, skills).

  No release ever installed a file into any of these places, so this release
  stops removing them. It keeps sweeping only folders in Apothem's own
  namespace that a release wrote into (`apothem/rules/` under the OpenCode,
  Qwen Code, Hermes and Open-Claw folders, and Kimi Code's
  `.kimi-code/.apothem/support/{skills,agents}/`).

  **To recover:** each removed folder was copied first to
  `~/.apothem/backups/<timestamp>/<harness>/`, under its path relative to your
  home, or to the project for a project install (for example
  `claude_code/.claude/commands/`). Releases 1.2.0 to 1.5.0 keep only the newest
  10 backup sets per harness and add one on every install, update, uninstall
  and rollback, so older sets may already be gone; 1.0.x and 1.1.0 kept every
  set. This release never deletes a backup set that holds one of these paths,
  automatically or through `apothem backups prune`.

  1. Copy `~/.apothem/backups/` somewhere else before you run Apothem again.
  2. Copy the files you need from that copy back to their place by hand.
  3. Run `apothem update` afterwards.

  `apothem rollback --install-id ID` is not a recovery step for this: it
  reverses the whole old install, including the files that install wrote or
  changed, such as `settings.json` and `CLAUDE.md`. For the swept folder alone,
  rollback now puts back each missing file and keeps every file that is there.

### Added

- **OpenClaw now loads Apothem's rules.** The Open-Claw install writes
  `apothem/AGENTS.md` into each OpenClaw workspace and lists that path in the
  bundled `bootstrap-extra-files` hook's entry in `openclaw.json`
  (`hooks.internal.entries.bootstrap-extra-files`). The file holds the profile's
  managed block and the pointer to the installed rule index. Because it is named
  `AGENTS.md`, OpenClaw also loads it in cron and sub-agent sessions. The
  workspace's own `AGENTS.md` is never edited.
  - **Workspaces:** the default workspace and each `agents.entries` (or older
    `agents.list`) workspace that exists in the home directory, resolved as
    OpenClaw does: ids normalized, and the entry marked `default: true` or a
    sole entry uses the default workspace.
    One OpenClaw has not created yet is filled by the next `apothem update`
    (`apothem verify` fails until then). One outside the home directory, or
    reached through a link, is skipped with a warning. When a workspace leaves
    the config, the next install or update takes the Apothem block out of the
    file it wrote there.
  - **Hook settings:** left alone, with a warning, when internal hooks are off,
    the hook's entry is off, or `hooks.internal.enabled: true` names no hook
    (naming one would switch the others off).
  - **Size limits:** a rules file that OpenClaw would cut or skip is not written,
    and an earlier copy is taken out. That covers the per-file limit
    (`bootstrapMaxChars`, 20,000 by default) and the room the six workspace
    files and the entry's other extra files leave in the total
    (`bootstrapTotalMaxChars`, 60,000), with each entry's own limits and
    characters counted as OpenClaw counts them. When the file fits no
    workspace, no path is registered.
  - **Upgrading with a commented `openclaw.json`:** Apothem cannot add the hook
    entry to a file with comments or other JSON5 syntax without dropping them.
    If you added the `skills.load.extraDirs` entry by hand, as these docs said
    before, install and update now print the hook entry to add as well;
    `apothem verify` fails until you add it.
  - **Uninstall** removes the managed blocks, the files and folders they leave
    empty, and only the hook entries Apothem added. Apothem's entries in a
    commented `openclaw.json` stop it before anything changes, with an error
    naming what to remove; a rules file behind a link is left in place and the
    uninstall reported unfinished (exit 2). Either way the install record
    stays, so a second uninstall after the hand fix finishes. `apothem verify`
    reports a missing file or registration.

- **The operator-file parsers are fuzzed.** Five Atheris fuzz targets in
  `tests/fuzz/` cover the JSONC / JSON5 config reader, the hook-file merge and
  removal (Kiro, GitHub Copilot, Cursor), the shared-profile loader, the install
  ledger and the frontmatter probe. Each checks invariants, not just crashes:
  the config reader parses whatever `json.loads` accepts to the same value, a
  second install leaves a hook file byte for byte the same and keeps the
  operator's hooks in order, a loaded profile normalizes to itself, and a ledger
  record reads back unchanged. ClusterFuzzLite (`.clusterfuzzlite/`,
  `.github/workflows/fuzzing.yml`) fuzzes each pull request that touches
  `src/apothem/` for five minutes and runs a fifteen-minute batch every day, and
  `tests/fuzz/test_fuzz_seed_replay.py` replays every target's seeds in the
  ordinary test run. The OpenSSF Scorecard Fuzzing check credits the setup.
- **An answer sheet for the OpenSSF Best Practices badge.** The new
  [OpenSSF Best Practices badge](https://apothem.ahmedgad.com/docs/security/openssf-best-practices)
  page answers all 67 passing criteria from bestpractices.dev (Met, N/A or
  Unmet), each with a one-line justification and a link to the file or page
  that shows it, and lists the steps to register the project. The answers
  meet every MUST criterion; the one Unmet SHOULD criterion,
  `crypto_weaknesses`, is explained there, along with the other remaining
  gaps. The CII-Best-Practices row on the Scorecard page links to it.
  CONTRIBUTING.md now states that a pull request adding functionality adds
  tests for it, and that a bug fix adds a regression test.
- **Every docs link with a `#section` is checked against the page it opens.**
  `scripts/dev/check_site_anchor_links.py` reads the English pages and the
  eleven translations, makes each heading's id the way the site does (a Python
  port of github-slugger, `scripts/dev/github_slugger.py`), and fails when a
  link names a heading the page it opens does not have. It also fails a
  translation that records the current English text but has other headings than
  the English page, and a component that links into `/docs` past the link
  localization below. `tests/unit/docs/test_site_anchor_links.py` runs it in the
  `quality` job with Python alone, and `scripts/dev/check_built_docs_links.py`
  repeats the check on the built site in `docs-build`, where it also fails a
  translated page whose link still opens the English page. Before, nothing read
  heading ids until the site was built, and 252 links on translated pages named
  a heading that exists only on the translated copy.
- **The Marketplace publish can use Trusted Publishing.** With the
  repository variable `VSCE_AUTH=oidc`, the VS Code publish job runs
  `vsce publish --oidc`, which exchanges the job's GitHub OIDC token for a
  short-lived Marketplace credential: no stored secret and no Azure setup.
  The publisher adds one Trusted Publishing policy for this repository, the
  publish workflow and the `release` environment. The job first checks that
  the vsce release locked in `tools/vsce` supports the final token
  exchange, and stops with a plain error when it does not. The Entra route
  and the `VSCE_PAT` token stay as alternatives. An unrecognised
  `VSCE_AUTH` value now logs a warning, without echoing the value. The
  release-cycle runbook gains the setup procedure.
- **The weekly convention monitor watches each tool's release channels.**
  OpenCode 2 shipped as the npm package `@opencode/cli`, with its first
  GitHub Release, v2.2.0, on 2026-10-27, and the pins did not record it for a
  week. `scripts/dev/vendor-release-channels.json` now has an entry for every
  harness: its release channels (an npm package and its dist-tag, a GitHub
  repository's latest release or, for a channel with a tag pattern, its
  newest stable release with a matching tag among the newest 100, a PyPI
  project, or an installer address whose redirect is watched), or the reason
  it has none. Each channel records the version last reviewed (the one its
  pin names or, where the pin names none, the one the registry served when
  the channel was recorded), the date, and the phrase of the pin that cites
  it. Each week `scripts/dev/check_vendor_releases.py` asks every registry
  for the current version, and each installer address where it redirects. A
  new major version, a release past a trigger the file names, an installer
  address that redirects somewhere else, or a package, dist-tag, release or
  address that no longer exists files an issue, and so does a check that
  cannot run, with the reason. A newer minor or patch version is listed in
  the run summary and does not fail the check, and a registry that does not
  answer, or whose answer breaks off partway, is reported as unreachable.
  OpenCode has four channels: `opencode-ai` for OpenCode 1, `@opencode/cli`
  for OpenCode 2, the GitHub releases of `anomalyco/opencode`, where a new
  major line shows whatever npm package it ships as, and
  `opencode.ai/install`. Two of them watch the OpenCode decision's second
  signal, OpenCode 1's installer or npm package moving to OpenCode 2: the
  check fails when `opencode-ai`'s `latest` version moves past major version
  1, or when `opencode.ai/install` stops redirecting to the OpenCode 1
  installer script. The decision's first signal, a date to remove OpenCode
  2's translation of OpenCode 1's formats, stays a check by hand.
  Antigravity, Cursor, Kiro, Trae and Windsurf have no release channel a
  script can query, and the file gives the reason for each. The check job
  sends the workflow's `GITHUB_TOKEN` to the GitHub API with read access
  only, and a separate job files the issue. The Claude Code, CodeBuddy,
  Codex, Gemini CLI, Hermes, OpenClaw and Zed pins now cite the vendor page
  that names their package or release repository, and the OpenCode pin
  records where `opencode.ai/install` redirects and how that script picks the
  version it installs.

### Changed

- **A link in a translated docs page keeps the reader in their language.** A
  link such as `/docs/install#choose-a-channel` in the body of a translated page
  now opens the translated copy of the page, at the matching section, when the
  language has one. Before, every such link on a translated page opened the
  English page. A page the language has not translated still opens in English,
  as does a link to a section of a translation whose headings differ from the
  English page. A cross-page `#section` in a translation is the English id, which the
  site maps to the translated heading by position; the internationalization page
  says how.
- **Dependabot checks the vsce packager weekly.** The `tools/vsce` lockfile
  was checked monthly, so a new vsce release waited up to a month after its
  seven-day cooldown before a pull request proposed it. It is now checked
  every Monday, like the website and the pre-commit hooks, because the
  Marketplace publish route depends on the vsce release: Trusted Publishing
  needs vsce 4.1.0 or later.
- **Tool lockfile pull requests test themselves.** A pull request that
  changes `tools/vsce` now packages the VS Code extension and runs the vsce
  release tests, and one that changes `tools/channel-smoke` runs the channel
  smoke, so a Dependabot update to either lockfile is checked before it
  merges. The pull request runs these checks without the full `ci.yml`
  matrix.
- **CI installs pip from a hash-locked file.** Every workflow upgrades pip
  with `--require-hashes` from `scripts/ci/requirements-ci-pip.txt` instead
  of a version pin, so the download is checked against its published hash,
  and Dependabot proposes pip upgrades with their hashes. The same pip,
  26.2.1, still runs in CI; the lock holds it at 26.2 or later, which fixes
  CVE-2026-13346. `check_pip_pin_drift.py` now checks the lock file and the
  workflows' install lines instead of the per-workflow version setting, and
  `pip-audit.yml` audits the lock. The PowerShell steps that install it now
  stop on a failed install.
- **CI installs its Python dependencies from hash-locked files.** The jobs
  that install the project, the test tools or the engine's prerequisites now
  use `--require-hashes` with `scripts/ci/requirements-ci-dev.txt`,
  `requirements-ci-runtime.txt`, `requirements-ci-test.txt` or
  `requirements-ci-prereqs.txt`, and install the package itself with
  `--no-deps -e .`, so every download is checked against its published hash and
  OpenSSF Scorecard counts the installs as pinned. CI therefore tests the
  versions locked on the date written in each file (2026-10-29), not the
  newest release on the day of a run; `python scripts/dev/refresh_ci_locks.py`
  regenerates the locks, and `--check` compares them with a fresh compile.
  `tests/scripts/test_ci_locks_fresh.py` fails when a lock no longer satisfies
  `pyproject.toml`. `pip-audit.yml` still resolves the newest allowed versions
  each week and now audits the locks too, `check_pip_pin_drift.py` fails on
  any other workflow `pip install` that Scorecard counts as unpinned, and
  Dependabot's version updates for `scripts/ci` are limited to the pip lock.
- **The CI tools install from hash-locked files.** `ruff`, `bandit`,
  `pip-audit`, `pip-licenses` and `pre-commit` no longer install as exact
  version pins. Each installs with `--require-hashes` from its own file in
  `scripts/ci/` (`requirements-ci-ruff.txt`, `-bandit.txt`, `-pip-audit.txt`,
  `-pip-licenses.txt` and `-pre-commit.txt`), so every download is checked
  against its published hash and OpenSSF Scorecard counts the installs as
  pinned; only the SLSA generator's release tag and the evals workflow's
  Claude Code CLI install keep Pinned-Dependencies below 10. The tool versions
  are written once, in `scripts/dev/ci_lock_table.py`, and
  `check_pip_pin_drift.py` now fails on any unhashed tool install. The
  pip-audit lock leaves pip out, and `refresh_ci_locks.py` now excludes pip
  from every lock, because a second pip pin would replace the one in
  `requirements-ci-pip.txt` that Dependabot maintains. The pre-commit lock needs
  Python 3.11, which `markdown-lint.yml` already uses. The pip-audit lock is
  compiled for Python 3.11 too: the newest `filelock` that supports 3.10 has
  published advisories that only a release for 3.11 or later fixes, and
  Dependency review and Scorecard read a lock line whatever its environment
  marker says.
- **`pip-audit.yml` audits the new locks with OSV, on Python 3.12.** The weekly
  run, and any pull request that touches a lock, audits the nine locks beside
  the pip lock. Every audit in the workflow now asks the OSV service
  (`pip-audit -s osv`) instead of pip-audit's default PyPI feed, which lists an
  advisory later than GitHub does: on 2026-10-29 a high advisory against
  `virtualenv` 21.14.12, published on 2026-10-23, was in OSV and not in that
  feed. The audits run on one interpreter, so the lines that apply only below
  Python 3.11 are no longer audited by `pip-audit.yml`; Dependabot alerts,
  Dependency review and Scorecard still read them.
- **ruff and mypy each have one version.** ruff is pinned to 0.17.1 where
  `pyproject.toml` named a floor, and the `ruff-pre-commit` hook, the ruff lock
  and the dev lock carry the same version. mypy is pinned to 2.4.0, the version
  in the dev lock, and the mypy pre-commit hook moves from 2.1.0 to it. The hook
  also pins the dev lock's versions of click, rich, PyYAML, jsonschema and their
  type stubs, and no longer passes `--ignore-missing-imports`, so it runs mypy
  with the same settings as CI. `tests/scripts/test_ci_tool_locks.py` fails
  when any of these differ, so a Dependabot security pull request for either
  tool is adapted by hand. The tree needs no source change at either version.
  The `ruff-format` pre-commit hook now also formats Markdown files, because
  ruff 0.17 formats the Python code blocks in them and CI's
  `ruff format --check .` checks them.
- **The CI locks wait a week.** All nine locks now wait out a seven-day
  cooldown that matches Dependabot's: `refresh_ci_locks.py` locks the files
  uploaded before the lock date less seven days, `--cooldown-days N` changes
  that, and `--cooldown-days 0` locks every file uploaded before 00:00 UTC of
  the lock date, for an urgent security fix. Dependabot's cooldown does not
  apply to its security updates, so a row of `scripts/dev/ci_lock_table.py` can
  lift it for one package with `cooldown_exceptions`: the pre-commit lock takes
  `virtualenv` 21.14.13, which fixes GHSA-cx6f-vjhg-g3cc (high) but was uploaded
  after the cutoff. The refresh refuses an exception once the cutoff has
  reached its timestamp. Each lock records its lock date, cooldown, cutoff and
  exceptions, and `--check` reproduces them. The locks are at lock date
  2026-10-29 with cutoff 2026-10-22.
- **The weekly vendor URL check names the hosts it cannot check.**
  CodeBuddy's documentation host answers `0.0.0.1` to name lookups from the
  United States, where GitHub's hosted runners are, so the check never
  reached the twelve CodeBuddy pages the pins cite. It waited out three
  30-second timeouts on each, about 20 of the job's 30 minutes, and counted
  them as unreachable. A host whose name resolves only to an address no
  server can hold, anything in `0.0.0.0/8` or `::`, is now reported as
  `unroutable` and gets no request. Like an unreachable URL, it does not fail
  the check. Each run carries a warning naming such a host, and the issue the
  monitor files lists its URLs to check by hand.

### Fixed

- **A deleted project no longer lets an install overwrite your own skill.**
  After you deleted a project (or a `CODEX_HOME`) that had an Apothem install,
  a skill folder you then put in a shared skills folder (`~/.agents/skills/`,
  `~/.codebuddy/skills/`, `~/.kiro/skills/` or `~/.trae/skills/`) under an
  Apothem skill's name was overwritten by the next install (a backup was
  kept). The install now skips it with the `skill_conflict` warning. A project
  folder that still exists but holds none of the files its install recorded
  there with Apothem's content in them (a re-cloned project that keeps only
  its own instruction file, say) counts as deleted too, and so does one on a
  drive or network share that does not answer. The deleted install still
  counts while the skill folder holds exactly the files it recorded,
  unchanged, so an update still refreshes a folder Apothem wrote. A folder
  that already holds what this release writes is kept as it is. Otherwise,
  when only deleted installs list a skill folder, or only an earlier install
  in the same folder did, the install skips it and leaves it untouched unless
  it holds exactly the files one of them recorded: you made it or edited it
  (changed, added or removed a file), or an earlier release wrote it without
  recording its files. For a skipped folder, the install, update and dry-run
  warning and `apothem verify` give the same cause and fix: keep it there and
  the harness stays not verified, or move it out of the skills folder, then
  run `apothem update` for that harness (with `--project` for a project
  install). `apothem verify` looks for these folders only for a harness that
  is installed. A project installed at the home folder itself no longer counts
  as present through the shared folders it writes there. A Codex install into
  a removed or emptied `~/.codex` skips such a folder too: the files it had
  just written there no longer make its old install count as present.
- **`apothem doctor` checks the hooks of the install it is looking at.** It
  read the newest install record of a harness from any folder. When that
  record came from another folder (another project, a `CODEX_HOME`, or one you
  had since deleted), doctor checked the wrong install's hooks or none, and
  could report the harness as healthy even when its hook command could not
  start. It now reads the record of the harness folder, or of the `--project`
  folder, that it checks, under whichever spelling of that folder the install
  used. When that folder has no record, the plain report shows the hook check
  as `not checked`, its last line says which hook commands were not checked
  rather than `All checks passed`, and for a project-scope harness the fix
  names `--project`, quoted for the shell as uninstall's steps are (double
  quotes on Windows, single quotes elsewhere), or in words, with the folder as
  it is, when those quotes cannot carry it. The command, or that folder, ends
  the fix, after a colon. `verify`, and the next step `quickstart` prints,
  quote `--project` the same way; when the quotes cannot carry the folder,
  `quickstart` prints the command up to `--project` and names the folder in
  words after it.
- **`apothem doctor` starts Cursor's hook command on Windows.** The command a
  Windows install writes begins with PowerShell's `&`, which doctor tried to
  start as a program, so every healthy Cursor install failed the hook check.
- **The JSONC / JSON5 config reader accepts LINE SEPARATOR and PARAGRAPH
  SEPARATOR inside strings.** JSON and JSON5 allow U+2028 and U+2029 unescaped
  in a string, but the reader rejected them, so an OpenCode or OpenClaw config
  holding one read as unparseable and the install refused to merge into a valid
  file. Found by the new fuzzer.
- **The OpenSSF Best Practices answer sheet describes the installers' checks
  accurately.** The `crypto_weaknesses` answer and its Remaining gaps entry say
  that the one-shot installers and the update scripts check a signed tag that
  names its commit by a SHA-1 object ID, that they pin the maintainer key by
  its OpenPGP v4 fingerprint, also a SHA-1 hash, and that an install without
  cosign, and every install or update over an existing Apothem clone,
  installs a git checkout in which every file rests on SHA-1. The
  `crypto_keylength`, `crypto_working` and `crypto_published` answers name the
  same SHA-1 uses, the TLS rows name the programs that make Apothem's TLS
  connections (pip and npm included), and `delivery_mitm` says which release
  files carry SLSA provenance and when the cosign check runs. Every answer
  stays as it was; `crypto_weaknesses` is still Unmet.
- **Deeply nested input is a parse error, not a crash.** The config reader now
  stops at 200 levels of objects and arrays with a `LenientJSONError`, and the
  install-ledger reader reports a line nested too deeply to parse as invalid
  JSON (or drops it as a torn final line), where both raised `RecursionError`.
  `apothem install` and `apothem uninstall` also crashed on a Kiro, GitHub
  Copilot or Cursor hook file nested that deeply; they now treat it like any
  other file that does not parse.
- **A damaged install ledger is reported, not a traceback.** A ledger holding
  bytes that are not UTF-8 raised `UnicodeDecodeError`, which `apothem doctor`
  and `apothem update` do not catch; the reader now raises `LedgerError`, which
  they report. Found by the new fuzzer.
- **Recovering folders an earlier release swept is safer.**
  - Rolling such an install back writes each missing file atomically. A file
    it cannot write (a file now stands where a folder was, or no permission)
    is listed for you to copy by hand, and the rollback exits 2 (partial)
    and names the files it did write. A swept path that is now a link (a
    symlink or a Windows junction), a file where a folder was or the other
    way round, or a path whose backup is gone, is left in place. The
    rollback still exits 0 and prints a `Warning:` line (a `warnings` entry
    under `--json`) naming the backup to copy from by hand.
  - Retention, and `apothem backups prune`, now keep every backup set that
    holds a path releases 1.0.1 to 1.5.0 removed whole, for every adapter
    and for Codex under a custom `CODEX_HOME` too. They include the old
    `apothem/hooks` and `apothem/templates` folders of OpenCode, Qwen Code,
    Hermes and Open-Claw, the old `apothem/skills` and `apothem/agents`
    folders of Hermes and Open-Claw, Gemini CLI's `.gemini/apothem/` and Kimi
    Code's old `.kimi-code/apothem/`.
    `prune` names why it keeps such a set.
  - Uninstall no longer deletes a `~/.claude/statuslines/__init__.py` of your
    own: install never writes that name, and uninstall now skips it too.
  - The docs say rollback reaches an install only while its record is among
    the newest 10 kept, and that the install deletes any file it did not put
    in the `apothem/rules/` folders OpenCode, Qwen Code, Hermes and Open-Claw
    use, or in Kimi Code's old support folders.
- **The launch-size metric follows six more tools' loading rules.** The
  metrics collector, which reports how many bytes of instructions each tool
  loads at launch, now counts:
  - OpenClaw's bootstrap files by name and in order, with its per-file and
    total character limits;
  - Hermes's `SOUL.md` only when it holds text;
  - CodeBuddy's user `CODEBUDDY.md` and `CODEBUDDY.local.md`, one project
    memory file, `AGENTS.md` only without one, and no rule marked
    `enabled: false`;
  - Kimi Code's `~/.agents/AGENTS.md`, skipping blank files;
  - Claude Code's `CLAUDE.local.md`, and `AGENTS.md` only when the project has
    no CLAUDE file;
  - Antigravity's project `.agents/` folder, with each file cut at 24,000
    bytes.

  No published number changes: Apothem's installs write none of these files.
- **The launch-size metric counts Antigravity's plugin rules.** The five
  always-on rules in `~/.gemini/config/plugins/apothem/rules/` now count, so
  Antigravity's figure rises by 38,395 bytes and 5 files. The rest of its
  figure is `~/.gemini/GEMINI.md`, whose size depends on the install path it
  names. The count reads only plugins with a `plugin.json`, includes a
  plugin's `rules/AGENTS.md` or `rules/GEMINI.md`, and skips a rule file that

- **Removing a leftover folder no longer deletes files through a link.**
  Releases up to 1.5.0 remove folders that earlier layouts wrote, such as
  `~/.config/opencode/apothem/rules/` or
  `~/.gemini/antigravity-cli/plugins/apothem/`. When such a folder still held

  through a link above it. That includes a link from the

  link stays after an uninstall, so you remove it when nothing uses the old
  path. An uninstall that finds installed files reached through a link (a

  keeps the install recorded and exits 2, so it can be run again once the link
  is replaced. `apothem uninstall` now prints these warnings, grouped by link
  (and lists them in `--format json`), and it reports a failure, not
  "Uninstalled", when a step such as backing up a file fails, once per reason;
  running it again removes what the failed run left.

  and undoing a failed install also leave a link inside the folder in place,
  with a warning. A
  rollback leaves a link at a restored folder in place, with a reason, and
  copies the backup into the folder around any link in it, keeping the files
  the backup does not hold; before, rolling back such an install failed with
  a "file already exists" error, and records written by earlier releases
  still roll back this way. A junction above a path an install writes is now
  refused like a symbolic link, with a message that names the link and says
  to replace it with a real folder, and a leftover link no longer makes an
  uninstalled tool read as installed.

  template folders. A `~/.config` link that leaves your home directory still
  stops the install before it writes any file. To install OpenCode there, set
  `XDG_CONFIG_HOME` to the folder the link leads to, spelled as that folder's
  own path outside your home directory. An install made earlier in
  `~/.config/opencode` then keeps one set of `instructions` entries, and an
  uninstall with the same setting removes that earlier install too. A Codex
  install cannot be moved out of the home this way, because it also writes
  `~/.config/apothem/`. An `XDG_CONFIG_HOME` or `CODEX_HOME` spelled inside
  your home directory that a link leads out of it, such as `~/work/codex` with
  `~/work` linked to another drive, stops the install, the uninstall and
  `apothem rollback` too, wherever above the folder the link sits; a refused
  rollback changes nothing, writes no `rollback` record and exits 1. A link
  on a path the install writes inside the harness folder still stops it, with
  `target path crosses a link`, or with `target escapes the allowed
  materialization root` when that link leads out of the folder holding the
  harness folder.
- **The profile is not written through a link that leaves your home
  directory.** A first `apothem install`, `apothem quickstart`, `apothem
  profile init`, `apothem profile set` and `apothem profile edit` write the
  profile at `~/.config/apothem/profile.yaml`. When `~/.config` is a link that
  leads out of your home directory, each now stops before it writes or opens
  the editor, with `Apothem could not create the starter profile` when there
  is no profile yet and `Apothem could not write the profile` over an existing
  one, also for `profile init --force`. Before, `quickstart`, `profile init`
  and `profile set` wrote the profile outside your home directory, and
  `profile set` created its folder there even when it then failed. A
  `--profile PATH` spelled inside your home directory follows the same rule; a
  `--profile PATH` spelled outside your home directory is written as before.
  A profile file that is itself a link out of your home directory is refused
  the same way, and the error names it as the link. With no profile yet, the
  error says to create one outside your home directory with `apothem profile
  init --profile PATH` first. Commands that only read the profile still read
  it.
- **`install --clean` does not remove through a link that leaves your home
  directory.** When `~/.config` was a link out of your home directory, the
  clean-slate step deleted the `apothem` folder at the far end of that link
  and then wrote the profile back there. It now stops with `Clean-slate
  removal was refused` before it backs up or removes anything. On Windows a
  junction at `~/.claude`, `~/.codex` or `~/.agents` was entered: the files it
  led to were deleted and the run ended with a traceback. The clean-slate step
  now removes a target that is a link or a junction as a link, and removes a
  link inside a target without entering it. The backup under
  `~/.apothem/backups/clean-slate-*` still holds what an earlier run removed.
- **A home folder that is itself a link installs.** On Linux and macOS, a home
  folder that is a symbolic link, such as `/home/name` leading to
  `/data/home/name`, stopped every install of a tool whose folder sits directly
  in the home, such as Claude Code or Codex, with `target path crosses a
  symlink`. That link leads to the home folder itself, so every write stays in
  it, and the install now follows it. On Windows a home folder that is a
  junction, as moving a user profile to another drive makes it, is followed
  the same way.
- **A refused uninstall is reported as failed.** When the write guard, a
  failed backup or an unreadable install record stopped part of an uninstall,
  `apothem uninstall` still printed `Uninstalled` and exited 0, while the files
  and the install record stayed. It now prints the error and exits non-zero.
- **An uninstall that a link refuses no longer asks first.** When a link
  leads a tool's folder in your home directory out of it, `apothem uninstall`
  asked `Remove ... configuration?` and only then refused. It now refuses
  before the question, as `apothem rollback` does. The install, update,
  uninstall and rollback errors for such a link now name the link and the
  folder it leads to, and say to replace the link with a real folder or make
  it lead inside your home directory. The `install --clean` error for a
  `~/.config` link that leaves your home directory gives the same fix instead
  of asking you to re-run interactively. A write refused at a link inside a
  tool's folder also names where the link leads, and for a link to a file it
  says to replace the link with a copy of the file. In `--format json`
  output, a result refused at a link carries a new key, `detail.leads_to`,
  the path the link leads to. A result refused because a link leads a
  tool's folder out of your home directory now also carries `detail.fix`,
  the fix, as other refused results already do. No existing key changed.
- **`install --clean` writes your profile back when a removal stops
  partway.** When the clean-slate step could not remove a folder, for example
  because another program held a file in it, the command stopped with a
  traceback, and a profile it had already removed was not written back. It now
  writes the profile back first and names the backup folder.
- **OpenCode update and uninstall find an MCP server converted to OpenCode 2's
  shape.** OpenCode 2 keeps MCP servers under `mcp.servers` and reads the
  `mcp.<name>` entries the install writes in place, without rewriting the file.
  An operator who converted such an entry to the `mcp.servers` shape got a
  server that uninstall left behind and that update added a second time. For an
  install made or last updated by Apothem 1.2.0 or later, which records the
  entries it wrote, both now recognize the converted server, as a whole: only
  when its `mcp.<name>` entry is gone and it matches what the install wrote. An
  operator's own server of the same name, a conversion the operator edited and
  one the operator disabled stay as they are; beside those, update writes the
  server under `mcp` again, so OpenCode 1 uses that copy and OpenCode 2 the
  converted one. An operator's own server under `mcp.servers` that matches one
  the install wrote, after the operator removed the install's `mcp` entry,
  cannot be told from a converted copy and is removed with it on uninstall; the
  file is backed up first. The OpenCode page and convention pin record what
  OpenCode 1 and OpenCode 2 each read, and that the install writes one
  configuration in the OpenCode 1 shapes, which OpenCode 2 translates; the pin
  names what would make it write OpenCode 2's own shapes instead. The page also
  states that OpenCode 1 loads the Claude Code block in `~/.claude/CLAUDE.md`.
- **The always-on bytes metric counts only the instruction files Hermes and
  Codex load.** Hermes loads one kind of project context per session, the
  first with a non-empty file: `.hermes.md` or `HERMES.md` (the first of the
  two that exists is the only candidate of its kind), `AGENTS.override.md` or
  `AGENTS.md`, `CLAUDE.md`, then `.cursorrules` with every
  `.cursor/rules/*.mdc`. The metrics collector added up `.hermes.md`,
  `AGENTS.md` and `CLAUDE.md` together and left out the other files. It now
  counts `~/.hermes/SOUL.md` plus that one kind. Codex loads the first
  non-empty of `AGENTS.override.md` and `AGENTS.md` in its home folder, and in
  the project the first of `AGENTS.override.md`, `AGENTS.md` and its
  `project_doc_fallback_filenames` names that exists, where an empty one loads
  nothing. The collector counted the two `AGENTS.md` files only; it now
  follows that order and counts project files up to `project_doc_max_bytes`
  (32 KiB by default). The developer guide states both rules. On Python 3.10,
  which has no TOML reader, a `~/.codex/config.toml` gives a null for Codex
  instead of ending the run.

### Security

- **`install --clean` no longer rewrites a profile it did not remove.** After
  the clean-slate step, the install wrote the profile back to the `--profile
  PATH` it was given, whether or not the step had removed it, and without the
  link check every other profile write has. With `--profile ~/ext/profile.yaml`
  and `~/ext` a link or a junction leading out of your home directory, it
  replaced the file at the far end of the link. The profile is now written back
  only when the clean-slate step removed it, and that write is refused when a
  link would lead it out of your home directory. A refused or failed write back
  names the backup copy that holds your profile.
- **The folder you name with `--project` is followed wherever it leads.**
  A project folder that is itself a link, `~/.config` among them, is the
  folder you named, so Apothem writes in the folder the link leads to, also
  outside your home directory. A link inside the project folder stops the
  install, also when it leads back into the project folder. A tool that also
  writes in `~/.config/apothem` still stops when `~/.config` leads out of your
  home directory. The command line already followed the folder you name.
  Python code that calls Apothem's install functions with a project folder now
  follows the same rule; before, it refused a project folder that was a
  symbolic link.
- **Two folders whose names differ only in case are no longer taken for one
  folder where the system keeps them apart.** On Linux, and in a Windows
  folder set to keep case, a folder such as `/home/U` beside `/home/u` counted
  as inside `/home/u`, so a write could land in the other folder. Apothem now
  checks the case exactly first, and treats the names as one folder only when
  both name the same folder on disk.
- **A piped install no longer adopts a source tree from the current folder
  (GHSA-799g-h543-w5gg).** In releases 1.0.1 to 1.5.0, `curl ... | sh` and
  `irm ... | iex` fell back to the folder they were started in, and to its
  parent folders, looking for a source tree that has the shape of Apothem. They
  then ran its interpreter locator and installed that tree without checking it.
  On Windows, any local user can create a folder such as `C:\src\apothem`, so
  an administrator who ran the one-liner below `C:\` could run code that the
  user planted. The installers (`install.sh`, `install.ps1`) now use a local
  tree only when `APOTHEM_SOURCE` names it, or when the script runs by path from
  inside its own checkout, where the tree is found from the script's own path.
  A piped run reads nothing from the current folder or its parents, and takes
  the normal fetched and verified path. The installers' `git` commands that do
  not work on a clone also no longer read a repository in the current folder: an
  installer started from inside a folder that has its own `.git` no longer reads
  that folder's git configuration. To install from a checkout, run that
  checkout's own `scripts/installer/install.sh` (or `install.ps1`) by its path,
  from any folder, or set `APOTHEM_SOURCE`.
- **The current folder no longer shadows the engine's Python modules
  (GHSA-4rh9-7m5x-94j9).** In releases 1.0.1 to 1.5.0, Python put the current
  folder first on its module search path when the installers checked for
  `click` and `rich`, when they and the `apothem` command shim started the
  engine, and when `npx @ahmed-g-gad/apothem` did. A file such as `click.py`,
  or a folder named `rich` or `apothem`, in the folder you ran the command from
  ran instead of the real package. Every one of these starts (the installers,
  the updaters, the uninstallers, the start of `pip` for the dependency
  install, the `apothem` shims they write for POSIX and Windows, and the npm
  launcher) now keeps the current folder off the module search path on
  Python 3.10 to 3.14. Empty and relative entries in your own `PYTHONPATH`,
  which Python reads as the current folder, are no longer passed on by any of
  these launchers: the POSIX shim, the Windows `apothem.cmd` shim, the
  installers, the updaters, the uninstallers and the npm launcher. A kept
  entry must be a full path: on Windows a drive path such as `C:\lib` or a
  network path, elsewhere a path that starts with `/`. A rooted `\lib` or a
  drive-relative `C:lib` is dropped. The sh scripts ask the Python they run
  which form it reads, and the `apothem` shim they write keeps that form. A
  Windows Python (the usual one under Git Bash) gets the engine paths in
  Windows form, joined with `;`, and keeps only the drive and network paths
  of your `PYTHONPATH`. A POSIX Python, including Cygwin's and MSYS2's own
  `python3`, gets POSIX paths joined with `:` and keeps only entries that
  start with `/`. The conformity gate starts its validators the same way.
  Your working directory and the arguments you pass are not changed, and your
  full-path `PYTHONPATH` entries and user-installed packages still work. The
  updaters do not rewrite an existing shim: to replace a shim written by an
  earlier release, run the installer (`install.sh` or `install.ps1`) again.
  Updating alone does not.
- **A link no longer takes an install out of your home directory through
  `~/.config` or a moved tool folder.** A junction at `~/.config` leading out
  of your home directory let an OpenCode install, and the starter profile of a
  first run, write outside it. On every system, a link two or more folders
  above a `CODEX_HOME` spelled inside your home directory let a Codex install
  write outside it. Both now stop before anything is written. On Windows a
  junction on a path an install writes counts as a link, as a symbolic link
  already did, so a junction at or inside a tool's folder, such as
  `~/.claude`, `~/.claude/skills`, or a project's `.cursor` or `.gemini`
  folder, now stops the install with `target path crosses a link`, also
  when it leads somewhere inside your home directory or project. Replace such
  a junction with the folder itself, or link `~/.config` or `~/.agents`
  instead, which are followed while they lead somewhere inside your home
  directory.
- **The installers accept only the maintainer key, and with cosign they
  also check the signed release archive.** `install.sh`, `install.ps1`,
  `update.sh` and `update.ps1` checked a release tag with `git verify-tag`,
  which accepts a valid signature from any key the local GnuPG keyring holds.
  They now read GnuPG's `VALIDSIG` status and refuse the tag unless its
  primary-key fingerprint is `5C8998F9F241720445D3F28B70396FED9C634163`, the
  key SECURITY.md publishes. They also read the signed tag object and refuse
  it unless it names the release being installed: a validly signed tag for
  another release, re-pointed at this tag's name, would otherwise roll an
  install back to that release. `APOTHEM_ALLOW_UNVERIFIED` does not bypass
  that check, but because it lets an unsigned tag, or one signed by another
  key, through, the check protects only tags that carry the maintainer
  key's signature. The installers check out the tag by its full `refs/tags/` name
  and confirm the checkout is the tag's commit. A missing `gpg` is now named
  as such.
- **A new release check needs both signatures.** `APOTHEM_VERIFY=release`
  first checks the release tag against the maintainer key, then downloads the
  platform archive, `SHA256SUMS` and `SHA256SUMS.cosign.bundle`. cosign must
  confirm that the release workflow at that exact tag signed `SHA256SUMS`
  and, through its `--certificate-github-workflow-sha` check, that the
  certificate it verified was issued to a run on the commit the signed tag
  points at. The installers do not read the certificate themselves; cosign
  makes that comparison. Only then is the archive's SHA-256 checked. The
  release workflow runs for any tag that is pushed, so its signature alone
  would accept a release nobody signed off; the tag signature alone says
  nothing about the archive. `APOTHEM_ALLOW_UNVERIFIED` never relaxes this
  path. The new default, `APOTHEM_VERIFY=auto`, takes it whenever `cosign` is
  on `PATH` and uses the tag check alone otherwise, and keeps an existing git
  clone at `APOTHEM_HOME` on the tag check; `signature` and `checksum` stay
  available. The checks pass under cosign v2 and v3, and a CI job runs them
  against the real cosign binaries.
- **An existing clone is no longer checked out before its tag is checked.**
  In releases up to 1.5.0, `install.sh`, `install.ps1`, `update.sh` and
  `update.ps1` fetched into an existing clone at `APOTHEM_HOME`, checked out
  the new tag, and only then checked its signature. When the check failed,
  the clone stayed at that tag, and the `apothem` command runs its code from
  there. They now fetch, check the tag, and check it out only when the check
  passes, so a failed check leaves the clone as it was. The checkout also no
  longer forces: a clone with changes to tracked files stops the update,
  with a message to commit or stash them, instead of losing them. A failed
  `git fetch` now stops the run. A non-release ref such as `main` on an
  existing clone follows origin's copy of the branch, and a `.git` file (a
  linked worktree) counts as a clone. Before the fetch, the update in place
  also stops when files are marked assume-unchanged or skip-worktree, which
  hides their changes from git, when the clone's work tree is not
  `APOTHEM_HOME`, or when the clone's own `.git/config` sets `gpg.program`,
  `gpg.openpgp.program`, `core.fsmonitor`, `core.hooksPath`, `include.*` or
  `includeIf.*`, any of which makes git run a program or read other config
  during the update. Every git command on the clone runs with its hooks
  turned off, and a git clone of anything other than Apothem is no longer
  treated as an Apothem clone. The installers also ignore git's redirecting
  and config environment variables (`GIT_DIR`, `GIT_CONFIG_PARAMETERS` and
  similar) and refuse an `APOTHEM_REPO` that starts with `-`.
- **`APOTHEM_VERIFY=checksum` now needs `APOTHEM_ALLOW_UNVERIFIED=1`.**
  This is a behaviour change for anyone who sets `APOTHEM_VERIFY=checksum`:
  add `APOTHEM_ALLOW_UNVERIFIED=1`, or the installer stops and says so.
  Checksum mode does not verify the release. SHA256SUMS comes from the same
  release as the archive, so a match only shows the download isn't damaged;
  anyone who can change the release's files can change both. The installers
  now warn about this before they download anything, and the install guide,
  SECURITY.md and the help text use the same wording.
- **The installers no longer delete the engine's backups, state and other
  data.** Replacing an install at `APOTHEM_HOME` with `--yes` removed the
  whole folder, including the rollback backups (`backups/`), install ledgers
  (`state/`), plans, memory and other data the engine keeps there. The new
  source is now checked in a staging folder beside `APOTHEM_HOME`, swapped in
  only after every check passes, and everything in the earlier Apothem install
  that is not part of its source tree is kept. If a step fails or the run is
  interrupted, the earlier install is put back unchanged, or the message says
  where it was left. `--yes` on a folder that holds no Apothem install no
  longer merges the new files into it: the folder moves, unchanged, to
  `<APOTHEM_HOME>.before-apothem-<time>` and the install starts fresh. A
  symbolic link at `APOTHEM_HOME` (on Windows, a symbolic link or a junction)
  is refused when the install would replace it, since replacing it would
  replace the link and not the folder it leads to; an existing clone behind a
  link is still updated in place. `--yes` no longer replaces a git clone with
  a release archive while the clone holds local work (changes, stashes,
  unpushed commits, or untracked files in its source tree), also in a dry run,
  and when it replaces a clone, the clone's own tree moves to
  `<APOTHEM_HOME>.before-apothem-<time>` instead of being deleted.
  A folder that holds only the engine's data (`backups`, `state`, `plans`,
  `memory`, `contexts`, `learning`, `providers`) is updated without `--yes`.
  On Linux and macOS, a file or folder to carry over whose name has a space
  or another special character stops the install. A re-run in an archive
  mode updates an earlier archive install without `--yes`, and the update
  scripts tell an archive install to re-run the installer. `--dry-run`
  (`-DryRun`) now checks the release in a temporary folder, applies the same
  refusals as a real run, and leaves `APOTHEM_HOME` unchanged. The
  [install guide](https://apothem.ahmedgad.com/docs/install#trust-model)
  explains each mode.
- **OpenCode helpers no longer turn off the `.env` read prompt.** OpenCode
  allows every tool by default and asks before reading `.env` and `.env.*`
  files. A helper's rules come after those defaults and after the operator's
  own `permission` config, and the last matching rule wins, in OpenCode 1
  (v1.19.5) and OpenCode 2 (v2.2.5). Every helper the OpenCode install wrote
  carried `read: allow`, which turned that prompt off, and `allow` rules for
  the other tools it may use, which overrode a stricter rule the operator set,
  such as a global `bash: ask`. Helpers now carry only `deny` rules, for the
  tools they must not use, so the `.env` prompt and the operator's rules apply
  to them.
- **The VS Code packaging tool's lockfile takes the `minimatch` fix.** The
  locked `vsce` toolchain (`tools/vsce`) moves its transitive `minimatch` from
  10.2.6 to 11.0.1, which fixes GHSA-g3hv-75wg-m249 (a denial of service
  through a crafted glob pattern). vsce 4.0.0 and 4.1.0 still require
  `minimatch` 10.x, which has no fixed release, so `tools/vsce/package.json`
  overrides it. vsce did not reach the affected code, which runs only at
  optimization level 2 or higher: it matches its own ignore list and the
  extension's `.vscodeignore` at the default level. The packaged extension is
  unchanged.

## [1.0.2] - 2026-08-14

### Fixed

- **The `Stop` hook no longer re-asserts the session-end protocol on every turn.**
  `Stop` fires at the end of every assistant turn, not only at the end of a
  session, and the hook emitted `hooks/messages/stop.md` verbatim each time. Because
  that body reads as a fresh work order rather than a status check, every response
  triggered another firing and nothing the agent did changed what the hook
  asserted — the loop had no fixed point, and an operator could only escape it by
  restarting the harness, since hook configuration and message bodies are both
  snapshotted at session start. A new dispatch-routed handler,
  `hooks/session_end_gate.py`, supplies the missing termination condition: the
  protocol is emitted at most once per session, and only once the session has
  accumulated enough turn-ends to have state worth externalizing. The message file
  still owns the protocol text — the gate decides only when it is emitted — so its
  path and its cross-references from `rules/context-management.md` and
  `rules/auto-memory.md` are unchanged. Two environment variables tune it:
  `APOTHEM_SESSION_END_MIN_STOPS` (default `3`) sets the firing floor, and
  `APOTHEM_SESSION_END_ENABLED=0` silences the protocol entirely without editing
  installed plugin files.
- **The detection pseudocode in the canonical option-shapes rule is fenced as
  text rather than Python.** The block uses the hyphenated schema field names the
  same document defines in its field table, which are not valid Python.
  Correcting the fence language leaves the pseudocode byte-identical.

## [1.0.1] - 2026-07-07

Apothem is a host-agnostic AI-harness configuration manager: one governed shared
profile materializes into the native configuration of seventeen assistant
harnesses behind a conformity governance gate and signed, reproducible releases.

### Added

- **Shared-profile model.** One governed profile at
  `~/.config/apothem/profile.yaml` is the single source for the synced unit —
  rules, slash-commands, skills, hooks, output-styles, settings, schemas, docs,
  and MCP servers — plus the wrapped-workflow orchestrators that drive whole
  missions end to end (`/plan`, `/research`, `/audit`, and the `/fortress`
  closed-loop production-hardening pipeline).
- **Seventeen harness adapters.** Antigravity, Claude Code, CodeBuddy, Codex,
  Cursor, Gemini CLI, GitHub Copilot, Hermes, Kimi Code, Kiro, Open-Claw,
  OpenCode, Qwen Code, Trae, Windsurf, Zed, and GLM (Z.ai) each install, verify,
  update, and uninstall through a shared, reversible adapter contract that emits
  the tool's native file layout. Installs back up existing targets before
  replacement; uninstalls reverse cleanly with zero orphans.
- **CLI.** `quickstart`, `install`, `uninstall`, `update`, `verify`, `status`,
  `diff`, `rollback`, `migrate-workspace`, `harnesses`, `profile`, `doctor`, and
  `completion`, with dry-run reporting, drift detection, and structured JSON
  output (`--format json`). The engine is self-contained — the source tree
  carries its vendored dependencies and runs from a checkout as
  `python -m apothem` on system Python 3.10+.
- **Conformity governance gate.** A pre-emission validator suite checks the
  synced unit — authorship headers, frontmatter contracts, naming, determinism,
  cross-references, and harness capability coverage, including a cross-file
  binding-reciprocity validator that keeps every rule cross-binding closed at
  its cited peer — before any surface is materialized.
- **Install paths.** The Claude Code plugin
  (`/plugin marketplace add ahmed-g-gad/apothem`), a Gemini CLI extension, a
  Qwen Code extension, a Codex plugin, the npm shim
  (`npx @ahmed-g-gad/apothem <command>`), and the one-shot POSIX and PowerShell
  installers (`install.sh` / `install.ps1`) with matching update and uninstall
  scripts. The source of a VS Code-family extension is in `vscode-extension/`;
  this release attaches no packaged `.vsix`, and the extension is not listed on
  the Visual Studio Marketplace.

### Changed

- **Unified install layout.** Materialized machinery (hooks, the conformity
  gate, schemas, templates) and non-native cohorts (rules, skills, agents)
  install under a single Apothem-owned `.apothem/support/` tree inside each
  harness's configuration root, so each profile carries one Apothem-owned dotted
  directory rather than two similarly-named siblings.
- **Leaner always-on rules tier.** The always-loaded behavioral rules were
  consolidated to twenty-eight, with situational depth moved into demand-loaded
  companion rules, so a session — or a fleet of sub-agents — ingests fewer
  tokens up front while every discipline still fires where it applies.

### Security

- Every release attaches an sdist, a wheel, SHA-256 checksums, Sigstore cosign
  signatures, SLSA build provenance, and a CycloneDX SBOM as verification
  evidence; the npm package publishes with Sigstore build provenance signed
  from the GitHub Actions OIDC identity, and a conformity validator holds every
  release workflow to a provenance-signed, pinned publish path.
- The pipeline gates every change on lint, tests, type checks, a documentation
  build, CodeQL, OpenSSF Scorecard, dependency review, a scheduled OSV
  vulnerability scan, and supply-chain checks before publication. The one-shot
  installers pin their `click` / `rich` prerequisites to the engine's declared
  constraints and document an inspect-first alternative to the pipe-to-shell
  one-liner.
