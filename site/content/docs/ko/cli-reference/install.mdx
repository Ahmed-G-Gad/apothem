공유 프로필로부터 하니스 어댑터 구성을 설치합니다.

## 개요

```
apothem install --harness NAME|all [--profile PATH] [--dry-run]
                 [--clean|--fresh] [--yes] [--project PATH]
                 [--quiet|-q] [--verbose|-v]
                 [--format plain|json] [--json] [--no-color]
```

공유 프로필을 로드하고 검증한 뒤, 이름이 지정된 어댑터 또는 레지스트리 전체의
`all` 집합을 선택하고, 머티리얼라이즈 계획을 검증한 다음, 하니스 네이티브
구성과 지원 코호트를 씁니다. 프로젝트 범위 어댑터에는 `--project PATH`가
필요합니다.

연속형 별칭 `apothem installing`(`apothem Installing`으로도 받아들여짐)은 같은
핸들러로 해석됩니다.

## 프로필 없이 처음 실행하기

`--profile`을 생략했고 기본 경로(`~/.config/apothem/profile.yaml`)에 프로필이
없으면, `install`은 먼저 그 위치에 스타터 프로필을 쓰고,
`Created a starter profile at <path>`를 출력한 다음, 계속 진행합니다. 스타터
프로필은 플레이스홀더 신원 필드를 담고 있으므로, 설치는 플레이스홀더 신원 참고도
함께 출력합니다. 프로필을 개인화한 다음 [`update`](/docs/cli-reference/update)를
실행하여 적용하세요. `--json`에서는 이 생성이
`"operation": "profile_created"`가 담긴 `warnings` 항목으로 보고됩니다.

- `--dry-run`은 절대 프로필을 쓰지 않습니다. 미리보기는 메모리 안의 스타터
  프로필을 사용하며 `"operation": "profile_scaffold_preview"`를 보고합니다.
- 명시적으로 지정한 `--profile PATH`가 존재하지 않으면 절대 생성되지 않습니다.
  명령은 `profile.not_found`와 함께 1로 종료합니다.

## 영향 범위 미리보기

`install --harness all`은 혼합된 범위로 퍼져 나갑니다. 프로젝트 범위 어댑터는 지정된 `--project` 루트 아래에 쓰고, 사용자 범위 어댑터는 사용자의 홈 디렉터리 아래에 씁니다. 즉 그 루트 바깥입니다. 설치가 어떤 파일도 쓰기 전에, 명령은 구체적인 대상을 두 개의 제목 아래에 묶어 출력합니다. 프로젝트 루트 안에 있는 대상과 홈 디렉터리 아래에 있는 대상입니다. 유일한 예외는 `--clean`입니다. 이 옵션의 초기화 단계는 이 미리 보기보다 먼저 실행되며, 아래에 설명된 대로 백업을 쓰고 이전 대상을 제거합니다.

선택 항목이 프로젝트 루트 바깥에 쓰는 경우, 대화형 확인이 홈 디렉터리 기준
쓰기를 보호합니다. `--yes`, 비대화형 셸(TTY 없음), `--dry-run`, `--format json`은
각각 프롬프트 없이 진행합니다. `--dry-run`만 아무것도 쓰지 않습니다. `--format json`은
미리보기와 확인 프롬프트를 건너뛰지만 쓰기는 그대로 수행합니다. 홈 디렉터리
프롬프트를 거부하면 설치 쓰기 전에 중단됩니다. `--clean`을 함께 사용하면 클린
슬레이트 단계가 먼저 실행되며, 이 단계는 자체 대상별 확인을 거칩니다. 이 단계는
`~/.apothem/backups` 아래에 백업을 쓰고, 확인된 대상을 제거합니다. 설치 프롬프트를
거부해도 그 제거와 백업은 그대로 남습니다.

## 기능 참고 사항

각 어댑터는 해당 하니스가 네이티브로 지원하는 기능만 투영합니다. 네이티브
표면이 없는 기능은 조용히 버려지지 않고 보고됩니다. plain 모드에서는 하니스당
하나의 묶인 참고로 표시됩니다(예:
`Note: <harness> - 9 capabilities not projected; pass --verbose for detail`).
`--verbose`에서는 각 기능이 자체 근거 줄을 출력합니다. 그 밖의 어댑터 경고도
plain 모드에서 각자의 `Warning:` 줄에 출력됩니다. 예를 들어 새 `.rules`가 가리는
지침 파일의 이름을 알려 주는 Zed 경고가 그렇습니다. `--format json` 봉투는
상세 수준과 관계없이 항상 전체 `warnings` 배열을 담습니다.

설치와 업데이트는 권고도 `Note:` 줄로 출력합니다. 권고는 설치가 쓰는 내용을
절대 바꾸지 않습니다. 설치가 공유 루트, 즉 다른 도구도 로드하는 경로(예: 스킬
폴더 `~/.agents/skills/`)에 쓰는 경우, 참고는 그 도구들의 이름을 알려 줍니다.
설치 대상 도구가 이미 다른 설치의 공유 루트에서 Apothem 콘텐츠를 로드하고 있는
경우, 참고는 그 설치의 이름을 알려 줍니다. `--format json` 봉투에서 각 권고는
`"outcome": "advisory"`와 `"operation": "shared_root"`가 담긴 `warnings`
항목입니다.

프로필의 MCP 서버에는 세 가지 권고가 적용되며, 각 권고는 해당 프로필 필드의
이름을 알려 줍니다.

| 작업 | 조건 | 해결 방법 |
| --- | --- | --- |
| `mcp_deprecated_transport` | `transport: sse`(MCP 사양은 HTTP+SSE를 지원 중단함) | 서버가 지원하면 `streamable-http`를 사용하세요. |
| `mcp_plain_http` | 루프백이 아닌 호스트를 가리키는 `http://` URL | `https://` URL을 사용하세요. |
| `mcp_literal_credential` | 토큰처럼 생긴 `headers` 또는 `env` 값(`ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_`, `sk-`, `xoxa-`, `xoxb-`, `xoxo-`, `xoxp-`, `xoxr-`, `xoxs-`, 또는 긴 토큰이 붙은 `Bearer`) | 시크릿은 환경 변수에 보관하고 `${GITHUB_TOKEN}` 형식의 참조를 쓰세요. |

자격 증명 권고는 발견한 값을 절대 출력하지 않습니다. `${...}` 참조가 포함된 값은
절대 플래그 처리되지 않습니다.

## 주석이 있는 운영자 구성

일부 하니스 구성은 여러분도 직접 편집하는 파일입니다. 예를 들어
`settings.json`, `opencode.json`(JSONC일 수 있음), `openclaw.json`(JSON5),
`config.yaml`이 그렇습니다. 설치는 자신의 키를 이 파일들에 병합하며, 여러분이
추가한 모든 키를 유지합니다.

병합은 파일을 일반 JSON 또는 YAML로 다시 쓰므로, 주석, 후행 쉼표, JSON5 구문이
사라지게 됩니다. 따라서 다음과 같이 동작합니다.

- 병합으로 어떤 값도 바뀌지 않는 경우(예: Apothem의 키를 이미 직접 추가한
  경우), 파일은 바이트 단위로 그대로 남습니다.
- 주석이나 JSON5 구문을 담은 파일, 또는 아예 파싱되지 않는 파일에서 병합이 값을
  바꿔야 하는 경우, 설치는 해당 하니스에 대해 아무것도 쓰지 않고 오류 코드
  `config.unparseable`과 함께 1로 종료합니다. `fix` 필드는 설치가 추가할 키의
  이름을 알려 주므로, 파일을 일반 JSON 또는 YAML로 변환하거나, 그 키들을 직접
  추가한 다음 다시 실행할 수 있습니다.

## 옵션

| 옵션 | 설명 |
|---|---|
| `--harness NAME` | 설치할 하니스 어댑터, 또는 레지스트리 전체 집합을 뜻하는 `all`(필수). `all`을 사용하면 프로필의 `exclude_harnesses`에 나열된 하니스는 건너뛰지만, 명시적으로 이름을 지정한 하니스는 나열되어 있어도 설치됩니다. 등록된 이름은 `apothem harnesses list`를 실행하여 확인하세요. |
| `--profile PATH` | 공유 프로필 YAML 경로. 기본값은 `~/.config/apothem/profile.yaml`입니다. |
| `--dry-run` | 파일을 쓰지 않고 설치를 미리 봅니다. |
| `--clean`, `--fresh` | 선택형 클린 슬레이트: 설치 전에 이전의 하니스별 설치 상태를 백업한 뒤 제거합니다. |
| `--yes` | 클린 슬레이트 제거 중 대상별 확인을 건너뜁니다(비대화형 `--clean` 실행에 필수). |
| `--project PATH` | 프로젝트 범위 하니스의 프로젝트 루트. |
| `--quiet`, `-q` | 정보성 출력을 억제합니다. 오류만 출력됩니다. |
| `--verbose`, `-v` | 하니스별로 묶인 참고 대신 투영되지 않은 각 기능의 근거를 출력합니다. |
| `--format plain\|json` | 출력 형식(기본값: `plain`). |
| `--json` | `--format json`의 축약형. |
| `--no-color` | 출력에서 ANSI 색상 코드를 비활성화합니다. |
| `-h`, `--help` | 도움말을 표시하고 종료합니다. |

## JSON 출력

`--json`(또는 `--format json`)을 지정하면, 하나의 JSON 문서가 stdout에
쓰입니다.

```json
{
  "schema_version": 1,
  "status": "success",
  "command": "install",
  "action": "installed",
  "harness": "claude-code",
  "profile_path": "C:\\Users\\Example\\.config\\apothem\\profile.yaml",
  "project": null,
  "files_written": ["C:\\Users\\Example\\.claude\\settings.json"],
  "results": [],
  "warnings": [],
  "error": null,
  "output_path": "C:\\Users\\Example\\.claude\\settings.json"
}
```

`--dry-run`에서는 아무것도 쓰이지 않으며, `results`는 설치가 쓸 모든 경로를
나열합니다. 각 경로에는 그 경로가 갖게 될 결과(`created`, `updated` 또는
`unchanged`)가 함께 표시되고, 여러분도 직접 편집하는 파일의 경우 `detail.diff`에
통합 diff가 담깁니다. 이는 [`apothem diff`](/docs/cli-reference/diff)가
보여 주는 것과 같은 계획입니다.

```json
{
  "schema_version": 1,
  "status": "dry_run",
  "command": "install",
  "action": "dry_run",
  "harness": "claude-code",
  "files_written": [],
  "results": [
    {
      "harness": "claude-code",
      "outcome": "created",
      "operation": "write_text",
      "path": "C:\\Users\\Example\\.claude\\settings.json",
      "message": "dry run: no filesystem changes made"
    }
  ],
  "warnings": [],
  "error": null
}
```

`--clean`을 지정하면, 봉투는 제거 단계를 설명하는 `clean` 객체를 추가로
담습니다. 이 객체에는 대상별 처리 목록, 실행이 미리보기였는지 여부, 타임스탬프가
붙은 백업 디렉터리(드라이 런에서는 `null`)가 들어 있습니다.

```json
{
  "clean": {
    "dry_run": true,
    "backup_dir": null,
    "targets": [
      {
        "path": "C:\\Users\\Example\\.claude",
        "present": true,
        "removed": false,
        "skipped_reason": null
      }
    ]
  }
}
```

클린 드라이 런은 두 단계를 하나의 문서로 미리 보여 줍니다. `clean` 아래에는 제거
미리보기가, `results` 아래에는 새로 쓰기 미리보기가 담깁니다.

예상된 검증 오류는 같은 봉투를 사용하며 오류 객체를 포함합니다.

```json
{
  "schema_version": 1,
  "status": "error",
  "command": "install",
  "harness": "all",
  "files_written": [],
  "error": {
    "code": "project.required",
    "field": "project",
    "reason": "project-scope harnesses require --project: cursor, gemini-cli, github-copilot, kimi-code, windsurf, codebuddy, kiro, trae, zed, glm.",
    "fix": "Pass --project PATH or select only user-scope harnesses."
  }
}
```

## 예제

```bash
apothem install --harness claude-code
apothem install --harness claude-code --dry-run
apothem install --harness cursor --project . --profile ~/profile.yaml --json
apothem install --harness all --project . --dry-run --json
apothem installing --harness claude-code   # continuous-form alias
apothem Installing --harness claude-code   # capitalized variant
```

## 종료 코드

| 코드 | 의미 |
|---|---|
| 0 | 어댑터가 성공적으로 설치되었거나 드라이 런이 문제없이 계획됨 |
| 1 | 예상된 검증, 프로필, 하니스, 프로젝트, 또는 어댑터 오류 |
| 2 | 적어도 한 번 쓴 뒤에 발생한 부분적인 일괄 머티리얼라이즈 |
| 64 | 사용법 오류: 알 수 없는 옵션이나 명령, 또는 누락되었거나 잘못된 옵션 값. `--json`에서는 이 오류가 코드 `cli.usage`를 담은 JSON 봉투로 출력됩니다. |
