하니스 어댑터 설치를 검증합니다.

## 개요

```
apothem verify --harness NAME|all [--profile PATH] [--project PATH]
                [--quiet|-q] [--verbose|-v]
                [--format plain|json] [--json] [--no-color]
```

선택한 각 어댑터의 `verify()` 구현을 호출합니다. 선택한 모든 어댑터가 자신의
관리 대상이 존재하고 유효하다고 보고할 때만 0으로 종료합니다. `--profile`이
없으면 검사는 **구조적**입니다. 모든 관리 대상이 존재하고 유효해야 합니다.
`--profile`이 있으면 검사는 추가로 **프로필 충실도**를 요구하므로, 존재하지만
드리프트된 설치는 검증에 실패합니다. 이 검사는 단순히 "존재하는가?"가 아니라
"바로 이 프로필이 충실하게 설치되었는가?"에 답합니다. 줄 끝 문자는 따지지
않으므로, CRLF나 CR 줄 끝으로 저장된 파일도 통과합니다. 어느 쪽이든, Apothem이
관리 블록을 두는 파일은 다음을 담고 있는 동안 검증에 실패합니다: END 마커가
사라진 경우처럼 완전한 블록을 시작하지 않는 BEGIN 마커
([문제 해결](/docs/install/troubleshooting#a-file-has-an-apothem-begin-marker-with-no-end-marker)
참조), Apothem의 마커 사이에 있는 둘 이상의 완전한 블록
([파일이 Apothem의 마커 사이에 두 블록을 담고 있음](/docs/install/troubleshooting#a-file-holds-two-blocks-between-apothems-markers)
참조), 또는 완전한 블록은 없지만 여러분의 코드 블록 안에 있는 Apothem 블록처럼
Apothem이 여러분의 텍스트와 구별할 수 없는 마커 쌍
([Apothem이 자신의 블록과 여러분의 텍스트를 구별할 수 없음](/docs/install/troubleshooting#apothem-cannot-tell-its-block-from-your-text)
참조). 업데이트는 그런 마커를 유지하거나 그런 파일을 그대로 두므로,
`apothem update`를 실행해도 실패는 해소되지 않습니다.
검사하는 파일은 그 하니스의 설치가 블록을 쓰는 파일과, 마지막으로 완료된 제거
이후의 설치 기록이 나열하는 파일이며, 설치가 더 이상 사용하지 않는 OpenClaw
워크스페이스의 규칙 파일도 포함됩니다. 프로젝트의 노트 파일처럼 여러분 자신의 파일에
있는 마커는 검증을 실패시키지 않습니다. 설치 기록이 없으면 `CLAUDE.md`와 프로필
문서는 검사하지 않습니다. 설치가 그 파일들을 썼다는 것은 기록만이 보여 주기
때문입니다. OpenClaw verify는 찾아낸 워크스페이스의 규칙 파일에 완전한 블록이 없거나
블록을 시작하지 않는 BEGIN 마커가 있으면, 파일 이름을 알려 주지 않은 채 여전히
실패합니다.
실패한 행은 그런 파일을 각각 알려 주고 무엇을 고칠지 말해 줍니다. 떨어져 나온
마커의 줄과 함께, 그 줄과 Apothem 블록을 여는 줄을 제외한 다른 모든 BEGIN 마커
줄(코드 안에 인용한 BEGIN 마커 포함)을 파일마다 따로 바꾸는 번호 매긴 단계를
알려 주거나(안내는 대신 END 마커를 다시 추가하지 말라고도 말합니다. 설치나
업데이트가 Apothem 블록을 그와 따로 쓴 뒤라면 Apothem 블록이 두 개 남게 되기
때문입니다), 각 완전한 블록을 줄 번호로 알려 주거나,
Apothem이 여러분의 텍스트와 구별할 수 없는 마커 쌍의 경우 각 쌍의 줄, 그 줄들이
어디서 읽히는지, 고치는 방법을 어떤 마커 쌍도 시작하지 않는 각 BEGIN 마커와 함께
알려 줍니다.
업데이트가 OpenClaw의 파일별 한도에 맞을 때만 쓰는 OpenClaw 규칙 파일의 경우,
안내는 파일이 그때 그 한도에 맞으면 다음 업데이트가 Apothem 블록을 쓴다고
말하며, 여러분이 남겨 둔 오래된 Apothem 텍스트도 그 한도에 포함됩니다
([Open-Claw](/docs/harnesses/open-claw#rules-in-each-workspace) 참조).
plain 모드에서는 행 뒤에 `Note:` 줄이 이어지고,
이때 행은 예상 경로를 생략하며, JSON 행에는 `files`와 `message`를 담은
`stray_begin` 객체가 추가됩니다.

홈 디렉터리에 스킬을 쓰는 어댑터의 경우, verify는 어느 설치가 썼든 상관없이
예상하는 모든 스킬 폴더가 `SKILL.md`와 함께 존재하는지도 검사하므로, 폴더를
공유하는 도구 중 하나만 설치된 머신도 검증을 통과합니다. 폴더가 누락된 경우,
그리고 Apothem 스킬의 이름을 가진 폴더가 Apothem이 쓰지 않은 무언가에 속한 경우
검증에 실패합니다. 실패한 행은 어느 쪽인지 알려 줍니다. plain 모드에서는 그 뒤에
`Note:` 줄이 이어지고, JSON 행에서는 `user_level` 객체가 `missing`,
`unlisted`, `unproven` 경로와 `message`를 나열합니다. 누락된 폴더를 복원하려면
[`install`](/docs/cli-reference/install)을 실행하세요. 외부 폴더는 이름을 바꾸거나
옮긴 다음 [`update`](/docs/cli-reference/update)를 실행하세요.
`unproven` 폴더는 Apothem이 자신이 썼음을 증명할 수 없는 폴더입니다. 그 폴더를
나열한 설치들이 사라졌거나 Apothem 파일이 없거나 읽을 수 없는 폴더에 있거나,
그 설치들이 더 이상 그 폴더를 나열하지 않습니다. 그리고 그 폴더는 그 설치들이 기록한 파일을
정확히 담고 있지 않습니다([`install`](/docs/cli-reference/install) 참조).
여러분이 만들었거나 편집했거나, 이전 릴리스가 파일을 기록하지 않고 썼을 수
있습니다. 안내는 각 폴더를 알려 주고 설치 경고의 두 가지 진행 방법을 제시합니다.
유지하려면 그 자리에 그대로 두세요. Apothem의 버전을 사용하려면 스킬 폴더 밖으로
옮긴 다음 그 하니스에 대해 `update`를 실행하세요. 프로젝트 범위 하니스의 경우
안내는 `--project`를 doctor가 인용하는 방식대로 셸에 맞게 인용하거나 말로
알려 줍니다. 이 릴리스가 쓰는 내용을 이미 담고 있는 폴더는 설치가 그대로
유지하므로 절대 언급되지 않습니다. verify는 설치된 하니스에 대해서만 unproven
폴더와 unlisted 폴더를 찾으므로, `verify --harness all`은 설치된 하니스 아래에서만
그런 폴더를 알려 줍니다.

검증되었든 아니든, 행 뒤에 안내가 이어질 수 있습니다. Apothem이 쓴 내용은 제자리에
있지만 여러분의 파일 때문에 도구가 그것을 불러오지 못할 때, `Note:` 줄이 그 파일을
알려 주고 JSON 봉투의 `warnings`에는 `"operation": "instruction_override"`를 담은
항목이 추가됩니다([`install`](/docs/cli-reference/install)에서 설명). 그런 파일
하나는
[지원되는 한 도구](/docs/harnesses/codex#compatibility-notes)가 홈 폴더에서
불러오는 `AGENTS.md` 옆에 있는, 텍스트가 담긴 `AGENTS.override.md`입니다. 다른
파일들은 [OpenCode 1](/docs/harnesses/opencode#compatibility-notes)이 구성 폴더에서
불러오는 파일입니다. 자체 `instructions` 목록을 가진 `opencode.jsonc`, 그리고
OpenCode 1이 전혀 불러올 수 없는 `config.json`, `opencode.json` 또는
`opencode.jsonc`입니다. 이 안내는 검사를 실패시키지 않습니다. Apothem 블록이 그
`AGENTS.md`에 없거나, `opencode.json`이 설치가 쓴 항목을 하나도 나열하지 않으면
안내가 없습니다. OpenCode 1이 불러올 수 없는 `opencode.json`에 대한 안내는 설치가
쓰는 프로필 문서에 Apothem 블록이 담겨 있기만 하면 나옵니다.

`--harness all` 스윕은 프로필의 `exclude_harnesses`, 즉 `install`/`update`
일괄 작업이 적용한 것과 같은 제외 항목을 따르므로, verify는 의도적으로 제외된
하니스를 절대 누락으로 보고하지 않습니다. 제외 항목은 `--profile`이 지정되면
그 프로필에서, 그렇지 않으면 기본 프로필에서 가져옵니다. 기본 프로필을 읽을 수
없거나 없으면 전체 레지스트리로 대체됩니다.

## 옵션

| 옵션 | 설명 |
|---|---|
| `--harness NAME` | 검증할 하니스 어댑터, 또는 레지스트리 전체 집합을 뜻하는 `all`(필수). |
| `--profile PATH` | 충실도를 검사할 기준이 되는 공유 프로필 YAML. 이 옵션이 없으면 검사는 순수하게 구조적입니다. |
| `--project PATH` | 프로젝트 범위 하니스의 프로젝트 루트. |
| `--quiet`, `-q` | 정보성 출력을 억제합니다. 오류만 출력됩니다. |
| `--verbose`, `-v` | 추가 진단 출력을 내보냅니다. |
| `--format plain\|json` | 출력 형식(기본값: `plain`). |
| `--json` | `--format json`의 축약형. |
| `--no-color` | 출력에서 ANSI 색상 코드를 비활성화합니다. |
| `-h`, `--help` | 도움말을 표시하고 종료합니다. |

## JSON 출력

```json
{
  "schema_version": 1,
  "status": "success",
  "command": "verify",
  "action": "verified",
  "harness": "claude-code",
  "files_written": [],
  "results": [
    {
      "harness": "claude-code",
      "outcome": "unchanged",
      "operation": "verify",
      "path": "C:\\Users\\Example\\.claude\\settings.json",
      "message": "managed targets verified",
      "installed": true,
      "verified": true
    }
  ],
  "warnings": [],
  "error": null,
  "installed": true,
  "verified": true,
  "output_path": "C:\\Users\\Example\\.claude\\settings.json"
}
```

선택한 하니스 중 하나라도 누락되었거나 유효하지 않으면, `status`는 `error`가
되고, 실패한 결과 행은 `verified: false`를 담으며, 프로세스는 코드 1로
종료합니다.

## 예제

```bash
apothem verify --harness claude-code
apothem verify --harness claude-code --json
apothem verify --harness all --project .
```

## 종료 코드

| 코드 | 의미 |
|---|---|
| 0 | 하니스 검증됨 — 모든 관리 대상이 존재하고 유효함 |
| 1 | 하니스 검증 안 됨 — 관리 대상이 누락되었거나 유효하지 않음 |
| 64 | 사용법 오류: 알 수 없는 옵션이나 명령, 또는 누락되었거나 잘못된 옵션 값. `--json`에서는 이 오류가 코드 `cli.usage`를 담은 JSON 봉투로 출력됩니다. |
