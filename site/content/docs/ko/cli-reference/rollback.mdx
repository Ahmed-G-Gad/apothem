하니스를 기록된 설치 이전의 상태로 복원합니다.

## 개요

```
apothem rollback --harness NAME|all [--install-id ULID | --last] [--yes]
                 [--project PATH]
                 [--quiet|-q] [--verbose|-v]
                 [--format plain|json] [--json] [--no-color]
```

`rollback`은 선택한 각 하니스를 기록된 설치 패스(기본값은 아직 적용된 상태인
가장 최근 설치, 또는 `--install-id`로 지정한 패스) 이전의 상태로 되돌립니다.
따라서 두 번째 `rollback`은 첫 번째 rollback이 되돌린 설치의 바로 앞 설치를
되돌립니다. rollback이나 uninstall이 이미 되돌린 설치를 지정한 `--install-id`는
`rollback.already_reversed`(종료 코드 1)로 거부되며, 아무것도 바뀌지 않습니다.
해당 설치의 원장 기록을 가장 최근 변경부터 차례로 처리하면서 다음을 수행합니다.

- 설치가 덮어쓴 모든 파일과 디렉터리를 설치가 캡처한 백업에서 기록된 경로로
  복원합니다(설치가 교체한 디렉터리는 설치가 그 안에 추가한 파일 없이 정확히
  복원됩니다).
- 설치가 만든 모든 파일과 디렉터리를, 그 설치가 쓴 내용을 아직 그대로 담고
  있는 한 제거합니다. 그 이후 그 경로에 사용자가 만든 파일이나 사용자가 편집한
  파일은 `Warning:` 줄(`--json`에서는 `warnings` 항목)과 함께 남으며, 그런 파일을
  담은 폴더도 마찬가지입니다. 설치가 만든 폴더 안의 빈 폴더는, 사용자가 만든
  것이라도 제거됩니다. 그 줄은 복원 실패 여부와 관계없이 남겨 둔 각 파일을,
  남겨 둔 폴더 안의 파일까지 포함해 나열하며, `warnings` 항목은 이를 `files`로
  나열합니다. 이전 릴리스가 기록한 설치는 무엇을 썼는지 알려 주지 않고,
  rollback은 아무것도 이번 릴리스가 쓰는 내용과 비교하지 않으므로, 그 설치가 만든 것은
  남습니다. 그런 경로마다 rollback이 그것이 Apothem의 것인지 알 수 없다는
  `Warning:` 줄이 생깁니다. 또한 설치가 정리하며 없앤 레거시 레이아웃 경로를
  되돌려 놓습니다.
  현재 릴리스가 더 이상 정리하지 않는 경로(사용자 자신의 파일이 있을 수 있는
  폴더)는 파일이 없는 곳에서만 복원됩니다. 지금 그곳에 있는 모든 파일은
  유지되며, 출력은 사용한 백업을 지목합니다. 쓸 수 없는 파일은 직접 복사하도록
  나열되며, 그 밖의 파일을 하나라도 썼다면 rollback은 2(부분 결과)로 종료합니다.
  지금 링크(심볼릭 링크나 Windows 정션)인 경로, 또는 백업에는 폴더가 있는데
  파일이 있거나 그 반대인 경로는 절대 그것을 거쳐 쓰지 않습니다. 그곳에는
  아무것도 복원되지 않으며, 경로의 백업이 없어진 경우에도 아무것도 복원되지
  않습니다. 그래도 rollback은 0으로 종료하며, 직접 복사할 백업을 지목하는
  `Warning:` 줄(`--json`에서는 `warnings` 항목)을 출력합니다. rollback은 그
  설치의 기록이 보관된 가장 최근 10개(아래 참조) 안에 있는 동안에만 그 설치에
  도달합니다. `apothem backups prune --keep N`은 한 번 `N`개로 정리하며, 다음
  install, update, uninstall 또는 rollback이 다시 10개로 정리합니다. 기록이
  사라진 뒤에도 백업 세트 자체는 남으므로, 그 안의 파일을 직접 복사해 내는 것이
  확실하게 되돌리는 방법입니다.
- 설치가 만든 공유 데이터 저장소(`memory`, `contexts`, `learning`)를 제거합니다.
  단, 설치된 다른 하니스가 아직 사용 중이면 제거하지 않습니다.
- 설치가 만든 디렉터리가 비게 되면 해당 디렉터리를 제거합니다.

다른 설치도 사용하는 홈 디렉터리의 파일이나 폴더(스킬 폴더, 또는
`~/.config/apothem/`)는 공유 데이터 저장소처럼 취급됩니다. rollback은 다른 설치가
아직 그것을 나열하는 동안에는 유지하며, 그것을 사용하는 마지막 설치에 대해서만
복원하거나 제거합니다. 이 설치가 이미 자리에 있는 것으로 발견한 폴더(첫 번째
도구 다음에 설치된 두 번째 도구)는, 그 이후 그 폴더를 놓아 준 설치가 그 폴더를
만들었다면 그 폴더를 사용하는 마지막 설치와 함께 사라지므로, 그 폴더를 만든
도구가 그사이에 다시 설치되었거나 업데이트되었더라도 모든 도구를 롤백하면
아무것도 남지 않습니다. Apothem이 제거한 폴더를 사용자가 (예를 들어 백업에서)
직접 되돌려 놓았다면 그것은 사용자의 것이므로, rollback은 그것을 유지합니다.
rollback은 rollback을 실행할 때의 표기 그대로 홈 경로가 기록된 설치만
되돌립니다. 같은 도구가 다른 표기의 홈 경로로도(홈으로 가는 링크를 거쳐, 또는
Windows나 macOS에서 대소문자를 달리하여) 설치되었다면, 그 설치는 여전히 공유
폴더를 사용하며 그것을 유지합니다. 도구 자체 폴더의 파일은 하나씩 처리됩니다.
그 파일을 처음 쓴 설치를 롤백하면, 다른 설치가 그대로 둔 파일(예: 훅
스크립트)은 제거하고, 다른 설치가 다시 쓴 파일(예: 지침 파일)은 경고와 함께
유지합니다. 그 후 다른 표기의 홈 경로로 `apothem update`를 실행하여, 그 설치가
다시 `apothem verify`를 통과하도록 하세요. 그 표기의 홈 경로로 실행한 rollback은
그 설치도 되돌립니다. 폴더를 사용할 수 있는 설치의 기록을 읽을 수 없으면,
rollback은 어떤 것도 바꾸기 전에 오류와 함께 중단되며 `rollback` 기록을 쓰지
않습니다. 기록을 복구한 다음 다시 실행하세요.

링크가 도구의 폴더를 홈 디렉터리 밖으로 이어 줄 때에도 rollback은 어떤 것도
바꾸기 전에 중단되며 `rollback` 기록을 쓰지 않습니다. 예를 들어 `CODEX_HOME`이나
`XDG_CONFIG_HOME`을 `~/work/tool`처럼 홈 디렉터리 안의 경로로 표기했는데, 설치
이후 `~/work`가 다른 드라이브로 가는 링크가 된 경우입니다. Windows에서는 정션도
링크로 간주됩니다. 오류 메시지는 `rollback
refused: target path crosses a link`이며 링크와 그 링크가 가리키는 폴더를
지목하고, 명령은 먼저 확인을 요청하지 않고 1로 종료합니다. 링크가 홈 디렉터리
안의 폴더를 가리키게 하거나 링크를 폴더 자체로 바꾼 다음, rollback을 다시
실행하세요. 홈 디렉터리 밖의 경로로 표기한 폴더는 그대로 따라갑니다.

rollback이 제거하거나 교체하는 모든 대상은 먼저 Apothem 백업 루트
(`~/.apothem/backups/`)에 복사되므로, 롤백 자체도 수동으로 되돌릴 수 있습니다.
rollback은 이어서 하니스 원장에 `rollback` 기록을 추가합니다. 이전 설치를
롤백하면 그 설치가 기록한 대상만 복원하거나 제거하며, 같은 루트의 원장 활성
설치에서 그 이후의 모든 설치를 제외합니다. 이후 설치가 그 대상 바깥에 추가한
파일은 그대로 남습니다.

원장은 설치 루트마다 가장 최근의 설치 기록 10개(그리고 그 기록이 참조하는
백업)를 보관합니다. 그보다 오래된 설치는 더 이상 id로 롤백할 수 없으며
`rollback.no_record`를 보고합니다.
[`apothem backups prune`](/docs/cli-reference/backups)은 요청 시 이 한도를
낮추며, 최신 설치가 복원 원본으로 삼는 백업은 절대 제거하지 않습니다.

설치가 어떤 파일을 만들었는지 표시하지 않는 이전 릴리스의 설치 기록은, 덮어쓴
파일만 복원하는 방식으로 롤백됩니다.

`--yes`를 제공하지 않으면 하니스마다 확인을 요청합니다. 프롬프트를 띄울 수 없는
경우, 즉 `--format json`(프롬프트 텍스트가 단일 JSON 문서를 손상시킴) 또는
비대화형 셸(TTY 없음)에서는 `--yes`를 제공하지 않는 한 명령이 구조화된
`rollback.confirmation_required` 오류(종료 코드 1)와 함께 처음부터 거부합니다.
`--install-id`와 `--last`는 설치 패스를 선택하며 상호 배타적입니다.

`--harness all` 롤백은 의도적으로 빠짐없이 동작합니다. 등록된 모든 하니스를 대상으로 하며, 프로필의 `exclude_harnesses`가 설치 중에 건너뛰는 하니스도 포함합니다. 설치 전 상태로 되돌리는 것은 정리 작업이므로, 이전에 더 넓은 범위로 수행된 설치가 남겼을 수 있는 기록까지 다룹니다. 기록된 설치가 없는 하니스는 `results`에 `"outcome": "error"` 행으로 실패로 기록되며(JSON 출력 참조), 실행은 나머지 하니스로 계속됩니다. 그런 다음 롤백된 대상이 없으면 명령은 1로 종료하고, 대상이 하나 이상 롤백되었고 실패도 함께 기록된 경우에는 2(부분 결과)로 종료합니다.

## 옵션

| 옵션 | 설명 |
|---|---|
| `--harness NAME` | 롤백할 하니스 어댑터, 또는 레지스트리 전역 집합을 나타내는 `all`(필수). |
| `--install-id ULID` | 지정한 설치 패스가 아직 적용된 상태라면 그것을 롤백합니다. 기본값은 아직 적용된 상태인 가장 최근 설치입니다. |
| `--last` | 아직 적용된 상태인 가장 최근 설치를 롤백합니다(기본 동작을 명시하는 형식). `--install-id`와 상호 배타적입니다. |
| `--yes` | 하니스별 확인 프롬프트를 건너뜁니다. |
| `--project PATH` | 프로젝트 범위 하니스의 프로젝트 루트. 선택한 집합에 프로젝트 범위 어댑터가 포함되면 필수입니다. |
| `--quiet`, `-q` | 정보성 출력을 억제하고 오류만 내보냅니다. |
| `--verbose`, `-v` | 추가 진단 출력을 내보냅니다. |
| `--format plain\|json` | 출력 형식(기본값: `plain`). |
| `--json` | `--format json`의 단축형. |
| `--no-color` | 출력에서 ANSI 색상 코드를 비활성화합니다. |
| `-h`, `--help` | 도움말을 표시하고 종료합니다. |

## JSON 출력

이 예시는 이름이 지정된 단일 하니스에 대한 응답 구조입니다. `--harness all`에서는 `harness`가 `all`이고, `output_path`는 `null`이며, `results`에는 선택된 모든 하니스의 행이 담깁니다.

```json
{
  "schema_version": 1,
  "status": "success",
  "command": "rollback",
  "action": "rolled_back",
  "harness": "claude-code",
  "profile_path": null,
  "project": null,
  "files_written": [],
  "results": [],
  "warnings": [],
  "error": null,
  "output_path": "C:\\Users\\Example\\.claude\\settings.json"
}
```

복원되거나 제거된 각 대상은 `"operation": "rollback"`과 `created` 또는
`updated`인 `outcome`으로 `results`에 나타납니다(`files_written`에도 나타남).
`message`는 해당 경로가 복원되었는지 제거되었는지를 알려 줍니다. 실패한
복원(예: 백업이 삭제된 경우)은 `"outcome": "error"`입니다. 변경 사항을 기록하지
않은 설치는 `"outcome": "skipped"`로 보고됩니다. 아무것도 복원되지 않은 정리 대상
경로(지금 링크이거나, 백업에는 폴더가 있는데 파일이 있거나 그 반대이거나, 그
백업이 없어진 경우)는 `results`의 `skipped` 행이자 `warnings`의 항목이기도 하며,
rollback은 그래도 0으로 종료합니다.

```json
{
  "harness": "claude-code",
  "outcome": "advisory",
  "operation": "rollback",
  "path": "C:\\Users\\Example\\.claude\\commands",
  "message": "left in place: C:\\Users\\Example\\.claude\\commands is now a link, so nothing was restored there; copy what you need from C:\\Users\\Example\\.apothem\\backups\\20261001T000000Z\\claude_code\\.claude\\commands"
}
```

링크에서 거부된 결과는 [`apothem install`](/docs/cli-reference/install#json-output)과
마찬가지로 `detail.symlink`에 링크를, `detail.leads_to`에 그 링크가 가리키는
폴더를 지목합니다.

이름을 지정한 단일 하니스에
일치하는 설치 기록이 없으면 명령은 `"status": "error"`와 함께
`rollback.no_record` 오류를 보고하며, 이미 롤백되었거나 제거된 설치의
`--install-id`는 `rollback.already_reversed`를 보고합니다. 원장이 그 기록을
정리한 뒤에는(위 참조) 그런 id가 대신 `rollback.no_record`를 보고합니다.
`--harness all`에서는 일치하는 기록이 없는
하니스가 대신 `results`의 `"outcome": "error"` 행이 됩니다.

## 예시

```bash
apothem rollback --harness claude-code --last
apothem rollback --harness claude-code --install-id 01J9Z… --yes
apothem rollback --harness cursor --project . --last --json
```

## 종료 코드

| 코드 | 의미 |
|---|---|
| 0 | 롤백 성공, 또는 롤백할 것이 없음(설치가 변경 사항을 기록하지 않음). 정리 대상 경로가 `Warning:` 줄(`--json`에서는 `warnings` 항목)과 함께 그대로 남은 경우도 포함 |
| 1 | 예상된 오류 — 설치 기록 없음, 충돌하는 선택자, 알 수 없는 하니스, 프로젝트 루트 누락, 또는 확인이 거부되었거나 불가능함(`--yes` 없는 비대화형 또는 JSON 모드) |
| 2 | 부분 결과 — 하나 이상의 대상이 롤백되었고 실패도 함께 기록됨(복원 실패, 또는 `--harness all`에서 설치 기록이 없는 하니스) |
| 64 | 사용법 오류: 알 수 없는 옵션이나 명령, 또는 누락되었거나 잘못된 옵션 값. `--json`에서는 오류가 코드 `cli.usage`를 담은 JSON 봉투로 반환됩니다. |
