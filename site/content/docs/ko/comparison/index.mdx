Apothem은 호스트 비종속 AI-하니스 구성 관리자입니다. `~/.config/apothem/profile.yaml`
에 있는 하나의 공유 프로필이 열일곱 개의 하니스 네이티브 구성 표면으로 머티리얼라이즈됩니다.
이 섹션은 당신이 이미 사용하는 대안들과 비교해 Apothem을 어떻게 평가할지에 대한
틀을 제시합니다.

## Apothem의 비교

다른 도구들은 이 문제의 인접한 일부를 해결합니다. **chezmoi**나 **GNU Stow** 같은
파일 기반 구성 관리자는 파일을 배치하거나 템플릿화하지만, 하나의 소스를 각 하니스의
*네이티브* 구성 스키마로 번역하는 일은 결코 하지 않습니다. **rulesync** 같은 도구 간
규칙 동기화 CLI는 Apothem의 열일곱 개보다 많은 도구에서 도구별 네이티브 파일을
생성하며, 동기화되는 단위도 비슷하게 넓습니다. Apothem의 차별점은 **동기화 주위에
배포되는 거버넌스와 라이프사이클 규율**입니다 — 기계적 적합성 게이트, 결정적
파이프라인, 감사 요새, 그리고 가역적이고 검증된 라이프사이클.

| 능력 | Apothem | 파일 구성 관리자 (chezmoi, Stow) | 도구 간 규칙 동기화 (rulesync) | 도구별 네이티브 구성 |
| ---------- | :-----: | :----------------------------------: | :-----------------------------: | :--------------------: |
| 하나의 소스를 많은 도구의 네이티브 스키마로 | 예 — 열일곱 개 하니스 어댑터 | 아니요 — 복사 / 심볼릭 링크, 번역 없음 | 예 | 아니요 — 단일 도구 |
| 동기화되는 단위 | 규칙, 스킬, 훅, 슬래시 명령, MCP | 임의의 파일 | 규칙, 무시, MCP, 명령, 서브에이전트, 스킬, 훅, 권한 | — |
| 거버넌스 코퍼스(동작 규칙에 더해 기계적 적합성 게이트) | 예 — `python -m apothem.conformity.gate` | 아니요 | 아니요 | 아니요 |
| 결정적 계획·리서치 파이프라인 | 예 — `/plan-spec`에서 `/plan-execute`, 13단계 `/research` | 아니요 | 아니요 | 아니요 |
| 탐지하고 시정하는 감사 요새 | 예 — 11개 명령 스윕, `/fortress` 재감사 루프 | 아니요 | 아니요 | 아니요 |
| 공급망에 대해 강화된 릴리스 | 예 — SBOM, Sigstore, SLSA, Scorecard 목표 | 아니요 | 경우에 따라 | 아니요 |
| 가역적이고 검증된 라이프사이클 | 예 — 백업, `apothem verify --json`, 고아 없는 제거 | 경우에 따라 | 경우에 따라 | — |

경쟁자가 더 강한 곳에서는 그것을 직접 거명합니다. **rulesync**는 더 많은 도구에
도달하고 비슷하게 넓은 동기화 단위를 갖추며, 여러 동기화 도구가 네이티브 스키마를
머티리얼라이즈합니다. Apothem은 도구의 단순 개수를, 동기화 주위에 배포되는 거버넌스·감사·
라이프사이클 규율 — 적합성 게이트, 결정적 `/plan` 및 `/research` 파이프라인, 11개
명령의 감사 요새, 지속적 메모리, 그리고 가역적이고 검증된 라이프사이클 — 과
맞바꾸며, 이는 규칙 동기화 도구가 갖추지 못한 것입니다.

## 비교하는 방법

세 가지 축을 따라 비교하세요.

1. **진실의 원천.** 당신의 규칙, 에이전트, 명령, 설정은 어디에 있는가? Apothem은
   하나의 공유 코퍼스를 유지하고 거기서 각 하니스의 네이티브 형식을 렌더링합니다.
   손으로 유지하는 구성은 도구마다 사본을 보관합니다.
2. **드리프트 비용.** 규칙 하나를 바꾸면 무슨 일이 일어나는가? Apothem은
   `apothem update`를 실행하면 변경을 설치된 각 하니스로 전파합니다. 손으로 유지하는
   구성은 각 도구의 네이티브 파일을 따로 편집하고 기억에 의존해 정렬을 유지하도록
   요구합니다.
3. **검증.** 각 하니스가 올바르게 구성되었음을 어떻게 아는가? Apothem에는
   `apothem verify --harness <name>`과 `apothem doctor`가 함께 제공됩니다. 손으로
   유지하는 구성에는 내장된 검증이 없습니다.

## 기능 매트릭스

이 매트릭스는 운영자가 가장 먼저 의지하는 두 가지 대안과 비교해 Apothem을 대조합니다 —
각 하니스의 네이티브 구성을 손으로 유지하는 것, 그리고 그 파일들을 범용 dotfiles
관리자로 관리하는 것입니다.

| 능력 | 손으로 유지하는 구성 | dotfiles 관리자 | Apothem |
| ---------- | ---------------------- | --------------- | ------- |
| 단일하고 공유되는 진실의 원천 | 아니요(도구마다 사본 하나) | 아니요(프로필이 아니라 파일을 추적) | 예(프로필 하나) |
| 하니스 네이티브 형식 렌더링 | 수동 | 아니요 | 예(어댑터별 머티리얼라이저) |
| 하니스 간 드리프트 방지 | 수동 정렬 | 파일 동기화만 | 예(`apothem update`) |
| 하니스별 설치/제거 | 수동 | 부분적(링크/복사) | 예(`install` / `uninstall`) |
| 내장 검증 | 없음 | 없음 | 예(`verify` / `doctor`) |
| 도구별 형식 번역 | 없음 | 없음 | 예(`.mdc`, `.toml`, 임베디드 `.md`) |
| 단일 입력에서 열일곱 개 하니스 | 아니요 | 아니요 | 예 |
