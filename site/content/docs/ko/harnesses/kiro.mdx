**공급업체:** AWS
**설치 이름:** `kiro`
**상태:** GA
**네이티브 구성:** `<project>/.kiro/steering/apothem-rules.md`

## 설치

```bash
apothem install --harness kiro --project /path/to/project
```

어댑터는 공유 Apothem 규칙과 거버넌스 표면으로부터 프로젝트 범위의 Kiro
스티어링 파일 하나를 작성합니다.

**작성되는 파일:** `<project>/.kiro/steering/apothem-rules.md`

## 프로필에서 네이티브 구성으로의 매핑

어댑터는 Apothem의 공유 프로필을 읽고 매 `apothem install` 또는 `apothem update`
실행마다 프로젝트 스티어링 파일을 렌더링합니다. 공유 프로필이 진실의
원천입니다. 생성된 파일에 대한 프로젝트 로컬 편집은 다음 동기화가 Apothem 관리
콘텐츠를 교체하기 전에 백업됩니다.

이 파일은 `inclusion: always` 프런트매터로 시작합니다. Kiro는 inclusion 구성이
파일의 첫 번째 콘텐츠여야 한다고 요구하기 때문입니다. Apothem 관리 블록이 그
뒤에 오며, 블록 뒤에 여러분이 추가한 텍스트는 매 동기화 때 유지됩니다.

## 호환성 참고 사항

Kiro의 스티어링 표면은 `.kiro/steering/` 아래에서 프로젝트 범위로 지정됩니다.
어댑터는 `inclusion: always` 프런트매터가 있는 전용 `apothem-rules.md` 스티어링
파일을 작성하며, 운영자가 작성한 Kiro의 기초 파일(`product.md`, `tech.md`,
`structure.md`)을 절대 덮어쓰지 않습니다. Kiro 스펙(`.kiro/specs/`)과 에이전트
훅은 운영자 소유입니다. Apothem은 이를 작성하지 않습니다.

## 검증

```bash
apothem verify --harness kiro --project /path/to/project
```

verify 명령은 다음을 확인합니다.

1. 네이티브 구성이 예상 경로에 존재합니다.
2. 각 관리 대상이 존재하고, 관리되는 파일은 비어 있지 않으며, JSON 또는 YAML 구성은 파싱됩니다. 설치된 파일이 그 프로필과도 일치하는지 확인하려면 `--profile PATH`를 추가하세요.
3. 어댑터별 검증 루틴이 성공을 보고합니다.

## 업데이트

```bash
apothem update --harness kiro --project /path/to/project
```

현재 공유 프로필 상태에서 프로젝트 스티어링 파일을 다시 도출합니다.

## 제거

```bash
apothem uninstall --harness kiro --project /path/to/project
```

어댑터가 작성한 네이티브 구성 파일을 제거합니다.
공유 프로필 YAML과 Apothem 엔진은 영향을 받지 않습니다.

## 적합성 게이트

```bash
python -m apothem.conformity.gate --all .
```

## 문제 해결

| 증상 | 해결 |
|---------|-----|
| 구성 파일을 찾을 수 없음 | `apothem install --harness kiro --project /path/to/project`를 다시 실행 |
| 검증 실패 | `apothem update --harness kiro --project /path/to/project`를 실행한 다음 다시 검증 |
| 예기치 않은 구성 내용 | `~/.config/apothem/profile.yaml` 또는 `--profile PATH`를 확인한 다음 `apothem update --harness kiro --project /path/to/project`를 다시 실행 |

## 구성 노브

| 플래그 | 기본값 | 설명 |
|------|---------|-------------|
| `--dry-run` | `false` | 파일을 작성하지 않고 설치를 미리 봅니다. |
