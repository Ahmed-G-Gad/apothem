일반적인 Apothem 설치 및 런타임 문제에 대한 해결책입니다.

## 설치 문제

### Python 3.10+를 찾을 수 없음

설치 프로그램은 `python3`, `python`, 그리고 버전이 지정된 이름(`python3.14`부터 `python3.10`까지)을 탐색하며 — Microsoft Store 런처 심은 거부합니다 — 3.10 하한선을 충족하는 후보가 없으면 `No Python >= 3.10 found in PATH`라는 메시지와 함께 중단합니다. npx 심은 `APOTHEM_PYTHON`이 설정되어 있으면 이를 먼저 탐색하고, 그다음 `python3`, `python`, `py -3`을 탐색하며, 조건을 충족하는 후보가 없으면 자체 메시지를 출력하고 종료 코드 1로 종료합니다. python.org 또는 OS 패키지 저장소에서 CPython 3.10 이상을 설치하고, `python3 --version`(또는 Windows에서 `py -3 --version`)이 최소 3.10을 보고하는지 확인한 다음, 다시 실행하세요.

### 런타임 종속성 누락: click, rich

엔진은 대부분의 서드파티 종속성을 소스 트리 내부에 벤더링하지만, `click`과 `rich`는 설치 프로그램이 선택한 인터프리터에서 임포트 가능해야 합니다. 둘 중 하나가 누락되면 설치 프로그램은 그것의 이름을 알려 주고 사용자를 대신해 설치하겠다고 제안합니다.

```text
! Missing Python prerequisites under <python>: click rich
  Install click rich under <python> now? [y/N]
```

프롬프트를 수락하면 설치 프로그램이 해당 인터프리터에서 `pip install`을 실행합니다. 프롬프트를 건너뛰려면 `--yes`(PowerShell에서는 `-Yes`)를 전달하거나 `APOTHEM_AUTO_INSTALL_DEPS=1`을 설정하여 자동으로 설치하세요. 거부하거나 — `pip`을 사용할 수 없거나, OS 패키지 관리자를 선호하는 경우 — 명명된 패키지를 직접 설치한 다음(예: Debian 계열 호스트에서 `python3-click` 및 `python3-rich`, 또는 `pip install click rich`) 다시 실행하세요.

### 설치 프로그램 실행 후 `apothem`을 찾을 수 없음

설치 프로그램은 소스 트리를 `~/.apothem`에 배치하고, 기본적으로 `apothem` 심을 `~/.local/bin`(POSIX) 또는 `%LOCALAPPDATA%\Microsoft\WindowsApps`(Windows)에 씁니다. `APOTHEM_BIN_DIR`로 그 폴더를 바꿀 수 있습니다. `PATH`는 수정하지 않습니다. `apothem`을 찾을 수 없다면 그 디렉터리가 `PATH`에 없는 것입니다. 디렉터리를 추가하거나, 심을 전체 경로로 실행하세요. 설치 프로그램은 완료될 때 그 경로를 출력합니다. 심을 쓰지 않았을 때는 현재 폴더를 `sys.path`에서 제외한 채 엔진을 시작하는 명령을 출력하므로, 배너에서 그 명령을 복사하세요. npx 형식(`npx @ahmed-g-gad/apothem <command>`)은 `PATH` 항목이 필요 없습니다.

### `/plugin marketplace add`가 실패함

`/plugin marketplace add ahmed-g-gad/apothem`은 GitHub에서 마켓플레이스 목록을 가져옵니다. 실패하는 경우, 머신이 `https://github.com/ahmed-g-gad/apothem`에 도달할 수 있는지(네트워크, 프록시, 또는 방화벽 규칙) 확인한 다음 다시 시도하세요. 부분 가져오기 상태에서 마켓플레이스가 이전에 추가된 경우, `/plugin install apothem@apothem`을 실행하기 전에 제거하고 다시 추가하세요.

### 플러그인 호스트의 마켓플레이스 추가가 시간 초과됨

마켓플레이스를 추가하는 플러그인 호스트의 명령은 해당 저장소를 클론하며 30초가 지나면 포기합니다. 이 저장소의 전체 클론은 WSL 아래의 Windows 드라이브처럼 느린 디스크에서 그보다 오래 걸릴 수 있으며, 이전에 받은 전체 클론 때문에 이후의 새로 고침이 시간 초과될 때 플러그인이 오래된 버전에 머물 수도 있습니다. 플러그인에 필요한 두 폴더만 가져오세요:

```bash
codex plugin marketplace remove apothem
codex plugin marketplace add ahmed-g-gad/apothem --sparse .agents/plugins --sparse plugins/apothem
codex plugin add apothem@apothem
```

그러면 호스트의 플러그인 목록에 `apothem@apothem`의 현재 버전이 표시됩니다.

### npx가 오래된 버전을 제공함

`npx`는 다운로드된 패키지를 캐시합니다. `npx @ahmed-g-gad/apothem --version`이 현재 릴리스보다 이전 버전을 보고하는 경우, 캐시를 지우거나 dist-tag를 고정하세요.

```bash
npx clear-npx-cache
npx @ahmed-g-gad/apothem@latest --version
```

### 설치 프로그램 중단: 메인테이너 공개 키가 로컬 키링에 없습니다

모든 네트워크 설치는 cosign이 있든 없든 서명된 릴리스 태그를 검증하며, 서명 키가 키링에 없으면 중단합니다. 키를 한 번 가져오고, 지문이 `5C89 98F9 F241 7204 45D3  F28B 7039 6FED 9C63 4163`인지 확인한 다음, 설치 프로그램을 다시 실행하세요:

```bash title="macOS · Linux · WSL2 · BSD — import the key once"
curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import
gpg --fingerprint 70396FED9C634163
```

```powershell title="Windows · PowerShell — import the key once"
& "$env:ProgramFiles\Git\bin\bash.exe" -c 'curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import && gpg --fingerprint 70396FED9C634163'
```

Windows에서는 위와 같이 Git의 `bash`를 통해 가져오세요. `git verify-tag`는 Git for Windows에 포함된 `gpg`의 키링을 읽습니다. [cosign](https://docs.sigstore.dev/cosign/system_config/installation/)을 설치해도 키 가져오기를 대신하지는 않습니다. cosign이 `PATH`에 있으면 설치 프로그램은 태그뿐 아니라 서명된 릴리스 아카이브도 검사합니다. `gpg`가 없는 호스트는 `APOTHEM_VERIFY=checksum`과 `APOTHEM_ALLOW_UNVERIFIED=1`로 설치할 수 있지만, 이 모드는 릴리스를 검증하지 않습니다([설치 프로그램 중단: 체크섬 모드에는 두 번째 변수가 필요함](#the-installer-stops-checksum-mode-needs-a-second-variable) 참조).

### 설치 프로그램 중단: gpg를 찾을 수 없음

GnuPG를 설치하거나, Windows에서는 `git verify-tag`가 실행하는 `gpg`를 포함한 Git for Windows를 설치하세요. 그런 다음 위와 같이 메인테이너 키를 가져오고 설치 프로그램을 다시 실행하세요.

### 설치 프로그램 중단: 태그가 메인테이너 키로 서명되지 않음

메시지는 "Tag ... is signed by the key ..."이며, 태그에 서명한 키를 지목합니다. 태그의 서명 자체는 유효하지만, 그 키는 [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md#maintainer-signing-key)가 게시하는 키가 아닙니다. Apothem 릴리스 태그는 그 키로만 서명되므로, 이를 변조 가능성으로 취급하세요. 설치하지 말고 SECURITY.md에 안내된 채널로 신고하세요. 자체 키로 서명한 포크는 여기서 멈추는 것이 정상입니다.

### 설치 프로그램 중단: cosign이 릴리스 서명을 확인하지 못함

먼저 메시지 끝의 `cosign said:` 텍스트를 읽으세요.

- 네트워크, 프록시 또는 신뢰 루트 오류는 cosign이 Sigstore에 도달하지 못했다는 뜻입니다. 온라인 상태일 때 다시 시도하거나, cosign을 업그레이드하거나, 메인테이너 키만으로 릴리스 태그를 검사하는 `APOTHEM_VERIFY=signature`로 설치하세요.
- `APOTHEM_REPO`로 지정한 포크는 여기서 멈추는 것이 정상입니다. 설치 프로그램은 Apothem 자체의 릴리스 워크플로만 받아들입니다.
- "expected GitHub Workflow SHA not found in certificate"는 cosign이 검증한 인증서가 서명된 태그가 가리키는 커밋이 아닌 다른 커밋에서 실행된 작업에 발급되었다는 뜻이므로, 그 인증서는 `SHA256SUMS`를 해당 커밋에 묶지 않습니다. 설치하지 말고 [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md)에 안내된 채널로 신고하세요.
- Apothem 자체 릴리스에서 ID 또는 서명이 일치하지 않는다면 `SHA256SUMS`가 이 태그에 대해 Apothem의 릴리스 워크플로로 서명되지 않았다는 뜻입니다. 설치하지 말고 [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md)에 안내된 채널로 신고하세요.

설치 프로그램이 대신 번들을 다운로드하지 못했다고 말한다면 연결을 확인하세요. 릴리스가 번들을 게시하지 않는다면 `APOTHEM_VERIFY=signature`로 설치하세요.

### 설치 프로그램 중단: 서명된 태그가 릴리스 태그가 아님

메시지는 "the signed tag object is not the vX.Y.Z release tag"입니다. 태그에 메인테이너 키의 서명이 있지만, 서명된 객체는 다른 태그를 지목하므로, 다른 릴리스의 서명된 태그가 이 이름으로 다시 지정된 것입니다. 이를 변조 가능성으로 취급하세요. 설치하지 말고 [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md)에 안내된 채널로 신고하세요. `APOTHEM_ALLOW_UNVERIFIED=1`은 이 검사를 우회하지 않지만, 그 변수는 서명되지 않은 태그나 다른 키로 서명된 태그를 통과시키므로, 이 검사는 메인테이너 키의 서명이 있는 태그만 보호합니다.

### 설치 프로그램 중단: 체크섬 모드에는 두 번째 변수가 필요함 [#the-installer-stops-checksum-mode-needs-a-second-variable]

체크섬 모드는 릴리스를 검증하지 않습니다. SHA256SUMS는 아카이브와 같은 릴리스에서 오므로, 일치한다는 것은 다운로드가 손상되지 않았다는 것만 보여 줍니다. 릴리스의 파일을 바꿀 수 있는 사람은 둘 다 바꿀 수 있습니다. 그래서 `APOTHEM_VERIFY=checksum`은 `APOTHEM_ALLOW_UNVERIFIED=1`도 설정되어 있을 때만 실행됩니다. 이를 받아들인다면 둘 다 설정하거나, `gpg`(및 cosign)를 설치하고 `APOTHEM_VERIFY=checksum` 없이 실행하세요.

### 설치 프로그램 중단: APOTHEM_HOME의 폴더가 Apothem 설치가 아님

설치 프로그램은 Apothem 설치가 아닌 다른 것을 담은 폴더를 대체하지 않습니다. 그 폴더를 다른 곳으로 옮기거나, `APOTHEM_HOME`이 다른 폴더를 가리키게 하거나, `--yes`(PowerShell에서는 `-Yes`)로 다시 실행하세요. `--yes`를 사용하면 설치 프로그램은 폴더 전체를 바꾸지 않고 그대로, 그 옆의 새 폴더 `<APOTHEM_HOME>.before-apothem-<time>` 안으로 옮기고(안에서 원래 이름을 유지합니다), 그 위치를 알려 준 뒤 새로 설치합니다. 다른 프로젝트의 git 클론도 그런 폴더로 간주됩니다. `<APOTHEM_HOME>.before-apothem-<time>`과 같은 이름에 설치 프로그램의 프로세스 ID를 붙인 이름이 둘 다 이미 있으면, 설치 프로그램은 무엇이든 옮기기 전에 "Could not move the existing ... aside; nothing was changed"와 함께 중단합니다. 둘 중 하나의 이름을 바꾸거나 제거한 다음 다시 실행하세요.

### 설치 프로그램 중단: APOTHEM_HOME이 심볼릭 링크임

메시지는 "is a symbolic link"입니다(Windows에서는 심볼릭 링크 또는 정션). 폴더를 대체하면 링크가 이끄는 폴더가 아니라 링크가 대체되므로, 설치 프로그램은 이를 거부합니다. `APOTHEM_HOME`을 링크가 이끄는 폴더로 설정한 다음 다시 실행하세요. 링크 뒤에 있는 기존 git 클론은 여전히 제자리에서 업데이트됩니다.

### 설치 프로그램 중단: git 클론에 로컬 작업이 있음

git 클론을 릴리스 아카이브로 대체하려면 `--yes`가 필요하며, 클론에 잃게 될 로컬 작업이 있으면 그때도 설치 프로그램은 거부합니다. 로컬 작업이란 추적되는 파일의 변경, stash, 원격에 없는 커밋, 또는 클론의 소스 트리에 있는 추적되지 않는 파일입니다. 그 작업을 커밋하고 푸시하거나 다른 곳으로 옮긴 다음 다시 실행하세요. 이 검사는 `--dry-run`에서도 실행됩니다. 클론에 그런 작업이 없으면 `--yes`가 클론을 대체하고 클론 자체의 트리를 `<APOTHEM_HOME>.before-apothem-<time>/<name>`에 보관합니다. 여기서 `<name>`은 `APOTHEM_HOME`의 마지막 부분입니다. 설치 프로그램이 그 경로를 출력하며, 더 이상 필요 없을 때 여러분이 그 폴더를 삭제하면 됩니다.

### 설치 프로그램 중단: 기존 클론이 업데이트가 그대로 신뢰하게 될 방식으로 설정되어 있음 [#the-installer-stops-the-existing-clone-is-set-up-in-a-way-the-update-would-trust]

기존 클론으로 가져오기 전에 설치 프로그램(과 업데이트 스크립트)은 클론이 어떻게 설정되어 있는지 검사합니다. `--dry-run`도 이 검사를 합니다. "has changes to tracked files"는 파일이 assume-unchanged 또는 skip-worktree로 표시되어 git에서 변경이 숨겨져 있을 때에도 나타납니다. `git update-index --no-assume-unchanged <file>` 또는 `git update-index --no-skip-worktree <file>`을 실행한 다음, 그 변경을 커밋하거나 stash하세요. "is not the work tree of its git clone"은 git이 `APOTHEM_HOME`에서 작업 트리를 찾지 못한다는 뜻이며, 클론의 git 설정이 `core.bare`를 `true`로 설정한 경우가 그렇습니다. 클론이 `APOTHEM_HOME`에 체크아웃되도록 그 값을 `false`로 설정하세요. 체크아웃을 다른 폴더로 보내는 `core.worktree` 설정은 제자리 업데이트가 받아들이지 않는 설정으로 보고됩니다(아래 참조).

"own git config sets `<key>`, which an update in place does not accept in a clone's own config"는 클론의 `.git/config`에 있는 설정, 또는 클론에 `.git/config.worktree`가 있다면 그 파일에 있는 설정을 지목합니다. 제자리 업데이트는 그곳에서 다음 설정만 받아들입니다(섹션과 키는 대소문자를 구분하지 않고 비교합니다).

- `git clone`과 `git init`이 전체 클론에 대해 쓰는 설정: `core.repositoryformatversion`, `core.filemode`, `core.bare`, `core.logallrefupdates`, `core.symlinks`, `core.ignorecase`, `core.precomposeunicode`, `core.longpaths`, `extensions.objectformat`, `extensions.refstorage`(값이 `files` 또는 `reftable`일 때만), `extensions.worktreeconfig`, `remote.origin.url`, `remote.origin.fetch`, `remote.origin.tagopt`
- git과 편집기가 추가하는 브랜치 설정 `branch.<name>.<key>`. 단, `branch.<name>.remote`와 `branch.<name>.pushremote`는 정확히 `origin`이어야 합니다.
- `user.name`, `user.email`, `maintenance.auto`, `maintenance.strategy`, `pull.rebase`, `pull.ff`

그 밖의 설정은 업데이트를 중단시킵니다. 그런 설정은 git이 프로그램을 실행하게 하거나, 다른 곳에서 설정, 훅, 속성 또는 객체를 읽게 하거나, 다른 곳에 연결하게 할 수 있기 때문입니다. `--mirror`, `--sparse`, `--recurse-submodules`로 만들었거나 `origin`이 아닌 이름의 원격이 있는 클론도 여기서 멈추며, `--filter`로 만든 부분 클론도 마찬가지입니다. 이 경우 메시지는 `remote.origin.promisor`를 지목합니다. git이 클론을 읽는 동안 누락된 객체를 스스로 원격에서 가져오기 때문입니다. `--filter` 없이 다시 클론하세요. 메시지가 지목하는 파일에서 설정을 제거한 다음(예: `git config --file ~/.apothem/.git/config --unset-all <key>`) 다시 실행하세요. `--unset-all`은 두 번 이상 들어 있는 설정도 제거합니다. 브랜치의 `remote` 또는 `pushremote`는 대신 `origin`으로 설정하세요(예: `git config --file ~/.apothem/.git/config branch.main.remote origin`). "own git attributes name a filter or diff driver"는 `.git/info/attributes`를 지목합니다. `filter=` 또는 `diff=` 설정을 제거하세요. git은 파일을 읽는 동안 필터를 실행하고, `git diff`는 diff 드라이버의 텍스트 변환(`textconv`)을 실행하므로, 여러분 자신의 git 설정이나 시스템 git 설정이 정의한 드라이버가 클론의 파일에서 실행될 수 있습니다.

"which is not a plain file"은 `.git/info/attributes`, `.git/config` 또는 `.git/config.worktree`가 폴더, 명명된 파이프 또는 다른 특수 파일이거나, Windows에서 링크일 때 그 파일을 지목합니다. git은 그런 파일에서 검사가 읽는 것과 다른 텍스트를 읽을 수 있습니다. 일반 파일로 바꾸거나 제거한 다음 다시 실행하세요.

"has a setting whose name holds a line break"는 메시지가 지목하는 파일의 섹션 이름에 캐리지 리턴이 들어 있다는 뜻입니다. git은 이를 결코 쓰지 않으며, 읽는 쪽에서 그 이름을 두 개의 설정으로 받아들일 수 있습니다. 텍스트 편집기에서 파일을 열고 그 섹션을 제거한 다음 다시 실행하세요.

"borrows objects from another repository"는 `--reference` 또는 `--shared`로 만든 클론처럼 클론에 `objects/info/alternates` 또는 `objects/info/http-alternates` 파일이 있다는 뜻입니다. 그러면 git은 설치 프로그램이 검사하지 않는 설정 아래에서 그 다른 저장소의 객체를 읽게 됩니다. `git -C ~/.apothem repack -a -d`를 실행해 객체를 클론으로 복사하고, 메시지가 지목하는 파일을 제거한 다음 다시 실행하세요.

"keeps submodule repositories in ..."과 "holds a submodule at ..."은 클론에 서브모듈이 있다는 뜻으로, 첫 번째 메시지가 지목하는 폴더에 보관되어 있거나 두 번째 메시지가 지목하는 경로에 인덱스로 기록되어 있습니다. 릴리스 트리에는 서브모듈이 없으며, git은 설치 프로그램이 검사하지 않는 자체 설정을 가진 서브모듈 안에서 실행될 수 있습니다. 클론에서 서브모듈과 그 폴더를 제거하거나 클론을 다른 곳으로 옮긴 다음 다시 실행하세요. `--yes`로 클론을 대체할 때도 `git status`가 로컬 작업을 찾기 전에 이 검사를 합니다. 클론의 git 훅은 업데이트 중에 결코 실행되지 않습니다.

### 설치 프로그램 중단: 클론의 .gitattributes 파일이 추적되지 않거나, 변경되었거나, 드라이버를 지목함

git은 파일을 비교하고 체크아웃하는 동안 작업 트리의 `.gitattributes` 파일을 적용하며, 그런 파일은 git이 프로그램을 실행하게 만들 수 있습니다. 그런 명령을 실행하기 전에, 설치 프로그램과 업데이트 스크립트는 클론의 어느 폴더에 있든, 이름에 대문자가 어떻게 섞여 있든, 커밋된 것과 다른 `.gitattributes` 파일이 있으면 멈추고, git이 추적하지 않는 git 저장소가 클론 안에 있어도 멈춥니다. git이 그 안의 `.gitattributes` 파일도 읽기 때문입니다. `--dry-run`과 `--yes`도 이 검사를 합니다. 클론이 그곳의 파일을 추적하지 않는 한, 어떤 릴리스도 쓰지 않는 엔진 자체의 데이터 폴더(`backups`, `state`, `plans`, `memory`, `contexts`, `learning`, `providers`)는 읽지 않습니다.

- "has a .gitattributes file that git does not track, at ..."은 무시된 파일과 추적되지 않는 폴더 안의 파일을 포함해 git이 추적하지 않는 파일을 지목합니다. 그 파일을 제거한 다음 다시 실행하세요.
- "has a changed .gitattributes file at ..."은 내용이 커밋된 사본과 다르거나, 변경이 스테이징되었거나, 링크 또는 폴더인 추적 파일을 지목합니다. 그 변경을 여러분이 했다면 커밋된 사본을 되돌린 다음(예: `git -C ~/.apothem checkout HEAD -- <path>`) 다시 실행하세요.
- "has a .gitattributes file at ... that names a filter or diff driver (filter= or diff=)"는 커밋된 사본이나 작업 트리의 사본이 주석 밖에서 드라이버를 지목하는 추적 파일을 지목하며, 드라이버를 지목하는 매크로(`[attr]` 줄)도 포함됩니다. git은 클론을 읽는 동안, 여러분 자신의 git 설정이나 시스템 git 설정이 정의할 수 있는 그 드라이버를 실행하게 됩니다. 그 설정을 제거하고 변경을 커밋한 다음 다시 실행하세요. 여러분 자신의 속성 파일이나 시스템 속성 파일에서만 정의하는 매크로는 해당하지 않습니다. 실행 중에 git은 클론 바깥의 속성 파일을 읽지 않으므로, 그런 매크로는 그곳에서 어떤 드라이버도 지목하지 않습니다.
- "has a .gitattributes file at ... whose committed copy git could not read"는 클론의 git 폴더에 있는 사본이 누락되었거나 손상되었거나, 그 바이트가 ID와 일치하지 않는다는 뜻입니다. git은 읽을 때 이를 검사하지 않습니다. 그러면 설치 프로그램은 파일의 내용을 검사할 수 없지만, git은 여전히 작업 트리의 사본을 적용합니다. `git -C ~/.apothem fsck`를 실행해 무엇이 손상되었는지 확인하고, 클론을 복구하거나 다른 곳으로 옮겨 새로 설치한 다음 다시 실행하세요.
- "Could not run git to read the committed .gitattributes files in ..."은 `install.ps1`과 `update.ps1`에서만 나옵니다. 여러분의 PowerShell 세션에서 `git`이 함수나 스크립트(예: 프로필의 래퍼)이고, 설치 프로그램이 파일을 읽는 데 쓸 git 프로그램이 `PATH`에 없는 경우입니다. `Get-Command git -CommandType Application`이 git을 찾도록 git의 폴더를 `PATH`에 추가한 다음 다시 실행하세요.
- "holds a git repository that git does not track, at ..."은 자체 `.git`이 있는 폴더를 지목합니다. git은 그런 폴더 안의 아무것도 나열하지 않으므로 그곳의 `.gitattributes` 파일은 보이지 않지만, git은 업데이트가 그곳에 쓰는 파일에 그것을 적용합니다. 릴리스 트리에는 그런 폴더가 없습니다. 폴더를 클론 밖으로 옮긴 다음 다시 실행하세요.

그 파일이나 변경을 여러분이 만들지 않았다면, 다른 누군가가 클론에 쓸 수 있는 것입니다. 클론을 다른 곳으로 옮기고, 새로 설치하고, `APOTHEM_HOME`이 여러분만 쓸 수 있는 폴더인지 확인하세요.

### 설치 프로그램 중단: git이 추적하지 않는 src 아래의 파일

메시지는 "has files under src that git does not track, and the engine could load them:"이며 각 파일을 나열합니다(처음 20개, 그다음 나머지 개수). 엔진은 클론의 `src` 폴더에서 실행되므로, 그곳의 추가 파일이 엔진의 일부로 실행될 수 있습니다. 무시된 파일도 해당하며, 소스 옆의 `.pyc` 파일도 마찬가지입니다. `Src` 또는 `SRC`라는 폴더도 `src`로 간주됩니다. Windows와 macOS는 그 이름으로도 그 폴더를 찾기 때문입니다. 클론의 편집 가능한 `pip install`은 `src/apothem.egg-info`를 쓰고, 파일 관리자는 `.DS_Store` 또는 `desktop.ini`를 쓸 수 있습니다. 파일을 `~/.apothem/src` 밖으로 옮긴 다음 다시 실행하세요. 아무것도 변경되지 않았습니다. 이 검사는 가져오기 전에, 제자리 업데이트와 드라이 런에서 실행됩니다. Python의 캐시 폴더(`__pycache__`)는 해당하지 않습니다. 체크아웃 후, 그리고 엔진이 클론에서 처음 실행되기 전에, 업데이트가 `src` 아래의 모든 `__pycache__` 폴더를 제거하므로 업데이트 이전의 캐시된 바이트코드는 로드되지 않습니다.

"Could not remove the Python cache folders (__pycache__) under ..."는 그 제거가 실패했다는 뜻입니다. 예를 들어 그 폴더 중 하나의 파일이 다른 사용자 소유이거나, Windows에서 다른 프로그램에 열려 있는 경우입니다. 클론은 이미 새 릴리스로 체크아웃되어 있습니다. 그 폴더들을 직접 제거한 다음 다시 실행하세요.

### 설치 프로그램 중단: 다른 실행이 잠금을 보유함 [#the-installer-stops-another-run-holds-the-lock]

설치, 업데이트, 제거 스크립트의 각 실행은 실행되는 동안 `APOTHEM_HOME` 옆에 잠금(`<APOTHEM_HOME>.lock`, 즉 기본값으로 `~/.apothem.lock`)을 보유합니다. `apothem install`, `apothem update`, `apothem uninstall` 명령은 이 잠금을 잡지 않습니다. "Another Apothem install, update or uninstall is running on ..." 메시지는 두 번째 실행이 잠금이 보유된 것을 발견했다는 뜻입니다. 다른 실행이 끝날 때까지 기다린 다음 다시 실행하세요. 실행 중인 것이 없다면 메시지가 지목하는 잠금을 제거한 다음 다시 실행하세요.

- "was left by an Apothem run that did not finish (process N is no longer running)"와 "exists but names no running process"는 실행이 잠금을 해제하기 전에 종료되었다는 뜻입니다. Apothem 설치, 업데이트 또는 제거가 실행 중이 아닌지 확인하고, 잠금을 제거한 다음 다시 실행하세요. 설치 프로그램은 잠금을 대신 제거하지 않습니다. POSIX에서 잠금은 폴더이며(`rm -rf ~/.apothem.lock`), Windows PowerShell에서는 실행이 끝날 때 Windows가 삭제하는 파일입니다.
- "is the lock file of an Apothem PowerShell run"은 Git Bash, MSYS2, Cygwin 또는 WSL 아래의 POSIX 스크립트가 PowerShell 실행이 보유한 파일을 발견했을 때 나옵니다. Windows는 실행이 끝나면 그 파일을 제거하고, 실행 중에는 아무도 제거하지 못하게 합니다. 그 실행이 끝날 때까지 기다리세요. Apothem 설치, 업데이트 또는 제거가 실행 중이 아니라면 파일을 제거한 다음 다시 실행하세요. 다른 시스템에서는 메시지가 "is a file where the Apothem lock folder belongs"입니다. 활성 실행이 없다면 파일을 제거한 다음 다시 실행하세요.
- "was made by an Apothem run in another environment"는 잠금 폴더가 다른 환경의 프로세스를 지목한다는 뜻입니다. 예를 들어 실행이 Git Bash 아래에 있을 때의 WSL, WSL이나 MSYS2 아래에 있을 때의 Git Bash, 또는 다른 컨테이너입니다. 그 프로세스는 여기서 검사할 수 없습니다. 그 실행이 끝날 때까지 기다리고, 어디에서도 Apothem 설치, 업데이트 또는 제거가 실행 중이지 않을 때만 잠금을 제거하세요.
- POSIX 스크립트는 `sudo` 아래의 실행처럼 다른 사용자에게 속한 프로세스를 실행 중으로 간주하므로, 그 잠금은 보유된 것으로 읽힙니다. PowerShell은 POSIX 스크립트(예: Git Bash 아래)가 만든 잠금 폴더의 프로세스 ID를 검사할 수 없으므로, 그 잠금도 보유된 것으로 보고합니다.
- `APOTHEM_HOME`이 심볼릭 링크(또는 Windows에서 정션)이면 POSIX 스크립트와 PowerShell 스크립트는 링크가 이끄는 폴더 옆에서 잠금을 잡으므로, 링크를 통한 실행과 그 폴더를 통한 실행은 서로를 멈춥니다. 메시지는 그 잠금을 지목합니다.
- "Could not create the lock ... Check that you can write to ..."는 메시지가 지목하는 폴더, 즉 `APOTHEM_HOME`을 담은 폴더, 또는 `APOTHEM_HOME`이 링크일 때는 링크가 이끄는 폴더를 담은 폴더에 쓸 수 없다는 뜻입니다. 제자리 업데이트, 제거, 드라이 런을 포함해 모든 실행은 그곳에 써야 합니다.

### 설치 프로그램 중단: 이전 실행이 APOTHEM_HOME 옆에 폴더를 남김 [#the-installer-stops-an-earlier-run-left-folders-beside-apothem_home]

메시지는 "An earlier run was stopped part-way and left these folders beside ..."이며 각 폴더와 그 내용을 나열합니다. Ctrl+C와 종료 신호는 포착되어 실행이 정리하지만, 교체 중의 강제 종료나 전원 차단은 그렇지 않으며 다음을 남길 수 있습니다.

- `.apothem-old.<name>.*`: 대체되던 이전 설치로, 그 `home` 폴더 안에 있습니다. 그 `home` 폴더에 git 클론이 있고 `APOTHEM_HOME`이 제자리에 있으면(새 설치가 들어온 뒤에는 그렇습니다), 그 줄은 대신 그 실행이 보관하던 클론의 트리를 담고 있다고 말합니다. 아직 필요하다면 여러분 자신의 폴더로 옮기세요. `home` 폴더에 Apothem 설치가 없고 `APOTHEM_HOME`이 제자리에 있으면, 그 줄이 그렇게 말합니다. 실행이 이전 설치를 옮기는 동안 그곳에 폴더가 나타났고, 실행은 설치를 되돌려 놓고 그 폴더는 그대로 두었습니다. 제거하기 전에 그 내용을 확인하세요.
- `.apothem-extract.<name>.*` 또는 `.apothem-clone.<name>.*`: 설치되던 새 소스입니다. 실행이 이미 `APOTHEM_HOME`의 항목을 그 안으로 옮겼다면, 그 줄은 `backups`와 `state` 같은 엔진 데이터, 그리고 그곳에 있던 다른 모든 파일이나 폴더를 하나하나 지목합니다.
- `<APOTHEM_HOME>.before-apothem-<time>`: `APOTHEM_HOME` 자체가 없을 때만 나열됩니다. `APOTHEM_HOME`의 이전 내용을, `APOTHEM_HOME`의 마지막 부분을 이름으로 한 폴더 안에, 또는 이전 설치 프로그램이 만든 폴더라면 바로 그 안에 담고 있습니다. 어느 쪽인지는 그 줄이 말해 줍니다.

`<name>`은 `APOTHEM_HOME`의 마지막 부분(기본값 `.apothem`)이므로, 같은 상위 폴더에 있는 다른 `APOTHEM_HOME`의 폴더는 그 홈에 대한 실행이 사용 중일 수 있으므로 나열되지 않습니다. Windows와 macOS에서는 대문자만 다른 `<name>`도 이 홈의 것으로 간주합니다. 그곳에서는 기본적으로 `APP`과 `app`이 같은 폴더를 가리키기 때문입니다. 이 규칙은 파일 시스템이 아니라 운영 체제를 따릅니다. WSL 아래에서는 Windows 드라이브 위라도 대문자가 다른 이름은 서로 다른 홈이며, 대소문자를 구분하는 macOS 볼륨이나 Windows 폴더에서는 여전히 하나로 간주되므로, 그곳에서 대문자만 다른 이름의 다른 홈도 나열됩니다. 이름에 `<name>` 부분이 없는 폴더는 홈을 기록하지 않던 이전 설치 프로그램이 만든 것입니다. 그런 폴더는 그 폴더의 어느 Apothem 홈에든 속할 수 있다는 메모와 함께 나열되며, 그 줄은 항목이 그 폴더를 만든 홈에서 옮겨졌다고 말합니다. 클론 설치가 만든 그런 폴더의 경우, 그 줄은 찾은 엔진 데이터만 지목하므로 그 밖의 것은 안을 직접 확인하세요. 폴더만 해당합니다. 그런 이름의 파일이나 링크는 나열되지 않습니다. 설치 프로그램이 읽을 수 없는 폴더는 "could not be read"로 나열됩니다.

아무것도 변경되지 않았고 아무것도 삭제되지 않습니다. `APOTHEM_HOME`이 없다면 먼저 이전 설치를 그곳으로 되돌리세요. 그런 다음 목록이 새 소스로 옮겨졌다고 지목하는 모든 항목을 원래 홈으로 되돌리고(메모가 있는 폴더는 어느 홈인지 먼저 확인하세요), 나열된 폴더를 제거한 다음 다시 실행하세요. 이 검사는 드라이 런을 포함해 가져온 설치에서 실행되며, 여러분 자신의 체크아웃에서 하는 설치에서는 실행되지 않으며, 업데이트나 제거에서도 실행되지 않습니다.

### 설치 프로그램 중단: 다른 사용자가 클론을 소유함

메시지는 "is owned by someone else, so git refuses to work in it (git reports "dubious ownership")"입니다. git은 다른 사용자가 소유한 클론을 읽지 않습니다. `APOTHEM_HOME`을 소유한 사용자로 설치 프로그램을 실행하거나, 폴더의 소유권을 가져오거나, `APOTHEM_HOME`이 여러분이 소유한 폴더를 가리키게 한 다음 다시 실행하세요. 설치 프로그램은 폴더를 git의 `safe.directory` 목록에 추가하지 않습니다. 그 첫 git 명령의 다른 모든 실패는 "git could not read the clone at ..." 다음에 git 자체 설명의 첫 줄이 이어집니다.

### 설치 프로그램 경고: 다른 사용자가 APOTHEM_HOME을 변경할 수 있음 [#the-installer-warns-other-users-can-change-apothem_home]

설치 및 업데이트 스크립트는 드라이 런을 포함해, 여러분이 아닌 사용자가 `APOTHEM_HOME`이나 그것을 담은 폴더에 쓸 수 있거나 둘 중 하나를 소유하면 경고합니다. 그러면 그들이 `apothem` 명령이 여러분의 권한으로 실행하는 코드를 바꿀 수 있기 때문입니다. 이 검사를 건너뛰는 실행은 아래에 나열되어 있습니다. 실행은 계속되며, 경고는 폴더, 그 폴더에 쓸 수 있거나 소유한 사람, 그리고 해결책을 지목합니다. 경고는 다음 중 하나로 시작합니다.

- "Other users can change the code Apothem runs as you": 그들이 `APOTHEM_HOME`에 쓸 수 있을 때, 또는 `APOTHEM_HOME`이나 그것을 담은 폴더가 다른 사람에게 속할 때입니다(이때 메시지는 누가 어느 폴더를 소유하는지 말합니다). `APOTHEM_HOME`이 링크이면 메시지는 링크가 이끄는 폴더를 지목합니다.
- "Other users can replace ...": 그들이 `APOTHEM_HOME`을 담은 폴더(또는 그것으로 가는 링크를 담은 폴더)에 쓸 수 있어서 이름을 바꾸거나 제거할 수 있을 때입니다.
- "A new ... would let": `APOTHEM_HOME`이 아직 없고 그곳에 새로 만들 폴더가 다른 사람에게 열려 있게 될 때입니다.

로컬 체크아웃에서 하는 설치는 `APOTHEM_SOURCE`가 그것을 지목하든, 그 체크아웃 자체의 `scripts/installer/install.sh` 또는 `install.ps1`을 실행하든 검사하지 않습니다. 업데이트 스크립트는 `APOTHEM_SOURCE`가 설정되어 있을 때만 검사를 건너뜁니다. 경고가 코드를 바꿔도 된다고 신뢰하는 사람들과 의도적으로 공유하는 그룹을 지목한다면 무시해도 됩니다.

검사는 안의 각 파일이 아니라 `APOTHEM_HOME`과 그것을 담은 폴더의 권한을 읽습니다.

Linux와 macOS에서 경고는 폴더의 권한 비트에서 찾은 "all users" 또는 "the group"을 지목하고, 접근 목록(ACL)이 쓰기를 허용하는 각 사용자나 그룹도 지목합니다. 접근 목록은 `getfacl`이 설치되어 있으면 그것으로 읽습니다. 접근 목록이 있으면 `ls`가 보여 주는 그룹 비트는 목록의 마스크이므로, `getfacl`이 그룹 자체의 항목(`group::`)을 나열하는 곳에서는 그 항목이 그룹을 지목할지 결정합니다. `getfacl`이 없으면 지목된 그룹은 마스크는 쓰기를 허용하지만 그룹 자체의 항목은 허용하지 않는 그룹일 수 있습니다. 경고는 여러분, root 사용자, 또는 여러분의 사용자 이름과 같은 이름의 그룹(여러분 자신의 그룹)은 결코 지목하지 않습니다. 도메인 계정의 `CORP\alice`처럼 `getfacl`이 이스케이프로 쓰는 이름은 그것이 나타내는 이름으로 간주합니다. 해결하려면 메시지가 제시하는 명령을 실행하세요(Linux에서는 접근 목록이 지목하는 각 사용자와 그룹의 쓰기 권한도 제거합니다).

```bash
chmod go-w "$HOME/.apothem"
```

같은 설정 아래에서 만든 파일도 쓰기 가능할 수 있습니다. 폴더에 `chmod -R go-w`를 실행하면 그것들도 해결됩니다. `/tmp`처럼 다른 사람이 `APOTHEM_HOME`을 담은 폴더에 써야 한다면, `chmod +t`로 스티키 비트를 설정해 여러분이 그곳에 둔 것의 이름을 바꾸거나 제거하지 못하게 하거나, `APOTHEM_HOME`을 옮기세요. 새 설치의 경우 경고가 여러분의 umask를 보고합니다. `umask 022`를 실행하고 설치 프로그램을 다시 실행하세요. WSL에서는 모든 파일이 모든 사용자에게 쓰기 가능하게 보이는 `/mnt/c` 아래가 아니라 Linux 홈에 `APOTHEM_HOME`을 두세요.

메시지가 어떤 사용자가 폴더를 "owns"한다고 말하면, 그 사용자는 권한과 관계없이 폴더를 바꿀 수 있으며, root만이 여러분을 소유자로 만들 수 있습니다. root가 소유한 폴더는 괜찮습니다. `APOTHEM_HOME`을 여러분이 소유한 폴더로 옮기세요.

Windows에서 경고는 권한 항목이 폴더 변경을 허용하는 각 계정이나 그룹을, 폴더의 보안 탭에 나오는 이름대로 지목합니다. Users, Authenticated Users, Everyone, INTERACTIVE(컴퓨터에서 또는 원격 데스크톱으로 로그인한 모든 사람으로, `C:\Users\Public`에서 만든 것을 바꿀 수 있습니다), Guests, 또는 여러분의 조직이나 다른 프로그램이 만든 그룹입니다. 여러분, 여러분 자신의 로그인 세션, SYSTEM, Administrators, TrustedInstaller, CREATOR OWNER, OWNER RIGHTS는 결코 지목하지 않습니다. 마지막 두 개는 항목을 만들거나 소유한 사람을 나타내며, 다른 사람인 소유자는 별도의 메시지를 받습니다. 폴더가 다른 계정에 속하면 메시지가 그렇게 말하고 `APOTHEM_HOME`을 여러분의 사용자 폴더로 옮기라고 요청합니다. 메시지에 "access that folders made at the root of a drive inherit from the drive's default permissions"가 덧붙으면, 폴더가 `C:\apothem`처럼 드라이브의 루트에 있는 것입니다. Windows는 로그인하는 모든 사용자가 그곳에 만든 폴더를 추가하고 바꿀 수 있게 합니다. 가장 간단한 해결책은 기본값 `~\.apothem`처럼 `APOTHEM_HOME`을 여러분의 사용자 폴더(`%USERPROFILE%`)로 옮기는 것입니다. 폴더를 그 자리에 두려면 상속을 끄고, 여러분 자신에게 모든 권한을 준 다음, 경고가 지목하는 그룹을 제거하세요. 드라이브 루트의 폴더라면 Windows 10과 11에서는 Authenticated Users, Windows Server에서는 Users입니다. 아래 명령은 둘 다 제거합니다.

```powershell
icacls "C:\apothem" /inheritance:d
icacls "C:\apothem" /grant:r "${env:USERNAME}:(OI)(CI)F"
icacls "C:\apothem" /remove:g *S-1-5-11 *S-1-5-32-545 *S-1-1-0 *S-1-5-4
```

그룹을 제거하기 전에 여러분 자신에게 접근 권한을 주세요. 제거하는 항목이 여러분이 폴더에 쓸 수 있는 유일한 방법일 수 있습니다. `*S-...` 이름은 그룹의 보안 ID(Authenticated Users, Users, Everyone, INTERACTIVE)로, 모든 Windows 언어에서 작동합니다. 경고가 제시하는 다른 이름은 따옴표로 감싸 각각 별도의 `icacls` 줄에서 제거하세요. `icacls`가 찾을 수 없는 이름은 그 줄 전체를 멈추게 하며, 그러면 그 줄은 아무것도 제거하지 않으면서도 "Successfully processed 0 files"를 출력합니다. `S-`와 숫자로 이루어진 이름은 삭제된 계정이나 다른 로그인 세션처럼 Windows가 조회할 수 없는 계정의 보안 ID입니다. 그 앞에 `*`를 붙이고, 그래도 `icacls`가 아무것도 제거하지 않으면 폴더의 속성 > 보안 > 고급에서 제거하세요. 모든 변경을 그곳에서 할 수도 있습니다. 경고가 `APOTHEM_HOME`을 담은 폴더에 관한 것이라면 그곳에서 변경하거나 `APOTHEM_HOME`을 옮기세요. `APOTHEM_HOME`에 있는 링크나 정션은 그 폴더에서 권한을 가져오므로, 그 폴더를 바꿀 수 있는 다른 사람은 링크를 삭제하고 자신의 링크를 만들 수 있습니다.

`install.sh`와 `update.sh`는 권한 비트가 Windows 권한에서 만들어지는 Git Bash, MSYS2 또는 Cygwin 아래에서는 검사하지 않으므로, 그곳에서는 경고하지 않습니다. Windows에서는 폴더를 검사하려면 Windows 권한을 읽는 `install.ps1` 또는 `update.ps1`을 실행하세요.

### 설치 프로그램 중단: 기존 클론을 업데이트할 수 없음

설치 프로그램은 기존 클론으로 가져오고 클론을 체크아웃하기 전에 새 태그를 검사하므로, 검사에 실패하면 클론은 원래 상태 그대로 남습니다. 다른 두 메시지도 체크아웃 전에 업데이트를 멈춥니다. "Could not fetch"는 대개 로컬 태그가 origin의 태그와 다르다는 뜻입니다. `git -C ~/.apothem tag -d <tag>`로 삭제한 다음 다시 실행하세요. "has changes to tracked files. Commit or stash them, then re-run."은 클론에 git이 추적하는 파일의 커밋되지 않은 변경이 있다는 뜻입니다. 커밋하거나 stash한 다음 다시 실행하세요. 검사는 여러분 자신의 git 속성 파일이나 시스템 git 속성 파일의 줄 끝 설정(`eol`과 `text`)을 무시하므로, 한 번도 바꾸지 않은 클론이 이렇게 보고될 수 있습니다. `git -C ~/.apothem status`를 한 번 실행한 다음 다시 실행하세요. 드라이 런은 클론으로 가져오지 않으므로 일반적인 커밋되지 않은 변경을 검사하지 않지만, 파일이 assume-unchanged 또는 skip-worktree로 표시되어 있으면 같은 메시지와 함께 멈춥니다(위의 클론 설정 섹션 참조). "Could not check out"은 체크아웃이 여전히 로컬 변경을 덮어쓰게 된다는 뜻입니다. 설치 프로그램은 로컬 변경을 결코 버리지 않습니다. `main` 같은 릴리스가 아닌 ref의 경우, 기존 클론은 origin에 있는 그 브랜치의 사본을 따릅니다.

### 설치 프로그램 또는 업데이트 스크립트가 종료 코드 2로 끝남

엔진이 부분 완료로 끝났습니다. Apothem 마커 줄 때문에 Apothem의 블록을 담은 파일을 그대로 두고 나머지를 썼거나, 무언가를 쓴 뒤에 멈췄습니다. 예를 들어 `APOTHEM_HARNESS=all` 실행에서 앞의 도구 다음에 한 도구가 실패한 경우입니다. 엔진의 메시지는 파일을 지목하거나 엔진을 멈춘 오류를 보여 주며, 스크립트는 "The engine ended as partial (exit code 2)."로 시작하는 한 줄을 덧붙입니다. 설치 프로그램은 여전히 verify를 실행하고, `apothem` 명령을 배치하고, 배너를 출력하며, 업데이트 스크립트는 여전히 마지막 줄을 출력합니다. 파이프로 연결한 PowerShell 실행(`irm ... | iex`)은 `$LASTEXITCODE`를 `2`로 남기고 세션을 열어 둡니다. 일회성 `pwsh -Command "irm ... | iex"`(또는 `powershell -c`)는 부분 실행을 `$LASTEXITCODE`로만 보고하고 `0`으로 종료합니다. 프로세스에서 종료 코드 `2`를 얻으려면 명령 끝에 `; exit $LASTEXITCODE`를 붙이거나, `-File`로 스크립트를 경로로 실행하세요. PowerShell, bash 또는 다른 POSIX 셸에서는 그 명령을 작은따옴표로 감싸세요. 큰따옴표 안에서는 호출하는 셸이 새 프로세스가 시작되기 전에 자신의 `$LASTEXITCODE`를 넣으므로(POSIX 셸은 빈 문자열을 넣습니다), 프로세스가 실행의 코드로 종료하지 않습니다. cmd.exe에서는 큰따옴표를 써도 됩니다. 드라이 런은 아무것도 쓰지 않으므로 부분 완료로 끝나지 않습니다. 메시지가 지목하는 것을 고치세요. 파일의 경우 여러분 자신의 텍스트를 유지하고([파일이 Apothem의 마커 사이에 두 블록을 담고 있음](#a-file-holds-two-blocks-between-apothems-markers) 및 [Apothem이 자신의 블록과 여러분의 텍스트를 구별할 수 없음](#apothem-cannot-tell-its-block-from-your-text) 참조), 실행이 끝내지 못한 각 도구에 대해 `apothem update --harness <name>`을 다시 실행하세요. [엔진이 파일을 그대로 둘 때](/docs/install/updating#when-the-engine-leaves-a-file-as-it-is)에서 전체 실행을 설명합니다.

### Windows에서 irm / iex가 차단됨

PowerShell 실행 정책이 설치 프로그램을 차단하는 경우:

```powershell
Set-ExecutionPolicy RemoteSigned -Scope CurrentUser
irm https://apothem.ahmedgad.com/install.ps1 | iex
```

### 설치 프로그램이 현재 폴더의 체크아웃을 무시함

의도된 동작입니다. 파이프로 연결한 한 줄 명령(`curl ... | sh`, `irm ... | iex`)은 로컬 트리를 결코 사용하지 않으며, 현재 폴더나 그 상위 폴더를 결코 살펴보지 않습니다. 릴리스를 가져와 검증합니다. 체크아웃에서 설치하려면 어느 폴더에서든 그 체크아웃 자체의 `scripts/installer/install.sh`(또는 `install.ps1`)를 경로로 실행하거나(예: `sh ~/src/apothem/scripts/installer/install.sh`), `APOTHEM_SOURCE`를 그 체크아웃으로 설정하세요. 스크립트에는 폴더 부분이 있는 경로를 주세요. `sh scripts/installer/install.sh`나 `sh ./scripts/installer/install.sh`는 작동하지만, 폴더 부분이 없는 `sh install.sh`는 체크아웃에서 실행하는 것으로 간주되지 않으므로, 설치 프로그램은 "Not using a checkout: to install from one, run this script as ./install.sh or by its full path, or set APOTHEM_SOURCE."를 출력하고 대신 릴리스를 가져와 검증합니다. `-c` 실행을 표시하는 셸에서는 `sh -c`로 시작한 스크립트도 체크아웃으로 취급되지 않습니다. dash는 이를 표시하지 않으므로, dash 아래에서 소스 트리 안의 `scripts/installer`라는 폴더에서 시작한 `sh -c "<script>" ./install.sh`는 그 트리를 사용합니다. 스크립트 텍스트는 신뢰하는 폴더에서만 그렇게 시작하세요. 같은 방식으로, 다른 소스 트리의 `scripts/installer` 폴더에 저장하고 그곳에서 경로로 실행한 `install.sh` 사본은 그 트리 자체의 설치 프로그램이 되어 그 트리를 설치합니다. 다운로드한 스크립트는 빈 폴더에 저장하세요. `install.sh`는 심볼릭 링크를 따라 실제 파일로 가서 그 파일을 담은 체크아웃을 사용합니다. `install.ps1`은 반대로 동작합니다. 심볼릭 링크나 정션을 통해 도달한 체크아웃을 거부하고, 한 줄 메모를 출력한 뒤, 가져와서 검증하는 경로를 택합니다. 실제 폴더에서 실행하거나 `APOTHEM_SOURCE`를 설정하세요. 설치 프로그램, `apothem` 명령, npm 실행기, 훅은 또한 현재 폴더를 Python의 모듈 검색 경로에서 제외하므로, 여러분이 작업하는 폴더의 `click.py`라는 파일은 이들에 아무 영향도 주지 않습니다. 여러분이 직접 입력하는 `python -m apothem` 명령은 그렇지 않습니다. `-m`은 현재 폴더에서 모듈을 먼저 읽으므로, 신뢰하는 폴더에서만 실행하세요.

### 오래된 `apothem` 명령이 여전히 현재 폴더를 살펴봄

이전 릴리스는 현재 폴더가 엔진의 모듈을 가릴 수 있는 방식으로 Python을 시작하는 `apothem` 명령 심을 썼습니다. 업데이트는 그 심을 다시 쓰지 않습니다. 설치 프로그램(`install.sh` 또는 `install.ps1`)을 다시 실행해 심을 교체하세요. 제거 프로그램은 이전 심과 새 심을 모두 제거합니다.

### Git Bash: `/c/...` PYTHONPATH 항목이 무시됨

Git Bash 아래에서 설치 프로그램은 대개 Windows Python을 실행하며, Windows Python은 `PYTHONPATH`를 `;`로 구분된 Windows 경로로 읽습니다. sh 스크립트와 그것이 쓰는 `apothem` 심은 그 Python을 위해 `PYTHONPATH`의 드라이브 경로와 네트워크 경로만 유지하므로, `/c/Users/me/lib` 같은 POSIX 형식 항목은 버려집니다. 항목을 드라이브 경로 `C:\Users\me\lib` 또는 `C:/Users/me/lib`로 쓰고, 항목은 `;`로 구분하세요. Cygwin이나 MSYS2 자체의 `python3` 같은 POSIX Python은 `/`로 시작하는 `:` 구분 경로를 읽으며, 스크립트는 그 Python을 위해 그런 경로를 유지합니다.

## 런타임 문제

### apothem install이 하니스를 찾지 못함

apothem doctor를 실행하여 하니스마다 한 행씩 있는 Harness Status 표를 확인하세요. `not installed`로 표시된 행은 Apothem이 해당 하니스의 설치를 찾지 못했다는 뜻입니다. `needs --project`로 표시된 행은 프로젝트 범위 하니스이며, doctor는 `--project <path>`를 전달할 때만 이를 검사합니다. doctor가 `No harness is installed yet`을 보고하면 하니스가 설치되어 있는지 확인한 다음 `apothem install --harness <name>`을 실행하세요.

### apothem verify가 실패한 어댑터를 보고함

apothem install을 다시 실행하여 어댑터를 다시 머티리얼라이즈하세요. 문제가 지속되면 [하니스 어댑터](/docs/harnesses) 아래의 어댑터별 페이지를 확인하세요. 설치가 END가 없는 BEGIN 마커에 대해 경고했거나, 실패한 행이 그런 마커를 담은 파일을 지목한다면 다시 실행해도 소용없습니다. [파일에 END 마커가 없는 Apothem BEGIN 마커가 있음](#a-file-has-an-apothem-begin-marker-with-no-end-marker)을 참조하세요. 경고나 행이 파일이 Apothem의 마커 사이에 둘 이상의 온전한 블록을 담고 있다고 말하면 [파일이 Apothem의 마커 사이에 두 블록을 담고 있음](#a-file-holds-two-blocks-between-apothems-markers)을 참조하세요. Apothem이 파일의 마커 줄이 자신의 블록을 표시하는지 여러분의 텍스트인지 구별할 수 없다고 말하면 [Apothem이 자신의 블록과 여러분의 텍스트를 구별할 수 없음](#apothem-cannot-tell-its-block-from-your-text)을 참조하세요.

### 파일에 END 마커가 없는 Apothem BEGIN 마커가 있음 [#a-file-has-an-apothem-begin-marker-with-no-end-marker]

Apothem은 자신의 텍스트를 `<!-- BEGIN APOTHEM MANAGED BLOCK -->` 마커에서 다음 `<!-- END APOTHEM MANAGED BLOCK -->` 마커까지 이어지는 블록에 보관합니다. END 마커가 사라졌거나(손으로 한 편집이나 그 줄을 빠뜨린 병합), 여러분의 BEGIN 마커가 온전한 블록 바깥에 있으면, Apothem의 텍스트가 어디서 끝나고 여러분의 텍스트가 어디서 시작하는지 보여 주는 것이 없습니다. 그래서 Apothem은 그 마커 뒤의 텍스트를 결코 잘라 내지 않습니다.

- `apothem install`과 `apothem update`는 그것을 그대로 두고, Apothem의 블록을 그것과 떨어진 곳에 쓰고, 파일과 마커의 줄을 지목하는 경고를 그 줄을 바꾸는 번호가 매겨진 단계와 함께 출력합니다(아래 참조). 경고는 대신 END 마커를 다시 추가하지 말라고도 말합니다. Apothem의 블록이 그것과 떨어진 곳에 쓰인 상태에서는 파일이 두 개의 Apothem 블록을 담게 되며, 설치와 업데이트는 그런 파일을 그대로 둡니다. 드라이 런은 무엇이든 쓰기 전에 파일을 읽으므로, 파일에 아직 온전한 블록이 없을 때 그 경고는 대신 END 마커를 다시 추가한다면 두 마커 사이에 여러분의 줄이 있어서는 안 된다고 말합니다. 다음 실행이 둘 사이의 모든 줄을 교체하거나 빼내기 때문입니다. 그리고 설치나 업데이트가 Apothem의 블록을 마커와 떨어진 곳에 쓴 뒤에는 아예 다시 추가하지 말라고 말합니다. 그 전까지는, END 마커를 이전 Apothem 텍스트 바로 아래, 여러분의 줄 위에 되돌려 놓으면 하나의 온전한 블록이 남고, 다음 업데이트가 그것을 다시 씁니다.
- `apothem uninstall`은 Apothem의 온전한 블록을 빼내고, 나머지는 그대로 두며, 같은 번호가 매겨진 단계와 함께 파일과 마커의 줄을 지목합니다. 설치는 마커를 그대로 두며, 도구는 여전히 그 아래의 텍스트를 읽습니다.
- `apothem verify`와 `apothem doctor`는 잘못된 마커가 바뀔 때까지 실패하며, 같은 번호가 매겨진 단계와 함께 파일과 마커의 줄을 지목합니다. 현재 설치가 쓰는 파일이라면 그때까지 `apothem status --profile`도 드리프트를 보여 줍니다. `apothem install`을 다시 실행해도 해결되지 않습니다. Apothem이 그 하니스에 대해 블록을 보관하는 파일만 해당하므로, 여러분 자신의 파일에 있는 마커는 이들을 실패시키지 않습니다.

설치 기록이 온전한 블록은 없지만 코드 안에 마커 쌍(예: 코드 블록에서 인용한 마커 예시)이 있는 파일을 나열하는 동안, 설치, 업데이트, 제거는 그 파일 전체를 그대로 둡니다. 그 쌍이 여러분의 코드 블록 안에 있는 Apothem의 블록일 수 있기 때문입니다. 그 경고는 `apothem verify` 메모와 마찬가지로 그 BEGIN 마커를 먼저 지목하고, 그다음 각 쌍을 지목하며, 제거는 완료되지 않은 채로 남습니다([Apothem이 자신의 블록과 여러분의 텍스트를 구별할 수 없음](#apothem-cannot-tell-its-block-from-your-text) 참조). 설치 기록이 없으면 코드에서 인용한 쌍은 여러분의 텍스트이며, 설치와 업데이트는 Apothem의 블록을 잘못된 마커와 떨어진 곳에 씁니다. 더 아래에서 뒤에 마커 쌍 없이 코드에서 단독으로 인용한 END 마커는 다릅니다. 그것은 그 BEGIN 마커를 닫으므로, 업데이트는 둘 사이의 줄을 Apothem의 블록으로 교체하고, 제거는 그 줄들을 제거합니다.

Apothem은 Markdown 뷰어처럼 코드 바깥에 있는 독립된 줄만 마커로 읽습니다. 따라서 문장 안에서, 펜스 코드 블록 안에서, 또는 빈 줄 뒤에 목록 항목(또는 여백)보다 네 칸 더 들여 쓴 코드 안에서 인용한 마커는 마커로 간주되지 않으며, 두 개의 별도 코드 블록에서 인용한 BEGIN 마커와 END 마커도 마찬가지입니다. 파일 끝까지 열려 있는 코드 펜스는 개수와 관계없이 텍스트로 읽힙니다. 단, 그 위에서 코드 바깥에 있는 BEGIN 마커의 END 마커가 코드 안에 있고 그 뒤에 다른 마커 쌍이 이어지는 경우는 예외입니다. HTML 블록이나 인용 블록 안의 마커, 또는 텍스트가 왼쪽 여백에서 이어지는 목록 항목 뒤의 마커는 여전히 Markdown 뷰어와 다르게 읽힐 수 있습니다.

이 경고들이 제시하는 모든 줄 번호는 Apothem이 파일을 읽는 방식으로 줄을 셉니다. 줄은 CRLF, LF, 또는 단독 CR에서 끝납니다. CR 줄 끝으로 저장된 파일이나, 줄 안에 단독 CR이 하나 있는 파일에서는 경고가 지목하는 줄을 바꾸기 전에 같은 방식으로 줄을 세세요.

해결하려면 경고의 번호가 매겨진 단계를 따르세요. 예: "Fix A, if lines 77 to 148 are Apothem's block: A1. Change line 3: add a word inside its comment." 3번 줄이 잘못된 BEGIN 마커입니다. 다음 BEGIN 마커 전에 END 마커가 없거나, END 마커가 아예 없는 마커입니다. `<!-- BEGIN APOTHEM MANAGED BLOCK (example) -->`처럼 닫는 `-->` 바로 앞에 단어를 하나 추가하면 그 줄은 더 이상 마커로 읽히지 않습니다. 이는 줄을 추가하거나 제거하지 않으므로 파일의 다른 부분은 다르게 읽히지 않으며, Apothem의 현재 블록을 여는 BEGIN 줄은 그대로 남습니다. 이 해결책은 코드 블록에서 인용한 것을 포함해 파일의 다른 모든 BEGIN 마커 줄도 각각 한 단계씩, 파일 아래에서 위로 바꿉니다([번호가 매겨진 해결책 따르기](#follow-a-numbered-fix) 참조). 인용한 BEGIN 마커를 그대로 두면 제거가 Apothem의 블록을 빼낸 뒤에 그 아래의 END 마커와 쌍을 이룰 수 있기 때문입니다. 그 줄들이 바뀐 뒤에도 Apothem의 블록이 온전하게 남는다는 것을 파일의 레이아웃이 보여 주지 않을 때는(예: 어떤 줄도 닫지 않는 여러분의 코드 블록이 그 블록을 담고 있을 때), 해결책은 블록의 마커를 포함해 파일의 모든 BEGIN 마커 줄을 바꿉니다. 예: "Fix A: A1. Below line 6, add a line of 3 backticks. A2. Change line 3: add a word inside its comment. A3. Change line 2: add a word inside its comment. Apothem then reads none of these lines as its markers, and the next update writes its block at the end of the file." 이 예처럼 파일이 어떤 줄도 닫지 않는 코드 블록 안에서 끝나면, 해결책은 먼저 마지막 줄 아래에 그 코드 블록의 닫는 줄을 추가하므로, 다음 업데이트가 그곳에 쓰는 블록은 코드가 아닙니다. 여러분이 바꾸는 마커 줄 아래에 있는, Apothem의 규칙을 반복하는 이전 Apothem 텍스트는 그 후 여러분이 손으로 삭제하면 됩니다. 마커 줄을 바꾸는 대신 END 마커를 다시 추가하지 마세요. 설치나 업데이트가 Apothem의 블록을 그것과 떨어진 곳에 쓴 뒤라면, 파일이 두 개의 Apothem 블록을 담게 됩니다([파일이 Apothem의 마커 사이에 두 블록을 담고 있음](#a-file-holds-two-blocks-between-apothems-markers) 참조). 마커 줄을 바꾸고 나면 그 아래의 END 마커는 어떤 것과도 쌍을 이루지 않습니다. 그런 다음 파일에 더 이상 블록이 없으면 Apothem의 블록을 다시 쓰는 `apothem update`를 실행하고, `apothem verify`를 다시 실행하세요. END 마커가 코드 안에 있고 그 뒤에 다른 마커 쌍이 있는 BEGIN 마커는 다른 경고를 받습니다. [Apothem이 자신의 블록과 여러분의 텍스트를 구별할 수 없음](#apothem-cannot-tell-its-block-from-your-text)을 참조하세요.

### 파일이 Apothem의 마커 사이에 두 블록을 담고 있음 [#a-file-holds-two-blocks-between-apothems-markers]

Apothem은 파일당 하나의 블록을 씁니다. 그래도 파일에 두 개의 온전한 블록이 생길 수 있습니다. 업데이트가 아래에 새 블록을 쓴 뒤에 여러분이 END 마커를 되돌려 놓은 이전 블록, 코드 바깥에 있는 여러분의 마커 쌍(예: 인용한 예시), 또는 두 번 붙여 넣은 블록입니다. 그러면 Apothem은 어느 것이 자신의 블록인지 구별할 수 없습니다.

- `apothem install`과 `apothem update`는 파일을 그대로 두고, 각 블록을 줄로 지목하는 경고를 출력합니다. 예: "holds 2 whole blocks between Apothem's markers (lines 1 to 32, and lines 36 to 67)". 실행은 부분 완료로 끝납니다. `✓` 줄 대신 파일을 지목하는 `✗` 줄을 출력하고, `--format json`의 `status`는 `"partial"`이며, 파일을 고칠 때까지 코드 `2`로 종료합니다. 드라이 런에서 경고는 Apothem이 "would leave the file as it is"라고 말합니다.
- `apothem verify`(`--profile` 유무와 관계없이)와 `apothem doctor`는 파일을 고칠 때까지 실패하며 각 블록과 함께 파일을 지목합니다(doctor의 검사는 `harness.stray_begin`이고, 그 메시지는 파일이 "Apothem markers to fix by hand"를 담고 있다고 말합니다). 현재 설치가 쓰는 파일이라면 그때까지 `apothem status --profile`도 드리프트를 보여 줍니다.
- `apothem uninstall`은 서로 정확히 같은 블록(예: 두 번 붙여 넣은 블록)을 빼냅니다. 다른 블록이 남게 될 때는 파일을 그대로 두고, "then run the uninstall again"으로 끝나는 같은 경고를 출력하며, 여러분이 고칠 때까지 완료되지 않은 채로 남습니다(종료 코드 `2`)([완료되지 않은 제거](/docs/cli-reference/uninstall#an-uninstall-that-did-not-finish) 참조). 설치 기록이 없으면 두 블록을 담은 Claude Code의 `CLAUDE.md`나 프로필 문서도 그대로 두며, 그 경고는 각 블록을 같은 방식으로 지목합니다. 그 경고는 고친 뒤에 `apothem update`를 실행한 다음 `apothem uninstall`을 다시 실행하라고 말하며, 제거를 멈추지 않습니다. 그러면 제거 실행은 블록을 빼내기 전에 Apothem의 블록 주변에 있는 여러분의 마커 줄을 지목합니다.

그런 다음 경고는 각 블록에 대해, 그 블록이 Apothem의 블록인 경우를 위한 번호가 매겨진 해결책을 하나씩 제시합니다. 예: "Fix A, if lines 1 to 32 are Apothem's block: A1. Change line 36: add a word inside its comment. Lines 1 to 32 are then the one block in the file."([번호가 매겨진 해결책 따르기](#follow-a-numbered-fix) 참조). 해결책은 다른 모든 블록의 BEGIN 마커 줄을 바꿉니다. 위에 BEGIN 마커가 없는 END 마커는 어떤 것과도 쌍을 이루지 않습니다. 파일의 레이아웃이 그 경우를 보여 주지 않는 블록(예: 코드 블록을 담은 블록 아래의 블록)은 자체 해결책을 받지 않으며, 그러면 해결책이 하나 더, "in any other case"로 추가되어 파일의 모든 BEGIN 마커 줄을 바꿉니다. 경고가 제시하는 줄에서 지목된 파일을 여세요.

1. Apothem의 규칙을 담은 블록에 대한 해결책을 고르세요. Apothem의 frontmatter로 시작하는 파일에서는 바로 그 아래의 블록입니다. 제거는 바로 아래의 블록과 함께일 때만 그 frontmatter를 빼냅니다.
2. 그 해결책의 단계를 주어진 순서대로 하세요. 각 단계는 BEGIN 마커 줄을 제자리에서 바꾸므로 그 아래의 텍스트는 남습니다. 여러분의 마커 쌍은 예시를 유지하며, 이전 Apothem 블록이나 붙여 넣은 Apothem 블록의 텍스트는 END 마커 줄까지 그 후 여러분이 손으로 삭제하면 됩니다. 각 해결책은 제거뿐 아니라 다음 업데이트에도 유효합니다. 여러분의 쌍을 유지하려고 Apothem의 블록을 삭제하지 마세요. 그러면 다음 제거가 여러분의 쌍을 남은 하나의 블록으로 보고 빼낼 것입니다. 여러분의 쌍을 코드 블록 안으로 옮기지도 마세요. Apothem 자체의 블록이 더 이상 온전하지 않게 되면(예: END 마커를 잃었을 때), 설치 기록이 그 파일을 나열하는 동안 코드 안의 마커 쌍이 설치와 업데이트가 Apothem의 블록을 쓰지 못하게 막습니다([Apothem이 자신의 블록과 여러분의 텍스트를 구별할 수 없음](#apothem-cannot-tell-its-block-from-your-text) 참조).
3. `apothem update`를 실행한 다음 `apothem verify`를 다시 실행하세요. 완료되지 않은 제거 뒤라면 대신 `apothem uninstall`을 다시 실행하세요.

Apothem의 블록 위의 BEGIN 마커와 그 아래의 END 마커는 Apothem의 블록이 빠진 뒤에야 드러나는 두 번째 블록을 만듭니다. 그러면 제거의 경고는 Apothem의 블록과 그 두 마커 줄을 지목합니다. 예: "once the block from line 5 to line 36 is out, the BEGIN marker at line 2 and the END marker at line 39 make another". 그리고 "Do not delete the block from line 5 to line 36"이라고 말합니다. 그러면 다음 실행이 2번부터 39번 줄까지를 Apothem의 블록으로 읽고, 그 사이에 있는 것을 교체하거나 빼낼 것이기 때문입니다. 그 하나의 해결책은 대신 그 BEGIN 마커 줄을 바꿔 여러분 자신의 텍스트를 유지합니다. 예: "Fix A, if lines 5 to 36 are Apothem's block: A1. Change line 2: add a word inside its comment. Lines 5 to 36 are then the one block in the file." 그런 다음 제거를 다시 실행하세요. 그러면 아래의 END 마커는 어떤 것과도 쌍을 이루지 않으므로, 예를 들어 코드 블록에서 인용한 예시로 남겨 둘 수 있습니다. 두 줄을 하나의 코드 블록에 넣지 마세요. 그 코드 블록이 Apothem의 블록도 담게 됩니다. 그 BEGIN 마커가 이전 Apothem 블록의 잔재라면, 그 아래의 이전 Apothem 텍스트는 그 후 여러분이 손으로 삭제하면 됩니다. `apothem update`도 그런 파일을 고치지 않으며, 여러분이 고칠 때까지 `apothem verify`는 실패합니다.

### Apothem이 자신의 블록과 여러분의 텍스트를 구별할 수 없음 [#apothem-cannot-tell-its-block-from-your-text]

경고는 파일을 지목하고 "Apothem cannot tell whether the marker lines in this file mark its block or text of yours"라고 말합니다. Apothem의 블록 위의 코드 펜스가 열린 채로 남아 있고 여러분이 더 아래에 추가한 펜스가 그것을 닫았을 때 이 경고를 봅니다. 그러면 블록이 여러분의 코드 블록 안에 놓입니다. Markdown 뷰어는 그 줄들을 코드로 보여 주며, 같은 줄들이 여러분이 예시로 인용한 마커 쌍일 수도 있으므로, Apothem은 그것이 자신의 블록인지 여러분의 텍스트인지 구별할 수 없습니다. 들여 쓴 코드 안이나 문단 아래에 들여 쓴 쌍, 그리고 END 마커가 코드 안에 있고 다른 마커 쌍이 뒤따르는, 코드 바깥의 BEGIN 마커도 마찬가지입니다. 어느 쌍이든 Apothem의 블록일 수 있습니다. Apothem 자체 블록 안의 닫는 줄이 그 위에 열린 채로 남은 여러분의 코드 블록을 닫을 수도 있습니다(아래 참조).

경고는 파일의 각 마커 쌍을 두 마커의 줄로 지목하고 그것들이 어디서 읽히는지 말합니다. 예: "The BEGIN marker at line 6 and the END marker at line 38 sit inside a code block that opens at line 3." 또한 마커 쌍을 시작하지 않는, 코드 바깥의 각 BEGIN 마커도 지목합니다. 예: "The BEGIN marker at line 1 starts no marker pair: its END marker is gone, or the marker is yours." 그다음 `apothem install`, `apothem update`, `apothem uninstall`의 경고, `apothem verify` 메모, `apothem doctor`가 출력하는 해결책에 번호가 매겨진 해결책이 이어집니다. 예: "Fix A: A1. Change line 6: add a word inside its comment. Apothem then reads none of these lines as its markers, and the next update writes its block at the end of the file." 두 마커 줄이 모두 코드 바깥에서 읽히는 쌍(END 마커가 코드 안에 있는 BEGIN 마커 다음의 쌍)은, 그것이 Apothem의 블록인 경우를 위한 자체 해결책을 받으며, 파일의 레이아웃이 그 쌍이 그때 하나의 온전한 블록으로 읽힌다는 것을 보여 줄 때 그렇습니다. 마지막 해결책은 앞에 다른 해결책이 있으면 "in any other case"이며, 파일의 모든 BEGIN 마커 줄을 바꿉니다. 읽는 방법은 [번호가 매겨진 해결책 따르기](#follow-a-numbered-fix)를 참조하세요.

설치 기록이 파일을 나열하는 동안(제거가 완료될 때까지이며, 읽을 수 없는 설치 원장도 기록으로 간주됩니다. 링크를 통해 도달한 홈처럼 폴더의 다른 표기로 만든 기록도, 제거에서와 마찬가지로, 여러분이 실행하는 표기에 자체 설치가 아직 남아 있고 도구가 [홈 디렉터리의 공유 폴더](/docs/cli-reference/install#folders-in-your-home-directory)에 쓸 때 간주됩니다), `apothem install`과 `apothem update`는 그 파일에서 아무것도 바꾸지 않고 그 경고를 출력합니다. 드라이 런에서는 Apothem이 "would leave the file as it is"라고 말합니다. END 마커가 코드 안에 있고 그 뒤에 다른 마커 쌍이 있는, 코드 바깥의 BEGIN 마커에 대해서는 기록 유무와 관계없이 그렇게 합니다. 그런 실행은 각각 부분 완료로 끝납니다. `✓` 줄 대신 파일을 지목하는 `✗` 줄을 출력하고, `--format json`의 `status`는 `"partial"`이며, 코드 `2`로 종료합니다. 경고가 이렇게 말합니다: "Until you fix these marker lines as this text says, install and update leave this file as it is and end as partial (exit code 2)." 파일을 써서 성공으로 끝나는 실행의 경고는 그 문장을 "From the next run on, until you fix these marker lines"로 시작합니다. 이 상태는 마커 줄이 그대로인 한 지속되며, 코드 블록 안에 있는 여러분의 마커 예시도 포함됩니다. 그런 쌍은 여러분의 코드 블록 안에 있는 Apothem의 블록일 수 있으므로, 경고는 여러분의 예시가 BEGIN 마커 줄을 바꿀 때까지(예: `<!-- BEGIN APOTHEM MANAGED BLOCK (example) -->`처럼 주석 안에 단어를 추가해서) 파일을 같은 방식으로 붙잡아 둔다고 덧붙입니다. 마커 줄이 위 문단의 일부로 읽히는 쌍에 대해서는 그 쌍을 "a marker example of yours that reads as part of a paragraph"라고 부릅니다. 다른 어떤 것도 이 상태를 끝내지 않습니다. 쌍이 있는 동안에는 제거도 완료되지 않습니다. 쌍을 시작하지 않는 코드 바깥의 BEGIN 마커는, 파일의 모든 마커 쌍이 그 아래의 코드에서 인용된 것이라도 이를 바꾸지 않습니다. 그 마커는 END 마커를 잃은 뒤 남은 Apothem 블록의 잔재일 수 있지만, 코드 안의 쌍이 여러분의 코드 블록 안에 있는 Apothem의 블록일 수도 있기 때문입니다. 경고는 그런 BEGIN 마커를 먼저 지목하며, 각 해결책이 그것을 바꿉니다. `apothem verify` 메모와 `apothem doctor`가 출력하는 해결책은 설치와 업데이트가 파일을 그대로 둘 경우에만 부분 완료로 끝난다는 같은 문장을 제시합니다. 설치 기록이 없으면 코드에서 인용한 마커 쌍은 파일을 붙잡아 두지 않습니다(아래 참조). 단, 그 쌍이 설치가 쓰는 블록과 정확히 같은 블록을 담고 있으면 예외입니다. 메모와 해결책은 그 블록을 검사하지 않으므로, 그런 쌍에 대해서는 그 문장을 생략합니다. 다음 업데이트가 파일을 그대로 두고, 부분 완료로 끝나며, 그렇게 말합니다.

Apothem은 여러분의 프로필의 규칙이 열고 닫지 않는 코드 블록을 자신이 쓰는 블록의 끝에서 닫으므로, 그 블록의 END 마커는 결코 코드 안에 놓이지 않습니다. 이전 릴리스가 그런 규칙으로 쓴 블록에는 닫는 줄이 없습니다. 그 뒤에 여러분의 마커 쌍이 있으면 설치와 업데이트는 파일을 그대로 둡니다. 어떤 해결책도 그 이전 블록을 유지하지 않습니다. 그 아래에 있는 여러분의 줄이 그 규칙이 연 코드 블록을 닫으며, 다음 업데이트가 블록을 교체하고 나면 그 줄이 여러분의 텍스트 위로 코드 블록을 열게 되기 때문입니다. 그 뒤의 쌍이 Apothem의 블록인 경우를 위한 해결책은 이전 블록의 BEGIN 마커 줄을 바꿉니다. 예: "Fix A, if lines 8 to 10 are Apothem's block: A1. Change line 1: add a word inside its comment." 그리고 마지막 해결책은 모든 BEGIN 마커 줄을 바꿉니다. 이전 블록의 텍스트는 그 후 여러분이 손으로 삭제하면 됩니다.

그 닫는 줄, 또는 여러분의 프로필의 규칙이 쓰는 코드 블록의 닫는 줄은, Apothem의 블록 위에서 열리고 닫히지 않는(예: 메모 끝에 있는) 여러분의 코드 블록을 닫을 수도 있습니다. 그러면 블록은 BEGIN 마커부터 코드로 읽힙니다. 그 블록을 쓴 설치나 업데이트는 파일을 그대로 두었다는 말 없이 즉시 경고를 출력합니다. 예: "The BEGIN marker at line 6 sits inside a code block that opens at line 3, and the END marker at line 44 is outside code." 그 해결책은 "Fix A: A1. Change line 6: add a word inside its comment."처럼 그 BEGIN 마커 줄을 바꿉니다. 그러면 다음 업데이트가 Apothem의 블록을 파일 끝, 여러분의 코드 블록을 닫는 줄 아래에 쓰며, 이전 블록은 여러분이 손으로 삭제하면 됩니다. 드라이 런은 무엇이든 쓰기 전에 파일을 읽으므로, 블록이 쓰인 뒤 코드로 읽힐 것이라는 점을 보여 주지 않습니다. 대신 블록을 삭제해도 소용없습니다. 다음 업데이트가 같은 열린 코드 블록 아래에 다시 쓰기 때문입니다. 규칙이 코드 블록을 열어 둔 채 END 마커를 잃은 이전 블록 아래에 블록을 쓰는 업데이트도 같은 경고를 받습니다. 그 경고는 그 이전 BEGIN 마커도 지목하며, 각 해결책이 그것을 바꿉니다.

파일을 고칠 때까지 `apothem verify`는 실패하고 `apothem doctor`는 그것을 보고합니다(`harness.stray_begin`으로). 현재 설치가 쓰는 파일이라면 `apothem status --profile`도 드리프트를 보여 줍니다. 설치 기록이 없으면 verify와 doctor는 `CLAUDE.md`나 프로필 문서를 검사하지 않습니다. 설치가 그 파일들을 썼다는 것은 기록만이 보여 주기 때문입니다. OpenClaw verify는 여전히 찾은 각 워크스페이스의 규칙 파일을 검사하며, 파일을 지목하지 않고 실패합니다.

설치 기록이 있으면 `apothem uninstall`은 파일을 그대로 두고, 설치의 나머지를 제거하며, 여러분이 파일을 고칠 때까지 완료되지 않은 채로 남습니다(두 번째 실행을 포함해 종료 코드 `2`). 설치 기록이 남아 있으므로, 이후의 설치도 파일을 그대로 두고, 다음 제거가 그것을 다시 지목합니다. 그 경고는 같은 방식으로 번호가 매겨진 해결책을 제시하고 "Then run the uninstall again."으로 끝납니다. 예: "Fix A: A1. Change line 6: add a word inside its comment. Apothem then finds no block of its own in this file." 그런 파일에 남은 마커 쌍은 여러분의 것을 포함해 무엇이든 제거를 완료되지 않은 채로 두므로, 각 해결책은 Apothem의 블록이라고 부르지 않는 모든 쌍의 BEGIN 마커 줄을 바꿉니다. 그 `✗ <harness> uninstall did not finish:` 줄은 "1 file(s) hold marker lines Apothem cannot tell from your text, so Apothem left them as they are; fix the marker lines each warning names, keeping your own text, then run apothem uninstall again"으로 이어집니다. 설치 기록이 없으면, END 마커가 코드 안에 있고 그 뒤에 다른 마커 쌍이 있는, 코드 바깥의 BEGIN 마커만 경고를 받으며, 제거는 그것과 기록이 보여 주지 않는 경로에 대해 완료되지 않은 채로 남습니다(종료 코드 `2`)([완료되지 않은 제거](/docs/cli-reference/uninstall#an-uninstall-that-did-not-finish) 참조).

고른 해결책의 모든 단계를 하세요. Apothem의 블록만 삭제하고, 코드에서 인용한 END 마커 위에 여러분의 BEGIN 마커를 그 뒤에 마커 쌍 없이 남겨 두면, 그 두 마커가 Apothem의 블록으로 읽힙니다. 다시 실행하는 제거가 그 사이의 줄을 빼내고, 이후의 설치나 업데이트가 그 줄들을 교체합니다.

설치 기록이 없으면 코드에서 인용한 마커 쌍은 여러분의 텍스트입니다. 설치는 그 뒤에 블록을 추가합니다(Apothem이 frontmatter와 함께 쓰는 규칙 파일에서는 그 frontmatter와 블록이 대신 맨 위로 갑니다). 단, 그 쌍이 설치가 쓰는 블록과 정확히 같은 블록을 담고 있으면 파일을 그대로 두고 경고를 출력합니다. 따라서 설치 기록이 사라졌다면(예: 원장이 삭제되었을 때), 여러분의 코드 블록에서 Apothem의 블록을 손으로 삭제하세요. 이후의 설치는 그것을 여러분의 텍스트로 취급합니다.

해결하려면 경고가 제시하는 줄에서 지목된 파일을 여세요. 해결책이 지목하는 줄이 마커 사이에 Apothem의 규칙을 담은 Apothem의 블록인지, 여러분의 예시인지 어느 쪽이 맞는지 판단하세요. 그 해결책의 단계를 주어진 순서대로 하고, 다른 단계는 하지 마세요([번호가 매겨진 해결책 따르기](#follow-a-numbered-fix) 참조). 그런 다음 `apothem update`를 실행하고, 이어서 `apothem verify`를 다시 실행하세요. 완료되지 않은 제거 뒤라면 대신 `apothem uninstall`을 다시 실행하세요.

### 번호가 매겨진 해결책 따르기 [#follow-a-numbered-fix]

Apothem이 마커 줄의 위치를 정할 수 없는 파일, 둘 이상의 온전한 블록이 있는 파일, END 마커가 없는 BEGIN 마커, 그리고 설치 기록이 없는 제거가 남기는 Apothem의 블록에 대한 경고는 각 해결책을 그 경우를 지목하는 레이블 아래의 번호가 매겨진 단계로 제시합니다. 예: "Fix A, if lines 6 to 38 are Apothem's block:", 또는 어느 줄이 Apothem의 것이든 유효한 해결책이라면 "Fix A:". 해결책 A의 단계는 "A1.", "A2." 등이고, 해결책 B의 단계는 "B1.", "B2."이며, 한 문단 안에 있고, 해결책은 다음 실행이 그때 무엇을 하는지로 끝납니다. 한 해결책의 단계만 하세요.

단계의 모든 줄 번호는 경고가 출력될 때의 파일에서 그 줄의 번호이며, Apothem이 줄을 세는 방식으로 셉니다([파일에 END 마커가 없는 Apothem BEGIN 마커가 있음](#a-file-has-an-apothem-begin-marker-with-no-end-marker) 참조). 단계는 파일 아래에서 위로, 주어진 순서대로 진행됩니다. 각 단계는 다음 중 하나와 글자 그대로 같으며, 마침표로 끝납니다.

| 단계 | 할 일 |
| --- | --- |
| `Change line N: add a word inside its comment.` | `<!-- BEGIN APOTHEM MANAGED BLOCK (example) -->`처럼 N번 줄의 닫는 `-->` 바로 앞에 단어를 하나 추가하세요. 그 줄은 제자리에 남고 더 이상 마커로 읽히지 않습니다. |
| `Below line N, add a line of 3 backticks.` | 파일의 마지막 줄인 N번 줄 바로 아래에, 그 개수만큼의 백틱 문자(`tildes`라면 물결표 문자)만 담은 새 줄을 추가하세요. 마침표 앞에 `, indented 2 spaces`가 있으면 그 앞에 그만큼의 공백을 넣고, 없으면 줄을 왼쪽 여백에서 시작하세요. |

각 `Change line` 단계는 BEGIN 마커 줄을 제자리에서 바꿉니다. 모든 Apothem 블록, 마커 쌍, 잘못된 마커는 BEGIN 마커에서 시작하며, END 마커는 바로 위의 BEGIN 마커와만 쌍을 이루므로, 위에 BEGIN 마커가 없는 END 마커는 아무것도 표시하지 않으며, 여러분이 인용한 END 마커는 그대로 여러분의 텍스트로 남습니다. 바뀐 줄은 여전히 독립된 줄의 HTML 주석입니다. 어떤 줄도 움직이지 않으며, Markdown 뷰어는 다른 모든 줄을 이전과 같이 읽습니다.

블록을 유지하는 해결책은 파일의 다른 모든 BEGIN 마커 줄을 바꿉니다. 경고는 그 블록이 그때 하나의 온전한 블록으로 읽힌다는 것을 파일의 레이아웃이 보여 줄 때만 그런 해결책을 제시합니다. 즉, 파일 끝까지 이어지는 여러분의 코드 블록이 그 블록을 담고 있지 않고, 처음 바뀐 줄부터 블록까지의 어떤 줄도 그 BEGIN 마커가 읽히는 방식을 바꾸지 않을 때입니다. 그런 해결책은 "The next update then replaces Apothem's block", "Lines 1 to 32 are then the one block in the file", 또는 제거의 경우 "The uninstall run again then takes Apothem's block out"으로 끝납니다. 블록을 유지하지 않는 해결책은 파일의 모든 BEGIN 마커 줄을 바꾸며 "Apothem then reads none of these lines as its markers, and the next update writes its block at the end of the file", 또는 제거의 경우 "Apothem then finds no block of its own in this file"로 끝납니다. 어느 쪽이든, 여러분이 바꾸는 줄 아래의 이전 Apothem 텍스트는 END 마커 줄과 함께 그 후 여러분이 손으로 삭제하면 됩니다.

어떤 줄도 닫지 않는 여러분의 코드 블록은 Markdown 뷰어에서 파일 끝까지 이어지지만, Apothem은 그 여는 줄을 텍스트로 읽습니다. 여러분의 프로필 규칙에 있는 코드 블록이 그것을 닫게 되고, 그러면 Apothem 블록의 BEGIN 마커가 코드로 읽힙니다. 그래서 파일이 그런 코드 블록 안에서 끝나면, 파일에 Apothem 블록을 남기지 않는 해결책은 먼저 "A1. Below line 7, add a line of 3 backticks."처럼 마지막 줄 아래에 그 코드 블록의 닫는 줄을 추가합니다. 그러면 다음 설치나 업데이트가 그 뒤, 파일 끝에 블록을 추가합니다. 그런 코드 블록이 담고 있는 블록을 유지하는 해결책은 없습니다.

Apothem은 `<!--`로 열리고 이후의 줄에서 끝나는 주석처럼 HTML 블록 안의 코드 펜스를 다른 코드 펜스와 같이 읽으며, 목록 항목의 텍스트가 왼쪽 여백에서 이어지는 줄은 Apothem에게는 그 항목을 끝냅니다. Markdown 뷰어는 둘 다 하지 않습니다. 파일이 끝나는 코드 블록 위의 줄이 HTML 블록을 시작할 수 있거나(태그로 시작하는 모든 줄이 해당하며, 꺾쇠괄호 안의 링크, 일반 텍스트 줄 바로 아래 줄의 태그, 코드 블록 안의 HTML은 제외), 그 위에서 목록 항목의 텍스트가 왼쪽 여백에서 이어지고 들여 쓴 줄이 뒤따르면, 그 닫는 줄은 뷰어에서 대신 코드 블록을 시작할 수 있습니다. 그러면 그 해결책은 번호가 매겨진 단계를 제시하지 않습니다. "Apothem cannot give numbered steps for this fix"라고 말하고 코드 블록을 여는 줄을 지목합니다. 그 줄이 코드 블록을 열지 않도록, 또는 뷰어가 보여 주는 끝에서 코드 블록이 닫히도록 파일을 손으로 편집하세요. 그러면 그 파일에 대한 다음 경고가 번호가 매겨진 단계를 제시합니다.

### Claude Code에서 훅이 실행되지 않음

~/.claude/settings.json에서 훅 항목을 확인하여 Apothem이 연결되어 있는지 확인하세요. 파일에 훅이 누락된 경우, apothem install을 다시 실행하세요.

### OpenCode가 Apothem 규칙을 로드하지 않음

`apothem install`, `apothem update`, `apothem verify`는 OpenCode의 구성 폴더에 있는 여러분의 파일이 OpenCode 1에서 Apothem이 `opencode.json`에 쓰는 `instructions` 목록을 로드하지 못하게 할 때 메모를 출력합니다.

- 자체 `instructions` 목록이 있는 `opencode.jsonc`는, 빈 목록이라도 Apothem의 목록을 대체합니다. 그 키를 제거하거나, 그 항목들을 `opencode.json`의 목록으로 옮기세요. 설치는 그곳에서 자신이 쓰지 않은 항목을 유지합니다.
- 그곳에 있는 `config.json`, `opencode.json` 또는 `opencode.jsonc`를 OpenCode 1이 읽거나 구문 분석할 수 없으면, OpenCode 1은 어떤 구성도 로드하지 못합니다. 최상위가 객체가 아니거나, `instructions` 값이 텍스트 목록이 아니거나, `{file:path}`가 OpenCode 1이 읽을 수 없는 파일을 지목하는 파일, 그리고 그런 이름의 폴더도 마찬가지입니다. 파일을 주석과 후행 쉼표만 추가된 하나의 JSON 객체로, `instructions`는 텍스트 목록으로 고치거나, 파일을 폴더 밖으로 옮기세요. 메모가 OpenCode 1이 `{env:NAME}` 값을 넣으면 파일이 깨진다고 말하면, 그 변수의 값에 백슬래시, 큰따옴표, 제어 문자가 없도록 바꾸세요. 예를 들어 Windows 경로를 슬래시로 쓰세요. 메모가 Apothem이 프로필의 MCP 서버에 대해 그 `{env:NAME}`을 쓴다고 말하면, 업데이트는 파일에서 제거된 참조를 다시 쓰므로, 변수를 바꾸거나, 그대로 유지하려면 그 서버를 `harnesses.opencode.mcp_servers.<name>` 아래에 다시 정의하고 값을 파일에 저장한 뒤 그 파일을 지목하는 `{file:path}`로 쓰세요. 메모가 파일의 두 번째 문제를 지목하면 그것도 고치세요. Apothem이 `{file:path}`가 지목하는 파일을 OpenCode 1이 읽을 수 있는지 구별할 수 없다고 말하면, 그 파일도 읽을 수 있는지 확인하세요.

이 메모들은 OpenCode 1에 관한 것입니다. OpenCode 2는 두 목록을 모두 읽으며 `config.json`은 읽지 않습니다. 구문 분석할 수 없거나 최상위가 객체가 아닌 파일은 건너뛰므로, `opencode.json`의 경우 규칙도 놓치게 됩니다. OpenCode 2가 그 파일로 무엇을 하는지 알려져 있으면 메모가 그것을 말합니다. 메모는 어떤 파일이나 종료 코드도 바꾸지 않습니다. 설치나 업데이트가 `opencode.json`을 전혀 구문 분석할 수 없으면 대신 `config.unparseable` 오류와 함께 멈춥니다. 자세한 내용은 [OpenCode](/docs/harnesses/opencode)를 참조하세요.
