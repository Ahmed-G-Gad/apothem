Apothem은 2분 이내에 설치되며 기존 하니스 구성과 함께 동작합니다. 모든 경로는
동일한 자체 완결형 엔진을 실행합니다 — 소스 트리가 벤더링된 종속성을 담고 있으며,
시스템 Python 3.10 이상에서 체크아웃으로부터 실행됩니다
([자체 완결형 런타임](/docs/architecture/self-contained-runtime) 참조).

**모든 경로가 공유하는 두 가지 사전 요건:** `PATH`에 있는 시스템 **Python 3.10
이상**, 그리고 그 인터프리터에서 임포트할 수 있는 `click`과 `rich` 패키지입니다.
npm 심(채널 2), VS Code 계열 확장(채널 4), 명령줄 부트스트랩(채널 5–7)은 `npx`를
실행하기 위해 추가로 **Node.js 18 이상**이 필요합니다. Python 3.10과 Node.js 18 및
20은 업스트림 수명 종료를 지났습니다. 이들은 계속 지원되고 테스트되지만, 더 새로운
버전을 권장합니다([사전 요건 한눈에](#사전-요건-한눈에) 참조). 아래 각 채널의
섹션은 해당 채널의 정확한 사전 요건, 복사해서 바로 쓸 수 있는 명령 하나, 그리고
검증 단계를 다시 제시합니다.

모든 경로는 멱등적입니다. 재실행은 안전하며 같은 상태로 수렴합니다.

## 1. Claude Code 플러그인

**사전 요건:** Claude Code, 그리고 `PATH`에 있는 시스템 Python 3.10+.

플러그인 경로는 전적으로 Claude Code 내부에서 실행됩니다. Apothem 엔진을 슬래시
명령, 위임 작업자, 스킬, 규칙, 훅과 함께 번들하며, 이 모두를 자체 완결형 플러그인
트리에서 실행할 수 있습니다.

```text title="Inside Claude Code"
/plugin marketplace add ahmed-g-gad/apothem
/plugin install apothem@apothem
```

설치 후에는 Apothem 명령 세트, 번들된 위임 작업자, 스킬, 그리고 네 가지
[출력 스타일](/docs/reference/output-styles)(`/output-style`로 또는 `/config`에서
하나를 고릅니다)을 모든 Claude Code 세션에서 사용할 수 있습니다. 플러그인은 각
명령을 스킬로 제공합니다. 스킬은 `SKILL.md`와, 필요할 때 로드하는 세부 내용을 담아
그 옆에 두는 `references/` 폴더로 이루어지므로, Claude Code는 플러그인의 접두사를
붙여 호출합니다: `/apothem:plan-spec`, `/apothem:security-audit` 등. 두 이름은
Claude Code 자체가 사용합니다. `/plan`은 플랜 모드로 들어가고 `/code-review`는
번들된 리뷰를 실행하므로, Apothem 명령을 쓰려면 `/apothem:plan`과
`/apothem:code-review`를 입력하세요. 플러그인 대신 Apothem 엔진이 Claude Code에
설치하는 경우, 같은 스킬이 접두사 없이 `~/.claude/skills/`에 쓰이며, 개인
`code-review` 스킬이 번들된 `/code-review`를 대체합니다(그 `/review` 별칭은
여전히 번들된 것을 실행합니다). 두 이름, `projectify`와 `workflow`는 네이티브
스킬이기도 합니다. 플러그인과 엔진 설치가 제공하는 것은 네이티브 스킬이며, 명령에서
파생한 스킬이 아닙니다. 명령이 어떻게 나뉘는지는
[Claude Code](/docs/harnesses/claude-code#command-skills-and-reference-files)를, 전체 명령
카탈로그는 [슬래시 명령](/docs/reference/commands)을 참조하세요.

**검증:** Claude Code 내부에서 `/plugin`을 실행하여 **apothem**이 설치됨으로
나열되는지 확인하거나, 터미널에서 드리프트 보고서를 확인하세요.

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 2. npm 심(`npx`)

**사전 요건:** Node.js 18+(`npx`용)와 `PATH`에 있는 시스템 Python 3.10+. 심은
인터프리터를 찾아 모든 CLI 명령을 번들된 엔진으로 전달합니다 — 시스템에 영구적으로
배치되는 것은 없습니다. 심은 `python3`, `python`, `py -3`을 이 순서대로 시도합니다.
<strong><code>APOTHEM_PYTHON</code></strong>을 인터프리터 경로로 설정하면 그 인터프리터를 먼저 시도하며,
Python이 설치되어 있지만 `PATH`에 없을 때, 또는 여러 버전이 설치되어 있고 그중 특정
버전을 원할 때 필요한 설정입니다. 지정한 인터프리터도 여전히 Python 3.10+ 검사를
통과해야 합니다. 통과하지 못하면 심은 대신 `python3`, `python`, `py -3`을 이
순서대로 시도합니다.

```bash title="npx"
npx @ahmed-g-gad/apothem install --harness claude-code
```

프로필이 없는 머신에서는 이 첫 `install`이 `~/.config/apothem/profile.yaml`에 초기
프로필을 생성하고 그 사실을 알립니다. 이 프로필의 신원 필드는 플레이스홀더입니다.
이를 개인화한 다음(`npx @ahmed-g-gad/apothem profile edit`), 적용하려면 `install`
대신 `update`로 명령을 다시 실행하세요.

저장소에서 곧바로 실행할 수도 있습니다.

```bash title="npx from the repository"
npx github:ahmed-g-gad/apothem install --harness claude-code
```

[CLI 참조](/docs/cli-reference)의 모든 명령이 이 형식으로 동작합니다. `apothem`
대신 `npx @ahmed-g-gad/apothem`을 쓰세요. 이는 별도의 플러그인이나 확장 레지스트리를
노출하지 않는 OpenCode와 그 밖의 모든 도구의 설치 경로이기도 합니다 — Apothem은
이 도구들을 네이티브 구성 디렉터리로 곧바로 동기화합니다
(`npx @ahmed-g-gad/apothem install --harness opencode`).

**검증:**

```bash title="Verify"
npx @ahmed-g-gad/apothem --version
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 3. 원샷 설치 프로그램

**사전 요건:** `PATH`에 있는 시스템 Python 3.10+(설치 프로그램이 `click` / `rich` 사전 요건을 대신 추가하겠다고 제안합니다). 네트워크 설치에는 최신 릴리스를 찾기 위한 `git`과 서명된 릴리스 태그를 확인하기 위한 `gpg`가 필요합니다(Git for Windows에는 두 도구가 모두 포함되어 있습니다). [cosign](https://docs.sigstore.dev/cosign/system_config/installation/)은 선택 사항입니다. cosign이 있으면 설치 프로그램은 서명된 릴리스 아카이브도 확인합니다.

설치 스크립트는 한 번의 실행으로 최신 릴리스를 해석하고, 이를 확인하고
([신뢰 모델](#신뢰-모델) 참조), Apothem 소스 트리를 `~/.apothem`에 배치하고,
프로필이 없으면 초기 프로필을 생성하고, 첫 하니스를 머티리얼라이즈하고, 결과를
검증합니다. 초기 프로필에는 플레이스홀더 신원 필드가 들어 있습니다. 프로필을 편집한
다음 `apothem update --harness <name>`을 실행하여 여러분의 값을 적용하세요. 재실행은
멱등적입니다. git 클론은 가져오기(fetch)되고 그 새 태그가 확인된 뒤에야 해석된
태그로 체크아웃되며, 릴리스 아카이브 설치는 제자리에서 업데이트되고, 하니스는 다시
머티리얼라이즈됩니다. 엔진이 부분 완료(종료 코드 `2`)로 끝나면, 설치 프로그램은
경고 한 줄을 출력하고, 그래도 검증을 수행하고, `apothem` 명령을 배치하고 그 배너를
출력한 다음, 종료 코드 `2`로 끝납니다. 엔진은 Apothem 마커 줄 때문에 파일을 그대로
두었을 때, 또는 무언가를 기록한 뒤 중지했을 때 부분 완료로 끝납니다
([엔진이 파일을 그대로 두는 경우](/docs/install/updating#when-the-engine-leaves-a-file-as-it-is) 참조).
검증 설치가 기본이자 권장 경로입니다.

먼저 메인테이너 서명 키를 한 번 가져오세요. 모든 네트워크 설치는 cosign 유무와 관계없이 릴리스 태그를 이 키와 대조하여 확인하며, 키가 사용자의 키링에 없으면 중단됩니다. 지문이 `5C89 98F9 F241 7204 45D3  F28B 7039 6FED 9C63 4163`인지 확인하세요. 이 값은 [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md#maintainer-signing-key)에 게시되어 있습니다. Windows에서는 `git verify-tag`가 Git for Windows에 포함된 `gpg`의 키링을 읽으므로, 키 가져오기는 Git 자체의 `bash`를 통해 실행합니다:

```bash title="macOS · Linux · WSL2 · BSD — import the key once"
curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import
gpg --fingerprint 70396FED9C634163
```

```powershell title="Windows · PowerShell — import the key once"
& "$env:ProgramFiles\Git\bin\bash.exe" -c 'curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import && gpg --fingerprint 70396FED9C634163'
```

```bash title="macOS · Linux · WSL2 · BSD — latest signed tag, verified"
curl -fsSL https://apothem.ahmedgad.com/install.sh | bash
```

```powershell title="Windows · PowerShell — latest signed tag, verified"
irm https://apothem.ahmedgad.com/install.ps1 | iex
```

같은 스크립트가 체크아웃의 `scripts/installer/` 아래에 함께 들어 있으므로
— `.sh`, `.ps1`, `.bat` 형식의 `install`, `uninstall`, `update` — 클론한 뒤 직접
실행할 수 있습니다.

```bash title="From a checkout"
APOTHEM_HARNESS=claude-code sh scripts/installer/install.sh                                 # POSIX
$env:APOTHEM_HARNESS = 'claude-code'; pwsh -NoProfile -File scripts/installer/install.ps1   # Windows
```

파이프로 연결한 한 줄 명령은 로컬 트리를 결코 사용하지 않습니다. `curl ... | sh`와
`irm ... | iex`는 실행한 폴더와 그 상위 폴더를 무시하고 릴리스를 가져와 검증합니다.
설치 프로그램은 체크아웃 자체의 `scripts/installer/install.sh`(또는 `install.ps1`)를
그 경로로 실행할 때(어느 폴더에서든, 예: `sh ~/src/apothem/scripts/installer/install.sh`),
또는 `APOTHEM_SOURCE`가 그 트리를 가리킬 때에만 로컬 트리를 사용합니다. 설치
프로그램, 업데이트 프로그램, 제거 프로그램, `apothem` 심, npm 런처, 훅, 그리고 적합성
게이트의 검증기 프로세스는 현재 폴더를 Python의 모듈 검색 경로에서 제외합니다.
직접 입력한 `python -m apothem` 명령은 그렇지 않습니다. `-m`은 현재 폴더에서 모듈을
먼저 읽습니다.

어떤 런처(설치 프로그램, 업데이트 프로그램, 제거 프로그램, POSIX 및 Windows
`apothem` 심, npm 런처)도 여러분 자신의 `PYTHONPATH`에 있는 빈 항목과 상대 항목을
엔진에 전달하지 않습니다. 유지되는 항목은 전체 경로여야 합니다. Windows에서는
`C:\lib` 같은 드라이브 경로나 네트워크 경로, 그 밖의 환경에서는 `/`로 시작하는
경로입니다. 루트 기준의 `\lib`나 드라이브 상대 경로 `C:lib`는 제외됩니다. sh
스크립트는 자신이 실행하는 Python에 어떤 형식을 읽는지 묻고, 그 스크립트가 쓰는
`apothem` 심은 그 형식을 유지합니다. Windows Python(Git Bash에서 흔히 쓰는 것)은
엔진 경로를 `;`로 연결된 Windows 형식으로 받고, 여러분의 `PYTHONPATH` 중 드라이브
경로와 네트워크 경로만 유지합니다. Cygwin과 MSYS2 자체의 `python3`를 포함한 POSIX
Python은 `:`로 연결된 POSIX 경로를 받고, `/`로 시작하는 항목만 유지합니다. 설치
프로그램의 `git` 명령 중 클론을 대상으로 하지 않는 명령은 현재 폴더의 저장소를 읽지
않습니다.

### 신뢰 모델

`APOTHEM_REF`가 설정되지 않으면 설치 프로그램은 가장 높은 `vMAJOR.MINOR.PATCH`
릴리스를 해석하고 <em>그 릴리스</em>를 설치합니다 — 움직이는 `main` 브랜치는 결코
설치하지 않습니다. 구성이 머티리얼라이즈되기 전에 릴리스를 확인하며, 그 확인 방식은
`cosign`이 `PATH`에 있는지에 따라 달라집니다.

- <strong>cosign이 있으면</strong> 두 가지 확인을 모두 통과해야 합니다. 먼저, 릴리스
  태그는 다음 항목에서처럼 확인되는 메인테이너 키의 유효한 서명을 지녀야 하며, 서명된
  태그는 그 릴리스의 이름이 붙은 태그여야 합니다. 다른 릴리스의 서명된 태그를 이
  이름으로 다시 가리키게 한 것은 거부됩니다. 그런 다음 설치 프로그램은 릴리스의
  플랫폼 아카이브, 그 `SHA256SUMS` 파일, 그리고 `SHA256SUMS.cosign.bundle`을
  다운로드합니다. cosign은 Apothem의 릴리스 워크플로가 바로 그 태그에 대해
  `SHA256SUMS`에 서명했음을, 그리고 `--certificate-github-workflow-sha` 확인을 통해
  자신이 검증한 인증서가 서명된 태그가 가리키는 커밋에서 이루어진 실행에
  발급되었음을 확인해야 합니다. 설치 프로그램이 인증서를 직접 읽지는 않습니다. 그런
  다음 아카이브의 SHA-256이 나열된 다이제스트와 일치해야 합니다. 워크플로는 푸시되는
  모든 태그에 대해 실행되므로 그 서명만으로는 충분하지 않습니다. 태그 서명은
  메인테이너가 그 커밋을 릴리스했음을 보여 줍니다.
- <strong>cosign이 없을 때</strong>, 또는 `APOTHEM_HOME`에 이미 git 클론이 있을 때,
  설치 프로그램은 저장소를 클론하거나 업데이트하고 `git verify-tag`로 태그만
  확인합니다. 서명은 유효해야 <em>하고</em>, [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md)에 게시된 메인테이너 키로 만들어진 것이어야 하며, 서명된 태그는
  그 릴리스의 이름이 붙은 태그여야 합니다. 다른 키로 서명된 태그는 여러분의 키링이
  그 키를 신뢰하더라도 거부됩니다. 서명된 git 태그는 자신의 커밋을 SHA-1 ID로
  지칭합니다. cosign이 있으면 설치 프로그램은 아카이브의 SHA-256도 확인합니다. 기존
  클론은 가져오기되고 그 새 태그가 확인된 <em>뒤에</em> 체크아웃됩니다. 확인에
  실패하면 클론은 그대로 남으며, 추적 파일에 변경 사항이 있는 클론은 그 변경을 잃는
  대신 커밋하거나 stash하라는 메시지와 함께 업데이트를 중지합니다. `main` 같은
  비릴리스 ref를 사용하면 기존 클론은 origin에 있는 그 브랜치의 사본을 따릅니다.

설치 프로그램은 git을 다른 곳으로 돌리는 git 환경 변수(`GIT_DIR`, `GIT_WORK_TREE`
등)와, git이 다른 구성 파일을 가리키게 하는 변수(`GIT_CONFIG`, `GIT_CONFIG_GLOBAL`,
`GIT_CONFIG_SYSTEM`) 또는 다른 트리에서 속성을 읽게 하는 변수(`GIT_ATTR_SOURCE`.
여러분 자신의 구성에 있는 `attr.tree`는 클론에서 실행되는 모든 git 명령에서
비워집니다)를 무시하며, `APOTHEM_REPO`가 `-`로 시작하면 중지합니다.
`GIT_CONFIG_NOSYSTEM`은 여러분이 설정한 그대로 유지됩니다. 이 변수는 git이 시스템
구성을 읽지 않게 할 뿐입니다. git은 여전히 여러분 자신의 전역 구성과,
`GIT_CONFIG_NOSYSTEM`을 설정하지 않았다면 시스템 구성을 늘 찾던 위치에서 읽으며,
`git`, `gpg`, `cosign`은 여러분의 `PATH`가 찾는 프로그램입니다. 설치 프로그램은 찾은
그대로 이들을 신뢰합니다. 실행 전체 동안 설치 프로그램은 `GIT_NO_REPLACE_OBJECTS=1`을
설정하여 git이 replace ref를 통해 객체를 바꾸지 않게 하고, `GIT_NO_LAZY_FETCH=1`을
설정하여 git이 누락된 객체를 원격에서 스스로 가져오지 않게 하고, `GIT_ALLOW_PROTOCOL`을
file, git, http, https, ssh 전송으로 설정하여 환경에 있는 값이 그 목록을 넓힐 수 없게
하며, `GIT_ATTR_NOSYSTEM=1`을 설정합니다. 클론에서 실행되는 모든 git 명령에서
`core.attributesFile`이 비워지므로 git은 클론 밖의 어떤 속성 파일도 읽지 않으며,
따라서 여러분의 속성 파일에 정의된 매크로가 그곳에서 필터를 지정할 수 없습니다.
PowerShell 스크립트는 실행이 끝나면 네 변수를 모두 원래대로 되돌립니다. 설치
프로그램은 릴리스 태그를 한 번 읽고, 그 태그가 가리키는 커밋을 기록하고, 태그를
검증하고, 그 커밋을 ID로 체크아웃하며, `HEAD`가 그 커밋이어야 한다고 요구하므로,
확인 뒤에 태그가 옮겨져도 아무것도 바뀌지 않습니다. Windows PowerShell 5.1과 7에서는
https가 아닌 주소로 리디렉션되는 다운로드가 거부되며, 이는 POSIX 설치 프로그램의
`curl`과 같습니다.

`APOTHEM_HOME`은 여러분만 쓸 수 있는 폴더여야 합니다. 그 폴더에 쓸 수 있는 사람은
누구나 `apothem` 명령이 실행하는 코드를 바꿀 수 있기 때문입니다. Windows에서는
`C:\apothem`처럼 드라이브 루트에 만든 폴더를 Windows의 기본 권한 아래에서 그
컴퓨터에 로그인하는 모든 사용자가 변경할 수 있습니다. 기본값인 `~/.apothem`은
여러분 자신의 사용자 폴더에 있습니다. 가져오기를 거치는 각 설치, 업데이트, 드라이
런은 그렇지 않을 때, 또는 그 폴더나 그것을 담은 폴더를 다른 사람이 소유할 때 중지하지
않고 경고하며, 그 폴더, 그 폴더에 쓸 수 있거나 그것을 소유한 사람, 그리고 해결
방법을 알려 줍니다. 로컬 체크아웃에서의 설치와 `APOTHEM_SOURCE`가 설정된 업데이트는
이 확인을 건너뜁니다. Windows에서 이 경고는 `install.ps1`과 `update.ps1`에서
나옵니다. `install.sh`와 `update.sh`는 Git Bash, MSYS2, Cygwin에서 확인하지 않습니다
([문제 해결](/docs/install/troubleshooting#the-installer-warns-other-users-can-change-apothem_home) 참조).

확인에 실패하면 구성이 기록되기 전에, 그리고 설치 프로그램이 `APOTHEM_HOME`을
교체하기 전에 설치가 중단됩니다. 서명은 되어 있지만 메인테이너 공개 키가 아직 로컬
키링에 없는 태그는 대신 키 가져오기 안내와 함께 중단됩니다. 위에 표시된 대로 키를
가져오고, 그 지문을 [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md)에 게시된 값과 대조한 뒤 다시 실행하세요.

cosign이 있는 상태에서 다시 실행하면 이전의 릴리스 아카이브 설치가 업데이트됩니다.
새 소스는 먼저 `~/.apothem` 옆의 폴더에서 확인되고 압축이 풀린 다음 교체됩니다.
`~/.apothem`에서 소스 트리에 속하지 않는 모든 것은 새 설치로 이어집니다. 엔진의
롤백 백업(`backups/`), 설치 원장(`state/`), 플랜, 메모리, 그리고 그 밖의 데이터입니다.
어떤 단계가 실패하거나 Ctrl+C 또는 종료 신호로 실행을 멈추면 이전 설치가 변경 없이
복원됩니다. 그마저 실패하면 메시지가 이전 파일이 있는 위치를 알려 줍니다. 교체 중의
강제 종료나 정전은 잡아낼 수 없습니다. 이 경우 `~/.apothem` 옆에 폴더가 남을 수
있으며, 다음 가져오기 설치가 이를 보고합니다(아래 참조). 설치 프로그램이
`~/.apothem`을 교체할 때는 다음 규칙이 적용됩니다.

- git 클론은 `--yes` 없이 릴리스 아카이브로 교체되지 않습니다. 클론이 추적하지 않는
  파일은 새 설치로 옮겨지고, 클론 자체의 트리(그 기록과 소스)는 새 폴더
  `~/.apothem.before-apothem-<time>` 안으로 원래 이름(`.apothem`) 그대로 옮겨집니다.
  설치 프로그램이 그 위치를 알려 주며, 더 이상 필요하지 않으면 삭제하면 됩니다.
  `--yes`를 지정해도 클론에 잃게 될 로컬 작업, 즉 변경 사항, stash, 푸시되지 않은
  커밋, 또는 소스 트리의 추적되지 않은 파일이 있으면 설치 프로그램은 거부합니다. 그
  작업을 커밋하고 푸시하거나 다른 곳으로 옮긴 다음 다시 실행하세요. 이 확인은
  `--dry-run`에서도 실행됩니다. `.git` 파일(연결된 워크트리)도 클론으로 간주되며,
  `.git` 폴더도 마찬가지입니다.
- Apothem이 아닌 다른 것의 git 클론은 Apothem 설치를 담지 않은 다른 폴더와 똑같이
  취급되며(아래 참조), 클론으로서 업데이트되거나 교체되지 않습니다.
- 기존 클론은 git이 그 안의 모든 변경을 볼 수 있고 그 자체 설정의 어떤 것도 업데이트
  중에 코드를 실행하지 않을 때에만 제자리에서 업데이트됩니다. 가져오기 전에 설치
  프로그램은 다음 경우에 중지합니다. 파일이 assume-unchanged 또는 skip-worktree로
  표시된 경우, git이 `APOTHEM_HOME`에서 작업 트리를 찾지 못한 경우(클론의 구성이
  `core.bare`를 `true`로 설정한 경우처럼), 클론에 서브모듈이 있는 경우(인덱스에
  기록되었거나 `.git/modules`에 보관된 경우), `.git/info/attributes`가 필터나 diff
  드라이버(`filter=` 또는 `diff=`)를 지정하는 경우, 그 파일이나 구성 파일이 일반
  파일이 아닌 경우, 또는 클론이 다른 저장소에서 객체를 빌려 오는 경우
  (`objects/info/alternates`)입니다. 또한 클론 자체의 `.git/config` 또는
  `.git/config.worktree`에 `git clone`과 `git init`이 전체 클론을 위해 그곳에 쓰는
  설정, 브랜치 설정(브랜치의 `remote`와 `pushremote`는 `origin`이어야 합니다),
  `user.name`, `user.email`, `maintenance.auto`, `maintenance.strategy`, `pull.rebase`,
  `pull.ff` 이외의 설정이 있으면 중지하므로, `--filter`로 만든 부분 클론도 중지됩니다.
  [문제 해결](/docs/install/troubleshooting#the-installer-stops-the-existing-clone-is-set-up-in-a-way-the-update-would-trust)에
  그 목록이 있습니다. 메시지는 해당 설정과 그것이 들어 있는 파일을 알려 줍니다. 설정,
  속성, 객체 확인은 클론의 인덱스나 객체를 읽는 어떤 git 명령보다도 먼저 실행되며,
  `--yes`가 클론을 교체하려 할 때에도 서브모듈 확인과 함께 실행됩니다.
  작업 트리의 `.gitattributes` 파일을 적용하는 어떤 git 명령보다도 먼저, 설치
  프로그램은 git이 추적하지 않거나, 커밋된 사본과 다르거나, 커밋된 사본을 git이 읽을
  수 없거나 그 사본이 필터나 diff 드라이버를 지정하는 그런 파일(작업
  트리의 사본도 읽습니다)에서 중지하며, git이 추적하지 않는 클론 안의 git
  저장소에서도 중지합니다. git이 그 저장소의 `.gitattributes` 파일도 읽을 것이기
  때문입니다. 어떤 릴리스도 쓰지 않는 `backups` 같은 엔진 자체의 데이터 폴더는 이
  확인을 위해 읽지 않습니다. 가져오기 전에 설치 프로그램은 `src` 아래(대소문자
  표기와 무관하게)에 git이 추적하지 않는 파일이 있으면 중지합니다. 엔진이 그 파일을
  로드할 수 있기 때문입니다. 체크아웃 뒤에는 엔진이 클론에서 실행되기 전에 `src`
  아래의 Python 캐시 폴더(`__pycache__`)를 제거합니다. 클론의 git 훅은 업데이트 중에
  결코 실행되지 않으며, 클론에 대한 모든 git 명령은 페이저 없이, 자동 유지 관리 없이,
  파일 시스템 모니터를 끈 채로, file, git, http, https, ssh 전송만 허용하고(따라서
  클론 구성의 주소가 git이 `ext::` 같은 헬퍼 프로그램을 실행하게 만들 수 없습니다),
  서브모듈 재귀 없이 실행됩니다. `git diff`와 `git status`는 서브모듈을 건너뜁니다.
  다른 사용자가 소유한 클론은 설명과 함께 실행을 중지합니다(문제 해결 참조).
- 엔진 자체의 데이터(`backups`, `state`, `plans`, `memory`, `contexts`, `learning`,
  `providers`)만 담은 폴더는 `--yes` 없이 업데이트되며, 그 데이터는 유지됩니다.
- Apothem 설치를 담지 않은 폴더는 `--yes` 없이는 건드리지 않습니다. `--yes`를
  지정하면 설치 프로그램은 폴더 전체를 변경 없이 새 폴더
  `~/.apothem.before-apothem-<time>` 안으로 옮기고(안에서 원래 이름을 유지합니다),
  그 위치를 알려 준 뒤 새로 설치합니다.
- `APOTHEM_HOME`에 있는 심볼릭 링크(Windows에서는 심볼릭 링크 또는 정션)는
  거부됩니다. 그것을 교체하면 링크가 가리키는 폴더가 아니라 링크가 교체되기
  때문입니다. `APOTHEM_HOME`이 그 폴더를 가리키게 한 다음 다시 실행하세요. 예외는
  기존 git 클론으로, 이는 제자리에서 업데이트됩니다.
- Linux와 macOS에서는 이어 가져갈 파일이나 폴더의 이름에 공백이나 다른 특수 문자가
  있으면 설치가 중지됩니다. 먼저 그것을 `APOTHEM_HOME` 밖으로 옮기세요.

**한 번에 하나의 실행, 그리고 중지된 실행.** 설치, 업데이트, 제거 스크립트의 각
실행은 실행 전체 동안 `APOTHEM_HOME` 옆에 잠금(기본값 `~/.apothem.lock`)을 잡고,
실행이 성공, 실패, Ctrl+C, 또는 종료 신호로 끝나면 이를 놓습니다. `apothem` 명령
자체는 이 잠금을 잡지 않습니다. 두 번째 실행은 "Another Apothem install, update or
uninstall is running"과 함께 중지합니다. POSIX에서 잠금은 실행의 프로세스 ID를 담은
폴더입니다. 강제 종료된 실행이 남긴 잠금은 제거 방법과 함께 보고되며 결코 넘겨받지
않고, 다른 환경(예: 한 머신의 WSL과 Git Bash)에서 만든 잠금은 그곳에서 프로세스를
확인할 수 없는 잠금으로 보고됩니다. Windows PowerShell에서 잠금은 프로세스가 끝나면
Windows가 닫고 삭제하는 파일입니다. `APOTHEM_HOME`이 링크이면 모든 스크립트는 링크가
가리키는 폴더 옆에 잠금을 잡습니다. 드라이 런도 잠금을 잡습니다. 단, `APOTHEM_HOME`을
담을 폴더가 아직 없으면 예외입니다. 따라서 제자리 업데이트, 제거, 드라이 런을 포함한
모든 실행에는 `APOTHEM_HOME`을 담은 폴더에 대한 쓰기 권한이 필요하며, 권한이 없으면
실행은 아무것도 변경하기 전에 중지합니다.

교체 중의 강제 종료나 정전은 이전 설치나 `APOTHEM_HOME`의 다른 항목을 그 옆의
`.apothem-old.<name>.*`, `.apothem-extract.<name>.*` 또는 `.apothem-clone.<name>.*`
(여기서 `<name>`은 `APOTHEM_HOME`의 마지막 부분)에, 또는
`APOTHEM_HOME.before-apothem-<time>` 폴더에 남길 수 있습니다. 그 `APOTHEM_HOME`에
대한 다음 가져오기 설치는 드라이 런을 포함해 아무것도 변경하기 전에 중지하고, 각
폴더와 그 안으로 옮겨진 항목을 알려 주며, 되돌리는 방법을 안내합니다. 어느 홈에
속하는지 기록하지 않는 이전 설치 프로그램이 만든 폴더의 경우, 그 줄은 엔진 데이터만
알려 줄 수 있으니 폴더 안을 직접 살펴보세요. 이 확인은 아무것도 삭제하지 않습니다.
[문제 해결](/docs/install/troubleshooting#the-installer-stops-an-earlier-run-left-folders-beside-apothem_home)을
참조하세요.

`--dry-run`(Windows에서는 `-DryRun`)은 임시 폴더에서 릴리스를 가져와 확인하며
`~/.apothem`은 변경하지 않습니다. 실제 실행과 같은 확인을 수행하지만 기존 클론에
대해서는 한 가지 예외가 있습니다. 위에 나열된 대로 클론 자체의 설정은 확인하지만
클론으로 가져오기는 하지 않으므로, 실제 업데이트가 가져오기 뒤에 수행하는 추적 파일
변경 확인은 하지 않습니다. 특정 릴리스를 고정하려면 `APOTHEM_REF`를 사용하세요:

```bash title="Pinned, verified install"
APOTHEM_REF=vMAJOR.MINOR.PATCH sh -c "$(curl -fsSL https://apothem.ahmedgad.com/install.sh)"
```

`vMAJOR.MINOR.PATCH`를
[릴리스 페이지](https://github.com/ahmed-g-gad/apothem/releases)의 태그로 바꾸세요.
가장 오래된 릴리스 태그는 자체 서명이 없는 경량 태그이므로, 그 커밋이 서명되어
있더라도 태그 검사가 이 태그에서 중단됩니다. 그 이후의 모든 릴리스 태그는 주석
태그이며 서명되어 있습니다.
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md)의
릴리스 서명 섹션에 각 태그와 그 검증 방법이 나열되어 있습니다.

명시적 재정의는 기본 동작을 완화합니다. `APOTHEM_ALLOW_UNVERIFIED=1`은 클론 경로에서의 태그 확인 실패를 경고로 낮추고 계속 진행합니다. 에어갭 또는 로컬 용도이거나, 태그 서명 이전에 나온 릴리스를 설치하려는 경우에 사용합니다. 이 재정의는 cosign 경로를 결코 완화하지 않으므로, cosign이 있는 호스트에서는 `APOTHEM_VERIFY=signature`와 함께 설정하세요. 또한 서명된 태그가 그 릴리스의 이름이 붙은 태그인지에 대한 확인도 결코 완화하지 않습니다. 이 재정의는 서명되지 않은 태그나 다른 키로 서명된 태그를 통과시키므로, 그 확인은 메인테이너 키의 서명을 지닌 태그만 보호합니다. `APOTHEM_REF=main`은 `APOTHEM_ALLOW_UNVERIFIED=1`과 함께 지정할 때에만 검증 없이 움직이는 브랜치를 체크아웃합니다. `APOTHEM_REF=main`만 지정하면, 설치 프로그램은 `main`을 스테이징 폴더로(`APOTHEM_HOME`이 기존 클론이면 그 클론으로) 가져온 뒤, 무엇이든 체크아웃하거나 `APOTHEM_HOME`을 교체하거나 구성을 머티리얼라이즈하기 전에 중단합니다. 브랜치는 서명된 릴리스 태그가 아니기 때문입니다. `APOTHEM_SOURCE`를 통한 로컬 체크아웃은 아무것도 가져오지 않으며 검증도 건너뜁니다.

확인 방식을 직접 고르려면 `APOTHEM_VERIFY`를 설정하세요. 기본값은 `auto`입니다.

| 값 | 설치 프로그램이 확인하는 내용 |
| --- | --- |
| `auto`(기본값) | `cosign`이 `PATH`에 있고 `APOTHEM_HOME`이 git 클론이 아니면 `release`, 그렇지 않으면 `signature` |
| `release` | 메인테이너 키로 된 릴리스 태그의 서명과 서명된 태그가 그 릴리스의 이름이 붙은 태그인지, 이어서 릴리스 워크플로가 태그의 커밋에서 이루어진 실행에서 `SHA256SUMS`에 서명했는지에 대한 cosign의 확인, 그다음 아카이브의 SHA-256. cosign이나 `gpg`가 없으면 중지합니다 |
| `signature` | 메인테이너 키로 만들어져야 하는 릴리스 태그의 GPG 서명과, 서명된 태그가 그 릴리스의 이름이 붙은 태그인지 |
| `checksum` | `SHA256SUMS`에 대한 아카이브의 SHA-256만. `APOTHEM_ALLOW_UNVERIFIED=1`이 필요하며, 다운로드 전에 경고합니다. 체크섬 모드는 릴리스를 검증하지 않습니다. SHA256SUMS는 아카이브와 같은 릴리스에서 오므로, 일치는 다운로드가 손상되지 않았다는 것만 보여 줍니다. 릴리스의 파일을 바꿀 수 있는 사람은 누구나 둘 다 바꿀 수 있습니다. cosign도 `gpg`도 없는 호스트에서만, 그리고 이를 감수할 때에만 사용하세요 |

모든 아카이브 모드는 무엇이든 추출하기 전에 다이제스트가 일치하지 않으면 중단합니다.
초기 릴리스는 번들 이름을 `SHA256SUMS.sig`로 지정하며, 설치 프로그램은
`SHA256SUMS.cosign.bundle`이 없을 때 그 이름을 읽습니다.

그런 다음 엔진은 배치된 트리에서 직접 실행됩니다. `click`과 `rich`를 제외한 모든
서드파티 종속성은 소스 트리 내부에 벤더링되어 있으며, 진입점이 그 벤더 디렉터리를
직접 `sys.path`에 올립니다. 설치 프로그램은 자신이 쓴 `apothem` 심의 전체 경로를
출력합니다. 심을 쓰지 않았다면, 현재 폴더를 `sys.path`에서 제외한 채 엔진을 시작하는
명령을 출력합니다. 그 명령을 배너에서 복사하세요.

두 스크립트 모두 동일한 구성 환경 변수(`APOTHEM_HOME`, `APOTHEM_REPO`,
`APOTHEM_REF`, `APOTHEM_ALLOW_UNVERIFIED`, `APOTHEM_VERIFY`,
`APOTHEM_RELEASE_BASE`, `APOTHEM_SOURCE`, `APOTHEM_HARNESS`, `APOTHEM_PROFILE`,
`APOTHEM_SKIP_VERIFY`, `APOTHEM_AUTO_INSTALL_DEPS`, `APOTHEM_BIN_DIR`)를 읽습니다.
전체 표는 [설치 프로그램 환경 변수](/docs/how-to/installer-environment-variables)를,
`python -m` 호출 모델의 작동 방식은
[자체 완결형 런타임](/docs/architecture/self-contained-runtime)을 참조하세요.

**`apothem` 명령.** 설치가 성공하면 설치 프로그램은 번들된 엔진으로 전달하는
`apothem` 심을 씁니다 — POSIX에서는 `$HOME/.local/bin`에, Windows에서는
`%LOCALAPPDATA%\Microsoft\WindowsApps`(기본 Windows `PATH`에 이미 포함된 사용자
디렉터리)에 씁니다. 설치 프로그램은 여러분의 `PATH`를 결코 편집하지 않습니다. 그
디렉터리가 `PATH`에 오르면 수동 `PYTHONPATH` 설정 없이 `apothem <command>`를 직접
실행합니다.

**검증:**

```bash title="Verify"
apothem verify --harness claude-code

# or, before the shim is on PATH, by the shim's full path:
~/.local/bin/apothem verify --harness claude-code
```

## 4. VS Code 계열 확장

**사전 요건:** VS Code, Node.js 18+, 그리고 `PATH`에 있는 시스템 Python 3.10+.

**Apothem for VS Code** 확장은 [Visual Studio Marketplace](https://marketplace.visualstudio.com/items?itemName=ahmed-g-gad.apothem-vscode)에
`ahmed-g-gad.apothem-vscode`로 등록되어 있습니다. 확장 보기에서 설치하거나
`code --install-extension ahmed-g-gad.apothem-vscode`를 실행하세요. 또한 `apothem.vsix`
패키지로도 설치합니다: `code --install-extension apothem.vsix`를 실행하거나 에디터의
*Install from VSIX…* 명령을 사용하세요. 릴리스 워크플로가 패키지에 서명하고 각 GitHub
Release에 첨부합니다. 워크플로가 확장을 패키징하기 전에 게시된 릴리스에는 `.vsix`가 없습니다.
최신 릴리스에 없으면, `tools/vsce/`에 고정된 vsce 릴리스(이 vsce 릴리스에는
Node.js 22 이상이 필요합니다)로 체크아웃에서 패키지를 빌드하세요.
`npm ci --prefix tools/vsce --ignore-scripts`를 실행한 다음
`cd vscode-extension && ../tools/vsce/node_modules/.bin/vsce package --no-dependencies --out apothem.vsix`를
실행합니다. 이전 `apothem.vsix`로 설치한 사본은 식별자 `ahmed-g-gad.apothem`을 가지므로,
두 사본이 같은 명령을 모두 등록하지 않도록 `code --uninstall-extension ahmed-g-gad.apothem`으로
제거하세요. 하나의 확장이 VS Code 계열의 에디터를 모두 다룹니다. 팔레트 명령(`Apothem: Install`, `Verify`,
`Update`, `Uninstall`, `Doctor`)은 구성된 러너를 통해 동일한 엔진을 실행합니다(기본
러너는 `npx @ahmed-g-gad/apothem@<extension version>`이므로 확장은 함께 배포된 엔진
버전을 실행합니다. 소스에서 실행하려면 `apothem.runner` 사용자 설정이 로컬
체크아웃을 가리키도록 하세요). Install, Verify, Update, Uninstall은 어느 하니스에
적용할지 묻고 에디터 자체의 하니스를 먼저 제시합니다. `all`은 선택지 중 하나일 뿐
결코 기본값이 아닙니다. `apothem.runner` 설정은 머신 범위이므로 워크스페이스가
변경할 수 없으며, 확장은 신뢰할 수 있는 워크스페이스에서만 실행됩니다.

**검증:** 에디터의 명령 팔레트에서 **Apothem: Verify** 명령을 실행하거나,
터미널에서 다음을 실행하세요.

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 8. 직접 엔진(`python -m apothem`)

**사전 요건:** `click`과 `rich` 패키지를 임포트할 수 있는 시스템 Python 3.10+,
그리고 저장소의 체크아웃. Node.js는 필요하지 않습니다.

클론에서 곧바로 엔진을 실행하세요. 진입점이 벤더링된 종속성
(`src/apothem/_vendor`)을 `sys.path`에 올리므로, `click`과 `rich`를 임포트할 수
있다면 `PYTHONPATH=src`가 설정의 전부입니다.

```bash title="Direct engine"
git clone https://github.com/ahmed-g-gad/apothem
cd apothem
PYTHONPATH=src python -m apothem install --harness claude-code
```

`python -m`은 현재 폴더를 Python의 모듈 검색 경로 맨 앞에 두므로, 그곳에 있는
`click.py` 같은 파일이나 `apothem`이라는 폴더가 실제 모듈 대신 실행될 수 있습니다.
이 명령들은 체크아웃 루트나 여러분이 신뢰하는 다른 폴더에서 실행하세요. 설치된
`apothem` 명령은 현재 폴더를 읽지 않습니다.

npm 심과 마찬가지로, 프로필이 없는 머신에서 첫 `install`은
`~/.config/apothem/profile.yaml`에 초기 프로필을 생성하고 계속 진행합니다.

**검증:**

```bash title="Verify"
PYTHONPATH=src python -m apothem verify --harness claude-code
```

## 어떤 설치든 검증하기

위의 모든 채널은 각자의 검증 명령을 제시합니다. 두 가지 일반 형식은 다음과
같습니다.

```bash title="Installer path"
apothem verify --harness claude-code
```

```bash title="npx path"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

하니스 이름을 설치한 어댑터로 바꾸세요. 지원되는 모든 이름은
[하니스 목록](/docs/harnesses)을 참조하세요. 설치된 모든 어댑터를 한 번에
점검하려면(각 어댑터의 verify와 훅 명령), `verify --harness NAME` 대신 `doctor`를
위에서 사용한 형식 그대로 실행하세요. 즉 `apothem doctor`(그 폴더가 `PATH`에 없으면
심의 전체 경로나 설치 프로그램이 출력한 명령), 또는
`npx @ahmed-g-gad/apothem doctor`입니다. 플러그인 경로의 경우 Claude Code
내부에서 `/plugin`을 실행하여 **apothem**이 설치됨으로 나열되는지 확인하세요.

## 사전 요건 한눈에

- **Python 3.10 이상** — 이를 찾는 경로는 이름으로 찾으며, 그 이름은 경로마다
  다릅니다. npm 심은 `python3`, `python`, `py -3` 순으로 시도합니다. 설치 프로그램은
  `python3`, `python`, 그리고 버전이 붙은 이름 `python3.14`부터 `python3.10`까지
  시도합니다.
- **`click`과 `rich` 임포트 가능**(해당 인터프리터에서) — 엔진이 벤더링하지 않는
  터미널 대면 종속성 두 가지입니다. 설치 프로그램은 둘 다 확인하고, 누락된 항목의
  이름을 알려 주며, 대신 설치하겠다고 제안합니다 — 여러분의 확인을 받아서, 또는
  `--yes`(PowerShell에서는 `-Yes`)나 `APOTHEM_AUTO_INSTALL_DEPS=1`이 있으면
  자동으로. 그 밖의 모든 채널에서는 누락된 패키지가 오류(종료 코드 1)와 함께 엔진을
  중지시키며, 이 오류는 엔진이 찾은 인터프리터에 맞는 정확한 명령을, Apothem을
  테스트하는 기준이 되는 버전 제약 조건과 함께 제시합니다
  (`<interpreter> -m pip install "click==…" "rich>=…"`). `--json`을 사용하면 같은
  오류가 코드 `runtime.dependency_missing`이 담긴 JSON 엔벨로프로 전달됩니다.
- **Node.js 18 이상** — `npx`를 실행하는 경로에서만 필요합니다. npm 심(2),
  VS Code 계열 확장(4), 명령줄 부트스트랩(5–7)입니다.
- **수명 종료 런타임.** Python 3.10은 2026-10-01에, Node.js 18과 20은 각각
  2025-04-30과 2026-04-30에 업스트림 수명 종료에 도달했습니다. Apothem은 이들을
  선언된 최저 버전으로서 여전히 지원하고 CI에서 각각을 테스트하지만, 이들은 더 이상
  업스트림 보안 수정을 받지 않으므로 Python 3.11 이상과 Node.js 22 이상을 우선
  사용하세요.
  [런타임 최저 버전 정책](/docs/governance/release-engineering-policy#runtime-floors)이
  최저 버전을 올리는 방법을 설명합니다.
- **Git과 GnuPG** — 설치 프로그램 경로에서만, 그것도 네트워크 형식에서만
  필요합니다(스크립트는 이 둘로 최신 릴리스를 찾고 서명된 태그를 확인하며, cosign이
  없으면 소스를 클론합니다. 로컬 체크아웃에는 둘 다 필요하지 않습니다).
- **Claude Code** — 플러그인 경로에서만 필요합니다. **VS Code**와 각 명령줄
  부트스트랩 자체의 호스트 도구는 각자의 채널(4–7)에서만 필요합니다.
