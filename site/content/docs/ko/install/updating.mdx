## Claude Code 플러그인 업데이트

마켓플레이스 목록을 새로 고친 다음, Claude Code 내부의 `/plugin` 메뉴에서 플러그인을 업데이트하세요.

```text title="Inside Claude Code"
/plugin marketplace update apothem
```

`/plugin`을 열고 **apothem**을 선택한 뒤, 더 최신 플러그인 버전이 표시되면 업데이트 작업을 선택하세요.

## VS Code 확장 업데이트

확장은 함께 배포된 엔진 버전을 실행합니다. 기본 실행기는
`npx @ahmed-g-gad/apothem@<extension version>`이므로, 확장 자체가 업데이트될 때에만
새 엔진을 받습니다.

VS Code는 [확장 자동 업데이트](https://code.visualstudio.com/docs/configure/extensions/extension-marketplace#_extension-auto-update)
문서에 설명된 대로 확장 업데이트를 확인하고 스스로 설치합니다. 기본적으로 업데이트가
게시된 뒤 12시간을 기다립니다. 바로 설치하려면 확장 보기에서 확장의 **Update** 버튼을
선택하세요. 자동 업데이트를 껐다면 **Show Extension Updates** 명령을 실행하고
**Update**를 선택하거나, **Update All Extensions**를 실행하세요.

VS Code는 `.vsix` 파일에서 설치한 확장의 자동 업데이트를 끕니다. `apothem.vsix`로
설치했다면, 더 새로운 [GitHub Release](https://github.com/ahmed-g-gad/apothem/releases)에
첨부된 `apothem.vsix`를 같은 방법으로 설치하세요.

## npx는 항상 현재 릴리스를 실행합니다

`npx @ahmed-g-gad/apothem`은 실행할 때마다 현재 게시된 패키지를 확인하므로 업데이트할 것이 없습니다. 오래된 npx 캐시가 이전 사본을 제공하는 경우, dist-tag를 명시적으로 고정하세요.

```bash
npx @ahmed-g-gad/apothem@latest --version
```

## 설치 프로그램 기반 설정 업데이트

설치 프로그램을 다시 실행하거나 — 이는 멱등적입니다. 기존 git 클론을 가져오고(fetch), 새 릴리스 태그를 확인한 뒤에야 클론을 체크아웃하며, 릴리스 아카이브 설치도 업데이트합니다 — git 클론에서 동작하는 전용 업데이트 스크립트를 실행하세요.

```bash title="macOS · Linux · WSL2 · BSD"
bash scripts/installer/update.sh
```

```powershell title="Windows · PowerShell"
pwsh -NoProfile -File scripts/installer/update.ps1
```

업데이트 스크립트는 `APOTHEM_HOME`(기본값 `~/.apothem`)의 소스 트리를 `APOTHEM_REF`로 옮깁니다. 이 값을 설정하지 않으면 서명된 최신 `vMAJOR.MINOR.PATCH` 릴리스 태그로 해석되고, 태그 값을 지정하면 그 태그로 고정되며, `main`은 `APOTHEM_ALLOW_UNVERIFIED=1`도 함께 설정된 경우에만 움직이는 브랜치를 선택합니다. 이 재정의가 없으면 업데이트는 무엇도 체크아웃하거나 다시 머티리얼라이즈하기 전에 중단합니다. 브랜치는 서명된 릴리스 태그가 아니기 때문입니다. 먼저 ref를 가져오고 체크아웃하기 전에 `git verify-tag`로 태그 서명을 검증하므로, 검사에 실패하면 클론은 원래 버전에 그대로 남습니다. 서명은 SECURITY.md에 게시된 메인테이너 키로 만들어져야 하며, 서명된 태그는 해당 릴리스의 이름을 가진 태그여야 합니다. 서명되지 않았거나 변조된 태그, 또는 다른 키로 서명된 태그는 `APOTHEM_ALLOW_UNVERIFIED=1`이 중단을 경고로 낮추지 않는 한 중단됩니다(이 변수는 서명된 태그가 릴리스 태그인지 확인하는 검사를 우회하지 않습니다). 이 변수는 서명되지 않은 태그나 다른 키로 서명된 태그를 통과시키므로, 이 검사는 메인테이너 키의 서명을 지닌 태그만 보호합니다. `main` 같은 릴리스가 아닌 ref를 쓰면 클론은 origin에 있는 그 브랜치의 사본을 따릅니다. 체크아웃은 로컬 변경 사항을 절대 버리지 않습니다. 추적되는 파일에 변경 사항이 있는 클론은 업데이트를 멈추며, 변경 사항을 커밋하거나 stash한 뒤 다시 실행하면 됩니다. 가져오기 전에, 업데이트는 다음 경우에도 멈춥니다. 파일이 assume-unchanged 또는 skip-worktree로 표시된 경우(git이 그 변경 사항을 보지 못합니다), 클론의 작업 트리가 `APOTHEM_HOME`이 아닌 경우, 클론에 서브모듈이 있는 경우, `.git/info/attributes`가 filter 또는 diff 드라이버(`filter=` 또는 `diff=`)를 지정하는 경우, 그 파일이나 구성 파일이 일반 파일이 아닌 경우, 클론이 다른 저장소에서 객체를 빌려 오는 경우(`objects/info/alternates`), 또는 클론의 `.git/config`나 `.git/config.worktree`에 다음 설정 이외의 설정이 있는 경우입니다. 허용되는 설정은 전체 클론에 대해 `git clone`과 `git init`이 그곳에 쓰는 설정, 브랜치 설정(브랜치의 `remote`와 `pushremote`는 `origin`이어야 합니다), `user.name`, `user.email`, `maintenance.auto`, `maintenance.strategy`, `pull.rebase`, `pull.ff`입니다. `--filter`로 만든 부분 클론도 그 지점에서 멈춥니다. 메시지는 해당 설정과 그 설정이 있는 파일을 알려 주며, [문제 해결](/docs/install/troubleshooting#the-installer-stops-the-existing-clone-is-set-up-in-a-way-the-update-would-trust)에 허용되는 설정이 나열되어 있습니다. 또한 가져오기 전에 다음 경우에도 멈춥니다. 작업 트리에 git이 추적하지 않거나, 커밋된 사본과 다르거나, 커밋된 사본을 git이 읽을 수 없거나 그 사본이 filter 또는 diff 드라이버를 지정하는 `.gitattributes` 파일이 있는 경우(작업 트리의 사본도 읽습니다), `backups` 같은 엔진 자체의 데이터 폴더 밖에서 클론 안에 git이 추적하지 않는 git 저장소가 있는 경우(git이 그 안의 `.gitattributes` 파일을 읽게 됩니다), 그리고 엔진이 로드할 수 있으므로 `src`(대소문자 상관없이) 아래에 git이 추적하지 않는 파일이 있는 경우입니다. 체크아웃 후에는 엔진이 클론에서 실행되기 전에 `src` 아래의 Python 캐시 폴더(`__pycache__`)를 제거합니다. 업데이트 중에는 클론의 git 훅이 절대 실행되지 않으며, Apothem이 아닌 다른 프로젝트의 클론은 전혀 업데이트되지 않습니다. 업데이트는 실행하는 동안 `GIT_NO_REPLACE_OBJECTS=1`, `GIT_NO_LAZY_FETCH=1`, `GIT_ALLOW_PROTOCOL`, `GIT_ATTR_NOSYSTEM=1`을 설정하며, git은 클론 밖의 어떤 속성 파일도 읽지 않습니다([설치 프로그램 환경 변수](/docs/how-to/installer-environment-variables#the-installer-variables) 참조). 각 실행은 실행 내내 잠금 `<APOTHEM_HOME>.lock`을 유지하므로, 같은 `APOTHEM_HOME`에 대한 두 번째 설치, 업데이트 또는 제거는 멈춥니다. 잠금이 남아 있다면 [문제 해결](/docs/install/troubleshooting#the-installer-stops-another-run-holds-the-lock)을 참조하세요. 메인테이너 공개 키가 로컬 키링에 없는 서명된 태그는 [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md)에 게시된 지문을 가리키는 키 가져오기 안내와 함께 중단됩니다. 그런 다음 새로 고쳐진 트리에서 `apothem update`를 실행해 `APOTHEM_HARNESS`로 지정된 하니스를 다시 머티리얼라이즈합니다(하니스 기본값은 [설치 프로그램 환경 변수](/docs/how-to/installer-environment-variables) 표를 따릅니다). 이 명령은 사전 설치가 필요합니다. `APOTHEM_HOME`에 트리가 없고 `APOTHEM_SOURCE`도 설정되지 않은 경우, 먼저 설치 프로그램을 실행하라는 메시지와 함께 종료합니다.

업데이트 스크립트는 git 클론에서만 동작합니다. cosign으로, 또는 `APOTHEM_VERIFY=checksum`으로 만든 설치는 대신 릴리스 아카이브를 배치하므로, 업데이트 스크립트는 멈추고 cosign과 `gpg`를 `PATH`에 둔 채 설치 프로그램을 다시 실행하라고 알려 줍니다. 그 재실행은 새 릴리스로 교체하고, 엔진의 백업과 설치 원장을 포함해 릴리스에 포함되지 않은 모든 파일을 유지합니다. cosign이 없으면 설치 프로그램을 `--yes`(Windows에서는 `-Yes`)와 함께 다시 실행하세요. 아카이브 설치를 메인테이너 키로 확인된 git 클론으로 전환하고, 백업, 원장, 플랜, 메모리를 포함해 소스 트리에 속하지 않는 모든 것을 유지합니다. `APOTHEM_VERIFY=checksum`도 아카이브를 제자리에서 업데이트하며 `APOTHEM_ALLOW_UNVERIFIED=1`이 필요합니다. 체크섬 모드는 릴리스를 검증하지 않습니다. SHA256SUMS는 아카이브와 같은 릴리스에서 오므로, 일치한다는 것은 다운로드가 손상되지 않았다는 것만 보여 줍니다. 릴리스의 파일을 바꿀 수 있는 사람은 둘 다 바꿀 수 있습니다.

### 엔진이 파일을 그대로 두는 경우

엔진은 Apothem 블록을 담은 파일(예: `CLAUDE.md` 또는 `AGENTS.md`)을 그 파일의 Apothem 마커 줄 때문에 그대로 둘 수 있습니다. 예를 들어 파일의 Apothem 마커 사이에 온전한 블록이 두 개 있을 때입니다. 그러면 엔진은 나머지를 모두 쓰고, 그 파일을 지목하며 고치는 방법을 알려 주는 경고를 출력한 뒤, 종료 코드 `2`로 부분 완료(partial)로 끝납니다. 엔진은 무언가를 쓴 뒤에 멈출 때도 부분 완료로 끝납니다. 예를 들어 `APOTHEM_HARNESS=all` 실행에서 앞선 도구가 파일을 쓴 뒤 다른 도구 하나가 실패할 때입니다. 그 오류는 무엇이 실패했는지 알려 주며, 그 전에 끝난 각 도구는 오류 위에 자신의 줄을 가집니다. 그러면 설치 프로그램과 업데이트 스크립트는 한 줄을 더 출력합니다.

```text
! The engine ended as partial (exit code 2): its messages above name the files it left as they are, or the error that stopped it. Fix what they name, then run 'apothem update --harness claude-code' again.
```

두 스크립트는 완전히 성공했을 때처럼 실행을 마칩니다. 설치 프로그램은 여전히 verify를 실행하고, `apothem` 명령을 배치하고, 마무리 배너를 출력하며, 업데이트 스크립트는 여전히 마지막 줄로 "Update complete."를 출력합니다. 그런 다음 각 스크립트는 종료 코드 `2`로 끝납니다. 파이프로 연결한 PowerShell 실행(`irm ... | iex`)은 대신 `$LASTEXITCODE`를 `2`로 남기므로, PowerShell 세션은 열린 채로 유지됩니다. 한 번에 실행하는 `pwsh -Command "irm ... | iex"`(또는 `powershell -c`)는 부분 완료 실행을 `$LASTEXITCODE`로만 보고하므로, 프로세스 자체는 `0`으로 종료합니다. CI 작업이나 스크립트에 그 코드가 필요하면 명령 끝에 `; exit $LASTEXITCODE`를 붙이거나, `-File`로 스크립트를 경로로 실행하세요. PowerShell, bash 또는 다른 POSIX 셸에서는 그 명령을 작은따옴표로 감싸세요. 큰따옴표 안에서는 새 프로세스가 시작되기 전에 호출하는 셸이 자신의 `$LASTEXITCODE`를 넣으므로(POSIX 셸은 빈 문자열을 넣습니다), 프로세스가 실행의 코드로 종료하지 않습니다. cmd.exe에서는 큰따옴표를 써도 됩니다. 설치 프로그램의 시험 실행(`--dry-run`, Windows에서는 `-DryRun`)은 아무것도 쓰지 않으므로, 엔진이 그것을 부분 완료로 끝내지 않습니다. 엔진의 메시지가 지목한 것을 고치세요. 파일의 경우 여러분 자신의 텍스트를 유지하세요([파일이 Apothem의 마커 사이에 두 블록을 담고 있음](/docs/install/troubleshooting#a-file-holds-two-blocks-between-apothems-markers) 및 [Apothem이 자신의 블록과 여러분의 텍스트를 구별할 수 없음](/docs/install/troubleshooting#apothem-cannot-tell-its-block-from-your-text) 참조). 그런 다음 실행이 끝내지 못한 각 도구에 대해 `apothem update --harness <name>` 또는 업데이트 스크립트를 다시 실행하세요. 엔진의 그 밖의 0이 아닌 종료 코드는 그 자리에서 스크립트를 멈춥니다.

## 하니스 출력 재머티리얼라이즈

엔진을 업데이트하거나 `~/.config/apothem/profile.yaml`을 편집한 후에는 설치된 하니스 구성을 다시 도출하세요. 사용자 범위 어댑터에는 `--project`가 필요 없지만, 프로젝트 범위 어댑터에는 필요합니다.

```bash
apothem update --harness claude-code
apothem update --harness cursor --project /path/to/project
apothem update --harness all --project /path/to/project
```

파일 시스템 쓰기 없이 기계 판독 가능한 미리 보기가 필요하면 동일한 명령을 `--dry-run --json`과 함께 실행하세요.

## 현재 명령 경계

`apothem update`는 하니스 출력만 업데이트합니다. CLI는 `update --self`, `update --check`, `update --apply`를 구현하지 않습니다. 엔진 자체는 설치한 채널을 통해 업데이트하세요 — `/plugin` 흐름, 새로운 `npx` 실행, 또는 위의 설치 프로그램/업데이트 스크립트입니다.

## 엔진 버전 확인

```bash
apothem --version
npx @ahmed-g-gad/apothem --version
```
