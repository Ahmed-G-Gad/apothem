> **횡단 맨데이트의 표준 레지스트리.** 이 문서는 CM-N 레지스트리의 본문 전체를 담습니다. 실질적인 열거는 여기에 있으며, `src/apothem/rules/` 아래의 규칙 파일이 이를 운영합니다. 자세한 CM-N 본문이 필요한 모든 세션은 필요할 때 이 문서를 로드합니다.

## 레지스트리 자기 참조 예외

이 문서가 바로 표준 CM-N 레지스트리이며, `CM-1`부터 `CM-28`까지의 토큰이 *정의되는* 출처입니다. 이 토큰들을 *레지스트리 자체의 본문 안에서* 다시 기술하는 것은 표준이며, 플랜 내부 용어의 누출이 아닙니다. 코드베이스 격리 불변 조건은 *그 밖의* 모든 아티팩트(규칙, 헬퍼, 명령, 훅, 스키마, 스크립트, 도구, 테스트, 문서, README, 변경 로그, 커밋 제목/본문, 브랜치 이름, PR 제목/설명)에 계속 온전히 적용됩니다. `CM-N` / `TM-N` / `CP-N` 토큰은 쓰지 않으며, 자연스러운 도메인 언어만 사용합니다.

## 네임스페이스

`CM-N` = 구성 맨데이트(여기에서 정의되거나, 아티팩트 레지스트리의 규칙 행에 따라 `src/apothem/rules/*.md`에서 정의됨), `TM-N` = 템플릿 맨데이트(`src/apothem/skills/plan-suite/master-template.md` §4 "General Mandates", TM-1–28에서 정의됨), `CP-N` = 핵심 원칙(같은 템플릿 §6 "Core Principles", CP-1–27에서 정의됨)입니다. 플랜 스위트 템플릿이 표준 TM/CP 레지스트리이며, `/plan` 명령은 그 파일을 통해 상호 참조를 해석합니다. 헬퍼 아티팩트(규칙, 헬퍼, 명령, 훅)는 이 레지스트리를 참조로 인용합니다.

## 활성화

CM-1–10과 인지적 정체성은 모든 상호작용을 규율합니다. CM-11, CM-13, CM-15, CM-16, CM-20은 `/plan` 파이프라인 안에서만 적용됩니다. CM-12, CM-14, CM-17–19, CM-21–22, CM-24–26은 보편적으로 적용됩니다(항상 활성). CM-23, CM-27, CM-28은 각자 선언된 경로 필터 범위 안에서 보편적으로 적용됩니다. 임시 작업의 기본 심각도 등급: PERSONAL_USE.

## CM-1–10 (운영)

(1) 비판적 평가(→TM-10), (2) 가정 없음(→TM-1), (3) 구성 주도(→TM-2), (4) 구현 전 검색(→TM-4), (5) 최선의 해법(→TM-7), (6) 자기 개선(→CP-20), (7) 일관된 제품(→TM-11), (8) 병목 우선 집중, (9) 의사 결정 속도, (10) 가차 없는 정직함. 위반 지표를 포함한 전체 정의: `src/apothem/rules/operational-mandates.md`.

## CM-7 (플랜 내부 격리)

> 이것은 CM-7의 코드베이스 측면입니다. 제품 완결성 측면은 `src/apothem/rules/operational-mandates.md §CM-7`에 **일관된 제품(→TM-11)** 항목으로 문서화되어 있습니다. 두 레이블은 같은 맨데이트를 가리킵니다.

코드베이스 아티팩트는 플랜 내부 참조를 절대(NEVER) 포함해서는 안 됩니다. **금지 용어(표준 블록 — 형제 소비자는 이 열거를 상호 참조함):** TM-N, CM-N, CP-N, "Resumption Contract", "Phase Output Registry", "convention anchors", 단계 폴더 이름, 플랜 스위트 파일 이름(PROGRESS.md, PLAN-NOTES.md, PREAMBLE, MASTER-PLAN), 심각도 등급 이름(EXPLORING, PERSONAL_USE, SHARED, PUBLIC_LAUNCH). **보호 대상 아티팩트:** 소스 코드, 테스트, 구성, 스키마, 빌드 스크립트, 데이터, 자산, 커밋 메시지, 브랜치 이름, PR 제목/설명, README, CONTRIBUTING, API 문서, 변경 로그 등 Apothem 소스 트리 밖에서 보이는 모든 아티팩트(Claude Code의 `~/.claude/` 같은 하니스별 설치 대상 포함). 자연스러운 도메인 언어만 사용합니다. **형제 소비자**(각각 이 블록을 다시 열거하지 않고 참조로 인용함): `src/apothem/hooks/messages/pretooluse-bash.md`, `src/apothem/hooks/messages/pretooluse-write.md`, `src/apothem/hooks/messages/pretooluse-edit.md`, `src/apothem/hooks/messages/pretooluse-notebookedit.md`, `src/apothem/rules/operational-mandates.md` §CM-7 위반 지표.

## CM-11 (플랜 무결성)

**A — 산문 충실도:** 모든 요구 사항은 산문↔플랜 사이에서 추적할 수 있어야 합니다. 스코어카드: PASS ≥90% STRONG/0 ABSENT.
**B — 내부 일관성:** 플랜 스위트 안의 문서 간 일관성입니다. 스코어카드: PASS 100%.
**C — 게이트:** FAIL은 SHARED+에서 실행을 차단합니다(SHARED에서는 근거를 기록하면 Product Owner의 재정의 허용, PUBLIC_LAUNCH에서는 강제 차단). PERSONAL_USE에서는 권고입니다.

## CM-12 (컨텍스트 관리)

항상 간결하게 컨텍스트를 관리합니다. CM-24 규칙을 참조하세요. 네 개의 하위 계층은 아래 하위 참조 규약 섹션에 열거되어 있습니다. 압축 규율(CM-19)은 실행 행위를 규율하고, CM-12는 평상시 규율을 규율합니다.

## CM-13 (커밋)

- **A — 작업 단위 주기:** SHARED+에서는 작업마다 커밋합니다. PERSONAL_USE에서는 단계마다 커밋합니다. EXPLORING에서는 선택 사항입니다.
- **B — 품질/교정 커밋:** 품질 게이트 수정과 교정 변경은 기능 작업과 분리하여 즉시 커밋합니다.
- **C — 단계 종료 게이트:** 커밋되지 않은 변경은 단계 경계를 넘지 않습니다. CM-7 격리는 모든 git 아티팩트에 적용됩니다. PUBLIC_LAUNCH에서는 GPG 서명 커밋(`git commit -S`)이 필수입니다.
- **D — 사람 전용 작성자 표기:** 모든 git 아티팩트의 모든 작성자 표기 표면(커밋 제목, 커밋 본문, `Author:`, `Co-Authored-By:` 트레일러, `Signed-off-by:` 트레일러, 브랜치 이름, 태그 이름, 태그 주석, stash 이름, git-notes 본문, PR 제목, PR 설명)에는 **사람 기여자만** 표기합니다. 어시스턴트는 이 표면 어디에도 자신, 기반 언어 모델, 런타임 / 하니스 / IDE / 확장 / 공급업체, 그 밖의 어떤 자동화 도구도 작성자로 절대 표기하지 않습니다. 금지 패턴은 `src/apothem/rules/production-ready-prs.md` §6(Commit-Message Discipline → Human-only authorship)에 열거되어 기계적으로 강제되며, 매처는 `src/apothem/hooks/messages/pretooluse-bash.md` Scan 3에 있어 git에 쓰는 모든 Bash 호출에서 작동합니다.
- **E — git-mv / git-rm 대상의 숫자 접두사 규율:** 파일 시스템 경로의 숫자 접두사(`NN-`)는 순서를 나타내며, 순서가 본질적인 곳에만 적용됩니다. 단계 폴더 시퀀스, 하위 단계 시퀀스, 호스트가 발견한 서수 명명 체계가 여기에 해당합니다. 형제 시퀀스가 없는 루트 수준의 단일 항목에는 숫자 접두사를 붙이지 않습니다. 접두사를 붙이는 것은 존재하지 않는 순서 관계를 잘못 암시하는 무의미한 장식입니다. 전체 사양은 `src/apothem/rules/canonical-layout.md` §2.1에 있습니다. `src/apothem/hooks/messages/pretooluse-bash.md` Scan 2가 `git mv` / `git rm`과 커밋 본문의 경로 참조에 대해 기계적으로 강제합니다.

## CM-14 (세션 프로토콜)

**시작:** Blind Bootstrap을 실행합니다(CM-24 §6). **종료:** Phase Exit(CM-24 §2.5) + 메모리 평가(CM-26) + 아티팩트 진화(CM-22 §2+§4)를 실행합니다.

## CM-15–21 (파이프라인)

CM-15와 CM-16은 여기에서 인라인으로 정의됩니다(별도 규칙 없음). CM-17–21은 아티팩트 레지스트리의 규칙 표에 따라 규칙에 위임됩니다.

- **CM-15 집합적 일관성:** 수정 후에도 플랜 아티팩트가 일관성을 유지하는지 검증합니다.
- **CM-16 자율 실행:** SHARED+에서는 단계 사이에서 절대 멈추지 않습니다. 단계 전환 시 압축은 필수입니다(PERSONAL_USE+).
- **CM-17 작업자 팀:** 병렬화할 수 있는 작업에는 위임 작업자 팀을 배치합니다. CM-25 규칙을 참조하세요.
- **CM-18 오류 복구:** 일반 클래스 여섯 가지(CM-24 §8), 플랜 실행 클래스는 TM-18에 있습니다. 3회 실패 후 에스컬레이션합니다.
- **CM-19 압축 규율:** 선제적 압축 트리거입니다. CM-24 §3을 참조하세요.
- **CM-20 파이프라인 오케스트레이션:** prose→[approval]→generate→[approval]→review→[approval]→execute(01→NN). 검토 기법: `src/apothem/rules/planning-techniques.md`.
- **CM-21 창의적 품질:** 인지 필터는 장식이 아니라 품질 게이트입니다. 규모 조정은 인지적 정체성 규칙 §2를 따릅니다.

## CM-22–28 (규칙 위임)

규칙에 위임된 맨데이트의 한 줄 앵커입니다(전체 사양은 인용된 파일에 있음).

- **CM-22 규약 경계** — 생태계 규약과 선제적 아티팩트 진화. `src/apothem/rules/persistent-conventions-vigilance.md`를 참조하세요.
- **CM-23 대용량 파일 생성** — 단일 쓰기 임계값을 넘는 파일을 위한 증분 추가 프로토콜. `src/apothem/rules/large-file-generation.md`를 참조하세요.
- **CM-24 컨텍스트 관리 프로토콜** — 외부화, 압축, 블라인드 부트스트랩, 예산 규율. `src/apothem/rules/context-management.md`를 참조하세요.
- **CM-25 작업자 오케스트레이션** — 배치 패턴, 반환 계약, 컨텍스트 격리. 전체 사양은 [작업자 오케스트레이션 규칙](https://github.com/ahmed-g-gad/apothem/blob/main/src/apothem/rules/agent-orchestration.md)에 있습니다.
- **CM-26 자동 메모리 수명 주기** — 메모리 규율, 주제 파일 구성, 세션 종료 평가. `src/apothem/rules/auto-memory.md`를 참조하세요.
- **CM-27 클린 아키텍처 계층** — Domain / Application / Infrastructure / Presentation 분리. `src/apothem/rules/clean-architecture-layers.md`를 참조하세요.
- **CM-28 Python 시니어 아키텍트** — Python 아티팩트를 위한 SOLID, 스타일, 테스트, 보안 가드레일. `src/apothem/rules/code-craft-python.md`를 참조하세요.

## 규칙 위임 맨데이트와 인라인 정의 맨데이트

- **규칙 위임**(전체 사양은 `src/apothem/rules/`에 있음): 아티팩트 레지스트리 규칙 표의 "Implements" 열을 참조하세요. CM-1–10, CM-12, CM-14, CM-17–28을 포함합니다.
- **인라인 정의**(전체 사양은 여기에 있으며 별도 규칙 없음): CM-11(플랜 무결성), CM-13(커밋), CM-15(집합적 일관성), CM-16(자율 실행).

## 하위 참조 규약

명령은 맨데이트 안의 특정 하위 섹션을 참조하기 위해 문자 접미사를 사용합니다. 패턴: `CM-N` + 접미사 문자 = 규칙 섹션. **대소문자 규약:** 대문자 접미사는 맨데이트 안의 구조적 하위 섹션을 나타내고, 소문자 접미사는 관리(Stewardship) 계층 안의 더 세분화된 지시를 나타냅니다. 표준 하위 참조 키 매핑 표(레지스트리 내부 정의)는 아래 펜스 블록에 원문 그대로 보존되어 있습니다.
