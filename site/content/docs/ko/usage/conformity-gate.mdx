`src/apothem/conformity/gate.py`에 있는 적합성 게이트는 운영자가 작성하는 모든
아티팩트에 대해 15개 막대 사전 방출 게이트(M1-M15)의 기계적 부분을 실행합니다.

이 페이지의 명령은 Apothem 체크아웃을 전제로 하므로, 실행하는 각 명령 앞에
`PYTHONPATH=src`를 붙이세요. 스크립트로 설치한 뒤에는 `PYTHONPATH=src` 대신
`PYTHONPATH="$HOME/.apothem/src"`를 사용하세요.

## 게이트 실행

게이트는 **기본적으로 권고 모드**입니다. 발견 사항을 보고하고 `0`으로
종료하므로, 로컬 실행이 여러분을 막는 일은 절대 없습니다. 차단 수준의 발견
사항이 있을 때 0이 아닌 코드로 종료하려면 `--strict`를 추가하세요(또는
`APOTHEM_CONFORMITY_STRICT=1`을 설정하세요). 이는 CI와 pre-commit이 위반 변경을
실패시키는 데 사용하는 모드입니다.

```bash
# Advisory: report every validator's findings across the repo, exit 0
PYTHONPATH=src python -m apothem.conformity.gate --all .

# Strict: exit non-zero (code 2) when a blocking finding is present
PYTHONPATH=src python -m apothem.conformity.gate --all --strict .
```

이 명령들은 Apothem 체크아웃에서 게이트를 실행합니다. `python -m`은 현재
폴더에서 먼저 모듈을 읽으므로, 체크아웃 루트나 신뢰하는 다른 폴더에서
실행하세요. 파일을 신뢰할 수 없는 프로젝트를 검사하려면, 대신 스크립트 경로와
`-E -s`로 게이트를 실행하세요. 체크아웃에서는
`python3 -E -s src/apothem/conformity/gate.py --all .`, 스크립트로 설치한
뒤에는 `python3 -E -s ~/.apothem/src/apothem/conformity/gate.py --all .`입니다.
Windows에서는 Windows PowerShell과 cmd가 `~`를 확장하지 않으므로, `python3`
대신 `python`과 전체 경로를 사용하세요. PowerShell에서는
`$HOME\.apothem\src\apothem\conformity\gate.py`, cmd에서는
`%USERPROFILE%\.apothem\src\apothem\conformity\gate.py`입니다. 스크립트로
시작하면 현재 폴더가 Python 모듈 검색 경로의 첫 항목에 들어가지 않습니다.
`-E`는 `PYTHONPATH`도 제외하는데, 그 안의 빈 항목이나 상대 항목도 현재 폴더를
가리키기 때문입니다. `-s`는 사용자 site-packages를 제외합니다. 이것은 프로젝트의
파일을 게이트 자체의 Python 코드에서만 떼어 놓습니다. 게이트가 실행하는 `git`은
이어서 다룹니다.

세 개의 독립 실행형 검증기는 검사하는 프로젝트에서 `git`을 실행하며, 이들을
실행하는 `--all`과, `git ls-files`로 추적 파일을 나열하는 `--all-perwrite`도
마찬가지입니다.

```text
agents-md-coverage-grep
conventional-commit-grep
no-global-plans-grep
```

그 저장소 자체의 설정, 즉 `.git/config`, 그것이 포함하는 파일,
`.git/config.worktree`는 git이 읽기만 하는 동안에도 시작할 프로그램을 지정할 수
있습니다. 게이트는 알고 있는 그런 설정을 각각 git 명령줄의 옵션으로 끕니다. 이
옵션은 git이 읽는 모든 파일보다 우선하며, git이 서브모듈에서 시작하는 git에도
전달됩니다.

- 파일 시스템 모니터 없음(`core.fsmonitor`).
- 서명 프로그램 없음(`gpg.program`, `gpg.ssh.program`,
  `gpg.x509.program`은 아무것도 존재할 수 없는 경로를 가리키고,
  `log.showSignature`는 꺼져 있음).
- 훅, 페이저, 자동 유지 관리 없음.
- 외부 diff 프로그램이나 텍스트 변환 프로그램 없음. 서브모듈 변경은 커밋 id로만
  표시되므로, git이 서브모듈 안에서 두 번째 git을 시작하지 않음.
- 파일 내용은 `git cat-file blob`으로 읽음. `git show`라면 커밋으로 보여 줄
  서브모듈 항목을 이 명령은 거부함.

세 가지 설정은 프로그램이 아니라 git이 읽을 파일을 지정하며, 그 파일은 네트워크
경로에 있을 수 있습니다. 게이트의 명령줄은 git이 이것들도 읽지 못하게 합니다.
diff 순서 파일(`diff.orderFile`), 제외 파일(`core.excludesFile`), mailmap
파일입니다.

게이트는 또한 `GIT_NO_LAZY_FETCH=1`과 빈 `GIT_ALLOW_PROTOCOL`을 설정하므로, git은
부분 클론의 누락된 객체를 저장소가 지정한 주소로 가져오는 일이 없습니다.
게이트는 `PATH`의 전체 경로 항목에서만 git을 시작합니다. 현재 폴더에서 git을
가져오는 일은 없습니다. 그 폴더를 가리키는 빈 항목과 상대 `PATH` 항목을
건너뛰며, Windows가 경로 없는 프로그램 이름에 대해 하듯 그곳을 먼저 찾지도
않습니다. git이 이름으로 시작하는 프로그램에 대해서도 git은 그 전체 경로 항목만
받습니다.

따라서 다른 사람에게서 압축 파일이나 공유 폴더로 `.git` 폴더와 함께 받은
프로젝트에서도 이 명령들을 실행할 수 있습니다. 위의 어떤 설정도 게이트가
프로그램을 시작하게 만들 수 없습니다. 두 가지 한계가 남습니다. 저장소는 경로를
지정하는 어떤 설정이나 파일을 통해서든 여전히 git이 다른 곳의 경로를 읽게 할 수
있습니다. 예를 들어 `include.path`나 `includeIf`, `core.worktree`, `.git` 파일의
`gitdir:` 줄, `.git/objects/info/alternates`가 그렇습니다. Windows에서는 그곳의
네트워크 경로(`\\server\share`)가 Windows로 하여금 그 서버에 연결하고 여러분을
로그인시키게 합니다. 한 경우는 범위가 더 좁습니다. Git for Windows 2.55는 여러분
자신의 `safe.directory` 설정이 그 경로를 허용하지 않는 한, `gitdir:` 줄의
네트워크 경로를 연결하기 전에 거부합니다. 그리고 이 목록은 현재 알려진 설정을
다룹니다. 이후의 git 릴리스는 새 설정을 추가할 수 있습니다. 여러분 자신의 전역
및 시스템 git 설정은 여전히 적용되지만, 위의 설정은 예외로 게이트의 명령줄이
재정의합니다. 이것은 git에만 해당합니다. `python -m`은 현재 폴더에서 먼저 Python
모듈을 읽으므로, 신뢰하는 폴더에서 게이트를 시작하세요.

종료 코드: `0`은 깨끗함(또는 권고 모드), `2`는 strict 모드의 발견 사항 차단,
`3`은 사용법 오류로, 알 수 없는 플래그나 검증기 이름, 존재하지 않는 파일, 또는
존재하지 않는 루트 디렉터리입니다. `--help`는 전체 사용법을 출력하고 `0`으로
종료합니다. 모든 독립 실행형 검증기는 같은 `--help`를 받아들이며, 알 수 없는
플래그나 누락된 루트에 대해 `3`으로 종료합니다.

`.` 같은 상대 루트는 어떤 검증기든 실행되기 전에 절대 경로로 해석되므로,
`--all .`과 `--all "$PWD"`는 같은 트리를 검사합니다. 각 검증기는 검사한 대상의
수인 `inspected`를 보고하며, `--all`은 그 수를 모든 결과 항목에 복사합니다.
아무것도 검사하지 않은 검증기는 `passed: false`를 보고하므로, 잘못된 작업
디렉터리가 조용히 통과할 수 없습니다. 두 플랜 스위트 검증기는 예외입니다. 플랜
스위트는 gitignore된 `.apothem/plans/` 트리에 있으므로, 이 두 검증기는 깨끗한
체크아웃에서 `empty_scope_expected: true`를 보고하고도 통과합니다. 워크플로
검증기도 프로젝트에 아직 `.github/workflows/` 디렉터리가 없을 때 같은 방식으로
동작하며, 커밋 제목 검증기는 루트에 커밋 기록이 없을 때 같은 방식으로
동작합니다.

프로젝트에는 다른 사람이 만든 파일이 압축 파일이나 공유 폴더를 통해 들어올 수 있으므로, 모든 `--all` 검증기는 루트 아래의 실제 폴더를 거쳐 도달한 일반 파일과 실제 폴더만 열고 나열합니다. 심볼릭 링크나 Windows의 정션은 절대 따라가지 않으며, 루트 아래 어느 단계에서든 다음 항목을 없는 것으로 취급합니다.

- 링크. 루트 안을 가리키는 링크도 포함합니다. 탐색이나 폴더 목록은 이를 건너뛰므로, 링크 대상은 검증기가 그 대상 자체의 경로로 도달하는 곳에서만 검사됩니다.
- 이름 있는 파이프, 장치, 소켓. 읽기가 기다리거나 끝나지 않기 때문입니다.
- Windows에서 점이나 공백으로 끝나는 이름. Windows가 그 이름으로 다른 항목을 열기 때문입니다.

일부 검사는 링크 안으로 들어가지 않고 링크를 계속 사용합니다.

- 다른 파일을 가리키는 `CLAUDE.md`처럼 고정 파일이 심볼릭 링크인 경우, 게이트는 링크 자체의 텍스트를 읽고, 그것이 가리키는 파일이 실제 폴더를 거쳐 도달하는 프로젝트 안의 일반 파일일 때만 엽니다. 폴더별 `README.md` 링크도 같은 방식으로 인정됩니다. 절대 경로 링크는 프로젝트 폴더가 해석된 모습 그대로를 거쳐 쓰였을 때, 또는 Windows에서는 대소문자만 다른 같은 경로를 거쳐 쓰였을 때 인정됩니다. 단독으로 실행한 검증기는 경로에 `..`가 없으면 입력한 그대로의 폴더도 받아들이며, 게이트는 각 검증기를 시작하기 전에 폴더를 해석합니다. 링크된 `.gitattributes`는 git이 읽지 않으므로 여전히 없는 것으로 취급됩니다.
- `no-global-plans-grep`의 떠도는 플랜 검사는 링크인 플랜 폴더나 `.apothem` 폴더를, 링크가 어디로 이어지든 이름으로 보고합니다.
- `no-toplevel-docs-grep`은 루트의 `docs` 링크를 이름으로 보고합니다.
- `naming-grep`은 링크 자체의 이름을 검사합니다.

각 검증기의 보고서는 제외한 링크와 특수 파일을 `skipped_links`에 나열하므로, 링크가 흔적 없이 파일을 숨기는 일은 없습니다. 나열할 수 없었던 폴더(접근 권한 없음, 너무 긴 경로, 읽기 오류)와, 중첩된 체크아웃으로 건너뛴 폴더의 `.git` 항목이 링크나 특수 파일인 경우 그 항목도 여기에 나열합니다. 폴더 자체는 아래에서 설명하는 `skipped_checkouts`에 나열됩니다. 워크플로 검증기처럼 폴더가 없을 때 통과하는 검증기는 그 폴더가 링크이면 통과하지 않습니다. 파일이 그 뒤에 있을 수 있으므로, 아무것도 검사하지 않은 실행처럼 실패합니다. 하드 링크는 일반 파일이며 일반 파일처럼 읽힙니다. `--all` 검증기들과 `--all-perwrite`는 각 단계에 도달할 때 그 단계를 확인한 뒤, 루트에서부터 한 단계씩, 각 폴더를 바로 앞에서 연 폴더 안에서 열어 파일을 열며, 링크를 거치는 일은 없습니다. 따라서 게이트가 실행되는 동안 프로젝트에 쓸 수 있는 누군가가 확인을 마친 파일이나 그 위의 폴더를 링크나 이름 있는 파이프로 바꿔치더라도, 게이트는 링크를 거쳐 읽지 않고 파이프에서 기다리지도 않습니다. 그 파일은 읽지 않습니다. `--all` 검증기는 링크를 세는 것과 같이 그 파일을 없거나 읽을 수 없는 것으로 세고, 바꿔친 항목을 `skipped_links`에 나열합니다. `--all-perwrite`는 그 파일을 `link`로 세며, 다시 바꿔친 경우에는 아래에서 설명하듯 `unreadable`로 셉니다. Windows에서는 일반적인 방식으로 열 때와 마찬가지로 기다림이 하나 남습니다. 프로젝트에 쓸 수 있는 프로그램은 파일에 기회적 잠금(oplock)을 걸고, 게이트가 그 파일을 열어도 놓아주지 않을 수 있습니다. 어떤 방식으로 열어도 이 기다림은 피할 수 없으므로, `--all` 검증기는 10분 제한까지 기다리고, 그런 제한이 없는 `--all-perwrite`는 그 프로그램이 놓아줄 때까지 기다립니다. `--all`과 `--all-perwrite`에서 게이트 자체는 루트 안의 일반 파일만 열고, git이 나열하는 모든 경로를 포함해 가는 길의 각 폴더를 `lstat`로 확인하며, `.git` 항목 안은 절대 읽지 않습니다. git을 실행하기 전에, git을 실행하는 세 개의 `--all` 검증기와 두 개의 `--staged` 검사는 그 순간의 트리 그대로 루트와 git이 찾는 그 위의 모든 폴더의 `.git` 항목을 `lstat`로 확인합니다. 그중 하나라도 링크이거나 확인할 수 없으면 git을 실행하지 않습니다. 이 때문에 `.git`이 링크인 홈 폴더 아래의 모든 프로젝트처럼, 자체 저장소가 있더라도 git이라면 안전하게 다룰 프로젝트도 거부됩니다. 이것은 단순한 규칙을 위한 의도된 대가입니다. 세 개의 `--all` 검증기는 저장소, 그 저장 공간, 인덱스를 지정하는 `GIT_DIR` 및 다른 변수 없이 git을 실행하며, `--staged` 검사는 훅의 `GIT_DIR`을 유지합니다. 그 뒤 git이 어떤 저장소를 읽는지는 검사하지 않습니다. `gitdir:` 줄, `commondir`, alternates, `core.worktree`, include, 또는 git 폴더 안의 링크가 다른 저장소를 가리킬 수 있고 git은 이를 따르므로, git이 네트워크 경로에 닿거나 시간 제한까지 기다릴 수 있습니다. 게이트는 git의 출력을 이름, 모드, 상태 문자, 마지막 커밋의 제목, 커밋 시각, 몇 가지 설정으로만 사용하며, git이 출력한 경로를 루트 안의 각 단계를 확인하지 않고 여는 일은 없습니다. 링크를 찾으면 세 개의 `--all` 검증기는 각각 이를 `skipped_links`에 나열합니다(루트 안에 있으면 루트 기준 상대 경로로, 루트 위에 있으면 전체 경로로). 이때 `conventional-commit-grep`은 체크아웃 밖에서처럼 `not-a-git-repo`를 보고하지만 통과하지 않으며, 링크를 지목하는 `check_error`를 냅니다. `no-global-plans-grep`은 링크를 발견 사항으로 보고하고 실패하며, 동반 파일 검사는 기록이 없을 때처럼 최신성 테스트를 건너뜁니다. `--all-perwrite`도 추적 파일을 나열하지 않고 링크를 지목하는 `check_error`로 실패합니다. 두 개의 `--staged` 검사도 마찬가지이지만 링크는 `check_error`에서만 지목하거나, 실행된 폴더의 `.git` 항목이 링크라고 그곳에서 밝힙니다. 이 검사들은 훅의 `GIT_DIR`이 가리키는 저장소를 읽지만 실행된 폴더에서 시작하는 검색 경로의 링크는 여전히 거부합니다. 게이트가 확인할 수 없는 `.git` 항목(너무 긴 경로, 닿을 수 없는 공유, 접근 권한 없음)은 링크가 아니며 `skipped_links`에 나열되지 않습니다. `conventional-commit-grep`은 상태 `git-failed`와 `check_error`로 실패하고, 동반 파일 검사, `--all-perwrite`, 두 개의 `--staged` 검사는 항목을 확인할 수 없었다는 `check_error`로 실패하며, `no-global-plans-grep`은 이를 발견 사항으로 보고합니다.

각 독립 실행형 검증기는 별도의 프로그램으로 실행되며, 게이트는 `--all`과
`--check`에서 각 검증기에 10분을 줍니다. 가장 느린 검증기도 Apothem 자체
저장소에서 약 1분이 걸립니다. 제한 시간에 아직 실행 중인 검증기는, 아직
기다리고 있는 `git` 명령처럼 그것이 시작한 모든 프로그램과 함께 중지되며,
`passed: false`와 끝나지 않았다는 `check_error`로 보고됩니다. Linux와 macOS에서는
각 검증기가 자체 세션에서 실행되며, `timeout`이나 닫힌 터미널에서 오는 것처럼
게이트에 `SIGTERM`이나 `SIGHUP`이 오면, 게이트가 128에 시그널 번호를 더한 코드로
종료하기 전에 검증기의 프로그램을 중지합니다. 게이트가 검증기를 시작하거나
중지하는 동안 도착한 시그널도 마찬가지입니다. 게이트는 그 단계가 끝날 때까지
기다리며, 그 단계 중에 Ctrl+C가 뒤따르더라도 종료 코드는 128에 그 시그널 번호를
더한 값으로 유지됩니다. 어떤 프로그램도 잡을 수 없는 `SIGKILL`은 그곳에서
게이트만 끝냅니다. 게이트가 시작한 검증기는 끝날 때까지 계속 실행되며, 그
검증기가 기다리는 `git` 명령은 여전히 자체 제한 시간에 멈춥니다. Windows에서는
각 검증기가 job object 안에서 실행되며, job object는 게이트 자체가 끝날 때 그
프로그램들도 끝냅니다.
게이트가 그곳에서 시작하는 각 프로그램은 job object에 들어갈 때까지 일시 중단된
상태로 기다립니다. 재개할 수 없는 프로그램은 중지되며, 오류는 그 프로그램이 job
object 안에 있는지 알려 줍니다. 재개되기 전에 다른 무언가가 끝내라고 한
프로그램은 실행된 적이 없으며, 종료 코드와 관계없이 같은 방식으로 실패합니다.
단, 두 가지 예외가 있습니다. Windows가 실행 중인 프로그램에도 주는 코드인 종료
코드 259로 끝난 프로그램은, Windows가 아직 그 프로그램을 끝내는 동안 실행 중으로
읽힙니다. 재개 직전에 끝난 프로그램은 게이트가 재개 후 1 ms 안에 그 종료 코드를
읽을 때만 잡힙니다. 그보다 늦게 읽으면, 예를 들어 바쁜 머신에서나 호출한
프로세스의 다른 스레드가 바쁠 때에는, 그 종료 코드를 프로그램 자체의 것으로
받아들입니다. 측정한 머신에서는 Windows가 실행할 수 있는 가장 작은 프로그램이
재개 후 최소 3 ms, `git`은 27 ms 동안 살아 있었으므로, 실행된 프로그램이 끝내진
프로그램으로 오인되지 않습니다. 재개 직후에 끝난 프로그램 역시 실행된 프로그램과
구별할 수 없습니다. 모든 플랫폼에서 게이트 자체의 실행 중에, 시작 도중 도착한
Ctrl+C는 프로그램이 실행될 때까지(Windows에서는 게이트가 재개를 시도할 때까지)
기다리므로, 일시 중단된 채로 남거나 제한 시간을 넘겨 실행되는 프로그램은
없습니다. 게이트가 프로그램을 중지하는 동안 도착한 두 번째 Ctrl+C는 중지가 끝날
때까지 기다립니다. 중지가 시작되기 직전에 도착한 Ctrl+C는 게이트가 중지를 최대
세 번까지 다시 시도하게 합니다. 그 시도들이 실패하거나 두 시도 사이에 Ctrl+C가
들어오면, 게이트는 시그널을 막지 않은 채 다시 최대 세 번 프로그램을 중지하므로,
Ctrl+C 한 번이 더 와도 중지를 건너뛰지 않습니다. 프로그램을 실행 중인 채로
남기려면 이 지점들 중 하나로부터 각각 수 마이크로초 안에 Ctrl+C를 여러 번 눌러야
합니다. 중지한 뒤 게이트는 중지된 프로그램이 끝나기를 최대 0.5초 기다리므로,
Linux와 macOS에서 그 프로그램이 종료된(defunct) 프로세스로 남아 있지 않으며, 그
대기 중의 Ctrl+C는 이미 진행 중인 종료를 대체하지 않습니다. 호출한 프로세스가
다른 시그널에 설정한 핸들러는, 그 오류가 프로그램이 시작된 뒤 게이트가 이를
기록하기 전의 수 마이크로초 안에 들어오면, 여전히 프로그램을 실행 중인
채로(Windows에서는 일시 중단된 채로) 남길 수 있습니다. 게이트가 자체 시그널
핸들러를 바꿀 때, 변경 도중 도착한 시그널이 핸들러를 바뀐 채로 남기지는
않습니다. Linux와 macOS에서 게이트는 변경에 걸리는 수 마이크로초 동안 Ctrl+C,
`SIGTERM`, `SIGHUP`만 막고 다른 시그널은 막지 않으므로, 그런 시그널은 변경이 끝날
때까지 기다렸다가 그때 자리 잡은 핸들러를 만납니다. 그런 다음 게이트는 자신이
막은 시그널만 풉니다. 그 밖의 시그널, Windows, 그리고 막기 직전에 도착한
시그널의 경우, 시그널이 중단시킨 변경은 최대 세 번까지 다시 이루어집니다.
핸들러를 되돌리는 일이 모든 시도에서 실패하면, 게이트는 남은 각 핸들러에 대해
마지막으로 한 번 더 시도합니다. 호출한 프로세스가 설정한, 매번 발동하는 타이머의
`TimeoutError`처럼 오류가 그 마지막 시도까지 막으면 핸들러는 바뀐 채로 남으며,
드물게 핸들러가 예외를 일으키는 여러 시그널이 수 마이크로초 안에 연달아 도착해
마지막 시도를 건너뛸 때도 그렇습니다. Python 재귀 한도 근처의
`RecursionError`처럼 모든 시도에서 다시 나타나는 오류는 두 번의 시도 안에 변경을
끝내고 계속 진행합니다. 게이트는 핸들러를 바꾼 호출보다 깊지 않은 호출로
핸들러를 되돌리므로, 그 한도 근처에서도 Ctrl+C를 무시된 채로 남기지 않습니다.
호출한 프로세스가 실행 중에 설정한 `SIGTERM` 핸들러는 그대로 유지됩니다. Linux와
macOS에서, 시그널 핸들러를 설정할 수 없는 Python 하위 인터프리터 안에서는
게이트가 핸들러를 바꾸지 않고 프로그램을 실행합니다. Windows에서는 데몬 스레드를
허용하지 않는 격리된 하위 인터프리터에서 Python이 프로그램의 출력을 읽을 수
없습니다. Ctrl+C는 한 줄을 출력하고 `130`으로 종료합니다. 제한 시간은
누적됩니다. 여러 검증기가 기다리는 실행은 그 제한 시간의 합만큼 걸립니다.

다섯 개의 검증기는 실행하는 각 `git` 명령에도 자체 제한 시간을 줍니다. 이 제한은
모든 플랫폼에서 유지되며, Windows에서 `PATH`의 `git`이 Git for Windows가
설치하는, 실제 git을 시작하는 런처인 경우에도 마찬가지입니다.

```text
conventional-commit-grep            git log -1, git rev-parse           1 minute
                                    git ls-files, git config            1 minute
agents-md-coverage-grep             git rev-parse, git config           1 minute
                                    git log over the whole history      5 minutes
no-global-plans-grep                git ls-files                        1 minute
production-ready-pr-grep --staged   git diff --cached                   1 minute
semver-stability-grep --staged      git diff --cached, git cat-file     1 minute
```

이 명령들은 대부분의 프로젝트에서 1초도 걸리지 않으므로, 제한 시간에 도달하는
것은 `git`이 결코 오지 않는 무언가를 기다릴 때뿐입니다. 프로젝트 자체의 git
설정은 git이 영원히 기다리게 할 수 있습니다. 예를 들어 `.git/config`의
`include.path`가 이름 있는 파이프를 가리키는 경우입니다. 제한 시간을 넘겨 실행된
`git` 명령은 통과하지 않습니다. 검증기는 그 명령을 지목하는 `check_error`와 함께
`passed: false`를 보고합니다. 찾은 체크아웃을 거부하는 `git`도 마찬가지입니다.
예를 들어 다른 사용자가 소유한 체크아웃이나 `.git/config`에 잘못된 줄이 있는
체크아웃이 그렇습니다. 이때 `check_error`는 git의 종료 코드를 알려 주며, 종료
코드 128은 git이 저장소를 열거나 읽을 수 없을 때 쓰는 코드입니다. git이 `.git`
항목을 열 수 없는 폴더도 그런 체크아웃으로 취급됩니다. 검사에 필요한 기록이
읽히지 않은 채 그곳에 있을 수 있기 때문입니다. 다른 체크아웃 밖에 있는 빈
`.git` 폴더나, 풀어 놓은 워크트리나 복사한 서브모듈이 남기는, 더 이상 존재하지
않는 폴더를 가리키는 `.git` 파일이 그 예입니다. 그 항목을 제거하거나 전체
체크아웃에서 게이트를 실행하세요. 이는 발견 사항이 원래는 권고성인 오래된 동반
파일 검사에도 적용되며, 이 경우 커밋 제목 검사도 `empty_scope_expected: false`와
함께 `inspected: 0`을 보고합니다. Windows에서 게이트가 시작했지만 재개할 수
없었던 `git`도 실패한 `git`입니다. `check_error`는 종료 코드 128을 알려 주며,
누락된 `git`으로 취급되는 일은 없습니다. 오래된 동반 파일 검사는 전체 기록을 한
번 읽으며, 그 읽기에는 5분이 주어지므로 큰 기록은 실패가 아니라 느릴 뿐입니다.
읽는 데 그보다 오래 걸리는 기록은 검사를 실패시킵니다. 어떤 git 체크아웃에도
속하지 않은 일반 폴더, 아직 커밋이 없는 저장소, `git`이 없는 머신은 이전과 같이
이 검사들을 통과합니다. `git clone --filter`로 만든 부분 클론도 마찬가지입니다.
게이트는 `git`이 클론이 빠뜨린 것을 가져오지 못하게 하며, git은 클론이 빠뜨린
객체와 손실된 객체를 구별해 주는 답을 주지 않습니다. 그래서 부분 클론에서 오래된
동반 파일 검사는 실패한 기록 읽기를 모두 사용할 수 없는 기록으로 취급합니다.
기록이 없을 때처럼 최신성 테스트를 건너뛰고 통과합니다. 이러한 예외와, git이
거부하는 체크아웃에 대한 `check_error`는 나머지 네 검증기에 해당합니다.
`no-global-plans-grep`은 git이 읽을 수 있는 체크아웃이 필요하므로, 체크아웃
밖에서, `git`이 없는 머신에서, 또는 git이 거부하는 체크아웃에서는 이전과 같이
실패하며, 그 이유를 표준 오류에 출력합니다. 출력되는 것은 git 자체의 텍스트가
아니라 git의 종료 코드입니다. 통과하지 않는 다른 결과와 마찬가지로, 권고 모드
기본값은 이를 보고하고 `0`으로 종료하며, `--strict`는 `2`로 종료합니다.

두 `--staged` 검사의 경우, `diff.renameLimit = abc`처럼 git이 읽을 수 없는 diff
설정 값도 그런 잘못된 줄입니다. `git diff`가 실패하며, 읽지 못한 변경 세트는 빈
변경 세트가 아닙니다. 이 두 검사, 커밋 제목 검사, 오래된 동반 파일 검사는 실행된
폴더와 그 위의 폴더에서 체크아웃을 찾으므로, 체크아웃의 하위 폴더에서도
마찬가지입니다. 이 검사들은 git이 찾기를 멈추는 곳에서 멈춥니다.
`GIT_CEILING_DIRECTORIES`에 지정된 폴더와, Windows가 아닌 환경에서는
`GIT_DISCOVERY_ACROSS_FILESYSTEM`이 설정되지 않은 한 다른 파일 시스템에 있는
폴더입니다. 따라서 자체 저장소 없이 저장소 아래에 마운트된 폴더는 여전히
통과합니다. 체크아웃의 하위 폴더에서 실행한 커밋 제목 검사는, 체크아웃이 그 하위
폴더의 파일을 추적하거나 그곳에 스테이징된 파일이 있을 때 체크아웃의 최신
커밋을 검사합니다. Windows와 macOS처럼 체크아웃이 대소문자를 무시하는 곳에서는,
디스크에서 이름의 대소문자만 바뀐 하위 폴더도 마찬가지입니다. 체크아웃이
추적하지 않는 폴더(추적되지 않거나 무시된 폴더)는 자체 기록이 없으므로
통과합니다. 홈 폴더 dotfiles 저장소 안의 새 프로젝트가 그 예입니다. 실행된 폴더
위에 빈 `.git` 폴더가 있고 그보다 위에 저장소가 없으면 git이 실패하며, 검사는
`git-failed`를 보고합니다.

두 `--staged` 검사는 여러분 자신의 `diff.relative` 설정과 관계없이 작업 트리의
최상위에서 스테이징된 이름을 읽으므로, 하위 폴더 설정이 스테이징된 파일을 숨기는
일은 없습니다.

`semver-stability-grep --staged`는 실행된 폴더에서, 그다음 그 위의 폴더들에서
패키지를 찾되, 저장소를 담은 가장 가까운 폴더나 git이 찾기를 멈추는 곳까지
찾습니다. 그리고 패키지를 담은 폴더에서 git을 실행하므로, 하위 폴더에서
실행해도 같은 변경 세트를 검사합니다. 버전 파일도 그 폴더에서 읽으므로, 저장소
최상위 아래에 있는 패키지도 검사됩니다. 실행된 폴더와 패키지 사이에 git이
거부하는 `.git` 파일이 있으면, git은 대신 실행된 폴더에서 실행되어 그 파일에서
멈추고, 검사는 `check_error`를 보고합니다. git은 저장소를 가리키지 않거나, 1
MiB보다 크거나, `gitdir:`, 공백 하나, 경로를 담고 그 뒤에 줄 끝만 있는 형식이
아닌 `.git` 파일을 거부합니다. Windows에서 이 검사는 네트워크, 장치 또는 NT
경로(`\\host\share`, `\\?\`, `\??\`)를 가리키는 `.git` 파일도 거부하며, 그
경로를 직접 찾아보지 않습니다. Git for Windows가 거부하는 경로도 거부합니다.
점이나 공백으로 끝나는 이름, `aux.d`, `lpt0`, `CONIN$` 같은 장치 이름(단, Git for
Windows가 받아들이는 `com0`은 제외), 또는 드라이브 다음의 `:`입니다. 경로에서
UTF-8이 아닌 바이트는 Git for Windows와 같은 방식으로 읽습니다. `0xA0` 이상은 그
문자로, 그 미만은 16진수 두 자리로 읽으므로, `0x9F`는 `9f`로 읽힙니다.
`src/apothem/__init__.py`를 담은 가장 가까운 폴더가 검사 대상이며,
`GIT_WORK_TREE`는 읽지 않습니다. 패키지가 없는 프로젝트에는 그곳에서 검사할 것이
없으므로, 저장소가 어떤 상태이든 git을 실행하지 않고 통과합니다.

게이트는 git이 내놓는 각 경로 이름 목록을 바이트 단위 그대로 읽으므로, 줄 바꿈,
캐리지 리턴 또는 UTF-8이 아닌 바이트를 담은 이름도 모든 검사에서 같은 파일을
가리킵니다. 읽을 수 없는 경우가 하나 있습니다. Windows는 UTF-8이 아닌 이름을
git에 넘길 수 없으며, 그런 이름은 다른 시스템에서 만든 인덱스만 담을 수
있습니다. 이때 `semver-stability-grep --staged`는 변경 세트에 대해 `check_error`를
보고하며, 그 파일을 건너뛰지 않습니다. 오래된 동반 파일 검사의 기록 읽기는 첫
문장의 예외입니다. 그곳에서 git은 제어 문자가 있는 이름을 따옴표로 감싼 형태로
출력하고, UTF-8이 아닌 바이트는 대체 문자로 읽히므로, 그 검사는 그런 이름의
폴더와 일치시킬 수 없습니다.

오래된 동반 파일 검사는 저장소 최상위의 `AGENTS.md`만 정본으로 취급합니다. 자체
README가 있는 하위 폴더에서 실행하면, 그 하위 폴더의 `AGENTS.md`는 폴더별 동반
파일입니다. 그 하위 폴더가 서브모듈이나 중첩 클론처럼 자체 저장소의 최상위이면,
그 `AGENTS.md`는 대신 그 저장소의 정본입니다. 저장소 전체에 대한 실행은 테스트
픽스처와 중첩 저장소처럼, 하위 폴더 자체에 대한 실행이라면 검사하는 일부 하위
폴더를 건너뜁니다. README가 없는 하위 폴더는 이런 방식으로 별도의 폴더로 검사되지
않으므로, 그 위의 폴더에서 검사를 실행하세요. 한 커밋에서 삭제되었다가 다시
작성된 동반 파일은 커밋할 때까지 새 파일로 취급됩니다.

여섯 개의 검증기는 저장소 루트에서 시작하여 검사할 파일을 트리 전체에서
찾습니다.

```text
agents-md-coverage-grep
agnosticism-grep
dynamism-grep
freshness-token-grep
plain-language-grep
reference-token-grep
```

이 검증기들은 워크트리, 서브모듈, 중첩 클론 같은 중첩된 git 체크아웃(`.git`
파일이나 폴더가 저장소를 담고 있거나 가리키는 폴더. 일반 `.git` 파일이나 빈
`.git` 폴더는 그 폴더를 숨기지 않습니다)을 건너뛰고, 링크된 폴더에는 절대 들어가지
않으며, `node_modules`, `venv`, `dist`처럼 의존성, 가상 환경, 캐시 또는 빌드
출력을 담은 디렉터리도 건너뜁니다. `no-global-plans-grep`의 떠도는 플랜 검사도
중첩된 체크아웃에서 멈춥니다. 중첩된 체크아웃으로 건너뛴 모든 폴더는 그 `.git`
항목이 무엇을 가리키든 보고서의 `skipped_checkouts`에 나열됩니다. `gitdir:` 줄
하나만으로도 git이 어떤 폴더든 건너뛰게 할 수 있기 때문입니다. 이 목록은 판정을
바꾸지 않으며, 이렇게 건너뛴 폴더는 검사되지 않습니다. `node_modules`처럼
이름으로 건너뛰는 폴더는 나열되지 않습니다. 이들 중 어느 것을 실행하든 지정된
체크아웃에 대해서만 보고하며 그 밖의 것은 보고하지 않습니다. `src/apothem/`
아래의 `naming-grep`처럼 고정된 폴더 하나를 읽는 검증기는 그 폴더 아래의 모든
것을 읽습니다.

`--all-perwrite`는 `git ls-files`가 루트 아래에 나열하는 파일을 검사합니다.
git은 각 항목을 저장소의 인덱스가 담고 있는 그대로 나열하며, 프로젝트에는 다른
사람이 만든 인덱스와 파일이 들어올 수 있으므로, 게이트는 나열된 경로가 루트 안에
있고 64 MiB 이하이며 UTF-8 텍스트를 담은 일반 파일일 때만 읽습니다. 나열된 그
밖의 모든 경로는 이유별로 `files_skipped`에 셉니다.

- `outside_project`: `../notes.md`, `a//b.md` 또는 `/`로 시작하는 이름처럼
  비어 있거나 `.` 또는 `..`인 부분이 있는 항목, 또는 Windows에서 `.git`을
  가리키는 부분이 있는 항목. 대소문자와 관계없는 `.git`, 그 뒤에 점, 공백 또는
  콜론이 붙은 것, 그리고 `GIT~1`이 해당합니다. git은 모든 시스템에서 기본적으로
  이들을 각각 거부하므로, 실행은 통과하지 않습니다.
- `unsupported_name`: Windows에서 시스템이 쓰인 그대로 담을 수 없는 이름.
  콜론이 있는 이름(`a:b.md`처럼, `a:`가 드라이브로 읽힘), 백슬래시, `<>"|?*` 중
  하나 또는 제어 문자가 있는 이름, 또는 점이나 공백으로 끝나는 부분이 있는
  이름입니다. 그리고 Windows가 다른 것으로 읽는 이름. `CON`, `NUL`, `COM1`처럼
  단독으로 쓰인 장치 이름, 또는 `GIT~2` 같은 짧은 이름입니다. Linux나 macOS의
  git은 그런 이름을 추적할 수 있으므로, 실행을 실패시키지 않고 셉니다. `C:/x`나
  `..\..\x` 같은 수작업 항목도 Windows에서는 여기에 해당합니다.
- `link`: 루트 아래 어느 단계에서든 있는 심볼릭 링크 또는 Windows의 정션(루트
  안을 가리키는 것도 포함), 또는 인덱스가 링크로 표시한 항목(병합 충돌의 어느
  단계에서든 해당하므로, 그런 파일은 충돌이 해결될 때까지 읽히지 않음).
  git은 링크를 그것이 가리키는 경로로 저장하며, 링크가 가리키는 추적 파일은 그
  자체의 경로로 검사됩니다.
- `submodule`: 서브모듈의 항목.
- `not_regular_file`: 폴더, 이름 있는 파이프, 장치처럼 일반 파일이 아닌 그 밖의
  모든 것. 읽기가 기다리거나 끝나지 않기 때문입니다.
- `missing`: 작업 트리에 없는 추적 파일. Windows에서는 git이 UTF-8이 아닌
  바이트로 나열한 이름(다른 시스템에서 만든 인덱스만 담을 수 있으며, Git for
  Windows는 그런 파일을 다른 이름으로 기록하므로 그 내용은 검사되지 않음)과, 긴
  경로가 켜져 있지 않을 때 시스템이 허용하는 것보다 긴 경로도 포함합니다.
- `unreadable`: 권한이 없거나, 다른 프로그램이 파일 또는 그 일부를 붙잡고
  있거나, 동기화 프로그램이 중지된 온라인 전용 파일처럼 시스템이 열 수 없어서,
  시스템이 게이트에게 확인하거나 열거나 읽도록 허용하지 않는 파일 또는 그 파일로
  가는 길의 폴더. 다른 프로그램이 파일 전체를 붙잡고 있으면 게이트는 0.2초
  기다린 뒤 한 번 더 시도합니다. Windows에서는 파일을 공유하지 않고 열어 둔
  프로그램이, 다른 곳에서는 Samba oplock이나 NFS 위임처럼 해제 중인 쓰기
  임대(lease)가 그런 경우입니다. 실행은 통과하지 않습니다. 그 안의 발견 사항이
  보이지 않게 되기 때문입니다. 파일에 아무 문제가 없는데도 이런 식으로 실행이
  실패하는 몇 가지 경우가 있습니다. 0.2초보다 오래 걸리는 임대 해제, 삭제 대기
  중인 파일, 그리고 각 읽기가 먼저 약 10초를 기다리는 `\\wsl$` 공유의 프로젝트에
  있는 이름 있는 파이프입니다.
- `too_large`: 처음 64 MiB가 UTF-8 텍스트인 64 MiB 초과 파일, 또는 게이트가
  읽는 동안 64 MiB를 넘어 커지는 파일. 같은 이유로 실행은 통과하지 않습니다.
- `not_utf8_text`: 바이트 순서 표시가 있는 UTF-16 파일처럼 바이트가 UTF-8
  텍스트가 아닌 파일. 64 MiB를 넘으면 처음 64 MiB가 결정하며, 처음 8000바이트의
  4분의 1 이상이 NUL인 파일은 바이너리입니다. 0으로 채워진 큰 이미지나, 바이트
  순서 표시가 없고 대부분 라틴 문자로 된 UTF-16 파일이 그 예이며, 이는 실행을
  실패시키지 않습니다. 텍스트 안의 NUL 바이트 몇 개는 세지 않습니다.
- `exempt`: 검사가 의도적으로 제외하는 파일. 이미지나 압축 파일처럼 접미사가
  바이너리임을 나타내는 파일, 그리고 루트 안 어느 깊이에서든 `.apothem/plans`,
  `tests/conformity`, `tests/fixtures`, `_vendor` 또는 `node_modules` 폴더 아래에
  있는 모든 것입니다. `outside_project`와 `unsupported_name` 검사가 먼저
  이루어지므로, 어떤 제외도 이를 숨기지 않습니다.

`outside_project`, `unreadable` 또는 `too_large` 때문에 실행이 통과하지 않으면,
`files_not_passed`가 각 이유에 해당하는 항목을 git이 나열한 그대로 정렬하여
이유당 최대 10개까지 알려 주며, `files_skipped`에는 전체 개수가 있습니다. stderr의
한 줄도 그 이유들과 개수를 알려 주므로, stderr만 보여 주는 CI 로그에서도 실행이
실패한 이유를 알 수 있습니다.

각 파일의 단계는 파일을 읽기 직전에 확인되며, 열리는 파일은 그 확인이 찾은
파일이어야 합니다. 그 사이에 다른 프로그램이 다른 파일, 링크 또는 이름 있는
파이프로 바꿔친 파일은 한 번 더 조회되며, 다시 바꿔치면 `unreadable`로 셉니다.
바꿔 넣은 심볼릭 링크나 Windows의 정션은 두 번째 조회에서 `link`로 발견됩니다.
게이트는 이름 있는 파이프에서 기다리거나 파일 자리를 차지한 링크를 거쳐 읽는
일이 결코 없습니다. Windows에서 Data Deduplication이나 클라우드 동기화 프로그램이
리파스 지점 뒤에 보관하는 파일은 평소처럼 그 프로그램을 통해 읽으며, 그
프로그램이 중지되어 있으면 그 파일은 `unreadable`입니다.

파일은 루트에서부터 한 단계씩 열리며 어떤 단계도 링크를 거쳐 열리지 않으므로,
확인과 열기 사이에 다른 프로그램이 파일 위의 폴더를 링크로 바꿔쳐도 따라가지
않습니다. 그 파일은 `link`로 셉니다.

이 검사들이 보지 못하는 것이 두 가지 있습니다. 하드 링크는 일반 파일로 읽히므로,
다른 곳의 파일에 대한 하드 링크는 읽힙니다. git은 하드 링크를 만들지 않습니다.
그리고 Windows에서 파일의 리파스 태그도 파일 ID도 제공하지 않지만 심볼릭 링크는
담을 수 있는 네트워크 파일 시스템에서는, 확인과 열기 사이에 파일이 링크로
바뀌어도 게이트가 알아차리지 못할 수 있습니다.

이 실행에서 `link-check` 매처는 링크 대상을 루트 안에서만 찾습니다. 루트를
벗어나는 상대 링크는 외부 링크로 취급하며, `site/content/docs` 폴더 검색은
루트에서 멈춥니다. 모든 모드에서 이 매처는 네트워크 공유(`\\host\share`),
드라이브(`C:/notes.md`), `file:` 주소처럼 그 자체로 위치를 지정하는 링크를 결코
조회하지 않습니다. Windows에서 공유를 조회하면 여러분의 로그인 정보가 그 호스트로
전송됩니다. Windows에서는 또한 Windows가 드라이브로 읽는 콜론을 담은 `/docs/`
경로 세그먼트와, 점이나 공백으로 끝나는 부분을 통해서만 찾아지는 링크를 검사하지
않은 채로 둡니다. Windows는 그 끝 부분을 버릴 수 있으므로(`ci.yml.`이 `ci.yml`을
찾음), 그렇게 찾았다는 것은 아무것도 증명하지 않습니다. 그런 링크가 아무것도
찾지 못하면 평소처럼 죽은 링크로 보고됩니다. 모든 시스템에서 `/docs/../x`처럼
`.` 또는 `..` 세그먼트가 있는 `/docs/` 경로는 외부 링크로 취급하며 조회하지
않습니다.

각 `git ls-files` 호출에는 60초가 주어집니다. 이 실행이 하는 호출과
`no-global-plans-grep`의 호출이며, 후자의 보고서는 그때 같은 `check_error`를
담고 실패합니다. 그곳에서 git 자체가 실패하면, 그 메시지는 git 자체의 텍스트가
아니라 git의 종료 코드를 알려 줍니다. 이름 있는 파이프를 가리키는
`include.path`처럼 자체 설정이 git을 기다리게 만드는 저장소는 이 호출들 각각을
최대 그 시간만큼 붙잡아 둡니다. Windows에서도 마찬가지이며, 그곳에서 제한 시간은
Git 런처가 시작한 git도 중지합니다. 아무 파일도 읽지 않은 `--all-perwrite`
실행은 통과하지 않으며, `empty_scope_expected: false`와 함께 `files_scanned: 0`을
보고합니다. 추적 파일 목록을 읽을 수 없으면 `check_error`는 정해진 이유를 알려
줍니다. git이 시작되지 않았거나, `git ls-files`가 특정 종료 코드로 실패했거나,
제시간에 끝나지 않았다는 것입니다. 예를 들어 루트가 git 작업 트리 안에 있지 않을
때 git 자체의 메시지를 보려면 루트에서 `git ls-files`를 실행하세요. 그 메시지는
프로젝트 밖의 파일 이름을 담을 수 있으므로 보고서에서는 빠집니다. `--strict`를
사용하면 통과하지 않은 실행은 `2`로 종료합니다.

## 표적 검사

```bash
# List every registered validator
PYTHONPATH=src python -m apothem.conformity.gate --list

# Run one per-write validator against one file
PYTHONPATH=src python -m apothem.conformity.gate --check multi-surface-coherence src/apothem/rules/my-rule.md

# Run one standalone validator over a root directory
PYTHONPATH=src python -m apothem.conformity.gate --check naming-grep .

# Run every per-write validator against one file
PYTHONPATH=src python -m apothem.conformity.gate src/apothem/rules/my-rule.md
```

쓰기별 검증기는 검사할 파일을 받거나, 표준 입력에서 내용을 읽으려면 `--stdin`을
받습니다. 둘 다 없으면 표준 입력에서 입력을 기다리므로, 터미널에서 실행할 때는
파일을 전달하세요. 독립 실행형 검증기는 루트 디렉터리를 받습니다(생략하면 현재
디렉터리). `--list`는 각 검증기가 어느 그룹에 속하는지 보여 줍니다.

`--hook` 모드(`<python> -E -s .../conformity/gate.py --hook`, 여기서
`<python>`은 설치 과정에서 찾은 인터프리터)는 하니스가 디스패치하는
진입점입니다. stdin에서 도구 입력 JSON 페이로드를 읽고, 보류 중인 쓰기에 대해
쓰기별 매처 체인을 실행합니다. 배포된 `PreToolUse` 훅이 호출하는 형태가 이것이며,
여러분이 직접 호출하는 일은 드뭅니다.

훅 모드는 **일련의 디렉터리로 범위가 한정됩니다**. 대상이 그중 하나의 아래에
있는 쓰기에 대해서만 매처 체인을 실행하며, 모든 범위 바깥의 쓰기는 즉시 조용한
통과로 처리됩니다. 기본값은 두 개의 루트입니다.

```text
~/.claude      Claude Code
$CODEX_HOME    Codex (~/.codex when CODEX_HOME is not set)
```

이를 교체하려면 `APOTHEM_CONFORMITY_SCOPE`를 디렉터리로 설정하세요.

```bash
# Run the per-write matcher chain against one project tree instead
export APOTHEM_CONFORMITY_SCOPE=/path/to/project
```

아무것도 하지 않는 것처럼 보이는 훅은 대개 실패가 아니라 범위 불일치입니다 —
먼저 쓰기 대상을 위의 범위와 대조해 확인하세요.

## CI 통합

`.github/workflows/ci.yml`의 quality 작업은 `main`에 푸시할 때와, 이 작업이 감시하는 경로를 건드리는 `main` 대상 풀 리퀘스트에서 게이트를 strict 모드로 실행합니다(`python -m apothem.conformity.gate --all . --strict`). 별도의 `.github/workflows/conformity.yml` 워크플로는 픽스처 스위프(`tests/conformity-scenarios/verify.py --strict`)를 실행합니다.
