목표: 실행하기 전에 환경 변수를 설정하여, 스크립트를 편집하지 않고
`install.sh` / `install.ps1`을 제어합니다.

## 사전 요건

- POSIX 셸(`bash`) 또는 PowerShell 5.1+. 아래의 PowerShell 예시는
  `pwsh`(PowerShell 7+)를 실행합니다. Windows PowerShell 5.1에서는 대신
  `powershell -NoProfile -ExecutionPolicy Bypass -File install.ps1`을 실행하세요.
- 변수는 설치 프로그램 맨 앞에서 한 번만 읽히므로, 같은 명령 안에서
  설정한(또는 먼저 export한) 다음 설치 프로그램을 실행하세요.

## 설치 프로그램 변수

| 변수 | 제어 대상 | 기본값 |
| --- | --- | --- |
| `APOTHEM_HOME` | 소스 트리의 설치 대상. 본인만 쓸 수 있는 폴더여야 하며(아래 참조), 다른 사용자가 그 폴더나 그 상위 폴더에 쓸 수 있으면 설치 프로그램이 경고합니다 | `$HOME/.apothem` |
| `APOTHEM_REPO` | 클론할 Git 원격 저장소. `-`로 시작하는 값은 거부됩니다 | `https://github.com/ahmed-g-gad/apothem` |
| `APOTHEM_REF` | 체크아웃할 Git ref. 설정하지 않으면 서명된 최신 `vMAJOR.MINOR.PATCH` 태그로 해석되고, 태그 값을 지정하면 그 태그로 고정되며, `main`은 움직이는 브랜치를 선택합니다. `main` 같은 태그가 아닌 ref는 `APOTHEM_ALLOW_UNVERIFIED=1`을 설정하지 않으면 중단됩니다. | 설정 안 함(서명된 최신 태그) |
| `APOTHEM_ALLOW_UNVERIFIED` | `1`로 설정하면 클론 경로에서 실패한 태그 검사를 치명적 중단에서 경고로 낮추고, `APOTHEM_VERIFY=checksum`을 허용합니다. `release` 경로는 절대 낮추지 않으며, 서명된 태그가 해당 릴리스에 지정된 태그인지 확인하는 검사는 어떤 설정으로도 건너뛸 수 없습니다. 다만 이 설정은 서명되지 않은 태그나 다른 키로 서명된 태그를 통과시키므로, 그 검사는 메인테이너 키의 서명을 지닌 태그만 보호합니다 | `0`(검증, 실패 시 차단) |
| `APOTHEM_VERIFY` | `auto`는 `cosign`이 `PATH`에 있고 `APOTHEM_HOME`이 git 클론이 아니면 `release`를, 그렇지 않으면 `signature`를 사용합니다. `release`는 태그가 메인테이너 키의 서명을 지니고, cosign이 릴리스 워크플로가 태그의 커밋에서 실행된 런에서 `SHA256SUMS`에 서명했음을 확인하고, 아카이브의 SHA-256이 그와 일치한 뒤에 플랫폼 아카이브를 설치합니다. `signature`는 릴리스 태그의 GPG 서명을 고정된 메인테이너 키와 대조해 확인합니다. `checksum`은 SHA-256 검사만 거친 뒤 아카이브를 설치하며 `APOTHEM_ALLOW_UNVERIFIED=1`이 필요합니다. 체크섬 모드는 릴리스를 검증하지 않습니다. SHA256SUMS는 아카이브와 같은 릴리스에서 오므로, 일치는 다운로드가 손상되지 않았다는 것만 보여 줍니다. 릴리스의 파일을 바꿀 수 있는 사람은 둘 다 바꿀 수 있습니다. | `auto` |
| `APOTHEM_RELEASE_BASE` | `release` 및 `checksum` 모드의 다운로드 기본 경로 | `<APOTHEM_REPO>/releases/download` |
| `APOTHEM_SOURCE` | 클론 대신 사용할 명시적 로컬 소스 트리 | 설정 안 함(클론) |
| `APOTHEM_HARNESS` | 설치할 사용자 범위 하니스(`antigravity`, `claude-code`, `codex`, `hermes`, `open-claw`, `opencode`, `qwen-code`). 설치 프로그램은 `--project`를 전달하지 않으므로 프로젝트 범위 하니스는 `project.required`로 실패합니다. 이러한 하니스는 이후에 `apothem install --harness NAME --project PATH`로 설치하세요. | `claude-code` |
| `APOTHEM_PROFILE` | 공유 프로필 YAML의 경로 | `$HOME/.config/apothem/profile.yaml` |
| `APOTHEM_SKIP_VERIFY` | `1`로 설정하면 설치 후 검증 단계를 건너뜁니다 | `0`(검증 실행) |
| `APOTHEM_AUTO_INSTALL_DEPS` | `1`로 설정하면 누락된 `click` / `rich` 사전 요건을 묻지 않고 자동으로 설치합니다 | `0`(묻기, 비대화형 파이프에서는 거부) |
| `APOTHEM_BIN_DIR` | 배치되는 `apothem` 명령 심(shim)의 디렉터리 | `$HOME/.local/bin`(POSIX); `%LOCALAPPDATA%\Microsoft\WindowsApps`(Windows) |
| `NO_COLOR` | 어떤 값으로든 설정하면 색상 출력을 끕니다([no-color.org](https://no-color.org/)). 출력이 터미널이 아닐 때(파이프, 파일, CI 로그)에도 색상은 항상 꺼집니다 | 설정 안 함(대화형 터미널에서만 색상 사용) |

`APOTHEM_SOURCE`는 클론보다 우선합니다. `src/apothem`을 포함하는 체크아웃으로
설정하면 설치 프로그램은 그 체크아웃을 직접 사용하고, `APOTHEM_REPO` /
`APOTHEM_REF`는 절대 건드리지 않으며, 태그 해석과 서명 검증을 건너뜁니다(검증할
대상을 가져오지 않기 때문입니다).

`APOTHEM_SOURCE`와, 체크아웃 자체의 설치 프로그램 스크립트를 경로로(어느
폴더에서든) 실행하는 것만이 로컬 트리를 사용하는 두 가지 방법입니다. 파이프로 실행하는
원라이너(`curl
... | sh`, `irm ... | iex`)는 로컬 트리를 절대 사용하지 않습니다. 현재 폴더와 그 상위
폴더를 무시하고, 릴리스를 가져와 검증합니다. 설치 프로그램, 업데이터와 제거 프로그램,
`apothem` 심, npm 런처, 훅, 그리고 적합성 게이트의 검증기 프로세스는 현재 폴더를
Python의 모듈 검색 경로에서 제외합니다. 여러분이 직접 입력하는 `python -m apothem`
명령은 그렇지 않습니다. `-m`은 현재 폴더에서 모듈을 먼저 읽습니다.

여러분의 `PYTHONPATH`에 있는 빈 항목과 상대 항목은 어떤 런처(설치 프로그램,
업데이터, 제거 프로그램, POSIX 및 Windows `apothem` 심, npm 런처)도 엔진에 전달하지
않습니다. 유지되는 항목은 전체 경로여야 합니다. Windows에서는 `C:\lib` 같은 드라이브
경로나 네트워크 경로, 그 밖의 시스템에서는 `/`로 시작하는 경로입니다. 루트 기준
`\lib`나 드라이브 상대 `C:lib`는 버려집니다. sh 스크립트는 자신이 실행하는 Python에
어떤 형식을 읽는지 묻고, 스크립트가 작성하는 `apothem` 심은 그 형식을 유지합니다.
Windows Python(Git Bash에서 흔히 쓰는 것)은 엔진 경로를 `;`로 연결된 Windows
형식으로 받고, 여러분의 `PYTHONPATH` 중 드라이브 경로와 네트워크 경로만 유지합니다.
Cygwin과 MSYS2 자체의 `python3`를 포함한 POSIX Python은 `:`로 연결된 POSIX 경로를
받고, `/`로 시작하는 항목만 유지합니다. 클론에 대해 작업하지 않는 설치 프로그램의
`git` 명령은 현재 폴더의 저장소를 읽지 않습니다.

그 `git` 명령들은 설치 프로그램이 실행마다 만드는 빈 임시 폴더에서 실행되므로, git
환경 변수(`GIT_SSH`, `GIT_ASKPASS` 등)에 있는 상대 경로는 더 이상 이전에 가리키던
곳을 가리키지 않습니다. 그런 변수에는 절대 경로를 사용하세요. 폴더나 파일(예: git
번들)을 가리키는 상대 `APOTHEM_REPO`는 여전히 여러분이 시작한 폴더를 기준으로
해석됩니다.

설치 프로그램은 git의 방향을 바꾸는 git 환경 변수(`GIT_DIR`, `GIT_WORK_TREE`,
`GIT_INDEX_FILE` 등)를 무시하고, `APOTHEM_REPO`가 `-`로 시작하면 중지하므로, 값이
git 옵션으로 읽힐 수 없습니다.

설치 프로그램과 업데이터는 `GIT_CONFIG`, `GIT_CONFIG_GLOBAL`,
`GIT_CONFIG_SYSTEM`도 비우므로, 여러분의 환경에서 상속된 값이 git을 다른 구성 파일로
향하게 할 수 없습니다. 또한 git이 검사가 읽는 작업 트리와 인덱스가 아닌 다른 트리에서
속성을 읽게 만드는 `GIT_ATTR_SOURCE`도 비웁니다(같은 이유로 여러분 자신의 구성에 있는
`attr.tree`는 클론에서 실행되는 모든 git 명령에서 비워지며, `core.attributesFile`도
마찬가지라서 git은 그것이 가리키는 속성 파일도, 매크로가 검사가 보지 못하는 필터를
지정할 수 있는 `~/.config/git/attributes`도 읽지 않습니다). 이 중 하나를 설정하면
설치 프로그램은 이를 무시합니다.
PowerShell 스크립트는 실행이 끝날 때 이를 되돌려 놓으므로, `irm ... | iex` 실행은
세션을 원래 상태로 남깁니다. `GIT_CONFIG_NOSYSTEM`은 여러분이 설정한 그대로
유지됩니다. 이 변수는 git이 시스템 구성을 읽지 않게 할 뿐입니다. git은 여전히 여러분
자신의 전역 구성(`~/.gitconfig` 또는 `$XDG_CONFIG_HOME/git/config`)과 시스템 구성을
늘 찾던 위치에서 읽으며, `git`, `gpg`, `cosign`은 여러분의 `PATH`가 찾는
프로그램입니다. 설치 프로그램은 찾은 그대로 이를 신뢰하므로, 그 구성도 신뢰합니다.

설치 프로그램과 업데이터는 실행 전체에 걸쳐 네 개의 git 변수도 설정합니다.
`GIT_NO_REPLACE_OBJECTS=1`은 git이 replace ref를 통해 객체를 다른 객체로 바꾸지 못하게
합니다. `GIT_NO_LAZY_FETCH=1`은 git이 클론을 읽는 동안 누락된 객체를 원격에서 스스로
가져오지 못하게 합니다.
`GIT_ALLOW_PROTOCOL=file:git:http:https:ssh`는 실행의 모든 git 명령에 이 다섯 가지
전송만 허용하므로, 여러분의 환경에 있는 값이 목록을 넓힐 수 없고 주소가 git으로 하여금
`ext::` 같은 도우미 프로그램을 실행하게 할 수 없습니다.
`APOTHEM_REPO`는 그중 하나를 사용해야 하며, 로컬 경로는 `file`로 간주됩니다.
`GIT_ATTR_NOSYSTEM=1`은 매크로가 필터를 지정할 수 있는 시스템 속성 파일을 git이 읽지
못하게 합니다. PowerShell 스크립트는 실행이 끝날 때 네 변수를 모두 원래대로 되돌려
놓습니다. 또한
실행 동안 콘솔의 코드 페이지와 관계없이 git의 출력을 UTF-8로 읽고, 실행이 끝날 때
콘솔의 설정을 되돌려 놓습니다.

`APOTHEM_HOME`은 본인만 쓸 수 있는 폴더여야 합니다. 그 폴더에 쓸 수 있는 사람은 누구나
`apothem` 명령이 실행하는 코드를 바꿀 수 있습니다. Windows에서 `C:\apothem`처럼
드라이브 루트에 만든 폴더는 Windows의 기본 권한에서 컴퓨터에 로그인하는 모든 사용자가
변경할 수 있습니다. 기본값처럼 여러분 자신의 사용자 폴더 아래에 두세요. 설치 및 업데이트
스크립트는 드라이 런을 포함해, 다른 사용자가 `APOTHEM_HOME`이나 그것을 담은 폴더에 쓸
수 있거나 둘 중 하나를 소유하면 중지하지 않고 경고합니다. 로컬 체크아웃에서의 설치와
`APOTHEM_SOURCE`를 설정한 업데이트는 이 검사를 건너뜁니다.
Windows에서는
`install.ps1`과 `update.ps1`이 경고를 냅니다. `install.sh`와
`update.sh`는 Git Bash, MSYS2, Cygwin에서 검사하지 않습니다.
[문제 해결](/docs/install/troubleshooting#the-installer-warns-other-users-can-change-apothem_home)에서
해결 방법을 보여 줍니다.

설치, 업데이트, 제거 스크립트의 각 실행은 실행 전체 동안 잠금
`<APOTHEM_HOME>.lock`을 유지하며, 같은 `APOTHEM_HOME`에 대한 두 번째 실행은
중지합니다. `APOTHEM_HOME`이 심볼릭 링크(Windows에서는 정션)이면, POSIX 스크립트와
PowerShell 스크립트 모두 그 링크가 이어지는 폴더 옆에 잠금을 둡니다. 강제 종료나 전원
손실은 `APOTHEM_HOME` 옆에 폴더를 남길 수 있으며, 다음에 가져오는 설치는 그 폴더들을
명시하고 아무것도 변경하기 전에 중지합니다.
[문제 해결](/docs/install/troubleshooting)을 참조하세요.

`APOTHEM_HOME`이 기존 디렉터리를 가리키면, 동작은 그 안에 무엇이 있는지에 따라
달라집니다.

- git 클론은 `auto` 또는 `signature` 모드에서 fetch됩니다. 새 태그를 먼저 검사하고,
  그다음에야 클론을 체크아웃합니다. 검사가 실패하면 클론은 변경되지 않으며, 추적되는
  파일의 변경 사항은 잃어버리는 대신 커밋하거나 stash하라는 메시지와 함께 업데이트를
  중지시킵니다. `main` 같은 릴리스가 아닌 ref에서는 클론이 origin에 있는 그 브랜치의
  사본을 따릅니다. `.git` 파일(연결된 worktree)도 클론으로 간주됩니다. `release`와
  `checksum`은 `--yes` 없이는 클론을 거부하며, `--yes`가 있어도 클론에 로컬
  작업(변경 사항, stash, 푸시되지 않은 커밋, 또는 소스 트리의 추적되지 않은 파일)이
  있으면 드라이 런에서도 여전히 거부합니다. `--yes`가 실제로 클론을 교체하면, 클론
  자체의 트리는 삭제되는 대신 자신의 이름으로 새 폴더
  `<APOTHEM_HOME>.before-apothem-<time>` 안으로 옮겨집니다. fetch 전에, 제자리
  업데이트는 다음 경우에 중지합니다. 파일이 assume-unchanged 또는 skip-worktree로
  표시된 경우, 클론의 작업 트리가 `APOTHEM_HOME`이 아닌 경우, 클론이 서브모듈이나 git이
  추적하지 않는 git 저장소를 담고 있는 경우(`backups` 같은 엔진 자체 데이터 폴더
  밖에서), `.git/info/attributes`가 filter 또는 diff
  드라이버를 지정하는 경우, 클론이 다른 저장소에서 객체를 빌려 오는 경우, 작업 트리의
  `.gitattributes` 파일이 추적되지 않거나, 커밋된 사본과 다르거나, 그런 드라이버를
  지정하거나, git이 읽을 수 없는 커밋된 사본을 가진 경우, `src` 아래 파일이 추적되지
  않는 경우, 또는 클론의
  `.git/config`나 `.git/config.worktree`에 전체 클론에 대해 `git clone`과 `git init`이
  그곳에 작성하는 설정, 브랜치 설정(브랜치의 `remote`와 `pushremote`는 `origin`이어야
  함), `user.name`,
  `user.email`, `maintenance.auto`, `maintenance.strategy`, `pull.rebase`,
  `pull.ff`
  외의 설정이 있는 경우입니다
  ([문제 해결](/docs/install/troubleshooting#the-installer-stops-the-existing-clone-is-set-up-in-a-way-the-update-would-trust)에
  목록이 있습니다). 클론의 git 훅은 업데이트 중에 절대 실행되지 않습니다. 체크아웃
  후, 업데이트는 엔진이 클론에서 실행되기 전에 `src` 아래의 Python 캐시
  폴더(`__pycache__`)를 제거합니다. Apothem 소스의 클론만 해당합니다. 다른 것의 클론은
  Apothem 설치를 담지 않은 폴더로 처리됩니다.
- 이전 릴리스 아카이브 설치는 cosign이 있는 `auto` 모드(또는 `release`, 또는
  `checksum`)로 다시 실행하면 업데이트됩니다.
- Apothem 설치를 담지 않은 폴더는 거부됩니다. 다른 곳으로 옮기거나,
  `APOTHEM_HOME`이 다른 곳을 가리키게 하거나, `--yes`(Windows에서는 `-Yes`)를
  전달하세요. `--yes`가 있으면 설치 프로그램은 폴더 전체를 변경 없이 새 폴더
  `<APOTHEM_HOME>.before-apothem-<time>` 안으로 옮기고 새로 설치합니다.
- 오래된 빈 디렉터리, 또는 엔진 자체 데이터(`backups`, `state`, `plans`, `memory`,
  `contexts`, `learning`,
  `providers`)만 담은 디렉터리는 플래그 없이 업데이트되며, 그 데이터는 유지됩니다.
- 심볼릭 링크(Windows에서는 심볼릭 링크 또는 정션)는 설치가 그것을 교체하게 될 때마다
  거부됩니다. `APOTHEM_HOME`이 링크가 이어지는 폴더를 가리키게 하세요. 링크 뒤에 있는
  기존 git 클론은 제자리에서 업데이트됩니다.
- Linux와 macOS에서, 이름에 공백이나 다른 특수 문자가 있는 옮겨 갈 파일이나 폴더는
  설치를 중지시킵니다. 먼저 `APOTHEM_HOME` 밖으로 옮기세요.

교체되는 Apothem 설치의 경우, 새 소스는 `APOTHEM_HOME` 옆의 스테이징 폴더에서 검사되며
모든 검사를 통과한 뒤에만 교체됩니다. 엔진의 백업, 설치 원장, 플랜, 메모리를 포함해
이전 설치에서 소스 트리에 속하지 않는 모든 것은 유지됩니다. 어떤 단계가 실패하거나
실행이 Ctrl+C 또는 종료 시그널로 중지되면, 이전 설치가 변경 없이 되돌려집니다. 강제
종료나 전원 손실은 다음에 가져오는 설치가 보고하는 폴더를 `APOTHEM_HOME` 옆에 남길 수
있습니다. `--dry-run`(Windows에서는 `-DryRun`)은 임시 폴더에서 검사를 수행하고
`APOTHEM_HOME`을 변경하지 않습니다. 실제 실행과 같은 검사를 하지만, 기존 클론으로
fetch하지 않으므로 실제 업데이트가 fetch 후에 하는 추적 파일 변경 검사는 하지 않습니다.

## 신뢰 모델

`APOTHEM_REF`가 설정되지 않은 경우, 설치 프로그램은 최신 릴리스를 해석하고 구성을
머티리얼라이즈하기 전에 이를 검사합니다. 항상 `git verify-tag`로 릴리스 태그를
검증하고, 서명이 SECURITY.md에 게시된 메인테이너 키에서 온 것이어야 합니다. 서명되지
않았거나 변조된 태그, 또는 다른 키로 서명된 태그는 설치를 중단시키며, 해당 릴리스에
지정된 태그가 아닌 서명된 태그 객체(다른 릴리스용으로 서명된 태그를 이 이름으로 다시
가리키게 한 것)도 마찬가지입니다. `cosign`이 `PATH`에 있으면, 이어서 cosign이 릴리스
워크플로가 `SHA256SUMS`에 서명했음을, 그리고 `--certificate-github-workflow-sha` 검사를
통해 검증한 인증서가 태그의 커밋에서 실행된 런에 발급되었음을 확인하고, 아카이브의
SHA-256이 그와 일치하면 릴리스 아카이브를 설치합니다. 이 경로에는 `gpg`와 cosign이
필요합니다. 기존 git 클론의 경우, 설치 프로그램은 클론을 체크아웃하기 전에 태그를
fetch하고 검사하므로, 검사가 실패하면 클론은 그대로 남습니다. 메인테이너 공개 키가 로컬
키링에 없는 서명된 태그는 대신 키 가져오기 안내와 함께 중단됩니다. 키를 가져온
다음, 그 지문을
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md)에
게시된 값과 대조하세요.
알려진 릴리스를 `APOTHEM_REF=<tag>`로 고정하되, 태그는
[릴리스 페이지](https://github.com/ahmed-g-gad/apothem/releases)에서
가져오세요. 고정된 태그도 같은 방식으로 검증됩니다. 움직이는 브랜치는
`APOTHEM_REF=main`과 `APOTHEM_ALLOW_UNVERIFIED=1`을 함께 설정하여 선택합니다.
이 설치는 검증되지 않으며, `main`만 설정하면 브랜치는 서명된 태그가 아니므로
중단됩니다. `APOTHEM_ALLOW_UNVERIFIED=1`을 설정하면 실패한 태그 검사를 경고와 함께
넘기고 진행합니다(에어갭, 로컬, 또는 서명된 릴리스 이전의 용도). 이 설정은 클론
경로에만 적용되며 cosign 경로에는 절대 적용되지 않으므로, cosign이 있는 호스트에서는
`APOTHEM_VERIFY=signature`를 함께 설정하세요.

```bash title="Pinned, verified install"
APOTHEM_REF=vMAJOR.MINOR.PATCH bash install.sh
```

```bash title="Require the tag check and the cosign check"
APOTHEM_VERIFY=release bash install.sh
```

체크섬 모드는 릴리스를 검증하지 않습니다. SHA256SUMS는 아카이브와 같은 릴리스에서
오므로, 일치는 다운로드가 손상되지 않았다는 것만 보여 줍니다. 릴리스의 파일을 바꿀 수
있는 사람은 둘 다 바꿀 수 있습니다. 설치 프로그램은 `APOTHEM_ALLOW_UNVERIFIED=1`도
함께 설정된 경우에만 이 모드를 실행합니다.

```bash title="Check the archive digest alone (no cosign, no gpg; does not verify the release)"
APOTHEM_VERIFY=checksum APOTHEM_ALLOW_UNVERIFIED=1 bash install.sh
```

```bash title="Proceed past a failed tag check (interim / air-gapped)"
APOTHEM_VERIFY=signature APOTHEM_ALLOW_UNVERIFIED=1 bash install.sh
```

## 단계 (POSIX bash)

1. 기본값이 아닌 사용자 범위 하니스를 설치합니다.

   ```bash
   APOTHEM_HARNESS=codex bash install.sh
   ```

2. 설치 대상을 고정하고 움직이는 `main` 브랜치를 선택합니다. 브랜치는 서명된 태그가
   아니므로, 설치 프로그램에는 `APOTHEM_ALLOW_UNVERIFIED=1`도 필요합니다.

   ```bash
   APOTHEM_REF=main APOTHEM_ALLOW_UNVERIFIED=1 APOTHEM_HOME="$HOME/tools/apothem" bash install.sh
   ```

3. 로컬 체크아웃과 사용자 지정 프로필을 사용하고, 검증을 건너뜁니다.

   ```bash
   APOTHEM_SOURCE=/work/apothem \
   APOTHEM_PROFILE=/work/profile.yaml \
   APOTHEM_SKIP_VERIFY=1 \
   bash install.sh
   ```

## 단계 (PowerShell)

설치 프로그램을 실행하기 전에 각 변수를 `$env:`에 설정하세요.

```powershell
$env:APOTHEM_HARNESS = 'codex'
pwsh -NoProfile -File install.ps1
```

```powershell
$env:APOTHEM_ALLOW_UNVERIFIED = '1'
$env:APOTHEM_REF = 'main'
$env:APOTHEM_HOME = "$HOME\tools\apothem"
pwsh -NoProfile -File install.ps1
```

```powershell
$env:APOTHEM_SOURCE = 'C:\work\apothem'
$env:APOTHEM_PROFILE = 'C:\work\profile.yaml'
$env:APOTHEM_SKIP_VERIFY = '1'
pwsh -NoProfile -File install.ps1
```

## 검증

설치 프로그램은 `✓ Harness <name> installed`를 출력한 다음
(`APOTHEM_SKIP_VERIFY=1`이 아니면) `✓ verify passed`를 출력합니다. 별도로
확인하세요.

```bash
apothem verify --harness codex
```

Cursor 같은 프로젝트 범위 하니스는 설치 프로그램 실행 후 `--project`를 붙여
설치와 검증을 직접 실행하세요.

```bash
apothem install --harness cursor --project /path/to/project
apothem verify --harness cursor --project /path/to/project
```

프로필이 아직 없었다면, 설치 프로그램은 예시에서 프로필을 만들고 같은 실행에서
설치와 검증을 계속 진행합니다. 예시의 신원 필드는 플레이스홀더이므로 설치 과정에서
안내 메시지가 출력됩니다. 예시에는 샘플 규칙, 두 개의 샘플 MCP 서버, 하니스별
재정의도 들어 있으며, OpenCode처럼 프로필에서 MCP 서버를 가져오는 하니스는 두 서버를
모두 받습니다. 원하지 않는 것을 제거하며 `$APOTHEM_PROFILE`을 편집한 다음
`apothem update --harness <name>`을 실행하여 적용하세요.
프로필이 없는 상태에서 `--dry-run`을 실행하면 예시를 프로필 자리에 둔 채 미리
보기를 하며 아무것도 쓰지 않습니다.
