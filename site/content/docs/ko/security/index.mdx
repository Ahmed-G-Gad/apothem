Apothem의 보안 태세는 공급망 강화, 취약점 대응, 브랜치 보호, 릴리스 서명, 지속적인 보안 분석이라는 다섯 가지 기둥 위에 세워져 있습니다. 이 섹션은 각 표면을 문서화합니다.

## 위협 모델

Apothem은 구성 머티리얼라이저입니다. 공유 프로필을 읽고, 각 하니스가 읽는
디렉터리에 하니스 네이티브 구성 파일을 씁니다. 이 단일 기능이 Apothem이 무엇을
신뢰하고 무엇을 신뢰하지 않는지의 경계를 정합니다.

- **Apothem이 신뢰하는 것.** 여러분이 작성하는 공유 프로필과 설치 프로그램이 배치한 번들 소스 트리입니다. 프로필은 여러분이 선언한 의도이며, 엔진은 스키마 검증 후 이를 권위 있는 입력으로 취급합니다.
- **Apothem이 신뢰하지 않는 것.** 프로필 내용은 검증을 거친 후에만 파일 시스템에 도달합니다. 스키마 실패, 알 수 없는 하니스 ID, 안전하지 않은 프로젝트 경로, 누락된 매니페스트 소스, 대상 경로 순회, 심볼릭 링크 경계 넘기는 모두 어떤 쓰기보다 먼저 중단되며, `files_written: []`가 포함된 구조화된 진단을 반환합니다. 예외는 dotfile 관리자가 `~/.config`에, 또는 공유 스킬, 규칙, 템플릿 폴더나 그 상위에 만드는 링크로, 홈 디렉터리 안의 어딘가로 이어지는 동안에는 따라갑니다. Windows에서는 정션도 링크로 간주합니다.
- **머티리얼라이즈된 출력이 절대 담지 않는 것.** 시크릿은 담지 않습니다. 프로필 진단은 시크릿처럼 보이는 키와 토큰 형태의 값을 일반 출력, JSON, 로그, 문서 스니펫, 테스트에 도달하기 전에 가립니다. 공개 예시는 가짜 플레이스홀더 신원과 도메인을 사용합니다. 머티리얼라이즈된 구성은 커밋하고 공유하도록 만들어졌으며, 자격 증명을 담지 않습니다.
- **보편적 거부 하한선.** Apothem이 머티리얼라이즈하는 Claude Code `settings.json`은 하니스별 허용 목록과 관계없이 협상할 수 없는 거부 하한선을 지닙니다. 다른 하니스에서는 같은 하한선이 설정 수준의 거부 목록이 아니라 머티리얼라이즈된 규칙 안의 정책 텍스트로 존재합니다. 하한선에는 시크릿 경로(`.env*`, `~/.ssh/**`, 자격 증명 저장소), 파괴적인 셸 작업(`rm -rf`, `sudo`, 보호된 브랜치로의 강제 푸시), 신뢰할 수 없는 입력의 실행이 포함됩니다. 어떤 허용 목록도 이 하한선을 조용히 넓히지 않습니다.
- **영향 반경.** 쓰기는 하니스 디렉터리와 Apothem 소유 지원 하위 트리로 범위가 한정됩니다. 기존 관리 대상은 교체 전에 백업되고, 공유 디스커버리 디렉터리는 하위 항목 단위로 병합되므로 관련 없는 운영자 작성 파일은 그대로 남습니다.

## 런타임 안전 태세

하니스 라이프사이클 명령과 프로필 쓰기 명령은 쓰기 전에 검증합니다. 프로필
스키마 실패, 알 수 없는 하니스 ID, 안전하지 않은 프로젝트 경로, 누락된
매니페스트 소스, 대상 경로 순회, 심볼릭 링크 경계 넘기는 파일 시스템 쓰기 전에
중단되며 `files_written: []`가 포함된 구조화된 진단을 반환합니다. Windows 정션은
심볼릭 링크로 간주합니다. 예외는 `~/.config`에 있거나 공유 스킬, 규칙, 템플릿 폴더 또는
그 상위에 있으면서 홈 디렉터리 안에 머무는 링크, 그리고 그 자체가 링크인 홈 폴더입니다.
링크는 홈 디렉터리에 있는 도구 폴더나 프로필에 대한 쓰기를 홈 디렉터리 밖으로 절대
가져가지 않습니다. 단, 여러분이 직접 홈 디렉터리 밖의 경로로 적은 `XDG_CONFIG_HOME`
또는 `CODEX_HOME`을 통해, 또는 프로필의 경우 같은 방식으로 적은 `--profile PATH`를 통해
홈 디렉터리 밖의 폴더를 지정한 경우는 예외입니다. 그렇게 적은 경로는 그 링크가
이어지는 곳 어디든 따라갑니다. 프로젝트 폴더는 아래의 자체 규칙을 따릅니다. 링크 규칙은
설치, 업데이트, 제거, `apothem rollback`, 그리고 기존 프로필 위에 실행하는 `profile set`과
`profile init --force`를 포함한 `apothem profile` 명령에 적용되며, `install --clean`이
다시 쓰는 프로필에도 적용됩니다. `install --clean`은 `~/.config`가 홈 디렉터리 밖으로
이어지는 링크이면 무엇을 백업하거나 제거하기 전에 멈추며, 그 자체가 링크인 대상은
안으로 들어가지 않고 링크로서 제거합니다. 따라서 Windows에서 도구 폴더에 있거나 그 안에
있는 정션은, 홈 디렉터리 안의 어딘가로 이어지더라도 설치를 멈춥니다. 그 정션을 실제
폴더로 바꾸세요.

`--project`로 지정한 폴더는 어디로 이어지든 따라가며, 그 상위의 링크도
마찬가지입니다. 그 폴더 자체가 링크인 경우(`~/.config`도 포함)와 링크가 홈 디렉터리
밖으로 이어지는 경우에도 그렇습니다. 여러분이 그 폴더를 지정했기 때문입니다. 프로젝트
폴더 안에서 설치가 쓰는 경로에 있는 링크는 설치를 멈춥니다. 그 링크가 프로젝트 폴더로
다시 이어지는 경우와 `--project`가 홈 디렉터리를 지정하는 경우에도 그렇습니다.
`~/.config/apothem`처럼 홈 디렉터리에도 쓰는 도구는 그 경로를 위의 홈 규칙으로
검사합니다. 따라서 홈 디렉터리 밖으로 이어지는 `~/.config` 링크는 `--project`가
`~/.config`를 지정하더라도 그 도구의 설치를 멈춥니다.

`XDG_CONFIG_HOME`과 `CODEX_HOME`은 셸 프로필뿐 아니라 프로젝트의 `.envrc`나 여러분이
source하는 스크립트에서도 올 수 있습니다. 둘 중 하나가 홈 디렉터리 밖의 폴더를
지정하면, Apothem은 그곳의 파일을 변경합니다. 그것이 지정된 폴더이기 때문입니다.

Apothem 자체 폴더인 `~/.apothem`은 이런 방식으로 검사하지 않습니다. 이 폴더에는
백업, 설치 원장, 그리고 그 잠금 파일이 있습니다. 이 폴더가 링크이면 그곳에 쓰는 모든
명령이 그 링크가 이어지는 곳 어디든 따라가며, `apothem backups
prune`과 자동 백업 보존은 그 링크 끝에 있는 오래된 백업 세트를 삭제합니다.

설치 및 업데이트 작업은 기존 관리 대상을 교체 전에 백업하여 보존합니다. 공유
디스커버리 디렉터리는 하위 항목 단위로 병합되므로 관련 없는 운영자 작성 파일은
그대로 남습니다. `--dry-run`은 같은 검증을 수행하고, 디렉터리나 파일을 만들지
않은 채 계획된 결과를 보고합니다.

프로필 진단은 시크릿처럼 보이는 키와 토큰 형태의 값이 일반 출력, JSON 출력,
로그, 문서 스니펫, 테스트에 도달하기 전에 가립니다. 공개 예시는 가짜
플레이스홀더 신원과 도메인을 사용합니다.

## 공급망 릴리스 증거

각 GitHub Release에는 다음 증거가 담겨 있습니다. 항목마다 다루는 파일이 다릅니다.

- [`sigstore/cosign-installer`](https://github.com/sigstore/cosign-installer)를 통한 **Sigstore 서명**.
  배포되는 모든 파일, 즉 sdist, wheel, VS Code 패키지 `apothem.vsix`, SBOM
  `sbom.cdx.json`, 세 개의 플랫폼 아카이브, `SHA256SUMS`에 적용됩니다. 각 파일에는
  자체 `<file>.cosign.bundle`이 있습니다. 출처 파일 `provenance.intoto.jsonl`에는 cosign
  번들이 없습니다. SLSA 생성기가 자체 DSSE 봉투 안에서 이를 서명합니다.
- [`slsa-framework/slsa-github-generator`](https://github.com/slsa-framework/slsa-github-generator)를 통한 **SLSA-3 빌드 출처**.
  `provenance.intoto.jsonl`에 네 파일, 즉 sdist, wheel, `apothem.vsix`,
  `sbom.cdx.json`에 대한 출처가 담깁니다. 릴리스 워크플로는 GitHub에도 같은 파일에 대한
  자체 빌드 출처 기록을 보관하도록 요청하는데, 이는 이 파일과 별개의 기록입니다. 그
  단계는 릴리스를 막지 않으므로 릴리스에 그 기록이 없을 수도 있습니다. 플랫폼 아카이브와
  `SHA256SUMS`에는 SLSA 출처가 없으며, 그 cosign 서명과 서명된 릴리스 태그가 이를
  다룹니다.
- 배포되는 wheel과 sdist의 **CycloneDX SBOM**. `scripts/release/generate_sbom.py`가 작성하며, apothem 패키지, `apothem/_vendor` 아래에 벤더링된 모든 패키지와 그 라이선스, 선언된 런타임 요구 사항, 각 배포판의 SHA-256을 담습니다. SBOM은 배포판과 마찬가지로 서명되고 빌드 출처의 적용을 받습니다
- `@ahmed-g-gad/apothem`의 Trusted Publishing OIDC를 통한 **npm 출처 명세**
- **GPG로 서명된 git 태그**(EDDSA 키 `70396FED9C634163`)

## 릴리스 검증

릴리스의 모든 자산을 빈 디렉터리에 다운로드한 다음 서명과 빌드 출처를
검사합니다. `vX.Y.Z`와 `X.Y.Z`를 다운로드한 릴리스로 바꾸세요.

```bash
gh release download vX.Y.Z --repo ahmed-g-gad/apothem
cosign verify-blob \
  --bundle apothem-X.Y.Z-py3-none-any.whl.cosign.bundle \
  --certificate-identity https://github.com/Ahmed-G-Gad/apothem/.github/workflows/release.yml@refs/tags/vX.Y.Z \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  apothem-X.Y.Z-py3-none-any.whl
slsa-verifier verify-artifact \
  --provenance-path provenance.intoto.jsonl \
  --source-uri github.com/Ahmed-G-Gad/apothem \
  --source-tag vX.Y.Z \
  apothem-X.Y.Z-py3-none-any.whl apothem-X.Y.Z.tar.gz
```

`cosign`은 `Verified OK`를, `slsa-verifier`는 `PASSED: SLSA
verification passed`를 출력합니다. 다른 자산에 대해서는 해당
`<asset>.cosign.bundle`로 `cosign` 명령을 반복합니다(이전 릴리스에서는 플랫폼
아카이브와 `SHA256SUMS` 번들의 이름이 `<asset>.sig`). darwin 아카이브와 linux
아카이브는 두 이름 아래의 같은 바이트이므로 `SHA256SUMS`에는 같은 다이제스트가
두 번 나열됩니다. 클론에서
`bash scripts/release/verify-provenance.sh --require-all <download-dir>`를 실행하면
세 가지 검사, 즉 `SHA256SUMS` 매니페스트, 모든 cosign 번들, 그리고 wheel, sdist,
`apothem.vsix`, 서명된 SBOM의 SLSA 출처를 한 번에 수행합니다. 도구(`cosign`,
`slsa-verifier`)나 파일(`SHA256SUMS`)이 없는 검사는 건너뛰며, 마지막 줄에 실행한 검사와
건너뛴 검사를 알려 줍니다. `chain OK (3 of 3 layers verified: ...)`만이 릴리스가
검증되었음을 뜻하며, `partial check`로 시작하는 줄은 그렇지 않습니다.
`--require-all`(`verify-provenance.ps1`에서는 `-RequireAll`)을 주면 부분 검사는 1로
종료하고, 주지 않으면 부분 검사는 0으로 종료합니다.

검증이 의미를 가지는지는 두 가지 세부 사항이 결정합니다.

- **소유자 대소문자.** 신원 검사는 대소문자를 구분하며, 인증서에는 GitHub가
  보고하는 대로의 소유자 `Ahmed-G-Gad`가 담겨 있습니다. 소문자 소유자는 두 도구
  모두에서 실패합니다.
- **정확한 신원.** 위의 전체 주체와 함께 `--certificate-identity`를 사용하는
  것이 좋습니다. 모든 릴리스 태그를 허용하려면 패턴의 양 끝을 고정하세요.

  ```bash
  --certificate-identity-regexp '^https://github\.com/Ahmed-G-Gad/apothem/\.github/workflows/release\.yml@refs/tags/v[0-9]+\.[0-9]+\.[0-9]+$'
  ```

  `github.com/Ahmed-G-Gad/apothem` 같은 고정되지 않은 패턴은 그 텍스트를
  포함하기만 하는 위조된 주체와도 일치합니다. 예를 들어 이 저장소의 이름을 딴
  브랜치에 있는 다른 저장소의 워크플로가 그렇습니다.

[릴리스 주기 런북](/docs/runbooks/release-cycle)은 같은 명령을 메인테이너의
릴리스 후 점검으로 기록합니다.

### 릴리스 재빌드와 비교

wheel과 sdist는 재현 가능합니다. 릴리스 툴체인으로 태그를 다시 빌드하면 게시된
SHA-256 다이제스트가 나옵니다. 릴리스와 마찬가지로 Linux에서 Python 3.12를
사용하세요.

```bash
git clone https://github.com/ahmed-g-gad/apothem && cd apothem
git checkout vX.Y.Z
python3.12 -m venv .build && . .build/bin/activate
pip install --require-hashes -r scripts/release/requirements-build-linux.txt
export SOURCE_DATE_EPOCH="$(git log -1 --pretty=%ct)"
python -m build --no-isolation
python scripts/release/normalize_sdist.py dist/*.tar.gz
sha256sum dist/*
```

다이제스트를 게시된 wheel 및 sdist와 비교합니다. 빌드는 `pyproject.toml`이
