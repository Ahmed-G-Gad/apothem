Apothem은 하나의 원칙을 중심으로 설계되었습니다. 거버넌스 구성은 어떤 단일 하니스보다도 오래 지속되어야 합니다. 공유 Apothem 프로필은 `~/.config/apothem/profile.yaml` 또는 `--profile PATH`에 있는 스키마 검증된 YAML 파일입니다. 패키지된 Apothem 코호트는 명령, 규칙, 스킬, 훅, 템플릿, 상태 표시줄, 출력 스타일, 위임 정의를 제공합니다. `src/apothem/harnesses/<harness>/` 아래의 하니스별 어댑터는 이러한 입력을 지원되는 각 하니스가 요구하는 형식으로 변환합니다.

```text
Claude Code, Cursor, Gemini CLI, GitHub Copilot, Codex, Windsurf,
OpenCode, Antigravity, Open-Claw, Hermes, Qwen Code,
CodeBuddy, Kiro, Trae, Zed
```

## 핵심 아이디어

호스트 비종속성은 당신의 *의도* — 당신이 누구인지, 어시스턴트가 어떻게 동작하기를 원하는지, 그들이 따라야 할 규칙 — 가 어떤 단일 하니스도 소유하지 않는 한곳에 산다는 것을 의미합니다. 하니스는 그 의도를 소비하는 교체 가능한 소비자입니다. 새로운 어시스턴트가 등장하면 구성을 다시 작성하는 것이 아니라 어댑터를 추가함으로써 그것을 도입합니다. 사용하던 어시스턴트가 인기를 잃으면, 구축한 거버넌스를 잃지 않고 그것을 버립니다. 프로필이 자산이고, 하니스는 렌더 대상입니다. 하니스는 코딩, 채팅, 협업, 리서치, 글쓰기 등 어디에 쓰이든 상관없습니다 — 프로필은 하니스의 용도에 비종속적입니다.

이는 의도적인 반전입니다. 일반적인 경로는 각 도구를 직접 구성하는 것인데, 이는 당신의 투자를 그 도구의 수명과 형식에 인질로 잡히게 만듭니다. Apothem은 구성을 이식 가능한 자본으로, 하니스를 일회용 터미널로 취급합니다.

## 문제

모든 하니스에는 고유한 구성 형식이 있습니다.

```text
Claude Code:    CLAUDE.md + settings.json
Cursor:         .cursor/rules/*.mdc
GitHub Copilot: .github/copilot-instructions.md
Windsurf:       .devin/rules/
Codex:          AGENTS.md
```

Apothem이 없으면, 시간이 지나면서 서로 벌어지는 N개의 개별 구성 파일을 유지 관리하게 됩니다.

## Apothem의 해법

```text
One shared Apothem profile (YAML) + packaged cohorts
    identity.name
    preferences.style
    rules[]
         |
         v
    Adapter layer (HarnessAdapter protocol — src/apothem/harnesses/<harness>/)
         |
         +---> Claude Code adapter   -> ~/.claude/
         +---> Cursor adapter        -> .cursor/rules/*.mdc
         +---> Copilot adapter       -> .github/copilot-instructions.md
         +---> Windsurf adapter      -> .devin/rules/
         +---> ...
```

공유 프로필을 한 번 편집한 다음, `apothem update --harness <name>` 또는 `apothem update --harness all --project <path>`를 실행하여 변경 사항을 전파합니다. `apothem harnesses list`는 등록된 집합을 출력합니다.

## 왜 "apothem"인가

이 이름은 아키텍처를 인코딩합니다. 기하학에서 *apothem*(변심거리)은 정다각형의 **중심**에서 **한 변의 중점**까지의 수직선입니다 — 핵심에서 모든 모서리까지의 단일 거리로, 모든 방향에서 동일합니다. 그것이 바로 이 설계입니다. 중심에 하나의 공유 프로필, 둘레에 등거리로 놓인 열일곱 개의 하니스, 모든 구체화가 진실 공급원으로부터 동일한 거리만큼 떨어져 있습니다. 모서리가 바뀌어도 핵심은 변하지 않습니다. 모서리들은 핵심과 단일한 관계를 공유합니다. 드리프트는 구조적으로 불가능합니다.

## 이식성 보장

`portability: universal`로 표시된 규칙은 지원되는 모든 하니스로 번역 가능함이 보장됩니다. `portability: project-specific`로 표시된 규칙은 규칙 본문에 하니스별 재정의 문서가 필요할 수 있습니다.
