Apothem 提供一个具备架构感知的 `/plan` 流水线、一个十三阶段的 `/research` 流水线，以及一个由十一条命令组成的审计评审序列——为每个项目提供一条结构化路径：从原始文字描述到生产级、经多维度评审的代码，以及从原始构想到经同行评审并已传播的论文。

## 流水线概览

```mermaid
flowchart LR
    accTitle: Plan pipeline command flow
    accDescr: Left-to-right flowchart of the apothem plan pipeline from the spec stage through the generate and review stages, then through a conditional architecture-bearing decision that either runs the design stage or skips directly to the execute stage. The orthogonal audit stage wraps the spec-through-review span as a closed remediation loop, and the re-entrant amend stage revises an existing suite and returns it to review.
    A[/plan-spec] --> B[/plan-generate]
    B --> C[/plan-review]
    AUD[/plan-audit<br/>orthogonal: wraps spec → review] -.->|closed-loop remediation| A
    AM[/plan-amend<br/>re-entrant: revises an existing suite] -.->|re-review| C
    C --> Q{Architecture-bearing suite?}
    Q -->|yes| F[/plan-design<br/>emit _inputs/design.md]
    Q -->|no| D[/plan-execute]
    F --> D
    D --> E[/plan-status]
    D --> G[Audit review sequence]
    G --> H[Completion milestone]
```

## 规划阶段

该流水线以八个一等斜杠命令的形式提供，每个阶段一个——每个都可作为 `/plan-<stage>` 独立调用。[/plan](/docs/pipeline/plan) 编排器驱动它们，从一项任务目标推进到一个已执行的套件。

| 阶段 | 角色 | 位置 |
|-------|------|----------|
| [/plan-spec](/docs/pipeline/plan-spec) | 锻造者——从文字描述到规范 | 链首 |
| [/plan-generate](/docs/pipeline/plan-generate) | 生成器——从规范到计划套件 | 链中 |
| [/plan-review](/docs/pipeline/plan-review) | 审计员——取证式计划审计 | 链中 |
| [/plan-design](/docs/pipeline/plan-design) | 架构师——为承载架构的套件生成 `_inputs/design.md` | 条件闸门 |
| [/plan-execute](/docs/pipeline/plan-execute) | 执行器——阶段执行 | 末端 |
| [/plan-status](/docs/pipeline/plan-status) | 报告器——只读状态 | 只读 |
| [/plan-audit](/docs/pipeline/plan-audit) | 守护者——对 spec → generate → review 的闭环包装 | 正交（执行前） |
| [/plan-amend](/docs/pipeline/plan-amend) | 管家——对现有套件的可重入修订 | 可重入 |

`/plan-audit` 与线性流程正交，而不是其中的一个阶段。它将 `/plan-spec → /plan-generate → /plan-review` 包装为一个单一闭环，只运行缺失的上游阶段，主动修复发现项，并使套件处于可交给 `/plan-execute` 的就绪状态。它不同于下文的审计评审序列，后者审计的是已执行的代码库，而不是计划套件。

`/plan-design` 不是一道普遍适用的仪式。`/plan-review` 判定套件是否变更承载架构的表面。如果是，`/plan-design` 生成供 `/plan-execute` 和 `/architecture-review` 使用的设计踪迹。如果不是，经评审的套件直接进入执行。

## 研究流水线

研究流水线以十三个一等斜杠命令的形式提供，每个阶段一个——每个都可作为 `/research-<stage>` 独立调用，由序列闸门和交接清单串联，并受十项严谨性强制规定约束（权威来源、可复现性、可证伪性、引用完整性、预注册、伦理 / 利益冲突、统计严谨性、开放科学 / FAIR、报告指南合规、理论基础 / 影响力）。

```mermaid
flowchart LR
    accTitle: Research pipeline command flow
    accDescr: Left-to-right flowchart of the apothem research pipeline from the ideate stage through spec, theory, sources, synthesis, proposal, study design, experiment, analysis, paper, and peer review to publish and disseminate, with a revision loop from review back to paper.
    RI[/research-ideate] --> RS[/research-spec]
    RS --> RT[/research-theory]
    RT --> RSO[/research-sources]
    RSO --> RSY[/research-synthesis]
    RSY --> RPR[/research-proposal]
    RPR --> RD[/research-design]
    RD --> RE[/research-experiment]
    RE --> RA[/research-analysis]
    RA --> RP[/research-paper]
    RP --> RR[/research-review]
    RR --> RPU[/research-publish]
    RPU --> RDI[/research-disseminate]
    RR -.->|revision loop| RP
```

| 阶段 | 角色 | 位置 |
|-------|------|----------|
| [/research-ideate](/docs/pipeline/research-ideate) | 提出问题——从领域种子生成候选问题 | 链首 |
| [/research-spec](/docs/pipeline/research-spec) | 框定问题——可证伪假设 + 范围 | 链中 |
| [/research-theory](/docs/pipeline/research-theory) | 概念框架 + 变革理论 | 链中 |
| [/research-sources](/docs/pipeline/research-sources) | 带可重新运行检索记录的系统性来源收集 | 链中 |
| [/research-synthesis](/docs/pipeline/research-synthesis) | SOTA 图谱 + 缺口分析 | 链中 |
| [/research-proposal](/docs/pipeline/research-proposal) | 目标 + 可行性 + 应急预案 + 影响力 + 数据计划 + 预注册计划；资助方征集公告矩阵或再次申请回应 | 链中 |
| [/research-design](/docs/pipeline/research-design) | 研究设计 + 预注册 | 链中 |
| [/research-experiment](/docs/pipeline/research-experiment) | 运行 + 记录，可复现 | 链中 |
| [/research-analysis](/docs/pipeline/research-analysis) | 结果 + 统计 | 链中 |
| [/research-paper](/docs/pipeline/research-paper) | 顶级论文草稿 | 链中 |
| [/research-review](/docs/pipeline/research-review) | 同行评审级别的批评 | 链中 |
| [/research-publish](/docs/pipeline/research-publish) | 面向发表渠道的材料包 + 投稿 | 链中 |
| [/research-disseminate](/docs/pipeline/research-disseminate) | 传播 + 影响力 + FAIR 归档 | 末端 |

[/research](/docs/pipeline/research) 包装式工作流编排器驱动这些阶段，从原始问题推进到已发表的论文（它本身不是一个阶段），并在下一阶段基于每个阶段的输出继续构建之前，独立检查该输出；`--quick` 只运行 `/research-sources` + `/research-synthesis`，用于生成一次性的带引用报告。

实证阶段（来源、设计、实验、分析）和写作阶段（论文、评审、发表、传播）还会借助若干将严谨性付诸实施的表面——公平的多方法比较、比较对象的来源记录、实验项目脚手架、算力利用计划、可选启用的自主实验循环、完成定义推进闸门、带分阶段披露的盲法、检索记录、研究分配与检验力规划、分析规范、计划应急预案、图表完整性，以及演讲与海报规划——它们为这十项强制规定补充操作细节，而不扩展这些规定。

## 审计评审序列

[/audit](/docs/pipeline/audit) 包装式工作流编排器以单次并行扫查覆盖下列全部十一个维度——它是审计堡垒中与 `/plan` 和 `/research` 相对应的命令——并综合出一份去重、按严重级别分诊的发现项报告（仅报告；修复交由 `/elevate`）。每个维度也都可以单独调用。

[/fortress](/docs/pipeline/fortress) 包装式工作流编排器闭合 `/audit` 所报告的回路：它通过 `/audit` 进行检测，核实每个发现项，在其所属表面修复每个留存的发现项，在有界循环中重新审计，并通过 [/release-readiness](/docs/pipeline/release-readiness) 为结果把关——它是生产加固中与 `/plan` 和 `/research` 相对应的命令。

|---------|--------------|
| [/code-review](/docs/pipeline/code-review) | 代码质量 |
| [/code-audit](/docs/pipeline/code-audit) | 代码语料 |

| [/perf-audit](/docs/pipeline/perf-audit) | 性能 |
| [/architecture-review](/docs/pipeline/architecture-review) | 架构 |
| [/ux-review](/docs/pipeline/ux-review) | 开发者体验 |
| [/a11y-audit](/docs/pipeline/a11y-audit) | 无障碍 |
| [/docs-review](/docs/pipeline/docs-review) | 文档 |
| [/dependency-audit](/docs/pipeline/dependency-audit) | 依赖 |
| [/supply-chain-audit](/docs/pipeline/supply-chain-audit) | 供应链 |
| [/threat-model-audit](/docs/pipeline/threat-model-audit) | 威胁模型 |
