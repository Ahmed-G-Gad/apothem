移除一个工具适配器配置。

## 概要

```
apothem uninstall --harness NAME|all [--yes] [--project PATH]
                   [--quiet|-q] [--verbose|-v]
                   [--format plain|json] [--json] [--no-color]
```

移除由适配器管理的工具目标，然后在安装所创建的目录变为空之后移除这些目录（包含你自己任何内容的目录会保留）。

## 卸载会移除什么

安装会在安装台账（`~/.apothem/state/<harness>/ledger.jsonl`）中记录它复制到位的每个文件（技能、命令、规则等）的 SHA-256。卸载只会在这样的文件仍保持该内容时移除它，然后移除每个变为空的文件夹，包括你在 Apothem 文件夹中创建的空文件夹。其他一切都会保留，并得到一条 `Warning:` 行：你添加到 Apothem 文件夹中的文件、你编辑过的 Apothem 文件、与 Apothem 文件同名的你自己的文件，以及安装记录未列出的路径。你保留的文件会让其所在的文件夹也保留下来。

由较早版本记录的安装不会说明哪些文件是 Apothem 写入的。对于这样的安装，卸载会将每个文件与本版本在该路径写入的内容进行比较，并移除字节相同的文件。有两处保存着安装时找到的 Python 解释器：状态栏的命令，以及合规闸门中的一条注释。只有当这样的位置保存的是 `py -3`（较早版本在那里写入的唯一启动器）或本机上某个解释器文件的完整路径，且别无其他内容时，它才会被视为相同。那里的路径若包含 `&`、`#` 或 `$`（例如 `R&D` 这样的 Windows 用户名），或者指向本机上不存在的文件，就永远不会被视为相同，因此该文件会被保留。指向你之后升级或移除了的解释器的路径同样指向本机上不存在的文件，因此该文件也会被保留：请运行 `apothem update`，然后再次卸载。设置文件或钩子文件中 Apothem 的钩子条目不会以这种方式比较：它们通过所运行的分派脚本来识别（无论其前面是哪个解释器），并在该文件备份之后被移除。

位于 Apothem 会写入的名称处、但内容不同的文件（由那个较早版本写入，或经你编辑）会保留，并且卸载不会完成：它会打印 `✗ <harness> uninstall did not finish:` 以及此类路径的数量（一个文件夹计为一次，其中的文件列在它的 `Warning:` 行下），并以 `2` 退出。该版本记录过、而本版本不再写入的路径也是如此，因为没有可以比较的对象。完全没有记录的安装（其台账已被删除）也会以同样方式结束，因为没有任何信息表明它的哪些文件是 Apothem 写入的；它在链接之外保留的每个路径都列在同一条 `Warning:` 行下，包括你添加的文件，因为没有任何信息能将它们区分开。你主目录中的共享文件夹也会为它保留。有些部分仍会被移除：共享文件（例如规则文件或 `hooks.json`）中 Apothem 的行（除此之外别无内容的文件也会被移除；其块丢失了 END 标记的文件保持原样，参见[未完成的卸载](#未完成的卸载)），数据文件夹中的记忆、上下文和学习存储（先备份；它们保存的是你的数据，而不仅仅是 Apothem 的），以及对于某些工具，该工具列为过时的旧布局文件夹。在 `✗` 行之后，一条 `Note:
<harness> - no install record matched` 行会指出它保留的共享文件夹以及它仍然移除的内容。对于项目作用域的工具，它还会提示你在运行 `apothem update` 之前检查 `--project` 是否指向你安装到的文件夹，因为在另一个文件夹中运行更新会安装到那里；该文件夹会像其他打印出的命令中那样加引号，或者在那些引号无法容纳它时按原样给出，情形与下文数据存储的 `Warning:` 行相同。当某条警告因卸载留下的 Apothem 标记而指出某个文件时（一个之后没有 END 的 BEGIN 标记、Apothem 标记之间的两个不同块，或 Apothem 无法定位的标记对），`✗` 行会提示在更新之前修复该文件，并附上针对其标记类型的建议（参见[未完成的卸载](#未完成的卸载)）；对于项目作用域的工具，`Note:` 行也会这样提示。只有包含两个不同块的 `CLAUDE.md` 或配置档案文档不在那一行中（见下文）。`Note:` 行在 `--quiet` 下也会打印，输出到错误流。在 `--format json` 输出中，该工具的 `uninstall` 行带有 `"outcome": "error"`，其消息中带有该说明，并带有 `"detail": {"kept_reason": "no-record"}`。`apothem update` 会写入本版本的文件并记录它们，因此先运行它、再运行 `apothem uninstall` 即可完成卸载。在此之前，请复制你编辑过或添加的任何列出的文件：更新会覆盖它写入的路径，并整体替换它写入的每个 Apothem 文件夹条目（它会先把两者都备份到 `~/.apothem/backups/` 下，但不会把它们放回去）。也请先修复任何因 Apothem 标记而被警告指出的文件（参见[未完成的卸载](#未完成的卸载)）。对于由较早版本记录的安装，Apothem 文件夹中位于 Apothem 从不写入的名称处的文件属于你：它会列在针对已更改或属于你的文件的 `Warning:` 行下，会保留，而卸载仍会完成。

当该位置最新的记录是一次已完成的卸载时（例如之后的一次安装在能够记录自身之前就停止了），卸载会将每个路径与本版本写入的内容进行比较，但你主目录中的共享文件夹除外：它们保持原样，与没有记录时一样（参见[主目录中的共享文件夹](#主目录中的共享文件夹)）。只有当文件的字节完全相同时它才会移除该文件，并会移除不含任何文件的文件夹。那里没有任何信息表明该安装找到的是哪个解释器，因此保存解释器路径的文件（状态栏的命令、合规闸门中的注释）永远不会被视为相同，会保留下来。只要该闸门文件仍在，该工具就仍显示为已安装，因此请检查该文件并手动移除它。其他一切也都会保留（你的文件、你编辑过的 Apothem 文件、另一个程序写入的缓存）并得到一条 `Warning:` 行，而卸载会完成。留在其他文件已被移除的文件夹中的文件，会列在针对已更改或属于你的文件的那一行下；任何其他路径会列在这样一行下：它说明没有安装记录列出该路径、它与本版本写入的内容不匹配，以及如果你不再需要它，可以手动移除。链接背后字节完全相同的文件会使卸载停止，就像对于已记录的安装、链接背后 Apothem 自己的文件那样（见下文）。如果这样的卸载未完成（例如有一个它无法移除的文件），该工具仍显示为已安装，再次运行卸载会以同样方式进行，在一次失败并撤销了自身更改的安装之后也是如此。在一次回滚之后，或者只有未完成的卸载时，这样的路径会使卸载停止，就像没有记录时那样。

当该位置没有记录任何安装时（如上述情形），卸载还会将 Apothem 的受管块留在原处：对于 Claude Code，在 `~/.claude/CLAUDE.md` 中；对于通过单个设置文件配置的工具（例如 Open-Claw、OpenCode 或 Qwen Code），在其文件夹中的配置档案文档 `apothem/rules/00-apothem-profile.md` 中。没有任何信息表明是哪次安装写入了该块，因此该文件保持原样，并有一条 `Warning:` 行指出它；该警告不会使卸载停止。如果你不再需要该块（Claude Code 仍会读取 `CLAUDE.md`），请按照警告给出的编号修复手动将其移除，例如 "Fix A: A1. Change line 5: add a word inside its comment. Apothem then finds no block of its own in this file."（参见[按编号修复操作](/docs/install/troubleshooting#follow-a-numbered-fix)）。警告按行号指出该块，而修复会就地更改其 BEGIN 标记行，因此你的任何一行读起来都不会改变；其下方直到 END 标记行的旧 Apothem 文本随后归你所有，可手动删除。块上方你自己的 BEGIN 标记，或你引用的标记对中的 BEGIN 标记，不属于该块：修复也会更改每一个这样的行，否则一旦该块被移出，它就会被读作 Apothem 的标记。当该文件在 Apothem 的标记之间包含两个不同的块时（例如你在代码之外的一个标记对），从第一个 BEGIN 标记删除到下一个 END 标记会把你的文本一并删除，因此警告会针对这样的文件给出相应的文本（参见[未完成的卸载](#未完成的卸载)）：它按行号指出每个块，或指出 Apothem 的块及其周围的标记行，并说明如何在保留你自己文本的前提下修复该文件。当它指出的是 Apothem 的块及其周围的标记行时，它接着会提示：如果你不再需要 Apothem 的块，请手动删除它。当它指出两个或更多完整的块时，它则提示运行 `apothem update`，然后再次运行 `apothem uninstall`：Apothem 块上方你自己的一个 BEGIN 标记和其下方的一个 END 标记（那段文本没有指出它们），在 Apothem 的块被手动删除后会构成一个块，而下一次更新会替换它们之间的行。再次运行的卸载会首先指出这些标记行。该警告同样不会使卸载停止，`✗` 行也不会指出该文件。在运行 `apothem update` 之前也请修复它：更新不会修复它。

共享工作目录的记忆、上下文和学习存储，只有当这是该目录中最后一个已安装的工具时，才会被备份并移除。卸载会在安装所记录的位置移除它们，因此无论安装把它们写到哪里，卸载都能找到（参见 `workspace` 配置档案字段）。`plans/` 目录永远不会被移除。在这里，文件夹已不存在的安装（已删除的项目）仍算作在使用这些存储，这与下文的共享文件夹不同，卸载会说明这一点（见下文）。

除非提供 `--yes`，否则会提示确认。在无法提示时——`--format json`（提示文本会破坏单个 JSON 文档）或非交互式 shell（无 TTY）——该命令会预先拒绝执行，并返回结构化的 `uninstall.confirmation_required` 错误（退出码 1），除非提供了 `--yes`。如果所选工具未安装，该命令会成功（退出码 0）；在纯文本输出中，它会打印 `NAME is not installed; nothing to remove.`，其中 `NAME` 为工具 ID。若某个文件包含 Apothem 无法与你的文本区分开的标记行，只要安装记录列出了它，它就算作已安装；在安装台账无法读取时也是如此：卸载随后会因损坏的台账而停止（退出码 1）并指出它，就像对于包含完整块的文件那样，而不是将该工具报告为未安装。

当某个链接把你主目录中某个工具的文件夹引向主目录之外时（例如 `~/work/tool`，而 `~/work` 链接到另一个驱动器），卸载会在移除任何内容之前停止。在 Windows 上，联接点 也算作链接。在交互式运行中，命令不会先请求确认。无法询问的运行（JSON 输出，或没有终端）仍会先停止并要求提供 `--yes`；传入它之后才会显示链接错误。该错误包含 `uninstall
refused: target path crosses a link`，指出该链接及其指向的文件夹，并说明该怎么做；命令以 1 退出。请让该链接指向你主目录中的某个文件夹，或用该文件夹本身替换它，然后再次运行卸载。你以主目录之外的路径写出的文件夹会被跟随。

安装根目录下 `.apothem/` 中的共享数据存储（`memory/`、`contexts/`、`learning/`），只要同一根目录下仍有另一个已安装的工具在使用它们，就会保留。当你移除的工具是该根目录下的最后一个工具时，该命令会先将每个数据存储复制到 Apothem 备份根目录（`~/.apothem/backups/`），然后连同其中的全部内容一并移除。你保存在 `plans/` 中的任何内容绝不会被移除。

当保留这些存储的安装都位于已不存在的文件夹中时，命令会保留这些存储，并打印一条 `Warning:` 行，指出其中一个这样的安装以及释放它的步骤。在一个重新创建的空文件夹中运行卸载不会找到任何已安装的内容，因此这些步骤会先在那里重新安装该工具，并使用该安装所用的同一个 `--profile`。这些存储位于该文件夹之外，因此是该安装的配置档案把它们放在了现在的位置。不带该选项的安装会写入它自己的存储，而之后的卸载会让这些存储没有任何安装在使用。Apothem 不会记录安装使用了哪个配置档案，因此警告会打印 `--profile <the profile it used>`，由你来填写。对于安装在项目中的工具，步骤如下：

```bash
mkdir -p /path/to/old-project
apothem install --harness cursor --project /path/to/old-project --profile /path/to/that-profile.yaml
apothem uninstall --harness cursor --project /path/to/old-project --yes
```

警告在 Windows 上用双引号、在其他系统上用单引号括起该文件夹。当这些引号无法容纳该文件夹时，警告会用文字给出同样的步骤，并按原样给出该文件夹。在 Windows 上，以下情况会如此：文件夹包含 `$`、反引号、`%`、`!`、直双引号或弯双引号，或控制字符，Windows shell 会在双引号内改变它们；不含空格的文件夹中出现 `&`、`^`、`|`、`<` 或 `>`，PowerShell 和 Git Bash 随后会将其不带引号地传给安装程序的 `apothem.cmd`，于是命令提示符会对它们进行处理；或者连续两个反斜杠，例如网络共享开头的那样（`\\server\share`），Git Bash 会将其读作一个。在其他系统上，当文件夹包含直单引号或弯单引号（shell 也可能在弯引号处结束单引号）、控制字符、连续两个反斜杠或结尾反斜杠时会如此（fish 在单引号内把两个读作一个，而结尾的一个会转义右引号）。

对于安装在你主目录中的工具，警告会用文字给出同样的步骤：它安装到的文件夹可能来自某个环境变量（例如 `XDG_CONFIG_HOME`），而打印出的命令不会重复该变量。当没有其他安装仍在使用这些存储时，它们会随那次卸载一并移除。你也可以手动移除这些存储。

## 主目录中的共享文件夹

多个安装可以使用你主目录中的同一个文件夹：技能文件夹（`~/.agents/skills/`，或 `~/.codebuddy/skills/`、`~/.kiro/skills/`、`~/.trae/skills/`）以及 `~/.config/apothem/rules/` 和 `~/.config/apothem/templates/`。[install](/docs/cli-reference/install#folders-in-your-home-directory) 页面列出了哪个适配器写入哪个文件夹。Apothem 会记录哪些安装使用每个文件夹，而卸载遵循一条规则：只有当没有其他 Apothem 安装仍在使用某个文件夹时，才会移除它。

- 卸载一个工具时，只要另一个安装仍在使用这些技能，就会保留它们，并会说明这一点。同一个工具安装在两个项目中算作两个安装，因此从项目 A 卸载它时，只要项目 B 仍在使用这些文件夹，就会保留它们。最后一次卸载会移除它们（见下文的第二个示例）。
- 无论每次安装运行时你的主文件夹是如何写出的，一个文件夹都算作一个文件夹。当你的主文件夹是一个链接时，例如 Fedora Silverblue 上 `/home` 指向 `/var/home`，或一个移到 联接点 背后的 Windows 用户配置文件夹，通过链接进行的安装与通过其指向的文件夹进行的安装使用相同的文件夹。以这种方式安装的两个工具是两个安装，卸载其中一个会为另一个保留这些文件夹。以两种方式安装的同一个工具是一个安装：卸载它时，无论你的主目录以哪种方式写出，都会移除两次安装写入的内容，以及没有其他安装使用的文件夹。如果该卸载在完成之前停止，两个安装都会保持已记录状态，直到你修复导致停止的问题并再次运行卸载。只有当你的主目录以该工具的某次安装所用的方式之一写出时，卸载才能找到该安装；以任何其他方式写出时，它找不到任何可移除的内容。
- 只会移除该安装自身记录所列出的内容。在这些文件夹开始受管理之前进行的安装没有这样的记录，因此卸载它不会移除你主目录中的任何内容。你添加到这些文件夹中的文件会保留，与某个 Apothem 技能同名、但并非由 Apothem 写入的文件夹也会保留。
- 项目文件夹已不存在的安装会被忽略，因此一个已删除的项目不会让这些文件夹永久保留。说明中会指出该安装。
- 如果一个可能使用这些文件夹的安装的记录无法读取，卸载会在移除任何内容之前以错误停止，而该安装仍保持已记录状态。修复或移走这条无法读取的记录，然后再次运行该命令。一个从不写入这些文件夹的工具的损坏记录会被忽略。
- 当最后一次使用消失时，变为空的文件夹也会被移除。每个文件夹在被移除之前都会备份到 `~/.apothem/backups/` 下。

每次卸载都会为每个文件夹打印一条 `Note:`，例如 `Note: <harness> -
~/.agents/skills/ was kept: still used by <harness> (/path/to/project)`，或 `was removed: no other Apothem install uses it`。在 `--format json` 信封中，每条说明都是一个 `warnings` 条目，带有 `"outcome": "advisory"`、`"operation": "shared_root"`，以及设为 `retained` 或 `released` 的 `"role"`。它携带 `path`、`holders`（保留该文件夹的安装）、`stale`（被忽略的安装），以及 `kept` 和 `total`（保留的已记录条目，以及该安装列出的条目）。

卸载还会为它有意留在原处的每一项打印一条 `Warning:` 行。Apothem 不会通过符号链接或 Windows 联接点 移除任何内容，因此它所移除的文件夹中的链接会保留，通过链接到达的较早版本遗留文件夹也会保留。因同一个链接或同一个原因（不是 Apothem 写入的内容、不在安装记录中）而保留的路径会合并为一行，并附上数量。在针对保留路径的行下，会列出它保留的每个文件，包括保留文件夹中的文件（不含任何内容的保留文件夹会列出其自身）。Apothem 写入但无法移除的文件会列在报告它的 `✗` 行下，而不是作为保留文件列出。使用 `--quiet` 时，这些行只在卸载未完成时打印，并与 `✗` 行一起输出到标准错误，使其建议所涉及的路径保持可见。指出文件中遗留的 Apothem 标记的行，即使卸载已完成，在 `--quiet` 下也会打印到标准错误：工具仍会读取该标记下方的任何旧 Apothem 文本，之后的安装会把两者都保留，而 `verify` 随后会失败，直到你删除它们。在 `--format json` 信封中，每条这样的行都是一个 `warnings` 条目，带有 `"outcome": "warning"`、该行的 `message`、`count`（它涵盖的路径数）、`paths`（其中每个路径），以及针对保留路径的 `files`（保留的每个文件）。这些警告不会使卸载停止。有四类会：由较早版本记录的安装中与本版本写入内容不同的文件、完全没有记录的安装的文件（参见[卸载会移除什么](#卸载会移除什么)）、在 Apothem 标记之间包含两个不同块的文件，以及标记行无法被 Apothem 与你的文本区分开的文件（参见[未完成的卸载](#未完成的卸载)）。

通过链接到达的 Apothem 自己的文件则不同：大多数工具仍会加载它们，因此卸载并未完成。（一旦卸载已将 Apothem 的路径从 OpenClaw 的钩子条目中移出，OpenClaw 就不再加载其规则文件，因此对于 OpenClaw，`✗` 行只在它仍加载时才这样说明；参见 [OpenClaw](/docs/harnesses/open-claw#uninstalling)。）假设 `~/.claude/rules` 是指向某个 dotfiles 文件夹的 联接点，而该文件夹仍保存着 Apothem 写入的规则：命令会打印 `✗ <harness> uninstall did not finish:`，以及该链接和它遗留的路径数，保持该安装为已记录状态，并以 `2` 退出。请用一个保存相同文件的真实文件夹替换该链接，然后再次运行该命令。对于记录中列出了其写入文件的安装，只保存你自己的文件或你编辑过的 Apothem 文件的链接文件夹不会使卸载停止：该链接会保留并附上警告，而卸载会完成。对于由较早版本记录的安装，链接背后任何位于本版本会写入的名称处的文件都会使卸载停止，无论是否被编辑过，因为没有任何信息能将它与该版本写入的内容区分开。请用一个保存相同文件的真实文件夹替换该链接，然后按照上文针对这类安装的步骤操作：复制你编辑过的任何文件，修复任何因 Apothem 标记而被警告指出的文件，运行 `apothem update`，然后再次卸载。

当某个移除步骤报告错误时（例如某个已安装文件的路径指向你的主文件夹之外），命令会打印 `✗ <harness> uninstall
did not finish: <reason>` 而不是 `Uninstalled`，每个原因一次，并附上它所涉及的路径数。当你主目录中某个文件夹里的链接把这些路径引向主目录之外时（`target escapes the allowed materialization root`），该行还会指出该链接及其指向的文件夹，并提示用一个真实文件夹替换该链接；位于两个链接背后的路径会产生两行。该链接仍会得到它被留在原处的警告。该安装保持已记录状态，因此再次运行该命令会移除第一次运行遗留的内容。保留说明不会打印，因为它们所描述的文件夹并未被释放。在 JSON 输出中，该工具会得到一个带有 `"outcome": "error"` 和 `"operation": "uninstall"` 的 `results` 行，其后是每个失败步骤各一行。当这些原因指出一个链接时，该行在 `detail.symlink` 中携带该链接，在 `detail.leads_to` 中携带其指向的文件夹。某个步骤的行将它保留的文件列为 `files`，将 Apothem 写入但无法移除的文件列为 `stuck`。当卸载在该步骤失败之前已移除文件，或另一个工具已被移除时，信封的 `status` 为 `"partial"`，退出码为 `2`；否则 `status` 为 `"error"`，退出码为 `1`。顶层的 `error` 保持为 `null`：原因位于 `results` 中。因异常而停止的卸载（例如无法写入的备份），如果在停止之前已移除文件，或已将 Apothem 的条目或块从某个文件（例如 `openclaw.json`）中移出，会打印 `✗ <harness> uninstall
stopped after removing files:`（如果它尚未更改任何内容，则打印 `failed:`）并附上消息，同时得到一个带有其消息的 `results` 行，其后是在它之前失败的每个步骤各一行。当在它停止之前已有步骤失败，或者它已发现会使卸载无法完成的情况（链接背后 Apothem 自己的文件、由较早版本记录的安装中与本版本写入内容不同的文件、没有记录的安装的文件、在 Apothem 标记之间包含两个不同块的文件，或标记行无法被 Apothem 与你的文本区分开的文件）时，会针对每个原因跟随一条 `✗ <harness> uninstall did not finish:` 行（如上所述），并在该行消息的末尾追加同样的文本。对于没有记录的安装，`Note:` 行会跟在它们之后，对于项目作用域的工具还附带对 `--project` 文件夹的检查，而该行的 `detail` 带有 `"kept_reason": "no-record"`，如[卸载会移除什么](#卸载会移除什么)中所述。当这些原因以及在它之前失败的步骤指出一个链接时，该行在 `detail.symlink` 中携带该链接，在 `detail.leads_to` 中携带其指向的文件夹。当它事先已移除或更改了文件、发现了链接背后 Apothem 自己的文件、保留了较早版本的安装或没有记录的安装的文件、遗留了在 Apothem 标记之间包含两个不同块或包含 Apothem 无法与你的文本区分开的标记行的文件，或者另一个工具已被移除时，它以 `2` 退出，`status` 为 `"partial"`，否则以 `1` 退出。在 Open-Claw、Antigravity 或 Kimi Code 卸载的第一个步骤中发生的意外错误（一个异常，例如无法写入的备份）不会报告该步骤所做的任何事情（参见[未完成的卸载](#未完成的卸载)）：无论该步骤已更改了什么，卸载都会打印 `failed:` 并以 `1` 退出（另一个工具已被移除时为 `2`）。当 Open-Claw 的规则文件步骤改为报告错误时（一个它无法重写的规则文件，或一个带注释的 `openclaw.json`），那就是一个失败的步骤，如上所述：卸载会打印 `did not finish:`，将自身连同该步骤的备份记录为未完成；当该步骤已更改某个文件或发现了链接背后 Apothem 的规则文件，或者另一个工具已被移除时，以 `2` 退出，否则以 `1` 退出。`Ctrl+C` 会打印 `Aborted!` 并以 `1` 退出，无论卸载此时已移除了什么。被拒绝的卸载（例如某个链接把该文件夹引向你的主目录之外）不会移除任何内容并以 `1` 退出；它的行在 `detail.symlink` 中指出该链接，在 `detail.leads_to` 中指出其指向的文件夹，其后跟随被拒绝步骤的一行。

### 未完成的卸载

当卸载未完成时，它会向安装台账追加一条 `uninstall-incomplete` 记录，而不是 `uninstall` 记录。这会在以下情况下发生：某个步骤失败；Apothem 自己的文件留在链接背后；某个文件在 Apothem 标记之间包含两个不同的块，或包含 Apothem 无法与你的文本区分开的标记行（见下文）；由较早版本记录的安装的文件与本版本写入的内容不同；以及该安装没有记录。后四种情况即使没有移除任何内容，也会以 `2` 退出，`status` 为 `"partial"`，包括在你修复它们指出的问题之前的第二次运行。最后两种情况只有在 `apothem update` 之后才能完成（参见[卸载会移除什么](#卸载会移除什么)）。因异常或 `Ctrl+C` 而停止的卸载，根据它停止时所在的步骤，追加的内容如下：

- 在 Open-Claw 的第一个步骤中（该步骤从每个工作区的规则文件中移出 Apothem 的块），或在 Antigravity 和 Kimi Code 的第一个步骤中（该步骤移除旧布局遗留的内容）：不追加任何内容，即使对于该步骤此时已更改的文件也是如此；这些文件的备份保留在 `~/.apothem/backups/` 下，没有记录能使它们免于 `backups prune`；
- 在从通过单个设置文件配置的工具（例如 Open-Claw、OpenCode 或 Qwen Code）的设置文件中移出 Apothem 条目的步骤中：只有当 Open-Claw 的第一个步骤已将 Apothem 的块从某个规则文件中移出或备份了某个规则文件时，才追加该记录，否则不追加任何内容，在该步骤发现链接背后 Apothem 的规则文件时也是如此；
- 在移除安装记录所列内容的步骤中（这是除 OpenCode 之外每次卸载的最后一个步骤）：追加该记录，即使它没有更改任何内容；
- 在 OpenCode 的卸载于其后执行的步骤中（该步骤会关闭在其文件夹的另一种写法下记录的安装，例如当 `XDG_CONFIG_HOME` 指定的是某个 `~/.config` 链接所指向的文件夹时）：不再追加任何内容，因此该安装保持已记录状态。之后的运行也还不会关闭它：由于该文件夹中 Apothem 的文件已不存在，OpenCode 在那里显示为未安装，因此 `uninstall` 会跳过它，`status`、`verify` 和 `rollback` 也看不到该安装。要关闭它，请在该文件夹再次安装 OpenCode，然后卸载它：使用位于该链接文件夹之外的配置档案运行 `apothem install --harness opencode --profile PATH`（`apothem profile init --profile PATH` 可以创建一个），然后运行 `apothem uninstall --harness opencode`。

当没有追加任何内容时，台账保持原样。无论哪种情况，该安装都保持已记录状态。除最后那种情况外，`apothem status`、`verify` 和 `rollback` 仍能看到它，并且只要安装写入的某些内容仍按其写入时的样子存在（见下文），该工具就显示为已安装，因此再次运行 `uninstall` 即可完成卸载。没有记录的安装则没有可保留的记录：只有它在磁盘上的文件让该工具显示为已安装，而 `rollback` 也没有可回滚的内容。该位置上该工具的一次 `install`、`update`、`rollback` 或已完成的 `uninstall` 会替换该状态，手动移除剩余文件也会：当 Apothem 的文件已没有任何一个保持其写入时的样子，且其 `.apothem` 文件夹中也没有任何内容时，无论该文件夹中还有什么，该工具都显示为未安装。随后第一个检查该工具是否已安装的命令（`status`、`verify`、`uninstall`）会追加一条关闭该安装的 `uninstall` 记录。不过，在一次已完成的卸载之后，没有任何记录列出安装写入的文件，因此在那种情况下只有一次安装、一次更新或一次完成的卸载才会替换该状态。只要该记录所属的安装被保留，`backups prune` 就会保留该记录及其引用的备份。在一次已完成的卸载之后，它会将该记录与那次卸载的记录一起保留，因此再次运行卸载仍会以同样方式进行。

仍算作已安装的内容：安装写入的完整文件，只要它未被更改（对于由较早版本记录的安装，只要它存在）；Apothem 在 `.apothem` 下安装到的文件夹中的任何内容；以及 Apothem 在你自己的文本旁保留受管块的文件，只要该块仍在其中，无论你在其周围写了什么。这些文件是 `CLAUDE.md`、共享配置档案投射到的配置档案文档、每个 OpenClaw 工作区中的规则文件，以及 `AGENTS.md` 和安装会向其添加块的其他指令文件。

受管块从一个 `<!-- BEGIN APOTHEM MANAGED BLOCK -->` 标记延续到下一个 `<!-- END APOTHEM MANAGED BLOCK -->` 标记，每个标记独占一行；Apothem 只以这种方式、并且只在代码之外读取标记，就像 Markdown 查看器那样：围栏代码块（由相同字符、至少同样长、其后没有任何内容的围栏关闭），或在空行之后比其列表项（或页边）多缩进四列的代码。因此你在句子或代码示例中引用的标记是你的文本，你在两个独立代码块中引用的一个 BEGIN 标记和一个 END 标记也不会构成一个块。如果配置档案中的某条规则在 Apothem 写入的块末尾留下未关闭的代码围栏，Apothem 会将其关闭；在较早版本写入的块中，这样的围栏只有在其后还有另一个标记对时才会隐藏 END 标记（见下文）。你一直到文件末尾都未关闭的围栏会被读作文本，无论有多少个，除非其上方代码之外的某个 BEGIN 标记的 END 标记位于代码中，且其后还有另一个标记对。文件开头的字节顺序标记（某些 Windows 编辑器会这样保存）不会隐藏第一行上的标记。位于 HTML 块或块引用中的标记，或位于文本在左边距继续的列表项之后的标记，仍可能被读成与 Markdown 查看器不同的样子。

如果 Apothem 的块位于你的某个代码块中（其上方一个未关闭的围栏由其下方的围栏关闭，或由块内的一个关闭行关闭），或者 BEGIN 标记与其 END 之间的一个代码块隐藏了该 END、且其后还有另一个标记对，Apothem 就无法将它的块与你的示例区分开。卸载会让这样的文件保持原样，移除安装的其余部分，并且不会完成：它会打印 `✗ <harness> uninstall did not finish:`，后跟 "1 file(s) hold marker lines Apothem cannot tell from your text, so Apothem left them as they are; fix the marker lines each warning names, keeping your own text, then run apothem uninstall again"，并以 `2` 退出，第二次运行也是如此。安装记录会保留，因此之后的安装仍会让该文件保持原样，而下一次卸载会再次指出它。它的警告按行号指出文件中的每个标记对，以及代码之外每个不开启任何标记对的 BEGIN 标记。没有安装记录时，只有其 END 标记以这种方式被隐藏的 BEGIN 标记才会得到该警告：此时位于你代码块中的标记对是你的文本，而卸载会因该标记以及没有记录显示的路径而保持未完成。警告随后会给出编号修复，并以 "Then run the uninstall again." 结尾，例如 "Fix A: A1. Change line 6: add a word inside its comment. Apothem then finds no block of its own in this file."。你更改的行下方直到其 END 标记行的旧 Apothem 文本，随后归你所有，可手动删除。有多个修复时，请选择情形属实的那一个，并按给出的顺序执行其每个步骤：该文件中遗留的标记对会使卸载保持未完成，包括你自己的标记对，因此每个修复都会更改它未称为 Apothem 块的每个标记对的 BEGIN 标记行，以及每个不开启任何标记对的 BEGIN 标记（参见 [Apothem 无法将它的块与你的文本区分开](/docs/install/troubleshooting#apothem-cannot-tell-its-block-from-your-text)）。一旦该文件不再包含这样的标记对，再次运行卸载即可完成。

如果 END 标记不见了，就没有任何信息表明 Apothem 的文本在哪里结束、你的文本从哪里开始，因此卸载会让该文件保持原样，在一条警告中指出它，然后完成（除非有其他情况使其保持未完成，例如没有记录的安装）；在一次未完成的卸载之后重试也是如此。如果在 Apothem 的块移出之后，留下了一个之后没有 END 的 BEGIN 标记（你自己的一行，或某个丢失了 END 标记的旧块的残留），卸载也会指出该文件及该标记所在的行，并给出一个更改该行的编号步骤（在其注释内添加一个词），使其不再被读作标记：安装会保持它原样，而工具仍会读取其下方的文本。其下方的任何旧 Apothem 文本随后归你所有，可手动删除。`install` 或 `update` 会让这样的标记之后的文本保持原样，将 Apothem 的块与之分开写入并指出该文件，而 `verify` 会失败，直到该标记被更改（参见[某个文件包含一个没有 END 标记的 Apothem BEGIN 标记](/docs/install/troubleshooting#a-file-has-an-apothem-begin-marker-with-no-end-marker)）。

在标记之间包含两个不同块的文件（你在代码块之外引用的一个标记对、你放回了其 END 标记的旧块，或你再次粘贴进去的块）会保持原样并被指出，而卸载不会完成：它会打印 `✗ <harness> uninstall did not finish:`，后跟 "1 file(s) hold two different blocks between Apothem's markers, so Apothem left them as they are; fix each as its warning says, keeping your own text (follow one of its numbered fixes, which change marker lines in place), then run apothem uninstall again"，并以 `2` 退出，第二次运行也是如此。它的警告像安装和更新那样按行号指出每个块，并为每个块给出一个编号修复，对应该块是 Apothem 的块的情形：该修复会更改其他每个块的 BEGIN 标记行并保留它们的文本（在以 Apothem 的前置元数据开头的文件中，Apothem 的块就是紧接其下方的那个）。不要为了保留你自己的标记对而删除 Apothem 的块：否则下一次卸载会移出剩下的那个块，也就是你自己的。`apothem update` 不会修复这样的文件：它会让包含两个完整块的文件保持原样，并给出同样的警告，而 `verify` 会失败，直到你修复它（参见[某个文件在 Apothem 的标记之间包含两个块](/docs/install/troubleshooting#a-file-holds-two-blocks-between-apothems-markers)）。

Apothem 块上方的一个 BEGIN 标记和其下方的一个 END 标记会构成第二个块，只有在 Apothem 的块移出之后才会显现。卸载的警告随后会指出 Apothem 的块和这两个标记行，例如 "once the block from line 5 to line 36 is out, the BEGIN marker at line 2 and the END marker at line 39 make another"，并提示不要删除 Apothem 的块：否则下一次运行会把第 2 行到第 39 行读作 Apothem 的块。它唯一的修复改为更改该 BEGIN 标记行，保留你自己的文本，而其下方的 END 标记随后不与任何标记配对；如果该 BEGIN 标记是某个旧 Apothem 块的残留，其下方的旧 Apothem 文本随后归你所有，可手动删除。不要把这两行放进同一个代码块：那样它也会包含 Apothem 的块。`apothem update` 同样不会修复这样的文件，而 `verify` 会失败，直到你修复它。行号会把单独的 CR 计为行尾，与 CRLF 和 LF 相同（参见[某个文件包含一个没有 END 标记的 Apothem BEGIN 标记](/docs/install/troubleshooting#a-file-has-an-apothem-begin-marker-with-no-end-marker)）。

当卸载的下一步是运行 `apothem update`，而某条警告因 Apothem 标记指出了某个文件时（在 `--format json` 信封中，其 `detail` 带有 `marker_left`），`✗` 行以及它为较早版本或缺失记录而保留的每个路径的警告，都会提示你先修复该文件，并附上针对其标记类型的建议。

如果台账无法写入 `uninstall-incomplete` 记录（例如磁盘已满），台账保持原样，并有一条 `Warning:` 行指出该台账以及卸载所做备份的文件夹：没有记录能使这些备份免于 `backups prune`，因此请复制你需要的备份。由于没有那次未完成过程的记录，再次运行该命令可能会发现该工具未安装而不移除任何内容；此时请手动移除 `✗` 和 `Warning:` 行列出的文件。只要该工具仍显示为已安装，再次运行该命令就会像之前一样进行：依据安装记录，或者在一次已完成且之后未记录任何安装的卸载之后，以与那次过程相同的方式进行（参见[卸载会移除什么](#卸载会移除什么)）。当已完成卸载的 `uninstall` 记录无法保存到磁盘时，卸载会再次将它从台账中移除，并以未完成结束。当台账仍以一次已完成的卸载结尾时，它会完成，并给出同类警告：该记录仍然留在了台账中，或者该卸载紧跟在一次已完成的卸载之后。在记录保存之后发生的中断（`Ctrl+C`）会让该卸载保持已完成。

如果某个文件夹因为一个你找不到的安装而保留，说明中会指出该安装。当项目文件夹已被删除时，该安装会被忽略，而该文件夹会随下一次卸载一并移除。当项目存在、但你手动从其规则文件中移除了 Apothem 块时，`uninstall` 会将该工具报告为未安装，并且不会释放它的占用；请为该工具和项目运行 `install`，然后运行 `uninstall`，以释放它。`apothem verify` 会显示某个文件夹是否仍然完整。

`--project` 在读取时会跟随其中的链接并展开 `~`。通过 Python 代码以另一种方式写出项目文件夹（例如通过链接）进行的安装，仍能以其记录所保存的写法被找到。`install` 或 `update` 会记录解析后的文件夹。一旦安装通过其检查，它会把在另一种写法下记录的安装移到解析后的写法下，因此在链接被移除之后仍能找到该安装；被拒绝的安装不会更改任何记录。`uninstall` 会在移除任何内容之前以同样方式移动这样的安装，因此未完成的卸载会被记录在解析后的文件夹下，在链接被移除后再次运行 `uninstall` 仍能在那里找到它。记录以另一种方式指向磁盘上同一文件夹时（指向记录为 `C:\...` 的文件夹的 `\\localhost\C$` 路径），会保留记录中的写法；而在一个自身仍有安装存在的文件夹中进行的安装或卸载，会让另一种写法下的记录保持原样。安装仍存在的写法优先于安装已被移除的写法；两个都存在时，先选文件夹中其文件更多的那个，其次选较新的那个。文件夹中没有任何其文件的安装不会被当作该文件夹的安装，除非它的卸载未完成：此时再次运行 `uninstall` 会完成它。文件夹名称按精确方式比较：在区分大小写的文件夹中（例如 WSL 创建的文件夹），`Proj` 和 `proj` 是两个文件夹，永远不会被互相当作对方，卸载其中一个会保留另一个使用的共享文件夹。在普通的 Windows 文件夹中，只要它存在，它们就是同一个文件夹；一旦它不存在了，只有记录中的写法才能找到它。当 Windows 能为两个卷都命名时，挂接在原卷旁边的克隆卷不会被当作原卷。位于另一个网络共享上的记录（`\\server\share` 路径或映射到共享的驱动器号）只按其文本进行比较，因此无法访问的共享不会拖住记录查找。关于共享文件夹的说明仍会检查每个已记录的文件夹，因此它们仍可能等待这样的共享。

有三种情况不会按你预期的那样被找到。较早版本记录了两次的安装（一次从命令行、一次通过链接从 Python），在 `uninstall` 之后会保留第二条记录，而共享文件夹会为它保留。请从 Python 以安装时的写法指定该文件夹来移除它。在本计算机上某个文件夹的 `\\localhost\C$` 写法下记录的安装，无法从其 `C:\` 写法找到，因为共享上的记录不会从别处查找。此外，当两个安装通过指向两个不同文件夹的两个链接进行，而其中一个链接后来改为指向另一个文件夹时，卸载会选取在该文件夹中其文件更多的那个安装。如果两者写入了相同的文件名（同一版本的两次安装），或者是由较早版本记录的（它不会列出其文件），则选取较新的那个，而它的文件可能位于该链接原先指向的文件夹中。

使用 `--harness all` 进行的移除刻意做到穷尽：它覆盖每个已注册的工具，包括配置档案的 `exclude_harnesses` 在安装时跳过的工具——清理会触及先前范围更广的安装可能遗留的状态。从未安装过的工具会收到同样的提示。

连续式别名 `apothem uninstalling`（也接受写作 `apothem Uninstalling`）解析到同一个处理程序。

## 选项

| 选项 | 描述 |
|---|---|
| `--harness NAME` | 要移除的工具适配器，或用 `all` 表示覆盖整个注册表的集合（必填）。 |
| `--yes` | 跳过确认提示。 |
| `--project PATH` | 项目作用域工具的项目根目录。 |
| `--quiet`, `-q` | 抑制信息性输出；只输出错误。未完成的卸载仍会将其 `Warning:` 行（列出它保留的内容）打印到标准错误，而任何卸载都会在那里打印指出文件中遗留的 Apothem 标记的 `Warning:` 行。 |
| `--verbose`, `-v` | 为与其他命令保持一致而接受；本命令不输出额外信息。 |
| `--format plain\|json` | 输出格式（默认：`plain`）。 |
| `--json` | `--format json` 的简写。 |
| `--no-color` | 在输出中禁用 ANSI 颜色代码。 |
| `-h`, `--help` | 显示帮助并退出。 |

## JSON 输出

当适配器已安装并被成功移除时：

```json
{
  "schema_version": 1,
  "status": "success",
  "command": "uninstall",
  "action": "uninstalled",
  "harness": "claude-code",
  "profile_path": null,
  "project": null,
  "files_written": [],
  "results": [
    {
      "harness": "claude-code",
      "outcome": "updated",
      "operation": "uninstall",
      "path": "C:\\Users\\Example\\.claude\\settings.json",
      "message": "managed files removed"
    }
  ],
  "warnings": [],
  "error": null,
  "output_path": "C:\\Users\\Example\\.claude\\settings.json"
}
```

当适配器未安装时，命令以 `0` 退出。在 JSON 输出中，信封包含 `"status": "success"` 和 `"action": "uninstalled"`；结果行包含 `"outcome": "skipped"`，其消息为 `"not installed; no files
removed"`。`status` 字段绝不会是 `"not_installed"`。

在链接处被拒绝的结果会在 `detail.symlink` 中指出该链接，在 `detail.leads_to` 中指出其指向的文件夹，与 [`apothem install`](/docs/cli-reference/install#json-output) 中相同。

## 示例

```bash
apothem uninstall --harness claude-code
apothem uninstall --harness claude-code --yes
apothem uninstall --harness cursor --project . --yes
apothem uninstall --harness all --project . --yes
apothem uninstalling --harness cursor --project . --yes   # continuous-form alias
```

共享技能文件夹会一直保留，直到使用它的最后一个安装消失为止：

```bash
apothem install --harness codex
apothem install --harness cursor --project A
apothem uninstall --harness codex --yes                  # keeps ~/.agents/skills/, the cursor install uses it
apothem uninstall --harness cursor --project A --yes     # removes it: no install uses it now
```

## 退出码

| 代码 | 含义 |
|---|---|
| 0 | 适配器已卸载，或本就未安装 |
| 1 | 未找到工具、确认被拒绝或无法进行确认（在未提供 `--yes` 的非交互式或 JSON 模式下）；由于每个已安装的工具都在移除或更改任何内容之前失败而未移除任何内容，且未指出任何使 Apothem 自己的文件留在原处的链接、未保留较早版本的安装或没有记录的安装的文件、也未遗留在 Apothem 标记之间包含两个不同块或包含 Apothem 无法与你的文本区分开的标记行的文件（Open-Claw、Antigravity 或 Kimi Code 卸载第一个步骤中的意外错误，即一个异常，无论该步骤已更改了什么，都算作这样的失败）；或者该命令被中断（`Ctrl+C`，会打印 `Aborted!`），无论此时已移除了什么 |
| 2 | 部分移除——某次卸载在移除文件或从某个文件中移出 Apothem 的条目之后失败或停止（这样的第一个步骤中的意外错误除外，见 `1`）；至少一个工具已被移除而另一个失败；某次卸载因为有链接指向 Apothem 自己的文件而将它们留在原处；某个文件在 Apothem 标记之间包含两个不同的块，或包含 Apothem 无法与你的文本区分开的标记行；由较早版本记录的安装的文件与本版本写入的内容不同；或者某个安装没有记录来表明哪些文件是 Apothem 写入的 |
| 64 | 用法错误：未知的选项或命令，或缺失或无效的选项值。在 `--json` 下，该错误是一个代码为 `cli.usage` 的 JSON 信封。 |
