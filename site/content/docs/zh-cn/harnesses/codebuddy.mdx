**厂商：** 腾讯
**安装名称：** `codebuddy`
**状态：** GA
**平台原生配置：** `<project>/.codebuddy/rules/apothem-rules.md`

## 安装

```bash
apothem install --harness codebuddy --project /path/to/project
```

适配器从共享的 Apothem 规则和治理界面写出一个项目范围的规则文件。

**写入的文件：** `<project>/.codebuddy/rules/apothem-rules.md`

## 配置档案到平台原生配置的映射

适配器读取 Apothem 的共享配置档案，并在每次 `apothem install` 或
`apothem update` 运行时渲染项目规则文件。CodeBuddy 将 `.codebuddy/rules/`
下的每个 `*.md` 文件读取为带可选 YAML 前置元数据（`alwaysApply`、`paths`、
`enabled`）的 Markdown，详见
[CodeBuddy Rules 文档](https://www.codebuddy.ai/docs/ide/Rules)；
Apothem 的文件携带 `alwaysApply: true`，因此治理界面在每次交互时都会应用。
共享配置档案才是真实来源；在下一次同步替换由 Apothem 管理的内容之前，对生成
文件的项目本地编辑会先被备份。

## 兼容性说明

CodeBuddy 的规则界面在 `.codebuddy/rules/` 下按项目范围划定。适配器写出一个
专用的 `apothem-rules.md` 文件，它与操作者在同一目录中编写的任何规则文件
共存。`CODEBUDDY.md` 项目记忆文件和 `.codebuddy/settings.json`（权限、MCP）
由操作者自有；Apothem 不会写入它们。技能、命令、智能体和钩子作为约束在规则
文件内被引用——CodeBuddy 没有为它们提供由适配器拥有的文件界面。适配器所依赖
的厂商界面约定固定在
`src/apothem/harnesses/codebuddy/STANDARD-CONVENTION-PIN.md`，对照实时的
CodeBuddy 文档进行快照。

## 验证

```bash
apothem verify --harness codebuddy --project /path/to/project
```

verify 命令确认：

1. 平台原生配置存在于预期路径。
2. 受管规则文件存在且非空。
3. 适配器专属的验证例程报告成功。

## 更新

```bash
apothem update --harness codebuddy --project /path/to/project
```

从当前的共享配置档案状态重新派生项目规则文件。`install` 和 `update`
是幂等的——重新运行会用最新渲染的内容覆盖受管文件。

## 卸载

```bash
apothem uninstall --harness codebuddy --project /path/to/project
```

移除适配器写入的平台原生配置文件，将受管规则文件重命名为带时间戳的备份。
共享配置档案 YAML 和 Apothem 引擎不受影响。

## 合规门

```bash
python -m apothem.conformity.gate --all .
```

## 故障排查

| 症状 | 修复方法 |
|---------|-----|
| 找不到配置文件 | 重新运行 `apothem install --harness codebuddy --project /path/to/project` |
| 验证失败 | 运行 `apothem update --harness codebuddy --project /path/to/project`，然后再次验证 |
| 意外的配置内容 | 检查 `~/.config/apothem/profile.yaml` 或 `--profile PATH`，然后重新运行 `apothem update --harness codebuddy --project /path/to/project` |

## 配置开关

| 标志 | 默认值 | 说明 |
|------|---------|-------------|
| `--dry-run` | `false` | 预览安装而不写入文件。 |
