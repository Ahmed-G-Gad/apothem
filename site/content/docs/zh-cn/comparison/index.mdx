Apothem 是一个与宿主无关的 AI 工具配置管理器。位于 `~/.config/apothem/profile.yaml` 的一份共享配置档案会物化为十七个工具原生的配置表面。本节说明如何将 Apothem 与你已在使用的替代方案进行比较评估。

## Apothem 的对比情况

本页中有关同类项目的事实截至 **2026-10-02**，取自各项目自己的 README 或文档（参见[来源](#来源)）；每次次版本发布时都要重新核对这些事实。

其他工具解决的是这一问题的相邻部分。基于文件的配置管理器（例如 **chezmoi** 和 **GNU Stow**）会放置、链接文件或以模板生成文件，但绝不会把一个来源翻译成每个工具的*原生*配置模式。跨工具同步 CLI 从一个来源生成按工具划分的文件：**rulesync** 为 60 个编码工具和两项开放标准生成原生配置，其同步单元比 Apothem 的更宽；**ruler** 将一个 `.ruler/` 目录分发到 33 个目标，把规则拼接进每个工具的指令文件，并将 MCP 服务器、技能和子代理翻译为原生配置。Apothem 的不同之处在于**围绕同步一并提供的治理与生命周期纪律**：一道机械化的合规闸门、确定性的流水线、一座审计堡垒，以及可逆且经过验证的生命周期。

| 能力 | Apothem | 文件配置管理器（chezmoi、Stow） | rulesync | ruler |
| ---------- | :-----: | :----------------------------------: | :------: | :---: |
| 从一个来源到多个工具的原生模式 | 是——十七个工具适配器 | 否——复制、符号链接或模板，不做翻译 | 是——60 个工具，外加 AGENTS.md 和 Agent Skills 标准 | 部分——规则拼接进每个工具的指令文件；MCP、技能和子代理以原生形式写入 |
| 同步单元 | 规则、技能、子代理、钩子、斜杠命令、输出样式、设置、MCP | 任意文件 | 规则、忽略文件、MCP、命令、子代理、技能、钩子、权限、检查（代码评审检查指令） | 规则、MCP、技能、子代理 |
| 治理语料（行为规则加上一道机械化的合规闸门） | 是——`python -m apothem.conformity.gate` | 否 | 否——其 `checks` 功能将代码评审检查同步到各工具；没有针对规则的合规闸门 | 否 |
| 确定性的计划与研究流水线 | 是——从 `/plan-spec` 到 `/plan-execute`，以及十三阶段的 `/research` | 否 | 否 | 否 |
| 能检测并修复问题的审计堡垒 | 是——十一条命令的扫查，`/fortress` 重新审计循环 | 否 | 否 | 否 |
| 经供应链加固的发布 | 是——SBOM、Sigstore、SLSA、Scorecard 目标 | 未作比较 | 其 README 中未说明 | 其 README 中未说明 |
| 可逆、经过验证的生命周期 | 是——备份、`apothem verify --json`、零孤儿卸载 | chezmoi：`chezmoi verify` 检查每个目标；Stow：仅符号链接 | 其 README 中未说明 | `.bak` 备份和 `ruler revert`；其 README 中没有 verify 命令 |

凡是同类项目更强之处，都会点明：**rulesync** 覆盖的工具数量是 Apothem 的三倍多，同步的单元也更宽（包括权限和评审检查）；**ruler** 覆盖的工具数量接近 Apothem 的两倍，并且有自己的还原命令。Apothem 以原始工具数量为代价，换取围绕同步一并提供的治理、审计与生命周期纪律——一道合规闸门、确定性的计划与研究流水线、一座十一条命令的审计堡垒、持久记忆，以及可逆且经过验证的生命周期——而这两个同步工具都不具备这些。

## 如何比较

沿三条维度进行比较：

1. **真相来源。** 你的规则、代理、命令和设置存放在哪里？Apothem 维护一份共享语料，并从中渲染每个工具的原生格式。手工维护的配置则为每个工具保留一份副本。
2. **漂移成本。** 当你修改一条规则时会发生什么？Apothem 在运行 `apothem update` 时将变更传播到每个已安装的工具。手工维护的配置要求你分别编辑每个工具的原生文件，并凭记忆保持它们一致。
3. **验证。** 你如何知道每个工具都已正确配置？Apothem 提供 `apothem verify --harness <name>` 和 `apothem doctor`。手工维护的配置没有内置验证。

## 功能矩阵

该矩阵将 Apothem 与操作者最先想到的两种替代方案进行对照：手工维护每个工具的原生配置，以及通过通用的 dotfile 管理器管理这些文件。

| 能力 | 手工维护的配置 | dotfile 管理器 | Apothem |
| ---------- | ---------------------- | --------------- | ------- |
| 单一共享的真相来源 | 否（每个工具一份副本） | 否（追踪文件，而非配置档案） | 是（一份配置档案） |
| 渲染工具原生格式 | 手动 | 否 | 是（按适配器的物化器） |
| 跨工具的漂移防护 | 手动对齐 | 仅文件同步 | 是（`apothem update`） |
| 按工具安装/卸载 | 手动 | 部分（符号链接/复制） | 是（`install` / `uninstall`） |
| 内置验证 | 无 | 无 | 是（`verify` / `doctor`） |
| 按工具的格式翻译 | 无 | 无 | 是（`.mdc`、`.toml`、内嵌 `.md`） |
| 从一个输入到十七个工具 | 否 | 否 | 是 |
