## 载荷集合支持

状态值为 `native`、`converted`、`support-tree`、`profile-projected`、`unsupported`、`not-applicable` 和 `discovery-pending`。

`converted` 集合会被改写为工具自身的格式，而其中有些源字段没有可放置的位置。对于每个已转换的命令、智能体或规则集合，适配器的 `capabilities.yml` 都带有一个 `conversion_losses` 映射，说明每个源前置元数据字段会如何处理：

| 值 | 含义 |
| --- | --- |
| `native:<field>` | 工具在该字段下读取它。 |
| `sidecar:<path>` | 它被写入紧邻转换后文件的一个单独文件，例如 Codex 的 `agents/openai.yaml`。 |
| `filename` | 由文件名或文件夹名承载它。 |
| `inlined` | 它被移入提示词或正文文本。 |
| `ignored` | 它保留在文件中，但工具不读取它。 |
| `dropped` | 它被省略。 |

一项测试会渲染每个转换后的文件，并对照输出检查这些映射。

## 共享根目录

有些安装目标会被写入它们的那个工具以外的其他工具加载。注册表在 `SHARED_ROOTS` 中记录每个这样的路径，附带一个注册所有者（厂商为其文档化该路径的适配器）、向该路径写入相同文件的共同安装者，以及若干读取者（其厂商文档默认会加载该路径），还有显示这一点的厂商页面和这些页面的获取日期。

带有共同安装者的路径是主目录中的一个用户级文件夹，多个安装会以相同的字节写入它。一台只安装了 `Cursor` 的机器上没有 `Codex` 来写入 `~/.agents/skills/`，因此每个指定该文件夹的安装都会写入它，而安装台账会统计使用它的安装。当注册所有者使用该文件夹时，记录在案的所有者就是注册所有者，否则是使用它的最早的安装；卸载注册所有者时，什么都不会转移。只有当没有其他安装仍在使用该文件夹时，卸载才会移除它（见 [`uninstall`](/docs/cli-reference/uninstall#主目录中的共享文件夹)）。安装读取者不会在该文件夹中放入任何文件；安装所有者或共同安装者会把 Apothem 内容呈现在每个读取者面前。

| 路径 | 所有者 | 共同安装者 | 读取者 |
| --- | --- | --- | --- |
| `~/.agents/skills/` | Codex | Cursor、GitHub Copilot、Windsurf、Zed | Gemini CLI、Kimi Code、Open-Claw、OpenCode、Qwen Code |
| `~/.config/apothem/rules/` | Codex | CodeBuddy、Cursor、GitHub Copilot、Kiro、Trae、Windsurf、Zed | 无 |
| `~/.config/apothem/templates/` | Codex | CodeBuddy、Cursor、GitHub Copilot、Kiro、Trae、Windsurf、Zed | 无 |
| `~/.claude/skills/` | Claude Code | 无 | Cursor、OpenCode |
| `~/.claude/agents/` | Claude Code | 无 | Cursor |
| `~/.codex/agents/` | Codex | 无 | Cursor |
| `~/.claude/CLAUDE.md` | Claude Code | 无 | OpenCode |
| `<project>/AGENTS.md` | Kimi Code | 无 | Antigravity、CodeBuddy、Codex、Cursor、GitHub Copilot、Hermes、Kiro、OpenCode、Windsurf、Zed |
| `<project>/GEMINI.md` | Gemini CLI | 无 | Antigravity、GitHub Copilot、Zed |
| `~/.gemini/GEMINI.md` | Antigravity | 无 | Gemini CLI |
| `<project>/.github/copilot-instructions.md` | GitHub Copilot | 无 | Zed |

`~/.config/apothem/rules/` 和 `~/.config/apothem/templates/` 存放 Apothem 自身的技能和指令文件所引用的文件。没有其他工具加载它们，因此它们没有读取者，也没有厂商页面。`CodeBuddy`、`Kiro` 和 `Trae` 还会写入各自专属的技能文件夹（`~/.codebuddy/skills/`、`~/.kiro/skills/` 和 `~/.trae/skills/`）；只有对应的工具会加载它，因此它不是共享根目录。

只有当读取者的厂商文档表明会默认加载那个确切路径时，它才会被列出。有一个读取者带有条件，安装说明会重复这一点：`Open-Claw` 仅在其默认状态目录下才会索引 `~/.agents/skills/`（当 `OPENCLAW_STATE_DIR` 指向别处时，它会跳过该文件夹）。`Cursor` 文档将 `~/.codex/agents/` 列为 `Codex` 兼容文件夹，但没有说明 `Cursor` 在那里解析哪些文件格式，而 `Codex` 安装写入的是 TOML 文件，因此 `Cursor` 是否读取这些辅助智能体尚未得到确认。`Cursor` 安装还会写入自己的 `<project>/.cursor/agents/` 辅助智能体副本，厂商的优先级规则将其排在它所导入的文件夹之上，因此在已安装的项目中，原生副本会取代来自 `~/.claude/agents/` 的那一份。

有些工具被有意不列为 `~/.agents/skills/` 的读取者：`Antigravity`、`CodeBuddy`、`Kiro` 和 `Trae` 的文档没有说明它们会默认加载它（`Trae` 只有在打开某项设置之后才会加载项目的 `.agents/skills/` 文件夹），这就是 `CodeBuddy`、`Kiro` 和 `Trae` 各自获得专属技能文件夹的原因。`Hermes` 文档仅将它作为 `skills.external_dirs` 的一个示例值提及。`GitHub Copilot` 不是 `~/.claude/agents/` 的读取者：VS Code 文档为 Anthropic Claude 智能体列出了该文件夹，而不是为 `GitHub Copilot` 运行的智能体。

所有者写入共享指令文件的 Apothem 区块不会把任何单一工具指定为其读取者。当写入某个注册表目标的适配器并不恰好是其所有者及其共同安装者时，以及当某个注册表目标的名称类似跨工具指令文件（`AGENTS.md`、`CLAUDE.md`、`GEMINI.md`、`copilot-instructions.md`）却没有声明所有者时，`tests/unit/test_shared_roots.py` 都会失败。唯一的例外是 `~/.codex/AGENTS.md`，没有其他已注册的工具在其文档中说明会加载它。

## 校验钩子

注册表通过以下检查保持同步：

| 检查 | 用途 |
| --- | --- |
| `python scripts/dev/validate_harness_convention_pins.py --today YYYY-MM-DD` | 确认每个适配器都有一份约定锁定，该锁定距今不超过 90 天，至少引用一个厂商 URL，并且没有逾期的发现目标。CI 会在每个拉取请求上、每周以及发布之前运行它。 |
| `python scripts/dev/check_vendor_urls.py` | 抓取各约定锁定和工具模板所引用的每个厂商 URL，并在遇到已迁移或已失效的页面时失败，包括主机名不再能解析或证书验证失败的情况；超时、连接被拒绝或被重置，或 5xx 服务器错误会被报告为不可达，并且不会导致它失败。每周的约定监视器会运行它。 |
| `python -m apothem.conformity.gate --all .` | 运行文档与实现的合规检查。 |
| `python -m pytest` | 执行注册表夹具测试与适配器契约测试。 |
