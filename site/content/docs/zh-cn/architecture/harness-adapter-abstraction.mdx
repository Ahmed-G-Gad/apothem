Apothem 使用一份经模式校验的 YAML 配置文件作为语义层面的权威来源，
并通过实现 `HarnessAdapter` 协议的适配器类，派生出每个工具专属的安装面。
每个适配器写入该工具所记录的用户位置或项目位置，
仅当该工具没有匹配的原生原语时，才使用 Apothem 自有的支持路径。

## 为何需要适配器抽象

每个工具都说着不同的配置方言：一个想要 JSON 设置文件，
另一个想要一目录的 `.mdc` 规则文件，第三个想要一份单一的 Markdown 指令
文件。如果 Apothem 把这些知识硬编码进 CLI，每个工具都会把它的假设
泄漏进核心，而新增一个工具就意味着要同步改动安装、更新、卸载和校验
逻辑。

适配器模式颠转了这一点。核心只认识 `HarnessAdapter` 协议——一份由生命周期方法组成的小型契约。每个工具的方言都封装在一个自包含的子包中，由该子包实现这份契约。核心请求适配器执行*安装*，而不必知道这意味着渲染一个 JSON 文件、写入规则目录，还是铺设支持子树。新的工具只需满足该协议，在 `src/apothem/lib/harness_registry_data.py` 中添加一条 `HARNESS_REGISTRY` 条目（并在那里更新 `SUPPORTED_HARNESS_COUNT`），在 `pyproject.toml` 的 `apothem.harnesses` 入口点中予以镜像，并把该 ID 加入 `src/apothem/schemas/profile.schema.json` 的 `harnessId` 枚举。这正是 Apothem 保持宿主无关的结构性原因——该抽象即是那道边界，阻止工具专属的知识扩散开来。

## 适配器的形态

适配器分为两种物化形态，两者在注册表中皆可见：

- **单文件渲染器**将配置档案字段转译为一份工具原生的配置文件。例如，OpenCode 适配器通过物化器，从共享配置档案渲染其原生配置文件。
- **规则面与支持树适配器**将 Apothem 载荷集合传播到该工具所记录的规则位置，在存在原生格式时把集合转换为原生格式，并把其余部分放在从原生锚点引用的 Apothem 自有支持子树下。Cursor 适配器将单个 `.cursor/rules/apothem-rules.mdc` 写入所提供的项目根目录。在写入该文件之前，它会在用户主目录中写入两个共享文件夹：技能以及包装为技能的命令写入 `~/.agents/skills/`，而这些技能所引用的规则和模板写入 `~/.config/apothem/`。Claude Code 适配器不从配置档案渲染 `settings.json`。它将随附的设置模板复制到 `~/.claude/settings.json` 并填入钩子解释器，把 Apothem 约定目录（`agents/`、`rules/`、`skills/`、……）扁平化铺设在其旁边，并将配置档案写入 `CLAUDE.md` 中由哨兵界定的受管块。

某个给定的适配器要么是**用户作用域**（写入主目录之下），要么是
**项目作用域**（需要 `--project <path>` 并将其项目文件写入该目录树内部）；
注册表记录了它属于哪一种。有七个项目作用域适配器（cursor、github-copilot、windsurf、zed、codebuddy、kiro 和 trae）还会在用户主目录中写入共享文件夹，例如 `~/.agents/skills/` 和 `~/.config/apothem/`，而 `--project` 不会改变这些文件夹的写入位置。

## 协议定义

```python
from pathlib import Path
from typing import Protocol

class HarnessAdapter(Protocol):
    name: str
    output_path: Path

    def install(self, profile: dict[str, object]) -> object:
        ...

    def update(self, profile: dict[str, object]) -> object:
        ...

    def uninstall(self) -> None:
        ...

    def is_installed(self) -> bool:
        ...

    def verify(self) -> bool:
        ...
```

项目作用域适配器还可以在生命周期方法上额外接受 `project: Path | None`，
并暴露 `resolve_output_path(project)`。CLI 仅向方法签名接受
`--project PATH` 的适配器传入该参数。

## 入口点注册

适配器通过 `apothem.harnesses` setuptools 入口点分组进行注册：

```toml
[project.entry-points."apothem.harnesses"]
cursor = "apothem.harnesses.cursor:CursorAdapter"
```

位于 `src/apothem/lib/harness_registry.py` 的中央注册表记录了精确的
十七个公开 ID、入口点、文档路径、目标路径、包数据
要求、能力状态以及标准约定固定路径。CLI
通过该注册表加载适配器，而不是在每个命令中重新发现产品事实。

## 配置文件到原生的映射

每个适配器实现与其工具相适配的转译逻辑：

```
YAML profile + payload cohort    Harness-native surface
-----------------------------    ----------------------
identity / preferences       --> native config fields or rendered instruction context
commands/*.md                --> native commands or SKILL.md folders
rules/*.md                   --> native rules where supported, otherwise support trees
hooks/messages/*.md          --> native hooks where supported, otherwise support trees
agents/*.md                  --> native agent formats where supported
skills/*/SKILL.md            --> native skill folders where supported
```

不受支持和待发现的能力单元会在写入前变成结构化警告。
它们不会被静默地投射进臆造的供应商面。
