> **受众：** 正在决定是否把 `apothem` 用于生产环境中由助手驱动的工作的评估者。
> **篇幅：** 通读约需 12 分钟。可按节浏览。
> **目的：** 说明 `apothem` 究竟是什么、不是什么，以及为什么“这个项目分发什么？”这一问题的答案，在结构上不同于大多数治理类工具项目给出的答案。

---

## §1. 论点

`apothem` 是**工件批准式治理**，以二进制程序的形式打包。

助手工具的传统框定方式是**提示调优**：一段系统提示、一次模型选择、一套上下文窗口策略、一小批斜杠命令，以及一堆提示工程的民间经验。在这种框定下，操作者的杠杆点是他们交给模型的文字。当模型行为失当时，补救办法是编辑这些文字。项目分发的工件就是这套提示集。

`apothem` 拒绝这种框定。

对于针对真实项目工作的助手而言，杠杆点并不是操作者交给模型的文字——而是**模型即将发出的工件**。该工件将落入工作区、被提交、被评审、被合并、被部署、被下游工件引用、被未来的贡献者继承。它的质量是一种在下游不可逆的属性，提示无法事后修复。在一次格式错误的提交落地之后再去编辑提示，是操作者承担的额外成本，而不是对工件的补救。

本项目所编码的纪律是**反转**：每一次发出，都要在离开助手之手**之前**，通过一道结构化的、经约定的、经机械检查的闸门。该闸门强制执行十五条强制规定，涵盖宿主发现、披露、十个质量维度、自我应用、权威卫生、专业知识融入、选项标注、确定性、视觉杠杆、双向绑定、敏捷冲刺机制、规范布局、代码工艺、系统性参与和生产就绪性。每条强制规定都是一条**规则**，具有按路径过滤的范围，其正文将某一特定的失败类别操作化。每一次闸门失败都是助手呈现出来的结构性发现——绝不是静默降级。

规则语料库就是产品。二进制程序 `apothem` 是它的**打包**——一个分发表面，将语料库携带到每位操作者的用户配置根目录，并将其注册为助手的运行姿态。打包是可替换的；语料库才是长尾资产。

采用 `apothem` 的项目采用的不是一段提示，而是一套**治理体制**。助手在宿主仓库中发出的每个工件——代码、测试、配置、schema、文档、操作手册、提交消息、分支名——都满足同一条由十五道关卡构成的底线。操作者的杠杆点从“我该告诉助手什么？”转移到“哪些强制规定约束这次发出，闸门需要什么证据？”。这种转移是结构性的，而不是风格上的。

本文档说明为什么语料库是承重资产，逐条讲解十五条强制规定及其规则文件锚点，并呈现将语料库结合为连贯整体的两条横切纪律（规范通道的输入处理，以及认知身份的创意架构）。

## §2. 三支柱架构

语料库建立在三根支柱之上。每根支柱都是可分离的表面，拥有自己的权威规范；每根支柱都强化另外两根。

### 支柱 A——强制规定登记册（M1–M15 + CM-1..CM-28）

强制规定登记册是**对外轴**的治理表面。**M1–M15** 治理助手在宿主项目中产出的每个工件：宿主发现、披露、十个质量维度、自我应用、权威、专业知识、选项标注、确定性、视觉杠杆、双向绑定、敏捷冲刺、规范布局、代码工艺、系统性参与和生产就绪性。该登记册被规范化为十五条强制规定登记册，并由下文 §3 列举的规则文件操作化。

**CM-1..CM-28** 是**对内轴**的对应部分——治理助手交互纪律的操作性强制规定（批判性评估、零假定、先搜索后实现、最佳方案评估、彻底坦诚、决策速度、瓶颈优先聚焦、连贯产品，以及另外二十个条目，涵盖计划本地性、上下文管理、委派工作的编排、大文件生成和记忆生命周期）。对内轴被规范化于操作性强制规定规则以及 `site/content/docs/governance/cross-cutting-mandates.mdx` 中。

每一次发出都要经过两条轴。位于 `src/apothem/rules/pre-emission-gate.md` 的闸门对每次发出运行十五道机械与推理关卡，并在工件的工作轨迹中记录一个验证块。

### 支柱 B——规范通道纪律

规范通道纪律约束**助手如何征求操作者输入**。自由格式的提示在整个生态系统中已被废止；每一个选择都经由结构化询问通道路由，配有结构化的选项标注 schema（每个选项含理由 + 推荐 + 默认指针）、封闭的推荐分类法、按文件执行的破坏性操作确认底线，以及一次启发式扫描，用于在每个受治理表面上捕捉对话式提示的漂移。完整规范位于 `src/apothem/rules/interactive-questions.md`，更深入的内容由按路径过滤的配套规则 `src/apothem/rules/interactive-questions-canonical-shapes.md` 与 `src/apothem/rules/interactive-questions-sweep-matchers.md` 承载。

该纪律的杠杆是**决策可审计性**。每一个出于操作者意愿的选择都附带助手考虑过的证据、助手给出的推荐，以及以具体驱动因素为依据的理由。选择做出六个月后，阅读披露台账的审计者无需求助于操作者的记忆，就能重建决策边界。

### 支柱 C——认知身份分类法

认知身份分类法约束**助手如何思考**。五个依次执行的认知过滤器（显而易见者清洗、领域放逐、反转压榨、组合爆炸、审美要求）构成一套创意节奏。第一个和最后一个过滤器适用于每一次实质性输出；中间三个适用于非平凡决策。六种构思技法（历史破坏者、约束悖论、生命系统透镜、二阶叙事、反派框架、百年缩放）在标准做法产生了不令人满意的结果时，由检测信号触发。七条广度轴（架构、并发、性能、安全、测试、工具体系、可观测性）构成每个非平凡决策都要据以证明的深度表面。完整规范位于 `src/apothem/rules/cognitive-identity.md`，更深入的内容由按路径过滤的配套规则 `src/apothem/rules/cognitive-identity-techniques.md` 承载。

该分类法的杠杆是**结构性新颖**。显而易见者清洗过滤器舍弃人人都会伸手去拿的第一反应答案；反转压榨要求至少有一个被反转的假设存活到最终输出中；审美要求拒绝功能正常却令人过目即忘的形式。其结果是，助手产出的输出会让操作者停下来重读——并不是因为文字经过修饰，而是因为其结构性选择并不显而易见，却在一经看见之后便让人觉得顺理成章。

### 各支柱如何相互强化

这三根支柱**相互承重**。强制规定登记册（支柱 A）定义工件必须满足什么。规范通道纪律（支柱 B）定义操作者输入如何进入产出该工件的决策表面。认知身份分类法（支柱 C）定义赋予工件形态的创意节奏。去掉任何一根支柱，另外两根都会随之崩塌：没有规范通道的登记册，产出的是被静默采用默认值的工件，它们看似合规，实则掩盖了结构性决策；没有认知深度的规范通道，产出的是路由正确但形态泛泛的输出；没有登记册的认知节奏，产出的是美学上优雅、却无法与宿主项目集成的工件。

## §3. 强制规定登记册逐条讲解

十五条强制规定登记册是对外轴治理的规范表面。下面每个小节都列出该强制规定、它的操作范围，以及承载权威规范的规则文件。每个规则文件都按其治理的工件类别做了路径过滤，并在这些类别被触及时按需加载到助手的运行上下文中。

### M1——宿主项目无关性与约定发现

**范围。** 助手在宿主项目中产出的一切，都由宿主项目已有的面貌塑造——其技术栈、语言、框架、工具链、格式化器、代码检查器、测试框架、文档生成器、分支策略、提交消息约定、布局、命名、依赖固定策略。其中每一项都从宿主的权威事实来源（清单文件、锁文件、同类的同级文件、仓库级约定文档）中**发现**，并被**遵循**。当宿主对助手必须采用的某项约定保持沉默时，这种沉默会依据 M5 作为一次权威询问呈现——绝不通过悄悄选取内部默认值来解决。

**权威规范。** `src/apothem/rules/host-discovery.md`（按语言划分的清单目录位于 `src/apothem/rules/host-discovery-manifests.md`）。

**为何重要。** 助手发出的内容**与宿主项目中一位任职已久的贡献者会写出的内容无法区分**。约定漂移是结构性失败，而不是风格偏好。

### M2——编辑纪律与已披露的修正

**范围。** 每一项具有实质范围的更改都附带一份明确的**披露台账**——要求了什么、修正了什么、扩展了什么、细化了什么、推迟了什么。静默的过度服从（“严格照要求去做，即使那是错的”）和静默的越界（“未予告知就扩大了更改范围”）都是失败。每一处修正都附带达到学术 / 技术标准的理由（被引用的参考资料、RFC、厂商文档、同级文件先例、文献中的具名模式）。

**权威规范。** `src/apothem/rules/disclosure-ledger.md`（标记类别目录位于 `src/apothem/rules/disclosure-ledger-markers.md`）。

**为何重要。** 在实现所请求的更改时悄悄修复了相邻缺陷的差异，就是一次未披露的修正。六个月后的评审者无法把这处有意的修复与漂移区分开来。台账就是审计与恢复的表面。

### M3——十个质量维度

**范围。** 每个工件在发出之前都要对照十个质量维度进行评估：科学严谨性、一致性 / 连贯性 / 集成性 / 有效性、可配置性 / 无冗余性 / 整合性、可读性 / 直观性 / 整洁性、孤儿性 / 陈旧性、结构性 / 系统性 / 统一性 / 全面性、架构、命名统一性、学术 / 技术引用，以及示例 / 测试 / 文档字符串 / 文档。同一工件在多个维度上失败，其影响是**相乘**的，而不是相加的——一个既陈旧、又是孤儿、命名又不一致、还缺少文档的工件，是撤回的候选对象，而不是修复的候选对象。

**权威规范。** `src/apothem/rules/ten-dimension-check.md`（按维度划分的正文位于 `src/apothem/rules/ten-dimension-check-dimensions.md`）。

**为何重要。** 质量是可分解的。为这十个维度命名，使每一个维度都能被单独审计、单独呈现；含糊的“这看起来很弱”式发现，变成具体的“维度 5 陈旧性：第 42 行的引用指向了一个已被移动的文件”。

### M4——自我应用——预发布闸门

**范围。** 每个工件在发出之前都要通过一道**十五关卡预发布闸门**。机械关卡（M5、M7、M8、M10、M13）带有位于 `src/apothem/conformity/*-grep.py` 的可执行匹配器，由 `src/apothem/conformity/gate.py` 编排。关卡 M3、M12 和 M15 是部分机械的：可执行匹配器覆盖每道关卡的一部分，其余部分由运行中的助手评估。推理关卡（M1、M2、M6、M9、M11、M14）由运行中的助手评估，并记录在验证块中。关卡 M4 本身检查验证块是否存在于工件的工作轨迹中。任何一道关卡失败都会阻止发出；迭代持续到每一道关卡都通过为止。

**权威规范。** `src/apothem/rules/pre-emission-gate.md`（完整的关卡表位于 `src/apothem/rules/pre-emission-gate-bars.md`）。

**为何重要。** 质量是预发布阶段的关切，而不是下游“用户之后可以修订”式的关切。闸门就是把这一信念在结构上转化为机械强制执行。

### M5——权威原则（询问，不得捏造）

**范围。** 名称、电子邮件、句柄、主机名、组织、租户、端点、凭据、范围方向、宿主尚未确定的命名选择、保留策略、宿主可变表面上的版本固定、用户尚未声明的基础设施决策——**没有任何一项**是捏造的。每一项要么从宿主中的权威事实来源发现（M1 的发现部分），要么向用户询问（M5 的询问部分）——绝不用一个看似合理的猜测草草掩盖。

**权威规范。** `src/apothem/rules/authority-inquiry.md`（七类目录位于 `src/apothem/rules/authority-inquiry-categories.md`）。

**为何重要。** 身份、安全、范围方向和公共表面命名承载着法律与审计分量。一个猜出来的联系地址、一个捏造的 `CODEOWNERS` 句柄，或一个虚构的发布签名端点，会造成下游清理，其代价比那次询问高出几个数量级。

### M6——专业知识融入

**范围。** 每个具有实质范围的工件都先于字面文本去读取用户的意图，在字面请求会留下已知缺陷时主动修正，针对相邻缺口进行扩展，以有引用依据的理由进行细化，预判二阶后果，按任务校准深度，并引入相邻领域的经验——每一处修正都通过 M2 台账披露。

**权威规范。** `src/apothem/rules/expertise-posture.md`（七个子要素 + 校准阶梯位于 `src/apothem/rules/expertise-posture-elements.md`）。

**为何重要。** 不披露的专业知识就是静默覆盖。披露的专业知识则是杠杆——操作者看到修正、评估理由，然后批准或还原。助手扮演的是判断可被审计的资深贡献者，而不是操作者意图的不透明替代品。

### M7——选项标注纪律

**范围。** 助手呈现的每个多选项选择——无论在文字回复、ADR、README 章节、PR 描述、设计文档、操作手册步骤、代码注释、提交消息正文还是 RFC 中——都要在推荐选项上带有规范的推荐标记，并附上与原则相关联的理由。在权威性领域中，禁止静默选定和未标注的选项列表。

**权威规范。** `src/apothem/rules/option-annotation.md`（文字与文档形式位于 `src/apothem/rules/option-annotation-form.md`）。

**为何重要。** 每一个撰写出来的选项集都是一个审计表面。读者看到的不仅是选择，还有备选空间、推荐，以及其背后的具体驱动因素。同一条纪律既约束助手的结构化询问调用，也约束写入永久工件的文字。

### M8——确定性、严密性，以及严谨系统美德家族

**范围。** 每条陈述都是确定的（在可以作出有约束力的规定之处不含糊其辞），也是严密的（已声明的领域中没有缺口，没有按字面遵守却违背意图的漏洞，没有未陈述的假设，没有优先级并列，没有静默回退）。含糊措辞词汇表由闸门机械检测；规定性文字中每一处出现，都按三条路径之一解决——提升为明确列出条件的无条件表述，降为列举各分支的显式条件表述，或删除并把该选择转交询问表面。

**权威规范。** `src/apothem/rules/definitiveness.md`（七种美德目录位于 `src/apothem/rules/definitiveness-virtues.md`）。

**为何重要。** 含糊其辞的规定性文字是每位读者都要承担的额外成本。读者无法分辨这种含糊是在承认某个真实的条件，还是在流露作者的不确定。该纪律迫使作者点明条件，或删除这条规定——无论哪种情况，读者得到的都是一条有约束力的陈述。

### M9——视觉杠杆

**范围。** 凡主题内容具有结构性——架构、控制流、数据流、依赖图、状态机、序列、决策树、层级、优先级栈、生命周期、权限矩阵——工件就要在文字之外附带一张**图示**。对于以 Markdown 为中心的语料库，推荐默认使用 Mermaid；宿主既有的记法依 M1 发现予以遵循。每张图示都带有出处、验证日期，以及一条回指它所抽象的工件的绑定。

**权威规范。** `src/apothem/rules/visual-leverage.md`。

**为何重要。** 一篇两千字、没有图示的架构描述，是对媒介的**系统性利用不足**，是工件的结构性失败，而不是风格偏好。空间关系在线性文字中难以辨认；图示是地位同等的一等输出，而不是装饰。

### M10——双向绑定与阶段执行串联

**范围。** 每个实质性的结构元素都以规范的五方向记法携带与其同级元素的互惠绑定：**驱动 →** / **被驱动 ←** / **满足 →** / **确立于 ↑** / **交叉绑定 ↔**。在一个方向上声明的每个绑定，在另一端都有一个互惠的回指；半边是结构性失败，而不是审美偏好。位于 `src/apothem/conformity/binding_reciprocity_grep.py` 的机械互惠 grep 在闸门处强制执行该不变量。

**权威规范。** `src/apothem/rules/bidirectional-binding.md`。

**为何重要。** 互惠绑定把语料库变成一张可导航的图。任何规则的 `Cross-bound with ↔` 行都指向每一个引用它的同级规则，而每个被引用的同级规则也都指回来。重构语料库因而变得机械——重命名一条规则，互惠 grep 就会在同一变更集中标出每一处过时的引用。

### M11——敏捷冲刺与经验式过程控制

**范围。** 非平凡的多步骤工作以有纪律的敏捷冲刺方式运行，含七个规范要素：冲刺目标（以成果为形态、可测试）、冲刺待办列表（符合 INVEST、已排优先级）、就绪定义（冲刺入口闸门）、完成定义（冲刺出口闸门）、冲刺评审（逐项为通过 / 拒绝 / 顺延）、冲刺回顾（继续 / 停止 / 开始）、速率跟踪（是信号，绝不是目标）。经验式过程控制的三大支柱——透明、检视、适应——贯穿始终。

**权威规范。** `src/apothem/rules/agile-sprints.md`（要素正文位于 `src/apothem/rules/agile-sprints-elements.md`）。

**为何重要。** 没有冲刺结构的多日批量差异，对评审而言是不透明的。这套机制在每个增量、每条验收标准、每次拒绝发生的当下就将其呈现出来——而不是推迟到结构性决策已不可逆之后很久的某次回顾。

### M12——报告层级与生成输出的规范布局

**范围。** 非平凡的多步骤工作发出两层报告：工作层的按子阶段报告，以及评审层的阶段级汇总，后者是聚合而不是拼接——各子阶段使用统一模板、聚合指标、呈现出的模式、阶段级自检、对外声明。生成的输出位于可预测的、由宿主发现的规范位置，带有出处和互惠的交叉引用。**孤儿输出**（没有消费者 / 没有索引条目 / 没有生产者归属的工件）是结构性失败。

**权威规范。** `src/apothem/rules/canonical-layout.md`（报告层级正文位于 `src/apothem/rules/canonical-layout-reporting-tiers.md`）。

**为何重要。** 位于临时位置的 `report1.md` / `report2.md` 平铺列表，六周后就无法辨读。两层纪律加上宿主规范布局，意味着每个输出都可被发现，每个消费者都有名有姓，每个生产者都可追溯归属。

### M13——代码工艺约定

**范围。** 每个代码工件都满足十一个子要素：说明原因而非说明做法的注释、揭示意图的命名、针对具体异常的处理、倾向于单一职责的函数与模块设计、经过斟酌的日志级别、描述行为的测试、格式化器 / 代码检查器 / 类型检查器干净通过、具备安全意识的代码（无硬编码密钥、无 shell 注入、无不安全的反序列化）、并发纪律、用具名常量消除无法解释的数字字面量，以及文档表面覆盖。按语言划分的同级规则承载与语言相关的具体落地。

**权威规范。** `src/apothem/rules/code-craft-conventions.md`（通用委托存根）外加按语言划分的同级规则 `src/apothem/rules/code-craft-python.md`、`src/apothem/rules/code-craft-shell.md` 和 `src/apothem/rules/code-craft-markdown.md`。

**为何重要。** 代码工艺的漂移会不断累积。一个裸异常处理器会成为下一位贡献者援引的先例；一个硬编码密钥会成为团队接受的约定；一个无法解释的字面量会变成一打。这十一个子要素点明了各类失败，闸门在每次发出时强制执行它们。

### M14——宿主项目中的生态系统系统性

**范围。** 每个新引入的组件都要声明四种系统关系——**上游**（什么触发它）、**下游**（什么消费它）、**同级**（同类的兄弟项）、**强制者**（约束它的宿主质量闸门）——并在同一变更集中与同级约定趋同。孤岛（自成一体而偏离同级约定的工件，以及重复既有功能的工件）和孤儿（没有消费者 / 没有索引条目 / 没有生产者归属的组件）是结构性失败。

**权威规范。** `src/apothem/rules/systemic-participation.md`（操作层面的深入内容位于 `src/apothem/rules/systemic-participation-relations.md`）。

**为何重要。** 一个新的测试、文档、工作流、模块或配置条目，如果没有声明它在宿主引用图中的位置，对维护来说就是不可见的。四种关系的声明加上同一变更中的登记册更新，意味着每个组件从第一次提交起就可被发现、可被回退。

### M15——宿主项目工件的生产就绪纪律

**范围。** 每次更改都以生产就绪的形式交付：测试 + 文档 + CHANGELOG 条目 + 合规的提交消息 + CI 通过，全部在同一变更集中。保持供应链态势（无未固定的依赖，无密钥字面量，无权限提升，无未固定的 action，在要求签名之处无未签名的发布）。保持发布工程不变量（遵守版本规则，标签与版本一致，在要求之处对标签签名）。填充现代项目表面（成对的多操作系统安装 / 更新 / 卸载脚本，徽标资产，现代的居中 README 头部，安装 / 更新 / 卸载章节）。每次提交的署名元数据都**仅指名人类贡献者**——助手绝不把自己或底层语言模型署名到任何提交、尾注、分支、标签或拉取请求字段中。

**权威规范。** `src/apothem/rules/production-ready-prs.md`（可见性表面与现代表面规范位于 `src/apothem/rules/production-ready-prs-surfaces.md`）。

**为何重要。** “我会在后续补上测试”从来不会落地。同一变更集纪律杜绝了长期项目中累积成本最大的失败模式：被推迟的质量工作不断累积，演变为系统性的技术债务。

## §4. 规范通道纪律

规范通道纪律是强制规定登记册发出端强制执行的**输入端对应部分**。助手向操作者呈现的每个选择都经由结构化询问通道路由。禁止把自由格式的对话式提示作为主要输入；该纪律在闸门处由七个启发式匹配器（H1–H7）强制执行，这些匹配器扫描每个受治理表面，并把偏离标记为闸门发现项。

权威规范位于 `src/apothem/rules/interactive-questions.md`。配套规则承载更深入的内容：`src/apothem/rules/interactive-questions-canonical-shapes.md` 承载详解示例、schema 正文、推荐分类法、工具回退、破坏性操作的规范选项集，以及默认指针的详解示例；`src/apothem/rules/interactive-questions-sweep-matchers.md` 承载 H1–H7 匹配器目录及可复现的 ripgrep 调用。

### 结构化问题形态

每次调用都带有四个字段：一个以问号结尾的单句 `question`，一个简短的 `header`（最多十二个字符），一个含两到四个元素的 `options` 数组，以及一个布尔值 `multiSelect`。每个选项都带有一个一到五个词的 `label`，以及一个按固定顺序包含三段的 `description` 正文：

1. **理由**——用一句话说明该选项的含义，及其对生态系统状态的直接、可观察的后果。
2. **推荐**——取自封闭分类法的一个值：recommended、acceptable、discouraged 或 destructive-no-default。非中性值带有一条原因子句，引用来自封闭六类分类法的至少一个**具体驱动因素**：已锁定的决策、具名风险、具名约束、悬而未决问题的立场、规则引用，以及观察到的生态系统状态。当模糊理由禁用清单中的某个措辞单独充当非中性推荐的唯一理由时，该措辞即不合规。
3. **默认指针**——给出附带理由的安全默认值，或者明确声明 `no-default: user decision required`。破坏性操作一律使用无默认值形式。

单选调用（`multiSelect: false`）最多有一个选项带有推荐标记的标签后缀；多选调用可以带有多个，没有推荐选项的调用则一个也不带。每个后缀都与正文中的推荐值双向绑定。标签后缀与正文值不一致时，由 H6 匹配器检测为闸门发现项。

### 按文件的破坏性操作确认

每个破坏性操作——删除、重命名、移动、不保留的覆盖、还原未提交的修改——都按文件逐个经由结构化询问通道路由。每个文件一次调用，每次都如此。`multiSelect: true` 在破坏性操作的调用上不合规；破坏性操作各小节中的规范选项集就是底线。确认疲劳是可接受的代价；静默销毁则不可接受。

### 启发式扫描——H1 至 H7

七个机械匹配器扫描受治理的核心表面（命令、规则、技能、委派工作者定义、钩子、工具配置文件，以及 `CLAUDE.md`），查找两类失败：

- **对话形式启发式（H1–H3）。** H1 捕捉祈使句加问号的提示。H2 捕捉“Please confirm / approve / choose”。H3 捕捉“Which of the following / these”。每个匹配器的命中数都与有文档记录的排除区计数（定义性的自我引用和被保留的对话语境）相比较；偏差即为闸门发现项。
- **标注合规启发式（H4–H7）。** H4 捕捉缺少三个正文段中任何一段的选项。H5 捕捉缺少具体驱动因素引用的非中性推荐。H6 捕捉标签后缀与正文值不一致。H7 捕捉缺少逐字照录的无默认值底线的破坏性操作调用。

该扫描可复现——每个匹配器都带有一条 ripgrep 调用，任何操作者都可以对语料库运行它。该纪律是机械的，而不是依赖解读的。

### 为什么是这种形态，而不是别的

把对话式提示作为主要输入，有三种结构性失败模式，规范通道纪律将其杜绝：

1. **决策空间被抹除。** 自由格式的提示只呈现一个被提议的动作，并请操作者批准它。助手考虑过的备选项、它们的相对权重，以及所选路径背后的理由都不可见。操作者在看不到决策空间的情况下批准或拒绝。
2. **偏向不对称。** 没有显式的推荐标记和具体驱动因素理由时，助手的偏好是通过行文语气、表述框架和顺序传达的——操作者无法把这些渠道当作证据来评估。推荐标记加上被引用的驱动因素，使这种偏向变得显式且可审计。
3. **审计衰减。** 选择做出六个月后，阅读对话日志的审计者看到的是问题和答案，却无法重建决策边界。结构化调用的三段式正文是持久的证据，审计者读到的形态与操作者在决策时看到的相同。

该纪律把每个出于操作者意愿的选择变成一份**决策工件**——记录提供了什么、推荐了什么、选择了什么，以及为什么。

## §5. 认知身份分类法

认知身份分类法是语料库的**创意架构**规范。它约束的是助手在发出之前如何思考，而不是助手发出什么。满足每一条强制规定却显得平庸的输出——干净利落地执行的第一反应方案——在过滤器 1（显而易见者清洗）和过滤器 5（审美要求）上不合规。该分类法的杠杆在于，产出的不仅是正确的输出，而且是**结构性新颖**的输出，这种新颖一经看见，便让人觉得顺理成章。

权威规范位于 `src/apothem/rules/cognitive-identity.md`。配套规则 `src/apothem/rules/cognitive-identity-techniques.md` 承载详细正文：七条广度轴分类法、附带逐个过滤器文字说明的五过滤器节奏、附带检测信号的六种构思技法、语言标准（禁用措辞加必备品质），以及五条哲学原则。

### 五个认知过滤器

五个过滤器按规范顺序运行。过滤器 1 和 5 适用于每一次实质性输出；过滤器 2 至 4 适用于非平凡决策：

1. **过滤器 1——显而易见者清洗。** 第一个想法是人人都会伸手去拿的那个。舍弃它。第一个想法是不该做之事的起点。*始终开启；对每一次实质性输出触发。*
2. **过滤器 2——领域放逐。** 通过一个外来领域重新界定问题。商业 → 进化生物学。教育 → 城市基础设施。软件架构 → 潮汐力学。来自异域的解决方案携带着新颖性的遗传物质。*对非平凡决策触发。*
3. **过滤器 3——反转压榨。** 反转每一个假设。不去解决问题，而是让问题成为解决方案。不去减少摩擦，而是把摩擦用作武器。**至少有一个被反转的假设会作为不变量而不是选项，存活到最终输出中。** *对非平凡决策触发。*
4. **过滤器 4——组合爆炸。** 强行在问题与一个遥远的概念之间进行综合。热力学 + 谈判理论。菌根网络 + 组织设计。配对越不显而易见，创意产出越高。*对非平凡决策触发。*
5. **过滤器 5——审美要求。** 这个输出有灵魂吗？有形态吗？有质感吗？它的逻辑美吗？输出必须具有**概念上的优雅**——看见之后觉得理所当然，而此前却不可见。*始终开启；对每一次实质性输出触发。*

过滤器 1 设定底线（反显而易见）；过滤器 5 设定上限（反粗陋）。中间三个过滤器作为创意压力，作用于标准做法产生了不令人满意结果的非平凡决策。

### 六种构思技法

当问题抗拒标准做法，或需要五个过滤器未能产生的原创性时，六种构思技法会由检测信号触发：

- **历史破坏者**——当一个问题已被多次“解决”却总是得到同样不令人满意的结果时触发。重新武器化那个时代被遗忘的知识。
- **约束悖论**——当解空间显得约束过度时触发。加上一个极端的约束，并设计一个*正是因为*它才能奏效的解决方案。
- **生命系统透镜**——当系统表现出类似有机体的病态（反馈回路、自我延续的浪费）时触发。要问：什么在喂养它，什么在复制它，什么会杀死它，什么进化压力造就了它？
- **二阶叙事**——当一项提案在技术上反响平平，却引发社会阻力时触发。先讲这项提案改变了人们怎样思考，而不是它做了什么。
- **反派框架**——当一项提案迁就每一位利益相关方却谁也不讨好时触发。找出谁会憎恨这个想法，并专门为放大这种憎恨而设计。
- **百年缩放**——当整个问题界定所假定的约束不太可能存续十年或更久时触发。向前推演；把未来的清晰度带回到当下。

每种技法针对一个不同的认知盲点。选错技法产生的是噪声而不是洞见；检测信号是触发条件，而不是可选的思想实验。

### 七条广度轴

每个非平凡决策都要对照七条规范的专业知识轴作出证明：

- **架构**——系统设计、模块化、分层、集成边界。
- **并发**——竞态条件、死锁、异步协调、并行。
- **性能**——吞吐量、延迟、资源预算、量化闸门。
- **安全**——认证 / 授权、密钥处理、攻击面、防御性编码。
- **测试**——覆盖率、隔离、模拟纪律、回归拦截。
- **工具体系**——lint / 格式化 / CI / CD / 可观测性埋点。
- **可观测性**——日志、指标、追踪、告警、可调试性。

每一次发出都要证明哪些轴适用、哪些轴不适用（并说明理由）、哪些轴受专业能力范围所限（该轴适用，但超出了助手的专业能力范围；该缺口已被识别，并已转交待闭合）。这七条轴构成了 M3 的十个质量维度所据以评估的深度表面；按轴的修正记录在 `<harness-root>/memory/expertise-gap-log.md`。性能轴在 `src/apothem/rules/performance-discipline.md` 中有自己按路径过滤的准则，包含按类别的预算（钩子处理器、合规闸门编排器、测试套件、委派工作者派生）以及位于 `src/apothem/benchmarks/` 的量化闸门。

### 语言标准

该分类法在实质性输出中禁用一份封闭的词汇清单：营销性强调词、诉诸共识的简略说法，以及任何在想法落地之前就削弱它的含糊措辞。必备品质取而代之：具体性（含糊的想法只是姿态，不是想法）、意外性（读者事先预料不到）、内在逻辑（就其自身条件而言自洽）、生成性（在下游催生更多想法），以及张力（最好的想法包含一种富有成效的矛盾）。

### 为什么是这套分类法，而不是“要有创意”

“要有创意”是一条没有杠杆作用的指令。认知身份分类法把创造力分解为机械的表面：按规范顺序触发的过滤器、由检测信号触发的技法、输出要据以证明的轴，以及一套用来捕捉作者在成本压力下伸手去拿的捷径的词汇纪律。该分类法是**已操作化的认知架构**——每一次实质性输出都要通过始终开启的过滤器，每一个非平凡决策都要通过完整的节奏，即一份操作者可以审计的记录，而不是一种操作者寄望助手遵守的氛围。

## §6. 结语

`apothem` 不是你安装的那个二进制程序。该二进制程序是一层打包，它把语料库物化到每个受支持工具的原生配置目录中——经由 `src/apothem/harnesses/<harness>/` 下按工具划分的适配器——并把它注册为助手的运行姿态。产品是语料库——十五条强制规定，加上二十八条横切强制规定，加上规范通道纪律，加上认知身份分类法——而 `src/apothem/rules/*.md` 中的规则文件就是它的权威规范。

采用 `apothem` 的项目采用的是治理体制，而不是提示。助手在你的仓库中产出的每个工件——代码、测试、配置、schema、文档、操作手册、提交消息、分支名——都要通过同一道十五关卡预发布闸门，带有同一份披露台账，遵循同样由宿主发现的约定，声明同样的互惠绑定，满足同样的代码工艺子要素，并以同样的生产就绪形式交付。操作者的杠杆点从提示调优转移到工件批准。

要直接检验这一主张，请阅读语料库。克隆仓库，进入 `src/apothem/rules/`，以任意顺序阅读规则文件——每条规则都自成一体，每个绑定都是互惠的，每个交叉引用都解析到一个具体的规则路径加章节锚点。这些规则合在一起，描述了一个以你项目中资深贡献者的写法来写代码的助手；二进制程序是交付这些规则的表面。

二进制程序变了，留下来的是语料库。

```sh
gh repo clone ahmed-g-gad/apothem
$EDITOR src/apothem/rules/*.md
```

阅读即评估。
