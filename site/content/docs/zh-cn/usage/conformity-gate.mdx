位于 `src/apothem/conformity/gate.py` 的合规闸门会针对操作者编写的每个工件，运行十五道预发布闸门关卡（M1-M15）中的机械部分。

本页上的命令假定位于 Apothem 检出中，因此请在你运行的每条命令前加上 `PYTHONPATH=src`。脚本安装之后，请使用 `PYTHONPATH="$HOME/.apothem/src"` 替代 `PYTHONPATH=src`。

## 运行闸门

闸门**默认为建议性**：它报告发现项并以 `0` 退出，因此本地运行绝不会阻塞你。添加 `--strict`（或设置 `APOTHEM_CONFORMITY_STRICT=1`），即可在出现阻断性发现项时以非零状态退出——CI 和 pre-commit 正是使用这种模式让违规的变更失败。

```bash
# Advisory: report every validator's findings across the repo, exit 0
PYTHONPATH=src python -m apothem.conformity.gate --all .

# Strict: exit non-zero (code 2) when a blocking finding is present
PYTHONPATH=src python -m apothem.conformity.gate --all --strict .
```

退出码：`0` 表示干净（或建议性模式），`2` 表示严格模式下的发现项阻断，`3` 表示用法错误：未知的标志或校验器名称、不存在的文件，或不存在的根目录。`--help` 打印完整用法并以 `0` 退出。每个独立校验器都接受同样的 `--help`，并在遇到未知标志或缺失的根目录时以 `3` 退出。

诸如 `.` 的相对根目录会在任何校验器运行之前被解析为绝对路径，因此 `--all .` 和 `--all "$PWD"` 检查的是同一棵树。每个校验器都会报告 `inspected`——即它检查了多少个目标——而 `--all` 会将该计数复制到每个结果条目中。未检查任何内容的校验器会报告 `passed: false`，因此错误的工作目录不会无声地通过。两个计划套件校验器是其中一种例外：计划套件位于被 git 忽略的 `.apothem/plans/` 树中，因此它们在干净的检出上报告 `empty_scope_expected: true` 并仍然通过。当项目还没有 `.github/workflows/` 目录时，工作流校验器也会这样做；当根目录没有提交历史时，提交主题校验器也会这样做。

项目可能带有他人制作的文件，来自压缩包或共享文件夹，因此每个 `--all` 校验器只打开和列出它经由根目录下的真实文件夹到达的普通文件和真实文件夹。它从不跟随符号链接，在 Windows 上也从不跟随联接点（junction），并且在根目录下的任何层级都把以下各项视为不存在：

- 链接，即使它指向根目录内部。遍历或文件夹列表会跳过它，因此它指向的内容只在校验器经由其自身路径到达时才会被检查；
- 命名管道、设备或套接字，对它们的读取会一直等待或永不结束；
- 在 Windows 上，以点或空格结尾的名称，因为 Windows 会以该名称打开另一个条目。

少数检查仍会使用链接，但不进入其中：

- 对于作为符号链接的固定文件，例如指向另一个文件的 `CLAUDE.md`，gate 会读取链接本身的文本，并且只有当它指向的是项目内、经由真实文件夹到达的普通文件时才会打开该文件。每个文件夹的 `README.md` 链接也按同样方式计算。绝对链接在经由解析后的项目文件夹写成时有效，在 Windows 上经由大小写不同的同一路径写成时也有效；单独运行的校验器还接受你键入的文件夹形式，除非该路径包含 `..`，而 gate 会在启动每个校验器之前解析该文件夹。被链接的 `.gitattributes` 仍被视为不存在，因为 git 不会读取它；
- `no-global-plans-grep` 中的游离计划检查会按名称报告作为链接的计划文件夹或 `.apothem` 文件夹，无论该链接指向何处；
- `no-toplevel-docs-grep` 会按名称报告根目录下的 `docs` 链接；
- `naming-grep` 检查链接自身的名称。

每个校验器的报告都会在 `skipped_links` 下列出它跳过的链接和特殊文件，因此链接永远不会不留痕迹地隐藏文件。它也会在其中列出无法列出内容的文件夹（无访问权限、路径过长、读取错误），以及作为嵌套检出而跳过的文件夹中、本身是链接或特殊文件的 `.git` 条目；该文件夹本身列在下文所述的 `skipped_checkouts` 下。在其文件夹缺失时通过的校验器（例如工作流校验器）在该文件夹是链接时不会通过：文件可能就在链接后面，因此这次运行会像什么都没检查的运行一样失败。硬链接是普通文件，并按普通文件读取。`--all` 校验器和 `--all-perwrite` 在到达每个层级时查看该层级，然后从根目录开始逐级打开文件，每个文件夹都在之前打开的文件夹内打开，从不经由链接。因此，当能够写入项目的人在 gate 运行期间把已检查过的文件或其上方的文件夹换成链接或命名管道时，gate 不会经由该链接读取，也不会在管道上等待：该文件不会被读取。`--all` 校验器会像对待链接那样，把它计为不存在或不可读，并把被替换的条目列在 `skipped_links` 下；`--all-perwrite` 把它计为 `link`，再次被替换时计为 `unreadable`，详见下文。在 Windows 上仍有一种等待，与普通打开时相同：能够写入项目的程序可以在文件上持有机会锁（oplock），并在 gate 打开该文件时不释放。任何打开文件的方式都无法避免这种等待，因此 `--all` 校验器会一直等到其 10 分钟的限制，而没有这种限制的 `--all-perwrite` 会一直等到该程序释放文件。在 `--all` 和 `--all-perwrite` 中，gate 本身只打开根目录内的普通文件，用 `lstat` 检查途经的每个文件夹（包括 git 列出的每个路径），并且从不读取 `.git` 条目内部。在运行 git 之前，运行 git 的三个 `--all` 校验器以及两个 `--staged` 检查，会按当时树的状态，用 `lstat` 查看根目录以及 git 会搜索的其上每个文件夹的 `.git` 条目；只要其中任何一个是链接或无法查看，它们就不运行 git。这也会拒绝 git 本可安全处理的项目，例如其 `.git` 是链接的主文件夹之下的所有项目，即使项目有自己的仓库：这是简单规则有意付出的代价。三个 `--all` 校验器运行 git 时不带 `GIT_DIR` 以及其他指定仓库、其存储或其索引的变量；`--staged` 检查保留钩子的 `GIT_DIR`。git 随后读取哪个仓库不会被检查：`gitdir:` 行、`commondir`、alternates、`core.worktree`、include 或 git 文件夹内的链接都可能指向另一个仓库，git 会跟随它们，因此 git 可能访问网络路径或一直等到其时间限制。gate 只把 git 的输出用作名称、模式、状态字母、最后一次提交的主题、提交时间和少数设置，并且在未检查根目录内每个层级之前，从不打开 git 输出的路径。发现链接时，三个 `--all` 校验器都会在 `skipped_links` 下列出它（位于根目录内时相对于根目录，位于根目录之上时使用完整路径）。此时 `conventional-commit-grep` 会像在检出之外那样报告 `not-a-git-repo`，但不会通过：它会给出指明该链接的 `check_error`。`no-global-plans-grep` 会把该链接作为发现项报告并失败，伴随文件检查会像没有历史记录时那样跳过其新鲜度测试。`--all-perwrite` 也不会列出被跟踪的文件：它以指明该链接的 `check_error` 失败；两个 `--staged` 检查同样如此，但只在 `check_error` 中指明链接，或在其中说明其运行所在文件夹中的 `.git` 条目是链接：它们读取钩子的 `GIT_DIR` 所指的仓库，但仍会拒绝从其运行所在文件夹开始的搜索路径上的链接。gate 无法查看的 `.git` 条目（路径过长、无法访问的共享、无访问权限）不是链接，也不会列在 `skipped_links` 下：`conventional-commit-grep` 以状态 `git-failed` 和一个 `check_error` 失败；伴随文件检查、`--all-perwrite` 和两个 `--staged` 检查以说明该条目无法查看的 `check_error` 失败；`no-global-plans-grep` 则把它作为发现项报告。

有六个校验器从仓库根目录开始，在整棵树中搜索它们要检查的文件：

```text
agents-md-coverage-grep
agnosticism-grep
dynamism-grep
freshness-token-grep
plain-language-grep
reference-token-grep
```

这些校验器会跳过嵌套的 git 检出（例如工作树、子模块和嵌套克隆；即其 `.git` 文件或文件夹包含或指向仓库的文件夹，普通的 `.git` 文件或空的 `.git` 文件夹不会隐藏其所在文件夹），也会跳过存放依赖项、虚拟环境、缓存或构建输出的目录（例如 `node_modules`、`venv` 和 `dist`）。`no-global-plans-grep` 中的游离计划检查同样会在嵌套检出处停止。每个作为嵌套检出而跳过的文件夹都会在报告的 `skipped_checkouts` 下列出，无论其 `.git` 条目指向什么，因为一行 `gitdir:` 就能让 git 跳过任何文件夹。该列表从不改变判定结果，以这种方式跳过的文件夹不会被检查；按名称跳过的文件夹（例如 `node_modules`）不会列出。运行其中任意一个校验器时，它只报告其所指向的那个检出，而不报告其他任何内容。读取某个固定文件夹的校验器（例如读取 `src/apothem/` 的 `naming-grep`）会读取该文件夹之下的全部内容。

## 定向检查

```bash
# List every registered validator
PYTHONPATH=src python -m apothem.conformity.gate --list

# Run one per-write validator against one file
PYTHONPATH=src python -m apothem.conformity.gate --check multi-surface-coherence src/apothem/rules/my-rule.md

# Run one standalone validator over a root directory
PYTHONPATH=src python -m apothem.conformity.gate --check naming-grep .

# Run every per-write validator against one file
PYTHONPATH=src python -m apothem.conformity.gate src/apothem/rules/my-rule.md
```

逐写入校验器接受要检查的文件，或者接受 `--stdin` 以从标准输入读取内容；两者都不提供时，它会等待标准输入上的输入，因此从终端运行时请传入该文件。独立校验器接受一个根目录（省略时为当前目录）。`--list` 会显示每个校验器所属的分组。

`--hook` 模式（`python -m apothem.conformity.gate --hook`）是由工具调度的入口点：它从 stdin 读取一个工具输入 JSON 载荷，并针对待处理的写入运行逐写入匹配器链。部署后的 `PreToolUse` 钩子调用的就是这种形式；你很少需要手动调用它。

钩子模式**限定于一组目录**。它只对目标位于其中某个目录之下的写入运行匹配器链；位于所有范围之外的写入会短路为无声通过。默认值是两个根目录：

```text
~/.claude      Claude Code
$CODEX_HOME    Codex (~/.codex when CODEX_HOME is not set)
```

将 `APOTHEM_CONFORMITY_SCOPE` 设置为某个目录即可替换它们：

```bash
# Run the per-write matcher chain against one project tree instead
export APOTHEM_CONFORMITY_SCOPE=/path/to/project
```

看似什么都没做的钩子，通常是未命中范围，而不是故障——请先对照上述范围检查该写入的目标。

## CI 集成

`.github/workflows/ci.yml` 中的 quality 作业会在向 `main` 的推送上，以及在针对 `main` 且涉及该作业所监视路径的拉取请求上，以严格模式运行闸门（`python -m apothem.conformity.gate --all . --strict`）。独立的 `.github/workflows/conformity.yml` 工作流则运行夹具扫描（`tests/conformity-scenarios/verify.py --strict`）。
