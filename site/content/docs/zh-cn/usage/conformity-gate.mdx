位于 `src/apothem/conformity/gate.py` 的合规闸门会针对操作者编写的每个工件，运行十五道预发布闸门关卡（M1-M15）中的机械部分。

本页上的命令假定位于 Apothem 检出中，因此请在你运行的每条命令前加上 `PYTHONPATH=src`。脚本安装之后，请使用 `PYTHONPATH="$HOME/.apothem/src"` 替代 `PYTHONPATH=src`。

## 运行闸门

闸门**默认为建议性**：它报告发现项并以 `0` 退出，因此本地运行绝不会阻塞你。添加 `--strict`（或设置 `APOTHEM_CONFORMITY_STRICT=1`），即可在出现阻断性发现项时以非零状态退出——CI 和 pre-commit 正是使用这种模式让违规的变更失败。

```bash
# Advisory: report every validator's findings across the repo, exit 0
PYTHONPATH=src python -m apothem.conformity.gate --all .

# Strict: exit non-zero (code 2) when a blocking finding is present
PYTHONPATH=src python -m apothem.conformity.gate --all --strict .
```

退出码：`0` 表示干净（或建议性模式），`2` 表示严格模式下的发现项阻断，`3` 表示用法错误：未知的标志或校验器名称、不存在的文件，或不存在的根目录。`--help` 打印完整用法并以 `0` 退出。每个独立校验器都接受同样的 `--help`，并在遇到未知标志或缺失的根目录时以 `3` 退出。

诸如 `.` 的相对根目录会在任何校验器运行之前被解析为绝对路径，因此 `--all .` 和 `--all "$PWD"` 检查的是同一棵树。每个校验器都会报告 `inspected`——即它检查了多少个目标——而 `--all` 会将该计数复制到每个结果条目中。未检查任何内容的校验器会报告 `passed: false`，因此错误的工作目录不会无声地通过。两个计划套件校验器是其中一种例外：计划套件位于被 git 忽略的 `.apothem/plans/` 树中，因此它们在干净的检出上报告 `empty_scope_expected: true` 并仍然通过。当项目还没有 `.github/workflows/` 目录时，工作流校验器也会这样做；当根目录没有提交历史时，提交主题校验器也会这样做。

## 定向检查

```bash
# List every registered validator
PYTHONPATH=src python -m apothem.conformity.gate --list

# Run a single named validator
PYTHONPATH=src python -m apothem.conformity.gate --check multi-surface-coherence

# Run every validator against one file
PYTHONPATH=src python -m apothem.conformity.gate src/apothem/rules/my-rule.md
```

`--hook` 模式（`python -m apothem.conformity.gate --hook`）是由工具调度的入口点：它从 stdin 读取一个工具输入 JSON 载荷，并针对待处理的写入运行逐写入匹配器链。部署后的 `PreToolUse` 钩子调用的就是这种形式；你很少需要手动调用它。

钩子模式**限定于一组目录**。它只对目标位于其中某个目录之下的写入运行匹配器链；位于所有范围之外的写入会短路为无声通过。默认值是两个根目录：

```text
~/.claude      Claude Code
$CODEX_HOME    Codex (~/.codex when CODEX_HOME is not set)
```

将 `APOTHEM_CONFORMITY_SCOPE` 设置为某个目录即可替换它们：

```bash
# Run the per-write matcher chain against one project tree instead
export APOTHEM_CONFORMITY_SCOPE=/path/to/project
```

看似什么都没做的钩子，通常是未命中范围，而不是故障——请先对照上述范围检查该写入的目标。

## CI 集成

`.github/workflows/ci.yml` 中的 quality 作业会在向 `main` 的推送上，以及在针对 `main` 且涉及该作业所监视路径的拉取请求上，以严格模式运行闸门（`python -m apothem.conformity.gate --all . --strict`）。独立的 `.github/workflows/conformity.yml` 工作流则运行夹具扫描（`tests/conformity-scenarios/verify.py --strict`）。
