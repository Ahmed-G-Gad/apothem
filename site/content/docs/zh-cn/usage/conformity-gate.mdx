位于 `src/apothem/conformity/gate.py` 的合规闸门会针对操作者编写的每个工件，运行十五道预发布闸门关卡（M1-M15）中的机械部分。

本页上的命令假定位于 Apothem 检出中，因此请在你运行的每条命令前加上 `PYTHONPATH=src`。脚本安装之后，请使用 `PYTHONPATH="$HOME/.apothem/src"` 替代 `PYTHONPATH=src`。

## 运行闸门

闸门**默认为建议性**：它报告发现项并以 `0` 退出，因此本地运行绝不会阻塞你。添加 `--strict`（或设置 `APOTHEM_CONFORMITY_STRICT=1`），即可在出现阻断性发现项时以非零状态退出——CI 和 pre-commit 正是使用这种模式让违规的变更失败。

```bash
# Advisory: report every validator's findings across the repo, exit 0
PYTHONPATH=src python -m apothem.conformity.gate --all .

# Strict: exit non-zero (code 2) when a blocking finding is present
PYTHONPATH=src python -m apothem.conformity.gate --all --strict .
```

这些命令从 Apothem 检出中运行闸门。`python -m` 会优先从当前文件夹读取模块，因此请在检出根目录或你信任的其他文件夹中运行它们。若要检查你不信任其文件的项目，请改为按脚本路径并加上 `-E -s` 运行闸门：在检出中使用 `python3 -E -s src/apothem/conformity/gate.py --all .`，脚本安装之后使用 `python3 -E -s ~/.apothem/src/apothem/conformity/gate.py --all .`。在 Windows 上，请用 `python` 替代 `python3`，并使用完整路径，因为 Windows PowerShell 和 cmd 不会展开 `~`：在 PowerShell 中使用 `$HOME\.apothem\src\apothem\conformity\gate.py`，在 cmd 中使用 `%USERPROFILE%\.apothem\src\apothem\conformity\gate.py`。以脚本方式启动时，当前文件夹不会成为 Python 模块搜索路径的第一项；`-E` 还会排除 `PYTHONPATH`（其中空的或相对的条目同样指向当前文件夹），`-s` 则排除你的用户 site-packages。这只会让项目的文件远离闸门自身的 Python 代码；闸门所运行的 `git` 将在下文说明。

有三个独立校验器会在它们所检查的项目中运行 `git`，运行这三者的 `--all` 以及用 `git ls-files` 列出被跟踪文件的 `--all-perwrite` 也是如此：

```text
agents-md-coverage-grep
conventional-commit-grep
no-global-plans-grep
```

该仓库自身的设置（位于 `.git/config`、它所包含的文件以及 `.git/config.worktree` 中）可以指定一个程序，让 git 在仅进行读取时启动它。闸门会通过 git 命令行上的选项关闭它已知的每一项此类设置；这些选项优先于 git 读取的所有文件，并且也会传给 git 在子模块中启动的任何 git：

- 不使用文件系统监视器（`core.fsmonitor`）；
- 不使用签名程序（`gpg.program`、`gpg.ssh.program` 和 `gpg.x509.program` 指向一个不可能存在任何东西的路径，并且 `log.showSignature` 处于关闭状态）；
- 不运行钩子、不使用分页器，也不进行自动维护；
- 不使用外部 diff 或文本转换程序，并且子模块的变更只显示为提交 ID，因此 git 不会在子模块内启动第二个 git；
- 用 `git cat-file blob` 读取文件内容，它会拒绝子模块条目，而 `git show` 会把该条目显示为一个提交。

有三项设置指定的是供 git 读取的文件而不是程序，而该文件可能位于网络路径上。闸门的命令行同样会阻止 git 读取它们：diff 顺序文件（`diff.orderFile`）、排除文件（`core.excludesFile`）和 mailmap 文件。

它还会设置 `GIT_NO_LAZY_FETCH=1` 和空的 `GIT_ALLOW_PROTOCOL`，因此 git 永远不会通过仓库指定的地址去获取部分克隆中缺失的对象。闸门只从你的 `PATH` 中的完整路径条目启动 git。它从不从当前文件夹获取 git：它会跳过空的和相对的 `PATH` 条目（它们指向该文件夹），并且不会像 Windows 对待裸程序名那样先在那里查找。对于 git 按名称启动的程序，git 也只得到这些完整路径条目。

因此，你可以在一个连同其 `.git` 文件夹一起由他人提供的项目（来自压缩包或共享文件夹）上运行这些命令：上述任何设置都无法让闸门启动程序。仍有两个限制。仓库仍然可以通过任何指定路径的设置或文件，让 git 读取别处的路径，例如 `include.path` 或 `includeIf`、`core.worktree`、`.git` 文件中的 `gitdir:` 行，或 `.git/objects/info/alternates`；在 Windows 上，其中的网络路径（`\\server\share`）会让 Windows 连接到该服务器并为你登录。有一种情况范围更窄：Git for Windows 2.55 会在连接之前拒绝 `gitdir:` 行中的网络路径，除非你自己的 `safe.directory` 设置允许该路径。此外，该列表涵盖的是目前已知的设置；以后的 git 版本可能会新增设置。你自己的全局和系统 git 设置仍然适用，但上述设置除外，闸门的命令行会覆盖它们。这只涉及 git：`python -m` 会优先从当前文件夹读取 Python 模块，因此请从你信任的文件夹启动闸门。

退出码：`0` 表示干净（或建议性模式），`2` 表示严格模式下的发现项阻断，`3` 表示用法错误：未知的标志或校验器名称、不存在的文件，或不存在的根目录。`--help` 打印完整用法并以 `0` 退出。每个独立校验器都接受同样的 `--help`，并在遇到未知标志或缺失的根目录时以 `3` 退出。

诸如 `.` 的相对根目录会在任何校验器运行之前被解析为绝对路径，因此 `--all .` 和 `--all "$PWD"` 检查的是同一棵树。每个校验器都会报告 `inspected`——即它检查了多少个目标——而 `--all` 会将该计数复制到每个结果条目中。未检查任何内容的校验器会报告 `passed: false`，因此错误的工作目录不会无声地通过。两个计划套件校验器是其中一种例外：计划套件位于被 git 忽略的 `.apothem/plans/` 树中，因此它们在干净的检出上报告 `empty_scope_expected: true` 并仍然通过。当项目还没有 `.github/workflows/` 目录时，工作流校验器也会这样做；当根目录没有提交历史时，提交主题校验器也会这样做。

项目可能带有他人制作的文件，来自压缩包或共享文件夹，因此每个 `--all` 校验器只打开和列出它经由根目录下的真实文件夹到达的普通文件和真实文件夹。它从不跟随符号链接，在 Windows 上也从不跟随联接点（junction），并且在根目录下的任何层级都把以下各项视为不存在：

- 链接，即使它指向根目录内部。遍历或文件夹列表会跳过它，因此它指向的内容只在校验器经由其自身路径到达时才会被检查；
- 命名管道、设备或套接字，对它们的读取会一直等待或永不结束；
- 在 Windows 上，以点或空格结尾的名称，因为 Windows 会以该名称打开另一个条目。

少数检查仍会使用链接，但不进入其中：

- 对于作为符号链接的固定文件，例如指向另一个文件的 `CLAUDE.md`，闸门会读取链接本身的文本，并且只有当它指向的是项目内、经由真实文件夹到达的普通文件时才会打开该文件。每个文件夹的 `README.md` 链接也按同样方式计算。绝对链接在经由解析后的项目文件夹写成时有效，在 Windows 上经由大小写不同的同一路径写成时也有效；单独运行的校验器还接受你键入的文件夹形式，除非该路径包含 `..`，而闸门会在启动每个校验器之前解析该文件夹。被链接的 `.gitattributes` 仍被视为不存在，因为 git 不会读取它；
- `no-global-plans-grep` 中的游离计划检查会按名称报告作为链接的计划文件夹或 `.apothem` 文件夹，无论该链接指向何处；
- `no-toplevel-docs-grep` 会按名称报告根目录下的 `docs` 链接；
- `naming-grep` 检查链接自身的名称。

每个校验器的报告都会在 `skipped_links` 下列出它跳过的链接和特殊文件，因此链接永远不会不留痕迹地隐藏文件。它也会在其中列出无法列出内容的文件夹（无访问权限、路径过长、读取错误），以及作为嵌套检出而跳过的文件夹中、本身是链接或特殊文件的 `.git` 条目；该文件夹本身列在下文所述的 `skipped_checkouts` 下。在其文件夹缺失时通过的校验器（例如工作流校验器）在该文件夹是链接时不会通过：文件可能就在链接后面，因此这次运行会像什么都没检查的运行一样失败。硬链接是普通文件，并按普通文件读取。`--all` 校验器和 `--all-perwrite` 在到达每个层级时查看该层级，然后从根目录开始逐级打开文件，每个文件夹都在之前打开的文件夹内打开，从不经由链接。因此，当能够写入项目的人在闸门运行期间把已检查过的文件或其上方的文件夹换成链接或命名管道时，闸门不会经由该链接读取，也不会在管道上等待：该文件不会被读取。`--all` 校验器会像对待链接那样，把它计为不存在或不可读，并把被替换的条目列在 `skipped_links` 下；`--all-perwrite` 把它计为 `link`，再次被替换时计为 `unreadable`。在 Windows 上仍有一种等待，与普通打开时相同：能够写入项目的程序可以在文件上持有机会锁（oplock），并在闸门打开该文件时不释放。任何打开文件的方式都无法避免这种等待，因此 `--all` 校验器会一直等到其 10 分钟的限制，而没有这种限制的 `--all-perwrite` 会一直等到该程序释放文件。在 `--all` 和 `--all-perwrite` 中，闸门本身只打开根目录内的普通文件，用 `lstat` 检查途经的每个文件夹（包括 git 列出的每个路径），并且从不读取 `.git` 条目内部。在运行 git 之前，运行 git 的三个 `--all` 校验器以及两个 `--staged` 检查，会按当时树的状态，用 `lstat` 查看根目录以及 git 会搜索的其上每个文件夹的 `.git` 条目；只要其中任何一个是链接或无法查看，它们就不运行 git。这也会拒绝 git 本可安全处理的项目，例如其 `.git` 是链接的主文件夹之下的所有项目，即使项目有自己的仓库：这是简单规则有意付出的代价。三个 `--all` 校验器运行 git 时不带 `GIT_DIR` 以及其他指定仓库、其存储或其索引的变量；`--staged` 检查保留钩子的 `GIT_DIR`。git 随后读取哪个仓库不会被检查：`gitdir:` 行、`commondir`、alternates、`core.worktree`、include 或 git 文件夹内的链接都可能指向另一个仓库，git 会跟随它们，因此 git 可能访问网络路径或一直等到其时间限制。闸门只把 git 的输出用作名称、模式、状态字母、最后一次提交的主题、提交时间和少数设置，并且在未检查根目录内每个层级之前，从不打开 git 输出的路径。发现链接时，三个 `--all` 校验器都会在 `skipped_links` 下列出它（位于根目录内时相对于根目录，位于根目录之上时使用完整路径）。此时 `conventional-commit-grep` 会像在检出之外那样报告 `not-a-git-repo`，但不会通过：它会给出指明该链接的 `check_error`。`no-global-plans-grep` 会把该链接作为发现项报告并失败，伴随文件检查会像没有历史记录时那样跳过其新鲜度测试。`--all-perwrite` 也不会列出被跟踪的文件：它以指明该链接的 `check_error` 失败；两个 `--staged` 检查同样如此，但只在 `check_error` 中指明链接，或在其中说明其运行所在文件夹中的 `.git` 条目是链接：它们读取钩子的 `GIT_DIR` 所指的仓库，但仍会拒绝从其运行所在文件夹开始的搜索路径上的链接。闸门无法查看的 `.git` 条目（路径过长、无法访问的共享、无访问权限）不是链接，也不会列在 `skipped_links` 下：`conventional-commit-grep` 以状态 `git-failed` 和一个 `check_error` 失败；伴随文件检查、`--all-perwrite` 和两个 `--staged` 检查以说明该条目无法查看的 `check_error` 失败；`no-global-plans-grep` 则把它作为发现项报告。

每个独立校验器都作为单独的程序运行，闸门在 `--all` 和 `--check` 中都给它 10 分钟。在 Apothem 自身的仓库上，最慢的一个大约需要一分钟。到达限制时仍在运行的校验器会被停止，连同它启动的每个程序（例如仍在等待的 `git` 命令）一起，并以 `passed: false` 和一个说明它未完成的 `check_error` 报告。在 Linux 和 macOS 上，每个校验器都在自己的会话中运行，发给闸门的 `SIGTERM` 或 `SIGHUP`（例如来自 `timeout` 或已关闭的终端）会在闸门以 128 加信号编号的退出码退出之前，停止该校验器的程序。在闸门启动或停止校验器期间到达的信号也是如此：它会等到该步骤完成，并且即使在该步骤中随后又按了 Ctrl+C，退出码仍为 128 加该信号的编号。`SIGKILL` 无法被任何程序捕获，在那里它只会结束闸门本身：闸门启动的校验器会继续运行直到完成，而该校验器正在等待的 `git` 命令仍会在其自身的限制处停止。在 Windows 上，每个校验器都在一个作业对象（job object）中运行，闸门本身结束时，作业对象也会结束它的程序。闸门在那里启动的每个程序都会处于挂起状态等待，直到它进入作业对象。无法恢复的程序会被停止，错误信息会说明它是否在作业对象中。在恢复之前被其他东西告知结束的程序从未运行过，无论其退出码是什么，都会以同样的方式失败，但有两个例外。以退出码 259（Windows 也会为正在运行的程序给出这个代码）结束的程序，在 Windows 仍在结束它时会被读作正在运行。恰好在恢复之前结束的程序，只有当闸门在恢复后 1 毫秒内读取其退出码时才会被发现；更晚的读取（例如在繁忙的机器上，或调用进程中的其他线程繁忙时）会把它的退出码当作程序自己的退出码。在测量所用的机器上，Windows 能运行的最小程序在恢复后至少存活 3 毫秒，`git` 则为 27 毫秒，因此运行过的程序不会被误认为是被结束的程序。恰好在恢复之后结束的程序，同样无法与运行过的程序区分开。在所有平台上，在闸门自身的运行中，启动期间到达的 Ctrl+C 会等到程序运行起来（在 Windows 上，等到闸门已尝试恢复它），因此不会有程序被留在挂起状态或运行超过其限制。在闸门停止某个程序期间到达的第二次 Ctrl+C 会等到停止完成。恰好在停止开始之前到达的 Ctrl+C 会让闸门再次尝试停止，最多三次。当这些尝试失败，或者 Ctrl+C 落在两次尝试之间时，闸门会在不阻挡信号的情况下停止该程序，同样最多三次，因此再按一次 Ctrl+C 不会跳过停止。要让程序继续运行，需要按好几次 Ctrl+C，并且每次都落在这些时间点之一的几微秒之内。停止之后，闸门最多等待半秒让被停止的程序结束，因此在 Linux 和 macOS 上它不会作为僵尸进程残留，而在这段等待中按下的 Ctrl+C 也不会取代已在进行中的终止。调用进程为其他信号设置的处理程序仍可能让程序继续运行（在 Windows 上为挂起），前提是它的错误恰好落在程序启动之后、闸门记录它之前的几微秒内。当闸门更改它自己的信号处理程序时，在更改中途到达的信号不会让某个处理程序停留在已更改的状态。在 Linux 和 macOS 上，闸门会在更改所需的几微秒内阻塞 Ctrl+C、`SIGTERM` 和 `SIGHUP`，而不阻塞其他任何信号，因此这样的信号会等到更改完成，并遇到届时已就位的处理程序。随后闸门只解除阻塞它所阻塞的信号。对于任何其他信号、在 Windows 上，以及对于恰好在阻塞之前到达的信号，被信号打断的更改会重新进行，最多三次。当每次尝试恢复其处理程序都失败时，闸门会为剩下的每个处理程序做最后一次尝试。当某个错误也阻止了这最后一次尝试时（例如调用进程设置的、每次都会触发的计时器所引发的 `TimeoutError`），以及在少数情况下，当处理程序会引发异常的多个信号在几微秒内接连到达并跳过最后一次尝试时，处理程序会停留在已更改的状态。每次尝试都会再次出现的错误（例如接近 Python 递归限制时的 `RecursionError`）会在两次尝试之内结束更改并继续进行。闸门恢复其处理程序时所用的调用深度不超过更改它们时的调用，因此在接近该限制时，它不会让 Ctrl+C 处于被忽略的状态。调用进程在运行期间设置的 `SIGTERM` 处理程序会保持不变。在 Linux 和 macOS 上，在不允许设置信号处理程序的 Python 子解释器中，闸门会在不更改处理程序的情况下运行其程序；在 Windows 上，Python 无法从隔离的子解释器中读取程序的输出，因为隔离的子解释器不允许守护线程。Ctrl+C 会打印一行并以 `130` 退出。这些限制会累加：多个校验器都在等待的一次运行，耗时为它们各自限制之和。

有五个校验器还会为它们运行的每条 `git` 命令设置各自的时间限制。这些限制在所有平台上都有效，在 Windows 上，当 `PATH` 上的 `git` 是 Git for Windows 安装的启动器（它会再启动真正的 git）时也是如此：

```text
conventional-commit-grep            git log -1, git rev-parse           1 minute
                                    git ls-files, git config            1 minute
agents-md-coverage-grep             git rev-parse, git config           1 minute
                                    git log over the whole history      5 minutes
no-global-plans-grep                git ls-files                        1 minute
production-ready-pr-grep --staged   git diff --cached                   1 minute
semver-stability-grep --staged      git diff --cached, git cat-file     1 minute
```

这些命令在大多数项目上只需不到一秒，因此只有当 `git` 等待某个永远不会到来的东西时才会达到限制。项目自身的 git 设置可能让它永远等待，例如其 `.git/config` 中指向某个命名管道的 `include.path`。运行超过其限制的 `git` 命令不会通过：校验器会报告 `passed: false`，并附上指明该命令的 `check_error`。拒绝它所找到的检出的 `git` 也不会通过，例如该检出属于另一个用户，或其 `.git/config` 中有错误的行；此时 `check_error` 会给出 git 的退出码，而退出码 128 是 git 无法打开或读取仓库时使用的代码。`.git` 条目无法被 git 打开的文件夹也算作这样的检出，因为检查所需的历史记录可能就在那里而未被读取：任何其他检出之外的空 `.git` 文件夹，或者指向已不存在的文件夹的 `.git` 文件（解包后的工作树或复制来的子模块会留下这种文件）。请删除该条目，或在完整的检出上运行闸门。这同样适用于过期伴随文件检查，尽管它的发现项在其他情况下只是建议性的；此时提交主题检查还会报告 `inspected: 0` 和 `empty_scope_expected: false`。在 Windows 上，闸门已启动但无法恢复的 `git` 也是失败的 `git`：`check_error` 给出退出码 128，并且它从不算作缺失的 `git`。过期伴随文件检查会读取一次完整历史，这次读取有 5 分钟，因此大型历史只会变慢而不会失败；读取时间更长的历史会让该检查失败。不在任何 git 检出之内的普通文件夹、还没有任何提交的仓库，或没有 `git` 的机器，仍会像以前一样通过这些检查。部分克隆（用 `git clone --filter` 创建的克隆）也是如此：闸门不允许 `git` 获取克隆所省略的内容，而 git 给出的任何回答都无法区分被克隆省略的对象和丢失的对象。因此在部分克隆中，过期伴随文件检查会把任何失败的历史读取都视为不可用的历史：它跳过新鲜度测试并通过，就像没有历史记录时那样。这些豁免以及针对 git 拒绝的检出的 `check_error`，适用于另外四个校验器：`no-global-plans-grep` 需要一个 git 能够读取的检出，因此在检出之外、在没有 `git` 的机器上，或在 git 拒绝的检出中，它会像以前一样失败，并在标准错误上给出原因：git 的退出码，而不是 git 自己的文本。与任何未通过的结果一样，默认的建议性模式会报告它并以 `0` 退出，`--strict` 则以 `2` 退出。

对于两个 `--staged` 检查，git 无法读取的 diff 设置值（例如 `diff.renameLimit = abc`）就是这样一行错误：`git diff` 会失败，而未被读取的变更集并不是空的变更集。这两个检查、提交主题检查和过期伴随文件检查会在其运行所在的文件夹及其上方的文件夹中查找检出，因此在检出的子文件夹中同样如此。它们在 git 停止查找的地方停止：在 `GIT_CEILING_DIRECTORIES` 中列出的文件夹处，以及（Windows 之外）位于另一个文件系统上的文件夹处，除非设置了 `GIT_DISCOVERY_ACROSS_FILESYSTEM`。因此，挂载在某个仓库之下、自身没有仓库的文件夹仍会通过。在检出的子文件夹上运行的提交主题检查，会在检出跟踪该子文件夹中的某个文件或在那里暂存了某个文件时，检查该检出的最新提交。在检出不区分大小写的地方（例如 Windows 和 macOS），对于仅在磁盘上更改了名称大小写的子文件夹也是如此。检出不跟踪的文件夹（未跟踪或被忽略）没有自己的历史，因此会通过，例如主文件夹 dotfiles 仓库中的新项目。在其运行所在文件夹之上、且再往上没有仓库的空 `.git` 文件夹会让 git 失败，检查会报告 `git-failed`。

两个 `--staged` 检查都从工作树的顶层读取暂存的名称，无论你自己的 `diff.relative` 设置是什么，因此子文件夹设置永远不会隐藏已暂存的文件。

`semver-stability-grep --staged` 会先在其运行所在的文件夹中查找包，然后在其上方的文件夹中查找，直到最近的一个包含仓库的文件夹或 git 停止查找的地方为止，并在包含该包的文件夹中运行 git，因此从子文件夹运行时检查的是同一个变更集。它也从该文件夹读取版本文件，因此位于仓库顶层之下的包也会被检查。当其运行所在的文件夹与包之间存在 git 拒绝的 `.git` 文件时，git 会改在其运行所在的文件夹中运行，并在该文件处停止，检查会报告 `check_error`。git 会拒绝以下 `.git` 文件：不指向任何仓库的、大于 1 MiB 的，或者内容不是 `gitdir:`、一个空格和一个路径（其后只有换行符）的。在 Windows 上，该检查还会拒绝指向网络、设备或 NT 路径（`\\host\share`、`\\?\`、`\??\`）的 `.git` 文件，并且它自己不会去查找该路径。它也会拒绝 Git for Windows 拒绝的路径：以点或空格结尾的名称、设备名称（例如 `aux.d`、`lpt0` 或 `CONIN$`，但不包括 Git for Windows 接受的 `com0`），或驱动器之后的 `:`。它按 Git for Windows 的方式读取路径中不是 UTF-8 的字节：`0xA0` 及以上读作该字符，低于它的读作两位十六进制数字，因此 `0x9F` 读作 `9f`。被检查的是包含 `src/apothem/__init__.py` 的最近文件夹；它不读取 `GIT_WORK_TREE`。没有该包的项目在那里没有要检查的内容：无论其仓库处于什么状态，它都会在不运行 git 的情况下通过。

闸门逐字节读取来自 git 的每个路径名列表，因此包含换行符、回车符或非 UTF-8 字节的名称，对每个检查而言都指向同一个文件。有一种情况无法读取：Windows 无法把非 UTF-8 的名称交给 git，而这种名称只可能存在于在其他系统上创建的索引中。此时 `semver-stability-grep --staged` 会为该变更集报告 `check_error`；它不会跳过该文件。过期伴随文件检查的历史读取是第一句话的例外：在那里，git 以带引号的形式打印含有控制字符的名称，而非 UTF-8 字节会读作替换字符，因此该检查无法匹配具有这种名称的文件夹。

过期伴随文件检查只把仓库顶层的 `AGENTS.md` 视为规范。当你在拥有自己 README 的子文件夹上运行它时，该子文件夹的 `AGENTS.md` 是一个逐文件夹的伴随文件。当该子文件夹本身是一个独立仓库的顶层时（例如子模块或嵌套克隆），它的 `AGENTS.md` 则是那个仓库的规范。在整个仓库上运行时会跳过某些子文件夹（例如测试夹具和嵌套仓库），而在该子文件夹本身上运行时会检查它们。没有 README 的子文件夹不会以这种方式作为独立的文件夹被检查；请在它上方的文件夹上运行检查。在某次提交中被删除后又重新写入的伴随文件，在你提交它之前都算作新文件。

有六个校验器从仓库根目录开始，在整棵树中搜索它们要检查的文件：

```text
agents-md-coverage-grep
agnosticism-grep
dynamism-grep
freshness-token-grep
plain-language-grep
reference-token-grep
```

这些校验器会跳过嵌套的 git 检出（例如工作树、子模块和嵌套克隆；即其 `.git` 文件或文件夹包含或指向仓库的文件夹，普通的 `.git` 文件或空的 `.git` 文件夹不会隐藏其所在文件夹），从不进入被链接的文件夹，并且会跳过存放依赖项、虚拟环境、缓存或构建输出的目录（例如 `node_modules`、`venv` 和 `dist`）。`no-global-plans-grep` 中的游离计划检查同样会在嵌套检出处停止。每个作为嵌套检出而跳过的文件夹都会在报告的 `skipped_checkouts` 下列出，无论其 `.git` 条目指向什么，因为一行 `gitdir:` 就能让 git 跳过任何文件夹。该列表从不改变判定结果，以这种方式跳过的文件夹不会被检查；按名称跳过的文件夹（例如 `node_modules`）不会列出。运行其中任意一个校验器时，它只报告其所指向的那个检出，而不报告其他任何内容。读取某个固定文件夹的校验器（例如读取 `src/apothem/` 的 `naming-grep`）会读取该文件夹之下的全部内容。

`--all-perwrite` 检查 `git ls-files` 在根目录下列出的文件。git 完全按照仓库索引中保存的样子列出每个条目，而项目可能带有他人制作的索引和文件，因此闸门只有当列出的路径是根目录内、不超过 64 MiB、内容为 UTF-8 文本的普通文件时才会读取它。它把其他每个列出的路径按原因计入 `files_skipped`：

- `outside_project`：含有空的、`.` 或 `..` 部分的条目，例如 `../notes.md`、`a//b.md` 或以 `/` 开头的名称；或者在 Windows 上指向 `.git` 的部分：任意大小写的 `.git`，包括其后带有点、空格或冒号的形式，以及 `GIT~1`。git 在所有系统上默认都会拒绝这些条目，因此这次运行不会通过；
- `unsupported_name`：在 Windows 上，系统无法按原样保存的名称：含有冒号的名称（如 `a:b.md`，其中 `a:` 被读作驱动器）、反斜杠、`<>"|?*` 之一或控制字符，或者以点或空格结尾的部分；以及 Windows 会读作其他东西的名称：单独出现的设备名称（例如 `CON`、`NUL` 或 `COM1`），或短名称（例如 `GIT~2`）。Linux 或 macOS 上的 git 可以跟踪这样的名称，因此它会被计数，而不会让运行失败。手写的条目（例如 `C:/x` 或 `..\..\x`）在 Windows 上也归入此类；
- `link`：根目录下任何层级上的符号链接，或 Windows 上的联接点（即使它指向根目录内部），或者索引标记为链接的条目（在合并冲突的任何阶段都是如此，因此这样的文件在冲突解决之前不会被读取）。git 把链接存储为它所指向的路径，而链接指向的被跟踪文件会以其自身路径被检查；
- `submodule`：子模块的条目；
- `not_regular_file`：其他任何不是普通文件的东西，例如文件夹、命名管道或设备，对它们的读取会一直等待或永不结束；
- `missing`：不在工作树中的被跟踪文件；在 Windows 上，这包括 git 以非 UTF-8 字节列出的名称（只有在其他系统上创建的索引才会包含这种名称；Git for Windows 会以另一个名称写入这样的文件，因此其内容不会被检查），以及在未开启长路径时超出系统允许长度的路径；
- `unreadable`：系统不允许闸门查看、打开或读取的文件或通往它的文件夹：原因可能是缺少权限、另一个程序占用了该文件或其一部分，或者系统无法打开它，例如同步程序已停止的仅在线文件。当另一个程序占用整个文件时，闸门会等待 0.2 秒并再试一次：在 Windows 上，是指以不共享方式打开它的程序；在其他系统上，是指正在被打破的写租约，例如 Samba oplock 或 NFS 委派。这次运行不会通过，因为其中的发现项将不会被看到。少数情况下，即使文件本身没有问题，运行也会以这种方式失败：耗时超过 0.2 秒的租约打破、等待删除的文件，以及位于 `\\wsl$` 共享上的项目中的命名管道（对它的每次读取都会先等待约 10 秒）；
- `too_large`：超过 64 MiB 且前 64 MiB 为 UTF-8 文本的文件，或在闸门读取期间增长超过 64 MiB 的文件。出于同样的原因，这次运行不会通过；
- `not_utf8_text`：字节不是 UTF-8 文本的文件，例如带有字节顺序标记的 UTF-16 文件。超过 64 MiB 时由前 64 MiB 决定；当文件前 8000 个字节中有四分之一或更多为 NUL 时，该文件被视为二进制文件，例如大型的全零填充图像，或没有字节顺序标记、主要为拉丁文本的 UTF-16 文件，因此它不会让运行失败；文本中的少量 NUL 字节不计在内；
- `exempt`：检查按设计排除的文件：后缀表明其为二进制文件的文件（例如图像或压缩包），以及根目录内任意深度的 `.apothem/plans`、`tests/conformity`、`tests/fixtures`、`_vendor` 或 `node_modules` 文件夹之下的任何内容。`outside_project` 和 `unsupported_name` 的检查优先进行，因此任何豁免都不会隐藏它们。

当一次运行因 `outside_project`、`unreadable` 或 `too_large` 而未通过时，`files_not_passed` 会按 git 列出的形式、排序后列出这些原因各自背后的条目，每个原因最多 10 个；`files_skipped` 给出完整计数。stderr 上也会有一行列出这些原因及其计数，因此只显示 stderr 的 CI 日志也能说明运行失败的原因。

每个文件的各个层级会在读取之前立即被检查，并且打开的文件必须是该检查所找到的那个文件。在此期间被另一个程序换成另一个文件、链接或命名管道的文件会再被查找一次，如果再次被替换则计为 `unreadable`；被换入的符号链接或 Windows 上的联接点会在第二次查找时被识别为 `link`。闸门从不在命名管道上等待，也从不经由取代该文件的链接进行读取。在 Windows 上，由重复数据删除（Data Deduplication）或云同步程序保存在重解析点之后的文件，会照常通过该程序读取；当该程序已停止时，该文件为 `unreadable`。

文件从根目录开始逐级打开，任何层级都不会经由链接打开，因此在检查与打开之间被另一个程序换成链接的、位于文件上方的文件夹同样不会被跟随：该文件计为 `link`。

有两种情况这些检查看不到。硬链接读起来就是普通文件，因此指向别处文件的硬链接会被读取；git 不会创建硬链接。此外，在 Windows 上，既不提供文件的重解析标记也不提供其文件 ID、但确实支持符号链接的网络文件系统，可能在检查与打开之间把文件换成链接而不被闸门察觉。

在这种运行中，`link-check` 匹配器只在根目录内查找链接目标：离开根目录的相对链接计为外部链接，而对 `site/content/docs` 文件夹的搜索在根目录处停止。在所有模式下，它都从不查找本身指向某个位置的链接，例如网络共享（`\\host\share`）、驱动器（`C:/notes.md`）或 `file:` 地址。在 Windows 上，查找共享会把你的登录信息发送给该主机。在 Windows 上，它还不检查含有冒号（Windows 会将其读作驱动器）的 `/docs/` 路由段，以及只能经由以点或空格结尾的部分找到的链接：Windows 可能会去掉该结尾（`ci.yml.` 会找到 `ci.yml`），因此这样找到并不能证明任何东西。这样的链接如果什么都没找到，会照常报告为失效链接。在所有系统上，含有 `.` 或 `..` 段的 `/docs/` 路由（例如 `/docs/../x`）都计为外部链接，不会被查找。

每次 `git ls-files` 调用都有 60 秒：本次运行发出的调用，以及 `no-global-plans-grep` 中的调用（其报告随后会带有同样的 `check_error` 并失败）；当 git 本身在那里失败时，其消息给出的是 git 的退出码，而不是 git 自己的文本。其自身设置会让 git 等待的仓库（例如 `include.path` 指向命名管道的仓库）最多会让这些调用中的每一个停滞这么长时间，在 Windows 上也是如此，那里的限制还会停止 Git 启动器所启动的 git。没有读取任何文件的 `--all-perwrite` 运行不会通过：它报告 `files_scanned: 0` 和 `empty_scope_expected: false`。当无法读取被跟踪文件的列表时，`check_error` 会给出一个固定的原因：git 未能启动、`git ls-files` 以某个退出码失败，或者它未能及时完成。要查看 git 自己的消息（例如当根目录不在 git 工作树内时），请在根目录中运行 `git ls-files`；报告会省略它，因为它可能会指出项目之外的文件。使用 `--strict` 时，未通过的运行以 `2` 退出。

## 定向检查

```bash
# List every registered validator
PYTHONPATH=src python -m apothem.conformity.gate --list

# Run one per-write validator against one file
PYTHONPATH=src python -m apothem.conformity.gate --check multi-surface-coherence src/apothem/rules/my-rule.md

# Run one standalone validator over a root directory
PYTHONPATH=src python -m apothem.conformity.gate --check naming-grep .

# Run every per-write validator against one file
PYTHONPATH=src python -m apothem.conformity.gate src/apothem/rules/my-rule.md
```

逐写入校验器接受要检查的文件，或者接受 `--stdin` 以从标准输入读取内容；两者都不提供时，它会等待标准输入上的输入，因此从终端运行时请传入该文件。独立校验器接受一个根目录（省略时为当前目录）。`--list` 会显示每个校验器所属的分组。

`--hook` 模式（`<python> -E -s .../conformity/gate.py --hook`，其中 `<python>` 是安装时找到的解释器）是由工具调度的入口点：它从 stdin 读取一个工具输入 JSON 载荷，并针对待处理的写入运行逐写入匹配器链。部署后的 `PreToolUse` 钩子调用的就是这种形式；你很少需要手动调用它。

钩子模式**限定于一组目录**。它只对目标位于其中某个目录之下的写入运行匹配器链；位于所有范围之外的写入会短路为无声通过。默认值是两个根目录：

```text
~/.claude      Claude Code
$CODEX_HOME    Codex (~/.codex when CODEX_HOME is not set)
```

将 `APOTHEM_CONFORMITY_SCOPE` 设置为某个目录即可替换它们：

```bash
# Run the per-write matcher chain against one project tree instead
export APOTHEM_CONFORMITY_SCOPE=/path/to/project
```

看似什么都没做的钩子，通常是未命中范围，而不是故障——请先对照上述范围检查该写入的目标。

`.github/workflows/ci.yml` 中的 quality 作业会在向 `main` 的推送上，以及在针对 `main` 且涉及该作业所监视路径的拉取请求上，以严格模式运行闸门（`python -m apothem.conformity.gate --all . --strict`）。独立的 `.github/workflows/conformity.yml` 工作流则运行夹具扫描（`tests/conformity-scenarios/verify.py --strict`）。
