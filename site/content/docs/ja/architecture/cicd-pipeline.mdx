## レーンの役割

- **静的解析レーン** —— 高速なフィードバック。Ruff は Python のスタイルと
  厳選されたルールセットを扱います。mypy は strict で型の規律を強制します。
  frontmatter バリデーターは、ルール、スキル、委任されたワーカー、コマンドの
  アーティファクトスキーマへの準拠を門にかけます。markdownlint はこのレーンには
  含まれません。pre-commit フックとしてのみ実行され、CI では実行されません
  （[Markdown 規約](/docs/reference/markdown-conventions)を参照してください）。
- **テストレーン** —— `pytest tests/hooks` は、フックランタイムを完全な
  イベントマトリクスに対して実行します。`validate_ecosystem.py` は、
  アーティファクト横断の整合性に対する主要な構造ゲートです。`chaos_pass.py` は、
  `main` へのプッシュとプルリクエストに対して、CI の品質ジョブ内で（パスフィルター付きで）
  実行され、劣化した入力のもとでの品質低下を捕捉します。`src/apothem/benchmarks/` 配下の
  クラス別ベンチマークスイートは、どの CI ワークフローでも実行されません。
- **セキュリティレーン** —— シークレットスキャンは、誤ってコミットされた認証情報を
  捕捉します。SBOM 生成とライセンス監査は、あらゆる本番準備インストールについて、
  サプライチェーンの表面を門にかけます。
- **公開レーン** —— リリースワークフローはタグのプッシュによって起動されます。npm と
  VS Code の公開処理は、既存のタグに対して手動ディスパッチによって再実行することもできます。
  署名済みタグの検証は、リリースブランチの来歴を確認します。リリースノートは
  `CHANGELOG.md` の Keep-A-Changelog 形式から派生します。プロジェクトのウェブサイトは、
  ビルド入力に触れる `main` へのプッシュ時、または手動ディスパッチ時に、
  `site/dist/` から GitHub Pages のターゲットへ公開されます。

## 具体的な構成

実際のワークフローファイル（`.github/workflows/ci.yml`、
`.github/workflows/release.yml` など）はリポジトリにあります。この図は、今後のあらゆる構成が
反映する正規の形を定義します。

## 権威ある相互参照

- `pyproject.toml` —— Ruff / mypy / pytest 構成の真実の源。
- `scripts/dev/validate_ecosystem.py` —— 主要なアーティファクト横断ゲート。
- `scripts/dev/validate_hooks.py` —— フック固有の構造検証。
- `scripts/dev/chaos_pass.py` —— 構成された各フックへの敵対的スイープ。
- `src/apothem/benchmarks/` —— クラス別の実行時予算検証器。
- `site/content/docs/developer-guide.mdx` —— オペレーター向けの貢献者ワークフロー。
- `CHANGELOG.md` —— リリースノートの源。
