現在の共有プロファイルからハーネスアダプターの設定を再インストールします。

## 構文

```
apothem update --harness NAME|all [--profile PATH] [--dry-run]
                [--project PATH]
                [--quiet|-q] [--verbose|-v]
                [--format plain|json] [--json] [--no-color]
```

`update` は、現在の共有プロファイルからハーネスの出力を再マテリアライズします。
`install` と同じプロファイル検証、`--harness all` の選択、プロジェクトスコープのチェック、ドライランの動作、JSON エンベロープを使用し、同じ注意事項を出力します。これには、あなたのファイルがツールに Apothem の書き込んだ内容を読み込ませない場合の `instruction_override` 注記も含まれます（[`install`](/docs/cli-reference/install) を参照）。
`install` と同様に、解決された `--project` フォルダーを記録し、そのフォルダーの別の表記で記録されたインストールをそのフォルダーへ移します。
また、後に END マーカーのない BEGIN マーカーを保持するファイルについても警告します。そのマーカーの後のテキストはそのまま保持され、Apothem のブロックはそれとは別に書き込まれます。そのため警告は、マーカーの行を示し、その行を変更する番号付きの手順を示し、代わりに END マーカーを戻さないよう案内します。そうすると Apothem のブロックが 2 つ残ってしまうためです
（[トラブルシューティング](/docs/install/troubleshooting#a-file-has-an-apothem-begin-marker-with-no-end-marker)を参照）。
Apothem のマーカーの間に完全なブロックを 2 つ以上保持するファイルはそのまま残され、各ブロックをその行で示す警告が出力されます
（[ファイルが Apothem のマーカーの間に 2 つのブロックを持つ](/docs/install/troubleshooting#a-file-holds-two-blocks-between-apothems-markers)を参照）。
Apothem が自身のブロックをあなたのテキストと区別できないファイル（たとえば、そのブロックがあなたのコードブロックの中にある場合）は、インストールレコードがそのファイルを列挙している間はそのまま残されます（読み取れないインストール台帳もレコードとして数えます。また、ホームディレクトリにリンク経由でたどり着いた場合のように、そのフォルダーの別の表記で作られたレコードも、アンインストールの場合と同様に、実行している表記にまだ独自のインストールが残っていて、そのツールが[ホームディレクトリの共有フォルダー](/docs/cli-reference/install#folders-in-your-home-directory)に書き込む場合には数えます）。そのとき、ファイル内の各マーカーのペアとその修正方法を示す警告が出力されます
（[Apothem が自身のブロックをあなたのテキストと区別できない](/docs/install/troubleshooting#apothem-cannot-tell-its-block-from-your-text)を参照）。
これは、END マーカーが失われた後に残った Apothem のブロックのように、マーカーのペアを開始しない BEGIN マーカーが併存する場合にも当てはまります。警告はその BEGIN マーカーを最初に示し、警告内の番号付きの各修正はその行を変更します。インストールレコードがない場合、あなたがコード内で引用しているマーカーのペアはあなたのテキストであり、そのような BEGIN マーカーの有無にかかわらず、更新はその後に自身のブロックを追加します。ただし、そのペアが更新の書き込むブロックとまったく同じものを保持している場合は、ファイルをそのまま残し、警告を出力します。
コードの外にある BEGIN マーカーの END マーカーがコードの中にあり、その後に別のマーカーのペアがあるファイルは、レコードの有無にかかわらず、警告とともにそのまま残されます。
プロファイル内のルールがコードブロックを開いたまま閉じない場合でも、更新が書き込むブロックについてはそうはなりません。更新はブロックの末尾でそのコードブロックを閉じます。
以前のリリースがそのようなルールから書き込んだブロックにはそのような閉じる行がないため、そうなることがあります。
Apothem のブロックより上で開き、閉じられないあなたのコードブロックは別のケースです。ブロック内の閉じる行がそれを閉じるため、ブロックはコードとして読まれます。そのようなブロックを書き込む更新はすぐに警告し、BEGIN マーカーより上で閉じるべきコードブロックを示します。
ドライランは何かが書き込まれる前にファイルを読み取るため、書き込まれた後にブロックがコードとして読まれることは示しません。
ドライランでは、そのまま残されるファイルに対する警告は、Apothem が "would leave the file as it is"（ファイルをそのまま残す予定である）と示します。

マーカー行のためにファイルをそのまま残す更新（完全なブロックが 2 つ以上ある場合、または Apothem が配置できないマーカーのペアがある場合）は、インストールと同様に部分的な結果で終わります。
ツールはそのファイルから最新の Apothem ブロックを得られないため、`✓` 行の代わりに、そのファイルを示す `✗` 行を標準エラーに出力します。`--format json` エンベロープの `status` は `"partial"` になり、そのファイルの警告は `"detail": {"left_as_is": "1"}` を持ち、終了コードは `2` になります。
警告が示すマーカー行を修正するまで、すべての更新はそのように終わります。コードブロック内のあなたのマーカーの例も、その BEGIN マーカー行を変更するまで、そのようなファイルを止めたままにします。
`--quiet` がない場合、`--harness all` を指定したそのような更新は、`✓` の代わりに `!` で始まり、そのまま残されたファイルを数える要約行で終わります:
`! Updated <n> harnesses (<m> files written); <k> file(s) left as they are, named above.`
ドライランは引き続き `status` `"dry_run"` と終了コード `0` で終わります。

Apothem が書き込む各フォルダー（スキルフォルダー、`.apothem/support/` 以下のサポートファイル）で、`update` は書き込むすべてのエントリーを比較します。
ファイルのエントリーは、異なる場合に書き直されます。
フォルダーのエントリー（スキル、コマンドのスキルフォルダー、または `hooks/lib/` のようなサポートファイル内のフォルダー）は、その中の何かがこのリリースの書き込む内容と異なる場合、まるごと置き換えられます。更新は事前にそれを `~/.apothem/backups/` 以下にバックアップするため、その中にあなたが追加したファイルや、あなたが編集した Apothem のファイルは、その後そこからなくなります。
そのようなファイルはバックアップセットからコピーするか、更新の前に移動してください。
Apothem が書き込むフォルダーに直接置かれたあなたのファイル（たとえば `.apothem/support/hooks/mine.py`）や、Apothem のフォルダーの横にあるあなた自身のフォルダーには触れません。

スキルをホームディレクトリに書き込むプロジェクトスコープのアダプター（[`install`](/docs/cli-reference/install#folders-in-your-home-directory) を参照）については、`update` はそれらのフォルダーも最新の状態にし、それらの名前を挙げる同じ `Note:` を出力します。
スキルを書き込むようになる前にインストールされたアダプターは、次回の更新でスキルを受け取ります。
Apothem が書き込んだものではない、または書き込んだことを証明できないスキルフォルダーは、[`install`](/docs/cli-reference/install#folders-in-your-home-directory) と同様に、修正方法を示す警告とともにスキップされます。
以前に共有スキルフォルダーを書き込んだインストールは、次回の更新で、すべてのインストールが共有する形式に書き直されます。変更される各フォルダーは、事前にバックアップされます。

進行形のエイリアス `apothem updating`（`apothem Updating` としても受け付けられます）は、同じハンドラーに解決されます。

## オプション

| オプション | 説明 |
|---|---|
| `--harness NAME` | 更新するハーネスアダプター、またはレジストリ全体のセットを表す `all`（必須）。`all` を指定すると、プロファイルの `exclude_harnesses` に記載されたハーネスはスキップされます。ただし、名前を明示的に指定したハーネスは、記載されていても更新されます。 |
| `--profile PATH` | 共有プロファイル YAML へのパス。デフォルトは `~/.config/apothem/profile.yaml` です。 |
| `--dry-run` | ファイルを書き込まずに更新をプレビューします。 |
| `--project PATH` | プロジェクトスコープのハーネス向けのプロジェクトルート。選択したハーネスのセットにプロジェクトスコープのアダプターが含まれる場合は必須です。 |
| `--quiet`, `-q` | 情報出力を抑制します。エラーのみが出力されます。 |
| `--verbose`, `-v` | 追加の診断出力を出力します。 |
| `--format plain\|json` | 出力形式（デフォルト: `plain`）。 |
| `--json` | `--format json` の短縮形です。 |
| `--no-color` | 出力中の ANSI カラーコードを無効にします。 |
| `-h`, `--help` | ヘルプを表示して終了します。 |

## JSON 出力

```json
{
  "schema_version": 1,
  "status": "success",
  "command": "update",
  "action": "updated",
  "harness": "claude-code",
  "profile_path": "C:\\Users\\Example\\.config\\apothem\\profile.yaml",
  "project": null,
  "files_written": [],
  "results": [],
  "warnings": [],
  "error": null,
  "output_path": "C:\\Users\\Example\\.claude\\settings.json"
}
```

`--dry-run` は `status: "dry_run"` と `files_written: []` を返します。
Apothem のマーカー行のためにファイルをそのまま残した更新は、`status: "partial"` を返し、コード `2` で終了します。

## 例

```bash
apothem update --harness claude-code
apothem update --harness claude-code --dry-run
apothem update --harness all --project . --dry-run --json
apothem Updating --harness claude-code   # continuous-form alias
apothem updating --harness claude-code   # lowercase variant
```

## 終了コード

| コード | 意味 |
|---|---|
| 0 | アダプターが正常に更新された、またはドライランが問題なく計画された |
| 1 | 想定された検証、プロファイル、ハーネス、プロジェクト、またはアダプターのエラー |
| 2 | 部分的: バッチが少なくとも 1 回の書き込みの後に停止した、または更新が、Apothem がブロックを保持するファイルを、その Apothem のマーカー行のためにそのまま残した。`status` は `"partial"` |
| 64 | 使用法エラー: 不明なオプションまたはコマンド、あるいは欠落した、または無効なオプション値。`--json` のもとでは、エラーはコード `cli.usage` を持つ JSON エンベロープになります。 |
