ハーネスアダプターの設定を削除します。

## 構文

```
apothem uninstall --harness NAME|all [--yes] [--project PATH]
                   [--quiet|-q] [--verbose|-v]
                   [--format plain|json] [--json] [--no-color]
```

アダプターが管理するハーネスのターゲットを削除し、続いて、インストールが作成した
ディレクトリを、空になった時点で削除します（あなたのものが何か入っている
ディレクトリは残ります）。

## アンインストールが削除するもの [#what-an-uninstall-removes]

インストールは、配置するすべてのファイル（スキル、コマンド、ルールなど）の SHA-256 を、インストール台帳（`~/.apothem/state/<harness>/ledger.jsonl`）に記録します。
アンインストールは、そのようなファイルがまだその内容を保っている場合にのみそれを削除し、続いて、何も入っていない状態になった各フォルダーを削除します。Apothem のフォルダー内にあなたが作成した空のフォルダーも含まれます。
それ以外はすべて残り、`Warning:` 行が出力されます。Apothem のフォルダーにあなたが追加したファイル、あなたが編集した Apothem のファイル、Apothem の名前を持つあなた自身のファイル、そしてインストール記録に列挙されていないパスです。
あなたが残すファイルがあれば、そのフォルダーも残ります。

以前のリリースが記録したインストールには、Apothem がどのファイルを書き込んだかが記されていません。
その場合、アンインストールは各ファイルを、このリリースがそのパスに書き込む内容と比較し、同じバイト列のものを削除します。
インストールが見つけた Python インタープリターを保持する箇所が 2 つあります。ステータスラインのコマンドと、コンフォーミティゲート内のコメントです。
そのような箇所は、以前のリリースがそこに書き込んだ唯一のランチャーである `py -3`、またはこのマシン上のインタープリターファイルのフルパスを保持し、それ以外何も含まない場合にのみ、同じとみなされます。
そこにあるパスが `&`、`#`、`$` を含む場合（`R&D` のような Windows のユーザー名）や、ここにあるどのファイルも指さない場合は、決して同じとはみなされず、そのファイルは残ります。
その後にアップグレードまたは削除したインタープリターへのパスも、ここにあるどのファイルも指さないため、そのファイルも残ります。`apothem update` を実行してから、再度アンインストールしてください。
設定ファイルやフックファイル内の Apothem のフックエントリは、このように比較されません。前にどのインタープリターがあっても、それらが実行するディスパッチャースクリプトによって識別され、ファイルがバックアップされた後に削除されます。

Apothem が書き込む名前にあるファイルで内容が異なるもの（その以前のリリースが書き込んだもの、またはあなたが編集したもの）は残り、アンインストールは完了しません。
そのようなパスの数とともに `✗ <harness> uninstall did not finish:` を出力し（フォルダーは 1 つとして数えられ、そのファイルはその `Warning:` 行の下に列挙されます）、`2` で終了します。
そのリリースが記録し、このリリースがもはや書き込まないパスも同様です。比較する対象がないためです。
記録がまったくないインストール（台帳が削除された場合）も同じように終わります。そのファイルのうちどれを Apothem が書き込んだかを示すものが何もないためです。リンクの外で残すすべてのパスは 1 つの `Warning:` 行の下に列挙され、あなたが追加したファイルも含まれます。それらを区別するものが何もないためです。
その場合も、ホーム内の共有フォルダーは残ります。
一部はそれでも削除されます。ルールファイルや `hooks.json` などの共有ファイル内の Apothem の行（ほかに何も残らないファイルも削除されます。ブロックが END マーカーを失ったファイルはそのまま残ります。[完了しなかったアンインストール](#an-uninstall-that-did-not-finish) を参照）、データフォルダーのメモリ、コンテキスト、学習ストア（先にバックアップされます。Apothem のデータだけでなく、あなたのデータも保持しているためです）、そして一部のハーネスでは、そのハーネスが古いものとして列挙する以前のレイアウトのフォルダーです。
`✗` 行の後に、`Note:
<harness> - no install record matched` 行が、残した共有フォルダーと、それでも削除したものを挙げます。
プロジェクトスコープのハーネスでは、`apothem update` を実行する前に、`--project` がインストール先のフォルダーを指していることを確認するようにも伝えます。別のフォルダーで update を実行すると、そこにインストールされるためです。フォルダーは、出力される他のコマンドと同じように引用符で囲まれるか、その引用符で表せない場合は、下記のデータストアの `Warning:` 行と同じ場合に、そのままの形で名前が挙げられます。
アンインストールが残した Apothem マーカー（後に END のない BEGIN マーカー、Apothem のマーカー間にある 2 つの異なるブロック、または Apothem が配置できないマーカーの組）について警告がファイルの名前を挙げる場合、`✗` 行は、update の前にそのファイルを修正するよう伝え、そのマーカーの種類に応じた助言を添えます（[完了しなかったアンインストール](#an-uninstall-that-did-not-finish) を参照）。プロジェクトスコープのハーネスでは、`Note:` 行もそう伝えます。
2 つの異なるブロックを保持する `CLAUDE.md` またはプロファイルドキュメントだけは、その行から除かれます（下記を参照）。
`Note:` 行は `--quiet` でも、エラーストリームに出力されます。
`--format json` の出力では、そのハーネスの `uninstall` 行は `"outcome": "error"` を持ち、メッセージにその注記を含み、`"detail": {"kept_reason": "no-record"}` を持ちます。
`apothem update` はこのリリースのファイルを書き込んで記録するため、それを実行してから再度 `apothem uninstall` を実行すると処理が完了します。
その前に、列挙されたファイルのうち、あなたが編集または追加したものをコピーしてください。update は書き込むパスを上書きし、まるごと書き込む各 Apothem フォルダーのエントリを置き換えます（どちらも先に `~/.apothem/backups/` の下にバックアップしますが、元に戻すものは何もありません）。
警告が Apothem マーカーについて名前を挙げるファイルも、先に修正してください（[完了しなかったアンインストール](#an-uninstall-that-did-not-finish) を参照）。
以前のリリースが記録したインストールでは、Apothem のフォルダー内にある、Apothem が決して書き込まない名前のファイルはあなたのものです。変更されたファイルまたはあなたのファイルを示す `Warning:` 行の下に列挙され、残り、アンインストールはそれでも完了します。

その場所での最新の記録が完了したアンインストールである場合（たとえば、その後のインストールが自身を記録する前に停止した場合）、アンインストールは、ホームディレクトリ内の共有フォルダーを除き、各パスをこのリリースが書き込む内容と比較します。共有フォルダーは、記録がない場合と同様にそのまま残ります（[ホームディレクトリ内の共有フォルダー](#ホームディレクトリ内の共有フォルダー) を参照）。
ファイルがまったく同じバイト列を持つ場合にのみそのファイルを削除し、ファイルを含まないフォルダーを削除します。
そのインストールがどのインタープリターを見つけたかを示すものは何もないため、インタープリターのパスを保持するファイル（ステータスラインのコマンド、コンフォーミティゲート内のコメント）は決して同じとはみなされず、残ります。
ゲートが残っている間、そのハーネスはインストール済みとして読み取られるため、そのファイルを確認して手作業で削除してください。
それ以外もすべて残り（あなたのファイル、あなたが編集した Apothem のファイル、別のプログラムが書き込んだキャッシュ）、`Warning:` 行が出力され、アンインストールは完了します。
他のファイルが削除されたフォルダーに残ったファイルは、変更されたファイルまたはあなたのファイルを示す行の下に列挙されます。それ以外のパスは、どのインストール記録にも列挙されておらず、このリリースが書き込む内容と一致せず、不要になったら手作業で削除できる旨を示す行の下に列挙されます。
リンクの向こうにあるまったく同じバイト列のファイルは、記録されたインストールで Apothem 自身のファイルがリンクの向こうにある場合と同様に、アンインストールを停止させます（下記を参照）。
そのようなアンインストールが完了しない場合（たとえば、削除できなかったファイルがある場合）、そのハーネスはインストール済みとして読み取られたままで、アンインストールを再度実行すると同じように動作します。自身の変更を取り消した失敗したインストールの後でも同様です。
ロールバックの後、または完了しなかったアンインストールしかない場合、そのようなパスは、記録がない場合と同様にアンインストールを停止させます。

上記の場合のように、その場所にインストールが記録されていない場合、アンインストールは Apothem の管理ブロックもその場所に残します。Claude Code では `~/.claude/CLAUDE.md` に、Open-Claw、OpenCode、Qwen Code など 1 つの設定ファイルで構成されるツールでは、そのフォルダー内のプロファイルドキュメント `apothem/rules/00-apothem-profile.md` にあるものです。
どのインストールがそのブロックを書き込んだかを示すものは何もないため、ファイルはそのまま残り、`Warning:` 行がその名前を挙げます。この警告はアンインストールを停止させません。
ブロックが不要になった場合（Claude Code は引き続き `CLAUDE.md` を読み込みます）、警告が示す番号付きの修正を使って手作業で取り除いてください。たとえば "Fix A: A1. Change
line 5: add a word inside its comment. Apothem then finds no block of its own
in this file." です（[番号付きの修正に従う](/docs/install/troubleshooting#follow-a-numbered-fix) を参照）。
警告はブロックをその行で示し、修正はその BEGIN マーカーの行をその場で変更するため、あなたの行の内容が変わることはありません。その下にある、END マーカーの行までの古い Apothem のテキストは、その後あなたが手作業で削除するものになります。
ブロックの上にあるあなたの BEGIN マーカーや、あなたが引用するマーカーの組の中にあるものは、ブロックの一部ではありません。ブロックが取り除かれると Apothem のものとして読み取られてしまうため、修正はそのような行もそれぞれ変更します。
そのファイルが Apothem のマーカー間に 2 つの異なるブロックを保持している場合（たとえば、コードの外にあるあなたのマーカーの組）、最初の BEGIN マーカーから次の END マーカーまでを削除すると、あなたのテキストも一緒に削除されてしまうため、警告は代わりにそのようなファイル向けのテキストを示します（[完了しなかったアンインストール](#an-uninstall-that-did-not-finish) を参照）。各ブロックをその行で示すか、Apothem のブロックとその周囲のマーカー行を示し、あなた自身のテキストを残したままファイルを修正する方法を伝えます。
Apothem のブロックとその周囲のマーカー行を示す場合は、続いて、不要であれば Apothem のブロックを手作業で削除するよう伝えます。
2 つ以上のブロック全体を示す場合は、代わりに `apothem update` を実行してから、再度 `apothem uninstall` を実行するよう伝えます。そのテキストが示さない、Apothem のブロックの上にあるあなたの BEGIN マーカーと下にある END マーカーは、Apothem のブロックを手作業で削除すると 1 つのブロックになり、次の update がそれらの間の行を置き換えてしまうためです。
再度実行したアンインストールは、それらのマーカー行を最初に挙げます。
この警告もアンインストールを停止させず、`✗` 行はそのファイルの名前を挙げません。
`apothem update` を実行する前にも修正してください。update はそれを修正しません。

共有の作業ディレクトリのメモリ、コンテキスト、学習ストアは、このハーネスがそのディレクトリに
インストールされた最後のハーネスである場合にのみ、バックアップしたうえで削除
されます。アンインストールは、インストール時に記録された場所でそれらを削除する
ため、インストールがそれらを書き込んだ場所に関係なく見つけられます（`workspace`
プロファイルのフィールドを参照）。`plans/` ディレクトリは決して削除されません。
ここでは、フォルダーがもはや存在しないインストール（削除されたプロジェクト）も、下記の共有フォルダーの場合とは異なり、ストアを使用しているものとして数えられ、アンインストールはその旨を伝えます（下記を参照）。

`--yes` が指定されない限り、確認を求めます。プロンプトを表示できない場合 —
`--format json`（プロンプトのテキストが単一の JSON ドキュメントを壊してしまうため）
または非対話型のシェル（TTY なし）— の場合、`--yes` が指定されない限り、
コマンドは処理を始める前に、構造化された `uninstall.confirmation_required`
エラー（終了コード 1）で拒否します。選択したハーネスがインストールされていない
場合、コマンドは成功し（終了コード 0）、通常の出力では
`NAME is not installed; nothing to remove.` と表示します（`NAME` はハーネス ID です）。
Apothem があなたのテキストと区別できないマーカー行を持つファイルは、インストール記録がそれを列挙している間、またインストール台帳が読み取れない間も、インストール済みとして数えられます。その場合、アンインストールは、ブロック全体を持つファイルの場合と同様に、ハーネスをインストールされていないと報告するのではなく、破損した台帳で停止し（終了コード 1）、その名前を挙げます。

ホームディレクトリ内のツールのフォルダーをリンクがその外へ導いている場合、たとえば `~/work` が別のドライブにリンクされている `~/work/tool` のような場合、アンインストールは何かを削除する前に停止します。
Windows では、ジャンクションもリンクとして数えられます。
対話型の実行では、コマンドは先に確認を求めません。
確認を求められない実行（JSON 出力、または端末なし）は、それでも先に停止して `--yes` を求めます。それを渡すと、リンクのエラーが表示されます。
エラーには `uninstall
refused: target path crosses a link` が含まれ、リンクとその導く先のフォルダーの名前を挙げ、何をすべきかを伝えます。コマンドは 1 で終了します。
リンクがホームディレクトリ内のフォルダーを指すようにするか、リンクをフォルダーそのものに置き換えてから、アンインストールを再度実行してください。
ホームディレクトリの外のパスとして指定したフォルダーは、たどられます。

インストールルートの `.apothem/` 配下にある共有データストア（`memory/`、`contexts/`、`learning/`）は、同じルートにある別のインストール済みハーネスがそれらをまだ使用している間は残ります。
削除するハーネスがそのルートで最後の 1 つである場合、コマンドは各ストアをまず Apothem のバックアップルート（`~/.apothem/backups/`）へコピーし、その後、中身ごとストアを削除します。
あなたが `plans/` に保管しているものは、決して削除されません。

ストアを保持しているインストールが、もはや存在しないフォルダーにあるものだけの場合、コマンドはストアを残し、そのようなインストールの 1 つと、それを解放する手順を挙げる `Warning:` 行を出力します。
空の状態で作り直したフォルダーでのアンインストールは何もインストールされていないと判断するため、手順ではまず、そのインストールが使ったのと同じ `--profile` を使って、そこにツールを再度インストールします。
ストアはそのフォルダーの外にあるため、そのインストールのプロファイルがストアを現在の場所に置いたのです。
それを指定しないインストールは独自のストアを書き込み、その後のアンインストールは、これらのストアを使用するインストールがない状態で残してしまいます。
Apothem はインストールがどのプロファイルを使ったかを記録しないため、警告は、あなたが埋めるための `--profile <the profile it used>` を出力します。
プロジェクトにインストールされたツールの場合、手順は次のとおりです。

```bash
mkdir -p /path/to/old-project
apothem install --harness cursor --project /path/to/old-project --profile /path/to/that-profile.yaml
apothem uninstall --harness cursor --project /path/to/old-project --yes
```

警告は、Windows ではフォルダーを二重引用符で、それ以外では一重引用符で囲みます。
その引用符でフォルダーを表せない場合、警告は同じ手順を文章で示し、フォルダーをそのままの形で挙げます。
Windows でそうなるのは、次の場合です。フォルダーが `$`、バッククォート、`%`、`!`、ストレートまたはカーリーの二重引用符、あるいは制御文字を含む場合（Windows のシェルは二重引用符の中でもこれらを変えてしまいます）。空白を含まないフォルダーが `&`、`^`、`|`、`<`、`>` を含む場合（PowerShell と Git Bash はそれをインストーラーの `apothem.cmd` に引用符なしで渡すため、コマンドプロンプトがそれらに作用します）。あるいは、ネットワーク共有の先頭（`\\server\share`）のように 2 つのバックスラッシュが連続する場合（Git Bash はそれを 1 つとして読み取ります）。
それ以外では、フォルダーがストレートまたはカーリーの一重引用符（シェルはカーリーのものでも一重引用符を終えることがあります）、制御文字、連続する 2 つのバックスラッシュ、または末尾のバックスラッシュを含む場合です（fish は一重引用符の中で 2 つを 1 つとして読み取り、そこで末尾にあるものは閉じ引用符をエスケープします）。

ホームディレクトリにインストールされたツールの場合、警告は同じ手順を文章で示します。それがインストールされたフォルダーは、出力されるコマンドでは再現されない環境変数（たとえば `XDG_CONFIG_HOME`）に由来している可能性があるためです。
ストアは、ほかにそれを使用するインストールがない場合、そのアンインストールとともに削除されます。
ストアを手作業で削除することもできます。

## ホームディレクトリ内の共有フォルダー

複数のインストールが、ホームディレクトリ内の 1 つのフォルダーを使用することがあります。スキルフォルダー（`~/.agents/skills/`、または `~/.codebuddy/skills/`、`~/.kiro/skills/`、`~/.trae/skills/`）と、`~/.config/apothem/rules/` および `~/.config/apothem/templates/` です。
どのアダプターがどれに書き込むかは、[install](/docs/cli-reference/install#folders-in-your-home-directory) のページに記載されています。
Apothem は各フォルダーをどのインストールが使用しているかを記録しており、アンインストールは 1 つのルールに従います。そのフォルダーをまだ使用している他の Apothem インストールがない場合にのみ、フォルダーを削除します。

- 1 つのツールをアンインストールしても、別のインストールがまだスキルを使用している間はスキルが残り、その旨が表示されます。
  2 つのプロジェクトにインストールされた 1 つのツールは 2 つのインストールとして数えられるため、プロジェクト A からそれをアンインストールしても、プロジェクト B がまだ使用している間はフォルダーが残ります。最後のアンインストールがそれらを削除します（以下の 2 つ目の例を参照）。
- 各インストールの実行時にホームフォルダーがどのように表記されていても、1 つのフォルダーは 1 つのフォルダーとして数えられます。
  ホームフォルダーがリンクである場合、たとえば Fedora Silverblue で `/home` が `/var/home` を指している場合や、Windows のユーザープロファイルがジャンクションの向こうに移動されている場合、リンク経由で行ったインストールと、リンク先のフォルダー経由で行ったインストールは同じフォルダーを使用します。
  そのようにインストールされた 2 つのツールは 2 つのインストールであり、一方をアンインストールしても、もう一方のためにフォルダーは残ります。
  両方の方法でインストールされた 1 つのツールは 1 つのインストールです。ホームをどちらの表記にしてアンインストールしても、どちらのインストールが書き込んだものも、他のインストールが使用していないフォルダーも削除されます。
  そのアンインストールが完了前に停止した場合、停止の原因を修正してアンインストールを再度実行するまで、両方のインストールが記録されたまま残ります。
  アンインストールがインストールを見つけるのは、ホームが、そのツールのインストールが使った表記のいずれかである場合だけです。それ以外の表記では、削除するものが何も見つかりません。
- 削除されるのは、そのインストール自身の記録に列挙されているものだけです。
  フォルダーが管理されるようになる前に行われたインストールにはそのような記録がないため、それをアンインストールしてもホーム内の何も削除されません。
  あなたがフォルダーに追加したファイルは残り、Apothem のスキルの名前を持ち、Apothem が書き込んだものではないフォルダーも残ります。
- プロジェクトフォルダーがもはや存在しないインストールは無視されるため、削除されたプロジェクトがフォルダーをいつまでも保持し続けることはありません。注記はその名前を挙げます。
- フォルダーを使用し得るインストールの記録が読み取れない場合、アンインストールは何も削除する前にエラーとともに停止し、そのインストールは記録されたまま残ります。
  読み取れない記録を修復または移動してから、コマンドを再度実行してください。これらのフォルダーに一度も書き込まないツールの破損した記録は無視されます。
- 最後の使用がなくなると、空になったフォルダーも削除されます。
  各フォルダーは、削除される前に `~/.apothem/backups/` の下にバックアップされます。

各アンインストールは、フォルダーごとに 1 つの `Note:` を出力します。たとえば `Note: <harness> -
~/.agents/skills/ was kept: still used by <harness> (/path/to/project)`、または `was removed: no other Apothem install uses it` です。
`--format json` のエンベロープでは、各注記は `"outcome": "advisory"`、`"operation": "shared_root"`、および `retained` または `released` に設定された `"role"` を持つ `warnings` エントリです。
これは `path`、`holders`（フォルダーを保持しているインストール）、`stale`（無視されたインストール）、および `kept` と `total`（保持された記録済みエントリと、インストールが列挙したエントリ）を含みます。

アンインストールは、意図的にその場に残した各ものについても `Warning:` 行を出力します。
Apothem はシンボリックリンクや Windows のジャンクションを通して何かを削除することはないため、削除するフォルダー内のリンクは残り、リンク経由でたどり着く以前のリリースの残りのフォルダーも残ります。
同じリンクのために、または同じ理由（Apothem が書き込んだものではない、インストール記録にない）で残されたパスは、その数とともに 1 行として出力されます。
残されたパスを示す行の下には、残された各ファイルが列挙されます。残されたフォルダー内のファイルも含まれます（何も入っていない残されたフォルダーは、それ自体が列挙されます）。
Apothem が書き込んだものの削除できなかったファイルは、残されたファイルとしてではなく、それを報告する `✗` 行の下に列挙されます。
`--quiet` では、これらの行はアンインストールが完了しない場合にのみ、`✗` 行とともに標準エラーに出力されるため、その助言が対象とするパスが見える状態に保たれます。
ファイルに残された Apothem マーカーを挙げる行は、アンインストールが完了した場合でも、`--quiet` では標準エラーに出力されます。ツールはそのマーカーの下にある古い Apothem のテキストを引き続き読み込み、後のインストールは両方を残し、`verify` はあなたがそれらを削除するまで失敗するためです。
`--format json` のエンベロープでは、そのような各行は、`"outcome": "warning"`、行の `message`、`count`（対象となるパスの数）、`paths`（その各パス）、そして残されたパスについては `files`（残された各ファイル）を持つ 1 つの `warnings` エントリです。
これらの警告はアンインストールを停止させません。
停止させるのは 4 種類です。以前のリリースが記録したインストールのファイルで、このリリースが書き込む内容と異なるもの、記録がまったくないインストールのファイル（[アンインストールが削除するもの](#what-an-uninstall-removes) を参照）、Apothem のマーカー間に 2 つの異なるブロックを保持するファイル、そして Apothem があなたのテキストと区別できないマーカー行を持つファイルです（[完了しなかったアンインストール](#an-uninstall-that-did-not-finish) を参照）。

リンク経由でたどり着く Apothem 自身のファイルは別です。ほとんどのツールはそれらを引き続き読み込むため、アンインストールは完了しません。
（OpenClaw は、アンインストールがそのフックエントリから Apothem のパスを取り除いた後は、ルールファイルを読み込まなくなるため、OpenClaw では `✗` 行がそう伝えるのは、まだ読み込んでいる間だけです。[OpenClaw](/docs/harnesses/open-claw#uninstalling) を参照してください。）
たとえば `~/.claude/rules` が、Apothem が書き込んだルールをまだ保持している dotfiles フォルダーへのジャンクションだとします。コマンドは、リンクと残したパスの数とともに `✗ <harness> uninstall did not finish:` を出力し、インストールを記録したまま残し、`2` で終了します。
リンクを、同じファイルを保持する実際のフォルダーに置き換えてから、コマンドを再度実行してください。
記録に書き込んだファイルが列挙されているインストールでは、あなた自身のファイル、またはあなたが編集した Apothem のファイルだけを保持するリンク先のフォルダーは、アンインストールを停止させません。リンクは警告とともに残り、アンインストールは完了します。
以前のリリースが記録したインストールでは、このリリースが書き込む名前にあるリンクの向こうのファイルは、編集されているかどうかに関係なく、アンインストールを停止させます。そのリリースが書き込んだものと区別するものが何もないためです。
リンクを、同じファイルを保持する実際のフォルダーに置き換えてから、上記のそのようなインストール向けの手順に従ってください。編集したファイルをコピーし、警告が Apothem マーカーについて名前を挙げるファイルを修正し、`apothem update` を実行してから、再度アンインストールします。

削除の手順がエラーを報告した場合（たとえば、パスがホームフォルダーの外へ導かれるインストール済みファイル）、コマンドは `Uninstalled` の代わりに `✗ <harness> uninstall
did not finish: <reason>` を、理由ごとに 1 回、それが当てはまるパスの数とともに出力します。
ホームのフォルダー内のリンクがそれらのパスをその外へ導いている場合（`target escapes the allowed materialization root`）、その行はリンクとその導く先のフォルダーの名前も挙げ、リンクを実際のフォルダーに置き換えるよう伝えます。2 つのリンクの向こうにあるパスでは 2 行になります。
リンクには、その場に残されたという警告も引き続き出力されます。
インストールは記録されたまま残るため、コマンドを再度実行すると、最初の実行が残したものが削除されます。
保持に関する注記は出力されません。それらが説明するフォルダーは解放されていないためです。
JSON 出力では、そのハーネスは `"outcome": "error"` と `"operation": "uninstall"` を持つ `results` 行を得て、その後に失敗した手順ごとに 1 行が続きます。
理由が 1 つのリンクを挙げる場合、その行はそれを `detail.symlink` に、その導く先のフォルダーを `detail.leads_to` に持ちます。
手順の行は、残したファイルを `files` として、Apothem が書き込んだものの削除できなかったファイルを `stuck` として列挙します。
アンインストールが手順の失敗前にファイルを削除していた場合、または別のハーネスが削除された場合、エンベロープの `status` は `"partial"`、終了コードは `2` です。それ以外の場合、`status` は `"error"`、終了コードは `1` です。
トップレベルの `error` は `null` のままです。理由は `results` にあります。
例外で停止したアンインストール（たとえば、バックアップを書き込めない場合）は、停止する前にファイルを削除していた場合、または `openclaw.json` などのファイルから Apothem のエントリやブロックを取り除いていた場合は `✗ <harness> uninstall
stopped after removing files:` を（何も変更していなかった場合は `failed:` を）メッセージとともに出力し、そのメッセージを持つ `results` 行を得て、その後に、それより前に失敗した手順ごとに 1 行が続きます。
停止する前に手順が失敗していた場合、またはアンインストールを未完了のままにするもの（リンクの向こうにある Apothem 自身のファイル、以前のリリースが記録したインストールのファイルでこのリリースが書き込む内容と異なるもの、記録がないインストールのファイル、Apothem のマーカー間に 2 つの異なるブロックを保持するファイル、または Apothem があなたのテキストと区別できないマーカー行を持つファイル）を見つけていた場合、上記と同様に理由ごとに `✗ <harness> uninstall did not finish:` 行が続き、同じテキストが行のメッセージの末尾に追加されます。
記録がないインストールでは、その後に `Note:` 行が続き（プロジェクトスコープのハーネスでは `--project` フォルダーの確認を含みます）、行の `detail` は、[アンインストールが削除するもの](#what-an-uninstall-removes) で説明したとおり `"kept_reason": "no-record"` を持ちます。
それらの理由と、それより前に失敗した手順が 1 つのリンクを挙げる場合、行はそれを `detail.symlink` に、その導く先のフォルダーを `detail.leads_to` に持ちます。
先にファイルを削除または変更していた場合、リンクの向こうに Apothem 自身のファイルを見つけた場合、以前のリリースのインストールまたは記録がないインストールのファイルを残した場合、Apothem のマーカー間に 2 つの異なるブロックを保持するファイルや Apothem があなたのテキストと区別できないマーカー行を持つファイルを残した場合、または別のハーネスが削除された場合は、`status` `"partial"` で `2` で終了します。それ以外の場合は `1` です。
Open-Claw、Antigravity、Kimi Code のアンインストールの最初の手順の中で発生した予期しないエラー（バックアップを書き込めないなどの例外）は、その手順が行ったことを何も報告しません（[完了しなかったアンインストール](#an-uninstall-that-did-not-finish) を参照）。その手順が何を変更していたかに関係なく、アンインストールは `failed:` を出力し、`1` で終了します（別のハーネスが削除された場合は `2`）。
Open-Claw のルールファイルの手順が代わりにエラーを報告した場合（書き換えられないルールファイル、またはコメントを含む `openclaw.json`）、それは上記と同様に失敗した手順です。アンインストールは `did not finish:` を出力し、その手順のバックアップとともに自身を未完了として記録し、その手順がファイルを変更していた場合、リンクの向こうに Apothem のルールファイルを見つけた場合、または別のハーネスが削除された場合は `2` で、それ以外の場合は `1` で終了します。
`Ctrl+C` は `Aborted!` を出力し、それまでにアンインストールが何を削除していたかに関係なく `1` で終了します。
拒否されたアンインストール（たとえば、フォルダーをホームディレクトリの外へ導くリンク）は何も削除せず `1` で終了します。その行は、そのリンクを `detail.symlink` に、その導く先のフォルダーを `detail.leads_to` に挙げ、その後に拒否された手順の行が続きます。

### 完了しなかったアンインストール [#an-uninstall-that-did-not-finish]

アンインストールが完了しない場合、インストール台帳に `uninstall` 記録の代わりに `uninstall-incomplete` 記録を追加します。
それが起こるのは、手順が失敗した場合、Apothem 自身のファイルがリンクの向こうに残る場合、ファイルが Apothem のマーカー間に 2 つの異なるブロック、または Apothem があなたのテキストと区別できないマーカー行を保持する場合（下記を参照）、以前のリリースが記録したインストールのファイルがこのリリースが書き込む内容と異なる場合、そしてインストールに記録がない場合です。
最後の 4 つは、何も削除されなかった場合でも、また、それらが挙げるものを修正する前の 2 回目の実行でも、`status` `"partial"` で `2` で終了します。
最後の 2 つは、`apothem update` の後にのみ完了します（[アンインストールが削除するもの](#what-an-uninstall-removes) を参照）。
例外または `Ctrl+C` で停止したアンインストールは、停止した手順に応じて次のものを追加します。

- Open-Claw の最初の手順（各ワークスペースのルールファイルから Apothem のブロックを取り除く）、または Antigravity と Kimi Code の最初の手順（以前のレイアウトが残したものを削除する）の中では、何も追加しません。その手順がそれまでに変更したファイルについても同様で、そのバックアップは `~/.apothem/backups/` の下に残りますが、それらを `backups prune` から守る記録はありません。
- Open-Claw、OpenCode、Qwen Code など 1 つの設定ファイルで構成されるツールの設定ファイルから Apothem のエントリを取り除く手順の中では、Open-Claw の最初の手順がルールファイルから Apothem のブロックを取り除いていたか、ルールファイルをバックアップしていた場合にのみ記録を追加し、それ以外の場合は何も追加しません。その手順がリンクの向こうに Apothem のルールファイルを見つけた場合も同様です。
- インストール記録に列挙されているものを削除する手順（OpenCode 以外のすべてのアンインストールの最後の手順）の中では、何も変更していなかった場合でも記録を追加します。
- OpenCode のアンインストールがその後に行う手順（そのフォルダーの別の表記で記録されたインストールを閉じる手順。たとえば `XDG_CONFIG_HOME` が、`~/.config` のリンクが指すフォルダーを指定している場合）の中では、それ以上何も追加しないため、そのインストールは記録されたまま残ります。
  後の実行でも、まだそれは閉じられません。そのフォルダーの Apothem のファイルがなくなると、OpenCode はそこにインストールされていないものとして読み取られるため、`uninstall` はそれをスキップし、`status`、`verify`、`rollback` もそのインストールを認識しません。
  それを閉じるには、そのフォルダーに OpenCode を再度インストールしてから、アンインストールします。リンクされたフォルダーの外にあるプロファイルを使って `apothem install --harness opencode --profile PATH` を実行し（`apothem profile init --profile PATH` で作成できます）、続いて `apothem uninstall --harness opencode` を実行します。

何も追加されない場合、台帳は元のままです。
いずれの場合もインストールは記録されたまま残ります。
最後の場合を除き、`apothem status`、`verify`、`rollback` は引き続きそれを認識し、インストールが書き込んだものが書き込んだときのまま残っている間、そのハーネスはインストール済みとして読み取られる（下記を参照）ため、`uninstall` を再度実行すると処理が完了します。
記録がないインストールには、保持する記録がありません。ディスク上のそのファイルだけがハーネスをインストール済みとして読み取らせ、`rollback` にはロールバックするものがありません。
その場所でのそのハーネスの `install`、`update`、`rollback`、または完了した `uninstall` は状態を置き換えます。残りのファイルを手作業で削除することも同様です。Apothem のファイルが書き込まれたときのまま 1 つも残っておらず、その `.apothem` フォルダーに何も残っていなければ、フォルダーにほかに何があっても、そのハーネスはインストールされていないものとして読み取られます。
その後、ハーネスがインストール済みかどうかを確認する最初のコマンド（`status`、`verify`、`uninstall`）が、そのインストールを閉じる `uninstall` 記録を追加します。
ただし、完了したアンインストールの後は、インストールが書き込んだファイルを列挙する記録がないため、そこで状態を置き換えるのは、インストール、update、または完了するアンインストールだけです。
`backups prune` は、その記録が属するインストールが保持されている間、その記録と、それが参照するバックアップを保持します。
完了したアンインストールの後は、その記録をそのアンインストールの記録とともに保持するため、アンインストールを再度実行しても同じように動作します。

引き続き数えられるもの: インストールが書き込んだファイル全体（変更されていない間。以前のリリースが記録したインストールでは、存在する間）、Apothem が `.apothem` の下でインストール先とするフォルダー内のあらゆるもの、そして Apothem があなた自身のテキストの隣に管理ブロックを保持するファイル（その周りにあなたが何を書いていても、ブロックがまだその中にある間）。
それらのファイルは、`CLAUDE.md`、共有プロファイルが投影されるプロファイルドキュメント、各 OpenClaw ワークスペースのルールファイル、そして `AGENTS.md` と、インストールがブロックを追加するその他の命令ファイルです。

管理ブロックは、`<!-- BEGIN APOTHEM MANAGED BLOCK -->` マーカーから次の `<!-- END APOTHEM MANAGED BLOCK -->` マーカーまでで、それぞれが独立した行にあります。
Apothem は、Markdown ビューアーと同じように、マーカーをそのような形で、かつコードの外にある場合にのみ読み取ります。コードとは、フェンスで囲まれたコードブロック（同じ文字で、少なくとも同じ長さで、後に何もないフェンスで閉じられるもの）、または空行の後でリスト項目（または余白）より 4 桁深くインデントされたコードです。
そのため、文中やコード例であなたが引用するマーカーはあなたのテキストであり、別々の 2 つのコードブロックであなたが引用する BEGIN マーカーと END マーカーはブロックになりません。
Apothem は、プロファイル内のルールが開いたままにしたコードフェンスを、書き込むブロックの末尾で閉じます。以前のリリースが書き込んだブロックでは、そのようなフェンスが END マーカーを隠すのは、別のマーカーの組が続く場合だけです（下記を参照）。
ファイルの末尾まで開いたままにしたフェンスは、いくつあってもテキストとして読み取られます。ただし、その上にあるコード外の BEGIN マーカーの END マーカーがコード内にあり、その後に別のマーカーの組が続く場合は除きます。
ファイルの先頭にあるバイトオーダーマーク（一部の Windows エディターが保存するもの）は、1 行目のマーカーを隠しません。
HTML ブロックや引用ブロックの中にあるマーカー、またはテキストが左余白で続くリスト項目の後にあるマーカーは、それでも Markdown ビューアーとは異なる形で読み取られることがあります。

Apothem のブロックがあなたのコードブロックの中にある場合（その上で開いたままにされ、下にあるフェンス、またはブロック内の閉じ行で閉じられるフェンス）、あるいは BEGIN マーカーとその END の間にあるコードブロックが、その後に別のマーカーの組を伴ってその END を隠す場合、Apothem は自身のブロックとあなたの例を区別できません。
アンインストールはそのようなファイルをそのまま残し、インストールの残りを削除し、完了しません。`✗ <harness> uninstall did not finish:` の後に "1 file(s) hold marker
lines Apothem cannot tell from your text, so Apothem left them as they are;
fix the marker lines each warning names, keeping your own text, then run
apothem uninstall again" を出力し、2 回目の実行も含めて `2` で終了します。
インストール記録は残るため、後のインストールもそのファイルをそのまま残し、次のアンインストールは再びその名前を挙げます。
その警告は、ファイル内の各マーカーの組をその行で示し、マーカーの組を開始しないコード外の各 BEGIN マーカーも示します。
インストール記録がない場合、警告が出るのは、そのようにして END マーカーが隠されている BEGIN マーカーだけです。あなたのコードブロックの中にある組はその場合あなたのテキストであり、アンインストールは、そのマーカーと、記録が示さないパスについて未完了のままです。
警告は続いて番号付きの修正を示し、"Then run the
uninstall again." で終わります。たとえば "Fix A: A1. Change line 6: add a word inside
its comment. Apothem then finds no block of its own in this file." です。
あなたが変更した行の下にある、END マーカーの行までの古い Apothem のテキストは、その後あなたが手作業で削除するものになります。
修正が複数ある場合は、当てはまる場合の修正を選び、その各手順を示された順序で行ってください。そのファイルに残ったマーカーの組は、あなたのものも含めてアンインストールを未完了のままにするため、各修正は、Apothem のブロックと呼ばないすべての組の BEGIN マーカーの行と、組を開始しない各 BEGIN マーカーを変更します（[Apothem が自身のブロックをあなたのテキストと区別できない](/docs/install/troubleshooting#apothem-cannot-tell-its-block-from-your-text) を参照）。
ファイルにそのような組がなくなれば、アンインストールを再度実行すると完了します。

END マーカーがなくなっている場合、Apothem のテキストがどこで終わり、あなたのテキストがどこから始まるかを示すものが何もないため、アンインストールはファイルをそのまま残し、警告でその名前を挙げて完了します（記録がないインストールなど、ほかに未完了にするものがない限り）。完了しなかったアンインストールの後の再試行も同様です。
Apothem のブロックが取り除かれた後に END のない BEGIN マーカーが残る場合（あなたの行、または END マーカーを失った古いブロックの残り）、アンインストールはそのファイルとマーカーの行も挙げ、その行を変更する（コメントの中に単語を追加する）番号付きの手順を示すため、それはもはやマーカーとして読み取られません。インストールはそれをそのまま残し、ツールはその下のテキストを引き続き読み込みます。
その下にある古い Apothem のテキストは、その後あなたが手作業で削除するものになります。
`install` または `update` は、そのようなマーカーの後のテキストをそのまま残し、Apothem のブロックをそれとは別に書き込み、ファイルの名前を挙げます。`verify` はマーカーが変更されるまで失敗します（[ファイルに END マーカーのない Apothem の BEGIN マーカーがある](/docs/install/troubleshooting#a-file-has-an-apothem-begin-marker-with-no-end-marker) を参照）。

マーカー間に 2 つの異なるブロックを保持するファイル（コードブロックの外であなたが引用するマーカーの組、あなたが END マーカーを戻した古いブロック、または 2 回目に貼り付けたブロック）はそのまま残されて名前が挙げられ、アンインストールは完了しません。`✗ <harness> uninstall did not finish:` の後に "1 file(s) hold two different blocks between Apothem's markers, so
Apothem left them as they are; fix each as its warning says, keeping your own
text (follow one of its numbered fixes, which change marker lines in place),
then run apothem uninstall again" を出力し、2 回目の実行も含めて `2` で終了します。
その警告は、install と update と同様に各ブロックをその行で示し、各ブロックについて、それが Apothem のブロックである場合の番号付きの修正を 1 つ示します。その修正は、他の各ブロックの BEGIN マーカーの行を変更し、そのテキストを残します（Apothem のフロントマターで始まるファイルでは、Apothem のブロックはそのすぐ下にあるものです）。
あなたの組を残すために Apothem のブロックを削除しないでください。次のアンインストールが、残った 1 つのブロック、つまりあなた自身のものを取り除いてしまいます。
`apothem update` はそのようなファイルを修正しません。2 つのブロック全体を持つファイルを同じ警告とともにそのまま残し、`verify` はあなたが修正するまで失敗します（[ファイルが Apothem のマーカー間に 2 つのブロックを保持している](/docs/install/troubleshooting#a-file-holds-two-blocks-between-apothems-markers) を参照）。

Apothem のブロックの上にある BEGIN マーカーと下にある END マーカーは、Apothem のブロックが取り除かれて初めて現れる 2 つ目のブロックを作ります。
その場合、アンインストールの警告は Apothem のブロックとそれら 2 つのマーカー行を挙げ（たとえば "once the block
from line 5 to line 36 is out, the BEGIN marker at line 2 and the END marker at
line 39 make another"）、Apothem のブロックを削除しないよう伝えます。次の実行が 2 行目から 39 行目までを Apothem のブロックとして読み取ってしまうためです。
その 1 つの修正は、代わりにその BEGIN マーカーの行を変更し、あなた自身のテキストを残します。下にある END マーカーは、その後何とも組になりません。その BEGIN マーカーが古い Apothem のブロックの残りである場合、その下にある古い Apothem のテキストは、その後あなたが手作業で削除するものになります。
両方の行を 1 つのコードブロックに入れないでください。そのコードブロックは Apothem のブロックも含んでしまいます。
`apothem update` もそのようなファイルを修正せず、`verify` はあなたが修正するまで失敗します。
行番号は、CRLF や LF と同様に、単独の CR も行の終わりとして数えます（[ファイルに END マーカーのない Apothem の BEGIN マーカーがある](/docs/install/troubleshooting#a-file-has-an-apothem-begin-marker-with-no-end-marker) を参照）。

アンインストールの次の手順が `apothem update` の実行であり、警告が Apothem マーカーについてファイルの名前を挙げる場合（`--format json` のエンベロープでは、その `detail` が `marker_left` を持ちます）、`✗` 行と、以前のリリースのため、または記録がないために残す各パスの警告は、そのマーカーの種類に応じた助言とともに、まずそのファイルを修正するよう伝えます。

台帳が `uninstall-incomplete` 記録を受け取れない場合（たとえば、ディスクがいっぱいの場合）、台帳は元のままで、`Warning:` 行が台帳と、アンインストールが作成したバックアップのフォルダーの名前を挙げます。それらのバックアップを `backups prune` から守る記録はないため、必要なものはコピーしてください。
その未完了の処理の記録がないため、コマンドを再度実行すると、ハーネスがインストールされていないと判断して何も削除しないことがあります。その場合は、`✗` 行と `Warning:` 行が列挙したファイルを手作業で削除してください。
ハーネスがインストール済みとして読み取られている間は、コマンドを再度実行すると以前と同じように動作します。インストール記録に照らして、または、完了したアンインストールの後にインストールが記録されていない場合は、その処理と同じ方法で動作します（[アンインストールが削除するもの](#what-an-uninstall-removes) を参照）。
完了したアンインストールの `uninstall` 記録をディスクに保存できない場合、アンインストールはそれを台帳から再び取り除き、未完了として終わります。
台帳がまだ完了したアンインストールで終わっている場合は、同じ種類の警告とともに完了します。記録がそれでも台帳に残った場合、またはアンインストールが完了したアンインストールに続くものだった場合です。
記録が保存された後の割り込み（`Ctrl+C`）は、アンインストールを完了した状態のまま残します。

見つけられないインストールのためにフォルダーが残っている場合、注記はその名前を挙げます。
プロジェクトフォルダーが削除されていた場合、そのインストールは無視され、フォルダーは次のアンインストールで削除されます。
プロジェクトは存在するものの、そのルールファイルから Apothem ブロックを手作業で削除した場合、`uninstall` はそのハーネスをインストールされていないと報告し、その使用の登録を解除しません。解除するには、そのハーネスとプロジェクトに対して `install` を実行してから `uninstall` を実行してください。
`apothem verify` は、フォルダーがまだ完全であるかどうかを表示します。

`--project` は、リンクをたどり `~` を展開して読み取られます。
Python コードから、リンク経由など別の表記のプロジェクトフォルダーで行われたインストールも、その記録が保持する表記で引き続き見つかります。
`install` または `update` は、解決済みのフォルダーを記録します。
インストールがチェックに合格すると、別の表記で記録されたインストールを解決済みの表記へ移すため、リンクが削除された後もインストールは引き続き見つかります。拒否されたインストールはどの記録も変更しません。
`uninstall` は何かを削除する前に同じようにそのようなインストールを移すため、完了しなかったアンインストールは解決済みのフォルダーの下に記録され、リンクが削除された後も `uninstall` を再度実行するとそれが見つかります。
記録がディスク上で別の名前で示すフォルダー（`C:\...` として記録されたフォルダーへの `\\localhost\C$` パス）は、記録が持つ表記を保持します。また、独自のインストールがまだ存在するフォルダーでのインストールまたはアンインストールは、別の表記の記録をそのまま残します。
インストールがまだ存在する表記は、インストールが削除された表記より優先されます。存在する 2 つの間では、フォルダー内にそのファイルがより多くあるもの、次に新しいものが優先されます。
ファイルが 1 つもフォルダー内にないインストールは、そのアンインストールが完了しなかった場合を除き、そのフォルダーのものとはみなされません。その場合は、`uninstall` を再度実行すると完了します。
フォルダー名は厳密に比較されます。大文字と小文字を区別するフォルダー（たとえば WSL が作成したもの）では、`Proj` と `proj` は 2 つのフォルダーであり、互いのものとみなされることはなく、一方をアンインストールしても、もう一方が使用する共有フォルダーは残ります。
通常の Windows フォルダーでは、存在する間はそれらは 1 つのフォルダーです。なくなった後は、記録が持つ表記でのみ見つかります。
元のボリュームの隣に接続された複製ボリュームは、Windows が両方のボリュームを識別できる場合、元のものとはみなされません。
別のネットワーク共有上の記録（`\\server\share` パス、またはそれにマップされたドライブ文字）はテキストのみで比較されるため、到達できない共有が記録の検索を止めることはありません。
共有フォルダーに関する注記は、それでも記録された各フォルダーを確認するため、そのような共有で待機することがあります。

想定どおりに見つからない場合が 3 つあります。
以前のリリースが 2 回記録したインストール（1 回はコマンドラインから、1 回は Python からリンク経由で）は、`uninstall` の後も 2 つ目の記録を保持し、共有フォルダーはそのために残ります。
それは、インストールしたときの表記のフォルダーを使って Python から削除してください。
このコンピューター上のフォルダーの `\\localhost\C$` 表記で記録されたインストールは、その `C:\` 表記からは見つかりません。共有上の記録は他の場所から検索されないためです。
そして、2 つの異なるフォルダーへの 2 つのリンクを通して 2 つのインストールが行われ、後に一方のリンクがもう一方のフォルダーを指すように変更された場合、アンインストールは、そのフォルダー内にそのファイルがより多くあるインストールを選びます。
両方が同じファイル名を書き込んだ場合（同じリリースの 2 つのインストール）、または以前のリリースがそれらを記録した場合（そのファイルを列挙しませんでした）、新しい方を選びます。そのファイルは、リンクが以前指していたフォルダーにある可能性があります。

`--harness all` による削除は意図的に網羅的です。登録済みのすべてのハーネスを対象とし、
インストール時にプロファイルの `exclude_harnesses` がスキップするハーネスも含みます。
クリーンアップは、以前のより広範なインストールが残した可能性のある状態にまで及びます。
一度もインストールされていないハーネスにも、同じ通知が表示されます。

進行形のエイリアス `apothem uninstalling`（`apothem Uninstalling` としても受け付けられます）は、同じハンドラーに解決されます。

## オプション

| オプション | 説明 |
|---|---|
| `--harness NAME` | 削除するハーネスアダプター、またはレジストリ全体の集合を表す `all`（必須）。 |
| `--yes` | 確認プロンプトをスキップします。 |
| `--project PATH` | プロジェクトスコープのハーネス向けのプロジェクトルート。 |
| `--quiet`, `-q` | 情報出力を抑制します。エラーのみが出力されます。完了しないアンインストールは、残したものを列挙する `Warning:` 行を引き続き標準エラーに出力し、どのアンインストールも、ファイルに残された Apothem マーカーを挙げる `Warning:` 行をそこに出力します。 |
| `--verbose`, `-v` | 他のコマンドとの一貫性のために受け付けられます。このコマンドは追加の出力を表示しません。 |
| `--format plain\|json` | 出力形式（デフォルト: `plain`）。 |
| `--json` | `--format json` の短縮形です。 |
| `--no-color` | 出力中の ANSI カラーコードを無効にします。 |
| `-h`, `--help` | ヘルプを表示して終了します。 |

## JSON 出力

アダプターがインストールされていて、正常に削除された場合:

```json
{
  "schema_version": 1,
  "status": "success",
  "command": "uninstall",
  "action": "uninstalled",
  "harness": "claude-code",
  "profile_path": null,
  "project": null,
  "files_written": [],
  "results": [
    {
      "harness": "claude-code",
      "outcome": "updated",
      "operation": "uninstall",
      "path": "C:\\Users\\Example\\.claude\\settings.json",
      "message": "managed files removed"
    }
  ],
  "warnings": [],
  "error": null,
  "output_path": "C:\\Users\\Example\\.claude\\settings.json"
}
```

アダプターがインストールされていなかった場合、コマンドは `0` で終了します。JSON 出力では、エンベロープに `"status": "success"` と `"action": "uninstalled"` が含まれ、結果の行には `"outcome": "skipped"` と、メッセージ `"not installed; no files
removed"` が含まれます。`status` フィールドが `"not_installed"` になることはありません。

リンクで拒否された結果は、[`apothem install`](/docs/cli-reference/install#json-output) と同様に、リンクを `detail.symlink` に、その導く先のフォルダーを `detail.leads_to` に挙げます。

## 例

```bash
apothem uninstall --harness claude-code
apothem uninstall --harness claude-code --yes
apothem uninstall --harness cursor --project . --yes
apothem uninstall --harness all --project . --yes
apothem uninstalling --harness cursor --project . --yes   # continuous-form alias
```

共有スキルフォルダーは、それを使用する最後のインストールがなくなるまで残ります。

```bash
apothem install --harness codex
apothem install --harness cursor --project A
apothem uninstall --harness codex --yes                  # keeps ~/.agents/skills/, the cursor install uses it
apothem uninstall --harness cursor --project A --yes     # removes it: no install uses it now
```

## 終了コード

| コード | 意味 |
|---|---|
| 0 | アダプターがアンインストールされた、またはインストールされていなかった |
| 1 | ハーネスが見つからない、確認が拒否されたか利用できない（`--yes` なしの非対話モードまたは JSON モード）、インストール済みの各ハーネスが何かを削除または変更する前に失敗し、Apothem 自身のファイルをその場に残すリンクを挙げず、以前のリリースのインストールまたは記録がないインストールのファイルを残さず、Apothem のマーカー間に 2 つの異なるブロックを保持するファイルや Apothem があなたのテキストと区別できないマーカー行を持つファイルを残さなかったため、何も削除されなかった（Open-Claw、Antigravity、Kimi Code のアンインストールの最初の手順の中で発生した予期しないエラー、つまり例外は、その手順が何を変更していたかに関係なく、そのような失敗として数えられます）、またはコマンドが割り込まれた（`Ctrl+C`。`Aborted!` を出力します。それまでに何を削除していたかに関係ありません） |
| 2 | 部分的な削除 — アンインストールが、ファイルを削除した後、またはファイルから Apothem のエントリを取り除いた後に失敗または停止した（そのような最初の手順の中での予期しないエラーを除きます。`1` を参照）、少なくとも 1 つのハーネスが削除され別のハーネスが失敗した、リンクが Apothem 自身のファイルを指しているためにアンインストールがそれらをその場に残した、ファイルが Apothem のマーカー間に 2 つの異なるブロック、または Apothem があなたのテキストと区別できないマーカー行を保持している、以前のリリースが記録したインストールのファイルがこのリリースが書き込む内容と異なる、またはインストールに Apothem がどのファイルを書き込んだかを示す記録がない |
| 64 | 使用法エラー: 不明なオプションまたはコマンド、あるいは欠落した、または無効なオプション値。`--json` の下では、エラーはコード `cli.usage` を持つ JSON エンベロープになります。 |
