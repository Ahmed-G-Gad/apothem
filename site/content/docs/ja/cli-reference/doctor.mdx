インストールされているものの健全性をチェックします。
[`apothem verify`](/docs/cli-reference/verify) が選択したハーネスをチェックするのに対し、`doctor` はインストール済みのすべてのハーネスと共有プロファイルを 1 回でチェックします。

## 構文

```
apothem doctor [--project PATH] [--quiet|-q] [--verbose|-v]
               [--format plain|json] [--json] [--no-color]
```

## チェック内容

- **共有プロファイル。** 存在するプロファイルは、同梱のスキーマに照らして検証されます。不正な形式のプロファイルは、その診断コードとともに失敗します。
  プロファイルが存在しない場合は報告されますが、失敗にはなりません（`install` が作成します）。
- **インストール済みのハーネスのみ。** インストールされていないハーネスは `not_installed` として報告され、失敗にはならないため、健全なハーネスが 1 つあるマシンは合格します。
  プロジェクトスコープのハーネスは、`--project` がそのルートを指定した場合にチェックされます。指定がない場合は `needs_project` として報告されます。
  Apothem があなたのテキストと区別できないマーカー行を持つファイルは、インストール台帳を読み取れない間はインストールとして扱われるため、そのようなハーネスは `not_installed` として報告されずにチェックされます。
  doctor は、ハーネスのフックを起動するためにその台帳を読み取る場面（後述の<strong>フックランタイム</strong>を参照）で読み取れなかった台帳を、`ledger.unreadable` チェックで示します。対象は、検証に合格したハーネスと、失敗したチェックが Apothem マーカーを持つファイルを示すハーネス（`harness.stray_begin`）です。
  その修正方法は、破損した台帳を脇へ移動して `update` を実行するよう、あるいは doctor が開けない台帳（たとえば別のプログラムが開いたままにしている）であれば、そのファイルを読み取れるようにするよう案内します。
  それ以外の理由で検証に失敗したハーネスには `harness.verify_failed` チェックが付き、フックのチェックは行われないため、`ledger.unreadable` チェックも付きません。
- **検証。** インストール済みの各ハーネスは、[`verify`](/docs/cli-reference/verify) と同じチェックに合格しなければなりません。
  ファイルに END マーカーのない Apothem の BEGIN マーカーがある場合、失敗するチェックは `harness.stray_begin` です。その修正方法は、該当する各ファイルとマーカーの行を示し、その行と、Apothem のブロックを開始する行を除くほかのすべての BEGIN マーカー行を変更する番号付きの手順（各コメントの中に単語を 1 つ加える）を示します。
  また、代わりに END マーカーを戻さないよう案内します。そうすると、インストールまたは更新が Apothem のブロックをそれとは別に書き込んだ時点で、Apothem のブロックが 2 つ残ってしまうためです。更新だけではこれは解消されません
  （[トラブルシューティング](/docs/install/troubleshooting#a-file-has-an-apothem-begin-marker-with-no-end-marker)を参照）。
  Apothem のマーカーの間に完全なブロックを 2 つ以上持つファイルや、Apothem がマーカーのペアをあなたのテキストと区別できないファイル（たとえば、そのブロックがあなたのコードブロックの中にある場合）も、同じチェックに失敗します。そのメッセージは、ファイルに "Apothem markers to fix by hand" があることを示し、その修正方法は各ブロックをその行で示すか
  （[ファイルが Apothem のマーカーの間に 2 つのブロックを持つ](/docs/install/troubleshooting#a-file-holds-two-blocks-between-apothems-markers)を参照）、
  各マーカーのペアについて、その行の内容と修正方法を示し、あわせてマーカーのペアを開始しない各 BEGIN マーカーも示します
  （[Apothem が自身のブロックをあなたのテキストと区別できない](/docs/install/troubleshooting#apothem-cannot-tell-its-block-from-your-text)を参照）。
  OpenClaw のルールファイルについては、verify の注記と同様に、修正方法は、ファイルがその時点で OpenClaw のファイルごとの上限に収まっていれば次の更新が Apothem のブロックを書き込むこと、そしてあなたが残す古い Apothem のテキストもその上限に数えられることを案内します。
- **フックランタイム。** 検証された各ハーネスと、そのようなマーカーで失敗した各ハーネスについて、doctor はチェック対象のインストールが書き込んだファイルを読み取ります。
  対象は、ハーネス自身のフォルダーにあるインストール（doctor を実行する場所で設定された `CODEX_HOME` がそのフォルダーです）、またはプロジェクトスコープのハーネスの場合は `--project` フォルダーにあるインストールです。
  別のフォルダーにあるインストール（doctor が指していない `CODEX_HOME` や、その後削除したプロジェクトなど）が代わりに使われることはありません。
  doctor は、それらのうち JSON ファイルの中で Apothem が登録したフックコマンドを見つけ、各インタープリターとフックスクリプトを何もしないペイロード（登録された引数に `--help` を加えたもの、stdin 上の `{}`、スクラッチの作業ディレクトリ、そして `PYTHONPATH` の除去）で 1 回ずつ起動します。
  何も書き込まれません。
  インタープリターの欠落、スクリプトの欠落、またはインポート時のクラッシュは、チェックを失敗させます。
  フックがシステムごとに別のコマンド行を持つ場合、doctor はツールがこのマシンで実行する行を起動します。そのキーを読み取るツールであれば、Windows では `powershell` または `commandWindows` の行、macOS と Linux では `bash` の行です。
  `command` だけを読み取るツールでは、その `command` 行が起動されます。
  doctor はツール自身が読み取るキーのみを読み取り、`args` リストはコマンドをそれとともに実行するツールの場合にのみ読み取るため、別のキーの下に置かれた行やリストは起動もされず、数えられもしません。
  doctor はシェルを介さずにプログラム自体を起動するため、Windows では、PowerShell 向けに書かれた行の先頭にある `&` を省きます。
  JSON ファイル以外で登録されたフックは起動されず、`N started` にも数えられません。
  インストールレコードは、そのフォルダーのどの表記でも（Windows での大文字・小文字の違いなど）見つかります。
  インストール台帳にそのフォルダーのレコードがない場合、チェックは実行されません。レポートには `not checked` と表示され、最後の行は `All checks passed` の代わりに、フックコマンドがチェックされなかったハーネスを示します（ほかに起動して合格したフックコマンドもあるハーネスについては "some hook commands" と示します）。そして JSON 出力には `hook.unchecked` チェックが含まれます。
- **プロジェクトのフックファイル。** プロジェクトにコミットできる人なら誰でもそのファイルを変更できるため、プロジェクトスコープのハーネスについては、doctor は実行するものがすべて既知である場合にのみフックコマンドを起動します。
  doctor は `--project` が指定するプロジェクトのインストールレコードを読み取り、ツールがフックコマンドを読み取る場所からのみそれを取得します（1 つのファイルから最大 100 件まで。それを超えると、1 行の `hook.unchecked` がそのファイルを示し、残りは起動されません）。
  そしてコマンドを起動するのは、次のすべてを満たす場合のみです。インタープリターが、そのインストールが記録したもの（ただし、他人が変更できるプロジェクト内にある場合を除く）か、Apothem 自身が実行されている Python であること。スクリプトより前のオプションがコードを実行しないもの（`-E` や `-s` など）であること。スクリプトが、そのインストールが書き込んだフックスクリプトであり、そのフォルダー内のファイルがインストールの記録した SHA-256 チェックサムとまだ一致し、ほかの Python ファイルもリンクも含まないこと。そして、その後の引数が Apothem が書き込むものであること。
  そのうえで doctor は、読み取ったテキストではなく、これらの既知のパスを起動し、フックコマンドが示すほかのパスは参照しません。
  記録されたインタープリターやフックスクリプトが存在しない場合は、何も起動せずにチェックが失敗します。フックスクリプトが欠落している場合、修正方法は `update` を実行してスクリプトを戻します。
  doctor はそれ以外のプロジェクトのフックコマンドを起動せず、それぞれを理由とともに `hook.unchecked`（失敗ではなく info で、plain 出力では `!` が付きます）として報告します。
  doctor が既知のパスを参照できないコマンド（開くことのできないフォルダーにあるものなど）も同様です。
  プロジェクト内に記録されたインタープリターは、他人が変更できるため、doctor 自身がそれで実行されている場合を除いて起動されません。その修正方法は、プロジェクト外の Python で実行される Apothem を使って、プロジェクト外のフォルダーから `update` を実行し、代わりにその Python を記録させます。
  プロジェクト自身の環境にインストールされた Apothem ではこれができないため、その外にインストールされたものを使ってください。
  プロジェクトの仮想環境が有効な場合は、まずそれを無効にしてください。有効な間はその Python が `PATH` の先頭に来るため、npx コマンドがその下で実行され、再びそれを記録してしまいます。
  npx コマンドを実行する Python を選ぶには、`APOTHEM_PYTHON` にそのパスを設定します。
  動作する Python 3.10 以降でないパスはメッセージなしでスキップされ、代わりに `PATH` が検索されるため、doctor を再度実行してその行が消えたことを確認してください。
  更新をプロジェクトの外から実行するのは、プロジェクトフォルダーで実行した `python -m apothem` が、Apothem の代わりに、そこにコミットされた `apothem` という名前のフォルダーを起動してしまうためです。
  インタープリターやチェックサムを記録しなかった以前のリリースでインストールされたフックは、インストール時と同じオプションで `update` を実行するまで、チェックされないままになります。
- **チェックが読み取らないフックファイル。** フックのチェックは、4 MB を超えるフックファイルや、通常のファイル以外のもの（たとえばパイプやデバイス）を読み取りません。
  そのようなファイルには、それぞれ 1 行の `hook.unchecked` が付き、そのファイルを示します。これは、ファイルがフックだけを保持するものか、フックがマージされる設定ファイルかにかかわらず、またプロジェクト内にあるかホームフォルダーの下にあるかにかかわらず同じです。
  更新は、大きすぎるファイルや通常でないファイルをそのまま残すため、その修正方法は、ファイルを 4 MB 未満に縮小するか通常のファイルに置き換え、doctor を再度実行するよう案内します。
  ツールがフックを実行しないファイルには行が付きません。Apothem がフックをサポートフォルダーにのみ保持するツールの設定ファイルや、`.apothem/support` の下に保持されるコピーがこれにあたります。
  ホームフォルダーの下にあるファイルは、あなたのものであるため、リンクを介しても読み取られます。
  プロジェクト内では、チェックはリンクを介して到達するフックファイル（たとえば、プロジェクト外のフォルダーへのリンクに置き換えられた設定フォルダー）を読み取りません。
  そのようなファイルには、フックだけを保持するものか、フックがマージされる設定ファイルかにかかわらず、それぞれ `hook.unchecked` 行が付きます。
  その行はファイルとリンクを示します。リンクはファイル自体の場合も、そのフォルダーのいずれかの場合もあります。
  修正方法は、リンクの行き先を確認するよう案内します。自分で作ったリンクであれば、リンク先のフォルダーやファイルの実際のコピーに置き換えてその中のフックコマンドを確認し、作った覚えのないリンクであれば削除して、修正方法の最後にある `update` コマンドを実行します。
  いずれの場合も、削除されるのはリンク自体のみで、リンク先のフォルダーやファイルは削除されません。
  フックスクリプトにリンクを介して到達するフックコマンドは起動されません。その行はスクリプトとリンク（スクリプト自体の場合も、そのフォルダーのいずれかの場合もあります）を示し、その修正方法は、確認すべきフックコマンドがないことを除いて同じです。
  インストールがプロジェクト外に記録したフックスクリプトも起動されず、その行がそのことを示します。
  フックスクリプトのフォルダー内にあるリンクや、インストールが書き込んでいない Python ファイルも、コマンドを起動しないままにします。
  更新はどちらもそのまま残すため、修正方法は、その行が示すエントリを削除し（リンクの場合はリンク自体のみ。自分のスクリプトは別の場所へ移動してください）、doctor を再度実行するよう案内します。
  リンクがインストールの書き込んだフォルダーに取って代わっていた場合、次の実行でそのフォルダーは欠落として報告され、`update` を実行すると元に戻ります。
  チェックが開けないプロジェクトフォルダーにも行が付き、その修正方法は、あなたのアカウントにそれを開く権限を与えるよう案内します。
  リンクを拒否しながらファイルを開く方法がない Windows では、リンクのチェックはファイルを開く直前に行われます。
  4 MB を超えるフックスクリプトは、Apothem が書き込むものにそれほど大きなものはないため、インストール以降に変更されたものとして扱われます。

失敗した各チェックは、修正方法を示します。
`update` を実行する修正方法は、コロンの後にそのコマンドを置いて終わります。
プロジェクトスコープのハーネスの場合、そのコマンドは、[`uninstall`](/docs/cli-reference/uninstall) が手順を引用符で囲むのと同じように、シェル向けにフォルダーを引用符で囲んだ `--project` を示します。
その引用符でフォルダーを表せない場合、修正方法は `--project` を言葉で示し、フォルダーをそのままの形で最後に置きます。
失敗したチェックがない場合は 0 で、それ以外の場合は 1 で終了します。

## JSON 出力

`--json` は従来のフィールド（`version`、`python`、`platform`、`profile_path`、`profile_exists`、`profile_valid`、`harnesses`、`all_ok`、そしてプロファイルが無効な場合の `profile_error`）を維持し、次のフィールドを追加します。

- `profile_error_code` — プロファイルが無効な場合の、プロファイルの診断コード。
- `project` — 解決された `--project` ルート、または `null`。
- `harnesses[].status` — `ok`、`not_installed`、`needs_project`、`verify_failed`、`hook_failed`、`error` のいずれか。加えて `verified` と `hooks`（`{"probed": N, "failed": [...]}`、または、チェック対象のフォルダーにインストールレコードがない場合、インストール台帳を読み取れない場合、もしくは doctor がフックコマンドのチェックを完了できなかった場合は `null`。その理由は `hook.unchecked` チェックが示します）。
- `checks` — チェックごとに 1 つのレコード。`code`（たとえば `harness.verify_failed`、`harness.stray_begin`、`hook.start_failed`、`hook.unchecked`、`ledger.unreadable`、または `profile.*` コード）、`status`（`pass`、`fail`、`info` のいずれか）、`harness`、`message`、`fix` を含みます。

```json
{
  "schema_version": 1,
  "all_ok": false,
  "checks": [
    {
      "code": "hook.start_failed",
      "status": "fail",
      "harness": "claude-code",
      "message": "claude-code: a registered hook command cannot start: …",
      "fix": "Check that the interpreter in the hook command exists and runs, then …"
    }
  ]
}
```

## オプション

| オプション | 説明 |
|---|---|
| `--project PATH` | プロジェクトスコープのハーネス向けのプロジェクトルート。指定がない場合、それらは `needs_project` として報告されます。 |
| `--quiet`, `-q` | 情報出力を抑制し、エラーのみを出力します。 |
| `--verbose`, `-v` | 他のコマンドとの一貫性のために受け付けられます。このコマンドは追加の出力を表示しません。 |
| `--format plain\|json` | 出力形式（デフォルト: `plain`）。 |
| `--json` | `--format json` の短縮形です。 |
| `--no-color` | 出力中の ANSI カラーコードを無効にします。 |
| `-h`, `--help` | ヘルプを表示して終了します。 |

## 例

```bash
apothem doctor
apothem doctor --project .
apothem doctor --json
```

デフォルトの `plain` 形式は、人間が読める診断を出力します。`--json`（`--format json` と同等）は、機械可読なドキュメントを stdout に出力し、他のツールへのパイプに適しています。

## 終了コード

| コード | 意味 |
|---|---|
| 0 | すべてのチェックに合格した（まだハーネスが 1 つもインストールされていない場合も含む） |
| 1 | インストール済みのハーネスが検証に合格しない、登録されたフックコマンドを起動できない、インストール台帳を読み取れない、アダプターを読み込めなかったかプローブできなかった、または存在するプロファイルがスキーマ検証に失敗した |
| 64 | 使用法エラー: 不明なオプションまたはコマンド、あるいは欠落した、または無効なオプション値。`--json` の下では、エラーはコード `cli.usage` を持つ JSON エンベロープになります。 |
