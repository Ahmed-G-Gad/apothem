**ベンダー：** AWS
**インストール名：** `kiro`
**ステータス：** GA
**ネイティブ設定：** `<project>/.kiro/steering/apothem-rules.md`

## インストール

```bash
apothem install --harness kiro --project /path/to/project
```

アダプターは、共有の Apothem ルールとガバナンス面から、プロジェクトスコープの Kiro
ステアリングファイルを 1 つ書き込みます。

**書き込まれるファイル：** `<project>/.kiro/steering/apothem-rules.md`

## プロファイルからネイティブ設定へのマッピング

アダプターは Apothem の共有プロファイルを読み取り、`apothem install` または `apothem update` を
実行するたびに、プロジェクトのステアリングファイルをレンダリングします。共有プロファイルが
信頼できる情報源です。生成されたファイルへのプロジェクトローカルな編集は、次回の同期が
Apothem 管理のコンテンツを置き換える前にバックアップされます。

Kiro はインクルージョン設定がファイルの最初の内容であることを要求するため、このファイルは
`inclusion: always` フロントマターで始まります。Apothem 管理のブロックはその後に続きます。
ブロックの後にあなたが追加したテキストは、同期のたびに保持されます。

## 互換性に関する注意

Kiro のステアリング面は `.kiro/steering/` 配下のプロジェクトスコープです。アダプターは
`inclusion: always` フロントマターを持つ専用の `apothem-rules.md` ステアリングファイルを書き込み、
オペレーターが作成した Kiro の基盤ファイル（`product.md`、`tech.md`、`structure.md`）を
決して上書きしません。Kiro のスペック（`.kiro/specs/`）とエージェントフックはオペレーターの
所有です。Apothem はそれらを書き込みません。

## 検証

```bash
apothem verify --harness kiro --project /path/to/project
```

verify コマンドは次のことを確認します。

1. ネイティブ設定が想定されたパスに存在すること。
2. 共有プロファイルのすべての必須フィールドが存在すること。
3. アダプター固有の検証ルーチンが成功を報告すること。

## 更新

```bash
apothem update --harness kiro --project /path/to/project
```

現在の共有プロファイルの状態から、プロジェクトのステアリングファイルを再導出します。

## アンインストール

```bash
apothem uninstall --harness kiro --project /path/to/project
```

アダプターが書き込んだネイティブ設定ファイルを削除します。
共有プロファイルの YAML と Apothem エンジンには影響しません。

## コンフォーミティゲート

```bash
python -m apothem.conformity.gate --all .
```

## トラブルシューティング

| 症状 | 対処 |
|---------|-----|
| 設定ファイルが見つからない | `apothem install --harness kiro --project /path/to/project` を再実行する |
| 検証が失敗した | `apothem update --harness kiro --project /path/to/project` を実行してから、再度検証する |
| 想定外の設定内容 | `~/.config/apothem/profile.yaml` または `--profile PATH` を確認してから、`apothem update --harness kiro --project /path/to/project` を再実行する |

## 設定ノブ

| フラグ | デフォルト | 説明 |
|------|---------|-------------|
| `--dry-run` | `false` | ファイルを書き込まずにインストールをプレビューする。 |
