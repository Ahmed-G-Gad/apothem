- **ベンダー：** OpenCode
- **インストール名：** `opencode`
- **ステータス：** ベータ版
- **ネイティブ設定：** `~/.config/opencode/`（または `$XDG_CONFIG_HOME/opencode/`）

## インストール

```bash
apothem install --harness opencode
```

アダプターは OpenCode の JSON 設定を書き込み、Apothem のスキルを OpenCode のスキル面にインストールし、コマンドプロンプトを OpenCode の Markdown コマンドファイルに変換し、Apothem のヘルパー定義を OpenCode のサブヘルパーとして正規化します。

**書き込まれるファイル：**

```text
~/.config/opencode/opencode.json
~/.config/opencode/apothem/rules/00-apothem-profile.md
~/.config/opencode/commands/
~/.config/opencode/skills/
~/.config/opencode/agents/
~/.config/opencode/.apothem/support/{rules,templates,hooks}/
```

インストールは、Apothem のデータフォルダー（デフォルトでは `~/.config/opencode/.apothem/`）も作成し、その中に `contexts/`、`learning/`、`memory/`、`plans/` を置きます。

これらはデフォルトのパスです。
`XDG_CONFIG_HOME` が絶対パスのフォルダーに設定されている場合、アダプターは代わりに `$XDG_CONFIG_HOME/opencode/` に書き込みます。これは OpenCode 1 と OpenCode 2 の両方が読み取るフォルダーです。
相対パスの値やファイルシステムのルートは使用されず、インストールはその旨を伝えます。
`OPENCODE_CONFIG_DIR` には従いません。OpenCode 1 はそのフォルダーをデフォルトのフォルダーに加えて読み取りますが、OpenCode 2 はデフォルトの代わりにそのフォルダーを読み取るため、この変数が別のフォルダーを指している場合、インストールは OpenCode 2 がこのインストールを読み込まないことを警告します。

ドットファイルマネージャーが作るような、ホームディレクトリ内を指すリンクである `~/.config` は、たどられます。
Windows ではジャンクションもリンクとみなされます。
そのリンクがホームディレクトリの外を指している場合、インストールはファイルを 1 つも書き込む前に `target path crosses a symlink` で停止します。
プロファイルがまだない初回実行では、その 1 段階前、スターター用プロファイルを書き込む前に、`Apothem could not create the starter profile` で停止します。
プロファイルをホームディレクトリの外に置くには、`apothem profile init --profile PATH` でそこに作成し、同じ `--profile PATH` をインストールに渡してください。その場合でも、インストールには後述のとおり `XDG_CONFIG_HOME` が必要です。
ホームディレクトリ内として記述されていても、リンクによってその外へ出る `XDG_CONFIG_HOME`（別のドライブにリンクされた `~/xdg` など）は、インストールだけでなく、アンインストールと `apothem rollback` も停止させます。
`~/.config/opencode/` 内でインストールが書き込むパス上のリンクも同様にインストールを停止させ、`target path crosses a link` となるか、そのリンクが `~/.config` の外を指す場合は `target escapes the allowed materialization root` となります。

ホームディレクトリの外へ出る `~/.config` リンクを通じてインストールするには、`XDG_CONFIG_HOME` をリンクの指す先のフォルダーに設定し、ホームディレクトリの外にあるそのフォルダー自身のパスとして記述してください。
意味を持つのは記述したとおりのパスだけです。ホームディレクトリの外にあるパスは、そのリンクがどこを指していてもたどられます。
その後インストールはそこに書き込み、以前 `~/.config/opencode` に行われたインストールが書き込んだ `instructions` エントリは置き換えられるため、設定は各ファイルを 1 回だけ列挙します。
同じ設定でのアンインストールは、その以前のインストールも削除します。先にこの設定でインストールしたものが何もない場合でも同様です。その `opencode.json` は、Apothem のエントリだけが含まれていた場合、削除される前に Apothem のバックアップルート（`~/.apothem/backups/`）にコピーされ、そのインストールが作成した空のフォルダーも削除されます。
`XDG_CONFIG_HOME` がホームディレクトリ内の別の書き方で `~/.config` を指している場合（リンク経由の `$HOME/.config`、大文字小文字の違い、短縮名など）、インストールは引き続き `~/.config/opencode` を使うため、インストールは 1 つのままです。

`XDG_CONFIG_HOME` はシェルプロファイルから来るとは限りません。
プロジェクトの `.envrc` や、あなたが source するスクリプトでも設定できます。
それがホームディレクトリの外のフォルダーを指している場合、インストール、更新、アンインストール、`apothem rollback` はそのフォルダー内のファイルを変更します。それがこの変数の指すフォルダーだからです。
`XDG_CONFIG_HOME` を設定するプロジェクトフォルダーで Apothem を実行する前に、この変数を確認してください。

## プロファイルからネイティブ設定へのマッピング

アダプターは、あなたのプロファイルドキュメント、4 つのコアルール、ルールインデックスを指定する `instructions` ファイルリストを含めて `opencode.json` をレンダリングし、その後、共有された各 Apothem コホートを、OpenCode のネイティブ面または Apothem 所有のサポートサブツリーのいずれかへ伝播します。
既存の、一致する Apothem 管理の子要素は、置き換えの前にバックアップされます。

## 互換性に関する注意

このインストールは OpenCode 1 と OpenCode 2 の両方で動作します。
インストールは 1 つの設定を書き込み、OpenCode 1 はそれをそのまま読み取り、OpenCode 2 は読み替えます。
どちらも同じ設定フォルダーを読み取り、OpenCode 2 は、インストールが書き込む OpenCode 1 形式を、ファイルを書き換えずにメモリ上で変換します。
ヘルパーの `permission` リストと `mcp` サーバーエントリは、この読み替えを通じて OpenCode 2 に読み込まれます。
OpenCode 1 は、その設定フォルダーに `AGENTS.md` がなく、かつ `OPENCODE_DISABLE_CLAUDE_CODE` も `OPENCODE_DISABLE_CLAUDE_CODE_PROMPT` も設定されていない場合、Claude Code のインストールが `~/.claude/CLAUDE.md` に書き込むブロックも読み込みます。
OpenCode 2 には `CLAUDE.md` のフォールバックがないため、そのファイルを読み込みません。

ヘルパー定義が持つのは `deny` ルールだけで、ヘルパーが使ってはならないツールに対するものです。
OpenCode はデフォルトですべてのツールを許可し、`.env` ファイルまたは `.env.*` ファイルを読む前に確認を求めます。
ヘルパーに `allow` ルールがあると、その確認が無効になり、あなた自身の OpenCode 設定にあるより厳格なルールも上書きしてしまうため、ヘルパーはあなたの `permission` 設定に従います。

共有プロファイルが MCP サーバーを列挙している場合、インストールはそれらを `opencode.json` の `mcp` ブロックに書き込みます。
OpenCode が置換するのは `${NAME}` ではなく `{env:NAME}` であるため、サーバーの環境、ヘッダー、URL にある各 `${NAME}` は `{env:NAME}` として書き込まれます。ただし、後述するパススルーの環境エントリは除きます。
コマンド引数は書かれたとおりにコピーされます。
そこにある参照は、サーバー、またはサーバーが実行するシェルが展開するものとして、そのまま残されます。
インストールは、OpenCode が展開せず、サーバーが書かれたとおりに受け取ることになる 2 種類の `$` 参照について警告します。環境値またはヘッダー値にある `$NAME` と、それ以外の `${...}` 形式（コマンド引数にあるプレーンな `${NAME}` を含む）です。
警告は `environment.TOKEN` のように参照のある場所を示し、値を出力することはありません。

`GITHUB_TOKEN: ${GITHUB_TOKEN}` のように、変数を同じ名前のまま受け渡すだけの環境エントリは、インストールでは書き込まれず、環境エントリが何も残らないサーバーには `environment` を書き込みません。
OpenCode 1 と OpenCode 2 は、OpenCode 自身の環境でローカルサーバーを起動し、その上にサーバーの `environment` を追加するため、サーバーは OpenCode の実行時の `GITHUB_TOKEN` を引き続き受け取ります。
このエントリを書き込まないことは、`{env:GITHUB_TOKEN}` として書き込むこととは次の点で異なります。

- 変数が設定されていない場合、サーバーからは未設定に見えます。`{env:GITHUB_TOKEN}` として書き込むと、空文字列が設定されることになります。
- OpenCode 1 は、設定を読み込んだ後に一部の変数を自分で設定します。保存されたプロバイダーのログインに由来する `AWS_BEARER_TOKEN_BEDROCK` と `AICORE_SERVICE_KEY`、そして `OPENCODE_CONSOLE_TOKEN` です。
  OpenCode 2 は、`AICORE_SERVICE_KEY` を、それを使うプロバイダーの `serviceKey` 設定から、そのプロバイダーを初めて使うときに設定します。
  サーバーは、そうした変数がサーバー起動時に持つ値を受け取ります。`{env:NAME}` として書き込むと、設定が読み込まれた時点の値を保持することになり、それは多くの場合、空文字列です。
- OpenCode 1 は、`opencode auth login <url>` で行った組織ログインからも `{env:NAME}` を埋め、そのログインのトークンを自身の環境より先に読みますが、そのトークンを自身の環境には入れません。
  ログインだけが変数を設定している場合、サーバーはそれを受け取りません。両方が設定している場合、サーバーは環境の値を受け取ります。
  `{env:NAME}` として書き込むと、どちらの場合もログインの値を受け取ることになります。
- OpenCode SDK 上に構築されたアプリケーションは、サンドボックス内でサーバーを実行するワークスペースプロバイダーを登録できます。`opencode` CLI とデスクトップアプリは何も登録しません。
  OpenCode のソースによると、そのようなサーバーは OpenCode が実行される環境ではなくサンドボックスの環境を受け取るため、OpenCode が実行される場所でのみ設定された変数はそこに届きません。
- 変数名の大文字小文字が区別されない Windows では、OpenCode の環境がエントリのキーとは異なる大文字小文字でその名前を持っている場合（`GITHUB_TOKEN` に対する `Github_Token` など）、サーバーはその大文字小文字のまま受け取ります。`{env:GITHUB_TOKEN}` として書き込むと、エントリはそれを `GITHUB_TOKEN` として渡すことになります。
  Git Bash や Cygwin のシェルなど、名前を大文字小文字どおりに読むプログラムは、その場合それを見つけられないことがあります。
- `{env:NAME}` として書き込むと、値自体が `{file:path}` というテキストを含む場合、その部分がそのファイルの内容に置き換えられ、コマンドが `opencode` であるサーバーの `BUN_BE_BUN` エントリは、OpenCode がそこに設定する `1` を置き換えることになります。
  書き込まなければ、値はそのままサーバーに届き、OpenCode の `1` も残ります。

サーバーがそのエントリから得ていたものを必要とする場合は、そのサーバーを `harnesses.opencode.mcp_servers.<name>` の下に改めて記述し、値を `{env:NAME}` として書いてください。インストールはそれをそのままコピーします。
その場合、後述する OpenCode 1 のリスクが戻ってきます。

変数の名前を変えるエントリ（`TOKEN: ${FS_TOKEN}`）、より長い値の中にある参照、すべてのヘッダーと URL の参照、オーバーライドに書かれた `{env:NAME}` は、引き続き `{env:NAME}` として書き込まれ、次の段落がそれらに当てはまります。

OpenCode は、`{env:NAME}` の値を、読み込む設定テキストにエスケープせずに挿入します。
OpenCode 2 は、そのテキストがそのままでは解析できない場合にのみエスケープします。
そのため、バックスラッシュ（Windows のパスなど）、二重引用符、制御文字を含む値は、OpenCode 1 がファイルを読み取れなくなる原因になり得ます。その場合、OpenCode 1 のエラーは各値を埋めた設定テキストを、シークレットも含めて出力します。
どちらのバージョンでも、そのような値の中の `\t` や `\n` は制御文字としてサーバーに届きます。
インストールは実行時にそのような変数を 1 つずつ確認し、これらの文字を含むものについて警告します。
オーバーライドはサーバー全体を置き換えるため、そのサーバー全体を `harnesses.opencode.mcp_servers.<name>` の下に改めて記述し、そこで値を `{file:path}` として書いてください。他のツールは `${NAME}` 参照を保持します。

OpenCode は、`instructions` リストが指定するすべてのファイルを、すべてのセッションに結合します（[OpenCode のルール](https://opencode.ai/docs/rules/)）。
そのため、このリストは最初にあなたのプロファイルドキュメントを指定し、続いて `alwaysApply` が `true` であるルールのみを、それぞれ 1 つの明示的なパス（デフォルトでは `~/.config/opencode/.apothem/support/rules/<name>.md`）として指定します。
OpenCode は先頭の `~/` をあなたのホームディレクトリに展開します。
設定フォルダーがホームディレクトリの外にある場合、パスは絶対パスになり、サポートツリーは常に設定フォルダーの配下に置かれます。
それらのルールは、`agnostic-posture`、`authority-inquiry`、`context-management`、`session-closure`、そしてルールインデックスの `apothem-rule-index` です。
OpenCode はどのルールもパスでスコープしないため、それ以外のすべてのルールはオンデマンドで読み込まれます。
それらは `~/.config/opencode/.apothem/support/` 配下に参照素材としてインストールされたまま残り、インデックスが各ルールとそれを必要とする状況を名指しします。
ルール、テンプレート、フックプロンプトを参照するルール、スキル、コマンドは、そこからそれを読み込みます。
コマンド、スキル、ヘルパー定義はネイティブの検出場所を使用します。

OpenCode 1 は、設定フォルダーから `config.json`、`opencode.json`、`opencode.jsonc` の順に読み込み、後のファイルにあるリストは前のファイルにあるリストを置き換えます。
これは、ソースを確認した OpenCode 1 のすべてのリリース（最初のものから最新のものまで）で同じです。
そのため、Apothem が書き込む `opencode.json` の隣にある `opencode.jsonc` に `instructions` リストがあると、それが空であっても、OpenCode 1 はプロファイルドキュメントとルールを読み込まなくなります。
その場合、`apothem install`、`apothem update`、`apothem verify` はそのファイルを示す注意書きを出力します。verify がそれを出力するのは、`opencode.json` にインストールが書き込んだエントリが記載されている間だけで、この注意書きはチェックを失敗させません。
`opencode.jsonc` のリストに、Apothem が書き込むすべてのエントリがすでに含まれている場合、OpenCode 1 はそれらを読み込みますが、それはインストールや更新が更新しないコピーからであり、注意書きはその旨を伝えます。
一部だけが含まれている場合、注意書きはいくつ含まれているか、そして残りが OpenCode 1 に届かないことを伝えます。
OpenCode 2 は読み込むすべてのファイルの `instructions` リストを結合するため、この注意書きは OpenCode 1 だけに関するものです。

後述する OpenCode 1 を停止させるファイルを除き、`instructions` リストのない `opencode.jsonc` や、`opencode.json` へのシンボリックリンクについては注意書きは出ません。
`OPENCODE_CONFIG_DIR` がこのフォルダーを指している間も注意書きは出ません。現在の OpenCode 1 のリリースは、その場合そこにある両方のファイルをもう一度読み込み、それらのリストを結合するためです（最初の OpenCode 1 リリースはそれらを再度読み込みませんでした）。
`OPENCODE_CONFIG` がこの `opencode.json` を指している間も注意書きは出ません。OpenCode 1 はその場合、そのファイルを他のファイルの後にもう一度読み込み、そのリストを結合するためです。
OpenCode 1 でリストを読み込ませるには、`opencode.jsonc` から `instructions` キーを削除するか、そのエントリを `opencode.json` のリストに移してください。そこでは、インストールや更新は自分が書き込んでいないエントリを保持します。

OpenCode 1 は `config.json`、`opencode.json`、`opencode.jsonc` を JSONC として読み込みます。これはコメントと末尾のカンマを許す JSON であり、それ以上のものではありません。
各ファイルでは、まず各 `{env:NAME}` をその変数の値に、各 `{file:path}` をそのファイルのテキストに置き換えます。
そうしたファイルのいずれかが次に当てはまる場合、OpenCode 1 はエラーで停止し、設定を何も読み込まないため、プロファイルドキュメントとルールも届きません。

- それらの値を埋めた後に解析できない。引用符のないキーや一重引用符などの JSON5 構文、`NaN`、閉じられていないコメント、空白だけまたはコメントだけを含むファイルはすべてこれに当たります。
  何も埋めない `{env:NAME}` または `{file:path}` 1 つだけから成るファイルも同様です。
  OpenCode 1 は `{env:NAME}` の値をそのまま埋めるため、バックスラッシュ（Windows のパスなど）、二重引用符、制御文字を含む値は、それ以外は有効なファイルを壊すことがあります。注意書きはその旨を伝え、値を直した後でも OpenCode 1 が拒否するトップレベルや `instructions` の値がファイルにある場合も、その旨を伝えます。
  Apothem 自身も、プロファイル内の MCP サーバーの環境、ヘッダー、URL にある各 `${NAME}` について `opencode.json` に `{env:NAME}` を書き込み、それをファイルから削除しても更新が書き戻します。そのため、そうした参照については、注意書きはサーバー名とその対処を示します。そのサーバーを `harnesses.opencode.mcp_servers.<name>` の下に改めて記述し、値をファイルに保存して、それを指す `{file:path}` として書いてください。
- トップレベルがオブジェクトではない、または `instructions` の値がテキストのリストではない。
- `/* */` コメントの中であっても、OpenCode 1 が読み取れないファイルを指す `{file:path}` がある。
  `//` で始まる行にある `{file:path}` はそのまま残されます。
  ソケットは読み取れません。
  Linux と macOS では、OpenCode 1 は絶対パスを書かれたとおりに使い、`~/` パスの末尾の `/` も保持するため、ファイルへのパスを末尾の `/` 付きで書いたもの、または絶対パスを末尾の `/.` 付きで書いたものは読み取れません。
- フォルダーである、または後述する理由以外で OpenCode 1 が読み取れないファイルである（自分自身へ戻るシンボリックリンクなど）。

`apothem install`、`apothem update`、`apothem verify` は、そのようなファイルごとにそれを示す注意書きを出力します。OpenCode 1 は依然としてそのファイルを読むため、この注意書きは `OPENCODE_CONFIG_DIR` や `OPENCODE_CONFIG` が設定されている間も出ます。
シンボリックリンクを通じて 1 つのファイルを指すこれらの名前のうち 2 つには、合わせて 1 つの注意書きが出ます。シンボリックリンクのループにある名前はどのファイルも指さないため、それぞれに注意書きが出ます。
チェックはトップレベルと `instructions` の値だけを見て、OpenCode が読むすべての設定を見るわけではなく、名前付きパイプやデバイスのような通常ファイルではないファイルや、非常に大きなファイルは読み込みません。
そのような種類の設定ファイルには注意書きは出ません。
`{file:path}` のうち、非常に大きなファイルを指すもの、ファイルの `{env:NAME}` の値と `{file:path}` のファイルが埋める最初の 16 MiB より後にあるもの（埋められたテキストをエスケープ後の文字数で数えるため、制御文字は 6 文字として数えます）、または Windows でドライブ文字のないルートから始まるもの（OpenCode 1 は、起動されたフォルダーのドライブ上でそれを読みます）は、文字列値の中にある間は空のテキストとしてチェックされます。そこではそのテキストが結果を変えられないため、ファイルの残りは引き続きチェックされます。
Windows で、`NUL` デバイスのようにファイルでもフォルダーでもないものを指すもの、あるいは末尾がドットまたは空白で終わる部分を持つパス（Windows は通常そのドットや空白を除いて読みますが、OpenCode 1 はそうしないことがあります）も同様です。その注意書きには、OpenCode 1 がそのファイルを読めない場合、まずその参照で停止することが付け加えられます。
キーの中、引用符の外、`\u00` のようなエスケープシーケンスの途中、または閉じられていない `/*` コメントの後では、そのテキストが結果を決めるため、ファイル内の別の `{file:path}` が OpenCode 1 の読み取れないファイルを指していない限り、そのファイルには注意書きは出ません。
16 MiB を超えるテキストを埋める `{env:NAME}` の値も、ファイルに注意書きを出さず、1,000 を超える異なるパスを指す `{file:path}` トークンも同様です。
null デバイス `/dev/null` を指す `{file:path}` は、OpenCode 1 と同じく、どこにあっても空のテキストとして読まれます。
Linux と macOS で名前付きパイプやその他のデバイスを指すものは、OpenCode 1 がそれを永久に待つことがあるため、ファイルに注意書きを出しません。
注意書きは `{env:NAME}` 参照の名前を示し、その値は決して示しません。また、`{file:path}` は制御文字をエスケープし、200 文字で切り詰めて示します。
verify は、`opencode.json` にインストールが書き込んだエントリが記載されている間、これらの注意書きを出力します。`opencode.json` 自体についての注意書きは、プロファイルドキュメントが Apothem のブロックを保持している間も出力されます。そのようなファイルには、Apothem が読めるものが何も記載されていない可能性があるためです。
インストールや更新が `opencode.json` を JSON5 としても解析できない場合、それらは注意書きの代わりに、そのファイルを示す `config.unparseable` エラーで停止します。その場合チェックを失敗させる verify は、注意書きを出力します。

OpenCode 2 は `config.json` を読みません。
解析できない、またはトップレベルがオブジェクトではない `opencode.json` や `opencode.jsonc` はスキップするため、`opencode.jsonc` だけが壊れている場合でも `opencode.json` は読み込みます。
ファイルがそのままでは解析できない場合は `{env:NAME}` の値をエスケープし、読み取れない `{file:path}` には空のテキストを埋め、リストではない `instructions` の値（単一のテキスト値を含む）を無視し、テキストではないリストの項目を取り除くため、いずれもファイルの読み込みを止めません。
OpenCode 2 がそのファイルをどう扱うかがわかっている場合、注意書きはそれを伝えます。

Apothem は `{env:NAME}` を自身の環境にある値で置き換えるため、Apothem が OpenCode の見るのと同じ環境変数で実行されている場合に、注意書きは正しくなります。
OpenCode 1 は、`opencode auth` でサインインしたプロバイダーからも `{env:NAME}` の値を取得しますが、Apothem はそれを見られないため、引用符の外にあってそのような値を持つトークンには、OpenCode 1 とは一致しない解析の注意書きが出ることがあります。

現在の OpenCode 1 のリリースでは、バイトがまったくないファイル、またはバイトオーダーマークだけのファイルは空の設定として読まれ、注意書きは出ません。
Linux と macOS では、現在の OpenCode 1 のリリースは読み取りを許可されていないファイル（`Permission denied`）をスキップするため、そこでは注意書きは出ません。システムが `Operation not permitted` で拒否する読み取りはそれらを停止させ、注意書きが出ます。
Windows では、読み取りを許可されていないファイルで停止するため、注意書きが出ます。
それより前の OpenCode 1 のリリースはどのシステムでもそれで停止しますが、Apothem が注意書きを出すのは Windows だけです。

インストールと更新のたびに、`~/.config/opencode/apothem/rules/` 内で Apothem が置いたものではないすべてのファイルが、`~/.apothem/backups/` 配下のバックアップセットに保存された後で削除されます。
そのバックアップは、そのハーネスのより新しいバックアップセットが 10 個できた時点で削除されるため、あなた自身のファイルは別の場所に置いてください。

プロファイルドキュメント `~/.config/opencode/apothem/rules/00-apothem-profile.md` は、共有プロファイルに由来するあなたのアイデンティティとプリファレンスを保持し、Apothem サポートファイルのセクションで終わります。
このセクションは、リポジトリ形式の各参照（`rules/<name>.md`、`templates/...`、`hooks/...`）が解決される先の、`~/.config/opencode/.apothem/support/` 配下の絶対ディレクトリを示します。
このドキュメントは最初の `instructions` エントリであるため、OpenCode はすべてのセッションでこれを読み込みます。

以前のリリースが書き込んだ `opencode.json` には、すべてのルールを読み込む単一のグロブ `~/.config/opencode/.apothem/support/rules/*.md`、または当時常時適用だった 28 のルールそれぞれの明示的なパスが記載されています。
`apothem install` と `apothem update` はどちらの形式も上記のリストに置き換え、起動時にもはや読み込まれない 24 のパスを取り除きます。`apothem uninstall` はそれらすべてを削除します。
あなた自身の `instructions` エントリは、いずれの場合も保持されます。

## 検証

```bash
apothem verify --harness opencode
```

verify コマンドは次のことを確認します。

1. ネイティブ設定が想定されたパスに存在すること。
2. 管理対象の各ターゲットが存在すること。管理対象のファイルは空ではなく、JSON または YAML の設定は解析できること。`--profile PATH` を追加すると、インストールされたファイルがそのプロファイルと一致することも確認します。
3. アダプター固有の検証ルーチンが成功を報告すること。

## 更新

```bash
apothem update --harness opencode
```

`opencode.json`、ネイティブコマンド、スキル、ヘルパー定義、Apothem サポートツリーを更新します。
インストールが書き込んだ MCP サーバーのうち、あなたが内容を変えずに OpenCode 2 の `mcp.servers` 形式に変換したものは、`mcp` の下に書き戻され、OpenCode の両方のバージョンがそれを読み取ります。
`mcp.servers` 配下のサーバーがその変換とみなされるのは、対応する `mcp` エントリがなくなっていて、インストールが書き込んだ内容と全体として一致する場合だけです。
同じ名前のあなた自身のサーバー、あなたが編集した変換結果、無効にした変換結果は、そのまま残されます。
そのような変換結果は残したまま、更新はそのサーバーを `mcp` の下にもう一度書き込むため、OpenCode 1 はそのコピーを使い、OpenCode 2 は変換されたほうを使います。
どちらのバージョンでもそのサーバーをオフにしておくには、プロファイルから削除してください。
これには、インストールが書き込んだエントリを列挙したインストールレコードが必要です。Apothem がその一覧を保持するようになる前のレコードは対象外です。

## アンインストール

```bash
apothem uninstall --harness opencode
```

アダプターが `~/.config/opencode/opencode.json` に追加したエントリを削除します（あなた自身のキー、MCP サーバー、`instructions` エントリは残り、このファイルは、Apothem が作成したものであり、かつあなたのものが何も残っていない場合にのみ削除されます）。
インストールが書き込んだ MCP サーバーのうち、あなたが内容を変えずに OpenCode 2 の `mcp.servers` 形式に変換したものも、全体として削除されます。`mcp.servers` 配下のその他のサーバーは残ります。
`mcp.servers` 配下にあるあなた自身のサーバーが、あなたがインストールの `mcp` エントリを削除した後に、インストールが書き込んだものと一致する場合、変換されたコピーと区別できないため、一緒に削除されます。その前にファイルはバックアップされます。
プロファイルドキュメント `~/.config/opencode/apothem/rules/00-apothem-profile.md` から Apothem のブロックを削除し、その中の他のテキストは残します。このファイルは、その中に他に何も残っていない場合にのみ削除されます。
また、`~/.config/opencode/commands/`、`~/.config/opencode/skills/`、`~/.config/opencode/agents/`、`~/.config/opencode/.apothem/support/` 内の Apothem のファイルも削除します。これらのフォルダー内のその他のファイルは残ります。
各ファイルは、変更または削除される前に `~/.apothem/backups/` 配下にバックアップされます。
共有プロファイルの YAML と Apothem エンジンには影響しません。

以前のリリースが、`XDG_CONFIG_HOME` が別のフォルダーを指している間に `~/.config/opencode/` に行ったインストールは、そこに残り、OpenCode がそれを読み取ったことはありません。
そのファイルがそこにある間、次回のインストールがその旨を伝えます。削除するには、`XDG_CONFIG_HOME` を未設定にしてアンインストールを実行してください。
その後 `~/.config` がホームディレクトリの外を指すリンクになっている場合、そのアンインストールは `target path crosses a link` で拒否され、注意書きは代わりにリンクの指す先のフォルダーを示します。`XDG_CONFIG_HOME` をそのフォルダーに設定してアンインストールを実行してください。

## コンフォーミティゲート

```bash
python3 -E -s ~/.apothem/src/apothem/conformity/gate.py --all .
```

プロジェクトフォルダーから実行してください。
Windows では、Windows PowerShell と cmd は `~` を展開しないため、`python3` の代わりに `python` を使い、フルパスを指定します。
PowerShell では `$HOME\.apothem\src\apothem\conformity\gate.py`、cmd では `%USERPROFILE%\.apothem\src\apothem\conformity\gate.py` です。
このパスはインストーラーがエンジンを置く場所で、`-E -s` はあなたの `PYTHONPATH` とユーザーの site-packages をゲートから締め出します。[コンフォーミティゲート](/docs/conformity-gate)では、その両方と、その他のインストールについて説明しています。

## トラブルシューティング

| 症状 | 対処 |
|---------|-----|
| 設定ファイルが見つからない | `apothem install --harness opencode` を再実行する |
| 検証が失敗した | `apothem update --harness opencode` を実行してから、再度検証する |
| 想定外の設定内容 | `~/.config/apothem/profile.yaml` または `--profile PATH` を確認してから、`apothem update --harness opencode` を再実行する |
| OpenCode 1 が `opencode.jsonc` の `instructions` リストを読むという注意書きが出る | 設定フォルダーの `opencode.jsonc` から `instructions` キーを削除するか、そのエントリを `opencode.json` のリストに移す |
| OpenCode 1 がファイルを解析できないという注意書きが出る | 設定フォルダーのそのファイルを、コメントと末尾のカンマだけを加えた JSON になるよう修正する（すべてのキーを引用符で囲み、二重引用符を使い、すべての `/*` コメントを閉じる）か、ファイルを削除する |
| OpenCode 1 が `{env:NAME}` の値を埋めるとファイルを解析できないという注意書きが出る | 値にバックスラッシュ、二重引用符、制御文字が含まれないよう変数を変更する（Windows ではパスをスラッシュで書く）か、その `{env:NAME}` を削除する。プロファイル内の MCP サーバーのために Apothem がその参照を書き込むと注意書きが示している場合、削除しても更新が書き戻すため、変数を変更するか、変数をそのままにするなら、そのサーバーを `harnesses.opencode.mcp_servers.<name>` の下に改めて記述し、値をファイルに保存して、それを指す `{file:path}` として書く。注意書きが 2 つ目の問題を示している場合は、それも修正する |
| OpenCode 1 にはファイルのトップレベルにオブジェクトが、またはテキストのリストである `instructions` の値が必要だという注意書きが出る | ファイルを 1 つの JSON オブジェクトにし、`instructions` を `["notes.md"]` のようなテキストのリストにするか、そのキーを削除する |
| `{file:path}` が指すファイルを OpenCode 1 が読めないという注意書きが出る | そのファイルを作成するか、パスを修正するか、`{file:path}` を削除する |
| ファイルがフォルダーであるという注意書きが出る | 設定フォルダー内のそのフォルダーを移動するか、名前を変更する |
| OpenCode 1 がファイルを読めないという注意書きが出る | あなたのユーザーアカウントがそのファイルを読めるようにするか、自分自身へ戻るシンボリックリンクを置き換えるか、ファイルを削除する |
