Apothem は 2 分未満でインストールでき、既存のハーネス構成と並行して動作します。
どの経路も同じ自己完結型エンジンを実行します——ソースツリーはベンダリングした依存関係を同梱しており、システムの Python 3.10 以降でチェックアウトから実行されます（[自己完結型ランタイム](/docs/architecture/self-contained-runtime)を参照）。

**すべての経路に共通する 2 つの前提条件:** `PATH` 上のシステム **Python 3.10 以降**と、そのもとでインポート可能な `click` および `rich` パッケージです。
npm シム（チャネル 2）、VS Code 系拡張機能（チャネル 4）、コマンドラインブートストラップ（チャネル 5–7）は、`npx` を実行するために、さらに **Node.js 18 以降**を必要とします。
Python 3.10 と Node.js 18 および 20 は上流のサポート終了を過ぎています。引き続きサポートされテストされていますが、より新しいバージョンが推奨されます（[前提条件の一覧](#前提条件の一覧)を参照）。
以下の各チャネル固有の節では、その正確な前提条件、コピーしてすぐ使える 1 つのコマンド、検証ステップを改めて示します。

## チャネルを選ぶ

8 つのインストールチャネルが利用できます。すでに使っている作業方法に合わせて選んでください。

| # | チャネル | 提供内容 | 前提条件 |

| 1 | [Claude Code プラグイン](#1-claude-code-プラグイン) | Claude Code での完全なハーネス | Claude Code · Python 3.10+ |
| 2 | [npm シム（`npx`）](#2-npm-シムnpx) | 完全なハーネス、任意のツール | Node 18+ · Python 3.10+ |
| 3 | [ワンショットインストーラー](#3-ワンショットインストーラー) | 完全なハーネス + `apothem` コマンド | Python 3.10+（ネットワークインストールには `git`） |
| 4 | [VS Code 系拡張機能](#4-vs-code-系拡張機能) | エディターからの完全なハーネス | VS Code · Node 18+ · Python 3.10+ |
| 5 | [コマンドラインブートストラップ（拡張機能ホスト）](#5-コマンドラインブートストラップ拡張機能ホスト) | エンジンを実行するブートストラップ | そのホストツール · Node 18+ · Python 3.10+ |
| 6 | [コマンドラインブートストラップ（`qwen-code` ホスト）](#6-コマンドラインブートストラップqwen-code-ホスト) | エンジンを実行するブートストラップ | そのホストツール · Node 18+ · Python 3.10+ |

| 8 | [直接エンジン（`python -m apothem`）](#8-直接エンジンpython--m-apothem) | チェックアウトからの完全なハーネス | Python 3.10+（`click`、`rich`） |

<Callout title="完全なハーネスを提供するチャネル">
  npm シム（2）、ワンショットインストーラー（3）、直接エンジン（8）は、単独で任意のハーネス向けに同期ユニット全体をマテリアライズします。
  3 つのコマンドライン拡張機能（5–7）は、エンジン（`npx @ahmed-g-gad/apothem install`）へシェルアウトして完全なハーネスをマテリアライズする小さな**ブートストラップ**をインストールします——これらはエントリーポイントであり、それ自体で完全な提供物ではありません。
  Claude Code プラグイン（1）はエンジンを同梱し、それを直接実行します。
  VS Code 系拡張機能（4）は独自のエンジンを同梱しません。そのコマンドは、デフォルトでは npm シムを通してエンジンを実行します。
</Callout>

どの経路も冪等です。再実行は安全で、同じ状態に収束します。

## 1. Claude Code プラグイン

**前提条件:** Claude Code、および `PATH` 上のシステム Python 3.10+。

プラグイン経路は完全に Claude Code の内部で動作します。
Apothem エンジンを、そのスラッシュコマンド、委任ワーカー、スキル、ルール、フックとともに同梱しており、すべて自己完結型のプラグインツリーから実行できます。

```text title="Inside Claude Code"
/plugin marketplace add ahmed-g-gad/apothem
/plugin install apothem@apothem
```

インストール後、Apothem のコマンド一式、同梱の委任ワーカー、スキル、そして 4 つの[出力スタイル](/docs/reference/output-styles)（`/output-style` で、または `/config` から 1 つを選びます）が、すべての Claude Code セッションで利用可能になります。
プラグインは各コマンドをスキルとして出荷します。これは `SKILL.md` と、それが必要に応じて読み込む詳細を収めた、その隣の `references/` フォルダーからなるため、Claude Code はプラグインの接頭辞を付けてそれを呼び出します: `/apothem:plan-spec`、`/apothem:security-audit` などです。
2 つの名前は Claude Code 自身が使用しています。`/plan` はプランモードに入り、`/code-review` は同梱のレビューを実行するため、Apothem のコマンドには `/apothem:plan` と `/apothem:code-review` を入力してください。
プラグインではなく Apothem エンジンが Claude Code へのインストールを行う場合、同じスキルが接頭辞なしで `~/.claude/skills/` に書き込まれ、個人用の `code-review` スキルが同梱の `/code-review` を置き換えます（その `/review` エイリアスは引き続き同梱のものを実行します）。
`projectify` と `workflow` の 2 つの名前はネイティブスキルでもあります。プラグインとエンジンのインストールが出荷するのはネイティブスキルであり、コマンドから派生させたスキルではありません。
コマンドがどのように分割されるかは [Claude Code](/docs/harnesses/claude-code#command-skills-and-reference-files) を、コマンドの完全なカタログは[スラッシュコマンド](/docs/reference/commands)を参照してください。

**検証:** Claude Code 内で `/plugin` を実行し、**apothem** がインストール済みとして一覧に表示されることを確認するか、ターミナルからドリフトレポートを確認します。

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 2. npm シム（`npx`）

**前提条件:** Node.js 18+（`npx` 用）と、`PATH` 上のシステム Python 3.10+。
シムはインタープリターを見つけ、すべての CLI コマンドを同梱のエンジンへ転送します——システムには何も恒久的に配置されません。
`python3`、`python`、`py -3` の順に試します。**`APOTHEM_PYTHON`** にインタープリターのパスを設定すると、そのインタープリターが最初に試されます。これは、Python がインストールされているが `PATH` 上にない場合や、複数のバージョンがあり特定のものを使いたい場合に必要な設定です。
指定したインタープリターも、Python 3.10+ のチェックに合格する必要があります。合格しない場合、シムは `python3`、`python`、`py -3` の順にフォールバックします。

```bash title="npx"
npx @ahmed-g-gad/apothem install --harness claude-code
```

プロファイルのないマシンでは、この最初の `install` が `~/.config/apothem/profile.yaml` にスタータープロファイルを作成し、その旨を表示します。
そのアイデンティティフィールドはプレースホルダーです。それらを個人設定し（`npx @ahmed-g-gad/apothem profile edit`）、`install` の代わりに `update` を指定してコマンドを再実行し、適用してください。

リポジトリから直接実行することもできます。

```bash title="npx from the repository"
npx github:ahmed-g-gad/apothem install --harness claude-code
```

[CLI リファレンス](/docs/cli-reference)のすべてのコマンドがこの形式で動作します。`apothem` を `npx @ahmed-g-gad/apothem` に置き換えてください。
これは、OpenCode をはじめ、独立したプラグインや拡張機能のレジストリを公開しない他のすべてのツールのインストール経路でもあります——Apothem はそれらをネイティブな設定ディレクトリへ直接同期します（`npx @ahmed-g-gad/apothem install --harness opencode`）。

**検証:**

```bash title="Verify"
npx @ahmed-g-gad/apothem --version
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 3. ワンショットインストーラー

**前提条件:** `PATH` 上のシステム Python 3.10+（インストーラーは `click` / `rich` の前提条件を追加することを提案します）。ネットワークインストールの場合は、最新リリースを見つけるための `git` と、署名済みのリリースタグを確認するための `gpg` が必要です（Git for Windows には両方が含まれています）。[cosign](https://docs.sigstore.dev/cosign/system_config/installation/) は任意です。cosign があると、インストーラーは署名済みのリリースアーカイブも確認します。

インストーラースクリプトは、最新リリースを解決して確認し（[信頼モデル](#信頼モデル)を参照）、Apothem ソースツリーを `~/.apothem` に配置し、プロファイルが存在しない場合はスタータープロファイルを作成し、最初のハーネスをマテリアライズし、結果を検証します。これらすべてを 1 回の実行で行います。
スタータープロファイルにはプレースホルダーのアイデンティティフィールドが含まれています。それを編集してから `apothem update --harness <name>` を実行し、あなたの値を適用してください。
再実行は冪等です。git クローンはフェッチされ、その新しいタグが確認され、そのあとで初めてクローンが解決されたタグへチェックアウトされます。リリースアーカイブによるインストールはその場で更新されます。そしてハーネスは再マテリアライズされます。
エンジンが部分的な完了（終了コード `2`）で終わった場合、インストーラーは警告行を表示し、それでも検証を行い、`apothem` コマンドを配置してそのバナーを表示したうえで、終了コード `2` で終了します。
エンジンが部分的な完了で終わるのは、Apothem のマーカー行のためにファイルをそのまま残した場合、または何かを書き込んだあとで停止した場合です（[エンジンがファイルをそのまま残す場合](/docs/install/updating#when-the-engine-leaves-a-file-as-it-is)を参照）。
検証済みインストールが、デフォルトかつ推奨の経路です。

まず一度、メンテナーの署名鍵をインポートしてください。すべてのネットワークインストールは、cosign の有無にかかわらずリリースタグをこの鍵と照合し、お使いのキーリングに鍵がない場合は停止します。フィンガープリントが `5C89 98F9 F241 7204 45D3  F28B 7039 6FED 9C63 4163` と表示されることを確認してください。この値は [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md#maintainer-signing-key) で公開されています。Windows では、`git verify-tag` は Git for Windows に同梱されている `gpg` のキーリングを読み取るため、インポートは Git 自身の `bash` を通して実行します:

```bash title="macOS · Linux · WSL2 · BSD — import the key once"
curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import
gpg --fingerprint 70396FED9C634163
```

```powershell title="Windows · PowerShell — import the key once"
& "$env:ProgramFiles\Git\bin\bash.exe" -c 'curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import && gpg --fingerprint 70396FED9C634163'
```

```bash title="macOS · Linux · WSL2 · BSD — latest signed tag, verified"
curl -fsSL https://apothem.ahmedgad.com/install.sh | bash
```

```powershell title="Windows · PowerShell — latest signed tag, verified"
irm https://apothem.ahmedgad.com/install.ps1 | iex
```

同じスクリプトはチェックアウト内の `scripts/installer/` 配下にも同梱されています——`.sh`、`.ps1`、`.bat` 形式の `install`、`uninstall`、`update` です——そのため、クローン後に直接実行できます。

```bash title="From a checkout"
APOTHEM_HARNESS=claude-code sh scripts/installer/install.sh                                 # POSIX
$env:APOTHEM_HARNESS = 'claude-code'; pwsh -NoProfile -File scripts/installer/install.ps1   # Windows
```

パイプで渡すワンライナーは、ローカルツリーを決して使いません。`curl ... | sh` と `irm ... | iex` は、実行したフォルダーとその親フォルダーを無視し、リリースを取得して検証します。
インストーラーがローカルツリーを使うのは、チェックアウト自身の `scripts/installer/install.sh`（または `install.ps1`）をそのパスで任意のフォルダーから実行した場合（たとえば `sh ~/src/apothem/scripts/installer/install.sh`）、または `APOTHEM_SOURCE` がそのツリーを指定している場合だけです。
インストーラー、アップデーター、アンインストーラー、`apothem` シム、npm ランチャー、フック、コンフォーミティゲートのバリデータープロセスは、カレントフォルダーを Python のモジュール検索パスに含めません。
自分で入力した `python -m apothem` コマンドはそうではありません。`-m` はカレントフォルダーから先にモジュールを読み込みます。

あなた自身の `PYTHONPATH` にある空のエントリーと相対エントリーは、どのランチャー（インストーラー、アップデーター、アンインストーラー、POSIX と Windows の `apothem` シム、npm ランチャー）からもエンジンへ渡されません。
残すエントリーは完全なパスでなければなりません。Windows では `C:\lib` のようなドライブパスかネットワークパス、それ以外では `/` で始まるパスです。
ルート相対の `\lib` やドライブ相対の `C:lib` は除外されます。
sh スクリプトは、実行する Python にどの形式を読むかを問い合わせ、スクリプトが書き込む `apothem` シムはその形式を保ちます。
Windows の Python（Git Bash で通常使われるもの）は、エンジンのパスを `;` で連結した Windows 形式で受け取り、あなたの `PYTHONPATH` のうちドライブパスとネットワークパスだけを残します。
POSIX の Python（Cygwin や MSYS2 自身の `python3` を含む）は、`:` で連結した POSIX パスを受け取り、`/` で始まるエントリーだけを残します。
インストーラーの `git` コマンドのうちクローンを操作しないものは、カレントフォルダーのリポジトリを読みません。

### インストーラーのフラグ

`install.sh` は以下のフラグを受け付け、`install.ps1` は同じスイッチを PowerShell のパラメーターとして受け付けます。
`install.bat` は最初の 3 行の `install.sh` の書き方を受け付け、それぞれを `install.ps1` に渡します。
パイプで実行するワンライナーでは PowerShell のパラメーターを渡せないため、使うときは先に `install.ps1` をダウンロードしてください。

```bash title="Pass a flag"
curl -fsSL https://apothem.ahmedgad.com/install.sh | sh -s -- --dry-run    # POSIX
irm https://apothem.ahmedgad.com/install.ps1 -OutFile install.ps1; pwsh -NoProfile -File install.ps1 -DryRun   # Windows
```

| `install.sh` | `install.ps1` | 効果 |
|---|---|---|
| `--clean`, `--fresh` | `-Clean`, `-Fresh` | インストールの前に、どのハーネスをインストールする場合でも、[`apothem install`](/docs/cli-reference/install#blast-radius-preview) が挙げるホームディレクトリ内の 4 つのフォルダー（`~/.claude` と `~/.agents` を含む）をバックアップして削除し、その後新しくインストールします。インストーラーはこれを `apothem install --clean` としてエンジンに渡します。エンジンは削除のたびに確認し、バックアップを `~/.apothem/backups` に残し、プロファイルを書き戻します。 |
| `--dry-run` | `-DryRun` | 一時フォルダーでリリースを取得して確認し、インストールで何が変わるかを、何も変えずに表示します（[信頼モデル](#信頼モデル)を参照）。 |
| `--yes` | `-Yes` | `--clean` による各削除の前に確認しません。また、[信頼モデル](#信頼モデル)が `--yes` を必要とするとしている、`APOTHEM_HOME` にあるものの置き換えも許可します。 |
| `-h`, `--help` | なし | フラグと信頼モデルを表示して終了します。 |

### 信頼モデル

`APOTHEM_REF` が設定されていない場合、インストーラーは最も高い `vMAJOR.MINOR.PATCH` リリースを解決し、<em>そのリリース</em>をインストールします——動き続ける `main` ブランチを決してインストールしません。
いずれかの設定がマテリアライズされる前にリリースを確認し、その確認の内容は `cosign` が `PATH` 上にあるかどうかで変わります:

- <strong>cosign がある場合</strong>、2 つの確認の両方に合格する必要があります。
  まず、リリースタグが、次の項目と同じ方法で確認されるメンテナー鍵による有効な署名を持ち、その署名済みタグがそのリリースの名前を持つタグでなければなりません。別のリリース用の署名済みタグをこの名前に付け替えたものは拒否されます。
  次に、インストーラーはリリースのプラットフォームアーカイブ、その `SHA256SUMS` ファイル、`SHA256SUMS.cosign.bundle` をダウンロードします。
  cosign は、Apothem のリリースワークフローがまさにそのタグについて `SHA256SUMS` に署名したこと、そして `--certificate-github-workflow-sha` チェックによって、検証した証明書が署名済みタグの指すコミット上の実行に発行されたものであることを確認しなければなりません。
  インストーラー自身は証明書を読みません。
  そのうえで、アーカイブの SHA-256 が記載されたダイジェストと一致しなければなりません。
  ワークフローはプッシュされたあらゆるタグに対して実行されるため、その署名だけでは不十分です。タグの署名が、メンテナーがそのコミットをリリースしたことを示します。
- <strong>cosign がない場合</strong>、または `APOTHEM_HOME` にすでに git クローンがある場合、インストーラーはリポジトリをクローンまたは更新し、`git verify-tag` でタグだけを確認します。
  署名は有効で、<em>かつ</em> [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md) で公開されているメンテナー鍵によるものでなければならず、署名済みタグはそのリリースの名前を持つタグでなければなりません。
  ほかの鍵で署名されたタグは、お使いのキーリングがその鍵を信頼していても拒否されます。
  署名済みの git タグはコミットを SHA-1 ID で指定します。cosign がある場合、インストーラーはアーカイブの SHA-256 も確認します。
  既存のクローンはフェッチされ、その新しいタグはクローンがチェックアウトされる<em>前に</em>確認されます。
  確認に失敗するとクローンは元のまま残り、追跡対象のファイルに変更があるクローンでは、変更を失う代わりに、それらをコミットまたはスタッシュするよう求めるメッセージとともに更新が停止します。
  `main` のようなリリース以外の ref では、既存のクローンは origin にあるそのブランチのコピーに追従します。

インストーラーは、git をリダイレクトする git の環境変数（`GIT_DIR`、`GIT_WORK_TREE` など）、git に別の設定ファイルを指し示す環境変数（`GIT_CONFIG`、`GIT_CONFIG_GLOBAL`、`GIT_CONFIG_SYSTEM`）、または別のツリーから属性を読ませる環境変数（`GIT_ATTR_SOURCE`。あなた自身の設定にある `attr.tree` は、クローン上で実行されるすべての git コマンドで空にされます）を無視し、`APOTHEM_REPO` が `-` で始まる場合は停止します。
`GIT_CONFIG_NOSYSTEM` はあなたが設定したとおりに残ります。これは git にシステム設定を読ませないようにするだけです。
git は引き続き、あなた自身のグローバル設定と、`GIT_CONFIG_NOSYSTEM` を設定していなければシステム設定を、いつもの場所から読みます。また、`git`、`gpg`、`cosign` はあなたの `PATH` で見つかるプログラムであり、インストーラーは見つかったとおりにそれらを信頼します。
実行全体を通して、インストーラーは `GIT_NO_REPLACE_OBJECTS=1`（git が replace ref を通じてオブジェクトを差し替えないようにする）、`GIT_NO_LAZY_FETCH=1`（git が欠けているオブジェクトを自らリモートから取得しないようにする）、`GIT_ALLOW_PROTOCOL`（file、git、http、https、ssh のトランスポートに設定し、環境内の値でこの一覧を広げられないようにする）、`GIT_ATTR_NOSYSTEM=1` を設定します。クローン上で実行されるすべての git コマンドで `core.attributesFile` が空にされるため、git はクローン外の属性ファイルを一切読まず、あなたの属性ファイルで定義されたマクロがそこでフィルターを指定することはできません。
PowerShell スクリプトは、実行の終了時に 4 つすべてを元に戻します。
インストーラーはリリースタグを一度だけ読み、それが指すコミットを記録し、タグを検証し、そのコミットを ID でチェックアウトし、`HEAD` がそのコミットであることを要求します。そのため、確認後にタグが動かされても何も変わりません。
Windows PowerShell 5.1 と 7 では、https ではないアドレスへリダイレクトするダウンロードは、POSIX インストーラーの `curl` と同様に拒否されます。

`APOTHEM_HOME` は、あなただけが書き込めるフォルダーでなければなりません。そこに書き込める人は誰でも、`apothem` コマンドが実行するコードを変更できるためです。
Windows では、`C:\apothem` のようにドライブのルートに作成したフォルダーは、Windows の既定のアクセス許可のもとで、そのコンピューターにサインインするすべてのユーザーが変更できます。
既定の `~/.apothem` は、あなた自身のユーザーフォルダー内にあります。
取得を伴うインストール、更新、ドライランは、そうでない場合、またはそのフォルダーかそれを含むフォルダーが他人の所有である場合に、停止せずに警告し、そのフォルダー、書き込みできる人または所有者、そして修正方法を示します。ローカルチェックアウトからのインストールと、`APOTHEM_SOURCE` を設定した更新では、この確認は省略されます。
Windows では警告は `install.ps1` と `update.ps1` から出ます。`install.sh` と `update.sh` は Git Bash、MSYS2、Cygwin のもとでは確認を行いません（[トラブルシューティング](/docs/install/troubleshooting#the-installer-warns-other-users-can-change-apothem_home)を参照）。

確認に失敗すると、いずれかの設定が書き込まれる前、かつインストーラーが `APOTHEM_HOME` を置き換える前にインストールは中止されます。
メンテナーの公開鍵がまだローカルのキーリングにない署名済みタグの場合は、代わりに鍵のインポートの案内を表示して中止します。上に示したとおりに鍵をインポートし、そのフィンガープリントを [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md) に公開されている値と照合してから、再実行してください。

cosign がある状態での再実行は、以前のリリースアーカイブによるインストールを更新します。
新しいソースはまず `~/.apothem` の隣のフォルダーで確認されて展開され、そのあとで入れ替えられます。
`~/.apothem` 内にあってソースツリーの一部ではないものはすべて、新しいインストールへ引き継がれます。エンジンのロールバック用バックアップ（`backups/`）、インストール台帳（`state/`）、プラン、メモリ、その他のデータです。
いずれかのステップが失敗した場合、または Ctrl+C や終了シグナルで実行を止めた場合、以前のインストールは変更されずに元に戻されます。それさえ失敗した場合は、メッセージが以前のファイルの場所を示します。
入れ替え中の強制終了や電源断は捕捉できません。それによって `~/.apothem` の隣にフォルダーが残ることがあり、次回の取得を伴うインストールがそれらを報告します（下記を参照）。
インストーラーが `~/.apothem` を置き換えるときには、次の規則が適用されます:

- git クローンは、`--yes` なしではリリースアーカイブに置き換えられません。
  クローンが追跡していないファイルは新しいインストールへ移動し、クローン自体のツリー（その履歴とソース）は新しいフォルダー `~/.apothem.before-apothem-<time>` に、元の名前（`.apothem`）のまま移動します。インストーラーはその場所を示すので、不要になったら削除してください。
  `--yes` を指定しても、失われることになるローカルの作業をクローンが保持している間は、インストーラーは拒否します。変更、スタッシュ、未プッシュのコミット、またはソースツリー内の追跡されていないファイルです。
  その作業をコミットしてプッシュするか、別の場所へ移動してから、再実行してください。
  この確認は `--dry-run` でも実行されます。
  `.git` ファイル（リンクされたワークツリー）はクローンとみなされ、`.git` フォルダーも同様です。
- Apothem 以外のものの git クローンは、Apothem のインストールを含まない任意のフォルダーと同様に扱われ（下記を参照）、クローンとして更新されたり置き換えられたりすることはありません。
- 既存のクローンがその場で更新されるのは、git がその中のすべての変更を把握でき、かつクローン自身の設定の中に更新中にコードを実行するものが何もない場合だけです。
  フェッチの前に、インストーラーは次の場合に停止します。ファイルに assume-unchanged または skip-worktree の印が付いている場合、git が `APOTHEM_HOME` にワークツリーを見つけられない場合（クローンの設定で `core.bare` が `true` になっている場合など）、クローンがサブモジュールを保持している場合（インデックスに記録されているか、`.git/modules` に保持されている）、`.git/info/attributes` がフィルターまたは diff ドライバー（`filter=` または `diff=`）を指定している場合、それまたは設定ファイルが通常のファイルではない場合、クローンが別のリポジトリからオブジェクトを借用している場合（`objects/info/alternates`）です。
  また、クローン自身の `.git/config` または `.git/config.worktree` にある設定のうち、`git clone` と `git init` が完全なクローンのためにそこへ書き込むもの、ブランチの設定（ブランチの `remote` と `pushremote` は `origin` でなければなりません）、`user.name`、`user.email`、`maintenance.auto`、`maintenance.strategy`、`pull.rebase`、`pull.ff` 以外のものがあれば停止します。そのため、`--filter` で作成した部分クローンも停止します。それらは[トラブルシューティング](/docs/install/troubleshooting#the-installer-stops-the-existing-clone-is-set-up-in-a-way-the-update-would-trust)に一覧があります。
  メッセージは、その設定と、それが含まれるファイルを示します。
  設定、属性、オブジェクトの確認は、クローンのインデックスやオブジェクトを読むいずれかの git コマンドの前に実行され、さらにサブモジュールの確認とともに、`--yes` がクローンを置き換えようとするときにも実行されます。
  ワークツリーの `.gitattributes` ファイルを適用する git コマンドの前に、インストーラーは次のものがあれば停止します。git が追跡していないもの、コミット済みのコピーと異なるもの、コミット済みのコピーを git が読めないかそれがフィルターまたは diff ドライバーを指定しているもの（ワークツリー内のコピーも読まれます）、そして git が追跡していないクローン内の git リポジトリです。後者の `.gitattributes` ファイルも git は読むためです。
  リリースが一切書き込まない `backups` などのエンジン自身のデータフォルダーは、これらの確認では読まれません。
  フェッチの前に、`src` 配下（大文字・小文字の表記を問わない）にある git が追跡していないファイルでも停止します。エンジンがそれらを読み込む可能性があるためです。
  チェックアウトの後、エンジンがクローンから実行される前に、`src` 配下の Python キャッシュフォルダー（`__pycache__`）を削除します。
  クローンの git フックは更新中に決して実行されず、クローン上のすべての git コマンドは、ページャーなし、自動メンテナンスなし、ファイルシステムモニターをオフにし、file、git、http、https、ssh のトランスポートのみを許可し（そのため、クローンの設定にあるアドレスによって git に `ext::` のようなヘルパープログラムを実行させることはできません）、サブモジュールの再帰なしで実行されます。`git diff` と `git status` はサブモジュールを省略します。
  別のユーザーが所有するクローンは、説明とともに実行を停止させます（トラブルシューティングを参照）。
- エンジン自身のデータ（`backups`、`state`、`plans`、`memory`、`contexts`、`learning`、`providers`）だけを含むフォルダーは `--yes` なしで更新され、そのデータは保持されます。
- Apothem のインストールを含まないフォルダーは、`--yes` なしでは変更されません。
  `--yes` を指定すると、インストーラーはフォルダー全体をそのまま新しいフォルダー `~/.apothem.before-apothem-<time>` に移動し（内部では元の名前を保ちます）、その場所を示してから、新規にインストールします。
- `APOTHEM_HOME` にあるシンボリックリンク（Windows ではシンボリックリンクまたはジャンクション）は拒否されます。それを置き換えると、リンク先のフォルダーではなくリンクそのものが置き換えられるためです。
  `APOTHEM_HOME` をそのフォルダーに向けてから再実行してください。
  例外は既存の git クローンで、これはその場で更新されます。
- Linux と macOS では、引き継ぐファイルやフォルダーの名前にスペースやその他の特殊文字が含まれていると、インストールが停止します。
  先にそれを `APOTHEM_HOME` の外へ移動してください。

<strong>一度に 1 つの実行、そして停止された実行。</strong>
インストール、更新、アンインストールの各スクリプトは、実行ごとに `APOTHEM_HOME` の隣（既定では `~/.apothem.lock`）にロックを実行全体にわたって取得し、実行が成功、失敗、Ctrl+C、または終了シグナルで終わるとそれを解放します。
`apothem` コマンド自体はロックを取得しません。
2 つ目の実行は "Another Apothem install, update or uninstall is running" と表示して停止します。
POSIX では、ロックは実行のプロセス ID を保持するフォルダーです。
強制終了された実行が残したロックは、削除方法とともに報告され、決して引き継がれません。また、別の環境（たとえば同じマシン上の WSL と Git Bash）で作成されたロックは、そのプロセスをそこから確認できないロックとして報告されます。
Windows PowerShell では、ロックはプロセスの終了時に Windows が閉じて削除するファイルです。
`APOTHEM_HOME` がリンクの場合、すべてのスクリプトはリンク先のフォルダーの隣でロックを取得します。
ドライランもロックを取得します。ただし、`APOTHEM_HOME` を含むフォルダーがまだ存在しない場合は除きます。
そのため、その場での更新、アンインストール、ドライランを含むすべての実行には、`APOTHEM_HOME` を含むフォルダーへの書き込みアクセスが必要です。それがない場合、実行は何かを変更する前に停止します。

入れ替え中の強制終了や電源断によって、以前のインストールや `APOTHEM_HOME` のその他のエントリーが、その隣の `.apothem-old.<name>.*`、`.apothem-extract.<name>.*`、`.apothem-clone.<name>.*`（`<name>` は `APOTHEM_HOME` の最後の部分）、または `APOTHEM_HOME.before-apothem-<time>` フォルダーに残ることがあります。
その `APOTHEM_HOME` に対する次回の取得を伴うインストールは、ドライランも含めて、何かを変更する前に停止し、各フォルダーとそこへ移動されたエントリーを示し、それらを元に戻す方法を案内します。
以前のインストーラーが作成したフォルダーは、どのホームに属するかを示さないため、その行はエンジンのデータしか示さないことがあります。中を確認してください。
インストーラーは何も削除しません。
[トラブルシューティング](/docs/install/troubleshooting#the-installer-stops-an-earlier-run-left-folders-beside-apothem_home)を参照してください。

`--dry-run`（Windows では `-DryRun`）は、一時フォルダーでリリースを取得して確認し、`~/.apothem` を変更せずに残します。
実際の実行と同じ確認を行いますが、既存のクローンについては 1 つ例外があります。クローン自身の設定は上記のとおり確認しますが、クローンへのフェッチは行わないため、追跡対象のファイルへの変更は確認しません。実際の更新はフェッチの後にそれを確認します。
特定のリリースに固定するには、`APOTHEM_REF` を使います:

```bash title="Pinned, verified install"
APOTHEM_REF=vMAJOR.MINOR.PATCH sh -c "$(curl -fsSL https://apothem.ahmedgad.com/install.sh)"
```

`vMAJOR.MINOR.PATCH` を[リリースページ](https://github.com/ahmed-g-gad/apothem/releases)のタグに置き換えてください。
最も古いリリースタグは、それ自体の署名を持たない軽量タグであるため、そのコミットが署名されていても、タグのチェックはそのタグで中止します。それ以降のすべてのリリースタグは注釈付きで署名されています。
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md) のリリース署名のセクションに、各タグとその検証方法が記載されています。

明示的なオーバーライドは、既定の動作を緩めます。`APOTHEM_ALLOW_UNVERIFIED=1` は、クローン経路でのタグ確認の失敗を警告に格下げして続行します。エアギャップ環境またはローカル環境での利用、あるいはタグ署名より前のリリースをインストールする場合を想定しています。
これは cosign 経路を決して緩めないため、cosign があるホストではこれと一緒に `APOTHEM_VERIFY=signature` を設定してください。
また、署名済みタグがそのリリースの名前を持つタグであるという確認も決して緩めません。このオーバーライドは署名のないタグや別の鍵で署名されたタグを通してしまうため、この確認が保護するのはメンテナー鍵の署名を持つタグだけです。
`APOTHEM_REF=main` は、`APOTHEM_ALLOW_UNVERIFIED=1` と組み合わせた場合にのみ、検証なしで移動するブランチをチェックアウトします。
`APOTHEM_REF=main` だけを指定すると、インストーラーは `main` をステージングフォルダーに（`APOTHEM_HOME` が既存のクローンである場合はそのクローンに）取得したうえで、ブランチは署名付きリリースタグではないため、何かをチェックアウトしたり、`APOTHEM_HOME` を置き換えたり、いずれかの設定をマテリアライズしたりする前に中止します。
`APOTHEM_SOURCE` によるローカルチェックアウトは何も取得せず、検証もスキップします。

確認方法を自分で選ぶには `APOTHEM_VERIFY` を設定します。既定値は `auto` です:

| 値 | インストーラーが確認する内容 |
| --- | --- |
| `auto`（既定） | `cosign` が `PATH` 上にあり、`APOTHEM_HOME` が git クローンでない場合は `release`、それ以外の場合は `signature` |
| `release` | メンテナー鍵によるリリースタグの署名と、署名済みタグがそのリリースの名前を持つタグであること、次にリリースワークフローがタグのコミット上の実行で `SHA256SUMS` に署名したことの cosign による確認、最後にアーカイブの SHA-256。cosign または `gpg` がない場合は停止します |
| `signature` | リリースタグの GPG 署名（メンテナー鍵によるものでなければなりません）と、署名済みタグがそのリリースの名前を持つタグであること |
| `checksum` | `SHA256SUMS` に対するアーカイブの SHA-256 のみ。`APOTHEM_ALLOW_UNVERIFIED=1` が必要で、ダウンロードの前に警告します。チェックサムモードはリリースを検証しません。SHA256SUMS はアーカイブと同じリリースから取得されるため、一致してもダウンロードが破損していないことを示すだけです。リリースのファイルを変更できる人は、両方を変更できます。cosign も `gpg` もないホストで、それを受け入れる場合にのみ使用してください |

すべてのアーカイブモードは、ダイジェストの不一致があれば何かを展開する前に中止します。
初期のリリースではバンドルの名前が `SHA256SUMS.sig` であり、`SHA256SUMS.cosign.bundle` がない場合、インストーラーはその名前を読みます。

その後、エンジンは配置されたツリーから直接実行されます。
`click` と `rich` を除くすべてのサードパーティ依存関係はソースツリー内にベンダリングされており、エントリーポイントがそのベンダーディレクトリを自ら `sys.path` に追加します。
インストーラーは、書き込んだ `apothem` シムの完全なパスを表示します。
シムを書き込まなかった場合は、カレントフォルダーを `sys.path` から外した状態でエンジンを起動するコマンドを表示します。そのコマンドをバナーからコピーしてください。

両方のスクリプトは同じ設定用環境変数（`APOTHEM_HOME`、`APOTHEM_REPO`、`APOTHEM_REF`、`APOTHEM_ALLOW_UNVERIFIED`、`APOTHEM_VERIFY`、`APOTHEM_RELEASE_BASE`、`APOTHEM_SOURCE`、`APOTHEM_HARNESS`、`APOTHEM_PROFILE`、`APOTHEM_SKIP_VERIFY`、`APOTHEM_AUTO_INSTALL_DEPS`、`APOTHEM_BIN_DIR`）を読み取ります。
完全な表は[インストーラーの環境変数](/docs/how-to/installer-environment-variables)を、`python -m` の呼び出しモデルの仕組みは[自己完結型ランタイム](/docs/architecture/self-contained-runtime)を参照してください。

**`apothem` コマンド。** インストールが成功すると、インストーラーは同梱のエンジンへ転送する `apothem` シムを書き込みます——POSIX では `$HOME/.local/bin` に、Windows では `%LOCALAPPDATA%\Microsoft\WindowsApps`（デフォルトの Windows `PATH` にすでに含まれているユーザーディレクトリ）に書き込みます。
インストーラーがあなたの `PATH` を編集することは決してありません。
そのディレクトリが `PATH` 上に入れば、手動の `PYTHONPATH` なしで `apothem <command>` を直接実行できます。

**検証:**

```bash title="Verify"
apothem verify --harness claude-code

# or, before the shim is on PATH, by the shim's full path:
~/.local/bin/apothem verify --harness claude-code
```

## 4. VS Code 系拡張機能

**前提条件:** VS Code、Node.js 18+、および `PATH` 上のシステム Python 3.10+。

**Apothem for VS Code** 拡張機能は [Visual Studio Marketplace](https://marketplace.visualstudio.com/items?itemName=ahmed-g-gad.apothem-vscode) に `ahmed-g-gad.apothem-vscode` として公開されています。拡張機能ビューから、または `code --install-extension ahmed-g-gad.apothem-vscode` でインストールできます。
`apothem.vsix` パッケージからもインストールできます: `code --install-extension apothem.vsix`、またはエディターの *Install from VSIX…* コマンドを使います。
リリースワークフローがパッケージに署名し、各 GitHub Release に添付します。
ワークフローが拡張機能をパッケージ化するようになる前に公開されたリリースには、`.vsix` は含まれていません。最新のリリースにそれがない場合は、`tools/vsce/` にロックされた vsce リリース（その vsce リリースには Node.js 22 以降が必要です）を使って、チェックアウトからパッケージをビルドしてください。
`npm ci --prefix tools/vsce --ignore-scripts` を実行し、続いて
`cd vscode-extension && ../tools/vsce/node_modules/.bin/vsce package --no-dependencies --out apothem.vsix` を実行します。
以前の `apothem.vsix` からインストールしたコピーは、識別子 `ahmed-g-gad.apothem` を持ちます。両方のコピーが同じコマンドを登録しないように、`code --uninstall-extension ahmed-g-gad.apothem` で削除してください。
1 つの拡張機能で、VS Code 系のエディターをカバーします。
そのパレットコマンド（`Apothem: Install`、`Verify`、`Update`、`Uninstall`、`Doctor`）は、設定されたランナーを通して同じエンジンを実行します（デフォルトは `npx @ahmed-g-gad/apothem@<extension version>` で、拡張機能は自身とともに出荷されたバージョンのエンジンを実行します。ソースから実行するには、ユーザー設定 `apothem.runner` をローカルチェックアウトに向けます）。
Install、Verify、Update、Uninstall はどのハーネスを対象にするかを尋ね、エディター自身のハーネスを最初に提示します。`all` は選択肢の 1 つであり、決してデフォルトにはなりません。
`apothem.runner` 設定はマシンスコープであるため、ワークスペースから変更することはできません。また、拡張機能は信頼されたワークスペースでのみ動作します。

**検証:** エディターのコマンドパレットから **Apothem: Verify** コマンドを実行するか、ターミナルから次を実行します。

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 5. コマンドラインブートストラップ（拡張機能ホスト）

**前提条件:** そのホストのコマンドラインツール、Node.js 18+、および `PATH` 上のシステム Python 3.10+。

Apothem をリポジトリから直接、拡張機能としてインストールします——コマンドには正確なホストとハーネスのスラッグが含まれています。

```bash title="Install the extension"
gemini extensions install https://github.com/ahmed-g-gad/apothem
```

この拡張機能は**ブートストラップ**であり、それ単独では完全なインストールではありません。Apothem のコンテキストファイルを読み込み、エンジン（`npx @ahmed-g-gad/apothem`）へシェルアウトする `/apothem` コマンドを追加します。
それを通してインストールを実行し、完全なハーネスをマテリアライズしてください。

```bash title="Materialize the full harness"
npx @ahmed-g-gad/apothem install --harness gemini-cli --project .
```

**検証:**

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness gemini-cli --project .
```

それを通してインストールを実行し、完全なハーネスをマテリアライズしてください。

```bash title="Materialize the full harness"
npx @ahmed-g-gad/apothem install --harness qwen-code
```

**検証:**


## 7. コマンドラインブートストラップ（プラグインホスト）

**前提条件:** そのホストのコマンドラインツール、Node.js 18+、および `PATH` 上のシステム Python 3.10+。

リポジトリをプラグインマーケットプレイスとして追加してから、プラグインをインストールします——コマンドには正確なホストとハーネスのスラッグが含まれています。

```bash title="Install the plugin"
codex plugin marketplace add ahmed-g-gad/apothem --sparse .agents/plugins --sparse plugins/apothem
codex plugin add apothem@apothem
```

2 つの `--sparse` パスは、リポジトリ全体ではなく、マーケットプレイスの一覧とプラグインだけを取得します。完全なクローンは、WSL 配下の Windows ドライブのような低速なディスクでは、ホストの 30 秒のクローン制限を超えることがあります。

チャネル 5 とチャネル 6 の拡張機能と同様に、これはエンジンへシェルアウトする**ブートストラップ**です。
プラグインは 1 つのエントリースキルを同梱します。そのマニフェストはルートの `plugin.json` であり、[プラグインホストのハーネスページ](/docs/harnesses/codex#codex-plugin)では、そのレイアウトと、プラグインがエンジンに任せる部分を説明しています。
それを通してインストールを実行し、完全なハーネスをマテリアライズしてください。

```bash title="Materialize the full harness"
npx @ahmed-g-gad/apothem install --harness codex
```

**検証:**

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness codex
```

## 8. 直接エンジン（`python -m apothem`）

**前提条件:** `click` と `rich` パッケージがインポート可能なシステム Python 3.10+、加えてリポジトリのチェックアウト。Node.js は不要です。

クローンからエンジンを直接実行します。
エントリーポイントがベンダリングされた依存関係（`src/apothem/_vendor`）を `sys.path` に追加するため、`click` と `rich` がインポート可能であれば、セットアップは `PYTHONPATH=src` だけで完了します。

```bash title="Direct engine"
git clone https://github.com/ahmed-g-gad/apothem
cd apothem
PYTHONPATH=src python -m apothem install --harness claude-code
```

`python -m` はカレントフォルダーを Python のモジュール検索パスの先頭に置くため、そこにある `click.py` のようなファイルや `apothem` という名前のフォルダーが、本物のモジュールの代わりに実行されてしまいます。
これらのコマンドは、チェックアウトのルート、または信頼できる別のフォルダーから実行してください。
インストール済みの `apothem` コマンドはカレントフォルダーを読みません。

npm シムと同様に、プロファイルのないマシンでの最初の `install` は `~/.config/apothem/profile.yaml` にスタータープロファイルを作成し、処理を続行します。

**検証:**

```bash title="Verify"
PYTHONPATH=src python -m apothem verify --harness claude-code
```

## 任意のインストールを検証する

上記の各チャネルには、それぞれ独自の検証コマンドが示されています。2 つの汎用形式は次のとおりです。

```bash title="Installer path"
apothem verify --harness claude-code
```

```bash title="npx path"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

ハーネス名は、インストールしたアダプターに置き換えてください。サポートされているすべての名前は[ハーネス一覧](/docs/harnesses)を参照してください。
インストール済みのすべてのアダプター（その検証とフックコマンド）を一度にチェックするには、`verify --harness NAME` の代わりに `doctor` を、上で使用した形式のまま実行します。
形式は `apothem doctor`（またはシムの完全なパス、あるいはそのフォルダーが `PATH` 上にない場合はインストーラーが表示したコマンド）、`npx @ahmed-g-gad/apothem doctor` のいずれかです。
プラグイン経路の場合は、Claude Code 内で `/plugin` を実行し、**apothem** がインストール済みとして一覧に表示されることを確認してください。

## 前提条件の一覧

- **Python 3.10 以降** —— Python を見つける経路は名前で見つけます。その名前は経路によって異なります。
  npm シムは `python3`、`python`、`py -3` の順に試します。
  インストーラーは `python3`、`python`、およびバージョン付きの名前 `python3.14` から `python3.10` まで順に試します。
- そのインタープリターで **`click` と `rich` がインポート可能であること** —— エンジンがベンダリングしない、ターミナル向けの 2 つの依存関係です。
  インストーラーは両方をチェックし、欠けているものを示し、あなたの代わりにインストールすることを提案します——あなたの確認を得て、または `--yes`（PowerShell では `-Yes`）か `APOTHEM_AUTO_INSTALL_DEPS=1` によって自動的に。
  その他のすべてのチャネルでは、パッケージが欠けているとエンジンはエラー（終了コード 1）で停止します。このエラーは、見つかったインタープリター用の正確なコマンドを、Apothem がテストされているバージョン制約とともに示します（`<interpreter> -m pip install "click==…" "rich>=…"`）。
  `--json` を指定すると、同じエラーがコード `runtime.dependency_missing` を持つ JSON エンベロープとして届きます。
- **Node.js 18 以降** —— `npx` を実行する経路のみ: npm シム（2）、VS Code 系拡張機能（4）、コマンドラインブートストラップ（5–7）。
- **サポート終了したランタイム。** Python 3.10 は 2026-10-01 に、Node.js 18 と 20 はそれぞれ 2025-04-30 と 2026-04-30 に、上流のサポート終了を迎えました。
  Apothem は宣言された下限としてこれらを引き続きサポートし、CI でそれぞれをテストしていますが、これらはもう上流のセキュリティ修正を受け取らないため、Python 3.11 以降と Node.js 22 以降を優先して使用してください。
  下限の引き上げ方は[ランタイム下限ポリシー](/docs/governance/release-engineering-policy#runtime-floors)で説明しています。
- **Git と GnuPG** —— インストーラー経路のみ、それもネットワーク形式の場合のみです（スクリプトはこれらを使って最新リリースを見つけてその署名済みタグを確認し、cosign がない場合はソースをクローンします。ローカルチェックアウトにはどちらも不要です）。
- **Claude Code** —— プラグイン経路のみ。**VS Code** と、各コマンドラインブートストラップ自身のホストツールは、それぞれのチャネル（4–7）でのみ必要です。
