Apothem は 2 分未満でインストールでき、既存のハーネス構成と並行して動作します。
どの経路も同じ自己完結型エンジンを実行します——ソースツリーはベンダリングした依存関係を同梱しており、システムの Python 3.10 以降でチェックアウトから実行されます（[自己完結型ランタイム](/docs/architecture/self-contained-runtime)を参照）。

**すべての経路に共通する 2 つの前提条件:** `PATH` 上のシステム **Python 3.10 以降**と、そのもとでインポート可能な `click` および `rich` パッケージです。
npm シムとツールプラグインの経路は、`npx` を実行するために、さらに **Node.js 18 以降**を必要とします。
Python 3.10 と Node.js 18 および 20 は上流のサポート終了を過ぎています。引き続きサポートされテストされていますが、より新しいバージョンが推奨されます（[前提条件の一覧](#前提条件の一覧)を参照）。
以下の各チャネル固有の節では、その正確な前提条件、コピーしてすぐ使える 1 つのコマンド、検証ステップを改めて示します。

## チャネルを選ぶ

8 つのインストールチャネルが利用できます。すでに使っている作業方法に合わせて選んでください。

| # | チャネル | 提供内容 | 前提条件 |
|---|---------|----------|---------------|
| 1 | [Claude Code プラグイン](#1-claude-code-プラグイン) | Claude Code での完全なハーネス | Claude Code · Python 3.10+ |
| 2 | [npm シム（`npx`）](#2-npm-シムnpx) | 完全なハーネス、任意のツール | Node 18+ · Python 3.10+ |
| 3 | [ワンショットインストーラー](#3-ワンショットインストーラー) | 完全なハーネス + `apothem` コマンド | Python 3.10+（ネットワークインストールには `git`） |
| 4 | [VS Code 系拡張機能](#4-vs-code-系拡張機能) | エディターからの完全なハーネス | VS Code · Node 18+ · Python 3.10+ |
| 5 | [コマンドラインブートストラップ（拡張機能ホスト）](#5-コマンドラインブートストラップ拡張機能ホスト) | エンジンを実行するブートストラップ | そのホストツール · Node 18+ · Python 3.10+ |
| 6 | [コマンドラインブートストラップ（`qwen-code` ホスト）](#6-コマンドラインブートストラップqwen-code-ホスト) | エンジンを実行するブートストラップ | そのホストツール · Node 18+ · Python 3.10+ |
| 7 | [コマンドラインブートストラップ（プラグインホスト）](#7-コマンドラインブートストラッププラグインホスト) | エンジンを実行するブートストラップ | そのホストツール · Node 18+ · Python 3.10+ |
| 8 | [直接エンジン（`python -m apothem`）](#8-直接エンジンpython--m-apothem) | チェックアウトからの完全なハーネス | Python 3.10+（`click`、`rich`） |

<Callout title="完全なハーネスを提供するチャネル">
  npm シム（2）、ワンショットインストーラー（3）、直接エンジン（8）は、単独で任意のハーネス向けに同期ユニット全体をマテリアライズします。
  3 つのコマンドライン拡張機能（5–7）は、エンジン（`npx @ahmed-g-gad/apothem install`）へシェルアウトして完全なハーネスをマテリアライズする小さな**ブートストラップ**をインストールします——これらはエントリーポイントであり、それ自体で完全な提供物ではありません。
  Claude Code プラグイン（1）はエンジンを同梱し、それを直接実行します。
  VS Code 系拡張機能（4）は独自のエンジンを同梱しません。そのコマンドは、デフォルトでは npm シムを通してエンジンを実行します。
</Callout>

どの経路も冪等です。再実行は安全で、同じ状態に収束します。

## 1. Claude Code プラグイン

**前提条件:** Claude Code、および `PATH` 上のシステム Python 3.10+。

プラグイン経路は完全に Claude Code の内部で動作します。
Apothem エンジンを、そのスラッシュコマンド、委任ワーカー、スキル、ルール、フックとともに同梱しており、すべて自己完結型のプラグインツリーから実行できます。

```text title="Inside Claude Code"
/plugin marketplace add ahmed-g-gad/apothem
/plugin install apothem@apothem
```

インストール後、Apothem のコマンド一式、同梱の委任ワーカー、スキル、そして 4 つの[出力スタイル](/docs/reference/output-styles)（`/output-style` で、または `/config` から 1 つを選びます）が、すべての Claude Code セッションで利用可能になります。
プラグインのコマンドにはプラグインの接頭辞が付きます: `/apothem:plan-spec`、`/apothem:security-audit` などです。
他のコマンドがその名前を使っていない間は、Claude Code は短い形式（`/plan-spec`）も受け付けます。
2 つの名前は Claude Code 自身が使用しています。`/plan` はプランモードに入り、`/code-review` は同梱のレビューを実行するため、Apothem のコマンドには `/apothem:plan` と `/apothem:code-review` を入力してください。
プラグインではなく Apothem エンジンが Claude Code へのインストールを行う場合、コマンドは接頭辞のない、`~/.claude/skills/` 配下の個人用スキルになり、個人用の `code-review` スキルが同梱の `/code-review` を置き換えます（その `/review` エイリアスは引き続き同梱のものを実行します）。
`projectify` と `workflow` の 2 つの名前は、コマンドとスキルの両方として出荷されます。両方が存在する場合は Claude Code がスキルを実行するため、プラグインはスキルを実行し、エンジンのインストールはそのスロットにスキルを書き込みます。
コマンドの完全なカタログは[スラッシュコマンド](/docs/reference/commands)を参照してください。

**検証:** Claude Code 内で `/plugin` を実行し、**apothem** がインストール済みとして一覧に表示されることを確認するか、ターミナルからドリフトレポートを確認します。

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 2. npm シム（`npx`）

**前提条件:** Node.js 18+（`npx` 用）と、`PATH` 上のシステム Python 3.10+。
シムはインタープリターを見つけ、すべての CLI コマンドを同梱のエンジンへ転送します——システムには何も恒久的に配置されません。
`python3`、`python`、`py -3` の順に試します。**`APOTHEM_PYTHON`** にインタープリターのパスを設定すると、そのインタープリターが最初に試されます。これは、Python がインストールされているが `PATH` 上にない場合や、複数のバージョンがあり特定のものを使いたい場合に必要な設定です。
指定したインタープリターも、Python 3.10+ のチェックに合格する必要があります。合格しない場合、シムは `python3`、`python`、`py -3` の順にフォールバックします。

```bash title="npx"
npx @ahmed-g-gad/apothem install --harness claude-code
```

プロファイルのないマシンでは、この最初の `install` が `~/.config/apothem/profile.yaml` にスタータープロファイルを作成し、その旨を表示します。
そのアイデンティティフィールドはプレースホルダーです。それらを個人設定し（`npx @ahmed-g-gad/apothem profile edit`）、`install` の代わりに `update` を指定してコマンドを再実行し、適用してください。

リポジトリから直接実行することもできます。

```bash title="npx from the repository"
npx github:ahmed-g-gad/apothem install --harness claude-code
```

[CLI リファレンス](/docs/cli-reference)のすべてのコマンドがこの形式で動作します。`apothem` を `npx @ahmed-g-gad/apothem` に置き換えてください。
これは、OpenCode をはじめ、独立したプラグインや拡張機能のレジストリを公開しない他のすべてのツールのインストール経路でもあります——Apothem はそれらをネイティブな設定ディレクトリへ直接同期します（`npx @ahmed-g-gad/apothem install --harness opencode`）。

**検証:**

```bash title="Verify"
npx @ahmed-g-gad/apothem --version
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 3. ワンショットインストーラー

**前提条件:** `PATH` 上のシステム Python 3.10+（インストーラーは `click` / `rich` の前提条件を追加することを提案します）。`git` は、ソースをクローンするネットワークインストールの場合にのみ必要です。

インストーラースクリプトは、署名済みの最新リリースタグを解決し、その署名を検証し、そのタグの Apothem ソースツリーを `~/.apothem` に配置し、プロファイルが存在しない場合はスタータープロファイルを作成し、最初のハーネスをマテリアライズし、結果を検証します。これらすべてを 1 回の実行で行います。
スタータープロファイルにはプレースホルダーのアイデンティティフィールドが含まれています。それを編集してから `apothem update --harness <name>` を実行し、あなたの値を適用してください。
再実行は冪等です。既存のツリーは解決されたタグへ再チェックアウトされ、ハーネスは再マテリアライズされます。
タグに固定された検証済みインストールが、デフォルトかつ推奨の経路です。

```bash title="macOS · Linux · WSL2 · BSD — latest signed tag, verified"
curl -fsSL https://apothem.ahmedgad.com/install.sh | bash
```

```powershell title="Windows · PowerShell — latest signed tag, verified"
irm https://apothem.ahmedgad.com/install.ps1 | iex
```

同じスクリプトはチェックアウト内の `scripts/installer/` 配下にも同梱されています——`.sh`、`.ps1`、`.bat` 形式の `install`、`uninstall`、`update` です——そのため、クローン後に直接実行できます。

```bash title="From a checkout"
APOTHEM_HARNESS=claude-code sh scripts/installer/install.sh                                 # POSIX
$env:APOTHEM_HARNESS = 'claude-code'; pwsh -NoProfile -File scripts/installer/install.ps1   # Windows
```

### トラストモデル

`APOTHEM_REF` が設定されていない場合、インストーラーは最も高い `vMAJOR.MINOR.PATCH` リリースタグを解決し、*その*タグをチェックアウトします——動き続ける `main` ブランチをチェックアウトすることは決してありません。
いずれかの設定がマテリアライズされる前に、フェッチしたタグの署名が `git verify-tag` で検証されます。署名のない、改ざんされた、または検証できないタグは、何かが書き込まれる前にインストールを中止させます。
メンテナーの公開鍵がまだローカルのキーリングにない署名済みタグの場合は、代わりに鍵のインポートの案内を表示して中止します。鍵をインポートし、そのフィンガープリントを [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md) に公開されている値と照合してから、再実行してください。
特定のリリースに固定するには `APOTHEM_REF` を使います。

```bash title="Pinned, verified install"
APOTHEM_REF=vMAJOR.MINOR.PATCH sh -c "$(curl -fsSL https://apothem.ahmedgad.com/install.sh)"
```

`vMAJOR.MINOR.PATCH` を[リリースページ](https://github.com/ahmed-g-gad/apothem/releases)のタグに置き換えてください。
最も古いリリースタグは、それ自体の署名を持たない軽量タグであるため、そのコミットが署名されていても、タグのチェックはそのタグで中止します。それ以降のすべてのリリースタグは注釈付きで署名されています。
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md) のリリース署名のセクションに、各タグとその検証方法が記載されています。

明示的なオーバーライドは、既定の動作を緩めます。`APOTHEM_ALLOW_UNVERIFIED=1` は、検証の失敗を警告に格下げして続行します。エアギャップ環境、ローカル環境、または署名前のリリースでの利用を想定しています。`APOTHEM_REF=main` は、`APOTHEM_ALLOW_UNVERIFIED=1` と組み合わせた場合にのみ、検証なしで移動するブランチをチェックアウトします。`APOTHEM_REF=main` だけを指定すると、インストーラーは `main` を `APOTHEM_HOME` に取得したうえで、ブランチは署名付きリリースタグではないため、設定がマテリアライズされる前に中止します。`APOTHEM_SOURCE` によるローカルチェックアウトは何も取得せず、検証もスキップします。

`APOTHEM_VERIFY=checksum` は、メンテナーの公開鍵をまだ保持していないホスト向けの中間の経路です。
インストーラーはクローンする代わりに、リリースのプラットフォームアーカイブとその `SHA256SUMS` をダウンロードし、何かを展開する前にダイジェストの不一致があれば中止し、一致するダイジェストが証明するのは、そのアーカイブがリリースに記載されたものであることであって、誰が公開したかではないと警告します。

その後、エンジンは配置されたツリーから直接実行されます。
`click` と `rich` を除くすべてのサードパーティ依存関係はソースツリー内にベンダリングされており、エントリーポイントがそのベンダーディレクトリを自ら `sys.path` に追加します。

```bash
PYTHONPATH="$HOME/.apothem/src" python -m apothem <command>
```

両方のスクリプトは同じ設定用環境変数（`APOTHEM_HOME`、`APOTHEM_REPO`、`APOTHEM_REF`、`APOTHEM_ALLOW_UNVERIFIED`、`APOTHEM_VERIFY`、`APOTHEM_RELEASE_BASE`、`APOTHEM_SOURCE`、`APOTHEM_HARNESS`、`APOTHEM_PROFILE`、`APOTHEM_SKIP_VERIFY`、`APOTHEM_AUTO_INSTALL_DEPS`、`APOTHEM_BIN_DIR`）を読み取ります。
完全な表は[インストーラーの環境変数](/docs/how-to/installer-environment-variables)を、`python -m` の呼び出しモデルの仕組みは[自己完結型ランタイム](/docs/architecture/self-contained-runtime)を参照してください。

**`apothem` コマンド。** インストールが成功すると、インストーラーは同梱のエンジンへ転送する `apothem` シムを書き込みます——POSIX では `$HOME/.local/bin` に、Windows では `%LOCALAPPDATA%\Microsoft\WindowsApps`（デフォルトの Windows `PATH` にすでに含まれているユーザーディレクトリ）に書き込みます。
インストーラーがあなたの `PATH` を編集することは決してありません。
そのディレクトリが `PATH` 上に入れば、手動の `PYTHONPATH` なしで `apothem <command>` を直接実行できます。

**検証:**

```bash title="Verify"
apothem verify --harness claude-code

# or, before the shim is on PATH, from the bundled source:
PYTHONPATH="$HOME/.apothem/src" python -m apothem verify --harness claude-code
```

## 4. VS Code 系拡張機能

**前提条件:** VS Code、Node.js 18+、および `PATH` 上のシステム Python 3.10+。

**Apothem** 拡張機能は `apothem.vsix` パッケージからインストールします: `code --install-extension apothem.vsix`、またはエディターの *Install from VSIX…* コマンドを使います。
リリースワークフローがパッケージに署名し、各 GitHub Release に添付します。
ワークフローが拡張機能をパッケージ化するようになる前に公開されたリリースには、パッケージは含まれていません。最新のリリースにパッケージがない場合は、`.github/vsce/` にロックされた vsce リリースを使ってチェックアウトからパッケージをビルドしてください。これには Node.js 22 以降が必要です。`npm ci --prefix .github/vsce --ignore-scripts` を実行し、続いて
`cd vscode-extension && ../.github/vsce/node_modules/.bin/vsce package --no-dependencies --out apothem.vsix` を実行します。
[Visual Studio Marketplace](https://marketplace.visualstudio.com/) への掲載はまだ公開されていません。
1 つの拡張機能で、VS Code とそのエディター内のコンパニオンアシスタント面をカバーします。
そのパレットコマンド（`Apothem: Install`、`Verify`、`Update`、`Uninstall`、`Doctor`）は、設定されたランナーを通して同じエンジンを実行します（デフォルトは `npx @ahmed-g-gad/apothem@<extension version>` で、拡張機能は自身とともに出荷されたバージョンのエンジンを実行します。ソースから実行するには、ユーザー設定 `apothem.runner` をローカルチェックアウトに向けます）。
Install、Verify、Update、Uninstall はどのハーネスを対象にするかを尋ね、エディター自身のハーネスを最初に提示します。`all` は選択肢の 1 つであり、決してデフォルトにはなりません。
`apothem.runner` 設定はマシンスコープであるため、ワークスペースから変更することはできません。また、拡張機能は信頼されたワークスペースでのみ動作します。

**検証:** エディターのコマンドパレットから **Apothem: Verify** コマンドを実行するか、ターミナルから次を実行します。

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 5. コマンドラインブートストラップ（拡張機能ホスト）

**前提条件:** そのホストのコマンドラインツール、Node.js 18+、および `PATH` 上のシステム Python 3.10+。

Apothem をリポジトリから直接、拡張機能としてインストールします——コマンドには正確なホストとハーネスのスラッグが含まれています。

```bash title="Install the extension"
gemini extensions install https://github.com/ahmed-g-gad/apothem
```

この拡張機能は**ブートストラップ**であり、それ単独では完全なインストールではありません。Apothem のコンテキストファイルを読み込み、エンジン（`npx @ahmed-g-gad/apothem`）へシェルアウトする `/apothem` コマンドを追加します。
それを通してインストールを実行し、完全なハーネスをマテリアライズしてください。

```bash title="Materialize the full harness"
npx @ahmed-g-gad/apothem install --harness gemini-cli --project .
```

**検証:**

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness gemini-cli --project .
```

それを通してインストールを実行し、完全なハーネスをマテリアライズしてください。

```bash title="Materialize the full harness"
npx @ahmed-g-gad/apothem install --harness qwen-code
```

**検証:**

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness qwen-code
```

リポジトリをプラグインマーケットプレイスとして追加してから、プラグインをインストールします——コマンドには正確なホストとハーネスのスラッグが含まれています。

```bash title="Install the plugin"

codex plugin add apothem@apothem
```

それを通してインストールを実行し、完全なハーネスをマテリアライズしてください。

```bash title="Materialize the full harness"
npx @ahmed-g-gad/apothem install --harness codex
```

**検証:**

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness codex
```

## 8. 直接エンジン（`python -m apothem`）

**前提条件:** `click` と `rich` パッケージがインポート可能なシステム Python 3.10+、加えてリポジトリのチェックアウト。Node.js は不要です。

クローンからエンジンを直接実行します。
エントリーポイントがベンダリングされた依存関係（`src/apothem/_vendor`）を `sys.path` に追加するため、`click` と `rich` がインポート可能であれば、セットアップは `PYTHONPATH=src` だけで完了します。

```bash title="Direct engine"
git clone https://github.com/ahmed-g-gad/apothem
cd apothem
PYTHONPATH=src python -m apothem install --harness claude-code
```

npm シムと同様に、プロファイルのないマシンでの最初の `install` は `~/.config/apothem/profile.yaml` にスタータープロファイルを作成し、処理を続行します。

**検証:**

```bash title="Verify"
PYTHONPATH=src python -m apothem verify --harness claude-code
```

## 任意のインストールを検証する

上記の各チャネルには、それぞれ独自の検証コマンドが示されています。2 つの汎用形式は次のとおりです。

```bash title="Installer path"
PYTHONPATH="$HOME/.apothem/src" python -m apothem verify --harness claude-code
```

```bash title="npx path"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

ハーネス名は、インストールしたアダプターに置き換えてください。サポートされているすべての名前は[ハーネス一覧](/docs/harnesses)を参照してください。
インストール済みのすべてのアダプター（その検証とフックコマンド）を一度にチェックするには、同じ形式で `apothem doctor`（または `npx @ahmed-g-gad/apothem doctor`）を実行します。
プラグイン経路の場合は、Claude Code 内で `/plugin` を実行し、**apothem** がインストール済みとして一覧に表示されることを確認してください。

## 前提条件の一覧

- **Python 3.10 以降** —— エンジンを実行するすべての経路がこれを探します（`python3`、`python`、バージョン付きの名前、そして Windows では `py -3`）。
- そのインタープリターで **`click` と `rich` がインポート可能であること** —— エンジンがベンダリングしない、ターミナル向けの 2 つの依存関係です。
  インストーラーは両方をチェックし、欠けているものを示し、あなたの代わりにインストールすることを提案します——あなたの確認を得て、または `--yes`（PowerShell では `-Yes`）か `APOTHEM_AUTO_INSTALL_DEPS=1` によって自動的に。
  その他のすべてのチャネルでは、パッケージが欠けているとエンジンはエラー（終了コード 1）で停止します。このエラーは、見つかったインタープリター用の正確なコマンドを、Apothem がテストされているバージョン制約とともに示します（`<interpreter> -m pip install "click==…" "rich>=…"`）。
  `--json` を指定すると、同じエラーがコード `runtime.dependency_missing` を持つ JSON エンベロープとして届きます。
- **Node.js 18 以降** —— npm シムとツールプラグインの経路のみ。
- **サポート終了したランタイム。** Python 3.10 は 2026-10-01 に、Node.js 18 と 20 はそれぞれ 2025-04-30 と 2026-04-30 に、上流のサポート終了を迎えました。
  Apothem は宣言された下限としてこれらを引き続きサポートし、CI でそれぞれをテストしていますが、これらはもう上流のセキュリティ修正を受け取らないため、Python 3.11 以降と Node.js 22 以降を優先して使用してください。
  下限の引き上げ方は[ランタイム下限ポリシー](/docs/governance/release-engineering-policy#ランタイムの下限)で説明しています。
- **Git** —— インストーラー経路のみ、それもネットワーク形式の場合のみです（スクリプトがソースをクローンします。ローカルチェックアウトにはクローンは不要です）。
- **Claude Code** —— プラグイン経路のみ。**VS Code** と、各コマンドラインブートストラップ自身のホストツールは、それぞれのチャネル（4–7）でのみ必要です。
