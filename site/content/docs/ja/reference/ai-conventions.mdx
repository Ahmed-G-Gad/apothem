> **下流のコントリビューター向けの正規の規範的リファレンス。** このドキュメントは、プロジェクト仕様のマルチサーフェスハーネス規約のセクション（仕様 §0.6 + §2.8 + §4.7）を反映したものであり、公開リポジトリに同梱される独立したリファレンスです。アーキテクチャ上の根拠は [ADR-0003](/docs/architecture) に記録されています。

---

## 1. なぜ複数なのか

現代のエンジニアリングサーフェスには、複数のハーネス — チャットコンソール、IDE 内の補完エンジン、ペアプログラミングのコンパニオン、プルリクエストのレビュアー — が関わります。それぞれが独自の正規の設定ファイルを読み取ります。プロジェクトがそのようなファイルを 1 つしか出荷しない場合、残りのランタイムは明文化されていない規約に対して暗黙のうちに独自判断で動き、欠けているリポジトリ内のメモリはただちに漏れ出します。

サーフェスが欠けていることの代償は、**機械生成コードにおける気づかれないドリフト**です — 目に見えないまま蓄積するため、最悪の種類の欠陥です。機械生成されるアーティファクトのひとつひとつが乖離を増幅させ、人間のレビュアーが矛盾に気づくころには、コードベースは何週間分もの一貫しない規約を抱えています。

ハーネスランタイムの設定は、デプロイの現実からして複数になります。公開されるエコシステムは、チャットコンソールランタイム向けの振る舞いメモリファイルと、IDE 内補完ランタイム向けのリポジトリスコープの指示ファイルの両方を出荷しなければなりません（MUST）。2 つのサーフェスは相互に整合していなければならず（MUST）— 矛盾もドリフトもなく — 同じディシプリンを共同でエンコードしなければなりません（MUST）。

## 2. 整合性契約

スコープ内（§3）のすべての規約サーフェスは、プロジェクトの単一の規約仕様を表現する*チャネル*です。仕様は次のように分解されます:

- **共有セクション** — 計画ディシプリン、構造化照会（またはサーフェス上の同等手段）、著作者ヘッダー、命名、アンチパターン、モーダル階層。これらはすべての必須サーフェスに現れなければならず（MUST）、サーフェス間で意味的に等価でなければなりません（MUST）。
- **サーフェス固有のセクション** — 能力の位置づけ、ツール呼び出しのパターン、コード生成とチャットの違い。これらはサーフェス間で異なっていてもかまいません（MAY）が、共有セクションと矛盾してはなりません（MUST NOT）。

`multi-surface-coherence` バリデーター（§7）は、すべての CI 実行とプリコミットで実行され、契約が守られていることをアサートします。

2 つ（またはそれ以上）のサーフェスは、1 つの*仕様*を表現する異なる*チャネル*です。共有セクションは、サーフェス間で — 意味的に、そして可能な場合は字句的にも — 一致しなければなりません（MUST）。サーフェス固有のセクションは、共有セクションと矛盾してはなりません（MUST NOT）。

## 4. IDE 内指示ファイルのセクション一覧

`.github/` 配下のリポジトリスコープの指示ファイルは、以下のセクションをこの順序で含まなければなりません（MUST）（各セクションは下記の見出しテキストを正確に用います。セクション本文はテンプレートから刻印するのではなく執筆しますが、各セクションは列挙された主張を網羅しなければなりません（MUST））:

1. **Project Context** — 1 段落: このリポジトリが何であるか、誰が使うか、そのトップレベルの形状。具体的に書き、マーケティング表現は使わない。
2. **Coding Conventions** — 命名、モーダル階層、フロントマター、Markdown のスタイル、デフォルトから外れる箇所での言語固有のスタイル上の要点。
{/* REUSE-IgnoreStart */}
3. **File Headers** — ランタイムが生成するすべてのファイルは、[`site/content/docs/reference/authorship-header.mdx`](/docs/reference/authorship-header) に従い、ファイルタイプに合ったコメントの形式で、正規の単一の `SPDX-License-Identifier: MIT` 行から始まらなければなりません（MUST）。`scripts/inject-header.*` と `site/content/docs/reference/authorship-header.mdx` への参照。
{/* REUSE-IgnoreEnd */}
4. **Plans Discipline** — ランタイムは、ハーネスの設定ディレクトリ（たとえば `~/.claude/plans/` や `~/.codex/.plans/`）やその他のグローバルな計画の場所に書き込むコードやスクリプトを生成してはなりません（MUST NOT）。計画アーティファクトは、[`site/content/docs/reference/plans-discipline.mdx`](/docs/reference/plans-discipline) に従って `<project-root>/.apothem/plans/` に置かれます（レガシーの `<project-root>/.plans/` ツリーは `apothem migrate-workspace` でアップグレードします）。
5. **Structured Inquiry Behavior** — ランタイムは、確信が持てないときに、暗黙のうちに捏造してはなりません（MUST NOT）。代わりに、明確に示された確認ブロック（例: `# TODO(clarify): <question>` コメント）を挿入し、サーフェスが許す場合はチャットで質問を提示します。API をでっち上げない、モデル名をでっち上げない、ファイルパスをでっち上げない。
6. **Forbidden Patterns** — 明示的な禁止事項: マーケティング的な形容詞を使わない、曖昧にぼかす埋め草を使わない、console.log によるデバッグの残骸を残さない、ユーザーのホームへの絶対パスをハードコードしない、シークレットをコミットしない、`.apothem/plans/`（またはレガシーの `.plans/`）配下のファイルをコミットしない、正規のプロジェクト指示ファイルと矛盾しない。
7. **Output Format** — 生成されるコードや文章は、統一された会話出力規約に準拠します: 断定性、統一されたセクション構成、密度、要約のディシプリン、引用。コードについては: 公開サーフェスが文書化されていること、言語が型をサポートする場合は型付けされていること、テストの足場がある場合はテストされていること。
8. **Review Checklist** — レビュアー（人間、または PR レビューモードのランタイム）が承認前に検証しなければならない（MUST）事項: ヘッダーがあること、命名が準拠していること、`.apothem/plans/` への書き込みがないこと、正規のプロジェクト指示ファイルとの矛盾がないこと、バリデーターがローカルでグリーンであること。
9. **Pointers** — `AGENTS.md`、`CLAUDE.md`、`site/content/docs/reference/plans-discipline.mdx`、`site/content/docs/reference/authorship-header.mdx`、この規約ドキュメント、`schemas/`、`CONTRIBUTING.md` へのリンク。

このファイルは、[`site/content/docs/reference/authorship-header.mdx`](/docs/reference/authorship-header) §2 に従い、正規の著作者ヘッダーの SPDX 行（Markdown 形式）から始まります — 表示するか非表示にするかは、プロジェクトが選択したヘッダー可視性ポリシーに従います。

IDE 内指示ファイルは、`AGENTS.md` や `CLAUDE.md` の逐語的なコピーでは**ありません**。`AGENTS.md` は正規のプロジェクト指示サーフェスであり、`CLAUDE.md` はそれを Claude Code 向けに反映し、IDE 内指示ファイルは、開発者が採用または却下する提案を出すエディター内のコード補完ランタイムに向けた語り口で書かれます。*情報*（ディシプリン、規約、アンチパターン）は同一であり、*枠組み*が異なります。

## 5. 主張リストのリファレンス

[`tests/fixtures/multi-surface-claims.yaml`](https://github.com/ahmed-g-gad/apothem/blob/main/tests/fixtures/multi-surface-claims.yaml) にあるフィクスチャは、共有される各主張を列挙します。サンプルエントリ:

```yaml
- id: plans.location
  claim: "Planning artifacts live at <project-root>/.apothem/plans/, never inside a harness configuration directory."
  required-in: [AGENTS.md, CLAUDE.md, .github/copilot-instructions.md]
  optional-in: [site/content/docs/architecture/agents.mdx, .cursorrules]
- id: header.canonical
  claim: "Every applicable new file begins with the canonical authorship-header banner per site/content/docs/reference/authorship-header.mdx."
  required-in: [AGENTS.md, CLAUDE.md, .github/copilot-instructions.md]
- id: ambiguity.resolution
  claim: "Ambiguity is surfaced via the structured-inquiry channel or a clearly-marked TODO(clarify); never silently invented."
  required-in: [AGENTS.md, CLAUDE.md, .github/copilot-instructions.md]
# ... (one entry per shared claim)
```

バリデーターは各サーフェスをパースし、各主張がサーフェス上に存在するかどうかを（見出し階層 + 本文のキーワード抽出によって）探し、欠落や矛盾が 1 つでもあれば失敗します。

## 6. 調停ルール

共有される主張について 2 つのサーフェスが矛盾していると検出された場合、デフォルトの調停は次のとおりです:

> `AGENTS.md` は正規のプロジェクトの声です。矛盾するサーフェスはすべて、`AGENTS.md` のセマンティクスをそのサーフェスに適した枠組みで反映するように書き直されます。

サーフェス固有のオーバーライドは、意図的な乖離を説明する ADR を指す、明示的なファイル内の `<!-- coherence-override: <claim-id> -->` マーカーがある場合にのみ許可されます。オーバーライドマーカー自体もバリデーターの許可リストに列挙され、CI レポートに表示されます。

このリポジトリで承認された調停戦略は **`agents-md-wins`** です: `AGENTS.md` が正規であり、アクティブなすべてのハーネスミラーは意味的に等価な状態を保ちます。

## 7. バリデーター

3 つのバリデーターが整合性契約を共同で実装します:

```text
- in-IDE-instructions-presence    (src/apothem/conformity/copilot_instructions_presence_grep.py)
- multi-surface-coherence         (src/apothem/conformity/multi_surface_coherence_grep.py)
- license-author-consistency      (src/apothem/conformity/license_author_consistency_grep.py)
```

- 1 つ目は、IDE 内指示ファイルが存在し、パースでき、§4 に列挙されたすべての正規セクションを含み、正規の著作者バナーから始まることをアサートします。
- 2 つ目は、各サーフェスの正規セクションをパースし、共有セクションが正規化された比較器のもとで相互に一貫していることをアサートします（大文字と小文字を区別せず、空白の違いを許容し、字句的な言い換えは認めるが、フィクスチャで定義された主張リストについては意味的な等価性を要求する）。
- 3 つ目は、LICENSE の著作権行と、正規バナーの「Copyright (c)」行が同じ著作者を挙げていることをアサートします。

## 8. サーフェスのライフサイクル

- **サーフェスを追加する。** オペレーターは、構造化照会チャネルを通じて、またはその後の `make surfaces-add <name>` によってオプトインします。ジェネレーターは主張リストに照らしてサーフェスを執筆し、バリデーターを実行し、サーフェス固有のオーバーライドが必要な場合は ADR を起票します。
- **サーフェスを削除する。** 構造化照会が削除を確認し、ADR が根拠を記録し、バリデーターの required-in リストが修正されます。
- **ドリフトの検出。** 主張リストから逸脱するコミットは、プリコミット / CI によって拒否されます。コミットの作者は、整合性を回復するためにサーフェスを書き直します。
