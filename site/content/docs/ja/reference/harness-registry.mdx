ハーネスレジストリは、CLI、ドキュメント、フィクスチャテスト、規約ピンの検証が使用する、
信頼できる情報源としてのアダプターインベントリです。ランタイムのソースは
`src/apothem/lib/harness_registry.py` であり、以下のすべての行は、そのレジストリ、
アダプターごとの `capabilities.yml`、そして各アダプターの
`STANDARD-CONVENTION-PIN.md` まで追跡できます。

## ペイロードコホートのサポート

ステータス値は `native`、`converted`、`support-tree`、
`profile-projected`、`unsupported`、`not-applicable`、
`discovery-pending` です。

`converted` のコホートはハーネス独自のフォーマットに書き換えられ、ソースのフィールドの一部は
そこに収まる場所がありません。変換されるコマンド、エージェント、ルールの各コホートについて、
アダプターの `capabilities.yml` は、ソースの各 frontmatter フィールドがどうなるかを示す
`conversion_losses` マップを持ちます。

| 値 | 意味 |
| --- | --- |
| `native:<field>` | ハーネスはそのフィールドの下でそれを読み取ります。 |
| `sidecar:<path>` | 変換後のファイルの隣にある別のファイルに書き込まれます。たとえば Codex の `agents/openai.yaml` です。 |
| `filename` | ファイル名またはフォルダー名がそれを担います。 |
| `inlined` | プロンプトまたは本文のテキストに移されます。 |
| `ignored` | ファイルには残りますが、ハーネスはそれを読み取りません。 |
| `dropped` | 除外されます。 |

テストが変換後のすべてのファイルをレンダリングし、マップを出力と照合します。

| ハーネス | ネイティブまたは変換済みのペイロード | サポートツリーのペイロード | 未サポートまたは保留中の警告 |

## 共有ルート

一部のインストールターゲットは、それを書き込むハーネス以外のハーネスによって読み込まれます。
レジストリは、そのような各パスを `SHARED_ROOTS` に記録します。記録には、1 つの登録済みオーナー
（ベンダーがそのパスを文書化している対象のアダプター）、同じファイルをそこに書き込む共同インストーラー、
ベンダーのドキュメントがデフォルトでそれを読み込むとしているリーダー、さらにそれを示すベンダーの
ページと、それらを取得した日付が含まれます。

共同インストーラーを持つパスは、複数のインストールが同じバイト列で書き込む、ホームディレクトリ内の
ユーザーレベルのフォルダーです。`Cursor` だけがインストールされたマシンには `~/.agents/skills/` を
書き込む `Codex` がないため、そのフォルダーを挙げる各インストールがそれを書き込み、インストール台帳が
そのフォルダーを使うインストールの数を数えます。記録上のオーナーは、登録済みオーナーがそのフォルダーを
使っている間はそのオーナーであり、そうでなければフォルダーを使うインストールのうち最も古いものです。
登録済みオーナーがアンインストールされても、何も移動しません。アンインストールがフォルダーを削除するのは、
それをまだ使っている他のインストールがない場合だけです（[`uninstall`](/docs/cli-reference/uninstall#shared-folders-in-your-home-directory) を参照）。
リーダーをインストールしてもフォルダーにファイルは置かれません。オーナーまたは共同インストーラーを
インストールすると、Apothem のコンテンツがすべてのリーダーの前に置かれます。

| パス | オーナー | 共同インストーラー | リーダー |
| --- | --- | --- | --- |
| `~/.agents/skills/` | Codex | Cursor、GitHub Copilot、Windsurf、Zed | Gemini CLI、Kimi Code、Open-Claw、OpenCode、Qwen Code |
| `~/.config/apothem/rules/` | Codex | CodeBuddy、Cursor、GitHub Copilot、Kiro、Trae、Windsurf、Zed | なし |
| `~/.config/apothem/templates/` | Codex | CodeBuddy、Cursor、GitHub Copilot、Kiro、Trae、Windsurf、Zed | なし |
| `~/.claude/skills/` | Claude Code | なし | Cursor、OpenCode |
| `~/.claude/agents/` | Claude Code | なし | Cursor |
| `~/.codex/agents/` | Codex | なし | Cursor |
| `~/.claude/CLAUDE.md` | Claude Code | なし | OpenCode、Windsurf |
| `<project>/AGENTS.md` | Kimi Code | なし | Antigravity、Claude Code、CodeBuddy、Codex、Cursor、GitHub Copilot、Hermes、Kiro、OpenCode、Windsurf、Zed |
| `<project>/GEMINI.md` | Gemini CLI | なし | Antigravity、GitHub Copilot、Zed |
| `~/.gemini/GEMINI.md` | Antigravity | なし | Gemini CLI |
| `<project>/.github/copilot-instructions.md` | GitHub Copilot | なし | Zed |
| `<project>/.cursor/rules/apothem-rules.mdc` | Cursor | なし | Hermes、Windsurf |

`~/.config/apothem/rules/` と `~/.config/apothem/templates/` は、Apothem 自身のスキルと命令ファイルが
引用するファイルを保持します。他のツールはこれらを読み込まないため、リーダーもベンダーのページも
ありません。`CodeBuddy`、`Kiro`、`Trae` は、それぞれ独自のスキルフォルダー（`~/.codebuddy/skills/`、
`~/.kiro/skills/`、`~/.trae/skills/`）も書き込みます。それを読み込むのはそのツールだけなので、
共有ルートではありません。

リーダーが列挙されるのは、そのベンダーのドキュメントがまさにそのパスのデフォルトでの読み込みを
示している場合だけです。リーダーがあるパスを一部の場合にだけ読み込むときは、レジストリがその条件を
記録し、インストールの注記がそれを繰り返します。
`Open-Claw` は、デフォルトの状態ディレクトリのもとでのみ `~/.agents/skills/` を
インデックスします（`OPENCLAW_STATE_DIR` が別の場所を指している場合はそのフォルダーを
スキップします）。`OpenCode` 1 は、その設定フォルダー（デフォルトでは `~/.config/opencode/`）に
`AGENTS.md` が存在しない場合にのみ
`~/.claude/CLAUDE.md` を読み込み、`OPENCODE_DISABLE_CLAUDE_CODE_PROMPT=1` または
`OPENCODE_DISABLE_CLAUDE_CODE=1` が設定されている場合は読み込みません。`OpenCode` 2 は同じ
`~/.config/opencode/` 設定を読み取りますが、`CLAUDE.md` のフォールバックがないため、
`~/.claude/CLAUDE.md` を読み込みません。`Codex` は各フォルダーで `AGENTS.override.md` と
`AGENTS.md` のうち最初のものを採用するため、`<project>/AGENTS.md` を読み込むのは、
その隣に `AGENTS.override.md` がない場合だけです。`CodeBuddy` は、プロジェクトに `CODEBUDDY.md`
がない場合にのみ、`<project>/AGENTS.md` をプロジェクトメモリとして使います。`Claude Code` は、その[メモリのページ](https://code.claude.com/docs/en/memory#agents-md)が挙げるリリースで `AGENTS.md` を読み取り、インストールの注記がその最初のリリースを示します。既定の **Project
instructions** 設定のもとでは、セッションの開始時に、作業フォルダーとその上位のフォルダーにあるすべての `AGENTS.md` と `.claude/AGENTS.md` を読み込みますが、それはそれらのフォルダーのいずれにも `CLAUDE.md`、`.claude/CLAUDE.md`、`CLAUDE.local.md` がない場合に限られます。親フォルダーから開いたプロジェクトのように、作業フォルダーより下位にあるフォルダーの `AGENTS.md` は、その Read ツールがそこにあるファイルを開き、かつそのフォルダーにもその 3 つのファイルがいずれもない場合に読み込みます。
`~/.claude/CLAUDE.md` は数に入らないため、そこにある Apothem のブロックは `<project>/AGENTS.md` とともに読み込まれ続けます。`claude-md-and-agents-md` 設定は両方の種類のファイルを読み込み、`claude-md` と `managed-only` は `AGENTS.md` を読み込みません。
どの設定でも `AGENTS.md` を読み取らないセッションもあり、メモリのページがそれらを挙げています。`Zed` は、リストにある
プロジェクト命令ファイルのうち最初の 1 つだけを読み込みます。そのリストは、`.rules`、
`.cursorrules`、`.windsurfrules`、`.clinerules`、`.github/copilot-instructions.md`、`AGENT.md`、
`AGENTS.md`、`CLAUDE.md`、その後に `GEMINI.md` です。そのため、
`<project>/.github/copilot-instructions.md`、`<project>/AGENTS.md`、`<project>/GEMINI.md` は、
プロジェクトにリストでそのファイルより前のファイルが 1 つもない場合にのみ読み込まれます。`Zed` の
インストールは、リストの最初のファイルである `<project>/.rules` を書き込むため、`Zed` は、
インストール先のプロジェクトでは、この 3 つのいずれも読み込みません。

`Hermes` は、1 セッションにつきプロジェクトコンテキストを 1 種類しか読み込みません。読み込まれるのは、
空でないファイルがある最初の種類で、その順序は、`.hermes.md` または `HERMES.md`、`AGENTS.md`
チェーン（各フォルダーでは、空でない `AGENTS.override.md` が、その隣の `AGENTS.md` の代わりに
読み込まれます）、`CLAUDE.md`、その後に `Cursor` のルールです。そのため、`<project>/AGENTS.md` は、
プロジェクトに `.hermes.md` も `HERMES.md` もなく、その隣に `AGENTS.override.md` もない場合にのみ
読み込まれ、`<project>/.cursor/rules/apothem-rules.mdc` は、プロジェクトに `.hermes.md`、
`HERMES.md`、`AGENTS.override.md`、`AGENTS.md`、`CLAUDE.md` のいずれもない場合にのみ読み込まれます。
`Hermes` は、`.hermes.md` と `HERMES.md` を、開始したフォルダーから git ルートまで上方向に探し、
`AGENTS.md` チェーンを git ルートから下方向に読み取るため、プロジェクトより上位のフォルダーに
あるそのようなファイルも対象に含まれます。空のファイルは対象になりません。空の `.hermes.md` は、
その隣の `HERMES.md` も隠すため、その `HERMES.md` にテキストがあっても、`Hermes` は `AGENTS.md`
チェーンに進みます。これらの条件は、プロジェクト内で開始したセッションに適用されます。
プロジェクトより上位のフォルダーで開始したセッションでも、プロジェクトにどのような `.hermes.md` や
`HERMES.md` があっても、そのセッションがプロジェクト内のファイルを初めて操作するときに、
`<project>/AGENTS.md`、またはその隣にある空でない `AGENTS.override.md` を読み込むことがあります。
`Hermes` は、ホームフォルダーと一部のコンテナーフォルダーでは、これをスキップします。

`Cursor` の
ドキュメントは `~/.codex/agents/` を `Codex` 互換フォルダーとして挙げていますが、`Cursor` がそこで
どのファイル形式を解析するかは述べておらず、`Codex` のインストールは TOML ファイルを書き込むため、
`Cursor` がそれらのヘルパーを読むかどうかは確認されていません。`Cursor` のインストールは、ヘルパーの
独自のコピーを `<project>/.cursor/agents/` にも書き込み、ベンダーの優先順位ではそれがインポートする
フォルダーより上位に置かれるため、インストール済みのプロジェクトでは、ネイティブのコピーが
`~/.claude/agents/` からのコピーに優先します。

`Windsurf` は、Devin の設定インポートを通じて他のツールのルールファイルを読み込みます。
この設定インポートはデフォルトでオンであり、Devin Desktop の Local エージェントは
Devin CLI と同じ方法でファイルを見つけます。そのため、`~/.claude/CLAUDE.md` に `Claude Code` の
インストールが書き込むブロックと、`Cursor` のインストールが書き込む
`<project>/.cursor/rules/apothem-rules.mdc` を読み込みます。このファイルは、フロントマターの
`alwaysApply: true` によってすべてのセッションで有効のままになります。このインポートは
プロジェクトの `CLAUDE.md` も読み込みますが、どの Apothem インストールもこれを書き込みません。

一部のツールは、意図的に `~/.agents/skills/` のリーダーになっていません。`Antigravity`、`CodeBuddy`、
`Kiro`、`Trae` のドキュメントは、それをデフォルトで読み込むとは述べていません（`Trae` は、設定を
有効にした後でのみプロジェクトの `.agents/skills/` フォルダーを読み込みます）。これが、`CodeBuddy`、
`Kiro`、`Trae` が独自のスキルフォルダーを持つ理由です。`Hermes` のドキュメントは、それを
`skills.external_dirs` の値の例としてのみ挙げています。`GitHub Copilot` は `~/.claude/agents/` の
リーダーではありません。VS Code のドキュメントはそのフォルダーを Anthropic の Claude エージェント向けに
挙げており、`GitHub Copilot` が実行するエージェント向けではありません。

オーナーが共有の命令ファイルに書き込む Apothem ブロックは、特定の 1 つのツールをリーダーとして
名指ししません。
`tests/unit/test_shared_roots.py` は、レジストリターゲットを書き込むアダプターが
そのオーナーと共同インストーラーにちょうど一致しない場合、およびツール横断の命令ファイル（`AGENTS.md`、`CLAUDE.md`、
`GEMINI.md`、`copilot-instructions.md`）のような名前を持つレジストリターゲットに宣言された
オーナーがない場合に失敗します。ただし `~/.codex/AGENTS.md` は対象外で、これを読み込むと
文書化している登録済みのハーネスは他にありません。

## リリースチャネル

`scripts/dev/vendor-release-channels.json` には、ハーネスフォルダーごとに 1 つのエントリーがあります。監視対象のハーネスは、そのリリースチャネルを一覧にします。各チャネルは、最後にレビューされたバージョンを日付とともに記録します。それはそのピンが挙げるバージョン、またはピンがバージョンを挙げていない場合は、チャネルが記録された時点でレジストリが提供していたバージョンです。記録はメジャーバージョンだけを保持することもできます。各チャネルは、それを挙げるピンのフレーズを引用します。バージョンの最初の数字がそのメジャーバージョンであり、0 も含まれます。そのため、0.26 から 0.27 に移る 0.x 系列は、より新しいマイナーバージョンとして報告され、失敗にはなりません。OpenClaw の年.月.リリース番号のようなカレンダーバージョンを持つチャネルは、より新しいリリースをすべて失敗にせずに報告し、`watch` レベルを取りません。Codex、Gemini CLI、Hermes、Qwen Code、GLM は 0.x 系列にあるため、それらのいずれかの新しいバージョンは、そのチャネルが `watch` レベルを設定していない限り、1.0 に達するまでは実行のサマリーに一覧表示されるだけで issue は作成されません。

OpenCode には 4 つのチャネルがあります。`opencode-ai` は OpenCode 1 を、`@opencode/cli` は OpenCode 2 を提供します。`anomalyco/opencode` の GitHub リリースは、どの npm パッケージとして提供されるかに関係なく、新しいメジャー系列を示します。4 つ目のチャネルは、`opencode.ai/install` のリダイレクト先を問い合わせます。2026-11-03 には、OpenCode 1 のインストーラースクリプトにリダイレクトしていました。そのスクリプトは、`opencode-ai` の `latest` dist-tag が OpenCode 1 のバージョンを挙げている場合にそのバージョンをインストールし、OpenCode 2 をインストールすることは決してありません。2026-11-03 の OpenCode の決定では、2 つのシグナルのいずれかが現れたときに、OpenCode 2 が動作する場所で OpenCode 2 独自の形式を書き込むことに移行します。そのシグナルとは、OpenCode 2 が OpenCode 1 の形式の変換を削除する日付を告知すること、または `opencode.ai/install` か `opencode-ai` が OpenCode 2 に移ることです。チェックは 2 つ目のシグナルを監視します。`opencode-ai` チャネルとインストーラーチャネルはそれぞれトリガーを持ちます。`opencode-ai` の `latest` バージョンがメジャーバージョン 1 を超えたとき、または `opencode.ai/install` が OpenCode 1 のスクリプトへのリダイレクトをやめたときに、チェックは失敗します。そのスクリプト内部の変更はリダイレクトを変えないため、チェックはそれを認識しません。1 つ目のシグナルに答えるレジストリはないため、それは手作業での確認のままであり、OpenCode のピンの次回のレビューとともに 2027-02-01 までが期限です。

Antigravity、Cursor、Kiro、Trae、Windsurf は監視対象ではありません。それぞれがデスクトップアプリ、またはスクリプトでインストールするコマンドラインツールであり、そのピンは、スクリプトが認証情報なしで問い合わせられるリリースチャネルを挙げていません。ファイルにはそれぞれの理由が記載されています。

新しいリリースまたはリダイレクト先に対してピンを再確認した後は、そのチャネルの `reviewed`、`reviewed_on`、`reviewed_from` フィールドを更新してください。バージョンチャネルのトリガーは、それを削除または変更するまで毎週チェックを失敗させます。インストーラーのアドレスのトリガーは、`reviewed` が新しいリダイレクト先を記録すると止まるため、その先を記録するのはトリガーのアクションが完了した後にしてください。
