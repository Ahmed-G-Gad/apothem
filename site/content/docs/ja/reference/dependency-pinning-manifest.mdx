> Apothem が依存関係をどのように宣言・ピン留め・ロックするかについての承認済みの姿勢。
> 対象読者：再現性モデルを理解する必要があるコントリビューターおよび下流の利用者。

## 姿勢

Apothem は、小さなランタイム依存関係のセットに加えて、より大規模な開発・監査・
リリース・ドキュメントのツールチェーンを備えた Python CLI です。ランタイム依存関係は
`pyproject.toml` で保守的な下限を使用します。ウェブサイトは
`site/package-lock.json` をコミットします。GitHub Actions はバージョンコメント付きで
不変の SHA によってピン留めされ、Dependabot によって更新されます。

| クラス | 宣言 | ロックポリシー |
|---|---|---|
| ランタイム Python 依存関係 | `pyproject.toml` 内の `[project.dependencies]` | ユーザー向けには下限の範囲。パッケージに同梱される Python ランタイムロックはなし。CI はそれらのハッシュロックされたクロージャをインストール（CI 依存関係ロックを参照） |
| 開発 / セキュリティツール | `[project.optional-dependencies]` の extras | 下限の範囲。ただし `ruff` と `mypy` は、`dev` extra が CI の実行バージョンに厳密にピン留めする（ruff については CI ツールロックを参照）。CI は dev extra をハッシュロックされたクロージャからインストール（CI 依存関係ロックを参照） |
| リリースツール | リリースワークフロー向けは `scripts/release/requirements-build-linux.txt`。ローカルビルド向けは `[project.optional-dependencies]` の `release` extra | リリースワークフロー向けにハッシュロック。リリースツールのクロージャから生成。`release` extra は下限の範囲 |
| CI pip | `scripts/ci/requirements-ci-pip.txt` | ハッシュロック済み。wheel と sdist のハッシュを持つ `pip==X.Y.Z` のピンが 1 つで、pip をアップグレードするすべてのワークフローが `--require-hashes -r` でインストールする。Dependabot がアップグレードを提案してハッシュを書き換える。`scripts/dev/check_pip_pin_drift.py` が、ピンを pip 26.2 以降に保つ |
| CI 依存関係ロック | `scripts/ci/requirements-ci-dev.txt`、`-runtime.txt`、`-test.txt`、および `-prereqs.txt` | `pyproject.toml`（`-prereqs.txt` の場合はエンジンのホスト前提条件）から、ロック日を基準に 7 日間のクールダウンを差し引いて `uv pip compile` でコンパイルした、ハッシュロックされたユニバーサルなクロージャ。ロック日とクールダウンは各ファイルに記録される。クロージャは `--require-hashes -r` でインストールされる（パッケージ自体は `--no-deps -e .`）。`scripts/dev/refresh_ci_locks.py` が再生成するまで、CI はロックされたバージョンをテストする。`pip-audit.yml` は、許可される最新バージョンを毎週監査し、ロックも監査する。`tests/scripts/test_ci_locks_fresh.py` は、ロックが入力を満たさなくなると失敗する |
| CI ツールロック | `scripts/ci/requirements-ci-ruff.txt`、`-bandit.txt`、`-pip-audit.txt`、`-pip-licenses.txt`、および `-pre-commit.txt` | ワークフローが実行するツールごとに、ハッシュロックされたクロージャが 1 つ。同じスクリプトが `scripts/dev/ci_lock_table.py` の厳密な仕様から、同じロック日とクールダウンでコンパイルしたもので、`--require-hashes -r` でインストールされる。ツールのバージョンを記述するワークフローはない。`pre-commit` は Python 3.11 以降を必要とするため、そのロックもそうである。また `pip-audit` のロックも、3.10 をサポートする最新の `filelock` に未修正のアドバイザリがあるため、3.11 向けにコンパイルされる。pip をピン留めするロックは CI pip のみである |
| ドキュメントサイト | `site/package.json` | `site/package-lock.json` をコミットし、`npm ci` が消費 |
| VS Code パッケージャー | `tools/vsce/package.json` | `tools/vsce/package-lock.json` をコミット。リリースおよび公開ジョブは `npm ci --ignore-scripts` を実行 |
| channel-smoke のハーネス CLI | `tools/channel-smoke/package.json` | `tools/channel-smoke/package-lock.json` をコミットし、`npm ci` が消費 |
| GitHub Actions | バージョンコメント付きの SHA ピン `uses:` 参照 | Dependabot が毎週更新を提案。例外には `action-pinning-exempt:` マーカーが付く |

## リリース承認

| 面 | 承認済みの状態 | 根拠 |
|---|---|---|
| ランタイム依存関係 | 現在の下限は `pyproject.toml` の `[project.dependencies]` にある | リリース前に承認された現在の安定下限。既知のランタイム CVE による阻害要因はなし |
| 開発ツール | 現在の下限は `pyproject.toml` の `dev` extra にあり、`ruff` と `mypy` はそこでの厳密なピンである | リリース前に承認された最新の安定下限。ruff と mypy は、フック、CI、コントリビューターのためにそれぞれ 1 つのバージョンにピン留めされ、mypy フックは、それが列挙するライブラリの dev ロックでのバージョンをピン留めし、これらが食い違うと `tests/scripts/test_ci_tool_locks.py` が失敗する |
| セキュリティツール | 現在の下限は `pyproject.toml` の `security` extra にある | リリース前に承認された現在のスキャナー下限 |
| リリースツール | ハッシュロックされたクロージャは `scripts/release/requirements-build-linux.txt` にある | リリースワークフローは `--require-hashes` を付けてインストールする。ローカルのスクリプトは、変動する依存関係を黙ってインストールする代わりに、`build` がすでに存在することを要求する |
| CI pip | ハッシュロックされたピンは `scripts/ci/requirements-ci-pip.txt` にある | pip 26.2 以降は CVE-2026-13346 を解消する。ワークフローは `--require-hashes` を付けてインストールするため、ダウンロードは公開されているハッシュと照合される |
| CI 依存関係ロック | ハッシュロックされたクロージャは `scripts/ci/requirements-ci-{dev,runtime,test,prereqs}.txt` にある | ワークフローは `--require-hashes` を付けてインストールする。各ファイルはロック日、クールダウン、カットオフを記録し、鮮度テストが `pyproject.toml` との整合を保つ |
| CI ツールロック | ハッシュロックされたクロージャは `scripts/ci/requirements-ci-{ruff,bandit,pip-audit,pip-licenses,pre-commit}.txt` にある | ワークフローは `--require-hashes` を付けてインストールし、ツールのバージョンを持たない。仕様は `scripts/dev/ci_lock_table.py` にあり、ロック日、クールダウン、カットオフは依存関係ロックと一致する |
| ドキュメントツール | 現在の範囲は `site/package.json` にあり、厳密な解決は `site/package-lock.json` にある | ロックファイルの更新後、`npm outdated` は古くなったドキュメント依存関係を返さない |
| GitHub Actions | 現在のリリースでは既存の SHA ピンを保持する。SLSA の再利用可能ワークフローは、文書化されたタグピンの例外のままであり、`release.yml` 内で `action-pinning-exempt:` コメントによって示される | 公開 CI の再実行はグリーンである。リリース面の変動を避けるため、アクションのメジャーバージョンの広範なアップグレードは、意図的に依存関係自動化の PR に委ねられている |
| npm パッケージング | `publish-npm.yml` ワークフローは `v*.*.*` のタグのプッシュで実行され、`workflow_dispatch` がフォールバックとなる | 唯一の公開 npm パッケージは `@ahmed-g-gad/apothem`。公開は、`scripts/release/check-release-ready.sh` が通過した後に与えられる、オペレーターによる `release` 環境の承認を待つ |

## ロック

コントリビューター自身の Python ロックファイルはオンデマンドで生成され、
コミットされません。Apothem のランタイムクロージャが小さいこと、CLI が複数の Python
マイナーバージョンをサポートしていることが理由です。CI は例外です。
CI は `scripts/ci/` にあるハッシュロックされたファイルをインストールします。
4 つの依存関係ロック（`requirements-ci-dev.txt`、`-runtime.txt`、`-test.txt`、
および `-prereqs.txt`）と、ワークフローが実行するツールごとに 1 つのロック
（`-ruff.txt`、`-bandit.txt`、`-pip-audit.txt`、`-pip-licenses.txt`、および
`-pre-commit.txt`）です。`python scripts/dev/refresh_ci_locks.py` は、9 つすべてを
ロック日を基準にコンパイルし、そこから Dependabot のクールダウンと一致する 7 日間の
クールダウンを差し引きます。そのため CI は、ロック日の時点で公開から
1 週間以上経過していたリリースをテストし、ファイルを更新するとそれらが先に進みます。
各ファイルにはロック日、クールダウン、その結果のカットオフが記録され、`--check` は
カットオフを再現します。クールダウンより新しい緊急のセキュリティ修正には、
`--cooldown-days 0` を付けた更新の実行か、`scripts/dev/ci_lock_table.py` にある
そのパッケージのクールダウン例外が必要です。この例外は、そのパッケージだけ
クールダウンを解除します。毎週の `pip-audit.yml` の実行は、`pyproject.toml` が
許可する最新バージョンと 9 つのロックを監査し、OSV サービスにアドバイザリを
問い合わせます。コントリビューターは引き続き `pip install -e ".[dev]"` で
インストールします。

```sh
# Astral uv:
uv pip install -e ".[dev,security,release]"
uv pip freeze > requirements.dev.lock

# pip-tools:
pip-compile --extra=dev --extra=security --extra=release -o requirements.dev.lock pyproject.toml

# Plain pip:
pip install -e ".[dev,security,release]"
pip freeze > requirements.dev.lock
```

ウェブサイトは異なります。`site/package-lock.json` がコミットされ、CI は `npm ci`
を使用するため、レンダリングされるドキュメントサイトには再現可能な Node
クロージャがあります。

## 根拠

- **なぜ Python に範囲ピンか？** CLI は幅広い Python マトリクスをサポートしているため、
  `pyproject.toml` は保守的な下限を保ちます。CI はそれらの範囲のハッシュロックされた
  クロージャをインストールし、メンテナーが `scripts/dev/refresh_ci_locks.py` で
  それらを更新します（想定される頻度は毎週）。毎週の `pip-audit.yml` の実行は、
  許可される最新バージョンを解決して、現在のツールの問題を明らかにします。
- **なぜコミットされる Node ロックか？** ウェブサイトはデプロイされる静的成果物です。
  ロックファイルは、その公開面に対して決定的な `npm ci` ビルドをもたらします。
- **なぜ SHA ピンの Actions か？** タグは可変ですが、SHA は不変です。Dependabot は
  SHA の更新を提案して各バージョンコメントを書き換え、リリースゲートは意図的な保留を
  すべて記録します。
- **更新ボットが触れないもの。** Dependabot のバージョン更新
  （`.github/dependabot.yml`）は、GitHub Actions のピン、ウェブサイトの
  ロックファイル、vsce パッケージャーのロックファイル（`tools/vsce`）、channel smoke が
  インストールするハーネス CLI のロックファイル（`tools/channel-smoke`）、CI が
  インストールするハッシュロックされた pip（`scripts/ci/requirements-ci-pip.txt`）、
  および pre-commit フックを対象とします。`scripts/ci` のその他の 9 つのファイルは、
  `scripts/dev/refresh_ci_locks.py` で丸ごと再生成されるクロージャで、どれも pip を
  ピン留めしておらず、そのフォルダーに対する Dependabot のバージョン更新は pip に
  限られます。`pyproject.toml` のランタイム下限、ハッシュロックされた
  リリース要件、`src/apothem/_vendor/vendor.txt` のベンダリングされたクロージャ、
  そして `pyproject.toml` と歩調を合わせてピン留めされた pre-commit フックは手作業で
  更新します。単一のピンだけを上げると、それらが整合しているファイルが壊れるためです。
  ruff と mypy のフックはその 2 つです。`tests/scripts/test_ci_tool_locks.py` は、
  `pyproject.toml` の厳密な ruff ピン、フックの rev、ruff のロック、dev のロックが
  同じ 1 つのバージョンになるまで、また厳密な mypy ピン、mypy フックの rev、そのフックが
  列挙するライブラリが dev のロックと一致するまで失敗するため、どちらかのツールに
  対する Dependabot のセキュリティプルリクエストは手作業で調整します。
  ウェブサイトの `@types/node` のメジャーバージョンは Node の下限（`engines` と
  `.nvmrc`、Node 22）に従うため、Dependabot はそのマイナーおよびパッチ更新のみを
  提案します。そのメジャーバージョンは下限と一緒に引き上げてください。
  バージョン更新は npm の `overrides` ブロックには手を付けません。Dependabot の
  セキュリティ更新は引き続きすべてのマニフェストを対象とするため、セキュリティの
  プルリクエストがこれらのピンのいずれかを提案したり、override を動かしたりすることが
  あります。その場合は手作業で調整するか、クローズしてください。
- **Dependabot のプルリクエストのマージ。** リポジトリのスカッシュの既定では PR の
  タイトルが使われます。Dependabot のタイトルの一部、主にディレクトリ名を含む
  グループ化されたものは、72 文字のスカッシュ件名を超えます。PR Title チェックが
  それらを指摘し、タイトルの変更で修正できます。ツールのロックファイルを変更する
  プルリクエストでは `ci.yml` のジョブが一切実行されないため、npm audit ワークフローが
  それを監査してインストールし、vsce のロックファイルについては VS Code 拡張機能を
  パッケージ化して vsce のリリーステストを実行し、channel-smoke のロックファイルに
  ついては channel smoke ワークフローが実行されます。Markdown Lint ワークフローは、
  pre-commit フックのプルリクエストに対して markdownlint フックを実行します。
  その他のフックは CI で実行されないため、マージする前にそのブランチで
  `pre-commit run --all-files` を実行してください。
