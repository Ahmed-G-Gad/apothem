> **下流のコントリビューター向けの、正規かつ規範的なリファレンス。** このドキュメントは、プロジェクト仕様の著作者とファイルヘッダーのセクション（仕様 §0.5 + §4.6）を反映したものであり、公開リポジトリに同梱される単独のリファレンスです。アーキテクチャ上の根拠は [ADR-0002](/docs/reference/authorship-header) に記録されています。

---

## 1. 正規のヘッダー行

エコシステム内の適用対象となるすべてのファイルは、そのファイルタイプ族のコメント構文で書かれた、単一の正規の SPDX ライセンス識別子行から始まらなければなりません。この行はファイルの機械可読なライセンスマーカーです。免除されないファイルでは、その存在に交渉の余地はなく、その内容はファイルごとに即興で決めるのではなく、単一の信頼できる情報源によって定められます。著作権に関する完全な法的文書は、リポジトリルートの [`LICENSE`](https://github.com/ahmed-g-gad/apothem/blob/main/LICENSE) ファイルに 1 か所だけ存在し、各ソースファイルには複製されません。

### 1.1 情報内容（不変）

正規の内容は、ちょうど 1 行です:

1. `SPDX-License-Identifier: MIT` — FSFE が維持する [REUSE 仕様](https://reuse.software/spec/)に基づく機械可読なライセンスマーカー。SPDX ツールチェーン（`reuse lint`、`scancode`）、Linux カーネルのツール、下流のライセンススキャナーが、曖昧さなく解析します。視覚的な枠線はなく、ファイルごとの著作権、ウェブサイト、メール、GitHub の行もありません — ファイルごとの来歴は、設計上、単一の SPDX 行だけです（§4 を参照）。

### 1.2 参照形式（`#` コメント族）

正規のテキスト — ここでは `#` コメント構文の形式で記載 — の信頼できる情報源は、[`src/apothem/schemas/authorship-header.txt`](https://github.com/ahmed-g-gad/apothem/blob/main/src/apothem/schemas/authorship-header.txt) です:

```text
# SPDX-License-Identifier: MIT
```

このテキストが**唯一の**権威ある情報源です。`file-header` バリデーター（§7）は、このバイト単位で正確なフィクスチャに対して実行されます。ファイルのヘッダー行とこのフィクスチャとの間の（§2 に従った構文置換を前提とした）ずれは、どれも CI の失敗です。

## 2. ファイルタイプごとのバリアント（バイト単位で正確）

行の*情報内容*は不変であり、ファイルタイプごとに変わるのは*コメント構文*だけです。ファイルタイプごとのバリアントの完全な表は次のとおりです:

| ファイルタイプ族 | コメント構文 | バリアントのレンダリング |
|---|---|---|
| `#` 族 — `.sh`、`.bash`、`.zsh`、`.py`、`.rb`、`.pl`、`.ps1`、`.yml`、`.yaml`、`.toml`、`.cff`、`.gitignore`、`.gitattributes`、`.editorconfig`、`.shellcheckrc`、`.env.example`、`Makefile`、`Dockerfile`、`Procfile`、`CODEOWNERS`、`PKGBUILD`、`scripts/apothem` のような拡張子なしのシェルエントリーポイント | `#` 行コメント | `# SPDX-License-Identifier: MIT` |
| `//` 族 — `.js`、`.jsx`、`.mjs`、`.cjs`、`.ts`、`.tsx`、`.go`、`.rs`、`.java`、`.kt`、`.swift`、`.c`、`.cc`、`.cpp`、`.h`、`.hpp`、`.cs`、`.scala`、`.dart`、`.jsonc` | `//` 行コメント | `// SPDX-License-Identifier: MIT` |
| ブロックコメント族 — `.html`、`.htm`、`.md`、`.markdown`、`.xml`、`.vue`（テンプレート領域）、`.php`（テンプレート領域） | `<!-- ... -->` | `<!-- SPDX-License-Identifier: MIT -->` |
| MDX（`.mdx`） | `{/* ... */}`（JSX 式コメント） | `{/* SPDX-License-Identifier: MIT */}` |
| C ブロック族 — `.css`、`.scss`、`.less`、`.sql`（`/* */`） | `/* ... */` | `/* SPDX-License-Identifier: MIT */` |
| `;` 族 — `.ini`、`.cfg`、一部の `.lisp`/`.scm` | `;` 行コメント | `; SPDX-License-Identifier: MIT` |
| `--` 族 — `.sql`、`.lua`、`.hs`、`.elm`、`.ada` | `--` 行コメント | `-- SPDX-License-Identifier: MIT` |
| ロックファイル / 生成ファイル / JSON | なし / 該当なし | **免除。** §3 の例外リストを参照。 |

**Markdown バリアント（正規のレンダリング）:**

```markdown
<!-- SPDX-License-Identifier: MIT -->
```

HTML コメント（または MDX の `{/* */}`）のラッパーは目に見えない形でレンダリングされるため、レンダリング後の表面はすっきりしたまま保たれ、ソース内のライセンスマーカーは、どのファイルタイプでも機械可読のままです。

## 3. 例外リスト（クラス単位で免除）

次のクラスは、SPDX ヘッダー行が**免除**されます。`file-header` バリデーターの適用可否チェックは、これらに対して `not-applicable` を返します:

- **`LICENSE`** — それ自体が法的文書であり、`license-author-consistency` バリデーターがその存在を確認する、権威ある著作権行を含みます。
- **`*.svg` アセット** — XML コメントは行コメントのマーカーとしては壊れやすいため、SVG の来歴はアセットの README と、生成されたラスター出力によって担われます。
- **`CHANGELOG.md`** — フォーマットに縛られたリリースノート文書です。SPDX 行は、フォーマットの中に織り込まれるのではなく、CHANGELOG の見出しの上に、単一の HTML コメントとして置かれます。
- **JSON ファイル（`.json`）** — JSON にはコメント構文がありません。JSON 設定に帰属表示が必要な場合は、兄弟ファイルの `<file>.NOTICE.md` を置きます。
- **ロックファイル** — `package-lock.json`、`yarn.lock`、`pnpm-lock.yaml`、`Cargo.lock`、`Pipfile.lock`、`poetry.lock`、`go.sum` など（機械が管理するもの）。
- **生成ファイル** — `# Generated by ...` または `// Generated by ...` のマーカーを持つもの、および `.gitattributes` の `linguist-generated=true` に一致するもの。
- **ベンダリングされたサードパーティのコンテンツ** — `vendor/`、`third_party/`、`node_modules/` 配下のファイル。これらは上流自身のライセンスと通知を保持しています。上流の帰属表示の上に本プロジェクトのマーカーを注入することは、ライセンス違反です。
- **`.audit/` ファイル** — git で無視される一時的なものであり、公開ツリーの対象外です。
- **プランファイル（`<project-root>/.apothem/plans/**`、およびレガシーの `<project-root>/.plans/**`）** — git で無視される一時的なものです。来歴はプランのフロントマターです（[`plans-discipline.md`](/docs/reference/plans-discipline) §3 を参照）。
- **空のマーカー** — `.keep`、`.gitkeep` など（意味的にはゼロバイト）。
- あらゆる種類の**バイナリファイル**。

例外リスト自体は、[`src/apothem/schemas/header-exceptions.txt`](https://github.com/ahmed-g-gad/apothem/blob/main/src/apothem/schemas/header-exceptions.txt) に正規表現 / glob のリストとして記述されており、バリデーターの適用可否チェックへの入力となります。変更には、構造化照会と新しい ADR が必要です。

## 4. ライセンスとの関係

SPDX 行はプロジェクトのライセンスを機械可読な形で宣言し、LICENSE ファイルはそれを権威ある形で宣言します:

- **`SPDX-License-Identifier: MIT`** — [REUSE 仕様](https://reuse.software/spec/)と SPDX 標準に基づく機械可読なライセンスマーカー。自動のライセンススキャナーはこの行を直接解析します。SPDX 式の構文は、`reuse lint`、scancode-toolkit、FOSSology、Linux カーネルのライセンスツールと相互に互換性があります。

{/* REUSE-IgnoreEnd */}
- **リポジトリルートの [`LICENSE`](https://github.com/ahmed-g-gad/apothem/blob/main/LICENSE)** — 完全な MIT の条項と著作権者を記載した、権威ある法的文書。著作権表示の唯一の置き場所です。ファイルごとのヘッダーは、すべてのファイルで著作権を繰り返し記載するのではなく、共有の SPDX 識別子を通じて暗黙のうちにこれを参照します。

**単一行の形式。** ファイルごとの来歴は単一の SPDX 行であり、著作権に関する法的文書はルートの LICENSE に 1 か所だけ存在します。枠線付きの複数行バナーボックス（罫線の枠で囲んだ、著作権、ウェブサイト、メール、連絡先の行）は、バリデーターによって拒否されます。これらは、連絡先と著作権のメタデータをすべてのファイルに重複して持たせるだけで、機械可読なライセンスマーカーがすでに REUSE/SPDX/SBOM のツールに提供している以上のものを何も加えないからです。`src/apothem/schemas/authorship-header.txt` にあるバイト単位で正確なフィクスチャが単一行の形式を保持しており、バリデーターはこのフィクスチャに対して実行されます。

**相互参照。** LICENSE ファイル（MIT）— 食い違いがある場合は、法的文書が優先されます。ADR-0006 は、バナーの範囲を縮小する決定を正式に承認した際の根拠を記録しています。

## 5. 挿入位置

- SPDX 行はファイルの**最初のコンテンツ**であり、例外はただ 1 つだけです。shebang 行（`#!/usr/bin/env bash`、`#!/usr/bin/env python3` など）は常に 1 行目に残り、その場合 SPDX 行は 2 行目から始まります。
- YAML フロントマターを持つ Markdown / MDX ファイルでは、ツールが解析できるようにフロントマターはバイト 0 に置かれたままとし、SPDX コメントは閉じる `---` の後に続き、その後に H1 と本文が来ます。`scripts/inject-header.py` は、コメントをこの位置に置きます。
- 1 行の空行が、SPDX 行と次のコンテンツ（H1、本文など）を区切ります。

---

## 6. ヘッダー可視性ポリシー

とくに Markdown ファイルでは、SPDX 行は**デフォルトで不可視**です — `<!-- ... -->`（MDX では `{/* */}`）で包まれ、ソース上でのみ見えます。これは、README、CONTRIBUTING、CLAUDE.md、サポート対象ハーネスの指示ファイル、スキルの SKILL.md、コマンド本文、出力スタイル、ドキュメントページに対する正しいポリシーです。**可視**のレンダリング（出力の先頭に、SPDX 行をプレーンテキストまたはフェンス付きブロックとして置く形）は、来歴をすぐに読めることが役立つ単独のリファレンスドキュメントに対して認められます。このポリシーは `src/apothem/schemas/header-visibility.yaml` でファイルクラスごとに設定され（デフォルトは*不可視*）、ファイル単位のオーバーライドマーカー `<!-- header-visibility: visible -->` を、SPDX 行の直後に置くことが認められます。

## 7. インジェクター — `scripts/inject-header.{sh,py}`

次のことを行う、決定論的な CLI です:

- 1 つ以上のファイルパス（または glob）を受け取ります。
- 例外リスト（§3）によって適用可否を判定します。
- 既存のヘッダーの状態（正規 / 不正な形式 / 不在）を検出し、見つかった正規でないバナーブロックを取り除いて、再実行が冪等になるようにします。
- ファイルタイプごとに正しい SPDX バリアントをレンダリングします（§2）。
- shebang とフロントマターを尊重しつつ、正しい位置（§5）に挿入します。
- 3 つのモードで動作します: `fix-in-place`（書き込む）、`emit-patch`（unified diff を出力する）、`check`（ずれがあれば非ゼロで終了する — CI が使用）。
- 冪等: 2 回実行しても何も変更しません。

インジェクターは `make headers-fix` ターゲットから呼び出され、このターゲットは `scripts/inject-header.py --mode fix-in-place` を実行します。

## 8. バリデーター — `file-header`（CI）

[`src/apothem/conformity/file_header_grep.py`](https://github.com/ahmed-g-gad/apothem/blob/main/src/apothem/conformity/file_header_grep.py) にあります。バリデーターは、作業ツリー内のすべてのファイルについて、（§3 に従って）適用可否を調べ、適用対象であれば、正規の SPDX 行がファイルの先頭に存在することを検証します — 他のすべてのコンテンツより前であり、この行より前に置くことが認められるのは shebang だけです（§5）。

[`src/apothem/schemas/authorship-header.txt`](https://github.com/ahmed-g-gad/apothem/blob/main/src/apothem/schemas/authorship-header.txt) にあるバイト単位で正確なフィクスチャに裏付けられています。CI のサマリーに、ファイルごとの差分と全体のカバレッジ % を報告します。ずれがあれば、ビルドを失敗させます。

## 9. 自己強制の仕組み

この規律は、今後のあらゆるセッションと、今後のあらゆるコントリビューターを超えて存続しなければなりません。必須の強制面は次のとおりです:

1. **`src/apothem/schemas/authorship-header.txt`** — バイト単位で正確な正規のフィクスチャ。信頼できる情報源は 1 つだけです。
2. **`scripts/inject-header.{sh,py}`** — 機械的なインジェクター（§7）。
3. **`file-header` CI バリデーター**（§8）— ずれがあれば、ビルドを失敗させます。
4. **pre-commit フック** — ステージされたファイルに対して `--fix` を付けてバリデーターを実行し、インジェクターに接続されています。
5. **`CLAUDE.md` の必須動作ブロック** — 適用対象のファイルを作成するときは常に、正規の SPDX 行を注入するようアシスタントに指示します。
6. 正規の `.github/` パスにある**サポート対象ハーネスの指示ファイル** — ファイルの生成時に同じことを行うようハーネスに指示します。
7. `src/apothem/hooks/messages/pretooluse-{write,edit}-header-guard.md` にある **PreToolUse フック** — 適用対象のパスへの Write/Edit ツール呼び出しを横取りし、SPDX 行が、後で CI の失敗として見つかるのではなく、ファイルの作成時に注入されるようにします。
8. **プルリクエストテンプレートのチェックボックス** — すべての新しいファイルが正規の SPDX 行を持つという、コントリビューター向けの表明。
9. **このドキュメント**（`site/content/docs/reference/authorship-header.mdx`）— 正規かつ規範的な解説。
