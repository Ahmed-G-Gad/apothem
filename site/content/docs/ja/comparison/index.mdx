Apothem は、ホストに依存しない AI ハーネス構成マネージャーです。
`~/.config/apothem/profile.yaml` にある 1 つの共有プロファイルが、17 のハーネスネイティブな設定面へマテリアライズされます。
このセクションでは、すでに使っている代替手段に対して Apothem をどう評価するかの枠組みを示します。

## Apothem との比較

このページにある他プロジェクトに関する事実は **2026-10-02** 時点のもので、各プロジェクト自身の README またはドキュメントから読み取ったものです（[出典](#出典)を参照）。マイナーリリースのたびに再確認してください。

他のツールは、この問題の隣接する一部分を解決します。**chezmoi** や **GNU Stow** のようなファイルベースの設定マネージャーは、ファイルを配置、リンク、またはテンプレート化しますが、1 つのソースを各ハーネスの*ネイティブ*な設定スキーマへ変換することは決してありません。ツール横断の同期 CLI は、1 つのソースからツールごとのファイルを生成します。**rulesync** は 60 のコーディングツールと 2 つのオープン標準向けにネイティブ設定を生成します。その同期単位には MCP、無視ファイル、権限、レビューチェックが加わりますが、そのいずれも Apothem のマニフェストは同期しません。**ruler** は 1 つの `.ruler/` ディレクトリを 33 のターゲットへ配布し、ルールを各ツールの命令ファイルに連結し、MCP サーバー、スキル、サブエージェントをネイティブ設定へ変換します。Apothem の違いは、**同期の周囲に同梱されるガバナンスとライフサイクルの規律**にあります。機械化されたコンフォーミティゲート、決定的なパイプライン、監査フォートレス、そして可逆で検証済みのライフサイクルです。

| 機能 | Apothem | ファイル設定マネージャー（chezmoi、Stow） | rulesync | ruler |
| ---------- | :-----: | :----------------------------------: | :------: | :---: |
| 1 つのソースから多数のツールのネイティブスキーマへ | はい — 17 のハーネスアダプター | いいえ — コピー、シンボリックリンク、またはテンプレート。変換なし | はい — 60 のツールに加え、AGENTS.md と Agent Skills の標準 | 部分的 — ルールは各ツールの命令ファイルに連結され、MCP、スキル、サブエージェントはネイティブ形式で書き込まれる |
| 同期単位 | ルール、スキル、サブエージェント、スラッシュコマンド、フック、出力スタイル、ステータスライン、テンプレート、コンフォーミティバリデーター、スキーマ、ハーネスごとの命令テンプレート、Claude Code の設定テンプレート | 任意のファイル | ルール、無視設定、MCP、コマンド、サブエージェント、スキル、フック、権限、チェック（コードレビューのチェック指示） | ルール、MCP、スキル、サブエージェント |
| ガバナンスコーパス（振る舞いルールと機械的なコンフォーミティゲート） | はい — `python -m apothem.conformity.gate` | いいえ | いいえ — `checks` 機能はコードレビューのチェックをツールへ同期するが、ルールに対するコンフォーミティゲートはない | いいえ |
| 決定的な計画パイプラインと調査パイプライン | はい — `/plan-spec` から `/plan-execute` まで、13 ステージの `/research` | いいえ | いいえ | いいえ |
| 検出して是正する監査フォートレス | はい — 11 コマンドのスイープ、`/fortress` の再監査ループ | いいえ | いいえ | いいえ |
| セッションをまたぐ永続メモリ | はい — Apothem のデータホーム配下の `memory/records.json` ストア。インストール時に作成される | 比較対象外 | README に記載なし | README に記載なし |
| サプライチェーンを堅牢化したリリース | はい — SBOM、Sigstore、SLSA、Scorecard の目標 | 比較対象外 | README に記載なし | README に記載なし |
| 可逆で検証済みのライフサイクル | はい — バックアップ、`apothem verify --json`、孤立ファイルを残さないアンインストール | chezmoi: `chezmoi verify` がすべてのターゲットをチェックする。Stow: シンボリックリンクのみ | README に記載なし | `.bak` バックアップと `ruler revert`。README に verify コマンドの記載なし |

他のツールの方が優れている箇所は、名指しします：**rulesync** は 3 倍以上の数のツールに対応し、Apothem のマニフェストが同期しない MCP、無視ファイル、権限、レビューチェックを同期します。**ruler** は 2 倍近くの数のツールに対応し、独自の revert コマンドを備えています。Apothem は素のツール数を、同期の周囲に同梱されるガバナンス、監査、ライフサイクルの規律（コンフォーミティゲート、決定的な計画パイプラインと調査パイプライン、11 コマンドの監査フォートレス、永続メモリ、そして可逆で検証済みのライフサイクル）と引き換えにしています。これらは、どちらの同期ツールも備えていないものです。

## 比較の方法

次の 3 つの軸に沿って比較します。

1. **信頼できる情報源。** ルール、エージェント、コマンド、設定はどこにあるか。
   Apothem は 1 つの共有コーパスを保持し、そこから各ハーネスのネイティブ形式をレンダリングします。
   手作業で保守する設定は、ツールごとに 1 つのコピーを保持します。
2. **ドリフトのコスト。** ルールを変更すると何が起こるか。
   Apothem は `apothem update` で、変更をインストール済みのすべてのハーネスへ伝播します。
   手作業で保守する設定では、各ツールのネイティブファイルを個別に編集し、記憶を頼りにそれらの整合を保つ必要があります。
3. **検証。** 各ハーネスが正しく設定されていることをどう確認するか。
   Apothem には `apothem verify --harness <name>` と `apothem doctor` が同梱されています。
   手作業で保守する設定には、組み込みの検証がありません。

## 機能マトリクス

このマトリクスは、オペレーターが最初に頼る 2 つの代替手段、つまり各ハーネスのネイティブ設定を手作業で保守する方法と、それらのファイルを汎用の dotfile マネージャーで管理する方法に対して、Apothem を対比します。

| 機能 | 手作業で保守する設定 | dotfile マネージャー | Apothem |
| ---------- | ---------------------- | --------------- | ------- |
| 単一の共有された信頼できる情報源 | いいえ（ツールごとに 1 コピー） | いいえ（プロファイルではなくファイルを追跡） | はい（1 つのプロファイル） |
| ハーネスネイティブな形式をレンダリング | 手動 | いいえ | はい（アダプターごとのマテリアライザー） |
| ハーネス間のドリフト防止 | 手動での整合 | ファイル同期のみ | はい（`apothem update`） |
| ハーネスごとのインストール／アンインストール | 手動 | 部分的（シンボリックリンク／コピー） | はい（`install` / `uninstall`） |
| 組み込みの検証 | なし | なし | はい（`verify` / `doctor`） |
| ツールごとの形式変換 | なし | なし | はい（`.mdc`、`.toml`、埋め込みの `.md`） |
| 1 つの入力から 17 のハーネス | いいえ | いいえ | はい |
