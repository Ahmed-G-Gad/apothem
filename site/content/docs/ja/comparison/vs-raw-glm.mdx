GLM (Z.ai) は、互換性のあるハーネスがベース URL とキーを設定することで向けられる、モデルバックエンドです。
それらの環境変数は、プロジェクトごと、マシンごとに、永遠に手作業でエクスポートできます。
Apothem の glm アダプターは、バックエンドのエンドポイントとオペレーターが設定可能なプレースホルダーを 1 つのプロバイダーファイルに記録し、同じテンプレートをすべてのプロジェクトに書き込みます。
このページでは、そのバックエンドを手作業で配線する方法と、Apothem で管理する方法を対比します。

## 作業量の比較

| 作業 | 素の手作業設定 | Apothem 管理 |
| ---- | --------------- | --------------- |
| バックエンド URL を記録する | 覚えておき、プロジェクトごとに再エクスポートする | 1 つのプロバイダーファイルに書き込まれる |
| 信頼できる情報源 | 各シェル自身のエクスポート | 1 つの正規のプロバイダーファイル |
| プロジェクト間でバックエンドの整合を保つ | プロジェクトごとに配線し直す | 同じテンプレートが各プロジェクトに書き込まれる |
| 設定を復元する | すべてのプロジェクトで再エクスポートする | `apothem update --harness glm --project <path>` は、ファイルが存在しない場合にのみ、そのファイルを再び書き込む |
| 設定を削除する | 手動で削除 | バックアップ付きの `apothem uninstall` |

## Apothem が管理するもの

glm アダプターは、`<project>/.apothem/providers/glm.toml` に単一のプロバイダーファイルをレンダリングし、それ以外は何も書き込みません。
このファイルには、Anthropic 互換のベース URL（`https://api.z.ai/api/anthropic`）、OpenAI 互換のベース URL（`https://api.z.ai/api/coding/paas/v4`）、認証トークンのプレースホルダー、そしてモデル対応付けのプレースホルダーが記録されます。
あなたの Z.ai キーとモデル ID の選択は、オペレーターの所有のままです。Apothem が本物のシークレットを書き込むことは決してなく、バージョンによって変わりやすいモデル ID をピン留めすることもありません。

## 移行パス

1. まだ共有プロファイルを作成していない場合は、`apothem profile init` を実行して作成します。
2. `apothem install --harness glm --project <path>` を実行して、`glm.toml` プロバイダーファイルをレンダリングします。
3. 最新の [Z.ai ドキュメント](https://docs.z.ai/devpack/tool/claude)を参照して、あなたの Z.ai キーと、使いたいモデル ID を記入します。
4. `apothem verify --harness glm --project <path>` を実行して、設定が配置されたことを確認します。
5. 以降の変更はすべて `.apothem/providers/glm.toml` を編集して行います。Apothem が既存のプロバイダーファイルを書き換えることは決してありません。`apothem update --harness glm --project <path>` がそのファイルを再び書き込むのは、ファイルが存在しない場合のみです。
