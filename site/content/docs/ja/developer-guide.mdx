このガイドは、開発者が SOTA の品質基準で Apothem エコシステムを保守・拡張するのを支援します。

## クイックリファレンス: アーティファクトの種類

このガイドは 5 種類のアーティファクトを扱い、それぞれに固有の目的があります。
ルール、コマンド、ヘルパー、スキルは YAML フロントマターを持ちます。フックは `hooks.json` と `settings.json` に登録され、フロントマターを持ちません。
出力スタイルは、`name` と `description` の 2 つの必須フロントマターキーを持つ、さらに別のアーティファクトクラスです。[フロントマタースキーマ](/docs/reference/frontmatter-schema)を参照してください。

| アーティファクト | パス | 目的 | 作成する時機 |
| -------- | ---- | ------- | -------------- |
| **ルール** | `src/apothem/rules/*.md` | 振る舞いに関するマンデート、または運用上の指令 | 新しい原則、ポリシー、またはガバナンスマンデートが確立されたとき |
| **コマンド** | `src/apothem/commands/*.md` | 複雑なワークフロー向けのスラッシュコマンド（`/command-name`） | 新しい複数ステップのユーザーワークフロー |
| **ヘルパー** | `src/apothem/agents/*.md` | 並行タスク向けの永続的な委任ワーカー定義 | 新しく繰り返し発生する専門タスク（監査、探索、品質チェック） |
| **スキル** | `src/apothem/skills/{name}/SKILL.md` | 検出シグナルを伴う再利用可能な手法 | 新しい、検出可能で再利用可能な手法パターン |
| **フック** | `src/apothem/hooks/` + `hooks.json` + `settings.json` | イベントをトリガーとする検証または状態管理 | 新しいライフサイクルイベント、または検証のニーズ |

## ハーネスアダプターの契約

ハーネスのアイデンティティと能力に関する事実は `src/apothem/lib/harness_registry.py` にあります。
ハーネスの変更は、次の面がすべて一致したときにのみ完了します:

| 面 | 必要な更新 |
| --- | --- |
| レジストリの行 | 公開 ID、パッケージキー、エントリーポイント、スコープ、出力形式、ターゲットパス、ドキュメントパス、能力ファイル、標準ピン、フィクスチャテスト、package-data キー、テンプレートソース、能力ステータス。 |
| アダプターパッケージ | `__init__.py`、`install.py`、`update.py`、`uninstall.py`、`verify.py`。`materializer.py` は、ハーネスがネイティブ設定ファイルをレンダリングする場合にのみ追加します。 |
| 伝播マニフェスト | マニフェストに基づくアダプター向けの、テンプレートパスとコホートパス。 |
| 能力 | `src/apothem/harnesses/<package>/capabilities.yml`。必須のすべての能力と、サポート外または discovery-pending の状態についての根拠を記載し、さらに変換されるコマンド、エージェント、ルールの各コホートについて `conversion_losses` マップを含めます（[ハーネスレジストリ](/docs/reference/harness-registry)を参照）。 |
| 規約ピン | `STANDARD-CONVENTION-PIN.md`。ベンダー URL、スナップショット日付、正規のファイル名/スキーマ、証拠の参照、サポート外の能力についての根拠を記載します。 |
| テスト | レジストリのパリティ、アダプターのフィクスチャテスト、ゴールデンのインストールプラン行、ドライラン/書き込みなしの挙動、冪等性、package-data のカバレッジ。 |
| ドキュメント | ハーネスのリファレンスページ、比較ページ、能力/MCP に関する注記、架空のプレースホルダーを使う例。 |

プロジェクトスコープのアダプターは、`requires_project = True` を設定し、ライフサイクルメソッドで `project: Path | None` を受け取り、書き込みの前に、存在しないプロジェクトルートや安全でないプロジェクトルートを拒否しなければなりません。
ユーザースコープのアダプターは、パスを、ハーネスが文書化しているユーザー設定ルートの配下に保たなければなりません。

## ゴールデンフィクスチャのポリシー

`tests/fixtures/harness-golden-plans.json` は、レジストリにある 17 のハーネスすべてについて、公開インストールプランの形を記録します: 公開 ID、マテリアライズモード、ソースのコホート/テンプレートパス、`<ROOT>` 配下に正規化されたターゲットパスです。
レジストリ、マニフェスト、またはテンプレートのターゲット挙動を意図的に変更する場合は、差分に挙動の変化が表れるよう、ソースの変更と同じコミットでゴールデンフィクスチャを更新してください。

## 書き込み前の検証

共有のインストールドライバーは、最初の書き込みの前に、すべてのソースとターゲットを検証します。
存在しないマニフェストソース、ターゲットのトラバーサル、選択したルートの外にあるターゲットパス、シンボリックリンクの横断を拒否します。
ドライランも同じ検証を実行し、ファイルを作成せずに、構造化された `skipped` または `unchanged` の結果を返します。

## 伏せ字化とサンプルデータ

プロファイルの診断は、token、secret、password、credential、API key、private key、authorization、auth、header の形をしたフィールドを伏せ字にします。
ドキュメント、フィクスチャ、例、JSON スニペットでは、本物らしく見えるシークレットや個人アカウントの代わりに、`example.invalid`、`Example User`、`example-user`、そして明白なプレースホルダーを使用します。

## 書き始める前に: 正規スキーマ

**機械可読でゲートによって強制される契約は、`src/apothem/schemas/*.schema.json` 配下のクラスごとの JSON Schema です — `additionalProperties` が未知のキーを拒否するため、コンフォーミティゲートが最終的な判断を下します。**
人間が読むための 2 つの投影がこれらに追従しています: `site/content/docs/reference/frontmatter-schema.mdx`（必須キーの索引）と `site/content/docs/reference/artifact-schema.mdx`（クラスごとのテンプレートと実例）です。
ページが JSON Schema と食い違う場合は、スキーマが優先されます。

- `src/apothem/schemas/` 配下で、対象のアーティファクトの種類の JSON Schema を読む
- テンプレートと実例について、`site/content/docs/reference/artifact-schema.mdx` の §「Schema」を読む
- 必須フィールドをコピーし、必須の値を埋め、必要に応じて任意フィールドを追加する

## フロントマターのクイックチェック

すべてのアーティファクトのフロントマターは、次のチェックに合格しなければなりません。
`version`、`updated`、`portability` のチェックは、そのキーを持つクラスにのみ適用してください。ルールはそのいずれも持たず、スキルは `portability` を持ちません。

```yaml
✓ Valid YAML syntax (use tools: `yamllint` or PowerShell `ConvertFrom-Yaml` where available)
✓ All mandatory fields present (per schema for artifact type)
✓ name: uses kebab-case
✓ version: semantic MAJOR.MINOR.PATCH
✓ updated: ISO 8601 date (YYYY-MM-DD)
✓ description: single-line, non-empty
✓ scope fields valid per artifact type (rules: pathFilter + alwaysApply; CLAUDE.md root: scope)
✓ portability: string, for example `universal` (the schemas do not enumerate its values)
✓ No typos in field names — must match canonical schema exactly
✓ Optional fields use correct enum values
```

## 命名規約

### アーティファクト名（kebab-case）

- **ルール:** `operational-mandates`、`clean-room-generation`、`context-management`
- **コマンド:** `plan-execute`、`plan-spec`、`plan-generate`
- **ヘルパー:** `codebase-explorer`、`convention-auditor`、`quality-gate`
- **スキル:** `plan-suite`、`ecosystem-audit`

パターン: 小文字、単語の間はハイフン、スペースやアンダースコアは使わない。

### ファイルの命名

- **ルール:** `{name}.md`
- **コマンド:** `{name}.md`
- **ヘルパー:** `{name}.md`
- **スキル:** フォルダ `src/apothem/skills/{name}/SKILL.md` の中（大文字小文字は厳密に `SKILL.md`）
- **フック:** フォルダ `src/apothem/hooks/` の中。すべてのイベントハンドラーは Python です。Claude Code の `settings.json` テンプレートにあるすべてのフックコマンドは exec 形式を使い、`command` はインストール時に解決されるインタープリターのプレースホルダー `${PYTHON_BIN}`、`args` にはスクリプトのパスとその引数が入ります。このテンプレートは、`${HARNESS_ROOT}/.apothem/support/hooks/dispatch.py <event> [<message-name>]` と `${HARNESS_ROOT}/.apothem/support/conformity/gate.py --hook` を絶対パスで実行するため、インストール済みのコピーにはインポート可能な `apothem` パッケージは不要です。Claude Code プラグインは、代わりに `src/apothem/hooks/hooks.json` にフックを登録します。これらは `bash` を介して `hooks/lib/bootstrap.sh` を実行するシェルコマンドです。このスタブが Python を見つけて `dispatch.py` を実行するため、ハンドラーは Python のままです。新しいフックは、`hooks.json` と Claude Code の `settings.json` テンプレートの両方に登録します。`dispatch.py` は、`SessionStart` を `session_start_bootstrap.main()` へ、許可リストにあるそのほかのすべてのイベントを `emit_hook_context.main()` へルーティングします。`src/apothem/hooks/` または `scripts/` の下で許可されるシェルスタブは、6 つのロケーターおよびブートストラップファイル（`find-python.{ps1,sh}`、`find-pwsh.{ps1,sh}`、`bootstrap.{ps1,sh}`）だけです。それ以外の `.ps1` / `.sh` ファイルは、`scripts/dev/validate_hooks.py` の衛生チェックで不合格になります。

### 相互参照

他のアーティファクトを参照するときは、正確な名前を使用します:

- ルール: `"operational-mandates"`（name フィールドの値）
- コマンド: `/plan-execute`（人間向けのドキュメントではスラッシュ付き、コード内ではスラッシュなし）
- ヘルパー: `codebase-explorer`（name フィールドの値）
- スキル: `plan-suite`（name フィールドの値）

散文の中では、ファイルパスや省略した名前を決して使用しないでください。

## ポータビリティ: Windows と Unix

すべてのコマンドは、`portability` フィールドでポータビリティのステータスを明示的に宣言しなければなりません（MUST）。
ヘルパーは宣言してもかまいません（MAY）。
スキル、ルール、出力スタイルは `portability` フィールドを持ちません。

### ユニバーサル

- Windows、macOS、Linux で同一に動作する
- シェルに関する前提を置かない
- パスにはスラッシュ（`/`）を使う
- ハードコードされた絶対パスがない
- Windows 固有の PowerShell 構文がない

```yaml
portability: "universal"
```

### Windows の注意点付きユニバーサル

- POSIX ホスト全体でユニバーサル。コンテンツ内で宣言された Windows プラットフォームのバリアントでは、名指しされた注意点が適用される
- 注意点をコンテンツ内に明示的に文書化する
- 例: 「Win 10 より前の Windows ではシンボリックリンクはサポートされない」

```yaml
portability: "universal-with-windows-caveats"
```

注意点は、タイトルの直後の注記に文書化します。

### Unix 専用 / Windows 専用

- 明示的に 1 つのプラットフォームに限定される
- Apothem ではまれ — ほとんどはユニバーサルであるべき
- プラットフォーム固有の機能が不可欠な場合にのみ使用する

```yaml
portability: "unix-only"
```

理由は、アーティファクトの最初のセクションに文書化します。

## スコープ: 常時オンとパスフィルター

### 常時オン

ルールはあらゆる場所に適用されます。常時オンのルールは 5 つです: `agnostic-posture`、`authority-inquiry`、`session-closure`、`context-management`、そしてルールインデックス（`apothem-rule-index`）。常時オンのルールはどれもすべてのセッションでコンテキストを消費するため、この集合は小さく保たれています。

```yaml
pathFilter: ""
alwaysApply: true
```

### パスフィルター

ルールはファイルパスに基づいて、条件付きで適用されます。

```yaml
pathFilter: "**/*.py, **/*.toml"
alwaysApply: false
```

`pathFilter` は glob パターン（`.gitignore` と同じ形式）を使用します。
ファイルがフィルターに一致すると、ルールが有効になります。

## バージョンのセマンティクス

バージョンを持つ各アーティファクトは、独自のセマンティックバージョン（`MAJOR.MINOR.PATCH`）を持ちます。
コマンドとスキルはこれを必須とし、ヘルパーと出力スタイルはこれを持ってもかまわず（MAY）、ルールはこれを持ちません:

- **PATCH** — 既存の指令を、契約を壊さずに修正する挙動の変更。
- **MINOR** — 追加的で互換性を壊さない変更：新しい任意のセクション、新しい任意のフロントマターフィールド、新しい例。既存の利用者は変更なしで動作し続けます。
- **MAJOR** — 互換性を壊すスキーマまたは契約の変更：セクションの削除、フィールドの名前変更、既存の指令の挙動の変更、下流のアーティファクトに適応を求める変更。

誤字の修正、リンクの修正、整形、コメントのみ、またはドキュメントのみの編集では、バージョンは変わりません。挙動の変更のみがバージョンを上げます。そのような編集でも、アーティファクトの `updated` の日付は更新されます。

例:

- `vX.Y.Z` → `vX.Y.(Z+1)`（PATCH: 挙動を変える指令の修正）
- `vX.Y.Z` → `vX.Y.Z`（バージョン据え置き：誤字またはリンクの修正。`updated` は変更）
- `vX.Y.Z` → `vX.(Y+1).0`（MINOR: 新しい任意セクションを追加）
- `v0.Y.Z` → `v(0+1).0.0`（MAJOR: 契約を安定版と宣言。新しいアーティファクトは `v0.Y.Z` から始まる）
- `vX.Y.Z` → `v(X+1).0.0`（MAJOR: 必須のフロントマターフィールドを削除）

それらを持つアーティファクトに対する、挙動を変えるすべての編集で、`version` と `updated` をそろえて更新します。
アーティファクトの変更を含むリリースについては、エコシステムレベルの `CHANGELOG.md` に対応する行を追記します。

### プランスイートの改訂

上記の成果物のルールは、プランスイートには適用されません。プランスイートのバージョンは、その `MASTER-PLAN.md` のヘッダーと改訂履歴の表に記録された `vX.Y.Z` の値です。プランスイートの誤字修正は、PATCH 番号を上げる改訂です。`/plan-review` のステップ 10.2 が分類を設定し、改訂履歴の行を追加します。

- `vX.Y.Z` → `vX.Y.(Z+1)`（プランスイート、誤字修正：PATCH）
- `vX.Y.Z` → `vX.Y.Z`（成果物、誤字修正：番号の変更なし。上記の成果物のルールを参照）

## アーティファクトを編集する時機

### ルール

- Mandatory/Optional の構造は全体を支える要素として扱う — これを再構成すると、依存するすべてのアーティファクトに波及する。
- 理解が深まるにつれて、Anti-Patterns、Seriousness Scaling の例、引用を洗練する。
- どの構造上の変更についても、その根拠を該当するメモリトピックファイルに記録する。

### コマンド

- 引数の形は公開契約の一部である — 明示的な意図がある場合にのみ破壊し、その変更をすべての呼び出し元に伝播する（MAJOR の引き上げ）。
- ワークフローの手順と返却契約を、簡潔かつ最新の状態に保つ。
- 自明でない手順の順序は、インラインで文書化する。

### ヘルパー

- `disallowedTools` は最小限かつ十分に保ち、変更するときはその根拠を文書化する。
- ヘルパーの役割が成熟するにつれて、Operating Principles と Return Contracts を洗練する（MINOR の引き上げ）。
- 呼び出し元が期待値を調整し直せるよう、能力の変化をインラインで記録する。

### スキル

- Procedure のステップと Examples を、実態と同期させておく。
- 検出シグナルは、現在の利用における実際のユーザーの言い回しを反映しなければならない。
- スキルが約 150 行を超えたら分割する（`auto-memory.md` の § Topic File Management を参照）。

## ステップバイステップ: 新しいルールの追加

### 1. 直交性を評価する

このルールは既存のルールと重複していないか。関連する内容がないか `src/apothem/rules/` を検索します。

重複が 50% を超える場合は、代わりに既存のルールを拡張することを検討してください。
`persistent-conventions-vigilance.md` の § Artifact Evolution を参照してください。

### 2. 内容を書く

次の構造に従います:

- タイトル: `# Rule: {Title}`
- Purpose セクション
- Obligations / Core directives（番号付き、リンク付き）
- Seriousness Scaling の表（常に必須）
- Anti-Patterns セクション
- Enforcement セクション

### 3. フロントマターを作成する

`site/content/docs/reference/artifact-schema.mdx` の § Schema: Rules にあるスキーマを使用します。次を設定します:

- `name:` kebab-case の識別子
- `description:` レジストリ向けの 1 行の要約
- `pathFilter:` パスフィルター型のルールでは glob のリスト、常時オンのルールでは空文字列（`""`）
- `alwaysApply:` 常時オンのルールでは `true`、パスフィルター型のルールでは `false`

ルールが持つのはこの 4 つのフィールドだけです — `version` / `updated` / `scope` / `portability` / `implements` は持ちません。

新しいルールはパスフィルター型です。新しい常時オンのルールを追加するには、同じ変更でコアリストとバイト上限を引き上げる必要があります: `tests/unit/test_always_on_core.py` のリストと、`conformity/always_on_budget_grep.py` の上限です。
コンパニオンルール（`<parent>-<aspect>`）は、親の `pathFilter`、またはそれより狭いものを使います。

例:

```yaml
---
name: "my-new-rule"
description: "Brief one-liner"
pathFilter: "**/*.py"
alwaysApply: false
---
```

### 4. ルールの README を更新する

`src/apothem/rules/README.md` の Rule families セクションにある、そのルールのファミリーの表に行を追加します:

```markdown
| `my-new-rule.md` | One-line concern of the new rule. |
```

関心事がそのルールに合致するファミリーの表を選びます。
また、`src/apothem/rules/apothem-rule-index.md` の、そのルールを必要とする状況の行にルール名を記載します。ルールがインデックスにない場合、`tests/unit/test_always_on_core.py` は失敗します。

### 5. CHANGELOG.md に追記する

次のリリースの `### Added` セクションの下に、新しいルールを説明する行を追加します。

### 6. 検証を実行する

`ecosystem-audit` スキルを呼び出し、ルール領域に焦点を当てて新しいルールを検証します:

```text
Invoke the ecosystem-audit skill with --focus rules --fix
```

新しいルールについて、エラーが報告されていないことを確認します。

## ステップバイステップ: 新しいコマンドの追加

コマンドとは、`/plan-spec`、`/plan-execute`、`/security-audit` などのスラッシュコマンドです。

### 1. 役割を決める

コマンドは、ユーザーが起動するワークフローです。
モデルがコマンドを単独で実行するのは、その `disable-model-invocation` 設定が `false` の場合に限られます（手順 2）。次を確認します:

- ユーザーが `/command-name` と入力するワークフローか。
- 複数のステップをオーケストレーションするか。
- タイムアウトしたり、実行の途中でユーザーの入力を必要としたりする可能性があるか。

いずれかの答えが「いいえ」なら、それはおそらくコマンドではなくスキルです。

### 2. ファイルを作成する

パス: `src/apothem/commands/{name}.md`

フロントマター（`site/content/docs/reference/artifact-schema.mdx` の § Schema: Commands より）:

```yaml
---
name: "my-command"
version: "X.Y.Z"
updated: "2026-04-20"
description: "What this command does"
argument-hint: "[path/to/input] [--flag VALUE]"
disable-model-invocation: false
portability: "universal"
allowed-tools: "Read, Glob, Grep"
---
```

`disable-model-invocation: true` にすると、コマンドはオペレーターだけが呼び出せるものになります。`false` の場合、リクエストがコマンドの説明に一致するとき、モデルがそれを実行できます。
読み取り専用のコマンドと助言を行うコマンドでは、既定値は `false` で、説明はユースケースから書き始めます。45 個のコマンドのうち 35 個がこれを使います。
作業ツリーの外の状態を変更するコマンド、またはオペレーターがタイミングを選ぶことに依存するコマンドは `true` のままです（10 個のコマンド）。
`src/apothem/commands/README.md` の呼び出し表には、すべてのコマンドの設定が列挙されています。新しいコマンドには行を追加してください。
`allowed-tools` は読み取り専用に保ってください: それを尊重するハーネスは、確認を求めずにそれらのツールを実行します。
副作用のあるツールは、`Bash(git log *)` のようなスコープ付きのルールとしてのみ許可してください。スキーマは `"*"` と、スコープなしで書かれた `Bash`、`PowerShell`、`Write`、`Edit`、`NotebookEdit`、`WebFetch` のいずれかを拒否します。

### 3. 内容を書く

構造:

- タイトル: `# /{name} — Human-Readable Title`
- Role セクション（誰がこれを実行するか）
- 概要レベルの指示
- 手順を含む Workflow セクション
- 返却契約 / 出力形式

あるハーネスのスキル出力は、各コマンドを、スリムな `SKILL.md` と、H2 セクションごとの `references/` ファイルに分割します。
コマンドには `## Workflow` セクションを 1 つだけ持たせ、すべてのコードフェンスを閉じ、新しい種類の H2 は `src/apothem/lib/claude_skill_split.py` で分類してください。未分類の種類があると、`tests/unit/test_claude_skill_split.py` は失敗します。
ルールは `src/apothem/commands/README.md` の Skill-emission split contract に記載されています。

### 4. README と CHANGELOG.md を更新する

手順 2 の呼び出し表の行に加えて、`src/apothem/commands/README.md` にある、そのコマンドのセクションの表に行を追加します。次のリリースの `### Added` セクションの下に CHANGELOG の行を追加します。

### 5. 検証する

コマンドに焦点を当てて、`ecosystem-audit` スキルを呼び出します:

```text
Invoke the ecosystem-audit skill with --focus commands --fix
```

## テストと測定

### スイートを実行する

```bash
python -m pytest                      # unit, integration, property, conformity, scripts
python -m pytest tests/property       # Hypothesis properties (profile loader, frontmatter, merge)
```

このスイートは外部環境から隔離されています: チェックアウトが `$TMPDIR` 配下にある場合でも、`PATH` 上の `python` に CLI の前提条件が欠けている場合でも合格します。
これは、統合テストが pytest を実行しているインタープリターを起動し、入れ子になった一時パスとソースパスを長いものから順にトークン化するためです。

### パッケージごとのカバレッジ

CI は 3 つのパッケージを測定し、それぞれに独自の下限を課します。
どのパッケージも、他のパッケージに統合されることはありません。

| パッケージ | パス | 下限 | 下限の定義場所 |
| --- | --- | --- | --- |
| engine | `cli`、`harnesses`、`lib`、`hooks`、`statuslines` | 80 | `[tool.coverage.report] fail_under` |
| conformity | `src/apothem/conformity` | 81 | `[tool.coverage.package-floors]` |
| audit | `src/apothem/audit` | 70 | `[tool.coverage.package-floors]` |

この数値は行カバレッジと分岐カバレッジを合わせたもので、coverage.py が `branch = true` で報告するのと同じパーセンテージです。メトリクスアーティファクトは、ステートメントのみの数値も `coverage_lines` の下に記録します。
各パッケージの下限は、測定された行 + 分岐の値を切り捨てたものです。
カバレッジが上がったら下限を引き上げてください。変更を合格させるために下限を引き下げることは決してしないでください。
ローカルで確認するには:

```bash
python -m pytest --cov=src/apothem --cov-report=json:coverage.json
python scripts/dev/collect_metrics.py --coverage-json coverage.json --check-floors \
  --skip-hooks --skip-coldstart --harness zed
```

### メトリクスアーティファクト

CI の `metrics` ジョブは、すべてのプッシュとプルリクエストで `scripts/dev/collect_metrics.py` を実行し、`metrics.json`（`schema_version: 1`）をアップロードします。
`null` である値にはすべて、その理由が `nulls` の下に記録されています。

| キー | 測定対象 |
| --- | --- |
| `coverage.engine`、`coverage.conformity`、`coverage.audit` | パッケージごとの行 + 分岐のパーセンテージと、`coverage_floors`。 |
| `always_on_bytes[harness]`、`always_on_files[harness]` | 17 のハーネスそれぞれについて、スクラッチの `HOME` とプロジェクトに対して `profile init` と `install --harness <id>` を実行した後の、そのハーネスが起動時に全文を読み込む命令ファイルのディスク上のバイト数。 |
| `cli_coldstart_ms` | `python -m apothem --version` の中央値（`--help` は `cli_coldstart_detail_ms` の下）。 |
| `hook_e2e_ms[event]`、`hook_injected_chars[event]` | 登録されたイベントとマッチャーごと（`PreToolUse:Write`、`Stop`、…）: 実際のペイロードでのフックチェーンの合計時間の中央値と、それが注入するコンテキストの文字数。 |

説明だけを持つ一覧（スキル、コマンド、サブエージェント）は数えません。

### 振る舞い評価

`evals/` 配下のスイートは、形式ではなく振る舞いを測定します: 148 件のトリガーケース（モデルが呼び出せる各コマンド、スキル、サブエージェントが、その領域のリクエストでは発火し、ニアミスでは反応しないこと、そしてユーザーのみが呼び出せる 6 個のコマンドが自ら開始しないこと）、32 件の結果ケース（計画ステージ、リサーチステージ、監査の観点ごとに 1 件）、6 組のルール効果ペア（抽出したルールのテキストがある場合とない場合）です。
ケースは単なるデータであり、`python -m pytest tests/unit/test_eval_suite.py` によって無料で検証されます。ケースの実行は課金対象で、手動で行います。
`Evals` ワークフロー、ローカルでの実行、ケースの追加方法については、[振る舞い評価を実行する](/docs/how-to/evals)を参照してください。
ペアを持つルールを編集した後は、`python scripts/dev/sync_eval_rule_cases.py` を実行してください。

### ベンチマーク

`make benchmarks` は、`bench_agents.py` を除き、`src/apothem/benchmarks/` 配下のクラスごとのドライバーを実行します。
各ドライバーは、合格で `0`、予算超過で `1`、エラー（測定対象の実行が行われなかった）で `2`、未測定で `3` を返して終了します。

- `bench_hooks.py` は、`hooks/hooks.json` が登録しているすべての `shell: bash` コマンドを、書かれたとおりに、イベントとマッチャーごとの実際のペイロードで実行し、合計時間の中央値、最も遅いコマンド（イベントの予算と照合）、注入された文字数を報告します。
  登録どおりに実行できないコマンド（スクリプトに実行ビットがない場合の終了コード 126）は、合格ではなくエラーです。
- `bench_agents.py` は `NOT MEASURED`（終了コード 3）を報告します: サブエージェントの起動には、ホストハーネスとモデル呼び出しが必要だからです。
  `make benchmarks` はこれを実行しません。

常時オンの予算チェック（`always-on-budget-grep`）は、Bindings セクションとコンパニオンポインター行を除外して、空白区切りの単語を数えます。
その JSON レポートには `always-on-loaded` も含まれます: ハーネスが読み込む、フロントマターを除去した本文のバイト数、文字数、単語数を、常時オンのルール全体で合計したものです。
出荷されるルールディレクトリを対象にした場合、この合計がバイト上限（`always-on-ceiling-bytes` として報告されます）を超えるか、ルールインデックスがそれ自体の上限を超えると、チェックは失敗します。
Claude Code は Bindings セクションを除いたルールのコピーを読み込むため、その読み込みサイズは、このチェックが報告する値より小さくなります。

## エコシステム監査: 検証の実行

2 つの補完的な検証面が、エコシステムをカバーします:

**機械チェック可能（Python バリデーター）** — すべてのコミットの前に実行します:

```bash
python scripts/dev/validate_hooks.py       # Hook structure + Python-only hygiene
python scripts/dev/validate_ecosystem.py   # Full tree + frontmatter + delegated hook checks
python scripts/dev/chaos_pass.py           # Adversarial sweep across configured hooks
pytest tests                                    # Unit tests for the hook runtime
```

**アシスタント駆動** — 相互参照、説明文、規約の監査向け:

```bash
/ecosystem-audit --focus all --fix
```

これは次を並行して実行します:

- **構造監査:** レジストリの正確性、ファイルの存在、フロントマターの妥当性
- **アーティファクト監査:** 相互参照、マンデートのカバレッジ、パイプラインの順序
- **メモリ監査:** メモリファイルの主張とファイルシステムの状態の比較

期待される出力: 両方の面から所見ゼロの `PASS`。

`FINDINGS` が報告された場合:

- 各所見の重大度（Critical / Important / Advisory）を確認する
- Critical の項目には直ちに対処する
- Important の項目は次のサイクルに計画する
- Advisory の項目は次の反復で検討する
