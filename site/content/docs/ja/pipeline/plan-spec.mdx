**役割：** フォージ
**パイプライン位置：** 先頭

自由形式の散文や生のメモを、`/plan-generate` で使える spec 級の `_spec/spec.md` 仕様へと洗練します。

## 正規の呼び出し

```bash
/plan-spec
```

引数付き：

```bash
/plan-spec [path/to/prose-source] [--suite-name NAME] [--refine-existing] [--standalone] [--quick SLUG [--tag TAG]]
```

## 入力

自由形式の散文、生のメモ、またはアドホックな要件（操作者がインラインで、またはパスとして提供）。

## 出力

`_spec/spec.md`（昇格された仕様）+ `_inputs/handoff-manifest.yml`。`--quick` の場合は代わりに、`<project-root>/.apothem/plans/<YYYY-MM-DD>--<kebab-slug>.md` に単一のプロジェクトローカルな軽量プランファイルを書き込みます。

## 下流

/plan-generate（下流の消費者）

## ワークフローのフェーズ

フォージは 6 つの変換フェーズを実行します（仕様は G4 で `_inputs/forge.md` から `_spec/spec.md` へ昇格されます）。

1. **発見と抽出** — 散文／メモを読み、すべての要件、決定、制約を抽出します。
2. **綿密な検討** — 各面を推論し、構造化問い合わせチャネルを通じてあらゆる矛盾を表面化します。
3. **潜在力マッピング** — 各要件を下流のレバレッジへとマッピングします。
4. **保全の検証** — 昇格前に、候補仕様に対して 15 バーの事前発出ゲート（G4）を実行します。
5. **専門知識の適用** — ドメインの専門知識を適用し、専門知識ギャップの所見を記録します。
6. **問い合わせ解決スイープ** — ゲート G0–G5 にわたってすべての未解決の問い合わせを解決し、その後 `_spec/spec.md` とハンドオフマニフェストを発行します。

## 失敗モード

| 症状 | 原因 | 復旧 |
|---------|-------|----------|
| 散文入力の欠落 | 散文／メモが提供されていない | 自由形式の散文をインラインで、またはパスとして提供する |
| 未解決の矛盾 | 散文に相反する要件が含まれている | G3（事前修正）で停止する。決して暗黙にではなく、構造化問い合わせで解決する |
| 仕様がゲートを通らない | G4 で事前発出バーが失敗する | `_inputs/forge.md` からの昇格の前に、失敗したバーを修正する |

## 例

```bash
# 生のメモを spec 級の仕様へとフォージする
/plan-spec ~/notes/feature.md --suite-name my-feature

# 軽量なプロジェクトローカルのプランファイル（フォージの引き出しをバイパス）
/plan-spec --quick my-feature
```
