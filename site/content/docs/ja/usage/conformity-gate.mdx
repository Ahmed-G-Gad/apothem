`src/apothem/conformity/gate.py` にあるコンフォーミティゲートは、15 バーの事前出力ゲート
（M1-M15）のうち機械的に判定される部分を、オペレーターが作成するすべてのアーティファクトに
対して実行します。

このページのコマンドは Apothem のチェックアウトを前提としているため、実行するコマンド
それぞれの先頭に `PYTHONPATH=src` を付けてください。スクリプトでインストールした後は、
`PYTHONPATH=src` の代わりに `PYTHONPATH="$HOME/.apothem/src"` を使います。

## ゲートの実行

ゲートは**デフォルトでは助言的**です。検出事項を報告して `0` で終了するため、ローカルでの
実行があなたの作業を妨げることはありません。ブロッキングの検出事項があるときに非ゼロで
終了させるには、`--strict` を追加します（または `APOTHEM_CONFORMITY_STRICT=1` を設定します）。
これは、CI と pre-commit が、違反している変更を失敗させるために使うモードです。

```bash
# Advisory: report every validator's findings across the repo, exit 0
PYTHONPATH=src python -m apothem.conformity.gate --all .

# Strict: exit non-zero (code 2) when a blocking finding is present
PYTHONPATH=src python -m apothem.conformity.gate --all --strict .
```

終了コード: `0` はクリーン（または助言モード）、`2` は strict モードでの検出事項によるブロック、
`3` は使用法エラー（未知のフラグまたはバリデーター名、存在しないファイル、存在しない
ルートディレクトリ）です。`--help` は完全な使用方法を表示して `0` で終了します。すべての
スタンドアロンバリデーターは同じ `--help` を受け付け、未知のフラグまたはルートの欠落に対して
`3` で終了します。

`.` のような相対ルートは、どのバリデーターも実行される前に絶対パスへ解決されるため、
`--all .` と `--all "$PWD"` は同じツリーを検査します。各バリデーターは `inspected`
（検査した対象の数）を報告し、`--all` はその数をすべての結果エントリにコピーします。何も
検査しなかったバリデーターは `passed: false` を報告するため、誤った作業ディレクトリでも無言の
まま合格することはありません。2 つのプランスイートバリデーターは、その例外の 1 つです。
プランスイートは gitignore 対象の `.apothem/plans/` ツリーに置かれるため、これらはクリーンな
チェックアウトでは `empty_scope_expected: true` を報告し、それでも合格します。ワークフロー
バリデーターも、プロジェクトにまだ `.github/workflows/` ディレクトリがない場合に同じ動作を
し、コミットサブジェクトバリデーターは、ルートにコミット履歴がない場合に同じ動作をします。

プロジェクトには、アーカイブや共有フォルダーを通じて他の人が作成したファイルが含まれることがあります。そのため、すべての `--all` バリデーターは、ルートより下の実フォルダーをたどって到達した通常ファイルと実フォルダーだけを開き、一覧にします。シンボリックリンクや、Windows ではジャンクションをたどることはなく、ルートより下のどの階層でも次のものを存在しないものとして扱います。

- リンク。ルートの内側を指すものも含みます。走査やフォルダーの一覧はこれを飛ばすため、リンク先はバリデーターがそれ自身のパスで到達した場所でのみ検査されます。
- 名前付きパイプ、デバイス、ソケット。読み取りが待ち続けたり、終わらなかったりするためです。
- Windows では、末尾がドットまたは空白の名前。Windows がその名前で別のエントリを開くためです。

いくつかの検査は、リンクの中に入らずにリンクを使います。

- `CLAUDE.md` が別のファイルを指している場合のように、固定ファイルがシンボリックリンクであるとき、ゲートはリンク自体のテキストを読み、それが指すファイルが実フォルダーを通って到達できるプロジェクト内の通常ファイルである場合にだけ開きます。フォルダーごとの `README.md` リンクも同じように扱われます。絶対パスのリンクは、解決後のプロジェクトフォルダーを通して書かれている場合、または Windows では大文字と小文字だけが異なる同じパスを通して書かれている場合に有効です。単独で実行したバリデーターは、パスに `..` が含まれない限り、入力したとおりのフォルダーも受け付けます。一方、ゲートは各バリデーターを起動する前にフォルダーを解決します。リンクされた `.gitattributes` は、git が読まないため、引き続き存在しないものとして扱われます。
- `no-global-plans-grep` の迷子プラン検査は、リンクになっているプランフォルダーや `.apothem` フォルダーを、リンク先がどこであっても名前で報告します。
- `no-toplevel-docs-grep` は、ルートにある `docs` リンクを名前で報告します。
- `naming-grep` は、リンク自体の名前を検査します。

各バリデーターのレポートは、除外したリンクと特殊ファイルを `skipped_links` に一覧するため、リンクが痕跡なくファイルを隠すことはありません。一覧にできなかったフォルダー（アクセス権がない、パスが長すぎる、読み取りエラー）や、入れ子のチェックアウトとして飛ばしたフォルダーの `.git` エントリがリンクまたは特殊ファイルである場合のそのエントリも、ここに一覧されます。ワークフローのバリデーターのように、フォルダーがないときに合格するバリデーターは、そのフォルダーがリンクである場合は合格しません。ファイルがその先にあるかもしれないため、何も検査しなかった実行と同じく失敗します。ハードリンクは通常ファイルであり、通常ファイルとして読まれます。これらの検査は各階層に到達したときにその階層を確認し、その後でファイルを名前で開きます。そのため、ゲートの実行中にプロジェクトへ書き込める別のユーザーは、確認済みのファイルやフォルダーを開かれる前にリンクへ差し替えることができます。ゲートはこれを防ぎません。`--all` と `--all-perwrite` では、ゲート自体はルート内の通常ファイルだけを開き、git が一覧にするすべてのパスを含め、途中の各フォルダーを `lstat` で確認し、`.git` エントリの内部は決して読みません。git を実行する前に、git を実行する 3 つの `--all` バリデーターと 2 つの `--staged` 検査は、その時点のツリーのとおりに、ルートと、git が探索するその上の各フォルダーの `.git` エントリを `lstat` で確認します。そのいずれかがリンクであるか、確認できない場合は git を実行しません。これにより、`.git` がリンクになっているホームフォルダーの下にあるすべてのプロジェクトのように、git なら安全に扱えるプロジェクトも、独自のリポジトリを持つものでさえ拒否されます。これは単純なルールのための意図的な代償です。これらは、リポジトリ、そのストア、インデックスを指定する `GIT_DIR` などの変数なしで git を実行します。その後 git がどのリポジトリを読むかは検査しません。`gitdir:` 行、`commondir`、alternates、`core.worktree`、include、または git フォルダー内のリンクが別のリポジトリを指すことがあり、git はそれに従うため、git がネットワークパスに到達したり、制限時間まで待ったりすることがあります。ゲートは git の出力を、名前、モード、状態を示す文字、最後のコミットの件名、コミット時刻、いくつかの設定としてだけ使い、git が出力したパスを、ルート内の各階層を確認せずに開くことはありません。リンクが見つかった場合、それぞれがそのリンクを `skipped_links` に一覧します（ルート内にあればルートからの相対パス、ルートより上にあればフルパスで示します）。その場合 `conventional-commit-grep` はチェックアウトの外と同じく `not-a-git-repo` を報告しますが、合格はしません。リンクを示す `check_error` を出します。`no-global-plans-grep` はリンクを指摘として報告して失敗し、コンパニオンファイルの検査は、履歴がない場合と同じく鮮度テストを飛ばします。`--all-perwrite` も追跡対象ファイルを一覧にせず、リンクを示す `check_error` で失敗します。2 つの `--staged` 検査も同様で、フックの `GIT_DIR` が指すリポジトリを読みますが、実行したフォルダーからの探索パス上のリンクはやはり拒否します。ゲートが確認できない `.git` エントリ（パスが長すぎる、共有に到達できない、アクセス権がない）はリンクではなく、`skipped_links` には一覧されません。`conventional-commit-grep` は状態 `git-failed` と `check_error` で失敗し、コンパニオンファイルの検査、`--all-perwrite`、2 つの `--staged` 検査は、エントリを確認できなかったことを示す `check_error` で失敗し、`no-global-plans-grep` はそれを指摘として報告します。

6 つのバリデーターは、リポジトリのルートから開始し、チェック対象のファイルをツリー全体から
探します。

```text
agents-md-coverage-grep
agnosticism-grep
dynamism-grep
freshness-token-grep
plain-language-grep
reference-token-grep
```

これらは、ワークツリー、サブモジュール、入れ子のクローンなど、入れ子になった git チェック
アウトをスキップし、`node_modules`、`venv`、`dist` など、依存関係、仮想環境、キャッシュ、
ビルド出力を保持するディレクトリもスキップします。`no-global-plans-grep` の迷子プランの
チェックも、入れ子のチェックアウトで止まります。これらのいずれかの実行は、指定された
チェックアウトについてのみ報告し、それ以外については何も報告しません。`src/apothem/` の下を
読む `naming-grep` のように、1 つの固定フォルダーを読むバリデーターは、そのフォルダーの下の
すべてを読みます。

## 対象を絞ったチェック

```bash
# List every registered validator
PYTHONPATH=src python -m apothem.conformity.gate --list

# Run one per-write validator against one file
PYTHONPATH=src python -m apothem.conformity.gate --check multi-surface-coherence src/apothem/rules/my-rule.md

# Run one standalone validator over a root directory
PYTHONPATH=src python -m apothem.conformity.gate --check naming-grep .

# Run every per-write validator against one file
PYTHONPATH=src python -m apothem.conformity.gate src/apothem/rules/my-rule.md
```

書き込みごとのバリデーターは、チェック対象のファイルを受け取るか、`--stdin` で標準入力から
内容を読み取ります。どちらも指定しない場合は標準入力からの入力を待つため、ターミナルから
実行するときはファイルを渡してください。スタンドアロンバリデーターは、ルートディレクトリを
受け取ります（省略した場合はカレントディレクトリ）。`--list` は、各バリデーターがどちらの
グループに属するかを示します。

`--hook` モード（`python -m apothem.conformity.gate --hook`）は、ハーネスからディスパッチ
されるエントリーポイントです。標準入力からツール入力の JSON ペイロードを読み取り、保留中の
書き込みに対して、書き込みごとのマッチャーチェーンを実行します。これはデプロイされた
`PreToolUse` フックが呼び出す形式であり、手動で呼び出すことはほとんどありません。

フックモードは**一連のディレクトリにスコープされます**。マッチャーチェーンは、ターゲットが
それらのいずれかの配下にある書き込みに対してのみ実行されます。どのスコープにも含まれない
書き込みは短絡され、無言で合格となります。デフォルトは次の 2 つのルートです。

```text
~/.claude      Claude Code
$CODEX_HOME    Codex (~/.codex when CODEX_HOME is not set)
```

それらを置き換えるには、`APOTHEM_CONFORMITY_SCOPE` にディレクトリを設定します。

```bash
# Run the per-write matcher chain against one project tree instead
export APOTHEM_CONFORMITY_SCOPE=/path/to/project
```

何もしていないように見えるフックは、通常は失敗ではなくスコープの不一致です。まず、書き込みの
ターゲットを上記のスコープと照らし合わせて確認してください。

## CI 統合

`.github/workflows/ci.yml` の品質ジョブは、`main` へのプッシュ時と、`main` へのプルリクエストのうちそのジョブが監視するパスに触れるものに対して、ゲートを strict モード（`python -m apothem.conformity.gate --all . --strict`）で実行します。別のワークフロー `.github/workflows/conformity.yml` は、フィクスチャのスイープ（`tests/conformity-scenarios/verify.py --strict`）を実行します。
