`src/apothem/conformity/gate.py` にあるコンフォーミティゲートは、15 バーの事前出力ゲート
（M1-M15）のうち機械的に判定される部分を、オペレーターが作成するすべてのアーティファクトに
対して実行します。

このページのコマンドは Apothem のチェックアウトを前提としているため、実行するコマンド
それぞれの先頭に `PYTHONPATH=src` を付けてください。スクリプトでインストールした後は、
`PYTHONPATH=src` の代わりに `PYTHONPATH="$HOME/.apothem/src"` を使います。

## ゲートの実行

ゲートは**デフォルトでは助言的**です。検出事項を報告して `0` で終了するため、ローカルでの
実行があなたの作業を妨げることはありません。ブロッキングの検出事項があるときに非ゼロで
終了させるには、`--strict` を追加します（または `APOTHEM_CONFORMITY_STRICT=1` を設定します）。
これは、CI と pre-commit が、違反している変更を失敗させるために使うモードです。

```bash
# Advisory: report every validator's findings across the repo, exit 0
PYTHONPATH=src python -m apothem.conformity.gate --all .

# Strict: exit non-zero (code 2) when a blocking finding is present
PYTHONPATH=src python -m apothem.conformity.gate --all --strict .
```

これらのコマンドは、Apothem のチェックアウトからゲートを実行します。`python -m` はまずカレントフォルダーからモジュールを読み込むため、チェックアウトのルートか、信頼できる別のフォルダーから実行してください。ファイルを信頼できないプロジェクトを検査するには、代わりにスクリプトのパスと `-E -s` でゲートを実行します。チェックアウトでは `python3 -E -s src/apothem/conformity/gate.py --all .`、スクリプトでインストールした後は `python3 -E -s ~/.apothem/src/apothem/conformity/gate.py --all .` です。Windows では、Windows PowerShell と cmd が `~` を展開しないため、`python3` の代わりに `python` を使い、フルパスを指定します。PowerShell では `$HOME\.apothem\src\apothem\conformity\gate.py`、cmd では `%USERPROFILE%\.apothem\src\apothem\conformity\gate.py` です。スクリプトとして起動すると、カレントフォルダーは Python のモジュール検索パスの先頭エントリに入りません。`-E` は `PYTHONPATH` も除外します（その空のエントリや相対のエントリもカレントフォルダーを指します）。`-s` はユーザーの site-packages を除外します。これによってプロジェクトのファイルが遠ざけられるのは、ゲート自身の Python コードからだけです。ゲートが実行する `git` については次に説明します。

3 つのスタンドアロンバリデーターは、検査するプロジェクトで `git` を実行します。それらを実行する `--all` と、`git ls-files` で追跡対象ファイルを一覧にする `--all-perwrite` も同様です。

```text
agents-md-coverage-grep
conventional-commit-grep
no-global-plans-grep
```

そのリポジトリ自身の設定（`.git/config`、それがインクルードするファイル、`.git/config.worktree`）は、git が読み取りしか行わない場合でも、git に起動させるプログラムを指定できます。ゲートは、把握しているそのような設定のそれぞれを git のコマンドラインのオプションで無効にします。コマンドラインのオプションは git が読むどのファイルよりも優先され、git がサブモジュール内で起動する git にも届きます。

- ファイルシステムモニターなし（`core.fsmonitor`）。
- 署名プログラムなし（`gpg.program`、`gpg.ssh.program`、
  `gpg.x509.program` は何も存在し得ないパスを指し、`log.showSignature` はオフ）。
- フックなし、ページャーなし、自動メンテナンスなし。
- 外部 diff やテキスト変換のプログラムなし。サブモジュールの変更はコミット ID だけで
  示されるため、git がサブモジュール内で 2 つ目の git を起動することはありません。
- ファイルの内容は `git cat-file blob` で読みます。`git show` ならサブモジュールの
  エントリをコミットとして表示するところを、これは拒否します。

3 つの設定は、プログラムではなく git が読むファイルを指定し、そのファイルはネットワークパス上に置くことができます。ゲートのコマンドラインは、git がそれらを読むことも防ぎます。diff の順序ファイル（`diff.orderFile`）、除外ファイル（`core.excludesFile`）、mailmap ファイルです。

また、ゲートは `GIT_NO_LAZY_FETCH=1` と空の `GIT_ALLOW_PROTOCOL` を設定するため、git が部分クローンの欠けたオブジェクトを、リポジトリが指定するアドレスから取得することはありません。ゲートは `PATH` のフルパスのエントリからだけ git を起動します。カレントフォルダーから git を取ることは決してありません。カレントフォルダーを指す空の `PATH` エントリや相対の `PATH` エントリは飛ばし、Windows が単なるプログラム名に対して行うように、カレントフォルダーを最初に探すこともしません。git が名前で起動するプログラムについても、git に渡されるのはそれらのフルパスのエントリだけです。

そのため、アーカイブや共有フォルダーを通じて他の人から `.git` フォルダーごと受け取ったプロジェクトに対しても、これらのコマンドを実行できます。上記の設定のどれも、ゲートにプログラムを起動させることはできません。制限が 2 つ残ります。リポジトリは、パスを指定する任意の設定やファイルを通じて、git に別の場所のパスを読ませることができます。たとえば `include.path` や `includeIf`、`core.worktree`、`.git` ファイルの `gitdir:` 行、`.git/objects/info/alternates` です。Windows では、そこにあるネットワークパス（`\\server\share`）によって、Windows がそのサーバーに接続し、あなたをサインインさせます。1 つのケースでは範囲がより狭くなります。Git for Windows 2.55 は、あなた自身の `safe.directory` 設定がそのパスを許可していない限り、`gitdir:` 行にあるネットワークパスを接続の前に拒否します。また、この一覧は現在知られている設定を対象としており、後の git のリリースで新しい設定が加わる可能性があります。あなた自身のグローバルおよびシステムの git 設定は、ゲートのコマンドラインが上書きする上記の設定を除き、引き続き適用されます。これは git だけを対象としています。`python -m` はまずカレントフォルダーから Python モジュールを読み込むため、ゲートは信頼できるフォルダーから起動してください。

終了コード: `0` はクリーン（または助言モード）、`2` は strict モードでの検出事項によるブロック、
`3` は使用法エラー（未知のフラグまたはバリデーター名、存在しないファイル、存在しない
ルートディレクトリ）です。`--help` は完全な使用方法を表示して `0` で終了します。すべての
スタンドアロンバリデーターは同じ `--help` を受け付け、未知のフラグまたはルートの欠落に対して
`3` で終了します。

`.` のような相対ルートは、どのバリデーターも実行される前に絶対パスへ解決されるため、
`--all .` と `--all "$PWD"` は同じツリーを検査します。各バリデーターは `inspected`
（検査した対象の数）を報告し、`--all` はその数をすべての結果エントリにコピーします。何も
検査しなかったバリデーターは `passed: false` を報告するため、誤った作業ディレクトリでも無言の
まま合格することはありません。2 つのプランスイートバリデーターは、その例外の 1 つです。
プランスイートは gitignore 対象の `.apothem/plans/` ツリーに置かれるため、これらはクリーンな
チェックアウトでは `empty_scope_expected: true` を報告し、それでも合格します。ワークフロー
バリデーターも、プロジェクトにまだ `.github/workflows/` ディレクトリがない場合に同じ動作を
し、コミットサブジェクトバリデーターは、ルートにコミット履歴がない場合に同じ動作をします。

プロジェクトには、アーカイブや共有フォルダーを通じて他の人が作成したファイルが含まれることがあります。そのため、すべての `--all` バリデーターは、ルートより下の実フォルダーをたどって到達した通常ファイルと実フォルダーだけを開き、一覧にします。シンボリックリンクや、Windows ではジャンクションをたどることはなく、ルートより下のどの階層でも次のものを存在しないものとして扱います。

- リンク。ルートの内側を指すものも含みます。走査やフォルダーの一覧はこれを飛ばすため、リンク先はバリデーターがそれ自身のパスで到達した場所でのみ検査されます。
- 名前付きパイプ、デバイス、ソケット。読み取りが待ち続けたり、終わらなかったりするためです。
- Windows では、末尾がドットまたは空白の名前。Windows がその名前で別のエントリを開くためです。

いくつかの検査は、リンクの中に入らずにリンクを使います。

- `CLAUDE.md` が別のファイルを指している場合のように、固定ファイルがシンボリックリンクであるとき、ゲートはリンク自体のテキストを読み、それが指すファイルが実フォルダーを通って到達できるプロジェクト内の通常ファイルである場合にだけ開きます。フォルダーごとの `README.md` リンクも同じように扱われます。絶対パスのリンクは、解決後のプロジェクトフォルダーを通して書かれている場合、または Windows では大文字と小文字だけが異なる同じパスを通して書かれている場合に有効です。単独で実行したバリデーターは、パスに `..` が含まれない限り、入力したとおりのフォルダーも受け付けます。一方、ゲートは各バリデーターを起動する前にフォルダーを解決します。リンクされた `.gitattributes` は、git が読まないため、引き続き存在しないものとして扱われます。
- `no-global-plans-grep` の迷子プラン検査は、リンクになっているプランフォルダーや `.apothem` フォルダーを、リンク先がどこであっても名前で報告します。
- `no-toplevel-docs-grep` は、ルートにある `docs` リンクを名前で報告します。
- `naming-grep` は、リンク自体の名前を検査します。

各バリデーターのレポートは、除外したリンクと特殊ファイルを `skipped_links` に一覧するため、リンクが痕跡なくファイルを隠すことはありません。一覧にできなかったフォルダー（アクセス権がない、パスが長すぎる、読み取りエラー）や、入れ子のチェックアウトとして飛ばしたフォルダーの `.git` エントリがリンクまたは特殊ファイルである場合のそのエントリも、ここに一覧されます。フォルダー自体は、後述の `skipped_checkouts` に一覧されます。ワークフローのバリデーターのように、フォルダーがないときに合格するバリデーターは、そのフォルダーがリンクである場合は合格しません。ファイルがその先にあるかもしれないため、何も検査しなかった実行と同じく失敗します。ハードリンクは通常ファイルであり、通常ファイルとして読まれます。`--all` のバリデーターと `--all-perwrite` は各階層に到達したときにその階層を確認し、その後ルートから 1 階層ずつ、各フォルダーを直前に開いたフォルダーの中で開いてファイルを開きます。リンクを通ることはありません。そのため、ゲートの実行中にプロジェクトへ書き込める人が、確認済みのファイルやその上のフォルダーをリンクや名前付きパイプへ差し替えても、ゲートはリンクを通して読まず、パイプで待つこともありません。そのファイルは読まれません。`--all` のバリデーターは、リンクと同じく、そのファイルを存在しないもの、または読めないものとして数え、差し替えられたエントリを `skipped_links` に一覧します。`--all-perwrite` はそのファイルを `link` として数え、再び差し替えられた場合は、後述のとおり `unreadable` として数えます。Windows では、通常の方法で開く場合と同じく、待ちが 1 つ残ります。プロジェクトへ書き込めるプログラムは、ファイルに日和見ロック（oplock）をかけたまま、ゲートがそのファイルを開いても解放しないことができます。どの開き方でもこの待ちは避けられないため、`--all` のバリデーターは 10 分の制限まで待ち、そのような制限のない `--all-perwrite` は、そのプログラムが解放するまで待ちます。`--all` と `--all-perwrite` では、ゲート自体はルート内の通常ファイルだけを開き、git が一覧にするすべてのパスを含め、途中の各フォルダーを `lstat` で確認し、`.git` エントリの内部は決して読みません。git を実行する前に、git を実行する 3 つの `--all` バリデーターと 2 つの `--staged` 検査は、その時点のツリーのとおりに、ルートと、git が探索するその上の各フォルダーの `.git` エントリを `lstat` で確認します。そのいずれかがリンクであるか、確認できない場合は git を実行しません。これにより、`.git` がリンクになっているホームフォルダーの下にあるすべてのプロジェクトのように、git なら安全に扱えるプロジェクトも、独自のリポジトリを持つものでさえ拒否されます。これは単純なルールのための意図的な代償です。3 つの `--all` バリデーターは、リポジトリ、そのストア、インデックスを指定する `GIT_DIR` などの変数なしで git を実行します。`--staged` 検査はフックの `GIT_DIR` を保持します。その後 git がどのリポジトリを読むかは検査しません。`gitdir:` 行、`commondir`、alternates、`core.worktree`、include、または git フォルダー内のリンクが別のリポジトリを指すことがあり、git はそれに従うため、git がネットワークパスに到達したり、制限時間まで待ったりすることがあります。ゲートは git の出力を、名前、モード、状態を示す文字、最後のコミットの件名、コミット時刻、いくつかの設定としてだけ使い、git が出力したパスを、ルート内の各階層を確認せずに開くことはありません。リンクが見つかった場合、3 つの `--all` バリデーターはそれぞれそのリンクを `skipped_links` に一覧します（ルート内にあればルートからの相対パス、ルートより上にあればフルパスで示します）。その場合 `conventional-commit-grep` はチェックアウトの外と同じく `not-a-git-repo` を報告しますが、合格はしません。リンクを示す `check_error` を出します。`no-global-plans-grep` はリンクを指摘として報告して失敗し、コンパニオンファイルの検査は、履歴がない場合と同じく鮮度テストを飛ばします。`--all-perwrite` も追跡対象ファイルを一覧にせず、リンクを示す `check_error` で失敗します。2 つの `--staged` 検査も同様ですが、リンクを示すのは `check_error` の中だけで、実行したフォルダーの `.git` エントリがリンクであると述べる場合もあります。これらはフックの `GIT_DIR` が指すリポジトリを読みますが、実行したフォルダーからの探索パス上のリンクはやはり拒否します。ゲートが確認できない `.git` エントリ（パスが長すぎる、共有に到達できない、アクセス権がない）はリンクではなく、`skipped_links` には一覧されません。`conventional-commit-grep` は状態 `git-failed` と `check_error` で失敗し、コンパニオンファイルの検査、`--all-perwrite`、2 つの `--staged` 検査は、エントリを確認できなかったことを示す `check_error` で失敗し、`no-global-plans-grep` はそれを指摘として報告します。

各スタンドアロンバリデーターは独立したプログラムとして実行され、ゲートは `--all` でも `--check` でも、それぞれに 10 分を与えます。最も遅いものでも、Apothem 自身のリポジトリで約 1 分です。制限の時点でまだ実行中のバリデーターは、それが起動したすべてのプログラム（まだ待機中の `git` コマンドなど）とともに停止され、`passed: false` と、完了しなかったことを示す `check_error` とともに報告されます。Linux と macOS では、各バリデーターは独自のセッションで実行され、`timeout` や閉じられたターミナルなどからゲートに `SIGTERM` または `SIGHUP` が届くと、ゲートはバリデーターのプログラムを停止してから、128 にそのシグナルの番号を足したコードで終了します。ゲートがバリデーターを起動または停止している最中に届いたシグナルについても同じです。ゲートはその手順が終わるまで待ち、その手順の間に Ctrl+C が続いても、終了コードは 128 にそのシグナルの番号を足したもののままです。どのプログラムも捕捉できない `SIGKILL` は、そこではゲートだけを終了させます。ゲートが起動したバリデーターは完了するまで実行を続け、そのバリデーターが待っている `git` コマンドは、それ自身の制限でやはり停止します。Windows では、各バリデーターはジョブオブジェクト内で実行され、ゲート自体が終了したときにもそのプログラムが終了します。
そこでゲートが起動する各プログラムは、ジョブオブジェクトに入るまで一時停止した状態で待ちます。再開できなかったプログラムは停止され、エラーには、それがジョブオブジェクトに入っているかどうかが示されます。再開される前に他の何かから終了を指示されたプログラムは一度も実行されておらず、終了コードにかかわらず同じように失敗します。ただし、例外が 2 つあります。終了コード 259（Windows が実行中のプログラムにも与えるコード）で終了したプログラムは、Windows がまだ終了処理をしている間は実行中として読まれます。再開の直前に終了したプログラムが検出されるのは、ゲートが再開から 1 ms 以内にその終了コードを読んだ場合だけです。それより後に読んだ場合、たとえば負荷の高いマシンや、呼び出し元プロセスの他のスレッドが忙しいときは、その終了コードをプログラム自身のものとして扱います。測定したマシンでは、Windows が実行できる最小のプログラムは再開から少なくとも 3 ms、`git` は 27 ms 生存したため、実行されたプログラムが終了させられたものと取り違えられることはありません。再開の直後に終了したプログラムも、実行されたものと区別できません。すべてのプラットフォームで、ゲート自身の実行において、起動の最中に届いた Ctrl+C はプログラムが実行されるまで（Windows では、ゲートが再開を試みるまで）待つため、一時停止のまま、または制限を過ぎて実行されたまま残るプログラムはありません。ゲートがプログラムを停止している最中に届いた 2 回目の Ctrl+C は、停止が完了するまで待ちます。停止が始まる直前に届いたものは、ゲートに停止を最大 3 回まで再試行させます。それらの試行が失敗した場合、または 2 つの試行の間に Ctrl+C が届いた場合、ゲートはシグナルを保留せずにプログラムを停止します。これも最大 3 回までなので、さらに 1 回 Ctrl+C を押しても停止が飛ばされることはありません。プログラムを実行したまま残すには、それぞれがこれらの時点のいずれかからマイクロ秒以内に届く、何回もの Ctrl+C が必要です。停止の後、ゲートは停止したプログラムの終了を最大 0.5 秒待つため、Linux と macOS ではそのプログラムが defunct プロセスとして残ることはなく、その待機中の Ctrl+C がすでに進行中の終了処理を置き換えることもありません。呼び出し元プロセスが別のシグナルに設定したハンドラーは、プログラムの起動後、ゲートがそれを記録する前の数マイクロ秒の間にそのエラーが発生した場合、プログラムを実行したまま（Windows では一時停止のまま）残すことがあります。ゲートが自身のシグナルハンドラーを変更するとき、変更の途中で届いたシグナルによってハンドラーが変更されたまま残ることはありません。Linux と macOS では、ゲートは変更にかかる数マイクロ秒の間、Ctrl+C、`SIGTERM`、`SIGHUP` をブロックし、それ以外のシグナルはブロックしません。そのため、そうしたシグナルは変更が完了するまで待ち、その時点で設定されているハンドラーに届きます。その後、ゲートは自分がブロックしたシグナルだけのブロックを解除します。それ以外のシグナル、Windows の場合、そしてブロックの直前に届いたシグナルについては、シグナルによって中断された変更を最大 3 回までやり直します。ハンドラーを元に戻す処理がすべての試行で失敗した場合、ゲートは残った各ハンドラーについて最後の試行を 1 回行います。呼び出し元プロセスが設定した、毎回発火するタイマーからの `TimeoutError` のように、エラーがその最後の試行も止めた場合、そしてまれに、ハンドラーが例外を送出するシグナルが数マイクロ秒以内に立て続けに複数届いて最後の試行を飛ばした場合には、ハンドラーは変更されたまま残ります。Python の再帰制限付近での `RecursionError` のように、毎回の試行で返ってくるエラーは、2 回の試行以内に変更を終わらせ、処理を続けます。ゲートは、ハンドラーを変更したときより深くない呼び出しでハンドラーを元に戻すため、その制限付近でも Ctrl+C が無視されたまま残ることはありません。呼び出し元プロセスが実行中に設定した `SIGTERM` ハンドラーは、そのまま残ります。Linux と macOS では、シグナルハンドラーを設定できない Python のサブインタープリター内では、ゲートはハンドラーを変更せずにプログラムを実行します。Windows では、デーモンスレッドを許さない分離されたサブインタープリターからは、Python がプログラムの出力を読み取れません。Ctrl+C は 1 行を表示して `130` で終了します。制限は合算されます。複数のバリデーターが待つ実行には、それらの制限の合計の時間がかかります。

5 つのバリデーターは、実行する各 `git` コマンドにも独自の制限時間を与えます。
この制限はすべてのプラットフォームで有効であり、Windows で `PATH` 上の `git` が、Git for Windows がインストールするランチャー（本物の git を起動するもの）である場合も含みます。

```text
conventional-commit-grep            git log -1, git rev-parse           1 minute
                                    git ls-files, git config            1 minute
agents-md-coverage-grep             git rev-parse, git config           1 minute
                                    git log over the whole history      5 minutes
no-global-plans-grep                git ls-files                        1 minute
production-ready-pr-grep --staged   git diff --cached                   1 minute
semver-stability-grep --staged      git diff --cached, git cat-file     1 minute
```

これらのコマンドはほとんどのプロジェクトで 1 秒もかからないため、制限に達するのは、`git` が決して来ないものを待っている場合だけです。プロジェクト自身の git 設定は、git をいつまでも待たせることがあります。たとえば、`.git/config` 内の、名前付きパイプを指す `include.path` です。制限を超えて実行された `git` コマンドは合格しません。バリデーターは、そのコマンドを示す `check_error` とともに `passed: false` を報告します。見つけたチェックアウトを拒否する `git` も同様です。たとえば、別のユーザーが所有するチェックアウトや、`.git/config` に不正な行があるチェックアウトです。その場合 `check_error` は git の終了コードを示します。終了コード 128 は、git がリポジトリを開けない、または読めないときに使うコードです。git が `.git` エントリを開けないフォルダーも、そのようなチェックアウトとして扱われます。検査に必要な履歴が、読まれないままそこにあるかもしれないためです。他のどのチェックアウトの外にもある空の `.git` フォルダーや、もう存在しないフォルダーを指す `.git` ファイル（展開されたワークツリーやコピーされたサブモジュールが残すもの）がその例です。そのエントリを削除するか、完全なチェックアウトでゲートを実行してください。これは、指摘が通常は助言にとどまる古いコンパニオンの検査についても同じであり、その場合コミットサブジェクトの検査も `inspected: 0` と `empty_scope_expected: false` を報告します。Windows では、ゲートが起動したものの再開できなかった `git` も、失敗した `git` です。`check_error` は終了コード 128 を示し、`git` がないものとして数えられることは決してありません。古いコンパニオンの検査は履歴全体を 1 回読み、その読み取りには 5 分が与えられるため、大きな履歴は失敗ではなく遅くなるだけです。それより読み取りに時間がかかる履歴では、検査は失敗します。どの git チェックアウトの中にもない普通のフォルダー、まだコミットのないリポジトリ、`git` のないマシンは、これまでどおりこれらの検査に合格します。`git clone --filter` で作った部分クローンも同様です。ゲートは、クローンが省いたものを `git` に取得させません。また git は、クローンが省いたオブジェクトと失われたオブジェクトを区別できる答えを返しません。そのため部分クローンでは、古いコンパニオンの検査は、失敗した履歴の読み取りをすべて利用できない履歴として数えます。履歴がない場合と同じく、鮮度テストを飛ばして合格します。これらの例外と、git が拒否するチェックアウトに対する `check_error` は、他の 4 つのバリデーターのためのものです。`no-global-plans-grep` は git が読めるチェックアウトを必要とするため、チェックアウトの外、`git` のないマシン、git が拒否するチェックアウトでは、これまでどおり失敗し、理由を標準エラーに出力します。示すのは git の終了コードであり、git 自身のテキストではありません。合格しない他の結果と同じく、助言的なデフォルトはそれを報告して `0` で終了し、`--strict` は `2` で終了します。

2 つの `--staged` 検査にとっては、`diff.renameLimit = abc` のように git が読めない diff 設定の値も、そのような不正な行の 1 つです。`git diff` は失敗し、読まれなかった変更セットは空の変更セットではありません。この 2 つの検査、コミットサブジェクトの検査、古いコンパニオンの検査は、実行したフォルダーとその上のフォルダーでチェックアウトを探すため、チェックアウトのサブフォルダーでも同じことが成り立ちます。探索は git が止まる場所で止まります。`GIT_CEILING_DIRECTORIES` に指定されたフォルダーと、Windows 以外では、`GIT_DISCOVERY_ACROSS_FILESYSTEM` が設定されていない限り、別のファイルシステム上のフォルダーです。したがって、独自のリポジトリを持たず、リポジトリの下にマウントされたフォルダーは、引き続き合格します。チェックアウトのサブフォルダーで実行したコミットサブジェクトの検査は、チェックアウトがそのサブフォルダー内のファイルを追跡しているか、そこにステージ済みのファイルがある場合に、チェックアウトの最新のコミットを検査します。Windows や macOS のように、チェックアウトが大文字と小文字を区別しない場合は、ディスク上で大文字と小文字だけ名前が変わったサブフォルダーについても同じです。チェックアウトが追跡していないフォルダー（未追跡のものや無視されたもの）は独自の履歴を持たないため合格します。ホームフォルダーのドットファイル用リポジトリの中にある新しいプロジェクトがその例です。実行したフォルダーの上に空の `.git` フォルダーがあり、さらに上にリポジトリがない場合は git が失敗し、検査は `git-failed` を報告します。

どちらの `--staged` 検査も、あなた自身の `diff.relative` 設定にかかわらず、ステージ済みの名前を作業ツリーの最上位から読むため、サブフォルダーの設定によってステージ済みのファイルが隠れることはありません。

`semver-stability-grep --staged` は、実行したフォルダー、続いてその上のフォルダーの順に、リポジトリを保持する最も近いフォルダー、または git が探索を止める場所までパッケージを探し、パッケージを保持するフォルダーで git を実行します。そのため、サブフォルダーから実行しても同じ変更セットを検査します。バージョンファイルもそのフォルダーから読むため、リポジトリの最上位より下にあるパッケージも検査されます。実行したフォルダーとパッケージの間に git が拒否する `.git` ファイルがある場合、git は代わりに実行したフォルダーで実行され、そのファイルで止まり、検査は `check_error` を報告します。git が拒否するのは、リポジトリを指していない `.git` ファイル、1 MiB より大きい `.git` ファイル、そして `gitdir:`、空白 1 つ、パスの後に行末しか続かないという形になっていない `.git` ファイルです。Windows では、ネットワーク、デバイス、NT のパス（`\\host\share`、`\\?\`、`\??\`）を指す `.git` ファイルも拒否し、そのパスを自分で調べることはしません。Git for Windows が拒否するパスも拒否します。末尾がドットまたは空白の名前、`aux.d`、`lpt0`、`CONIN$` のようなデバイス名（ただし Git for Windows が受け付ける `com0` は除きます）、またはドライブの後の `:` です。パス内の UTF-8 でないバイトは、Git for Windows と同じように読みます。`0xA0` 以上はその文字として、それ未満は 2 桁の 16 進数として読むため、`0x9F` は `9f` と読まれます。`src/apothem/__init__.py` を保持する最も近いフォルダーが検査対象です。`GIT_WORK_TREE` は読みません。パッケージを持たないプロジェクトにはそこで検査するものがないため、リポジトリがどの状態であっても、git を実行せずに合格します。

ゲートは git からのパス名の各リストをバイト単位で読むため、改行、復帰、UTF-8 でないバイトを含む名前も、すべての検査で同じファイルを指します。読めないケースが 1 つあります。Windows は UTF-8 でない名前を git に渡せず、そうした名前を保持できるのは別のシステムで作られたインデックスだけです。その場合 `semver-stability-grep --staged` は、変更セットについて `check_error` を報告します。そのファイルを飛ばすことはしません。古いコンパニオンの検査の履歴読み取りは、最初の文の例外です。そこでは git は制御文字を含む名前を引用符付きの形式で出力し、UTF-8 でないバイトは置換文字として読まれるため、この検査はそのような名前のフォルダーを照合できません。

古いコンパニオンの検査は、リポジトリの最上位にある `AGENTS.md` だけを正典として扱います。独自の README を持つサブフォルダーで実行すると、そのサブフォルダーの `AGENTS.md` はフォルダーごとのコンパニオンになります。サブフォルダーが、サブモジュールや入れ子のクローンのように独自のリポジトリの最上位である場合、その `AGENTS.md` は代わりにそのリポジトリの正典になります。リポジトリ全体での実行は、テストフィクスチャや入れ子のリポジトリなど、サブフォルダー自体で実行すれば検査される一部のサブフォルダーを飛ばします。README のないサブフォルダーは、このように独立したフォルダーとしては検査されません。その上のフォルダーで検査を実行してください。コミットで削除されて再び書かれたコンパニオンは、コミットするまで新しいものとして数えられます。

6 つのバリデーターは、リポジトリのルートから開始し、チェック対象のファイルをツリー全体から
探します。

```text
agents-md-coverage-grep
agnosticism-grep
dynamism-grep
freshness-token-grep
plain-language-grep
reference-token-grep
```

これらは、ワークツリー、サブモジュール、入れ子のクローンなど、入れ子になった git チェック
アウト（`.git` ファイルまたはフォルダーがリポジトリを保持または指しているフォルダー。
単なる `.git` ファイルや空の `.git` フォルダーは、そのフォルダーを隠しません）をスキップし、
リンクされたフォルダーには決して入らず、`node_modules`、`venv`、`dist` など、依存関係、
仮想環境、キャッシュ、ビルド出力を保持するディレクトリもスキップします。`no-global-plans-grep` の迷子プランの
チェックも、入れ子のチェックアウトで止まります。入れ子のチェックアウトとして飛ばしたフォルダーは、
その `.git` エントリが何を指していても、すべてレポートの `skipped_checkouts` に一覧されます。
`gitdir:` 行が 1 行あれば、git はどのフォルダーでも飛ばすためです。この一覧が判定を変えることはなく、
こうして飛ばしたフォルダーは検査されません。`node_modules` のように名前で飛ばすフォルダーは一覧されません。これらのいずれかの実行は、指定された
チェックアウトについてのみ報告し、それ以外については何も報告しません。`src/apothem/` の下を
読む `naming-grep` のように、1 つの固定フォルダーを読むバリデーターは、そのフォルダーの下の
すべてを読みます。

`--all-perwrite` は、`git ls-files` がルートの下に一覧にするファイルを検査します。git は各エントリをリポジトリのインデックスが保持するとおりに一覧にし、プロジェクトには他の人が作ったインデックスとファイルが含まれることがあります。そのため、ゲートは一覧にされたパスを、それがルート内の通常ファイルで、64 MiB 以下で、UTF-8 テキストを保持している場合にだけ読みます。それ以外の一覧にされたパスは、理由ごとに `files_skipped` に数えます。

- `outside_project`: `../notes.md`、`a//b.md`、`/` で始まる名前のように、空、`.`、`..` の
  部分を持つエントリ、または Windows で `.git` を指す部分を持つエントリ。大文字と小文字を問わない
  `.git`、その後にドット、空白、コロンが続くもの、そして `GIT~1` です。git はこれらのそれぞれを
  すべてのシステムでデフォルトで拒否するため、実行は合格しません。
- `unsupported_name`: Windows で、システムが書かれたとおりに保持できない名前。コロンを含むもの
  （`a:b.md` では `a:` がドライブとして読まれます）、バックスラッシュ、`<>"|?*` のいずれか、
  制御文字を含むもの、または末尾がドットか空白の部分を持つものです。そして Windows が別のものとして
  読む名前。`CON`、`NUL`、`COM1` のように単独で使われたデバイス名や、`GIT~2` のような短い名前です。
  Linux や macOS の git はそのような名前を追跡できるため、実行を失敗させずに数えられます。
  `C:/x` や `..\..\x` のような手書きのエントリも、Windows ではここに入ります。
- `link`: ルートより下のどの階層にあるシンボリックリンク、または Windows ではジャンクション
  （ルートの内側を指すものも含みます）、あるいはインデックスがリンクとして記録しているエントリ
  （マージ競合のどのステージでも同じなので、そのようなファイルは競合が解決されるまで読まれません）。
  git はリンクをそのリンク先のパスとして保存し、リンクが指す追跡対象ファイルは、それ自身のパスで
  検査されます。
- `submodule`: サブモジュールのエントリ。
- `not_regular_file`: フォルダー、名前付きパイプ、デバイスなど、通常ファイルではないその他のもの。
  読み取りが待ち続けたり、終わらなかったりするためです。
- `missing`: 作業ツリーにない追跡対象ファイル。Windows では、git が UTF-8 でないバイトで一覧にした
  名前（別のシステムで作られたインデックスだけが保持します。Git for Windows はそのようなファイルを
  別の名前で書き込むため、その内容は検査されません）と、長いパスが有効になっていないときに
  システムが許す長さを超えるパスも含みます。
- `unreadable`: システムがゲートに確認、オープン、読み取りを許さないファイル、またはそこへ至る途中の
  フォルダー。権限がない、別のプログラムがファイルやその一部を保持している、またはシステムがそれを
  開けない（同期プログラムが停止しているオンライン専用ファイルなど）という理由によります。別の
  プログラムがファイル全体を保持している場合、ゲートは 0.2 秒待ってもう一度だけ試みます。Windows では
  共有を許さずにファイルを開いているプログラム、それ以外では Samba の oplock や NFS の delegation の
  ように解除中の書き込みリースが対象です。その中の指摘が見落とされることになるため、実行は合格
  しません。ファイルに問題がないのにこうして実行が失敗するケースがいくつかあります。0.2 秒より長く
  かかるリースの解除、削除待ちのファイル、そして `\\wsl$` 共有上のプロジェクトにある名前付きパイプ
  （各読み取りがまず約 10 秒待ちます）です。
- `too_large`: 64 MiB を超え、最初の 64 MiB が UTF-8 テキストであるファイル、またはゲートが読んで
  いる間に 64 MiB を超えて大きくなったファイル。同じ理由で、実行は合格しません。
- `not_utf8_text`: バイト列が UTF-8 テキストではないファイル。バイトオーダーマーク付きの UTF-16
  ファイルなどです。64 MiB を超える場合は最初の 64 MiB で判定します。最初の 8000 バイトの 4 分の 1
  以上が NUL であるファイルはバイナリとみなされ（ゼロで埋められた大きな画像や、バイトオーダーマークの
  ない、ほぼラテン文字のテキストからなる UTF-16 ファイルなど）、実行を失敗させません。テキスト中の
  少数の NUL バイトは数に入りません。
- `exempt`: 設計上検査から除外されるファイル。画像やアーカイブのように接尾辞でバイナリとわかる
  ファイルと、ルート内の任意の深さにある `.apothem/plans`、`tests/conformity`、`tests/fixtures`、
  `_vendor`、`node_modules` フォルダーの下にあるすべてのものです。`outside_project` と
  `unsupported_name` の確認が先に行われるため、どの除外もそれらを隠しません。

`outside_project`、`unreadable`、`too_large` のために実行が合格しない場合、`files_not_passed` は、それぞれの理由の原因となったエントリを、git が一覧にしたとおりの形で並べ替えて、理由ごとに最大 10 件示します。`files_skipped` には全件数があります。標準エラーにもそれらの理由と件数を示す行が出力されるため、標準エラーだけを表示する CI ログでも、実行が失敗した理由がわかります。

各ファイルの階層は読み取りの直前に確認され、開いたファイルはその確認で見つかったものでなければなりません。その間に別のプログラムが別のファイル、リンク、名前付きパイプへ差し替えたファイルはもう一度調べられ、再び差し替えられた場合は `unreadable` として数えられます。差し替えられたシンボリックリンク、または Windows ではジャンクションは、2 回目の確認で `link` として見つかります。ゲートが名前付きパイプで待ったり、ファイルの代わりに置かれたリンクを通して読んだりすることは決してありません。Windows では、データ重複除去（Data Deduplication）やクラウド同期プログラムが再解析ポイントの背後に保持するファイルは、通常どおりそのプログラムを通じて読まれます。そのプログラムが停止している場合、そのファイルは `unreadable` になります。

ファイルはルートから 1 階層ずつ開かれ、どの階層もリンクを通して開かれることはありません。そのため、確認とオープンの間に別のプログラムがファイルの上のフォルダーをリンクに差し替えても、それをたどることはありません。そのファイルは `link` として数えられます。

これらの確認では見えないことが 2 つあります。ハードリンクは通常のファイルとして読まれるため、別の場所のファイルへのハードリンクは読まれます。git がハードリンクを作ることはありません。また Windows では、ファイルの再解析タグもファイル ID も返さないものの、シンボリックリンクは保持できるネットワークファイルシステムでは、確認とオープンの間にファイルがリンクに差し替えられても、ゲートがそれに気付かない可能性があります。

この実行では、`link-check` マッチャーはルートの内側でだけリンク先を調べます。ルートの外へ出る相対リンクは外部として数えられ、`site/content/docs` フォルダーの探索はルートで止まります。どのモードでも、ネットワーク共有（`\\host\share`）、ドライブ（`C:/notes.md`）、`file:` アドレスのように、それ自体で場所を指すリンクを調べることは決してありません。Windows では、共有を調べるとそのホストにあなたのサインイン情報が送られるためです。Windows ではまた、Windows がドライブとして読むコロンを含む `/docs/` ルートのセグメントと、末尾がドットまたは空白の部分を通してしか見つからないリンクも、検査せずに残します。Windows はその末尾を落とすことがあり（`ci.yml.` で `ci.yml` が見つかります）、見つかったことが何の証明にもならないためです。そのようなリンクで何も見つからないものは、通常どおりリンク切れとして報告されます。すべてのシステムで、`/docs/../x` のように `.` や `..` のセグメントを持つ `/docs/` ルートは外部として数えられ、調べられません。

各 `git ls-files` の呼び出しには 60 秒が与えられます。この実行が行う呼び出しと、`no-global-plans-grep` の呼び出しです。後者のレポートは、その場合同じ `check_error` を含んで失敗します。そこで git 自体が失敗した場合、そのメッセージが示すのは git の終了コードであり、git 自身のテキストではありません。名前付きパイプを指す `include.path` のように、リポジトリ自身の設定が git を待たせる場合でも、これらの各呼び出しが止められるのは最大でその時間までです。これは Windows でも同様で、そこでは制限が Git のランチャーが起動した git も停止します。ファイルを 1 つも読まなかった `--all-perwrite` の実行は合格せず、`files_scanned: 0` と `empty_scope_expected: false` を報告します。追跡対象ファイルの一覧を読めない場合、`check_error` は固定の理由を示します。git が起動しなかった、`git ls-files` が特定の終了コードで失敗した、または時間内に完了しなかった、のいずれかです。たとえばルートが git の作業ツリー内にない場合に git 自身のメッセージを見るには、ルートで `git ls-files` を実行してください。レポートはそのメッセージを含めません。プロジェクト外のファイルを示すことがあるためです。`--strict` を指定すると、合格しなかった実行は `2` で終了します。

## 対象を絞ったチェック

```bash
# List every registered validator
PYTHONPATH=src python -m apothem.conformity.gate --list

# Run one per-write validator against one file
PYTHONPATH=src python -m apothem.conformity.gate --check multi-surface-coherence src/apothem/rules/my-rule.md

# Run one standalone validator over a root directory
PYTHONPATH=src python -m apothem.conformity.gate --check naming-grep .

# Run every per-write validator against one file
PYTHONPATH=src python -m apothem.conformity.gate src/apothem/rules/my-rule.md
```

書き込みごとのバリデーターは、チェック対象のファイルを受け取るか、`--stdin` で標準入力から
内容を読み取ります。どちらも指定しない場合は標準入力からの入力を待つため、ターミナルから
実行するときはファイルを渡してください。スタンドアロンバリデーターは、ルートディレクトリを
受け取ります（省略した場合はカレントディレクトリ）。`--list` は、各バリデーターがどちらの
グループに属するかを示します。

`--hook` モード（`<python> -E -s .../conformity/gate.py --hook`。`<python>` はインストールが
見つけたインタープリターです）は、ハーネスからディスパッチされるエントリーポイントです。標準入力から
ツール入力の JSON ペイロードを読み取り、保留中の書き込みに対して、書き込みごとのマッチャーチェーンを
実行します。これはデプロイされた `PreToolUse` フックが呼び出す形式であり、手動で呼び出すことは
ほとんどありません。

フックモードは**一連のディレクトリにスコープされます**。マッチャーチェーンは、ターゲットが
それらのいずれかの配下にある書き込みに対してのみ実行されます。どのスコープにも含まれない
書き込みは短絡され、無言で合格となります。デフォルトは次の 2 つのルートです。

```text
~/.claude      Claude Code
$CODEX_HOME    Codex (~/.codex when CODEX_HOME is not set)
```

それらを置き換えるには、`APOTHEM_CONFORMITY_SCOPE` にディレクトリを設定します。

```bash
# Run the per-write matcher chain against one project tree instead
export APOTHEM_CONFORMITY_SCOPE=/path/to/project
```

何もしていないように見えるフックは、通常は失敗ではなくスコープの不一致です。まず、書き込みの
ターゲットを上記のスコープと照らし合わせて確認してください。

## CI 統合

`.github/workflows/ci.yml` の品質ジョブは、`main` へのプッシュ時と、`main` へのプルリクエストのうちそのジョブが監視するパスに触れるものに対して、ゲートを strict モード（`python -m apothem.conformity.gate --all . --strict`）で実行します。別のワークフロー `.github/workflows/conformity.yml` は、フィクスチャのスイープ（`tests/conformity-scenarios/verify.py --strict`）を実行します。
