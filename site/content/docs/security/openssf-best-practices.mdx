The [OpenSSF Best Practices badge](https://www.bestpractices.dev/) (formerly the CII Best Practices badge) is a self-assessment: a project answers a fixed list of criteria on bestpractices.dev, and the site awards the passing badge when every answer meets the rule for its level. OpenSSF Scorecard's CII-Best-Practices check reads the result, so this page also backs that row on the [Scorecard posture](/docs/security/openssf-scorecard-target) page.

This page lists the answers to keep in Apothem's entry on bestpractices.dev: every passing-level criterion, the answer Apothem gives, a one-line justification, and the file or page that shows it. Every answer here has the same Met, N/A or Unmet status as the entry. Some justifications and evidence links here are newer than the entry's, and these are the ones to copy into it the next time the entry is edited. The criteria were taken from the [live passing criteria](https://www.bestpractices.dev/en/criteria/0) and the [criteria source](https://github.com/ossf/best-practices-badge/blob/main/criteria/criteria.yml) on 2026-11-07 and checked again on 2026-11-27: 67 criteria, of which 43 are MUST, 10 are SHOULD and 14 are SUGGESTED.

Apothem is registered on bestpractices.dev as [project 16427](https://www.bestpractices.dev/en/projects/16427) and has held the passing badge since 2026-11-08. The entry also counts 13% of the silver criteria as met. The answers below cover every passing criterion:

The passing badge needs every MUST criterion Met, every SHOULD criterion Met or Unmet with a reason, and every SUGGESTED criterion answered Met or Unmet. An N/A answer counts as Met, and only criteria that allow it take one; the one N/A among the SUGGESTED criteria, `dynamic_analysis_unsafe`, is one of them. With these answers the project holds the passing badge.

One MUST answer changes with the next release. `release_notes_vulns` is N/A today, because no published release has yet fixed a publicly known run-time vulnerability; earlier releases' notes name the build-tool and docs-site advisories they took. Once the next release and its three advisories are published, that answer becomes Met and the MUST row reads 40 Met, 3 N/A, 0 Unmet.

Three MUST answers rest on facts only the maintainer can confirm, and they are marked "maintainer confirms" in the tables: `vulnerability_report_response` (no report arrived by email in the last 6 months) and `know_secure_design` and `know_common_errors` (the developers' own knowledge). They count in the table above as the answer shown. The one Unmet SHOULD criterion, `crypto_weaknesses`, carries its reason in the table and in [Remaining gaps](#remaining-gaps).

| `crypto_keylength` | MUST | Met | The software generates no keys. Every release tag published so far is signed over a SHA-512 digest (OpenPGP digest algorithm 10, as `gpg --list-packets` shows for the tag's signature); the signer's GnuPG settings choose that digest, not the key. The installers' checks also rely on 160-bit SHA-1 hashes: Git's object IDs, which on a clone install reach every checked-out file, and the OpenPGP v4 fingerprint that pins the maintainer key. Git's object format and the OpenPGP key format set those sizes, not a setting in Apothem; the `crypto_weaknesses` answer covers this reliance, since that criterion names SHA-1. | [src/apothem/lib/propagation.py](https://github.com/ahmed-g-gad/apothem/blob/main/src/apothem/lib/propagation.py) |
| `crypto_working` | MUST | Met | No default mechanism uses a broken algorithm such as MD4, MD5, single DES or RC4, and the code uses no cipher modes. Apothem's own hashing is SHA-256, except that install.ps1 and update.ps1 recompute the git object ID of each committed `.gitattributes` file they read, which is SHA-1 in this repository. The installers' checks also rely on SHA-1, in Git's object IDs (on a clone install, for every checked-out file) and in the maintainer key's OpenPGP v4 fingerprint; the criteria name SHA-1, under `crypto_weaknesses`, as an algorithm with known serious weaknesses, not among the broken algorithms listed here. | [src/apothem/audit/build_inventory.py](https://github.com/ahmed-g-gad/apothem/blob/main/src/apothem/audit/build_inventory.py) |
| `crypto_weaknesses` | SHOULD | Unmet | Apothem's own hashing is SHA-256, except that install.ps1 and update.ps1 recompute the SHA-1 git object ID of each committed `.gitattributes` file they read, and the checks in its one-shot installers and update scripts still rest on SHA-1. By default, every network install through the installers and every update of an existing clone through the update scripts checks a maintainer-signed git tag, which names its commit by a SHA-1 object ID (the repository uses Git's SHA-1 object format), and the scripts pin the maintainer key by its OpenPGP v4 fingerprint, which is also a SHA-1 hash. With cosign installed and no existing Apothem clone, the installed files rest on SHA-256: cosign checks the Sigstore signature on the release SHA256SUMS and that its certificate was issued to a run on the tag's commit, and the installer then checks the archive's SHA-256. The link from the signed tag to that commit still rests on SHA-1; the collision detection in Git's default build lowers that risk but does not remove it. The npm shim and the plugin and extension channels run no signature or digest check of their own. | [scripts/installer/install.sh](https://github.com/ahmed-g-gad/apothem/blob/main/scripts/installer/install.sh) |

| `crypto_password_storage` | MUST | N/A | Apothem is a local configuration CLI that does not authenticate external users and does not store passwords. | [README.md](https://github.com/ahmed-g-gad/apothem/blob/main/README.md) |

## Remaining gaps

These items are not blockers for the passing badge, and they need more than a statement in a repository file:

- **`crypto_weaknesses` (SHOULD, Unmet).** The signed tag that the one-shot installers and the update scripts check names the release commit by a SHA-1 object ID, because the repository uses Git's SHA-1 object format, and the scripts pin the maintainer key by its OpenPGP v4 fingerprint, a SHA-1 hash; forging that pin would take a SHA-1 second preimage, not a collision. An install without cosign, and every install or update over an existing Apothem clone, installs a checkout of that commit, where every installed file rests on SHA-1. With cosign installed and no existing Apothem clone, the installed files rest on SHA-256 (the signed `SHA256SUMS`, checked by cosign against the tag's commit, and the archive digest), but the link from the maintainer's signed tag to that commit still rests on SHA-1. The gap stays open because the scripts check no maintainer-signed SHA-256 digest when they install a checkout, and the repository still uses Git's SHA-1 object format. Meeting the criterion needs a SHA-256 digest that the maintainer signs, checked on every default path, or a repository in Git's SHA-256 object format on a host that offers one, together with a way to pin the maintainer key that does not rest on SHA-1.
- **README badge.** Registration gave the project ID 16427, and the passing badge is not yet in the README header. Add `[![OpenSSF Best Practices](https://www.bestpractices.dev/projects/16427/badge)](https://www.bestpractices.dev/projects/16427)` next to the Scorecard badge. It is a third-party registry badge, so the change also adds its row to the per-badge table on the [Badge policy](/docs/governance/badge-policy) page.
