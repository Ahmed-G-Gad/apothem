The [OpenSSF Best Practices badge](https://www.bestpractices.dev/) (formerly the CII Best Practices badge) is a self-assessment: a project answers a fixed list of criteria on bestpractices.dev, and the site awards the passing badge when every answer meets the rule for its level. OpenSSF Scorecard's CII-Best-Practices check reads the result, so this page also backs that row on the [Scorecard posture](/docs/security/openssf-scorecard-target) page.

This page is the answer sheet. It lists every passing-level criterion, the answer Apothem gives, a one-line justification, and the file or page that shows it. The criteria were taken from the [live passing criteria](https://www.bestpractices.dev/en/criteria/0) and the [criteria source](https://github.com/coreinfrastructure/best-practices-badge/blob/main/criteria/criteria.yml) on 2026-11-07: 67 criteria, of which 43 are MUST, 10 are SHOULD and 14 are SUGGESTED.

## Status

Apothem is not yet registered on bestpractices.dev, so it has no badge yet. The answers below cover every passing criterion:

| Level | Met | N/A | Unmet |
|---|---|---|---|
| MUST (43) | 39 | 4 | 0 |
| SHOULD (10) | 8 | 1 | 1 |
| SUGGESTED (14) | 13 | 1 | 0 |

The passing badge needs every MUST criterion Met, every SHOULD criterion Met or Unmet with a reason, and every SUGGESTED criterion answered Met or Unmet. An N/A answer counts as Met, and only criteria that allow it take one; the one N/A among the SUGGESTED criteria, `dynamic_analysis_unsafe`, is one of them. With these answers the project qualifies.

Three MUST answers depend on facts only the maintainer can confirm, and they are marked "maintainer confirms" in the tables: `vulnerability_report_response` (no report arrived by email) and `know_secure_design` and `know_common_errors` (the developers' own knowledge). They count in the table above as the answer shown. The one Unmet SHOULD criterion, `crypto_weaknesses`, carries its reason in the table and in [Remaining gaps](#remaining-gaps).

## Register the project

Registration is done by the maintainer in one sitting:

1. Sign in at [bestpractices.dev](https://www.bestpractices.dev/en/login) with the GitHub account that owns the repository.
2. Choose **Get Your Badge Now!** and enter the repository URL, `https://github.com/ahmed-g-gad/apothem`. The site fills in some answers on its own; check each one against the tables below.
3. Work through the six sections (Basics, Change Control, Reporting, Quality, Security, Analysis). For each criterion, choose the answer in the **Answer** column, paste the **Justification**, and add the **Evidence** link. Eight Met answers must carry a URL in the justification text: `contribution`, `contribution_requirements`, `license_location`, `release_notes`, `report_process`, `report_archive`, `vulnerability_report_process` and `vulnerability_report_private`. Their justifications below already include it.
4. Before answering `vulnerability_report_response`, confirm that no vulnerability report reached the email address in SECURITY.md in the last 6 months. If one did, answer Met and give the time to the first response, which must be 14 days or less.
5. Answer `know_secure_design` and `know_common_errors` only after confirming they describe the maintainer's own knowledge; the site asks about the people who develop the project, and the linked files are the supporting evidence.
6. Save each section. When the site shows 100% for the passing level, copy the badge Markdown it offers and add the badge to the README header next to the Scorecard badge, with its row in the [Badge policy](/docs/governance/badge-policy) table.

Scorecard reads the badge level through the bestpractices.dev API on its next run. Its CII-Best-Practices check scores a registered project that is still in progress at 2, a passing badge at 5, silver at 7 and gold at 10; gold needs more than one developer.

### Security: Use basic good cryptographic practices

| Criterion | Level | Answer | Justification | Evidence |
|---|---|---|---|---|
| `crypto_published` | MUST | Met | The only cryptography the software relies on is published, expert-reviewed algorithms and protocols: SHA-256 through Python's hashlib, Sigstore signatures on the release SHA256SUMS checked by cosign in the installers, OpenPGP Ed25519 tag signatures checked by git verify-tag, SHA-1 in Git's object IDs (which link a signed tag to its commit and, on a clone install, to every checked-out file) and in the OpenPGP v4 fingerprint that pins the maintainer key, SHA-256 release checksums, and TLS made by curl, git, cosign, pip, npm, Invoke-WebRequest or Python's urllib. | [scripts/installer/install.sh](https://github.com/ahmed-g-gad/apothem/blob/main/scripts/installer/install.sh) |
| `crypto_call` | SHOULD | Met | Apothem implements no cryptographic primitive itself; it calls Python's hashlib, cosign, git with GnuPG, and sha256sum/shasum or Get-FileHash, and leaves TLS to curl, git, cosign, pip, npm, Invoke-WebRequest and Python's urllib. | [scripts/installer/install.sh](https://github.com/ahmed-g-gad/apothem/blob/main/scripts/installer/install.sh) |
| `crypto_floss` | MUST | Met | Every function that depends on cryptography can be built from FLOSS: CPython's hashlib and ssl modules with OpenSSL, git with GnuPG, coreutils sha256sum or Perl's shasum, curl, and Sigstore cosign for release signing and for checking release signatures. | `crypto_keylength` | MUST | Met | The software generates no keys. Every digest Apothem's own code computes is SHA-256 (256 bits, above the 224-bit minimum), the release tags it verifies are signed with an Ed25519 key over SHA-512 digests, and the Sigstore signatures cosign checks on SHA256SUMS use ECDSA P-256 (both above the 224-bit elliptic-curve minimum). The installers' checks also rely on 160-bit SHA-1 hashes: Git's object IDs, which on a clone install reach every checked-out file, and the OpenPGP v4 fingerprint that pins the maintainer key. Git's object format and the OpenPGP key format set those sizes, not a setting in Apothem; the `crypto_weaknesses` answer covers this reliance, since that criterion names SHA-1. | [src/apothem/lib/propagation.py](https://github.com/ahmed-g-gad/apothem/blob/main/src/apothem/lib/propagation.py) |
| `crypto_working` | MUST | Met | No default mechanism uses a broken algorithm such as MD4, MD5, single DES or RC4, and the code uses no cipher modes. Apothem's own hashing is SHA-256. The installers' checks also rely on SHA-1, in Git's object IDs (on a clone install, for every checked-out file) and in the maintainer key's OpenPGP v4 fingerprint; the criteria name SHA-1, under `crypto_weaknesses`, as an algorithm with known serious weaknesses, not among the broken algorithms listed here. | [src/apothem/audit/build_inventory.py](https://github.com/ahmed-g-gad/apothem/blob/main/src/apothem/audit/build_inventory.py) |
| `crypto_weaknesses` | SHOULD | Unmet | Apothem's own hashing is SHA-256, but the checks in its one-shot installers and update scripts still rest on SHA-1. Every default network install through the installers, and every run of the update scripts, checks a maintainer-signed git tag, which names its commit by a SHA-1 object ID (the repository uses Git's SHA-1 object format), and the scripts pin the maintainer key by its OpenPGP v4 fingerprint, which is also a SHA-1 hash. The npm shim and the plugin and extension channels run no signature or digest check of their own. | [scripts/installer/install.sh](https://github.com/ahmed-g-gad/apothem/blob/main/scripts/installer/install.sh) |
| `crypto_pfs` | SHOULD | N/A | Apothem implements no key agreement protocol; curl, git, cosign, pip, npm, Invoke-WebRequest and Python's urllib make its TLS connections, each through the TLS library it is built with or the operating system's. | [src/apothem/audit/check_links.py](https://github.com/ahmed-g-gad/apothem/blob/main/src/apothem/audit/check_links.py) |

| `crypto_random` | MUST | N/A | The software generates no cryptographic keys or nonces; it does not import random or secrets, and release signing uses short-lived Sigstore keys created by cosign in CI. | [.github/workflows/release.yml](https://github.com/ahmed-g-gad/apothem/blob/main/.github/workflows/release.yml) |

### Security: Secured delivery against man-in-the-middle (MITM) attacks

| Criterion | Level | Answer | Justification | Evidence |
|---|---|---|---|---|
| `delivery_mitm` | MUST | Met | Every delivery channel uses HTTPS (the GitHub repo and Releases, npm, the Marketplace, and apothem.ahmedgad.com, which redirects http to https with a 301). Release artifacts carry cosign signatures, and the sdist, wheel, SBOM and VS Code package also carry SLSA provenance. The installers check the release tag's GPG signature against the pinned maintainer key and confirm that the signed tag is the one named for the release. When cosign is installed and the install folder is not already an Apothem git clone, they also check the cosign signature on SHA256SUMS from a run on that tag's commit. | [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md) |

SHA256SUMS comes from the same release as the archive, so a match only shows the download isn't damaged; anyone who can change the release's files can change both. An existing clone is fetched and its tag is checked before the clone is checked out. | [scripts/installer/install.sh](https://github.com/ahmed-g-gad/apothem/blob/main/scripts/installer/install.sh) |

## Remaining gaps

These items are not blockers for the passing badge, and they need more than a statement in a repository file:

- **`crypto_weaknesses` (SHOULD, Unmet).** The signed tag that the one-shot installers and the update scripts check names the release commit by a SHA-1 object ID, because the repository uses Git's SHA-1 object format, and the scripts pin the maintainer key by its OpenPGP v4 fingerprint, a SHA-1 hash; forging that pin would take a SHA-1 second preimage, not a collision. An install without cosign or over an existing Apothem clone, and every run of the update scripts, installs a checkout of that commit, where every installed file rests on SHA-1. With cosign installed and no existing Apothem clone, the installed files rest on SHA-256 (the signed `SHA256SUMS`, checked by cosign against the tag's commit, and the archive digest), but the link from the maintainer's signed tag to that commit still rests on SHA-1. The gap stays open because the scripts check no maintainer-signed SHA-256 digest when they install a checkout, and the repository still uses Git's SHA-1 object format. Meeting the criterion needs a SHA-256 digest that the maintainer signs, checked on every default path, or a repository in Git's SHA-256 object format on a host that offers one, together with a way to pin the maintainer key that does not rest on SHA-1.
- **README badge.** The badge itself can be added to the README only after registration gives the project its bestpractices.dev ID. It is a third-party registry badge, so the change also adds its row to the per-badge table on the [Badge policy](/docs/governance/badge-policy) page.
