Apothem's security posture is built on five pillars: supply-chain hardening, vulnerability response, branch protection, release signing, and continuous security analysis. This section documents each surface.

## Threat model

Apothem is a configuration materializer. It reads a shared profile and writes
harness-native configuration files into the directories each
harness reads. That single function bounds what it trusts and what it does not.

- **What Apothem trusts.** The shared profile you author and the bundled source
  tree placed by the installer. The profile is your declared intent; the engine
  treats it as authoritative input after schema validation.
- **What Apothem does not trust.** Profile contents reach the filesystem only
  after validation: schema failures, unknown harness IDs, unsafe project paths,
  missing manifest sources, target traversal, and symlink crossings all stop
  before any write and return structured diagnostics with `files_written: []`.
  The exceptions are the links dotfile managers make at `~/.config`, or at or
  above a shared skill, rule or template folder, which are followed while they
  lead somewhere inside your home directory. On Windows a junction counts as a
  link.
- **What materialized output never carries.** No secrets. Profile diagnostics
  redact secret-like keys and token-shaped values before they reach plain
  output, JSON, logs, docs snippets, or tests, and public examples use fake
  placeholder identities and domains. Materialized configuration is meant to be
  committed and shared; it carries no credentials.
- **The universal-deny floor.** The Claude Code `settings.json` that Apothem materializes carries a
  non-negotiable deny floor regardless of any per-harness allow-list; on other harnesses the same floor is policy text in the materialized rules, not a settings-level deny list — secrets
  paths (`.env*`, `~/.ssh/**`, credential stores), destructive shell operations
  (`rm -rf`, `sudo`, force-pushes to protected branches), and execution of
  untrusted input. No allow-list silently widens this floor.
- **Blast radius.** Writes are scoped to the harness directories and the
  Apothem-owned support subtrees. Existing managed targets are backed up before
  replacement and shared discovery directories are merged child-by-child, so
  unrelated operator-authored files remain in place.

## Runtime safety posture

Harness lifecycle and profile-write commands validate before writing. Profile
schema failures, unknown harness IDs, unsafe project paths, missing manifest
sources, target traversal, and symlink crossings stop before filesystem writes
and return structured diagnostics with `files_written: []`. A Windows junction
counts as a symlink. The exceptions are a link at `~/.config`, or at or above a
shared skill, rule or template folder, that stays inside your home directory,
and a home folder that is itself a link. A link never takes a write to a tool's
folder in your home directory, or to the profile, out of your home directory
unless you name the folder outside it yourself, through `XDG_CONFIG_HOME` or
`CODEX_HOME` spelled as a path outside your home directory, or through
`--profile PATH` spelled the same way for the profile. Such a spelled path is
followed wherever its links lead. A project folder follows its own rule, below.
The link rule holds for install, update, uninstall, `apothem rollback` and the
`apothem profile` commands, including `profile set` and `profile init --force`
over an existing profile, and for the profile that `install --clean` writes
back. `install --clean` stops before it backs up or removes anything when
`~/.config` is a link that leads out of your home directory, and it removes a
target that is itself a link as a link, without entering it. On Windows a
junction at or inside a tool's folder therefore stops the install, also when it
leads somewhere inside your home directory; replace it with the folder itself.

The folder you name with `--project` is followed wherever it leads, and so
are the links above it. That holds when the folder is itself a link,
`~/.config` among them, and when the link leads out of your home directory,
because you named that folder. A link inside the project folder, on a path the
install writes there, stops the install. That holds also when the link leads
back into the project folder, and when `--project` names your home directory.
A tool that also writes in your home directory, such as in `~/.config/apothem`,
checks those paths by the home rules above. So a `~/.config` link that leads
out of your home directory stops that tool's install even when `--project`
names `~/.config`.

`XDG_CONFIG_HOME` and `CODEX_HOME` can come from a project's `.envrc` or a
script you source, not only from your shell profile. When either names a
folder outside your home directory, Apothem changes files there, because that
is the folder it names.

Apothem's own folder, `~/.apothem`, is not checked this way. It holds the
backups, the install ledger and their lock files; when it is a link, every
command that writes there follows it wherever it leads, and `apothem backups
prune` and the automatic backup retention delete old backup sets at the far
end of that link.

Install and update operations preserve existing managed targets by backing them
up before replacement. Shared discovery directories are merged child-by-child so
unrelated operator-authored files remain in place. `--dry-run` performs the
same validation and reports planned outcomes without creating directories or
files.

Profile diagnostics redact secret-like keys and token-shaped values before
they reach plain output, JSON output, logs, docs snippets, or tests. Public
examples use fake placeholder identities and domains.

## Supply-chain release evidence

Each GitHub Release carries this evidence. Which files it covers differs per
item:

- **Sigstore signatures** via [`sigstore/cosign-installer`](https://github.com/sigstore/cosign-installer)
  for every distributed file: the sdist, the wheel, the VS Code package
  `apothem.vsix`, the SBOM `sbom.cdx.json`, the three platform archives and
  `SHA256SUMS`. Each has its own `<file>.cosign.bundle`. The provenance file
  `provenance.intoto.jsonl` has no cosign bundle; the SLSA generator signs it
  inside its own DSSE envelope.
- **SLSA-3 build provenance** via [`slsa-framework/slsa-github-generator`](https://github.com/slsa-framework/slsa-github-generator)
  in `provenance.intoto.jsonl` for four files: the sdist, the wheel,
  `apothem.vsix` and `sbom.cdx.json`. The release workflow also asks GitHub
  to keep its own build-provenance record of the same files, a separate
  record from this file; that step does not gate the release, so a release
  can lack it. The
  platform archives and `SHA256SUMS` have no SLSA provenance; their cosign
  signatures and the signed release tag cover them.
- **CycloneDX SBOM** of the shipped wheel and sdist, written by `scripts/release/generate_sbom.py`: the apothem package, every package vendored under `apothem/_vendor` with its license, the declared runtime requirements, and each distribution's SHA-256. The SBOM is signed and covered by the build provenance like the distributions
- **npm provenance statements** via Trusted Publishing OIDC on `@ahmed-g-gad/apothem`
- **GPG-signed git tags** (EDDSA key `70396FED9C634163`)

## Verify a release

Download every asset of a release into an empty directory, then check the
signatures and the build provenance. Replace `vX.Y.Z` and `X.Y.Z` with the
release you downloaded.

```bash
gh release download vX.Y.Z --repo ahmed-g-gad/apothem
cosign verify-blob \
  --bundle apothem-X.Y.Z-py3-none-any.whl.cosign.bundle \
  --certificate-identity https://github.com/Ahmed-G-Gad/apothem/.github/workflows/release.yml@refs/tags/vX.Y.Z \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  apothem-X.Y.Z-py3-none-any.whl
slsa-verifier verify-artifact \
  --provenance-path provenance.intoto.jsonl \
  --source-uri github.com/Ahmed-G-Gad/apothem \
  --source-tag vX.Y.Z \
  apothem-X.Y.Z-py3-none-any.whl apothem-X.Y.Z.tar.gz
```

`cosign` prints `Verified OK` and `slsa-verifier` prints `PASSED: SLSA
verification passed`. Repeat the `cosign` command for any other asset with its
`<asset>.cosign.bundle` (earlier releases name the platform-archive and
`SHA256SUMS` bundles `<asset>.sig`). The darwin and linux archives are the same
bytes under two names, so `SHA256SUMS` lists one digest twice. From a clone,
`bash scripts/release/verify-provenance.sh --require-all <download-dir>`
runs the three checks in one pass: the `SHA256SUMS` manifest, every cosign
bundle, and the SLSA provenance of the wheel, the sdist, `apothem.vsix` and the
signed SBOM. It skips a check whose tool (`cosign`, `slsa-verifier`) or file
(`SHA256SUMS`) is missing, and its last line names the checks that ran and the
ones it skipped. Only `chain OK (3 of 3 layers verified: ...)` means the
release is verified; a line that starts `partial check` does not. With
`--require-all` (`-RequireAll` for `verify-provenance.ps1`) a partial check
exits 1; without it, a partial check exits 0.

Two details decide whether verification means anything:

- **Owner casing.** Identity checks are case-sensitive, and the certificates
  carry the owner as GitHub reports it: `Ahmed-G-Gad`. A lowercase owner fails
  both tools.
- **Exact identity.** Prefer `--certificate-identity` with the full subject
  above. To accept any release tag, anchor the pattern at both ends:

  ```bash
  --certificate-identity-regexp '^https://github\.com/Ahmed-G-Gad/apothem/\.github/workflows/release\.yml@refs/tags/v[0-9]+\.[0-9]+\.[0-9]+$'
  ```

  An unanchored pattern such as `github.com/Ahmed-G-Gad/apothem` also matches
  a forged subject that only contains that text, for example a workflow in
  another repository on a branch named after this one.

The [release-cycle runbook](/docs/runbooks/release-cycle) records the same
commands as the maintainer's post-release check.

### Rebuild a release and compare

The wheel and sdist are reproducible: rebuilding the tag with the release
toolchain gives the published SHA-256 digests. Use Python 3.12 on Linux, as
the release does:

```bash
git clone https://github.com/ahmed-g-gad/apothem && cd apothem
git checkout vX.Y.Z
python3.12 -m venv .build && . .build/bin/activate
pip install --require-hashes -r scripts/release/requirements-build-linux.txt
export SOURCE_DATE_EPOCH="$(git log -1 --pretty=%ct)"
python -m build --no-isolation
python scripts/release/normalize_sdist.py dist/*.tar.gz
sha256sum dist/*
```

Compare the digests with the published wheel and sdist. The build uses the
hash-locked setuptools that `pyproject.toml` pins, and `normalize_sdist.py`
removes the build time, file owners and checkout timestamps from the sdist.
