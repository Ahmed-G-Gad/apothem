# Контракт упаковки когорт

Этот документ задаёт стабильный контракт для упаковки когорт и манифестов
плагинов, предназначенный для внешних потребителей. Потребитель читает этот
контракт, чтобы перечислить когорты и разрешить их нативные цели по окружениям
**без повторного выведения сопоставления**.

## Артефакты

| Артефакт | Роль |
| -------- | ---- |
| `src/apothem/schemas/cohort.schema.json` | JSON Schema для документа манифеста когорт. |
| `src/apothem/schemas/cohort-manifest.yaml` | Экземпляр манифеста когорт — все шесть когорт (`core`, `developer`, `security`, `research`, `ai-engineering`, `full`), заполненные своими наборами участников; `full` — объединение остальных пяти. |
| `src/apothem/schemas/plugin.schema.json` | JSON Schema для манифеста плагина отдельного пакета (`plugin.json`). |
| `src/apothem/lib/propagation-manifest.yaml` | **Источник истины** для нативных целей по окружениям. |

## Форма манифеста когорт

Манифест когорт — это объект верхнего уровня с тремя ключами:

- `version` — строка SemVer манифеста.
- `cohorts[]` — одна запись на когорту. Каждая запись содержит `id` (из
  закрытого набора `core | developer | security | research | ai-engineering | full`),
  `name`, `description` и `members` (объект, группирующий идентификаторы
  участников по типу каталога: `skills` / `agents` / `commands` / `rules` / `hooks`).
- `per_harness_targets` — контракт разрешения (см. ниже).

Каждый идентификатор участника — это стабильное имя в kebab-case, которое
соответствует реальному артефакту под `src/apothem/` (`skills/<name>/`,
`agents/<name>.md`, `commands/<name>.md`, `rules/<name>.md` или запись хука —
либо исполняемый `hooks/<name>.py`, либо рекомендательный контекст сообщения в
`hooks/messages/<name>.md`, доставляемый через диспетчер).

## Перечисление когорт

Потребитель загружает `cohort-manifest.yaml`, проверяет его по
`cohort.schema.json`, затем перебирает `cohorts[]`. Для каждой когорты он читает
`members.<type>`, чтобы получить идентификаторы участников каждого типа каталога.

## Разрешение нативных целей по окружениям (без повторного выведения)

Манифест когорт **не** повторяет сопоставление окружений. Вместо этого
`per_harness_targets.source` указывает на `lib/propagation-manifest.yaml` —
единственный источник истины. Правило разрешения:

> Для участника когорты с типом каталога `T` (одним из `skills`, `agents`,
> `commands`, `rules`, `hooks`) и целевого окружения `H` (одного из
> перечисленных в `per_harness_targets.harnesses`) нативная цель плагина — это
> поле `target` той записи в `lib/propagation-manifest.yaml` под
> `harnesses.H.install`, чей `source` совпадает с `T/`.

Например, навык когорты `core`, устанавливаемый для `claude_code`, разрешается
через запись `harnesses.claude_code.install` с `source: "skills/"` в
`target: "${HARNESS_ROOT}/skills/"`. Тот же навык для `opencode` разрешается в
`${HARNESS_ROOT}/skills/`; для `gemini_cli` — в `${PROJECT_ROOT}/.gemini/skills/`.
Потребители никогда не выдумывают цели окружений — они их ищут.

Заполнители `${HARNESS_ROOT}` / `${PROJECT_ROOT}` разрешаются во время установки
каждым адаптером окружения; потребители когорт используют разрешённый `target`
дословно.

## Роль манифеста плагина

`plugin.schema.json` описывает `plugin.json` — самоописывающий пакет участников
каталога (`skills` / `commands` / `agents` / `hooks` / `rules`) с обязательными
`name`, `version` в формате SemVer и `description`. Необязательные метаданные
охватывают `displayName` (имя, показываемое вместо `name`) и поля для листинга
в каталоге плагинов: `documentationUrl`, `supportUrl`, `privacyPolicyUrl` и
`termsOfServiceUrl`, каждое из которых является URL с `https://`, а также путь
`icon` внутри плагина. Сгенерированный пакет Claude Code задаёт `displayName`,
`documentationUrl` и `supportUrl`. Манифест плагина — это единица, которую
адаптер окружения материализует в свою нативную поверхность плагинов; когорты
выбирают, каких участников несёт плагин, а манифест распространения
разрешает, куда эти участники попадают в каждом окружении.

## Решение об упаковке — один зонтичный пакет, логические когорты

Когорты — это **логический слой выбора** (данный манифест), а не набор отдельных,
независимо устанавливаемых пакетов. Apothem поставляет **один зонтичный пакет**,
несущий полный каталог; манифест когорт позволяет потребителю выбрать
согласованное подмножество, а манифест распространения разрешает, куда попадает
каждый выбранный участник в каждом окружении.

Разделение каталога на отдельные пакеты по когортам (например, по одному пакету
на семейство `developer` / `security` / `research`) **достижимо без
дублирования на уровне репозитория** с помощью задокументированного основной
поверхностью распространения **паттерна символических ссылок мета-плагина**:
один каталог маркетплейса перечисляет несколько плагинов когорт, и каталог
каждого плагина когорты содержит **символические ссылки** на единый общий
каталог-источник, а не копии. Когда когорта устанавливается, окружение
разыменовывает каждую символическую ссылку внутри маркетплейса, копируя
содержимое цели в *кэш* этой когорты, поэтому установленная когорта
самодостаточна, тогда как **репозиторий сохраняет единый источник истины,
связанный символическими ссылками** (связывание вместо избыточности, ровно как
предпочитает дисциплина дедупликации). Прежнее толкование, согласно которому
пакеты когорт «механически дублируют» каталог, смешивало дублирование *кэша во
время установки* (обычную копию каждого плагина, которую делает окружение) с
дублированием в *репозитории*; паттерн символических ссылок избегает последнего.

Apothem сейчас поставляет **один зонтичный пакет**, потому что это самая
простая поверхность распространения, а не потому, что когорты механически
невозможны. Переход к форме с пакетами по когортам — это настоящий
**компромисс между UX и сопровождением**, а не нарушение дедупликации:
выигрыш — более точечный сценарий «установить только это семейство»; затраты —
сопровождение N каталогов символических ссылок когорт и их записей в
маркетплейсе, более крупная поверхность соответствия / тестов / эталонных
снимков и копии кэша во время установки для каждой когорты. Описанный выше
логический слой когорт уже обеспечивает результат *выбора* «установить только
то, что нужно» из единого пакета; *упаковка* по когортам — это следующий шаг,
когда понадобится более точечный UX установки.
