Проверяет установку адаптера окружения.

## Синтаксис

```
apothem verify --harness NAME|all [--profile PATH] [--project PATH]
                [--quiet|-q] [--verbose|-v]
                [--format plain|json] [--json] [--no-color]
```

Вызывает реализацию `verify()` каждого выбранного адаптера. Завершается с кодом
0 только тогда, когда все выбранные адаптеры сообщают, что их управляемые цели
присутствуют и корректны. Без `--profile` проверка **структурная** — каждая
управляемая цель должна присутствовать и быть корректной. С `--profile`
проверка дополнительно требует **соответствия профилю**, поэтому установка,
которая присутствует, но разошлась с профилем, не проходит verify; так команда
отвечает на вопрос «установлен ли ИМЕННО ЭТОТ профиль точно?», а не просто
«существует ли установка?». Окончания строк не учитываются, поэтому файл,
сохранённый с окончаниями CRLF или CR, тоже проходит проверку.
В любом случае файл, в котором Apothem хранит управляемый блок, не проходит
verify, пока содержит маркер BEGIN, который не начинает целого блока, например
маркер, чей маркер END пропал (см.
[Устранение неполадок](/docs/install/troubleshooting#a-file-has-an-apothem-begin-marker-with-no-end-marker)),
два или более целых блока между маркерами Apothem (см.
[Файл содержит два блока между маркерами Apothem](/docs/install/troubleshooting#a-file-holds-two-blocks-between-apothems-markers))
или ни одного целого блока, но пары маркеров, которые Apothem не может отличить
от вашего текста, например свой блок внутри вашего блока кода (см.
[Apothem не может отличить свой блок от вашего текста](/docs/install/troubleshooting#apothem-cannot-tell-its-block-from-your-text)).
Обновление сохраняет такой маркер или оставляет такой файл как есть, поэтому
запуск `apothem update` не устраняет сбой.
Проверяются файлы, в которые установка окружения записывает блок, и файлы,
которые перечисляют её записи об установке со времени последнего завершённого
удаления, включая файл правил в рабочем пространстве OpenClaw, которое
установка больше не использует. Маркер в вашем собственном файле, например в
файле заметок проекта, не приводит к сбою. Без записи об установке `CLAUDE.md`
и документ профиля не проверяются: только запись показывает, что их записала
установка. Проверка verify для OpenClaw всё равно не проходит, не называя
файл, когда файл правил в найденном ею рабочем пространстве не содержит целого
блока или содержит маркер BEGIN, который не начинает ни одного.
Неудавшаяся строка называет каждый такой файл и
говорит, что исправить: строку лишнего маркера с пронумерованными шагами,
которые изменяют эту строку и каждую другую строку маркера BEGIN, кроме той,
что открывает блок Apothem, включая маркер BEGIN, который вы цитируете в коде,
для каждого файла отдельно (примечание также говорит не добавлять вместо этого
маркер END обратно, что оставило бы два блока Apothem, как только установка или
обновление запишет блок Apothem отдельно от него); каждый целый блок по его
строкам; или,
для пар маркеров,
которые Apothem не может отличить от вашего текста, строки каждой пары, где они
находятся и как их исправить, вместе с каждым маркером BEGIN, который не
начинает пару маркеров.
Для файла правил OpenClaw, который обновление записывает, только пока он
укладывается в ограничение OpenClaw на размер одного файла, примечание
говорит, что следующее обновление запишет блок Apothem, если файл тогда
уложится в это ограничение, в которое засчитывается сохраняемый вами старый
текст Apothem (см.
[Open-Claw](/docs/harnesses/open-claw#rules-in-each-workspace)).
В режиме plain за строкой следует строка `Note:`,
и тогда строка не содержит ожидаемого пути, а строка JSON получает объект
`stray_begin` с `files` и `message`.

Для адаптера, который записывает навыки в ваш домашний каталог, verify также
проверяет, что каждая ожидаемая им папка навыка существует и содержит
`SKILL.md`, какая бы установка её ни записала, поэтому машина, на которой
установлен только один из инструментов, разделяющих папку, проходит проверку.
Проверка не проходит, когда папка отсутствует и когда папка с именем навыка
Apothem принадлежит чему-то, что Apothem не записывал. Неудавшаяся строка
сообщает, что именно: в режиме plain за ней следует строка `Note:`, а в строке
JSON объект `user_level` перечисляет пути `missing`, `unlisted` и `unproven` и
содержит `message`. Выполните [`install`](/docs/cli-reference/install), чтобы
восстановить отсутствующую папку; переименуйте или переместите чужую папку,
затем выполните [`update`](/docs/cli-reference/update). Папка
`unproven` — это папка, запись которой Apothem не может доказать. Установки,
которые её перечисляли, находятся в папках, которые пропали, не содержат файлов
Apothem или не читаются, либо они её больше не перечисляют. И она не содержит в
точности те файлы, которые они записали (см.
[`install`](/docs/cli-reference/install)). Вы создали или отредактировали её,
либо более ранний выпуск записал её, не записав её файлы. Примечание называет
каждую такую папку и даёт два пути дальше из предупреждения установки. Чтобы
сохранить её, оставьте её на месте. Чтобы использовать версию Apothem,
перенесите её из папки навыков, затем выполните `update` для этого окружения;
для окружения с областью проекта примечание называет `--project`, заключённый в
кавычки для оболочки так, как это делает doctor, или словами. Папка, которая
уже содержит то, что записывает этот выпуск, никогда не называется, потому что
установка её сохраняет. Verify ищет недоказанные и неперечисленные папки только
для установленного окружения, поэтому `verify --harness all` называет их только
для установленных окружений.

Строка, прошедшая проверку или нет, может сопровождаться примечанием. Когда то,
что записал Apothem, на месте, но ваш файл мешает инструменту загрузить это,
строка `Note:` называет этот файл, а `warnings` конверта JSON получает запись
с `"operation": "instruction_override"` (описано в
[`install`](/docs/cli-reference/install)). Один такой файл — это
`AGENTS.override.md` с текстом рядом с `AGENTS.md`, который
[один из поддерживаемых инструментов](/docs/harnesses/codex#compatibility-notes)
загружает из своей домашней папки. Другие — файлы, которые
[OpenCode 1](/docs/harnesses/opencode#compatibility-notes) загружает из своей
папки конфигурации: `opencode.jsonc` с собственным списком `instructions`, а
также `config.json`, `opencode.json` или `opencode.jsonc`, которые OpenCode 1
вообще не может загрузить. Примечание не приводит к сбою проверки. Примечания
нет, когда блока Apothem нет в этом `AGENTS.md` или когда `opencode.json` не
перечисляет ни одной записи, которую записала установка; для примечания об
`opencode.json`, который OpenCode 1 не может загрузить, нужно лишь, чтобы
документ профиля, который записывает установка, содержал блок Apothem.

Проход с `--harness all` учитывает `exclude_harnesses` профиля — те же
исключения, которые применил пакетный запуск `install`/`update`, — поэтому
verify никогда не сообщает об отсутствии намеренно исключённого окружения.
Исключения берутся из `--profile`, если он указан, иначе — из профиля по
умолчанию; если профиль по умолчанию нечитаем или отсутствует, проверка
откатывается к полному реестру.

## Параметры

| Параметр | Описание |
|---|---|
| `--harness NAME` | Адаптер окружения для проверки или `all` для набора уровня всего реестра (обязателен). |
| `--profile PATH` | YAML общего профиля, на соответствие которому выполняется проверка. Без него проверка чисто структурная. |
| `--project PATH` | Корень проекта для окружений с областью проекта. |
| `--quiet`, `-q` | Подавить информационный вывод; выводятся только ошибки. |
| `--verbose`, `-v` | Выводить дополнительную диагностическую информацию. |
| `--format plain\|json` | Формат вывода (по умолчанию: `plain`). |
| `--json` | Сокращение для `--format json`. |
| `--no-color` | Отключить цветовые коды ANSI в выводе. |
| `-h`, `--help` | Показать справку и завершить работу. |

## Вывод JSON

```json
{
  "schema_version": 1,
  "status": "success",
  "command": "verify",
  "action": "verified",
  "harness": "claude-code",
  "files_written": [],
  "results": [
    {
      "harness": "claude-code",
      "outcome": "unchanged",
      "operation": "verify",
      "path": "C:\\Users\\Example\\.claude\\settings.json",
      "message": "managed targets verified",
      "installed": true,
      "verified": true
    }
  ],
  "warnings": [],
  "error": null,
  "installed": true,
  "verified": true,
  "output_path": "C:\\Users\\Example\\.claude\\settings.json"
}
```

Когда любое выбранное окружение отсутствует или некорректно, `status` равен
`error`, строка результата со сбоем содержит `verified: false`, а процесс
завершается с кодом 1.

## Примеры

```bash
apothem verify --harness claude-code
apothem verify --harness claude-code --json
apothem verify --harness all --project .
```

## Коды выхода

| Код | Значение |
|---|---|
| 0 | Окружение проверено — все управляемые цели присутствуют и корректны |
| 1 | Окружение не прошло проверку — управляемые цели отсутствуют или некорректны |
| 64 | Ошибка использования: неизвестный параметр или команда либо отсутствующее или недопустимое значение параметра. При `--json` ошибка представляет собой конверт JSON с кодом `cli.usage`. |
