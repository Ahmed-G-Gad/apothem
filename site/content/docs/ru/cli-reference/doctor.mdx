Проверяет работоспособность того, что установлено. Если
[`apothem verify`](/docs/cli-reference/verify) проверяет выбранные вами
окружения, то `doctor` за один проход проверяет каждое установленное окружение
и общий профиль.

## Сводка

```
apothem doctor [--project PATH] [--quiet|-q] [--verbose|-v]
               [--format plain|json] [--json] [--no-color]
```

## Что проверяется

- **Общий профиль.** Присутствующий профиль проверяется по поставляемой схеме;
  некорректный профиль не проходит проверку со своим диагностическим кодом. Об
  отсутствующем профиле сообщается, но это не считается сбоем (`install`
  создаёт его).
- **Только установленные окружения.** Неустановленное окружение отображается
  как `not_installed` и не считается сбоем, поэтому машина с одним исправным
  окружением проходит проверку. Окружения с областью проекта проверяются, когда
  `--project` указывает их корень; без него они отображаются как
  `needs_project`. Файл со строками маркеров, которые Apothem не может отличить
  от вашего текста, считается установкой, пока журнал установок невозможно
  прочитать, поэтому такое окружение проверяется, а не отображается как
  `not_installed`. Doctor называет журнал, который не может прочитать, в
  проверке `ledger.unreadable` там, где он читает этот журнал, чтобы запустить
  хуки окружения (см. **Среда выполнения хуков** ниже): для окружения, которое
  проходит проверку, и для окружения, чья проваленная проверка называет файлы с
  маркерами Apothem (`harness.stray_begin`). Её способ исправления предлагает
  переместить повреждённый журнал в сторону и запустить `update`, а для
  журнала, который doctor не может открыть (например, его держит открытым
  другая программа), — сделать этот файл доступным для чтения. Окружение,
  проверка которого проваливается по другой причине, получает проверку
  `harness.verify_failed` и не получает проверки хуков, а значит, и проверки
  `ledger.unreadable`.
- **Проверка установки.** Каждое установленное окружение должно пройти ту же
  проверку, что и [`verify`](/docs/cli-reference/verify). Когда файл содержит
  маркер BEGIN Apothem без маркера END, проваленная проверка — это
  `harness.stray_begin`, и её способ исправления называет каждый такой файл и
  строку маркера, даёт пронумерованные шаги, которые изменяют эту строку и
  каждую другую строку маркера BEGIN, кроме той, что открывает блок Apothem
  (слово, добавленное внутрь каждого комментария), и говорит не добавлять
  вместо этого маркер END обратно: это оставило бы два блока Apothem, как только
  установка или обновление запишет блок Apothem отдельно от него. Одно лишь
  обновление это не исправляет
  (см.
  [Устранение неполадок](/docs/install/troubleshooting#a-file-has-an-apothem-begin-marker-with-no-end-marker)).
  Файл, который содержит два или более целых блока между маркерами Apothem или
  пары маркеров которого Apothem не может отличить от вашего текста (например,
  его блок внутри вашего блока кода), проваливает ту же проверку: её сообщение
  говорит, что в файле есть «Apothem markers to fix by hand», а способ
  исправления называет каждый блок по его строкам (см.
  [Файл содержит два блока между маркерами Apothem](/docs/install/troubleshooting#a-file-holds-two-blocks-between-apothems-markers))
  или каждую пару маркеров, где расположены её строки и как это исправить,
  вместе с каждым маркером BEGIN, который не начинает пару маркеров (см.
  [Apothem не может отличить свой блок от вашего текста](/docs/install/troubleshooting#apothem-cannot-tell-its-block-from-your-text)).
  Для файла правил OpenClaw способ исправления, как и примечание verify,
  говорит, что следующее обновление запишет блок Apothem, если файл тогда
  уложится в ограничение OpenClaw на размер одного файла, в которое
  засчитывается и сохранённый вами старый текст Apothem.
- **Среда выполнения хуков.** Для каждого проверенного окружения и для каждого,
  которое проваливает такой маркер, doctor читает файлы, записанные
  проверяемой им установкой: установкой в собственной папке окружения
  (`CODEX_HOME`, заданная там, где запускается doctor, и есть эта папка) или,
  для окружения с областью проекта, в папке `--project`. Установка в другой
  папке, например в `CODEX_HOME`, на которую doctor не направлен, или в
  проекте, который вы с тех пор удалили, вместо неё не используется. Doctor
  находит команды хуков, которые Apothem зарегистрировал в файлах JSON среди
  них, и один раз запускает каждый интерпретатор и скрипт хука с холостой
  полезной нагрузкой (зарегистрированные аргументы плюс `--help`, `{}` на
  stdin, временный рабочий каталог и удалённая переменная `PYTHONPATH`).
  Ничего не записывается. Отсутствующий интерпретатор, отсутствующий скрипт
  или аварийное завершение во время импорта означают провал проверки. Когда у
  хука есть отдельная командная строка для каждой системы, doctor запускает ту,
  которую инструмент выполняет на этой машине: строку `powershell` или
  `commandWindows` на Windows и строку `bash` на macOS и Linux — для
  инструмента, который читает этот ключ. Для инструмента, который читает только
  `command`, запускается его строка `command`. Doctor читает только те ключи,
  которые читает сам инструмент, и список `args` — только для инструмента,
  который запускает свою команду с ним, поэтому строка или список, хранящиеся
  под другим ключом, не запускаются и не учитываются. Doctor запускает саму
  программу, без оболочки, поэтому на Windows он опускает `&`, с которого
  начинается строка, написанная для PowerShell. Хук, зарегистрированный вне
  файла JSON, не запускается и не учитывается в `N started`. Запись об
  установке находится при любом написании этой папки, например в другом
  регистре букв на Windows. Когда в журнале установок нет записи для этой
  папки, проверка не выполняется: отчёт показывает `not checked`, его
  последняя строка вместо `All checks passed` называет окружения, чьи команды
  хуков не были проверены (для окружения, которое также запустило другие
  команды и они прошли, она говорит «some hook commands»), а вывод JSON
  содержит проверку `hook.unchecked`.
- **Файлы хуков проекта.** Любой, кто может делать коммиты в проект, может
  менять его файлы, поэтому для окружения с областью проекта doctor запускает
  команду хука, только когда известно всё, что она запускает. Он читает запись
  об установке проекта, указанного через `--project`, берёт команды хуков только
  из тех мест, откуда их читает инструмент (не более 100 из одного файла; сверх
  этого одна строка `hook.unchecked` называет файл, а остальные не
  запускаются), и запускает команду, только когда её интерпретатор — тот,
  который записала установка (если только он не находится внутри проекта, где
  его могут изменить другие), или тот Python, под которым работает сам Apothem,
  параметры перед скриптом не выполняют кода (например, `-E` и `-s`), скрипт —
  это скрипт хука, записанный установкой, в папке, файлы которой всё ещё
  совпадают с контрольными суммами SHA-256, записанными установкой, и в которой
  нет ни другого файла Python, ни ссылки, а аргументы после него — те, которые
  записывает Apothem. Затем doctor запускает эти известные пути, а не
  прочитанный им текст, и не ищет никакой другой путь, который называет команда
  хука. Если записанный интерпретатор или скрипт хука пропал, проверка
  проваливается без запуска чего-либо; для отсутствующего скрипта хука способ
  исправления запускает `update`, чтобы вернуть скрипты на место. Никакую другую
  команду хука проекта doctor не запускает и сообщает о каждой, с причиной, как
  о `hook.unchecked` (информация, а не сбой, помеченная `!` в обычном выводе).
  То же относится к команде, известные пути которой doctor не может найти,
  например к команде в папке, которую вы не можете открыть. Записанный
  интерпретатор внутри проекта не запускается, поскольку его могут изменить
  другие, если только сам doctor не работает под ним: способ исправления
  запускает `update` из папки вне проекта с Apothem, который работает под
  Python вне проекта, и тот записывает этот Python. Apothem, установленный в
  собственное окружение проекта, сделать этого не может; используйте
  установленный вне его. Если виртуальное окружение проекта активно, сначала
  деактивируйте его: пока оно активно, его Python стоит первым в `PATH`, и
  команда npx запустится под ним и снова запишет его. Чтобы выбрать Python,
  под которым запускается команда npx, задайте в `APOTHEM_PYTHON` путь к нему.
  Путь, который не является рабочим Python 3.10 или новее, пропускается без
  сообщения, и вместо него просматривается `PATH`, поэтому запустите doctor
  снова, чтобы убедиться, что строка исчезла. Обновление запускается вне
  проекта, потому что `python -m apothem`, запущенный в папке проекта,
  запустил бы закоммиченную там папку с именем `apothem` вместо Apothem. Хуки,
  установленные более ранним релизом, который не записывал интерпретатор или
  контрольные суммы, остаются непроверенными, пока вы не запустите `update` с
  теми же параметрами, с которыми устанавливали.
- **Файлы хуков, которые проверка не читает.** Проверка хуков не читает файлы
  хуков больше 4 МБ и ничего, кроме обычного файла (например, канал или
  устройство). Каждый такой файл получает одну строку `hook.unchecked`, которая
  его называет, — содержит ли он только хуки или это файл настроек, в который
  объединены хуки, и находится ли он в проекте или в вашем домашнем каталоге.
  Обновление сохраняет слишком большой или необычный файл как есть, поэтому
  способ исправления предлагает уменьшить файл до размера меньше 4 МБ или
  заменить его обычным файлом, а затем снова запустить doctor. Файл, из
  которого инструмент не запускает хуки, строки не получает: файл настроек
  инструмента, хуки которого Apothem хранит только в своей папке поддержки,
  или копия, хранящаяся в `.apothem/support`.
  Файл в вашем домашнем каталоге читается через ссылку, поскольку он ваш.
  В проекте проверка не читает файл хуков, к которому ведёт ссылка, например
  папку настроек, заменённую ссылкой на папку вне проекта. Каждый такой файл
  получает строку `hook.unchecked` — содержит ли он только хуки или это файл
  настроек, в который объединены хуки. Строка называет файл и ссылку, которой
  может быть сам файл или одна из его папок. Способ исправления предлагает
  проверить, куда ведёт ссылка: замените созданную вами ссылку настоящей копией
  папки или файла, к которым она ведёт, и проверьте команды хуков в ней, или
  удалите ссылку, которую вы не создавали, и запустите команду `update`, которой
  заканчивается способ исправления. В обоих случаях удаляется только сама
  ссылка, а не папка или файл, к которым она ведёт. Команда хука, к скрипту
  которой ведёт ссылка, не запускается; её строка называет скрипт и ссылку,
  которой может быть сам скрипт или одна из его папок, а способ исправления
  тот же, только проверять команды хуков не нужно. Скрипт хука, записанный
  установкой вне проекта, тоже не запускается, и его строка об этом сообщает.
  Ссылка или файл Python, который не записывала установка, внутри папки
  скрипта хука также оставляют команду незапущенной. Обновление сохраняет и то
  и другое, поэтому способ исправления предлагает удалить элемент, который
  называет строка (для ссылки — только саму ссылку; свои скрипты перенесите в
  другое место), а затем снова запустить doctor. Если ссылка заняла место
  папки, записанной установкой, следующий запуск сообщит, что эта папка
  отсутствует, и запуск `update` вернёт её на место. Папка проекта, которую
  проверка не может открыть, тоже получает строку, и её способ исправления
  предлагает дать вашей учётной записи разрешение её открывать. На Windows, где
  нет способа открыть файл с отказом от ссылки, проверка ссылки выполняется
  непосредственно перед открытием файла. Скрипт хука больше 4 МБ считается
  изменённым после установки, поскольку ни один из записываемых Apothem
  скриптов не бывает такого размера.

Каждая проваленная проверка указывает способ исправления. Способ исправления,
который запускает `update`, заканчивается командой после двоеточия. Для
окружения с областью проекта команда указывает `--project` с папкой, заключённой
в кавычки для оболочки, так же как [`uninstall`](/docs/cli-reference/uninstall)
заключает в кавычки свои шаги. Когда такие кавычки не могут передать папку,
способ исправления описывает `--project` словами и заканчивается папкой как она
есть. Завершается с кодом 0, если ни одна проверка не провалена, и с кодом 1 в
противном случае.

## Вывод JSON

`--json` сохраняет прежние поля (`version`, `python`, `platform`,
`profile_path`, `profile_exists`, `profile_valid`, `harnesses`, `all_ok`,
а также `profile_error`, когда профиль недействителен) и добавляет:

- `profile_error_code` — диагностический код профиля, когда профиль
  недействителен.
- `project` — разрешённый корень `--project` или `null`.
- `harnesses[].status` — `ok`, `not_installed`, `needs_project`,
  `verify_failed`, `hook_failed` или `error`; а также `verified` и `hooks`
  (`{"probed": N, "failed": [...]}` или `null`, когда в проверяемой папке нет
  записи об установке, журнал установок невозможно прочитать или doctor не
  смог завершить проверку команд хуков; проверка `hook.unchecked` сообщает
  причину).
- `checks` — по одной записи на проверку: `code` (например,
  `harness.verify_failed`, `harness.stray_begin`, `hook.start_failed`,
  `hook.unchecked`, `ledger.unreadable` или код
  `profile.*`), `status` (`pass`, `fail` или `info`), `harness`, `message` и
  `fix`.

```json
{
  "schema_version": 1,
  "all_ok": false,
  "checks": [
    {
      "code": "hook.start_failed",
      "status": "fail",
      "harness": "claude-code",
      "message": "claude-code: a registered hook command cannot start: …",
      "fix": "Check that the interpreter in the hook command exists and runs, then …"
    }
  ]
}
```

## Параметры

| Параметр | Описание |
|---|---|
| `--project PATH` | Корень проекта для окружений с областью проекта; без него они отображаются как `needs_project`. |
| `--quiet`, `-q` | Подавляет информационный вывод; выводятся только ошибки. |
| `--verbose`, `-v` | Принимается для единообразия с другими командами; эта команда не выводит дополнительных данных. |
| `--format plain\|json` | Формат вывода (по умолчанию: `plain`). |
| `--json` | Сокращение для `--format json`. |
| `--no-color` | Отключает цветовые коды ANSI в выводе. |
| `-h`, `--help` | Показывает справку и завершает работу. |

## Примеры

```bash
apothem doctor
apothem doctor --project .
apothem doctor --json
```

Формат по умолчанию `plain` выводит диагностику в удобочитаемом виде; `--json`
(эквивалент `--format json`) выводит машиночитаемый документ в stdout,
пригодный для передачи по конвейеру в другие инструменты.

## Коды выхода

| Код | Значение |
|---|---|
| 0 | Все проверки пройдены (в том числе когда ещё не установлено ни одного окружения) |
| 1 | Установленное окружение не проходит проверку, зарегистрированная команда хука не может запуститься, журнал установок невозможно прочитать, адаптер не удалось загрузить или опросить либо присутствующий профиль не прошёл проверку схемы |
| 64 | Ошибка использования: неизвестный параметр или команда либо отсутствующее или недопустимое значение параметра. При `--json` ошибка выводится как конверт JSON с кодом `cli.usage`. |
