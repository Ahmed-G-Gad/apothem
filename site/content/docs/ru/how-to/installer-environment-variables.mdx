Цель: управлять `install.sh` / `install.ps1` без редактирования скрипта, задавая
переменные окружения перед его запуском.

## Предварительные условия

- POSIX-оболочка (`bash`) или PowerShell 5.1+. Приведённые ниже примеры для
  PowerShell запускают `pwsh` (PowerShell 7+). В Windows PowerShell 5.1 вместо
  этого выполните
  `powershell -NoProfile -ExecutionPolicy Bypass -File install.ps1`.
- Переменные читаются один раз в начале установщика, поэтому задайте их в той
  же команде (или сначала экспортируйте их), затем запустите установщик.

## Переменные установщика

| Переменная | Чем управляет | По умолчанию |
| --- | --- | --- |
| `APOTHEM_HOME` | Место установки дерева исходного кода; это должна быть папка, в которую можете писать только вы (см. ниже), и установщики предупреждают, когда в неё или в содержащую её папку могут писать другие | `$HOME/.apothem` |
| `APOTHEM_REPO` | Удалённый Git-репозиторий для клонирования; значение, начинающееся с `-`, отклоняется | `https://github.com/ahmed-g-gad/apothem` |
| `APOTHEM_REF` | Git-ссылка для переключения; если не задана, выбирается последний подписанный тег `vMAJOR.MINOR.PATCH`, значение-тег закрепляет его, `main` выбирает подвижную ветку. Ссылка, которая не является тегом, например `main`, прерывает выполнение, если не задано `APOTHEM_ALLOW_UNVERIFIED=1`. | не задана (последний подписанный тег) |
| `APOTHEM_ALLOW_UNVERIFIED` | При значении `1` понижает неудачную проверку тега на пути клонирования с фатального прерывания до предупреждения и разрешает `APOTHEM_VERIFY=checksum`; путь `release` никогда не понижает её, и никакая настройка не пропускает проверку того, что подписанный тег — именно тот, что назван для релиза, но поскольку она пропускает неподписанный тег или тег, подписанный другим ключом, эта проверка защищает только теги с подписью ключа сопровождающего | `0` (проверка; при сбое — прерывание) |
| `APOTHEM_VERIFY` | `auto` использует `release`, когда `cosign` есть в `PATH`, а `APOTHEM_HOME` не является git-клоном, и `signature` в остальных случаях; `release` устанавливает архив для платформы после того, как тег оказывается подписан ключом сопровождающего, cosign подтверждает, что рабочий процесс релиза подписал `SHA256SUMS` в запуске на коммите тега, а SHA-256 архива совпадает с ним; `signature` проверяет GPG-подпись тега релиза по закреплённому ключу сопровождающего; `checksum` устанавливает архив только после проверки SHA-256 и требует `APOTHEM_ALLOW_UNVERIFIED=1`. Режим контрольных сумм не проверяет релиз. SHA256SUMS берётся из того же релиза, что и архив, поэтому совпадение показывает лишь, что загрузка не повреждена; любой, кто может изменить файлы релиза, может изменить и то и другое. | `auto` |
| `APOTHEM_RELEASE_BASE` | Базовый адрес загрузки для режимов `release` и `checksum` | `<APOTHEM_REPO>/releases/download` |
| `APOTHEM_SOURCE` | Явно заданное локальное дерево исходного кода вместо клонирования | не задана (клонирование) |
| `APOTHEM_HARNESS` | Окружение уровня пользователя для установки (`antigravity`, `claude-code`, `codex`, `hermes`, `open-claw`, `opencode`, `qwen-code`). Установщик не передаёт `--project`, поэтому окружение уровня проекта завершается ошибкой `project.required`; устанавливайте такие окружения после этого командой `apothem install --harness NAME --project PATH`. | `claude-code` |
| `APOTHEM_PROFILE` | Путь к YAML-файлу общего профиля | `$HOME/.config/apothem/profile.yaml` |
| `APOTHEM_SKIP_VERIFY` | При значении `1` пропускает шаг проверки после установки | `0` (проверка выполняется) |
| `APOTHEM_AUTO_INSTALL_DEPS` | При значении `1` автоматически, без запроса, устанавливает недостающие предварительные требования `click` / `rich` | `0` (запрос; в неинтерактивном конвейере — отказ) |
| `APOTHEM_BIN_DIR` | Каталог для размещаемого шима команды `apothem` | `$HOME/.local/bin` (POSIX); `%LOCALAPPDATA%\Microsoft\WindowsApps` (Windows) |
| `NO_COLOR` | Отключает цветной вывод, если задана с любым значением ([no-color.org](https://no-color.org/)); цвет также всегда отключён, когда вывод направлен не в терминал (в конвейер, файл или журнал CI) | не задана (цвет только в интерактивном терминале) |

`APOTHEM_SOURCE` имеет приоритет над клонированием: если переменная указывает
на чекаут, содержащий `src/apothem`, установщик использует его напрямую,
никогда не обращается к `APOTHEM_REPO` / `APOTHEM_REF` и пропускает определение
тега и проверку подписи (ничего не загружается, поэтому проверять нечего).

`APOTHEM_SOURCE` и запуск собственного скрипта установщика из чекаута по его пути (из
любой папки) — единственные два способа использовать локальное дерево. Однострочник
через конвейер (`curl
... | sh`, `irm ... | iex`) никогда его не использует: он игнорирует текущую папку и
её родительские папки, а загружает и проверяет релиз. Установщики,
скрипты обновления и удаления, шимы `apothem`, лаунчер npm, хуки и
процессы валидаторов шлюза соответствия не допускают текущую папку в путь поиска
модулей Python. Команда `python -m apothem`, которую вы набираете сами, этого не делает:
`-m` сначала читает модули из текущей папки.

Пустые и относительные записи в вашем собственном `PYTHONPATH` не передаются
движку ни одним лаунчером (установщиками, скриптами обновления и удаления, шимами
`apothem` для POSIX и Windows и лаунчером npm). Сохраняемая запись должна быть полным
путём: в Windows — путь с буквой диска, например `C:\lib`, или сетевой путь, в
остальных системах — путь, начинающийся с `/`. Путь от корня `\lib` или путь
относительно диска `C:lib` отбрасывается. Скрипты sh спрашивают у Python, который они
запускают, какую форму он читает, и шим `apothem`, который они записывают, сохраняет эту
форму. Python для Windows (обычный под Git Bash) получает пути движка в форме
Windows, соединённые через `;`, и сохраняет только пути с буквой диска и сетевые пути
вашего `PYTHONPATH`. Python для POSIX, включая собственный `python3` Cygwin и MSYS2,
получает пути POSIX, соединённые через `:`, и сохраняет только записи, начинающиеся с
`/`. Команды `git` установщиков, которые не работают с клоном, не читают
репозиторий в текущей папке.

Эти команды `git` запускаются из пустой временной папки, которую установщик
создаёт для запуска, поэтому относительный путь в переменной окружения git
(`GIT_SSH`, `GIT_ASKPASS` и подобных) больше не указывает туда, куда указывал
раньше. Используйте в этих переменных абсолютный путь. Относительный `APOTHEM_REPO`,
который называет папку или файл (например, git bundle), по-прежнему разрешается
относительно папки, из которой вы начали.

Установщики игнорируют переменные окружения git, которые перенаправляют git
(`GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE` и подобные), и останавливаются,
когда `APOTHEM_REPO` начинается с `-`, чтобы значение нельзя было прочитать как
параметр git.

Установщики и скрипты обновления также очищают `GIT_CONFIG`, `GIT_CONFIG_GLOBAL` и
`GIT_CONFIG_SYSTEM`, чтобы значение, унаследованное из вашего окружения, не могло
направить git на другой файл конфигурации, а также `GIT_ATTR_SOURCE`, из-за которой
git читал бы атрибуты из другого дерева, чем рабочее дерево и индекс, которые читают
проверки (`attr.tree` в вашей собственной конфигурации по той же причине
опустошается в каждой команде git, выполняемой на клоне, как и `core.attributesFile`,
поэтому git не читает ни файл атрибутов, который она называет, ни
`~/.config/git/attributes`, макросы которого могли бы назвать фильтр, не видимый
проверкам). Если вы задали одну из них, установщик её игнорирует;
скрипты PowerShell восстанавливают её по окончании запуска, поэтому запуск
`irm ... | iex` оставляет ваш сеанс таким, каким он был. `GIT_CONFIG_NOSYSTEM`
остаётся таким, как вы его задали: он лишь запрещает git читать системную
конфигурацию. git по-прежнему читает вашу собственную глобальную конфигурацию
(`~/.gitconfig` или `$XDG_CONFIG_HOME/git/config`) и системную конфигурацию из
обычных мест, а `git`, `gpg` и `cosign` — это программы, которые находит ваш
`PATH`. Установщики доверяют им в найденном виде, а значит, доверяют и этой
конфигурации.

Установщики и скрипты обновления также задают четыре переменные git на весь запуск.
`GIT_NO_REPLACE_OBJECTS=1` не даёт git подменить объект другим
через replace-ссылки. `GIT_NO_LAZY_FETCH=1` не даёт git самостоятельно загружать
недостающий объект с удалённого репозитория, пока он читает клон.
`GIT_ALLOW_PROTOCOL=file:git:http:https:ssh` разрешает только эти пять транспортов
для каждой команды git в запуске, поэтому значение в вашем окружении не может
расширить список, а адрес не может заставить git запустить вспомогательную
программу, например `ext::`.
`APOTHEM_REPO` должен использовать один из них; локальный путь считается `file`.
`GIT_ATTR_NOSYSTEM=1` не даёт git читать системный файл атрибутов, макросы которого
могли бы назвать фильтр. Скрипты PowerShell восстанавливают все четыре в прежнем
виде по окончании запуска. Они
также читают вывод git как UTF-8 на время запуска, какой бы ни была кодовая страница
вашей консоли, и восстанавливают настройку консоли по окончании запуска.

`APOTHEM_HOME` должна быть папкой, в которую можете писать только вы. Любой, кто
может писать в неё, может изменить код, который запускает команда `apothem`. В
Windows папку, созданную в корне диска, например `C:\apothem`, при стандартных
разрешениях Windows может изменить каждый пользователь, который входит на этот
компьютер. Держите её в своей пользовательской папке, как и по умолчанию. Скрипты
установки и обновления, включая пробные запуски, предупреждают, не останавливаясь,
когда другие пользователи могут писать в `APOTHEM_HOME` или в содержащую её папку
либо владеют одной из них; установка из локального чекаута и обновление с заданной
`APOTHEM_SOURCE` пропускают эту проверку. В
Windows предупреждение выдают `install.ps1` и `update.ps1`: `install.sh` и
`update.sh` не выполняют проверку под Git Bash, MSYS2 или Cygwin;
[Устранение неполадок](/docs/install/troubleshooting#the-installer-warns-other-users-can-change-apothem_home)
показывает, как это исправить.

Каждый запуск скриптов установки, обновления и удаления удерживает блокировку,
`<APOTHEM_HOME>.lock`, на весь запуск; второй запуск на той же
`APOTHEM_HOME` останавливается. Когда `APOTHEM_HOME` — символическая ссылка (или, в
Windows, соединение (junction)), скрипты POSIX и PowerShell берут блокировку рядом
с папкой, на которую она ведёт. Принудительное завершение или отключение питания
может оставить папки рядом с `APOTHEM_HOME`, и следующая загружаемая установка
называет их и останавливается, ничего не изменив; см.
[Устранение неполадок](/docs/install/troubleshooting).

Когда `APOTHEM_HOME` указывает на существующий каталог, происходящее зависит от
того, что в нём находится.

- Git-клон обновляется через fetch в режиме `auto` или `signature`; сначала
  проверяется новый тег, и только затем клон переключается. Неудачная проверка
  оставляет клон без изменений, а изменения в отслеживаемых файлах не теряются, а
  останавливают обновление с сообщением зафиксировать их или убрать в stash. Со
  ссылкой, не являющейся релизом, например `main`, клон следует копии этой ветки в
  origin. Файл `.git` (связанное рабочее дерево) считается клоном. `release` и
  `checksum` отклоняют клон без `--yes`, а с `--yes` всё равно отклоняют его, пока
  клон содержит локальную работу (изменения, stash, неотправленные коммиты или
  неотслеживаемые файлы в его дереве исходного кода), в том числе при пробном
  запуске. Когда `--yes` всё же заменяет клон, собственное дерево клона
  перемещается в новую папку,
  `<APOTHEM_HOME>.before-apothem-<time>`, под своим именем, а не удаляется. Перед
  fetch обновление на месте останавливается, когда файлы помечены как
  assume-unchanged или skip-worktree, когда рабочее дерево клона не является
  `APOTHEM_HOME`, когда клон содержит подмодуль или git-репозиторий, который git
  не отслеживает (вне собственных папок данных движка, например
  `backups`), когда `.git/info/attributes` называет фильтр или драйвер
  diff, когда клон заимствует объекты из другого репозитория, когда файл
  `.gitattributes` в рабочем дереве не отслеживается, отличается от
  зафиксированной копии, называет такой драйвер или имеет зафиксированную копию,
  которую git не может прочитать, когда файлы в `src` не отслеживаются или когда
  `.git/config` или `.git/config.worktree` клона содержит настройку, отличную от
  тех, что `git clone` и `git init` записывают туда для полного клона, настроек
  веток (`remote` и `pushremote` ветки должны быть `origin`), `user.name`,
  `user.email`, `maintenance.auto`, `maintenance.strategy`, `pull.rebase` и
  `pull.ff`
  ([Устранение неполадок](/docs/install/troubleshooting#the-installer-stops-the-existing-clone-is-set-up-in-a-way-the-update-would-trust)
  перечисляет их); git-хуки клона никогда не запускаются во время обновления. После
  переключения обновление удаляет папки кэша Python (`__pycache__`) в
  `src`, прежде чем движок запустится из клона. Учитывается только клон
  исходного кода Apothem: клон чего-либо другого обрабатывается как папка,
  не содержащая установки Apothem.
- Более ранняя установка из архива релиза обновляется повторным запуском в режиме
  `auto` с cosign (или `release`, или `checksum`).
- Папка, не содержащая установки Apothem, отклоняется: переместите её в сторону,
  направьте `APOTHEM_HOME` в другое место или передайте `--yes` (`-Yes` в Windows).
  С `--yes` установщик перемещает всю папку без изменений в новую папку,
  `<APOTHEM_HOME>.before-apothem-<time>`, и выполняет установку заново.
- Устаревший пустой каталог или каталог, содержащий только собственные данные
  движка (`backups`, `state`, `plans`, `memory`, `contexts`, `learning`,
  `providers`), обновляется без флага, и эти данные сохраняются.
- Символическая ссылка (в Windows — символическая ссылка или соединение (junction))
  отклоняется всякий раз, когда установка заменила бы её: направьте `APOTHEM_HOME`
  на папку, на которую ведёт ссылка. Существующий git-клон за ссылкой обновляется
  на месте.
- В Linux и macOS файл или папка для переноса, имя которых содержит пробел или
  другой специальный символ, останавливает установку: сначала переместите их из
  `APOTHEM_HOME`.

Для заменяемой установки Apothem новый исходный код проверяется в промежуточной
папке рядом с `APOTHEM_HOME` и подставляется только после прохождения всех проверок.
Всё в старой установке, что не входит в её дерево исходного кода, включая
резервные копии движка, журналы установок, планы и память, сохраняется. Если шаг
завершается сбоем или запуск прерывается нажатием Ctrl+C или сигналом завершения,
прежняя установка восстанавливается без изменений; принудительное завершение или
отключение питания может оставить папки рядом с
`APOTHEM_HOME`, о которых сообщит следующая загружаемая установка. `--dry-run` (`-DryRun` в
Windows) выполняет свои проверки во временной папке и оставляет `APOTHEM_HOME`
без изменений. Он выполняет те же проверки, что и реальный запуск, за исключением
того, что не выполняет fetch в существующий клон и поэтому не проверяет его на
изменения в отслеживаемых файлах, что реальное обновление делает после fetch.

## Модель доверия

Если `APOTHEM_REF` не задана, установщик определяет последний релиз и проверяет
его до материализации какой-либо конфигурации. Он всегда проверяет тег релиза с
помощью `git verify-tag` и требует, чтобы подпись была сделана ключом
сопровождающего, опубликованным в SECURITY.md; неподписанный или подделанный тег,
или тег, подписанный любым другим ключом, прерывает установку, как и подписанный
объект тега, который не является тем, что назван для релиза (подписанный тег
другого релиза, перенаправленный на это имя). Если `cosign` есть в `PATH`, затем
он устанавливает архив релиза, как только cosign подтвердит, что рабочий процесс
релиза подписал `SHA256SUMS`, и с помощью своей проверки
`--certificate-github-workflow-sha` — что проверенный им сертификат был выдан
запуску на коммите тега, а SHA-256 архива совпадает с ним. Этому пути нужны `gpg`
и cosign. Для существующего git-клона установщик загружает и проверяет тег, прежде
чем переключить клон, поэтому неудачная проверка оставляет клон как был.
Если открытый ключ сопровождающего, которым подписан тег, отсутствует в
локальной связке ключей, установка вместо этого прерывается с инструкциями по
импорту ключа — импортируйте ключ и сверьте его отпечаток со значением,
опубликованным в
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md).
Закрепите известный релиз с помощью `APOTHEM_REF=<tag>`, взяв тег со
[страницы релизов](https://github.com/ahmed-g-gad/apothem/releases);
закреплённый тег проверяется так же. Выберите подвижную ветку с помощью
`APOTHEM_REF=main` вместе с `APOTHEM_ALLOW_UNVERIFIED=1`; такая установка не
проверяется, а `main` без этой переменной прерывает установку, потому что ветка
не является подписанным тегом. Задайте `APOTHEM_ALLOW_UNVERIFIED=1`, чтобы
продолжить после неудачной проверки тега с предупреждением (для изолированной от
сети среды, локального использования или использования до появления
подписанного релиза). Это относится только к пути клонирования и никогда к пути
cosign, поэтому на машине с cosign задайте вместе с ней
`APOTHEM_VERIFY=signature`.

```bash title="Pinned, verified install"
APOTHEM_REF=vMAJOR.MINOR.PATCH bash install.sh
```

```bash title="Require the tag check and the cosign check"
APOTHEM_VERIFY=release bash install.sh
```

Режим контрольных сумм не проверяет релиз. SHA256SUMS берётся из того же
релиза, что и архив, поэтому совпадение показывает лишь, что загрузка не
повреждена; любой, кто может изменить файлы релиза, может изменить и то и
другое. Установщик запускает его, только если также задана
`APOTHEM_ALLOW_UNVERIFIED=1`.

```bash title="Check the archive digest alone (no cosign, no gpg; does not verify the release)"
APOTHEM_VERIFY=checksum APOTHEM_ALLOW_UNVERIFIED=1 bash install.sh
```

```bash title="Proceed past a failed tag check (interim / air-gapped)"
APOTHEM_VERIFY=signature APOTHEM_ALLOW_UNVERIFIED=1 bash install.sh
```

## Шаги (POSIX bash)

1. Установите окружение уровня пользователя, отличное от окружения по умолчанию:

   ```bash
   APOTHEM_HARNESS=codex bash install.sh
   ```

2. Закрепите место установки и выберите подвижную ветку `main`. Ветка не
   является подписанным тегом, поэтому установщику также нужен
   `APOTHEM_ALLOW_UNVERIFIED=1`:

   ```bash
   APOTHEM_REF=main APOTHEM_ALLOW_UNVERIFIED=1 APOTHEM_HOME="$HOME/tools/apothem" bash install.sh
   ```

3. Используйте локальный чекаут и собственный профиль, пропустив проверку:

   ```bash
   APOTHEM_SOURCE=/work/apothem \
   APOTHEM_PROFILE=/work/profile.yaml \
   APOTHEM_SKIP_VERIFY=1 \
   bash install.sh
   ```

## Шаги (PowerShell)

Задайте каждую переменную через `$env:` перед запуском установщика:

```powershell
$env:APOTHEM_HARNESS = 'codex'
pwsh -NoProfile -File install.ps1
```

```powershell
$env:APOTHEM_ALLOW_UNVERIFIED = '1'
$env:APOTHEM_REF = 'main'
$env:APOTHEM_HOME = "$HOME\tools\apothem"
pwsh -NoProfile -File install.ps1
```

```powershell
$env:APOTHEM_SOURCE = 'C:\work\apothem'
$env:APOTHEM_PROFILE = 'C:\work\profile.yaml'
$env:APOTHEM_SKIP_VERIFY = '1'
pwsh -NoProfile -File install.ps1
```

## Проверка

Установщик выводит `✓ Harness <name> installed`, затем (если не задано
`APOTHEM_SKIP_VERIFY=1`) `✓ verify passed`. Подтвердите это независимо:

```bash
apothem verify --harness codex
```

Для окружения уровня проекта, например Cursor, выполните установку и проверку
самостоятельно после установщика, с `--project`:

```bash
apothem install --harness cursor --project /path/to/project
apothem verify --harness cursor --project /path/to/project
```

Если профиля ещё не было, установщик создаёт его из примера и продолжает
установку и проверку в том же запуске. Поля идентичности в примере —
заполнители, поэтому установка выводит примечание. Пример также содержит
образцы правил, два образца серверов MCP и переопределения для отдельных
окружений, и окружение, которое берёт серверы MCP из профиля, например OpenCode,
получает оба сервера. Отредактируйте `$APOTHEM_PROFILE`, удалив то, что вам не
нужно, затем выполните `apothem update --harness <name>`, чтобы применить его. `--dry-run` без профиля выполняет предварительный
просмотр с подставленным примером и ничего не записывает.
