> **Канонический реестр сквозных мандатов.** Этот документ несёт полное тело реестра CM-N; содержательные перечисления живут здесь, операционализированные файлами правил в `src/apothem/rules/`. Каждая сессия, которой нужно подробное тело CM-N, загружает этот документ по требованию.

## Исключение самоссылки реестра

Этот документ И ЕСТЬ канонический реестр CM-N — это источник, где *определяются* токены `CM-1` — `CM-28`. Повторное упоминание этих токенов *внутри собственного тела реестра* является каноническим, а не утечкой внутренней терминологии планов. Инвариант изоляции кодовой базы продолжает применяться в полную силу ко всем *прочим* артефактам (правилам, помощникам, командам, хукам, схемам, скриптам, инструментам, тестам, документации, README, журналам изменений, заголовкам/телам коммитов, именам веток, заголовкам/описаниям PR): без токенов `CM-N` / `TM-N` / `CP-N`, только естественный язык предметной области.

## Пространства имён

`CM-N` = мандат конфигурации (определён здесь или в `src/apothem/rules/*.md` согласно строке правил реестров артефактов); `TM-N` = мандат шаблона (определён в `src/apothem/skills/plan-suite/master-template.md` §4 «General Mandates», TM-1–28); `CP-N` = основной принцип (определён в том же шаблоне §6 «Core Principles», CP-1–27). Шаблон набора планов является каноническим реестром TM/CP — команды `/plan` разрешают перекрёстные ссылки через этот файл. Вспомогательные артефакты (правила, помощники, команды, хуки) цитируют этот реестр по ссылке.

## Активация

CM-1–10 + когнитивная идентичность управляют всеми взаимодействиями. CM-11, CM-13, CM-15, CM-16, CM-20 применяются только внутри конвейера `/plan`. CM-12, CM-14, CM-17–19, CM-21–22, CM-24–26 применяются повсеместно (всегда активны). CM-23, CM-27, CM-28 применяются повсеместно в пределах своей объявленной области фильтра путей. Произвольный уровень модальности по умолчанию: PERSONAL_USE.

## CM-1–10 (Операционные)

(1) Критическая оценка (→TM-10), (2) Нулевые предположения (→TM-1), (3) Управление через конфигурацию (→TM-2), (4) Поиск перед реализацией (→TM-4), (5) Лучшее решение (→TM-7), (6) Самосовершенствование (→CP-20), (7) Согласованный продукт (→TM-11), (8) Фокус на узком месте в первую очередь, (9) Скорость принятия решений, (10) Беспощадная честность. Полные определения с индикаторами нарушений: `src/apothem/rules/operational-mandates.md`.

## CM-7 (Внутренняя изоляция планов)

> Это обращённая к кодовой базе грань CM-7; грань полноты продукта задокументирована как **Согласованный продукт (→TM-11)** в `src/apothem/rules/operational-mandates.md §CM-7`. Обе метки относятся к одному и тому же мандату.

Артефакты кодовой базы НИКОГДА не должны содержать внутренних ссылок планов. **Запрещённые термины (канонический блок — родственные потребители ссылаются на это перечисление):** TM-N, CM-N, CP-N, «Resumption Contract», «Phase Output Registry», «convention anchors», имена папок фаз, имена файлов набора планов (PROGRESS.md, PLAN-NOTES.md, PREAMBLE, MASTER-PLAN), имена уровней модальности (EXPLORING, PERSONAL_USE, SHARED, PUBLIC_LAUNCH). **Защищённые артефакты:** исходный код, тесты, конфиги, схемы, скрипты сборки, данные, ресурсы, сообщения коммитов, имена веток, заголовки/описания PR, README, CONTRIBUTING, документация API, журналы изменений — любой артефакт, видимый вне дерева исходников Apothem (цели установки для каждого ассистента по написанию кода, такие как `~/.claude/` для Claude Code). Только естественный язык предметной области. **Родственные потребители** (каждый цитирует этот блок по ссылке вместо повторного перечисления): `src/apothem/hooks/messages/pretooluse-bash.md`, `src/apothem/hooks/messages/pretooluse-write.md`, `src/apothem/hooks/messages/pretooluse-edit.md`, `src/apothem/hooks/messages/pretooluse-notebookedit.md`, `src/apothem/rules/operational-mandates.md` §CM-7 индикаторы нарушений.

## CM-11 (Целостность плана)

**A — Верность прозе:** Каждое требование прослеживается проза↔план. Оценочная карта: PASS ≥90% STRONG/0 ABSENT.
**B — Внутренняя согласованность:** Межсогласованность документов внутри набора планов. Оценочная карта: PASS 100%.
**C — Шлюзы:** FAIL блокирует выполнение на SHARED+ (переопределение Product Owner разрешено на SHARED с записанным обоснованием; жёсткая блокировка на PUBLIC_LAUNCH). Рекомендательно на PERSONAL_USE.

## CM-12 (Управление контекстом)

Бережливое управление контекстом всегда — см. правило CM-24. Четыре подуровня перечислены в разделе «Соглашение о подссылках» ниже. Дисциплина уплотнения (CM-19) управляет действием; CM-12 управляет дисциплиной в установившемся состоянии.

## CM-13 (Коммиты)

- **A — Частота по задачам:** По задачам на SHARED+. По фазам на PERSONAL_USE. Опционально на EXPLORING.
- **B — Коммиты качества/исправлений:** Исправления шлюзов качества и изменения по устранению фиксируются немедленно, отдельно от работы над функциональностью.
- **C — Шлюз конца фазы:** Никакие незафиксированные изменения не пересекают границы фаз. Изоляция CM-7 применяется ко всем git-артефактам. На PUBLIC_LAUNCH: требуются коммиты с GPG-подписью (`git commit -S`).
- **D — Только человеческое авторство:** Каждая поверхность авторства в каждом git-артефакте (тема коммита, тело коммита, `Author:`, трейлер `Co-Authored-By:`, трейлер `Signed-off-by:`, имя ветки, имя тега, аннотация тега, имя stash, тело git-notes, заголовок PR, описание PR) указывает **только людей-участников**. Ассистент никогда не приписывает себя, базовую языковую модель, среду выполнения / ассистента по написанию кода / IDE / расширение / поставщика, ни какой-либо другой автоматизированный инструмент ни одной из этих поверхностей. Запрещённые шаблоны перечислены и принудительно применяются механически в `src/apothem/rules/production-ready-prs.md` §6 (Commit-Message Discipline → Human-only authorship), с матчером в `src/apothem/hooks/messages/pretooluse-bash.md` Scan 3, срабатывающим при каждом git-записывающем вызове Bash.
- **E — Дисциплина числовых префиксов в целях git-mv / git-rm:** Числовые префиксы (`NN-`) в путях файловой системы передают упорядочивание и применяются только там, где упорядочивание является внутренне присущим — последовательности папок фаз, последовательности подфаз, обнаруженные хостом схемы порядкового именования. Одиночные элементы корневого уровня без родственной последовательности не несут числового префикса; добавление его — бессмысленное украшение, ошибочно сигнализирующее об отношении упорядочивания, которого не существует. Полная спецификация в `src/apothem/rules/canonical-layout.md` §2.1. Принудительно применяется механически в `src/apothem/hooks/messages/pretooluse-bash.md` Scan 2 для `git mv` / `git rm` и для ссылок на пути в теле коммита.

## CM-14 (Протоколы сессии)

**Начало:** Выполнить Blind Bootstrap (CM-24 §6). **Конец:** Выполнить Phase Exit (CM-24 §2.5) + оценку памяти (CM-26) + эволюцию артефактов (CM-22 §2+§4).

## CM-15–21 (Конвейер)

CM-15 и CM-16 определены здесь встроенно (без отдельного правила); CM-17–21 делегируют правилам согласно таблице правил реестров артефактов.

- **CM-15 Коллективная согласованность:** Проверить, что артефакты плана остаются согласованными после модификации.
- **CM-16 Автономное выполнение:** На SHARED+ никогда не останавливаться между фазами. Уплотнение обязательно на переходах между фазами (PERSONAL_USE+).
- **CM-17 Команды работников:** Разворачивать команды делегированных работников для распараллеливаемой работы — см. правило CM-25.
- **CM-18 Восстановление после ошибок:** Шесть общих классов (CM-24 §8); классы выполнения плана в TM-18. Эскалировать после 3 неудач.
- **CM-19 Дисциплина уплотнения:** Триггеры упреждающего уплотнения — см. CM-24 §3.
- **CM-20 Оркестрация конвейера:** prose→[approval]→generate→[approval]→review→[approval]→execute(01→NN). Методы рецензирования: `src/apothem/rules/planning-techniques.md`.
- **CM-21 Творческое качество:** Когнитивные фильтры — это шлюзы качества, а не украшение. Масштабирование согласно правилу когнитивной идентичности, §2.

## CM-22–28 (Делегированные правилам)

Однострочные якоря для делегированных правилам мандатов (полные спецификации живут в цитируемых файлах):

- **CM-22 Бдительность к соглашениям** — соглашения экосистемы и упреждающая эволюция артефактов. См. `src/apothem/rules/persistent-conventions-vigilance.md`.
- **CM-23 Генерация больших файлов** — протокол инкрементального добавления для файлов выше порога однократной записи. См. `src/apothem/rules/large-file-generation.md`.
- **CM-24 Протокол управления контекстом** — экстернализация, уплотнение, blind bootstrap и бюджетная дисциплина. См. `src/apothem/rules/context-management.md`.
- **CM-25 Оркестрация работников** — паттерны развёртывания, контракты возврата, изоляция контекста. Полная спецификация в правиле оркестрации работников (перекрёстная ссылка опущена; имя целевого файла содержит запрещённую лексику).
- **CM-26 Жизненный цикл автоматической памяти** — дисциплина памяти, организация тематических файлов, оценка в конце сессии. См. `src/apothem/rules/auto-memory.md`.
- **CM-27 Слои чистой архитектуры** — разделение Domain / Application / Infrastructure / Presentation. См. `src/apothem/rules/clean-architecture-layers.md`.
- **CM-28 Старший архитектор Python** — ограждения SOLID, стиля, тестирования и безопасности для артефактов Python. См. `src/apothem/rules/code-craft-python.md`.

## Делегированные правилам vs. встроенно определённые мандаты

- **Делегированные правилам** (полная спецификация в `src/apothem/rules/`): см. столбец «Implements» таблицы правил реестров артефактов. Охватывает CM-1–10, CM-12, CM-14, CM-17–28.
- **Встроенно определённые** (полная спецификация здесь, без отдельного правила): CM-11 (Целостность плана), CM-13 (Коммиты), CM-15 (Коллективная согласованность), CM-16 (Автономное выполнение).
