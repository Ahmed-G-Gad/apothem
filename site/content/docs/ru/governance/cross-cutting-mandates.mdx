> **Канонический реестр сквозных мандатов.** Этот документ содержит полный текст реестра CM-N; содержательные перечисления находятся здесь и операционализируются файлами правил в `src/apothem/rules/`. Каждая сессия, которой нужен подробный текст CM-N, загружает этот документ по требованию.

## Исключение для самоссылок реестра

Этот документ И ЕСТЬ канонический реестр CM-N — источник, в котором *определяются* токены от `CM-1` до `CM-28`. Повторение этих токенов *внутри собственного текста реестра* является каноническим, а не утечкой внутренней терминологии планов. Инвариант изоляции кодовой базы по-прежнему применяется в полную силу ко всем *прочим* артефактам (правилам, помощникам, командам, хукам, схемам, скриптам, инструментам, тестам, документации, README, журналам изменений, заголовкам и телам коммитов, именам веток, заголовкам и описаниям PR): никаких токенов `CM-N` / `TM-N` / `CP-N`, только естественный язык предметной области.

## Пространства имён

`CM-N` = мандат конфигурации (определён здесь или в `src/apothem/rules/*.md` согласно таблице правил в `site/content/docs/reference/rules.mdx`); `TM-N` = мандат шаблона (определён в `src/apothem/skills/plan-suite/master-template.md` §4 «General Mandates», TM-1–28); `CP-N` = основной принцип (определён в том же шаблоне, §6 «Core Principles», CP-1–27). Шаблон набора планов является каноническим реестром TM/CP — команды `/plan` разрешают перекрёстные ссылки через этот файл. Вспомогательные артефакты (правила, помощники, команды, хуки) ссылаются на этот реестр.

## Активация

CM-1–10 + когнитивная идентичность управляют всеми взаимодействиями. CM-11, CM-13 (подправила от A до C), CM-15, CM-16, CM-20 применяются только внутри конвейера `/plan`. Подправило D правила CM-13 применяется к каждой записи в git, а подправило E — к целям `git mv` / `git rm` и путям в теле коммита, внутри этого конвейера или вне его. CM-12, CM-14, CM-17–19, CM-21–22, CM-24–26 применяются повсеместно (всегда активны). CM-23, CM-27, CM-28 применяются повсеместно в пределах объявленной для них области фильтра путей. Уровень серьёзности по умолчанию для разовой работы: PERSONAL_USE.

## CM-1–10 (Операционные)

(1) Критическая оценка (→TM-10), (2) Никаких допущений (→TM-1), (3) Управление через конфигурацию (→TM-2), (4) Поиск перед реализацией (→TM-4), (5) Лучшее решение (→TM-7), (6) Самосовершенствование (→CP-20), (7) Целостный продукт (→TM-11), (8) Фокус на узком месте в первую очередь, (9) Скорость принятия решений, (10) Беспощадная честность. Полные определения с признаками нарушений: `src/apothem/rules/operational-mandates.md`.

## CM-7 (Изоляция внутренних сведений плана)

> Это обращённая к кодовой базе грань CM-7; грань полноты продукта задокументирована как **Целостный продукт (→TM-11)** в `src/apothem/rules/operational-mandates.md §CM-7`. Обе метки относятся к одному и тому же мандату.

Артефакты кодовой базы НИКОГДА не должны содержать ссылок на внутренние сведения плана. **Запрещённые термины (канонический блок — родственные потребители ссылаются на это перечисление):** TM-N, CM-N, CP-N, «Resumption Contract», «Phase Output Registry», «convention anchors», имена папок фаз, имена файлов набора планов (PROGRESS.md, PLAN-NOTES.md, PREAMBLE, MASTER-PLAN), названия уровней серьёзности (EXPLORING, PERSONAL_USE, SHARED, PUBLIC_LAUNCH). **Защищённые артефакты:** исходный код, тесты, конфигурации, схемы, скрипты сборки, данные, ресурсы, сообщения коммитов, имена веток, заголовки и описания PR, README, CONTRIBUTING, документация API, журналы изменений — любой артефакт, видимый вне дерева исходного кода Apothem (места установки для каждого окружения, такие как `~/.claude/` для Claude Code). Только естественный язык предметной области. **Родственные потребители** (каждый ссылается на этот блок, а не перечисляет его заново): `src/apothem/hooks/messages/pretooluse-bash.md`, `src/apothem/hooks/messages/pretooluse-write.md`, `src/apothem/hooks/messages/pretooluse-edit.md`, `src/apothem/hooks/messages/pretooluse-notebookedit.md`, `src/apothem/rules/operational-mandates.md` (§CM-7, признаки нарушений).

## CM-11 (Целостность плана)

**A — Верность прозе:** Каждое требование прослеживается по связи проза↔план. Оценочная карта: PASS ≥90% STRONG/0 ABSENT.
**B — Внутренняя согласованность:** Согласованность документов между собой внутри набора планов. Оценочная карта: PASS 100%.
**C — Шлюзы:** FAIL блокирует выполнение на SHARED+ (переопределение владельцем продукта разрешено на SHARED с записанным обоснованием; жёсткая блокировка на PUBLIC_LAUNCH). На PERSONAL_USE — рекомендательно.

## CM-12 (Управление контекстом)

Экономное управление контекстом постоянно — см. правило CM-24. Четыре подуровня перечислены в разделе «Соглашение о подссылках» ниже. Дисциплина сжатия (CM-19) управляет самим актом сжатия; CM-12 управляет дисциплиной в установившемся режиме.

## CM-13 (Коммиты)

- **A — Частота по задачам:** По задачам на SHARED+. По фазам на PERSONAL_USE. Необязательно на EXPLORING.
- **B — Коммиты качества и исправлений:** Исправления по шлюзам качества и изменения по устранению замечаний коммитятся немедленно, отдельно от работы над функциональностью.
- **C — Шлюз конца фазы:** Никакие незакоммиченные изменения не пересекают границы фаз. Изоляция CM-7 применяется ко всем git-артефактам. На PUBLIC_LAUNCH: требуются коммиты с подписью GPG (`git commit -S`).
- **D — Только человеческое авторство:** Каждая поверхность авторства в каждом git-артефакте (тема коммита, тело коммита, `Author:`, трейлер `Co-Authored-By:`, трейлер `Signed-off-by:`, имя ветки, имя тега, аннотация тега, имя stash, тело git-notes, заголовок PR, описание PR) называет **только людей-участников**. Ассистент никогда не указывает ни на одной из этих поверхностей себя, лежащую в его основе языковую модель, среду выполнения / окружение / IDE / расширение / вендора или любой другой автоматизированный инструмент. Запрещённые шаблоны перечислены и механически проверяются в `src/apothem/rules/production-ready-prs.md` §6 (Commit-Message Discipline → Human-only authorship), а сопоставитель в `src/apothem/hooks/messages/pretooluse-bash.md` Scan 3 срабатывает при каждом вызове Bash, выполняющем запись в git.
- **E — Дисциплина числовых префиксов для целей git-mv / git-rm:** Числовые префиксы (`NN-`) в путях файловой системы передают порядок и применяются только там, где порядок присущ по сути, — последовательности папок фаз, последовательности подфаз, схемы порядкового именования, обнаруживаемые хостом. Одиночные элементы корневого уровня, у которых нет родственной последовательности, не несут числового префикса; его добавление — бессмысленное украшение, ложно сигнализирующее о несуществующем отношении порядка. Полная спецификация — в `src/apothem/rules/canonical-layout.md` §2.1. Механически проверяется в `src/apothem/hooks/messages/pretooluse-bash.md` Scan 2 при `git mv` / `git rm` и для ссылок на пути в теле коммита.

## CM-14 (Протоколы сессии)

**Начало:** выполнить Blind Bootstrap (CM-24 §6). **Конец:** выполнить Phase Exit (CM-24 §2.5) + оценку памяти (CM-26) + эволюцию артефактов (CM-22 §2+§4).

## CM-15–21 (Конвейер)

CM-15 и CM-16 определены непосредственно здесь (без отдельного правила); CM-17–21 делегированы правилам согласно таблице правил в `site/content/docs/reference/rules.mdx`. Заголовок группирует эти мандаты по теме; их область действия задаётся абзацем раздела «Активация»: CM-15, CM-16 и CM-20 применяются только внутри конвейера `/plan`, а CM-17–19 и CM-21 применяются повсеместно.

- **CM-15 Коллективная согласованность:** Проверять, что артефакты плана остаются согласованными после изменения.
- **CM-16 Автономное выполнение:** На SHARED+ никогда не останавливаться между фазами. Сжатие обязательно при переходах между фазами (PERSONAL_USE+).
- **CM-17 Команды исполнителей:** Развёртывать команды делегированных исполнителей для распараллеливаемой работы — см. правило CM-25.
- **CM-18 Восстановление после ошибок:** Шесть общих классов (CM-24 §8); классы выполнения плана — в TM-18. Эскалировать после 3 неудач.
- **CM-19 Дисциплина сжатия:** Триггеры упреждающего сжатия — см. CM-24 §3.
- **CM-20 Оркестрация конвейера:** prose→[approval]→generate→[approval]→review→[approval]→execute(01→NN). Методы ревью: `src/apothem/rules/planning-techniques.md`.
- **CM-21 Творческое качество:** Когнитивные фильтры — это шлюзы качества, а не украшение. Масштабирование — согласно правилу когнитивной идентичности, §2.

## CM-22–28 (Делегированные правилам)

Однострочные якоря для мандатов, делегированных правилам (полные спецификации находятся в указанных файлах):

- **CM-22 Бдительность к соглашениям** — соглашения экосистемы и упреждающая эволюция артефактов. См. `src/apothem/rules/persistent-conventions-vigilance.md`.
- **CM-23 Генерация больших файлов** — протокол пошагового дописывания для файлов, превышающих порог однократной записи. См. `src/apothem/rules/large-file-generation.md`.
- **CM-24 Протокол управления контекстом** — вынесение во внешние файлы, сжатие, blind bootstrap и дисциплина бюджета. См. `src/apothem/rules/context-management.md`.
- **CM-25 Оркестрация исполнителей** — паттерны развёртывания, контракты возврата, изоляция контекста. Полная спецификация — в [правиле оркестрации исполнителей](https://github.com/ahmed-g-gad/apothem/blob/main/src/apothem/rules/agent-orchestration.md).
- **CM-26 Жизненный цикл автоматической памяти** — дисциплина памяти, организация тематических файлов, оценка в конце сессии. См. `src/apothem/rules/auto-memory.md`.
- **CM-27 Слои чистой архитектуры** — разделение Domain / Application / Infrastructure / Presentation. См. `src/apothem/rules/clean-architecture-layers.md`.
- **CM-28 Старший архитектор Python** — ограничители SOLID, стиля, тестирования и безопасности для артефактов на Python. См. `src/apothem/rules/code-craft-python.md`.
