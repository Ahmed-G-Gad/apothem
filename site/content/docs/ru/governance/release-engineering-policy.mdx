Пять политик определяют, как выпускаются релизы `apothem`.

## 1. Семантическое версионирование

Проект поставляется в соответствии с [семантическим версионированием 2.0](https://semver.org/).
Номера версий имеют вид `MAJOR.MINOR.PATCH[-PRERELEASE][+BUILD]`.

| Повышение | Триггеры |
|------|----------|
| **MAJOR** | Несовместимые изменения схем артефактов, идентификаторов мандатов (CM-N / TM-N / CP-N) или контрактов хуков |
| **MINOR** | Новые правила, делегированные исполнители, команды, навыки, события хуков или совместимые расширения схем |
| **PATCH** | Уточнения, добавления антипаттернов, исправления документации, правки, не меняющие поведение |

Теги кандидатов используют формат `vX.Y.Z-rc.N` (кандидат в релиз)
или `vX.Y.Z-alpha.N` / `vX.Y.Z-beta.N` (ранний доступ).

## 2. Теги релизов

Каждый релиз помещает в `main` подписанный git-тег вида
`vMAJOR.MINOR.PATCH`. Тег запускает `.github/workflows/release.yml`, который
собирает, подписывает, генерирует SBOM и происхождение SLSA-3 и
публикует страницу GitHub Release.

Соглашения по тегам:

- **Формат** — ровно `vMAJOR.MINOR.PATCH`. Без префикса `release-`,
  без суффикса `-final`.
- **Аннотация** — каждый тег является аннотированным тегом (`git tag -a -s`),
  несущим сводку примечаний к релизу в сообщении тега.
- **Подпись** — каждый тег подписан GPG. Рабочий процесс релиза
  дополнительно создаёт бесключевую подпись Sigstore cosign для
  каждого артефакта и доказательство происхождения релиза SLSA-3; оба
  прикрепляются к странице GitHub Release.

### Модель релизов: аддитивная

Релизы аддитивны. Каждый релиз добавляет один коммит в `main` и один
тег; `main` никогда не отправляется через force-push, и ни один опубликованный
тег, GitHub Release или версия npm не удаляется, не перемещается и не
используется повторно. У проекта три релиза, каждый со своим тегом, своим
GitHub Release и своей версией npm, и все три остаются опубликованными. Версии
npm неизменяемы: опубликованный `name@version` никогда не может быть заменён, а
номер, публикация которого была отозвана, никогда не может быть использован
повторно. Закреплённые установки и воспроизводимые сборки зависят от каждого
опубликованного тега. Руководства по
[циклу релиза](/docs/runbooks/release-cycle) и
[восстановлению релиза](/docs/runbooks/release-recovery) оба следуют этой
модели.

Правило фасада релиза репозитория (раздел «Release Facade» инструкций для
участников, отражённый в правиле freshness-facade) требует
«один видимый тег релиза, один GitHub Release». Это противоречит данной
модели: существуют три релиза, а npm не может удалить опубликованную версию.
Правило остаётся неизменным, пока сопровождающий его не урегулирует. До тех
пор действует аддитивная модель, и ничего опубликованного не удаляется и не
перезаписывается ради соблюдения правила.

## 3. Политика устаревания

Текущая линия публичной поддержки — последняя выпущенная минорная версия. Когда
у проекта несколько публичных минорных версий, матрица поддерживаемых версий в
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md)
является источником истины для любых дополнительных окон поддержки только
критических исправлений.

Ритм устаревания:

- **Объявление** — устаревший символ или поведение
  объявляется в разделе `### Deprecated` файла `CHANGELOG.md`
  того релиза, в котором появляется устаревание. Примечания к релизу
  отражают объявление об устаревании.
- **Окно отсрочки** — устаревшие символы остаются доступными в течение
  как минимум одного полного минорного цикла до удаления.
- **Удаление** — удаление происходит при повышении `MAJOR`. Каждый удалённый
  символ несёт строку `### Removed` в `CHANGELOG.md` и
  запись руководства по миграции в разделе
  [Практические руководства](/docs/how-to-guides).

### Минимальные версии сред выполнения

Apothem объявляет две минимальные версии сред выполнения: `requires-python = ">=3.10"` в
`pyproject.toml` и `"engines": {"node": ">=18"}` в `package.json`.

- **Каждая объявленная минимальная версия тестируется.** Минимальная версия
  Python выполняется в матрице CI `quality` и в рабочем процессе `CI Matrix`.
  Рабочий процесс `npm Shim` запускает npm-шим на минимальной версии Node и на
  каждой более поздней мажорной LTS-версии: он проверяет ошибку об отсутствующем
  предварительном требовании, `node bin/apothem.mjs --version`, пробную
  установку в изолированном домашнем каталоге и упакованный tarball
  через `npx`. Среда выполнения, которая не тестируется, не объявляется.
- **Окончание срока поддержки раскрывается.** Когда среда выполнения, которая
  всё ещё является объявленной минимальной версией, достигает окончания срока
  поддержки в upstream, это сообщает
  [руководство по установке](/docs/install#предварительные-требования-кратко),
  называя версии, которым следует отдавать предпочтение. Срок поддержки
  Python 3.10 закончился 2026-10-01; Node.js 18 и 20 — 2025-04-30 и
  2026-04-30. Все три остаются поддерживаемыми минимальными версиями.
- **Повышение минимальной версии — это устаревание.** Оно следует ритму,
  описанному выше: объявление в `### Deprecated`, как минимум один полный
  минорный цикл, в течение которого старая минимальная версия продолжает
  тестироваться, затем релиз, который её повышает, фиксирует изменение.
  `requires-python`, `engines.node`, проверки версий в установщиках и матрицы
  CI меняются вместе в этом релизе.

## 4. Политика несовместимых изменений

Несовместимые изменения требуют:

1. **Тикета RFC** — открытого с меткой тикета `rfcs`,
   описывающего несовместимое изменение, путь миграции и
   стратегию отката.
2. **30-дневного окна для комментариев** — RFC остаётся открытым не менее
   30 дней до слияния. Сопровождающие могут продлить окно, когда
   это оправдано обратной связью.
3. **Повышения MAJOR** — релиз, вносящий несовместимое
   изменение, повышает компонент MAJOR.
4. **Руководства по миграции** — изменение поставляется с
   записью в [Практических руководствах](/docs/how-to-guides), которая проводит
   оператора через миграцию.

## 5. Политика отката

Если релиз демонстрирует регрессию, блокирующую внедрение:

1. **Отмена** — проблемные коммиты отменяются в `main`.
2. **Релиз с исправлением вперёд** — последующий релиз выходит как
   `vMAJOR.MINOR.PATCH+1`, неся отмену плюс любые
   инкрементальные исправления. Предыдущий плохой релиз **не**
   удаляется из GitHub Releases, а его версия npm остаётся
   опубликованной (версии npm неизменяемы) и помечается с помощью
   `npm deprecate`. Аннотация `### Yanked` в `CHANGELOG.md`
   документирует ситуацию, чтобы воспроизводимые сборки оставались привязанными.
3. **Коммуникация** — откат сопровождается уведомлением security-advisories (когда
   это относится к безопасности) или закреплённым для инцидента тикетом GitHub
   (когда это относится к надёжности).
