Решения для распространённых проблем установки и времени выполнения Apothem.

## Проблемы установки

### Не найден Python 3.10+

Установщики проверяют `python3`, `python` и версионированные имена (от
`python3.14` до `python3.10`) — отклоняя шимы-лаунчеры Microsoft Store — и
останавливаются с сообщением `No Python >= 3.10 found in PATH`, когда ни один
кандидат не соответствует порогу 3.10. Шим npx проверяет `APOTHEM_PYTHON`,
если он задан, затем `python3`, `python` и `py -3`, и завершается с кодом 1 и
собственным сообщением, когда ни один не подходит. Установите CPython 3.10 или
новее с python.org или из репозитория пакетов вашей ОС, убедитесь, что
`python3 --version` (или `py -3 --version` в Windows) сообщает как минимум 3.10,
затем запустите заново.

### Отсутствуют зависимости времени выполнения: click, rich

Движок вендорит большинство своих сторонних зависимостей внутри дерева
исходного кода, но `click` и `rich` должны быть импортируемы под
интерпретатором, который выбирает установщик. Если какой-либо из них
отсутствует, установщик называет его и предлагает установить за вас:

```text
! Missing Python prerequisites under <python>: click rich
  Install click rich under <python> now? [y/N]
```

Примите запрос, чтобы установщик выполнил `pip install` под этим
интерпретатором. Чтобы пропустить запрос, передайте `--yes` (`-Yes` в
PowerShell) или задайте `APOTHEM_AUTO_INSTALL_DEPS=1` для автоматической
установки. Если вы откажетесь — или `pip` недоступен, или вы предпочитаете
менеджер пакетов вашей ОС — установите названные пакеты сами (например,
`python3-click` и `python3-rich` на хостах семейства Debian, или
`pip install click rich`) и затем запустите заново.

### `apothem` не найден после запуска установщика

Установщик размещает дерево исходного кода в `~/.apothem` и по умолчанию
записывает шим `apothem` в `~/.local/bin` (POSIX) или
`%LOCALAPPDATA%\Microsoft\WindowsApps` (Windows); `APOTHEM_BIN_DIR` меняет эту
папку. Он не редактирует ваш `PATH`. Если `apothem` не найден, значит, этот
каталог не входит в `PATH`: добавьте его или запускайте шим по полному пути.
Установщик выводит этот путь по завершении. Если он не записал шим, он выводит
команду, которая запускает движок, не допуская текущую папку в `sys.path`;
скопируйте эту команду из итогового сообщения. Форме npx
(`npx @ahmed-g-gad/apothem <command>`) не нужна запись в `PATH`.

### `/plugin marketplace add` завершается с ошибкой

`/plugin marketplace add ahmed-g-gad/apothem` загружает запись маркетплейса
с GitHub. Если это не удаётся, убедитесь, что машина может достичь
`https://github.com/ahmed-g-gad/apothem` (правила сети, прокси или брандмауэра),
затем повторите. Если маркетплейс был добавлен ранее при частичной
загрузке, удалите и добавьте его заново перед запуском
`/plugin install apothem@apothem`.

### Добавление маркетплейса хоста плагинов завершается по тайм-ауту

Команда хоста плагинов, добавляющая маркетплейс, клонирует его репозиторий и
прекращает попытку через 30 секунд. Полное клонирование этого репозитория может занять больше времени на медленном
диске, например на диске Windows под WSL, а ранее выполненное полное клонирование также может
оставить плагин на старой версии, когда последующее обновление завершается по тайм-ауту.
Загрузите только две папки, которые нужны плагину:

```bash
codex plugin marketplace remove apothem
codex plugin marketplace add ahmed-g-gad/apothem --sparse .agents/plugins --sparse plugins/apothem
codex plugin add apothem@apothem
```

После этого список плагинов хоста показывает текущую версию `apothem@apothem`.

### npx выдаёт устаревшую версию

`npx` кэширует загруженные пакеты. Если `npx @ahmed-g-gad/apothem --version`
сообщает версию старее текущего релиза, очистите кэш или закрепите
dist-тег:

```bash
npx clear-npx-cache
npx @ahmed-g-gad/apothem@latest --version
```

### Установщик останавливается: открытого ключа сопровождающего нет в локальной связке ключей

Каждая сетевая установка проверяет подписанный тег релиза, с cosign или без
него, и останавливается, если ключа подписи нет в вашей связке ключей.
Импортируйте его один раз, проверьте, что отпечаток равен
`5C89 98F9 F241 7204 45D3  F28B 7039 6FED 9C63 4163`, и затем снова запустите
установщик:

```bash title="macOS · Linux · WSL2 · BSD — import the key once"
curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import
gpg --fingerprint 70396FED9C634163
```

```powershell title="Windows · PowerShell — import the key once"
& "$env:ProgramFiles\Git\bin\bash.exe" -c 'curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import && gpg --fingerprint 70396FED9C634163'
```

В Windows импортируйте ключ через `bash` Git, как показано выше:
`git verify-tag` читает связку ключей `gpg`, которая поставляется с Git for
Windows. Установка
[cosign](https://docs.sigstore.dev/cosign/system_config/installation/) не
заменяет импорт ключа: когда cosign есть в `PATH`, установщик проверяет
подписанный архив релиза в дополнение к тегу. Хост без `gpg` может выполнить
установку с `APOTHEM_VERIFY=checksum` и `APOTHEM_ALLOW_UNVERIFIED=1`, но этот
режим не проверяет релиз (см.
[Установщик останавливается: режиму контрольной суммы нужна вторая переменная](#the-installer-stops-checksum-mode-needs-a-second-variable)).

### Установщик останавливается: gpg не найден

Установите GnuPG, а в Windows — Git for Windows, который поставляет `gpg`,
запускаемый `git verify-tag`. Затем импортируйте ключ сопровождающего, как
показано выше, и снова запустите установщик.

### Установщик останавливается: тег подписан не ключом сопровождающего

Сообщение гласит "Tag ... is signed by the key ..." и называет ключ, которым
тег подписан. Подпись тега действительна, но этот ключ не тот, который
публикует
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md#maintainer-signing-key).
Теги релизов Apothem подписываются только этим ключом, поэтому считайте это
возможной подделкой: не устанавливайте и сообщите об этом по каналам из
SECURITY.md. Форк, подписанный собственным ключом, ожидаемо останавливается
здесь.

### Установщик останавливается: cosign не смог подтвердить подпись релиза

Сначала прочитайте текст `cosign said:` в конце сообщения.

- Ошибка сети, прокси или доверенного корня означает, что cosign не смог
  связаться с Sigstore. Повторите попытку, когда будете в сети, обновите
  cosign или выполните установку с `APOTHEM_VERIFY=signature`, который
  проверяет тег релиза только по ключу сопровождающего.
- Форк, заданный через `APOTHEM_REPO`, ожидаемо останавливается здесь:
  установщик принимает только собственный процесс выпуска релизов Apothem.
- "expected GitHub Workflow SHA not found in certificate" означает, что
  сертификат, проверенный cosign, был выдан запуску на другом коммите, чем
  тот, на который указывает подписанный тег, поэтому он не связывает
  `SHA256SUMS` с этим коммитом. Не устанавливайте; сообщите об этом по каналам
  из [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md).
- Несовпадение идентичности или подписи у собственных релизов Apothem
  означает, что `SHA256SUMS` не был подписан процессом выпуска Apothem для
  этого тега. Не устанавливайте; сообщите об этом по каналам из
  [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md).

Если вместо этого установщик сообщает, что не смог загрузить пакет подписи
(bundle), проверьте подключение; если релиз не публикует такой пакет,
выполните установку с `APOTHEM_VERIFY=signature`.

### Установщик останавливается: подписанный тег не является тегом релиза

Сообщение гласит "the signed tag object is not the vX.Y.Z release tag". Тег
несёт подпись ключа сопровождающего, но подписанный объект называет другой
тег, то есть подписанный тег другого релиза был перенаправлен на это имя.
Считайте это возможной подделкой: не устанавливайте и сообщите об этом по
каналам из
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md).
`APOTHEM_ALLOW_UNVERIFIED=1` не обходит эту проверку, но эта переменная
пропускает неподписанный тег или тег, подписанный другим ключом, поэтому
проверка защищает только теги, которые несут подпись ключа сопровождающего.

### Установщик останавливается: режиму контрольной суммы нужна вторая переменная [#the-installer-stops-checksum-mode-needs-a-second-variable]

Режим контрольной суммы не проверяет релиз. SHA256SUMS берётся из того же
релиза, что и архив, поэтому совпадение показывает лишь, что загрузка не
повреждена; любой, кто может изменить файлы релиза, может изменить и то, и
другое. Поэтому `APOTHEM_VERIFY=checksum` работает, только когда также задан
`APOTHEM_ALLOW_UNVERIFIED=1`. Задайте обе переменные, если вы с этим
согласны, или установите `gpg` (и cosign) и запускайте без
`APOTHEM_VERIFY=checksum`.

### Установщик останавливается: папка в APOTHEM_HOME не является установкой Apothem

Установщик не заменяет папку, в которой находится что-то кроме установки
Apothem. Переместите её в сторону, направьте `APOTHEM_HOME` на другую папку
или запустите заново с `--yes` (`-Yes` в PowerShell). С `--yes` установщик
перемещает всю папку без изменений в новую папку
`<APOTHEM_HOME>.before-apothem-<time>` рядом с ней (внутри она сохраняет своё
имя), сообщает, куда, и выполняет чистую установку. Git-клон другого проекта
считается такой папкой. Если уже существуют и
`<APOTHEM_HOME>.before-apothem-<time>`, и то же имя с добавленным
идентификатором процесса установщика, установщик останавливается с
сообщением "Could not move the existing ... aside; nothing was changed" до
того, как что-либо переместится; переименуйте или удалите одну из них и
запустите заново.

### Установщик останавливается: APOTHEM_HOME является символической ссылкой

Сообщение гласит "is a symbolic link" (в Windows — символическая ссылка или
соединение). Замена папки заменила бы ссылку, а не папку, на которую она
ведёт, поэтому установщик отказывается. Задайте `APOTHEM_HOME` как папку, на
которую ведёт ссылка, затем запустите заново. Существующий git-клон за
ссылкой по-прежнему обновляется на месте.

### Установщик останавливается: git-клон содержит локальную работу

Замена git-клона архивом релиза требует `--yes`, и установщик отказывается
даже тогда, пока клон содержит локальную работу, которую он потерял бы:
изменения отслеживаемых файлов, stash-записи, коммиты, которых нет ни на
одном удалённом репозитории, или неотслеживаемые файлы в дереве исходного
кода клона. Закоммитьте и отправьте эту работу или перенесите её в другое
место, затем запустите заново. Проверка выполняется и с `--dry-run`. Когда
такой работы в клоне нет, `--yes` заменяет его и сохраняет собственное
дерево клона в `<APOTHEM_HOME>.before-apothem-<time>/<name>`, где `<name>` —
последняя часть `APOTHEM_HOME`; установщик выводит этот путь, а вы удаляете
папку, когда она вам больше не нужна.

### Установщик останавливается: существующий клон настроен так, что обновление ему доверилось бы

Прежде чем загружать изменения в существующий клон, установщик (и скрипт
обновления) проверяет, как настроен клон. `--dry-run` тоже выполняет эти
проверки. "has changes to tracked files" появляется и тогда, когда файлы
помечены как assume-unchanged или skip-worktree, что скрывает их изменения от
git: выполните `git update-index --no-assume-unchanged <file>` или
`git update-index --no-skip-worktree <file>`, затем закоммитьте изменение или
уберите его в stash. "is not the work tree of its git clone" означает, что git
не находит рабочего дерева в `APOTHEM_HOME`, как бывает, когда git-конфигурация
клона задаёт `core.bare` равным `true`: задайте `false`, чтобы клон
извлекался в `APOTHEM_HOME`. Настройка `core.worktree`, которая направила бы
извлечение в другую папку, сообщается как настройка, которую обновление на
месте не принимает (см. ниже).

"own git config sets `<key>`, which an update in place does not accept in a
clone's own config" называет настройку в `.git/config` клона или в
`.git/config.worktree`, если он у клона есть. Обновление на месте принимает
там только следующие настройки (раздел и ключ сравниваются без учёта
регистра):

- настройки, которые `git clone` и `git init` записывают для полного клона:
  `core.repositoryformatversion`, `core.filemode`, `core.bare`,
  `core.logallrefupdates`, `core.symlinks`, `core.ignorecase`,
  `core.precomposeunicode`, `core.longpaths`, `extensions.objectformat`,
  `extensions.refstorage` (только со значением `files` или `reftable`),
  `extensions.worktreeconfig`, `remote.origin.url`, `remote.origin.fetch` и
  `remote.origin.tagopt`;
- настройки веток, `branch.<name>.<key>`, которые добавляют git и редакторы,
  за исключением того, что `branch.<name>.remote` и
  `branch.<name>.pushremote` должны быть ровно `origin`;
- `user.name`, `user.email`, `maintenance.auto`, `maintenance.strategy`,
  `pull.rebase` и `pull.ff`.

Любая другая настройка останавливает обновление, потому что она могла бы
заставить git запустить программу, читать настройки, хуки, атрибуты или
объекты из другого места или подключиться куда-то ещё. Клон, сделанный с
`--mirror`, `--sparse`, `--recurse-submodules` или с удалённым репозиторием,
имя которого не `origin`, тоже останавливается здесь, как и частичный клон,
сделанный с `--filter`: сообщение называет `remote.origin.promisor`, потому
что git сам загружал бы недостающие объекты с удалённого репозитория, пока
читает клон. Клонируйте заново без `--filter`. Удалите настройку из файла,
который называет сообщение, например
`git config --file ~/.apothem/.git/config --unset-all <key>`, затем
запустите заново. `--unset-all` удаляет и настройку, которая встречается
больше одного раза. Для `remote` или `pushremote` ветки вместо этого задайте
значение `origin`, например
`git config --file ~/.apothem/.git/config branch.main.remote origin`. "own git
attributes name a filter or diff driver" называет `.git/info/attributes`:
удалите настройку `filter=` или `diff=`. git запускает фильтр, пока читает
файлы, а `git diff` запускает текстовое преобразование драйвера сравнения
(`textconv`), поэтому драйвер, который определяет ваша собственная или
системная git-конфигурация, запускался бы на файлах клона.

"which is not a plain file" называет `.git/info/attributes`, `.git/config`
или `.git/config.worktree`, когда это папка, именованный канал или другой
специальный файл либо, в Windows, ссылка. git мог бы прочитать из такого
файла другой текст, чем тот, что читает проверка. Замените его обычным файлом
или удалите, затем запустите заново.

"has a setting whose name holds a line break" означает, что имя раздела в
файле, который называет сообщение, содержит возврат каретки. git никогда его
не записывает, а читающая программа могла бы принять такое имя за две
настройки. Откройте файл в текстовом редакторе, удалите этот раздел, затем
запустите заново.

"borrows objects from another repository" означает, что у клона есть файл
`objects/info/alternates` или `objects/info/http-alternates`, как у клона,
сделанного с `--reference` или `--shared`. Тогда git читал бы объекты из
того другого репозитория, с настройками, которые установщик не проверяет.
Выполните `git -C ~/.apothem repack -a -d`, чтобы скопировать объекты в клон,
удалите файл, который называет сообщение, затем запустите заново.

"keeps submodule repositories in ..." и "holds a submodule at ..." означают,
что у клона есть подмодуль, хранящийся в папке, которую называет первое
сообщение, или записанный в его индексе по пути, который называет второе.
В дереве релиза подмодулей нет, а git работал бы внутри подмодуля, собственные
настройки которого установщик не проверяет. Удалите подмодуль и эту папку из
клона или переместите клон в сторону, затем запустите заново. Замена клона с
`--yes` тоже выполняет эту проверку, прежде чем `git status` ищет локальную
работу. Git-хуки клона никогда не запускаются во время обновления.

### Установщик останавливается: файл .gitattributes в клоне не отслеживается, изменён или называет драйвер

git применяет файлы `.gitattributes` из рабочего дерева, пока сравнивает и
извлекает файлы, и такой файл может заставить git запустить программу. Перед
любой из этих команд установщик и скрипт обновления останавливаются на файле
`.gitattributes`, который не совпадает с закоммиченным, в любой папке клона и
с любым сочетанием заглавных букв в имени, а также на git-репозитории в
клоне, который git не отслеживает, поскольку git читал бы и файлы
`.gitattributes` в нём. `--dry-run` и `--yes` тоже выполняют эту проверку.
Она не читает собственные папки данных движка (`backups`, `state`, `plans`,
`memory`, `contexts`, `learning` и `providers`), куда не пишет ни один
релиз, если только клон не отслеживает там файлы.

- "has a .gitattributes file that git does not track, at ..." называет файл,
  который git не отслеживает, включая игнорируемые файлы и файлы в
  неотслеживаемых папках. Удалите его, затем запустите заново.
- "has a changed .gitattributes file at ..." называет отслеживаемый файл,
  содержимое которого отличается от закоммиченной копии, изменение которого
  проиндексировано или который является ссылкой или папкой. Если изменение
  внесли вы, верните закоммиченную копию, например с помощью
  `git -C ~/.apothem checkout HEAD -- <path>`, затем запустите заново.
- "has a .gitattributes file at ... that names a filter or diff driver
  (filter= or diff=)" называет отслеживаемый файл, закоммиченная копия
  которого или копия в рабочем дереве называет такой драйвер вне комментария,
  включая макрос (строку `[attr]`), который его называет. git запускал бы
  этот драйвер, который может определять ваша собственная или системная
  git-конфигурация, пока читает клон. Удалите настройку, закоммитьте это
  изменение, затем запустите заново. Макрос, который определяет только ваш
  собственный или системный файл атрибутов, не считается: во время запуска git
  не читает ни одного файла атрибутов вне клона, поэтому такой макрос там не
  называет драйвера.
- "has a .gitattributes file at ... whose committed copy git could not read"
  означает, что копия в git-папке клона отсутствует или повреждена либо её
  байты не совпадают с её идентификатором, чего git не проверяет при чтении.
  Тогда установщик не может проверить, что говорит файл, а git всё равно
  применил бы копию из рабочего дерева. Выполните `git -C ~/.apothem fsck`,
  чтобы увидеть, что повреждено, восстановите клон или переместите его в
  сторону и выполните чистую установку, затем запустите заново.
- "Could not run git to read the committed .gitattributes files in ..."
  выводят только `install.ps1` и `update.ps1`. В вашем сеансе PowerShell `git`
  является функцией или скриптом, например обёрткой в вашем профиле, и в
  `PATH` нет программы git, которой установщик мог бы прочитать файлы.
  Добавьте папку git в `PATH`, чтобы `Get-Command git -CommandType Application`
  её находил, затем запустите заново.
- "holds a git repository that git does not track, at ..." называет папку с
  собственным `.git`. git ничего не перечисляет внутри такой папки, поэтому
  файл `.gitattributes` в ней остаётся незамеченным, но git применяет его к
  файлам, которые там записывает обновление. В дереве релиза таких папок нет.
  Переместите папку из клона, затем запустите заново.

Если файл или изменение сделали не вы, значит, в клон может писать кто-то
другой: переместите клон в сторону, выполните чистую установку и убедитесь,
что `APOTHEM_HOME` — папка, в которую можете писать только вы.

### Установщик останавливается: файлы в src, которые git не отслеживает

Сообщение гласит "has files under src that git does not track, and the engine
could load them:" и перечисляет каждый из них (первые 20, затем сколько ещё).
Движок запускается из папки `src` клона, поэтому лишний файл там мог бы
выполниться как его часть. Игнорируемые файлы учитываются, как и файл `.pyc`
рядом с исходниками. Папка с именем `Src` или `SRC` считается `src`,
поскольку Windows и macOS находят её под этим именем.
Редактируемая установка клона через `pip install` записывает
`src/apothem.egg-info`, а файловый менеджер может записать `.DS_Store` или
`desktop.ini`. Переместите файлы из `~/.apothem/src`, затем запустите заново;
ничего не было изменено. Проверка выполняется перед загрузкой изменений, при
обновлении на месте и при пробном запуске. Папки кэша Python (`__pycache__`)
не учитываются: после извлечения и до первого запуска движка из клона
обновление удаляет каждую папку `__pycache__` в `src`, так что никакой
кэшированный байт-код из времени до обновления не загружается.

"Could not remove the Python cache folders (__pycache__) under ..." означает,
что это удаление не удалось, например потому что файл в одной из них
принадлежит другому пользователю или, в Windows, открыт в другой программе.
Клон уже извлечён на новый релиз. Удалите эти папки сами, затем запустите
заново.

### Установщик останавливается: блокировку держит другой запуск

Каждый запуск скриптов установки, обновления и удаления держит блокировку
рядом с `APOTHEM_HOME` (`<APOTHEM_HOME>.lock`, то есть по умолчанию
`~/.apothem.lock`), пока работает; команды `apothem install`,
`apothem update` и `apothem uninstall` её не берут. Сообщение "Another
Apothem install, update or uninstall is running on ..." означает, что второй
запуск обнаружил её занятой. Дождитесь завершения другого запуска, затем
запустите заново. Если ни один не выполняется, удалите блокировку, которую
называет сообщение, затем запустите заново.

- "was left by an Apothem run that did not finish (process N is no longer
  running)" и "exists but names no running process" означают, что запуск был
  принудительно завершён, прежде чем успел освободить блокировку. Убедитесь,
  что не выполняется ни одна установка, обновление или удаление Apothem,
  удалите блокировку и запустите заново. Установщик никогда не удаляет её за
  вас. В POSIX блокировка — это папка (`rm -rf ~/.apothem.lock`); в Windows
  PowerShell это файл, который Windows удаляет, когда его запуск
  заканчивается.
- "is the lock file of an Apothem PowerShell run" выводит POSIX-скрипт под
  Git Bash, MSYS2, Cygwin или WSL, который обнаружил файл, удерживаемый
  запуском PowerShell. Windows удаляет этот файл, когда запуск заканчивается,
  и никому не даёт удалить его, пока запуск активен. Дождитесь завершения
  этого запуска. Если не выполняется ни одна установка, обновление или
  удаление Apothem, удалите файл, затем запустите заново. В других системах
  сообщение гласит "is a file where the Apothem lock folder belongs": удалите
  файл, если ни один запуск не активен, затем запустите заново.
- "was made by an Apothem run in another environment" означает, что папка
  блокировки называет процесс в другой среде, например в WSL, когда запуск
  идёт под Git Bash, в Git Bash, когда он идёт под WSL или MSYS2, или в другом
  контейнере. Отсюда этот процесс проверить нельзя. Дождитесь завершения того
  запуска; удаляйте блокировку, только если нигде не выполняется ни одна
  установка, обновление или удаление Apothem.
- POSIX-скрипты считают процесс, принадлежащий другому пользователю, например
  запуск под `sudo`, выполняющимся, поэтому его блокировка читается как
  занятая. PowerShell не может проверить идентификатор процесса папки
  блокировки, созданной POSIX-скриптами (например, под Git Bash), поэтому
  такую блокировку он тоже считает занятой.
- Когда `APOTHEM_HOME` — символическая ссылка (или, в Windows, соединение),
  POSIX-скрипты и скрипты PowerShell берут блокировку рядом с папкой, на
  которую ведёт ссылка, поэтому запуск через ссылку и запуск через эту папку
  останавливают друг друга; сообщение называет эту блокировку.
- "Could not create the lock ... Check that you can write to ..." означает,
  что вы не можете писать в папку, которую называет сообщение: в ту, что
  содержит `APOTHEM_HOME`, или, когда `APOTHEM_HOME` — ссылка, в ту, что
  содержит папку, на которую она ведёт. Каждому запуску нужно писать туда,
  включая обновление на месте, удаление и пробный запуск.

### Установщик останавливается: предыдущий запуск оставил папки рядом с APOTHEM_HOME

Сообщение гласит "An earlier run was stopped part-way and left these
folders beside ..." и перечисляет каждую папку с тем, что в ней находится.
Ctrl+C и сигнал завершения перехватываются, и запуск прибирает за собой;
принудительное завершение или отключение питания во время подмены — нет, и
могут оставить:

- `.apothem-old.<name>.*`: предыдущую установку, которая заменялась, в её
  папке `home`. Когда эта папка `home` содержит git-клон, а `APOTHEM_HOME` на
  месте (как это бывает после того, как новая установка заняла своё место),
  строка вместо этого говорит, что в ней дерево клона, которое тот запуск
  сохранял: перенесите его в свою папку, если оно вам ещё нужно. Когда папка
  `home` не содержит установки Apothem, а `APOTHEM_HOME` на месте, строка так
  и говорит: там появилась папка, пока запуск перемещал предыдущую установку,
  запуск вернул установку на место и не тронул эту папку. Проверьте, что в
  ней, прежде чем её удалять.
- `.apothem-extract.<name>.*` или `.apothem-clone.<name>.*`: новый исходный
  код, который устанавливался. Когда запуск уже переместил в неё элементы
  `APOTHEM_HOME`, строка называет каждый из них: данные движка, например
  `backups` и `state`, и любой другой файл или папку, которые там были.
- `<APOTHEM_HOME>.before-apothem-<time>`: перечисляется, только когда самой
  `APOTHEM_HOME` нет. Она содержит прежнее содержимое `APOTHEM_HOME` в папке,
  названной по последней части `APOTHEM_HOME`, или прямо внутри себя для
  папки, созданной более ранним установщиком; строка говорит, какой вариант.

`<name>` — последняя часть `APOTHEM_HOME` (по умолчанию `.apothem`), поэтому
папки другого `APOTHEM_HOME` в той же родительской папке, которые может
использовать запуск для того каталога, не перечисляются. В Windows и macOS
`<name>`, отличающееся только заглавными буквами, считается относящимся к
этому каталогу, потому что `APP` и `app` по умолчанию называют там одну и ту
же папку. Правило следует операционной системе, а не файловой системе: под
WSL, даже на диске Windows, имена, отличающиеся заглавными буквами, — разные
каталоги, а на томе macOS или в папке Windows с учётом регистра они
по-прежнему считаются одним, поэтому другой каталог там, имя которого
отличается только заглавными буквами, тоже перечисляется. Папку, в имени
которой нет части `<name>`, создал более ранний установщик, который не
записывал каталог; она перечисляется с пометкой, что может относиться к любому
каталогу Apothem в этой папке, а её строка говорит, что элементы были
перемещены из каталога, для которого она была создана. Для такой папки,
созданной установкой из клона, строка называет только найденные данные
движка, поэтому загляните внутрь, нет ли там чего-то ещё. Учитываются только
папки: файл или ссылка с таким именем не перечисляются. Папка, которую
установщик не может прочитать, перечисляется как "could not be read".

Ничего не было изменено и ничего не удаляется. Если `APOTHEM_HOME` нет,
сначала верните в неё предыдущую установку. Затем верните каждый элемент,
который список называет перемещённым в новый исходный код, в каталог, из
которого он пришёл (для папки с пометкой сначала проверьте, какой это
каталог), удалите перечисленные папки и запустите заново. Проверка
выполняется для загружаемой установки, включая пробный запуск; она не
выполняется для установки из вашей собственной рабочей копии, а также для
обновления или удаления.

### Установщик останавливается: клон принадлежит другому пользователю

Сообщение гласит "is owned by someone else, so git refuses to work in it
(git reports "dubious ownership")". git не будет читать клон, который
принадлежит другому пользователю. Запустите установщик от имени
пользователя, которому принадлежит `APOTHEM_HOME`, станьте владельцем папки
или направьте `APOTHEM_HOME` на папку, которой владеете вы, затем запустите
заново. Установщик не добавляет папку в список `safe.directory` git. Любой
другой сбой этой первой команды git выводится как "git could not read the
clone at ...", за которым следует первая строка собственного объяснения git.

### Установщик предупреждает: другие пользователи могут изменять APOTHEM_HOME

Скрипты установки и обновления, включая пробные запуски, предупреждают, когда
пользователи, кроме вас, могут писать в `APOTHEM_HOME` или в папку, которая
её содержит, или владеют одной из них, поскольку тогда они могут изменить
код, который команда `apothem` запускает от вашего имени; запуски, которые
пропускают проверку, перечислены ниже. Запуск продолжается; предупреждение
называет папку, кто может в неё писать или владеет ею, и способ исправления.
Предупреждение начинается с одного из следующих:

- "Other users can change the code Apothem runs as you", когда они могут
  писать в `APOTHEM_HOME` или когда `APOTHEM_HOME` или папка, которая её
  содержит, принадлежит кому-то другому (тогда сообщение говорит, кто какой
  папкой владеет). Когда `APOTHEM_HOME` — ссылка, сообщение называет папку,
  на которую она ведёт.
- "Other users can replace ...", когда они могут писать в папку, которая
  содержит `APOTHEM_HOME` (или ссылку на неё), и поэтому переименовать или
  удалить её.
- "A new ... would let", когда `APOTHEM_HOME` ещё не существует и новая
  папка там была бы открыта для других.

Установка из локальной рабочей копии не проверяется, называет ли её
`APOTHEM_SOURCE` или вы запускаете собственный `scripts/installer/install.sh`
или `install.ps1` этой рабочей копии. Скрипты обновления пропускают проверку,
только когда задан `APOTHEM_SOURCE`. Если предупреждение называет группу,
которую вы намеренно разделяете с людьми, которым доверяете изменять код,
его можно игнорировать.

Проверка читает права доступа `APOTHEM_HOME` и папки, которая её содержит,
а не каждого файла внутри.

В Linux и macOS предупреждение называет «всех пользователей» ("all users")
или «группу» ("the group"), которые оно нашло в битах прав доступа папки, а
также каждого пользователя или группу, которым список управления доступом
(ACL) разрешает запись; его оно читает с помощью `getfacl`, если тот
установлен. При наличии списка доступа биты группы, которые показывает `ls`,
являются маской списка, поэтому там, где `getfacl` перечисляет собственную
запись группы (`group::`), именно эта запись решает, называется ли группа;
без `getfacl` названная группа может оказаться той, которой запись
разрешает маска, но не её собственная запись. Предупреждение никогда не
называет вас, пользователя root или группу с вашим собственным именем
пользователя (вашу собственную группу). Имя, которое `getfacl` записывает с
экранированием, например `CORP\alice` доменной учётной записи, считается
именем, которое оно обозначает. Чтобы исправить это, выполните команду,
которую даёт сообщение (в Linux она также отнимает право записи у каждого
пользователя и группы, которых называет список доступа):

```bash
chmod go-w "$HOME/.apothem"
```

Файлы, созданные при тех же настройках, тоже могут быть доступны для записи:
`chmod -R go-w` для папки исправляет и их. Если другим нужно писать в папку,
которая содержит `APOTHEM_HOME`, как в случае `/tmp`, установите на ней
sticky-бит с помощью `chmod +t`, чтобы они не могли переименовать или
удалить то, что вы туда положили, или перенесите `APOTHEM_HOME`. Для новой
установки предупреждение сообщает ваш umask: выполните `umask 022` и снова
запустите установщик. В WSL держите `APOTHEM_HOME` в своём домашнем каталоге
Linux, а не в `/mnt/c`, где каждый файл выглядит доступным для записи всем
пользователям.

Когда сообщение говорит, что пользователь «владеет» ("owns") папкой, этот
пользователь может изменять её независимо от прав доступа, и только root
может сделать владельцем вас. Папка, которой владеет root, — это нормально.
Перенесите `APOTHEM_HOME` в папку, которой владеете вы.

В Windows предупреждение называет каждую учётную запись или группу, которой
запись о разрешении позволяет изменять папку, так, как её называет вкладка
«Безопасность» папки: Users, Authenticated Users, Everyone, INTERACTIVE (все,
кто вошёл в систему за компьютером или через удалённый рабочий стол и кто
может изменять то, что создано в `C:\Users\Public`), Guests или группу,
созданную вашей организацией или другой программой. Оно никогда не называет
вас, ваш собственный сеанс входа, SYSTEM, Administrators, TrustedInstaller,
CREATOR OWNER или OWNER RIGHTS; последние две обозначают того, кто создаёт
элемент или владеет им, а владелец, который является кем-то другим, получает
отдельное сообщение. Когда папка принадлежит другой учётной записи,
сообщение так и говорит и предлагает перенести `APOTHEM_HOME` в вашу папку
пользователя. Когда сообщение добавляет "access that folders made at the root
of a drive inherit from the drive's default permissions", папка находится в
корне диска, например `C:\apothem`: Windows позволяет каждому пользователю,
который входит в систему, добавлять и изменять созданные там папки. Самое
простое исправление — перенести `APOTHEM_HOME` в вашу папку пользователя
(`%USERPROFILE%`), как и находится `~\.apothem` по умолчанию. Чтобы оставить
папку на месте, отключите наследование, дайте себе полный доступ, затем
удалите группы, которые называет предупреждение. Для папки в корне диска это
Authenticated Users в Windows 10 и 11 и Users в Windows Server; команды ниже
удаляют обе:

```powershell
icacls "C:\apothem" /inheritance:d
icacls "C:\apothem" /grant:r "${env:USERNAME}:(OI)(CI)F"
icacls "C:\apothem" /remove:g *S-1-5-11 *S-1-5-32-545 *S-1-1-0 *S-1-5-4
```

Дайте себе доступ, прежде чем удалять группы: удаляемая запись может быть
вашим единственным способом писать в папку. Имена `*S-...` — это
идентификаторы безопасности групп (Authenticated Users, Users, Everyone и
INTERACTIVE), которые работают в Windows на любом языке. Удаляйте любое
другое имя, которое даёт предупреждение, отдельной строкой `icacls`, в
кавычках: имя, которое `icacls` не может найти, останавливает всю строку,
которая тогда ничего не удаляет и всё равно выводит "Successfully processed 0
files". Имя из `S-` и цифр — это идентификатор безопасности учётной записи,
которую Windows не может найти, например удалённой учётной записи или
другого сеанса входа: поставьте перед ним `*`, а если `icacls` всё равно
ничего не удаляет, удалите его в окне «Свойства > Безопасность >
Дополнительно» папки. Там же можно внести и все остальные изменения. Когда
предупреждение касается папки, которая содержит `APOTHEM_HOME`, вносите
изменения там или перенесите `APOTHEM_HOME`. Ссылка или соединение в
`APOTHEM_HOME` получает права доступа от той папки, поэтому другие, кто может
изменять папку, могут удалить ссылку и создать свою.

`install.sh` и `update.sh` не выполняют проверку под Git Bash, MSYS2 или
Cygwin, где биты прав доступа составляются из разрешений Windows, поэтому
там они не выдают предупреждения. В Windows запускайте `install.ps1` или
`update.ps1`, которые читают разрешения Windows, чтобы папка была проверена.

### Установщик останавливается: существующий клон не удалось обновить

Установщик загружает изменения в существующий клон и проверяет новый тег,
прежде чем извлекать его, поэтому неудачная проверка оставляет клон как был.
Ещё два сообщения останавливают обновление до извлечения. "Could not fetch"
обычно означает, что локальный тег отличается от тега в origin: удалите его
с помощью `git -C ~/.apothem tag -d <tag>` и запустите заново. "has changes to
tracked files. Commit or stash them, then re-run." означает, что в клоне есть
незакоммиченные изменения файлов, которые отслеживает git: закоммитьте их или
уберите в stash, затем запустите заново. Проверка игнорирует настройки
окончаний строк (`eol` и `text`) в вашем собственном или системном файле
git-атрибутов, поэтому так может быть описан и клон, который вы никогда не
меняли: выполните `git -C ~/.apothem status` один раз, затем запустите
заново. Пробный запуск не проверяет обычные незакоммиченные изменения,
поскольку не загружает изменения в клон, но останавливается с тем же
сообщением, когда файлы помечены как assume-unchanged или skip-worktree (см.
раздел о настройке клона выше). "Could not check out" означает, что
извлечение всё равно перезаписало бы локальные изменения. Установщик никогда
не отбрасывает локальные изменения. Для ссылки, не являющейся релизом,
например `main`, существующий клон следует копии этой ветки в origin.

### Установщик или скрипт обновления завершается с кодом выхода 2

Движок завершился частично. Либо он оставил как есть файл, который содержит
блок Apothem, из-за строк маркеров Apothem в нём, и записал остальное, либо
остановился после того, как уже что-то записал, например когда один
инструмент завершился сбоем после предыдущего в запуске
`APOTHEM_HARNESS=all`. Его сообщения называют файл или показывают ошибку,
которая его остановила, а скрипт добавляет одну строку, которая начинается с
"The engine ended as partial (exit code 2)." Установщик всё равно выполняет
проверку, размещает команду `apothem` и выводит итоговое сообщение, а скрипт
обновления всё равно выводит свою последнюю строку. Запуск PowerShell через
конвейер (`irm ... | iex`) оставляет `$LASTEXITCODE` равным `2`, а ваш сеанс
— открытым. Однократный
`pwsh -Command "irm ... | iex"` (или `powershell -c`) сообщает о частичном
запуске только через `$LASTEXITCODE` и завершается с кодом `0`: чтобы
получить код выхода `2` от процесса, завершите команду на
`; exit $LASTEXITCODE` или запустите скрипт по пути с `-File`. Из
PowerShell, bash или другой оболочки POSIX заключайте эту команду в
одинарные кавычки. В двойных кавычках вызывающая оболочка подставляет свой
собственный `$LASTEXITCODE` до запуска нового процесса (оболочка POSIX
подставляет пустую строку), поэтому процесс завершается не с кодом запуска.
Из cmd.exe двойные кавычки подходят. Пробный запуск ничего не записывает,
поэтому он не завершается частично.
Исправьте то, что называют сообщения. Для файла сохраните свой собственный
текст (см.
[В файле два блока между маркерами Apothem](#a-file-holds-two-blocks-between-apothems-markers)
и
[Apothem не может отличить свой блок от вашего текста](#apothem-cannot-tell-its-block-from-your-text)),
затем снова выполните `apothem update --harness <name>` для каждого
инструмента, который запуск оставил незавершённым.
[Когда движок оставляет файл как есть](/docs/install/updating#when-the-engine-leaves-a-file-as-it-is)
описывает весь запуск.

### irm / iex заблокированы в Windows

Если политика выполнения PowerShell блокирует установщик:

```powershell
Set-ExecutionPolicy RemoteSigned -Scope CurrentUser
irm https://apothem.ahmedgad.com/install.ps1 | iex
```

### Установщик проигнорировал рабочую копию в моей текущей папке

Так задумано. Однострочник через конвейер (`curl ... | sh`, `irm ... | iex`)
никогда не использует локальное дерево и никогда не заглядывает в текущую
папку или её родительские папки: он загружает и проверяет релиз. Чтобы
установить из рабочей копии, запустите собственный
`scripts/installer/install.sh` (или `install.ps1`) этой рабочей копии по его
пути из любой папки (например,
`sh ~/src/apothem/scripts/installer/install.sh`) или задайте `APOTHEM_SOURCE`
как путь к рабочей копии. Передайте скрипту путь с частью папки:
`sh scripts/installer/install.sh` или `sh ./scripts/installer/install.sh`
работает, но `sh install.sh` без части папки не считается запуском из рабочей
копии, поэтому установщик выводит "Not using a checkout: to install from one,
run this script as ./install.sh or by its full path, or set APOTHEM_SOURCE." и
вместо этого загружает и проверяет релиз. Скрипт, запущенный через `sh -c`,
тоже не считается рабочей копией в оболочках, которые помечают запуски `-c`.
dash их не помечает, поэтому под dash `sh -c "<script>" ./install.sh`,
запущенный из папки `scripts/installer` внутри дерева исходного кода,
использует это дерево: запускайте текст скрипта таким способом только из
папки, которой доверяете. Точно так же копия `install.sh`, которую вы
сохраняете в папку `scripts/installer` другого дерева исходного кода и
запускаете там по пути, становится собственным установщиком этого дерева и
устанавливает его. Сохраняйте загруженный скрипт в пустую папку.
`install.sh` следует по символической ссылке к реальному файлу и использует
рабочую копию, которая его содержит. `install.ps1` поступает наоборот: он
отклоняет рабочую копию, до которой добирается через символическую ссылку или
соединение, выводит однострочное примечание и выбирает путь с загрузкой и
проверкой. Запускайте его из реальной папки или задайте `APOTHEM_SOURCE`.
Установщики, команда `apothem`, npm-лаунчер и хуки также не допускают текущую
папку в путь поиска модулей Python, поэтому файл с именем `click.py` в папке,
где вы работаете, на них не влияет. Команда `python -m apothem`, которую вы
вводите сами, этого не делает: `-m` сначала читает модули из текущей папки,
поэтому запускайте её только из папки, которой доверяете.

### Старая команда `apothem` всё ещё смотрит в мою текущую папку

Более ранние релизы записывали шим команды `apothem`, который запускал Python
так, что текущая папка могла перекрыть модули движка. Обновление не
перезаписывает этот шим. Запустите установщик (`install.sh` или
`install.ps1`) снова, чтобы заменить его. Программы удаления удаляют и
старый, и новый шим.

### Git Bash: мои записи `/c/...` в PYTHONPATH игнорируются

Под Git Bash установщики обычно запускают Python для Windows, а Python для
Windows читает `PYTHONPATH` как пути Windows, разделённые `;`. Скрипты sh и
шим `apothem`, который они записывают, оставляют для этого Python только пути
к дискам и сетевые пути из вашего `PYTHONPATH`, поэтому запись в стиле POSIX,
например `/c/Users/me/lib`, отбрасывается. Записывайте её как путь к диску,
`C:\Users\me\lib` или `C:/Users/me/lib`, и разделяйте записи с помощью `;`.
Python для POSIX, например собственный `python3` Cygwin или MSYS2, читает
пути, разделённые `:` и начинающиеся с `/`, и скрипты сохраняют их для него.

## Проблемы времени выполнения

### apothem install не находит окружений

Запустите apothem doctor, чтобы прочитать его таблицу Harness Status, в которой одна строка на каждое окружение. Строка с пометкой `not installed` означает, что Apothem не нашёл установки для этого окружения. Строка с пометкой `needs --project` относится к окружению с областью проекта, которое doctor проверяет только при передаче `--project <path>`. Если doctor сообщает `No harness is installed yet`, убедитесь, что нужное окружение установлено, затем выполните `apothem install --harness <name>`.

### apothem verify сообщает о неисправном адаптере

Повторно запустите apothem install, чтобы заново материализовать адаптер. Если
проблема сохраняется, проверьте страницу конкретного адаптера в разделе
[Адаптеры окружений](/docs/harnesses). Если установка предупредила о маркере
BEGIN без END или строка со сбоем называет файл, который его содержит,
повторный запуск не поможет; см.
[В файле есть маркер BEGIN Apothem без маркера END](#a-file-has-an-apothem-begin-marker-with-no-end-marker).
Если предупреждение или строка говорит, что файл содержит два или более целых
блока между маркерами Apothem, см.
[В файле два блока между маркерами Apothem](#a-file-holds-two-blocks-between-apothems-markers).
Если в нём сказано, что Apothem не может определить, отмечают ли строки
маркеров в файле его блок или ваш текст, см.
[Apothem не может отличить свой блок от вашего текста](#apothem-cannot-tell-its-block-from-your-text).

### В файле есть маркер BEGIN Apothem без маркера END [#a-file-has-an-apothem-begin-marker-with-no-end-marker]

Apothem хранит собственный текст в блоке, который идёт от маркера
`<!-- BEGIN APOTHEM MANAGED BLOCK -->` до следующего маркера
`<!-- END APOTHEM MANAGED BLOCK -->`. Если маркер END пропал (ручная правка
или слияние, при котором строка потерялась) или ваш маркер BEGIN находится
вне целого блока, ничто не показывает, где кончается текст Apothem и
начинается ваш. Поэтому Apothem никогда не обрезает текст после этого
маркера:

- `apothem install` и `apothem update` сохраняют его как есть, записывают
  блок Apothem отдельно от него и выводят предупреждение, которое называет
  файл и строку маркера, с пронумерованным шагом, который меняет эту строку
  (см. ниже). Предупреждение также говорит не возвращать вместо этого маркер
  END: когда блок Apothem записан отдельно от него, файл содержал бы два
  блока Apothem, которые установка и обновление оставляют как есть. Пробный
  запуск читает файл до того, как что-либо записано, поэтому, когда файл ещё
  не содержит целого блока, его предупреждение говорит, что если вы вместо
  этого вернёте маркер END, между двумя маркерами не должно быть ни одной
  вашей строки, поскольку следующий запуск заменяет или убирает каждую строку
  между ними, и что возвращать его вообще не следует, как только установка
  или обновление записали блок Apothem отдельно от маркера. До тех пор
  возврат маркера сразу под старым текстом Apothem, над вашими собственными
  строками, оставляет один целый блок, который следующее обновление
  перезаписывает.
- `apothem uninstall` убирает весь блок Apothem, оставляет остальное как
  есть и называет файл и строку маркера с тем же пронумерованным шагом:
  установка сохраняет маркер как есть, а инструмент по-прежнему читает текст
  под ним.
- `apothem verify` и `apothem doctor` завершаются сбоем и называют файл и
  строку маркера с тем же пронумерованным шагом, пока лишний маркер не будет
  изменён; для файла, который записывает текущая установка,
  `apothem status --profile` до тех пор тоже показывает дрейф. Повторный
  запуск `apothem install` этого не устраняет. Учитываются только файлы, в
  которых Apothem хранит блок для этого окружения, поэтому маркер в вашем
  собственном файле не приводит к их сбою.

Пока запись об установке перечисляет файл, который не содержит целого блока,
но содержит пару маркеров в коде, например пример маркера, который вы
цитируете в блоке кода, установка, обновление и удаление оставляют весь этот
файл как есть: эта пара может быть блоком Apothem внутри вашего блока кода.
Их предупреждение, как и примечание `apothem verify`, сначала называет этот
маркер BEGIN, затем каждую пару, и удаление остаётся незавершённым (см.
[Apothem не может отличить свой блок от вашего текста](#apothem-cannot-tell-its-block-from-your-text)).
Без записи об установке пара, которую вы цитируете в коде, — это ваш текст,
и установка и обновление записывают блок Apothem отдельно от лишнего
маркера. Маркер END, который вы цитируете в коде отдельно ниже, без пары
маркеров после него, — другое дело: он закрывает этот маркер BEGIN, поэтому
обновление заменяет строки между ними как блок Apothem, а удаление убирает
их.

Apothem читает маркер только как отдельную строку вне кода, так же как
программа просмотра Markdown, поэтому маркер, который вы цитируете в
предложении, в огороженном блоке кода или в коде с отступом на четыре
столбца дальше его элемента списка (или поля) после пустой строки, не
принимается за маркер, как и маркеры BEGIN и END, которые вы цитируете в двух
разных блоках кода. Ограждение кода, которое вы оставили открытым до конца
файла, читается как текст, сколько бы их ни было, если только маркер BEGIN
вне кода выше него не имеет свой маркер END в коде и за ними не следует ещё
одна пара маркеров. Маркеры внутри блока HTML или цитаты либо после элемента
списка, текст которого продолжается у левого поля, всё ещё могут читаться
иначе, чем в программе просмотра Markdown.

Каждый номер строки, который дают эти предупреждения, считает строки так,
как Apothem читает файл: строка заканчивается на CRLF, на LF или на
отдельном CR. В файле, сохранённом с окончаниями CR, или с одним лишним CR
внутри строки, считайте строки тем же способом, прежде чем менять строки,
которые называет предупреждение.

Чтобы исправить это, выполните пронумерованный шаг из предупреждения,
например "Fix A, if lines 77 to 148 are Apothem's block: A1. Change line 3: add a word
inside its comment." Строка 3 — это лишний маркер BEGIN: тот, у которого нет
маркера END до следующего маркера BEGIN или нет вообще. Добавьте слово прямо
перед его закрывающим `-->`, как в
`<!-- BEGIN APOTHEM MANAGED BLOCK (example) -->`, и строка больше не
читается как маркер. Это не добавляет и не удаляет ни одной строки, поэтому
ничто другое в файле не читается иначе, а строка BEGIN, которая открывает
текущий блок Apothem, остаётся как есть. Исправление также меняет каждую
другую строку маркера BEGIN в файле, включая ту, которую вы цитируете в блоке
кода, по одному шагу на каждую, снизу файла вверх (см.
[Следование пронумерованному исправлению](#follow-a-numbered-fix)): цитируемый
маркер BEGIN, оставленный как есть, мог бы образовать пару с маркером END под
ним, как только удаление уберёт блок Apothem. Когда структура файла
не показывает, что блок Apothem остаётся целым после изменения этих строк
(скажем, его содержит ваш блок кода, который не закрывает ни одна строка),
исправление меняет каждую строку маркера BEGIN в файле, включая строку
блока, например "Fix A: A1. Below
line 6, add a line of 3 backticks. A2. Change line 3: add a word inside its
comment. A3. Change line 2: add a word inside its comment. Apothem then reads
none of these lines as its markers, and the next update writes its block at
the end of the file." Когда файл заканчивается внутри блока кода, который не
закрывает ни одна строка, как здесь, исправление сначала добавляет
закрывающую строку этого блока кода под последней строкой, чтобы блок,
который следующее обновление запишет там, не был кодом. Старый текст
Apothem под изменённой вами строкой маркера, который повторяет правила
Apothem, затем удаляете вручную вы. Не возвращайте маркер END
вместо изменения строки маркера: как только установка или обновление
записали блок Apothem отдельно от него, файл содержал бы два блока Apothem
(см.
[В файле два блока между маркерами Apothem](#a-file-holds-two-blocks-between-apothems-markers)).
Как только вы измените строку маркера, маркер END под ней ни с чем не
образует пару. Затем выполните `apothem update`, который записывает блок
Apothem обратно, если файл его больше не содержит, и снова выполните
`apothem verify`. Маркер BEGIN, маркер END которого находится в коде, а за
ними следует ещё одна пара маркеров, получает другое предупреждение; см.
[Apothem не может отличить свой блок от вашего текста](#apothem-cannot-tell-its-block-from-your-text).

### В файле два блока между маркерами Apothem [#a-file-holds-two-blocks-between-apothems-markers]

Apothem записывает один блок на файл. Тем не менее файл может оказаться с
двумя целыми блоками: старый блок, маркер END которого вы вернули после того,
как обновление записало под ним свежий блок, ваша пара маркеров вне кода
(скажем, цитируемый вами пример) или блок, который вы вставили второй раз.
Тогда Apothem не может определить, какой из них его собственный:

- `apothem install` и `apothem update` оставляют файл как есть и выводят
  предупреждение, которое называет каждый блок по его строкам, например
  "holds 2 whole blocks between Apothem's markers (lines 1 to 32, and lines
  36 to 67)". Запуск завершается частично: вместо строки `✓` он выводит
  строку `✗`, которая называет файл, его `status` в `--format json` равен
  `"partial"`, и он завершается с кодом `2`, пока вы не исправите файл. При
  пробном запуске предупреждение говорит, что Apothem "would leave the file as
  it is".
- `apothem verify`, с `--profile` или без него, и `apothem doctor`
  завершаются сбоем и называют файл с каждым блоком (проверка doctor —
  `harness.stray_begin`, и её сообщение говорит, что файл содержит "Apothem
  markers to fix by hand"), пока вы не исправите файл; для файла, который
  записывает текущая установка, `apothem status --profile` до тех пор тоже
  показывает дрейф.
- `apothem uninstall` убирает блоки, которые являются точными копиями друг
  друга (скажем, блок, вставленный дважды). Когда остался бы другой блок, оно
  оставляет файл как есть, выводит то же предупреждение, которое
  заканчивается словами "then run the uninstall again", и остаётся
  незавершённым (код выхода `2`), пока вы его не исправите (см.
  [Удаление, которое не завершилось](/docs/cli-reference/uninstall#an-uninstall-that-did-not-finish)).
  Без записи об установке оно также оставляет как есть `CLAUDE.md` Claude Code
  или документ профиля, содержащий два блока, и его предупреждение называет
  каждый блок тем же образом. Это предупреждение советует после исправления
  выполнить `apothem update`, а затем снова `apothem uninstall`, и оно не
  останавливает удаление. Затем запуск удаления называет любые ваши строки
  маркеров вокруг блока Apothem, прежде чем убрать блок.

Затем предупреждение даёт по одному пронумерованному исправлению для каждого
блока, на случай если это блок Apothem, например "Fix A, if lines 1 to 32 are
Apothem's block: A1. Change line 36: add a word inside its comment. Lines 1 to
32 are then the one block in the file." (см.
[Следование пронумерованному исправлению](#follow-a-numbered-fix)).
Исправление меняет строку маркера BEGIN каждого другого блока; маркер END без
маркера BEGIN над ним ни с чем не образует пару. Блок, для которого структура
файла не показывает его случай (скажем, блок под блоком, содержащим блок
кода), не получает собственного исправления, и тогда ещё одно исправление,
"in any other case", меняет каждую строку маркера BEGIN в файле. Откройте
названный файл на строках, которые даёт предупреждение:

1. Выберите исправление для блока, который содержит правила Apothem. В файле,
   который начинается с frontmatter Apothem, это блок прямо под ним: удаление
   убирает этот frontmatter только вместе с блоком прямо под ним.
2. Выполните шаги этого исправления в указанном порядке. Каждый шаг меняет
   строку маркера BEGIN на месте, поэтому текст под ней остаётся: ваша пара
   маркеров сохраняет ваш пример, а текст более старого или вставленного блока
   Apothem, вплоть до строки его маркера END, затем удаляете вручную вы.
   Каждое исправление действует как для следующего обновления, так и для
   удаления. Не удаляйте блок Apothem, чтобы сохранить свою пару: тогда
   следующее удаление убрало бы вашу пару как единственный оставшийся блок.
   Не перемещайте свою пару и в блок кода: как только собственный блок
   Apothem перестанет быть целым (скажем, потеряет свой маркер END), пара
   маркеров в коде не даёт установке и обновлению записать блок Apothem, пока
   запись об установке перечисляет файл (см.
   [Apothem не может отличить свой блок от вашего текста](#apothem-cannot-tell-its-block-from-your-text)).
3. Выполните `apothem update`, затем снова `apothem verify`. После удаления,
   которое не завершилось, вместо этого снова выполните `apothem uninstall`.

Маркер BEGIN над блоком Apothem и маркер END под ним образуют второй блок,
который проявляется, только когда блок Apothem убран. Тогда предупреждение
удаления называет блок Apothem и эти две строки маркеров, например "once the
block from line 5 to line 36 is out, the BEGIN marker at line 2 and the END
marker at line 39 make another", и говорит "Do not delete the block from line
5 to line 36": тогда следующий запуск прочитал бы строки со 2 по 39 как блок
Apothem и заменил бы или убрал то, что между ними. Его единственное
исправление вместо этого меняет ту строку маркера BEGIN, сохраняя ваш
собственный текст, например "Fix A, if lines 5 to 36 are Apothem's block: A1.
Change line 2: add a word inside its comment. Lines 5 to 36 are then the one
block in the file."; затем снова запустите удаление. Маркер END ниже тогда ни
с чем не образует пару, поэтому может остаться, скажем, как пример, который
вы цитируете в блоке кода. Не помещайте обе строки в один блок кода: он
содержал бы и блок Apothem. Если этот маркер BEGIN — то, что осталось от
более старого блока Apothem, старый текст Apothem под ним затем удаляете
вручную вы. `apothem update` тоже не исправляет такой файл, а
`apothem verify` завершается сбоем, пока вы его не исправите.

### Apothem не может отличить свой блок от вашего текста [#apothem-cannot-tell-its-block-from-your-text]

Предупреждение называет файл и говорит "Apothem cannot tell whether the marker
lines in this file mark its block or text of yours". Вы видите его, когда
ограждение кода над блоком Apothem осталось открытым, а ограждение, которое
вы добавили ниже, закрыло его: тогда блок оказывается внутри вашего блока
кода. Программа просмотра Markdown показывает эти строки как код, и те же
строки могли бы быть парой маркеров, которую вы цитируете как пример, поэтому
Apothem не может определить, его ли это блок или ваш текст. То же относится к
паре в коде с отступом или с отступом под абзацем, а также к маркеру BEGIN вне
кода, маркер END которого находится в коде, а за ними следует ещё одна пара
маркеров: любая из пар может быть блоком Apothem. Закрывающая строка внутри
собственного блока Apothem тоже может закрыть ваш блок кода, оставленный
открытым над ним (см. ниже).

Предупреждение называет каждую пару маркеров в файле по строкам двух её
маркеров и говорит, как они читаются, например "The BEGIN marker at line 6
and the END marker at line 38 sit inside a code block that opens at line 3."
Оно также называет каждый маркер BEGIN вне кода, который не начинает пару
маркеров, например "The BEGIN marker at line 1 starts no marker pair: its END
marker is gone, or the marker is yours." Затем идут пронумерованные
исправления — в предупреждениях `apothem install`, `apothem update` и
`apothem uninstall`, в примечании `apothem verify` и в исправлении, которое
выводит `apothem doctor`, — например "Fix A:
A1. Change line 6: add a word inside its comment. Apothem then reads none of
these lines as its markers, and the next update writes its block at the end of
the file." Пара, обе строки маркеров которой читаются вне кода (идущая после
маркера BEGIN, маркер END которого находится в коде), получает собственное
исправление на случай, если это блок Apothem, там, где структура файла
показывает, что тогда она читается как единственный целый блок; последнее
исправление, "in any other case", когда перед ним есть другие, меняет каждую
строку маркера BEGIN в файле. Как их читать, см.
[Следование пронумерованному исправлению](#follow-a-numbered-fix).

Пока запись об установке перечисляет файл (до завершения удаления; журнал
установки, который невозможно прочитать, считается такой записью; запись,
сделанная при другом написании пути к папке, например при доступе к вашему
домашнему каталогу через ссылку, тоже считается, как и для удаления, когда у
написания, под которым вы запускаете, есть собственная установка, всё ещё
находящаяся на месте, и инструмент записывает
[общие папки в вашем домашнем каталоге](/docs/cli-reference/install#folders-in-your-home-directory)),
`apothem install` и `apothem update` ничего в нём не меняют и выводят это
предупреждение; при пробном запуске оно говорит, что Apothem "would leave the
file as it is". Для маркера BEGIN вне кода, маркер END которого находится в
коде, а за ними следует ещё одна пара маркеров, они поступают так с записью
или без неё. Каждый такой запуск завершается частично: вместо строки `✓` он
выводит строку `✗`, которая называет файл, его `status` в `--format json`
равен `"partial"`, и он завершается с кодом `2`. Предупреждение так и
говорит: "Until you fix these marker lines as this text says, install
and update leave this file as it is and end as partial (exit code 2)."
Предупреждение запуска, который записал файл и поэтому завершается успешно,
начинает это предложение словами "From the next run on, until you fix these
marker lines". Это длится, пока строки маркеров остаются как есть, включая
ваш пример маркеров в блоке кода: такая пара может быть блоком Apothem внутри
вашего блока кода, поэтому предупреждение добавляет, что ваш пример так же
удерживает файл, пока вы не измените строку его маркера BEGIN, например
добавив слово внутрь его комментария, как в
`<!-- BEGIN APOTHEM MANAGED BLOCK (example) -->`. Для пары, строки маркеров
которой читаются как часть абзаца над ними, оно называет пару "a marker
example of yours that reads as part of a paragraph". Ничто другое этого не
прекращает: удаление тоже не завершается, пока пара на месте. Маркер BEGIN
вне кода, который не начинает пару, этого не меняет, даже когда каждая пара
маркеров в файле цитируется в коде под ним: маркер может быть остатком блока
Apothem после потери его маркера END, но пара в коде может быть блоком
Apothem внутри вашего блока кода. Предупреждение называет такой маркер BEGIN
первым, и каждое исправление меняет его. Примечание
`apothem verify` и исправление, которое выводит `apothem doctor`, дают то же
предложение о частичном завершении только там, где установка и обновление
оставили бы файл как есть: без записи об установке пара маркеров, которую вы
цитируете в коде, не удерживает файл (см. ниже), если только пара не содержит
ровно тот блок, который записывает установка. Примечание и исправление не
проверяют наличие этого блока, поэтому для такой пары они опускают это
предложение; следующее обновление оставляет файл как есть, завершается
частично и сообщает об этом.

Apothem закрывает блок кода, который правило в вашем профиле открывает и
никогда не закрывает, в конце записываемого им блока, поэтому маркер END
этого блока никогда не оказывается в коде. В блоке, который более ранний
релиз записал из такого правила, закрывающей строки нет. Если за ним следует
ваша пара маркеров, установка и обновление оставляют файл как есть. Ни одно
исправление не сохраняет этот более старый блок: ваша строка под ним
закрывает блок кода, который открыло его правило, и как только следующее
обновление заменило бы блок, эта строка открыла бы блок кода поверх вашего
текста. Исправление на случай, если пара после него является блоком Apothem,
меняет строку маркера BEGIN более старого блока, например "Fix A, if lines 8
to 10 are Apothem's block: A1. Change line 1: add a word inside its
comment.", а последнее исправление меняет каждую строку маркера BEGIN; текст
более старого блока затем удаляете вручную вы.

Эта закрывающая строка или закрывающая строка блока кода, который записывает
правило в вашем профиле, также может закрыть ваш блок кода, который
открывается над блоком Apothem и никогда не закрывается, скажем, в конце
ваших заметок. Тогда блок читается как код начиная с его маркера BEGIN.
Установка или обновление, которые его записали, сразу выводят
предупреждение, не говоря, что оставили файл как есть, например "The
BEGIN marker at line 6 sits inside a code block that opens at line 3, and the
END marker at line 44 is outside code." Его исправление меняет эту строку
маркера BEGIN, как в "Fix A: A1. Change line 6: add a word inside its
comment.": следующее обновление записывает блок Apothem в конец файла, под
строкой, которая закрывает ваш блок кода, а старый блок затем удаляете
вручную вы. Пробный
запуск читает файл до того, как что-либо записано, поэтому не показывает, что
блок читался бы как код после записи. Удаление блока вместо этого не
помогает: следующее обновление снова записывает его под тем же открытым
блоком кода. Обновление, которое записывает свой блок под более старым
блоком, потерявшим свой маркер END, где правило оставило блок кода открытым,
получает то же предупреждение; оно также называет этот более старый маркер
BEGIN, и каждое исправление меняет его.

Пока вы не исправите файл, `apothem verify` завершается сбоем, а
`apothem doctor` сообщает о нём (как `harness.stray_begin`); для файла,
который записывает текущая установка, `apothem status --profile` тоже
показывает дрейф. Без записи об установке verify и doctor не проверяют
`CLAUDE.md` или документ профиля: только запись показывает, что эти файлы
записала установка. Проверка OpenClaw всё равно проверяет файл правил в
каждом рабочем пространстве, которое находит, и завершается сбоем, не называя
файл.

С записью об установке `apothem uninstall` оставляет файл как есть, удаляет
остальную часть установки и остаётся незавершённым (код выхода `2`, включая
повторный запуск), пока вы не исправите файл: запись об установке остаётся,
поэтому последующая установка тоже оставляет файл как есть, а следующее
удаление снова называет его. Его предупреждение даёт пронумерованные
исправления тем же образом и заканчивается словами "Then run the
uninstall again.", например "Fix A: A1. Change line 6: add a word inside
its comment. Apothem then finds no block of its own in this file." Любая пара
маркеров, оставшаяся в таком файле, оставляет удаление незавершённым, даже
если она ваша, поэтому каждое исправление меняет строку маркера BEGIN каждой
пары, которую оно не называет блоком Apothem. Его строка
`✗ <harness> uninstall did not finish:` продолжается словами "1 file(s) hold
marker lines Apothem cannot tell from your text, so Apothem left them as they
are; fix the marker lines each warning names, keeping your own text, then run
apothem uninstall again". Без записи об установке предупреждение получает
только маркер BEGIN вне кода, маркер END которого находится в коде, а за
ними следует ещё одна пара маркеров, и удаление остаётся незавершённым (код
выхода `2`) из-за него и из-за путей, которые не показывает ни одна запись
(см.
[Удаление, которое не завершилось](/docs/cli-reference/uninstall#an-uninstall-that-did-not-finish)).

Выполните каждый шаг выбранного исправления. Если вы удалите только блок
Apothem и оставите свой маркер BEGIN над маркером END, который вы цитируете в
коде, без пары маркеров после них, эти два маркера читаются как блок
Apothem: повторно запущенное удаление убирает строки между ними, а
последующая установка или обновление заменяет их.

Без записи об установке пара маркеров, которую вы цитируете в коде, — это ваш
текст: установка добавляет свой блок после неё (в файле правил, который
Apothem записывает с frontmatter, этот frontmatter и блок вместо этого
помещаются в начало), если только пара не содержит ровно тот блок, который
записывает установка, и тогда она оставляет файл как есть и выводит
предупреждение. Поэтому если запись об установке пропала (скажем, журнал был
удалён), удалите блок Apothem из вашего блока кода вручную: последующая
установка считает его вашим текстом.

Чтобы исправить это, откройте названный файл на строках, которые даёт
предупреждение. Определите, какой случай верен: являются ли строки, которые
называет исправление, блоком Apothem, с правилами Apothem между маркерами,
или вашим примером. Выполните шаги этого исправления в указанном порядке и
никаких других шагов (см.
[Следование пронумерованному исправлению](#follow-a-numbered-fix)). Затем
выполните `apothem update`, а затем снова `apothem verify`. После удаления,
которое не завершилось, вместо этого снова выполните `apothem uninstall`.

### Следование пронумерованному исправлению [#follow-a-numbered-fix]

Предупреждения для файла, строки маркеров которого Apothem не может
разместить, для файла с двумя или более целыми блоками, для маркера BEGIN без
маркера END и для блока Apothem, который оставляет удаление без записи об
установке, дают каждое исправление в виде пронумерованных шагов под меткой,
которая называет его случай, например "Fix A,
if lines 6 to 38 are Apothem's block:", или "Fix A:" для исправления, которое
действует независимо от того, какие строки принадлежат Apothem. Шаги
исправления A — "A1.", "A2." и так далее, исправления B — "B1.", "B2.", в
одном абзаце, а исправление заканчивается тем, что затем делает следующий
запуск. Выполняйте шаги только одного исправления.

Каждый номер строки в шаге — это номер строки в файле в том виде, в каком он
есть, когда выводится предупреждение, подсчитанный так, как Apothem считает
строки (см.
[В файле есть маркер BEGIN Apothem без маркера END](#a-file-has-an-apothem-begin-marker-with-no-end-marker)).
Шаги идут снизу файла вверх, в указанном порядке. Каждый шаг — один из
следующих, слово в слово, и заканчивается точкой:

| Шаг | Что делать |
| --- | --- |
| `Change line N: add a word inside its comment.` | Добавьте слово в строку N прямо перед её закрывающим `-->`, как в `<!-- BEGIN APOTHEM MANAGED BLOCK (example) -->`. Строка остаётся на месте и больше не читается как маркер. |
| `Below line N, add a line of 3 backticks.` | Добавьте новую строку прямо под строкой N, последней строкой файла, которая содержит указанное число символов обратного апострофа, или символов тильды для `tildes`, и ничего больше. Если перед точкой стоит `, indented 2 spaces`, поставьте перед ними столько пробелов; без этого начинайте строку у левого поля. |

Каждый шаг `Change line` меняет строку маркера BEGIN на месте. Каждый блок
Apothem, пара маркеров и лишний маркер начинается с маркера BEGIN, а маркер
END образует пару только с маркером BEGIN прямо над ним, поэтому маркер END
без маркера BEGIN над ним ничего не отмечает, а тот, который вы цитируете,
остаётся вашим текстом как есть. Изменённая строка по-прежнему является
комментарием HTML на отдельной строке: ни одна строка не сдвигается, и
программа просмотра Markdown читает каждую другую строку как прежде.

Исправление, которое сохраняет блок, меняет каждую другую строку маркера
BEGIN в файле. Предупреждение даёт его только там, где структура файла
показывает, что тогда блок читается как единственный целый блок: его не
содержит ни один ваш блок кода, идущий до конца файла, и ни одна строка от
первой изменённой строки вниз до блока не меняет того, как читается его
маркер BEGIN. Оно заканчивается словами "The next update then
replaces Apothem's block", "Lines 1 to 32 are then the one block in the
file" или, для удаления, "The uninstall run again then takes Apothem's
block out". Исправление, которое не сохраняет ни одного блока, меняет каждую
строку маркера BEGIN в файле и заканчивается словами "Apothem then reads none
of these lines as its markers, and the next update writes its block at the
end of the file" или, для удаления, "Apothem then finds no block of its own in
this file". В любом случае любой старый текст Apothem под изменённой вами
строкой, вместе со строкой его маркера END, затем удаляете вручную вы.

Ваш блок кода, который не закрывает ни одна строка, в программе просмотра
Markdown идёт до конца файла, но Apothem читает его открывающую строку как
текст. Блок кода в правилах вашего профиля закрыл бы его, и тогда маркер
BEGIN блока Apothem читался бы как код. Поэтому, когда ваш файл заканчивается
внутри такого блока кода, исправление, которое не оставляет в файле блока
Apothem, сначала добавляет закрывающую строку этого блока кода под последней
строкой, как в "A1. Below line 7, add a line of 3
backticks.": следующая установка или обновление добавляет свой блок в конец
файла, после неё. Ни одно исправление не сохраняет блок, который содержит
такой блок кода.

Apothem читает ограждение кода внутри блока HTML, например комментария,
который открывается с `<!--` и заканчивается на более поздней строке, так же
как любое другое ограждение кода, а строка текста элемента списка, которая
продолжается у левого поля, для Apothem завершает этот элемент. Программа
просмотра Markdown не делает ни того, ни другого. Когда строка над блоком
кода, которым заканчивается ваш файл, может начинать блок HTML (считается
любая строка, начинающаяся с тега, кроме ссылки в угловых скобках, тега на
строке прямо под строкой обычного текста и HTML в блоке кода), или текст
элемента списка продолжается у левого поля над ним и за ним следует строка с
отступом, та закрывающая строка могла бы вместо этого начать блок кода в
программе просмотра. Тогда это исправление не даёт пронумерованных шагов:
оно говорит "Apothem cannot give numbered steps for this fix" и называет
строку, которая открывает блок кода. Отредактируйте файл вручную так, чтобы
эта строка не открывала блок кода или чтобы блок кода был закрыт там, где,
по показу вашей программы просмотра, он заканчивается; следующее
предупреждение для файла тогда даёт пронумерованные шаги.

### Хуки не срабатывают в Claude Code

Убедитесь, что Apothem подключён, проверив наличие записей хуков в
~/.claude/settings.json. Если в файле отсутствуют хуки, запустите apothem
install снова.

### OpenCode не загружает правила Apothem

`apothem install`, `apothem update` и `apothem verify` выводят примечание,
когда ваш файл в папке конфигурации OpenCode не даёт OpenCode 1 загрузить
список `instructions`, который Apothem записывает в `opencode.json`:

- `opencode.jsonc` с собственным списком `instructions`, даже пустым,
  заменяет список Apothem. Удалите этот ключ или перенесите его элементы в
  список в `opencode.json`, где установки сохраняют элементы, которые они не
  записывали.
- `config.json`, `opencode.json` или `opencode.jsonc` там, который OpenCode 1
  не может прочитать или разобрать, не даёт OpenCode 1 загрузить какую-либо
  его конфигурацию. То же самое делает файл, верхний уровень которого не
  является объектом, значение `instructions` которого не является списком
  текстовых строк или `{file:path}` которого называет файл, который
  OpenCode 1 не может прочитать, а также папка с одним из этих имён.
  Исправьте файл так, чтобы он был одним объектом JSON, к которому добавлены
  только комментарии и завершающие запятые, с `instructions` в виде списка
  текстовых строк, или перенесите его из папки. Когда примечание говорит, что
  файл ломается, как только OpenCode 1 подставляет свои значения
  `{env:NAME}`, измените эту переменную так, чтобы её значение не содержало
  обратной косой черты, двойной кавычки или управляющего символа, например
  путь Windows, записанный с прямыми косыми чертами. Когда примечание
  говорит, что Apothem записывает этот `{env:NAME}` для сервера MCP в вашем
  профиле, обновление записывает обратно ссылку, удалённую из файла, поэтому
  измените переменную или, чтобы сохранить её как есть, заново укажите этот
  сервер в `harnesses.opencode.mcp_servers.<name>` со значением, сохранённым
  в файле и записанным как `{file:path}`, который его называет. Когда
  примечание называет вторую проблему с файлом, исправьте и её. Когда оно
  говорит, что Apothem не может определить, может ли OpenCode 1 прочитать
  файл, который называет `{file:path}`, убедитесь, что и этот файл доступен
  для чтения.

Эти примечания касаются OpenCode 1. OpenCode 2 читает оба списка и не читает
`config.json`. Он пропускает файл, который не может разобрать или верхний
уровень которого не является объектом, а для `opencode.json` это означает,
что он пропускает и правила; примечание говорит, что OpenCode 2 делает со
своим файлом, когда это известно. Примечания не меняют ни файлов, ни кода
выхода. Когда установка или обновление вообще не могут разобрать
`opencode.json`, они вместо этого останавливаются с ошибкой
`config.unparseable`. Подробности см. на странице
[OpenCode](/docs/harnesses/opencode).
