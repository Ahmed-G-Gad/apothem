Apothem устанавливается менее чем за две минуты и работает рядом с вашей
существующей конфигурацией окружения. Каждый путь запускает один и тот же
самодостаточный движок — дерево исходного кода несёт свои вендоренные
зависимости и запускается из чекаута на системном Python 3.10 или новее (см.
[самодостаточную среду выполнения](/docs/architecture/self-contained-runtime)).

**Два предварительных требования общие для всех путей:** системный
**Python 3.10 или новее** в `PATH`, под которым импортируются пакеты `click` и
`rich`. Для npm-шима (канал 2), расширения для семейства VS Code (канал 4) и
загрузчиков командной строки (каналы 5–7) дополнительно нужен **Node.js 18 или
новее** для запуска `npx`. У Python 3.10 и Node.js 18 и 20 закончился срок
поддержки в upstream; они остаются поддерживаемыми и тестируемыми, но
предпочтительны более новые версии (см.
[Предварительные требования кратко](#предварительные-требования-кратко)).
Собственный раздел каждого канала ниже повторяет его точные предварительные
требования, одну готовую к копированию команду и шаг проверки.

Каждый путь идемпотентен: повторный запуск безопасен и приводит к тому же
состоянию.

## 1. Плагин Claude Code

**Предварительные требования:** Claude Code и системный Python 3.10+ в `PATH`.

Путь плагина выполняется целиком внутри Claude Code. Он поставляет движок
Apothem вместе с его слеш-командами, делегированными исполнителями, навыками,
правилами и хуками — всё это запускается из самодостаточного дерева плагина:

```text title="Inside Claude Code"
/plugin marketplace add ahmed-g-gad/apothem
/plugin install apothem@apothem
```

После установки набор команд Apothem, входящие в комплект делегированные
исполнители, навыки и четыре [output-стиля](/docs/reference/output-styles)
(выберите один через `/output-style` или в `/config`) доступны в каждой сессии
Claude Code. Плагин поставляет каждую команду как навык — файл `SKILL.md`,
подробности к которому, загружаемые по требованию, лежат рядом в папке
`references/`, — поэтому Claude Code вызывает её с префиксом плагина:
`/apothem:plan-spec`, `/apothem:security-audit` и остальные. Два имени заняты
самим Claude Code: `/plan` включает режим планирования, а `/code-review`
запускает встроенное ревью, поэтому для команд Apothem вводите
`/apothem:plan` и `/apothem:code-review`. Когда в Claude Code вместо плагина
устанавливается движок Apothem, те же навыки записываются в
`~/.claude/skills/` без префикса, а личный навык `code-review` заменяет
встроенный `/code-review` (его псевдоним `/review` по-прежнему запускает
встроенный). Два имени, `projectify` и `workflow`, также являются нативными
навыками; плагин и установка движка поставляют именно нативный навык, а не
навык, созданный из команды. О том, как разделены команды, см.
[Claude Code](/docs/harnesses/claude-code#command-skills-and-reference-files),
а полный каталог команд — в разделе [Слеш-команды](/docs/reference/commands).

**Проверка:** запустите `/plugin` внутри Claude Code и убедитесь, что
**apothem** указан как установленный, либо проверьте отчёт о дрейфе из
терминала:

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 2. npm-шим (`npx`)

**Предварительные требования:** Node.js 18+ (для `npx`) и системный Python 3.10+
в `PATH`. Шим находит интерпретатор и передаёт каждую команду CLI встроенному
движку — ничего не размещается в вашей системе постоянно. Он пробует
`python3`, `python`, затем `py -3` в этом порядке; задайте в
**`APOTHEM_PYTHON`** путь к интерпретатору, чтобы он был опробован первым, —
это нужно, когда Python установлен, но не находится в `PATH`, или когда
установлено несколько версий и вам нужна конкретная. Указанный вами
интерпретатор всё равно должен пройти проверку на Python 3.10+; если он её не
проходит, шим переходит к `python3`, `python`, затем `py -3`.

```bash title="npx"
npx @ahmed-g-gad/apothem install --harness claude-code
```

На машине без профиля эта первая команда `install` создаёт начальный профиль в
`~/.config/apothem/profile.yaml` и сообщает об этом. Его поля идентичности —
заполнители: персонализируйте их (`npx @ahmed-g-gad/apothem profile edit`),
затем повторите команду с `update` вместо `install`, чтобы применить их.

Он также запускается прямо из репозитория:

```bash title="npx from the repository"
npx github:ahmed-g-gad/apothem install --harness claude-code
```

Каждая команда из [справочника CLI](/docs/cli-reference) работает в этой форме;
замените `apothem` на `npx @ahmed-g-gad/apothem`. Это также путь установки для
OpenCode и любого другого инструмента, который не предоставляет отдельного
реестра плагинов или расширений, — Apothem синхронизирует их прямо в их
нативный каталог конфигурации
(`npx @ahmed-g-gad/apothem install --harness opencode`).

**Проверка:**

```bash title="Verify"
npx @ahmed-g-gad/apothem --version
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 3. Одношаговые установщики

**Предварительные требования:** системный Python 3.10+ в `PATH` (установщик предлагает добавить за вас предварительные требования `click` / `rich`). Для сетевой установки: `git`, чтобы найти последний релиз, и `gpg`, чтобы проверить подписанный тег релиза (Git for Windows поставляется с обоими). [cosign](https://docs.sigstore.dev/cosign/system_config/installation/)
необязателен: с ним установщик также проверяет подписанный архив релиза.

Скрипты установщика определяют последний релиз, проверяют его (см.
[Модель доверия](#trust-model)), размещают дерево исходного кода Apothem в
`~/.apothem`, создают начальный профиль, если его нет, материализуют ваше
первое окружение и проверяют результат — всё за один запуск. Начальный профиль
содержит поля идентичности с заполнителями: отредактируйте его, затем
выполните `apothem update --harness <name>`, чтобы применить свои значения.
Повторный запуск идемпотентен: в git-клон загружаются изменения, его новый тег
проверяется, и только после этого клон переключается на определённый тег;
установка из архива релиза обновляется на месте; а окружение материализуется
повторно. Когда движок завершается частично (код выхода `2`), установщик
выводит строку предупреждения, всё равно выполняет проверку, размещает команду
`apothem` и выводит её баннер, а затем завершается с кодом выхода `2`. Движок
завершается частично, когда оставляет файл как есть из-за его маркерных строк
Apothem или когда останавливается уже после того, как что-то записал (см.
[Когда движок оставляет файл как есть](/docs/install/updating#when-the-engine-leaves-a-file-as-it-is)).
Проверенная установка — путь по умолчанию и рекомендуемый путь.

Сначала однократно импортируйте ключ подписи сопровождающего. Каждая сетевая установка проверяет по нему тег релиза, с cosign или без него, и останавливается, если ключа нет в вашей связке ключей. Проверьте, что отпечаток равен `5C89 98F9 F241 7204 45D3  F28B 7039 6FED 9C63 4163`, то есть значению, которое публикует [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md#maintainer-signing-key). В Windows `git verify-tag` читает связку ключей `gpg`, которая поставляется с Git for Windows, поэтому импорт выполняется через собственный `bash` Git:

```bash title="macOS · Linux · WSL2 · BSD — import the key once"
curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import
gpg --fingerprint 70396FED9C634163
```

```powershell title="Windows · PowerShell — import the key once"
& "$env:ProgramFiles\Git\bin\bash.exe" -c 'curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import && gpg --fingerprint 70396FED9C634163'
```

```bash title="macOS · Linux · WSL2 · BSD — latest signed tag, verified"
curl -fsSL https://apothem.ahmedgad.com/install.sh | bash
```

```powershell title="Windows · PowerShell — latest signed tag, verified"
irm https://apothem.ahmedgad.com/install.ps1 | iex
```

Те же скрипты поставляются в чекауте в `scripts/installer/` — `install`,
`uninstall` и `update` в формах `.sh`, `.ps1` и `.bat`, — так что вы можете
запускать их напрямую после клонирования:

```bash title="From a checkout"
APOTHEM_HARNESS=claude-code sh scripts/installer/install.sh                                 # POSIX
$env:APOTHEM_HARNESS = 'claude-code'; pwsh -NoProfile -File scripts/installer/install.ps1   # Windows
```

Однострочник с конвейером никогда не использует локальное дерево: `curl ... | sh`
и `irm ... | iex` игнорируют папку, из которой вы их запускаете, и её
родительские папки, а загружают и проверяют релиз. Установщик использует
локальное дерево, только когда вы запускаете собственный
`scripts/installer/install.sh` (или `install.ps1`) чекаута по его пути из любой
папки (например, `sh ~/src/apothem/scripts/installer/install.sh`) или когда
`APOTHEM_SOURCE` указывает на это дерево. Установщики, скрипты обновления и
удаления, шимы `apothem`, npm-лаунчер, хуки и процессы валидаторов шлюза
соответствия не допускают текущую папку в путь поиска модулей Python. Команда
`python -m apothem`, которую вы вводите сами, этого не делает: `-m` сначала
читает модули из текущей папки.

Пустые и относительные записи вашего собственного `PYTHONPATH` не передаются
движку ни одним лаунчером (установщики, скрипты обновления и удаления, шимы
`apothem` для POSIX и Windows и npm-лаунчер). Сохраняемая запись должна быть
полным путём: в Windows — путь с буквой диска, например `C:\lib`, или сетевой
путь, в остальных системах — путь, начинающийся с `/`. Корневой путь `\lib` или
путь относительно диска `C:lib` отбрасывается. Скрипты sh спрашивают
запускаемый ими Python, какую форму он читает, и шим `apothem`, который они
записывают, сохраняет эту форму. Python для Windows (обычный под Git Bash)
получает пути движка в форме Windows, объединённые через `;`, и сохраняет
только пути с буквой диска и сетевые пути из вашего `PYTHONPATH`. Python для
POSIX, включая собственный `python3` Cygwin и MSYS2, получает пути POSIX,
объединённые через `:`, и сохраняет только записи, начинающиеся с `/`. Команды
`git` установщиков, которые не работают с клоном, не читают репозиторий в
текущей папке.

### Флаги установщика

`install.sh` принимает флаги ниже, а `install.ps1` — те же переключатели в виде
параметров PowerShell. `install.bat` принимает написание `install.sh` для первых
трёх строк и передаёт каждый флаг в `install.ps1`. Однострочная команда через
конвейер не может передать параметр PowerShell, поэтому, чтобы использовать
его, сначала скачайте `install.ps1`:

```bash title="Pass a flag"
curl -fsSL https://apothem.ahmedgad.com/install.sh | sh -s -- --dry-run    # POSIX
irm https://apothem.ahmedgad.com/install.ps1 -OutFile install.ps1; pwsh -NoProfile -File install.ps1 -DryRun   # Windows
```

| `install.sh` | `install.ps1` | Действие |
|---|---|---|
| `--clean`, `--fresh` | `-Clean`, `-Fresh` | Перед установкой создаёт резервную копию и удаляет четыре папки в вашем домашнем каталоге, которые перечисляет [`apothem install`](/docs/cli-reference/install#blast-radius-preview), в том числе `~/.claude` и `~/.agents`, какое бы окружение вы ни устанавливали, а затем устанавливает заново. Установщик передаёт флаг движку как `apothem install --clean`; движок спрашивает перед каждым удалением, хранит резервную копию в `~/.apothem/backups` и записывает ваш профиль обратно. |
| `--dry-run` | `-DryRun` | Загружает и проверяет выпуск во временной папке и показывает, что изменила бы установка, ничего не меняя (см. [Модель доверия](#trust-model)). |
| `--yes` | `-Yes` | Не спрашивает перед каждым удалением при `--clean`. Также разрешает замены содержимого `APOTHEM_HOME`, для которых [Модель доверия](#trust-model) требует `--yes`. |
| `-h`, `--help` | нет | Выводит флаги и модель доверия и завершает работу. |

### Модель доверия [#trust-model]

Если `APOTHEM_REF` не задана, установщик определяет наивысший релиз
`vMAJOR.MINOR.PATCH` и устанавливает *именно его* — никогда не подвижную ветку
`main`. Он проверяет релиз до материализации любой конфигурации, и проверка
зависит от того, есть ли `cosign` в вашем `PATH`:

- **С cosign** должны пройти обе проверки. Сначала тег релиза должен нести
  действительную подпись ключом сопровождающего, проверяемую как в следующем
  пункте, и подписанный тег должен быть тем, что назван для этого релиза:
  подписанный тег другого релиза, перенаправленный на это имя, отклоняется.
  Затем установщик скачивает платформенный архив релиза, его файл `SHA256SUMS`
  и `SHA256SUMS.cosign.bundle`. cosign должен подтвердить, что релизный рабочий
  процесс Apothem подписал `SHA256SUMS` именно для этого тега, и с помощью
  своей проверки `--certificate-github-workflow-sha` — что проверенный им
  сертификат был выдан запуску на коммите, на который указывает подписанный
  тег. Сам установщик сертификат не читает. Затем SHA-256 архива должен
  совпасть с указанным дайджестом. Рабочий процесс запускается для любого
  отправленного тега, поэтому одной его подписи недостаточно; подпись тега
  показывает, что сопровождающий выпустил этот коммит.
- **Без cosign**, или когда `APOTHEM_HOME` уже содержит git-клон, установщик
  клонирует или обновляет репозиторий и проверяет только тег с помощью
  `git verify-tag`. Подпись должна быть действительной *и* сделанной ключом
  сопровождающего, опубликованным в [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md), а подписанный тег должен быть тем, что назван для
  релиза. Тег, подписанный любым другим ключом, отклоняется, даже если ваша
  связка ключей доверяет этому ключу. Подписанный git-тег называет свой коммит
  по идентификатору SHA-1; с cosign установщик также проверяет SHA-256 архива.
  В существующий клон загружаются изменения, и его новый тег проверяется
  *до* переключения клона. Неудачная проверка оставляет клон как был, а клон с
  изменениями в отслеживаемых файлах останавливает обновление с сообщением
  зафиксировать их или убрать в stash, вместо того чтобы их потерять. С
  нерелизной ссылкой, например `main`, существующий клон следует за копией
  этой ветки в origin.

Установщик игнорирует переменные окружения git, которые перенаправляют git
(`GIT_DIR`, `GIT_WORK_TREE` и подобные), и те, что указывают git на другой
файл конфигурации (`GIT_CONFIG`, `GIT_CONFIG_GLOBAL` и `GIT_CONFIG_SYSTEM`) или
заставляют его читать атрибуты из другого дерева (`GIT_ATTR_SOURCE`; `attr.tree`
в вашей собственной конфигурации очищается в каждой команде git, выполняемой на
клоне), и останавливается, когда `APOTHEM_REPO` начинается с `-`.
`GIT_CONFIG_NOSYSTEM` остаётся таким, как вы его задали; он лишь запрещает git
читать системную конфигурацию. git по-прежнему читает вашу собственную
глобальную конфигурацию и, если вы не задали `GIT_CONFIG_NOSYSTEM`, системную
конфигурацию из обычных мест, а `git`, `gpg` и `cosign` — это программы,
которые находит ваш `PATH`: установщик доверяет им в найденном виде. На всё
время запуска установщик задаёт `GIT_NO_REPLACE_OBJECTS=1`, чтобы git никогда
не подменял объект через ссылки замены, `GIT_NO_LAZY_FETCH=1`, чтобы git
никогда сам не загружал отсутствующий объект с удалённого репозитория,
`GIT_ALLOW_PROTOCOL` — на транспорты file, git, http, https и ssh, чтобы
значение в вашем окружении не могло расширить этот список, и
`GIT_ATTR_NOSYSTEM=1`; поскольку `core.attributesFile` очищается в каждой
команде git, выполняемой на клоне, git тогда не читает ни одного файла
атрибутов вне клона, и макрос, определённый в вашем, не может назвать там
фильтр. Скрипт PowerShell восстанавливает все четыре по окончании запуска.
Установщик читает тег релиза один раз, запоминает названный им коммит,
проверяет тег, переключается на этот коммит по идентификатору и требует, чтобы
`HEAD` был этим коммитом, так что тег, перемещённый после проверки, ничего не
меняет. В Windows PowerShell 5.1 и 7 загрузка, перенаправляющая на адрес не по
https, отклоняется, как это делает `curl` в установщиках POSIX.

`APOTHEM_HOME` должна быть папкой, в которую можете писать только вы, поскольку
любой, кто может в неё писать, может изменить код, который запускает команда
`apothem`. В Windows папку, созданную в корне диска, например `C:\apothem`,
при стандартных разрешениях Windows может изменить любой пользователь, который
входит на этот компьютер. Значение по умолчанию, `~/.apothem`, находится в
вашей собственной пользовательской папке. Каждая загружаемая установка,
обновление и пробный запуск предупреждают, не останавливаясь, когда это не
так или когда папка или содержащая её папка принадлежит кому-то другому,
называя папку, того, кто может в неё писать или владеет ею, и способ
исправления; установка из локального чекаута и обновление с заданной
`APOTHEM_SOURCE` пропускают эту проверку. В Windows предупреждение выдают
`install.ps1` и `update.ps1`: `install.sh` и `update.sh` не выполняют проверку
под Git Bash, MSYS2 или Cygwin (см.
[Устранение неполадок](/docs/install/troubleshooting#the-installer-warns-other-users-can-change-apothem_home)).

Неудачная проверка прерывает установку до записи любой конфигурации и до того,
как установщик заменит `APOTHEM_HOME`. Подписанный тег, для которого открытого
ключа сопровождающего ещё нет в локальной связке ключей, вместо этого прерывает
установку с указаниями по импорту ключа: импортируйте ключ, как показано выше,
сверьте его отпечаток со значением, опубликованным в [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md), и запустите установку снова.

Повторный запуск с cosign обновляет более раннюю установку из архива релиза.
Новый исходный код сначала проверяется и распаковывается в папку рядом с
`~/.apothem`, а затем подставляется на её место. Всё в `~/.apothem`, что не
относится к дереву исходного кода, переносится в новую установку: резервные
копии отката движка (`backups/`), журналы установки (`state/`), планы, память и
другие его данные. Если шаг завершается неудачей или вы останавливаете запуск
с помощью Ctrl+C или сигнала завершения, прежняя установка возвращается без
изменений; если не удаётся и это, сообщение называет, где находятся прежние
файлы. Принудительное завершение или отключение питания во время подмены
перехватить нельзя: оно может оставить папки рядом с `~/.apothem`, и следующая
загружаемая установка сообщит о них (см. ниже). Эти правила действуют, когда
установщик заменяет `~/.apothem`:

- Git-клон не заменяется архивом релиза без `--yes`. Файлы, которые клон не
  отслеживает, переносятся в новую установку, а собственное дерево клона (его
  история и исходный код) переносится в новую папку
  `~/.apothem.before-apothem-<time>` под своим именем (`.apothem`); установщик
  сообщает, куда, и вы удаляете её, когда она больше не нужна. Даже с `--yes`
  установщик отказывается, пока клон содержит локальную работу, которую он бы
  потерял: изменения, stash-записи, неотправленные коммиты или
  неотслеживаемые файлы в его дереве исходного кода. Зафиксируйте и отправьте
  эту работу или перенесите её в другое место, затем запустите снова. Эта
  проверка выполняется и с `--dry-run`. Файл `.git` (связанное рабочее дерево)
  считается клоном, как и папка `.git`.
- Git-клон чего-либо, кроме Apothem, обрабатывается как любая папка, не
  содержащая установки Apothem (см. ниже), и никогда не обновляется и не
  заменяется как клон.
- Существующий клон обновляется на месте, только когда git видит каждое
  изменение в нём и ничто в его собственной настройке не запускает код во
  время обновления. Перед загрузкой изменений установщик останавливается,
  когда файлы помечены как assume-unchanged или skip-worktree, когда git не
  находит рабочего дерева в `APOTHEM_HOME` (например, когда конфигурация клона
  задаёт `core.bare` как `true`), когда клон содержит подмодуль (записанный в
  его индексе или хранящийся в `.git/modules`), когда `.git/info/attributes`
  называет фильтр или драйвер diff (`filter=` или `diff=`), когда он или файл
  конфигурации не является обычным файлом или когда клон заимствует объекты из
  другого репозитория (`objects/info/alternates`). Он также останавливается на
  любой настройке в собственных `.git/config` или `.git/config.worktree` клона,
  кроме тех, что `git clone` и `git init` записывают туда для полного клона,
  настроек веток (`remote` и `pushremote` ветки должны быть `origin`),
  `user.name`, `user.email`, `maintenance.auto`, `maintenance.strategy`,
  `pull.rebase` и `pull.ff`, так что частичный клон, созданный с `--filter`,
  тоже останавливает его;
  [Устранение неполадок](/docs/install/troubleshooting#the-installer-stops-the-existing-clone-is-set-up-in-a-way-the-update-would-trust)
  перечисляет их. Сообщение называет настройку и файл, в котором она
  находится. Проверки настроек, атрибутов и объектов выполняются перед любой
  командой git, которая читает индекс или объекты клона, а также, вместе с
  проверкой подмодулей, когда `--yes` вот-вот заменит клон.
  Перед любой командой git, которая применяет файлы `.gitattributes` рабочего
  дерева, установщик останавливается на таком файле, который git не
  отслеживает, который отличается от зафиксированной копии или чью
  зафиксированную копию git не может прочитать либо который называет фильтр
  или драйвер diff (копия в рабочем дереве тоже читается), а также на
  git-репозитории внутри клона, который git не отслеживает и чьи файлы
  `.gitattributes` git тоже прочитал бы. Собственные папки данных движка,
  например `backups`, куда не пишет ни один релиз, для этого не читаются. Перед
  загрузкой изменений он останавливается на файлах в `src` (в любом регистре
  написания), которые git не отслеживает, поскольку движок мог бы их загрузить.
  После переключения он удаляет папки кэша Python (`__pycache__`) в `src` до
  того, как движок запустится из клона. Git-хуки клона никогда не запускаются
  во время обновления, и каждая команда git на клоне выполняется без пейджера,
  без автоматического обслуживания, с отключённым монитором файловой системы,
  только с разрешёнными транспортами file, git, http, https и ssh (так что
  адрес в конфигурации клона не может заставить git запустить
  вспомогательную программу, например `ext::`) и без рекурсии по подмодулям;
  `git diff` и `git status` пропускают подмодули. Клон, которым владеет другой
  пользователь, останавливает запуск с объяснением (см. «Устранение
  неполадок»).
- Папка, которая содержит только собственные данные движка (`backups`,
  `state`, `plans`, `memory`, `contexts`, `learning`, `providers`), обновляется
  без `--yes`, и эти данные сохраняются.
- Папка, которая не содержит установки Apothem, не затрагивается без `--yes`.
  С `--yes` установщик переносит всю папку без изменений в новую папку
  `~/.apothem.before-apothem-<time>` (внутри она сохраняет своё имя), сообщает,
  куда, и выполняет новую установку.
- Символическая ссылка в `APOTHEM_HOME` (в Windows — символическая ссылка или
  соединение) отклоняется, поскольку её замена заменила бы ссылку, а не
  папку, на которую она ведёт. Укажите в `APOTHEM_HOME` эту папку и запустите
  снова. Исключение — существующий git-клон, который обновляется на месте.
- В Linux и macOS файл или папка для переноса, в имени которых есть пробел или
  другой специальный символ, останавливают установку. Сначала перенесите их из
  `APOTHEM_HOME`.

**Один запуск за раз и остановленные запуски.** Каждый запуск скриптов
установки, обновления и удаления берёт блокировку рядом с `APOTHEM_HOME`, по
умолчанию `~/.apothem.lock`, на всё время запуска и освобождает её, когда
запуск заканчивается успехом, неудачей, Ctrl+C или сигналом завершения. Сами
команды `apothem` её не берут. Второй запуск останавливается с сообщением
"Another Apothem install, update or uninstall is running". В POSIX блокировка —
это папка, которая содержит идентификатор процесса запуска. О блокировке,
оставленной принудительно завершённым запуском, сообщается вместе со способом
её удалить, и она никогда не перехватывается, а о блокировке, созданной в
другой среде (например, в WSL и Git Bash на одной машине), сообщается как о
блокировке, процесс которой оттуда проверить нельзя. В Windows PowerShell
блокировка — это файл, который Windows закрывает и удаляет при завершении
процесса. Когда `APOTHEM_HOME` — ссылка, каждый скрипт берёт блокировку рядом с
папкой, на которую она ведёт. Пробный запуск тоже берёт блокировку, если
только папка, содержащая `APOTHEM_HOME`, ещё не существует. Поэтому каждому
запуску, включая обновление на месте, удаление и пробный запуск, нужен доступ
на запись в папку, содержащую `APOTHEM_HOME`; без него запуск
останавливается, ничего не изменив.

Принудительное завершение или отключение питания во время подмены может
оставить прежнюю установку или другие записи `APOTHEM_HOME` в
`.apothem-old.<name>.*`, `.apothem-extract.<name>.*` или
`.apothem-clone.<name>.*` рядом с ней, где `<name>` — последняя часть
`APOTHEM_HOME`, или в папке `APOTHEM_HOME.before-apothem-<time>`. Следующая
загружаемая установка для этой `APOTHEM_HOME`, включая пробный запуск,
останавливается, ничего не изменив, называет каждую папку и перенесённые в неё
записи и объясняет, как перенести их обратно. Для папки, созданной более
ранним установщиком, которая не сообщает, к какой домашней папке относится,
строка может назвать только данные движка: загляните внутрь. Он ничего не
удаляет. См.
[Устранение неполадок](/docs/install/troubleshooting#the-installer-stops-an-earlier-run-left-folders-beside-apothem_home).

`--dry-run` (`-DryRun` в Windows) загружает и проверяет релиз во временной
папке и оставляет `~/.apothem` без изменений. Он выполняет те же проверки, что
и настоящий запуск, с одним исключением для существующего клона: он проверяет
собственную настройку клона, как перечислено выше, но не загружает изменения
в клон и поэтому не проверяет его на изменения в отслеживаемых файлах, что
настоящее обновление делает после загрузки. Закрепите конкретный релиз с
помощью `APOTHEM_REF`:

```bash title="Pinned, verified install"
APOTHEM_REF=vMAJOR.MINOR.PATCH sh -c "$(curl -fsSL https://apothem.ahmedgad.com/install.sh)"
```

Замените `vMAJOR.MINOR.PATCH` на тег со
[страницы релизов](https://github.com/ahmed-g-gad/apothem/releases). Самый
старый тег релиза — легковесный тег без собственной подписи, поэтому проверка
тега прерывается на нём, хотя его коммит подписан; каждый более поздний тег
релиза аннотирован и подписан. Раздел о подписи релизов в
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md)
перечисляет каждый тег и способ его проверки.

Явные переопределения ослабляют поведение по умолчанию. `APOTHEM_ALLOW_UNVERIFIED=1` понижает неудачную проверку тега на пути клона до предупреждения и продолжает работу — для работы в изолированной от сети среде или локально, либо чтобы установить релиз, вышедший до подписи тегов. Он никогда не ослабляет путь cosign, поэтому на хосте с cosign задавайте вместе с ним `APOTHEM_VERIFY=signature`. Он также никогда не ослабляет проверку того, что подписанный тег — тот, что назван для релиза. Поскольку переопределение пропускает неподписанный тег или тег, подписанный другим ключом, эта проверка защищает только теги, несущие подпись ключом сопровождающего. `APOTHEM_REF=main` переключается на подвижную ветку без проверки только вместе с `APOTHEM_ALLOW_UNVERIFIED=1`. Если задан один лишь `APOTHEM_REF=main`, установщик загружает `main` в промежуточную папку (в существующий клон, когда `APOTHEM_HOME` им является), а затем прерывает работу до того, как что-либо переключит, заменит `APOTHEM_HOME` или материализует какую-либо конфигурацию, поскольку ветка не является подписанным тегом релиза. Локальный чекаут через `APOTHEM_SOURCE` ничего не загружает и пропускает проверку.

Задайте `APOTHEM_VERIFY`, чтобы выбрать проверку самостоятельно. По умолчанию
используется `auto`:

| Значение | Что проверяет установщик |
| --- | --- |
| `auto` (по умолчанию) | `release`, когда `cosign` есть в `PATH` и `APOTHEM_HOME` не является git-клоном, иначе `signature` |
| `release` | Подпись тега релиза ключом сопровождающего и то, что подписанный тег — тот, что назван для релиза, затем проверку cosign, что релизный рабочий процесс подписал `SHA256SUMS` в запуске на коммите тега, затем SHA-256 архива. Останавливается, если отсутствует cosign или `gpg` |
| `signature` | GPG-подпись тега релиза, которая должна быть сделана ключом сопровождающего, и то, что подписанный тег — тот, что назван для релиза |
| `checksum` | Только SHA-256 архива по `SHA256SUMS`. Требует `APOTHEM_ALLOW_UNVERIFIED=1` и выдаёт предупреждение перед загрузкой. Режим checksum не проверяет релиз. SHA256SUMS берётся из того же релиза, что и архив, поэтому совпадение лишь показывает, что загрузка не повреждена; любой, кто может изменить файлы релиза, может изменить оба. Используйте его только на хосте без cosign и без `gpg` и только если вы с этим согласны |

Каждый режим с архивом прерывает работу при несовпадении дайджеста до
извлечения чего-либо. В ранних релизах пакет называется `SHA256SUMS.sig`, и
установщик читает это имя, когда `SHA256SUMS.cosign.bundle` отсутствует.

Затем движок выполняется прямо из размещённого дерева. Каждая сторонняя
зависимость, кроме `click` и `rich`, вендорена внутри дерева исходного кода, а
точка входа сама добавляет этот каталог вендоренных зависимостей в `sys.path`.
Установщик выводит полный путь записанного им шима `apothem`. Если он не
записал шим, он выводит команду, которая запускает движок, не допуская текущую
папку в `sys.path`; скопируйте эту команду из баннера.

Оба скрипта читают одни и те же конфигурационные переменные окружения
(`APOTHEM_HOME`, `APOTHEM_REPO`, `APOTHEM_REF`, `APOTHEM_ALLOW_UNVERIFIED`,
`APOTHEM_VERIFY`, `APOTHEM_RELEASE_BASE`, `APOTHEM_SOURCE`, `APOTHEM_HARNESS`,
`APOTHEM_PROFILE`, `APOTHEM_SKIP_VERIFY`, `APOTHEM_AUTO_INSTALL_DEPS`,
`APOTHEM_BIN_DIR`); полную таблицу см. в разделе
[Переменные окружения установщика](/docs/how-to/installer-environment-variables),
а как работает модель вызова `python -m` — в разделе
[Самодостаточная среда выполнения](/docs/architecture/self-contained-runtime).

**Команда `apothem`.** После успешной установки установщик записывает шим
`apothem`, который перенаправляет вызовы встроенному движку, — в POSIX в
`$HOME/.local/bin`, в Windows в `%LOCALAPPDATA%\Microsoft\WindowsApps`
(пользовательский каталог, который уже есть в стандартном `PATH` Windows).
Установщик никогда не редактирует ваш `PATH`. Как только каталог окажется в
`PATH`, вы запускаете `apothem <command>` напрямую, без ручной настройки
`PYTHONPATH`.

**Проверка:**

```bash title="Verify"
apothem verify --harness claude-code

# or, before the shim is on PATH, by the shim's full path:
~/.local/bin/apothem verify --harness claude-code
```

## 4. Расширение для семейства VS Code

**Предварительные требования:** VS Code, Node.js 18+ и системный Python 3.10+ в
`PATH`.

Расширение **Apothem for VS Code** доступно в
[Visual Studio Marketplace](https://marketplace.visualstudio.com/items?itemName=ahmed-g-gad.apothem-vscode)
как `ahmed-g-gad.apothem-vscode`: установите его из представления «Расширения»
или командой `code --install-extension ahmed-g-gad.apothem-vscode`. Оно также
устанавливается из пакета `apothem.vsix`: `code --install-extension apothem.vsix`
или командой редактора *Install from VSIX…*. Релизный рабочий процесс подписывает
пакет и прикладывает его к каждому GitHub Release. Релизы, опубликованные до того,
как рабочий процесс начал упаковывать расширение, не содержат `.vsix`; если в последнем
релизе его нет, соберите пакет из чекаута с версией vsce, зафиксированной в
`tools/vsce/` (этой версии vsce нужен Node.js 22 или новее): выполните
`npm ci --prefix tools/vsce --ignore-scripts`, затем
`cd vscode-extension && ../tools/vsce/node_modules/.bin/vsce package --no-dependencies --out apothem.vsix`.
Копия, установленная из более раннего `apothem.vsix`, имеет идентификатор
`ahmed-g-gad.apothem`; удалите её (`code --uninstall-extension ahmed-g-gad.apothem`),
чтобы обе копии не регистрировали одни и те же команды. Одно расширение охватывает
редакторы семейства VS Code. Его команды палитры (`Apothem: Install`, `Verify`, `Update`, `Uninstall`, `Doctor`)
запускают тот же движок через настроенное средство запуска (по умолчанию
`npx @ahmed-g-gad/apothem@<extension version>`, поэтому расширение запускает
ту версию движка, с которой оно поставлялось; укажите в пользовательской
настройке `apothem.runner` локальный чекаут, чтобы запускать из исходного
кода). Install, Verify, Update и Uninstall спрашивают, с каким окружением
работать, и первым предлагают окружение самого редактора; `all` — один из
вариантов выбора, но никогда не вариант по умолчанию. Настройка
`apothem.runner` действует на уровне машины, поэтому рабочая область не может
её изменить, а расширение работает только в доверенной рабочей области.

**Проверка:** запустите команду **Apothem: Verify** из палитры команд
редактора или из терминала:

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 5. Загрузчик командной строки (хост расширений)

**Предварительные требования:** его хост-инструмент командной строки,
Node.js 18+ и системный Python 3.10+ в `PATH`.

Установите Apothem как расширение прямо из репозитория — команда содержит
точный slug хоста и окружения:

```bash title="Install the extension"
gemini extensions install https://github.com/ahmed-g-gad/apothem
```

Это расширение — **загрузчик**, а не полная установка сама по себе: оно
загружает контекстный файл Apothem и добавляет команду `/apothem`, которая
через оболочку вызывает движок (`npx @ahmed-g-gad/apothem`). Материализуйте
полное окружение, запустив установку через него:

```bash title="Materialize the full harness"
npx @ahmed-g-gad/apothem install --harness gemini-cli --project .
```

**Проверка:**

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness gemini-cli --project .
```

## 7. Загрузчик командной строки (хост плагинов)

**Предварительные требования:** его хост-инструмент командной строки,
Node.js 18+ и системный Python 3.10+ в `PATH`.

Добавьте репозиторий как маркетплейс плагинов, затем установите плагин —
команда содержит точный slug хоста и окружения:

```bash title="Install the plugin"
codex plugin marketplace add ahmed-g-gad/apothem --sparse .agents/plugins --sparse plugins/apothem
codex plugin add apothem@apothem
```

Два пути `--sparse` загружают только листинг маркетплейса и плагин, а не весь
репозиторий; полное клонирование может превысить 30-секундный лимит
клонирования хоста на медленном диске, например на диске Windows под WSL.

Как и расширения каналов 5 и 6, это **загрузчик**, который через оболочку
вызывает движок. Плагин включает один входной навык; его манифест — корневой
`plugin.json`, а
[страница окружения хоста плагинов](/docs/harnesses/codex#codex-plugin) описывает
структуру и то, что плагин оставляет движку. Материализуйте полное окружение,
запустив установку через него:

```bash title="Materialize the full harness"
npx @ahmed-g-gad/apothem install --harness codex
```

**Проверка:**

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness codex
```

## 8. Прямой движок (`python -m apothem`)

**Предварительные требования:** системный Python 3.10+ с импортируемыми
пакетами `click` и `rich`, а также чекаут репозитория. Node.js не требуется.

Запустите движок прямо из клона. Точка входа добавляет вендоренные зависимости
(`src/apothem/_vendor`) в `sys.path`, поэтому, когда `click` и `rich`
импортируются, `PYTHONPATH=src` — это вся настройка:

```bash title="Direct engine"
git clone https://github.com/ahmed-g-gad/apothem
cd apothem
PYTHONPATH=src python -m apothem install --harness claude-code
```

`python -m` ставит текущую папку первой в пути поиска модулей Python, поэтому
файл в ней, например `click.py`, или папка с именем `apothem` запустились бы
вместо настоящего модуля. Запускайте эти команды из корня чекаута или из
другой папки, которой вы доверяете. Установленная команда `apothem` не читает
текущую папку.

Как и в случае npm-шима, первая команда `install` на машине без профиля создаёт
начальный профиль в `~/.config/apothem/profile.yaml` и продолжает работу.

**Проверка:**

```bash title="Verify"
PYTHONPATH=src python -m apothem verify --harness claude-code
```

## Проверка любой установки

Каждый канал выше называет свою собственную команду проверки. Две общие формы
таковы:

```bash title="Installer path"
apothem verify --harness claude-code
```

```bash title="npx path"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

Замените имя окружения на тот адаптер, который вы установили; все
поддерживаемые имена см. в [списке окружений](/docs/harnesses). Чтобы
проверить сразу каждый установленный адаптер (его действие verify и его
команды хуков), запустите `doctor` вместо `verify --harness NAME` в той же
форме, которую вы использовали выше: `apothem doctor` (или полный путь шима,
или команду, которую вывел установщик, когда его папки нет в `PATH`), или
`npx @ahmed-g-gad/apothem doctor`. Для пути плагина запустите `/plugin` внутри
Claude Code и убедитесь, что **apothem** указан как установленный.

## Предварительные требования кратко

- **Python 3.10 или новее** — пути, которые находят его сами, ищут его по
  имени, и имена различаются от пути к пути. npm-шим пробует `python3`,
  `python`, затем `py -3`. Установщики пробуют `python3`, `python` и имена с
  номером версии от `python3.14` до `python3.10` по убыванию.
- **Импортируемые `click` и `rich`** под этим интерпретатором — две
  обращённые к терминалу зависимости, которые движок не вендорит. Установщики
  проверяют обе, называют всё недостающее и предлагают установить это за вас —
  с вашего подтверждения или автоматически с `--yes` (`-Yes` в PowerShell) либо
  `APOTHEM_AUTO_INSTALL_DEPS=1`. На любом другом канале отсутствующий пакет
  останавливает движок с ошибкой (код выхода 1), которая называет точную
  команду для найденного интерпретатора с ограничениями версий, на которых
  тестируется Apothem (`<interpreter> -m pip install "click==…" "rich>=…"`); с
  `--json` та же ошибка приходит в виде JSON-конверта с кодом
  `runtime.dependency_missing`.
- **Node.js 18 или новее** — только пути, которые запускают `npx`: npm-шим (2),
  расширение для семейства VS Code (4) и загрузчики командной строки (5–7).
- **Среды выполнения с истёкшим сроком поддержки.** Срок поддержки Python 3.10
  в upstream закончился 2026-10-01, а Node.js 18 и 20 — 2025-04-30 и
  2026-04-30. Apothem по-прежнему поддерживает их как свои объявленные
  минимальные версии и тестирует каждую в CI, но они больше не получают
  исправлений безопасности из upstream, поэтому отдавайте предпочтение
  Python 3.11 или новее и Node.js 22 или новее.
  [Политика минимальных версий сред выполнения](/docs/governance/release-engineering-policy#runtime-floors)
  объясняет, как повышается минимальная версия.
- **Git и GnuPG** — только путь установщика и только для сетевой формы (с их
  помощью скрипт находит последний релиз и проверяет его подписанный тег, а без
  cosign клонирует исходный код; локальному чекауту не нужно ни то, ни другое).
- **Claude Code** — только путь плагина. **VS Code** и собственный
  хост-инструмент каждого загрузчика командной строки нужны только для их
  собственного канала (4–7).
