<Callout title="Обновляетесь с более раннего релиза? Сначала сохраните резервные копии">
  В более ранних релизах (их называет журнал изменений) каждая установка и
  каждое обновление удаляли некоторые папки с вашими собственными файлами,
  например slash-команды и скрипты хуков Claude Code, после того как копировали
  их в `~/.apothem/backups/`. Большинство этих релизов хранят только 10 самых
  новых наборов резервных копий на окружение, поэтому каждый следующий запуск
  одного из них может удалить самый старый набор, в котором может быть ваша
  единственная копия. Прежде чем снова запускать Apothem, скопируйте
  `~/.apothem/backups/` в другое место.
  [Журнал изменений](/docs/changelog#data-loss-in-earlier-releases-recover-your-files)
  перечисляет все затронутые папки и объясняет, как скопировать ваши файлы
  обратно.
</Callout>

## Обновление плагина Claude Code

Обновите запись в маркетплейсе, затем обновите плагин из меню `/plugin`
внутри Claude Code:

```text title="Inside Claude Code"
/plugin marketplace update apothem
```

Откройте `/plugin`, выберите **apothem** и выберите действие обновления, когда в списке появится более новая
версия плагина.

## Обновление расширения VS Code

Расширение запускает ту версию движка, с которой оно поставлялось. Его способ
запуска по умолчанию — `npx @ahmed-g-gad/apothem@<extension version>`, поэтому
новый движок вы получаете только тогда, когда обновляется само расширение.

VS Code сам проверяет обновления расширений и устанавливает их, как описано в
его документации об
[автообновлении расширений](https://code.visualstudio.com/docs/configure/extensions/extension-marketplace#_extension-auto-update).
По умолчанию он ждёт 12 часов после публикации обновления. Чтобы установить
его сразу, нажмите кнопку **Update** расширения в представлении Extensions.
Если вы отключили автообновление, выполните команду
**Show Extension Updates** и нажмите **Update** или выполните
**Update All Extensions**.

VS Code отключает автообновление для расширения, установленного из файла
`.vsix`. Если вы установили `apothem.vsix`, установите тем же способом
`apothem.vsix`, приложенный к более новому
[GitHub Release](https://github.com/ahmed-g-gad/apothem/releases).

## npx всегда запускает текущий релиз

`npx @ahmed-g-gad/apothem` разрешает текущий опубликованный пакет при каждом
запуске, поэтому обновлять нечего. Если устаревший кэш npx выдаёт более старую
копию, явно закрепите dist-тег:

```bash
npx @ahmed-g-gad/apothem@latest --version
```

## Обновление установки на основе инсталлятора

Перезапустите инсталлятор — он идемпотентен: он загружает изменения в
существующий git-клон, проверяет новый релизный тег и только затем переключает
клон, а также обновляет установку из релизного архива — или запустите
специальный скрипт обновления, который работает с git-клоном:

```bash title="macOS · Linux · WSL2 · BSD"
bash scripts/installer/update.sh
```

```powershell title="Windows · PowerShell"
pwsh -NoProfile -File scripts/installer/update.ps1
```

Скрипт обновления переводит дерево исходного кода в `APOTHEM_HOME` (по умолчанию
`~/.apothem`) на `APOTHEM_REF`. Если значение не задано, выбирается последний
подписанный релизный тег `vMAJOR.MINOR.PATCH`; значение-тег закрепляет его;
`main` выбирает подвижную ветку, только если также задано
`APOTHEM_ALLOW_UNVERIFIED=1`. Без этого переопределения обновление прерывается
до того, как что-либо переключить или повторно материализовать, поскольку
ветка не является подписанным релизным тегом. Сначала оно загружает ссылку и
проверяет подпись тега командой `git verify-tag` до переключения, поэтому
неудавшаяся проверка оставляет клон на той версии, на которой он был. Подпись
должна быть сделана ключом сопровождающего, опубликованным в SECURITY.md, а
подписанный тег должен быть тем, который назван для релиза; неподписанный или
подделанный тег либо тег, подписанный любым другим ключом, прерывает
выполнение, если только `APOTHEM_ALLOW_UNVERIFIED=1` не понижает прерывание до
предупреждения (эта переменная не обходит проверку того, что подписанный тег —
это релизный тег). Поскольку эта переменная пропускает неподписанный тег или
тег, подписанный другим ключом, проверка защищает только теги, несущие подпись
ключа сопровождающего. С нерелизной ссылкой, например `main`, клон следует за
копией этой ветки в origin. Переключение никогда не отбрасывает локальные
изменения: клон с изменениями в отслеживаемых файлах останавливает обновление,
и вы фиксируете или откладываете их (commit или stash) и запускаете снова.
Перед загрузкой обновление также останавливается, когда файлы помечены как
assume-unchanged или skip-worktree (git не увидел бы их изменений), когда
рабочее дерево клона — не `APOTHEM_HOME`, когда клон содержит подмодуль,
когда `.git/info/attributes` называет фильтр или драйвер сравнения (`filter=`
или `diff=`), когда он или файл конфигурации не является обычным файлом, когда
клон заимствует объекты из другого репозитория (`objects/info/alternates`) или
когда
`.git/config` или `.git/config.worktree` клона содержит настройку, отличную от
тех, которые `git clone` и `git init` записывают туда для полного клона,
настроек веток (`remote` и `pushremote` ветки должны быть `origin`),
`user.name`, `user.email`, `maintenance.auto`, `maintenance.strategy`,
`pull.rebase` и `pull.ff`. Частичный клон, созданный с `--filter`, тоже
останавливается там. Сообщение называет настройку и файл, в котором она
находится, а
[Устранение неполадок](/docs/install/troubleshooting#the-installer-stops-the-existing-clone-is-set-up-in-a-way-the-update-would-trust)
перечисляет допустимые настройки. Оно также останавливается, до загрузки, на
файле `.gitattributes` в рабочем дереве, который git не отслеживает, который
отличается от зафиксированной копии или зафиксированную копию которого git не
может прочитать либо в ней назван фильтр или драйвер сравнения (копия в
рабочем дереве тоже читается), на git-репозитории в клоне, который git не
отслеживает, вне собственных папок данных движка, таких как `backups` (git
прочитал бы файлы `.gitattributes` в нём), и на файлах в
`src` (в любом регистре написания), которые git не отслеживает, поскольку
движок мог бы их загрузить. После переключения оно удаляет папки кэша Python
(`__pycache__`) в `src`, прежде чем движок запустится из клона. Git-хуки клона
никогда не запускаются во время обновления, а клон проекта, отличного от
Apothem, не обновляется вовсе. Обновление задаёт
`GIT_NO_REPLACE_OBJECTS=1`, `GIT_NO_LAZY_FETCH=1`, `GIT_ALLOW_PROTOCOL` и
`GIT_ATTR_NOSYSTEM=1` на время своего запуска, и git не читает файлы атрибутов
вне клона (см.
[переменные окружения инсталлятора](/docs/how-to/installer-environment-variables#the-installer-variables)).
Каждый запуск удерживает блокировку `<APOTHEM_HOME>.lock` всё своё время,
поэтому вторая установка, обновление или удаление в том же `APOTHEM_HOME`
останавливается; см.
[Устранение неполадок](/docs/install/troubleshooting#the-installer-stops-another-run-holds-the-lock),
если блокировка осталась. Подписанный тег, открытый ключ сопровождающего которого отсутствует в локальном хранилище ключей, прерывает выполнение с инструкцией по импорту ключа и ссылкой на отпечаток, опубликованный в [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md). Затем оно повторно материализует окружение, названное в `APOTHEM_HARNESS`, запуская `apothem update` из обновлённого дерева (значение по умолчанию для окружения см. в таблице [переменных окружения инсталлятора](/docs/how-to/installer-environment-variables)). Требуется предыдущая установка: если дерева в `APOTHEM_HOME` нет и `APOTHEM_SOURCE` не задана, команда завершается с сообщением, которое направляет сначала к инсталлятору.

Скрипт обновления работает только с git-клоном. Установка, выполненная с
cosign или с `APOTHEM_VERIFY=checksum`, вместо этого размещает релизный архив,
поэтому скрипт обновления останавливается и предлагает перезапустить
инсталлятор с cosign и `gpg` в `PATH`. Такой перезапуск подставляет новый
релиз и сохраняет каждый файл, который он не поставляет, включая резервные
копии и журналы установки движка. Без cosign перезапустите инсталлятор с
`--yes` (`-Yes` в Windows): он переводит установку из архива на git-клон,
проверенный ключом сопровождающего, и сохраняет всё, что не входит в дерево
исходного кода, включая резервные копии, журналы, планы и память.
`APOTHEM_VERIFY=checksum` тоже обновляет архив на месте и требует
`APOTHEM_ALLOW_UNVERIFIED=1`. Режим контрольных сумм не проверяет релиз.
SHA256SUMS берётся из того же релиза, что и архив, поэтому совпадение лишь
показывает, что загрузка не повреждена; любой, кто может изменить файлы
релиза, может изменить и то, и другое.

### Когда движок оставляет файл как есть

Движок может оставить файл, содержащий блок Apothem (скажем, `CLAUDE.md` или
`AGENTS.md`), как есть из-за его строк маркеров Apothem: например, когда файл
содержит два целых блока между маркерами Apothem. Тогда он записывает всё
остальное, выводит предупреждение, которое называет файл и объясняет, как его
исправить, и завершается как частичный запуск с кодом выхода `2`. Движок также
завершается как частичный запуск, когда останавливается после того, как что-то
записал: например, когда один инструмент завершается сбоем после того, как
предыдущий в запуске `APOTHEM_HARNESS=all` записал свои файлы. Его ошибка
говорит, что не удалось, а у каждого инструмента, завершившегося до неё, есть
своя строка над ошибкой. Затем инсталлятор и скрипт обновления выводят ещё
одну строку:

```text
! The engine ended as partial (exit code 2): its messages above name the files it left as they are, or the error that stopped it. Fix what they name, then run 'apothem update --harness claude-code' again.
```

Они завершают запуск как после полного успеха: инсталлятор всё равно выполняет
проверку, размещает команду `apothem` и выводит свой заключительный баннер, а
скрипт обновления всё равно выводит "Update complete." последней строкой.
Затем каждый скрипт завершается с кодом выхода `2`. Запуск PowerShell через
конвейер (`irm ... | iex`) вместо этого оставляет `$LASTEXITCODE` равным `2`,
поэтому ваш сеанс PowerShell остаётся открытым. Однократный
`pwsh -Command "irm ... | iex"` (или `powershell -c`) сообщает о частичном
запуске только через `$LASTEXITCODE`, поэтому сам процесс завершается с кодом
`0`. Когда задаче CI или скрипту нужен этот код, завершите команду
`; exit $LASTEXITCODE` или запустите скрипт по пути с `-File`. Из PowerShell,
bash или другой POSIX-оболочки заключите эту команду в одинарные кавычки. В
двойных кавычках вызывающая оболочка подставляет собственный `$LASTEXITCODE`
до запуска нового процесса (POSIX-оболочка подставляет пустую строку), поэтому
процесс не завершается с кодом запуска. Из cmd.exe двойные кавычки подходят.
Пробный запуск инсталлятора (`--dry-run` или `-DryRun` в Windows) ничего не
записывает, поэтому движок не завершает его как частичный. Исправьте то, что
называют сообщения движка. Для файла сохраните собственный текст (см.
[Файл содержит два блока между маркерами Apothem](/docs/install/troubleshooting#a-file-holds-two-blocks-between-apothems-markers)
и
[Apothem не может отличить свой блок от вашего текста](/docs/install/troubleshooting#apothem-cannot-tell-its-block-from-your-text)),
затем снова выполните `apothem update --harness <name>` или скрипт обновления
для каждого инструмента, который запуск оставил незавершённым. Любой другой
ненулевой код выхода движка останавливает скрипт на этом месте.

## Повторная материализация вывода окружения

После обновления движка или редактирования `~/.config/apothem/profile.yaml`
заново выведите установленную конфигурацию окружения. Адаптерам с областью действия пользователя не нужен
`--project`; адаптерам с областью действия проекта он нужен.

```bash
apothem update --harness claude-code
apothem update --harness cursor --project /path/to/project
apothem update --harness all --project /path/to/project
```

Запустите ту же команду с `--dry-run --json`, когда вам нужен машиночитаемый
предпросмотр без записи на файловую систему.

## Граница текущей команды

`apothem update` обновляет только вывод окружения. CLI не реализует
`update --self`, `update --check` или `update --apply`; обновляйте сам движок
через тот канал, которым вы устанавливали, — поток `/plugin`, свежий
запуск `npx` или скрипты инсталлятора/обновления выше.

## Проверка версии движка

apothem --version
