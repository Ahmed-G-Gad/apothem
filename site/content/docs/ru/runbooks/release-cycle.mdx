Это руководство проводит релиз `vX.Y.Z` проекта `apothem` от чистого
рабочего дерева до проверенных поверхностей распространения. Процедура
написана для сопровождающего, владеющего `gh`, `git` и оболочкой релизного
уровня; она завершается проверенной страницей Release, заполненным
CHANGELOG и дымовой проверкой пути установки, подтверждающей, что каждая
пользовательская поверхность отвечает на каноническую команду установки.

Модель релизов — **аддитивная**. Каждый релиз добавляет один коммит в `main`
и один подписанный аннотированный тег `vX.Y.Z`; ничего не отправляется через
force-push, и ни один более ранний тег, GitHub Release или версия npm не
удаляется. У проекта три релиза, каждый со своим тегом, своим GitHub Release
и своей версией npm, и все остаются опубликованными: версии npm неизменяемы
(опубликованный `name@version` никогда не может быть заменён), а закреплённые
установки зависят от тегов.

Push тега запускает два рабочих процесса. `.github/workflows/release.yml`
собирает, подписывает, аттестует и публикует GitHub Release с полным набором
артефактов: sdist, wheel, CycloneDX SBOM, бандлы Sigstore cosign,
происхождение SLSA-3 и архивы платформенной среды выполнения. `publish-npm.yml`
публикует `@ahmed-g-gad/apothem` на npmjs.com через доверенную публикацию npm.
Версионный раздел CHANGELOG попадает в коммит релиза; оператор запускает
дымовую проверку пути установки после завершения обоих рабочих процессов.

## 1. Предварительные условия

Сопровождающий подтверждает следующее перед тегированием:

- **Рабочее дерево.** Чистое (`git status` не показывает ничего
  ожидающего). Вся работа над функциями для релиза находится в `main`.
- **CI зелёный.** Для последнего `main` `gh run list --branch=main --limit=1
  --json conclusion --jq '.[0].conclusion'` возвращает `success`.
- **Инструментарий.** `gh` (GitHub CLI) версии 2.40 или новее,
  авторизованный в `ahmed-g-gad`; `git` 2.40 или новее с загруженным
  подключом подписи GPG; привязка доверенного издателя npm для
  `@ahmed-g-gad/apothem` действует (проверено согласно
  [руководству по настройке учётной записи издателя](/docs/runbooks/publisher-account-setup)).
- **Якоря версий выровнены.** Строка версии, объявленная в
  `pyproject.toml`, совпадает с планируемым тегом без префикса `v`
  (§2.1 устанавливает её вместе со всеми остальными якорями). Проверьте:

  ```bash
  grep '^version' pyproject.toml
  ```

  Ожидаемый вывод (для релиза `vX.Y.Z`; заполнители обозначают тег текущего выпускаемого релиза):

  ```text
  version = "X.Y.Z"
  ```

- **Записи CHANGELOG подготовлены.** Пункты релиза находятся под
  `## [Unreleased]` в заголовках Keep-a-Changelog; §2.1 превращает их в
  датированный раздел версии в коммите, на который ставится тег.

## 2. Тегирование и запуск

### 2.1 Создание коммита релиза

Версия хранится более чем в десятке файлов, поэтому не редактируйте их
вручную. Одна команда обновляет их все:

```bash
git checkout main
git pull --ff-only origin main
python scripts/release/bump_version.py X.Y.Z
```

`bump_version.py` обновляет все якоря версий вместе:

- Каждый манифест упаковки, расширения, плагина и маркетплейса, а также
  файл цитирования (версия и дата релиза). Полный список:

  ```text
  pyproject.toml
  package.json
  site/package.json
  site/package-lock.json            (the project entries only)
  vscode-extension/package.json
  gemini-extension.json
  qwen-extension.json
  .claude-plugin/marketplace.json   (top level and metadata)
  plugins/apothem/.codex-plugin/plugin.json
  src/apothem/harnesses/antigravity/templates/plugin.json
  CITATION.cff
  ```

- `CHANGELOG.md`: записи `[Unreleased]` становятся датированным разделом
  `## [X.Y.Z]`, `[Unreleased]` сравнивается начиная с `vX.Y.Z`, и
  добавляется ссылка `[X.Y.Z]`.
- `SECURITY.md`: новая минорная версия получает строку поддерживаемой
  версии `X.Y.x`. Оставлять ли в списке более старые минорные версии — решать
  вам; скрипт выводит напоминание.

Затем он регенерирует производные деревья: пакет плагина Claude Code,
эталонные снимки behavior-diff, а также справочные страницы документации и
страницы журнала изменений. Передайте `--dry-run`, чтобы сначала вывести
список изменений, `--date
YYYY-MM-DD`, чтобы задать дату релиза (по умолчанию: сегодня по UTC), или
`--no-regen`, чтобы пропустить регенерацию. Скрипт отклоняет некорректную
версию или понижение версии, а его повторный запуск с текущей версией только
заново выравнивает отбившиеся якоря.

Просмотрите diff, затем сделайте коммит:

```bash
git add -A
git commit -S -m "chore(release): cut vX.Y.Z"
git push origin main
```

Флаг `-S` подписывает коммит ключом GPG. Push запускает стандартную
матрицу CI (lint, test, build); дождитесь зелёного статуса перед
тегированием.

### 2.2 Подпись и push тега

```bash
git tag -a -s vX.Y.Z -m "vX.Y.Z"
git push origin vX.Y.Z
```

Комбинация `-a -s` создаёт аннотированный тег с подписью GPG. Push
запускает `.github/workflows/release.yml`, который собирает, подписывает,
аттестует и публикует.

### 2.3 Подтверждение завершения рабочего процесса релиза

```bash
gh run watch $(gh run list --workflow=release.yml --limit=1 --json databaseId --jq '.[0].databaseId')
```

Рабочий процесс выполняет сборку (sdist + wheel, затем CycloneDX SBOM этих
дистрибутивов, записываемый рядом с ними), бесключевую подпись cosign,
генерацию и проверку происхождения SLSA-3, сборку платформенных архивов
(darwin / linux / windows), подпись архивов с агрегированным манифестом
`SHA256SUMS` и финальную публикацию GitHub Release. Сопровождающий
просматривает журнал задания `publish GitHub Release` на предмет
подтверждений загрузки ресурсов.

### 2.4 Подтверждение публикации в npm

Push тега также запускает `publish-npm.yml`. Одобрите развёртывание в среде
`release`, когда будет предложено. Рабочий процесс публикует
`@ahmed-g-gad/apothem@X.Y.Z` на npmjs.com через доверенную публикацию npm
(OIDC); в репозитории не хранится токен реестра. Затем подтвердите
готовность:

```bash
bash scripts/release/check-release-ready.sh vX.Y.Z
```

Чтобы опубликовать снова после сбойного запуска, запустите рабочий процесс
для того же тега (`gh workflow run publish-npm.yml --field tag=vX.Y.Z`). Он
пропускает публикацию, когда версия уже есть в реестре, потому что версии
npm неизменяемы.

## 3. Поверхности распространения

У каждой поверхности есть команда проверки, отвечающая на вопрос
«попал ли релиз сюда?»:

| # | Поверхность | Артефакт | Проверка |
|---|---|---|---|
| 1 | GitHub Release (дистрибутивы Python) | `apothem-X.Y.Z.tar.gz` (sdist) + `apothem-X.Y.Z-py3-none-any.whl` | `gh release view vX.Y.Z --json assets --jq '.assets[].name'` включает оба имени файлов |
| 2 | GitHub Release (SBOM) | `sbom.cdx.json` + `sbom.cdx.json.cosign.bundle` | список ресурсов включает оба; `metadata.component.purl` в SBOM равен `pkg:pypi/apothem@X.Y.Z`, а его компоненты включают каждый пакет из `src/apothem/_vendor/vendor.txt` |
| 3 | GitHub Release (подписи) | по одному `<asset>.cosign.bundle` на sdist, wheel, SBOM, расширение VS Code, платформенный архив и `SHA256SUMS` (в более ранних релизах бандлы архивов и `SHA256SUMS` называются `<asset>.sig`) | `cosign verify-blob` с точной идентичностью из §5.5 завершается с кодом 0 |
| 4 | GitHub Release (происхождение) | `provenance.intoto.jsonl` | `bash scripts/release/verify-provenance.sh <download-dir>` завершается с кодом 0 (§5.5) |
| 5 | GitHub Release (платформенные архивы) | `apothem-vX.Y.Z-darwin.tar.gz`, `apothem-vX.Y.Z-linux.tar.gz`, `apothem-vX.Y.Z-windows.zip` | список ресурсов включает каждый архив плюс `SHA256SUMS`. Архивы darwin и linux — это одни и те же байты под двумя именами (среда выполнения не зависит от платформы; `--platform` выбирает только tar.gz или zip), поэтому их строки в `SHA256SUMS` показывают один дайджест дважды |
| 6 | GitHub Release (расширение VS Code) | `apothem.vsix` + `apothem.vsix.cosign.bundle` | список ресурсов включает оба; `code --install-extension apothem.vsix` устанавливает его. Релизы, вышедшие до того, как рабочий процесс релиза начал упаковывать расширение, не содержат ни того, ни другого |
| 7 | npmjs.com | `@ahmed-g-gad/apothem@X.Y.Z` | `npm view @ahmed-g-gad/apothem version` возвращает `X.Y.Z`; `npx @ahmed-g-gad/apothem@X.Y.Z --version` печатает `Apothem, version X.Y.Z` |
| 8 | Pages (скриптовые установщики) | `install.sh` / `install.ps1` на сайте документации | `curl -fsSL https://apothem.ahmedgad.com/install.sh \| head -n 1` возвращает заголовок скрипта |

GitHub Release — это каноническая поверхность артефактов; пакет npm и
скриптовые установщики — это пути установки, построенные поверх него.
Публикация в npm выполняется параллельно с рабочим процессом релиза при том
же push тега.

## 4. Дисциплина CHANGELOG

`CHANGELOG.md` содержит один раздел на релиз согласно соглашению
Keep-a-Changelog. Правка CHANGELOG в коммите релиза:

- Подтверждает, что раздел версии использует заголовок
  `## [X.Y.Z] - YYYY-MM-DD` (дефис; его пишет `bump_version.py`, а
  `extract_release_notes.py` сопоставляет префикс `## [X.Y.Z]`).
- Подтверждает, что стандартные заголовки — Added, Changed, Deprecated,
  Removed, Fixed, Security — используются там, где это применимо. Пустые
  заголовки удаляются из отрендеренного файла.
- Фиксирует **возможности**, а не реализацию. Только язык предметной
  области; никаких ссылок на внутренние планы; никаких хешей коммитов;
  никаких идентификаторов плана или фазы.

Раздел CHANGELOG, прошедший проверку сопровождающего, служит якорем
примечаний к релизу для текста анонса.

## 5. Дымовая проверка пути установки

После завершения обоих этапов сопровождающий запускает дымовую проверку.
Дымовая проверка — это каноническое подтверждение того, что
пользовательские команды установки отвечают.

### 5.1 Плагин Claude Code

```text
/plugin marketplace add ahmed-g-gad/apothem
/plugin install apothem@apothem
```

Ожидается: плагин устанавливается, и команды `apothem` доступны внутри
Claude Code.

### 5.2 Node.js (npx)

```bash
npx @ahmed-g-gad/apothem@X.Y.Z --version
```

Ожидаемый вывод: `Apothem, version X.Y.Z`.

### 5.3 Одношаговый скриптовый установщик (POSIX)

```bash
curl -fsSL https://apothem.ahmedgad.com/install.sh | sh
apothem --version
```

Ожидаемый вывод: `Apothem, version X.Y.Z`.

### 5.4 Одношаговый скриптовый установщик (Windows)

```powershell
irm https://apothem.ahmedgad.com/install.ps1 | iex
apothem --version
```

Ожидаемый вывод: `Apothem, version X.Y.Z`.

### 5.5 Проверка артефактов (свидетельства цепочки поставок)

Скачайте все ресурсы в пустой каталог, затем выполните проверку. Идентичность
сертификата — это рабочий процесс релиза именно на этом теге. Проверки
идентичности чувствительны к регистру, а сертификаты содержат владельца в том
виде, в каком его сообщает GitHub, — `Ahmed-G-Gad`, поэтому владелец в нижнем
регистре не проходит проверку.

```bash
mkdir release-vX.Y.Z && cd release-vX.Y.Z
gh release download vX.Y.Z --repo ahmed-g-gad/apothem
cosign verify-blob \
  --bundle apothem-X.Y.Z-py3-none-any.whl.cosign.bundle \
  --certificate-identity https://github.com/Ahmed-G-Gad/apothem/.github/workflows/release.yml@refs/tags/vX.Y.Z \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  apothem-X.Y.Z-py3-none-any.whl
slsa-verifier verify-artifact \
  --provenance-path provenance.intoto.jsonl \
  --source-uri github.com/Ahmed-G-Gad/apothem \
  --source-tag vX.Y.Z \
  apothem-X.Y.Z-py3-none-any.whl apothem-X.Y.Z.tar.gz
bash ../scripts/release/verify-provenance.sh .
```

Ожидается: `Verified OK`, `PASSED: SLSA verification passed` и
`verify-provenance: chain OK (3 of 3 layers verified)`. Скрипт проверяет
`SHA256SUMS`, каждый бандл подписи и происхождение за один запуск; он
выводит тег из имени wheel (`--tag vX.Y.Z` переопределяет его).

Дымовая проверка выдаёт по одной строке PASS / FAIL на поверхность;
запишите эти строки в журнал релизов сопровождающего.

## 6. Восстановление после сбоев

У рабочего процесса релиза есть задокументированные режимы сбоя для
релизного движка и публикатора npm:

| Сбой | Диагностика | Восстановление |
|---|---|---|
| Push тега отклонён (сбой подписи) | `git push origin vX.Y.Z` возвращает `error: failed to push some refs` с сообщением, связанным с GPG | Проверьте, что подключ GPG загружен (`gpg --list-secret-keys --keyid-format=long`); заново поставьте тег локально с `-s` после исправления связки ключей; повторите push |
| Сборка релиза останавливается на `Check the plugin version changed with the plugin` | Журнал задания сборки называет плагин и предыдущий тег; ни один ресурс не был собран или опубликован | Пакет плагина изменился с предыдущего релиза, а его версия — нет. Удалите тег (`git push --delete origin vX.Y.Z`, `git tag -d vX.Y.Z`), выполните `python scripts/release/bump_version.py X.Y.Z`, сделайте коммит, затем снова подпишите и отправьте тег (§2.2). Та же проверка выполняется на каждом pull request как аннотация-предупреждение, поэтому обычно это проявляется до тегирования |
| Задание `release.yml` даёт сбой на одном этапе | `gh run view <run-id> --log` называет сбойное задание (build, которое также записывает SBOM / sign / provenance / archive / publish) | Перезапустите только сбойное задание через `gh run rerun <run-id> --failed`; если сбой повторяется, исправьте входные данные задания в их источнике перед повторным тегированием |
| Проверка происхождения SLSA не проходит | Задание `verify SLSA provenance artifact` завершается с ненулевым кодом | Проверьте артефакт происхождения на несоответствие дайджеста субъекта; пересоберите из того же тега — происхождение привязано к точным дайджестам артефактов, поэтому любая регенерация артефакта требует полного перезапуска рабочего процесса |
| Публикация на npmjs.com отклонена | Задание npm завершается с ненулевым кодом во время `npm publish`; ошибка реестра `404` во время `PUT` — это несоответствие авторизации / доверенного издателя, а не доказательство отсутствия кода пакета | Проверьте, что npm Trusted Publishing для `@ahmed-g-gad/apothem` называет владельца `ahmed-g-gad`, репозиторий `apothem`, рабочий процесс `publish-npm.yml` и разрешённое действие `npm publish`; убедитесь, что задание выполняется с версией Node и минимальной версией npm CLI для OIDC, закреплёнными в рабочем процессе |
| Тег виден, но ресурсы отсутствуют | `gh release view vX.Y.Z` возвращает релиз-заглушку | Перезапустите задание публикации рабочего процесса релиза; оно редактирует существующий релиз и повторно загружает каждый ресурс. Удаляйте тег и ставьте его заново только тогда, когда ничего из этого тега не дошло до пользователей (нет ресурсов, нет версии npm); в противном случае исправьте вперёд следующим патч-релизом ([руководство по восстановлению релиза](/docs/runbooks/release-recovery), §2) |

Если цикл восстановления не доводит поверхность до готовности за один
диагностический проход, поверхность регистрируется как известный сбой в
примечаниях к релизу со ссылкой на открытый тикет; нижестоящих пользователей
направляют на работающие поверхности, пока сломанная исправляется в
патч-релизе.

## 7. Перекрёстные ссылки

- **Настройка издателя.**
  [Руководство по настройке учётной записи издателя](/docs/runbooks/publisher-account-setup)
  устанавливает привязку доверенного издателя npm и предварительные условия
  на стороне GitHub, которые предполагает это руководство.
- **Поток восстановления.** [Руководство по восстановлению релиза](/docs/runbooks/release-recovery)
  следует той же аддитивной модели: оно поэтапно восстанавливает сбойный тег
  или этап публикатора и выполняет откат выпуском исправления как новой
  патч-версии, никогда не удаляя и не перенаправляя опубликованный тег,
  релиз или версию npm.
- **Включение Pages.** Рабочий процесс `publish-static-site.yml`
  проверяет и развёртывает сайт проекта на пользовательском домене;
  руководство по включению Pages (`site/content/docs/runbooks/pages-enablement.mdx`)
  — это вышестоящая процедура, которая изначально установила
  пользовательский домен.
- **Политика версионирования.** `site/content/docs/governance/release-engineering-policy.mdx`
  содержит политику SemVer + подписи + устаревания, которую соблюдает это
  руководство.
