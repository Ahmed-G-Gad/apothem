Реестр окружений — это инвентарь адаптеров, служащий источником истины, который
используют CLI, документация, фикстурные тесты и проверка закреплений
соглашений. Источник во время выполнения — `src/apothem/lib/harness_registry.py`;
каждую строку ниже можно проследить до этого реестра, до файла
`capabilities.yml` каждого адаптера и до файла `STANDARD-CONVENTION-PIN.md`
каждого адаптера.

## Поддержка групп полезной нагрузки

Значения статуса: `native`, `converted`, `support-tree`,
`profile-projected`, `unsupported`, `not-applicable` и
`discovery-pending`.

Группа со статусом `converted` переписывается в собственный формат окружения, и
для некоторых исходных полей в нём нет места. Для каждой преобразованной группы
команд, исполнителей или правил файл `capabilities.yml` адаптера содержит
отображение `conversion_losses`, которое указывает, что происходит с каждым
исходным полем фронтматтера:

| Значение | Смысл |
| --- | --- |
| `native:<field>` | Окружение читает его под этим полем. |
| `sidecar:<path>` | Оно записывается в отдельный файл рядом с преобразованным, например в `agents/openai.yaml` у Codex. |
| `filename` | Его несёт имя файла или папки. |
| `inlined` | Оно переносится в текст промпта или тела. |
| `ignored` | Оно остаётся в файле, но окружение его не читает. |
| `dropped` | Оно отбрасывается. |

## Общие корни

Некоторые цели установки загружаются другими окружениями, а не только тем,
которое их записывает. Реестр записывает каждый такой путь в `SHARED_ROOTS` с
одним зарегистрированным владельцем (адаптером, для которого вендор
документирует этот путь), соустановщиками, которые записывают в него те же
файлы, и читателями, чья документация вендора загружает его по умолчанию, а
также страницами вендора, на которых это показано, и датой, когда эти страницы
были получены.

Путь с соустановщиками — это папка уровня пользователя в домашнем каталоге,
которую несколько установок записывают с одинаковыми байтами. На машине, где
установлен только `Cursor`, нет `Codex`, который записал бы `~/.agents/skills/`,
поэтому каждая установка, называющая эту папку, записывает её, а журнал
установок подсчитывает установки, которые её используют. Учётным владельцем
является зарегистрированный владелец, пока он использует папку, а в противном
случае — самая старая установка, которая её использует; при удалении
зарегистрированного владельца ничего не перемещается. Удаление убирает папку,
только если её больше не использует ни одна другая установка (см.
[`uninstall`](/docs/cli-reference/uninstall#shared-folders-in-your-home-directory)).
Установка читателя не кладёт в папку никаких файлов; установка владельца или
соустановщика делает содержимое Apothem доступным каждому читателю.

| Путь | Владелец | Соустановщики | Читатели |
| --- | --- | --- | --- |
| `~/.agents/skills/` | Codex | Cursor, GitHub Copilot, Windsurf, Zed | Gemini CLI, Kimi Code, Open-Claw, OpenCode, Qwen Code |
| `~/.config/apothem/rules/` | Codex | CodeBuddy, Cursor, GitHub Copilot, Kiro, Trae, Windsurf, Zed | нет |
| `~/.config/apothem/templates/` | Codex | CodeBuddy, Cursor, GitHub Copilot, Kiro, Trae, Windsurf, Zed | нет |
| `~/.claude/skills/` | Claude Code | нет | Cursor, OpenCode |
| `~/.claude/agents/` | Claude Code | нет | Cursor |
| `~/.codex/agents/` | Codex | нет | Cursor |
| `~/.claude/CLAUDE.md` | Claude Code | нет | OpenCode, Windsurf |
| `<project>/AGENTS.md` | Kimi Code | нет | Antigravity, Claude Code, CodeBuddy, Codex, Cursor, GitHub Copilot, Hermes, Kiro, OpenCode, Windsurf, Zed |
| `<project>/GEMINI.md` | Gemini CLI | нет | Antigravity, GitHub Copilot, Zed |
| `~/.gemini/GEMINI.md` | Antigravity | нет | Gemini CLI |
| `<project>/.github/copilot-instructions.md` | GitHub Copilot | нет | Zed |
| `<project>/.cursor/rules/apothem-rules.mdc` | Cursor | нет | Hermes, Windsurf |

`~/.config/apothem/rules/` и `~/.config/apothem/templates/` содержат файлы, на
которые ссылаются собственные навыки и файлы инструкций Apothem. Ни один другой
инструмент их не загружает, поэтому у них нет читателей и страниц вендора.
`CodeBuddy`, `Kiro` и `Trae` также записывают собственную папку навыков
(`~/.codebuddy/skills/`, `~/.kiro/skills/` и `~/.trae/skills/`); её загружает
только этот инструмент, поэтому она не является общим корнем.

Читатель указывается только там, где документация его вендора показывает
загрузку именно этого пути по умолчанию. Когда читатель загружает путь только в
некоторых случаях, реестр записывает условие, а примечание установки повторяет
его. `Open-Claw` индексирует
`~/.agents/skills/` только в своём каталоге состояния по умолчанию (он
пропускает папку, когда `OPENCLAW_STATE_DIR` указывает в другое место).
`OpenCode` 1 загружает `~/.claude/CLAUDE.md` только тогда, когда в его папке
конфигурации (по умолчанию `~/.config/opencode/`) нет `AGENTS.md`, и пропускает
его, когда задано
`OPENCODE_DISABLE_CLAUDE_CODE_PROMPT=1` или `OPENCODE_DISABLE_CLAUDE_CODE=1`.
`OpenCode` 2 читает ту же конфигурацию `~/.config/opencode/`, но не использует
`CLAUDE.md` как резервный вариант, поэтому не загружает `~/.claude/CLAUDE.md`.
`Codex` берёт первый из `AGENTS.override.md` и `AGENTS.md` в каждой папке,
поэтому загружает `<project>/AGENTS.md` только тогда, когда рядом с этим файлом
нет `AGENTS.override.md`. `CodeBuddy` использует `<project>/AGENTS.md` как память
проекта только тогда, когда в проекте нет `CODEBUDDY.md`. `Claude Code` читает
`AGENTS.md` в релизах, которые называет его
[страница о памяти](https://code.claude.com/docs/en/memory#agents-md), а
примечание об установке указывает первый из них. При настройке по умолчанию
**Project instructions** он загружает каждый `AGENTS.md` и `.claude/AGENTS.md`
в рабочей папке и в папках над ней при запуске сеанса, но только тогда, когда
ни в одной из этих папок нет `CLAUDE.md`, `.claude/CLAUDE.md` или
`CLAUDE.local.md`. Он загружает `AGENTS.md` папки ниже рабочей папки, например
проекта, открытого из родительской папки, когда его инструмент Read открывает
там файл и в этой папке тоже нет ни одного из этих трёх файлов.
`~/.claude/CLAUDE.md` не учитывается, поэтому блок Apothem в нём продолжает
загружаться вместе с `<project>/AGENTS.md`. Настройка `claude-md-and-agents-md`
загружает оба вида файлов, а `claude-md` и `managed-only` не загружают
`AGENTS.md`. Некоторые сеансы не читают `AGENTS.md` ни при какой настройке;
страница о памяти перечисляет их. `Zed` загружает только
первый файл инструкций проекта из своего списка: `.rules`, `.cursorrules`,
`.windsurfrules`, `.clinerules`, `.github/copilot-instructions.md`, `AGENT.md`,
`AGENTS.md`, `CLAUDE.md`, затем `GEMINI.md`. Поэтому он загружает
`<project>/.github/copilot-instructions.md`, `<project>/AGENTS.md` и
`<project>/GEMINI.md` только тогда, когда в проекте нет ни одного из файлов,
стоящих в списке перед этим файлом. Установка `Zed` записывает
`<project>/.rules`, первый файл в списке, поэтому `Zed` не загружает ни один из
этих трёх в проекте, где он установлен.

`Hermes` загружает один вид контекста проекта за сессию: первый вид с непустым
файлом, в порядке `.hermes.md` или `HERMES.md`, цепочка `AGENTS.md` (в каждой
папке непустой `AGENTS.override.md` заменяет `AGENTS.md` рядом с ним),
`CLAUDE.md`, затем правила `Cursor`. Поэтому он загружает `<project>/AGENTS.md`
только тогда, когда в проекте нет ни `.hermes.md`, ни `HERMES.md` и рядом с этим
файлом нет `AGENTS.override.md`, а `<project>/.cursor/rules/apothem-rules.mdc` —
только тогда, когда в проекте нет ни `.hermes.md`, ни `HERMES.md`, ни
`AGENTS.override.md`, ни `AGENTS.md`, ни `CLAUDE.md`. `Hermes` ищет `.hermes.md`
и `HERMES.md` от папки, в которой запускается, вверх до корня репозитория, а
цепочку `AGENTS.md` читает от корня репозитория вниз, поэтому такой файл в папке
выше проекта тоже учитывается. Пустой файл не учитывается. Пустой `.hermes.md`
также скрывает `HERMES.md` рядом с ним, поэтому `Hermes` переходит к цепочке
`AGENTS.md`, даже если в этом `HERMES.md` есть текст. Эти условия относятся к
сессии, начатой в проекте. Сессия, начатая в папке выше проекта, всё же может
загрузить `<project>/AGENTS.md` или непустой `AGENTS.override.md` рядом с ним,
когда впервые работает с файлом в проекте, независимо от того, какой из файлов
`.hermes.md` или `HERMES.md` есть в проекте. `Hermes` пропускает это в домашнем
каталоге и в нескольких папках-контейнерах.

Документация `Cursor` называет
`~/.codex/agents/` папкой совместимости с `Codex`, но не говорит, какие форматы
файлов `Cursor` там разбирает, а установка `Codex` записывает файлы TOML, поэтому
то, читает ли `Cursor` этих помощников, не подтверждено. Установка `Cursor` также
записывает собственную копию помощников в `<project>/.cursor/agents/`, которую
порядок приоритета вендора ставит выше импортируемых папок, поэтому в проекте с
установкой нативная копия заменяет копию из `~/.claude/agents/`.

`Windsurf` читает файлы правил других инструментов через импорт конфигурации
Devin, который включён по умолчанию, и агент Local в Devin Desktop находит свои
файлы так же, как Devin CLI. Поэтому он загружает блок из `~/.claude/CLAUDE.md`,
который записывает установка `Claude Code`, и файл установки `Cursor` —
`<project>/.cursor/rules/apothem-rules.mdc`, который благодаря фронтматтеру
`alwaysApply: true` остаётся активным в каждой сессии. Импорт также читает
`CLAUDE.md` проекта, который не записывает ни одна установка Apothem.

Некоторые инструменты намеренно не являются читателями `~/.agents/skills/`:
документация `Antigravity`, `CodeBuddy`, `Kiro` и `Trae` не говорит, что они
загружают её по умолчанию (`Trae` загружает проектную папку `.agents/skills/`
только после включения настройки), поэтому `CodeBuddy`, `Kiro` и `Trae` получают
собственную папку навыков. Документация `Hermes` называет её только как пример
значения для `skills.external_dirs`. `GitHub Copilot` не является читателем
`~/.claude/agents/`: документация VS Code указывает эту папку для агента
Anthropic Claude, а не для агента, которого запускает `GitHub Copilot`.

Блок Apothem, который владелец записывает в общий файл инструкций, не называет
своим читателем ни один отдельный инструмент.
`tests/unit/test_shared_roots.py`
завершается неудачей, когда адаптеры, записывающие цель реестра, не совпадают в
точности с её владельцем и её соустановщиками, и
когда у цели реестра, названной как межинструментальный файл инструкций
(`AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `copilot-instructions.md`), нет
объявленного владельца, кроме `~/.codex/AGENTS.md`, загрузку
которого не документирует ни одно другое зарегистрированное окружение.

## Хуки валидации

Реестр поддерживается в синхронизированном состоянии следующими проверками:

| Проверка | Назначение |
| --- | --- |
| `python scripts/dev/validate_harness_convention_pins.py --today YYYY-MM-DD` | Подтверждает, что у каждого адаптера есть закрепление соглашения возрастом не более 90 дней, которое ссылается как минимум на один URL вендора и не имеет просроченной цели обнаружения. CI запускает эту проверку на каждом pull request, еженедельно и перед релизом. |
| `python scripts/dev/check_vendor_urls.py` | Загружает каждый URL вендора, на который ссылаются закрепления и шаблоны окружений, и завершается неудачей на перемещённой или несуществующей странице, включая имя хоста, которое больше не разрешается, или сертификат, не прошедший проверку; тайм-аут, отклонённое или сброшенное соединение либо ошибка сервера 5xx регистрируются как недоступность и не приводят к неудаче. Имя хоста, которое разрешается только в адрес-заполнитель, которого не может быть ни у одного сервера (такой адрес могут вернуть серверы имён вендора для региона, из которого выполняется проверка), запроса не получает: оно регистрируется как немаршрутизируемое, не приводит проверку к неудаче, а его страницы нужно проверять вручную. Его запускает еженедельный монитор соглашений, который при каждом запуске выдаёт предупреждение о каждом таком хосте и перечисляет страницы таких хостов в issue, которое создаёт. |
| `python scripts/dev/check_vendor_releases.py` | Запрашивает у каждого канала релизов в `scripts/dev/vendor-release-channels.json` его текущую версию: dist-тег пакета npm, последний релиз репозитория GitHub (или, для канала с шаблоном тега, его самый новый стабильный релиз с подходящим тегом среди 100 самых новых) или проект PyPI. Для адреса инсталлятора она запрашивает, куда перенаправляет адрес. Она сравнивает ответ с тем, что было проверено последним. Новая мажорная версия, релиз, вышедший за триггер, названный в файле, адрес инсталлятора, перенаправляющий куда-то ещё, или пакет, dist-тег, релиз или адрес, которых больше нет, приводят к её неудаче, как и шаблон тега, которому не соответствует ни один стабильный релиз среди 100 самых новых. Более новая минорная или патч-версия выводится в отчёте и не приводит к неудаче, если только уровень `watch` канала не называет этот уровень. Реестр, который не отвечает или ответ которого обрывается на полпути, выводится в отчёте как недоступный и тоже не приводит к неудаче. Каждая попытка запроса имеет в общей сложности 30 секунд, а через 20 минут проверка больше не опрашивает каналы, поэтому она всегда записывает свой отчёт. Перед любым запросом она проверяет, что у каждой папки окружения есть запись и что фраза-свидетельство каждого канала есть в его закреплении, и завершается с кодом 1, если это не так; отчёт и issue тогда говорят, что не так. Еженедельный монитор соглашений запускает её с токеном только для чтения, перечисляет каждый канал в сводке запуска и создаёт issue, когда она не проходит. `--list` выводит каналы, не обращаясь ни к одному реестру. |
| `python3 -E -s src/apothem/conformity/gate.py --all .` | Запускает проверки соответствия документации и реализации. |
| `python -m pytest` | Прогоняет фикстурные тесты реестра и контрактные тесты адаптеров. |

## Каналы релизов

`scripts/dev/vendor-release-channels.json` содержит одну запись для каждой
папки окружения. Отслеживаемое окружение перечисляет свои каналы релизов.
Каждый канал записывает последнюю проверенную версию с датой. Это версия,
которую называет его закрепление, или, если закрепление не называет никакой,
версия, которую реестр отдавал, когда канал был записан. Запись также может
содержать только мажорную версию. Каждый канал цитирует фразу закрепления,
которая его называет. Первое число версии — её мажорная версия, включая 0,
поэтому линия 0.x, переходящая с 0.26 на 0.27, сообщает о более новой
минорной версии и не приводит к неудаче. Канал с календарными версиями,
например с номерами год.месяц.релиз у OpenClaw, сообщает о каждом более новом
релизе без неудачи и не принимает уровень `watch`. Codex, Gemini CLI, Hermes,
Qwen Code и GLM находятся на линиях 0.x, поэтому новая версия одного из них
перечисляется в сводке запуска и не создаёт issue, пока не достигнет 1.0, если
только его канал не задаёт уровень `watch`.

У OpenCode четыре канала. `opencode-ai` несёт OpenCode 1, а `@opencode/cli`
несёт OpenCode 2. Релизы GitHub для `anomalyco/opencode` показывают новую
мажорную линию, каким бы пакетом npm она ни поставлялась. Четвёртый канал
запрашивает, куда перенаправляет `opencode.ai/install`. 2026-11-03 он
перенаправлял на скрипт инсталлятора OpenCode 1. Этот скрипт устанавливает
версию, которую называет dist-тег `latest` пакета `opencode-ai`, когда это
версия OpenCode 1, и никогда не устанавливает OpenCode 2. Решение по OpenCode
от 2026-11-03 переходит к записи собственных форматов OpenCode 2 там, где
работает OpenCode 2, когда появляется любой из двух сигналов: OpenCode 2
объявляет дату удаления своего перевода форматов OpenCode 1 или
`opencode.ai/install` либо `opencode-ai` переходит на OpenCode 2. Проверка
следит за вторым сигналом. Канал `opencode-ai` и канал инсталлятора несут по
триггеру: проверка не проходит, когда версия `latest` пакета `opencode-ai`
выходит за мажорную версию 1 или когда `opencode.ai/install` перестаёт
перенаправлять на скрипт OpenCode 1. Изменение внутри этого скрипта не меняет
перенаправление, поэтому проверка его не видит. Ни один реестр не отвечает на
первый сигнал, поэтому он остаётся ручной проверкой со сроком до 2027-02-01
вместе со следующим пересмотром закрепления OpenCode.

Antigravity, Cursor, Kiro, Trae и Windsurf не отслеживаются. Каждое из них —
настольное приложение или инструмент командной строки, устанавливаемый
скриптом, и его закрепление не называет канала релизов, который скрипт может
запросить без учётных данных. Файл указывает причину для каждого.

После того как вы перепроверите закрепление по новому релизу или новой цели
перенаправления, обновите поля `reviewed`, `reviewed_on` и `reviewed_from`
этого канала. Триггер на канале версий не даёт проверке пройти каждую неделю,
пока вы не удалите или не измените его. Триггер на адресе инсталлятора
прекращает срабатывать, как только `reviewed` записывает новую цель, поэтому
записывайте эту цель только после того, как действие триггера выполнено.
