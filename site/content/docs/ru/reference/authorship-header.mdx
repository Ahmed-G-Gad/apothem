> **Каноническая нормативная справка для нижестоящих участников.** Этот документ отражает разделы спецификации проекта «Авторство и заголовки файлов» (Спецификация §0.5 + §4.6); это самостоятельная справка, которая поставляется вместе с опубликованным репозиторием. Архитектурное обоснование зафиксировано в ADR-0002.

---

## 1. Каноническая строка заголовка

Каждый применимый файл в экосистеме ДОЛЖЕН начинаться с одной канонической строки SPDX-идентификатора лицензии в синтаксисе комментариев своего семейства типов файлов; перед ней могут стоять только shebang или, в файлах Markdown, YAML-фронтматтер (§5). Эта строка — машиночитаемый маркер лицензии файла; её наличие не подлежит обсуждению для файлов, не подпадающих под исключения, а её содержимое определяется единым источником истины и не придумывается заново для каждого файла. Полный правовой документ об авторских правах находится один раз в корневом файле [`LICENSE`](https://github.com/ahmed-g-gad/apothem/blob/main/LICENSE) репозитория — он не дублируется в каждый исходный файл.

### 1.1 Информационное содержимое (инвариант)

Каноническое содержимое — это ровно одна строка:

1. `SPDX-License-Identifier: MIT` — машиночитаемый маркер лицензии согласно [спецификации REUSE](https://reuse.software/spec/), которую поддерживает FSFE; однозначно разбирается инструментарием SPDX (`reuse lint`, `scancode`), инструментами ядра Linux и нижестоящими сканерами лицензий. Он не содержит визуальной рамки и пофайловых строк с копирайтом, веб-сайтом, e-mail или GitHub — по замыслу пофайловое происхождение выражается единственной строкой SPDX (см. §4).

### 1.2 Эталонная форма (семейство `#`-комментариев)

Канонический текст — записанный здесь в форме с синтаксисом комментариев `#` — служит источником истины в [`src/apothem/schemas/authorship-header.txt`](https://github.com/ahmed-g-gad/apothem/blob/main/src/apothem/schemas/authorship-header.txt):

```text
# SPDX-License-Identifier: MIT
```

Этот текст — **единственный** авторитетный источник. Валидатор `file-header` (§8) сверяет файлы с этой байт-точной фикстурой. Любое расхождение между строкой заголовка файла и этой фикстурой (с учётом подстановки синтаксиса по §2) фиксируется как замечание. Валидатор носит рекомендательный характер, поэтому замечание не проваливает сборку (§8).

## 2. Варианты по типам файлов (байт-точные)

*Информационное содержимое* строки инвариантно; от типа файла зависит только её *синтаксис комментариев*. Полная таблица вариантов по типам файлов:

| Семейство типов файлов | Синтаксис комментариев | Вид варианта |
|---|---|---|
| Семейство `#` — `.sh`, `.bash`, `.zsh`, `.py`, `.rb`, `.pl`, `.ps1`, `.yml`, `.yaml`, `.toml`, `.cff`, `.cfg`, `.gitignore`, `.gitattributes`, `.editorconfig`, `.shellcheckrc`, `.env.example`, `Makefile`, `Dockerfile`, `Procfile`, `CODEOWNERS`, `PKGBUILD`, точки входа shell-скриптов без расширения, такие как `scripts/apothem` | строчный комментарий `#` | `# SPDX-License-Identifier: MIT` |
| Семейство `//` — `.js`, `.jsx`, `.mjs`, `.cjs`, `.ts`, `.tsx`, `.go`, `.rs`, `.java`, `.kt`, `.swift`, `.cs`, `.scala`, `.dart`, `.jsonc` | строчный комментарий `//` | `// SPDX-License-Identifier: MIT` |
| Семейство блочных комментариев — `.html`, `.htm`, `.md`, `.markdown`, `.xml`, `.vue` (область шаблона), `.php` (область шаблона) | `<!-- ... -->` | `<!-- SPDX-License-Identifier: MIT -->` |
| MDX (`.mdx`) | `{/* ... */}` (комментарий JSX-выражения) | `{/* SPDX-License-Identifier: MIT */}` |
| Семейство C-блоков — `.c`, `.cc`, `.cpp`, `.h`, `.hpp`, `.css`, `.scss`, `.less` (`/* */`) | `/* ... */` | `/* SPDX-License-Identifier: MIT */` |
| Семейство `;` — `.ini`, некоторые `.lisp`/`.scm` | строчный комментарий `;` | `; SPDX-License-Identifier: MIT` |
| Семейство `--` — `.sql`, `.lua`, `.hs`, `.elm`, `.ada` | строчный комментарий `--` | `-- SPDX-License-Identifier: MIT` |
| Lock-файлы / сгенерированные / JSON | нет / неприменимо | **Освобождены.** См. §3, список исключений. |

**Вариант для Markdown (каноническая запись):**

```markdown
<!-- SPDX-License-Identifier: MIT -->
```

Обёртка в виде HTML-комментария (или MDX `{/* */}`) в отображаемом виде невидима, поэтому отображаемая поверхность остаётся чистой, а лицензионный маркер в исходнике остаётся машиночитаемым для всех типов файлов.

## 3. Список исключений (категорически освобождены)

Следующие классы **освобождены** от строки заголовка SPDX. Валидатор `file-header` пропускает эти файлы, не проверяя их:

- **`LICENSE`** — сам по себе юридический документ; содержит авторитетную строку с копирайтом, наличие которой подтверждает валидатор `license-author-consistency`.
- **Ассеты `*.svg`** — XML-комментарии ненадёжны для маркеров в виде строчных комментариев, поэтому происхождение SVG фиксируют README ассета и сгенерированные растровые файлы.
- **Файлы JSON (`.json`)** — в JSON нет синтаксиса комментариев. Если для JSON-конфигурации требуется указание авторства, разместите рядом файл `<file>.NOTICE.md`.
- **Lock-файлы** — `package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `Cargo.lock`, `Pipfile.lock`, `poetry.lock`, `go.sum` и т. д. (управляются машиной).
- **Сгенерированные файлы** — всё, что содержит маркер `# Generated by ...` или `// Generated by ...`, либо всё, что соответствует `.gitattributes` `linguist-generated=true`.
- **Вендоренное стороннее содержимое** — файлы в `vendor/`, `third_party/`, `node_modules/`. Они несут собственную лицензию и уведомление вышестоящего проекта; внедрение нашего маркера поверх вышестоящего указания авторства — нарушение лицензии.
- **Файлы `.audit/`** — эфемерные файлы, исключённые через gitignore; вне области опубликованного дерева.
- **Файлы планов (`<project-root>/.apothem/plans/**` и устаревший `<project-root>/.plans/**`)** — эфемерные файлы, исключённые через gitignore; происхождение задаёт фронтматтер плана (см. [`plans-discipline.md`](/docs/reference/plans-discipline) §3).
- **Пустые маркеры** — `.keep`, `.gitkeep` и т. д. (семантически нулевого размера).
- **Бинарные файлы** любого рода.

Сам список исключений закодирован как список regex/glob в [`src/apothem/schemas/header-exceptions.txt`](https://github.com/ahmed-g-gad/apothem/blob/main/src/apothem/schemas/header-exceptions.txt) и служит входными данными для проверки применимости валидатором. Изменения требуют структурированного запроса и нового ADR.

## 4. Взаимодействие с лицензией

Строка SPDX объявляет лицензию проекта в машиночитаемом виде; файл LICENSE объявляет её авторитетно:

- **`SPDX-License-Identifier: MIT`** — машиночитаемый маркер лицензии согласно [спецификации REUSE](https://reuse.software/spec/) и стандарту SPDX. Автоматические сканеры лицензий разбирают эту строку напрямую; синтаксис выражений SPDX совместим с `reuse lint`, scancode-toolkit, FOSSology и инструментарием лицензий ядра Linux.

{/* REUSE-IgnoreEnd */}
- **Корневой [`LICENSE`](https://github.com/ahmed-g-gad/apothem/blob/main/LICENSE) репозитория** — авторитетный юридический документ, содержащий полные условия MIT и имя правообладателя. Это единственное место для заявления об авторских правах; пофайловые заголовки ссылаются на него неявно через общий идентификатор SPDX и не повторяют заявление об авторских правах в каждом файле.

**Однострочная форма.** Пофайловое происхождение — это единственная строка SPDX; правовой документ об авторских правах находится один раз в корневом LICENSE. Многострочные баннеры в рамке (строки с копирайтом, веб-сайтом, e-mail и контактами, заключённые в линованную рамку) отклоняются валидатором: они дублируют в каждом файле контактные метаданные и метаданные об авторских правах, не добавляя ничего, чего машиночитаемый маркер лицензии уже не даёт инструментарию REUSE/SPDX/SBOM. Байт-точная фикстура `src/apothem/schemas/authorship-header.txt` содержит однострочную форму; валидатор сверяется с этой фикстурой.

**Перекрёстные ссылки.** Файл LICENSE (MIT) — при конфликте приоритет имеет юридический документ. ADR-0006 документирует обоснование ратификации сужения баннера.

## 5. Позиция вставки

- Строка SPDX — это **первое содержимое** файла, за двумя исключениями. Строка shebang (`#!/usr/bin/env bash`, `#!/usr/bin/env python3` и т. д.) всегда остаётся строкой 1, а строка SPDX начинается со строки 2. В файлах Markdown / MDX с YAML-фронтматтером первым идёт фронтматтер (следующий пункт).
- Для файлов Markdown / MDX с YAML-фронтматтером фронтматтер остаётся на байте 0, чтобы инструменты могли его разобрать, а комментарий SPDX следует за закрывающим `---`, затем идёт тело, которое в файлах, имеющих H1, открывается этим заголовком. `scripts/inject-header.py` размещает комментарий именно так.
- Одна пустая строка отделяет строку SPDX от следующего содержимого (H1, тела и т. д.).

---

## 6. Политика видимости заголовка

Для файлов Markdown и MDX строка SPDX всегда записывается внутри своей комментарной обёртки (`<!-- ... -->` или `{/* */}`). Она видна только в исходном коде и не появляется в отображаемой странице. У инжектора нет видимого отображения и нет переопределения для отдельного файла. Ни один инструмент в репозитории не читает фикстуру `src/apothem/schemas/header-visibility.yaml`.

## 7. Инжектор — `scripts/inject-header.{sh,py}`

Детерминированный CLI, который:

- Принимает один или несколько путей к файлам (или glob-шаблонов).
- Определяет применимость по списку исключений (§3).
- Определяет текущее состояние заголовка (канонический, некорректный или отсутствует), удаляя найденный неканонический блок баннера, чтобы повторные запуски были идемпотентными.
- Формирует корректный вариант SPDX для типа файла (§2).
- Вставляет строку в правильную позицию (§5), учитывая shebang и фронтматтер.
- Добавляет недостающую пустую строку к строке SPDX, которая стоит в месте вставки без неё, вместо того чтобы вставлять вторую копию выше.
- Работает в трёх режимах: `fix-in-place` (записывает изменения), `emit-patch` (печатает унифицированный diff), `check` (завершается с ненулевым кодом при любом расхождении; ни одно задание CI не запускает его по отслеживаемому дереву).
- Идемпотентен: двукратный запуск ничего не меняет.

Инжектор вызывается целью `make headers-fix`, которая запускает `scripts/inject-header.py --mode fix-in-place`.

## 8. Валидатор — `file-header`

Находится в [`src/apothem/conformity/file_header_grep.py`](https://github.com/ahmed-g-gad/apothem/blob/main/src/apothem/conformity/file_header_grep.py). Для каждого файла в рабочем дереве валидатор определяет его применимость (по §3) и, если файл применим, проверяет, что каноническая строка SPDX присутствует в начале файла, а единственное содержимое, которое он допускает перед ней, — shebang (§5). Из его текущего кода следуют два пробела в покрытии. Во-первых, он не пропускает YAML-фронтматтер, поэтому сообщает как замечания файлы Markdown, у которых строка SPDX стоит после фронтматтера, как того требует §5. Во-вторых, таблица его вариантов не содержит `.mdx`, поэтому файлы MDX он пропускает без проверки.

Опирается на байт-точную фикстуру [`src/apothem/schemas/authorship-header.txt`](https://github.com/ahmed-g-gad/apothem/blob/main/src/apothem/schemas/authorship-header.txt). Прогон по корпусу выводит число замечаний и выборку помеченных файлов для этого сопоставителя. Diff по каждому файлу и процент покрытия не выводятся. Сопоставитель носит рекомендательный характер: его замечания фиксируются и не проваливают сборку ни с `--strict`, ни без него.

## 9. Механизмы самоприменения

Эта дисциплина должна пережить каждую будущую сессию и каждого будущего участника. Обязательные поверхности принудительного применения:

1. **`src/apothem/schemas/authorship-header.txt`** — байт-точная каноническая фикстура; единый источник истины.
2. **`scripts/inject-header.{sh,py}`** — механический инжектор (§7).
3. **Валидатор `file-header`** (§8) — сообщает о расхождениях как о рекомендательных замечаниях; сборку он не проваливает.
4. **Хук pre-commit** — хук `conformity-corpus-perwrite` запускает каждый сопоставитель для записи, включая валидатор `file-header` (§8), по отслеживаемому дереву с `--strict`. Сопоставитель `file-header` носит рекомендательный характер, поэтому его замечания фиксируются и не блокируют коммит. Хук только проверяет. У него нет режима исправления, и он никогда не запускает инжектор (§7), который работает через `make headers-fix`.
5. **Блок обязательного поведения в `CLAUDE.md`** — предписывает ассистенту вставлять каноническую строку SPDX при создании каждого применимого файла.
6. **Файл инструкций GitHub Copilot** по пути `.github/copilot-instructions.md` — предписывает Copilot делать то же при генерации файлов.
7. **Хуки PreToolUse** в `src/apothem/hooks/messages/pretooluse-{write,edit}-header-guard.md` — перехватывают вызовы инструментов Write/Edit для применимых путей, так что строка SPDX вставляется при создании файла, а не обнаруживается позже как замечание валидатора.
8. **Флажок в шаблоне PR** — заявление участника о том, что каждый новый файл содержит каноническую строку SPDX.
9. **Этот документ** (`site/content/docs/reference/authorship-header.mdx`) — каноническое нормативное пояснение.
