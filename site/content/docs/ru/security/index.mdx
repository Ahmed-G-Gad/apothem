Позиция безопасности Apothem опирается на пять опор: усиление защиты цепочки поставок, реагирование на уязвимости, защита веток, подпись релизов и непрерывный анализ безопасности. В этом разделе документируется каждая поверхность.

## Модель угроз

Apothem — это материализатор конфигурации. Он читает общий профиль и
записывает нативные для окружения файлы конфигурации в каталоги, которые
читает каждое окружение. Эта единственная функция ограничивает то, чему он
доверяет, и то, чему не доверяет.

- **Чему Apothem доверяет.** Общему профилю, который составляете вы, и поставляемому дереву исходного кода, размещённому установщиком. Профиль — это ваше заявленное намерение; после проверки по схеме движок рассматривает его как авторитетные входные данные.
- **Чему Apothem не доверяет.** Содержимое профиля попадает в файловую систему только после проверки: сбои схемы, неизвестные идентификаторы окружений, небезопасные пути проекта, отсутствующие источники манифеста, выход за пределы цели и пересечения символических ссылок — всё это останавливает выполнение до любой записи и возвращает структурированную диагностику с `files_written: []`. Исключение составляют ссылки, которые менеджеры dotfiles создают в `~/.config` либо в общей папке навыков, правил или шаблонов или выше неё: по ним выполняется переход, пока они ведут куда-либо внутри вашего домашнего каталога. В Windows соединение считается ссылкой.
- **Чего материализованный вывод никогда не содержит.** Никаких секретов. Диагностика профиля маскирует ключи, похожие на секреты, и значения, похожие на токены, прежде чем они попадут в обычный вывод, JSON, журналы, фрагменты документации или тесты; публичные примеры используют вымышленные идентичности-заполнители и домены. Материализованная конфигурация предназначена для коммита и совместного использования; она не содержит учётных данных.
- **Универсальный минимальный запрет.** Файл `settings.json` Claude Code, который материализует Apothem, несёт не подлежащий обсуждению минимальный порог запретов независимо от любого списка разрешений для окружения; в других окружениях тот же порог — это текст политики в материализованных правилах, а не список запретов на уровне настроек — пути к секретам (`.env*`, `~/.ssh/**`, хранилища учётных данных), деструктивные операции оболочки (`rm -rf`, `sudo`, force-push в защищённые ветки) и выполнение недоверенных входных данных. Ни один список разрешений не расширяет этот порог молча.
- **Радиус поражения.** Записи ограничены каталогами окружений и принадлежащими Apothem поддеревьями поддержки. Существующие управляемые цели перед заменой сохраняются в резервной копии, а общие каталоги обнаружения объединяются поэлементно, поэтому не связанные с ними файлы, созданные оператором, остаются на месте.

## Позиция безопасности во время выполнения

Команды жизненного цикла окружений и записи профиля выполняют проверку перед
записью. Сбои схемы профиля, неизвестные идентификаторы окружений,
небезопасные пути проекта, отсутствующие источники манифеста, выход за пределы
цели и пересечения символических ссылок останавливают выполнение до записи в
файловую систему и возвращают структурированную диагностику с
`files_written: []`. Junction в Windows считается символической ссылкой.
Исключение составляют ссылка в `~/.config` либо в общей папке навыков, правил
или шаблонов или выше неё, которая остаётся внутри вашего домашнего каталога,
и домашняя папка, которая сама является ссылкой. Ссылка никогда не выводит
запись в папку инструмента в вашем домашнем каталоге или в профиль за пределы
домашнего каталога, если только вы сами не назовёте папку вне его через
`XDG_CONFIG_HOME` или `CODEX_HOME`, записанные как путь вне домашнего
каталога, или, для профиля, через `--profile PATH`, записанный так же. По
такому записанному пути выполняется переход, куда бы ни вели его ссылки. Папка
проекта подчиняется собственному правилу, приведённому ниже. Правило для
ссылок действует для установки, обновления, удаления, `apothem rollback` и
команд `apothem profile`, включая `profile set` и `profile init --force` поверх
существующего профиля, а также для профиля, который записывает обратно
`install --clean`. `install --clean` останавливается до того, как что-либо
сохранить в резервной копии или удалить, когда `~/.config` — это ссылка,
ведущая за пределы вашего домашнего каталога, и удаляет цель, которая сама
является ссылкой, как ссылку, не заходя в неё. Поэтому в Windows соединение в
папке инструмента или внутри неё останавливает установку, даже когда ведёт
куда-либо внутри вашего домашнего каталога; замените её самой папкой.

По папке, которую вы называете с помощью `--project`, выполняется переход,
куда бы она ни вела, как и по ссылкам над ней. Это действует, когда папка сама
является ссылкой, в том числе `~/.config`, и когда ссылка ведёт за пределы
вашего домашнего каталога, потому что эту папку назвали вы. Ссылка внутри
папки проекта, на пути, по которому установка там пишет, останавливает
установку. Это действует и тогда, когда ссылка ведёт обратно в папку проекта,
и когда `--project` называет ваш домашний каталог. Инструмент, который также
пишет в вашем домашнем каталоге, например в `~/.config/apothem`, проверяет эти
пути по приведённым выше правилам для домашнего каталога. Поэтому ссылка
`~/.config`, ведущая за пределы домашнего каталога, останавливает установку
этого инструмента, даже когда `--project` называет `~/.config`.

`XDG_CONFIG_HOME` и `CODEX_HOME` могут поступать из файла `.envrc` проекта или
из скрипта, который вы подключаете через source, а не только из профиля вашей
оболочки. Когда любая из них называет папку вне вашего домашнего каталога,
Apothem изменяет файлы там, потому что именно эту папку она называет.

Собственная папка Apothem, `~/.apothem`, так не проверяется. Она содержит
резервные копии, журнал установки и их файлы блокировки; когда она является
ссылкой, каждая команда, которая там пишет, следует по ней, куда бы она ни
вела, а `apothem backups
prune` и автоматическое хранение резервных копий удаляют старые наборы
резервных копий на дальнем конце этой ссылки.

Операции установки и обновления сохраняют существующие управляемые цели,
создавая их резервные копии перед заменой. Общие каталоги обнаружения
объединяются поэлементно, поэтому не связанные с ними файлы, созданные
оператором, остаются на месте. `--dry-run` выполняет ту же проверку и сообщает
о запланированных результатах, не создавая каталогов или файлов.

Диагностика профиля маскирует ключи, похожие на секреты, и значения, похожие
на токены, прежде чем они попадут в обычный вывод, вывод JSON, журналы,
фрагменты документации или тесты. Публичные примеры используют вымышленные
идентичности-заполнители и домены.

## Доказательства выпуска для цепочки поставок

Каждый GitHub Release несёт следующие доказательства. Какие файлы они
охватывают, зависит от пункта:

- **Подписи Sigstore** через [`sigstore/cosign-installer`](https://github.com/sigstore/cosign-installer)
  для каждого распространяемого файла: sdist, wheel, пакета VS Code
  `apothem.vsix`, SBOM `sbom.cdx.json`, трёх платформенных архивов и
  `SHA256SUMS`. У каждого есть собственный `<file>.cosign.bundle`. У файла
  происхождения `provenance.intoto.jsonl` нет бандла cosign; генератор SLSA
  подписывает его внутри собственного конверта DSSE.
- **Происхождение сборки SLSA-3** через [`slsa-framework/slsa-github-generator`](https://github.com/slsa-framework/slsa-github-generator)
  в `provenance.intoto.jsonl` для четырёх файлов: sdist, wheel,
  `apothem.vsix` и `sbom.cdx.json`. Релизный рабочий процесс также просит GitHub
  хранить собственную запись о происхождении сборки тех же файлов — запись,
  отдельную от этого файла; этот шаг не блокирует релиз, поэтому у релиза её
  может не быть. У
  платформенных архивов и `SHA256SUMS` нет происхождения SLSA; их покрывают
  подписи cosign и подписанный тег релиза.
- **CycloneDX SBOM** поставляемых wheel и sdist, который записывает `scripts/release/generate_sbom.py`: пакет apothem, каждый пакет, вендоренный в `apothem/_vendor`, с его лицензией, объявленные требования времени выполнения и SHA-256 каждого дистрибутива. SBOM подписан и покрыт происхождением сборки так же, как дистрибутивы
- **Заявления о происхождении npm** через OIDC Trusted Publishing для `@ahmed-g-gad/apothem`
- **Подписанные GPG теги git** (ключ EDDSA `70396FED9C634163`)

## Проверка релиза

Скачайте все ресурсы релиза в пустой каталог, затем проверьте подписи и
происхождение сборки. Замените `vX.Y.Z` и `X.Y.Z` на скачанный релиз.

```bash
gh release download vX.Y.Z --repo ahmed-g-gad/apothem
cosign verify-blob \
  --bundle apothem-X.Y.Z-py3-none-any.whl.cosign.bundle \
  --certificate-identity https://github.com/Ahmed-G-Gad/apothem/.github/workflows/release.yml@refs/tags/vX.Y.Z \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  apothem-X.Y.Z-py3-none-any.whl
slsa-verifier verify-artifact \
  --provenance-path provenance.intoto.jsonl \
  --source-uri github.com/Ahmed-G-Gad/apothem \
  --source-tag vX.Y.Z \
  apothem-X.Y.Z-py3-none-any.whl apothem-X.Y.Z.tar.gz
```

`cosign` печатает `Verified OK`, а `slsa-verifier` печатает `PASSED: SLSA
verification passed`. Повторите команду `cosign` для любого другого ресурса с
его `<asset>.cosign.bundle` (в более ранних релизах бандлы платформенных
архивов и `SHA256SUMS` называются `<asset>.sig`). Архивы darwin и linux — это
одни и те же байты под двумя именами, поэтому `SHA256SUMS` перечисляет один
дайджест дважды. Из клона
`bash scripts/release/verify-provenance.sh --require-all <download-dir>`
выполняет три проверки за один проход: манифест `SHA256SUMS`, каждый бандл
cosign и происхождение SLSA для wheel, sdist, `apothem.vsix` и подписанного
SBOM. Он пропускает проверку, для которой отсутствует инструмент (`cosign`,
`slsa-verifier`) или файл (`SHA256SUMS`), а его последняя строка называет
выполненные и пропущенные проверки. Только
`chain OK (3 of 3 layers verified: ...)` означает, что релиз проверен; строка,
начинающаяся с `partial check`, этого не означает. С `--require-all`
(`-RequireAll` для `verify-provenance.ps1`) частичная проверка завершается с
кодом 1; без него частичная проверка завершается с кодом 0.

От двух деталей зависит, имеет ли проверка какой-либо смысл:

- **Регистр владельца.** Проверки идентичности чувствительны к регистру, а
  сертификаты содержат владельца в том виде, в каком его сообщает GitHub:
  `Ahmed-G-Gad`. Владелец в нижнем регистре не проходит проверку ни в одном
  из двух инструментов.
- **Точная идентичность.** Предпочитайте `--certificate-identity` с полным
  субъектом, указанным выше. Чтобы принимать любой тег релиза, привяжите
  шаблон с обоих концов:

  ```bash
  --certificate-identity-regexp '^https://github\.com/Ahmed-G-Gad/apothem/\.github/workflows/release\.yml@refs/tags/v[0-9]+\.[0-9]+\.[0-9]+$'
  ```

  Непривязанный шаблон, такой как `github.com/Ahmed-G-Gad/apothem`, также
  совпадает с поддельным субъектом, который лишь содержит этот текст,
  например с рабочим процессом в другом репозитории на ветке, названной в
  честь этого репозитория.

[Руководство по циклу релиза](/docs/runbooks/release-cycle) фиксирует те же
команды как проверку сопровождающего после релиза.

### Пересборка релиза и сравнение

Wheel и sdist воспроизводимы: пересборка тега с помощью релизного
инструментария даёт опубликованные дайджесты SHA-256. Используйте Python 3.12
в Linux, как это делает релиз:

```bash
git clone https://github.com/ahmed-g-gad/apothem && cd apothem
git checkout vX.Y.Z
python3.12 -m venv .build && . .build/bin/activate
pip install --require-hashes -r scripts/release/requirements-build-linux.txt
export SOURCE_DATE_EPOCH="$(git log -1 --pretty=%ct)"
python -m build --no-isolation
python scripts/release/normalize_sdist.py dist/*.tar.gz
sha256sum dist/*
```

Сравните дайджесты с опубликованными wheel и sdist. Сборка использует
зафиксированный по хешу setuptools, закреплённый в `pyproject.toml`, а
`normalize_sdist.py` удаляет из sdist время сборки, владельцев файлов и
временные метки чекаута.
