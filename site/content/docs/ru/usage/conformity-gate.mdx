Шлюз соответствия в `src/apothem/conformity/gate.py` выполняет механическую
часть пятнадцатипунктного шлюза предэмиссии (M1-M15) для каждого артефакта,
который создаёт оператор.

Команды на этой странице предполагают чекаут Apothem, поэтому перед каждой
запускаемой вами командой добавляйте `PYTHONPATH=src`. После установки через
скрипт используйте `PYTHONPATH="$HOME/.apothem/src"` вместо `PYTHONPATH=src`.

## Запуск шлюза

Шлюз **по умолчанию рекомендательный**: он сообщает о находках и завершается с
кодом `0`, поэтому локальный запуск никогда вас не блокирует. Добавьте
`--strict` (или задайте `APOTHEM_CONFORMITY_STRICT=1`), чтобы завершаться с
ненулевым кодом при блокирующей находке, — этот режим используют CI и
pre-commit, чтобы проверка нарушающего изменения завершалась неудачей.

```bash
# Advisory: report every validator's findings across the repo, exit 0
PYTHONPATH=src python -m apothem.conformity.gate --all .

# Strict: exit non-zero (code 2) when a blocking finding is present
PYTHONPATH=src python -m apothem.conformity.gate --all --strict .
```

Эти команды запускают шлюз из чекаута Apothem. `python -m` сначала читает
модули из текущей папки, поэтому запускайте их из корня чекаута или из другой
папки, которой вы доверяете. Чтобы проверить проект, файлам которого вы не
доверяете, запускайте шлюз по пути к его скрипту с `-E -s`:
`python3 -E -s src/apothem/conformity/gate.py --all .` в чекауте или
`python3 -E -s ~/.apothem/src/apothem/conformity/gate.py --all .` после
установки через скрипт. В Windows используйте `python` вместо `python3` и
полный путь, поскольку Windows PowerShell и cmd не раскрывают `~`:
`$HOME\.apothem\src\apothem\conformity\gate.py` в PowerShell или
`%USERPROFILE%\.apothem\src\apothem\conformity\gate.py` в cmd. Запуск по пути
к скрипту не пускает текущую папку в первую запись пути поиска модулей Python;
`-E` также исключает `PYTHONPATH`, где пустая или относительная запись тоже
означает текущую папку, а `-s` исключает ваши пользовательские site-packages.
Так файлы проекта не попадают только в собственный код Python шлюза; о `git`,
который запускает шлюз, речь пойдёт дальше.

Три автономных валидатора запускают `git` в проверяемом проекте, как и
`--all`, который их запускает, и `--all-perwrite`, который перечисляет
отслеживаемые файлы через `git ls-files`:

```text
agents-md-coverage-grep
conventional-commit-grep
no-global-plans-grep
```

Собственные настройки этого репозитория — в `.git/config`, во включаемых им
файлах и в `.git/config.worktree` — могут назвать программу, которую git
запустит, даже когда только читает. Шлюз отключает каждую известную ему такую
настройку параметрами в командной строке git, которые имеют приоритет над
каждым файлом, читаемым git, и также доходят до любого git, который git
запускает в подмодуле:

- никакого монитора файловой системы (`core.fsmonitor`);
- никакой программы подписи (`gpg.program`, `gpg.ssh.program` и
  `gpg.x509.program` указывают на путь, где ничего не может существовать, а
  `log.showSignature` выключен);
- никаких хуков, никакого пейджера и никакого автоматического обслуживания;
- никакой внешней программы diff или преобразования текста, а изменения
  подмодулей показываются только как идентификаторы коммитов, поэтому git не
  запускает второй git внутри подмодуля;
- содержимое файлов читается через `git cat-file blob`, который отклоняет
  запись подмодуля там, где `git show` показал бы её как коммит.

Три настройки называют не программу, а файл, который git читает, и этот файл
может лежать на сетевом пути. Командная строка шлюза не даёт git читать и их:
файл порядка diff (`diff.orderFile`), файл исключений (`core.excludesFile`) и
файл mailmap.

Шлюз также задаёт `GIT_NO_LAZY_FETCH=1` и пустую `GIT_ALLOW_PROTOCOL`, поэтому
git никогда не загружает недостающий объект частичного клона по адресу,
который называет репозиторий. Шлюз запускает git только из записи вашего
`PATH` с полным путём. Он никогда не берёт git из текущей папки: он пропускает
пустые и относительные записи `PATH`, которые означают эту папку, и не ищет
там в первую очередь, как Windows делает для голого имени программы. git
получает только эти записи с полным путём для программ, которые он запускает
по имени.

Поэтому эти команды можно запускать на проекте, который пришёл со своей папкой
`.git` от кого-то другого, в архиве или в общей папке: ни одна из настроек выше
не может заставить шлюз запустить программу. Остаются два ограничения.
Репозиторий всё ещё может заставить git читать путь где-то ещё через любую
настройку или файл, которые его называют, например `include.path` или
`includeIf`, `core.worktree`, строку `gitdir:` файла `.git` или
`.git/objects/info/alternates`; в Windows сетевой путь там (`\\server\share`)
заставляет Windows подключиться к этому серверу и выполнить ваш вход. Один
случай уже: Git for Windows 2.55 отклоняет сетевой путь в строке `gitdir:` до
подключения, если ваша собственная настройка `safe.directory` не разрешает
этот путь. Кроме того, список охватывает настройки, известные сегодня; более
поздний релиз git может добавить новую. Ваши собственные глобальные и
системные настройки git по-прежнему действуют, кроме перечисленных выше,
которые переопределяет командная строка шлюза. Это касается только git:
`python -m` сначала читает модули Python из текущей папки, поэтому запускайте
шлюз из папки, которой вы доверяете.

Коды выхода: `0` — чисто (или рекомендательный режим), `2` — блокировка по
находкам в строгом режиме, `3` — ошибка использования: неизвестный флаг или имя
валидатора, несуществующий файл или несуществующий корневой каталог. `--help`
выводит полную справку по использованию и завершается с кодом `0`. Каждый
автономный валидатор принимает тот же `--help` и завершается с кодом `3` при
неизвестном флаге или отсутствующем корне.

Относительный корень, например `.`, разрешается в абсолютный путь до запуска
любого валидатора, поэтому `--all .` и `--all "$PWD"` проверяют одно и то же
дерево. Каждый валидатор сообщает `inspected` — сколько целей он проверил, — и
`--all` копирует это число в каждую запись результата. Валидатор, который ничего
не проверил, сообщает `passed: false`, поэтому неверный рабочий каталог не может
пройти молча. Два валидатора наборов планов — это одно из исключений: наборы
планов размещаются в игнорируемом git дереве `.apothem/plans/`, поэтому на чистом
чекауте они сообщают `empty_scope_expected: true` и всё равно проходят.
Валидаторы рабочих процессов поступают так же, когда в проекте ещё нет каталога
`.github/workflows/`, а валидатор темы коммита — когда в корневом каталоге нет
истории коммитов.

Проект может прийти с файлами, созданными кем-то другим, в архиве или в общей
папке, поэтому каждый валидатор `--all` открывает и перечисляет только обычные
файлы и настоящие папки, до которых доходит через настоящие папки под корнем.
Он никогда не следует по символической ссылке или, в Windows, по точке
соединения (junction) и на любом уровне под корнем считает отсутствующим
каждый из этих элементов:

- ссылку, даже ведущую внутрь корня. Обход или список папки пропускает её,
  поэтому её цель проверяется только там, где валидатор доходит до неё по её
  собственному пути;
- именованный канал, устройство или сокет, где чтение ждало бы или никогда не
  закончилось бы;
- в Windows — имя, оканчивающееся точкой или пробелом, потому что Windows
  открыла бы под этим именем другую запись.

Некоторые проверки всё же используют ссылку, не заходя в неё:

- для фиксированного файла, который является символической ссылкой, например
  `CLAUDE.md`, указывающего на другой файл, шлюз читает текст самой ссылки и
  открывает названный файл, только если это обычный файл внутри проекта,
  достигнутый через настоящие папки. Ссылка `README.md` в папке учитывается так
  же. Абсолютная ссылка учитывается, если она записана через папку проекта в
  том виде, в каком та разрешается, или в Windows через тот же путь в другом
  регистре букв; валидатор, запущенный отдельно, также принимает папку в том
  виде, в каком вы её ввели, если этот путь не содержит `..`, а шлюз разрешает
  папку до запуска каждого валидатора. Связанный `.gitattributes` по-прежнему
  считается отсутствующим, потому что git его не читает;
- проверка заблудившихся планов в `no-global-plans-grep` сообщает по имени о
  папке планов или папке `.apothem`, которая является ссылкой, куда бы ссылка
  ни вела;
- `no-toplevel-docs-grep` сообщает по имени о ссылке `docs` в корне;
- `naming-grep` проверяет собственное имя ссылки.

Отчёт каждого валидатора перечисляет в `skipped_links` ссылки и специальные
файлы, которые он пропустил, поэтому ссылка никогда не скрывает файл бесследно.
Там же перечисляется папка, содержимое которой он не смог перечислить (нет доступа, слишком
длинный путь, ошибка чтения), и запись `.git` папки, которую он пропустил как
вложенный чекаут, если эта запись — ссылка или специальный файл; сама папка
перечисляется в `skipped_checkouts`, описанном ниже. Валидатор,
который проходит при отсутствии своей папки, например валидаторы рабочих процессов, не
проходит, если эта папка — ссылка: файлы могут быть за ней, поэтому запуск
завершается неудачей, как запуск, ничего не проверивший. Жёсткая ссылка —
обычный файл и читается как обычный файл. Валидаторы `--all` и `--all-perwrite`
смотрят на каждый уровень, когда доходят до него, а затем открывают файл уровень
за уровнем от корня, каждую папку внутри открытой перед ней, никогда не через
ссылку. Поэтому, если кто-то, кто может писать в проект, во время работы шлюза
подменит уже проверенный файл или папку над ним ссылкой или именованным каналом,
шлюз не читает через ссылку и не ждёт на канале: файл не читается. Валидатор
`--all` считает его отсутствующим или нечитаемым, как считает ссылку, и
перечисляет подменённую запись в `skipped_links`; `--all-perwrite` считает его
`link`, а при повторной подмене — `unreadable`, как описано ниже. В Windows
остаётся одно ожидание, как и при обычном открытии: программа, которая может
писать в проект, может держать на файле оппортунистическую блокировку (oplock)
и не отпускать её, когда шлюз открывает файл. Ни один способ открыть файл не
обходит это ожидание, поэтому валидатор `--all` ждёт до своего предела в 10
минут, а `--all-perwrite`, у которого такого предела нет, — пока эта программа
не отпустит файл. В `--all` и `--all-perwrite`
сам шлюз открывает
только обычные файлы внутри корня, проверяя каждую папку на пути с помощью
`lstat`, включая каждый путь, который перечисляет git, и никогда не читает
внутри записи `.git`. Перед запуском git три валидатора `--all`, запускающие
git, и две проверки `--staged` смотрят с помощью `lstat` на запись `.git` корня
и каждой папки выше него, в которой ищет git, в том состоянии, в каком дерево
находится в этот момент; если какая-либо из них — ссылка или на неё нельзя
посмотреть, они не запускают git. Это отклоняет и проекты, с которыми git
справился бы безопасно, например любой проект под домашней папкой, чей `.git` —
ссылка, даже проект с собственным репозиторием: это сознательная цена простого
правила. Три валидатора `--all` запускают git без `GIT_DIR` и других переменных,
которые называют репозиторий, его хранилища или его индекс; проверки `--staged`
сохраняют `GIT_DIR` хука. Какой репозиторий затем читает git, не проверяется:
строка `gitdir:`, `commondir`, alternates, `core.worktree`, include или ссылка
внутри папки git могут назвать другой, и git следует за ними, поэтому git может
дойти до сетевого пути или ждать до своего предела времени. Шлюз использует
вывод git только как имена, режимы, буквы состояния, тему последнего коммита,
время коммитов и несколько настроек и никогда не открывает путь, выведенный git,
не проверив каждый уровень внутри корня. Найдя ссылку, каждый из трёх
валидаторов `--all` перечисляет её в `skipped_links` (относительно корня, если
она внутри него, полным путём, если выше). `conventional-commit-grep` тогда
сообщает `not-a-git-repo`, как вне чекаута, но не проходит: он выдаёт
`check_error`, который называет ссылку. `no-global-plans-grep` сообщает о ссылке
как о находке и завершается неудачей, а проверка сопутствующих файлов пропускает
свой тест актуальности, как и без истории. `--all-perwrite` тоже не перечисляет
отслеживаемые файлы: он завершается неудачей с `check_error`, который называет
ссылку, как и обе проверки `--staged`, которые называют ссылку только в
`check_error` или сообщают там, что запись `.git` в папке, где они запущены,
является ссылкой: они читают репозиторий, названный в `GIT_DIR` хука, но всё
равно отклоняют ссылку на пути поиска от папки, в которой они запущены. Запись
`.git`, на которую шлюз не может посмотреть (слишком длинный путь, недоступный
сетевой ресурс, нет доступа), не является ссылкой и не указывается в
`skipped_links`: `conventional-commit-grep` завершается неудачей со статусом
`git-failed` и `check_error`; проверка сопутствующих файлов, `--all-perwrite` и
обе проверки `--staged` завершаются неудачей с `check_error`, который говорит,
что на запись нельзя посмотреть, а `no-global-plans-grep` сообщает о ней как о
находке.

Каждый автономный валидатор выполняется как отдельная программа, и шлюз даёт
ему 10 минут — в `--all` и в `--check`. Самый медленный занимает около минуты
на собственном репозитории Apothem. Валидатор, который всё ещё работает к
пределу, останавливается вместе с каждой программой, которую он запустил,
например командой `git`, которая всё ещё ждёт, и сообщается с
`passed: false` и `check_error`, где сказано, что он не завершился. В Linux и
macOS каждый валидатор выполняется в собственном сеансе, и `SIGTERM` или
`SIGHUP`, отправленный шлюзу, например от `timeout` или закрытого терминала,
останавливает программы валидатора до того, как шлюз завершится с кодом 128
плюс номер сигнала. Это верно и для сигнала, который приходит, пока шлюз
запускает или останавливает валидатор: он ждёт окончания этого шага, и код
выхода остаётся 128 плюс его номер, даже если во время этого шага следует
Ctrl+C. `SIGKILL`, который не может перехватить ни одна программа, завершает
там только сам шлюз: запущенный им валидатор работает дальше
до своего завершения, а команда `git`, которую этот валидатор ждёт, всё равно
останавливается по своему пределу. В Windows каждый валидатор выполняется в
объекте задания (job object), который также завершает его программы, когда
завершается сам шлюз.
Каждая программа, которую шлюз запускает там, ждёт в приостановленном
состоянии, пока не окажется в объекте задания. Программа, которую он не может
возобновить, останавливается, и ошибка сообщает, находится ли она в объекте
задания. Программа, которой что-то другое велело завершиться до её
возобновления, так и не выполнялась и завершается неудачей так же, каким бы ни
был её код выхода, с двумя исключениями. Программа, завершившаяся с кодом
выхода 259 — тем же кодом, который Windows даёт работающей программе, —
читается как работающая, пока Windows ещё её завершает. Программа,
завершившаяся непосредственно перед возобновлением, распознаётся, только когда
шлюз читает её код выхода в пределах 1 мс после возобновления; более позднее
чтение, например на загруженной машине или когда заняты другие потоки
вызывающего процесса, принимает её код выхода за собственный код программы. На
машине, где проводились
измерения, самая маленькая программа, которую может запустить Windows, жила не
меньше 3 мс после возобновления, а `git` — 27 мс, поэтому программа, которая
выполнялась, не принимается за завершённую. Программу, завершившуюся сразу
после возобновления, тоже нельзя отличить от выполнившейся. На
любой платформе, в собственном запуске шлюза, Ctrl+C, пришедший во время
запуска, ждёт, пока программа не начнёт выполняться (в Windows — пока шлюз не
попытается её возобновить), поэтому ни одна программа не остаётся
приостановленной или работающей сверх своего предела. Второй Ctrl+C,
пришедший, пока шлюз останавливает программу, ждёт окончания остановки.
Пришедший непосредственно перед началом остановки заставляет шлюз повторить
остановку, до трёх раз. Если эти попытки не удаются или Ctrl+C попадает между
двумя из них, шлюз останавливает программу, не задерживая сигналы, снова до
трёх раз, поэтому ещё один Ctrl+C не пропускает остановку. Чтобы программа
осталась работать, нужно несколько нажатий Ctrl+C, каждое в пределах
микросекунд от одной из этих точек. После остановки шлюз ждёт до полсекунды,
пока остановленная программа завершится, поэтому в Linux и macOS она не
остаётся висеть как завершённый, но не убранный процесс (defunct), а Ctrl+C во
время этого ожидания не заменяет уже идущее завершение. Обработчик другого
сигнала, заданный вызывающим процессом, всё же может оставить программу
работающей (в Windows — приостановленной), когда его ошибка приходится на
несколько микросекунд после запуска программы, до того как шлюз её
зарегистрирует. Когда шлюз меняет
собственные обработчики сигналов, сигнал,
пришедший посреди изменения, не оставляет обработчик изменённым. В Linux и
macOS шлюз блокирует Ctrl+C, `SIGTERM` и `SIGHUP`, и никакой другой сигнал, на
те несколько микросекунд, которые занимает изменение, поэтому такой сигнал ждёт
окончания изменения и встречает обработчики, действующие на тот момент. Затем
шлюз снимает блокировку только с тех сигналов, которые он заблокировал. Для
любого другого сигнала, в Windows и для сигнала, пришедшего непосредственно
перед блокировкой, изменение, прерванное сигналом, выполняется снова, до трёх
раз. Если восстановить обработчики не удаётся ни с одной попытки, шлюз делает
последнюю попытку для каждого оставшегося обработчика. Обработчик остаётся
изменённым, когда ошибка прерывает и эту последнюю попытку, например
`TimeoutError` от таймера, заданного вызывающим процессом и срабатывающего
каждый раз, а в редких случаях — когда несколько сигналов, чьи обработчики
выбрасывают исключения, приходят один за другим в пределах микросекунд и
пропускают последнюю попытку. Ошибка, которая
возвращается при каждой попытке, например `RecursionError` у предела рекурсии
Python, завершает изменение не более чем за две попытки, и работа
продолжается. Шлюз восстанавливает свои обработчики вызовами не глубже тех,
которые их изменили, поэтому у этого предела он не оставляет Ctrl+C
игнорируемым. Обработчик `SIGTERM`, который вызывающий процесс задаёт во время
запуска, остаётся на месте. В Linux и macOS, в субинтерпретаторе Python, где
нельзя задавать обработчики сигналов, шлюз запускает свои программы, не меняя
обработчики; в Windows Python не может читать вывод программы из
изолированного субинтерпретатора, который не допускает фоновых (daemon)
потоков. Ctrl+C выводит одну строку и завершается с кодом
`130`. Пределы складываются: запуск, в
котором ждут несколько валидаторов, занимает сумму их пределов.

Пять валидаторов также дают каждой выполняемой ими команде `git` собственный
предел времени. Пределы действуют на любой платформе, в том числе в Windows,
когда `git` в `PATH` — это лаунчер, который устанавливает Git for Windows и
который запускает настоящий git:

```text
conventional-commit-grep            git log -1, git rev-parse           1 minute
                                    git ls-files, git config            1 minute
agents-md-coverage-grep             git rev-parse, git config           1 minute
                                    git log over the whole history      5 minutes
no-global-plans-grep                git ls-files                        1 minute
production-ready-pr-grep --staged   git diff --cached                   1 minute
semver-stability-grep --staged      git diff --cached, git cat-file     1 minute
```

В большинстве проектов эти команды занимают доли секунды, поэтому предел
достигается, только когда `git` ждёт того, что никогда не наступит.
Собственные настройки git проекта могут заставить его ждать бесконечно,
например `include.path` в его `.git/config`, который называет именованный
канал. Команда `git`, работающая дольше своего предела, не проходит: валидатор
сообщает `passed: false` с `check_error`, который называет эту команду. Не
проходит и `git`, отклоняющий найденный им чекаут, например принадлежащий
другому пользователю или содержащий неверную строку в `.git/config`; тогда
`check_error` приводит код выхода git, а код выхода 128 git использует, когда
не может открыть или прочитать репозиторий. Папка, запись `.git` которой git
не может открыть, считается таким чекаутом, потому что нужная проверкам
история может быть там, непрочитанная: пустая папка `.git` вне любого другого
чекаута или файл `.git`, называющий папку, которой больше нет, — такие остаются
от распакованного рабочего дерева или скопированного подмодуля. Удалите эту
запись или запустите шлюз на полном чекауте. Это относится и к проверке
устаревших сопутствующих файлов, хотя в остальном её находки рекомендательные,
а проверка темы коммита тогда также сообщает `inspected: 0` с
`empty_scope_expected: false`. В Windows `git`, который шлюз запустил, но не
смог возобновить, тоже считается неудавшимся `git`: `check_error` приводит код
выхода 128, и это никогда не считается отсутствием `git`. Проверка устаревших
сопутствующих файлов читает всю историю один раз, и на это чтение отводится 5
минут, поэтому большая история означает медленную работу, а не сбой; история,
чтение которой занимает больше времени, проваливает проверку. Обычная папка вне
любого git-чекаута, репозиторий без единого коммита или машина без `git`
проходят эти проверки, как и раньше. Так же проходит частичный клон,
созданный через `git clone --filter`: шлюз не даёт `git` загружать то, что клон
пропустил, а git не даёт ответа, который отличал бы объект, пропущенный клоном,
от потерянного. Поэтому в частичном клоне проверка устаревших сопутствующих
файлов считает любое неудачное чтение истории недоступной историей: она
пропускает свой тест актуальности и проходит, как и без истории. Эти
исключения, как и `check_error` для чекаута, который отклоняет git, относятся к
остальным четырём валидаторам: `no-global-plans-grep` нужен чекаут, который git
может прочитать, поэтому вне чекаута, на машине без `git` или в чекауте,
который git отклоняет, он завершается неудачей, как и раньше, с причиной в
стандартном потоке ошибок: кодом выхода git, а не собственным текстом git. Как
и для любого непрошедшего результата, рекомендательный режим по умолчанию
сообщает о нём и завершается с кодом `0`, а `--strict` — с кодом `2`.

Для двух проверок `--staged` значение настройки diff, которое git не может
прочитать, например `diff.renameLimit = abc`, — одна из таких неверных строк:
`git diff` завершается неудачей, а непрочитанный набор изменений — это не
пустой набор. Эти две проверки, проверка темы коммита и проверка устаревших
сопутствующих файлов ищут чекаут в папке, где они запущены, и в папках выше
неё, поэтому то же самое верно и в подпапке чекаута. Они прекращают поиск там
же, где git: на папке, названной в `GIT_CEILING_DIRECTORIES`, и, вне Windows, на
папке в другой файловой системе, если не задана
`GIT_DISCOVERY_ACROSS_FILESYSTEM`. Поэтому папка без собственного репозитория,
смонтированная ниже другой, по-прежнему проходит. Проверка темы коммита,
запущенная на подпапке чекаута, проверяет последний коммит чекаута, когда
чекаут отслеживает файл в этой подпапке или в ней есть подготовленный (staged)
файл. Там, где чекаут не различает регистр, как в Windows и macOS, это верно и
для подпапки, имя которой на диске изменилось только в регистре букв. Папка,
которую чекаут не отслеживает, неотслеживаемая или игнорируемая, не имеет
собственной истории и проходит, например новый проект внутри репозитория
dotfiles в домашней папке. Пустая папка `.git` выше папки, где запущена
проверка, без репозитория дальше вверх заставляет git завершиться неудачей, и
проверка сообщает `git-failed`.

Обе проверки `--staged` читают имена подготовленных файлов от вершины рабочего
дерева, какой бы ни была ваша настройка `diff.relative`, поэтому настройка для
подпапки никогда не скрывает подготовленный файл.

`semver-stability-grep --staged` ищет пакет в папке, где он запущен, а затем в
папках выше неё — до ближайшей папки, в которой есть репозиторий или где git
прекращает поиск, — и запускает git в папке, где находится пакет, поэтому
запуск из подпапки проверяет тот же набор изменений. Файл версии он тоже читает
из этой папки, поэтому проверяется и пакет, лежащий ниже вершины репозитория.
Если между папкой, где он запущен, и пакетом лежит файл `.git`, который git
отклоняет, git вместо этого запускается в папке, где запущена проверка,
останавливается на этом файле, и проверка сообщает `check_error`. git
отклоняет файл `.git`, который не называет репозиторий, больше 1 MiB или не
содержит `gitdir:`, один пробел и путь, за которыми следуют только концы строк.
В Windows проверка также отклоняет файл `.git`, называющий сетевой путь, путь
устройства или путь NT (`\\host\share`, `\\?\`, `\??\`), и сама этот путь не
ищет. Она также отклоняет путь, который отклоняет Git for Windows: имя,
оканчивающееся точкой или пробелом либо являющееся именем устройства, например
`aux.d`, `lpt0` или `CONIN$` (но не `com0`, который Git for Windows
принимает), или `:` после буквы диска. Байт пути, не являющийся UTF-8, она
читает так же, как Git for
Windows: начиная с `0xA0` — как этот символ, а ниже — как две шестнадцатеричные
цифры, поэтому `0x9F` читается как `9f`. Проверяется ближайшая папка, в которой
есть `src/apothem/__init__.py`; `GIT_WORK_TREE` проверка не читает. В проекте
без этого пакета там проверять нечего: он проходит без запуска git, в каком бы
состоянии ни был его репозиторий.

Шлюз читает каждый список имён путей от git байт в байт, поэтому имя,
содержащее перевод строки, возврат каретки или байт, не являющийся UTF-8,
называет один и тот же файл для каждой проверки. Один случай прочитать нельзя:
Windows не может передать git имя не в UTF-8, а такое может содержать только
индекс, созданный в другой системе. Тогда `semver-stability-grep --staged`
сообщает `check_error` для набора изменений; этот файл она не пропускает.
Чтение истории в проверке устаревших сопутствующих файлов — исключение из
первого предложения: там git выводит имя с управляющим символом в
экранированной форме, а байт не в UTF-8 читается как символ замены, поэтому эта
проверка не может сопоставить папку с таким именем.

Проверка устаревших сопутствующих файлов считает каноном только `AGENTS.md` на
вершине репозитория. Когда вы запускаете её на подпапке с собственным README,
`AGENTS.md` этой подпапки — сопутствующий файл папки. Когда подпапка является
вершиной собственного репозитория, например подмодуля или вложенного клона, её
`AGENTS.md` — канон этого репозитория. Запуск на всём репозитории пропускает
некоторые подпапки, например тестовые фикстуры и вложенные репозитории, которые
проверяет запуск на самой подпапке. Подпапка без README таким образом не
проверяется как отдельная папка; запустите проверку на папке выше неё.
Сопутствующий файл, удалённый в коммите и записанный снова, считается новым,
пока вы его не закоммитите.

Шесть валидаторов начинают с корня репозитория и ищут проверяемые ими файлы по
всему дереву:

```text
agents-md-coverage-grep
agnosticism-grep
dynamism-grep
freshness-token-grep
plain-language-grep
reference-token-grep
```

Они пропускают вложенные git-чекауты, такие как рабочие деревья (worktrees),
подмодули и вложенные клоны (папка, чей файл или папка `.git` содержит или
называет репозиторий; обычный файл `.git` или пустая папка `.git` не скрывает
свою папку), никогда не заходят в папку-ссылку и пропускают каталоги с
зависимостями, виртуальными окружениями, кешами или результатами сборки, такие как `node_modules`, `venv` и `dist`. Проверка
заблудившихся планов в `no-global-plans-grep` также останавливается на вложенном
чекауте. Каждая папка, пропущенная как вложенный чекаут, перечисляется в отчёте
в `skipped_checkouts`, что бы ни называла её запись `.git`, ведь одной строки
`gitdir:` достаточно, чтобы git пропустил любую папку. Этот список никогда не
меняет вердикт, и папка, пропущенная так, не проверяется; папки, пропущенные по
имени, например `node_modules`, в него не входят. Запуск любого из них сообщает о чекауте,
на который он был направлен, и ни о чём другом. Валидатор, который читает одну
фиксированную папку, например `naming-grep` в `src/apothem/`, читает всё, что
находится ниже этой папки.

`--all-perwrite` проверяет файлы, которые `git ls-files` перечисляет под
корнем. git перечисляет каждую запись точно так, как её хранит индекс
репозитория, а проект может прийти с индексом и файлами, созданными кем-то
другим, поэтому шлюз читает перечисленный путь, только если это обычный файл
внутри корня размером не более 64 MiB, содержащий текст в UTF-8. Каждый другой
перечисленный путь он учитывает в `files_skipped` по причине:

- `outside_project`: запись с пустой частью, частью `.` или `..`, например
  `../notes.md`, `a//b.md` или имя, начинающееся с `/`, либо, в Windows, с
  частью, которая называет `.git`: `.git` в любом регистре, также с точками,
  пробелами или двоеточием после него, и `GIT~1`. По умолчанию git отклоняет
  каждую такую запись в любой системе, поэтому запуск не проходит;
- `unsupported_name`: в Windows — имя, которое система не может хранить в
  записанном виде: с двоеточием (как в `a:b.md`, где `a:` читается как диск),
  обратной косой чертой, одним из `<>"|?*` или управляющим символом, либо с
  частью, оканчивающейся точкой или пробелом; а также имя, которое Windows
  читает как нечто иное: отдельно стоящее имя устройства, например `CON`, `NUL`
  или `COM1`, или короткое имя, например `GIT~2`. git в Linux или macOS может
  отслеживать такое имя, поэтому оно учитывается, не проваливая запуск.
  Написанная вручную запись, например `C:/x` или `..\..\x`, в Windows тоже
  попадает сюда;
- `link`: символическая ссылка или, в Windows, точка соединения на любом
  уровне под корнем, даже указывающая внутрь него, или запись, которую индекс
  помечает как ссылку (на любой стадии конфликта слияния, поэтому такой файл не
  читается, пока конфликт не разрешён).
  git хранит ссылку как путь, на который она указывает, а отслеживаемый файл,
  на который указывает ссылка, проверяется по его собственному пути;
- `submodule`: запись подмодуля;
- `not_regular_file`: всё остальное, что не является обычным файлом, например
  папка, именованный канал или устройство, где чтение ждало бы или никогда не
  закончилось бы;
- `missing`: отслеживаемый файл, которого нет в рабочем дереве; в Windows сюда
  входят имя, которое git перечислил в байтах не в UTF-8, а такое содержит
  только индекс, созданный в другой системе (Git for Windows записывает такой
  файл под другим именем, поэтому его содержимое не проверяется), и путь
  длиннее допустимого системой, когда длинные пути не включены;
- `unreadable`: файл или папка на пути к нему, которые система не даёт шлюзу
  осмотреть, открыть или прочитать: из-за отсутствия прав, потому что другая
  программа удерживает файл или его часть, или потому что система не может его
  открыть, например файл, доступный только в сети, программа синхронизации
  которого остановлена. Когда другая программа удерживает весь файл, шлюз ждёт
  0,2 секунды и пробует ещё раз: в Windows — программа, открывшая его без
  совместного доступа; в других системах — прерываемая аренда на запись
  (write lease), например oplock Samba или делегирование NFS. Запуск не
  проходит, поскольку находка в таком файле осталась бы незамеченной. В
  нескольких случаях запуск проваливается так, хотя с файлом всё в порядке:
  прерывание аренды, которое занимает больше 0,2 секунды, файл, ожидающий
  удаления, и именованный канал в проекте на общем ресурсе `\\wsl$`, где каждое
  чтение сначала ждёт около 10 секунд;
- `too_large`: файл больше 64 MiB, первые 64 MiB которого — текст в UTF-8, или
  файл, который вырастает больше 64 MiB, пока шлюз его читает. Запуск не
  проходит по той же причине;
- `not_utf8_text`: файл, байты которого не являются текстом в UTF-8, например
  файл UTF-16 с меткой порядка байтов. Свыше 64 MiB решают первые 64 MiB, а
  файл считается двоичным, когда четверть или больше его первых 8000 байт —
  NUL, например большое изображение, заполненное нулями, или файл UTF-16 с
  преимущественно латинским текстом без метки порядка байтов, поэтому он не
  проваливает запуск; несколько байтов NUL в тексте не учитываются;
- `exempt`: файл, который проверки исключают намеренно: файл, суффикс которого
  помечает его как двоичный, например изображение или архив, и всё, что лежит в
  папке `.apothem/plans`, `tests/conformity`, `tests/fixtures`, `_vendor` или
  `node_modules` на любой глубине внутри корня. Проверки для `outside_project`
  и `unsupported_name` выполняются первыми, поэтому никакое исключение их не
  скрывает.

Когда запуск не проходит из-за `outside_project`, `unreadable` или `too_large`,
`files_not_passed` называет записи, стоящие за каждой из этих причин, в том
виде, как их перечисляет git, отсортированными, до 10 на причину;
`files_skipped` содержит полное количество. Строка в stderr тоже называет эти
причины и их количество, поэтому журнал CI, показывающий только stderr,
сообщает, почему запуск не прошёл.

Уровни каждого файла проверяются прямо перед его чтением, и открытый файл
должен быть тем, который нашла эта проверка. Файл, который другая программа
подменяет в промежутке на другой файл, ссылку или именованный канал, ищется
ещё раз и учитывается как `unreadable`, если его снова подменили; подставленная
символическая ссылка или, в Windows, точка соединения при втором поиске
обнаруживается как `link`. Шлюз никогда не ждёт на именованном канале и не
читает через ссылку, занявшую место файла. В Windows файл, который Data Deduplication или программа облачной синхронизации
держит за точкой повторной обработки (reparse point), читается через эту
программу как обычно; когда программа остановлена, файл — `unreadable`.

Файл открывается от корня по одному уровню за раз, и ни один уровень не
открывается через ссылку, поэтому папка над файлом, которую другая программа
подменяет ссылкой между проверкой и открытием, тоже не используется для
перехода: файл учитывается как `link`.

Две вещи эти проверки не видят. Жёсткая ссылка читается как обычный файл,
поэтому жёсткая ссылка на файл в другом месте читается; git такие не создаёт.
И в Windows сетевая файловая система, которая не сообщает ни тег точки
повторной обработки файла, ни его идентификатор файла, но поддерживает
символические ссылки, могла бы допустить подмену файла ссылкой между проверкой
и открытием так, что шлюз этого не заметит.

В этом запуске сопоставитель `link-check` ищет цель ссылки только внутри
корня: относительная ссылка, выходящая за корень, считается внешней, а поиск
папки `site/content/docs` останавливается на корне. В любом режиме он никогда
не ищет ссылку, которая сама по себе называет место, например сетевой ресурс
(`\\host\share`), диск (`C:/notes.md`) или адрес `file:`. В Windows поиск на
сетевом ресурсе отправляет ваши учётные данные входа этому хосту. В Windows он
также оставляет непроверенными сегмент маршрута `/docs/`, содержащий
двоеточие, которое Windows читает как диск, и ссылку, которую он находит
только через часть, оканчивающуюся точкой или пробелом: Windows может
отбросить это окончание (`ci.yml.` находит `ci.yml`), поэтому такая находка
ничего не доказывает. Такая ссылка, которая ничего не находит, как обычно
сообщается как мёртвая. В любой системе маршрут `/docs/` с сегментом `.` или
`..`, например `/docs/../x`, считается внешним и не ищется.

Каждому вызову `git ls-files` отводится 60 секунд: вызову этого запуска и
вызову в `no-global-plans-grep`, отчёт которого тогда несёт тот же
`check_error` и не проходит; когда там завершается неудачей сам git, его
сообщение приводит код выхода git, а не собственный текст git. Репозиторий,
собственные настройки которого заставляют git ждать, например `include.path`,
указывающий на именованный канал, задерживает каждый из этих вызовов не дольше
этого времени, в том числе в Windows, где предел также останавливает git,
запущенный лаунчером Git. Запуск
`--all-perwrite`, который не прочитал ни одного файла, не проходит: он
сообщает `files_scanned: 0` с `empty_scope_expected: false`. Когда список
отслеживаемых файлов прочитать нельзя, `check_error` приводит фиксированную
причину: git не запустился, `git ls-files` завершился неудачей с указанным
кодом выхода или не завершился вовремя. Чтобы увидеть собственное сообщение
git, например когда корень не находится внутри рабочего дерева git, выполните
`git ls-files` в корне; отчёт его не приводит, потому что оно может называть
файлы вне проекта. С `--strict` запуск, который не прошёл, завершается с кодом
`2`.

## Целевые проверки

```bash
# List every registered validator
PYTHONPATH=src python -m apothem.conformity.gate --list

# Run one per-write validator against one file
PYTHONPATH=src python -m apothem.conformity.gate --check multi-surface-coherence src/apothem/rules/my-rule.md

# Run one standalone validator over a root directory
PYTHONPATH=src python -m apothem.conformity.gate --check naming-grep .

# Run every per-write validator against one file
PYTHONPATH=src python -m apothem.conformity.gate src/apothem/rules/my-rule.md
```

Валидатор per-write принимает проверяемый файл или `--stdin`, чтобы прочитать
содержимое из стандартного ввода; без того и другого он ожидает ввод на
стандартном вводе, поэтому при запуске из терминала передавайте файл. Автономный
валидатор принимает корневой каталог (текущий каталог, если он опущен). `--list`
показывает, к какой группе относится каждый валидатор.

Режим `--hook` (`<python> -E -s .../conformity/gate.py --hook`, где
`<python>` — интерпретатор, найденный при установке) — это точка входа,
которую вызывает окружение: он читает из stdin полезную нагрузку JSON с входными
данными инструмента и прогоняет ожидающую запись через цепочку сопоставителей
per-write. Именно эту форму вызывает развёрнутый хук `PreToolUse`; вручную вы
вызываете её редко.

Режим хука **ограничен набором каталогов**. Он выполняет цепочку сопоставителей
только для записей, цель которых находится в одном из них; запись за пределами
всех областей сразу завершается молчаливым прохождением. По умолчанию
используются два корня:

```text
~/.claude      Claude Code
$CODEX_HOME    Codex (~/.codex when CODEX_HOME is not set)
```

Задайте для `APOTHEM_CONFORMITY_SCOPE` каталог, чтобы заменить их:

```bash
# Run the per-write matcher chain against one project tree instead
export APOTHEM_CONFORMITY_SCOPE=/path/to/project
```

Хук, который, по всей видимости, ничего не делает, обычно означает промах мимо
области, а не сбой, — сначала сверьте цель записи с перечисленными выше
областями.

## Интеграция с CI

Задание quality в `.github/workflows/ci.yml` запускает шлюз в строгом режиме
(`python -m apothem.conformity.gate --all . --strict`) при push в `main` и при
pull request в `main`, затрагивающих пути, которые отслеживает это задание.
Отдельный рабочий процесс `.github/workflows/conformity.yml` выполняет прогон
фикстур (`tests/conformity-scenarios/verify.py --strict`).
