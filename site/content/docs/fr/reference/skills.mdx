Les skills vivent sous forme de dossiers sous `src/apothem/skills/`, chacune
dotée d'un point d'entrée `SKILL.md`. Les skills capturent des techniques
détectables réutilisables — elles ont un signal de détection, une procédure et
un hook d'application.

Le catalogue complet des skills est généré plus bas, dans l'[Inventaire généré
des skills](#inventaire-généré-des-skills).

## Contrat de frontmatter

`SKILL.md` porte le frontmatter canonique à huit clés. Le contrat lisible par
machine est [`skill.schema.json`](https://github.com/ahmed-g-gad/apothem/blob/main/src/apothem/schemas/skill.schema.json)
(`additionalProperties: false`) ; ce bloc le reflète :

```yaml
---
name: <skill name>
version: <semver>
updated: <YYYY-MM-DD>
description: <one-line role>
archetype: <class-template, e.g. workflow-template>
userInvocable: <true | false>
disable-model-invocation: <true | false>
allowed-tools: <comma-separated read-only tools and scoped rules, e.g. "Read, Glob, Grep" or "Read, Bash(git log *)">
---
```

## Émission par environnement

Les skills sources utilisent les clés ci-dessus. Certains environnements lisent
des clés différentes ; l'installation les traduit donc pour cet environnement
uniquement :

| Environnement | Ce que l'installation modifie |
| --- | --- |
| Claude Code (installation et plugin) | Renomme `userInvocable` en `user-invocable`, la clé que lit Claude Code. Claude Code ignore la clé en camelCase ; sans ce renommage, une skill marquée `userInvocable: false` apparaîtrait donc toujours dans le menu `/`. |
| Dossiers de skills partagés de niveau utilisateur : `~/.agents/skills/` (écrit par Codex, Cursor, GitHub Copilot, Windsurf et Zed) et `~/.codebuddy/skills/`, `~/.kiro/skills/` et `~/.trae/skills/` | Une seule forme pour toute installation qui écrit l'un de ces dossiers, de sorte que les installations ne réécrivent jamais les fichiers les unes des autres. Elle renomme `userInvocable` en `user-invocable`, déplace `version`, `updated`, `archetype` et `portability` sous une table `metadata:` finale de chaînes entre guillemets, et écrit `agents/openai.yaml` avec `policy.allow_implicit_invocation: false` à côté de chaque skill dont la source définit `disable-model-invocation: true`, car Codex ignore cette clé et lit `~/.agents/skills/`, qu'un adaptateur Codex l'ait écrit ou non. Une commande enveloppée en skill conserve son corps entier et s'ouvre sur une note fixe qui nomme les dossiers des règles et des modèles, `~/.config/apothem/rules/` et `~/.config/apothem/templates/`. Les clés de premier niveau restantes sont `name`, `description`, `user-invocable`, `disable-model-invocation`, `allowed-tools`, `argument-hint` et `metadata`. |
| Qwen Code | Réécrit la chaîne `allowed-tools` séparée par des virgules sous forme de liste `allowedTools`, une entrée YAML par ligne, car `Qwen Code` ne lit que la clé en camelCase et exige une liste. Chaque entrée conserve la graphie de la source, y compris des motifs tels que `Bash(git status *)`. Toutes les autres clés et le corps de la skill s'installent sans modification. |
| Autres environnements | Aucune modification. |

`skill.schema.json` accepte l'une ou l'autre graphie de l'indicateur
d'invocabilité par l'utilisateur et exige exactement l'une des deux.

## Discipline de rédaction

- **Un dossier par skill.** Chaque skill est son propre dossier, avec le point
  d'entrée à `SKILL.md`.
- **Signal de détection.** Le corps des skills s'ouvre sur le signal de
  détection qui déclenche la technique.
- **Procédure + application.** Les skills portent à la fois la procédure à
  appliquer et le signal d'application qui ferme la boucle.
- **Longueur de la description.** `description` compte au plus 1 024
  caractères, la limite fixée par [Agent Skills](https://agentskills.io/specification).
  Les outils plus stricts rejettent ou tronquent une description plus longue, et
  le schéma impose cette limite.
