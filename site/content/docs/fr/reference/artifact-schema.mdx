**Modèles de frontmatter YAML par classe et champs requis pour tous les artefacts de l'écosystème Apothem.**

> **Source de vérité.** Le contrat lisible par machine et appliqué par le portail
> est constitué des JSON Schemas par classe sous [`src/apothem/schemas/`](https://github.com/ahmed-g-gad/apothem/blob/main/src/apothem/schemas)
> (`agent.schema.json`, `command.schema.json`, `skill.schema.json`, …), chacun
> déclarant `additionalProperties` afin que le portail de conformité rejette les
> clés inconnues. Cette page et [`frontmatter-schema.mdx`](/docs/reference/frontmatter-schema)
> sont les deux projections lisibles par un humain de ces schémas : cette page
> porte les **modèles et exemples détaillés** par classe, frontmatter-schema
> l'**index concis des clés requises**. Lorsqu'une page contredit les JSON
> Schemas, les schémas l'emportent.

## Vue d'ensemble

Tous les artefacts de l'arbre des sources d'Apothem (sous `src/apothem/` et la
surface de configuration racine) doivent inclure un bloc de frontmatter YAML
(entre des délimiteurs `---`) contenant des champs obligatoires et optionnels
propres à leur type d'artefact. Ce document définit le schéma canonique de
chaque type.

**Règles universelles :**

- Le frontmatter est conforme à YAML 1.2
- Toutes les valeurs de chaîne utilisent des guillemets doubles, sauf lorsqu'elles sont vides
- Ordre des champs : les champs obligatoires d'abord, les champs optionnels regroupés par pertinence
- Les commentaires dans le frontmatter utilisent `#` suivi d'un espace : `# comment`
- Les valeurs de chemin doivent être relatives (sans `/` initial) et utiliser des barres obliques (`/`) pour la compatibilité multiplateforme

**Convention de versionnage (classes d'artefacts versionnées : commandes, assistants, skills, CLAUDE.md) :**

- `version` est **sémantique** (`MAJOR.MINOR.PATCH`). Incrémentez MAJOR pour les changements incompatibles de schéma ou de contrat ; MINOR pour les changements additifs compatibles (nouveaux champs optionnels, sections supplémentaires, anti-modèles supplémentaires) ; PATCH pour les clarifications, les corrections de mise en forme ou les modifications portant uniquement sur la documentation, sans changement de comportement.
- `updated` est la **date ISO 8601** (`YYYY-MM-DD`) de la modification la plus récente. Elle doit changer à chaque incrément de `version` et peut être mise à jour indépendamment lors de rafraîchissements de liens qui n'incrémentent pas la version.
- Les nouveaux artefacts démarrent à `v0.Y.Z`. La promotion vers `vX.Y.Z` indique que le contrat de l'artefact est suffisamment stable pour constituer un engagement public.

## Schéma : règles

**Motif de chemin :** `src/apothem/rules/*.md`

**Objectif :** Mandats comportementaux et directives opérationnelles.

### Champs obligatoires

```yaml
---
name: "kebab-case-identifier"
description: "One-line description"
pathFilter: "**/*.py, **/*.toml"
alwaysApply: true | false
---
```

| Champ | Type | Objectif | Exemple |
| ----- | ---- | ------- | ------- |
| `name` | string | Identifiant lisible par machine | `"operational-mandates"` |
| `description` | string | Description d'une ligne pour les registres | `"Operational mandates CM-1–10"` |
| `pathFilter` | string | Liste de globs séparés par des virgules qui délimite la portée d'une règle filtrée par chemin ; la chaîne vide (`""`) pour les règles toujours actives | `"**/*.py, **/*.toml"` |
| `alwaysApply` | boolean | `true` pour les règles toujours actives (chargées partout) ; `false` pour les règles filtrées par chemin (chargées lorsque `pathFilter` correspond) | `true` |

### Champs optionnels

Les règles ne portent aucun champ de frontmatter optionnel et, contrairement aux autres classes d'artefacts, aucun champ `version` / `updated` / `scope` / `portability` non plus. Les quatre champs obligatoires ci-dessus constituent le contrat complet de frontmatter des règles, appliqué par `frontmatter_grep`.

### Exemple

```yaml
---
name: "operational-mandates"
description: "Behavioral definitions for CM-1 through CM-10: violation indicators and recovery actions"
pathFilter: ""
alwaysApply: true
---

# Rule: Operational Mandates
...
```

## Schéma : commandes

**Motif de chemin :** `src/apothem/commands/*.md`

**Objectif :** Définitions de commandes slash (`/plan-execute`, `/freshify`, etc.).

### Champs obligatoires

```yaml
---
name: "command-name"
version: "MAJOR.MINOR.PATCH"
updated: "YYYY-MM-DD"
description: "What this command does"
argument-hint: "[argument-pattern]"
disable-model-invocation: true | false
portability: "universal"
allowed-tools: "Read, Glob, Grep"
---
```

| Champ | Type | Objectif | Exemple |
| ----- | ---- | ------- | ------- |
| `name` | string | Nom de la commande (sans `/` initial) | `"plan-execute"` |
| `version` | string | Version sémantique | `"X.Y.Z"` |
| `updated` | string (ISO 8601) | Date de la dernière mise à jour | `"2026-04-20"` |
| `description` | string | Description courte | `"Executes a phase with quality gates"` |
| `argument-hint` | string | Motif d'utilisation, ou `"[args...]"` s'il n'y en a aucun | `"[path/to/plan] [phase-id]"` |
| `disable-model-invocation` | boolean | Si true, seul l'opérateur démarre la commande ; le modèle ne l'invoque jamais de lui-même | `true` |
| `portability` | string | Classification de portabilité entre les adaptateurs d'environnement | `"universal"` |
| `allowed-tools` | string | Outils pré-approuvés pendant l'exécution de la commande : les outils en lecture seule, plus les outils à effets de bord uniquement sous forme de règles délimitées telles que `Bash(git log *)`. Le joker nu `"*"` est rejeté | `"Read, Glob, Grep"` |

### Champs optionnels

Les commandes ne portent aucun champ de frontmatter optionnel : les huit champs obligatoires ci-dessus constituent le contrat complet de frontmatter des commandes, appliqué par `command.schema.json` (`additionalProperties: false`).

### Exemple

```yaml
---
name: "plan-execute"
version: "X.Y.Z"
updated: "2026-04-20"
description: "Executes a specific phase from a Master Plan Suite with conformity checking and quality gates"
argument-hint: "[path/to/plan-suite/] [phase-id] [--dry-run]"
disable-model-invocation: true
portability: "universal"
allowed-tools: "Read, Glob, Grep"
---

# /plan-execute — Execute a Specific Phase
...
```

## Schéma : assistants

**Motif de chemin :**

```text
src/apothem/agents/*.md
```

**Objectif :** Définitions d'assistants persistants pour l'exploration
parallèle, l'audit et les portails de qualité.

### Champs obligatoires

```yaml
---
name: "agent-name"
version: "MAJOR.MINOR.PATCH"
updated: "YYYY-MM-DD"
description: "What this agent specializes in"
tools: "Tool1, Tool2, Tool3"
disallowedTools: "Write, Edit"
maxTurns: 20
effort: "high" | "medium" | "low"
---
```

| Champ | Type | Objectif | Exemple |
| ----- | ---- | ------- | ------- |
| `name` | string | Identifiant de l'assistant | `"codebase-explorer"` |
| `version` | string | Version sémantique | `"X.Y.Z"` |
| `updated` | string (ISO 8601) | Date de la dernière mise à jour | `"2026-04-20"` |
| `description` | string | Description de la spécialisation | `"Deep codebase exploration"` |
| `tools` | string (séparée par des virgules) | Outils autorisés | `"Read, Glob, Grep, Bash"` |
| `disallowedTools` | string (séparée par des virgules) | Outils interdits | `"Write, Edit, TodoWrite"` |
| `maxTurns` | integer | Nombre maximal de tours de conversation (typiquement 5–20 ; les valeurs supérieures à 20 exigent un commentaire de justification en ligne) | `20` |
| `effort` | enum | Portée de calcul | `"high"` |

### Champs optionnels

```yaml
permissionMode: "default"       # Permission handling
memory: user | project | local  # Persistent-memory scope; omit for none
pattern: "Research" | "Audit" | "Implementation" | "Quality"  # Agent team pattern
portability: "universal"
```

### Exemple

```yaml
---
name: "codebase-explorer"
version: "X.Y.Z"
updated: "2026-04-20"
description: "Deep codebase exploration — find patterns, trace dependencies, discover conventions, map architecture"
tools: "Read, Glob, Grep, Bash"
disallowedTools: "Write, Edit, TodoWrite"
maxTurns: 20
effort: "high"
permissionMode: "default"
portability: "universal"
---

You are a codebase exploration specialist...
```

## Schéma : skills

**Motif de chemin :** `src/apothem/skills/*/SKILL.md`

**Objectif :** Définitions de techniques réutilisables, avec signaux de
détection et procédures d'exécution.

### Champs obligatoires

```yaml
---
name: "skill-name"
version: "MAJOR.MINOR.PATCH"
updated: "YYYY-MM-DD"
description: "What this skill teaches"
archetype: "workflow-template"
userInvocable: true | false
disable-model-invocation: true | false
allowed-tools: "Read, Glob, Grep"
---
```

| Champ | Type | Objectif | Exemple |
| ----- | ---- | ------- | ------- |
| `name` | string | Identifiant de la skill | `"plan-suite"` |
| `version` | string | Version sémantique | `"X.Y.Z"` |
| `updated` | string (ISO 8601) | Date de la dernière mise à jour | `"2026-04-20"` |
| `description` | string | Ce que fournit la skill | `"Master Plan Suite template"` |
| `archetype` | string | Classe de forme, un identifiant `<class>-template` en kebab-case | `"workflow-template"` |
| `userInvocable` | boolean | Si true, l'utilisateur peut demander explicitement cette skill | `false` |
| `disable-model-invocation` | boolean | Si true, la skill n'est atteinte que par invocation explicite | `true` |
| `allowed-tools` | string | Outils pré-approuvés pendant l'exécution de la skill : les outils en lecture seule, plus les outils à effets de bord uniquement sous forme de règles délimitées telles que `Bash(git log *)`. Le joker nu `"*"` est rejeté | `"Read, Glob, Grep"` |

### Champs optionnels

```yaml
argument-hint: "[args...]"                           # Usage pattern if userInvocable
```

### Exemple

```yaml
---
name: "ecosystem-audit"
version: "X.Y.Z"
updated: "2026-04-20"
description: "Comprehensive blind audit of the apothem ecosystem"
archetype: "audit-template"
userInvocable: true
disable-model-invocation: true
allowed-tools: "Read, Glob, Grep, Agent, TodoWrite"
argument-hint: "[--focus area] [--fix]"
---

## Purpose
...
```

## Schéma : hooks

**Motif de chemin :** le bloc `hooks` de `settings.json`, ainsi que les
implémentations Python sous `src/apothem/hooks/`.

**Objectif :** Déclarer des validateurs déclenchés par des événements et des
gestionnaires de gestion d'état que l'hôte invoque à des points bien définis du
cycle de vie.

### Schéma du fichier de settings

La clé de premier niveau `hooks` associe des noms d'événements à des tableaux de
blocs de matcher :

```json
"hooks": {
  "<EventName>": [
    {
      "matcher": "<pattern>",
      "hooks": [
        {
          "type": "command",
          "command": "${PYTHON_BIN}",
          "args": ["${HARNESS_ROOT}/.apothem/support/hooks/dispatch.py", "<EventName>", "<message-name>"],
          "timeout": <seconds>,
          "statusMessage": "<short human-readable label>"
        }
      ]
    }
  ]
}
```

La forme `-m apothem.hooks.dispatch` ne sert qu'au développement depuis un checkout des sources avec `PYTHONPATH=src`.

| Champ | Type | Objectif | Exemple |
| ----- | ---- | ------- | ------- |
| `matcher` | string | Motif de nom d'outil (ou `"*"` pour les événements indépendants de tout outil) | `"Write"` |
| `hooks[].type` | littéral `"command"` | Le seul type de gestionnaire de hook pris en charge aujourd'hui | `"command"` |
| `hooks[].command` | string | Commande exécutable ; Apothem utilise le marqueur `${PYTHON_BIN}`, résolu à l'installation | `"${PYTHON_BIN}"` |
| `hooks[].args` | tableau de chaînes | Arguments en forme exec : un chemin de script sous `${HARNESS_ROOT}/.apothem/support/`, suivi de ses arguments | `["${HARNESS_ROOT}/.apothem/support/hooks/dispatch.py", "SessionStart"]` |
| `hooks[].timeout` | entier (secondes) | Durée d'exécution maximale avant que l'hôte ne tue le hook | `30` |
| `hooks[].statusMessage` | string | Libellé court affiché dans l'interface de l'hôte | `"Session start"` |

### Événements requis

Le modèle Claude Code enregistre SessionStart, PreToolUse, PostToolUse et Stop. PreCompact et PostCompact ne sont pas enregistrés sur Claude Code ([référence des hooks](/docs/reference/hooks)), et `scripts/dev/validate_hooks.py` signale chacun d'eux comme manquant, sous forme d'avertissement. Le tableau suivant liste les cinq événements que `validate_hooks.py` vérifie :

> **Les valeurs de timeout reprennent les budgets canoniques des événements de hook** : le
> tableau ci-dessous les reproduit pour la commodité du lecteur ; la source canonique fait foi.

| Événement | Timeout typique | Objectif |
| ----- | --------------- | ------- |
| `SessionStart` | 30 secondes | Lire la mémoire, vérifier l'état du plan, signaler l'état de préparation |
| `PreToolUse` | 10 secondes | Valider les écritures au regard des politiques d'isolation du contenu + frontmatter |
| `PreCompact` | 30 secondes | Vérifier que l'état est externalisé avant le compactage du contexte |
| `PostCompact` | 30 secondes | Restaurer l'état de travail après le compactage du contexte |
| `Stop` | 60 secondes | Externalisation de fin de session : état de reprise, sorties, décisions |

`dispatch.py` accepte aussi `UserPromptSubmit` et `Notification` dans sa liste
blanche d'événements, pour la compatibilité ascendante ; aucun des deux n'est
câblé dans les modèles livrés. Pour les activer, ajoutez un bloc de matcher
suivant le même motif sous forme exec.

### Couche Python

Chaque commande de hook passe par le même répartiteur Python :

| Fichier | Rôle |
| ---- | ---- |
| `src/apothem/hooks/dispatch.py` | Achemine `SessionStart` vers `session_start_bootstrap.main()` et chaque autre événement de la liste blanche vers `emit_hook_context.main()`. Se termine toujours avec le code 0. |
| `src/apothem/hooks/session_start_bootstrap.py` | Script de hook de démarrage de session : émet un contexte de synthèse de la mémoire et de la suite de plan. |
| `src/apothem/hooks/emit_hook_context.py` | Émetteur de hook par défaut : écrit une enveloppe valide portant la charge utile `--context-file` enregistrée. |
| `src/apothem/hooks/messages/*.md` | Charge utile de contexte statique référencée par `--context-file`. |

### Validation

`scripts/dev/validate_hooks.py` applique le contrat des hooks :

- `settings.json` s'analyse comme du JSON et déclare chaque événement requis.
- Les trois scripts Python existent et s'analysent comme du Python valide.
- Tous les fichiers de message référencés par des arguments `--context-file` existent.
- Aucun chemin utilisateur absolu codé en dur (`C:\Users\...`, etc.) n'apparaît dans `src/apothem/hooks/**.py`.
- Les artefacts shell sous `src/apothem/hooks/` et `scripts/` se limitent aux stubs approuvés de localisation / d'amorçage.

## Schéma : CLAUDE.md

**Chemin :** `CLAUDE.md` (racine)

**Objectif :** Index global de configuration de l'écosystème.

### Frontmatter YAML obligatoire

```yaml
---
name: "CLAUDE"
version: "MAJOR.MINOR.PATCH"
updated: "YYYY-MM-DD"
description: "Global Claude Code ecosystem configuration and mandate index"
scope: "always-on"
```

### Sections requises (dans l'ordre)

1. **§1 Suite de plan** — Référence à l'emplacement du modèle
2. **§2 Identité cognitive** — Mandat d'architecture créative
3. **§3 Répertoires d'artefacts** — Tableau des chemins et de leurs objectifs
4. **§4 Gouvernance modulée par le niveau de sérieux** — Définition des quatre niveaux
5. **§5 Directives opérationnelles** — Résolution de problèmes, principes de communication
6. **§6 Mandats transversaux** — Aperçu de CM-1–28
7. **§7 Registres** — Tableaux d'artefacts :
   - 7.1 Commandes
   - 7.2 Règles
   - 7.3 Assistants
   - 7.4 Hooks
   - 7.5 Skills
   - 7.6 Évolution des artefacts

## Liste de contrôle de validation

Chaque artefact doit satisfaire les vérifications suivantes :

### Validation du frontmatter

- [ ] Le YAML est syntaxiquement valide (aucune erreur d'analyse)
- [ ] Tous les champs obligatoires du type d'artefact sont présents
- [ ] `name` suit la convention kebab-case
- [ ] `version` est sémantique (`MAJOR.MINOR.PATCH`)
- [ ] `updated` est au format de date ISO 8601 (`YYYY-MM-DD`)
- [ ] `description` est une chaîne non vide, sur une seule ligne
- [ ] Les champs optionnels correspondent aux valeurs d'énumération attendues (le cas échéant)
- [ ] Aucune faute de frappe dans les noms de champs (utilisez les noms canoniques du schéma)
- [ ] Aucun espace superflu ni problème de mise en forme

### Validation du contenu

- [ ] Le contenu commence immédiatement après le `---` de fermeture, sur une nouvelle ligne
- [ ] Aucune référence interne au plan (conformité CM-7)
- [ ] Les références croisées se résolvent (si d'autres artefacts sont listés)
- [ ] Les liens utilisent des chemins relatifs avec des barres obliques

### Validation de la portabilité

- [ ] Aucun chemin absolu codé en dur (utilisez des chemins relatifs)
- [ ] Aucune syntaxe propre à Windows dans les artefacts de portée universelle
- [ ] Les séparateurs de chemin utilisent des barres obliques
- [ ] Les variables d'environnement utilisent un format indépendant de la plateforme (`${VAR}` ou natif à l'outil)

## Notes

- **La cohérence comme sécurité :** un frontmatter canonique permet la
  validation automatisée, l'outillage et la vérification entre artefacts. Les
  écarts se cumulent rapidement.
- **Déclaration de portabilité :** tous les artefacts ne peuvent pas être
  universels. Déclarez explicitement les contraintes : mieux vaut documenter une
  réserve que livrer un bogue silencieux.
- **Kebab-case pour les noms :** facile à utiliser dans les URL, les scripts et
  les contextes de ligne de commande. Évitez les espaces, les traits de
  soulignement et le camelCase dans les noms.
- **Hygiène des incréments de version :** toute modification qui change le comportement doit incrémenter `version` et `updated` ensemble. Les corrections purement de mise en forme ou de fautes de frappe incrémentent PATCH ; les nouvelles sections optionnelles ou les nouveaux anti-modèles incrémentent MINOR ; une réorganisation structurelle ou des changements de contrat incrémentent MAJOR.
