Installe la configuration d'un adaptateur d'environnement à partir du profil
partagé.

## Synopsis

```
apothem install --harness NAME|all [--profile PATH] [--dry-run]
                 [--clean|--fresh] [--yes] [--project PATH]
                 [--quiet|-q] [--verbose|-v]
                 [--format plain|json] [--json] [--no-color]
```

Charge et valide le profil partagé, sélectionne un adaptateur nommé ou
l'ensemble `all` couvrant tout le registre, valide le plan de matérialisation,
puis écrit la configuration native de l'environnement ainsi que les cohortes de
support. Les adaptateurs à portée de projet exigent `--project PATH`.

L'alias en forme continue `apothem installing` (également accepté sous la forme
`apothem Installing`) se résout vers le même gestionnaire.

## Première exécution sans profil

Lorsque `--profile` est omis et qu'aucun profil n'existe au chemin par défaut
(`~/.config/apothem/profile.yaml`), `install` y écrit d'abord le profil de
démarrage, affiche `Created a starter profile at <path>`, puis poursuit. Le
profil de démarrage porte des champs d'identité servant d'espaces réservés ;
l'installation affiche donc aussi la note sur l'identité provisoire.
Personnalisez le profil, puis exécutez
[`update`](/docs/cli-reference/update) pour l'appliquer. Sous `--json`, la
création est signalée comme une entrée `warnings` avec
`"operation": "profile_created"`.

- `--dry-run` n'écrit jamais le profil : l'aperçu utilise le profil de
  démarrage en mémoire et signale `"operation": "profile_scaffold_preview"`.
- Un `--profile PATH` explicite qui n'existe pas n'est jamais créé ; la
  commande se termine avec le code 1 et l'erreur `profile.not_found`.

## Aperçu du rayon d'impact

`install --harness all` se déploie sur des portées mixtes : les adaptateurs à portée de projet écrivent sous la racine `--project` fournie, tandis que les adaptateurs à portée d'utilisateur écrivent sous votre répertoire personnel — en dehors de cette racine. Avant que l'installation n'écrive le moindre fichier, la commande affiche les cibles concrètes regroupées sous deux en-têtes : celles situées à l'intérieur de la racine du projet et celles situées sous votre répertoire personnel. Un troisième en-tête liste les
dossiers partagés de votre répertoire personnel dans lesquels les adaptateurs à
portée de projet écrivent, en dehors de `--project` : le dossier de skills et
`~/.config/apothem/` (voir
[Dossiers dans votre répertoire personnel](#dossiers-dans-votre-répertoire-personnel)).
La seule exception est `--clean` : son étape de remise à zéro s'exécute avant cet aperçu, écrit une sauvegarde et supprime les cibles précédentes, comme décrit ci-dessous.

Lorsque la sélection écrit en dehors de la racine du projet, que ce soit dans le
dossier d'un adaptateur enraciné dans le répertoire personnel ou dans un dossier
partagé, une confirmation interactive protège les écritures enracinées dans le
répertoire personnel.
`--yes`, un shell non interactif (sans TTY), `--dry-run` et `--format json`
poursuivent chacun sans demander de confirmation. Seul `--dry-run` n'écrit
rien ; `--format json` ignore l'aperçu et l'invite de confirmation, mais
effectue tout de même les écritures. Refuser l'invite du répertoire personnel
interrompt l'installation avant que celle-ci n'écrive. Avec `--clean`, l'étape de
remise à zéro s'exécute d'abord, sous sa propre confirmation par cible : elle
écrit une sauvegarde sous `~/.apothem/backups` et supprime les cibles qu'elle
confirme. Ces suppressions et la sauvegarde restent en place lorsque l'invite
d'installation est refusée.

## Dossiers dans votre répertoire personnel

Sept adaptateurs à portée de projet écrivent les skills d'Apothem, ainsi que les
règles et templates que ces skills citent, dans des dossiers de votre
répertoire personnel :

```text
cursor, github-copilot, windsurf, zed  ->  ~/.agents/skills/ (codex writes it too)
codebuddy                               ->  ~/.codebuddy/skills/
kiro                                    ->  ~/.kiro/skills/
trae                                    ->  ~/.trae/skills/
all seven                               ->  ~/.config/apothem/rules/ and templates/ (codex uses them too)
```

- `--project` sélectionne le fichier de règles et le projet auquel appartient
  l'installation. Il ne change pas l'emplacement des skills : une installation
  avec `--project A` et une autre avec `--project B` écrivent les mêmes dossiers.
- Chaque installation qui nomme un dossier écrit les mêmes fichiers. Une
  seconde installation les trouve et signale `unchanged`, et l'ordre dans lequel
  vous installez n'a pas d'importance.
- Les dossiers du répertoire personnel sont écrits avant tout élément du
  projet. Si une écriture y échoue, l'installation de l'adaptateur s'arrête avec
  l'erreur et le projet reste inchangé. L'erreur nomme le chemin qui fait
  obstacle, par exemple un fichier nommé `~/.agents` là où le dossier doit se
  trouver.
- Chaque dossier de skill est écrit dans un dossier caché
  `.<name>.apothem-staging` placé à côté de lui, puis renommé à sa place une fois
  complet ; une écriture échouée ou interrompue ne laisse donc jamais un dossier
  de skill à moitié écrit sous son nom final. Relancez l'installation pour
  terminer ; elle remplace un dossier de staging restant.
- Un lien symbolique situé sur l'un de ces dossiers ou au-dessus, comme ceux que
  créent les gestionnaires de dotfiles pour `~/.config` ou `~/.agents`, est suivi
  lorsqu'il mène à un emplacement situé dans votre répertoire personnel. Un lien
  qui sort de votre répertoire personnel arrête l'installation avec
  `target escapes the allowed materialization root`, tout comme un lien situé à
  l'intérieur d'un dossier de skill.
- L'installation n'ajoute aucun fichier de skill ni de règle à votre dépôt. Le
  projet reçoit le fichier de règles de l'adaptateur, plus le dossier de données
  `.apothem/` que crée chaque installation de projet.
- Un dossier de skill qui porte le nom d'un skill Apothem et qu'Apothem n'a pas
  écrit est ignoré. L'installation affiche une ligne `Warning:` et l'enveloppe
  `--format json` porte une entrée `warnings` avec `"outcome": "warning"` et
  `"operation": "skill_conflict"` qui nomme le dossier. Renommez ou déplacez le
  dossier, puis exécutez [`update`](/docs/cli-reference/update).
- Chacune de ces installations, mises à jour et dry runs affiche une
  `Note:` qui nomme les dossiers qu'elle écrit en dehors de `--project`. Dans
  l'enveloppe JSON, il s'agit d'une entrée `warnings` avec
  `"operation": "user_level_write"` et une liste `paths`.

## Notes sur les capacités

Chaque adaptateur ne projette que les capacités que son environnement prend en
charge nativement ; les capacités dépourvues de surface native sont signalées,
et non abandonnées silencieusement. En mode plain, cela prend la forme d'une
seule note groupée par environnement (par exemple
`Note: <harness> - 9 capabilities not projected; pass --verbose for detail`) ;
sous `--verbose`, chaque capacité affiche sa propre ligne de justification. Tout
autre avertissement d'adaptateur s'affiche aussi sur sa propre ligne `Warning:`
en mode plain, par exemple l'avertissement de Zed qui nomme un fichier
d'instructions que le nouveau `.rules` masque. L'enveloppe `--format json`
porte toujours le tableau `warnings` complet, quel que soit le niveau de
détail.

L'installation et la mise à jour affichent aussi des avis sous forme de lignes
`Note:`. Un avis ne modifie jamais ce que l'installation écrit. Lorsqu'une
installation écrit dans une racine partagée, un chemin que d'autres outils
chargent aussi (par exemple le dossier de skills `~/.agents/skills/`), la note
nomme ces outils, et place entre parenthèses un outil qui ne charge ce chemin
que sous une condition, par exemple `Open-Claw (only under its default state
directory)`. Une installation qui écrit un dossier que d'autres installations
écrivent aussi (le rôle `holder`) indique que le dossier reste en place jusqu'à
la désinstallation de la dernière installation Apothem qui l'utilise, et nomme
les installations qui l'utilisent actuellement. Lorsqu'une installation cible
un outil qui charge déjà du contenu Apothem depuis la racine partagée d'une
autre installation, la note nomme l'installation qui l'y a placé : le
propriétaire enregistré tant qu'il utilise encore le dossier, sinon la plus
ancienne installation qui l'utilise. Dans l'enveloppe `--format json`, chaque
avis est une entrée `warnings` avec `"outcome": "advisory"` et
`"operation": "shared_root"` ; son `role` vaut `owner`, `holder` ou `reader`,
`holders` liste les installations qui utilisent le dossier, et
`owner_of_record` nomme le propriétaire enregistré.

Une installation qui enregistre des hooks affiche aussi des notes sur le
fichier de hooks. Un avis `hook_review` nomme l'étape dont l'outil a besoin
avant d'exécuter les hooks (un redémarrage et une revue, ou l'approbation de
l'espace de travail), ou le risque d'un fichier de hooks qu'un dépôt commite et
qui nomme l'interpréteur de cette machine. Un avis `hook_import` apparaît pour
un outil qui exécute aussi les hooks présents dans les fichiers de paramètres de
Claude Code, comme ceux qu'écrit l'installation Apothem pour Claude Code, et
nomme le commutateur propre à l'outil qui désactive cet import ainsi que ce que
ce commutateur arrête également. Chacun est une entrée `warnings` avec
`"outcome": "advisory"`, le `harness`, le `path` du fichier de hooks et un
`message`.

Une commande de hook place le chemin du projet et celui de l'interpréteur entre
guillemets doubles, que `sh`, Git Bash et PowerShell lisent chacun. Un chemin
contenant `$`, un accent grave, un guillemet double ou une barre oblique inverse
ferait exécuter un autre fichier à la commande ; l'installation (et
`--dry-run`) s'arrête donc avec une erreur qui nomme le chemin et n'écrit rien ;
déplacez ou renommez le projet, puis relancez la commande. Une espace ou une
apostrophe dans un chemin ne pose pas de problème.

Les serveurs MCP du profil font l'objet de trois avis, chacun nommant le champ
du profil concerné :

| Opération | Condition | Correction |
| --- | --- | --- |
| `mcp_deprecated_transport` | `transport: sse` (la spécification MCP rend HTTP+SSE obsolète) | Utilisez `streamable-http` lorsque le serveur le prend en charge. |
| `mcp_plain_http` | une URL `http://` vers un hôte qui n'est pas une adresse de bouclage | Utilisez une URL `https://`. |
| `mcp_literal_credential` | une valeur `headers` ou `env` ayant la forme d'un jeton (`ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_`, `sk-`, `xoxa-`, `xoxb-`, `xoxo-`, `xoxp-`, `xoxr-`, `xoxs-`, ou `Bearer` suivi d'un long jeton) | Conservez le secret dans une variable d'environnement et écrivez des références de type `${GITHUB_TOKEN}`. |

L'avis sur les identifiants n'affiche jamais la valeur qu'il a trouvée. Une
valeur contenant une référence `${...}` n'est jamais signalée.

## Configurations de l'opérateur avec commentaires

Certaines configurations d'environnement sont des fichiers que vous modifiez
aussi, comme `settings.json`, `opencode.json` (qui peut être du JSONC),
`openclaw.json` (JSON5) et `config.yaml`. L'installation fusionne ses clés dans
ces fichiers et conserve chaque clé que vous avez ajoutée.

Une fusion réécrit le fichier en JSON ou en YAML simple, ce qui supprimerait
les commentaires, les virgules finales et la syntaxe JSON5. Par conséquent :

- Lorsque la fusion ne modifierait aucune valeur (par exemple, parce que vous
  avez déjà ajouté vous-même les clés d'Apothem), le fichier est laissé tel
  quel, octet pour octet.
- Lorsque la fusion doit modifier une valeur dans un fichier qui porte des
  commentaires ou une syntaxe JSON5, ou dans un fichier qui ne peut pas être
  analysé du tout, l'installation n'écrit rien pour cet environnement et se
  termine avec le code 1 et l'erreur `config.unparseable`. Le champ `fix`
  nomme les clés que l'installation ajouterait ; vous pouvez ainsi convertir
  le fichier en JSON ou en YAML simple, ou ajouter ces clés à la main et
  relancer la commande.
- Lorsqu'une clé que l'installation remplit avec un mapping ou une liste (par
  exemple `skills.external_dirs` dans `config.yaml`) contient dans votre fichier
  une valeur scalaire, ou l'autre forme de conteneur, l'installation n'écrit rien
  pour cet environnement et se termine avec le code 1 et le même code d'erreur,
  car remplir la clé supprimerait votre valeur. L'erreur nomme la clé ;
  donnez-lui la forme qu'elle indique, ou supprimez-la, puis relancez la
  commande. Une clé que vous avez laissée vide (`skills:` sans rien en dessous)
  est remplie.

## Options

| Option | Description |
|---|---|
| `--harness NAME` | Adaptateur d'environnement à installer, ou `all` pour l'ensemble couvrant tout le registre (obligatoire). Avec `all`, les environnements listés dans `exclude_harnesses` du profil sont ignorés, mais un environnement nommé explicitement est installé même s'il figure dans cette liste. Exécutez `apothem harnesses list` pour obtenir les noms enregistrés. |
| `--profile PATH` | Chemin vers le YAML du profil partagé. Par défaut : `~/.config/apothem/profile.yaml`. |
| `--dry-run` | Prévisualise l'installation sans écrire de fichiers. |
| `--clean`, `--fresh` | Table rase à activer explicitement : sauvegarde puis supprime l'état d'installation antérieur propre à chaque environnement avant d'installer. |
| `--yes` | Ignore la confirmation par cible lors d'une suppression en table rase (obligatoire pour les exécutions `--clean` non interactives). |
| `--project PATH` | Racine de projet pour les environnements à portée de projet. |
| `--quiet`, `-q` | Supprime la sortie informative ; seules les erreurs sont émises. |
| `--verbose`, `-v` | Affiche la justification de chaque capacité non projetée au lieu de la note groupée par environnement. |
| `--format plain\|json` | Format de sortie (par défaut : `plain`). |
| `--json` | Raccourci de `--format json`. |
| `--no-color` | Désactive les codes de couleur ANSI dans la sortie. |
| `-h`, `--help` | Affiche l'aide et quitte. |

## Sortie JSON

Lorsque `--json` (ou `--format json`) est fourni, un seul document JSON
est écrit sur stdout :

```json
{
  "schema_version": 1,
  "status": "success",
  "command": "install",
  "action": "installed",
  "harness": "claude-code",
  "profile_path": "C:\\Users\\Example\\.config\\apothem\\profile.yaml",
  "project": null,
  "files_written": ["C:\\Users\\Example\\.claude\\settings.json"],
  "results": [],
  "warnings": [],
  "error": null,
  "output_path": "C:\\Users\\Example\\.claude\\settings.json"
}
```

Pour `--dry-run`, rien n'est écrit et `results` liste chaque chemin que
l'installation écrirait, chacun avec le résultat qu'il aurait (`created`,
`updated` ou `unchanged`) et, pour un fichier que vous modifiez aussi, le diff
unifié dans `detail.diff` — le même plan que celui affiché par
[`apothem diff`](/docs/cli-reference/diff) :

```json
{
  "schema_version": 1,
  "status": "dry_run",
  "command": "install",
  "action": "dry_run",
  "harness": "claude-code",
  "files_written": [],
  "results": [
    {
      "harness": "claude-code",
      "outcome": "created",
      "operation": "write_text",
      "path": "C:\\Users\\Example\\.claude\\settings.json",
      "message": "dry run: no filesystem changes made"
    }
  ],
  "warnings": [],
  "error": null
}
```

Lorsque `--clean` est fourni, l'enveloppe porte en plus un objet `clean`
décrivant la phase de suppression — la liste des dispositions par cible,
l'indication que l'exécution était ou non un aperçu, et le répertoire de
sauvegarde horodaté (`null` lors d'un dry run) :

```json
{
  "clean": {
    "dry_run": true,
    "backup_dir": null,
    "targets": [
      {
        "path": "C:\\Users\\Example\\.claude",
        "present": true,
        "removed": false,
        "skipped_reason": null
      }
    ]
  }
}
```

Un dry run avec table rase prévisualise les deux phases dans un seul document :
l'aperçu de la suppression sous `clean` et l'aperçu des nouvelles écritures sous
`results`.

Les erreurs de validation attendues utilisent la même enveloppe et incluent un
objet d'erreur :

```json
{
  "schema_version": 1,
  "status": "error",
  "command": "install",
  "harness": "all",
  "files_written": [],
  "error": {
    "code": "project.required",
    "field": "project",
    "reason": "project-scope harnesses require --project: cursor, gemini-cli, github-copilot, kimi-code, windsurf, codebuddy, kiro, trae, zed, glm.",
    "fix": "Pass --project PATH or select only user-scope harnesses."
  }
}
```

## Exemples

```bash
apothem install --harness claude-code
apothem install --harness claude-code --dry-run
apothem install --harness cursor --project . --profile ~/profile.yaml --json
apothem install --harness all --project . --dry-run --json
apothem installing --harness claude-code   # continuous-form alias
apothem Installing --harness claude-code   # capitalized variant
```

## Codes de sortie

| Code | Signification |
|---|---|
| 0 | Adaptateur installé avec succès ou dry-run planifié sans erreur |
| 1 | Erreur attendue de validation, de profil, d'environnement, de projet ou d'adaptateur |
| 2 | Matérialisation partielle du lot après au moins une écriture |
| 64 | Erreur d'utilisation : une option ou une commande inconnue, ou une valeur d'option manquante ou invalide. Sous `--json`, l'erreur est une enveloppe JSON avec le code `cli.usage`. |
