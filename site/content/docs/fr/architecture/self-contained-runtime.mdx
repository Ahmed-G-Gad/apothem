Le moteur d'Apothem est un runtime autonome : il s'exécute sans registre,
directement depuis n'importe quel checkout ou arbre de code source déposé, parce
que ses dépendances tierces voyagent avec lui. Deux pièces rendent cela
possible — un arbre de dépendances vendorisées et un modèle d'invocation
`python -m` qui n'a besoin d'aucun script de console installé.

## Arbre de dépendances vendorisées

La pile de validation et de sérialisation est vendorisée sous forme de code
source en Python pur sous `src/apothem/_vendor/`, chaque paquet accompagné du
fichier de licence de son projet amont :

- `yaml` (le parseur/émetteur en Python pur ; l'extension C optionnelle libyaml
  n'est pas embarquée)
- `jsonschema`, avec sa chaîne de dépendances `attrs` (et son alias `attr`),
  `referencing` et `jsonschema_specifications`
- `rpds` — un shim en Python pur qui réimplémente la surface `HashTrieMap`,
  `HashTrieSet` et `List` qu'utilisent `jsonschema` et `referencing`, adossé à
  des types intégrés, de sorte que la pile s'exécute sans aucune extension
  compilée
- `typing_extensions`

Les copies vendorisées priment sur toute version installée sur le système : le
bootstrap du plugin, le shim npm, les installateurs et le point d'entrée
`python -m apothem` lui-même placent chacun le répertoire vendor dans `sys.path`
devant site-packages. La politique de sélection — ce qui est vendorisé, ce qui
ne l'est pas et comment les paquets vendorisés sont rafraîchis — est documentée
dans la
[stratégie de vendorisation des dépendances](/docs/architecture/vendoring-strategy).

Deux dépendances restent hors de l'arbre : **`click`** et **`rich`**, les
bibliothèques orientées terminal qu'importe la CLI. Elles doivent être
importables sous l'interpréteur qui exécute le moteur ; les installateurs
vérifient les deux, nomment celle qui manque et proposent de l'installer pour
vous — avec votre confirmation, ou automatiquement avec `--yes` /
`APOTHEM_AUTO_INSTALL_DEPS=1`. Sur tous les autres canaux, le point d'entrée
vérifie les deux avec la bibliothèque standard avant d'importer la CLI, et une
dépendance manquante l'arrête avec une erreur qui nomme la commande `pip` exacte
pour l'interpréteur en cours d'exécution (une enveloppe JSON avec le code
`runtime.dependency_missing` sous `--json`).

## Le modèle d'invocation `python -m`

Apothem ne déclare intentionnellement aucun script de console dans
`pyproject.toml` — les scripts de console n'existent que lorsqu'un gestionnaire
de paquets les place sur le `PATH`, et le runtime autonome n'en suppose jamais
un. Le moteur dispose plutôt de deux surfaces d'invocation :

| Surface | Invocation | Contexte |
| ------- | ---------- | ------- |
| CLI du moteur | `apothem <command>` ; depuis un checkout, `PYTHONPATH=src python -m apothem <command>` | Le shim `apothem` des installateurs et le lanceur npm exécutent le paquet depuis son arbre de code source en gardant le dossier courant hors de `sys.path` ; la forme `-m` est destinée à un checkout auquel vous faites confiance |
| Runtime des hooks | `<resolved CPython> -E -s "<harness-root>/.apothem/support/hooks/dispatch.py" <event>` | Matérialisation Claude Code : la copie située sous l'arborescence partagée `.apothem/support/` de la racine de l'environnement, par chemin absolu |

- Le point d'entrée du moteur, `src/apothem/__main__.py`, place
  `src/apothem/_vendor` dans `sys.path`, vérifie que `click` et `rich` sont
  importables, puis appelle `apothem.cli:main` — le groupe de commandes Click.
  `python -m apothem` l'exécute directement. Les shims `apothem` et le lanceur
  npm l'exécutent via `runpy` depuis un programme `-c` qui retire d'abord le
  dossier courant de `sys.path`.
- Les entrées de hook du `settings.json` / `hooks.json` matérialisé invoquent
  le répartiteur (et, pour Claude Code, le portail de conformité à
  `<harness-root>/.apothem/support/conformity/gate.py`) par chemin de script
  absolu, en démarrant Python avec `-E -s` afin qu'aucune variable `PYTHON*` ni
  aucun site-packages de l'utilisateur n'atteigne le hook. Tous deux sont des scripts autonomes de la bibliothèque standard qui
  amorcent leur propre `sys.path`, et les fixtures de schéma du portail
  voyagent à côté de lui dans `<harness-root>/.apothem/support/schemas/`, de
  sorte que les hooks s'exécutent **sans aucun paquet `apothem` importable sur
  l'hôte**. Les templates portent un jeton `${HARNESS_ROOT}` qu'`apothem install`
  rend en chemin réel de la racine de l'environnement, sous forme à barres
  obliques.
- Depuis un checkout du code source, les formes de module
  `python -m apothem.hooks.dispatch` et
  `python -m apothem.conformity.gate` exécutent le même code pour le
  développement.

Dans un checkout, le répertoire du paquet devient importable en plaçant le
répertoire `src/` du checkout en tête de `PYTHONPATH` :

```bash
PYTHONPATH=src python -m apothem <command>    # from the checkout root
```

`-m` lit d'abord les modules du dossier courant ; n'exécutez donc cette forme
que depuis la racine du checkout ou un autre dossier auquel vous faites
confiance.

Les installateurs n'affichent jamais de commande `-m`. Lorsque la commande
`apothem` ne figure pas dans le `PATH` à la fin, `install.sh` et `install.ps1`
affichent le chemin complet du shim `apothem` qu'ils ont placé. Lorsqu'aucun
shim n'a pu être placé, ils affichent à la place une commande autonome.
`install.sh` affiche
`PYTHONSAFEPATH=1 PYTHONPATH='<vendor>:<src>' '<CPython>' -c '<program>'`,
suivi de la commande. `install.ps1` affiche un bloc PowerShell qui définit
`PYTHONSAFEPATH` et `PYTHONPATH` (les dossiers vendorisé et `src/` joints avec
`;`) le temps d'une exécution de `& '<CPython>' -c "<program>"`, puis rétablit
les deux. Le programme retire le dossier courant de `sys.path` et exécute le
paquet `apothem` ; `PYTHONSAFEPATH=1` empêche Python 3.11 et les versions
ultérieures d'ajouter ce dossier dès le départ.

## Bootstrap de l'arbre du plugin

Le plugin Claude Code embarque le moteur sous `<plugin_root>/lib/apothem` plutôt
que de s'appuyer sur `PYTHONPATH`. Le module de bootstrap
`apothem.lib.plugin_bootstrap` expose `bootstrap_syspath`, qui place de façon
idempotente `<plugin_root>/lib` et le répertoire vendor en tête de `sys.path`
afin qu'`import apothem` et chaque dépendance vendorisée se résolvent depuis
l'arbre du plugin. Un arbre malformé (sans `lib/`) lève `PluginBootstrapError`
plutôt que d'importer silencieusement une copie système périmée.

## Ce que l'installateur dépose sur le disque

Les installateurs par script déposent un clone git de l'arbre de code source à
`~/.apothem` (remplaçable par `APOTHEM_HOME`) et exécutent le moteur depuis
lui — aucun paquet Python n'est installé dans `site-packages` au-delà de la
proposition optionnelle des prérequis `click` / `rich`. Le clone est le dépôt
complet, y compris la suite de tests et le site de documentation que le runtime
n'importe jamais, pour deux raisons délibérées : le moteur **matérialise ses
cohortes** — règles, skills, commandes et templates — directement depuis l'arbre
dans chaque environnement, de sorte que l'arbre est la source de vérité vivante
et pas seulement un runtime ; et le répertoire `.git` reste en place pour
qu'`apothem update` extraie le tag de version dans le clone existant au lieu
de le retélécharger.

Cette disposition d'exécution depuis le code source suit le même motif que des
outils comme `nvm`, `pyenv` et `oh-my-zsh` — quelques mégaoctets de code source
plus l'historique, supprimables en une seule étape avec le désinstallateur (il
n'y a aucun état système à défaire). Une empreinte plus légère — un checkout
superficiel ou partiel qui omet `tests/` et `site/` — est possible, mais
sacrifierait le chemin de mise à jour sur place, vérifié par signature et fondé
sur `git` ; la disposition actuelle privilégie une mise à jour simple et
vérifiable plutôt qu'un espace disque minimal.

## Comment le runtime trouve Python

Les installateurs en une étape et le shim npx sondent des noms différents et
appliquent les mêmes règles. Les installateurs sondent `python3`, `python` et
les noms versionnés (`python3.14` jusqu'à `python3.10`). Le shim npx sonde
`APOTHEM_PYTHON` lorsqu'elle est définie, puis `python3`, `python` et `py -3` ;
il n'a aucun nom versionné. Tous deux rejettent les shims du lanceur Microsoft
Store et acceptent le premier candidat signalant la version 3.10 ou une version
plus récente.
Lorsqu'ils sont exécutés depuis un arbre de code source, les installateurs
réutilisent le localisateur embarqué `hooks/lib/find-python`, qui applique le
même plancher.

## Prochaine étape recommandée

**Exécutez `PYTHONPATH=src python -m apothem --help`** depuis la racine d'un
checkout d'Apothem pour confirmer que le chemin de la CLI autonome se résout sur
votre hôte.
