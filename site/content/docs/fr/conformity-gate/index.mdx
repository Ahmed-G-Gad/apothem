## Les quinze barres

| Barre | ID | Mandat | Classe de vérification | Échec → action |
|---|---|---|---|---|
| 1 | M1 | Agnosticisme vis-à-vis du projet hôte | Raisonnée | Réviser pour correspondre aux conventions de l'hôte |
| 2 | M2 | Discipline éditoriale (registre de divulgation) | Raisonnée | Ajouter les marqueurs de divulgation |
| 3 | M3 | Dix dimensions de qualité | Mécanique + raisonnée | Réviser sur les dimensions en échec |
| 4 | M4 | Auto-application (bloc de vérification présent) | Raisonnée | Consigner le bloc de vérification |
| 5 | M5 | Principe d'autorité (aucune identité / aucun endpoint / aucun secret fabriqué) | Mécanique | Acheminer vers une demande de précision |
| 6 | M6 | Incorporation de l'expertise (lacunes mises au jour) | Raisonnée | Mettre les lacunes au jour ; citer les affinements |
| 7 | M7 | Annotation des options (marqueur « Recommended » + justification des facteurs déterminants) | Mécanique | Annoter les ensembles d'options |
| 8 | M8 | Caractère définitif (aucune formulation évasive dans la prose prescriptive) | Mécanique | Transformer les formulations évasives en énoncés conditionnels |
| 9 | M9 | Levier visuel (les sujets structurels portent des diagrammes) | Raisonnée | Créer / actualiser le diagramme |
| 10 | M10 | Liaison bidirectionnelle (pointeurs de retour réciproques fermés) | Mécanique | Fermer les demi-arêtes |
| 11 | M11 | Sprints agiles (Objectif / Backlog / DoR / DoD / Revue / Rétrospective) | Raisonnée | Restructurer en sprints |
| 12 | M12 | Rapports de phase et disposition canonique | Mécanique + raisonnée | Rédiger la synthèse ; déplacer vers la disposition canonique |
| 13 | M13 | Artisanat du code (lint / formatage / vérification de types ; nombre magique ; bare-except) | Mécanique | Appliquer les règles d'artisanat du code propres à chaque langage |
| 14 | M14 | Systémicité (déclare amont / aval / pairs / applicateurs) | Raisonnée | Déclarer ; indexer dans les registres |
| 15 | M15 | Prêt pour la production (tests + documentation + CHANGELOG + commit conforme + CI au vert + stabilité semver) | Mécanique + raisonnée | Ajouter les surfaces manquantes |

Le portail n'exécute que des validateurs vérifiables par machine. Le jugement raisonné que réclament les barres de classe Raisonnée, ainsi que la moitié raisonnée de chaque barre de classe Mécanique + raisonnée, est évalué en revue.

## Échelle de sévérité

Le portail ne comporte ni échelle de sévérité Critique, Importante ou Consultative, ni seuil de deux constats. Sans `--strict` (ou `APOTHEM_CONFORMITY_STRICT=1`), le portail signale les constats et se termine avec le code `0`. Avec `--strict`, un contrôle sur un seul fichier ou un hook se termine avec le code `2` dès qu'un matcher échoue, et une exécution sur le corpus (`--all` ou `--all-perwrite`) se termine avec le code `2` lorsqu'un validateur ou un matcher bloquant échoue ; les constats consultatifs sont uniquement signalés. Le hook Write/Edit installé ne passe pas `--strict` : il signale les constats et l'écriture se poursuit, sauf si `APOTHEM_CONFORMITY_STRICT=1` est défini dans son environnement.

## Validateurs

La fraction mécanique vit dans [`src/apothem/conformity/`](https://github.com/ahmed-g-gad/apothem/tree/main/src/apothem/conformity), orchestrée par [`src/apothem/conformity/gate.py`](https://github.com/ahmed-g-gad/apothem/blob/main/src/apothem/conformity/gate.py).
Chaque validateur s'exécute de l'une des trois façons suivantes :

- **par écriture** : sur chaque écriture en attente (`--hook`), ou sur chaque fichier suivi avec `--all-perwrite`.
- **autonome** : sur l'ensemble du dépôt avec `--all`, ou un par un avec `--check <name>`.
- **par ensemble de modifications** : sur un diff indexé, exécuté directement avec `python -m apothem.conformity.semver_stability_grep --staged`, et non via le portail.

## Exécuter le portail

Sur un environnement installé, le portail s'exécute automatiquement : le
`settings.json` de Claude Code le branche en tant que hook `PreToolUse` qui
invoque la copie matérialisée à `~/.claude/.apothem/support/conformity/gate.py`
avant chaque Write/Edit. Le portail ne vérifie alors que les écritures situées
dans la portée de son hook, et une écriture hors de cette portée passe
silencieusement ; [Exécuter le portail de conformité](/docs/usage/conformity-gate)
liste cette portée. Depuis un checkout du code source, la forme module exécute le
même code ; faites précéder chaque commande `python` ci-dessous de
`PYTHONPATH=src`. Le portail est consultatif par défaut : il signale les
constats et se termine avec le code `0`. Ajoutez `--strict` pour qu'il se
termine avec le code `2` sur un constat bloquant. Un nom de validateur inconnu
se termine avec le code `3`.

```shell
# Every standalone validator across the repository:
python -m apothem.conformity.gate --all .

# The same sweep, failing on a blocking finding (the CI form):
python -m apothem.conformity.gate --all --strict .

# Every per-write validator against every tracked file:
python -m apothem.conformity.gate --all-perwrite .

# One validator by name (names come from --list):
python -m apothem.conformity.gate --check naming-grep .

# List every registered validator as JSON:
python -m apothem.conformity.gate --list

# Single-file dispatch (mimics the PreToolUse hook):
echo '{"tool_input": {"file_path": "path/to/file", "content": "..."}}' \
    | python -m apothem.conformity.gate --hook
```

`python -m apothem.conformity.gate --help` affiche le résumé d'utilisation.
Voir [Exécuter le portail de conformité](/docs/usage/conformity-gate) pour la procédure complète.
