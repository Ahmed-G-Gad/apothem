Apothem fournit un pipeline `/plan` conscient de l'architecture, un pipeline
`/research` à treize étapes, ainsi qu'une séquence d'audit de onze commandes —
ce qui donne à chaque projet un parcours structuré de la prose brute jusqu'à du
code de niveau production revu sur plusieurs axes, et d'une idée brute jusqu'à
un article diffusé et évalué par les pairs.

## Vue d'ensemble du pipeline

```mermaid
flowchart LR
    accTitle: Plan pipeline command flow
    accDescr: Left-to-right flowchart of the apothem plan pipeline from the spec stage through the generate and review stages, then through a conditional architecture-bearing decision that either runs the design stage or skips directly to the execute stage. The orthogonal audit stage wraps the spec-through-review span as a closed remediation loop, and the re-entrant amend stage revises an existing suite and returns it to review.
    A[/plan-spec] --> B[/plan-generate]
    B --> C[/plan-review]
    AUD[/plan-audit<br/>orthogonal: wraps spec → review] -.->|closed-loop remediation| A
    AM[/plan-amend<br/>re-entrant: revises an existing suite] -.->|re-review| C
    C --> Q{Architecture-bearing suite?}
    Q -->|yes| F[/plan-design<br/>emit _inputs/design.md]
    Q -->|no| D[/plan-execute]
    F --> D
    D --> E[/plan-status]
    D --> G[Audit review sequence]
    G --> H[Completion milestone]
```

## Les étapes de planification

Le pipeline est livré sous forme de huit commandes slash de premier rang, une
par étape — chacune invocable indépendamment sous la forme `/plan-<stage>`.
L'orchestrateur [/plan](/docs/pipeline/plan) les pilote d'une mission jusqu'à
une suite exécutée.

| Étape | Rôle | Position |
|-------|------|----------|
| [/plan-spec](/docs/pipeline/plan-spec) | Forge — de la prose à la spécification | Tête |
| [/plan-generate](/docs/pipeline/plan-generate) | Générateur — de la spécification à la suite de planification | Milieu de chaîne |
| [/plan-review](/docs/pipeline/plan-review) | Auditeur — audit forensique du plan | Milieu de chaîne |
| [/plan-design](/docs/pipeline/plan-design) | Architecte — `_inputs/design.md` pour les suites porteuses d'architecture | Portail conditionnel |
| [/plan-execute](/docs/pipeline/plan-execute) | Exécuteur — exécution des phases | Terminale |
| [/plan-status](/docs/pipeline/plan-status) | Rapporteur — état en lecture seule | Lecture seule |
| [/plan-audit](/docs/pipeline/plan-audit) | Gardien — enveloppe en boucle fermée de spec → generate → review | Orthogonale (avant l'exécution) |
| [/plan-amend](/docs/pipeline/plan-amend) | Intendant — amendement réentrant d'une suite existante | Réentrante |

`/plan-audit` est orthogonal au flux linéaire, et non une étape en son sein. Il
enveloppe `/plan-spec → /plan-generate → /plan-review` en une seule boucle
fermée, n'exécute que les étapes amont manquantes, remédie activement aux
constats et laisse la suite prête pour `/plan-execute`. Il est distinct de la
séquence de revue d'audit ci-dessous, qui audite une base de code exécutée
plutôt qu'une suite de planification.

`/plan-design` n'est pas une cérémonie universelle. `/plan-review` détermine si
la suite modifie des surfaces porteuses d'architecture. Si oui, `/plan-design`
émet la trace de conception que consomment `/plan-execute` et
`/architecture-review`. Si non, la suite revue passe directement à l'exécution.

## Le pipeline de recherche

Le pipeline de recherche est livré sous forme de treize commandes slash de
premier rang, une par étape — chacune invocable indépendamment sous la forme
`/research-<stage>`, enchaînées par un Portail de séquence et un Manifeste de transfert, sous dix mandats de rigueur (sources faisant autorité,
reproductibilité, falsifiabilité, intégrité des citations, préenregistrement,
éthique / conflits d'intérêts, rigueur statistique, science ouverte / FAIR,
conformité aux lignes directrices de rédaction, ancrage théorique / impact).

```mermaid
flowchart LR
    accTitle: Research pipeline command flow
    accDescr: Left-to-right flowchart of the apothem research pipeline from the ideate stage through spec, theory, sources, synthesis, proposal, study design, experiment, analysis, paper, and peer review to publish and disseminate, with a revision loop from review back to paper.
    RI[/research-ideate] --> RS[/research-spec]
    RS --> RT[/research-theory]
    RT --> RSO[/research-sources]
    RSO --> RSY[/research-synthesis]
    RSY --> RPR[/research-proposal]
    RPR --> RD[/research-design]
    RD --> RE[/research-experiment]
    RE --> RA[/research-analysis]
    RA --> RP[/research-paper]
    RP --> RR[/research-review]
    RR --> RPU[/research-publish]
    RPU --> RDI[/research-disseminate]
    RR -.->|revision loop| RP
```

| Étape | Rôle | Position |
|-------|------|----------|
| [/research-ideate](/docs/pipeline/research-ideate) | Formuler le problème — questions candidates à partir d'une amorce de domaine | Tête |
| [/research-spec](/docs/pipeline/research-spec) | Cadrer la question — hypothèses falsifiables + périmètre | Milieu de chaîne |
| [/research-theory](/docs/pipeline/research-theory) | Cadre conceptuel + théorie du changement | Milieu de chaîne |
| [/research-sources](/docs/pipeline/research-sources) | Collecte systématique des sources avec un registre de recherche réexécutable | Milieu de chaîne |
| [/research-synthesis](/docs/pipeline/research-synthesis) | Cartographie de l'état de l'art + analyse des lacunes | Milieu de chaîne |
| [/research-proposal](/docs/pipeline/research-proposal) | Objectifs + faisabilité + plans de contingence + impact + plan de données + plan de préenregistrement ; matrice de l'appel du financeur ou réponse de resoumission | Milieu de chaîne |
| [/research-design](/docs/pipeline/research-design) | Conception de l'étude + préenregistrement | Milieu de chaîne |
| [/research-experiment](/docs/pipeline/research-experiment) | Exécuter + consigner, de façon reproductible | Milieu de chaîne |
| [/research-analysis](/docs/pipeline/research-analysis) | Résultats + statistiques | Milieu de chaîne |
| [/research-paper](/docs/pipeline/research-paper) | Brouillon d'article de premier plan | Milieu de chaîne |
| [/research-review](/docs/pipeline/research-review) | Critique de niveau évaluation par les pairs | Milieu de chaîne |
| [/research-publish](/docs/pipeline/research-publish) | Dossier pour le lieu de publication + soumission | Milieu de chaîne |
| [/research-disseminate](/docs/pipeline/research-disseminate) | Diffusion + impact + archivage FAIR | Terminale |

L'orchestrateur de flux de travail enveloppé [/research](/docs/pipeline/research) pilote ces étapes de la
question brute jusqu'à l'article publié (il n'est pas lui-même une étape), en
vérifiant indépendamment la sortie de chaque étape avant que l'étape suivante ne
s'appuie dessus ; `--quick` n'exécute que `/research-sources` +
`/research-synthesis` pour produire un rapport cité en une seule passe.

Les étapes empiriques (sources, conception, expérience, analyse) et les étapes
de rédaction (article, évaluation, publication, diffusion) s'appuient en outre
sur des surfaces de rigueur opérationnelles — comparaison multi-méthodes
équitable, provenance des comparateurs, une structure de programme
d'expérimentation, un plan d'utilisation du calcul, une boucle d'expérimentation
autonome optionnelle, un portail d'avancement fondé sur la définition de « fini »,
l'aveuglement avec divulgation par étapes, un registre de recherche,
l'allocation de l'étude et la planification de la puissance, la discipline
d'analyse, les plans de contingence, l'intégrité des figures et la
planification des présentations et des posters — qui ajoutent du détail
opérationnel aux dix mandats sans les étendre.

## Séquence de revue d'audit

L'orchestrateur de flux de travail enveloppé [/audit](/docs/pipeline/audit) balaie les onze dimensions ci-dessous en une seule passe parallèle — l'analogue, pour la forteresse d'audit, de `/plan` et `/research` — et synthétise un unique rapport de constats dédupliqué et trié par sévérité (rapport uniquement ; la remédiation est confiée à `/elevate`). Chaque dimension est aussi invocable individuellement.

L'orchestrateur de flux de travail enveloppé [/fortress](/docs/pipeline/fortress) ferme la boucle dont `/audit` rend compte : il détecte via `/audit`, vérifie chaque constat, remédie à chaque constat retenu sur la surface dont il relève, réaudite dans une boucle bornée et soumet le résultat au portail [/release-readiness](/docs/pipeline/release-readiness) — l'analogue, pour le durcissement de production, de `/plan` et `/research`.

| Commande | Domaine de qualité |
|---------|--------------|
| [/code-review](/docs/pipeline/code-review) | Qualité du code |
| [/code-audit](/docs/pipeline/code-audit) | Corpus de code |
| [/security-audit](/docs/pipeline/security-audit) | OWASP / ASVS |
| [/perf-audit](/docs/pipeline/perf-audit) | Performance |
| [/architecture-review](/docs/pipeline/architecture-review) | Architecture |
| [/ux-review](/docs/pipeline/ux-review) | Expérience développeur |
| [/a11y-audit](/docs/pipeline/a11y-audit) | Accessibilité |
| [/docs-review](/docs/pipeline/docs-review) | Documentation |
| [/dependency-audit](/docs/pipeline/dependency-audit) | Dépendances |
| [/supply-chain-audit](/docs/pipeline/supply-chain-audit) | Chaîne d'approvisionnement |
| [/threat-model-audit](/docs/pipeline/threat-model-audit) | Modèle de menaces |
