**Éditeur :** Z.ai
**Nom d'installation :** `glm`
**Statut :** GA
**Configuration native :** `<project>/.apothem/providers/glm.toml`

GLM (Z.ai) est un **backend de modèle**, et non un outil de codage en propre.
Z.ai ne fournit aucune ligne de commande GLM officielle ; c'est un outil parlant
le protocole compatible Anthropic ou compatible OpenAI qui est dirigé vers GLM,
en définissant une URL de base de backend et une clé. Apothem compte néanmoins
GLM parmi ses adaptateurs d'environnement ; vous le sélectionnez donc avec
`--harness glm`, comme n'importe quel autre. L'adaptateur `glm` écrit un fichier
de configuration de fournisseur qui consigne les deux surfaces de compatibilité,
afin que tout outil compatible puisse être raccordé à la famille de modèles GLM.

## Installation

```bash
apothem install --harness glm --project /path/to/project
```

L'adaptateur écrit un seul fichier de fournisseur de portée projet, qui
consigne les points de terminaison du backend GLM et des espaces réservés
configurables par l'opérateur.

**Fichiers écrits :** `<project>/.apothem/providers/glm.toml`

## Correspondance entre le profil et la configuration native

Le fichier de fournisseur consigne deux backends. Le backend compatible
Anthropic utilise l'URL de base `https://api.z.ai/api/anthropic` ; un outil qui
parle le protocole Anthropic est routé vers GLM en définissant
`ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN` et, en option, `API_TIMEOUT_MS`.
La table `[backends.anthropic_compatible.env]` du fichier liste ces variables
ainsi que `ANTHROPIC_DEFAULT_OPUS_MODEL`, `ANTHROPIC_DEFAULT_SONNET_MODEL` et
`ANTHROPIC_DEFAULT_HAIKU_MODEL`, qui associent les rôles opus, sonnet et haiku
de l'outil à des modèles GLM. Le backend compatible OpenAI utilise l'URL de base
`https://api.z.ai/api/coding/paas/v4`. Le jeton d'authentification est un
espace réservé que vous remplacez par votre propre clé Z.ai — Apothem n'écrit
jamais de véritable secret. Les identifiants de modèle changent d'une version à
l'autre ; Apothem n'en épingle donc aucun, et le fichier porte des espaces
réservés `<GLM_MODEL_ID>` que vous renseignez à partir de la
[documentation de Z.ai](https://docs.z.ai/devpack/tool/claude) actuelle. Rien
du profil partagé n'entre dans ce fichier ; c'est un template fixe.

## Notes de compatibilité

Comme GLM est un backend et non un outil de codage, il n'expose aucune surface
pour les règles, les commandes, les skills ou les hooks — l'adaptateur n'écrit
que le fichier de fournisseur du backend et rien d'autre. Votre clé Z.ai et vos
choix d'identifiants de modèle restent détenus par l'opérateur. Les conventions
de la surface éditeur sur lesquelles l'adaptateur s'appuie sont épinglées dans
`src/apothem/harnesses/glm/STANDARD-CONVENTION-PIN.md`, dont l'instantané a été
pris par rapport à la documentation en ligne de Z.ai.

GLM exécute la famille de modèles GLM de Z.ai ; consultez la
[référence de configuration de l'éditeur](https://docs.z.ai/devpack/tool/claude)
pour connaître le backend, les modèles et la surface de configuration
compatible Anthropic actuels.

## Vérification

```bash
apothem verify --harness glm --project /path/to/project
```

La commande verify confirme que :

1. La configuration native existe au chemin attendu.
2. Le fichier de fournisseur est présent et non vide.
3. La routine de vérification propre à l'adaptateur signale un succès.

## Mise à jour

```bash
apothem update --harness glm --project /path/to/project
```

Le fichier de fournisseur vous appartient dès qu'il existe. `install` et
`update` n'écrivent tous deux le template que lorsque
`.apothem/providers/glm.toml` est absent, et ni l'un ni l'autre ne l'écrase
jamais par la suite ; votre référence de clé et vos choix de modèles survivent
donc à chaque nouvelle exécution. Pour récupérer un template plus récent,
mettez votre fichier de côté, exécutez `update`, puis recopiez vos valeurs dans
le nouveau fichier.

## Désinstallation

```bash
apothem uninstall --harness glm --project /path/to/project
```

Ne supprime le fichier de fournisseur que si Apothem l'a créé et qu'il s'agit
toujours du template non modifié, en le sauvegardant d'abord sous la racine de
sauvegarde d'Apothem. Un fichier que vous avez créé ou modifié est laissé en
place. Le YAML du profil partagé et le moteur Apothem ne sont pas affectés.

## Dépannage

| Symptôme | Correctif |
|---------|-----|
| Fichier de configuration introuvable | Relancez `apothem install --harness glm --project /path/to/project` |
| Échec de la vérification | Le fichier de fournisseur est absent ou vide. S'il est absent, exécutez `apothem update --harness glm --project /path/to/project`. S'il est vide, mettez d'abord `.apothem/providers/glm.toml` de côté, puis exécutez `update` et vérifiez à nouveau |
| Contenu de configuration inattendu | Modifiez directement `.apothem/providers/glm.toml` ; Apothem ne réécrit jamais un fichier existant, et le profil partagé n'y ajoute rien. Pour obtenir un template neuf, mettez le fichier de côté et exécutez `apothem update --harness glm --project /path/to/project` |
