Apothem fournit dix-sept adaptateurs d'environnement intégrés. Chaque adaptateur traduit les
mêmes cohortes partagées en fichiers natifs à la plateforme là où la plateforme les prend en charge,
et en arborescences de support détenues par Apothem là où elle ne le fait pas.

## Environnements pris en charge

Le registre pris en charge contient exactement dix-sept adaptateurs. Utilisez ces noms d'installation
exacts avec `--harness`, ou utilisez `all` pour l'ensemble déterministe du registre :

```text
antigravity
claude-code
codebuddy
codex
cursor
gemini-cli
github-copilot
glm
hermes
kimi-code
kiro
open-claw
opencode
qwen-code
trae
windsurf
zed
```

La matrice détaillée du registre, les chemins cibles, les états de capacité, la prise en charge MCP
et les preuves de convention-pin se trouvent dans la [référence technique du registre](/docs/reference/harness-registry).

## Installer plusieurs environnements

Installez un environnement, ou utilisez `all` pour sélectionner le registre dans un ordre
déterministe. Les environnements à portée de projet nécessitent `--project PATH` ; cela inclut `all`
car le registre comprend à la fois des cibles à portée utilisateur et à portée de projet.

```bash
apothem install --harness claude-code
apothem install --harness cursor --project /path/to/project
apothem install --harness gemini-cli --project /path/to/project
apothem install --harness all --project /path/to/project
```

## Vérifier vos installations

Vérifiez chaque adaptateur d'environnement individuellement, ou appelez `apothem doctor` pour obtenir un
résumé du statut d'installation par adaptateur sur chaque adaptateur enregistré :

```bash
apothem verify --harness claude-code
apothem verify --harness all --project /path/to/project
apothem doctor
```

## Comment fonctionnent les adaptateurs

Chaque adaptateur implémente le protocole `HarnessAdapter` enregistré via les
entry-points setuptools. À l'installation, la CLI charge et valide le profil
YAML partagé, résout l'adaptateur via le registre, valide le
plan de matérialisation, et écrit la configuration native à la plateforme à l'emplacement
utilisateur ou projet natif de l'environnement. À la mise à jour, elle re-dérive depuis l'état
actuel du profil.

```
profile.yaml + packaged cohorts
    identity / preferences / rules
    commands / skills / delegated definitions / hooks / templates
         |
         +-- antigravity    --> ~/.gemini/GEMINI.md + ~/.gemini/antigravity-cli/plugins/apothem/
         +-- claude-code    --> ~/.claude/ native folders + ~/.claude/.apothem/support/
         +-- codex          --> ~/.codex/ + ~/.agents/skills/ + ~/.config/apothem/{rules,templates}/
         +-- cursor         --> <project>/.cursor/rules/*.mdc + <project>/.cursor/agents/ + ~/.agents/skills/ + ~/.config/apothem/{rules,templates}/
         +-- gemini-cli     --> <project>/GEMINI.md + <project>/.gemini/
         +-- github-copilot --> <project>/.github/copilot-instructions.md + <project>/.github/agents/ + ~/.agents/skills/ + ~/.config/apothem/{rules,templates}/
         +-- windsurf       --> <project>/.devin/rules/ + <project>/.devin/agents/ + ~/.agents/skills/ + ~/.config/apothem/{rules,templates}/
         +-- ...
```

## Skills dans votre répertoire personnel

Sept adaptateurs de portée projet écrivent un fichier de règles dans votre projet
(six d'entre eux y écrivent aussi les auxiliaires d'Apothem sous forme de
fichiers de subagents ; chaque page d'environnement nomme le dossier), et ils
écrivent aussi les skills d'Apothem, ainsi que les règles et templates que les
skills citent, dans des dossiers de votre répertoire personnel :

```text
cursor, github-copilot, windsurf, zed  ->  ~/.agents/skills/ (codex writes it too)
codebuddy                               ->  ~/.codebuddy/skills/
kiro                                    ->  ~/.kiro/skills/
trae                                    ->  ~/.trae/skills/
all seven                               ->  ~/.config/apothem/rules/ and templates/ (codex uses them too)
```

- Chaque installation qui nomme un dossier écrit les mêmes fichiers, de sorte
  que l'ordre d'installation n'a pas d'importance, et une seule copie sert tous
  les projets.
- Une installation écrit d'abord les dossiers du répertoire personnel. Si cela
  échoue, elle s'arrête avant de modifier le projet, et elle n'ajoute aucun
  fichier de skill ni de règle à votre dépôt.
- Une désinstallation ne supprime un dossier partagé que si aucune autre
  installation Apothem ne l'utilise encore, et indique quelle installation le
  conserve.
- Un dossier de skill portant le nom d'un skill Apothem qu'Apothem n'a pas écrit
  est laissé tel quel, avec un avertissement.

Chaque page d'environnement liste ses dossiers. Le
[registre des environnements](/docs/reference/harness-registry#racines-partagées)
indique quels outils partagent quel dossier.

Consultez [Abstraction d'adaptateur d'environnement](/docs/architecture/harness-adapter-abstraction)
pour la spécification du protocole.
