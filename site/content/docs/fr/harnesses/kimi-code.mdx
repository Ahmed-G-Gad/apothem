**Éditeur :** Moonshot
**Nom d'installation :** `kimi-code`
**Statut :** GA
**Configuration native :** `<project>/AGENTS.md` plus `<project>/.kimi-code/.apothem/support/`

## Installation

```bash
apothem install --harness kimi-code --project /path/to/project
```

L'adaptateur écrit la surface de gouvernance partagée d'Apothem dans le
`AGENTS.md` à la racine du projet, sous la forme d'un bloc géré délimité par des
sentinelles (la prose de l'opérateur située hors des sentinelles est préservée),
et conserve les cohortes Markdown non natives sous l'arborescence de support
détenue par Apothem, à `<project>/.kimi-code/.apothem/support/`.
Un `AGENTS.md` de projet est lu par de nombreux outils de développement en plus
de Kimi Code ; le bloc est donc rédigé comme une consigne valable pour tout le
projet, qui ne désigne aucun outil unique comme son lecteur.

Kimi Code lit le fichier d'instructions `AGENTS.md` à la racine du projet selon
la convention universelle AGENTS.md, et la configuration du projet se trouve
sous `<project>/.kimi-code/`. La surface `<project>/.kimi-code/mcp.json` est
détenue par l'opérateur ; Apothem la nomme mais n'y rédige aucune entrée.

**Fichiers écrits :** `<project>/AGENTS.md` (bloc géré) et les cohortes de
commandes, de skills, de hooks, d'agents, de règles et de templates sous
`<project>/.kimi-code/.apothem/support/`.

## Correspondance entre le profil et la configuration native

L'adaptateur lit le profil partagé d'Apothem et rend la surface d'instructions
`AGENTS.md` à la racine du projet à chaque exécution de `apothem install` ou de
`apothem update`. Les règles comportementales et le corpus de gouvernance
atterrissent dans le bloc géré de `AGENTS.md` ; les cohortes de commandes, de
skills, de hooks, d'agents, de règles et de templates sont placées sous
`.kimi-code/.apothem/support/` et référencées depuis la surface d'instructions.
Il s'agit de la disposition choisie par l'adaptateur, et non d'une lacune de
Kimi Code : Kimi Code charge les skills depuis `.kimi-code/skills/` et
`.agents/skills/`, les assistants personnalisés depuis `.kimi-code/agents/` et
`.agents/agents/`, et les hooks depuis le tableau `[[hooks]]` de
`~/.kimi-code/config.toml`, mais il ne les charge pas depuis l'arborescence de
support ; les copies Apothem qui s'y trouvent sont donc du matériel de
référence vers lequel pointe le bloc `AGENTS.md`. Le bloc se termine par une
section consacrée aux fichiers de support Apothem, qui nomme, relativement à la
racine du projet, le répertoire sous `.kimi-code/.apothem/support/` par rapport
auquel se résout chaque citation de style dépôt (`rules/<name>.md`,
`templates/...`, `hooks/...`), de sorte qu'un `AGENTS.md` commité ne porte aucun
chemin propre à une machine. (Comportement de Kimi Code selon ses pages de
personnalisation consacrées aux
[skills](https://moonshotai.github.io/kimi-code/en/customization/skills),
aux [sous-assistants](https://moonshotai.github.io/kimi-code/en/customization/agents) et
aux [hooks](https://moonshotai.github.io/kimi-code/en/customization/hooks),
consultées le 2026-10-02.)

## Notes de compatibilité

Kimi Code lit les instructions du projet depuis `AGENTS.md` ou
`.kimi-code/AGENTS.md` et reconnaît `.kimi-code/mcp.json` comme la surface MCP
détenue par l'opérateur ; Apothem nomme cette surface mais n'y rédige aucune
entrée. La surface d'instructions rendue pilote directement le projet. Kimi Code
n'expose aucune surface de fichier pour la ligne d'état ni pour les
output-styles ; ces cohortes ne sont donc pas matérialisées.

Kimi Code s'exécute sur la famille de modèles Kimi de Moonshot ; consultez la
[référence de configuration de l'éditeur](https://moonshotai.github.io/kimi-code/en/configuration/config-files)
pour le modèle et la surface de configuration actuels.

## Vérification

```bash
apothem verify --harness kimi-code --project /path/to/project
```

La commande verify confirme que :

1. La configuration native existe au chemin attendu.
2. Chaque cible gérée existe ; les fichiers gérés ne sont pas vides, et les
   configurations JSON ou YAML s'analysent correctement. Ajoutez
   `--profile PATH` pour vérifier en plus que les fichiers installés
   correspondent à ce profil.
3. La routine de vérification propre à l'adaptateur signale un succès.

## Mise à jour

```bash
apothem update --harness kimi-code --project /path/to/project
```

Redérive le bloc géré de `AGENTS.md` à la racine du projet et les cohortes de
support à partir de l'état actuel du profil partagé.

## Désinstallation

```bash
apothem uninstall --harness kimi-code --project /path/to/project
```

Retire le bloc Apothem du `AGENTS.md` à la racine du projet et conserve tout
texte situé hors des sentinelles. Le fichier n'est supprimé que si plus rien
d'autre n'y subsiste. Retire aussi les fichiers de support qu'Apothem a placés
sous `<project>/.kimi-code/.apothem/support/`. Avant la modification, une copie
horodatée de chaque fichier est enregistrée sous `~/.apothem/backups/` ; aucun
fichier de sauvegarde n'est laissé dans le projet. Le YAML du profil partagé et
le moteur Apothem ne sont pas affectés.

## Portail de conformité

```bash
python -m apothem.conformity.gate --all .
```

## Dépannage

| Symptôme | Correctif |
|---------|-----|
| Fichier de configuration introuvable | Relancez `apothem install --harness kimi-code --project /path/to/project` |
| Échec de la vérification | Exécutez `apothem update --harness kimi-code --project /path/to/project`, puis vérifiez à nouveau |
| Contenu de configuration inattendu | Vérifiez `~/.config/apothem/profile.yaml` ou `--profile PATH`, puis relancez `apothem update --harness kimi-code --project /path/to/project` |

## Paramètres de configuration

| Option | Par défaut | Description |
|------|---------|-------------|
| `--dry-run` | `false` | Prévisualise l'installation sans écrire de fichiers. |
