**Éditeur :** Zed Industries
**Nom d'installation :** `zed`
**Statut :** GA
**Configuration native :** `<project>/.rules`

## Installation

```bash
apothem install --harness zed --project /path/to/project
```

L'adaptateur écrit un fichier d'instructions Zed de portée projet à partir des
règles partagées d'Apothem et de la surface de gouvernance. Zed lit un seul
fichier d'instructions de projet : la première correspondance dans cette liste :

```text
.rules
.cursorrules
.windsurfrules
.clinerules
.github/copilot-instructions.md
AGENT.md
AGENTS.md
CLAUDE.md
GEMINI.md
```

Il n'existe aucun répertoire de règles propre à chaque outil ; toute la surface
Apothem atterrit donc dans le fichier plat `.rules`, en tête de cette liste.

**Fichiers écrits :** `<project>/.rules`

## Correspondance entre le profil et la configuration native

L'adaptateur lit le profil partagé d'Apothem et rend le fichier `.rules` du
projet à chaque exécution de `apothem install` ou de `apothem update`. Le profil
partagé est la source de vérité ; tout `.rules` préexistant (ou toute
modification locale au projet apportée au fichier généré) est sauvegardé avant
que la synchronisation suivante ne remplace le contenu géré par Apothem.

## Notes de compatibilité

Zed désigne `AGENTS.md` comme son fichier d'instructions principal et conserve
le `.rules` de projet comme fichier de compatibilité pris en charge
([instructions de Zed](https://zed.dev/docs/ai/instructions)). Comme Zed ne lit
que la première correspondance, un nouveau `.rules` masque un `AGENTS.md`, un
`CLAUDE.md` ou tout autre fichier situé plus bas dans la liste dont le projet
dépend déjà. L'installation ne modifie jamais ces fichiers. Lorsque `.rules` ne
contient que le bloc Apothem et qu'un fichier de priorité inférieure contient
votre texte, l'installation et la mise à jour affichent un avertissement qui
nomme le fichier masqué ; copiez les instructions dont vous avez besoin dans
`.rules`, hors du bloc Apothem, pour les conserver dans Zed.

Le fichier d'instructions global `~/.config/zed/AGENTS.md` et le bloc de
serveurs de contexte MCP (`context_servers` de `.zed/settings.json`) sont
détenus par l'opérateur ; Apothem ne les écrit pas.

## Vérification

```bash
apothem verify --harness zed --project /path/to/project
```

La commande verify confirme que :

1. La configuration native existe au chemin attendu.
2. Chaque cible gérée existe ; les fichiers gérés ne sont pas vides, et les configurations JSON ou YAML s'analysent correctement. Ajoutez `--profile PATH` pour vérifier en plus que les fichiers installés correspondent à ce profil.
3. La routine de vérification propre à l'adaptateur signale un succès.

## Mise à jour

```bash
apothem update --harness zed --project /path/to/project
```

Redérive le fichier `.rules` du projet à partir de l'état actuel du profil
partagé.

## Désinstallation

```bash
apothem uninstall --harness zed --project /path/to/project
```

Supprime le bloc géré d'Apothem du fichier de configuration native `.rules` et conserve votre propre texte. Le fichier n'est supprimé que si rien d'autre n'y subsiste. Avant la modification, une copie horodatée du fichier est enregistrée sous `~/.apothem/backups/` ; aucun fichier de sauvegarde ne reste dans le projet. Le YAML du profil partagé et le moteur Apothem ne sont pas affectés.

## Portail de conformité

```bash
python -m apothem.conformity.gate --all .
```

## Dépannage

| Symptôme | Correctif |
|---------|-----|
| Fichier de configuration introuvable | Relancez `apothem install --harness zed --project /path/to/project` |
| Échec de la vérification | Exécutez `apothem update --harness zed --project /path/to/project`, puis vérifiez à nouveau |
| Contenu de configuration inattendu | Vérifiez `~/.config/apothem/profile.yaml` ou `--profile PATH`, puis relancez `apothem update --harness zed --project /path/to/project` |

## Paramètres de configuration

| Option | Par défaut | Description |
|------|---------|-------------|
| `--dry-run` | `false` | Prévisualise l'installation sans écrire de fichiers. |
