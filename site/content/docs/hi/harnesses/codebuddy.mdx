**विक्रेता:** Tencent
**इंस्टॉल नाम:** `codebuddy`
**स्थिति:** GA
**नेटिव कॉन्फ़िग:** `<project>/.codebuddy/rules/apothem-rules.md`

## इंस्टॉलेशन

```bash
apothem install --harness codebuddy --project /path/to/project
```

अडैप्टर साझा Apothem नियमों और शासन सतह से एक प्रोजेक्ट-स्कोप नियम फ़ाइल
लिखता है।

**लिखी गई फ़ाइलें:** `<project>/.codebuddy/rules/apothem-rules.md`

## प्रोफ़ाइल-से-नेटिव-कॉन्फ़िग मैपिंग

अडैप्टर Apothem की साझा प्रोफ़ाइल पढ़ता है और प्रत्येक `apothem install` या
`apothem update` रन पर प्रोजेक्ट नियम फ़ाइल रेंडर करता है। CodeBuddy,
[CodeBuddy Rules दस्तावेज़](https://www.codebuddy.ai/docs/ide/Rules) के अनुसार,
`.codebuddy/rules/` के अंतर्गत हर `*.md` फ़ाइल को वैकल्पिक YAML फ़्रंटमैटर
(`alwaysApply`, `paths`, `enabled`) वाले Markdown के रूप में पढ़ता है; Apothem
की फ़ाइल `alwaysApply: true` रखती है ताकि शासन सतह हर इंटरैक्शन पर लागू हो।
फ़्रंटमैटर फ़ाइल की पहली सामग्री है और Apothem-प्रबंधित ब्लॉक उसके बाद आता है;
ब्लॉक के बाद आपके द्वारा जोड़ा गया पाठ हर सिंक पर बना रहता है। सत्य का स्रोत
साझा प्रोफ़ाइल है; अगला सिंक Apothem-प्रबंधित सामग्री को बदले, उससे पहले उत्पन्न
फ़ाइल में किए गए प्रोजेक्ट-स्थानीय संपादनों का बैकअप लिया जाता है।

## संगतता टिप्पणियाँ

CodeBuddy की नियम सतह `.codebuddy/rules/` के अंतर्गत प्रोजेक्ट-स्कोप वाली है।
अडैप्टर एक समर्पित `apothem-rules.md` फ़ाइल लिखता है जो उसी डायरेक्टरी में
ऑपरेटर द्वारा लिखी गई किसी भी नियम फ़ाइल के साथ सह-अस्तित्व में रहती है।
`CODEBUDDY.md` प्रोजेक्ट मेमोरी फ़ाइल, `.codebuddy/settings.json`, और प्रोजेक्ट
`.mcp.json` (MCP सर्वर) ऑपरेटर-स्वामित्व वाले हैं; Apothem उन्हें नहीं लिखता।
CodeBuddy स्किल, कमांड, सब-एजेंट, और हुक का भी दस्तावेज़ीकरण करता है; अडैप्टर
इनमें से कोई भी नहीं लिखता और इसके बजाय नियम फ़ाइल के भीतर अनुशासनों का संदर्भ
देता है। जब किसी प्रोजेक्ट में कोई `CODEBUDDY.md` नहीं होती, तो CodeBuddy Code
`AGENTS.md` को प्रोजेक्ट मेमोरी के रूप में पढ़ता है, इसलिए किसी अन्य अडैप्टर
द्वारा लिखी गई `AGENTS.md` भी CodeBuddy तक पहुँचती है। अडैप्टर जिन विक्रेता सतह
परिपाटियों पर निर्भर करता है, वे
`src/apothem/harnesses/codebuddy/STANDARD-CONVENTION-PIN.md` पर पिन की गई हैं, और
उनका स्नैपशॉट लाइव CodeBuddy दस्तावेज़ के विरुद्ध लिया गया है।

## सत्यापन

```bash
apothem verify --harness codebuddy --project /path/to/project
```

verify कमांड पुष्टि करता है कि:

1. नेटिव कॉन्फ़िग अपेक्षित पथ पर मौजूद है।
2. प्रबंधित नियम फ़ाइल मौजूद है और खाली नहीं है।
3. अडैप्टर-विशिष्ट सत्यापन रूटीन सफलता की रिपोर्ट करता है।

## अपडेट करना

```bash
apothem update --harness codebuddy --project /path/to/project
```

वर्तमान साझा प्रोफ़ाइल स्थिति से प्रोजेक्ट नियम फ़ाइल को पुनः व्युत्पन्न करता है।
`install` और `update` इडेम्पोटेंट हैं — फिर से चलाने पर प्रबंधित फ़ाइल नवीनतम
रेंडर की गई सामग्री से अधिलेखित हो जाती है।

## अनइंस्टॉल करना

```bash
apothem uninstall --harness codebuddy --project /path/to/project
```

`apothem-rules.md` से Apothem ब्लॉक हटाता है और उसमें मौजूद किसी भी अन्य टेक्स्ट को रखता है। फ़ाइल तभी हटाई जाती है जब उसमें कुछ और न बचे। बदलाव से पहले फ़ाइल की एक टाइमस्टैम्प-युक्त प्रति `~/.apothem/backups/` के अंतर्गत सहेजी जाती है; प्रोजेक्ट में कोई बैकअप फ़ाइल नहीं छोड़ी जाती। साझा प्रोफ़ाइल YAML और Apothem इंजन अप्रभावित रहते हैं।

## अनुरूपता गेट

```bash
python -m apothem.conformity.gate --all .
```

## समस्या निवारण

| लक्षण | समाधान |
|---------|-----|
| कॉन्फ़िग फ़ाइल नहीं मिली | `apothem install --harness codebuddy --project /path/to/project` फिर से चलाएँ |
| सत्यापन विफल रहा | `apothem update --harness codebuddy --project /path/to/project` चलाएँ, फिर दोबारा सत्यापित करें |
| अप्रत्याशित कॉन्फ़िग सामग्री | `~/.config/apothem/profile.yaml` या `--profile PATH` जाँचें, फिर `apothem update --harness codebuddy --project /path/to/project` फिर से चलाएँ |
