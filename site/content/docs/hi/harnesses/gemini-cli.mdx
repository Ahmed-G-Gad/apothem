**विक्रेता:** Google
**इंस्टॉल नाम:** `gemini-cli`
**स्थिति:** GA
**नेटिव कॉन्फ़िग:** प्रोजेक्ट-स्थानीय `GEMINI.md` और `.gemini/`

## इंस्टॉलेशन

```bash
apothem install --harness gemini-cli --project /path/to/project
```

अडैप्टर प्रोजेक्ट-स्कोप वाला है। यह प्रोजेक्ट की `GEMINI.md` इंस्टॉल करता है,
Apothem कमांडों को Gemini TOML स्लैश कमांडों में परिवर्तित करता है, स्थानीय सहायक
परिभाषाओं को सामान्यीकृत करता है, और गैर-नेटिव समर्थन समूहों को
`.gemini/.apothem/support/` के अंतर्गत रखता है।
अन्य कोडिंग टूल भी प्रोजेक्ट की `GEMINI.md` पढ़ते हैं, इसलिए उसमें Apothem ब्लॉक
प्रोजेक्ट-व्यापी मार्गदर्शन के रूप में लिखा जाता है, जो किसी एक टूल को अपने पाठक
के रूप में नामित नहीं करता।

**लिखी गई फ़ाइलें:**

```text
GEMINI.md
.gemini/commands/*.toml
.gemini/agents/*.md
.gemini/skills/
.gemini/.apothem/support/
```

## प्रोफ़ाइल-से-नेटिव-कॉन्फ़िग मैपिंग

अडैप्टर Apothem के साझा समूहों को पढ़ता है और प्रत्येक को एक Gemini-संगत सतह के
माध्यम से भेजता है। Markdown नियम, टेम्पलेट, और हुक सामग्री
`.gemini/.apothem/support/` के अंतर्गत रहती है, क्योंकि वह समर्थन सामग्री है, कोई
Gemini-नेटिव नियम डायरेक्टरी नहीं।
`GEMINI.md` में Apothem ब्लॉक एक Apothem समर्थन फ़ाइल अनुभाग के साथ समाप्त होता
है, जो प्रत्येक रिपॉज़िटरी-शैली उद्धरण (`rules/<name>.md`, `templates/...`,
`hooks/...`) के लिए `.gemini/.apothem/support/` के अंतर्गत वह डायरेक्टरी, प्रोजेक्ट
रूट के सापेक्ष, बताता है जिसके सापेक्ष वह उद्धरण हल होता है। पथ सापेक्ष हैं ताकि
कमिट की गई `GEMINI.md` में कोई मशीन-विशिष्ट पथ न रहे।

`.gemini/commands/` में प्रत्येक परिवर्तित कमांड एक `description` और एक `prompt`
रखता है। प्रॉम्प्ट में केवल कमांड के निर्देश होते हैं; स्रोत फ़ाइल के शीर्ष पर
स्थित Apothem मेटाडेटा (संस्करण, टूल सूची, और इसी तरह के फ़ील्ड) छोड़ दिया जाता
है, ताकि मॉडल उसे कभी निर्देशों के रूप में न पढ़े। Gemini किसी कस्टम कमांड को
केवल तभी चलाता है जब आप उसे टाइप करते हैं।

`.gemini/agents/` में सहायक परिभाषाएँ अपनी टूल सीमाएँ और टर्न सीमा बनाए रखती हैं:
स्रोत `tools` अनुदान, `disallowedTools` घटाने के बाद, Gemini टूल नामों की एक
Gemini `tools` अनुमति-सूची बन जाता है, और `maxTurns` `max_turns` बन जाता है।
इसलिए किसी केवल-पठन सहायक को कोई `write_file` या `replace` टूल नहीं मिलता। कोई
मॉडल सेट नहीं किया जाता, इसलिए प्रत्येक सहायक सत्र का मॉडल विरासत में लेता है।

## संगतता टिप्पणियाँ

`~/.gemini/` उन टूल्स के लिए उपयोगकर्ता-स्कोप क्षेत्र बना रहता है जो एक वैश्विक
Gemini प्रोफ़ाइल का उपयोग करते हैं। Gemini CLI अडैप्टर केवल `--project` के माध्यम
से दिए गए प्रोजेक्ट में लिखता है।

## सत्यापन

```bash
apothem verify --harness gemini-cli --project /path/to/project
```

verify कमांड पुष्टि करता है कि:

1. नेटिव कॉन्फ़िग अपेक्षित पथ पर मौजूद है।
2. हर प्रबंधित टारगेट मौजूद है; प्रबंधित फ़ाइलें खाली नहीं हैं, और JSON या YAML
   कॉन्फ़िग पार्स होते हैं। `--profile PATH` जोड़ने पर यह भी पुष्टि होती है कि
   इंस्टॉल की गई फ़ाइलें उस प्रोफ़ाइल से मेल खाती हैं।
3. अडैप्टर-विशिष्ट सत्यापन रूटीन सफलता की रिपोर्ट करता है।

## अपडेट करना

```bash
apothem update --harness gemini-cli --project /path/to/project
```

`GEMINI.md`, परिवर्तित कमांडों, स्थानीय सहायक परिभाषाओं, इंस्टॉल किए गए स्किल, और
`.gemini/.apothem/support/` समर्थन वृक्ष को ताज़ा करता है।

## अनइंस्टॉल करना

```bash
apothem uninstall --harness gemini-cli --project /path/to/project
```

अडैप्टर द्वारा लिखी गई नेटिव कॉन्फ़िग फ़ाइलों को हटाता है।
साझा प्रोफ़ाइल YAML और Apothem इंजन अप्रभावित रहते हैं।

## अनुरूपता गेट

```bash
python -m apothem.conformity.gate --all .
```

## समस्या निवारण

| लक्षण | समाधान |
|---------|-----|
| कॉन्फ़िग फ़ाइल नहीं मिली | `apothem install --harness gemini-cli --project /path/to/project` फिर से चलाएँ |
| सत्यापन विफल रहा | `apothem update --harness gemini-cli --project /path/to/project` चलाएँ, फिर दोबारा सत्यापित करें |
| अप्रत्याशित कॉन्फ़िग सामग्री | `~/.config/apothem/profile.yaml` या `--profile PATH` जाँचें, फिर `apothem update --harness gemini-cli --project /path/to/project` फिर से चलाएँ |
