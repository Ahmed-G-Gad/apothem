`src/apothem/conformity/gate.py` पर स्थित अनुरूपता गेट, ऑपरेटर द्वारा लिखे गए
हर आर्टिफ़ैक्ट के विरुद्ध पंद्रह-बार प्री-एमिशन गेट (M1-M15) का यांत्रिक अंश
चलाता है।

इस पृष्ठ की कमांड एक Apothem चेकआउट मानती हैं, इसलिए आप जो भी कमांड चलाएँ, उसके
आगे `PYTHONPATH=src` लगाएँ। स्क्रिप्ट इंस्टॉल के बाद `PYTHONPATH=src` की जगह
`PYTHONPATH="$HOME/.apothem/src"` का उपयोग करें।

## गेट चलाना

गेट **डिफ़ॉल्ट रूप से परामर्शी** है: यह निष्कर्षों की रिपोर्ट करता है और `0`
के साथ बाहर निकलता है, इसलिए कोई स्थानीय रन आपको कभी अवरुद्ध नहीं करता। किसी
अवरोधक निष्कर्ष पर गैर-शून्य के साथ बाहर निकलने के लिए `--strict` जोड़ें (या
`APOTHEM_CONFORMITY_STRICT=1` सेट करें) — यही वह मोड है जिसका उपयोग CI और
pre-commit किसी उल्लंघनकारी बदलाव को विफल करने के लिए करते हैं।

```bash
# Advisory: report every validator's findings across the repo, exit 0
PYTHONPATH=src python -m apothem.conformity.gate --all .

# Strict: exit non-zero (code 2) when a blocking finding is present
PYTHONPATH=src python -m apothem.conformity.gate --all --strict .
```

ये कमांड गेट को एक Apothem चेकआउट से चलाती हैं। `python -m` मॉड्यूल सबसे पहले
वर्तमान फ़ोल्डर से पढ़ता है, इसलिए इन्हें चेकआउट रूट से या किसी ऐसे दूसरे फ़ोल्डर
से चलाएँ जिस पर आपको भरोसा हो। जिस प्रोजेक्ट की फ़ाइलों पर आपको भरोसा नहीं है,
उसकी जाँच के लिए गेट को उसकी स्क्रिप्ट के पथ से `-E -s` के साथ चलाएँ:
चेकआउट में `python3 -E -s src/apothem/conformity/gate.py --all .`, या स्क्रिप्ट
इंस्टॉल के बाद `python3 -E -s ~/.apothem/src/apothem/conformity/gate.py --all .`।
Windows पर `python3` की जगह `python` और पूरा पथ उपयोग करें, क्योंकि Windows
PowerShell और cmd `~` को नहीं फैलाते: PowerShell में
`$HOME\.apothem\src\apothem\conformity\gate.py`, या cmd में
`%USERPROFILE%\.apothem\src\apothem\conformity\gate.py`। स्क्रिप्ट से शुरू करने
पर वर्तमान फ़ोल्डर Python के मॉड्यूल खोज पथ की पहली प्रविष्टि में नहीं आता; `-E`
`PYTHONPATH` को भी बाहर रखता है, जहाँ कोई खाली या सापेक्ष प्रविष्टि भी वर्तमान
फ़ोल्डर को ही नामित करती है, और `-s` आपके उपयोगकर्ता site-packages को बाहर रखता
है। यह प्रोजेक्ट की फ़ाइलों को केवल गेट के अपने Python कोड से बाहर रखता है; गेट
जो `git` चलाता है, उसकी बात आगे है।

तीन स्टैंडअलोन वैलिडेटर उस प्रोजेक्ट में `git` चलाते हैं जिसकी वे जाँच करते हैं,
और यही `--all` भी करता है, जो उन्हें चलाता है, और `--all-perwrite` भी, जो ट्रैक
की गई फ़ाइलों को `git ls-files` से सूचीबद्ध करता है:

```text
agents-md-coverage-grep
conventional-commit-grep
no-global-plans-grep
```

उस रिपॉज़िटरी की अपनी सेटिंग, `.git/config` में, उन फ़ाइलों में जिन्हें वह शामिल
करती है और `.git/config.worktree` में, git के केवल पढ़ते समय भी उसे शुरू करने के
लिए कोई प्रोग्राम नामित कर सकती हैं। गेट ऐसी हर ज्ञात सेटिंग को git की कमांड
लाइन पर दिए गए विकल्पों से बंद कर देता है, जो git द्वारा पढ़ी जाने वाली हर फ़ाइल
पर भारी पड़ते हैं और उस git तक भी पहुँचते हैं जिसे git किसी सबमॉड्यूल में शुरू
करता है:

- कोई फ़ाइल-सिस्टम मॉनिटर नहीं (`core.fsmonitor`);
- कोई हस्ताक्षर प्रोग्राम नहीं (`gpg.program`, `gpg.ssh.program` और
  `gpg.x509.program` ऐसे पथ की ओर इशारा करते हैं जहाँ कुछ भी मौजूद नहीं हो सकता,
  और `log.showSignature` बंद है);
- कोई हुक नहीं, कोई पेजर नहीं, और कोई स्वचालित रखरखाव नहीं;
- कोई बाहरी diff या टेक्स्ट-रूपांतरण प्रोग्राम नहीं, और सबमॉड्यूल के बदलाव केवल
  कमिट id के रूप में दिखाए जाते हैं, इसलिए git किसी सबमॉड्यूल के भीतर दूसरा git
  शुरू नहीं करता;
- फ़ाइलों की सामग्री `git cat-file blob` से पढ़ी जाती है, जो सबमॉड्यूल प्रविष्टि
  को अस्वीकार कर देता है, जहाँ `git show` उसे एक कमिट के रूप में दिखा देता।

तीन सेटिंग git के पढ़ने के लिए किसी प्रोग्राम का नहीं, एक फ़ाइल का नाम देती हैं,
और वह फ़ाइल किसी नेटवर्क पथ पर हो सकती है। गेट की कमांड लाइन git को इन्हें भी
पढ़ने से रोकती है: diff क्रम फ़ाइल (`diff.orderFile`), excludes फ़ाइल
(`core.excludesFile`) और mailmap फ़ाइल।

यह `GIT_NO_LAZY_FETCH=1` और एक खाली `GIT_ALLOW_PROTOCOL` भी सेट करता है, ताकि git
किसी आंशिक क्लोन का लुप्त ऑब्जेक्ट कभी उस पते से न लाए जिसे रिपॉज़िटरी नामित करती
है। गेट git को केवल आपके `PATH` की किसी पूर्ण-पथ प्रविष्टि से शुरू करता है। वह
git को कभी वर्तमान फ़ोल्डर से नहीं लेता: वह खाली और सापेक्ष `PATH` प्रविष्टियों
को छोड़ देता है, जो उसी फ़ोल्डर को नामित करती हैं, और वहाँ पहले नहीं देखता, जैसा
Windows किसी बिना पथ वाले प्रोग्राम नाम के लिए करता है। git जिन प्रोग्रामों को
नाम से शुरू करता है, उनके लिए उसे केवल वही पूर्ण-पथ प्रविष्टियाँ मिलती हैं।

इसलिए आप ये कमांड किसी ऐसे प्रोजेक्ट पर चला सकते हैं जो अपने `.git` फ़ोल्डर के
साथ किसी और से, किसी आर्काइव या साझा फ़ोल्डर में, आया हो: ऊपर की कोई भी सेटिंग
गेट से कोई प्रोग्राम शुरू नहीं करवा सकती। दो सीमाएँ बची रहती हैं। रिपॉज़िटरी अब
भी git से कहीं और का कोई पथ पढ़वा सकती है, किसी भी ऐसी सेटिंग या फ़ाइल के ज़रिए
जो कोई पथ नामित करती है, उदाहरण के लिए `include.path` या `includeIf`,
`core.worktree`, किसी `.git` फ़ाइल की `gitdir:` पंक्ति, या
`.git/objects/info/alternates`; Windows पर, वहाँ दिया गया कोई नेटवर्क पथ
(`\\server\share`) Windows को उस सर्वर से जोड़ता है और आपको साइन इन करवाता है।
एक मामला इससे सीमित है: Git for Windows 2.55 किसी `gitdir:` पंक्ति में नेटवर्क पथ
को जुड़ने से पहले ही अस्वीकार कर देता है, जब तक आपकी अपनी `safe.directory` सेटिंग
उस पथ की अनुमति न दे। और यह सूची आज ज्ञात सेटिंग को ही कवर करती है; git की कोई
बाद की रिलीज़ कोई नई सेटिंग जोड़ सकती है। आपकी अपनी वैश्विक और सिस्टम git सेटिंग
अब भी लागू होती हैं, सिवाय ऊपर वाली सेटिंग के, जिन्हें गेट की कमांड लाइन ओवरराइड
करती है। यह केवल git को कवर करता है: `python -m` Python मॉड्यूल सबसे पहले वर्तमान
फ़ोल्डर से पढ़ता है, इसलिए गेट को किसी भरोसेमंद फ़ोल्डर से शुरू करें।

निकास कोड: `0` स्वच्छ (या परामर्शी), `2` सख़्त मोड में निष्कर्ष-अवरोध, `3` एक
उपयोग त्रुटि: कोई अज्ञात फ़्लैग या वैलिडेटर नाम, कोई ऐसी फ़ाइल जो मौजूद नहीं है,
या कोई ऐसी रूट डायरेक्टरी जो मौजूद नहीं है। `--help` पूरा उपयोग विवरण प्रिंट
करता है और `0` के साथ बाहर निकलता है। हर स्टैंडअलोन वैलिडेटर वही `--help`
स्वीकार करता है और किसी अज्ञात फ़्लैग या लुप्त रूट पर `3` के साथ बाहर निकलता है।

`.` जैसा कोई सापेक्ष रूट किसी भी वैलिडेटर के चलने से पहले एक निरपेक्ष पथ में हल
किया जाता है, इसलिए `--all .` और `--all "$PWD"` एक ही वृक्ष का निरीक्षण करते
हैं। प्रत्येक वैलिडेटर `inspected` रिपोर्ट करता है — उसने कितने टारगेट की जाँच
की — और `--all` उस गिनती को हर परिणाम प्रविष्टि में कॉपी करता है। जिस वैलिडेटर
ने कुछ भी निरीक्षण नहीं किया, वह `passed: false` रिपोर्ट करता है, ताकि कोई गलत
वर्किंग डायरेक्टरी चुपचाप पास न हो सके। दो प्लान-सूट वैलिडेटर एक अपवाद हैं:
प्लान सूट gitignore किए गए `.apothem/plans/` वृक्ष में रहते हैं, इसलिए वे एक
स्वच्छ चेकआउट पर `empty_scope_expected: true` रिपोर्ट करते हैं और फिर भी पास
होते हैं। वर्कफ़्लो वैलिडेटर भी यही करते हैं जब प्रोजेक्ट में अभी तक कोई
`.github/workflows/` डायरेक्टरी नहीं होती, और कमिट-सब्जेक्ट वैलिडेटर तब करता है
जब रूट में कोई कमिट इतिहास नहीं होता।

किसी प्रोजेक्ट में किसी और की बनाई फ़ाइलें आ सकती हैं, किसी आर्काइव या साझा
फ़ोल्डर में, इसलिए हर `--all` वैलिडेटर केवल वही सामान्य फ़ाइलें और असली फ़ोल्डर
खोलता और सूचीबद्ध करता है जिन तक वह रूट के नीचे असली फ़ोल्डरों के रास्ते
पहुँचता है। वह कभी किसी सिम्बॉलिक लिंक का, या Windows पर किसी जंक्शन का, पीछा
नहीं करता, और रूट के नीचे किसी भी स्तर पर इनमें से हर एक को अनुपस्थित मानता है:

- लिंक, वह भी जो रूट के भीतर इशारा करता है। कोई वॉक या फ़ोल्डर सूची उसे छोड़
  देती है, इसलिए उसका लक्ष्य केवल वहीं जाँचा जाता है जहाँ वैलिडेटर उसके अपने
  पथ से उस तक पहुँचता है;
- नेम्ड पाइप, डिवाइस या सॉकेट, जहाँ पढ़ना रुका रहेगा या कभी खत्म नहीं होगा;
- Windows पर, बिंदु या स्पेस पर खत्म होने वाला नाम, क्योंकि Windows उस नाम से
  कोई दूसरी प्रविष्टि खोल देगा।

कुछ जाँचें अब भी किसी लिंक के भीतर गए बिना उसका उपयोग करती हैं:

- किसी ऐसी स्थिर फ़ाइल के लिए जो सिम्बॉलिक लिंक है, जैसे किसी दूसरी फ़ाइल की ओर
  इशारा करने वाली `CLAUDE.md`, गेट लिंक का अपना पाठ पढ़ता है और उसमें नामित
  फ़ाइल को केवल तभी खोलता है जब वह प्रोजेक्ट के भीतर, असली फ़ोल्डरों के रास्ते
  पहुँची जाने वाली सामान्य फ़ाइल हो। प्रति-फ़ोल्डर `README.md` लिंक भी इसी तरह
  गिना जाता है। एक निरपेक्ष लिंक तब गिना जाता है जब वह प्रोजेक्ट फ़ोल्डर के उसी
  रूप से लिखा गया हो जिसमें वह हल होता है, या Windows पर अक्षरों के दूसरे
  छोटे-बड़े रूप वाले उसी पथ से; अकेले चलाया गया वैलिडेटर फ़ोल्डर को उसी रूप में
  भी स्वीकार करता है जैसा आपने टाइप किया, जब तक उस पथ में `..` न हो, जबकि गेट
  हर वैलिडेटर शुरू करने से पहले फ़ोल्डर को हल कर लेता है। लिंक की गई
  `.gitattributes` अब भी अनुपस्थित गिनी जाती है, क्योंकि git उसे नहीं पढ़ता;
- `no-global-plans-grep` में भटके प्लान की जाँच किसी ऐसे प्लान फ़ोल्डर या
  `.apothem` फ़ोल्डर की, जो लिंक है, उसके नाम से रिपोर्ट करती है, लिंक चाहे जहाँ
  ले जाए;
- `no-toplevel-docs-grep` रूट पर `docs` लिंक की उसके नाम से रिपोर्ट करता है;
- `naming-grep` किसी लिंक के अपने नाम की जाँच करता है।

हर वैलिडेटर की रिपोर्ट उन लिंक और विशेष फ़ाइलों को `skipped_links` के अंतर्गत
सूचीबद्ध करती है जिन्हें उसने छोड़ा, ताकि कोई लिंक कभी बिना निशान छोड़े किसी
फ़ाइल को न छिपाए। वहाँ वह फ़ोल्डर भी सूचीबद्ध होता है जिसे वह सूचीबद्ध नहीं कर
सका (कोई पहुँच नहीं, बहुत लंबा पथ, पढ़ने की त्रुटि), और उस फ़ोल्डर की `.git`
प्रविष्टि भी जिसे उसने नेस्टेड चेकआउट मानकर छोड़ा, जब वह प्रविष्टि लिंक या विशेष
फ़ाइल हो; वह फ़ोल्डर स्वयं `skipped_checkouts` के अंतर्गत सूचीबद्ध होता है, जिसका
वर्णन नीचे है। जो वैलिडेटर अपने फ़ोल्डर के न होने पर पास होता है, जैसे वर्कफ़्लो
वैलिडेटर, वह उस फ़ोल्डर के लिंक होने पर पास नहीं होता: फ़ाइलें उसके पीछे हो सकती
हैं, इसलिए रन उस रन की तरह विफल होता है जिसने कुछ नहीं जाँचा। हार्ड लिंक एक
सामान्य फ़ाइल है और उसी तरह पढ़ी जाती है। `--all` वैलिडेटर और `--all-perwrite`
हर स्तर तक पहुँचने पर उसे देखते हैं, फिर फ़ाइल को रूट से एक-एक स्तर करके खोलते
हैं, हर फ़ोल्डर को उससे पहले खोले गए फ़ोल्डर के भीतर, कभी किसी लिंक के ज़रिए
नहीं। इसलिए जब प्रोजेक्ट में लिख सकने वाला कोई व्यक्ति गेट चलते समय किसी जाँची
जा चुकी फ़ाइल, या उसके ऊपर के किसी फ़ोल्डर, को लिंक या नामित पाइप से बदल देता
है, तो गेट उस लिंक के ज़रिए नहीं पढ़ता और पाइप पर प्रतीक्षा नहीं करता: फ़ाइल
पढ़ी नहीं जाती। `--all` वैलिडेटर उसे अनुपस्थित या अपठनीय गिनता है, जैसे वह किसी
लिंक को गिनता है, और बदली गई प्रविष्टि को `skipped_links` के अंतर्गत सूचीबद्ध
करता है; `--all-perwrite` उसे `link` गिनता है, या दोबारा बदले जाने पर
`unreadable`, जैसा नीचे बताया गया है। Windows पर एक प्रतीक्षा बची रहती है, जैसी
सामान्य रूप से खोलने में भी थी: प्रोजेक्ट में लिख सकने वाला कोई प्रोग्राम किसी
फ़ाइल पर अवसरवादी लॉक (oplock) रख सकता है और गेट के उसे खोलने पर भी उसे नहीं
छोड़ता। फ़ाइल को खोलने का कोई भी तरीका इस प्रतीक्षा से नहीं बचता, इसलिए `--all`
वैलिडेटर अपनी 10 मिनट की सीमा तक प्रतीक्षा करता है, और `--all-perwrite`, जिसकी
ऐसी कोई सीमा नहीं है, तब तक जब तक वह प्रोग्राम फ़ाइल को छोड़ न दे। `--all` और
`--all-perwrite` में गेट स्वयं केवल रूट के भीतर की सामान्य फ़ाइलें खोलता है,
रास्ते के हर फ़ोल्डर को `lstat` से जाँचता है, जिसमें git द्वारा सूचीबद्ध हर पथ
शामिल है, और कभी किसी `.git` प्रविष्टि के भीतर नहीं पढ़ता। git चलाने से पहले,
git चलाने वाले तीन `--all` वैलिडेटर, और दोनों `--staged` जाँचें, उस क्षण वृक्ष
जैसा है उसी रूप में, रूट की और उसके ऊपर के हर उस फ़ोल्डर की `.git` प्रविष्टि को
`lstat` से देखते हैं जिसमें git खोजता है; यदि उनमें से कोई लिंक है, या देखी नहीं
जा सकती, तो वे git नहीं चलाते। इससे वे प्रोजेक्ट भी अस्वीकार हो जाते हैं जिन्हें
git सुरक्षित रूप से संभाल लेता, जैसे किसी ऐसे होम फ़ोल्डर के नीचे का हर
प्रोजेक्ट जिसका `.git` लिंक है, अपनी रिपॉज़िटरी वाला प्रोजेक्ट भी: यह एक सरल
नियम की जानबूझकर चुकाई गई कीमत है। तीन `--all` वैलिडेटर git को `GIT_DIR` और उन
दूसरे वेरिएबल के बिना चलाते हैं जो रिपॉज़िटरी, उसके स्टोर या उसके इंडेक्स का नाम
बताते हैं; `--staged` जाँचें किसी हुक का `GIT_DIR` बनाए रखती हैं। इसके बाद git
कौन-सी रिपॉज़िटरी पढ़ता है, यह नहीं जाँचा जाता: कोई `gitdir:` पंक्ति,
`commondir`, alternates, `core.worktree`, कोई include, या git फ़ोल्डर के भीतर का
कोई लिंक किसी दूसरी रिपॉज़िटरी का नाम दे सकता है, और git उनका पालन करता है,
इसलिए git किसी नेटवर्क पथ तक पहुँच सकता है या अपनी समय-सीमा तक प्रतीक्षा कर सकता
है। गेट git के आउटपुट का उपयोग केवल नामों, मोड, स्थिति अक्षरों, अंतिम कमिट के
विषय, कमिट समय और कुछ सेटिंग के रूप में करता है, और git द्वारा छापे गए किसी पथ
को रूट के भीतर हर स्तर जाँचे बिना कभी नहीं खोलता। लिंक मिलने पर, तीनों `--all`
वैलिडेटर में से हर एक उसे `skipped_links` के अंतर्गत सूचीबद्ध करता है (रूट के
भीतर हो तो रूट के सापेक्ष, ऊपर हो तो उसके पूरे पथ से)। तब
`conventional-commit-grep` चेकआउट के बाहर की तरह `not-a-git-repo` रिपोर्ट करता
है, पर पास नहीं होता: वह लिंक का नाम बताने वाला `check_error` देता है।
`no-global-plans-grep` लिंक को एक फ़ाइंडिंग के रूप में रिपोर्ट करता है और विफल
होता है, और साथी फ़ाइलों की जाँच अपना ताज़गी परीक्षण छोड़ देती है, जैसा वह
इतिहास न होने पर करती है। `--all-perwrite` भी ट्रैक की गई फ़ाइलें सूचीबद्ध नहीं
करता: वह लिंक का नाम बताने वाले `check_error` के साथ विफल होता है, और दोनों
`--staged` जाँचें भी, जो किसी लिंक का नाम केवल `check_error` में बताती हैं, या
वहाँ बताती हैं कि जिस फ़ोल्डर में वे चलती हैं उसकी `.git` प्रविष्टि एक लिंक है:
वे किसी हुक के `GIT_DIR` द्वारा नामित रिपॉज़िटरी पढ़ती हैं, फिर भी उस फ़ोल्डर से
शुरू होने वाले खोज पथ पर किसी लिंक को अस्वीकार करती हैं जिसमें वे चलती हैं। जिस
`.git` प्रविष्टि को गेट देख नहीं सकता (बहुत लंबा पथ, पहुँच से बाहर शेयर, कोई
पहुँच नहीं), वह लिंक नहीं है और `skipped_links` के अंतर्गत सूचीबद्ध नहीं होती:
`conventional-commit-grep` स्थिति `git-failed` और एक `check_error` के साथ विफल
होता है; साथी फ़ाइलों की जाँच, `--all-perwrite` और दोनों `--staged` जाँचें ऐसे
`check_error` के साथ विफल होती हैं जो बताता है कि प्रविष्टि देखी नहीं जा सकी, और
`no-global-plans-grep` उसे एक फ़ाइंडिंग के रूप में रिपोर्ट करता है।

हर स्टैंडअलोन वैलिडेटर अपने आप में एक अलग प्रोग्राम के रूप में चलता है, और गेट
उसे `--all` में और `--check` में 10 मिनट देता है। सबसे धीमा वैलिडेटर Apothem की
अपनी रिपॉज़िटरी पर लगभग एक मिनट लेता है। सीमा पर भी चल रहा वैलिडेटर रोक दिया
जाता है, उसके शुरू किए गए हर प्रोग्राम के साथ, जैसे अब भी प्रतीक्षा कर रही कोई
`git` कमांड, और `passed: false` तथा ऐसे `check_error` के साथ रिपोर्ट किया जाता
है जो बताता है कि वह पूरा नहीं हुआ। Linux और macOS पर हर वैलिडेटर अपने अलग सेशन
में चलता है, और गेट को मिला `SIGTERM` या `SIGHUP`, जैसे `timeout` से या बंद किए
गए टर्मिनल से, गेट के 128 और सिग्नल की संख्या के जोड़ वाले कोड के साथ बाहर निकलने
से पहले वैलिडेटर के प्रोग्रामों को रोक देता है। यह उस सिग्नल पर भी लागू होता है जो
तब आता है जब गेट कोई वैलिडेटर शुरू या बंद कर रहा हो: वह उस चरण के पूरा होने तक
प्रतीक्षा करता है, और निकास कोड 128 और उसकी संख्या का जोड़ ही रहता है, भले ही उस
चरण के दौरान बाद में Ctrl+C आए। `SIGKILL`, जिसे कोई प्रोग्राम पकड़ नहीं सकता,
वहाँ केवल गेट को समाप्त करता है: उसका शुरू किया गया वैलिडेटर पूरा होने तक चलता
रहता है, और जिस `git` कमांड पर वह वैलिडेटर प्रतीक्षा कर रहा है, वह फिर भी अपनी
सीमा पर रुक जाती है। Windows पर हर वैलिडेटर एक जॉब ऑब्जेक्ट में चलता है, जो गेट
के स्वयं समाप्त होने पर उसके प्रोग्रामों को भी समाप्त कर देता है।
वहाँ गेट द्वारा शुरू किया गया हर प्रोग्राम निलंबित अवस्था में तब तक प्रतीक्षा
करता है जब तक वह जॉब ऑब्जेक्ट में न आ जाए। जिस प्रोग्राम को वह फिर से चालू
(resume) नहीं कर सकता, उसे रोक दिया जाता है, और त्रुटि बताती है कि वह जॉब ऑब्जेक्ट
में है या नहीं। जिस प्रोग्राम को चालू किए जाने से पहले किसी और ने समाप्त होने को
कहा, वह कभी चला ही नहीं, और उसी तरह विफल होता है, उसका निकास कोड चाहे जो हो, दो
अपवादों के साथ। निकास कोड 259 के साथ समाप्त हुआ प्रोग्राम, यही कोड Windows किसी
चल रहे प्रोग्राम को भी देता है, तब तक चलता हुआ पढ़ा जाता है जब तक Windows उसे
समाप्त कर ही रहा हो। चालू किए जाने से ठीक पहले समाप्त हुआ प्रोग्राम तभी पकड़ा
जाता है जब गेट चालू करने के 1 ms के भीतर उसका निकास कोड पढ़ ले; बाद में पढ़ने पर,
उदाहरण के लिए किसी व्यस्त मशीन पर या जब कॉल करने वाली प्रोसेस के दूसरे थ्रेड
व्यस्त हों, उसका निकास कोड प्रोग्राम का अपना माना जाता है। जिस मशीन पर इसे मापा
गया, उस पर Windows जो सबसे छोटा प्रोग्राम चला सकता है, वह चालू किए जाने के बाद
कम से कम 3 ms जीवित रहा, और `git` 27 ms, इसलिए चला हुआ प्रोग्राम समाप्त किया गया
प्रोग्राम नहीं समझा जाता। चालू किए जाने के ठीक बाद समाप्त हुए प्रोग्राम को भी चले
हुए प्रोग्राम से अलग नहीं पहचाना जा सकता। हर प्लेटफ़ॉर्म पर, गेट के अपने रन में,
शुरू करते समय आया Ctrl+C तब तक प्रतीक्षा करता है जब तक प्रोग्राम चल न जाए (Windows
पर, तब तक जब तक गेट उसे चालू करने का प्रयास न कर ले), इसलिए कोई प्रोग्राम निलंबित
या अपनी सीमा के बाद भी चलता हुआ नहीं छूटता। गेट के किसी प्रोग्राम को रोकते समय
आया दूसरा Ctrl+C रोकने के पूरा होने तक प्रतीक्षा करता है। रोकना शुरू होने से ठीक
पहले आया Ctrl+C गेट से रोकने का प्रयास फिर से करवाता है, अधिकतम तीन बार। जब वे
प्रयास विफल होते हैं, या उनमें से दो के बीच कोई Ctrl+C आता है, तो गेट सिग्नलों को
रोके बिना प्रोग्राम को रोकता है, फिर से अधिकतम तीन बार, ताकि एक और Ctrl+C रोकने को
छोड़ न दे। प्रोग्राम को चलता हुआ छोड़ने के लिए कई बार Ctrl+C दबाना पड़ता है, हर बार
इन बिंदुओं में से किसी एक के माइक्रोसेकंड के भीतर। रोकने के बाद गेट रुके हुए
प्रोग्राम के समाप्त होने के लिए आधे सेकंड तक प्रतीक्षा करता है, ताकि Linux और
macOS पर वह एक निष्क्रिय (defunct) प्रोसेस के रूप में न बचा रहे, और उस प्रतीक्षा
के दौरान आया Ctrl+C पहले से चल रहे समापन की जगह नहीं लेता। कॉल करने वाली प्रोसेस
द्वारा किसी दूसरे सिग्नल के लिए सेट किया गया हैंडलर अब भी प्रोग्राम को चलता हुआ
(Windows पर, निलंबित) छोड़ सकता है, जब उसकी त्रुटि प्रोग्राम शुरू होने के बाद के
कुछ माइक्रोसेकंड में, गेट के उसे दर्ज करने से पहले, आती है। जब गेट
अपने सिग्नल हैंडलर बदलता है, तो बदलाव के बीच आया सिग्नल किसी हैंडलर को बदला हुआ
नहीं छोड़ता। Linux और macOS पर गेट बदलाव में लगने वाले कुछ माइक्रोसेकंड के लिए
Ctrl+C, `SIGTERM` और `SIGHUP` को रोकता है, और किसी दूसरे सिग्नल को नहीं, ताकि ऐसा
सिग्नल बदलाव पूरा होने तक प्रतीक्षा करे और तब लागू हैंडलरों से मिले। फिर गेट केवल
उन्हीं सिग्नलों को खोलता है जिन्हें उसने रोका था। किसी भी दूसरे सिग्नल के लिए,
Windows पर, और रोक से ठीक पहले आए सिग्नल के लिए, सिग्नल द्वारा रोका गया बदलाव फिर
से किया जाता है, अधिकतम तीन बार। जब अपने हैंडलर वापस लगाना हर प्रयास में विफल
होता है, तो गेट बचे हुए हर हैंडलर के लिए एक अंतिम प्रयास करता है। हैंडलर तब बदला
हुआ रह जाता है जब कोई त्रुटि उस अंतिम प्रयास को भी रोक दे, जैसे कॉल करने वाली
प्रोसेस द्वारा सेट किए गए हर बार चलने वाले टाइमर से आया `TimeoutError`, और दुर्लभ
मामलों में तब जब ऐसे कई सिग्नल, जिनके हैंडलर त्रुटि उठाते हैं, माइक्रोसेकंड के
भीतर एक के बाद एक आते हैं और अंतिम प्रयास को छोड़ देते हैं। हर प्रयास में लौटने
वाली त्रुटि, जैसे Python की रिकर्शन सीमा के पास `RecursionError`, बदलाव को दो
प्रयासों के भीतर समाप्त कर देती है और आगे बढ़ जाती है। गेट अपने हैंडलर उन कॉल से
अधिक गहरी नहीं कॉल से वापस लगाता है जिनसे उन्हें बदला गया था, इसलिए उस सीमा के
पास वह Ctrl+C को अनदेखा नहीं छोड़ता। कॉल करने वाली प्रोसेस द्वारा रन के दौरान सेट
किया गया `SIGTERM` हैंडलर अपनी जगह बना रहता है। Linux और macOS पर, किसी Python
सबइंटरप्रेटर में, जहाँ कोई सिग्नल हैंडलर सेट नहीं किया जा सकता, गेट हैंडलर बदले
बिना अपने प्रोग्राम चलाता है; Windows पर, Python किसी पृथक सबइंटरप्रेटर से किसी
प्रोग्राम का आउटपुट नहीं पढ़ सकता, क्योंकि वह कोई daemon थ्रेड नहीं चलने देता।
Ctrl+C एक पंक्ति प्रिंट करता है और `130` के साथ बाहर निकलता है। सीमाएँ जुड़ती हैं:
जिस रन में कई वैलिडेटर प्रतीक्षा करते हैं, वह उनकी सीमाओं का योग लेता है।

पाँच वैलिडेटर अपने द्वारा चलाई गई हर `git` कमांड को उसकी अपनी समय-सीमा भी देते
हैं। ये सीमाएँ हर प्लेटफ़ॉर्म पर लागू होती हैं, Windows पर भी, जब `PATH` पर
मौजूद `git` वह लॉन्चर हो जिसे Git for Windows इंस्टॉल करता है और जो असली git
शुरू करता है:

```text
conventional-commit-grep            git log -1, git rev-parse           1 minute
                                    git ls-files, git config            1 minute
agents-md-coverage-grep             git rev-parse, git config           1 minute
                                    git log over the whole history      5 minutes
no-global-plans-grep                git ls-files                        1 minute
production-ready-pr-grep --staged   git diff --cached                   1 minute
semver-stability-grep --staged      git diff --cached, git cat-file     1 minute
```

ये कमांड ज़्यादातर प्रोजेक्ट पर एक सेकंड का अंश लेती हैं, इसलिए सीमा तभी आती है
जब `git` किसी ऐसी चीज़ की प्रतीक्षा करता है जो कभी नहीं आती। किसी प्रोजेक्ट की
अपनी git सेटिंग उसे हमेशा के लिए प्रतीक्षा करवा सकती हैं, उदाहरण के लिए उसकी
`.git/config` में कोई `include.path` जो किसी नामित पाइप का नाम देता है। अपनी सीमा
से अधिक चलने वाली `git` कमांड पास नहीं होती: वैलिडेटर `passed: false` के साथ ऐसा
`check_error` रिपोर्ट करता है जो उस कमांड का नाम बताता है। न ही वह `git` पास होता
है जो मिले हुए किसी चेकआउट को अस्वीकार कर देता है, उदाहरण के लिए वह जिसका स्वामी
कोई दूसरा उपयोगकर्ता है या वह जिसकी `.git/config` में कोई ख़राब पंक्ति है; तब
`check_error` git का निकास कोड देता है, और निकास कोड 128 वह है जिसका उपयोग git तब
करता है जब वह कोई रिपॉज़िटरी खोल या पढ़ नहीं पाता। जिस फ़ोल्डर की `.git` प्रविष्टि
git नहीं खोल सकता, वह भी ऐसा ही चेकआउट गिना जाता है, क्योंकि जाँचों को जिस इतिहास
की ज़रूरत है वह वहाँ बिना पढ़ा पड़ा हो सकता है: किसी भी दूसरे चेकआउट के बाहर एक
खाली `.git` फ़ोल्डर, या ऐसी `.git` फ़ाइल जो किसी ऐसे फ़ोल्डर का नाम देती है जो अब
मौजूद नहीं है, जैसा कोई अनपैक किया गया वर्कट्री या कॉपी किया गया सबमॉड्यूल पीछे
छोड़ता है। वह प्रविष्टि हटाएँ, या गेट को पूरे चेकआउट पर चलाएँ। यह पुरानी साथी
फ़ाइलों की जाँच पर भी लागू होता है, हालाँकि उसकी फ़ाइंडिंग अन्यथा परामर्शी होती
हैं, और तब कमिट-सब्जेक्ट जाँच भी `empty_scope_expected: false` के साथ
`inspected: 0` रिपोर्ट करती है। Windows पर, वह `git` जिसे गेट ने शुरू किया पर फिर
से चालू नहीं कर सका, वह भी विफल `git` है: `check_error` निकास कोड 128 देता है, और
उसे कभी लुप्त `git` नहीं गिना जाता। पुरानी साथी फ़ाइलों की जाँच पूरा इतिहास एक बार
पढ़ती है, और उस पठन को 5 मिनट मिलते हैं, इसलिए बड़ा इतिहास विफलता के बजाय धीमा
होता है; जिस इतिहास को पढ़ने में इससे अधिक समय लगे, वह जाँच को विफल करता है। ऐसा
सादा फ़ोल्डर जो किसी git चेकआउट के भीतर नहीं है, ऐसी रिपॉज़िटरी जिसमें अभी कोई
कमिट नहीं है, या बिना `git` वाली मशीन अब भी पहले की तरह इन जाँचों में पास होती
है। आंशिक क्लोन भी, जो `git clone --filter` से बनाया गया हो: गेट `git` को वह नहीं
लाने देता जो क्लोन ने छोड़ दिया, और git ऐसा कोई उत्तर नहीं देता जो क्लोन द्वारा
छोड़े गए ऑब्जेक्ट को खोए हुए ऑब्जेक्ट से अलग बताए। इसलिए आंशिक क्लोन में पुरानी
साथी फ़ाइलों की जाँच इतिहास के किसी भी विफल पठन को अनुपलब्ध इतिहास गिनती है: वह
अपना ताज़गी परीक्षण छोड़ देती है और पास होती है, जैसा वह इतिहास न होने पर करती है।
ये छूट, और git द्वारा अस्वीकार किए गए चेकआउट के लिए `check_error`, बाकी चार
वैलिडेटर के लिए हैं: `no-global-plans-grep` को ऐसा चेकआउट चाहिए जिसे git पढ़ सके,
इसलिए उसके बाहर, बिना `git` वाली मशीन पर, या git द्वारा अस्वीकार किए गए चेकआउट में
वह पहले की तरह विफल होता है, मानक त्रुटि पर कारण के साथ: git का निकास कोड, git का
अपना पाठ नहीं। पास न होने वाले किसी भी परिणाम की तरह, परामर्शी डिफ़ॉल्ट उसे रिपोर्ट
करता है और `0` के साथ बाहर निकलता है, और `--strict` `2` के साथ बाहर निकलता है।

दोनों `--staged` जाँचों के लिए, किसी diff सेटिंग का ऐसा मान जिसे git पढ़ नहीं
सकता, जैसे `diff.renameLimit = abc`, ऐसी ही एक ख़राब पंक्ति है: `git diff` विफल
होता है, और जो बदलाव-समूह पढ़ा नहीं गया वह खाली बदलाव-समूह नहीं है। ये दोनों जाँचें,
कमिट-सब्जेक्ट जाँच और पुरानी साथी फ़ाइलों की जाँच चेकआउट को उस फ़ोल्डर में खोजती
हैं जिसमें वे चलती हैं और उसके ऊपर के फ़ोल्डरों में, इसलिए चेकआउट के किसी
सबफ़ोल्डर में भी यही लागू होता है। वे वहाँ खोजना बंद करती हैं जहाँ git बंद करता
है: `GIT_CEILING_DIRECTORIES` में नामित फ़ोल्डर पर और, Windows के बाहर, किसी दूसरे
फ़ाइल सिस्टम के फ़ोल्डर पर, जब तक `GIT_DISCOVERY_ACROSS_FILESYSTEM` सेट न हो।
इसलिए बिना अपनी रिपॉज़िटरी वाला फ़ोल्डर, जो किसी रिपॉज़िटरी के नीचे माउंट किया
गया हो, अब भी पास होता है। चेकआउट के किसी सबफ़ोल्डर पर चलाई गई कमिट-सब्जेक्ट
जाँच चेकआउट के सबसे नए कमिट की जाँच करती है जब चेकआउट उस सबफ़ोल्डर में कोई फ़ाइल
ट्रैक करता है, या वहाँ कोई फ़ाइल स्टेज की गई हो। जहाँ चेकआउट अक्षरों के छोटे-बड़े
रूप को अनदेखा करता है, जैसे Windows और macOS पर, यह उस सबफ़ोल्डर पर भी लागू होता
है जिसका नाम डिस्क पर केवल छोटे या बड़े अक्षरों में बदला गया हो। जिस फ़ोल्डर को
चेकआउट ट्रैक नहीं करता, अनट्रैक्ड या अनदेखा किया गया, उसका अपना कोई इतिहास नहीं
होता और वह पास होता है, जैसे किसी होम-फ़ोल्डर dotfiles रिपॉज़िटरी के भीतर कोई नया
प्रोजेक्ट। जिस फ़ोल्डर में जाँच चलती है उसके ऊपर का खाली `.git` फ़ोल्डर, जिसके
और ऊपर कोई रिपॉज़िटरी न हो, git को विफल करता है, और जाँच `git-failed` रिपोर्ट
करती है।

दोनों `--staged` जाँचें स्टेज किए गए नाम वर्क ट्री के शीर्ष से पढ़ती हैं, आपकी
अपनी `diff.relative` सेटिंग चाहे जो हो, इसलिए किसी सबफ़ोल्डर की सेटिंग कभी किसी
स्टेज की गई फ़ाइल को नहीं छिपाती।

`semver-stability-grep --staged` पैकेज को उस फ़ोल्डर में खोजता है जिसमें वह चलता
है और फिर उसके ऊपर के फ़ोल्डरों में, रिपॉज़िटरी रखने वाले निकटतम फ़ोल्डर तक या
वहाँ तक जहाँ git खोजना बंद करता है, और git को उस फ़ोल्डर में चलाता है जिसमें पैकेज
है, इसलिए किसी सबफ़ोल्डर से चलाया गया रन वही बदलाव-समूह जाँचता है। वह संस्करण
फ़ाइल भी उसी फ़ोल्डर से पढ़ता है, इसलिए रिपॉज़िटरी के शीर्ष के नीचे का पैकेज भी
जाँचा जाता है। जब git द्वारा अस्वीकार की गई कोई `.git` फ़ाइल उस फ़ोल्डर, जिसमें वह
चलता है, और पैकेज के बीच हो, तो git उसकी जगह उसी फ़ोल्डर में चलता है जिसमें जाँच
चलती है, उस फ़ाइल पर रुक जाता है, और जाँच `check_error` रिपोर्ट करती है। git ऐसी
`.git` फ़ाइल को अस्वीकार करता है जो किसी रिपॉज़िटरी का नाम नहीं देती, जो 1 MiB से
बड़ी है, या जिसमें `gitdir:`, एक स्पेस और एक पथ न हो, जिसके बाद केवल पंक्ति-अंत
हों। Windows पर जाँच ऐसी `.git` फ़ाइल को भी अस्वीकार करती है जो कोई नेटवर्क,
डिवाइस या NT पथ (`\\host\share`, `\\?\`, `\??\`) नामित करती है, और उस पथ को स्वयं
नहीं खोजती। वह ऐसा पथ भी अस्वीकार करती है जिसे Git for Windows अस्वीकार करता है:
ऐसा नाम जो बिंदु या स्पेस पर खत्म होता है या कोई डिवाइस नाम है, जैसे `aux.d`,
`lpt0` या `CONIN$` (पर `com0` नहीं, जिसे Git for Windows स्वीकार करता है), या
ड्राइव के बाद कोई `:`। वह पथ के ऐसे बाइट को, जो UTF-8 नहीं है, वैसे ही पढ़ती है
जैसे Git for Windows: `0xA0` और उससे ऊपर उस अक्षर के रूप में और उससे नीचे दो हेक्स
अंकों के रूप में, इसलिए `0x9F` `9f` पढ़ा जाता है। `src/apothem/__init__.py` रखने
वाला निकटतम फ़ोल्डर ही जाँचा जाता है; वह `GIT_WORK_TREE` नहीं पढ़ती। बिना पैकेज
वाले प्रोजेक्ट में वहाँ जाँचने को कुछ नहीं है: वह git चलाए बिना पास होता है, उसकी
रिपॉज़िटरी चाहे जिस स्थिति में हो।

गेट git से मिली पथ नामों की हर सूची बाइट-दर-बाइट पढ़ता है, इसलिए ऐसा नाम जिसमें
पंक्ति-विराम, कैरिज रिटर्न या UTF-8 से बाहर का कोई बाइट हो, हर जाँच के लिए एक ही
फ़ाइल नामित करता है। एक मामला पढ़ा नहीं जा सकता: Windows git को ऐसा नाम नहीं दे
सकता जो UTF-8 नहीं है, जिसे केवल किसी दूसरे सिस्टम पर बना इंडेक्स रख सकता है। तब
`semver-stability-grep --staged` बदलाव-समूह के लिए `check_error` रिपोर्ट करता है;
वह उस फ़ाइल को छोड़ता नहीं। पुरानी साथी फ़ाइलों की जाँच का इतिहास-पठन पहले वाक्य
का अपवाद है: वहाँ git नियंत्रण अक्षर वाले नाम को उसके उद्धृत रूप में छापता है, और
UTF-8 से बाहर का बाइट प्रतिस्थापन अक्षर के रूप में पढ़ा जाता है, इसलिए वह जाँच ऐसे
नाम वाले फ़ोल्डर से मेल नहीं बिठा सकती।

पुरानी साथी फ़ाइलों की जाँच केवल रिपॉज़िटरी के शीर्ष पर मौजूद `AGENTS.md` को कैनन
मानती है। जब आप इसे ऐसे सबफ़ोल्डर पर चलाते हैं जिसकी अपनी README है, तो उस
सबफ़ोल्डर की `AGENTS.md` एक प्रति-फ़ोल्डर साथी फ़ाइल है। जब सबफ़ोल्डर अपनी अलग
रिपॉज़िटरी का शीर्ष हो, जैसे कोई सबमॉड्यूल या नेस्टेड क्लोन, तो उसकी `AGENTS.md`
इसके बजाय उस रिपॉज़िटरी का कैनन है। पूरी रिपॉज़िटरी पर चलाया गया रन कुछ सबफ़ोल्डर,
जैसे टेस्ट फ़िक्स्चर और नेस्टेड रिपॉज़िटरी, छोड़ देता है, जिन्हें स्वयं उस सबफ़ोल्डर
पर चलाया गया रन जाँचता है। बिना README वाला सबफ़ोल्डर इस तरह अपने आप में एक फ़ोल्डर
के रूप में नहीं जाँचा जाता; जाँच को उसके ऊपर के किसी फ़ोल्डर पर चलाएँ। जो साथी फ़ाइल
किसी कमिट में हटाई गई और फिर से लिखी गई, वह तब तक नई गिनी जाती है जब तक आप उसे
कमिट न कर दें।

छह वैलिडेटर रिपॉज़िटरी रूट से शुरू होते हैं और जिन फ़ाइलों की वे जाँच करते हैं
उनके लिए पूरे वृक्ष में खोज करते हैं:

```text
agents-md-coverage-grep
agnosticism-grep
dynamism-grep
freshness-token-grep
plain-language-grep
reference-token-grep
```

ये नेस्टेड git चेकआउट, जैसे वर्कट्री, सबमॉड्यूल और नेस्टेड क्लोन (ऐसा फ़ोल्डर
जिसकी `.git` फ़ाइल या फ़ोल्डर किसी रिपॉज़िटरी को रखता या नामित करता है; एक
साधारण `.git` फ़ाइल या खाली `.git` फ़ोल्डर अपने फ़ोल्डर को नहीं छिपाता), को छोड़
देते हैं, किसी लिंक किए गए फ़ोल्डर में कभी नहीं जाते, और उन डायरेक्टरियों को भी
छोड़ देते हैं जिनमें निर्भरताएँ, वर्चुअल एनवायरनमेंट, कैश या बिल्ड आउटपुट होते
हैं, जैसे `node_modules`, `venv` और `dist`। `no-global-plans-grep` में
भटकी-योजनाओं की जाँच भी किसी नेस्टेड चेकआउट पर रुक जाती है। नेस्टेड चेकआउट मानकर
छोड़ा गया हर फ़ोल्डर रिपोर्ट में `skipped_checkouts` के अंतर्गत सूचीबद्ध होता है,
चाहे उसकी `.git` प्रविष्टि कुछ भी नामित करे, क्योंकि एक ही `gitdir:` पंक्ति git से
किसी भी फ़ोल्डर को छुड़वा सकती है। यह सूची निर्णय को कभी नहीं बदलती, और इस तरह
छोड़ा गया फ़ोल्डर जाँचा नहीं जाता; नाम से छोड़े गए फ़ोल्डर, जैसे `node_modules`,
सूचीबद्ध नहीं होते। इनमें से किसी का भी रन उसी चेकआउट पर रिपोर्ट करता है जिसकी ओर
उसे इंगित किया गया था, और किसी अन्य पर नहीं। जो वैलिडेटर एक निश्चित फ़ोल्डर पढ़ता
है, जैसे `src/apothem/` के अंतर्गत `naming-grep`, वह उस फ़ोल्डर के नीचे का सब कुछ
पढ़ता है।

`--all-perwrite` उन फ़ाइलों की जाँच करता है जिन्हें `git ls-files` रूट के अंतर्गत
सूचीबद्ध करता है। git हर प्रविष्टि को ठीक वैसे ही सूचीबद्ध करता है जैसे
रिपॉज़िटरी का इंडेक्स उसे रखता है, और किसी प्रोजेक्ट के साथ किसी और का बनाया
इंडेक्स और फ़ाइलें आ सकती हैं, इसलिए गेट सूचीबद्ध पथ को केवल तभी पढ़ता है जब वह
रूट के भीतर की सामान्य फ़ाइल हो, अधिकतम 64 MiB की, जिसमें UTF-8 पाठ हो। वह हर
दूसरे सूचीबद्ध पथ को `files_skipped` के अंतर्गत, कारण के अनुसार, गिनता है:

- `outside_project`: ऐसी प्रविष्टि जिसका कोई भाग खाली, `.` या `..` हो, जैसे
  `../notes.md`, `a//b.md` या `/` से शुरू होने वाला नाम, या Windows पर ऐसा भाग जो
  `.git` नामित करता है: किसी भी छोटे-बड़े रूप में `.git`, उसके बाद बिंदु, स्पेस या
  कोलन के साथ भी, और `GIT~1`। git इनमें से हर एक को हर सिस्टम पर डिफ़ॉल्ट रूप से
  अस्वीकार करता है, इसलिए रन पास नहीं होता;
- `unsupported_name`: Windows पर, ऐसा नाम जिसे सिस्टम लिखे गए रूप में नहीं रख
  सकता: कोलन वाला नाम (जैसे `a:b.md`, जिसका `a:` एक ड्राइव के रूप में पढ़ा जाता
  है), बैकस्लैश, `<>"|?*` में से कोई एक या कोई नियंत्रण अक्षर, या ऐसा भाग जो बिंदु
  या स्पेस पर खत्म होता है; और ऐसा नाम जिसे Windows कुछ और पढ़ता है: अकेला खड़ा
  कोई डिवाइस नाम, जैसे `CON`, `NUL` या `COM1`, या कोई छोटा नाम जैसे `GIT~2`।
  Linux या macOS पर git ऐसा नाम ट्रैक कर सकता है, इसलिए उसे रन विफल किए बिना गिना
  जाता है। `C:/x` या `..\..\x` जैसी हाथ से लिखी प्रविष्टि भी Windows पर यहीं आती
  है;
- `link`: रूट के नीचे किसी भी स्तर पर एक सिम्बॉलिक लिंक, या Windows पर जंक्शन, वह
  भी जो रूट के भीतर इशारा करता है, या ऐसी प्रविष्टि जिसे इंडेक्स लिंक चिह्नित करता
  है (merge conflict के किसी भी चरण में, इसलिए ऐसी फ़ाइल conflict सुलझने तक पढ़ी
  नहीं जाती)।
  git लिंक को उस पथ के रूप में संग्रहीत करता है जिसकी ओर वह इशारा करता है, और
  किसी लिंक द्वारा इंगित ट्रैक की गई फ़ाइल उसके अपने पथ से जाँची जाती है;
- `submodule`: किसी सबमॉड्यूल की प्रविष्टि;
- `not_regular_file`: कुछ भी और जो सामान्य फ़ाइल नहीं है, जैसे कोई फ़ोल्डर, नामित
  पाइप या डिवाइस, जहाँ पढ़ना रुका रहेगा या कभी खत्म नहीं होगा;
- `missing`: ट्रैक की गई ऐसी फ़ाइल जो वर्किंग ट्री में नहीं है; Windows पर इसमें
  ऐसा नाम भी शामिल है जिसे git ने UTF-8 से बाहर के बाइट में सूचीबद्ध किया, जिसे
  केवल किसी दूसरे सिस्टम पर बना इंडेक्स रखता है (Git for Windows ऐसी फ़ाइल को किसी
  दूसरे नाम से लिखता है, इसलिए उसकी सामग्री नहीं जाँची जाती), और ऐसा पथ जो लंबे पथ
  चालू न होने पर सिस्टम की अनुमति से लंबा है;
- `unreadable`: ऐसी फ़ाइल, या उस तक के रास्ते का कोई फ़ोल्डर, जिसे सिस्टम गेट को
  देखने, खोलने या पढ़ने नहीं देता: अनुमति की कमी से, क्योंकि कोई दूसरा प्रोग्राम
  फ़ाइल या उसका कोई भाग पकड़े हुए है, या क्योंकि सिस्टम उसे खोल नहीं सकता, जैसे
  कोई केवल-ऑनलाइन फ़ाइल जिसका सिंक प्रोग्राम रुका हुआ है। जब कोई दूसरा प्रोग्राम
  पूरी फ़ाइल पकड़े हुए हो, तो गेट 0.2 सेकंड प्रतीक्षा करता है और एक बार फिर प्रयास
  करता है: Windows पर, ऐसा प्रोग्राम जिसने उसे साझा किए बिना खोला हुआ है; अन्य
  सिस्टम पर, टूटती हुई कोई write lease, जैसे Samba oplock या NFS delegation। रन
  पास नहीं होता, क्योंकि उसमें कोई फ़ाइंडिंग अनदेखी रह जाती। कुछ मामले फ़ाइल में
  कुछ भी गलत न होने पर भी रन को इस तरह विफल करते हैं: 0.2 सेकंड से अधिक समय लेने
  वाला lease break, हटाए जाने की प्रतीक्षा में पड़ी फ़ाइल, और `\\wsl$` शेयर पर रखे
  प्रोजेक्ट में नामित पाइप, जहाँ हर पठन पहले लगभग 10 सेकंड प्रतीक्षा करता है;
- `too_large`: 64 MiB से बड़ी ऐसी फ़ाइल जिसके पहले 64 MiB UTF-8 पाठ हैं, या ऐसी
  फ़ाइल जो गेट के पढ़ते समय 64 MiB से आगे बढ़ जाती है। इसी कारण रन पास नहीं होता;
- `not_utf8_text`: ऐसी फ़ाइल जिसके बाइट UTF-8 पाठ नहीं हैं, जैसे बाइट-ऑर्डर मार्क
  वाली UTF-16 फ़ाइल। 64 MiB से ऊपर, पहले 64 MiB निर्णय करते हैं, और फ़ाइल तब बाइनरी
  है जब उसके पहले 8000 बाइट में से एक चौथाई या अधिक NUL हों, जैसे शून्य से भरी कोई
  बड़ी छवि या बिना बाइट-ऑर्डर मार्क के अधिकतर लैटिन पाठ वाली UTF-16 फ़ाइल, इसलिए वह
  रन को विफल नहीं करती; पाठ में कुछ NUL बाइट नहीं गिने जाते;
- `exempt`: ऐसी फ़ाइल जिसे जाँचें जानबूझकर छोड़ती हैं: ऐसी फ़ाइल जिसका प्रत्यय उसे
  बाइनरी चिह्नित करता है, जैसे कोई छवि या आर्काइव, और रूट के भीतर किसी भी गहराई पर
  `.apothem/plans`, `tests/conformity`, `tests/fixtures`, `_vendor` या
  `node_modules` फ़ोल्डर के अंतर्गत कुछ भी। `outside_project` और
  `unsupported_name` की जाँचें पहले आती हैं, इसलिए कोई छूट उन्हें नहीं छिपाती।

जब कोई रन `outside_project`, `unreadable` या `too_large` के कारण पास नहीं होता, तो
`files_not_passed` उन कारणों में से हर एक के पीछे की प्रविष्टियों के नाम देता है,
जैसे git उन्हें सूचीबद्ध करता है, क्रम में, हर कारण के लिए अधिकतम 10;
`files_skipped` में पूरी गिनती होती है। stderr पर एक पंक्ति भी उन कारणों और उनकी
गिनतियों के नाम देती है, ताकि केवल stderr दिखाने वाला CI लॉग बताए कि रन क्यों विफल
हुआ।

हर फ़ाइल के स्तर उसे पढ़े जाने से ठीक पहले जाँचे जाते हैं, और खोली गई फ़ाइल वही
होनी चाहिए जो उस जाँच में मिली। जिस फ़ाइल को कोई दूसरा प्रोग्राम इस बीच किसी दूसरी
फ़ाइल, लिंक या नामित पाइप से बदल देता है, उसे एक बार और खोजा जाता है, और यदि वह
फिर से बदली जाए तो `unreadable` गिनी जाती है; बदलकर लाया गया सिम्बॉलिक लिंक या,
Windows पर, जंक्शन दूसरी खोज में `link` के रूप में मिलता है। गेट कभी किसी नामित
पाइप पर प्रतीक्षा नहीं करता और फ़ाइल की जगह लेने वाले किसी लिंक के ज़रिए नहीं
पढ़ता। Windows पर, जिस फ़ाइल को Data Deduplication या कोई क्लाउड सिंक प्रोग्राम
किसी reparse point के पीछे रखता है, वह सामान्य रूप से उस प्रोग्राम के ज़रिए पढ़ी
जाती है; जब प्रोग्राम रुका हुआ हो, तो फ़ाइल `unreadable` होती है।

फ़ाइल रूट से एक-एक स्तर करके खोली जाती है, और कोई स्तर किसी लिंक के ज़रिए नहीं
खोला जाता, इसलिए फ़ाइल के ऊपर का ऐसा फ़ोल्डर, जिसे कोई दूसरा प्रोग्राम जाँच और
खोलने के बीच किसी लिंक से बदल देता है, उसका भी पीछा नहीं किया जाता: फ़ाइल `link`
गिनी जाती है।

दो चीज़ें ये जाँचें नहीं देखतीं। हार्ड लिंक एक सामान्य फ़ाइल के रूप में पढ़ा जाता
है, इसलिए कहीं और की फ़ाइल का हार्ड लिंक पढ़ा जाता है; git ऐसा लिंक नहीं बनाता। और
Windows पर, ऐसा नेटवर्क फ़ाइल सिस्टम जो न फ़ाइल का reparse tag देता है न उसका
file ID, पर सिम्बॉलिक लिंक रखता है, उस पर जाँच और खोलने के बीच कोई फ़ाइल गेट के
देखे बिना लिंक से बदली जा सकती है।

इस रन में `link-check` मैचर किसी लिंक का लक्ष्य केवल रूट के भीतर खोजता है: रूट से
बाहर जाने वाला सापेक्ष लिंक बाहरी गिना जाता है, और `site/content/docs` फ़ोल्डर की
खोज रूट पर रुक जाती है। हर मोड में, वह कभी ऐसा लिंक नहीं खोजता जो अपने आप में कोई
स्थान नामित करता है, जैसे कोई नेटवर्क शेयर (`\\host\share`), कोई ड्राइव
(`C:/notes.md`) या कोई `file:` पता। Windows पर किसी शेयर को खोजना आपका साइन-इन उस
होस्ट को भेज देता है। Windows पर वह कोलन वाले `/docs/` रूट खंड को भी, जिसे Windows
ड्राइव के रूप में पढ़ता है, बिना जाँचे छोड़ देता है, और ऐसे लिंक को भी जो उसे केवल
बिंदु या स्पेस पर खत्म होने वाले भाग के ज़रिए मिलता है: Windows वह अंत हटा सकता है
(`ci.yml.` `ci.yml` को ढूँढ लेता है), इसलिए ऐसा मिलना कुछ सिद्ध नहीं करता। ऐसा
लिंक जो कुछ नहीं ढूँढता, सामान्य रूप से मृत रिपोर्ट किया जाता है। हर सिस्टम पर,
`.` या `..` खंड वाला `/docs/` रूट, जैसे `/docs/../x`, बाहरी गिना जाता है और खोजा
नहीं जाता।

हर `git ls-files` कॉल को 60 सेकंड मिलते हैं: वह जो यह रन करता है, और वह जो
`no-global-plans-grep` में होती है, जिसकी रिपोर्ट तब वही `check_error` रखती है और
विफल होती है; जब वहाँ git स्वयं विफल होता है, तो उसका संदेश git का निकास कोड देता
है, git का अपना पाठ नहीं। ऐसी रिपॉज़िटरी जिसकी अपनी सेटिंग git को प्रतीक्षा
करवाती हैं, जैसे किसी नामित पाइप की ओर इशारा करने वाला `include.path`, इनमें से हर
कॉल को अधिकतम इतनी देर रोकती है, Windows पर भी, जहाँ सीमा उस git को भी रोकती है
जिसे Git का लॉन्चर शुरू करता है। जिस `--all-perwrite` रन ने कोई फ़ाइल नहीं पढ़ी,
वह पास नहीं होता: वह `empty_scope_expected: false` के साथ `files_scanned: 0`
रिपोर्ट करता है। जब ट्रैक की गई फ़ाइलों की सूची पढ़ी नहीं जा सकती, तो
`check_error` एक निश्चित कारण देता है: git शुरू नहीं हुआ, `git ls-files` किसी
दिए गए निकास कोड के साथ विफल हुआ, या वह समय पर पूरा नहीं हुआ। git का अपना संदेश
देखने के लिए, उदाहरण के लिए जब रूट किसी git वर्क ट्री के भीतर नहीं है, रूट में
`git ls-files` चलाएँ; रिपोर्ट उसे छोड़ देती है, क्योंकि वह प्रोजेक्ट के बाहर की
फ़ाइलों के नाम दे सकता है। `--strict` के साथ, पास न होने वाला रन `2` के साथ बाहर
निकलता है।

## लक्षित जाँचें

```bash
# List every registered validator
PYTHONPATH=src python -m apothem.conformity.gate --list

# Run one per-write validator against one file
PYTHONPATH=src python -m apothem.conformity.gate --check multi-surface-coherence src/apothem/rules/my-rule.md

# Run one standalone validator over a root directory
PYTHONPATH=src python -m apothem.conformity.gate --check naming-grep .

# Run every per-write validator against one file
PYTHONPATH=src python -m apothem.conformity.gate src/apothem/rules/my-rule.md
```

प्रति-लेखन वैलिडेटर जाँचने के लिए फ़ाइल लेता है, या मानक इनपुट से सामग्री पढ़ने
के लिए `--stdin`; दोनों में से कोई न होने पर वह मानक इनपुट पर इनपुट की प्रतीक्षा
करता है, इसलिए टर्मिनल से चलाते समय फ़ाइल पास करें। स्टैंडअलोन वैलिडेटर एक रूट
डायरेक्टरी लेता है (छोड़ दिए जाने पर वर्तमान डायरेक्टरी)। `--list` दिखाता है कि
हर वैलिडेटर किस समूह से संबंधित है।

`--hook` मोड (`<python> -E -s .../conformity/gate.py --hook`, जहाँ `<python>` वह
इंटरप्रेटर है जिसे इंस्टॉल ने ढूँढा) हार्नेस-प्रेषित एंट्री पॉइंट है: यह stdin से
एक टूल-इनपुट JSON पेलोड पढ़ता है और लंबित लेखन के विरुद्ध प्रति-लेखन मैचर शृंखला
चलाता है। यही वह रूप है जिसे डिप्लॉय किया गया `PreToolUse` हुक कॉल करता है; आप
इसे शायद ही कभी हाथ से कॉल करते हैं।

हुक मोड **डायरेक्टरियों के एक सेट तक सीमित** है। यह मैचर शृंखला केवल उन लेखनों
पर चलाता है जिनका टारगेट उनमें से किसी एक के अंतर्गत आता है; हर दायरे से बाहर का
लेखन शॉर्ट-सर्किट होकर एक मौन पास बन जाता है। डिफ़ॉल्ट दो रूट हैं:

```text
~/.claude      Claude Code
$CODEX_HOME    Codex (~/.codex when CODEX_HOME is not set)
```

उन्हें बदलने के लिए `APOTHEM_CONFORMITY_SCOPE` को किसी डायरेक्टरी पर सेट करें:

```bash
# Run the per-write matcher chain against one project tree instead
export APOTHEM_CONFORMITY_SCOPE=/path/to/project
```

कोई हुक जो कुछ भी न करता प्रतीत हो, वह सामान्यतः विफलता के बजाय दायरे की चूक
होता है — पहले लेखन के टारगेट को ऊपर दिए गए दायरों से मिलाकर जाँचें।

## CI एकीकरण

`.github/workflows/ci.yml` का quality जॉब `main` पर पुश पर, और `main` की ओर उन पुल
रिक्वेस्ट पर जो उस जॉब द्वारा देखे जाने वाले पथों को छूती हैं, गेट को सख़्त मोड में
चलाता है (`python -m apothem.conformity.gate --all . --strict`)। अलग
`.github/workflows/conformity.yml` वर्कफ़्लो फ़िक्स्चर स्वीप चलाता है
(`tests/conformity-scenarios/verify.py --strict`)।
