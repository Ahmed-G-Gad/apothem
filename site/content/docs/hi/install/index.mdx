Apothem दो मिनट से कम में इंस्टॉल हो जाता है और आपके मौजूदा हार्नेस
कॉन्फ़िगरेशन के साथ-साथ काम करता है। हर पथ वही स्व-निहित इंजन चलाता है — स्रोत
ट्री अपनी वेंडर की गई निर्भरताएँ साथ रखता है और सिस्टम Python 3.10 या नए पर एक
चेकआउट से चलता है (देखें
[स्व-निहित रनटाइम](/docs/architecture/self-contained-runtime))।

**दो पूर्वापेक्षाएँ हर पथ में साझा हैं:** `PATH` पर सिस्टम **Python 3.10 या नया**,
जिसके अंतर्गत `click` और `rich` पैकेज आयात-योग्य हों। npm शिम (चैनल 2),
VS Code-परिवार एक्सटेंशन (चैनल 4), और कमांड-लाइन बूटस्ट्रैप (चैनल 5–7) को `npx`
चलाने के लिए अतिरिक्त रूप से **Node.js 18 या नए** की आवश्यकता होती है।
Python 3.10 तथा Node.js 18 और 20 अपस्ट्रीम जीवन-अंत पार कर चुके हैं; वे समर्थित और
परीक्षित बने रहते हैं, लेकिन नए संस्करणों को प्राथमिकता दी जाती है (देखें
[पूर्वापेक्षाएँ एक नज़र में](#पूर्वापेक्षाएँ-एक-नज़र-में))। नीचे प्रत्येक चैनल का
अपना अनुभाग उसकी सटीक पूर्वापेक्षाएँ, एक कॉपी-रेडी कमांड, और एक सत्यापन चरण
दोहराता है।

## 1. Claude Code प्लगइन

**पूर्वापेक्षाएँ:** Claude Code, और `PATH` पर सिस्टम Python 3.10+।

प्लगइन पथ पूरी तरह Claude Code के भीतर चलता है। यह Apothem इंजन को उसके स्लैश
कमांड, प्रत्यायोजित वर्कर, स्किल, नियम, और हुक के साथ बंडल करता है, जो सभी
स्व-निहित प्लगइन ट्री से चलाए जा सकते हैं:

```text title="Inside Claude Code"
/plugin marketplace add ahmed-g-gad/apothem
/plugin install apothem@apothem
```

इंस्टॉल के बाद, Apothem कमांड सेट, बंडल किए गए प्रत्यायोजित वर्कर, स्किल, और चार
[आउटपुट शैलियाँ](/docs/reference/output-styles) (`/output-style` से या `/config`
से कोई एक चुनें) हर Claude Code सत्र में उपलब्ध होते हैं। प्लगइन हर कमांड को एक
स्किल के रूप में शिप करता है, एक `SKILL.md` जिसके साथ वह विवरण जिसे वह माँग पर लोड
करता है, उसके बगल में एक `references/` फ़ोल्डर में होता है, इसलिए Claude Code उसे
प्लगइन के उपसर्ग के साथ आह्वान करता है: `/apothem:plan-spec`,
`/apothem:security-audit`, और बाकी। दो नाम स्वयं Claude Code ने ले रखे हैं: `/plan`
प्लान मोड में प्रवेश करता है और `/code-review` बंडल की गई समीक्षा चलाता है, इसलिए
Apothem कमांड के लिए `/apothem:plan` और `/apothem:code-review` टाइप करें। जब प्लगइन
के बजाय Apothem इंजन Claude Code में इंस्टॉल होता है, तो वही स्किल बिना उपसर्ग के
`~/.claude/skills/` में लिखी जाती हैं, और एक व्यक्तिगत
`code-review` स्किल बंडल किए गए `/code-review` का स्थान ले लेती है (उसका `/review`
उपनाम अब भी बंडल की गई समीक्षा चलाता है)। दो नाम, `projectify` और `workflow`, नेटिव
स्किल भी हैं; प्लगइन और इंजन इंस्टॉल नेटिव स्किल ही शिप करते हैं, कमांड से
व्युत्पन्न कोई स्किल नहीं। कमांड कैसे विभाजित होते हैं, इसके लिए
[Claude Code](/docs/harnesses/claude-code#command-skills-and-reference-files) देखें, और
पूर्ण कमांड कैटलॉग के लिए [स्लैश कमांड](/docs/reference/commands) देखें।

**सत्यापित करें:** Claude Code के भीतर `/plugin` चलाएँ और पुष्टि करें कि **apothem**
इंस्टॉल के रूप में सूचीबद्ध है, या किसी टर्मिनल से ड्रिफ़्ट रिपोर्ट जाँचें:

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 2. npm शिम (`npx`)

**पूर्वापेक्षाएँ:** Node.js 18+ (`npx` के लिए) और `PATH` पर सिस्टम Python 3.10+।
शिम इंटरप्रेटर का पता लगाता है और हर CLI कमांड को बंडल किए गए इंजन को अग्रेषित
करता है — आपके सिस्टम पर स्थायी रूप से कुछ नहीं रखा जाता। यह इसी क्रम में
`python3`, `python`, फिर `py -3` आज़माता है; उसे सबसे पहले आज़माने के लिए
**`APOTHEM_PYTHON`** को किसी इंटरप्रेटर पथ पर सेट करें — इसकी आवश्यकता आपको तब होती
है जब Python इंस्टॉल है लेकिन `PATH` पर नहीं है, या जब कई संस्करण इंस्टॉल हैं और
आप कोई विशिष्ट संस्करण चाहते हैं। आपके द्वारा नामित इंटरप्रेटर को अब भी Python 3.10+
जाँच पास करनी होती है; जब वह पास नहीं करता, तो शिम `python3`, `python`, फिर
`py -3` पर लौट जाता है।

```bash title="npx"
npx @ahmed-g-gad/apothem install --harness claude-code
```

जिस मशीन पर कोई प्रोफ़ाइल नहीं है, वहाँ यह पहला `install`
`~/.config/apothem/profile.yaml` पर प्रारंभिक प्रोफ़ाइल बनाता है और इसकी सूचना देता
है। इसके पहचान फ़ील्ड प्लेसहोल्डर हैं: उन्हें वैयक्तिकृत करें
(`npx @ahmed-g-gad/apothem profile edit`), फिर उन्हें लागू करने के लिए `install` के
स्थान पर `update` के साथ कमांड दोबारा चलाएँ।

यह सीधे रिपॉज़िटरी से भी चलता है:

```bash title="npx from the repository"
npx github:ahmed-g-gad/apothem install --harness claude-code
```

[CLI संदर्भ](/docs/cli-reference) का हर कमांड इस रूप में काम करता है; `apothem` के
स्थान पर `npx @ahmed-g-gad/apothem` रखें। यही OpenCode और हर उस अन्य टूल के लिए भी
इंस्टॉल पथ है जो कोई अलग प्लगइन या एक्सटेंशन रजिस्ट्री उपलब्ध नहीं कराता — Apothem
उन्हें सीधे उनकी नेटिव कॉन्फ़िग डायरेक्टरी में सिंक करता है
(`npx @ahmed-g-gad/apothem install --harness opencode`)।

**सत्यापित करें:**

```bash title="Verify"
npx @ahmed-g-gad/apothem --version
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 3. वन-शॉट इंस्टॉलर

**पूर्वापेक्षाएँ:** `PATH` पर सिस्टम Python 3.10+ (इंस्टॉलर आपके लिए `click` /
`rich` पूर्वापेक्षाएँ जोड़ने की पेशकश करता है)। नेटवर्क इंस्टॉल के लिए: `git`,
नवीनतम रिलीज़ खोजने के लिए, और `gpg`, हस्ताक्षरित रिलीज़ टैग की जाँच के लिए
(Git for Windows दोनों के साथ आता है)। [cosign](https://docs.sigstore.dev/cosign/system_config/installation/)
वैकल्पिक है: उसके साथ, इंस्टॉलर हस्ताक्षरित रिलीज़ आर्काइव की भी जाँच करता है।

इंस्टॉलर स्क्रिप्ट नवीनतम रिलीज़ को हल करती हैं, उसकी जाँच करती हैं (देखें
[विश्वास मॉडल](#विश्वास-मॉडल)), Apothem स्रोत ट्री को `~/.apothem` में रखती हैं,
कोई प्रोफ़ाइल न होने पर एक प्रारंभिक प्रोफ़ाइल बनाती हैं, आपके पहले हार्नेस को
मूर्त रूप देती हैं, और परिणाम को सत्यापित करती हैं — यह सब एक ही रन में।
प्रारंभिक प्रोफ़ाइल में प्लेसहोल्डर पहचान फ़ील्ड होते हैं: उसे संपादित करें, फिर
अपने फ़ील्ड लागू करने के लिए `apothem update --harness <name>` चलाएँ। पुनः चलाना
इडेम्पोटेंट है: git क्लोन को फ़ेच किया जाता है, उसके नए टैग की जाँच होती है, और
उसके बाद ही क्लोन को हल किए गए टैग पर चेकआउट किया जाता है; रिलीज़-आर्काइव
इंस्टॉल को उसी स्थान पर अपडेट किया जाता है; और हार्नेस को फिर से मूर्त रूप दिया
जाता है। जब इंजन आंशिक स्थिति में समाप्त होता है (exit code `2`), तो इंस्टॉलर एक
चेतावनी पंक्ति प्रिंट करता है, फिर भी सत्यापन करता है, `apothem` कमांड को रखता
है और उसका बैनर प्रिंट करता है, फिर exit code `2` के साथ समाप्त होता है। इंजन
आंशिक स्थिति में तब समाप्त होता है जब वह किसी फ़ाइल को उसकी Apothem मार्कर
पंक्तियों के कारण जैसी है वैसी छोड़ देता है, या जब वह कुछ लिख चुकने के बाद रुक
जाता है (देखें
[जब इंजन किसी फ़ाइल को जैसी है वैसी छोड़ देता है](/docs/install/updating#when-the-engine-leaves-a-file-as-it-is))।
सत्यापित इंस्टॉल डिफ़ॉल्ट और अनुशंसित पथ है।

पहले एक बार मेंटेनर की हस्ताक्षर कुंजी आयात करें। हर नेटवर्क इंस्टॉल रिलीज़ टैग
को उसी के विरुद्ध जाँचता है, cosign के साथ या उसके बिना, और जब कुंजी आपकी
कीरिंग में नहीं होती तो रुक जाता है। जाँच करें कि फ़िंगरप्रिंट
`5C89 98F9 F241 7204 45D3  F28B 7039 6FED 9C63 4163` पढ़ता है, यह वही मान है
जिसे
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md#maintainer-signing-key)
प्रकाशित करता है। Windows पर, `git verify-tag` उस `gpg` की कीरिंग पढ़ता है जो
Git for Windows के साथ आता है, इसलिए आयात Git के अपने `bash` के माध्यम से चलता
है:

```bash title="macOS · Linux · WSL2 · BSD — import the key once"
curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import
gpg --fingerprint 70396FED9C634163
```

```powershell title="Windows · PowerShell — import the key once"
& "$env:ProgramFiles\Git\bin\bash.exe" -c 'curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import && gpg --fingerprint 70396FED9C634163'
```

```bash title="macOS · Linux · WSL2 · BSD — latest signed tag, verified"
curl -fsSL https://apothem.ahmedgad.com/install.sh | bash
```

```powershell title="Windows · PowerShell — latest signed tag, verified"
irm https://apothem.ahmedgad.com/install.ps1 | iex
```

वही स्क्रिप्ट एक चेकआउट में `scripts/installer/` के अंतर्गत शिप होती हैं —
`install`, `uninstall`, और `update`, `.sh`, `.ps1`, और `.bat` रूपों में — ताकि आप
क्लोन करने के बाद उन्हें सीधे चला सकें:

```bash title="From a checkout"
APOTHEM_HARNESS=claude-code sh scripts/installer/install.sh                                 # POSIX
$env:APOTHEM_HARNESS = 'claude-code'; pwsh -NoProfile -File scripts/installer/install.ps1   # Windows
```

पाइप किया गया वन-लाइनर कभी स्थानीय ट्री का उपयोग नहीं करता: `curl ... | sh` और
`irm ... | iex` उस फ़ोल्डर और उसके पैरेंट फ़ोल्डरों को अनदेखा करते हैं जहाँ से आप
उन्हें चलाते हैं, और रिलीज़ को फ़ेच और सत्यापित करते हैं। इंस्टॉलर स्थानीय ट्री का
उपयोग केवल तब करता है जब आप चेकआउट की अपनी `scripts/installer/install.sh` (या
`install.ps1`) को उसके पथ से, किसी भी फ़ोल्डर से चलाते हैं (उदाहरण के लिए
`sh ~/src/apothem/scripts/installer/install.sh`), या जब `APOTHEM_SOURCE` उस ट्री
का नाम देता है। इंस्टॉलर, अपडेटर और अनइंस्टॉलर, `apothem` शिम, npm लॉन्चर, हुक
और अनुरूपता गेट की वैलिडेटर प्रक्रियाएँ वर्तमान फ़ोल्डर को Python के मॉड्यूल खोज
पथ से बाहर रखती हैं। आपके द्वारा स्वयं टाइप की गई `python -m apothem` कमांड ऐसा
नहीं करती: `-m` मॉड्यूल पहले वर्तमान फ़ोल्डर से पढ़ता है।

आपके अपने `PYTHONPATH` की खाली और सापेक्ष प्रविष्टियाँ कोई भी लॉन्चर इंजन को
आगे नहीं देता (इंस्टॉलर, अपडेटर, अनइंस्टॉलर, POSIX और Windows `apothem` शिम, और
npm लॉन्चर)। रखी गई प्रविष्टि एक पूर्ण पथ होनी चाहिए: Windows पर `C:\lib` जैसा
ड्राइव पथ या नेटवर्क पथ, अन्यत्र `/` से शुरू होने वाला पथ। रूटेड `\lib` या
ड्राइव-सापेक्ष `C:lib` हटा दिया जाता है। sh स्क्रिप्ट जिस Python को चलाती हैं,
उससे पूछती हैं कि वह कौन-सा रूप पढ़ता है, और वे जो `apothem` शिम लिखती हैं वह
उसी रूप को रखता है। Windows Python (Git Bash के अंतर्गत सामान्य वाला) को इंजन पथ
Windows रूप में, `;` से जोड़कर मिलते हैं, और वह आपके `PYTHONPATH` के केवल ड्राइव
और नेटवर्क पथ रखता है। POSIX Python, जिसमें Cygwin और MSYS2 का अपना `python3`
भी शामिल है, को `:` से जोड़े गए POSIX पथ मिलते हैं और वह केवल `/` से शुरू होने
वाली प्रविष्टियाँ रखता है। इंस्टॉलर की वे `git` कमांड जो किसी क्लोन पर काम नहीं
करतीं, वर्तमान फ़ोल्डर की किसी रिपॉज़िटरी को नहीं पढ़तीं।

### इंस्टॉलर फ़्लैग

`install.sh` नीचे दिए फ़्लैग लेता है, और `install.ps1` वही स्विच PowerShell
पैरामीटर के रूप में लेता है। `install.bat` पहली तीन पंक्तियों की `install.sh`
वाली वर्तनी स्वीकार करता है और हर एक को `install.ps1` तक पहुँचाता है। पाइप से
चलाई गई एक-पंक्ति कमांड PowerShell पैरामीटर नहीं दे सकती, इसलिए किसी को
इस्तेमाल करने के लिए पहले `install.ps1` डाउनलोड करें:

```bash title="Pass a flag (POSIX)"
curl -fsSL https://apothem.ahmedgad.com/install.sh | sh -s -- --dry-run
```

```powershell title="Pass a flag (Windows PowerShell 5.1 or later)"
irm https://apothem.ahmedgad.com/install.ps1 -OutFile install.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File install.ps1 -DryRun
```

| `install.sh` | `install.ps1` | प्रभाव |
|---|---|---|
| `--clean`, `--fresh` | `-Clean`, `-Fresh` | इंस्टॉल से पहले आपकी होम डायरेक्टरी के वे चार फ़ोल्डर, जिन्हें [`apothem install`](/docs/cli-reference/install#blast-radius-preview) सूचीबद्ध करता है और जिनमें `~/.claude` और `~/.agents` शामिल हैं, उनका बैकअप लेता है और उन्हें हटाता है, चाहे आप कोई भी हार्नेस इंस्टॉल करें, फिर नए सिरे से इंस्टॉल करता है। इंस्टॉलर इसे इंजन को `apothem install --clean` के रूप में देता है, जो हर हटाने से पहले पूछता है, बैकअप `~/.apothem/backups` के अंतर्गत रखता है और आपकी प्रोफ़ाइल वापस लिखता है। |
| `--dry-run` | `-DryRun` | रिलीज़ को एक अस्थायी फ़ोल्डर में लाकर जाँचता है और दिखाता है कि इंस्टॉल क्या बदलेगा, कुछ भी बदले बिना ([विश्वास मॉडल](#विश्वास-मॉडल) देखें)। |
| `--yes` | `-Yes` | `--clean` के हर हटाने से पहले नहीं पूछता। यह `APOTHEM_HOME` में मौजूद चीज़ों के वे प्रतिस्थापन भी होने देता है जिनके लिए [विश्वास मॉडल](#विश्वास-मॉडल) `--yes` की ज़रूरत बताता है। यह गायब Python पूर्वापेक्षाएँ (`click`, `rich`) भी बिना पूछे pip से इंस्टॉल करता है, जैसा `APOTHEM_AUTO_INSTALL_DEPS=1` करता है। |
| `-h`, `--help` | कोई नहीं | फ़्लैग और विश्वास मॉडल छापता है, फिर बाहर निकल जाता है। |

### विश्वास मॉडल

`APOTHEM_REF` सेट न होने पर, इंस्टॉलर सबसे ऊँची `vMAJOR.MINOR.PATCH` रिलीज़ को हल
करता है और *उसी* को इंस्टॉल करता है — कभी भी चलती हुई `main` ब्रांच को
नहीं। वह किसी भी कॉन्फ़िगरेशन के मूर्त रूप दिए जाने से पहले रिलीज़ की जाँच करता
है, और जाँच इस पर निर्भर करती है कि `cosign` आपके `PATH` पर है या नहीं:

- **cosign के साथ**, दो जाँचें दोनों पास होनी चाहिए। पहली, रिलीज़ टैग पर
  मेंटेनर कुंजी का एक मान्य हस्ताक्षर होना चाहिए, जिसकी जाँच अगले बिंदु की तरह
  होती है, और हस्ताक्षरित टैग वही होना चाहिए जिसका नाम उस रिलीज़ के लिए है: किसी
  अन्य रिलीज़ का हस्ताक्षरित टैग, जिसे इस नाम पर फिर से इंगित किया गया हो, अस्वीकार
  कर दिया जाता है। फिर इंस्टॉलर रिलीज़ का प्लेटफ़ॉर्म आर्काइव, उसकी `SHA256SUMS`
  फ़ाइल और `SHA256SUMS.cosign.bundle` डाउनलोड करता है। cosign को पुष्टि करनी होती
  है कि Apothem के रिलीज़ वर्कफ़्लो ने ठीक उसी टैग के लिए `SHA256SUMS` पर हस्ताक्षर
  किए, और अपनी `--certificate-github-workflow-sha` जाँच के माध्यम से यह भी कि
  उसने जिस प्रमाणपत्र को सत्यापित किया वह उस कमिट पर चले रन को जारी किया गया था
  जिसकी ओर हस्ताक्षरित टैग इंगित करता है। इंस्टॉलर प्रमाणपत्र को स्वयं नहीं
  पढ़ता। इसके बाद आर्काइव का SHA-256 सूचीबद्ध डाइजेस्ट से मेल खाना चाहिए।
  वर्कफ़्लो पुश किए गए किसी भी टैग के लिए चलता है, इसलिए अकेले उसका हस्ताक्षर
  पर्याप्त नहीं है; टैग हस्ताक्षर दिखाता है कि मेंटेनर ने वह कमिट रिलीज़ किया।
- **cosign के बिना**, या जब `APOTHEM_HOME` में पहले से एक git क्लोन हो,
  इंस्टॉलर रिपॉज़िटरी को क्लोन या अपडेट करता है और केवल टैग की जाँच
  `git verify-tag` से करता है। हस्ताक्षर मान्य होना चाहिए *और*
  [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md) में
  प्रकाशित मेंटेनर कुंजी से बना होना चाहिए, और हस्ताक्षरित टैग वही होना चाहिए
  जिसका नाम उस रिलीज़ के लिए है। किसी अन्य कुंजी से हस्ताक्षरित टैग अस्वीकार कर
  दिया जाता है, भले ही आपकी कीरिंग उस कुंजी पर भरोसा करती हो। हस्ताक्षरित git टैग
  अपने कमिट को SHA-1 ID से नामित करता है; cosign के साथ, इंस्टॉलर आर्काइव का
  SHA-256 भी जाँचता है। मौजूदा क्लोन को फ़ेच किया जाता है और क्लोन को चेकआउट करने
  से *पहले* उसके नए टैग की जाँच होती है। विफल जाँच क्लोन को जैसा था वैसा
  छोड़ देती है, और ट्रैक की गई फ़ाइलों में बदलाव वाला क्लोन उन्हें खोने के बजाय
  उन्हें कमिट या स्टैश करने के संदेश के साथ अपडेट रोक देता है। `main` जैसे
  गैर-रिलीज़ ref के साथ, मौजूदा क्लोन origin की उस ब्रांच की प्रति का अनुसरण करता
  है।

इंस्टॉलर उन git पर्यावरण चरों को अनदेखा करता है जो git को पुनर्निर्देशित करते हैं
(`GIT_DIR`, `GIT_WORK_TREE` और इसी तरह के) और उन्हें भी जो git को किसी अन्य
कॉन्फ़िग फ़ाइल की ओर इंगित करते हैं (`GIT_CONFIG`, `GIT_CONFIG_GLOBAL` और
`GIT_CONFIG_SYSTEM`) या उसे किसी अन्य ट्री से एट्रिब्यूट पढ़ने को कहते हैं
(`GIT_ATTR_SOURCE`; आपके अपने कॉन्फ़िग का `attr.tree` क्लोन पर चलने वाली हर git
कमांड पर खाली कर दिया जाता है), और जब `APOTHEM_REPO` `-` से शुरू होता है तो रुक
जाता है। `GIT_CONFIG_NOSYSTEM` वैसा ही रहता है जैसा आपने सेट किया; वह git को केवल
सिस्टम कॉन्फ़िग पढ़ने से रोकता है। git अब भी आपका अपना ग्लोबल कॉन्फ़िग और, जब तक
आप `GIT_CONFIG_NOSYSTEM` सेट न करें, सिस्टम कॉन्फ़िग उन्हीं स्थानों से पढ़ता है
जहाँ वह हमेशा देखता है, और `git`, `gpg` और `cosign` वही प्रोग्राम हैं जो आपका
`PATH` खोजता है: इंस्टॉलर उन पर वैसे ही भरोसा करता है जैसे वे मिले। पूरे रन के
लिए इंस्टॉलर `GIT_NO_REPLACE_OBJECTS=1` सेट करता है, ताकि git कभी replace refs के
माध्यम से कोई ऑब्जेक्ट न बदले, `GIT_NO_LAZY_FETCH=1`, ताकि git कभी अपने आप
रिमोट से कोई अनुपस्थित ऑब्जेक्ट फ़ेच न करे, `GIT_ALLOW_PROTOCOL` को file, git,
http, https और ssh ट्रांसपोर्ट पर, ताकि आपके पर्यावरण का कोई मान उस सूची को
विस्तृत न कर सके, और `GIT_ATTR_NOSYSTEM=1`; क्लोन पर चलने वाली हर git कमांड पर
`core.attributesFile` खाली किए जाने के साथ, git तब क्लोन के बाहर कोई एट्रिब्यूट
फ़ाइल नहीं पढ़ता, इसलिए आपकी फ़ाइल में परिभाषित कोई मैक्रो वहाँ किसी फ़िल्टर का
नाम नहीं दे सकता। PowerShell स्क्रिप्ट रन समाप्त होने पर चारों को वापस रख देती
है। इंस्टॉलर रिलीज़ टैग को एक बार पढ़ता है, उसके द्वारा नामित कमिट दर्ज करता है,
टैग को सत्यापित करता है, उस कमिट को ID से चेकआउट करता है, और `HEAD` का वही कमिट
होना आवश्यक करता है, इसलिए जाँच के बाद खिसकाया गया टैग कुछ नहीं बदलता। Windows
PowerShell 5.1 और 7 पर, ऐसा डाउनलोड जो https न होने वाले पते पर रीडायरेक्ट करता
है, अस्वीकार कर दिया जाता है, जैसा POSIX इंस्टॉलरों का `curl` करता है।

`APOTHEM_HOME` ऐसा फ़ोल्डर होना चाहिए जिसमें केवल आप लिख सकें, क्योंकि जो कोई
भी उसमें लिख सकता है वह उस कोड को बदल सकता है जिसे `apothem` कमांड चलाती है।
Windows पर, किसी ड्राइव के रूट पर बनाया गया फ़ोल्डर, जैसे `C:\apothem`, Windows
की डिफ़ॉल्ट अनुमतियों के अंतर्गत कंप्यूटर में साइन इन करने वाला हर उपयोगकर्ता
बदल सकता है। डिफ़ॉल्ट, `~/.apothem`, आपके अपने उपयोगकर्ता फ़ोल्डर में है। हर
फ़ेच किया गया इंस्टॉल, अपडेट और ड्राई रन, बिना रुके, चेतावनी देता है जब ऐसा
नहीं होता, या जब वह फ़ोल्डर या उसे रखने वाला फ़ोल्डर किसी और का हो; चेतावनी
फ़ोल्डर का, उसमें कौन लिख सकता है या उसका स्वामी कौन है उसका, और सुधार का नाम
देती है; स्थानीय चेकआउट से इंस्टॉल, और `APOTHEM_SOURCE` सेट होने पर अपडेट, यह
जाँच छोड़ देते हैं। Windows पर चेतावनी
`install.ps1` और `update.ps1` से आती है: `install.sh` और `update.sh` Git Bash,
MSYS2 या Cygwin के अंतर्गत जाँच नहीं करते (देखें
[समस्या निवारण](/docs/install/troubleshooting#the-installer-warns-other-users-can-change-apothem_home))।

विफल जाँच किसी भी कॉन्फ़िगरेशन के लिखे जाने से पहले और इंस्टॉलर के
`APOTHEM_HOME` को बदलने से पहले इंस्टॉल को निरस्त कर देती है। जिस हस्ताक्षरित
टैग के मेंटेनर की सार्वजनिक कुंजी अभी स्थानीय कीरिंग में नहीं है, वह इसके बजाय
कुंजी-आयात मार्गदर्शन के साथ इंस्टॉल को निरस्त कर देता है: ऊपर दिखाए अनुसार
कुंजी आयात करें, उसके फ़िंगरप्रिंट की तुलना
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md) में
प्रकाशित मान से करें, और फिर से चलाएँ।

cosign के साथ फिर से चलाना पहले के रिलीज़-आर्काइव इंस्टॉल को अपडेट करता है। नया
स्रोत पहले `~/.apothem` के बगल के एक फ़ोल्डर में जाँचा और अनपैक किया जाता है,
फिर उसकी जगह बदल दिया जाता है। `~/.apothem` में जो कुछ भी स्रोत ट्री का हिस्सा
नहीं है, वह नए इंस्टॉल में आ जाता है: इंजन के रोलबैक बैकअप (`backups/`), इंस्टॉल
लेजर (`state/`), प्लान, मेमोरी और उसका अन्य डेटा। यदि कोई चरण विफल होता है या आप
Ctrl+C या समाप्ति सिग्नल से रन रोकते हैं, तो पहले का इंस्टॉल बिना बदले वापस रख
दिया जाता है; यदि वह भी विफल हो, तो संदेश बताता है कि पहले की फ़ाइलें कहाँ हैं।
अदला-बदली के दौरान जबरन किल या बिजली जाने को पकड़ा नहीं जा सकता: वह `~/.apothem`
के बगल में फ़ोल्डर छोड़ सकता है, और अगला फ़ेच किया गया इंस्टॉल उनकी रिपोर्ट करता
है (नीचे देखें)। जब इंस्टॉलर `~/.apothem` को बदलता है, तब ये नियम लागू होते हैं:

- git क्लोन को `--yes` के बिना रिलीज़ आर्काइव से नहीं बदला जाता। क्लोन जिन
  फ़ाइलों को ट्रैक नहीं करता वे नए इंस्टॉल में चली जाती हैं, और क्लोन का अपना
  ट्री (उसका इतिहास और स्रोत) एक नए फ़ोल्डर,
  `~/.apothem.before-apothem-<time>`, में अपने ही नाम (`.apothem`) के अंतर्गत चला
  जाता है; इंस्टॉलर बताता है कि कहाँ, और जब आपको उसकी आवश्यकता न रहे तब आप उसे
  हटा देते हैं। `--yes` के साथ भी, इंस्टॉलर तब मना कर देता है जब क्लोन में ऐसा
  स्थानीय काम हो जिसे वह खो देगा: बदलाव, स्टैश, अनपुश किए गए कमिट, या उसके स्रोत
  ट्री में अनट्रैक्ड फ़ाइलें। उस काम को कमिट और पुश करें, या उसे कहीं और ले जाएँ,
  फिर से चलाएँ। यह जाँच `--dry-run` के साथ भी चलती है। `.git` फ़ाइल (एक लिंक्ड
  वर्कट्री) क्लोन गिनी जाती है, और `.git` फ़ोल्डर भी।
- Apothem के अलावा किसी भी चीज़ का git क्लोन उस किसी भी फ़ोल्डर की तरह माना जाता
  है जिसमें कोई Apothem इंस्टॉल नहीं है (नीचे देखें), क्लोन के रूप में कभी अपडेट
  या बदला नहीं जाता।
- मौजूदा क्लोन को उसी स्थान पर केवल तब अपडेट किया जाता है जब git उसका हर बदलाव
  देख सके और उसके अपने सेटअप में कुछ भी अपडेट के दौरान कोड न चलाए। फ़ेच से पहले,
  इंस्टॉलर रुक जाता है जब फ़ाइलें assume-unchanged या skip-worktree चिह्नित हों,
  जब git को `APOTHEM_HOME` में कोई वर्क ट्री न मिले (जैसे जब क्लोन का कॉन्फ़िग
  `core.bare` को `true` सेट करता हो), जब क्लोन में कोई सबमॉड्यूल हो (उसके इंडेक्स
  में दर्ज, या `.git/modules` में रखा हुआ), जब `.git/info/attributes` किसी फ़िल्टर
  या diff ड्राइवर (`filter=` या `diff=`) का नाम देता हो, जब वह या कोई कॉन्फ़िग फ़ाइल
  साधारण फ़ाइल न हो, या जब क्लोन किसी अन्य रिपॉज़िटरी से ऑब्जेक्ट उधार लेता हो
  (`objects/info/alternates`)। वह क्लोन की अपनी `.git/config` या
  `.git/config.worktree` में किसी भी ऐसी सेटिंग पर भी रुक जाता है जो पूर्ण क्लोन के
  लिए `git clone` और `git init` द्वारा वहाँ लिखी गई सेटिंग, ब्रांच सेटिंग (किसी
  ब्रांच का `remote` और `pushremote` `origin` होना चाहिए), `user.name`,
  `user.email`, `maintenance.auto`, `maintenance.strategy`, `pull.rebase` और
  `pull.ff` से अलग हो, इसलिए `--filter` से बना आंशिक क्लोन भी रुक जाता है;
  [समस्या निवारण](/docs/install/troubleshooting#the-installer-stops-the-existing-clone-is-set-up-in-a-way-the-update-would-trust)
  उन्हें सूचीबद्ध करता है। संदेश सेटिंग और उस फ़ाइल का नाम देता है जिसमें वह है।
  सेटिंग, एट्रिब्यूट और ऑब्जेक्ट जाँचें किसी भी ऐसी git कमांड से पहले चलती हैं जो
  क्लोन का इंडेक्स या ऑब्जेक्ट पढ़ती है, और सबमॉड्यूल जाँच के साथ तब भी, जब
  `--yes` क्लोन को बदलने वाला हो।
  किसी भी ऐसी git कमांड से पहले जो वर्क ट्री की `.gitattributes` फ़ाइलें लागू करती
  है, इंस्टॉलर ऐसी फ़ाइल पर रुक जाता है जिसे git ट्रैक नहीं करता, जो कमिट की गई
  प्रति से भिन्न है, या जिसकी कमिट की गई प्रति git पढ़ नहीं सकता या जो किसी फ़िल्टर
  या diff ड्राइवर का नाम देती है (वर्क ट्री की प्रति भी पढ़ी जाती है), और क्लोन में
  ऐसी git रिपॉज़िटरी पर जिसे git ट्रैक नहीं करता, जिसकी `.gitattributes` फ़ाइलें
  git भी पढ़ेगा। इंजन के अपने डेटा फ़ोल्डर, जैसे `backups`, जहाँ कोई रिलीज़ नहीं
  लिखती, इनके लिए नहीं पढ़े जाते। फ़ेच से पहले वह `src` के अंतर्गत (किसी भी
  केस में लिखे गए) उन फ़ाइलों पर रुक जाता है जिन्हें git ट्रैक नहीं करता, क्योंकि
  इंजन उन्हें लोड कर सकता है। चेकआउट के बाद, वह क्लोन से इंजन चलने से पहले
  `src` के अंतर्गत Python कैश फ़ोल्डर (`__pycache__`) हटा देता है। क्लोन के git
  हुक अपडेट के दौरान कभी नहीं चलते, और क्लोन पर हर git कमांड बिना पेजर, बिना
  स्वचालित रखरखाव, फ़ाइल-सिस्टम मॉनिटर बंद रखकर, केवल file, git, http, https और
  ssh ट्रांसपोर्ट की अनुमति के साथ (ताकि क्लोन के कॉन्फ़िग का कोई पता git से
  `ext::` जैसा कोई सहायक प्रोग्राम न चलवा सके) और बिना सबमॉड्यूल रिकर्शन के चलती
  है; `git diff` और `git status` सबमॉड्यूल छोड़ देते हैं। किसी अन्य उपयोगकर्ता के
  स्वामित्व वाला क्लोन स्पष्टीकरण के साथ रन रोक देता है (समस्या निवारण देखें)।
- जिस फ़ोल्डर में केवल इंजन का अपना डेटा (`backups`, `state`, `plans`, `memory`,
  `contexts`, `learning`, `providers`) हो, उसे `--yes` के बिना अपडेट किया जाता है,
  और वह डेटा रखा जाता है।
- जिस फ़ोल्डर में कोई Apothem इंस्टॉल नहीं है, उसे `--yes` के बिना छुआ नहीं जाता।
  `--yes` के साथ, इंस्टॉलर पूरे फ़ोल्डर को, बिना बदले, एक नए फ़ोल्डर,
  `~/.apothem.before-apothem-<time>` में ले जाता है (भीतर वह अपना नाम रखता है),
  बताता है कि कहाँ, और नए सिरे से इंस्टॉल करता है।
- `APOTHEM_HOME` पर सिम्बॉलिक लिंक (Windows पर, सिम्बॉलिक लिंक या जंक्शन)
  अस्वीकार कर दिया जाता है, क्योंकि उसे बदलने से लिंक बदल जाएगा, वह फ़ोल्डर नहीं
  जिस तक वह ले जाता है। `APOTHEM_HOME` को उस फ़ोल्डर की ओर इंगित करें और फिर से
  चलाएँ। अपवाद मौजूदा git क्लोन है, जिसे उसी स्थान पर अपडेट किया जाता है।
- Linux और macOS पर, आगे ले जाई जाने वाली कोई फ़ाइल या फ़ोल्डर जिसके नाम में स्पेस
  या कोई अन्य विशेष वर्ण हो, इंस्टॉल रोक देता है। पहले उसे `APOTHEM_HOME` से बाहर
  ले जाएँ।

**एक समय में एक रन, और रोके गए रन।** install, update और uninstall
स्क्रिप्ट का हर रन पूरे रन के लिए `APOTHEM_HOME` के बगल में एक लॉक लेता है,
डिफ़ॉल्ट रूप से `~/.apothem.lock`, और रन के सफलता, विफलता, Ctrl+C या समाप्ति
सिग्नल से समाप्त होने पर उसे छोड़ देता है। `apothem` कमांड स्वयं इसे नहीं लेतीं।
दूसरा रन "Another Apothem install, update or uninstall is running" के साथ रुक
जाता है। POSIX पर लॉक एक फ़ोल्डर है जिसमें रन की प्रोसेस ID होती है। किल किए गए
रन द्वारा छोड़े गए लॉक की रिपोर्ट उसे हटाने के तरीके के साथ की जाती है और उसे
कभी अपने हाथ में नहीं लिया जाता, और किसी अन्य परिवेश (मान लीजिए, एक ही मशीन पर
WSL और Git Bash) में बने लॉक की रिपोर्ट ऐसे लॉक के रूप में की जाती है जिसकी
प्रोसेस वहाँ से जाँची नहीं जा सकती। Windows PowerShell पर लॉक एक फ़ाइल है जिसे
प्रोसेस समाप्त होने पर Windows बंद करके हटा देता है। जब `APOTHEM_HOME` एक लिंक
हो, तो हर स्क्रिप्ट उस फ़ोल्डर के बगल में लॉक लेती है जिस तक वह ले जाता है। ड्राई
रन भी लॉक लेता है, जब तक कि `APOTHEM_HOME` को रखने वाला फ़ोल्डर अभी मौजूद न हो।
इसलिए हर रन को, जिसमें उसी स्थान पर अपडेट, अनइंस्टॉल और ड्राई रन शामिल हैं,
`APOTHEM_HOME` को रखने वाले फ़ोल्डर में लिखने की पहुँच चाहिए; उसके बिना रन कुछ भी
बदलने से पहले रुक जाता है।

अदला-बदली के दौरान जबरन किल या बिजली जाना पहले के इंस्टॉल या `APOTHEM_HOME` की
अन्य प्रविष्टियों को उसके बगल में `.apothem-old.<name>.*`,
`.apothem-extract.<name>.*` या `.apothem-clone.<name>.*` में छोड़ सकता है, जहाँ
`<name>` `APOTHEM_HOME` का अंतिम भाग है, या किसी
`APOTHEM_HOME.before-apothem-<time>` फ़ोल्डर में। उस `APOTHEM_HOME` के लिए अगला
फ़ेच किया गया इंस्टॉल, ड्राई रन सहित, कुछ भी बदलने से पहले रुक जाता है, हर
फ़ोल्डर और उसमें ले जाई गई प्रविष्टियों का नाम देता है, और बताता है कि उन्हें
वापस कैसे ले जाएँ। किसी पहले के इंस्टॉलर द्वारा बनाए गए फ़ोल्डर के लिए, जो यह नहीं
बताता कि वह किस होम का है, पंक्ति केवल इंजन डेटा का नाम दे सकती है: उसके भीतर
देखें। वह कुछ भी नहीं हटाता। देखें
[समस्या निवारण](/docs/install/troubleshooting#the-installer-stops-an-earlier-run-left-folders-beside-apothem_home)।

`--dry-run` (Windows पर `-DryRun`) एक अस्थायी फ़ोल्डर में रिलीज़ को फ़ेच और जाँचता
है और `~/.apothem` को बिना बदले छोड़ता है। वह वास्तविक रन जैसी ही जाँचें करता है,
मौजूदा क्लोन के लिए एक अपवाद के साथ: वह ऊपर सूचीबद्ध अनुसार क्लोन के अपने सेटअप
की जाँच करता है, लेकिन क्लोन में फ़ेच नहीं करता, और इसलिए ट्रैक की गई फ़ाइलों में
बदलावों के लिए उसकी जाँच नहीं करता, जो एक वास्तविक अपडेट अपने फ़ेच के बाद करता
है। `APOTHEM_REF` से किसी विशिष्ट रिलीज़ को पिन करें:

```bash title="Pinned, verified install"
APOTHEM_REF=vMAJOR.MINOR.PATCH sh -c "$(curl -fsSL https://apothem.ahmedgad.com/install.sh)"
```

`vMAJOR.MINOR.PATCH` को
[रिलीज़ पृष्ठ](https://github.com/ahmed-g-gad/apothem/releases) के किसी टैग से
बदलें। सबसे पुराना रिलीज़ टैग एक लाइटवेट टैग है जिसका अपना कोई हस्ताक्षर नहीं है,
इसलिए टैग जाँच उस पर इंस्टॉल निरस्त कर देती है, भले ही उसका कमिट हस्ताक्षरित हो; उसके
बाद का हर रिलीज़ टैग एनोटेटेड और हस्ताक्षरित है।
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md) का
रिलीज़-हस्ताक्षर अनुभाग हर टैग और उसे सत्यापित करने का तरीका सूचीबद्ध करता है।

स्पष्ट ओवरराइड डिफ़ॉल्ट को शिथिल करते हैं। `APOTHEM_ALLOW_UNVERIFIED=1` क्लोन पथ
पर विफल टैग जाँच को चेतावनी में घटाकर आगे बढ़ता है — एयर-गैप्ड या स्थानीय उपयोग
के लिए, या ऐसी रिलीज़ इंस्टॉल करने के लिए जो टैग हस्ताक्षर से पहले की है। यह cosign
पथ को कभी शिथिल नहीं करता, इसलिए cosign वाले होस्ट पर इसके साथ
`APOTHEM_VERIFY=signature` सेट करें। यह इस जाँच को भी कभी शिथिल नहीं करता कि
हस्ताक्षरित टैग वही है जिसका नाम उस रिलीज़ के लिए है। चूँकि ओवरराइड किसी
बिना-हस्ताक्षर वाले टैग, या किसी अन्य कुंजी से हस्ताक्षरित टैग को आगे जाने देता
है, वह जाँच केवल उन टैग की रक्षा करती है जिन पर मेंटेनर कुंजी का हस्ताक्षर है।
`APOTHEM_REF=main` चलती हुई ब्रांच को सत्यापन के बिना केवल
`APOTHEM_ALLOW_UNVERIFIED=1` के साथ ही चेकआउट करता है। अकेले `APOTHEM_REF=main`
के साथ, इंस्टॉलर `main` को एक स्टेजिंग फ़ोल्डर में फ़ेच करता है (जब
`APOTHEM_HOME` एक मौजूदा क्लोन हो, तो उसी क्लोन में), फिर कुछ भी चेकआउट करने,
`APOTHEM_HOME` को बदलने या किसी भी कॉन्फ़िगरेशन को मूर्त रूप देने से पहले निरस्त
कर देता है, क्योंकि ब्रांच एक हस्ताक्षरित रिलीज़ टैग नहीं होती। `APOTHEM_SOURCE`
के माध्यम से स्थानीय चेकआउट कुछ भी फ़ेच नहीं करता और सत्यापन छोड़ देता है।

जाँच स्वयं चुनने के लिए `APOTHEM_VERIFY` सेट करें। डिफ़ॉल्ट `auto` है:

| मान | इंस्टॉलर क्या जाँचता है |
| --- | --- |
| `auto` (डिफ़ॉल्ट) | `release` जब `cosign` `PATH` पर हो और `APOTHEM_HOME` git क्लोन न हो, अन्यथा `signature` |
| `release` | मेंटेनर कुंजी से रिलीज़ टैग का हस्ताक्षर और यह कि हस्ताक्षरित टैग वही है जिसका नाम उस रिलीज़ के लिए है, फिर cosign की यह जाँच कि रिलीज़ वर्कफ़्लो ने टैग के कमिट पर चले रन में `SHA256SUMS` पर हस्ताक्षर किए, फिर आर्काइव का SHA-256। cosign या `gpg` अनुपस्थित होने पर रुक जाता है |
| `signature` | रिलीज़ टैग का GPG हस्ताक्षर, जो मेंटेनर कुंजी से आना चाहिए, और यह कि हस्ताक्षरित टैग वही है जिसका नाम उस रिलीज़ के लिए है |
| `checksum` | केवल `SHA256SUMS` के विरुद्ध आर्काइव का SHA-256। `APOTHEM_ALLOW_UNVERIFIED=1` आवश्यक है, और डाउनलोड से पहले चेतावनी देता है। checksum मोड रिलीज़ को सत्यापित नहीं करता। SHA256SUMS आर्काइव वाली उसी रिलीज़ से आता है, इसलिए मेल केवल यह दिखाता है कि डाउनलोड क्षतिग्रस्त नहीं है; जो कोई भी रिलीज़ की फ़ाइलें बदल सकता है, वह दोनों बदल सकता है। इसका उपयोग केवल ऐसे होस्ट पर करें जिस पर न cosign हो न `gpg`, और केवल तब जब आप यह स्वीकार करते हों |

हर आर्काइव मोड कुछ भी निकालने से पहले डाइजेस्ट बेमेल होने पर निरस्त कर देता है।
शुरुआती रिलीज़ बंडल का नाम `SHA256SUMS.sig` रखती हैं, और जब
`SHA256SUMS.cosign.bundle` अनुपस्थित हो तो इंस्टॉलर वह नाम पढ़ता है।

इसके बाद इंजन रखे गए ट्री से सीधे चलता है। `click` और `rich` को छोड़कर हर
तृतीय-पक्ष निर्भरता स्रोत ट्री के भीतर वेंडर की गई है, और एंट्री पॉइंट उस वेंडर
डायरेक्टरी को स्वयं `sys.path` पर रखता है। इंस्टॉलर अपने लिखे `apothem` शिम का
पूरा पथ प्रिंट करता है। जब उसने कोई शिम नहीं लिखा, तो वह एक कमांड प्रिंट करता है
जो वर्तमान फ़ोल्डर को `sys.path` से बाहर रखकर इंजन शुरू करती है; वह कमांड बैनर से
कॉपी करें।

दोनों स्क्रिप्ट एक ही कॉन्फ़िगरेशन पर्यावरण चर पढ़ती हैं (`APOTHEM_HOME`,
`APOTHEM_REPO`, `APOTHEM_REF`, `APOTHEM_ALLOW_UNVERIFIED`,
`APOTHEM_VERIFY`, `APOTHEM_RELEASE_BASE`, `APOTHEM_SOURCE`, `APOTHEM_HARNESS`, `APOTHEM_PROFILE`,
`APOTHEM_SKIP_VERIFY`, `APOTHEM_AUTO_INSTALL_DEPS`, `APOTHEM_BIN_DIR`); पूर्ण तालिका
के लिए
[इंस्टॉलर पर्यावरण चर](/docs/how-to/installer-environment-variables) देखें और
`python -m` आह्वान मॉडल कैसे काम करता है, इसके लिए
[स्व-निहित रनटाइम](/docs/architecture/self-contained-runtime) देखें।

**`apothem` कमांड।** सफल इंस्टॉल के बाद, इंस्टॉलर एक `apothem` शिम लिखता है जो
बंडल किए गए इंजन को अग्रेषित करता है — POSIX पर `$HOME/.local/bin` में, Windows पर
`%LOCALAPPDATA%\Microsoft\WindowsApps` में (एक उपयोगकर्ता डायरेक्टरी जो पहले से
डिफ़ॉल्ट Windows `PATH` पर है)। इंस्टॉलर कभी भी आपके `PATH` को संपादित नहीं करता।
डायरेक्टरी के `PATH` पर आ जाने के बाद आप बिना किसी मैनुअल `PYTHONPATH` के सीधे
`apothem <command>` चलाते हैं।

**सत्यापित करें:**

```bash title="Verify"
apothem verify --harness claude-code

# or, before the shim is on PATH, by the shim's full path:
~/.local/bin/apothem verify --harness claude-code
```

## 4. VS Code परिवार एक्सटेंशन

**पूर्वापेक्षाएँ:** VS Code, Node.js 18+, और `PATH` पर सिस्टम Python 3.10+।

**Apothem for VS Code** एक्सटेंशन [Visual Studio Marketplace](https://marketplace.visualstudio.com/items?itemName=ahmed-g-gad.apothem-vscode) पर
`ahmed-g-gad.apothem-vscode` के रूप में उपलब्ध है: इसे एक्सटेंशन व्यू से या
`code --install-extension ahmed-g-gad.apothem-vscode` से इंस्टॉल करें। यह एक
`apothem.vsix` पैकेज से भी इंस्टॉल होता है:
`code --install-extension apothem.vsix`, या संपादक का *Install from VSIX…*
कमांड। रिलीज़ वर्कफ़्लो पैकेज पर हस्ताक्षर करता है और उसे हर GitHub Release से
संलग्न करता है। जो रिलीज़ वर्कफ़्लो द्वारा एक्सटेंशन को पैकेज किए जाने से पहले प्रकाशित हुईं,
उनमें कोई `.vsix` नहीं होता; जब नवीनतम रिलीज़ में यह न हो, तो किसी चेकआउट से
`tools/vsce/` में लॉक की गई vsce रिलीज़ के साथ पैकेज बिल्ड करें (उस vsce रिलीज़ के लिए
Node.js 22 या उसके बाद का संस्करण चाहिए):
`npm ci --prefix tools/vsce --ignore-scripts` चलाएँ, फिर
`cd vscode-extension && ../tools/vsce/node_modules/.bin/vsce package --no-dependencies --out apothem.vsix`
चलाएँ। पहले के `apothem.vsix` से इंस्टॉल की गई प्रति पहचानकर्ता `ahmed-g-gad.apothem`
रखती है; उसे अनइंस्टॉल करें (`code --uninstall-extension ahmed-g-gad.apothem`), ताकि
दोनों प्रतियाँ एक साथ एक ही कमांड पंजीकृत न करें। एक ही एक्सटेंशन VS Code परिवार के संपादकों को कवर करता है।
इसके पैलेट कमांड
(`Apothem: Install`, `Verify`,
`Update`, `Uninstall`, `Doctor`) कॉन्फ़िगर किए गए रनर के माध्यम से वही इंजन चलाते
हैं (डिफ़ॉल्ट रूप से `npx @ahmed-g-gad/apothem@<extension version>`, ताकि
एक्सटेंशन वही इंजन संस्करण चलाए जिसके साथ वह शिप हुआ था; स्रोत से चलाने के लिए
`apothem.runner` उपयोगकर्ता सेटिंग को किसी स्थानीय चेकआउट की ओर इंगित करें)।
Install, Verify, Update और Uninstall पूछते हैं कि किस हार्नेस पर कार्य करना है, और
संपादक का अपना हार्नेस पहले प्रस्तुत करते हैं; `all` एक विकल्प है, कभी डिफ़ॉल्ट
नहीं। `apothem.runner` सेटिंग मशीन-स्कोप वाली है, इसलिए कोई वर्कस्पेस इसे बदल
नहीं सकता, और एक्सटेंशन केवल किसी विश्वसनीय वर्कस्पेस में चलता है।

**सत्यापित करें:** संपादक के कमांड पैलेट से **Apothem: Verify** कमांड चलाएँ, या
किसी टर्मिनल से:

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 7. कमांड-लाइन बूटस्ट्रैप (प्लगइन होस्ट)

**पूर्वापेक्षाएँ:** इसका होस्ट कमांड-लाइन टूल, Node.js 18+, और `PATH` पर सिस्टम

रिपॉज़िटरी को एक प्लगइन मार्केटप्लेस के रूप में जोड़ें, फिर प्लगइन इंस्टॉल करें —

```bash title="Install the plugin"
codex plugin marketplace add ahmed-g-gad/apothem --sparse .agents/plugins --sparse plugins/apothem
codex plugin add apothem@apothem
```

दोनों `--sparse` पथ पूरी रिपॉज़िटरी के बजाय केवल मार्केटप्लेस सूची और प्लगइन फ़ेच
करते हैं; धीमी डिस्क पर, जैसे WSL के अंतर्गत एक Windows ड्राइव पर, पूर्ण क्लोन होस्ट
की 30-सेकंड की क्लोन सीमा से आगे जा सकता है।

चैनल-5 और चैनल-6 एक्सटेंशन की तरह, यह एक **बूटस्ट्रैप** है जो इंजन को शेल-आउट
करता है। प्लगइन एक प्रवेश स्किल बंडल करता है; इसका मैनिफ़ेस्ट एक रूट
`plugin.json` है, और
[प्लगइन होस्ट का हार्नेस पृष्ठ](/docs/harnesses/codex#codex-plugin) लेआउट का और
इसका वर्णन करता है कि प्लगइन इंजन पर क्या छोड़ता है। इसके माध्यम से इंस्टॉल चलाकर
पूर्ण हार्नेस को मूर्त रूप दें:


## 8. प्रत्यक्ष इंजन (`python -m apothem`)

**पूर्वापेक्षाएँ:** सिस्टम Python 3.10+, जिसमें `click` और `rich` पैकेज आयात-योग्य
हों, साथ ही रिपॉज़िटरी का एक चेकआउट। Node.js की आवश्यकता नहीं।

इंजन को सीधे किसी क्लोन से चलाएँ। एंट्री पॉइंट वेंडर की गई निर्भरताओं
(`src/apothem/_vendor`) को `sys.path` पर रखता है, इसलिए `click` और `rich`
आयात-योग्य होने पर `PYTHONPATH=src` ही पूरा सेटअप है:

```bash title="Direct engine"
git clone https://github.com/ahmed-g-gad/apothem
cd apothem
PYTHONPATH=src python -m apothem install --harness claude-code
```

`python -m` वर्तमान फ़ोल्डर को Python के मॉड्यूल खोज पथ में सबसे पहले रखता है,
इसलिए वहाँ की कोई फ़ाइल जैसे `click.py`, या `apothem` नाम का कोई फ़ोल्डर, असली
मॉड्यूल के स्थान पर चल जाएगा। ये कमांड चेकआउट रूट से, या किसी अन्य ऐसे फ़ोल्डर से
चलाएँ जिस पर आप भरोसा करते हैं। इंस्टॉल की गई `apothem` कमांड वर्तमान फ़ोल्डर को
नहीं पढ़ती।

npm शिम की तरह, बिना प्रोफ़ाइल वाली मशीन पर पहला `install`
`~/.config/apothem/profile.yaml` पर प्रारंभिक प्रोफ़ाइल बनाता है और आगे बढ़ता है।

**सत्यापित करें:**

```bash title="Verify"
PYTHONPATH=src python -m apothem verify --harness claude-code
```

हार्नेस के नाम को उस अडैप्टर से बदलें जिसे आपने इंस्टॉल किया है; सभी समर्थित नामों
के लिए [हार्नेस सूची](/docs/harnesses) देखें। हर इंस्टॉल किए गए अडैप्टर को एक साथ
जाँचने के लिए (उसकी सत्यापन जाँच और उसके हुक कमांड), ऊपर जिस रूप का आपने उपयोग किया
उसी रूप में `verify --harness NAME` के स्थान पर `doctor` चलाएँ:
`apothem doctor` (या शिम का पूरा पथ, या इंस्टॉलर द्वारा प्रिंट की गई कमांड, जब
उसका फ़ोल्डर `PATH` पर न हो), या
`npx @ahmed-g-gad/apothem doctor`। प्लगइन पथ के लिए, Claude Code के
भीतर `/plugin` चलाएँ और पुष्टि करें कि **apothem** इंस्टॉल के रूप में सूचीबद्ध है।

## पूर्वापेक्षाएँ एक नज़र में

- **Python 3.10 या उसके बाद का** — जो पथ इसे खोजते हैं वे नाम से खोजते हैं, और नाम
  पथ के अनुसार भिन्न होते हैं। npm शिम `python3`, `python`, फिर `py -3` आज़माता है।
  इंस्टॉलर `python3`, `python`, और संस्करण-युक्त नाम `python3.14` से लेकर
  `python3.10` तक आज़माते हैं।
- उस इंटरप्रेटर के अंतर्गत **`click` और `rich` आयात-योग्य** — वे दो टर्मिनल-उन्मुख
  निर्भरताएँ जिन्हें इंजन वेंडर नहीं करता। इंस्टॉलर दोनों की जाँच करते हैं, जो भी
  अनुपस्थित हो उसका नाम बताते हैं, और उसे आपके लिए इंस्टॉल करने की पेशकश करते हैं
  — आपकी पुष्टि के साथ, या `--yes` (PowerShell पर `-Yes`) या
  `APOTHEM_AUTO_INSTALL_DEPS=1` के साथ स्वचालित रूप से। हर अन्य चैनल पर, कोई
  अनुपस्थित पैकेज इंजन को एक त्रुटि (exit 1) के साथ रोक देता है, जो मिले हुए
  इंटरप्रेटर के लिए सटीक कमांड बताती है, उन संस्करण बाधाओं के साथ जिनके विरुद्ध
  Apothem का परीक्षण होता है (`<interpreter> -m pip install "click==…" "rich>=…"`);
  `--json` के साथ वही त्रुटि `runtime.dependency_missing` कोड वाले एक JSON
  लिफ़ाफ़े के रूप में आती है।
- **Node.js 18 या उसके बाद का** — केवल वे पथ जो `npx` चलाते हैं: npm शिम (2),
  VS Code-परिवार एक्सटेंशन (4), और कमांड-लाइन बूटस्ट्रैप (5–7)।
- **जीवन-अंत तक पहुँच चुके रनटाइम।** Python 3.10 2026-10-01 को अपस्ट्रीम
  जीवन-अंत तक पहुँचा, और Node.js 18 और 20 क्रमशः 2025-04-30 और 2026-04-30 को।
  Apothem अब भी उन्हें अपने घोषित फ़्लोर के रूप में समर्थन देता है और CI में
  प्रत्येक का परीक्षण करता है, लेकिन उन्हें अब अपस्ट्रीम सुरक्षा सुधार नहीं मिलते,
  इसलिए Python 3.11 या नए और Node.js 22 या नए को प्राथमिकता दें।
  [रनटाइम-फ़्लोर नीति](/docs/governance/release-engineering-policy#runtime-floors)
  बताती है कि कोई फ़्लोर कैसे बढ़ाया जाता है।
- **Git और GnuPG** — केवल इंस्टॉलर पथ, और केवल नेटवर्क रूप के लिए (स्क्रिप्ट
  इनसे नवीनतम रिलीज़ खोजती है और उसके हस्ताक्षरित टैग की जाँच करती है, और cosign
  के बिना स्रोत को क्लोन करती है; स्थानीय चेकआउट को इनमें से किसी की आवश्यकता नहीं
  होती)।
- **Claude Code** — केवल प्लगइन पथ। **VS Code** और प्रत्येक कमांड-लाइन बूटस्ट्रैप
  का अपना होस्ट टूल केवल अपने-अपने चैनल (4–7) के लिए आवश्यक हैं।
