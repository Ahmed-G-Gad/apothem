## Claude Code प्लगइन अपडेट करें

मार्केटप्लेस लिस्टिंग रिफ़्रेश करें, फिर Claude Code के भीतर `/plugin`
मेन्यू से प्लगइन अपडेट करें:

```text title="Inside Claude Code"
/plugin marketplace update apothem
```

`/plugin` खोलें, **apothem** चुनें, और जब कोई नया प्लगइन संस्करण सूचीबद्ध हो तो
अपडेट क्रिया चुनें।

## VS Code एक्सटेंशन अपडेट करें

एक्सटेंशन वही इंजन संस्करण चलाता है जिसके साथ वह शिप हुआ था। उसका डिफ़ॉल्ट रनर
`npx @ahmed-g-gad/apothem@<extension version>` है, इसलिए आपको नया इंजन तभी मिलता है
जब एक्सटेंशन स्वयं अपडेट होता है।

VS Code एक्सटेंशन अपडेट जाँचता है और उन्हें अपने आप इंस्टॉल करता है, जैसा उसके
[एक्सटेंशन ऑटो-अपडेट](https://code.visualstudio.com/docs/configure/extensions/extension-marketplace#_extension-auto-update)
दस्तावेज़ बताते हैं। डिफ़ॉल्ट रूप से वह किसी अपडेट के प्रकाशित होने के बाद 12 घंटे
प्रतीक्षा करता है। उसे तुरंत इंस्टॉल करने के लिए, एक्सटेंशन व्यू में एक्सटेंशन का
**Update** बटन चुनें। यदि आपने ऑटो-अपडेट बंद किया है, तो **Show Extension Updates**
कमांड चलाएँ और **Update** चुनें, या **Update All Extensions** चलाएँ।

VS Code किसी `.vsix` फ़ाइल से इंस्टॉल किए गए एक्सटेंशन के लिए ऑटो-अपडेट बंद कर देता
है। यदि आपने `apothem.vsix` इंस्टॉल किया था, तो नई
[GitHub Release](https://github.com/ahmed-g-gad/apothem/releases) से संलग्न
`apothem.vsix` को उसी तरह इंस्टॉल करें।

## npx हमेशा वर्तमान रिलीज़ चलाता है

`npx @ahmed-g-gad/apothem` हर रन पर वर्तमान प्रकाशित पैकेज को रिज़ॉल्व करता है,
इसलिए अपडेट करने के लिए कुछ नहीं है। जब कोई बासी npx कैश पुरानी प्रति परोसे,
तो dist-tag को स्पष्ट रूप से पिन करें:

```bash
npx @ahmed-g-gad/apothem@latest --version
```

## इंस्टॉलर-आधारित सेटअप अपडेट करें

इंस्टॉलर को फिर से चलाएँ — यह आइडेम्पोटेंट है: यह मौजूदा git क्लोन को फ़ेच करता है,
नया रिलीज़ टैग जाँचता है, और उसके बाद ही क्लोन को चेक आउट करता है, और यह रिलीज़-आर्काइव
इंस्टॉल को अपडेट करता है — या समर्पित अपडेट स्क्रिप्ट चलाएँ, जो git क्लोन पर काम करती
है:

```bash title="macOS · Linux · WSL2 · BSD"
bash scripts/installer/update.sh
```

```powershell title="Windows · PowerShell"
pwsh -NoProfile -File scripts/installer/update.ps1
```

अपडेट स्क्रिप्ट `APOTHEM_HOME` (डिफ़ॉल्ट `~/.apothem`) पर स्रोत ट्री को
`APOTHEM_REF` पर ले जाती है — अनसेट होने पर नवीनतम हस्ताक्षरित
`vMAJOR.MINOR.PATCH` रिलीज़ टैग रिज़ॉल्व होता है, टैग मान उसे पिन करता है, और `main`
चलती हुई ब्रांच को तभी चुनता है जब `APOTHEM_ALLOW_UNVERIFIED=1` भी सेट हो। उस
ओवरराइड के बिना, अपडेट कुछ भी चेक आउट करने या फिर से मटेरियलाइज़ करने से पहले निरस्त
हो जाता है, क्योंकि ब्रांच हस्ताक्षरित रिलीज़ टैग नहीं होती। यह पहले ref को फ़ेच करता
है और चेकआउट से पहले `git verify-tag` से टैग के हस्ताक्षर का सत्यापन करता है, इसलिए
विफल जाँच क्लोन को उसी संस्करण पर छोड़ती है जिस पर वह था। हस्ताक्षर SECURITY.md में
प्रकाशित मेंटेनर कुंजी से बना होना चाहिए, और हस्ताक्षरित टैग वही होना चाहिए जिसका नाम
रिलीज़ के लिए है; अहस्ताक्षरित या छेड़छाड़ किया गया टैग, या किसी अन्य कुंजी से
हस्ताक्षरित टैग, तब तक निरस्त करता है जब तक `APOTHEM_ALLOW_UNVERIFIED=1` निरस्तीकरण को
चेतावनी में न बदल दे (वह वेरिएबल इस जाँच को नहीं छोड़ता कि हस्ताक्षरित टैग रिलीज़ टैग
है)। क्योंकि वह वेरिएबल अहस्ताक्षरित टैग, या किसी अन्य कुंजी से हस्ताक्षरित टैग, को
आगे जाने देता है, इसलिए जाँच केवल उन टैग की रक्षा करती है जिन पर मेंटेनर कुंजी का
हस्ताक्षर है। `main` जैसे गैर-रिलीज़ ref के साथ, क्लोन origin की उस ब्रांच की प्रति का
अनुसरण करता है। चेकआउट कभी स्थानीय बदलाव नहीं मिटाता: ट्रैक की गई फ़ाइलों में बदलाव
वाला क्लोन अपडेट रोक देता है, और आप उन्हें कमिट या stash करके फिर से चलाते हैं। फ़ेच
करने से पहले, अपडेट तब भी रुकता है जब फ़ाइलें assume-unchanged या skip-worktree
चिह्नित हों (git उनके बदलाव नहीं देखेगा), जब क्लोन का वर्क ट्री `APOTHEM_HOME` न हो, जब
क्लोन में कोई सबमॉड्यूल हो, जब `.git/info/attributes` किसी filter या diff ड्राइवर
(`filter=` या `diff=`) का नाम लेता हो, जब वह या कोई config फ़ाइल सादी फ़ाइल न हो, जब
क्लोन किसी अन्य रिपॉज़िटरी से ऑब्जेक्ट उधार लेता हो (`objects/info/alternates`), या जब
क्लोन की `.git/config` या `.git/config.worktree` में इनके अलावा कोई सेटिंग हो: वे
सेटिंग्स जो `git clone` और `git init` किसी पूर्ण क्लोन के लिए वहाँ लिखते हैं, ब्रांच
सेटिंग्स (किसी ब्रांच का `remote` और `pushremote` `origin` होना चाहिए), `user.name`,
`user.email`, `maintenance.auto`, `maintenance.strategy`, `pull.rebase` और
`pull.ff`। `--filter` से बना आंशिक क्लोन भी वहीं रुकता है। संदेश सेटिंग और जिस फ़ाइल में
वह है उसका नाम बताता है, और
[समस्या निवारण](/docs/install/troubleshooting#the-installer-stops-the-existing-clone-is-set-up-in-a-way-the-update-would-trust)
स्वीकृत सेटिंग्स सूचीबद्ध करता है। यह फ़ेच से पहले तब भी रुकता है जब वर्क ट्री में कोई
ऐसी `.gitattributes` फ़ाइल हो जिसे git ट्रैक नहीं करता, जो कमिट की गई प्रति से भिन्न
हो, या जिसकी कमिट की गई प्रति git पढ़ नहीं सकता या जो किसी filter या diff ड्राइवर का
नाम लेती हो (वर्क ट्री की प्रति भी पढ़ी जाती है), जब क्लोन में कोई ऐसी git रिपॉज़िटरी
हो जिसे git ट्रैक नहीं करता, इंजन के अपने डेटा फ़ोल्डरों जैसे `backups` के बाहर (git
उसमें की `.gitattributes` फ़ाइलें पढ़ेगा), और जब `src` (किसी भी केस में लिखा) के
अंतर्गत ऐसी फ़ाइलें हों जिन्हें git ट्रैक नहीं करता, क्योंकि इंजन उन्हें लोड कर सकता है।
चेकआउट के बाद, इंजन के क्लोन से चलने से पहले यह `src` के अंतर्गत Python कैश फ़ोल्डर
(`__pycache__`) हटाता है। अपडेट के दौरान क्लोन के git हुक कभी नहीं चलते, और Apothem के
अलावा किसी अन्य प्रोजेक्ट का क्लोन बिल्कुल अपडेट नहीं होता। अपडेट अपने रन के लिए
`GIT_NO_REPLACE_OBJECTS=1`, `GIT_NO_LAZY_FETCH=1`, `GIT_ALLOW_PROTOCOL` और
`GIT_ATTR_NOSYSTEM=1` सेट करता है, और git क्लोन के बाहर की कोई attributes फ़ाइल नहीं
पढ़ता (देखें
[इंस्टॉलर एनवायरनमेंट वेरिएबल्स](/docs/how-to/installer-environment-variables#the-installer-variables))।
हर रन अपनी पूरी अवधि के लिए एक लॉक, `<APOTHEM_HOME>.lock`, रखता है, इसलिए उसी
`APOTHEM_HOME` पर दूसरा इंस्टॉल, अपडेट या अनइंस्टॉल रुक जाता है; जब कोई लॉक पीछे छूट
जाए तो
[समस्या निवारण](/docs/install/troubleshooting#the-installer-stops-another-run-holds-the-lock)
देखें। जिस हस्ताक्षरित टैग की मेंटेनर सार्वजनिक कुंजी स्थानीय keyring में नहीं है, वह
कुंजी-आयात मार्गदर्शन के साथ निरस्त होता है, जो
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md) में
प्रकाशित फ़िंगरप्रिंट की ओर इशारा करता है। इसके बाद यह ताज़ा ट्री से `apothem update`
चलाकर `APOTHEM_HARNESS` द्वारा नामित हार्नेस को फिर से मटेरियलाइज़ करती है (हार्नेस का
डिफ़ॉल्ट [इंस्टॉलर एनवायरनमेंट वेरिएबल्स](/docs/how-to/installer-environment-variables)
तालिका के अनुसार होता है)। इसके लिए पूर्व इंस्टॉल आवश्यक है: जब `APOTHEM_HOME` पर कोई
ट्री न हो और `APOTHEM_SOURCE` अनसेट हो, तो यह आपको पहले इंस्टॉलर की ओर निर्देशित करने
वाले संदेश के साथ बाहर निकलती है।

अपडेट स्क्रिप्ट केवल git क्लोन पर काम करती है। cosign से, या
`APOTHEM_VERIFY=checksum` से किया गया इंस्टॉल इसके बजाय रिलीज़ आर्काइव रखता है, इसलिए
अपडेट स्क्रिप्ट रुक जाती है और आपसे `PATH` पर cosign और `gpg` के साथ इंस्टॉलर फिर से
चलाने को कहती है। वह दोबारा रन नई रिलीज़ लगाता है और हर वह फ़ाइल रखता है जिसे वह शिप
नहीं करता, जिनमें इंजन के बैकअप और इंस्टॉल लेजर शामिल हैं। cosign के बिना, इंस्टॉलर
को `--yes` (Windows पर `-Yes`) के साथ फिर से चलाएँ: यह आर्काइव इंस्टॉल को मेंटेनर कुंजी
के विरुद्ध जाँचे गए git क्लोन में बदल देता है, और हर वह चीज़ रखता है जो स्रोत ट्री का
हिस्सा नहीं है, जिनमें बैकअप, लेजर, प्लान और मेमोरी शामिल हैं।
`APOTHEM_VERIFY=checksum` भी आर्काइव को उसी जगह अपडेट करता है और उसे
`APOTHEM_ALLOW_UNVERIFIED=1` चाहिए। checksum मोड रिलीज़ का सत्यापन नहीं करता।
SHA256SUMS आर्काइव वाली उसी रिलीज़ से आता है, इसलिए मेल खाना केवल यह दिखाता है कि
डाउनलोड क्षतिग्रस्त नहीं है; जो कोई भी रिलीज़ की फ़ाइलें बदल सकता है, वह दोनों बदल
सकता है।

### जब इंजन किसी फ़ाइल को वैसा ही छोड़ देता है

इंजन Apothem का ब्लॉक रखने वाली किसी फ़ाइल (मान लीजिए `CLAUDE.md` या `AGENTS.md`) को
उसकी Apothem मार्कर पंक्तियों के कारण वैसा ही छोड़ सकता है: उदाहरण के लिए, जब फ़ाइल
में Apothem के मार्करों के बीच दो पूरे ब्लॉक हों। तब वह बाकी सब कुछ लिखता है, एक
चेतावनी प्रिंट करता है जो फ़ाइल का नाम और उसे ठीक करने का तरीका बताती है, और निकास कोड
`2` के साथ आंशिक के रूप में समाप्त होता है। इंजन तब भी आंशिक के रूप में समाप्त होता है
जब वह कुछ लिखने के बाद रुकता है: उदाहरण के लिए, जब किसी `APOTHEM_HARNESS=all` रन में
एक टूल विफल होता है जबकि उससे पहले के टूल ने अपनी फ़ाइलें लिख दी थीं। उसकी त्रुटि
बताती है कि क्या विफल हुआ, और उससे पहले पूरा हुआ हर टूल त्रुटि के ऊपर अपनी पंक्ति
रखता है। इंस्टॉलर और अपडेट स्क्रिप्ट फिर एक और पंक्ति प्रिंट करते हैं:

```text
! The engine ended as partial (exit code 2): its messages above name the files it left as they are, or the error that stopped it. Fix what they name, then run 'apothem update --harness claude-code' again.
```

वे रन को पूर्ण सफलता के बाद की तरह पूरा करते हैं: इंस्टॉलर फिर भी verify चलाता है,
`apothem` कमांड रखता है और अपना समापन बैनर प्रिंट करता है, और अपडेट स्क्रिप्ट फिर भी
अपनी अंतिम पंक्ति के रूप में "Update complete." प्रिंट करती है। फिर हर स्क्रिप्ट निकास
कोड `2` के साथ समाप्त होती है। पाइप किया गया PowerShell रन (`irm ... | iex`) इसके बजाय
`$LASTEXITCODE` को `2` पर छोड़ता है, ताकि आपका PowerShell सत्र खुला रहे। एक बार का
`pwsh -Command "irm ... | iex"` (या `powershell -c`) आंशिक रन केवल `$LASTEXITCODE` के
माध्यम से बताता है, इसलिए प्रक्रिया स्वयं `0` के साथ बाहर निकलती है। जब किसी CI जॉब या
स्क्रिप्ट को कोड चाहिए, तो कमांड को `; exit $LASTEXITCODE` से समाप्त करें, या स्क्रिप्ट
को `-File` के साथ उसके पाथ से चलाएँ। PowerShell, bash या किसी अन्य POSIX शेल से, उस
कमांड को सिंगल कोट्स में रखें। डबल कोट्स में, बुलाने वाला शेल नई प्रक्रिया शुरू होने से
पहले अपना `$LASTEXITCODE` डाल देता है (POSIX शेल एक खाली स्ट्रिंग डालता है), इसलिए
प्रक्रिया रन के कोड के साथ बाहर नहीं निकलती। cmd.exe से, डबल कोट्स ठीक हैं। इंस्टॉलर का
ड्राई रन (`--dry-run`, या Windows पर `-DryRun`) कुछ नहीं लिखता, इसलिए इंजन उसे आंशिक के
रूप में समाप्त नहीं करता। इंजन के संदेश जो बताते हैं उसे ठीक करें। किसी फ़ाइल के लिए,
अपना टेक्स्ट रखें (देखें
[किसी फ़ाइल में Apothem के मार्करों के बीच दो ब्लॉक हैं](/docs/install/troubleshooting#a-file-holds-two-blocks-between-apothems-markers)
और
[Apothem अपने ब्लॉक को आपके टेक्स्ट से अलग नहीं बता सकता](/docs/install/troubleshooting#apothem-cannot-tell-its-block-from-your-text)),
फिर हर उस टूल के लिए जिसे रन ने अधूरा छोड़ा, `apothem update --harness <name>`, या
अपडेट स्क्रिप्ट, फिर से चलाएँ। इंजन से कोई अन्य गैर-शून्य निकास कोड स्क्रिप्ट को वहीं
रोक देता है।

## हार्नेस आउटपुट फिर से-मटेरियलाइज़ करें

इंजन को अपडेट करने या `~/.config/apothem/profile.yaml` को संपादित करने के बाद,
इंस्टॉल किए गए हार्नेस कॉन्फ़िग को फिर से व्युत्पन्न करें। यूज़र-स्कोप अडैप्टर को
`--project` की आवश्यकता नहीं होती; प्रोजेक्ट-स्कोप अडैप्टर को होती है।

```bash
apothem update --harness claude-code
apothem update --harness cursor --project /path/to/project
apothem update --harness all --project /path/to/project
```

जब आपको बिना किसी फ़ाइलसिस्टम लेखन के मशीन-पठनीय
पूर्वावलोकन की आवश्यकता हो तो वही कमांड `--dry-run --json` के साथ चलाएँ।

## वर्तमान कमांड सीमा

`apothem update` केवल हार्नेस आउटपुट अपडेट करता है। CLI
`update --self`, `update --check`, या `update --apply` को लागू नहीं करता; इंजन को
स्वयं उसी चैनल के माध्यम से अपडेट करें जिससे आपने इंस्टॉल किया था — `/plugin` फ़्लो, एक ताज़ा
`npx` रन, या ऊपर दी गई इंस्टॉलर/अपडेट स्क्रिप्ट।
