लक्ष्य: स्क्रिप्ट को संपादित किए बिना, उसे चलाने से पहले पर्यावरण चर सेट करके
`install.sh` / `install.ps1` को निर्देशित करें।

## पूर्वापेक्षाएँ

- एक POSIX शेल (`bash`) या PowerShell 5.1+। नीचे के PowerShell उदाहरण `pwsh`
  (PowerShell 7+) चलाते हैं। Windows PowerShell 5.1 के अंतर्गत, इसके बजाय
  `powershell -NoProfile -ExecutionPolicy Bypass -File install.ps1` चलाएँ।
- चर इंस्टॉलर के शीर्ष पर एक बार पढ़े जाते हैं, इसलिए उन्हें उसी कमांड में सेट
  करें (या पहले उन्हें एक्सपोर्ट करें), फिर इंस्टॉलर चलाएँ।

## इंस्टॉलर चर

| चर | नियंत्रित करता है | डिफ़ॉल्ट |
| --- | --- | --- |
| `APOTHEM_HOME` | स्रोत ट्री के लिए इंस्टॉल गंतव्य; यह ऐसा फ़ोल्डर होना चाहिए जिसमें केवल आप लिख सकें (नीचे देखें), और जब अन्य लोग इसमें या इसके फ़ोल्डर में लिख सकते हों तो इंस्टॉलर चेतावनी देते हैं | `$HOME/.apothem` |
| `APOTHEM_REPO` | क्लोन करने के लिए Git रिमोट; `-` से शुरू होने वाला मान अस्वीकार किया जाता है | `https://github.com/ahmed-g-gad/apothem` |
| `APOTHEM_REF` | चेक आउट करने के लिए Git ref; अनसेट होने पर नवीनतम हस्ताक्षरित `vMAJOR.MINOR.PATCH` टैग रिज़ॉल्व होता है, कोई टैग मान उसे पिन करता है, `main` चलती ब्रांच चुनता है। `main` जैसा गैर-टैग ref `APOTHEM_ALLOW_UNVERIFIED=1` के बिना निरस्त हो जाता है। | अनसेट (नवीनतम हस्ताक्षरित टैग) |
| `APOTHEM_ALLOW_UNVERIFIED` | `1` पर सेट होने पर क्लोन पथ पर विफल टैग जाँच को घातक निरस्तीकरण के बजाय चेतावनी में घटाता है, और `APOTHEM_VERIFY=checksum` की अनुमति देता है; `release` पथ कभी नहीं घटाता, और कोई भी सेटिंग यह जाँच नहीं छोड़ती कि हस्ताक्षरित टैग वही है जो रिलीज़ के लिए नामित है, लेकिन चूँकि यह अहस्ताक्षरित टैग, या किसी अन्य कुंजी से हस्ताक्षरित टैग को आगे जाने देता है, वह जाँच केवल उन टैग की रक्षा करती है जिन पर अनुरक्षक कुंजी का हस्ताक्षर है | `0` (सत्यापन, विफल होने पर बंद) |
| `APOTHEM_VERIFY` | `auto` तब `release` का उपयोग करता है जब `cosign` `PATH` पर हो और `APOTHEM_HOME` git क्लोन न हो, अन्यथा `signature`; `release` प्लेटफ़ॉर्म आर्काइव तब इंस्टॉल करता है जब टैग पर अनुरक्षक कुंजी का हस्ताक्षर हो, cosign पुष्टि करे कि रिलीज़ वर्कफ़्लो ने टैग के कमिट पर एक रन में `SHA256SUMS` पर हस्ताक्षर किए, और आर्काइव का SHA-256 उससे मेल खाए; `signature` रिलीज़ टैग के GPG हस्ताक्षर को पिन की गई अनुरक्षक कुंजी से जाँचता है; `checksum` केवल SHA-256 जाँच के बाद आर्काइव इंस्टॉल करता है और उसे `APOTHEM_ALLOW_UNVERIFIED=1` चाहिए। चेकसम मोड रिलीज़ का सत्यापन नहीं करता। SHA256SUMS उसी रिलीज़ से आता है जिससे आर्काइव, इसलिए मेल खाना केवल यह दिखाता है कि डाउनलोड क्षतिग्रस्त नहीं है; जो कोई रिलीज़ की फ़ाइलें बदल सकता है, वह दोनों बदल सकता है। | `auto` |
| `APOTHEM_RELEASE_BASE` | `release` और `checksum` मोड के लिए डाउनलोड आधार | `<APOTHEM_REPO>/releases/download` |
| `APOTHEM_SOURCE` | क्लोन करने के बजाय उपयोग करने के लिए स्पष्ट स्थानीय स्रोत ट्री | अनसेट (क्लोन) |
| `APOTHEM_HARNESS` | इंस्टॉल करने के लिए उपयोगकर्ता-स्कोप हार्नेस (`antigravity`, `claude-code`, `codex`, `hermes`, `open-claw`, `opencode`, `qwen-code`)। इंस्टॉलर `--project` पास नहीं करता, इसलिए प्रोजेक्ट-स्कोप हार्नेस `project.required` के साथ विफल होता है; उन्हें बाद में `apothem install --harness NAME --project PATH` से इंस्टॉल करें। | `claude-code` |
| `APOTHEM_PROFILE` | साझा प्रोफ़ाइल YAML का पथ | `$HOME/.config/apothem/profile.yaml` |
| `APOTHEM_SKIP_VERIFY` | `1` पर सेट होने पर इंस्टॉल-पश्चात सत्यापन चरण छोड़ता है | `0` (सत्यापन चलता है) |
| `APOTHEM_AUTO_INSTALL_DEPS` | `1` पर सेट होने पर गायब `click` / `rich` पूर्वापेक्षाएँ बिना पूछे अपने-आप इंस्टॉल करता है | `0` (पूछता है, या गैर-इंटरैक्टिव पाइप में मना करता है) |
| `APOTHEM_BIN_DIR` | रखे गए `apothem` कमांड शिम के लिए डायरेक्टरी | `$HOME/.local/bin` (POSIX); `%LOCALAPPDATA%\Microsoft\WindowsApps` (Windows) |
| `NO_COLOR` | किसी भी मान पर सेट होने पर रंगीन आउटपुट बंद करता है ([no-color.org](https://no-color.org/)); जब भी आउटपुट टर्मिनल न हो (पाइप, फ़ाइल, CI लॉग), तब भी रंग बंद रहता है | अनसेट (रंग केवल इंटरैक्टिव टर्मिनल पर) |

`APOTHEM_SOURCE` क्लोन पर प्राथमिकता लेता है: जब इसे ऐसे चेकआउट पर सेट किया जाता
है जिसमें `src/apothem` हो, तो इंस्टॉलर उसका सीधे उपयोग करता है,
`APOTHEM_REPO` / `APOTHEM_REF` को कभी नहीं छूता, और टैग रिज़ॉल्यूशन तथा हस्ताक्षर
सत्यापन छोड़ देता है (सत्यापित करने के लिए कुछ भी फ़ेच नहीं किया जाता)।

`APOTHEM_SOURCE` और किसी चेकआउट की अपनी इंस्टॉलर स्क्रिप्ट को उसके पथ से चलाना (किसी
भी फ़ोल्डर से) स्थानीय ट्री का उपयोग करने के केवल दो तरीके हैं। पाइप किया गया वन-लाइनर (`curl
... | sh`, `irm ... | iex`) कभी स्थानीय ट्री का उपयोग नहीं करता: वह वर्तमान फ़ोल्डर और
उसके पैरेंट फ़ोल्डरों को अनदेखा करता है, और रिलीज़ को फ़ेच और सत्यापित करता है। इंस्टॉलर,
अपडेटर और अनइंस्टॉलर, `apothem` शिम, npm लॉन्चर, हुक और अनुरूपता गेट की वैलिडेटर
प्रक्रियाएँ वर्तमान फ़ोल्डर को Python के मॉड्यूल खोज पथ से बाहर रखती हैं। आपके द्वारा
स्वयं टाइप किया गया `python -m apothem` कमांड ऐसा नहीं करता: `-m` पहले वर्तमान फ़ोल्डर
से मॉड्यूल पढ़ता है।

आपके अपने `PYTHONPATH` की खाली और सापेक्ष प्रविष्टियाँ कोई भी लॉन्चर इंजन तक नहीं
पहुँचाता (इंस्टॉलर, अपडेटर, अनइंस्टॉलर, POSIX और Windows `apothem` शिम, और npm
लॉन्चर)। रखी गई प्रविष्टि पूरा पथ होनी चाहिए: Windows पर `C:\lib` जैसा ड्राइव पथ या
नेटवर्क पथ, अन्यत्र `/` से शुरू होने वाला पथ। रूटेड `\lib` या ड्राइव-सापेक्ष `C:lib`
हटा दिया जाता है। sh स्क्रिप्ट जिस Python को चलाती हैं उससे पूछती हैं कि वह कौन-सा रूप
पढ़ता है, और वे जो `apothem` शिम लिखती हैं वह उसी रूप को रखता है। Windows Python (Git
Bash के अंतर्गत सामान्य वाला) को इंजन पथ Windows रूप में, `;` से जुड़े हुए, मिलते हैं, और
वह आपके `PYTHONPATH` के केवल ड्राइव और नेटवर्क पथ रखता है। POSIX Python, Cygwin और
MSYS2 के अपने `python3` सहित, को `:` से जुड़े POSIX पथ मिलते हैं और वह केवल `/` से शुरू
होने वाली प्रविष्टियाँ रखता है। इंस्टॉलरों के वे `git` कमांड जो किसी क्लोन पर काम नहीं
करते, वर्तमान फ़ोल्डर की रिपॉज़िटरी नहीं पढ़ते।

वे `git` कमांड एक खाली अस्थायी फ़ोल्डर से चलते हैं जिसे इंस्टॉलर उस रन के लिए बनाता
है, इसलिए किसी git पर्यावरण चर (`GIT_SSH`, `GIT_ASKPASS` और समान) में सापेक्ष पथ अब
वहाँ इंगित नहीं करता जहाँ पहले करता था। उन चरों में निरपेक्ष पथ का उपयोग करें। किसी
फ़ोल्डर या फ़ाइल (जैसे git बंडल) को नामित करने वाला सापेक्ष `APOTHEM_REPO` अब भी उस
फ़ोल्डर से रिज़ॉल्व होता है जिससे आपने शुरू किया था।

इंस्टॉलर git को पुनर्निर्देशित करने वाले git पर्यावरण चरों (`GIT_DIR`, `GIT_WORK_TREE`,
`GIT_INDEX_FILE` और समान) को अनदेखा करते हैं, और जब `APOTHEM_REPO` `-` से शुरू होता है
तो रुक जाते हैं, ताकि कोई मान git विकल्प के रूप में न पढ़ा जा सके।

इंस्टॉलर और अपडेटर `GIT_CONFIG`, `GIT_CONFIG_GLOBAL` और `GIT_CONFIG_SYSTEM` को भी
खाली करते हैं, ताकि आपके पर्यावरण से विरासत में मिला मान git को किसी अन्य कॉन्फ़िग फ़ाइल
की ओर इंगित न कर सके, और `GIT_ATTR_SOURCE` को भी, जो git को उस वर्क ट्री और इंडेक्स के
बजाय, जिन्हें जाँचें पढ़ती हैं, किसी अन्य ट्री से एट्रिब्यूट पढ़ने देता (इसी कारण से किसी
क्लोन पर चलाए गए हर git कमांड पर आपके अपने कॉन्फ़िग का `attr.tree` खाली किया जाता है,
और `core.attributesFile` भी, इसलिए git न तो उसके द्वारा नामित एट्रिब्यूट फ़ाइल पढ़ता है
और न `~/.config/git/attributes`, जिसके मैक्रो ऐसे फ़िल्टर को नामित कर सकते हैं जिसे
जाँचें नहीं देखतीं)। यदि आप इनमें से कोई सेट करते हैं, तो इंस्टॉलर उसे अनदेखा करता है;
PowerShell स्क्रिप्ट रन समाप्त होने पर उसे वापस रख देती हैं, ताकि `irm ... | iex`
रन आपके सत्र को जैसा था वैसा छोड़े। `GIT_CONFIG_NOSYSTEM` जैसा आपने सेट किया वैसा ही
रहता है: वह केवल git को सिस्टम कॉन्फ़िग पढ़ने से रोकता है। git फिर भी आपका अपना ग्लोबल
कॉन्फ़िग (`~/.gitconfig` या `$XDG_CONFIG_HOME/git/config`) और सिस्टम कॉन्फ़िग उन्हीं
स्थानों से पढ़ता है जहाँ वह हमेशा देखता है, और `git`, `gpg` और `cosign` वे प्रोग्राम हैं
जो आपका `PATH` ढूँढता है। इंस्टॉलर उन पर वैसे ही भरोसा करते हैं जैसे वे मिले, और इसलिए
उस कॉन्फ़िग पर भी भरोसा करते हैं।

इंस्टॉलर और अपडेटर पूरे रन के लिए चार git चर भी सेट करते हैं।
`GIT_NO_REPLACE_OBJECTS=1` git को replace refs के माध्यम से किसी ऑब्जेक्ट को दूसरे से
बदलने से रोकता है। `GIT_NO_LAZY_FETCH=1` git को क्लोन पढ़ते समय गायब ऑब्जेक्ट को रिमोट
से अपने-आप फ़ेच करने से रोकता है।
`GIT_ALLOW_PROTOCOL=file:git:http:https:ssh` रन के हर git कमांड के लिए केवल उन पाँच
ट्रांसपोर्ट की अनुमति देता है, ताकि आपके पर्यावरण का कोई मान सूची को बढ़ा न सके और कोई
पता git से `ext::` जैसा हेल्पर प्रोग्राम न चलवा सके। `APOTHEM_REPO` को उनमें से किसी एक
का उपयोग करना होगा; स्थानीय पथ `file` के रूप में गिना जाता है। `GIT_ATTR_NOSYSTEM=1`
git को सिस्टम एट्रिब्यूट फ़ाइल पढ़ने से रोकता है, जिसके मैक्रो किसी फ़िल्टर को नामित कर
सकते हैं। PowerShell स्क्रिप्ट रन समाप्त होने पर चारों को वैसे ही वापस रख देती हैं जैसे वे
थे। वे रन के लिए git के आउटपुट को UTF-8 के रूप में भी पढ़ती हैं, आपके कंसोल का कोड पेज जो
भी हो, और रन समाप्त होने पर कंसोल की सेटिंग वापस रख देती हैं।

`APOTHEM_HOME` ऐसा फ़ोल्डर होना चाहिए जिसमें केवल आप लिख सकें। जो कोई उसमें लिख सकता
है, वह `apothem` कमांड द्वारा चलाया जाने वाला कोड बदल सकता है। Windows पर, ड्राइव के रूट
पर बनाया गया फ़ोल्डर, जैसे `C:\apothem`, Windows की डिफ़ॉल्ट अनुमतियों के अंतर्गत,
कंप्यूटर में साइन इन करने वाले हर उपयोगकर्ता द्वारा बदला जा सकता है। इसे अपने उपयोगकर्ता
फ़ोल्डर के अंतर्गत रखें, जैसा डिफ़ॉल्ट है। इंस्टॉल और अपडेट स्क्रिप्ट, ड्राई रन सहित, बिना
रुके चेतावनी देती हैं जब अन्य उपयोगकर्ता `APOTHEM_HOME` या उसे रखने वाले फ़ोल्डर में लिख
सकते हों, या उनमें से किसी के स्वामी हों; स्थानीय चेकआउट से इंस्टॉल, और `APOTHEM_SOURCE`
सेट होने पर अपडेट, यह जाँच छोड़ देते हैं। Windows पर चेतावनी `install.ps1` और
`update.ps1` से आती है: `install.sh` और `update.sh` Git Bash, MSYS2 या Cygwin के
अंतर्गत जाँच नहीं करते;
[समस्या निवारण](/docs/install/troubleshooting#the-installer-warns-other-users-can-change-apothem_home)
बताता है कि इसे कैसे ठीक करें।

इंस्टॉल, अपडेट और अनइंस्टॉल स्क्रिप्ट का हर रन पूरे रन के लिए एक लॉक,
`<APOTHEM_HOME>.lock`, रखता है; उसी `APOTHEM_HOME` पर दूसरा रन रुक जाता है। जब
`APOTHEM_HOME` एक सिम्बॉलिक लिंक (या, Windows पर, जंक्शन) होता है, तो POSIX और
PowerShell दोनों स्क्रिप्ट लॉक उस फ़ोल्डर के बगल में लेती हैं जिस तक वह ले जाता है। बलपूर्वक
समाप्ति या बिजली जाने से `APOTHEM_HOME` के बगल में फ़ोल्डर रह सकते हैं, और अगला फ़ेच किया
गया इंस्टॉल उनके नाम बताता है और कुछ भी बदलने से पहले रुक जाता है; देखें
[समस्या निवारण](/docs/install/troubleshooting)।

जब `APOTHEM_HOME` किसी मौजूदा डायरेक्टरी की ओर इंगित करता है, तो क्या होता है यह इस पर
निर्भर करता है कि उसमें क्या है।

- `auto` या `signature` मोड में git क्लोन फ़ेच किया जाता है; नए टैग की पहले जाँच होती है,
  और उसके बाद ही क्लोन चेक आउट होता है। विफल जाँच क्लोन को अपरिवर्तित छोड़ती है, और
  ट्रैक की गई फ़ाइलों में बदलाव खो जाने के बजाय अपडेट को रोक देते हैं, उन्हें कमिट या
  स्टैश करने के संदेश के साथ। `main` जैसे गैर-रिलीज़ ref के साथ, क्लोन उस ब्रांच की origin
  वाली प्रति का अनुसरण करता है। `.git` फ़ाइल (एक लिंक्ड वर्कट्री) क्लोन के रूप में गिनी
  जाती है। `release` और `checksum` `--yes` के बिना क्लोन को अस्वीकार करते हैं, और
  `--yes` के साथ भी तब तक अस्वीकार करते हैं जब तक क्लोन में स्थानीय काम हो (बदलाव, स्टैश,
  बिना पुश किए कमिट, या उसके स्रोत ट्री में अनट्रैक्ड फ़ाइलें), ड्राई रन में भी। जब `--yes`
  सचमुच किसी क्लोन को बदलता है, तो क्लोन का अपना ट्री एक नए फ़ोल्डर,
  `<APOTHEM_HOME>.before-apothem-<time>`, में अपने ही नाम से चला जाता है, न कि हटाया
  जाता है। फ़ेच से पहले, इन-प्लेस अपडेट तब रुक जाता है जब फ़ाइलें assume-unchanged या
  skip-worktree चिह्नित हों, जब क्लोन का वर्क ट्री `APOTHEM_HOME` न हो, जब क्लोन में कोई
  सबमॉड्यूल या ऐसी git रिपॉज़िटरी हो जिसे git ट्रैक नहीं करता (इंजन के अपने डेटा फ़ोल्डरों,
  जैसे `backups`, के बाहर), जब `.git/info/attributes` किसी फ़िल्टर या डिफ़ ड्राइवर को
  नामित करता हो, जब क्लोन किसी अन्य रिपॉज़िटरी से ऑब्जेक्ट उधार लेता हो, जब वर्क ट्री में
  कोई `.gitattributes` फ़ाइल अनट्रैक्ड हो, कमिट की गई प्रति से भिन्न हो, ऐसे ड्राइवर को
  नामित करती हो या उसकी कमिट की गई प्रति git पढ़ न सके, जब `src` के अंतर्गत फ़ाइलें
  अनट्रैक्ड हों, या जब क्लोन की `.git/config` या `.git/config.worktree` में ऐसी सेटिंग
  हो जो इनके अलावा हो: वे सेटिंग जिन्हें `git clone` और `git init` पूर्ण क्लोन के लिए वहाँ
  लिखते हैं, ब्रांच सेटिंग (ब्रांच का `remote` और `pushremote` `origin` होना चाहिए),
  `user.name`, `user.email`, `maintenance.auto`, `maintenance.strategy`, `pull.rebase`
  और `pull.ff`
  ([समस्या निवारण](/docs/install/troubleshooting#the-installer-stops-the-existing-clone-is-set-up-in-a-way-the-update-would-trust)
  उन्हें सूचीबद्ध करता है); अपडेट के दौरान क्लोन के git हुक कभी नहीं चलते। चेकआउट के बाद,
  इंजन के क्लोन से चलने से पहले अपडेट `src` के अंतर्गत Python कैश फ़ोल्डर (`__pycache__`)
  हटा देता है। केवल Apothem स्रोत का क्लोन गिना जाता है: किसी और चीज़ का क्लोन ऐसे फ़ोल्डर
  की तरह संभाला जाता है जिसमें कोई Apothem इंस्टॉल नहीं है।
- पहले का रिलीज़-आर्काइव इंस्टॉल cosign के साथ `auto` मोड में (या `release`, या
  `checksum` में) दोबारा चलाने पर अपडेट होता है।
- जिस फ़ोल्डर में कोई Apothem इंस्टॉल नहीं है, वह अस्वीकार किया जाता है: उसे किसी दूसरी
  जगह स्थानांतरित करें, `APOTHEM_HOME` को कहीं और इंगित करें, या `--yes` (Windows पर
  `-Yes`) पास करें। `--yes` के साथ, इंस्टॉलर पूरे फ़ोल्डर को, अपरिवर्तित, एक नए फ़ोल्डर,
  `<APOTHEM_HOME>.before-apothem-<time>`, में ले जाता है और नए सिरे से इंस्टॉल करता है।
- एक पुरानी खाली डायरेक्टरी, या ऐसी डायरेक्टरी जिसमें केवल इंजन का अपना डेटा हो
  (`backups`, `state`, `plans`, `memory`, `contexts`, `learning`,
  `providers`), फ़्लैग के बिना अपडेट होती है, और वह डेटा रखा जाता है।
- सिम्बॉलिक लिंक (Windows पर, सिम्बॉलिक लिंक या जंक्शन) तब अस्वीकार किया जाता है जब भी
  इंस्टॉल उसे बदलेगा: `APOTHEM_HOME` को उस फ़ोल्डर पर इंगित करें जिस तक लिंक ले जाता
  है। लिंक के पीछे का मौजूदा git क्लोन इन-प्लेस अपडेट होता है।
- Linux और macOS पर, आगे ले जाई जाने वाली कोई फ़ाइल या फ़ोल्डर जिसके नाम में रिक्त स्थान
  या कोई अन्य विशेष वर्ण हो, इंस्टॉल को रोक देता है: उसे पहले `APOTHEM_HOME` से बाहर ले
  जाएँ।

बदले जाने वाले Apothem इंस्टॉल के लिए, नए स्रोत की जाँच `APOTHEM_HOME` के बगल के एक
स्टेजिंग फ़ोल्डर में होती है और हर जाँच पास होने के बाद ही उसे बदला जाता है। पुराने इंस्टॉल
में जो कुछ भी उसके स्रोत ट्री का हिस्सा नहीं है, जिसमें इंजन के बैकअप, इंस्टॉल लेजर, प्लान
और मेमोरी शामिल हैं, रखा जाता है। यदि कोई चरण विफल हो या रन Ctrl+C या किसी समाप्ति सिग्नल
से रोका जाए, तो पहले का इंस्टॉल अपरिवर्तित वापस रख दिया जाता है; बलपूर्वक समाप्ति या बिजली
जाने से `APOTHEM_HOME` के बगल में ऐसे फ़ोल्डर रह सकते हैं जिनकी रिपोर्ट अगला फ़ेच किया गया
इंस्टॉल करता है। `--dry-run` (Windows पर `-DryRun`) अपनी जाँचें एक अस्थायी फ़ोल्डर में
करता है और `APOTHEM_HOME` को अपरिवर्तित छोड़ता है। यह वास्तविक रन जैसी ही जाँचें करता है,
सिवाय इसके कि यह किसी मौजूदा क्लोन में फ़ेच नहीं करता, और इसलिए ट्रैक की गई फ़ाइलों में
बदलावों के लिए उसकी जाँच नहीं करता, जो वास्तविक अपडेट अपने फ़ेच के बाद करता है।

## विश्वास मॉडल

जब `APOTHEM_REF` सेट नहीं होता, तो इंस्टॉलर नवीनतम रिलीज़ रिज़ॉल्व करता है और किसी
भी कॉन्फ़िगरेशन को मूर्त रूप देने से पहले उसकी जाँच करता है। वह हमेशा `git verify-tag`
से रिलीज़ टैग का सत्यापन करता है और माँगता है कि हस्ताक्षर SECURITY.md में प्रकाशित
अनुरक्षक कुंजी से आया हो; एक अहस्ताक्षरित या छेड़छाड़ किया गया टैग, या किसी अन्य कुंजी
से हस्ताक्षरित टैग, इंस्टॉल को निरस्त कर देता है, और वैसे ही ऐसा हस्ताक्षरित टैग ऑब्जेक्ट
भी जो रिलीज़ के लिए नामित टैग नहीं है (किसी अन्य रिलीज़ का हस्ताक्षरित टैग, जिसे इस नाम
पर फिर से इंगित किया गया हो)। `PATH` पर `cosign` होने पर, वह फिर रिलीज़ आर्काइव तब
इंस्टॉल करता है जब cosign पुष्टि करे कि रिलीज़ वर्कफ़्लो ने `SHA256SUMS` पर हस्ताक्षर
किए और, अपनी `--certificate-github-workflow-sha` जाँच के माध्यम से, कि उसके द्वारा
सत्यापित प्रमाणपत्र टैग के कमिट पर एक रन को जारी किया गया था, और आर्काइव का SHA-256
उससे मेल खाए। उस पथ को `gpg` और cosign चाहिए। मौजूदा git क्लोन के लिए, इंस्टॉलर क्लोन
को चेक आउट करने से पहले टैग फ़ेच करता है और उसकी जाँच करता है, इसलिए विफल जाँच क्लोन
को जैसा था वैसा छोड़ती है। जिस हस्ताक्षरित टैग की अनुरक्षक सार्वजनिक कुंजी स्थानीय कीरिंग
में नहीं है, वह इसके बजाय कुंजी-आयात मार्गदर्शन के साथ निरस्त होता है — कुंजी
आयात करें और उसके फ़िंगरप्रिंट की जाँच
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md) में
प्रकाशित मान से करें।
किसी ज्ञात रिलीज़ को `APOTHEM_REF=<tag>` से पिन करें, टैग
[रिलीज़ पृष्ठ](https://github.com/ahmed-g-gad/apothem/releases) से लें; पिन किया
गया टैग उसी तरह सत्यापित होता है। चलती ब्रांच को `APOTHEM_REF=main` के साथ
`APOTHEM_ALLOW_UNVERIFIED=1` जोड़कर चुनें; वह इंस्टॉल असत्यापित होता है, और अकेला
`main` इंस्टॉल को निरस्त कर देता है क्योंकि ब्रांच हस्ताक्षरित टैग नहीं होती। विफल टैग
जाँच से चेतावनी के साथ आगे बढ़ने के लिए `APOTHEM_ALLOW_UNVERIFIED=1` सेट करें
(एयर-गैप्ड, स्थानीय, या पूर्व-हस्ताक्षरित रिलीज़ के उपयोग के लिए)। यह केवल क्लोन पथ पर
लागू होता है, cosign पथ पर कभी नहीं, इसलिए cosign वाले होस्ट पर इसके साथ
`APOTHEM_VERIFY=signature` सेट करें।

```bash title="Pinned, verified install"
APOTHEM_REF=vMAJOR.MINOR.PATCH bash install.sh
```

```bash title="Require the tag check and the cosign check"
APOTHEM_VERIFY=release bash install.sh
```

चेकसम मोड रिलीज़ का सत्यापन नहीं करता। SHA256SUMS उसी रिलीज़ से आता है जिससे आर्काइव,
इसलिए मेल खाना केवल यह दिखाता है कि डाउनलोड क्षतिग्रस्त नहीं है; जो कोई रिलीज़ की फ़ाइलें
बदल सकता है, वह दोनों बदल सकता है। इंस्टॉलर इसे केवल तब चलाता है जब
`APOTHEM_ALLOW_UNVERIFIED=1` भी सेट हो।

```bash title="Check the archive digest alone (no cosign, no gpg; does not verify the release)"
APOTHEM_VERIFY=checksum APOTHEM_ALLOW_UNVERIFIED=1 bash install.sh
```

```bash title="Proceed past a failed tag check (interim / air-gapped)"
APOTHEM_VERIFY=signature APOTHEM_ALLOW_UNVERIFIED=1 bash install.sh
```

## चरण (POSIX bash)

1. एक गैर-डिफ़ॉल्ट उपयोगकर्ता-स्कोप हार्नेस इंस्टॉल करें:

   ```bash
   APOTHEM_HARNESS=codex bash install.sh
   ```

2. इंस्टॉल गंतव्य पिन करें और चलती हुई `main` ब्रांच चुनें। ब्रांच हस्ताक्षरित टैग
   नहीं होती, इसलिए इंस्टॉलर को `APOTHEM_ALLOW_UNVERIFIED=1` भी चाहिए:

   ```bash
   APOTHEM_REF=main APOTHEM_ALLOW_UNVERIFIED=1 APOTHEM_HOME="$HOME/tools/apothem" bash install.sh
   ```

3. सत्यापन छोड़ते हुए, एक स्थानीय चेकआउट और एक कस्टम प्रोफ़ाइल का उपयोग करें:

   ```bash
   APOTHEM_SOURCE=/work/apothem \
   APOTHEM_PROFILE=/work/profile.yaml \
   APOTHEM_SKIP_VERIFY=1 \
   bash install.sh
   ```

## चरण (PowerShell)

इंस्टॉलर चलाने से पहले हर चर को `$env:` पर सेट करें:

```powershell
$env:APOTHEM_HARNESS = 'codex'
pwsh -NoProfile -File install.ps1
```

```powershell
$env:APOTHEM_ALLOW_UNVERIFIED = '1'
$env:APOTHEM_REF = 'main'
$env:APOTHEM_HOME = "$HOME\tools\apothem"
pwsh -NoProfile -File install.ps1
```

```powershell
$env:APOTHEM_SOURCE = 'C:\work\apothem'
$env:APOTHEM_PROFILE = 'C:\work\profile.yaml'
$env:APOTHEM_SKIP_VERIFY = '1'
pwsh -NoProfile -File install.ps1
```

## सत्यापन

इंस्टॉलर `✓ Harness <name> installed` प्रिंट करता है, फिर (जब तक
`APOTHEM_SKIP_VERIFY=1` न हो) `✓ verify passed`। स्वतंत्र रूप से पुष्टि करें:

```bash
apothem verify --harness codex
```

Cursor जैसे प्रोजेक्ट-स्कोप हार्नेस के लिए, इंस्टॉलर के बाद इंस्टॉल और सत्यापन
स्वयं `--project` के साथ चलाएँ:

```bash
apothem install --harness cursor --project /path/to/project
apothem verify --harness cursor --project /path/to/project
```

जब प्रोफ़ाइल अभी मौजूद नहीं थी, तो इंस्टॉलर उदाहरण से एक प्रोफ़ाइल बनाता है और उसी
रन में इंस्टॉल और सत्यापन जारी रखता है। उदाहरण के पहचान फ़ील्ड प्लेसहोल्डर हैं,
इसलिए इंस्टॉल एक नोट प्रिंट करता है। उदाहरण में नमूना नियम, दो नमूना MCP सर्वर और
प्रति-हार्नेस ओवरराइड भी होते हैं, और जो हार्नेस प्रोफ़ाइल से MCP सर्वर लेता है, जैसे
OpenCode, उसे दोनों सर्वर मिलते हैं। `$APOTHEM_PROFILE` संपादित करें, जो आप नहीं चाहते
उसे हटाते हुए, फिर उसे लागू करने के लिए `apothem update --harness <name>` चलाएँ। बिना प्रोफ़ाइल के
एक `--dry-run` उदाहरण को प्रोफ़ाइल की जगह रखकर पूर्वावलोकन करता है और कुछ भी नहीं
लिखता।
