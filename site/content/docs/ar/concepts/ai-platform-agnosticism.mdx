صُمّم Apothem حول مبدأ واحد: ينبغي أن يبقى إعداد الحوكمة لديك
أطول من أي زمن تشغيل واحد للمساعد البرمجي. الملف التعريفي المشترك لـ Apothem
هو ملف YAML مُتحقَّق منه عبر مخطط في `~/.config/apothem/profile.yaml` أو
`--profile PATH`؛ وتوفّر مجموعات Apothem المُحزَّمة الأوامر، والقواعد، والمهارات،
والخطّافات، والقوالب، وأسطر الحالة، وأنماط الإخراج، وتعريفات التفويض.
وتترجم المحوّلات الخاصة بكل إطار عمل ضمن `src/apothem/harnesses/<harness>/` تلك المُدخَلات إلى الصيغة
التي يتطلّبها كل إطار عمل مدعوم:

```text
Claude Code, Cursor, Gemini CLI, GitHub Copilot, Codex, Windsurf,
OpenCode, Antigravity, Open-Claw, Hermes, Qwen Code,
CodeBuddy, Kiro, Trae, Zed, GLM (Z.ai), Kimi Code
```

## الفكرة الجوهرية

عدم الاعتماد على المضيف يعني أنّ *قصدك* — مَن أنت، وكيف تريد أن تتصرّف
المساعدات، والقواعد التي يجب أن تتّبعها — يقيم في مكان واحد لا يملكه أي إطار عمل
بمفرده. أُطُر العمل مستهلِكات قابلة للتبديل لذلك القصد. فعند ظهور
مساعد جديد، تتبنّاه بإضافة محوّل، لا بإعادة تأليف
إعدادك. وعندما يفقد مساعد كنت تستخدمه شعبيّته، فإنّك تتخلّى عنه
دون أن تفقد الحوكمة التي بنيتها. الملف التعريفي هو الأصل؛ وإطار العمل
هدف تجسيد (render target). قد يُستخدم إطار العمل في البرمجة أو الدردشة أو العمل التشاركي أو البحث أو الكتابة — والملف التعريفي غير معتمِد على الغرض الذي يخدمه إطار العمل.

هذا انعكاس متعمَّد. فالمسار الشائع هو تهيئة كل أداة
مباشرةً، ما يجعل استثمارك رهينةً لطول عمر تلك الأداة
وصيغتها. يعامل Apothem الإعداد بوصفه رأس مال محمول، ويعامل إطار العمل
بوصفه طرفيّةً قابلة للتخلّص منها.

## المشكلة

لكل إطار عمل برمجي صيغة إعداد خاصّة به:

```text
Claude Code:    CLAUDE.md + settings.json
Cursor:         .cursor/rules/*.mdc
GitHub Copilot: .github/copilot-instructions.md
Windsurf:       .devin/rules/
Codex:          AGENTS.md
```

من دون Apothem، تصون N ملف إعداد منفصل تتباعد عن بعضها مع الوقت.

## حلّ Apothem

```text
One shared Apothem profile (YAML) + packaged cohorts
    identity.name
    preferences.style
    rules[]
         |
         v
    Adapter layer (HarnessAdapter protocol — src/apothem/harnesses/<harness>/)
         |
         +---> Claude Code adapter   -> ~/.claude/
         +---> Cursor adapter        -> .cursor/rules/*.mdc
         +---> Copilot adapter       -> .github/copilot-instructions.md
         +---> Windsurf adapter      -> .devin/rules/
         +---> ...
```

تُحرِّر الملف التعريفي المشترك مرّةً واحدة، ثم تشغّل `apothem update --harness <name>` أو
`apothem update --harness all --project <path>` لنشر التغيير.
ويطبع `apothem harnesses list` المجموعة المُسجَّلة.

## لماذا "apothem"

يُرمِّز الاسم المعمارية. في الهندسة، *apothem* (محور الضلع) هو العمود
من **مركز** المضلّع المنتظم إلى **منتصف أحد أضلاعه** —
المسافة الوحيدة من النواة إلى كل حافة، المتطابقة في كل اتّجاه. وذلك
هو التصميم: ملف تعريفي مشترك واحد في المركز، وسبعة عشر إطار عمل متساوية البُعد على
المحيط، وكل تجسيد يبعد المسافة نفسها عن مصدر الحقيقة.
لا تتغيّر النواة عند تغيُّر حافة؛ وتتشارك الحواف علاقة واحدة مع
النواة. ولأنّ كل إطار عمل يُشتَقّ من ملف تعريفي واحد، فالانحراف قابل للكشف
(`apothem status` يُبلّغ عنه) وقابل للتصحيح (`apothem update` يُعيد تجسيده).

## ضمانات قابلية النقل

تُحوَّل الأوامر والمساعِدات المُعلَّمة بـ<bdi>`portability: universal`</bdi> إلى كل إطار عمل يدعم مدخله في السجلّ سطح أوامر (مُحوَّلًا أو عبر شجرة دعم)؛ وأُطُر العمل التي لا تملك ذلك لا تتلقّى أيّ أوامر. ولا يُقيِّم المحرّك هذه العلامة. وقد تستلزم الأوامر والمساعِدات المُعلَّمة بـ<bdi>`portability: project-specific`</bdi> توثيقًا للتجاوز الخاص بكل إطار عمل في متن الملف.
