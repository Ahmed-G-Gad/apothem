تثبيت إعداد محوّل إطار عمل من الملف التعريفي المشترك.

## الموجز

```
apothem install --harness NAME|all [--profile PATH] [--dry-run]
                 [--clean|--fresh] [--yes] [--project PATH]
                 [--quiet|-q] [--verbose|-v]
                 [--format plain|json] [--json] [--no-color]
```

يحمّل الملف التعريفي المشترك ويتحقّق منه، ويختار محوّلًا مُسمّى أو مجموعة
<bdi>`all`</bdi> الشاملة للسجلّ كله، ويتحقّق من خطة التجسيد، ويكتب الإعداد الأصلي
لإطار العمل إضافةً إلى حزم الدعم. وتتطلّب المحوّلات ذات نطاق المشروع
<bdi>`--project PATH`</bdi>.

يُحَلّ الاسم المستعار بصيغة الاستمرار <bdi>`apothem installing`</bdi> (ويُقبَل أيضًا
بالصيغة <bdi>`apothem Installing`</bdi>) إلى المعالج نفسه.

## التشغيل الأول دون ملف تعريفي

عند إغفال <bdi>`--profile`</bdi> وعدم وجود ملف تعريفي في المسار الافتراضي
(<bdi>`~/.config/apothem/profile.yaml`</bdi>)، يكتب <bdi>`install`</bdi> الملف
التعريفي المبدئي هناك أولًا، ويطبع <bdi>`Created a starter profile at <path>`</bdi>،
ثم يتابع. يحمل الملف التعريفي المبدئي حقول هوية نائبة، لذا يطبع التثبيت أيضًا ملاحظة
الهوية النائبة؛ خصّص الملف التعريفي، ثم شغّل
[<bdi>`update`</bdi>](/docs/cli-reference/update) لتطبيقه. ومع <bdi>`--json`</bdi>
يُبلَّغ عن الإنشاء بوصفه مُدخَلًا في <bdi>`warnings`</bdi> يحمل
<bdi>`"operation": "profile_created"`</bdi>.

- لا يكتب <bdi>`--dry-run`</bdi> الملف التعريفي أبدًا: تستخدم المعاينة الملف
  التعريفي المبدئي في الذاكرة وتُبلغ عن
  <bdi>`"operation": "profile_scaffold_preview"`</bdi>.
- لا يُنشَأ أبدًا ملفٌ مُحدَّد صراحةً عبر <bdi>`--profile PATH`</bdi> وغير موجود؛
  بل يخرج الأمر بالرمز 1 مع <bdi>`profile.not_found`</bdi>.

## معاينة نطاق الأثر

يتفرّع <bdi>`install --harness all`</bdi> إلى نطاقات مختلطة: تكتب المحوّلات ذات نطاق المشروع تحت جذر <bdi>`--project`</bdi> المُمرَّر، بينما تكتب المحوّلات ذات نطاق المستخدم تحت دليلك المنزلي — خارج ذلك الجذر. وقبل أن يكتب التثبيت أيّ ملف، يطبع الأمر الأهداف الفعلية مُجمَّعةً تحت عنوانين: تلك الموجودة داخل جذر المشروع، وتلك الموجودة تحت دليلك المنزلي. والاستثناء الوحيد هو <bdi>`--clean`</bdi>: فخطوة التنظيف الكامل فيه تعمل قبل هذه المعاينة، فتكتب نسخة احتياطية وتُزيل الأهداف السابقة، كما هو موضّح أدناه.

عندما يكتب الاختيار خارج جذر المشروع، يحرس تأكيدٌ تفاعلي عمليات الكتابة المتجذّرة
في الدليل المنزلي. ويمضي كلٌّ من <bdi>`--yes`</bdi>، والصدفة غير التفاعلية (دون
<bdi>TTY</bdi>)، و<bdi>`--dry-run`</bdi>، و<bdi>`--format json`</bdi> دون مطالبة. ولا
يكتب <bdi>`--dry-run`</bdi> وحده شيئًا؛ أما <bdi>`--format json`</bdi> فيتخطّى
المعاينة ومطالبة التأكيد لكنه يُجري عمليات الكتابة مع ذلك. ورفض مطالبة الدليل المنزلي
يُلغي التثبيت قبل كتاباته. ومع <bdi>`--clean`</bdi>، تعمل خطوة التنظيف الكامل أولًا
ضمن تأكيدها الخاص بكل هدف: تكتب نسخة احتياطية تحت <bdi>`~/.apothem/backups`</bdi>
وتُزيل الأهداف التي تؤكّدها. وتبقى تلك الإزالات والنسخة الاحتياطية في مكانها عند
رفض مطالبة التثبيت.

## ملاحظات القدرات

لا يُسقِط كل محوّل إلا القدرات التي يدعمها إطار عمله أصليًا؛ أمّا القدرات التي لا
سطح أصليًا لها فيُبلَّغ عنها، ولا تُستبعَد بصمت. وفي الوضع <bdi>plain</bdi> يكون ذلك
ملاحظةً مُجمَّعة واحدة لكل إطار عمل (مثلًا
<bdi>`Note: <harness> - 9 capabilities not projected; pass --verbose for detail`</bdi>)؛
ومع <bdi>`--verbose`</bdi> تطبع كل قدرة سطر تعليلها الخاص. وأي تحذير آخر من المحوّل
يُطبَع هو أيضًا في الوضع <bdi>plain</bdi> على سطر <bdi>`Warning:`</bdi> خاص به، مثل
تحذير <bdi>Zed</bdi> الذي يسمّي ملف تعليمات يحجبه الملف <bdi>`.rules`</bdi> الجديد.
ويحمل غلاف <bdi>`--format json`</bdi> دائمًا مصفوفة <bdi>`warnings`</bdi> كاملةً
بصرف النظر عن مستوى الإسهاب.

يطبع التثبيت والتحديث أيضًا تنبيهات استشارية على هيئة أسطر <bdi>`Note:`</bdi>. ولا
يغيّر التنبيه الاستشاري أبدًا ما يكتبه التثبيت. عندما يكتب تثبيتٌ جذرًا مشتركًا، أي
مسارًا تحمّله أدوات أخرى أيضًا (مثل مجلد المهارات <bdi>`~/.agents/skills/`</bdi>)،
تسمّي الملاحظة تلك الأدوات. وعندما يستهدف تثبيتٌ أداةً تحمّل بالفعل محتوى
<bdi>Apothem</bdi> من الجذر المشترك لتثبيت آخر، تسمّي الملاحظة ذلك التثبيت. وفي غلاف
<bdi>`--format json`</bdi> يكون كل تنبيه استشاري مُدخَلًا في <bdi>`warnings`</bdi>
يحمل <bdi>`"outcome": "advisory"`</bdi> و<bdi>`"operation": "shared_root"`</bdi>.

تحصل خوادم <bdi>MCP</bdi> في الملف التعريفي على ثلاثة تنبيهات استشارية، يسمّي كلٌّ
منها حقل الملف التعريفي المعنيّ:

| العملية | الشرط | الإصلاح |
| --- | --- | --- |
| <bdi>`mcp_deprecated_transport`</bdi> | <bdi>`transport: sse`</bdi> (تُهمِل مواصفة <bdi>MCP</bdi> نقل <bdi>HTTP+SSE</bdi>) | استخدم <bdi>`streamable-http`</bdi> حين يدعمه الخادم. |
| <bdi>`mcp_plain_http`</bdi> | عنوان <bdi>URL</bdi> بصيغة <bdi>`http://`</bdi> يشير إلى مضيف ليس مضيف الاسترجاع المحلي | استخدم عنوان <bdi>URL</bdi> بصيغة <bdi>`https://`</bdi>. |
| <bdi>`mcp_literal_credential`</bdi> | قيمة في <bdi>`headers`</bdi> أو <bdi>`env`</bdi> تشبه رمزًا مميّزًا (<bdi>`ghp_`</bdi>، أو <bdi>`gho_`</bdi>، أو <bdi>`ghu_`</bdi>، أو <bdi>`ghs_`</bdi>، أو <bdi>`ghr_`</bdi>، أو <bdi>`github_pat_`</bdi>، أو <bdi>`sk-`</bdi>، أو <bdi>`xoxa-`</bdi>، أو <bdi>`xoxb-`</bdi>، أو <bdi>`xoxo-`</bdi>، أو <bdi>`xoxp-`</bdi>، أو <bdi>`xoxr-`</bdi>، أو <bdi>`xoxs-`</bdi>، أو <bdi>`Bearer`</bdi> متبوعًا برمز مميّز طويل) | احتفظ بالسرّ في متغيّر بيئة واكتب مراجع بنمط <bdi>`${GITHUB_TOKEN}`</bdi>. |

لا يطبع تنبيه بيانات الاعتماد أبدًا القيمة التي عثر عليها. ولا تُعلَّم أبدًا قيمةٌ
تحتوي مرجعًا من نوع <bdi>`${...}`</bdi>.

## إعدادات المُشغِّل التي تحمل تعليقات

بعض إعدادات أُطُر العمل ملفات تحرّرها أنت أيضًا، مثل <bdi>`settings.json`</bdi>،
و<bdi>`opencode.json`</bdi> (الذي قد يكون بصيغة <bdi>JSONC</bdi>)،
و<bdi>`openclaw.json`</bdi> (<bdi>JSON5</bdi>)، و<bdi>`config.yaml`</bdi>. يدمج
التثبيت مفاتيحه في هذه الملفات ويُبقي كل مفتاح أضفته.

يعيد الدمج كتابة الملف بصيغة <bdi>JSON</bdi> أو <bdi>YAML</bdi> عادية، وهذا من شأنه
أن يُسقِط التعليقات، والفواصل اللاحقة، وصياغة <bdi>JSON5</bdi>. لذلك:

- عندما لا يغيّر الدمج أي قيمة (مثلًا، إذا كنت قد أضفت مفاتيح <bdi>Apothem</bdi>
  بنفسك مسبقًا)، يُترَك الملف كما هو بايتًا ببايت.
- عندما يتعيّن على الدمج تغيير قيمة في ملف يحمل تعليقات أو صياغة <bdi>JSON5</bdi>،
  أو في ملف لا يمكن تحليله إطلاقًا، لا يكتب التثبيت شيئًا لإطار العمل ذاك ويخرج
  بالرمز 1 مع رمز الخطأ <bdi>`config.unparseable`</bdi>. ويسمّي الحقل
  <bdi>`fix`</bdi> المفاتيح التي كان التثبيت سيضيفها، لتتمكّن من تحويل الملف إلى
  <bdi>JSON</bdi> أو <bdi>YAML</bdi> عادية، أو إضافة تلك المفاتيح يدويًا ثم إعادة
  التشغيل.

## الخيارات

| الخيار | الوصف |
|---|---|
| <bdi>`--harness NAME`</bdi> | محوّل إطار العمل المراد تثبيته، أو <bdi>`all`</bdi> للمجموعة الشاملة للسجلّ كله (مطلوب). مع <bdi>`all`</bdi>، تُتخطّى أُطُر العمل المُدرَجة في <bdi>`exclude_harnesses`</bdi> الخاصة بالملف التعريفي، لكن إطار العمل المُسمّى صراحةً يُثبَّت حتى لو كان مُدرَجًا فيها. شغّل <bdi>`apothem harnesses list`</bdi> لمعرفة الأسماء المُسجَّلة. |
| <bdi>`--profile PATH`</bdi> | مسار ملف <bdi>YAML</bdi> للملف التعريفي المشترك. القيمة الافتراضية <bdi>`~/.config/apothem/profile.yaml`</bdi>. |
| <bdi>`--dry-run`</bdi> | يعاين التثبيت دون كتابة ملفات. |
| <bdi>`--clean`</bdi>، <bdi>`--fresh`</bdi> | بداية نظيفة اختيارية: ينسخ احتياطيًا حالة التثبيت السابقة الخاصة بكل إطار عمل ويزيلها قبل التثبيت. |
| <bdi>`--yes`</bdi> | يتخطّى التأكيد لكل هدف أثناء إزالة البداية النظيفة (مطلوب لتشغيلات <bdi>`--clean`</bdi> غير التفاعلية). |
| <bdi>`--project PATH`</bdi> | جذر المشروع لأُطُر العمل ذات نطاق المشروع. |
| <bdi>`--quiet`</bdi>، <bdi>`-q`</bdi> | يُخمِد المخرجات المعلوماتية؛ لا تُصدَر إلا الأخطاء. |
| <bdi>`--verbose`</bdi>، <bdi>`-v`</bdi> | يطبع تعليل كل قدرة غير مُسقَطة بدلًا من الملاحظة المُجمَّعة لكل إطار عمل. |
| <bdi>`--format plain\|json`</bdi> | صيغة المخرجات (الافتراضي: <bdi>`plain`</bdi>). |
| <bdi>`--json`</bdi> | اختصار لـ <bdi>`--format json`</bdi>. |
| <bdi>`--no-color`</bdi> | يعطّل رموز ألوان <bdi>ANSI</bdi> في المخرجات. |
| <bdi>`-h`</bdi>، <bdi>`--help`</bdi> | يعرض المساعدة ويخرج. |

## مخرجات <bdi>JSON</bdi>

عند تمرير <bdi>`--json`</bdi> (أو <bdi>`--format json`</bdi>)، يُكتَب مستند
<bdi>JSON</bdi> واحد إلى <bdi>stdout</bdi>:

```json
{
  "schema_version": 1,
  "status": "success",
  "command": "install",
  "action": "installed",
  "harness": "claude-code",
  "profile_path": "C:\\Users\\Example\\.config\\apothem\\profile.yaml",
  "project": null,
  "files_written": ["C:\\Users\\Example\\.claude\\settings.json"],
  "results": [],
  "warnings": [],
  "error": null,
  "output_path": "C:\\Users\\Example\\.claude\\settings.json"
}
```

مع <bdi>`--dry-run`</bdi>، لا يُكتَب شيء ويسرد <bdi>`results`</bdi> كل مسار كان
التثبيت سيكتبه، ولكلٍّ منها النتيجة التي كانت ستكون له (<bdi>`created`</bdi> أو
<bdi>`updated`</bdi> أو <bdi>`unchanged`</bdi>)، ولملفٍ تحرّره أنت أيضًا، الفرق
الموحّد في <bdi>`detail.diff`</bdi> — وهي الخطة نفسها التي يعرضها
[<bdi>`apothem diff`</bdi>](/docs/cli-reference/diff):

```json
{
  "schema_version": 1,
  "status": "dry_run",
  "command": "install",
  "action": "dry_run",
  "harness": "claude-code",
  "files_written": [],
  "results": [
    {
      "harness": "claude-code",
      "outcome": "created",
      "operation": "write_text",
      "path": "C:\\Users\\Example\\.claude\\settings.json",
      "message": "dry run: no filesystem changes made"
    }
  ],
  "warnings": [],
  "error": null
}
```

عند تمرير <bdi>`--clean`</bdi>، يحمل الغلاف إضافةً إلى ذلك كائن <bdi>`clean`</bdi>
يصف مرحلة الإزالة — قائمة مآل كل هدف، وما إذا كان التشغيل معاينةً، ودليل النسخ
الاحتياطي المختوم بالوقت (<bdi>`null`</bdi> في التشغيل التجريبي):

```json
{
  "clean": {
    "dry_run": true,
    "backup_dir": null,
    "targets": [
      {
        "path": "C:\\Users\\Example\\.claude",
        "present": true,
        "removed": false,
        "skipped_reason": null
      }
    ]
  }
}
```

يعاين التشغيل التجريبي مع البداية النظيفة المرحلتين كلتيهما في مستند واحد: معاينة
الإزالة تحت <bdi>`clean`</bdi>، ومعاينة الكتابة الجديدة تحت <bdi>`results`</bdi>.

تستخدم أخطاء التحقّق المتوقّعة الغلاف نفسه وتتضمّن كائن خطأ:

```json
{
  "schema_version": 1,
  "status": "error",
  "command": "install",
  "harness": "all",
  "files_written": [],
  "error": {
    "code": "project.required",
    "field": "project",
    "reason": "project-scope harnesses require --project: cursor, gemini-cli, github-copilot, kimi-code, windsurf, codebuddy, kiro, trae, zed, glm.",
    "fix": "Pass --project PATH or select only user-scope harnesses."
  }
}
```

## أمثلة

```bash
apothem install --harness claude-code
apothem install --harness claude-code --dry-run
apothem install --harness cursor --project . --profile ~/profile.yaml --json
apothem install --harness all --project . --dry-run --json
apothem installing --harness claude-code   # continuous-form alias
apothem Installing --harness claude-code   # capitalized variant
```

## رموز الخروج

| الرمز | المعنى |
|---|---|
| 0 | ثُبِّت المحوّل بنجاح، أو خُطِّط التشغيل التجريبي دون أخطاء |
| 1 | خطأ متوقّع في التحقّق، أو الملف التعريفي، أو إطار العمل، أو المشروع، أو المحوّل |
| 2 | تجسيد جزئي للدفعة بعد عملية كتابة واحدة على الأقل |
| 64 | خطأ استخدام: خيار أو أمر غير معروف، أو قيمة خيار مفقودة أو غير صالحة. ومع <bdi>`--json`</bdi> يكون الخطأ غلاف <bdi>JSON</bdi> يحمل الرمز <bdi>`cli.usage`</bdi>. |

## انظر أيضًا

- <bdi>`apothem installing`</bdi> — اسم مستعار بصيغة الاستمرار لهذا الأمر (موثّق هنا؛
  تقبل واجهة سطر الأوامر الصيغتين كلتيهما)
- [<bdi>apothem update</bdi>](/docs/cli-reference/update) — إعادة تطبيق الملف
  التعريفي الحالي على إطار عمل
- [<bdi>apothem verify</bdi>](/docs/cli-reference/verify) — تأكيد أن المحوّل فعّال
- [البدء](/docs/install) — دليل التثبيت الكامل
