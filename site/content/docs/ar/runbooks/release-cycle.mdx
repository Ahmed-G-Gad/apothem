يقود دليل التشغيل هذا إصدار <bdi>`vX.Y.Z`</bdi> من <bdi>`apothem`</bdi> من شجرة عمل
نظيفة إلى أسطح توزيع مُتحقَّق منها. كُتب الإجراء للمشرف الذي يستخدم <bdi>`gh`</bdi>
و<bdi>`git`</bdi> وصدفة طبقة الإصدار؛ وينتهي بصفحة إصدار مُتحقَّق منها،
و<bdi>CHANGELOG</bdi> مُدوَّن، واختبار دخان لمسار التثبيت يؤكّد أن كل سطح يواجه
المستخدم يستجيب لأمر التثبيت المرجعي.

نموذج الإصدار **تراكمي**. يضيف كل إصدار كوميتًا واحدًا على <bdi>`main`</bdi> ووسم
<bdi>`vX.Y.Z`</bdi> واحدًا موقَّعًا ومُعلَّقًا؛ لا يُدفَع أي شيء بالقوة، ولا يُزال
أي وسم سابق أو إصدار <bdi>GitHub</bdi> سابق أو نسخة <bdi>npm</bdi> سابقة. يحتفظ كل إصدار بوسمه وإصدار <bdi>GitHub</bdi> الخاص به ونسخة <bdi>npm</bdi> الخاصة به، وتبقى جميعها منشورة: نسخ <bdi>npm</bdi> غير قابلة للتغيير (لا يمكن أبدًا
استبدال <bdi>`name@version`</bdi> منشور)، وعمليات التثبيت المقيّدة بنسخة محدّدة
تعتمد على الوسوم.

يبدأ دفعُ الوسم ثلاثةَ سير عمل. يبني <bdi>`.github/workflows/release.yml`</bdi> إصدار
<bdi>GitHub</bdi> ويوقّعه ويُصدِر شهاداته وينشره مع مجموعة مُنتَجاته الكاملة:
<bdi>sdist</bdi>، و<bdi>wheel</bdi>، و<bdi>CycloneDX SBOM</bdi>، وحِزم
<bdi>Sigstore cosign</bdi>، والمنشأ <bdi>SLSA-3</bdi>، وأرشيفات بيئة التشغيل
الخاصة بالمنصّات. وينشر <bdi>`publish-npm.yml`</bdi> الحزمة
<bdi>`@ahmed-g-gad/apothem`</bdi> على <bdi>npmjs.com</bdi> عبر النشر الموثوق في
<bdi>npm</bdi>، و<bdi>`publish-vscode.yml`</bdi> يحزّم امتداد <bdi>VS Code</bdi> وينشره على
<bdi>Visual Studio Marketplace</bdi>. يصل قسم <bdi>CHANGELOG</bdi> المُرقَّم بالنسخة في كوميت الإصدار؛
ويُشغِّل المُشغِّل اختبار دخان مسار التثبيت بعد انتهاء سيرَي العمل كليهما.

## 1. المتطلّبات المسبقة

يتأكّد المشرف مما يلي قبل وضع الوسم:

- **شجرة العمل.** نظيفة (لا يُظهر <bdi>`git status`</bdi> شيئًا معلّقًا). كل عمل
  الميزات الخاص بالإصدار موجود على <bdi>`main`</bdi>.
- **<bdi>CI</bdi> أخضر.** بالنسبة لأحدث <bdi>`main`</bdi>، يُرجِع
  <bdi>`gh run list --branch=main --limit=1 --json conclusion --jq '.[0].conclusion'`</bdi>
  القيمة <bdi>`success`</bdi>.
- **الأدوات.** <bdi>`gh`</bdi> (<bdi>GitHub CLI</bdi>) بالنسخة 2.40 أو أحدث،
  مُصادَق عليه لحساب <bdi>`ahmed-g-gad`</bdi>؛ و<bdi>`git`</bdi> 2.40 أو أحدث مع
  تحميل مفتاح توقيع <bdi>GPG</bdi> الفرعي؛ وربط الناشر الموثوق في <bdi>npm</bdi>
  للحزمة <bdi>`@ahmed-g-gad/apothem`</bdi> فعّال (مُتحقَّق منه وفق
  [دليل تشغيل إعداد حساب الناشر](/docs/runbooks/publisher-account-setup)).
- **مراسي النسخة متوائمة.** سلسلة النسخة المُعلَنة في <bdi>`pyproject.toml`</bdi>
  تطابق الوسم المُخطَّط له دون البادئة <bdi>`v`</bdi> (يضبطها القسم 2.1، مع كل
  مرساة أخرى). تحقّق:

  ```bash
  grep '^version' pyproject.toml
  ```

  المخرجات المتوقّعة (لإصدار <bdi>`vX.Y.Z`</bdi>؛ العناصر النائبة تُمثّل وسم الإصدار الجاري):

  ```text
  version = "X.Y.Z"
  ```

- **مدخلات <bdi>CHANGELOG</bdi> مُجهَّزة.** تقع نقاط الإصدار تحت
  <bdi>`## [Unreleased]`</bdi> ضمن عناوين <bdi>Keep-a-Changelog</bdi>؛ ويحوّلها
  القسم 2.1 إلى قسم النسخة المؤرَّخ في الكوميت الذي يحمل الوسم.

## 2. الوسم والتشغيل

### 2.1 تأليف كوميت الإصدار

تعيش النسخة في أكثر من اثني عشر ملفًا، لذا لا تعدّلها يدويًا. أمر واحد يُحرّكها
جميعًا:

```bash
git checkout main
git pull --ff-only origin main
python scripts/release/bump_version.py X.Y.Z
```

يُحدّث <bdi>`bump_version.py`</bdi> كل مراسي النسخة معًا:

- كل بيان تحزيم، وامتداد، وإضافة، وسوق إضافات، إضافةً إلى ملف الاستشهاد (النسخة
  وتاريخ الإصدار). القائمة الكاملة:

  ```text
  pyproject.toml
  package.json
  site/package.json
  site/package-lock.json            (the project entries only)
  vscode-extension/package.json
  gemini-extension.json
  qwen-extension.json
  .claude-plugin/marketplace.json   (top level and metadata)
  plugins/apothem/plugin.json
  plugins/apothem/.codex-plugin/plugin.json
  CITATION.cff
  ```

- <bdi>`CHANGELOG.md`</bdi>: تصبح مدخلات <bdi>`[Unreleased]`</bdi> قسمًا مؤرَّخًا
  <bdi>`## [X.Y.Z]`</bdi>، ويقارن <bdi>`[Unreleased]`</bdi> بدءًا من
  <bdi>`vX.Y.Z`</bdi>، ويُضاف رابط <bdi>`[X.Y.Z]`</bdi>.
- <bdi>`SECURITY.md`</bdi>: يحصل الإصدار الثانوي الجديد على صفّ مدعوم
  <bdi>`X.Y.x`</bdi>. أمّا بقاء الإصدارات الثانوية الأقدم مُدرَجة فقرارك؛ ويطبع
  السكربت تذكيرًا.

ثم يُعيد توليد الأشجار المشتقّة: حزمة إضافة <bdi>Claude Code</bdi>، واللقطات
الذهبية لفارق السلوك، وصفحات مرجع الوثائق وسجلّ التغييرات. مرِّر
<bdi>`--dry-run`</bdi> لسرد التغييرات أولًا، أو <bdi>`--date YYYY-MM-DD`</bdi> لضبط
تاريخ الإصدار (الافتراضي: تاريخ اليوم بتوقيت <bdi>UTC</bdi>)، أو
<bdi>`--no-regen`</bdi> لتخطّي إعادة التوليد. يرفض السكربت النسخة المشوّهة أو خفض
النسخة، وإعادة تشغيله بالنسخة الحالية لا تفعل سوى إعادة مواءمة المراسي الشاردة.

راجِع الفرق، ثم أنشئ الكوميت:

```bash
git add -A
git commit -S -m "chore(release): cut vX.Y.Z"
git push origin main
```

تُوقّع الراية <bdi>`-S`</bdi> الكوميت بمفتاح <bdi>GPG</bdi>. يُطلِق الدفع مصفوفة
<bdi>CI</bdi> القياسية (<bdi>lint</bdi>، <bdi>test</bdi>، <bdi>build</bdi>)؛ انتظر
النتيجة الخضراء قبل وضع الوسم.

يحتاج فحص الجاهزية في القسم 2.4 أيضًا إلى أن تكون نتيجة سيرَي عمل <bdi>CodeQL</bdi> و<bdi>Conformity</bdi> خضراء على كوميت الإصدار. يعمل كلٌّ منهما فقط عندما تتغيّر مساراته الخاصة، وعادةً لا يغيّر كوميت الإصدار أيًّا منها، لذا شغِّلهما بعد أن يصبح كوميت الإصدار رأس <bdi>`main`</bdi>، ثم تحقّق من أن كل تشغيل يُسمّي ذلك الكوميت:

```bash
gh workflow run codeql.yml --ref main
gh workflow run conformity.yml --ref main
gh run list --workflow codeql.yml --commit "$(git rev-parse HEAD)" --limit 1
gh run list --workflow conformity.yml --commit "$(git rev-parse HEAD)" --limit 1
```

انتظر حتى ينجح الاثنان قبل وضع الوسم، ولا تدفع شيئًا آخر إلى <bdi>`main`</bdi> حتى يُنشر الإصدار: فالدفع اللاحق يُبعد <bdi>`main`</bdi> عن كوميت الإصدار، و<bdi>CI</bdi> يُلغي أي تشغيل ما زال جاريًا على الفرع نفسه.

### 2.2 توقيع الوسم ودفعه

```bash
git tag -a -s vX.Y.Z -m "vX.Y.Z"
git push origin vX.Y.Z
```

يُنتِج الجمع بين <bdi>`-a -s`</bdi> وسمًا مُعلَّقًا موقَّعًا بـ <bdi>GPG</bdi>.
يُطلِق الدفع <bdi>`.github/workflows/release.yml`</bdi>، الذي يبني ويوقّع ويُصدِر
الشهادات وينشر.

### 2.3 تأكيد اكتمال سير عمل الإصدار

```bash
gh run watch $(gh run list --workflow=release.yml --limit=1 --json databaseId --jq '.[0].databaseId')
```

يُشغِّل سير العمل البناء (<bdi>sdist + wheel</bdi>، ثم <bdi>CycloneDX SBOM</bdi>
لتلك التوزيعات يُكتَب بجانبها)، وتوقيع <bdi>cosign</bdi> بلا مفاتيح، وتوليد المنشأ <bdi>SLSA-3</bdi> والتحقّق منه، وبناء أرشيفات المنصّات
(<bdi>darwin / linux / windows</bdi>)، وتوقيع الأرشيفات مع بيان
<bdi>`SHA256SUMS`</bdi> مُجمَّع، والنشر النهائي لإصدار <bdi>GitHub</bdi>. يفحص
المشرف سجلّ مهمة <bdi>`publish GitHub Release`</bdi> بحثًا عن تأكيدات رفع الأصول.

تعمل مهمة <bdi>`publish GitHub Release`</bdi> في بيئة <bdi>`release`</bdi>، وهي تتطلّب موافقة المشرف، لذا ينتظر التشغيل هناك بعد نجاح المهام السابقة. وافِق عليه من صفحة التشغيل عبر الزر **<bdi>Review deployments</bdi>** (مراجعة عمليات النشر)، أو من الصدفة:

```bash
run_id=$(gh run list --workflow=release.yml --limit=1 --json databaseId --jq '.[0].databaseId')
env_id=$(gh api repos/ahmed-g-gad/apothem/environments/release --jq .id)
gh api -X POST "repos/ahmed-g-gad/apothem/actions/runs/${run_id}/pending_deployments" \
  -F "environment_ids[]=${env_id}" -f state=approved -f comment="vX.Y.Z"
```

يُطلِق دفعُ الوسم أيضًا سيرَي عمل <bdi>npm</bdi> وامتداد <bdi>VS Code</bdi>. وتنتظر مهام النشر فيهما الموافقة نفسها حتى القسم 2.4.

### 2.4 تأكيد نشر <bdi>npm</bdi>

يُشغِّل دفعُ الوسم أيضًا <bdi>`publish-npm.yml`</bdi> بجانب <bdi>`release.yml`</bdi>. ولا ينتظر سيرُ عمل <bdi>npm</bdi> سيرَ عمل الإصدار؛ فموافقة بيئة <bdi>`release`</bdi> هي البوابة. وبعد أن ينتهي سير عمل الإصدار من القسم 2.3، تأكّد من الجاهزية. ويقرأ الفحص الإصدارات، وتشغيلات سير العمل، وملف <bdi>SBOM</bdi> المنشور، لذا جهّز مُدخلَين أولًا:

- **<bdi>`GH_TOKEN`</bdi>.** يرفض السكربت العمل بدونه، حتى عندما يكون <bdi>`gh`</bdi> مُسجَّل الدخول أصلًا. استخدم رمز وصول شخصيًا دقيق النطاق (fine-grained) مقصورًا على <bdi>`ahmed-g-gad/apothem`</bdi>، مع صلاحية **<bdi>Actions: Read</bdi>** (تشغيلات سير العمل) و**<bdi>Contents: Read</bdi>** (الإصدارات). ولا يكتب الفحص شيئًا، لذا لا تلزم صلاحية كتابة. ويحمل الرمز الصادر عن <bdi>`gh auth token`</bdi> كل نطاقات تسجيل الدخول، لذا يُفضَّل الرمز دقيق النطاق.
- **ملف <bdi>SBOM</bdi> المنشور.** يقرأ الفحص <bdi>`dist/release-assets/sbom.cdx.json`</bdi>، وهو ملف <bdi>CycloneDX</bdi> الذي يرفقه الإصدار. نزّل النسخة التي نشرها الإصدار بدلًا من بناء محلي.

```bash
read -rs GH_TOKEN && export GH_TOKEN
mkdir -p dist/release-assets
gh release download vX.Y.Z --repo ahmed-g-gad/apothem \
  --pattern sbom.cdx.json --dir dist/release-assets --clobber
bash scripts/release/check-release-ready.sh vX.Y.Z
```

يفشل الفحص عندما يكون الإصدار مسودّةً أو إصدارًا تجريبيًا (prerelease)، أو عندما لا يكون سير عمل مطلوب لإيداع الوسم أخضر، أو عندما يغيب ملف <bdi>SBOM</bdi>، أو عندما يصف إصدارًا آخر، أو عندما يُغفل حزمةً مُضمَّنة (vendored). وتُسمّي رسالة الفشل السببَ.

عند نجاح الفحص، وافِق على تشغيل <bdi>`Publish npm`</bdi> المنتظر بالطريقة نفسها المذكورة في القسم 2.3 (يأتي معرّف التشغيل من <bdi>`gh run list --workflow=publish-npm.yml`</bdi>). ينشر سير العمل <bdi>`@ahmed-g-gad/apothem@X.Y.Z`</bdi> على <bdi>npmjs.com</bdi> عبر النشر الموثوق في <bdi>npm</bdi> (<bdi>OIDC</bdi>)؛ ولا يُخزَّن أي رمز مميّز للسجلّ في المستودع. ووافِق كذلك على تشغيل <bdi>`Publish VS Code Extension`</bdi> المنتظر. وهو يحزّم <bdi>`apothem.vsix`</bdi> وينشره على <bdi>Visual Studio Marketplace</bdi> بالمعرّف <bdi>`ahmed-g-gad.apothem-vscode`</bdi>. لا تعمل خطوة النشر إلا حين يساوي متغيّر المستودع <bdi>`VSCODE_MARKETPLACE_READY`</bdi> القيمة <bdi>`true`</bdi> ويكون اعتماد واحد مهيّأً: المتغيّر <bdi>`VSCE_AUTH=oidc`</bdi> (النشر الموثوق في <bdi>Marketplace</bdi>، بلا سرّ مخزَّن)، أو المتغيّرات <bdi>`VSCE_AUTH=entra`</bdi> و<bdi>`AZURE_CLIENT_ID`</bdi> و<bdi>`AZURE_TENANT_ID`</bdi> (رمز <bdi>Microsoft Entra ID</bdi> قصير العمر، بلا سرّ مخزَّن)، أو سرّ <bdi>`VSCE_PAT`</bdi>. وفي غياب أيٍّ منها يحزّم التشغيل الامتداد ويتخطّى النشر. الاعتماد مفتاح تبديل لا إعادة محاولة: فالنشر الفاشل عبر أحد المسارات لا يرتدّ إلى مسار آخر من تلقاء نفسه. إعداد كل مسار موجود في [النشر على <bdi>Marketplace</bdi> عبر <bdi>Trusted Publishing</bdi>](#النشر-على-marketplace-عبر-trusted-publishing) (المُفضَّل) و[النشر على <bdi>Marketplace</bdi> عبر <bdi>Microsoft Entra ID</bdi>](#النشر-على-marketplace-عبر-microsoft-entra-id) أدناه.

لإعادة النشر بعد تشغيل فاشل، شغِّل سير العمل يدويًا للوسم نفسه
(<bdi>`gh workflow run publish-npm.yml --field tag=vX.Y.Z`</bdi>). يتخطّى سير العمل
النشر عندما تكون النسخة موجودة بالفعل في السجلّ، لأن نسخ <bdi>npm</bdi> غير قابلة
للتغيير.

#### النشر على Marketplace عبر Trusted Publishing

يتيح النشر الموثوق (<bdi>Trusted Publishing</bdi>) لـ <bdi>Marketplace</bdi> أن يقبل رمز <bdi>GitHub OIDC</bdi> الخاص بهذا المستودع مباشرةً: إذ يستبدل <bdi>`vsce publish --oidc`</bdi> رمزَ مهمة النشر باعتماد <bdi>Marketplace</bdi> قصير العمر. لا يوجد سرّ مخزَّن ولا مورد <bdi>Azure</bdi>، لذا فهذا هو المسار المُفضَّل. ويبقى مسار <bdi>Entra</bdi> أدناه وسرّ <bdi>`VSCE_PAT`</bdi> بديلَين يختارهما المشغِّل.

1. **استخدم إصدارًا من <bdi>vsce</bdi> يدعمه.** على هذا المسار تفحص مهمة النشر إصدار <bdi>vsce</bdi> المقفَل في <bdi>`tools/vsce`</bdi> قبل أن تنشر، وتتوقّف بخطأ يُسمّي الإصدار الأدنى حين يكون القفل أقدم منه. يقترح <bdi>Dependabot</bdi> تحديثات <bdi>vsce</bdi> لملف القفل ذاك؛ ادمج التحديث الذي يبلغ الإصدار الأدنى قبل أن تبدّل المسار.
2. **أنشئ السياسة.** سجّل الدخول بصفتك مالكًا (<bdi>Owner</bdi>) للناشر، وافتح
   <bdi>`https://marketplace.visualstudio.com/manage/publishers/ahmed-g-gad`</bdi>، وأضف
   سياسة تحت **<bdi>Trusted Publishing</bdi>**:
   - اسم السياسة: أي اسم، مثل <bdi>`apothem-release`</bdi>
   - مالك المستودع: <bdi>`Ahmed-G-Gad`</bdi>
   - المستودع: <bdi>`apothem`</bdi>
   - سير العمل: <bdi>`publish-vscode.yml`</bdi>
   - البيئة: <bdi>`release`</bdi>

   أسماء الحقول هي التي يسردها دليل النشر في <bdi>VS Code</bdi>، في قسمه عن النشر باستخدام <bdi>GitHub Actions</bdi> و<bdi>Trusted Publishing</bdi>
   (<bdi>`https://code.visualstudio.com/api/working-with-extensions/publishing-extension`</bdi>).
   غير مؤكَّد: ما إذا كان كل ناشر يرى تبويب <bdi>Trusted Publishing</bdi> حتى الآن. إن لم يظهر لك، فاستخدم مسار <bdi>Entra</bdi>.
3. **بدّل المسار.** أبقِ <bdi>`VSCODE_MARKETPLACE_READY`</bdi> مضبوطًا على <bdi>`true`</bdi> واضبط المُحدِّد. اضبطه حين لا يكون أي وسم في الانتظار، لأن دفع الوسم التالي ينشر عبر هذا المسار.

   ```bash
   gh variable set VSCE_AUTH --body oidc
   ```

4. **انشر.** يَنشر دفعُ الوسم التالي، أو تشغيلٌ يدوي لوسم موجود، عبر <bdi>Trusted Publishing</bdi>. لا يملك هذا المسار تشغيلًا تجريبيًا: النشر الأول هو الفحص، والتشغيل اليدوي مع <bdi>`dry_run`</bdi> لا يفعل سوى التحذير من أن شيئًا لم يُتحقَّق منه.
5. **ارجع إلى البديل إن فشل.** احذف المُحدِّد وشغِّل سير العمل يدويًا مرّة أخرى للوسم نفسه؛ ومع ضبط سرّ <bdi>`VSCE_PAT`</bdi> ينشر مسار الرمز. النشر الفاشل لم ينشر شيئًا، لذا يمكن تشغيل الوسم نفسه يدويًا مرّة أخرى.

   ```bash
   gh variable delete VSCE_AUTH
   ```

#### النشر على Marketplace عبر Microsoft Entra ID

يستبدل مسار <bdi>Entra</bdi> رمزَ الوصول الشخصي المخزَّن برمز قصير العمر. يطلب <bdi>`publish-vscode.yml`</bdi> من <bdi>GitHub</bdi> رمز <bdi>OIDC</bdi>، ويستبدله الإجراء <bdi>`Azure/login`</bdi> بتسجيل دخول إلى <bdi>Entra</bdi> عبر اعتماد اتحادي (federated credential)، وينشر <bdi>`vsce publish --azure-credential`</bdi> بالرمز الناتج. لا يوجد أي سرّ عميل (client secret). ويبقى سرّ <bdi>`VSCE_PAT`</bdi> بديلًا احتياطيًا يختاره المشغِّل؛ ولا ينتقل سير العمل إليه من تلقاء نفسه أبدًا.

يدعم إصدار <bdi>vsce</bdi> المثبَّت في <bdi>`tools/vsce`</bdi> هذا المسار. ويحتاج المسار إلى مستأجر (tenant) في <bdi>Entra</bdi>، وتسجيل تطبيق، وعضوية في الناشر، وهو ما لا يحتاجه <bdi>Trusted Publishing</bdi> أعلاه؛ استخدمه حين لا يكون <bdi>Trusted Publishing</bdi> متاحًا للناشر.

1. **تحقّق من الشروط المسبقة.** اعثر على الحساب الذي يملك الناشر <bdi>`ahmed-g-gad`</bdi> (تبويب <bdi>Members</bdi> في
   <bdi>`https://marketplace.visualstudio.com/manage/publishers/ahmed-g-gad`</bdi>) وعلى
   مستأجر <bdi>Entra</bdi> الذي يمكنك فيه تسجيل التطبيقات. غير مؤكَّد: ما إذا كان يجب أن يطابق مستأجرُ مالك الناشر مستأجرَ التطبيق، وما إذا كان يجب ربط مؤسسة <bdi>Azure DevOps</bdi> المسمّاة <bdi>`Ahmed-G-Gad`</bdi> بـ <bdi>Entra</bdi> (<bdi>`dev.azure.com/Ahmed-G-Gad`</bdi>، <bdi>Organization settings</bdi>، <bdi>Microsoft Entra</bdi>). لا يذكر أي مصدر أيًّا من الأمرين. إن فشلت الخطوة 5 أو 6، فتحقّق من هذين أولًا.

2. **سجّل التطبيق.** في <bdi>`https://entra.microsoft.com`</bdi>، افتح <bdi>App registrations</bdi>، ثم <bdi>New registration</bdi>. سمِّه <bdi>`apothem-vscode-publish`</bdi>، واختر مستأجرًا واحدًا (single tenant)، واترك عنوان إعادة التوجيه (redirect URI) فارغًا. ومن <bdi>Overview</bdi>، انسخ <bdi>Application (client) ID</bdi> و<bdi>Directory (tenant) ID</bdi>. لا تُنشئ أي سرّ عميل ولا تمنح أي صلاحية <bdi>API</bdi>. تحتاج الخطوة إلى حقوق مالك التطبيق أو إلى دور في <bdi>Entra</bdi> مثل <bdi>Application Administrator</bdi>.

3. **أضف الاعتماد الاتحادي.** على ذلك التطبيق، افتح <bdi>Certificates & secrets</bdi>، ثم <bdi>Federated credentials</bdi>، ثم <bdi>Add credential</bdi>، واختر السيناريو "GitHub Actions deploying Azure resources". أدخل المؤسسة <bdi>`Ahmed-G-Gad`</bdi>، والمستودع <bdi>`apothem`</bdi>، ونوع الكيان <bdi>`Environment`</bdi>، واسم البيئة <bdi>`release`</bdi>، واسم الاعتماد <bdi>`apothem-release`</bdi>. يجب أن تكون الحقول المولَّدة كما يلي:

   ```text
   issuer:   https://token.actions.githubusercontent.com
   subject:  repo:Ahmed-G-Gad/apothem:environment:release
   audience: api://AzureADTokenExchange
   ```

   المطابقة دقيقة وحسّاسة لحالة الأحرف. إن فشل تسجيل دخول لاحق مع <bdi>AADSTS700213</bdi> أو <bdi>AADSTS7002138</bdi>، فقارن الاعتماد بسطر <bdi>`subject claim`</bdi> الذي يكتبه <bdi>`Azure/login`</bdi> في سجلّ المهمة. ويعني <bdi>AADSTS70021</bdi> مباشرةً بعد الإنشاء أن الاعتماد لم ينتشر بعد؛ انتظر بضع دقائق وأعد المحاولة.

4. **اضبط متغيّرات المستودع.** ما دام <bdi>`VSCODE_MARKETPLACE_READY`</bdi> يساوي <bdi>`true`</bdi>، يصبح مسار <bdi>Entra</bdi> فعّالًا بمجرّد ضبط المتغيّرات الثلاثة كلها، لذا اضبطها حين لا يكون أي وسم إصدار في انتظار الموافقة. ومن دون <bdi>`VSCODE_MARKETPLACE_READY=true`</bdi> لا يجري أي تسجيل دخول ويتخطّى التشغيل النشر.

   ```bash
   gh variable set AZURE_CLIENT_ID --body "<application-client-id>"
   gh variable set AZURE_TENANT_ID --body "<directory-tenant-id>"
   gh variable set VSCE_AUTH --body entra
   ```

   اترك <bdi>`VSCODE_MARKETPLACE_READY`</bdi> و<bdi>`VSCE_PAT`</bdi> على حالهما. حين يكون <bdi>`VSCE_AUTH`</bdi> مساويًا لـ <bdi>`entra`</bdi> لكن <bdi>`AZURE_CLIENT_ID`</bdi> أو <bdi>`AZURE_TENANT_ID`</bdi> فارغ، يسجّل سير العمل تحذيرًا، سواء أكان <bdi>`VSCE_PAT`</bdi> مضبوطًا أم لا، ولا يستخدم مسار <bdi>Entra</bdi>. ثم يستخدم سرّ <bdi>`VSCE_PAT`</bdi> إن كان مضبوطًا؛ ومن دون السرّ لا ينشر شيئًا وينتهي التشغيل مع ذلك أخضر، لذا ابحث عن التحذير.

5. **شغِّل التشغيل التجريبي.** شغِّل سير العمل يدويًا لوسم إصدار موجود مع ضبط <bdi>`dry_run`</bdi>. على مسار <bdi>Entra</bdi> يسجّل الدخول، ويطبع ملف تعريف <bdi>Azure DevOps</bdi>، ويتحقّق من الوصول إلى الناشر دون نشر. لا يملك مسار الرمز تشغيلًا تجريبيًا: إن أظهر السجلّ <bdi>`Marketplace credential mode: pat`</bdi>، ينتهي التشغيل أخضر مع تحذير دون أن يتحقّق من شيء. وافِق على تشغيل بيئة <bdi>`release`</bdi> المنتظر.

   ```bash
   gh workflow run publish-vscode.yml --ref main -f tag=vX.Y.Z -f dry_run=true
   ```

   المتوقّع: <bdi>`Marketplace credential mode: entra`</bdi>، وسطر <bdi>`subject claim`</bdi> مساوٍ لقيمة subject في الخطوة 3، والقيمتان <bdi>`id`</bdi> و<bdi>`displayName`</bdi> لملف التعريف كما تطبعهما أول خطوة من التشغيل التجريبي. يُتوقَّع أن تفشل خطوة التحقّق بالرمز 403 حتى الخطوة 6. غير مؤكَّد: أن تسجيل دخول بلا اشتراك <bdi>Azure</bdi> يُنتِج رمزًا لـ <bdi>Marketplace</bdi> عبر <bdi>Azure CLI</bdi>. وهذا التشغيل هو أول اختبار لذلك. إن فشل هنا، فسجّل بدلًا من ذلك هوية مُدارة مُعيَّنة من المستخدم (user-assigned managed identity) ضمن اشتراك، وهو المسار الذي توثّقه <bdi>Microsoft</bdi>.

6. **أضف التطبيق إلى الناشر.** في تبويب <bdi>Members</bdi> من الخطوة 1، سجّل الدخول بصفتك مالكًا للناشر وأضف عضوًا باستخدام قيمة <bdi>`id`</bdi> لملف التعريف من الخطوة 5، بالدور <bdi>Contributor</bdi>. غير مؤكَّد: تسمية الحقل في مربّع الحوار، وما إذا كان يقبل المعرّف قبل أن يصبح التطبيق عضوًا في مؤسسة <bdi>Azure DevOps</bdi>. تضيف <bdi>Azure DevOps</bdi> هويات التطبيقات لكل مؤسسة على حدة كقاعدة عامة. إن رفض مربّع الحوار المعرّف، فأضف كيان الخدمة (service principal) إلى المؤسسة <bdi>`Ahmed-G-Gad`</bdi> (<bdi>Organization settings</bdi>، <bdi>Users</bdi>، باستخدام <bdi>Object ID</bdi> الخاص بـ <bdi>Enterprise application</bdi>) وأعد المحاولة. وغير مؤكَّد أيضًا: ما إذا كان ملف التعريف موجودًا قبل أول استدعاء تُجريه الهوية إلى <bdi>Azure DevOps</bdi>.

7. **كرّر التشغيل التجريبي.** تنجح خطوة التحقّق الآن بالرسالة "verification succeeded for the publisher"؛ ولا تزال رسائلها تذكر <bdi>Personal Access Token</bdi>، لأن رمز <bdi>Entra</bdi> يسلك المسار نفسه. يُثبت الفحص عضوية الناشر (<bdi>Creator</bdi> أو <bdi>Owner</bdi> أو <bdi>Contributor</bdi> أو <bdi>Reader</bdi>)، لا صلاحيات النشر. غير مؤكَّد: أن <bdi>Contributor</bdi> يكفي لنشر تحديث. يقول وصف <bdi>Microsoft</bdi> للدور إنه يكفي، ولا يُظهر أي مصدر نشرًا به، لذا فالنشر الحقيقي الأول هو البرهان.

8. **انشر إصدارًا.** ضع الوسم كما في القسم 2.2 ووافِق على التشغيل. تعمل الخطوة <bdi>`Publish to Visual Studio Marketplace (Entra ID)`</bdi>، وتُدرِج ترويسة بيئتها <bdi>`AZURE_TENANT_ID`</bdi> وحده، وتُتخطّى خطوة الرمز الاحتياطية، ويطبع <bdi>vsce</bdi> النص <bdi>`DONE Published ahmed-g-gad.apothem-vscode`</bdi>. ويُدرِج معرض <bdi>Marketplace</bdi> النسخة الجديدة بعد نحو أربع دقائق.

9. **قرّر بشأن الرمز.** احتفظ بـ <bdi>`VSCE_PAT`</bdi> حتى أول نشر ناجح عبر <bdi>Entra</bdi>، ثم احذف السرّ إن لم تكن تريد بديلًا احتياطيًا. وبمجرّد حذفه، يترك متغيّرُ <bdi>Entra</bdi> المحذوف أو الفارغ التشغيلَ أخضر بلا نشر: مع تحذير حين يظل <bdi>`VSCE_AUTH`</bdi> مساويًا لـ <bdi>`entra`</bdi>، ومع إشعار التخطّي وحده حين لا يكون كذلك. اقرأ تعليقات التشغيل التوضيحية (annotations) بعد كل وسم. وللاحتفاظ ببديل احتياطي بعد إيقاف رموز الوصول الشخصية العامّة (global)، أنشئ رمزًا مقصورًا على المؤسسة <bdi>`Ahmed-G-Gad`</bdi> بالنطاق المخصّص <bdi>Marketplace Manage</bdi> وأقصر مدّة صلاحية تقبلها، وخزّنه باسم <bdi>`VSCE_PAT`</bdi>. غير مؤكَّد: تسميات البوابة في هذه الخطوة مأخوذة من الذاكرة، لا من مصدر أوّلي؛ وتصف <bdi>Microsoft</bdi> الرموز المقصورة على المؤسسة بأنها حلّ التفافي مؤقّت ويمكنها أن تتوقّف عن قبولها؛ وتتعارض صفحات <bdi>Microsoft</bdi> بشأن تاريخ إيقاف الرموز العامّة.

10. **ارجع إلى الرمز.** احذف المُحدِّد وشغِّل سير العمل يدويًا مرّة أخرى، ثم وافِق على التشغيل. النشر الفاشل عبر <bdi>Entra</bdi> لم ينشر شيئًا، لذا يمكن تشغيل الوسم نفسه يدويًا مرّة أخرى؛ تحقّق من صفحة <bdi>Marketplace</bdi> أولًا، لأن النسخة التي وصلت لا يمكن نشرها مرّتين.

    ```bash
    gh variable delete VSCE_AUTH
    gh workflow run publish-vscode.yml --ref main -f tag=vX.Y.Z
    ```

حين يفشل النشر عبر <bdi>Entra</bdi>، اقرأ سجلّ الخطوة:

- الرسالة التي تبدأ بـ "Can not acquire a Microsoft Entra ID access token" تعني أن تسجيل الدخول أو سلسلة الاعتماد قد فشلت. تحقّق من خطوة <bdi>`Sign in to Microsoft Entra ID`</bdi> ومن الاعتماد الاتحادي أولًا. إن كان تسجيل الدخول أخضر، فأزِل <bdi>`AZURE_TENANT_ID`</bdi> من <bdi>`env`</bdi> في خطوة <bdi>vsce</bdi> ضمن سير العمل؛ فسير عمل إصدار الامتداد الذي تعتمده <bdi>GitHub</bdi> نفسها لا يُصدِّره.
- تعني "InvalidAccessException" أو "not allowed" أن هوية الرمز ليست عضوًا في الناشر. قارن قيمة <bdi>`id`</bdi> لملف التعريف من التشغيل التجريبي بتبويب <bdi>Members</bdi>.
- تعني الاستجابة 403 من خطوة التحقّق في التشغيل التجريبي أن التطبيق لا يملك دورًا بعد.

تنطبق ثلاثة قيود على هذا المسار:

- تُمنح <bdi>`id-token: write`</bdi> لمهمة النشر كلها، لذا يمكن لكل خطوة فيها أن تطلب رمز <bdi>OIDC</bdi>، في وضع الرمز أيضًا. ويرتبط subject الرمز ببيئة <bdi>`release`</bdi>، التي تتطلّب موافقة مُراجِع.
- لا تملك بيئة <bdi>`release`</bdi> أي سياسة فروع أو وسوم للنشر، لذا يمكن لأي مرجع (ref) يوافق عليه مشرف أن يحصل على الرمز ذي subject البيئة. ويحتاج تقييدها بوسوم <bdi>`v*.*.*`</bdi> إلى التحقّق أولًا مما يُشغِّله <bdi>`release.yml`</bdi> و<bdi>`publish-npm.yml`</bdi>.
- تغيير اسم المستودع أو نقله يغيّر صيغة subject في <bdi>OIDC</bdi> ويكسر الاعتماد الاتحادي بصمت. انسخ قيمة subject من سجلّ <bdi>`Azure/login`</bdi> إلى الاعتماد مرّة أخرى بعد أي تغيير للاسم.

### 2.5 تحديث القيم المثبَّتة لبصمات القوالب

بعد أن يوجد الوسم، اضبط <bdi>`_LATEST_RELEASE`</bdi> و<bdi>`_LATEST_RELEASE_DIGESTS`</bdi> في
<bdi>`tests/unit/test_template_digests.py`</bdi> على الإصدار الجديد وعلى بصمة <bdi>SHA-256</bdi>
لكل قالب نصي عادي كما شحنه ذلك الإصدار
(<bdi>`git show vX.Y.Z:<template path> | sha256sum`</bdi>). افعل ذلك في التغيير التالي على
<bdi>`main`</bdi>، وأضف البصمة السابقة إلى <bdi>`earlier_digests`</bdi> في مُدخل البيان حين
يكون القالب قد تغيّر. تستخرج مهمة <bdi>`release-preflight`</bdi> في <bdi>CI</bdi> كل وسم،
لذا تفشل مع ذكر أسماء الوسوم إلى أن تُحدَّث القيم المثبَّتة.

إصدار <bdi>GitHub</bdi> هو سطح المُنتَجات المرجعي؛ وحزمة <bdi>npm</bdi> ومُثبِّتات
السكربت هي مسارات التثبيت المبنيّة فوقه. ويعمل نشر <bdi>npm</bdi> بجانب سير عمل
الإصدار على دفع الوسم نفسه.

## 4. انضباط <bdi>CHANGELOG</bdi>

يحمل <bdi>`CHANGELOG.md`</bdi> قسمًا واحدًا لكل إصدار وفق اصطلاح
<bdi>Keep-a-Changelog</bdi>. تعديل <bdi>CHANGELOG</bdi> في كوميت الإصدار:

- يتأكّد من أن قسم النسخة يستخدم العنوان <bdi>`## [X.Y.Z] - YYYY-MM-DD`</bdi>
  (بشَرطة قصيرة؛ يكتبه <bdi>`bump_version.py`</bdi>، ويطابق
  <bdi>`extract_release_notes.py`</bdi> البادئة <bdi>`## [X.Y.Z]`</bdi>).
- يتأكّد من استخدام العناوين القياسية — <bdi>Added</bdi>، <bdi>Changed</bdi>،
  <bdi>Deprecated</bdi>، <bdi>Removed</bdi>، <bdi>Fixed</bdi>، <bdi>Security</bdi> —
  حيثما ينطبق. تُسقَط العناوين الفارغة من الملف المعروض.
- يلتقط **القدرات**، لا التنفيذ. لغة المجال فقط؛ بلا مراجع داخلية للخطط؛ بلا
  بصمات كوميتات؛ بلا مُعرِّفات خطط أو مراحل.

قسم <bdi>CHANGELOG</bdi> الذي اجتاز مراجعة المشرف يُقرأ بوصفه مرساة ملاحظات
الإصدار لسرد الإعلان.

## 5. اختبار دخان مسار التثبيت

بعد اكتمال المرحلتين كلتيهما، يُشغِّل المشرف اختبار الدخان. اختبار الدخان هو
التحقّق المرجعي من أن أوامر التثبيت التي تواجه المستخدم تستجيب.

### 5.1 إضافة <bdi>Claude Code</bdi>

```text
/plugin marketplace add ahmed-g-gad/apothem
/plugin install apothem@apothem
```

المتوقّع: تُثبَّت الإضافة وتصبح أوامر <bdi>`apothem`</bdi> متاحة داخل
<bdi>Claude Code</bdi>.

### 5.2 <bdi>Node.js (npx)</bdi>

```bash
npx @ahmed-g-gad/apothem@X.Y.Z --version
```

المخرجات المتوقّعة: <bdi>`Apothem, version X.Y.Z`</bdi>.

### 5.3 مُثبِّت السكربت بخطوة واحدة (<bdi>POSIX</bdi>)

يكتب المُثبِّت المُشغِّل <bdi>`apothem`</bdi> في <bdi>`~/.local/bin`</bdi>، أو في الدليل المسمّى في <bdi>`APOTHEM_BIN_DIR`</bdi> حين يكون هذا المتغيّر مضبوطًا. ويحتاج الفحص أدناه إلى أن يكون ذلك الدليل على <bdi>`PATH`</bdi>. وحين لا يكون كذلك، يطبع المُثبِّت سطر <bdi>`export PATH`</bdi> الذي يجب إضافته. وما لم يكن ذلك الدليل على <bdi>`PATH`</bdi>، فلن تجد الصدفة <bdi>`apothem`</bdi>، ويفشل الفحص. وإذا تعذّر على المُثبِّت وضع المُشغِّل، طبع تحذيرًا دون سطر <bdi>`export PATH`</bdi>. وفي مضيف لا يحمل مفتاح توقيع المشرف بعد، يستورده السطر الأول، ويتوقّف المُثبِّت من دونه.

```bash
curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import
curl -fsSL https://apothem.ahmedgad.com/install.sh | sh
apothem --version
```

المخرجات المتوقّعة: <bdi>`Apothem, version X.Y.Z`</bdi>.

### 5.4 مُثبِّت السكربت بخطوة واحدة (<bdi>Windows</bdi>)

يستورد السطر الأول مفتاح توقيع المشرف عبر <bdi>`bash`</bdi> الخاص بـ<bdi>Git</bdi> نفسه، إذ إن حلقة مفاتيح <bdi>`gpg`</bdi> التابعة له هي التي يقرأها <bdi>`git verify-tag`</bdi>.

```powershell
& "$env:ProgramFiles\Git\bin\bash.exe" -c 'curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import'
irm https://apothem.ahmedgad.com/install.ps1 | iex
apothem --version
```

المخرجات المتوقّعة: <bdi>`Apothem, version X.Y.Z`</bdi>.

### 5.5 التحقّق من المُنتَجات (أدلّة سلسلة التوريد)

نزِّل كل الأصول إلى دليل فارغ، ثم تحقّق. هوية الشهادة هي سير عمل الإصدار عند هذا
الوسم بالضبط. فحوص الهوية حسّاسة لحالة الأحرف، وتحمل الشهادات اسم المالك كما
يُبلغ عنه <bdi>GitHub</bdi>، أي <bdi>`Ahmed-G-Gad`</bdi>، لذا يفشل اسم المالك
المكتوب بأحرف صغيرة.

```bash
mkdir release-vX.Y.Z && cd release-vX.Y.Z
gh release download vX.Y.Z --repo ahmed-g-gad/apothem
cosign verify-blob \
  --bundle apothem-X.Y.Z-py3-none-any.whl.cosign.bundle \
  --certificate-identity https://github.com/Ahmed-G-Gad/apothem/.github/workflows/release.yml@refs/tags/vX.Y.Z \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  apothem-X.Y.Z-py3-none-any.whl
slsa-verifier verify-artifact \
  --provenance-path provenance.intoto.jsonl \
  --source-uri github.com/Ahmed-G-Gad/apothem \
  --source-tag vX.Y.Z \
  apothem-X.Y.Z-py3-none-any.whl apothem-X.Y.Z.tar.gz
bash ../scripts/release/verify-provenance.sh .
```

المتوقّع: <bdi>`Verified OK`</bdi>، و<bdi>`PASSED: SLSA verification passed`</bdi>،
و<bdi>`verify-provenance: chain OK (3 of 3 layers verified)`</bdi>. يفحص السكربت
<bdi>`SHA256SUMS`</bdi>، وكل حزمة توقيع، والمنشأ في تشغيل واحد؛ ويستنتج
الوسم من اسم الـ <bdi>wheel</bdi> (ويتجاوزه <bdi>`--tag vX.Y.Z`</bdi>).

يُنتِج اختبار الدخان صفًّا من سطر واحد <bdi>PASS / FAIL</bdi> لكل سطح؛ سجِّل الصفوف
في سجلّ إصدار المشرف.

## 6. الاسترداد من الفشل

لسير عمل الإصدار أنماط فشل موثّقة لمحرّك الإصدار ولناشر <bdi>npm</bdi>:

| الفشل | التشخيص | الاسترداد |
|---|---|---|
| رُفِض دفع الوسم (فشل التوقيع) | يُرجِع <bdi>`git push origin vX.Y.Z`</bdi> الخطأ <bdi>`error: failed to push some refs`</bdi> مع رسالة متعلّقة بـ <bdi>GPG</bdi> | تحقّق من أن مفتاح <bdi>GPG</bdi> الفرعي مُحمَّل (<bdi>`gpg --list-secret-keys --keyid-format=long`</bdi>)؛ أعِد وضع الوسم محليًا باستخدام <bdi>`-s`</bdi> بعد إصلاح حلقة المفاتيح؛ أعِد الدفع |
| يتوقّف بناء الإصدار عند <bdi>`Check the plugin version changed with the plugin`</bdi> | يُسمّي سجلّ مهمة البناء الإضافةَ والوسمَ السابق؛ لم يُبنَ أي أصل ولم يُنشَر | تغيّرت حزمة الإضافة منذ الإصدار السابق لكن نسختها لم تتغيّر. احذف الوسم (<bdi>`git push --delete origin vX.Y.Z`</bdi>، <bdi>`git tag -d vX.Y.Z`</bdi>)، وشغِّل <bdi>`python scripts/release/bump_version.py X.Y.Z`</bdi>، وأنشئ الكوميت، ثم وقِّع الوسم وادفعه مجددًا (القسم 2.2). يعمل الفحص نفسه على كل طلب سحب بوصفه تعليقًا تحذيريًا، لذا يظهر هذا عادةً قبل وضع الوسم |
| تفشل مهمة في <bdi>`release.yml`</bdi> في مرحلة واحدة | يُسمّي <bdi>`gh run view <run-id> --log`</bdi> المهمة الفاشلة (<bdi>build</bdi>، التي تكتب الـ <bdi>SBOM</bdi> أيضًا / <bdi>sign</bdi> / <bdi>provenance</bdi> / <bdi>archive</bdi> / <bdi>publish</bdi>) | أعِد تشغيل المهمة الفاشلة وحدها عبر <bdi>`gh run rerun <run-id> --failed`</bdi>؛ وإذا تكرّر الفشل، أصلِح مُدخَل المهمة عند مصدره قبل إعادة وضع الوسم |
| يفشل التحقّق من المنشأ <bdi>SLSA</bdi> | تخرج مهمة <bdi>`verify SLSA provenance artifact`</bdi> بقيمة غير صفرية | افحص مُنتَج المنشأ بحثًا عن عدم تطابق بصمة الموضوع؛ أعِد البناء من الوسم نفسه — يرتبط المنشأ ببصمات المُنتَجات الدقيقة، لذا تتطلّب أي إعادة توليد لمُنتَج إعادة تشغيل كاملة لسير العمل |
| رُفِض النشر على <bdi>npmjs.com</bdi> | تخرج مهمة <bdi>npm</bdi> بقيمة غير صفرية أثناء <bdi>`npm publish`</bdi>؛ والخطأ <bdi>`404`</bdi> من السجلّ أثناء <bdi>`PUT`</bdi> هو عدم تطابق في التفويض / الناشر الموثوق، لا دليل على أن شيفرة الحزمة مفقودة | تحقّق من أن <bdi>npm Trusted Publishing</bdi> للحزمة <bdi>`@ahmed-g-gad/apothem`</bdi> يُسمّي المالك <bdi>`ahmed-g-gad`</bdi>، والمستودع <bdi>`apothem`</bdi>، وسير العمل <bdi>`publish-npm.yml`</bdi>، والإجراء المسموح به <bdi>`npm publish`</bdi>؛ وتأكّد من أن المهمة تعمل بنسخة <bdi>Node</bdi> وبالحدّ الأدنى لدعم <bdi>OIDC</bdi> في <bdi>npm CLI</bdi>، المُثبَّتين في سير العمل |
| الوسم ظاهر لكن الأصول مفقودة | يُرجِع <bdi>`gh release view vX.Y.Z`</bdi> إصدارًا هيكليًا فارغًا | أعِد تشغيل مهمة النشر في سير عمل الإصدار؛ فهي تُعدِّل الإصدار الموجود وتُعيد رفع كل الأصول. لا تحذف الوسم وتُعِد وضعه إلا عندما لا يكون أي شيء من الوسم قد وصل إلى المستخدمين (لا أصول، ولا نسخة <bdi>npm</bdi>)؛ وإلا فأصلِح إلى الأمام بالإصدار التصحيحي التالي ([دليل تشغيل استرداد الإصدار](/docs/runbooks/release-recovery)، القسم 2) |

إذا أخفقت دورة استرداد في إيصال سطحٍ ما خلال تمريرة تشخيص واحدة، يُسجَّل السطح
بوصفه فشلًا معروفًا في ملاحظات الإصدار مع رابط إلى المسألة المفتوحة؛ ويُوجَّه
المستخدمون اللاحقون إلى الأسطح العاملة بينما يُصلَح السطح المعطوب في إصدار
تصحيحي.

## 7. الإحالات المرجعية

- **إعداد الناشر.** يُؤسِّس
  [دليل تشغيل إعداد حساب الناشر](/docs/runbooks/publisher-account-setup)
  ربط الناشر الموثوق في <bdi>npm</bdi> والمتطلّبات المسبقة على جانب
  <bdi>GitHub</bdi> التي يفترضها دليل التشغيل هذا.
- **مسار الاسترداد.** يتبع [دليل تشغيل استرداد الإصدار](/docs/runbooks/release-recovery)
  النموذج التراكمي نفسه: فهو يستردّ وسمًا أو مرحلة ناشر فاشلة مرحلةً بمرحلة، ويتراجع
  بإصدار الإصلاح بوصفه نسخة تصحيحية جديدة، لا بحذف وسم أو إصدار أو نسخة
  <bdi>npm</bdi> منشورة أو إعادة توجيهها أبدًا.
- **تفعيل <bdi>Pages</bdi>.** يتحقّق سير العمل <bdi>`publish-static-site.yml`</bdi>
  من موقع المشروع وينشره على النطاق المخصّص؛ ودليل تشغيل تفعيل <bdi>Pages</bdi>
  (<bdi>`site/content/docs/runbooks/pages-enablement.mdx`</bdi>) هو الإجراء السابق
  الذي أسّس النطاق المخصّص في المقام الأول.
- **سياسة ترقيم النسخ.**
  <bdi>`site/content/docs/governance/release-engineering-policy.mdx`</bdi> يحمل
  سياسة <bdi>SemVer</bdi> + التوقيع + الإهمال التي يلتزم بها دليل التشغيل هذا.
