> **المرجع المعياري لدمج طلبات السحب ذاتيًا في ظل ثابت حماية الفرع للمشروع.** عندما يكون المشرف هو المساهم الوحيد الذي يملك صلاحية الكتابة، تنشئ قواعد حماية الفرع في <bdi>GitHub</bdi> <bdi>`enforce_admins=true`</bdi> + <bdi>`required_approving_review_count=1`</bdi> تعطّلًا في الدمج الذاتي توثّق هذه الصفحة طريقة حلّه.

---

## 1. التعطّل

يحمل فرع <bdi>`main`</bdi> في المستودع مجموعة الحماية التالية:

- <bdi>`required_pull_request_reviews.required_approving_review_count: 1`</bdi>
- <bdi>`enforce_admins: true`</bdi>

هذه القواعد صحيحة لسيناريوهات تعدد المشرفين (كل تغيير يصل إلى <bdi>`main`</bdi> عبر طلب سحب مُراجَع من قِبل قرين؛ والمسؤولون غير معفيين). لكنها تنتج تعطّلًا للمشرفين المنفردين: تمنع سياسة <bdi>GitHub</bdi> الموافقة الذاتية على طلب سحب أنشأته بنفسك، ويمنع <bdi>`enforce_admins=true`</bdi> تجاوز <bdi>`gh pr merge --admin`</bdi> لمتطلب موافقة المراجعة.

توجد ثلاثة مسارات للحل:

| المسار | متى يُستخدَم |
|------|-------------|
| **مراسم التبديل المؤقت (المعيارية لهذا المستودع)** | الافتراضية للدمج الذاتي للمشرف المنفرد؛ تحافظ على ثابت الحماية خارج نافذة الدمج |
| توفير هوية روبوت تكامل مستمر بصلاحية كتابة | اعتمِدها فقط إذا كان انضمام عدة مشرفين وشيكًا؛ فموافقة الروبوت تقوّض نية المراجعة البشرية للحماية |
| تعيين <bdi>`required_approving_review_count: 0`</bdi> بشكل دائم | اعتمِدها فقط إذا كان المستودع سيبقى بمشرف منفرد إلى أجل غير مسمى؛ فهي تعكس نية المراجعة في الحماية |

يصادق هذا المستودع على **مراسم التبديل المؤقت** بوصفها المسار المعياري. أما الاثنان الآخران فهما مخرجا طوارئ موثَّقان، لا الخيار الافتراضي.

## 2. مراسم التبديل المؤقت

ثابت المراسم: حالة الحماية في بداية المراسم تساوي حالة الحماية في نهايتها. ولا يعيش التخفيف إلا داخل نافذة الدمج.

الصيغة اليدوية:

```bash
# 1. Open the PR, push branch, wait for CI green.
gh pr create --base main --head <feature-branch> --title "..." --body "..."
gh pr checks <pr-number>            # poll until all green

# 2. Relax approver-count to 0.
gh api repos/<owner>/<repo>/branches/main/protection/required_pull_request_reviews \
    -X PATCH -F required_approving_review_count=0

# 3. Squash-merge with admin override (admin override now succeeds because the
#    review-approval requirement is the only block enforce_admins refuses).
gh pr merge <pr-number> --squash --delete-branch --admin

# 4. Restore approver-count to 1.
gh api repos/<owner>/<repo>/branches/main/protection/required_pull_request_reviews \
    -X PATCH -F required_approving_review_count=1
```

الصيغة المُغلَّفة: انظر [`scripts/dev/admin_merge.py`](https://github.com/ahmed-g-gad/apothem/blob/main/scripts/dev/admin_merge.py) للحصول على غلاف <bdi>Python</bdi> الذرّي الذي ينفّذ الخطوات 2 ← 3 ← 4 في تسلسل واحد غير تفاعلي مع أمان التراجع عبر <bdi>`try`</bdi> / <bdi>`finally`</bdi> عند فشل الخطوة 3.

```bash
python scripts/dev/admin_merge.py <pr-number>
```

## 3. الثوابت

- **تقليص نافذة التبديل إلى أدنى حد.** تُنفَّذ الخطوات 2 ← 3 ← 4 في تسلسل واحد غير تفاعلي. تكون الحماية في حالتها المُخفَّفة طوال مدة استدعاء واجهة برمجة تطبيقات الدمج فقط — أقل من ثانية في كل تشغيل مُلاحَظ.
- **الاستعادة غير مشروطة.** تُنفَّذ الخطوة 4 حتى عند فشل الخطوة 3 (تضمن جملة <bdi>`try`</bdi> / <bdi>`finally`</bdi> في الغلاف الاستعادة في أي مسار خروج). ولا تترك محاولة دمج فاشلة الحماية مُخفَّفة.
- **بوابة التكامل المستمر محفوظة طوال الوقت.** لا يتأثر <bdi>`required_status_checks`</bdi> بالتبديل؛ ولا يزال الدمج يتطلب أن تكون سياقات فحص الحالة المُهيَّأة خضراء.
- **مسار التدقيق مرئي.** يظهر تعليق <bdi>`gh pr merge --admin`</bdi> في بيانات دمج طلب السحب الوصفية؛ وتظهر عمليات تبديل واجهة برمجة تطبيقات الحماية في سجل تدقيق المستودع تحت هوية المشرف.

## 4. متى لا تُستخدَم المراسم

المراسم مخصصة لـ**الدمج الذاتي** لطلبات سحب المشرف نفسه. وعندما يتوفر مراجع قرين (مساهم بصلاحية كتابة)، يكون المسار القياسي <bdi>`gh pr review --approve`</bdi> + <bdi>`gh pr merge --squash --delete-branch`</bdi> هو الصحيح وتغدو المراسم غير ضرورية.

إذا ضمّ المستودع مشرفًا ثانيًا، فأحِل المراسم على التقاعد: يستعيد سير مراجعة طلب السحب القياسي نية المراجعة البشرية للحماية دون أي تبديل.

## 5. تدقيق تشغيل سابق

كل استدعاء للمراسم يهبط على ثلاثة أسطح دائمة يمكن للمُشغِّل تفحّصها لاحقًا:

- **البيانات الوصفية لدمج طلب السحب.** يُرجِع <bdi>`gh pr view <pr-number> --json mergedBy,mergedAt,mergeCommit`</bdi> الفاعل المُنفِّذ للدمج، وطابع وقت الدمج، و<bdi>SHA</bdi> الخاص بكوميت الـ<bdi>squash</bdi>. ويطابق الفاعل <bdi>`mergedBy`</bdi> هوية المشرف الذي شغّل الخطوة 3.
- **سجل تدقيق المستودع.** يربط <bdi>`gh api /repos/<owner>/<repo>/actions/runs --jq '.workflow_runs[] | select(.event=="push")'`</bdi> تشغيل التكامل المستمر اللاحق للدمج بكوميت الدمج؛ ويُظهر سجل تدقيق قاعدة حماية المستودع (تاريخ <bdi>`gh api /repos/<owner>/<repo>/branches/main/protection`</bdi> عبر واجهة <bdi>Settings → Branches</bdi>) عمليتي تبديل الخطوة 2 والخطوة 4 المُحيطتين بنافذة الدمج.
- **تاريخ <bdi>git</bdi> للمشرف.** يسرد <bdi>`git log main --merges --first-parent`</bdi> كل كوميت دمج <bdi>squash</bdi> على <bdi>`main`</bdi> مع رقم طلب السحب المقابل في موضوع الكوميت (لاحقة <bdi>`(#<pr-number>)`</bdi> وفق افتراضي <bdi>`gh pr merge --squash`</bdi>)، مما يتيح للمُشغِّل تتبّع أي هبوط سابق رجوعًا إلى طلب السحب الخاص به واستدعاء المراسم.

عندما تكون <bdi>`scripts/dev/admin_merge.py`</bdi> هي نقطة الدخول، يُسمّي سجلّها غير التفاعلي (<bdi>stdout</bdi>) استدعاءات واجهة برمجة تطبيقات الحماية الثلاثة واستدعاء واجهة برمجة تطبيقات الدمج بالتسلسل؛ وتوجيه الغلاف عبر أنبوب إلى <bdi>`tee`</bdi> يلتقط جزءًا تدقيقيًا لكل تشغيل دون الاعتماد على احتفاظ <bdi>GitHub</bdi> بالسجل من جانبه.
