Las definiciones de los comandos de barra residen como archivos `.md` planos bajo `src/apothem/commands/`. El
conjunto canónico está encabezado por la canalización de la suite de planes consciente de la arquitectura, que se distribuye
como ocho comandos de etapa de primera clase, cada uno invocable directamente como `/plan-<stage>`,
más `/plan`, el orquestador que recorre la cadena de etapas de principio a fin. Cada etapa
es su propio archivo de comando registrado en `src/apothem/commands/plan-<stage>.md`, y
`/plan` no reimplementa ninguna de ellas.

| Invocación | Archivo de comando | Descripción |
|------------|--------------|-------------|
| `/plan` | `src/apothem/commands/plan.md` | Ejecuta las etapas spec, generate, review y design como un único flujo de trabajo verificado, con confirmación en cada traspaso; execute sigue siendo un paso manual |
| `/plan-spec` | `src/apothem/commands/plan-spec.md` | Refina contenido no estructurado en prosa de calidad de especificación |
| `/plan-generate` | `src/apothem/commands/plan-generate.md` | Materializa una suite de plan a partir de prosa / requisitos |
| `/plan-review` | `src/apothem/commands/plan-review.md` | Auditoría forense con tarjetas de puntuación |
| `/plan-design` | `src/apothem/commands/plan-design.md` | Emite `_inputs/design.md` para las suites que conllevan arquitectura |
| `/plan-execute` | `src/apothem/commands/plan-execute.md` | Ejecuta una fase con puertas de calidad |
| `/plan-status` | `src/apothem/commands/plan-status.md` | Informe de progreso de solo lectura |
| `/plan-amend` | `src/apothem/commands/plan-amend.md` | Enmienda, extiende, refina o revierte una suite existente sin perder las decisiones resueltas |
| `/plan-audit` | `src/apothem/commands/plan-audit.md` | Envoltura de bucle cerrado de spec → generate → review con remediación activa (ortogonal, previa a execute) |

Más allá de la canalización de planes, junto a ella se distribuyen comandos de
entorno que abarcan el proyecto completo — `/freshify`, `/github-deploy-fresh`,
`/github-deploy-next` y `/elevate` para la renovación y el lanzamiento; `/audit`,
`/fortress` y `/workflow` para la revisión y la orquestación multiagente;
`/projectify` para la elevación a un Project de una aplicación de chat —, además
de las once pasadas de auditoría/revisión (code-review, code-audit,
architecture-review, docs-review, security-audit, dependency-audit,
supply-chain-audit, threat-model-audit, perf-audit, a11y-audit, ux-review) y la
canalización `/research`:

## Contrato de frontmatter

Cada archivo de comando lleva el frontmatter canónico de ocho claves. El
contrato legible por máquina es [`command.schema.json`](https://github.com/ahmed-g-gad/apothem/blob/main/src/apothem/schemas/command.schema.json)
(`additionalProperties: false`); este bloque lo refleja:

```yaml
---
name: <slash-command name without leading slash>
version: <semver>
updated: <YYYY-MM-DD>
description: <one-line role>
argument-hint: <placeholder for the slash-command argument>
disable-model-invocation: <true | false>
portability: <portability classification, e.g. universal>
allowed-tools: <comma-separated read-only tools and scoped rules, e.g. "Read, Glob, Grep" or "Read, Bash(git log *)">
---
```

La comprobación `frontmatter-cohort` del validador (rama Command) verifica el
contrato en cada archivo de comando. `allowed-tools` lista las herramientas que
un entorno puede ejecutar sin preguntar mientras el comando está activo, por lo
que se mantiene de solo lectura por defecto: una herramienta con efectos
secundarios (Bash, PowerShell, Write, Edit, NotebookEdit, WebFetch) solo aparece
como una regla acotada, como `Bash(git log *)`, y el esquema rechaza el comodín
`"*"` sin acotar. Los comandos con efectos secundarios irreversibles o con un
momento elegido por el operador establecen `disable-model-invocation: true`, de
modo que solo el operador los inicia: `freshify`, `github-deploy-fresh`,
`github-deploy-next`, `release-readiness`, `elevate`, `fortress`, `workflow`,
`plan-execute`, `research-experiment` y `research-publish`. Los otros 35
comandos establecen `false` y se asocian a una solicitud por su descripción.

## Disciplina de autoría

- **Flujo de trabajo autocontenido.** El cuerpo de cada comando enumera el flujo
  de trabajo como pasos numerados para que el asistente pueda ejecutarlo desde
  un arranque en frío.
- **Bloque de Bindings.** Cada comando termina con el bloque canónico de Bindings
  de cinco direcciones.
- **Solo lenguaje del dominio.** Sin referencias internas del plan en los
  cuerpos.
