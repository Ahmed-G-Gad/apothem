Apothem distribuye una canalización `/plan` consciente de la arquitectura, una
canalización `/research` de trece etapas y una secuencia de auditoría de once
comandos, que dan a cada proyecto una ruta estructurada desde la prosa en bruto
hasta un código de nivel de producción revisado en múltiples ejes, y desde una
idea en bruto hasta un artículo difundido y revisado por pares.

## Visión general de la canalización

```mermaid
flowchart LR
    accTitle: Plan pipeline command flow
    accDescr: Left-to-right flowchart of the apothem plan pipeline from the spec stage through the generate and review stages, then through a conditional architecture-bearing decision that either runs the design stage or skips directly to the execute stage. The orthogonal audit stage wraps the spec-through-review span as a closed remediation loop, and the re-entrant amend stage revises an existing suite and returns it to review.
    A[/plan-spec] --> B[/plan-generate]
    B --> C[/plan-review]
    AUD[/plan-audit<br/>orthogonal: wraps spec → review] -.->|closed-loop remediation| A
    AM[/plan-amend<br/>re-entrant: revises an existing suite] -.->|re-review| C
    C --> Q{Architecture-bearing suite?}
    Q -->|yes| F[/plan-design<br/>emit _inputs/design.md]
    Q -->|no| D[/plan-execute]
    F --> D
    D --> E[/plan-status]
    D --> G[Audit review sequence]
    G --> H[Completion milestone]
```

## Las etapas de planificación

La canalización se distribuye como ocho comandos de barra de primera clase, uno
por etapa, cada uno invocable de forma independiente como `/plan-<stage>`. El
orquestador [/plan](/docs/pipeline/plan) las conduce desde una misión hasta una
suite ejecutada.

| Etapa | Función | Posición |
|-------|------|----------|
| [/plan-spec](/docs/pipeline/plan-spec) | Forja — de la prosa a la especificación | Inicio |
| [/plan-generate](/docs/pipeline/plan-generate) | Generador — de la especificación a la suite de plan | Intermedia |
| [/plan-review](/docs/pipeline/plan-review) | Auditor — auditoría forense del plan | Intermedia |
| [/plan-design](/docs/pipeline/plan-design) | Arquitecto — `_inputs/design.md` para las suites que afectan a la arquitectura | Puerta condicional |
| [/plan-execute](/docs/pipeline/plan-execute) | Ejecutor — ejecución de fases | Final |
| [/plan-status](/docs/pipeline/plan-status) | Informador — estado de solo lectura | Solo lectura |
| [/plan-audit](/docs/pipeline/plan-audit) | Guardián — envoltura de ciclo cerrado de spec → generate → review | Ortogonal (antes de execute) |
| [/plan-amend](/docs/pipeline/plan-amend) | Administrador — enmienda reentrante de una suite existente | Reentrante |

`/plan-audit` es ortogonal al flujo lineal, no una etapa dentro de él. Envuelve
`/plan-spec → /plan-generate → /plan-review` como un único ciclo cerrado,
ejecuta solo las etapas previas que faltan, remedia activamente los hallazgos y
deja la suite lista para `/plan-execute`. Es distinto de la secuencia de
revisión de auditoría que se describe más abajo, que audita una base de código
ejecutada en lugar de una suite de plan.

`/plan-design` no es una ceremonia universal. `/plan-review` clasifica si la
suite cambia superficies que afectan a la arquitectura. En caso afirmativo,
`/plan-design` emite la traza de diseño que consumen `/plan-execute` y
`/architecture-review`. En caso negativo, la suite revisada pasa directamente a
la ejecución.

## La canalización de investigación

La canalización de investigación se distribuye como trece comandos de barra de
primera clase, uno por etapa, cada uno invocable de forma independiente como
`/research-<stage>`, encadenados por una Puerta de secuencia y un Manifiesto de
traspaso, bajo diez mandatos de rigor (fuentes autorizadas, reproducibilidad,
falsabilidad, integridad de las citas, prerregistro, ética / conflictos, rigor
estadístico, ciencia abierta / FAIR, conformidad con las guías de publicación de
resultados, fundamentación teórica / impacto).

```mermaid
flowchart LR
    accTitle: Research pipeline command flow
    accDescr: Left-to-right flowchart of the apothem research pipeline from the ideate stage through spec, theory, sources, synthesis, proposal, study design, experiment, analysis, paper, and peer review to publish and disseminate, with a revision loop from review back to paper.
    RI[/research-ideate] --> RS[/research-spec]
    RS --> RT[/research-theory]
    RT --> RSO[/research-sources]
    RSO --> RSY[/research-synthesis]
    RSY --> RPR[/research-proposal]
    RPR --> RD[/research-design]
    RD --> RE[/research-experiment]
    RE --> RA[/research-analysis]
    RA --> RP[/research-paper]
    RP --> RR[/research-review]
    RR --> RPU[/research-publish]
    RPU --> RDI[/research-disseminate]
    RR -.->|revision loop| RP
```

| Etapa | Función | Posición |
|-------|------|----------|
| [/research-ideate](/docs/pipeline/research-ideate) | Formular el problema — preguntas candidatas a partir de una semilla de dominio | Inicio |
| [/research-spec](/docs/pipeline/research-spec) | Enmarcar la pregunta — hipótesis falsables + alcance | Intermedia |
| [/research-theory](/docs/pipeline/research-theory) | Marco conceptual + teoría del cambio | Intermedia |
| [/research-sources](/docs/pipeline/research-sources) | Recopilación sistemática de fuentes con un registro de búsqueda reejecutable | Intermedia |
| [/research-synthesis](/docs/pipeline/research-synthesis) | Mapa del estado del arte (SOTA) + análisis de lagunas | Intermedia |
| [/research-proposal](/docs/pipeline/research-proposal) | Objetivos + viabilidad + contingencias + impacto + plan de datos + plan de prerregistro; matriz de la convocatoria de financiación o respuesta de reenvío | Intermedia |
| [/research-design](/docs/pipeline/research-design) | Diseño del estudio + prerregistro | Intermedia |
| [/research-experiment](/docs/pipeline/research-experiment) | Ejecutar + registrar, de forma reproducible | Intermedia |
| [/research-analysis](/docs/pipeline/research-analysis) | Resultados + estadística | Intermedia |
| [/research-paper](/docs/pipeline/research-paper) | Borrador de artículo de primer nivel | Intermedia |
| [/research-review](/docs/pipeline/research-review) | Crítica con el nivel de una revisión por pares | Intermedia |
| [/research-publish](/docs/pipeline/research-publish) | Paquete para el medio de publicación + envío | Intermedia |
| [/research-disseminate](/docs/pipeline/research-disseminate) | Difusión + impacto + archivo FAIR | Final |

El orquestador de flujo de trabajo envuelto [/research](/docs/pipeline/research)
conduce estas etapas desde la pregunta en bruto hasta el artículo publicado (él
mismo no es una etapa), y comprueba de forma independiente la salida de cada
etapa antes de que la siguiente se construya sobre ella; `--quick` ejecuta solo
`/research-sources` + `/research-synthesis` para obtener un informe con citas en
una sola pasada.

Las etapas empíricas (fuentes, diseño, experimento, análisis) y las etapas de
redacción (artículo, revisión, publicación, difusión) se apoyan además en
superficies que llevan el rigor a la práctica — comparación justa entre varios
métodos, procedencia de los comparadores, un andamiaje de programa de
experimentos, un plan de uso de cómputo, un bucle de experimentación autónomo
opcional, una puerta de avance basada en la definición de terminado,
enmascaramiento con divulgación por etapas, un registro de búsqueda, la
asignación del estudio y la planificación de la potencia, la disciplina de
análisis, las contingencias del plan, la integridad de las figuras y la
planificación de charlas y pósteres — que agregan detalle operativo a los diez
mandatos sin ampliarlos.

## Secuencia de revisión de auditoría

El orquestador de flujo de trabajo envuelto [/audit](/docs/pipeline/audit) recorre las once dimensiones siguientes en una única pasada paralela — el equivalente de `/plan` y `/research` para la secuencia de auditoría — y sintetiza un único informe de hallazgos, deduplicado y clasificado por severidad (solo informa; la remediación se deriva a `/elevate`). Cada dimensión también se puede invocar por separado.

El orquestador de flujo de trabajo envuelto [/fortress](/docs/pipeline/fortress) cierra el ciclo que informa `/audit`: detecta mediante `/audit`, verifica cada hallazgo, remedia cada hallazgo que sobrevive en la superficie a la que pertenece, vuelve a auditar en un ciclo acotado y somete el resultado a la puerta [/release-readiness](/docs/pipeline/release-readiness) — el equivalente de `/plan` y `/research` para el endurecimiento de producción.

| Comando | Área de calidad |
|---------|--------------|
| [/code-review](/docs/pipeline/code-review) | Calidad del código |
| [/code-audit](/docs/pipeline/code-audit) | Corpus de código |
| [/security-audit](/docs/pipeline/security-audit) | OWASP / ASVS |
| [/perf-audit](/docs/pipeline/perf-audit) | Rendimiento |
| [/architecture-review](/docs/pipeline/architecture-review) | Arquitectura |
| [/ux-review](/docs/pipeline/ux-review) | Experiencia de desarrollo |
| [/a11y-audit](/docs/pipeline/a11y-audit) | Accesibilidad |
| [/docs-review](/docs/pipeline/docs-review) | Documentación |
| [/dependency-audit](/docs/pipeline/dependency-audit) | Dependencias |
| [/supply-chain-audit](/docs/pipeline/supply-chain-audit) | Cadena de suministro |
| [/threat-model-audit](/docs/pipeline/threat-model-audit) | Modelo de amenazas |
