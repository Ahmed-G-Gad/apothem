Este runbook lleva un lanzamiento `vX.Y.Z` de `apothem` desde un árbol de
trabajo limpio hasta superficies de distribución verificadas. El procedimiento
está escrito para el mantenedor que maneja `gh`, `git` y la shell de nivel de
lanzamiento; termina con una página de Release verificada, un CHANGELOG
archivado y una prueba de humo de las rutas de instalación que confirma que cada
superficie orientada al usuario responde al comando de instalación canónico.

El modelo de lanzamiento es **aditivo**. Cada lanzamiento agrega un commit en
`main` y una etiqueta `vX.Y.Z` anotada y firmada; no se hace force-push de nada y
no se elimina ninguna etiqueta, GitHub Release ni versión de npm anterior. El
proyecto tiene tres lanzamientos, cada uno con su etiqueta, su GitHub Release y
su versión de npm, y todos siguen publicados: las versiones de npm son
inmutables (un `name@version` publicado nunca puede reemplazarse), y las
instalaciones fijadas dependen de las etiquetas.

El push de la etiqueta inicia dos flujos de trabajo.
`.github/workflows/release.yml` compila, firma, atesta y publica el GitHub
Release con su conjunto completo de artefactos: sdist, wheel, SBOM de
CycloneDX, bundles cosign de Sigstore, procedencia SLSA-3 y los archivos
comprimidos del runtime por plataforma. `publish-npm.yml` publica
`@ahmed-g-gad/apothem` en npmjs.com mediante la publicación de confianza de npm.
La sección versionada del CHANGELOG llega en el commit de lanzamiento; el
operador ejecuta la prueba de humo de las rutas de instalación cuando ambos
flujos de trabajo terminan.

## 1. Requisitos previos

El mantenedor confirma lo siguiente antes de etiquetar:

- **Árbol de trabajo.** Limpio (`git status` no muestra nada pendiente). Todo
  el trabajo de funcionalidades del lanzamiento está en `main`.
- **CI en verde.** Para el último `main`, `gh run list --branch=main --limit=1
  --json conclusion --jq '.[0].conclusion'` devuelve `success`.
- **Herramientas.** `gh` (GitHub CLI) versión 2.40 o posterior, autenticado
  como `ahmed-g-gad`; `git` 2.40 o posterior con la subclave de firma GPG
  cargada; el vínculo de publicador de confianza de npm para
  `@ahmed-g-gad/apothem` está activo (verificado según el
  [runbook de configuración de la cuenta de publicador](/docs/runbooks/publisher-account-setup)).
- **Anclas de versión alineadas.** La cadena de versión declarada en
  `pyproject.toml` coincide con la etiqueta planificada sin el prefijo `v`
  (§2.1 la establece, junto con todas las demás anclas). Verifica:

  ```bash
  grep '^version' pyproject.toml
  ```

  Salida esperada (para un lanzamiento `vX.Y.Z`; los marcadores de posición representan la etiqueta del lanzamiento en curso):

  ```text
  version = "X.Y.Z"
  ```

- **Entradas del CHANGELOG preparadas.** Los puntos del lanzamiento están bajo
  `## [Unreleased]` en encabezados de Keep-a-Changelog; §2.1 los convierte en la
  sección de versión fechada en el commit que recibe la etiqueta.

## 2. Etiquetar y disparar

### 2.1 Redactar el commit de lanzamiento

La versión aparece en más de una docena de archivos, así que no los edites a
mano. Un solo comando los actualiza todos:

```bash
git checkout main
git pull --ff-only origin main
python scripts/release/bump_version.py X.Y.Z
```

`bump_version.py` actualiza todas las anclas de versión a la vez:

- Cada manifiesto de empaquetado, extensión, plugin y marketplace, además del
  archivo de cita (versión y fecha de lanzamiento). La lista completa:

  ```text
  pyproject.toml
  package.json
  site/package.json
  site/package-lock.json            (the project entries only)
  vscode-extension/package.json
  gemini-extension.json
  qwen-extension.json
  .claude-plugin/marketplace.json   (top level and metadata)
  plugins/apothem/.codex-plugin/plugin.json
  src/apothem/harnesses/antigravity/templates/plugin.json
  CITATION.cff
  ```

- `CHANGELOG.md`: las entradas de `[Unreleased]` se convierten en una sección
  `## [X.Y.Z]` fechada, `[Unreleased]` compara a partir de `vX.Y.Z` y se agrega
  un enlace `[X.Y.Z]`.
- `SECURITY.md`: una nueva versión menor recibe una fila `X.Y.x` admitida. Si
  las versiones menores anteriores siguen listadas es decisión tuya; el script
  imprime un recordatorio.

Después regenera los árboles derivados: el paquete del plugin de Claude Code,
los goldens de behavior-diff y las páginas de referencia y de changelog de la
documentación. Pasa `--dry-run` para listar primero los cambios, `--date
YYYY-MM-DD` para fijar la fecha de lanzamiento (predeterminada: hoy en UTC) o
`--no-regen` para omitir la regeneración. El script rechaza una versión mal
formada o un retroceso de versión, y volver a ejecutarlo con la versión actual
solo realinea las anclas desalineadas.

Revisa el diff y luego haz commit:

```bash
git add -A
git commit -S -m "chore(release): cut vX.Y.Z"
git push origin main
```

El indicador `-S` firma el commit con la clave GPG. El push dispara la matriz de
CI estándar (lint, test, build); espera a que esté en verde antes de etiquetar.

### 2.2 Firmar y hacer push de la etiqueta

```bash
git tag -a -s vX.Y.Z -m "vX.Y.Z"
git push origin vX.Y.Z
```

La combinación `-a -s` produce una etiqueta anotada y firmada con GPG. El push
dispara `.github/workflows/release.yml`, que compila, firma, atesta y publica.

### 2.3 Confirmar que el flujo de trabajo de lanzamiento se completó

```bash
gh run watch $(gh run list --workflow=release.yml --limit=1 --json databaseId --jq '.[0].databaseId')
```

El flujo de trabajo ejecuta la compilación (sdist + wheel, y luego un SBOM de
CycloneDX de esas distribuciones, escrito junto a ellas), la firma cosign sin
clave, la generación y verificación de la procedencia SLSA-3, la compilación de
los archivos comprimidos por plataforma (darwin / linux / windows), la firma de
esos archivos con un manifiesto `SHA256SUMS` agregado y la publicación final del
GitHub Release. El mantenedor revisa el registro del trabajo
`publish GitHub Release` en busca de las confirmaciones de subida de recursos.

### 2.4 Confirmar la publicación en npm

El push de la etiqueta también ejecuta `publish-npm.yml`. Aprueba el despliegue
del entorno `release` cuando se te solicite. El flujo de trabajo publica
`@ahmed-g-gad/apothem@X.Y.Z` en npmjs.com mediante la publicación de confianza
de npm (OIDC); no se almacena ningún token de registro en el repositorio.
Después confirma que todo está listo:

```bash
bash scripts/release/check-release-ready.sh vX.Y.Z
```

Para volver a publicar después de una ejecución fallida, despacha el flujo de
trabajo para la misma etiqueta
(`gh workflow run publish-npm.yml --field tag=vX.Y.Z`). El flujo de trabajo
omite la publicación cuando la versión ya está en el registro, porque las
versiones de npm son inmutables.

## 3. Superficies de distribución

Cada superficie tiene un comando de verificación que responde a «¿llegó el
lanzamiento aquí?»:

| # | Superficie | Artefacto | Verificación |
|---|---|---|---|
| 1 | GitHub Release (distribuciones de Python) | `apothem-X.Y.Z.tar.gz` (sdist) + `apothem-X.Y.Z-py3-none-any.whl` | `gh release view vX.Y.Z --json assets --jq '.assets[].name'` incluye ambos nombres de archivo |
| 2 | GitHub Release (SBOM) | `sbom.cdx.json` + `sbom.cdx.json.cosign.bundle` | la lista de recursos incluye ambos; el `metadata.component.purl` del SBOM es `pkg:pypi/apothem@X.Y.Z` y sus componentes incluyen cada paquete de `src/apothem/_vendor/vendor.txt` |
| 3 | GitHub Release (firmas) | un `<asset>.cosign.bundle` por cada sdist, wheel, SBOM, extensión de VS Code, archivo comprimido por plataforma y `SHA256SUMS` (en los lanzamientos anteriores, los bundles de los archivos comprimidos y de `SHA256SUMS` se llaman `<asset>.sig`) | `cosign verify-blob` con la identidad exacta de §5.5 termina con código 0 |
| 4 | GitHub Release (procedencia) | `provenance.intoto.jsonl` | `bash scripts/release/verify-provenance.sh <download-dir>` termina con código 0 (§5.5) |
| 5 | GitHub Release (archivos comprimidos por plataforma) | `apothem-vX.Y.Z-darwin.tar.gz`, `apothem-vX.Y.Z-linux.tar.gz`, `apothem-vX.Y.Z-windows.zip` | la lista de recursos incluye cada archivo comprimido más `SHA256SUMS`. Los archivos comprimidos de darwin y linux son los mismos bytes con dos nombres (el runtime es independiente de la plataforma; `--platform` solo elige entre tar.gz y zip), por lo que sus líneas de `SHA256SUMS` muestran un mismo digest dos veces |
| 6 | GitHub Release (extensión de VS Code) | `apothem.vsix` + `apothem.vsix.cosign.bundle` | la lista de recursos incluye ambos; `code --install-extension apothem.vsix` la instala. Los lanzamientos anteriores a que el flujo de trabajo de lanzamiento empaquetara la extensión no incluyen ninguno de los dos |
| 7 | npmjs.com | `@ahmed-g-gad/apothem@X.Y.Z` | `npm view @ahmed-g-gad/apothem version` devuelve `X.Y.Z`; `npx @ahmed-g-gad/apothem@X.Y.Z --version` imprime `Apothem, version X.Y.Z` |
| 8 | Pages (instaladores de script) | `install.sh` / `install.ps1` en el sitio de documentación | `curl -fsSL https://apothem.ahmedgad.com/install.sh \| head -n 1` devuelve el encabezado del script |

El GitHub Release es la superficie canónica de artefactos; el paquete de npm y
los instaladores de script son las rutas de instalación que se apoyan sobre él.
La publicación en npm se ejecuta junto al flujo de trabajo de lanzamiento, con
el mismo push de la etiqueta.

## 4. Disciplina del CHANGELOG

`CHANGELOG.md` lleva una sección por lanzamiento según la convención
Keep-a-Changelog. La edición del CHANGELOG en el commit de lanzamiento:

- Confirma que la sección de versión usa el encabezado `## [X.Y.Z] - YYYY-MM-DD`
  (con guion; `bump_version.py` lo escribe, y `extract_release_notes.py`
  reconoce el prefijo `## [X.Y.Z]`).
- Confirma que los encabezados estándar —Added, Changed, Deprecated, Removed,
  Fixed, Security— se usan donde corresponda. Los encabezados vacíos se eliminan
  del archivo renderizado.
- Recoge **capacidades**, no implementación. Solo lenguaje del dominio; sin
  referencias internas del plan; sin hashes de commit; sin identificadores de
  plan ni de fase.

Una sección del CHANGELOG que superó la revisión del mantenedor sirve como ancla
de las notas de lanzamiento para el relato del anuncio.

## 5. Prueba de humo de las rutas de instalación

Cuando ambas etapas se completan, el mantenedor ejecuta la prueba de humo. La
prueba de humo es la verificación canónica de que los comandos de instalación
orientados al usuario responden.

### 5.1 Plugin de Claude Code

```text
/plugin marketplace add ahmed-g-gad/apothem
/plugin install apothem@apothem
```

Esperado: el plugin se instala y los comandos `apothem` están disponibles dentro
de Claude Code.

### 5.2 Node.js (npx)

```bash
npx @ahmed-g-gad/apothem@X.Y.Z --version
```

Salida esperada: `Apothem, version X.Y.Z`.

### 5.3 Instalador de script de un solo paso (POSIX)

```bash
curl -fsSL https://apothem.ahmedgad.com/install.sh | sh
apothem --version
```

Salida esperada: `Apothem, version X.Y.Z`.

### 5.4 Instalador de script de un solo paso (Windows)

```powershell
irm https://apothem.ahmedgad.com/install.ps1 | iex
apothem --version
```

Salida esperada: `Apothem, version X.Y.Z`.

### 5.5 Verificación de artefactos (evidencia de la cadena de suministro)

Descarga todos los recursos en un directorio vacío y luego verifica. La
identidad del certificado es el flujo de trabajo de lanzamiento en esta etiqueta
exacta. Las comprobaciones de identidad distinguen entre mayúsculas y
minúsculas, y los certificados llevan el propietario tal como lo reporta GitHub,
`Ahmed-G-Gad`, por lo que un propietario en minúsculas falla.

```bash
mkdir release-vX.Y.Z && cd release-vX.Y.Z
gh release download vX.Y.Z --repo ahmed-g-gad/apothem
cosign verify-blob \
  --bundle apothem-X.Y.Z-py3-none-any.whl.cosign.bundle \
  --certificate-identity https://github.com/Ahmed-G-Gad/apothem/.github/workflows/release.yml@refs/tags/vX.Y.Z \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  apothem-X.Y.Z-py3-none-any.whl
slsa-verifier verify-artifact \
  --provenance-path provenance.intoto.jsonl \
  --source-uri github.com/Ahmed-G-Gad/apothem \
  --source-tag vX.Y.Z \
  apothem-X.Y.Z-py3-none-any.whl apothem-X.Y.Z.tar.gz
bash ../scripts/release/verify-provenance.sh .
```

Esperado: `Verified OK`, `PASSED: SLSA verification passed` y
`verify-provenance: chain OK (3 of 3 layers verified)`. El script comprueba
`SHA256SUMS`, cada bundle de firma y la procedencia en una sola ejecución; deriva
la etiqueta del nombre del wheel (`--tag vX.Y.Z` la reemplaza).

La prueba de humo produce una fila PASS / FAIL de una línea por superficie;
registra las filas en el registro de lanzamientos del mantenedor.

## 6. Recuperación ante fallos

El flujo de trabajo de lanzamiento tiene modos de fallo documentados para el
motor de lanzamiento y el publicador de npm:

| Fallo | Diagnóstico | Recuperación |
|---|---|---|
| Push de la etiqueta rechazado (fallo de firma) | `git push origin vX.Y.Z` devuelve `error: failed to push some refs` con un mensaje relacionado con GPG | Verifica que la subclave GPG esté cargada (`gpg --list-secret-keys --keyid-format=long`); vuelve a etiquetar localmente con `-s` después de corregir el llavero; vuelve a hacer push |
| La compilación del lanzamiento se detiene en `Check the plugin version changed with the plugin` | El registro del trabajo de compilación nombra el plugin y la etiqueta anterior; no se compiló ni se publicó ningún recurso | El paquete del plugin cambió desde el lanzamiento anterior, pero su versión no. Elimina la etiqueta (`git push --delete origin vX.Y.Z`, `git tag -d vX.Y.Z`), ejecuta `python scripts/release/bump_version.py X.Y.Z`, haz commit y luego vuelve a firmar y hacer push de la etiqueta (§2.2). La misma comprobación se ejecuta en cada pull request como anotación de advertencia, por lo que normalmente esto aparece antes de etiquetar |
| Un trabajo de `release.yml` falla en una sola etapa | `gh run view <run-id> --log` nombra el trabajo que falla (build, que también escribe el SBOM / sign / provenance / archive / publish) | Vuelve a ejecutar solo el trabajo fallido mediante `gh run rerun <run-id> --failed`; si el fallo se repite, corrige la entrada del trabajo en su origen antes de volver a etiquetar |
| La verificación de la procedencia SLSA falla | El trabajo `verify SLSA provenance artifact` termina con un código distinto de cero | Inspecciona el artefacto de procedencia en busca de un desajuste del digest del sujeto; recompila desde la misma etiqueta: la procedencia se vincula a los digests exactos de los artefactos, por lo que cualquier regeneración de artefactos requiere volver a ejecutar el flujo de trabajo completo |
| Publicación en npmjs.com rechazada | El trabajo de npm termina con un código distinto de cero durante `npm publish`; un `404` del registro durante `PUT` es un desajuste de autorización / publicador de confianza, no una prueba de que falte el código del paquete | Verifica que npm Trusted Publishing para `@ahmed-g-gad/apothem` nombre al propietario `ahmed-g-gad`, el repositorio `apothem`, el flujo de trabajo `publish-npm.yml` y la acción permitida `npm publish`; confirma que el trabajo se ejecuta con la versión de Node y la versión mínima de la CLI de npm para OIDC fijadas en el flujo de trabajo |
| Etiqueta visible, pero faltan recursos | `gh release view vX.Y.Z` devuelve un lanzamiento incompleto | Vuelve a ejecutar el trabajo de publicación del flujo de trabajo de lanzamiento; este edita el lanzamiento existente y vuelve a subir cada recurso. Elimina la etiqueta y vuelve a etiquetar solo cuando nada de la etiqueta llegó a los usuarios (sin recursos, sin versión de npm); en caso contrario, corrige hacia adelante con el siguiente lanzamiento de parche ([runbook de recuperación de lanzamientos](/docs/runbooks/release-recovery) §2) |

Si un ciclo de recuperación no logra completar una superficie en una sola pasada
de diagnóstico, la superficie se registra como fallo conocido en las notas de
lanzamiento, con un enlace al issue abierto; a los usuarios de aguas abajo se
les dirige a las superficies que funcionan mientras la defectuosa se corrige en
un lanzamiento de parche.

## 7. Referencias cruzadas

- **Configuración del publicador.** El
  [runbook de configuración de la cuenta de publicador](/docs/runbooks/publisher-account-setup)
  establece el vínculo de publicador de confianza de npm y los requisitos
  previos del lado de GitHub que este runbook da por supuestos.
- **Flujo de recuperación.** El [runbook de recuperación de lanzamientos](/docs/runbooks/release-recovery)
  sigue el mismo modelo aditivo: recupera una etiqueta o una etapa de publicador
  fallida, etapa por etapa, y revierte lanzando la corrección como una nueva
  versión de parche, nunca eliminando ni redirigiendo una etiqueta, un
  lanzamiento o una versión de npm publicados.
- **Habilitación de Pages.** El flujo de trabajo `publish-static-site.yml`
  valida y despliega el sitio web del proyecto en el dominio personalizado; el
  runbook de habilitación de Pages (`site/content/docs/runbooks/pages-enablement.mdx`)
  es el procedimiento previo que estableció el dominio personalizado en primer
  lugar.
- **Política de versionado.** `site/content/docs/governance/release-engineering-policy.mdx`
  contiene la política de SemVer + firma + obsolescencia que este runbook
  respeta.
