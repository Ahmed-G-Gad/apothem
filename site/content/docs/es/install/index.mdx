Apothem se instala en menos de dos minutos y funciona junto con la
configuración de entorno que ya tienes. Cada vía ejecuta el mismo motor
autónomo — el árbol de código fuente lleva sus dependencias incorporadas y se
ejecuta desde un checkout sobre el Python 3.10 o posterior del sistema
(consulta [el tiempo de ejecución autónomo](/docs/architecture/self-contained-runtime)).

**Todas las vías comparten dos requisitos previos:** **Python 3.10 o posterior**
del sistema en el `PATH`, con los paquetes `click` y `rich` importables bajo él.
El shim de npm (canal 2), la extensión de la familia VS Code (canal 4) y los
arranques de línea de comandos (canales 5–7) necesitan además **Node.js 18 o
posterior** para ejecutar `npx`. Python 3.10 y Node.js 18 y 20 ya superaron el
fin de vida en su proyecto de origen; siguen siendo admitidos y probados, pero
se prefieren versiones más recientes (consulta
[Requisitos previos de un vistazo](#requisitos-previos-de-un-vistazo)). La
sección propia de cada canal, más abajo, repite sus requisitos previos exactos,
un comando listo para copiar y un paso de verificación.

## Elige un canal

Hay ocho canales de instalación disponibles. Elige según cómo trabajas ya.

| # | Canal | Entrega | Requisitos previos |
|---|---------|----------|---------------|
| 1 | [Plugin de Claude Code](#1-plugin-de-claude-code) | Entorno completo en Claude Code | Claude Code · Python 3.10+ |
| 2 | [Shim de npm (`npx`)](#2-shim-de-npm-npx) | Entorno completo, cualquier herramienta | Node 18+ · Python 3.10+ |
| 3 | [Instaladores de un solo paso](#3-instaladores-de-un-solo-paso) | Entorno completo + un comando `apothem` | Python 3.10+ (`git` para una instalación por red) |
| 4 | [Extensión de la familia VS Code](#4-extensión-de-la-familia-vs-code) | Entorno completo desde el editor | VS Code · Node 18+ · Python 3.10+ |
| 5 | [Arranque de línea de comandos (host de extensión)](#5-arranque-de-línea-de-comandos-host-de-extensión) | Arranque que ejecuta el motor | Su herramienta anfitriona · Node 18+ · Python 3.10+ |
| 6 | [Arranque de línea de comandos (host `qwen-code`)](#6-arranque-de-línea-de-comandos-host-qwen-code) | Arranque que ejecuta el motor | Su herramienta anfitriona · Node 18+ · Python 3.10+ |
| 7 | [Arranque de línea de comandos (host de plugin)](#7-arranque-de-línea-de-comandos-host-de-plugin) | Arranque que ejecuta el motor | Su herramienta anfitriona · Node 18+ · Python 3.10+ |
| 8 | [Motor directo (`python -m apothem`)](#8-motor-directo-python--m-apothem) | Entorno completo desde un checkout | Python 3.10+ (`click`, `rich`) |

<Callout title="Qué canales entregan el entorno completo">
  El shim de npm (2), los instaladores de un solo paso (3) y el motor directo (8)
  materializan por sí solos toda la unidad sincronizada para cualquier entorno.
  Las tres extensiones de línea de comandos (5–7) instalan un pequeño
  **arranque** que delega en el motor (`npx @ahmed-g-gad/apothem install`) para
  materializar el entorno completo — son el punto de entrada, no la entrega
  completa por sí mismas. El plugin de Claude Code (1) lleva el motor y lo
  ejecuta directamente. La extensión de la familia VS Code (4) no lleva un motor
  propio: sus comandos ejecutan el motor a través del shim de npm de forma
  predeterminada.
</Callout>

Cada vía es idempotente: volver a ejecutarla es seguro y converge al mismo estado.

## 1. Plugin de Claude Code

**Requisitos previos:** Claude Code y el Python 3.10+ del sistema en el `PATH`.

La vía del plugin se ejecuta por completo dentro de Claude Code. Empaqueta el
motor de Apothem con sus comandos de barra, trabajadores delegados, skills,
reglas y hooks, todos ejecutables desde el árbol autónomo del plugin:

```text title="Inside Claude Code"
/plugin marketplace add ahmed-g-gad/apothem
/plugin install apothem@apothem
```

Tras la instalación, el conjunto de comandos de Apothem, los trabajadores
delegados incluidos, las skills y los cuatro
[output-styles](/docs/reference/output-styles) (elige uno con
`/output-style` o desde `/config`) están disponibles en cada sesión de Claude
Code. El plugin distribuye cada comando como una skill, un `SKILL.md` con el
detalle que carga bajo demanda en una carpeta `references/` junto a él, así que
Claude Code lo invoca con el prefijo del plugin: `/apothem:plan-spec`,
`/apothem:security-audit` y el resto. Dos nombres los ocupa el propio Claude
Code: `/plan` entra en el modo de plan y `/code-review` ejecuta la revisión
integrada, así que escribe `/apothem:plan` y `/apothem:code-review` para los
comandos de Apothem. Cuando el motor de Apothem se instala en Claude Code en
lugar del plugin, las mismas skills se escriben en `~/.claude/skills/` sin
prefijo, y una skill personal `code-review` reemplaza el `/code-review`
integrado (su alias `/review` sigue ejecutando el integrado). Dos nombres,
`projectify` y `workflow`, son también skills nativas; la skill nativa es la
que distribuyen el plugin y la instalación del motor, no una skill derivada del
comando. Consulta
[Claude Code](/docs/harnesses/claude-code#command-skills-and-reference-files)
para ver cómo se dividen los comandos, y [Comandos de barra](/docs/reference/commands)
para ver el catálogo completo de comandos.

**Verifica:** ejecuta `/plugin` dentro de Claude Code y confirma que **apothem**
aparece como instalado, o comprueba el informe de deriva desde una terminal:

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 2. Shim de npm (`npx`)

**Requisitos previos:** Node.js 18+ (para `npx`) y el Python 3.10+ del sistema en
el `PATH`. El shim localiza el intérprete y reenvía cada comando de la CLI al
motor incluido — no se coloca nada de forma permanente en tu sistema. Prueba
`python3`, `python` y después `py -3`, en ese orden; define **`APOTHEM_PYTHON`**
con la ruta de un intérprete para probarlo primero, que es lo que necesitas
cuando Python está instalado pero no está en el `PATH`, o cuando hay varias
versiones instaladas y quieres una concreta. El intérprete que indiques sigue
teniendo que superar la comprobación de Python 3.10+; cuando no la supera, el
shim recurre a `python3`, `python` y después `py -3`.

```bash title="npx"
npx @ahmed-g-gad/apothem install --harness claude-code
```

En una máquina sin perfil, este primer `install` crea el perfil inicial en
`~/.config/apothem/profile.yaml` y lo indica. Sus campos de identidad son
marcadores de posición: personalízalos (`npx @ahmed-g-gad/apothem profile edit`)
y luego vuelve a ejecutar el comando con `update` en lugar de `install` para
aplicarlos.

También se ejecuta directamente desde el repositorio:

```bash title="npx from the repository"
npx github:ahmed-g-gad/apothem install --harness claude-code
```

Cada comando de la [referencia de la CLI](/docs/cli-reference) funciona en esta
forma; escribe `npx @ahmed-g-gad/apothem` en lugar de `apothem`. Esta es también
la vía de instalación para OpenCode y cualquier otra herramienta que no exponga
un registro de plugins o extensiones propio — Apothem las sincroniza
directamente en su directorio de configuración nativo
(`npx @ahmed-g-gad/apothem install --harness opencode`).

**Verifica:**

```bash title="Verify"
npx @ahmed-g-gad/apothem --version
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 3. Instaladores de un solo paso

**Requisitos previos:** el Python 3.10+ del sistema en el `PATH` (el instalador se ofrece a añadir por ti los requisitos previos `click` / `rich`). Para una instalación por red: `git`, para encontrar el lanzamiento más reciente, y `gpg`, para comprobar la etiqueta de lanzamiento firmada (Git for Windows incluye ambos). [cosign](https://docs.sigstore.dev/cosign/system_config/installation/) es opcional: con él, el instalador también comprueba el archivo comprimido de lanzamiento firmado.

Los scripts del instalador resuelven el lanzamiento más reciente, lo comprueban
(consulta [Modelo de confianza](#modelo-de-confianza)), colocan el árbol de
código fuente de Apothem en `~/.apothem`, crean un perfil inicial cuando no
existe ninguno, materializan tu primer entorno y verifican el resultado, todo en
una sola ejecución. El perfil inicial lleva campos de identidad que son
marcadores de posición: edítalo y luego ejecuta `apothem update --harness <name>`
para aplicar los tuyos. Volver a ejecutarlos es idempotente: en un clon de git
se hace fetch, se comprueba su nueva etiqueta y solo entonces se hace checkout
del clon en la etiqueta resuelta; una instalación desde un archivo comprimido de
lanzamiento se actualiza en el sitio; y el entorno se vuelve a materializar.
Cuando el motor termina como parcial (código de salida `2`), el instalador
imprime una línea de advertencia, verifica igualmente, coloca el comando
`apothem` e imprime su banner, y después termina con el código de salida `2`. El
motor termina como parcial cuando deja un archivo como está a causa de sus
líneas de marcador de Apothem, o cuando se detiene después de haber escrito algo
(consulta
[Cuando el motor deja un archivo como está](/docs/install/updating#when-the-engine-leaves-a-file-as-it-is)).
La instalación verificada es la vía predeterminada y recomendada.

Importa primero la clave de firma del mantenedor, una sola vez. Cada instalación por red comprueba la etiqueta de lanzamiento con ella, con o sin cosign, y se detiene si la clave no está en tu llavero. Comprueba que la huella digital es `5C89 98F9 F241 7204 45D3  F28B 7039 6FED 9C63 4163`, el valor publicado en [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md#maintainer-signing-key). En Windows, `git verify-tag` lee el llavero del `gpg` que incluye Git for Windows, así que la importación se ejecuta mediante el propio `bash` de Git:

```bash title="macOS · Linux · WSL2 · BSD — import the key once"
curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import
gpg --fingerprint 70396FED9C634163
```

```powershell title="Windows · PowerShell — import the key once"
& "$env:ProgramFiles\Git\bin\bash.exe" -c 'curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import && gpg --fingerprint 70396FED9C634163'
```

```bash title="macOS · Linux · WSL2 · BSD — latest signed tag, verified"
curl -fsSL https://apothem.ahmedgad.com/install.sh | bash
```

```powershell title="Windows · PowerShell — latest signed tag, verified"
irm https://apothem.ahmedgad.com/install.ps1 | iex
```

Los mismos scripts se distribuyen en un checkout bajo `scripts/installer/` —
`install`, `uninstall` y `update` en las formas `.sh`, `.ps1` y `.bat` —, de
modo que puedes ejecutarlos directamente tras clonar:

```bash title="From a checkout"
APOTHEM_HARNESS=claude-code sh scripts/installer/install.sh                                 # POSIX
$env:APOTHEM_HARNESS = 'claude-code'; pwsh -NoProfile -File scripts/installer/install.ps1   # Windows
```

Un comando de una línea canalizado nunca usa un árbol local: `curl ... | sh` e
`irm ... | iex` ignoran la carpeta desde la que los ejecutas y sus carpetas
superiores, y descargan y verifican el lanzamiento. El instalador usa un árbol
local solo cuando ejecutas por su ruta el propio
`scripts/installer/install.sh` (o `install.ps1`) del checkout, desde cualquier
carpeta (por ejemplo `sh ~/src/apothem/scripts/installer/install.sh`), o cuando
`APOTHEM_SOURCE` nombra ese árbol. Los instaladores, los actualizadores y los
desinstaladores, los shims de `apothem`, el lanzador de npm, los hooks y los
procesos validadores de la puerta de conformidad mantienen la carpeta actual
fuera de la ruta de búsqueda de módulos de Python. Un comando
`python -m apothem` que escribas tú mismo no lo hace: `-m` lee primero los
módulos de la carpeta actual.

Ningún lanzador (los instaladores, los actualizadores, los desinstaladores, los
shims de `apothem` de POSIX y de Windows, y el lanzador de npm) pasa al motor las
entradas vacías y relativas de tu propio `PYTHONPATH`. Una entrada que se
conserva debe ser una ruta completa: en Windows, una ruta de unidad como
`C:\lib` o una ruta de red; en los demás sistemas, una ruta que empiece por `/`.
Se descartan una ruta con raíz `\lib` y una ruta relativa a la unidad `C:lib`.
Los scripts sh preguntan al Python que ejecutan qué forma lee, y el shim de
`apothem` que escriben conserva esa forma. Un Python de Windows (el habitual en
Git Bash) recibe las rutas del motor en forma de Windows, unidas con `;`, y
conserva solo las rutas de unidad y de red de tu `PYTHONPATH`. Un Python POSIX,
incluido el `python3` propio de Cygwin y de MSYS2, recibe rutas POSIX unidas con
`:` y conserva solo las entradas que empiezan por `/`. Los comandos `git` de los
instaladores que no trabajan sobre un clon no leen un repositorio de la carpeta
actual.

### Opciones del instalador

`install.sh` acepta las opciones siguientes, e `install.ps1` acepta los mismos
interruptores como parámetros de PowerShell. `install.bat` acepta la forma de
`install.sh` de las tres primeras filas y pasa cada una a `install.ps1`. Un comando
de una línea canalizado no puede pasar un parámetro de PowerShell, así que descarga
primero `install.ps1` para usar uno:

```bash title="Pass a flag"
curl -fsSL https://apothem.ahmedgad.com/install.sh | sh -s -- --dry-run    # POSIX
irm https://apothem.ahmedgad.com/install.ps1 -OutFile install.ps1; pwsh -NoProfile -File install.ps1 -DryRun   # Windows
```

| `install.sh` | `install.ps1` | Efecto |
|---|---|---|
| `--clean`, `--fresh` | `-Clean`, `-Fresh` | Antes de instalar, respalda y elimina las cuatro carpetas de tu directorio personal que lista [`apothem install`](/docs/cli-reference/install#blast-radius-preview), entre ellas `~/.claude` y `~/.agents`, sea cual sea el entorno que instales, y luego instala desde cero. El instalador lo pasa al motor como `apothem install --clean`, que pregunta antes de cada eliminación, guarda la copia de seguridad en `~/.apothem/backups` y vuelve a escribir tu perfil. |
| `--dry-run` | `-DryRun` | Descarga y comprueba la versión en una carpeta temporal y muestra lo que cambiaría la instalación, sin cambiar nada (consulta [Modelo de confianza](#modelo-de-confianza)). |
| `--yes` | `-Yes` | No pregunta antes de cada eliminación de `--clean`. También permite los reemplazos de lo que hay en `APOTHEM_HOME` que el [Modelo de confianza](#modelo-de-confianza) indica que necesitan `--yes`. |
| `-h`, `--help` | ninguno | Muestra las opciones y el modelo de confianza, y termina. |

### Modelo de confianza

Sin `APOTHEM_REF` definido, el instalador resuelve el lanzamiento
`vMAJOR.MINOR.PATCH` más alto e instala *ese* — nunca la rama `main` en
movimiento. Comprueba el lanzamiento antes de materializar cualquier
configuración, y la comprobación depende de si `cosign` está en tu `PATH`:

- **Con cosign**, deben pasar dos comprobaciones. Primero, la etiqueta de
  lanzamiento debe llevar una firma válida de la clave del mantenedor,
  comprobada como en el punto siguiente, y la etiqueta firmada debe ser la que
  lleva el nombre de ese lanzamiento: se rechaza una etiqueta firmada de otro
  lanzamiento redirigida a este nombre. Después, el instalador descarga el
  archivo comprimido de la plataforma del lanzamiento, su archivo `SHA256SUMS`
  y `SHA256SUMS.cosign.bundle`. cosign debe confirmar que el flujo de trabajo de
  lanzamiento de Apothem firmó `SHA256SUMS` para esa etiqueta exacta y, mediante
  su comprobación `--certificate-github-workflow-sha`, que el certificado que
  verificó se emitió para una ejecución sobre el commit al que apunta la
  etiqueta firmada. El instalador no lee el certificado por sí mismo. Después,
  el SHA-256 del archivo comprimido debe coincidir con el digest de la lista. El
  flujo de trabajo se ejecuta para cualquier etiqueta que se envíe, así que su
  firma por sí sola no basta; la firma de la etiqueta muestra que el mantenedor
  publicó ese commit.
- **Sin cosign**, o cuando `APOTHEM_HOME` ya contiene un clon de git, el
  instalador clona o actualiza el repositorio y comprueba solo la etiqueta con
  `git verify-tag`. La firma debe ser válida *y* estar hecha con la
  clave del mantenedor publicada en [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md), y la etiqueta firmada debe ser la que lleva el nombre del
  lanzamiento. Se rechaza una etiqueta firmada por cualquier otra clave, aunque
  tu llavero confíe en esa clave. Una etiqueta de git firmada nombra su commit
  mediante un ID SHA-1; con cosign, el instalador también comprueba el SHA-256
  del archivo comprimido. En un clon existente se hace fetch y su nueva etiqueta
  se comprueba *antes* de hacer checkout del clon. Una comprobación fallida deja
  el clon como estaba, y un clon con cambios en archivos rastreados detiene la
  actualización con un mensaje para hacer commit de ellos o guardarlos con
  stash, en lugar de perderlos. Con una ref que no es de lanzamiento, como
  `main`, un clon existente sigue la copia de esa rama en origin.

El instalador ignora las variables de entorno de git que redirigen git
(`GIT_DIR`, `GIT_WORK_TREE` y similares) y las que dirigen git a otro archivo
de configuración (`GIT_CONFIG`, `GIT_CONFIG_GLOBAL` y `GIT_CONFIG_SYSTEM`) o le
hacen leer atributos de otro árbol (`GIT_ATTR_SOURCE`; un `attr.tree` de tu
propia configuración se vacía en cada comando git que se ejecuta sobre un
clon), y se detiene cuando `APOTHEM_REPO` empieza por `-`.
`GIT_CONFIG_NOSYSTEM` se queda como lo definiste; solo impide que git lea la
configuración del sistema. git sigue leyendo tu propia configuración global y,
a menos que definas `GIT_CONFIG_NOSYSTEM`, la configuración del sistema desde
los lugares donde siempre busca, y `git`, `gpg` y `cosign` son los programas que
encuentra tu `PATH`: el instalador confía en ellos tal como se encuentran.
Durante toda la ejecución, el instalador establece `GIT_NO_REPLACE_OBJECTS=1`,
para que git nunca sustituya un objeto mediante refs de reemplazo,
`GIT_NO_LAZY_FETCH=1`, para que git nunca descargue por su cuenta un objeto que
falta desde el remoto, `GIT_ALLOW_PROTOCOL` con los transportes file, git, http,
https y ssh, para que un valor de tu entorno no pueda ampliar esa lista, y
`GIT_ATTR_NOSYSTEM=1`; con `core.attributesFile` vaciado en cada comando git que
se ejecuta sobre un clon, git no lee entonces ningún archivo de atributos fuera
del clon, así que una macro definida en el tuyo no puede nombrar un filtro ahí.
El script de PowerShell restaura las cuatro cuando termina la ejecución. El
instalador lee la etiqueta de lanzamiento una vez, registra el commit que
nombra, verifica la etiqueta, hace checkout de ese commit por su ID y exige que
`HEAD` sea ese commit, así que una etiqueta movida después de la comprobación no
cambia nada. En Windows PowerShell 5.1 y 7, se rechaza una descarga que redirige
a una dirección que no es https, igual que hace el `curl` de los instaladores
POSIX.

`APOTHEM_HOME` debe ser una carpeta en la que solo tú puedas escribir, ya que
quien pueda escribir en ella puede cambiar el código que ejecuta el comando
`apothem`. En Windows, una carpeta creada en la raíz de una unidad, como
`C:\apothem`, la puede cambiar cualquier usuario que inicie sesión en el equipo,
con los permisos predeterminados de Windows. El valor predeterminado,
`~/.apothem`, está en tu propia carpeta de usuario. Cada instalación descargada,
actualización y ejecución de prueba advierte, sin detenerse, cuando no es así, o
cuando la carpeta o la que la contiene pertenece a otra persona, nombrando la
carpeta, quién puede escribir en ella o es su propietario, y la corrección; una
instalación desde un checkout local y una actualización con `APOTHEM_SOURCE`
definido omiten la comprobación. En Windows, la advertencia procede de
`install.ps1` y `update.ps1`: `install.sh` y `update.sh` no comprueban en Git
Bash, MSYS2 ni Cygwin (consulta
[Solución de problemas](/docs/install/troubleshooting#the-installer-warns-other-users-can-change-apothem_home)).

Una comprobación fallida aborta la instalación antes de escribir ninguna
configuración y antes de que el instalador reemplace `APOTHEM_HOME`. Una
etiqueta firmada cuya clave pública del mantenedor todavía no está en el llavero
local aborta, en cambio, con indicaciones para importar la clave: importa la clave tal como se muestra arriba, comprueba su huella digital con el valor publicado en [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md), y vuelve a ejecutar.

Volver a ejecutar con cosign actualiza una instalación anterior desde un archivo
comprimido de lanzamiento. El nuevo código fuente se comprueba y se descomprime
primero en una carpeta junto a `~/.apothem` y después se intercambia. Todo lo de
`~/.apothem` que no forma parte del árbol de código fuente se traslada a la nueva
instalación: las copias de seguridad de reversión del motor (`backups/`), los
registros de instalación (`state/`), los planes, la memoria y sus demás datos.
Si un paso falla o detienes la ejecución con Ctrl+C o una señal de terminación,
la instalación anterior se restaura sin cambios; si incluso eso falla, el
mensaje indica dónde están los archivos anteriores. Una terminación forzada o un
corte de energía durante el intercambio no se pueden interceptar: pueden dejar
carpetas junto a `~/.apothem`, y la siguiente instalación descargada las notifica
(consulta más abajo). Estas reglas se aplican cuando el instalador reemplaza
`~/.apothem`:

- Un clon de git no se reemplaza por un archivo comprimido de lanzamiento sin
  `--yes`. Los archivos que el clon no rastrea pasan a la nueva instalación, y el
  árbol propio del clon (su historial y su código fuente) se mueve a una carpeta
  nueva, `~/.apothem.before-apothem-<time>`, con su propio nombre (`.apothem`);
  el instalador indica dónde, y tú la eliminas cuando ya no la necesites. Incluso
  con `--yes`, el instalador se niega mientras el clon contenga trabajo local que
  perdería: cambios, stashes, commits sin enviar o archivos no rastreados en su
  árbol de código fuente. Haz commit y push de ese trabajo, o muévelo a otro
  lugar, y vuelve a ejecutar. Esta comprobación también se ejecuta con
  `--dry-run`. Un archivo `.git` (un worktree vinculado) cuenta como clon, y
  también una carpeta `.git`.
- Un clon de git de cualquier cosa que no sea Apothem se trata como cualquier
  carpeta que no contiene ninguna instalación de Apothem (consulta más abajo);
  nunca se actualiza ni se reemplaza como clon.
- Un clon existente se actualiza en el sitio solo cuando git puede ver cada
  cambio que contiene y nada de su propia configuración ejecuta código durante
  la actualización. Antes del fetch, el instalador se detiene cuando hay
  archivos marcados como assume-unchanged o skip-worktree, cuando git no
  encuentra un árbol de trabajo en `APOTHEM_HOME` (como cuando la configuración
  del clon establece `core.bare` en `true`), cuando el clon contiene un
  submódulo (registrado en su índice o guardado en `.git/modules`), cuando
  `.git/info/attributes` nombra un filtro o un controlador de diff (`filter=` o
  `diff=`), cuando ese archivo o un archivo de configuración no es un archivo
  normal, o cuando el clon toma prestados objetos de otro repositorio
  (`objects/info/alternates`). También se detiene ante cualquier ajuste del
  `.git/config` o del `.git/config.worktree` propios del clon distinto de los
  que `git clone` y `git init` escriben ahí para un clon completo, los ajustes
  de rama (el `remote` y el `pushremote` de una rama deben ser `origin`),
  `user.name`, `user.email`, `maintenance.auto`, `maintenance.strategy`,
  `pull.rebase` y `pull.ff`, así que un clon parcial hecho con `--filter`
  también se detiene;
  [Solución de problemas](/docs/install/troubleshooting#the-installer-stops-the-existing-clone-is-set-up-in-a-way-the-update-would-trust)
  los enumera. El mensaje nombra el ajuste y el archivo en el que está. Las
  comprobaciones de ajustes, atributos y objetos se ejecutan antes de cualquier
  comando git que lea el índice o los objetos del clon, y también, junto con la
  comprobación de submódulos, cuando `--yes` está a punto de reemplazar el clon.
  Antes de cualquier comando git que aplique los archivos `.gitattributes` del
  árbol de trabajo, el instalador se detiene ante uno que git no rastrea, que
  difiere de la copia confirmada, o cuya copia confirmada git no puede leer o
  nombra un filtro o un controlador de diff (también se lee la copia del árbol
  de trabajo), y ante un repositorio git dentro del clon que git no rastrea,
  cuyos archivos `.gitattributes` git también leería. Las carpetas de datos
  propias del motor, como `backups`, donde ningún lanzamiento escribe, no se
  leen para esto. Antes del fetch se detiene ante archivos bajo `src` (escrito
  con cualquier combinación de mayúsculas y minúsculas) que git no rastrea, ya
  que el motor podría cargarlos. Después del checkout, elimina las carpetas de
  caché de Python (`__pycache__`) bajo `src` antes de que el motor se ejecute
  desde el clon. Los hooks de git del clon nunca se ejecutan durante la
  actualización, y cada comando git sobre el clon se ejecuta sin paginador, sin
  mantenimiento automático, con su monitor del sistema de archivos desactivado,
  permitiendo solo los transportes file, git, http, https y ssh (así que una
  dirección en la configuración del clon no puede hacer que git ejecute un
  programa auxiliar como `ext::`) y sin recursión en submódulos; `git diff` y
  `git status` omiten los submódulos. Un clon que pertenece a otro usuario
  detiene la ejecución con una explicación (consulta Solución de problemas).
- Una carpeta que contiene solo los datos propios del motor (`backups`, `state`,
  `plans`, `memory`, `contexts`, `learning`, `providers`) se actualiza sin
  `--yes`, y esos datos se conservan.
- Una carpeta que no contiene ninguna instalación de Apothem no se toca sin
  `--yes`. Con `--yes`, el instalador mueve la carpeta entera, sin cambios, a una
  carpeta nueva, `~/.apothem.before-apothem-<time>` (dentro conserva su propio
  nombre), indica dónde e instala desde cero.
- Un enlace simbólico en `APOTHEM_HOME` (en Windows, un enlace simbólico o una
  unión) se rechaza, porque reemplazarlo reemplazaría el enlace y no la carpeta a
  la que lleva. Apunta `APOTHEM_HOME` a esa carpeta y vuelve a ejecutar. La
  excepción es un clon de git existente, que se actualiza en el sitio.
- En Linux y macOS, un archivo o una carpeta que haya que trasladar cuyo nombre
  tenga un espacio u otro carácter especial detiene la instalación. Sácalo primero
  de `APOTHEM_HOME`.

**Una ejecución a la vez, y ejecuciones que se detuvieron.** Cada ejecución de
los scripts de instalación, actualización y desinstalación toma un bloqueo junto
a `APOTHEM_HOME`, `~/.apothem.lock` de forma predeterminada, durante toda la
ejecución, y lo libera cuando la ejecución termina con éxito, con fallo, con
Ctrl+C o con una señal de terminación. Los comandos `apothem` en sí no lo toman.
Una segunda ejecución se detiene con "Another Apothem install, update or
uninstall is running". En POSIX, el bloqueo es una carpeta que contiene el ID de
proceso de la ejecución. Un bloqueo que deja una ejecución terminada a la fuerza
se notifica con instrucciones para eliminarlo y nunca se toma, y un bloqueo
creado en otro entorno (WSL y Git Bash en una misma máquina, por ejemplo) se
notifica como uno cuyo proceso no se puede comprobar desde ahí. En Windows
PowerShell, el bloqueo es un archivo que Windows cierra y elimina cuando termina
el proceso. Cuando `APOTHEM_HOME` es un enlace, cada script toma el bloqueo junto
a la carpeta a la que lleva. Una ejecución de prueba también toma el bloqueo, a
menos que la carpeta que contiene `APOTHEM_HOME` todavía no exista. Así que cada
ejecución, incluidas una actualización en el sitio, una desinstalación y una
ejecución de prueba, necesita acceso de escritura a la carpeta que contiene
`APOTHEM_HOME`; sin él, la ejecución se detiene antes de cambiar nada.

Una terminación forzada o un corte de energía durante un intercambio pueden
dejar la instalación anterior u otras entradas de `APOTHEM_HOME` en
`.apothem-old.<name>.*`, `.apothem-extract.<name>.*` o
`.apothem-clone.<name>.*` junto a ella, donde `<name>` es la última parte de
`APOTHEM_HOME`, o en una carpeta `APOTHEM_HOME.before-apothem-<time>`. La
siguiente instalación descargada para ese `APOTHEM_HOME`, incluida una ejecución
de prueba, se detiene antes de cambiar nada, nombra cada carpeta y las entradas
que se movieron a ella, e indica cómo devolverlas. En una carpeta que creó un
instalador anterior, que no indica a qué directorio de instalación pertenece, la
línea puede nombrar solo los datos del motor: mira dentro. No elimina nada.
Consulta
[Solución de problemas](/docs/install/troubleshooting#the-installer-stops-an-earlier-run-left-folders-beside-apothem_home).

`--dry-run` (`-DryRun` en Windows) descarga y comprueba el lanzamiento en una
carpeta temporal y deja `~/.apothem` sin cambios. Hace las mismas comprobaciones
que una ejecución real, con una excepción para un clon existente: comprueba la
configuración propia del clon, tal como se enumera arriba, pero no hace fetch en
el clon, y por tanto no lo comprueba en busca de cambios en archivos rastreados,
algo que una actualización real hace después de su fetch. Fija un lanzamiento
concreto con `APOTHEM_REF`:

```bash title="Pinned, verified install"
APOTHEM_REF=vMAJOR.MINOR.PATCH sh -c "$(curl -fsSL https://apothem.ahmedgad.com/install.sh)"
```

Reemplaza `vMAJOR.MINOR.PATCH` por una etiqueta de la
[página de lanzamientos](https://github.com/ahmed-g-gad/apothem/releases). La
etiqueta de lanzamiento más antigua es una etiqueta ligera sin firma propia, por
lo que la comprobación de la etiqueta aborta con ella aunque su commit esté
firmado; todas las etiquetas de lanzamiento posteriores son anotadas y firmadas.
La sección de firma de lanzamientos de
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md)
lista cada etiqueta y cómo verificarla.

Las anulaciones explícitas relajan el comportamiento predeterminado. `APOTHEM_ALLOW_UNVERIFIED=1` degrada una comprobación fallida de la etiqueta en la ruta de clonado a una advertencia y continúa, para uso en sistemas aislados de la red o uso local, o para instalar un lanzamiento anterior a la firma de etiquetas. Nunca relaja la ruta de cosign, así que establece `APOTHEM_VERIFY=signature` junto con ella en un equipo que tenga cosign. Tampoco relaja nunca la comprobación de que la etiqueta firmada es la que lleva el nombre del lanzamiento. Como la anulación deja pasar una etiqueta sin firmar, o firmada por otra clave, esa comprobación solo protege las etiquetas que llevan la firma de la clave del mantenedor. `APOTHEM_REF=main` hace checkout de la rama móvil sin verificación solo junto con `APOTHEM_ALLOW_UNVERIFIED=1`. Con `APOTHEM_REF=main` por sí solo, el instalador descarga `main` en una carpeta de preparación (en el clon existente, cuando `APOTHEM_HOME` lo es) y después aborta antes de hacer checkout de nada, reemplazar `APOTHEM_HOME` o materializar ninguna configuración, porque una rama no es una etiqueta de lanzamiento firmada. Un checkout local mediante `APOTHEM_SOURCE` no descarga nada y omite la verificación.

Establece `APOTHEM_VERIFY` para elegir tú mismo la comprobación. El valor predeterminado es `auto`:

| Valor | Qué comprueba el instalador |
| --- | --- |
| `auto` (predeterminado) | `release` cuando `cosign` está en el `PATH` y `APOTHEM_HOME` no es un clon de git; en caso contrario, `signature` |
| `release` | La firma de la etiqueta de lanzamiento con la clave del mantenedor y que la etiqueta firmada es la que lleva el nombre del lanzamiento; después, la comprobación de cosign de que el flujo de trabajo de lanzamiento firmó `SHA256SUMS` en una ejecución sobre el commit de la etiqueta; después, el SHA-256 del archivo comprimido. Se detiene si falta cosign o `gpg` |
| `signature` | La firma GPG de la etiqueta de lanzamiento, que debe proceder de la clave del mantenedor, y que la etiqueta firmada es la que lleva el nombre del lanzamiento |
| `checksum` | Solo el SHA-256 del archivo comprimido frente a `SHA256SUMS`. Necesita `APOTHEM_ALLOW_UNVERIFIED=1` y advierte antes de descargar. El modo de suma de comprobación no verifica el lanzamiento. SHA256SUMS procede del mismo lanzamiento que el archivo comprimido, así que una coincidencia solo muestra que la descarga no está dañada; quien pueda cambiar los archivos del lanzamiento puede cambiar ambos. Úsalo solo en un equipo sin cosign ni `gpg`, y solo cuando lo aceptes |

Cada modo de archivo comprimido aborta ante una discrepancia del digest antes de
extraer nada. Los primeros lanzamientos llaman al bundle `SHA256SUMS.sig`, y el
instalador lee ese nombre cuando falta `SHA256SUMS.cosign.bundle`.

Después, el motor se ejecuta directamente desde el árbol colocado. Toda
dependencia de terceros, excepto `click` y `rich`, está incorporada dentro del
árbol de código fuente, y el propio punto de entrada coloca ese directorio de
dependencias incorporadas en `sys.path`. El instalador imprime la ruta completa
del shim `apothem` que escribió. Cuando no escribió ningún shim, imprime un
comando que inicia el motor manteniendo la carpeta actual fuera de `sys.path`;
copia ese comando del banner.

Ambos scripts leen las mismas variables de entorno de configuración
(`APOTHEM_HOME`, `APOTHEM_REPO`, `APOTHEM_REF`, `APOTHEM_ALLOW_UNVERIFIED`,
`APOTHEM_VERIFY`, `APOTHEM_RELEASE_BASE`, `APOTHEM_SOURCE`, `APOTHEM_HARNESS`, `APOTHEM_PROFILE`,
`APOTHEM_SKIP_VERIFY`, `APOTHEM_AUTO_INSTALL_DEPS`, `APOTHEM_BIN_DIR`); consulta
[Variables de entorno del instalador](/docs/how-to/installer-environment-variables)
para ver la tabla completa y
[Tiempo de ejecución autónomo](/docs/architecture/self-contained-runtime) para
ver cómo funciona el modelo de invocación `python -m`.

**El comando `apothem`.** Tras una instalación correcta, el instalador escribe
un shim `apothem` que reenvía al motor incluido — en POSIX en
`$HOME/.local/bin`, en Windows en `%LOCALAPPDATA%\Microsoft\WindowsApps` (un
directorio de usuario que ya está en el `PATH` predeterminado de Windows). El
instalador nunca edita tu `PATH`. Una vez que el directorio está en el `PATH`,
ejecutas `apothem <command>` directamente, sin `PYTHONPATH` manual.

**Verifica:**

```bash title="Verify"
apothem verify --harness claude-code

# or, before the shim is on PATH, by the shim's full path:
~/.local/bin/apothem verify --harness claude-code
```

## 4. Extensión de la familia VS Code

**Requisitos previos:** VS Code, Node.js 18+ y el Python 3.10+ del sistema en el
`PATH`.

La extensión **Apothem for VS Code** está en
[Visual Studio Marketplace](https://marketplace.visualstudio.com/items?itemName=ahmed-g-gad.apothem-vscode)
como `ahmed-g-gad.apothem-vscode`: instálala desde la vista de Extensiones o con
`code --install-extension ahmed-g-gad.apothem-vscode`. También se instala desde un
paquete `apothem.vsix`: `code --install-extension apothem.vsix`, o el comando
*Install from VSIX…* del editor. El flujo de trabajo de lanzamiento firma el
paquete y lo adjunta a cada GitHub Release. Los lanzamientos publicados antes
de que el flujo de trabajo empaquetara la extensión no incluyen ningún `.vsix`;
cuando al último lanzamiento le falta, compila el paquete desde un checkout
con la versión de vsce bloqueada en `tools/vsce/` (esa versión de vsce requiere Node.js 22 o
posterior): ejecuta `npm ci --prefix tools/vsce --ignore-scripts` y luego
`cd vscode-extension && ../tools/vsce/node_modules/.bin/vsce package --no-dependencies --out apothem.vsix`.
Una copia instalada desde un `apothem.vsix` anterior lleva el identificador
`ahmed-g-gad.apothem`; desinstálala (`code --uninstall-extension ahmed-g-gad.apothem`)
para que las dos copias no registren los mismos comandos. Una sola extensión
cubre los editores de la familia VS Code. Sus comandos de la paleta
(`Apothem: Install`, `Verify`,
`Update`, `Uninstall`, `Doctor`) ejecutan el mismo motor a través del ejecutor
configurado (`npx @ahmed-g-gad/apothem@<extension version>` de forma
predeterminada, de modo que la extensión ejecuta la versión del motor con la que
se distribuyó; apunta la configuración de usuario `apothem.runner` a un checkout
local para ejecutar desde el código fuente). Install, Verify, Update y Uninstall
preguntan sobre qué entorno actuar y ofrecen primero el entorno del propio
editor; `all` es una opción, nunca el valor predeterminado. La configuración
`apothem.runner` tiene alcance de máquina, así que un espacio de trabajo no
puede cambiarla, y la extensión solo se ejecuta en un espacio de trabajo de
confianza.

**Verifica:** ejecuta el comando **Apothem: Verify** desde la paleta de comandos
del editor, o desde una terminal:

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 7. Arranque de línea de comandos (host de plugin)

**Requisitos previos:** su herramienta anfitriona de línea de comandos, Node.js
18+ y el Python 3.10+ del sistema en el `PATH`.

Añade el repositorio como marketplace de plugins y luego instala el plugin — el
comando lleva el host y el slug de entorno exactos:

```bash title="Install the plugin"
codex plugin marketplace add ahmed-g-gad/apothem --sparse .agents/plugins --sparse plugins/apothem
```

Las dos rutas `--sparse` obtienen solo el listado del marketplace y el plugin,
no el repositorio completo; un clon completo puede superar el límite de clonado
de 30 segundos del host en un disco lento, como una unidad de Windows bajo WSL.

Como las extensiones de los canales 5 y 6, este es un **arranque** que delega en
el motor. El plugin incluye una skill de entrada; su manifiesto es un
`plugin.json` en la raíz, y la
[página de entorno del host de plugin](/docs/harnesses/codex#codex-plugin) describe la
estructura y lo que el plugin deja al motor. Materializa el entorno completo
ejecutando la instalación a través de él:

```bash title="Materialize the full harness"
npx @ahmed-g-gad/apothem install --harness codex
```

**Verifica:**

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness codex
```

## 8. Motor directo (`python -m apothem`)

**Requisitos previos:** el Python 3.10+ del sistema con los paquetes `click` y
`rich` importables, más un checkout del repositorio. No se requiere Node.js.

Ejecuta el motor directamente desde un clon. El punto de entrada coloca las
dependencias incorporadas (`src/apothem/_vendor`) en `sys.path`, así que, con
`click` y `rich` importables, `PYTHONPATH=src` es toda la configuración:

```bash title="Direct engine"
git clone https://github.com/ahmed-g-gad/apothem
cd apothem
PYTHONPATH=src python -m apothem install --harness claude-code
```

`python -m` coloca la carpeta actual en primer lugar en la ruta de búsqueda de
módulos de Python, así que un archivo de esa carpeta como `click.py`, o una
carpeta llamada `apothem`, se ejecutaría en lugar del módulo real. Ejecuta estos
comandos desde la raíz del checkout o desde otra carpeta de confianza. El
comando `apothem` instalado no lee la carpeta actual.

Igual que con el shim de npm, un primer `install` en una máquina sin perfil crea
el perfil inicial en `~/.config/apothem/profile.yaml` y continúa.

**Verifica:**

```bash title="Verify"
PYTHONPATH=src python -m apothem verify --harness claude-code
```

## Verifica cualquier instalación

Cada canal anterior nombra su propio comando de verificación. Las dos formas
generales son:

```bash title="Installer path"
apothem verify --harness claude-code
```

```bash title="npx path"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

Reemplaza el nombre del entorno por el adaptador que hayas instalado; consulta
la [lista de entornos](/docs/harnesses) para ver todos los nombres admitidos.
Para comprobar a la vez cada adaptador instalado (su verificación y sus comandos
de hook), ejecuta `doctor` en lugar de `verify --harness NAME`, en la forma que
hayas usado arriba: `apothem doctor` (o la ruta completa del shim, o el
comando que imprimió el instalador, cuando su carpeta no está en el `PATH`) o
`npx @ahmed-g-gad/apothem doctor`. Para la vía del plugin, ejecuta
`/plugin` dentro de Claude Code y confirma que **apothem** aparece como
instalado.

## Requisitos previos de un vistazo

- **Python 3.10 o posterior** — las vías que lo localizan lo hacen por nombre, y
  los nombres difieren según la vía. El shim de npm prueba `python3`, `python` y
  después `py -3`. Los instaladores prueban `python3`, `python` y los nombres con
  versión desde `python3.14` hasta `python3.10`.
- **`click` y `rich` importables** bajo ese intérprete — las dos dependencias
  orientadas a la terminal que el motor no incorpora. Los instaladores
  comprueban ambas, nombran lo que falte y se ofrecen a instalarlo por ti — con
  tu confirmación, o automáticamente con `--yes` (`-Yes` en PowerShell) o
  `APOTHEM_AUTO_INSTALL_DEPS=1`. En cualquier otro canal, un paquete que falte
  detiene el motor con un error (código de salida 1) que nombra el comando
  exacto para el intérprete que encontró, con las restricciones de versión con
  las que se prueba Apothem (`<interpreter> -m pip install "click==…" "rich>=…"`);
  con `--json`, el mismo error llega como un sobre JSON con el código
  `runtime.dependency_missing`.
- **Node.js 18 o posterior** — solo las vías que ejecutan `npx`: el shim de npm
  (2), la extensión de la familia VS Code (4) y los arranques de línea de
  comandos (5–7).
- **Tiempos de ejecución en fin de vida.** Python 3.10 alcanzó el fin de vida en
  su proyecto de origen el 2026-10-01, y Node.js 18 y 20, el 2025-04-30 y el
  2026-04-30. Apothem todavía los admite como sus versiones mínimas declaradas y
  prueba cada uno en CI, pero ya no reciben correcciones de seguridad de su
  proyecto de origen, así que prefiere Python 3.11 o posterior y Node.js 22 o
  posterior. La
  [política de versiones mínimas de tiempo de ejecución](/docs/governance/release-engineering-policy#runtime-floors)
  explica cómo se eleva una versión mínima.
- **Git y GnuPG** — solo la vía del instalador, y solo para la forma por red (el
  script encuentra con ellos el lanzamiento más reciente y comprueba su etiqueta
  firmada y, sin cosign, clona el código fuente; un checkout local no necesita
  ninguno de los dos).
- **Claude Code** — solo la vía del plugin. **VS Code** y la herramienta
  anfitriona propia de cada arranque de línea de comandos solo se necesitan para
  su propio canal (4–7).
