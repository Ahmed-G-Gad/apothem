**Proveedor:** Moonshot
**Nombre de instalación:** `kimi-code`
**Estado:** GA
**Configuración nativa:** `<project>/AGENTS.md` más `<project>/.kimi-code/.apothem/support/`

## Instalación

```bash
apothem install --harness kimi-code --project /path/to/project
```

El adaptador escribe la superficie de gobernanza compartida de Apothem en el
`AGENTS.md` de la raíz del proyecto como un bloque gestionado delimitado por
centinelas (el texto del operador fuera de los centinelas se conserva) y
mantiene las cohortes Markdown no nativas bajo el árbol de soporte propiedad de
Apothem en `<project>/.kimi-code/.apothem/support/`.
Muchas herramientas de programación además de Kimi Code leen un `AGENTS.md` de
proyecto, así que el bloque se escribe como orientación para todo el proyecto
que no nombra a ninguna herramienta concreta como su lector.

Kimi Code lee el archivo de instrucciones `AGENTS.md` de la raíz del proyecto
según la convención universal AGENTS.md, y la configuración del proyecto reside
bajo `<project>/.kimi-code/`. La superficie `<project>/.kimi-code/mcp.json` es
propiedad del operador; Apothem la nombra pero no redacta ninguna entrada.

**Archivos escritos:** `<project>/AGENTS.md` (bloque gestionado) y las cohortes
de comandos, skills, hooks, agentes, reglas y plantillas bajo
`<project>/.kimi-code/.apothem/support/`.

## Asignación del perfil a la configuración nativa

El adaptador lee el perfil compartido de Apothem y renderiza la superficie de
instrucciones `AGENTS.md` de la raíz del proyecto en cada ejecución de
`apothem install` o `apothem update`. Las reglas de comportamiento y el corpus
de gobernanza llegan al bloque gestionado de `AGENTS.md`; las cohortes de
comandos, skills, hooks, agentes, reglas y plantillas se colocan bajo
`.kimi-code/.apothem/support/` y se referencian desde la superficie de
instrucciones. Esta es la disposición que eligió el adaptador, no una carencia
de Kimi Code: Kimi Code carga las skills desde `.kimi-code/skills/` y
`.agents/skills/`, los agentes personalizados desde `.kimi-code/agents/` y
`.agents/agents/`, y los hooks desde el arreglo `[[hooks]]` de
`~/.kimi-code/config.toml`, pero no los carga desde el árbol de soporte, de modo
que las copias de Apothem que hay allí son material de referencia al que apunta
el bloque de `AGENTS.md`. El bloque termina con una sección de archivos de
soporte de Apothem que nombra, de forma relativa a la raíz del proyecto, el
directorio bajo `.kimi-code/.apothem/support/` contra el que se resuelve cada
cita con estilo de repositorio (`rules/<name>.md`, `templates/...`,
`hooks/...`), de modo que un `AGENTS.md` incluido en un commit no lleva ninguna
ruta específica de la máquina. (Comportamiento de Kimi Code según sus páginas de
personalización sobre
[skills](https://moonshotai.github.io/kimi-code/en/customization/skills),
[subagentes](https://moonshotai.github.io/kimi-code/en/customization/agents) y
[hooks](https://moonshotai.github.io/kimi-code/en/customization/hooks),
consultadas el 2026-10-02.)

## Notas de compatibilidad

Kimi Code lee las instrucciones del proyecto desde `AGENTS.md` o
`.kimi-code/AGENTS.md` y reconoce `.kimi-code/mcp.json` como la superficie MCP
propiedad del operador; Apothem nombra esa superficie, pero no redacta ninguna
entrada en ella. La superficie de instrucciones renderizada dirige el proyecto
directamente. Kimi Code no expone ninguna superficie de archivo de línea de
estado ni de estilo de salida, así que esas cohortes no se materializan.

Kimi Code funciona con la familia de modelos Kimi de Moonshot; consulta la
[referencia de configuración del proveedor](https://moonshotai.github.io/kimi-code/en/configuration/config-files)
para conocer el modelo y la superficie de configuración actuales.

## Verificación

```bash
apothem verify --harness kimi-code --project /path/to/project
```

El comando verify confirma que:

1. La configuración nativa existe en la ruta esperada.
2. Cada destino gestionado existe; los archivos gestionados no están vacíos y las configuraciones JSON o YAML se analizan correctamente. Añade `--profile PATH` para confirmar también que los archivos instalados coinciden con ese perfil.
3. La rutina de verificación específica del adaptador informa de éxito.

## Actualización

```bash
apothem update --harness kimi-code --project /path/to/project
```

Vuelve a derivar el bloque gestionado de `AGENTS.md` de la raíz del proyecto y
las cohortes de soporte a partir del estado actual del perfil compartido.

## Desinstalación

```bash
apothem uninstall --harness kimi-code --project /path/to/project
```

Elimina los archivos de configuración nativa escritos por el adaptador.
El YAML del perfil compartido y el motor de Apothem no se ven afectados.

## Puerta de conformidad

```bash
python -m apothem.conformity.gate --all .
```

## Solución de problemas

| Síntoma | Solución |
|---------|-----|
| No se encuentra el archivo de configuración | Vuelve a ejecutar `apothem install --harness kimi-code --project /path/to/project` |
| La verificación falló | Ejecuta `apothem update --harness kimi-code --project /path/to/project` y luego verifica de nuevo |
| Contenido de configuración inesperado | Revisa `~/.config/apothem/profile.yaml` o `--profile PATH` y luego vuelve a ejecutar `apothem update --harness kimi-code --project /path/to/project` |

## Opciones de configuración

| Indicador | Predeterminado | Descripción |
|------|---------|-------------|
| `--dry-run` | `false` | Previsualiza la instalación sin escribir archivos. |
