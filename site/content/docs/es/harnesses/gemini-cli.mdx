- **Proveedor:** Google
- **Nombre de instalación:** `gemini-cli`
- **Estado:** GA
- **Configuración nativa:** `GEMINI.md` y `.gemini/` locales del proyecto

## Instalación

```bash
apothem install --harness gemini-cli --project /path/to/project
```

El adaptador tiene alcance de proyecto. Instala el `GEMINI.md` del proyecto,
convierte los comandos de Apothem en comandos de barra TOML de Gemini,
normaliza las definiciones de ayudantes locales y coloca las cohortes de
soporte no nativas bajo `.gemini/.apothem/support/`.
Otras herramientas de programación también leen el `GEMINI.md` de un proyecto,
así que el bloque de Apothem en él se escribe como guía para todo el proyecto
que no nombra ninguna herramienta concreta como su lector.

**Archivos escritos:**

```text
GEMINI.md
.gemini/commands/*.toml
.gemini/agents/*.md
.gemini/skills/
.gemini/.apothem/support/
```

El proyecto también recibe la carpeta de datos que crea toda instalación de
proyecto, `.apothem/` de forma predeterminada, con `contexts/`, `learning/`,
`memory/` y `plans/` dentro.

## Asignación del perfil a la configuración nativa

El adaptador lee las cohortes compartidas de Apothem y enruta cada una a través
de una superficie compatible con Gemini. Las reglas Markdown, las plantillas y
el material de hooks permanecen bajo `.gemini/.apothem/support/` porque son
material de soporte, no un directorio de reglas nativo de Gemini.
El bloque de Apothem en `GEMINI.md` termina con una sección de archivos de
soporte de Apothem que nombra, de forma relativa a la raíz del proyecto, el
directorio bajo `.gemini/.apothem/support/` contra el que se resuelve cada cita
con estilo de repositorio (`rules/<name>.md`, `templates/...`, `hooks/...`).
Las rutas son relativas para que un `GEMINI.md` incluido en un commit no lleve
ninguna ruta específica de una máquina.

Cada comando convertido en `.gemini/commands/` contiene una `description` y un
`prompt`. El prompt contiene solo las instrucciones del comando; los metadatos
de Apothem al inicio del archivo de origen (versión, lista de herramientas y
campos similares) se omiten, de modo que el modelo nunca los lee como
instrucciones. Gemini ejecuta un comando personalizado solo cuando lo escribes.

Las definiciones de ayudantes en `.gemini/agents/` conservan sus límites de
herramientas y su límite de turnos: la concesión `tools` de origen, menos
`disallowedTools`, se convierte en una lista de permitidos `tools` de Gemini
con nombres de herramientas de Gemini, y `maxTurns` se convierte en
`max_turns`. Por tanto, un ayudante de solo lectura no recibe ninguna
herramienta `write_file` ni `replace`. No se establece ningún modelo, así que
cada ayudante hereda el modelo de la sesión.

Un ayudante que la clave `agent_mcp_servers` del perfil lista también obtiene una
entrada `mcp_<server>_*` por cada servidor nombrado en su lista de permitidos
`tools`, de modo que puede llamar a las herramientas de ese servidor y a las de
ningún otro; sin la clave, cada ayudante conserva la lista de permitidos simple
(consulta
[Servidores MCP](/docs/reference/mcp#give-a-helper-access-to-mcp-servers)).
Apothem escribe aquí una concesión solo para un nombre de servidor formado por
letras, dígitos y `-`, porque `Gemini CLI` no puede referirse a un nombre con
guion bajo; cualquier otro nombre se omite y se informa, y lo mismo ocurre con
una concesión para un ayudante que ya alcanza todos los servidores MCP.

## Notas de compatibilidad

`~/.gemini/` sigue siendo territorio con alcance de usuario para las
herramientas que usan un perfil global de Gemini. El adaptador de Gemini CLI
escribe únicamente en el proyecto pasado mediante `--project`.

Gemini CLI también carga dos ubicaciones de tu directorio personal que escriben
otras instalaciones de Apothem: `~/.agents/skills/`, parte de su nivel de skills
de usuario, donde varias instalaciones escriben las skills de Apothem (el
[registro de entornos](/docs/reference/harness-registry#shared-roots) las lista),
y `~/.gemini/GEMINI.md`, donde la instalación de
[Antigravity](/docs/harnesses/antigravity) escribe un bloque de Apothem.
Cuando alguna de las dos ubicaciones ya contiene contenido de Apothem, instalar
`gemini-cli` imprime una nota que la nombra junto con la instalación que lo
escribió.

## Verificación

```bash
apothem verify --harness gemini-cli --project /path/to/project
```

El comando verify confirma que:

1. La configuración nativa existe en la ruta esperada.
2. Cada destino gestionado existe; los archivos gestionados no están vacíos y
   las configuraciones JSON o YAML se analizan correctamente. Añade
   `--profile PATH` para confirmar también que los archivos instalados coinciden
   con ese perfil.
3. La rutina de verificación específica del adaptador informa de éxito.

## Actualización

```bash
apothem update --harness gemini-cli --project /path/to/project
```

Refresca `GEMINI.md`, los comandos convertidos, las definiciones de ayudantes
locales, las skills instaladas y el árbol de soporte
`.gemini/.apothem/support/`.

## Desinstalación

```bash
apothem uninstall --harness gemini-cli --project /path/to/project
```

Elimina el bloque de Apothem de `<project>/GEMINI.md` y conserva cualquier otro
texto que haya en él. El archivo se elimina solo cuando no queda nada más en él.
También elimina los archivos de Apothem en `<project>/.gemini/commands/`,
`<project>/.gemini/skills/`, `<project>/.gemini/agents/` y
`<project>/.gemini/.apothem/support/`; los demás archivos de esas carpetas
permanecen. Antes del cambio, se guarda bajo `~/.apothem/backups/` una copia con
marca de tiempo de cada archivo; no se deja ningún archivo de respaldo en el
proyecto. El YAML del perfil compartido y el motor de Apothem no se ven
afectados.

Las versiones anteriores (el [registro de cambios](/docs/changelog) las nombra)
también eliminaban el propio `skills/AGENTS.md` de un proyecto (en la raíz del
proyecto, no bajo `.gemini/`) en cada instalación y actualización, tras
copiarlo en un conjunto de respaldo bajo
`~/.apothem/backups/<timestamp>/gemini_cli/`. La versión actual deja ese archivo
intacto. Para recuperarlo, copia `~/.apothem/backups/` en otro lugar antes de
volver a ejecutar Apothem y luego copia a mano el archivo desde esa copia de
vuelta al proyecto. El
[registro de cambios](/docs/changelog#data-loss-in-earlier-releases-recover-your-files)
tiene los pasos completos de recuperación.

## Puerta de conformidad

```bash
python3 -E -s ~/.apothem/src/apothem/conformity/gate.py --all .
```

Ejecútalo desde la carpeta de tu proyecto. En Windows, usa `python` en lugar de
`python3` y la ruta completa, ya que Windows PowerShell y cmd no expanden `~`:
`$HOME\.apothem\src\apothem\conformity\gate.py` en PowerShell, o
`%USERPROFILE%\.apothem\src\apothem\conformity\gate.py` en cmd. La ruta es
donde el instalador coloca el motor, y `-E -s` mantiene tu `PYTHONPATH` y tus
site-packages de usuario fuera de la puerta;
[Puerta de conformidad](/docs/conformity-gate) explica ambas cosas y las demás
instalaciones.

## Solución de problemas

| Síntoma | Solución |
|---------|-----|
| No se encuentra el archivo de configuración | Vuelve a ejecutar `apothem install --harness gemini-cli --project /path/to/project` |
| La verificación falló | Ejecuta `apothem update --harness gemini-cli --project /path/to/project` y luego verifica de nuevo |
| Contenido de configuración inesperado | Revisa `~/.config/apothem/profile.yaml` o `--profile PATH` y luego vuelve a ejecutar `apothem update --harness gemini-cli --project /path/to/project` |

## Opciones de configuración

| Indicador | Predeterminado | Descripción |
|------|---------|-------------|
| `--dry-run` | `false` | Previsualiza la instalación sin escribir archivos. |
