Solutions for common Apothem install and runtime issues.

## Installation issues

### No Python 3.10+ found

The installers probe `python3`, `python`, and the versioned names (`python3.14`
through `python3.10`) — rejecting Microsoft Store launcher shims — and stop with
`No Python >= 3.10 found in PATH` when no candidate meets the 3.10 floor. The
npx shim probes `APOTHEM_PYTHON` when it is set, then `python3`, `python`, and
`py -3`, and exits 1 with its own message when none qualifies. Install CPython
3.10 or newer from python.org or your OS package repository, confirm
`python3 --version` (or `py -3 --version` on Windows) reports at least 3.10,
then re-run.

### Missing runtime dependencies: click, rich

The engine vendors most of its third-party dependencies inside the source
tree, but `click` and `rich` must be importable under the interpreter the
installer selects. When either is missing, the installer names it and offers
to install it for you:

```text
! Missing Python prerequisites under <python>: click rich
  Install click rich under <python> now? [y/N]
```

Accept the prompt to have the installer run `pip install` under that
interpreter. To skip the prompt, pass `--yes` (`-Yes` on PowerShell) or set
`APOTHEM_AUTO_INSTALL_DEPS=1` to install automatically. If you decline — or
`pip` is unavailable, or you prefer your OS package manager — install the
named packages yourself (for example `python3-click` and `python3-rich` on
Debian-family hosts, or `pip install click rich`) and re-run.

### `apothem` not found after running the installer

The installer places the source tree at `~/.apothem` and writes an `apothem`
shim to `~/.local/bin` by default (POSIX) or
`%LOCALAPPDATA%\Microsoft\WindowsApps` (Windows); `APOTHEM_BIN_DIR` changes the
folder. It does not edit your `PATH`. If `apothem` is not found, that directory
is not on `PATH`; add it, or run the shim by its full path. The installer prints
that path at completion. When it wrote no shim, it prints a command that starts
the engine with the current folder kept off `sys.path`; copy that command from
the banner. The npx form (`npx @ahmed-g-gad/apothem <command>`) needs no `PATH`
entry.

### `/plugin marketplace add` fails

`/plugin marketplace add ahmed-g-gad/apothem` fetches the marketplace
listing from GitHub. When it fails, confirm the machine can reach
`https://github.com/ahmed-g-gad/apothem` (network, proxy, or firewall
rules), then retry. If the marketplace was added earlier under a partial
fetch, remove and re-add it before running
`/plugin install apothem@apothem`.

### Adding the plugin host's marketplace times out

The plugin host's command that adds a marketplace clones its repository and
gives up after 30 seconds. A full clone of this repository can take longer on a slow
disk, such as a Windows drive under WSL, and an earlier full clone can also
leave the plugin stuck at an old version when a later refresh times out.
Fetch only the two folders the plugin needs:

```bash
codex plugin marketplace remove apothem
codex plugin marketplace add ahmed-g-gad/apothem --sparse .agents/plugins --sparse plugins/apothem
codex plugin add apothem@apothem
```

Listing the host's plugins then shows the current version of `apothem@apothem`.

### npx serves a stale version

`npx` caches downloaded packages. When `npx @ahmed-g-gad/apothem --version`
reports an older version than the current release, clear the cache or pin
the dist-tag:

```bash
npx clear-npx-cache
npx @ahmed-g-gad/apothem@latest --version
```

### The installer stops: the maintainer public key is not in the local keyring

Every network install verifies the signed release tag, with or without cosign,
and stops when the signing key is not in your keyring. Import it once, check that the fingerprint reads
`5C89 98F9 F241 7204 45D3  F28B 7039 6FED 9C63 4163`, then run the installer
again:

```bash title="macOS · Linux · WSL2 · BSD — import the key once"
curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import
gpg --fingerprint 70396FED9C634163
```

```powershell title="Windows · PowerShell — import the key once"
& "$env:ProgramFiles\Git\bin\bash.exe" -c 'curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import && gpg --fingerprint 70396FED9C634163'
```

On Windows, import through Git's `bash` as shown: `git verify-tag` reads the
keyring of the `gpg` that ships with Git for Windows. Installing
[cosign](https://docs.sigstore.dev/cosign/system_config/installation/) does
not replace the key import: with cosign on `PATH`, the installer checks the
signed release archive as well as the tag. A host without `gpg` can install
with `APOTHEM_VERIFY=checksum` and `APOTHEM_ALLOW_UNVERIFIED=1`, but that mode
does not verify the release (see
[The installer stops: checksum mode needs a second variable](#the-installer-stops-checksum-mode-needs-a-second-variable)).

### The installer stops: gpg not found

Install GnuPG, or on Windows Git for Windows, which ships the `gpg` that
`git verify-tag` runs. Then import the maintainer key as shown above and run
the installer again.

### The installer stops: the tag is not signed by the maintainer key

The message reads "Tag ... is signed by the key ..." and names the key that
signed it. The tag's signature is valid, but that key is not the one
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md#maintainer-signing-key)
publishes. Apothem release tags are signed only with that key, so treat this as
possible tampering: do not install, and report it through the channels in
SECURITY.md. A fork signed with its own key is expected to stop here.

### The installer stops: cosign could not confirm the release signature

Read the `cosign said:` text at the end of the message first.

- A network, proxy or trusted-root error means cosign could not reach
  Sigstore. Retry when you are online, upgrade cosign, or install with
  `APOTHEM_VERIFY=signature`, which checks the release tag against the
  maintainer key alone.
- A fork set through `APOTHEM_REPO` is expected to stop here: the installer
  accepts only Apothem's own release workflow.
- "expected GitHub Workflow SHA not found in certificate" means the
  certificate cosign verified was issued to a run on a different commit than
  the one the signed tag points at, so it does not tie `SHA256SUMS` to that
  commit. Do not install; report it through the channels in
  [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md).
- An identity or signature mismatch on Apothem's own releases means
  `SHA256SUMS` was not signed by Apothem's release workflow for this tag. Do
  not install; report it through the channels in
  [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md).

When the installer instead says it could not download the bundle, check your
connection; if the release publishes no bundle, install it with
`APOTHEM_VERIFY=signature`.

### The installer stops: the signed tag is not the release tag

The message reads "the signed tag object is not the vX.Y.Z release tag". The
tag carries the maintainer key's signature, but the object that was signed
names another tag, so a signed tag for a different release was re-pointed at
this name. Treat this as possible tampering: do not install, and report it
through the channels in
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md).
`APOTHEM_ALLOW_UNVERIFIED=1` does not bypass this check, but that variable
lets an unsigned tag, or one signed by another key, through, so the check
protects only tags that carry the maintainer key's signature.

### The installer stops: checksum mode needs a second variable

Checksum mode does not verify the release. SHA256SUMS comes from the same
release as the archive, so a match only shows the download isn't damaged;
anyone who can change the release's files can change both. For that reason
`APOTHEM_VERIFY=checksum` runs only when `APOTHEM_ALLOW_UNVERIFIED=1` is set
too. Set both if you accept that, or install `gpg` (and cosign) and run
without `APOTHEM_VERIFY=checksum`.

### The installer stops: the folder at APOTHEM_HOME is not an Apothem install

The installer does not replace a folder that holds something other than an
Apothem install. Move it aside, point `APOTHEM_HOME` at another folder, or
re-run with `--yes` (`-Yes` on PowerShell). With `--yes`, the installer moves
the whole folder, unchanged, into a new folder,
`<APOTHEM_HOME>.before-apothem-<time>`, beside it (it keeps its own name
inside), says where, and installs fresh. A git clone of another project counts
as such a folder. If both `<APOTHEM_HOME>.before-apothem-<time>` and the same
name with the installer's process ID added already exist, the installer stops
with "Could not move the existing ... aside; nothing was changed" before
anything moves; rename or remove one of them and re-run.

### The installer stops: APOTHEM_HOME is a symbolic link

The message reads "is a symbolic link" (on Windows, a symbolic link or a
junction). Replacing the folder would replace the link and not the folder it
leads to, so the installer refuses. Set `APOTHEM_HOME` to the folder the link
leads to, then re-run. An existing git clone behind a link is still updated
in place.

### The installer stops: the git clone holds local work

Replacing a git clone with a release archive needs `--yes`, and the installer
refuses even then while the clone holds local work it would lose: changes to
tracked files, stashes, commits that are not on a remote, or untracked files
in the clone's source tree. Commit and push that work, or move it elsewhere,
then re-run. The check also runs with `--dry-run`. When the clone has no
such work, `--yes` replaces it and keeps the clone's own tree at
`<APOTHEM_HOME>.before-apothem-<time>/<name>`, where `<name>` is the last part
of `APOTHEM_HOME`; the installer prints that path, and you delete the folder
once you no longer need it.

### The installer stops: the existing clone is set up in a way the update would trust

Before it fetches into an existing clone, the installer (and the update script)
checks how the clone is set up. `--dry-run` makes these checks too. "has
changes to tracked files" also appears when files are marked assume-unchanged
or skip-worktree, which hides their changes from git: run
`git update-index --no-assume-unchanged <file>` or
`git update-index --no-skip-worktree <file>`, then commit or stash the change.
"is not the work tree of its git clone" means git finds no work tree in
`APOTHEM_HOME`, as when the clone's git config sets `core.bare` to `true`: set
it to `false` so the clone checks out into `APOTHEM_HOME`. A `core.worktree`
setting, which would send the checkout to another folder, is reported as a
setting an update in place does not accept (below).

"own git config sets `<key>`, which an update in place does not accept in a
clone's own config" names a setting in the clone's `.git/config`, or in
`.git/config.worktree` when the clone has one. An update in place accepts only
these settings there (the section and the key compare without regard to case):

- the settings `git clone` and `git init` write for a full clone:
  `core.repositoryformatversion`, `core.filemode`, `core.bare`,
  `core.logallrefupdates`, `core.symlinks`, `core.ignorecase`,
  `core.precomposeunicode`, `core.longpaths`, `extensions.objectformat`,
  `extensions.refstorage` (only with the value `files` or `reftable`),
  `extensions.worktreeconfig`, `remote.origin.url`, `remote.origin.fetch` and
  `remote.origin.tagopt`;
- branch settings, `branch.<name>.<key>`, which git and editors add, except
  that `branch.<name>.remote` and `branch.<name>.pushremote` must be exactly
  `origin`;
- `user.name`, `user.email`, `maintenance.auto`, `maintenance.strategy`,
  `pull.rebase` and `pull.ff`.

Any other setting stops the update, because it could make git run a program,
read settings, hooks, attributes or objects from another place, or connect
somewhere else. A clone made with `--mirror`, `--sparse`,
`--recurse-submodules` or a remote not named `origin` stops here too, and so
does a partial clone, made with `--filter`: the message names
`remote.origin.promisor`, because git would fetch missing objects from the
remote on its own while it reads the clone. Clone again without `--filter`.
Remove the setting from the file the message names, for example
`git config --file ~/.apothem/.git/config --unset-all <key>`, then re-run.
`--unset-all` also removes a setting that is there more than once. For a
branch's `remote` or `pushremote`, set it to `origin` instead, for example
`git config --file ~/.apothem/.git/config branch.main.remote origin`. "own git
attributes set a filter" names `.git/info/attributes`: remove the `filter=`
line.

"which is not a plain file" names `.git/info/attributes`, `.git/config` or
`.git/config.worktree` when it is a folder, a named pipe or another special
file, or, on Windows, a link. git could read other text from such a file than
the check reads. Replace it with a plain file, or remove it, then re-run.

"has a setting whose name holds a line break" means a section name in the file
the message names holds a carriage return. git never writes one, and a reader
could take that name for two settings. Open the file in a text editor, remove
that section, then re-run.

"borrows objects from another repository" means the clone has an
`objects/info/alternates` or `objects/info/http-alternates` file, as a clone
made with `--reference` or `--shared` does. git would then read objects from
that other repository, under settings the installer does not check. Run
`git -C ~/.apothem repack -a -d` to copy the objects into the clone, remove the
file the message names, then re-run.

"keeps submodule repositories in ..." and "holds a submodule at ..." mean the
clone has a submodule, kept in the folder the first message names or recorded
in its index at the path the second one names. A release tree has none, and
git would run inside the submodule, whose own settings the installer does not
check. Remove the submodule and that folder from the clone, or move the clone
aside, then re-run. Replacing the clone with `--yes` makes this check too,
before `git status` looks for local work. The clone's git hooks never run
during an update.

### The installer stops: a .gitattributes file in the clone is untracked or changed

git applies the `.gitattributes` files in the work tree while it compares and
checks out files, and such a file can make git run a program. Before any of
those commands, the installer and the update script stop on a `.gitattributes`
file that is not the committed one, in any folder of the clone and with any
mix of capital letters in its name. `--dry-run` and `--yes` make this check
too.

- "has a .gitattributes file that git does not track, at ..." names a file git
  does not track, ignored files and files in untracked folders included.
  Remove it, then re-run.
- "has a changed .gitattributes file at ..." names a tracked file whose content
  differs from the committed copy, whose change is staged, or which is a link
  or a folder. If you made the change, put back the committed copy, for
  example with `git -C ~/.apothem checkout HEAD -- <path>`, then re-run.
- "has a .gitattributes file at ... that sets a filter (filter=)" names a
  committed file that names a filter outside a comment. git would run that
  filter, which your own git config may define, while it reads the clone.
  Remove the filter, commit that change, then re-run.

If you did not make the file or the change, someone else could write to the
clone: move it aside, install fresh, and make sure `APOTHEM_HOME` is a folder
only you can write.

### The installer stops: files under src that git does not track

The message reads "has files under src that git does not track, and the engine
could load them:" and lists each one (the first 20, then how many more). The
engine runs from the clone's `src` folder, so an extra file there could run as
part of it. Ignored files count, and so does a `.pyc` file beside the sources.
A folder named `Src` or `SRC` counts as `src`, since Windows and macOS find
it under that name.
An editable `pip install` of the clone writes `src/apothem.egg-info`, and a file
manager can write `.DS_Store` or `desktop.ini`. Move the files out of
`~/.apothem/src`, then re-run; nothing was changed. The check runs before the
fetch, in an update in place and in a dry run. Python's cache folders
(`__pycache__`) do not count: after the checkout, and before the engine first
runs from the clone, the update removes every `__pycache__` folder under `src`,
so no cached bytecode from before the update loads.

"Could not remove the Python cache folders (__pycache__) under ..." means that
removal failed, for example because a file in one of them belongs to another
user or, on Windows, is open in another program. The clone is already checked
out to the new release. Remove those folders yourself, then re-run.

### The installer stops: another run holds the lock

Each run of the install, update and uninstall scripts holds a lock beside
`APOTHEM_HOME` (`<APOTHEM_HOME>.lock`, so `~/.apothem.lock` by default) while
it runs; the `apothem install`, `apothem update` and `apothem uninstall`
commands do not take it. The message "Another Apothem install, update or
uninstall is running on ..." means a second run found it held. Wait for the
other run to finish, then re-run. If none is running, remove the lock the
message names, then re-run.

- "was left by an Apothem run that did not finish (process N is no longer
  running)" and "exists but names no running process" mean a run was killed
  before it could release the lock. Check that no Apothem install, update or
  uninstall is running, remove the lock, and re-run. The installer never
  removes it for you. On POSIX the lock is a folder (`rm -rf ~/.apothem.lock`);
  on Windows PowerShell it is a file that Windows deletes when its run ends.
- "is the lock file of an Apothem PowerShell run" comes from a POSIX script
  under Git Bash, MSYS2, Cygwin or WSL that found the file a PowerShell run
  holds. Windows removes that file when the run ends and lets no one remove it
  while the run is active. Wait for that run to finish. If no Apothem install,
  update or uninstall is running, remove the file, then re-run. On other
  systems the message reads "is a file where the Apothem lock folder belongs":
  remove the file if no run is active, then re-run.
- "was made by an Apothem run in another environment" means the lock folder
  names a process in another environment, such as WSL when the run is under
  Git Bash, Git Bash when it is under WSL or MSYS2, or another container.
  That process cannot be checked from here. Wait for that run to finish;
  remove the lock only if no Apothem install, update or uninstall is running
  anywhere.
- The POSIX scripts count a process that belongs to another user, such as a
  run under `sudo`, as running, so its lock reads as held. PowerShell cannot
  check the process ID of a lock folder made by the POSIX scripts (for example
  under Git Bash), so it reports that lock as held too.
- When `APOTHEM_HOME` is a symbolic link (or, on Windows, a junction), the
  POSIX and the PowerShell scripts take the lock beside the folder the link
  leads to, so a run through the link and a run through that folder stop each
  other; the message names that lock.
- "Could not create the lock ... Check that you can write to ..." means you
  cannot write to the folder the message names: the one that holds
  `APOTHEM_HOME` or, when `APOTHEM_HOME` is a link, the one that holds the
  folder it leads to. Every run
  needs to write there, an update in place, an uninstall and a dry run
  included.

### The installer stops: an earlier run left folders beside APOTHEM_HOME

The message reads "An earlier run was stopped part-way and left these
folders beside ..." and lists each folder with what it holds. Ctrl+C and a
termination signal are caught and the run cleans up; a forced kill or a
power loss during a swap is not, and can leave:

- `.apothem-old.<name>.*`: the earlier install that was being replaced, in its
  `home` folder. When that `home` folder holds a git clone and `APOTHEM_HOME`
  is in place (as it is once the new install has moved in), the line says
  instead that it holds the clone's tree, which that run was keeping: move it
  to a folder of your own if you still need it. When the `home` folder holds
  no Apothem install and `APOTHEM_HOME` is in place, the line says so: a folder
  appeared there while the run was moving the earlier install, the run put the
  install back and left that folder alone. Check what it holds before you
  remove it.
- `.apothem-extract.<name>.*` or `.apothem-clone.<name>.*`: the new source
  that was being installed. When the run had already moved entries of
  `APOTHEM_HOME` into it, the line names every one: engine data such as
  `backups` and `state`, and any other file or folder that was there.
- `<APOTHEM_HOME>.before-apothem-<time>`: listed only when `APOTHEM_HOME`
  itself is missing. It holds the earlier contents of `APOTHEM_HOME`, in a
  folder named after the last part of `APOTHEM_HOME`, or directly inside it
  for a folder an earlier installer made; the line says which.

`<name>` is the last part of `APOTHEM_HOME` (`.apothem` by default), so the
folders of another `APOTHEM_HOME` in the same parent folder, which a run on
that home may be using, are not listed. On Windows and macOS a `<name>` that
differs only in capital letters counts as this home's, because `APP` and
`app` name the same folder there by default. The rule follows the operating
system, not the file system: under WSL, even on a Windows drive, names that
differ in capitals are different homes, while on a case-sensitive macOS volume
or Windows folder they still count as one, so another home there whose name
differs only in capitals is listed too. A folder whose name has no `<name>` part was made by
an earlier installer that did not record the home; it is listed with a note
that it may belong to any Apothem home in that folder, and its line says the
entries were moved from the home it was made for. For such a folder made by
a clone install, the line names only the engine data it finds, so look inside
for anything else. Only folders count: a file or a link with such a name is
not listed. A folder the installer cannot read is listed as "could not be
read".

Nothing was changed and nothing is deleted. If `APOTHEM_HOME` is missing,
move the earlier install back to it first. Then move every entry the list
names as moved into a new source back into the home it came from (check
which home first for a folder with the note), remove the listed folders, and
re-run. The check runs for a fetched install, a dry run included; it does not
run for an install from your own checkout, nor for an update or an uninstall.

### The installer stops: another user owns the clone

The message reads "is owned by someone else, so git refuses to work in it
(git reports "dubious ownership")". git will not read a clone that another
user owns. Run the installer as the user who owns `APOTHEM_HOME`, take
ownership of the folder, or point `APOTHEM_HOME` at a folder you own, then
re-run. The installer does not add the folder to git's `safe.directory`
list. Any other failure of that first git command reads "git could not read
the clone at ..." followed by git's own first line of explanation.

### The installer warns: other users can change APOTHEM_HOME

The install and update scripts, dry runs included, warn when users other
than you can write to `APOTHEM_HOME`, since they can then change the code
the `apothem` command runs as you. The run goes on; the warning only names
the folder, who can write to it, and the fix. The warning starts with one of:

- "Other users can change the code Apothem runs as you", when they can write
  to `APOTHEM_HOME`. When `APOTHEM_HOME` is a link, the message names the
  folder it leads to.
- "Other users can replace ...", when they can write to the folder that holds
  `APOTHEM_HOME` (or holds the link to it), and so rename or remove it.
- "A new ... would let", when `APOTHEM_HOME` does not exist yet and a new
  folder there would be open to others.

An install from a local checkout is not checked, whether `APOTHEM_SOURCE`
names it or you run that checkout's own `scripts/installer/install.sh` or
`install.ps1`. The update scripts skip the check only when `APOTHEM_SOURCE` is
set. If the warning names a group that you share on purpose with people you trust to
change the code, you can ignore it.

On Linux and macOS, the warning names "all users" or "the group" it found in
the folder's permission bits. A group with your own user name is your own
group and is never named. To fix it, run the command the message gives:

```bash
chmod go-w "$HOME/.apothem"
```

Files made under the same settings can be writable too: `chmod -R go-w` on
the folder fixes those as well. If others need to write to the folder that
holds `APOTHEM_HOME`, as with `/tmp`, set its sticky bit with `chmod +t` so
they cannot rename or remove what you put there, or move `APOTHEM_HOME`. For
a new install, the warning reports your umask: run `umask 022` and run the
installer again. On WSL, keep `APOTHEM_HOME` in your Linux home, not under
`/mnt/c`, where every file looks writable by all users.

On Windows, the warning names Everyone, Authenticated Users, Users or
INTERACTIVE (everyone signed in at the computer or over Remote Desktop, who
can change what is made in `C:\Users\Public`) when a permission entry lets
them change the folder. When the message adds "access
that folders made at the root of a drive inherit from the drive's default
permissions", the folder sits at the root of a drive, such as `C:\apothem`:
Windows lets every user who signs in add and change folders made there. The
simplest fix is to move `APOTHEM_HOME` into your user folder (`%USERPROFILE%`),
as the default `~\.apothem` is. To keep the folder where it is, turn off
inheritance, give yourself full control, then remove the four groups:

```powershell
icacls "C:\apothem" /inheritance:d
icacls "C:\apothem" /grant:r "${env:USERNAME}:(OI)(CI)F"
icacls "C:\apothem" /remove:g *S-1-5-11 *S-1-5-32-545 *S-1-1-0 *S-1-5-4
```

Give yourself access before you remove the groups: the entry you remove can
be your only way to write to the folder. The `*S-...` names are the groups'
security IDs (Authenticated Users, Users, Everyone and INTERACTIVE), which
work in every
Windows language. You can make the same change in the folder's Properties >
Security > Advanced. When the warning is about the folder that holds
`APOTHEM_HOME`, make the change there, or move `APOTHEM_HOME`. A link or
junction at `APOTHEM_HOME` takes its permissions from that folder, so
others who can change the folder can delete the link and make their own.

The shell scripts skip the check under Git Bash, MSYS2 and Cygwin, where the
permission bits are made up from Windows permissions; `install.ps1` and
`update.ps1` read the Windows permissions themselves.

### The installer stops: the existing clone could not be updated

The installer fetches into an existing clone and checks the new tag before it
checks the clone out, so a failed check leaves the clone as it was. Two other
messages stop the update before the checkout. "Could not fetch" usually means a
local tag differs from the one on origin: delete it with
`git -C ~/.apothem tag -d <tag>` and re-run. "has changes to tracked files.
Commit or stash them, then re-run." means the clone has uncommitted changes to
files git tracks: commit or stash them, then re-run. A dry run does not check
for ordinary uncommitted changes, since it does not fetch into the clone, but
it stops with the same message when files are marked assume-unchanged or
skip-worktree (see the clone setup section above). "Could not check out"
means the checkout would still overwrite local changes. The installer never
discards local changes. For a non-release ref such as `main`, an existing
clone follows origin's copy of that branch.

### irm / iex blocked on Windows

If PowerShell execution policy blocks the installer:

```powershell
Set-ExecutionPolicy RemoteSigned -Scope CurrentUser
irm https://apothem.ahmedgad.com/install.ps1 | iex
```

### The installer ignored the checkout in my current folder

This is intended. A piped one-liner (`curl ... | sh`, `irm ... | iex`) never
uses a local tree, and never looks in the current folder or its parent folders:
it fetches and verifies the release. To install from a checkout, run that
checkout's own `scripts/installer/install.sh` (or `install.ps1`) by its path,
from any folder (for example `sh ~/src/apothem/scripts/installer/install.sh`),
or set `APOTHEM_SOURCE` to the checkout. Give the script a path with a folder
part: `sh scripts/installer/install.sh` or `sh ./scripts/installer/install.sh`
works, but `sh install.sh` with no folder part does not count as running from a
checkout, so the installer prints "Not using a checkout: to install from one,
run this script as ./install.sh or by its full path, or set APOTHEM_SOURCE." and
fetches and verifies the release instead. A script started through `sh -c` is
not treated as a checkout either, in shells that mark `-c` runs. dash does not
mark them, so under dash `sh -c "<script>" ./install.sh` started from a folder
named `scripts/installer` inside a source tree uses that tree: start script text
that way only from a folder you trust. In the same way, a copy of `install.sh`
that you save into another source tree's `scripts/installer` folder and run
there by path becomes that tree's own installer and installs it. Save a
downloaded script to an empty folder. `install.sh` follows a symlink to its real
file and uses the checkout that holds it. `install.ps1` does the opposite: it
refuses a checkout that it reaches through a symlink or junction, prints a
one-line note, and takes the fetched and verified path. Run it from the real
folder, or set `APOTHEM_SOURCE`. The installers, the `apothem` command, the npm
launcher and the hooks also keep the current folder off Python's module search
path, so a file named `click.py` in the folder you work in has no effect on
them. A `python -m apothem` command you type yourself does not: `-m` reads
modules from the current folder first, so run it only from a folder you trust.

### An old `apothem` command still looks at my current folder

Earlier releases wrote an `apothem` command shim that started Python in
a way that let the current folder shadow the engine's modules. Updating does
not rewrite that shim. Run the installer (`install.sh` or `install.ps1`) again
to replace it. The uninstallers remove both the old and the new shim.

### Git Bash: my `/c/...` PYTHONPATH entries are ignored

Under Git Bash the installers usually run a Windows Python, and a Windows
Python reads `PYTHONPATH` as `;`-separated Windows paths. The sh scripts and
the `apothem` shim they write keep only the drive and network paths of your
`PYTHONPATH` for that Python, so a POSIX-style entry such as `/c/Users/me/lib`
is dropped. Write the entry as a drive path, `C:\Users\me\lib` or
`C:/Users/me/lib`, and separate entries with `;`. A POSIX Python, such as
Cygwin's or MSYS2's own `python3`, reads `:`-separated paths that start with
`/`, and the scripts keep those for it.

## Runtime issues

### apothem install finds no harnesses

Run apothem doctor to read its Harness Status table, which has one row per
harness. A row marked `not installed` means Apothem found no install for that
harness. A row marked `needs --project` is a project-scope harness, which doctor
checks only when you pass `--project <path>`. If doctor reports
`No harness is installed yet`, ensure your harness is installed, then run
`apothem install --harness <name>`.

### apothem verify reports a failing adapter

Re-run apothem install to re-materialize the adapter. If the issue persists, check the
adapter-specific page under [Harness Adapters](/docs/harnesses).

### Hooks not firing in Claude Code

Confirm Apothem is wired by checking ~/.claude/settings.json for the hook entries.
If the file is missing the hooks, run apothem install again.
