Solutions for common Apothem install and runtime issues.

## Installation issues

### No Python 3.10+ found

The installers probe `python3`, `python`, and the versioned names (`python3.14`
through `python3.10`) — rejecting Microsoft Store launcher shims — and stop with
`No Python >= 3.10 found in PATH` when no candidate meets the 3.10 floor. The
npx shim probes `APOTHEM_PYTHON` when it is set, then `python3`, `python`, and
`py -3`, and exits 1 with its own message when none qualifies. Install CPython
3.10 or newer from python.org or your OS package repository, confirm
`python3 --version` (or `py -3 --version` on Windows) reports at least 3.10,
then re-run.

### Missing runtime dependencies: click, rich

The engine vendors most of its third-party dependencies inside the source
tree, but `click` and `rich` must be importable under the interpreter the
installer selects. When either is missing, the installer names it and offers
to install it for you:

```text
! Missing Python prerequisites under <python>: click rich
  Install click rich under <python> now? [y/N]
```

Accept the prompt to have the installer run `pip install` under that
interpreter. To skip the prompt, pass `--yes` (`-Yes` on PowerShell) or set
`APOTHEM_AUTO_INSTALL_DEPS=1` to install automatically. If you decline — or
`pip` is unavailable, or you prefer your OS package manager — install the
named packages yourself (for example `python3-click` and `python3-rich` on
Debian-family hosts, or `pip install click rich`) and re-run.

### `apothem` not found after running the installer

The installer places the source tree at `~/.apothem` and writes an `apothem`
shim to `~/.local/bin` by default (POSIX) or `%LOCALAPPDATA%\Microsoft\WindowsApps`
(Windows). It does not edit your `PATH`. If `apothem` is not found, that
directory is not on `PATH`; add it, or run the shim by its full path. The
installer prints that path at completion. When it wrote no shim, it prints a
command that starts the engine with the current folder kept off `sys.path`;
copy that command from the banner. The npx form
(`npx @ahmed-g-gad/apothem <command>`) needs no `PATH` entry.

### `/plugin marketplace add` fails

`/plugin marketplace add ahmed-g-gad/apothem` fetches the marketplace
listing from GitHub. When it fails, confirm the machine can reach
`https://github.com/ahmed-g-gad/apothem` (network, proxy, or firewall
rules), then retry. If the marketplace was added earlier under a partial
fetch, remove and re-add it before running
`/plugin install apothem@apothem`.

### Adding the plugin host's marketplace times out

The plugin host's command that adds a marketplace clones its repository and
gives up after 30 seconds. A full clone of this repository can take longer on a slow
disk, such as a Windows drive under WSL, and an earlier full clone can also
leave the plugin stuck at an old version when a later refresh times out.
Fetch only the two folders the plugin needs:

```bash
codex plugin marketplace remove apothem
codex plugin marketplace add ahmed-g-gad/apothem --sparse .agents/plugins --sparse plugins/apothem
codex plugin add apothem@apothem
```

Listing the host's plugins then shows the current version of `apothem@apothem`.

### npx serves a stale version

`npx` caches downloaded packages. When `npx @ahmed-g-gad/apothem --version`
reports an older version than the current release, clear the cache or pin
the dist-tag:

```bash
npx clear-npx-cache
npx @ahmed-g-gad/apothem@latest --version
```

### The installer stops: the maintainer public key is not in the local keyring

Every network install verifies the signed release tag, with or without cosign,
and stops when the signing key is not in your keyring. Import it once, check that the fingerprint reads
`5C89 98F9 F241 7204 45D3  F28B 7039 6FED 9C63 4163`, then run the installer
again:

```bash title="macOS · Linux · WSL2 · BSD — import the key once"
curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import
gpg --fingerprint 70396FED9C634163
```

```powershell title="Windows · PowerShell — import the key once"
& "$env:ProgramFiles\Git\bin\bash.exe" -c 'curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import && gpg --fingerprint 70396FED9C634163'
```

On Windows, import through Git's `bash` as shown: `git verify-tag` reads the
keyring of the `gpg` that ships with Git for Windows. Installing
[cosign](https://docs.sigstore.dev/cosign/system_config/installation/) does
not replace the key import: with cosign on `PATH`, the installer checks the
signed release archive as well as the tag. A host without `gpg` can install
with `APOTHEM_VERIFY=checksum` and `APOTHEM_ALLOW_UNVERIFIED=1`, but that mode
does not verify the release (see
[The installer stops: checksum mode needs a second variable](#the-installer-stops-checksum-mode-needs-a-second-variable)).

### The installer stops: gpg not found

Install GnuPG, or on Windows Git for Windows, which ships the `gpg` that
`git verify-tag` runs. Then import the maintainer key as shown above and run
the installer again.

### The installer stops: the tag is not signed by the maintainer key

The message reads "carries a valid signature, but not from the maintainer
key". The tag's signature is valid, but the key that made it is not the one
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md#maintainer-signing-key)
publishes. Apothem release tags are signed only with that key, so treat this
as possible tampering: do not install, and report it through the channels in
SECURITY.md. A fork signed with its own key is expected to stop here.

### The installer stops: cosign could not confirm the release signature

Read the `cosign said:` text at the end of the message first.

- A network, proxy or trusted-root error means cosign could not reach
  Sigstore. Retry when you are online, upgrade cosign, or install with
  `APOTHEM_VERIFY=signature`, which checks the release tag against the
  maintainer key alone.
- A fork set through `APOTHEM_REPO` is expected to stop here: the installer
  accepts only Apothem's own release workflow.
- "expected GitHub Workflow SHA not found in certificate" means the
  certificate cosign verified was issued to a run on a different commit than
  the one the signed tag points at, so it does not tie `SHA256SUMS` to that
  commit. Do not install; report it through the channels in
  [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md).
- An identity or signature mismatch on Apothem's own releases means
  `SHA256SUMS` was not signed by Apothem's release workflow for this tag. Do
  not install; report it through the channels in
  [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md).

When the installer instead says it could not download the bundle, check your
connection; if the release publishes no bundle, install it with
`APOTHEM_VERIFY=signature`.

### The installer stops: the signed tag is not the release tag

The message reads "the signed tag object is not the vX.Y.Z release tag". The
tag carries the maintainer key's signature, but the object that was signed
names another tag, so a signed tag for a different release was re-pointed at
this name. Treat this as possible tampering: do not install, and report it
through the channels in
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md).
`APOTHEM_ALLOW_UNVERIFIED=1` does not bypass this check, but that variable
lets an unsigned tag, or one signed by another key, through, so the check
protects only tags that carry the maintainer key's signature.

### The installer stops: checksum mode needs a second variable

Checksum mode does not verify the release. SHA256SUMS comes from the same
release as the archive, so a match only shows the download isn't damaged;
anyone who can change the release's files can change both. For that reason
`APOTHEM_VERIFY=checksum` runs only when `APOTHEM_ALLOW_UNVERIFIED=1` is set
too. Set both if you accept that, or install `gpg` (and cosign) and run
without `APOTHEM_VERIFY=checksum`.

### The installer stops: the folder at APOTHEM_HOME is not an Apothem install

The installer does not replace a folder that holds something other than an
Apothem install. Move it aside, point `APOTHEM_HOME` at another folder, or
re-run with `--yes` (`-Yes` on PowerShell). With `--yes`, the installer moves
the whole folder, unchanged, to `<APOTHEM_HOME>.before-apothem-<time>` beside
it, says where, and installs fresh. A git clone of another project counts as
such a folder. If both `<APOTHEM_HOME>.before-apothem-<time>` and the same
name with the installer's process ID added already exist, the installer stops
with "Could not move the existing ... aside; nothing was changed" before
anything moves; rename or remove one of them and re-run.

### The installer stops: APOTHEM_HOME is a symbolic link

The message reads "is a symbolic link" (on Windows, a symbolic link or a
junction). Replacing the folder would replace the link and not the folder it
leads to, so the installer refuses. Set `APOTHEM_HOME` to the folder the link
leads to, then re-run. An existing git clone behind a link is still updated
in place.

### The installer stops: the git clone holds local work

Replacing a git clone with a release archive needs `--yes`, and the installer
refuses even then while the clone holds local work it would lose: changes to
tracked files, stashes, commits that are not on a remote, or untracked files
in the clone's source tree. Commit and push that work, or move it elsewhere,
then re-run. The check also runs with `--dry-run`. When the clone has no
such work, `--yes` replaces it and keeps the clone's own tree at
`<APOTHEM_HOME>.before-apothem-<time>`; the installer prints that path, and
you delete the folder once you no longer need it.

### The installer stops: the existing clone is set up in a way the update would trust

Before it fetches into an existing clone, the installer (and the update
script) checks how the clone is set up. "has changes to tracked files" also
appears when files are marked assume-unchanged or skip-worktree, which hides
their changes from git: run `git update-index --no-assume-unchanged <file>`
or `git update-index --no-skip-worktree <file>`, then commit or stash the
change. "is not the work tree of its git clone" means `core.worktree` is set,
or the `.git` file points at another clone: remove that setting so the clone
checks out into `APOTHEM_HOME`. "own git config sets `<key>`, which the update
would trust" names a setting in the clone's `.git/config` (`gpg.program`,
`gpg.openpgp.program`, `core.fsmonitor`, `core.hooksPath`, `include.*` or
`includeIf.*`) that makes git run a program or read other config: remove it
with `git -C ~/.apothem config --unset <key>`, then re-run. The clone's git
hooks never run during an update.

### The installer stops: the existing clone could not be updated

The installer fetches into an existing clone and checks the new tag before it
checks the clone out, so a failed check leaves the clone as it was. Two other
messages stop the update before the checkout. "Could not fetch" usually means a
local tag differs from the one on origin: delete it with
`git -C ~/.apothem tag -d <tag>` and re-run. "has changes to tracked files.
Commit or stash them, then re-run." means the clone has uncommitted changes to
files git tracks: commit or stash them, then re-run. "Could not check out"
means the checkout would still overwrite local changes. The installer never
discards local changes. For a non-release ref such as `main`, an existing
clone follows origin's copy of that branch.

### The installer or update script ends with exit code 2

The engine left a file that holds Apothem's block as it is because of its
Apothem marker lines, and wrote the rest. Its warning names the file and says
how to fix it, and the script adds one line that starts "The engine left some
files as they are (exit code 2)." The installer still runs verify, places the
`apothem` command and prints its banner, and the update script still prints
its last line. A piped PowerShell run
(`irm ... | iex`) leaves `$LASTEXITCODE` at `2` and your session open. Fix the
file as the warning says, keeping your own text (see
[A file holds two blocks between Apothem's markers](#a-file-holds-two-blocks-between-apothems-markers)
and
[Apothem cannot tell its block from your text](#apothem-cannot-tell-its-block-from-your-text)),
then run `apothem update --harness <name>` again.
[When the engine leaves a file as it is](/docs/install/updating#when-the-engine-leaves-a-file-as-it-is)
describes the whole run.

### irm / iex blocked on Windows

If PowerShell execution policy blocks the installer:

```powershell
Set-ExecutionPolicy RemoteSigned -Scope CurrentUser
irm https://apothem.ahmedgad.com/install.ps1 | iex
```

### The installer ignored the checkout in my current folder

This is intended. A piped one-liner (`curl ... | sh`, `irm ... | iex`) never
uses a local tree, and never looks in the current folder or its parent folders:
it fetches and verifies the release. To install from a checkout, run that
checkout's own `scripts/installer/install.sh` (or `install.ps1`) by its path,
from any folder (for example `sh ~/src/apothem/scripts/installer/install.sh`),
or set `APOTHEM_SOURCE` to the checkout. Give the script a path with a folder
part: `sh scripts/installer/install.sh` or `sh ./scripts/installer/install.sh`
works, but `sh install.sh` with no folder part does not count as running from a
checkout, so the installer prints "Not using a checkout: to install from one,
run this script as ./install.sh or by its full path, or set APOTHEM_SOURCE." and
fetches and verifies the release instead. A script started through `sh -c` is
not treated as a checkout either, in shells that mark `-c` runs. dash does not
mark them, so under dash `sh -c "<script>" ./install.sh` started from a
folder named `scripts/installer` inside a source tree uses that tree: start
script text that way only from a folder you trust. In the same way, a copy of
`install.sh` that you save into another source tree's `scripts/installer`
folder and run there by path becomes that tree's own installer and installs
it. Save a downloaded script to an empty folder. `install.sh`
follows a symlink to its real file and uses the checkout that holds it.
`install.ps1` does the opposite: it refuses a checkout that it reaches through a
symlink or junction, prints a one-line note, and takes the fetched and verified
path. Run it from the real folder, or set `APOTHEM_SOURCE`. The engine and the
`apothem` command also never import `click`, `rich` or `apothem` modules from
the current folder, so a file named `click.py` in the folder you work in has no
effect on them.

### An old `apothem` command still looks at my current folder

Earlier releases wrote an `apothem` command shim that started Python in
a way that let the current folder shadow the engine's modules. Updating does
not rewrite that shim. Run the installer (`install.sh` or `install.ps1`) again
to replace it. The uninstallers remove both the old and the new shim.

### Git Bash: my `/c/...` PYTHONPATH entries are ignored

Under Git Bash the installers usually run a Windows Python, and a Windows
Python reads `PYTHONPATH` as `;`-separated Windows paths. The sh scripts and
the `apothem` shim they write keep only the drive and network paths of your
`PYTHONPATH` for that Python, so a POSIX-style entry such as `/c/Users/me/lib`
is dropped. Write the entry as a drive path, `C:\Users\me\lib` or
`C:/Users/me/lib`, and separate entries with `;`. A POSIX Python, such as
Cygwin's or MSYS2's own `python3`, reads `:`-separated paths that start with
`/`, and the scripts keep those for it.

## Runtime issues

### apothem install finds no harnesses

Run apothem doctor to read its Harness Status table, which has one row per
harness. A row marked `not installed` means Apothem found no install for that
harness. A row marked `needs --project` is a project-scope harness, which doctor
checks only when you pass `--project <path>`. If doctor reports
`No harness is installed yet`, ensure your harness is installed, then run
`apothem install --harness <name>`.

### apothem verify reports a failing adapter

Re-run apothem install to re-materialize the adapter. If the issue persists, check the
adapter-specific page under [Harness Adapters](/docs/harnesses). If the install
warned about a BEGIN marker with no END, or the failed row names a file that
holds one, re-running it does not help; see
[A file has an Apothem BEGIN marker with no END marker](#a-file-has-an-apothem-begin-marker-with-no-end-marker).
If the warning or the row says a file holds two or more whole blocks between
Apothem's markers, see
[A file holds two blocks between Apothem's markers](#a-file-holds-two-blocks-between-apothems-markers).
If it says Apothem cannot tell whether the marker lines in a file mark its
block or text of yours, see
[Apothem cannot tell its block from your text](#apothem-cannot-tell-its-block-from-your-text).

### A file has an Apothem BEGIN marker with no END marker

Apothem keeps its own text in a block that runs from a
`<!-- BEGIN APOTHEM MANAGED BLOCK -->` marker to the next
`<!-- END APOTHEM MANAGED BLOCK -->` marker. If the END marker is gone (an edit
by hand or a merge that dropped the line), or a BEGIN marker of yours sits
outside a whole block, nothing shows where Apothem's text stops and yours
starts. So Apothem never cuts the text after that marker:

- `apothem install` and `apothem update` keep it as it is, write Apothem's block
  apart from it, and print a warning that names the file and the marker's
  line, with a numbered step that changes that line (see below). The warning
  also says not to add the END marker back instead: with Apothem's block
  written apart from it, the file would then hold two Apothem blocks, which
  install and update leave as they are. A dry run reads the file before
  anything is written, so when the file holds no whole block yet, its warning
  says that if you add the END marker back instead, no line of yours may sit
  between the two markers, since the next run replaces or takes out every
  line between them, and not to add it back at all once an install or update
  has written Apothem's block apart from the marker. Until then, putting it
  back right below the old Apothem text, above your own lines, leaves one
  whole block, which the next update rewrites.
- `apothem uninstall` takes out Apothem's whole block, leaves the rest as it is,
  and names the file and the marker's line, with the same numbered step: an
  install keeps the marker as it is, and the tool still reads the text below
  it.
- `apothem verify` and `apothem doctor` fail and name the file and the
  marker's line, with the same numbered step, until the stray marker is
  changed; for a file the current install writes,
  `apothem status --profile` shows drift until then too. Running
  `apothem install` again does not clear it. Only the files Apothem keeps a
  block in for that harness count, so a marker in a file of your own does not
  fail them.

While an install record lists a file that holds no whole block but a marker
pair in code, such as a marker example you quote in a code block, install,
update and uninstall leave all of that file as it is: the pair may be Apothem's
block inside a code block of yours. Their warning, like the `apothem verify` note,
names that BEGIN marker first, then each pair, and the uninstall stays
unfinished (see
[Apothem cannot tell its block from your text](#apothem-cannot-tell-its-block-from-your-text)).
With no install record, a pair you quote in code is your text, and install and
update write Apothem's block apart from the stray marker. An END marker you
quote alone in code further down, with no marker pair after it, is different:
it closes that BEGIN marker, so an update replaces the lines between the two as
Apothem's block, and an uninstall removes them.

Apothem reads a marker only as a line of its own outside code, as a Markdown
viewer would, so a marker you quote in a sentence, in a fenced code block, or
in code indented four columns past its list item (or the margin) after a blank
line is not taken for one, and neither is a BEGIN and an END marker you quote
in two separate code blocks. A code fence you leave open to the end of the file
is read as text, however many there are, unless a BEGIN marker outside code
above it has its END marker in code and another marker pair follows them.
Markers inside an HTML block or a block quote, or after a list item whose text
goes on at the left margin, can still be read differently from a Markdown
viewer.

Every line number these warnings give counts lines as Apothem reads the file:
a line ends at CRLF, at LF, or at a CR on its own. In a file saved with CR
endings, or with one stray CR inside a line, count the lines the same way
before you change the lines a warning names.

To fix it, follow the numbered step in the warning, for example
"Fix A, if lines 77 to 148 are Apothem's block: A1. Change line 3: add a word
inside its comment." Line 3 is the stray BEGIN marker: the one with no END
marker before the next BEGIN marker, or none at all. Add a word just before
its closing `-->`, as in `<!-- BEGIN APOTHEM MANAGED BLOCK (example) -->`, and
the line no longer reads as a marker. That adds and removes no line, so
nothing else in the file reads differently, and the BEGIN line that opens
Apothem's current block stays as it is. A file with two such markers gets one
step for each, from the bottom of the file up. Apothem checks the step on a
copy of the file before it prints it (see
[Follow a numbered fix](#follow-a-numbered-fix)). When no step that keeps
Apothem's block passes, the fix calls that block your text and changes every
marker line, the block's too. If the file then ends inside a code block of
yours that no line closes, the fix also adds that code block's closing line
below the last line, for example "Fix A, if lines 3 to 5 are text of yours:
A1. Below line 6, add a line of 3 backticks. A2. Change line 5: add a word
inside its comment." The next update then adds Apothem's block after it.
When that check fails too, the warning numbers no edit and says to change
every Apothem marker line in the file instead. The old Apothem text below the
marker, which repeats Apothem's rules, is then yours to keep or delete. Do not add the END marker back
instead of changing the marker line: once an install or update has written
Apothem's block apart from it, the file would then hold two Apothem blocks
(see
[A file holds two blocks between Apothem's markers](#a-file-holds-two-blocks-between-apothems-markers)).
Once you change the marker line, an END marker below it pairs with nothing.
Then run `apothem update`, which writes Apothem's block back if the file no
longer holds one, and run `apothem verify` again. A BEGIN marker whose END
marker sits in code, with another marker pair after them, gets a different
warning; see
[Apothem cannot tell its block from your text](#apothem-cannot-tell-its-block-from-your-text).

### A file holds two blocks between Apothem's markers

Apothem writes one block per file. A file can still end up with two whole
blocks: an old block whose END marker you put back after an update had written
a fresh block below it, a marker pair of yours outside code (an example you
quote, say), or a block you pasted in a second time. Apothem then cannot tell
which one is its own:

- `apothem install` and `apothem update` leave the file as it is and print a
  warning that names each block by its lines, for example "holds 2 whole
  blocks between Apothem's markers (lines 1 to 32, and lines 36 to 67)". The
  run ends as partial: in place of its `✓` line it prints a `✗` line that
  names the file, its `--format json` `status` is `"partial"`, and it exits
  with code `2`, until you fix the file. In a dry run the warning says Apothem
  "would leave the file as it is".
- `apothem verify`, with or without `--profile`, and `apothem doctor` fail and
  name the file with each block (doctor's check is `harness.stray_begin`, and
  its message says the file holds "Apothem markers to fix by hand") until you
  fix the file; for a file the current install writes,
  `apothem status --profile` shows drift until then too.
- `apothem uninstall` takes out blocks that are exact copies of each other (a
  block pasted in twice, say). When a different block would be left, it
  leaves the file as it is, prints the same warning, which ends with "then run
  the uninstall again", and stays unfinished (exit code `2`) until you fix it
  (see
  [An uninstall that did not finish](/docs/cli-reference/uninstall#an-uninstall-that-did-not-finish)).
  With no install record, it leaves Claude Code's `CLAUDE.md` or a profile
  document that holds two blocks as it is too, and its warning names each
  block the same way. That warning says to run `apothem update`, then
  `apothem uninstall` again, after the fix, and it does not stop the
  uninstall. The uninstall run then names any marker lines of yours around
  Apothem's block before it takes the block out.

The warning then gives one numbered fix for each block, for the case that
it is Apothem's block, for example "Fix A, if lines 1 to 32 are Apothem's
block: A1. Change line 67: add a word inside its comment. A2. Change line 36:
add a word inside its comment. Lines 1 to 32 are then the one block in the
file." (see [Follow a numbered fix](#follow-a-numbered-fix)). Open the named
file at the lines the warning gives:

1. Pick the fix for the block that holds Apothem's rules. In a file that
   starts with Apothem's frontmatter, that is the block right below it: an
   uninstall takes that frontmatter out only with the block right below it.
2. Do that fix's steps in the order given. Most steps change a marker line
   of another block in place, so its text stays: a marker pair of yours keeps
   your example, and the text of an older or pasted Apothem block is then
   yours to keep or delete. When the block sits in a code block of yours
   that no line closes, the fix also closes that code block above it. Each
   fix holds for the next update as well as for an uninstall. Do not delete Apothem's block to keep a pair of
   yours: the next uninstall would then take out your pair as the one block
   left. Do not move a pair of yours into a code block either: once
   Apothem's own block is no longer whole (its END marker lost, say), a
   marker pair in code keeps install and update from writing Apothem's block
   while an install record lists the file (see
   [Apothem cannot tell its block from your text](#apothem-cannot-tell-its-block-from-your-text)).
3. Run `apothem update`, then `apothem verify` again. After an uninstall that
   did not finish, run `apothem uninstall` again instead.

A BEGIN marker above Apothem's block and an END marker below it make a second
block that shows only once Apothem's block is out. The uninstall's warning then
names Apothem's block and those two marker lines, for example "once the block
from line 5 to line 36 is out, the BEGIN marker at line 2 and the END marker at
line 39 make another", and says "Do not delete the block from line 5 to line
36": the next run would then read lines 2 to 39 as Apothem's block, and replace
or take out what is between them. Its one fix changes the two marker lines it
names instead, keeping your own text, for example "Fix A, if lines 5 to 36 are
Apothem's block: A1. Change line 39: add a word inside its comment. A2. Change
line 2: add a word inside its comment."; then run the uninstall again. Do not
put both lines in one code block: it would hold Apothem's block too. If that
BEGIN marker is what is left of an older Apothem block, the old Apothem text
below it is then yours to keep or delete. When that END marker sits in code or
text of yours (an example you quote in a code block, say), the fix changes
the BEGIN marker alone. An `apothem update` does not fix such a file either,
and `apothem verify` fails until you fix it.

### Apothem cannot tell its block from your text

The warning names the file and says "Apothem cannot tell whether the marker
lines in this file mark its block or text of yours". You see it when a code
fence above Apothem's block was left open and a fence you added further down
closed it: the block then sits inside your code block. A Markdown viewer shows
those lines as code, and the same lines could be a marker pair you quote as an
example, so Apothem cannot tell whether they are its block or your text. The
same goes for a pair in indented code or indented under a paragraph, and for a
BEGIN marker outside code whose END marker sits in code while another marker
pair follows: either pair could be Apothem's block. A closing line inside
Apothem's own block can also close a code block of yours left open above it
(see below).

The warning names each marker pair in the file by the lines of its two markers
and says where they read, for example "The BEGIN marker at line 6 and the END
marker at line 38 sit inside a code block that opens at line 3." It also names
each BEGIN marker outside code that starts no marker pair, for example "The
BEGIN marker at line 1 starts no marker pair: its END marker is gone, or the
marker is yours." Then come numbered fixes, one for each case, in the warnings
of `apothem install`, `apothem update` and `apothem uninstall`, the
`apothem verify` note and the fix `apothem doctor` prints, for example "Fix A,
if lines 6 to 38 are Apothem's block: A1. Move line 39 to just above line 6.
The next update then replaces Apothem's block. Fix B, if lines 6 to 38 are text
of yours: B1. Change line 38: add a word inside its comment. B2. Change line 6:
add a word inside its comment. The next update then adds Apothem's block to the
file." See [Follow a numbered fix](#follow-a-numbered-fix) for how to read
them.

While an install record lists the file (until an uninstall finishes; an
install ledger that cannot be read counts as one; a record made under another
spelling of the folder, such as your home reached through a link, counts too,
as it does for the uninstall, when the spelling you run under has an install
of its own still in place and the tool writes the
[shared folders in your home directory](/docs/cli-reference/install#folders-in-your-home-directory)),
`apothem install` and `apothem update` change nothing in it and print that
warning; in a dry run it says Apothem "would leave the file as it is". For a
BEGIN marker outside code whose END marker sits in code with another marker
pair after them, they do so with or without a record. Each such run ends as
partial: in place of its `✓` line it prints a `✗` line that names the file,
its `--format json` `status` is `"partial"`, and it exits with code `2`. The
warning says so: "Until you fix these marker lines as this text says, install
and update leave this file as it is and end as partial (exit code 2)." The
warning of a run that wrote the file, and so ends as a success, starts that
sentence "From the next run on, until you fix these marker lines". That
lasts as long as the marker lines stay as they are, a marker
example of yours in a code block included: such a pair may be Apothem's block
inside a code block of yours, so the warning adds that your example holds the
file back the same way until you change its two marker lines, for example by
adding a word inside each comment, as in
`<!-- END APOTHEM MANAGED BLOCK (example) -->`. For a pair whose marker lines
read as part of the paragraph above them, it calls the pair "a marker example
of yours that reads as part of a paragraph". Nothing else ends it: the
uninstall does not finish while the pair is there either. A BEGIN marker outside
code that starts no pair does not change that, even when every marker pair in
the file is quoted in code below it: the marker may be what is left of
Apothem's block after its END marker was lost, but a pair in code may be
Apothem's block inside a code block of yours. The warning names such a BEGIN
marker first, and each fix changes it. The
`apothem verify` note and the fix `apothem doctor` prints give the same
sentence about ending as partial only where install and update would leave
the file as it is: with no install record, a marker pair you quote in code
does not hold the file back (see
below), unless the pair holds exactly the block the install writes. The note
and the fix do not check for that block, so for such a pair they leave that
sentence out; the next update leaves the file as it is, ends as partial and
says so.

Apothem closes a code block that a rule in your profile opens and never
closes, at the end of the block it writes, so the END marker of that block
never sits in code. A block an earlier release wrote from such a rule has no
closing line. With a marker pair of yours after it, install and update leave
the file as it is. The fix for the case that the older block is Apothem's
closes that code block above its END marker and changes the marker lines of
the pair after it, for example "Fix A, if lines 1 to 4 are Apothem's block:
A1. Change line 8: add a word inside its comment. A2. Change line 6: add a
word inside its comment. A3. Move line 5 to just above line 4."

That closing line, or the closing line of a code block a rule in your profile
writes, can also close a code block of yours that opens above Apothem's block
and never closes, at the end of your notes, say. The block then reads as code
from its BEGIN marker on. The install or update that wrote it prints the
warning at once, without saying it left the file as it is, for example "The
BEGIN marker at line 6 sits inside a code block that opens at line 3, and the
END marker at line 44 is outside code." Its fix for the case that lines 6 to
44 are Apothem's block adds the closing fence above the BEGIN marker, as in
"A1. Above line 6, add a line of 3 backticks." A dry run reads the file before
anything is written, so it does not show that the block would read as code
once written. Deleting the block instead does not help: the next update writes
it again below the same open code block. An update that writes its block below
an older block that lost its END marker, where a rule left a code block open,
gets the same warning; it also names that older BEGIN marker, and each fix
changes it.

Until you fix the file, `apothem verify` fails and `apothem doctor` reports it
(as `harness.stray_begin`); for a file the current install writes,
`apothem status --profile` shows drift too. With no install record, verify and
doctor do not check `CLAUDE.md` or the profile document: only the record shows
that the install wrote those files. The OpenClaw verify still checks the rules
file in each workspace it finds, and fails without naming the file.

With an install record, `apothem uninstall` leaves the file as it is, removes
the rest of the install, and stays unfinished (exit code `2`, a second run
included) until you fix the file: the install record stays, so a later install
still leaves the file as it is, and the next uninstall names it again. Its
warning gives numbered fixes the same way and ends with "Then run the
uninstall again.", for example "Fix A, if lines 6 to 38 are Apothem's block:
A1. Delete lines 6 to 38. The uninstall run again then finds no Apothem block
in this file." Any marker pair left in such a file keeps the uninstall
unfinished, one of yours included, so each fix changes the marker lines of
every pair it does not call Apothem's block. Its
`✗ <harness> uninstall did not finish:` line goes on "1 file(s) hold marker
lines Apothem cannot tell from your text, so Apothem left them as they are; fix
the marker lines each warning names, keeping your own text, then run apothem
uninstall again". With no install record, only a BEGIN marker outside code
whose END marker sits in code, with another marker pair after them, gets the
warning, and the uninstall stays unfinished (exit code `2`) for it and for the
paths no record shows (see
[An uninstall that did not finish](/docs/cli-reference/uninstall#an-uninstall-that-did-not-finish)).

Do every step of the fix you pick. If you delete only Apothem's block and leave
a BEGIN marker of yours above an END marker you quote in code, with no marker
pair after them, those two markers read as Apothem's block: the uninstall you
run again takes the lines between them out, and a later install or update
replaces them.

With no install record, a marker pair you quote in code is your text: the
install adds its block after it (in a rules file that Apothem writes with
frontmatter, that frontmatter and the block go at the top instead), unless the
pair holds exactly the block the install writes, and then it leaves the file
as it is and prints the warning. So if the install record is gone (the ledger
was deleted, say), delete Apothem's block from your code block by hand: a
later install treats it as your text.

To fix it, open the named file at the lines the warning gives. Decide which
case is true: whether the lines a fix names are Apothem's block, with
Apothem's rules between the markers, or an example of yours. Do the steps of
that fix, in the order given, and no other step (see
[Follow a numbered fix](#follow-a-numbered-fix)). Then run `apothem update`,
then `apothem verify` again. After an uninstall that did not finish, run
`apothem uninstall` again instead.

### Follow a numbered fix

The warnings for a file whose marker lines Apothem cannot place, for a file
with two or more whole blocks, for a BEGIN marker with no END marker, and for
Apothem's block that an uninstall with no install record leaves, give each
fix as numbered steps under a
label that names its case, for example "Fix A, if lines 6 to 38 are Apothem's
block:". The steps of fix A are "A1.", "A2." and so on, those of fix B "B1.",
"B2.", in one paragraph, and the fix ends with what the next run then does.
Do the steps of one fix only.

Every line number in a step is the line's number in the file as it is when
the warning is printed, counted as Apothem counts lines (see
[A file has an Apothem BEGIN marker with no END marker](#a-file-has-an-apothem-begin-marker-with-no-end-marker)).
The steps run from the bottom of the file up: do them in the order given, and
no step moves a line that a later step names. Each step is one of these, word
for word, and ends with a period:

| Step | What to do |
| --- | --- |
| `Change line N: add a word inside its comment.` | Add a word to line N just before its closing `-->`, as in `<!-- BEGIN APOTHEM MANAGED BLOCK (example) -->`. The line stays where it is and no longer reads as a marker. |
| `Above line N, add a copy of line K.` | Add a new line just above line N with the same text as line K. With `Below line N`, add it just below line N. |
| `Above line N, add a line of 3 backticks.` | Add a new line just above line N (with `Below line N`, just below it) that holds that many backtick characters, or tilde characters for `tildes`, and nothing else. With `, indented 2 spaces` before the period, put that many spaces before them; without it, start the line at the left margin. |
| `Move line N to just above line M.` | Cut line N and put it back just above line M. Line M is above line N. |
| `Delete lines B to E.` | Delete line B, line E and every line between them. |

Apothem checks each fix on a copy of your file before it prints it. It does
the steps in the order printed, and checks that the file then holds the one
block the fix names (or none), that the next update or uninstall then does
what the fix says, and that each line of yours that is left reads as it did
in a Markdown viewer: as text, as code, or as the line that opens or closes a
code block. It checks the next update with rules that hold a code block too.
A fix whose steps fail that check is left out. When no fix passes,
the warning says "Apothem has no step-by-step fix it could check for this
file" and gives no numbered step: change every Apothem marker line in the file
instead, by adding a word inside each comment. That adds and removes no line,
so nothing else in the file reads differently; old Apothem text between those
lines is then yours to delete.

A code block of yours that no line closes runs to the end of the file in a
Markdown viewer, but Apothem reads its opening line as text. A code block in
your profile's rules would close it, and the BEGIN marker of Apothem's block
would then read as code. So when your file ends inside such a code block, a
fix that leaves no Apothem block in the file also adds that code block's
closing line below the last line, as in "B1. Below line 7, add a line of 3
backticks.": the next install or update adds its block at the end of the
file. A fix that keeps a block inside such a code block adds a closing line
above the block's BEGIN marker and, when lines of yours follow its END
marker, a copy of the opening line below it.

### Hooks not firing in Claude Code

Confirm Apothem is wired by checking ~/.claude/settings.json for the hook entries.
If the file is missing the hooks, run apothem install again.

### OpenCode does not load the Apothem rules

`apothem install`, `apothem update` and `apothem verify` print a note when a
file of yours in OpenCode's configuration folder keeps OpenCode 1 from loading
the `instructions` list Apothem writes in `opencode.json`:

- An `opencode.jsonc` with its own `instructions` list, even an empty one,
  replaces Apothem's list. Remove that key, or move its entries into the list
  in `opencode.json`, where installs keep the entries they did not write.
- A `config.json`, `opencode.json` or `opencode.jsonc` there that OpenCode 1
  cannot read or parse stops OpenCode 1 from loading any of its configuration.
  So does one whose top level is not an object, whose `instructions` value is
  not a list of text, or whose `{file:path}` names a file OpenCode 1 cannot
  read, and a folder with one of those names. Correct the file so it is one
  JSON object with only comments and trailing commas added, with `instructions`
  as a list of text, or move it out of the folder. When the note says the file
  breaks once OpenCode 1 puts in its `{env:NAME}` values, change that variable
  so its value holds no backslash, double quote or control character, for
  example a Windows path written with forward slashes. When the note says
  Apothem writes that `{env:NAME}` for an MCP server in your profile, an update
  writes back a reference removed from the file, so change the variable or, to
  keep it as it is, restate that server under
  `harnesses.opencode.mcp_servers.<name>` with the value saved in a file and
  written as a `{file:path}` that names it. When the note names a second
  problem with the file, fix that too. When it says Apothem cannot tell
  whether OpenCode 1 can read the file a `{file:path}` names, make sure that
  file can be read as well.

These notes are about OpenCode 1. OpenCode 2 reads both lists and reads no
`config.json`. It skips a file it cannot parse or whose top level is not an
object, which for `opencode.json` means it misses the rules too; a note says
what OpenCode 2 does with its file when that is known. The notes change no file
and no exit code. When install or update cannot parse `opencode.json` at all,
they stop with a `config.unparseable` error instead. See
[OpenCode](/docs/harnesses/opencode) for the details.
