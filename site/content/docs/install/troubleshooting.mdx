Solutions for common Apothem install and runtime issues.

## Installation issues

### No Python 3.10+ found

The installers probe `python3`, `python`, and the versioned names (`python3.14`
through `python3.10`) — rejecting Microsoft Store launcher shims — and stop with
`No Python >= 3.10 found in PATH` when no candidate meets the 3.10 floor. The
npx shim probes `APOTHEM_PYTHON` when it is set, then `python3`, `python`, and
`py -3`, and exits 1 with its own message when none qualifies. Install CPython
3.10 or newer from python.org or your OS package repository, confirm
`python3 --version` (or `py -3 --version` on Windows) reports at least 3.10,
then re-run.

### Missing runtime dependencies: click, rich

The engine vendors most of its third-party dependencies inside the source
tree, but `click` and `rich` must be importable under the interpreter the
installer selects. When either is missing, the installer names it and offers
to install it for you:

```text
! Missing Python prerequisites under <python>: click rich
  Install click rich under <python> now? [y/N]
```

Accept the prompt to have the installer run `pip install` under that
interpreter. To skip the prompt, pass `--yes` (`-Yes` on PowerShell) or set
`APOTHEM_AUTO_INSTALL_DEPS=1` to install automatically. If you decline — or
`pip` is unavailable, or you prefer your OS package manager — install the
named packages yourself (for example `python3-click` and `python3-rich` on
Debian-family hosts, or `pip install click rich`) and re-run.

### `apothem` not found after running the installer

The installer places the source tree at `~/.apothem` and writes an `apothem`
shim to `~/.local/bin` by default (POSIX) or
`%LOCALAPPDATA%\Microsoft\WindowsApps` (Windows); `APOTHEM_BIN_DIR` changes the
folder. It does not edit your `PATH`. If `apothem` is not found, that directory
is not on `PATH`; add it, or run the shim by its full path. The installer prints
that path at completion. When it wrote no shim, it prints a command that starts
the engine with the current folder kept off `sys.path`; copy that command from
the banner. The npx form (`npx @ahmed-g-gad/apothem <command>`) needs no `PATH`
entry.

### `/plugin marketplace add` fails

`/plugin marketplace add ahmed-g-gad/apothem` fetches the marketplace
listing from GitHub. When it fails, confirm the machine can reach
`https://github.com/ahmed-g-gad/apothem` (network, proxy, or firewall
rules), then retry. If the marketplace was added earlier under a partial
fetch, remove and re-add it before running
`/plugin install apothem@apothem`.

### Adding the plugin host's marketplace times out

The plugin host's command that adds a marketplace clones its repository and
gives up after 30 seconds. A full clone of this repository can take longer on a slow
disk, such as a Windows drive under WSL, and an earlier full clone can also
leave the plugin stuck at an old version when a later refresh times out.
Fetch only the two folders the plugin needs:

```bash
codex plugin marketplace remove apothem
codex plugin marketplace add ahmed-g-gad/apothem --sparse .agents/plugins --sparse plugins/apothem
codex plugin add apothem@apothem
```

Listing the host's plugins then shows the current version of `apothem@apothem`.

### npx serves a stale version

`npx` caches downloaded packages. When `npx @ahmed-g-gad/apothem --version`
reports an older version than the current release, clear the cache or pin
the dist-tag:

```bash
npx clear-npx-cache
npx @ahmed-g-gad/apothem@latest --version
```

### The installer stops: the maintainer public key is not in the local keyring

Every network install verifies the signed release tag, with or without cosign,
and stops when the signing key is not in your keyring. Import it once, check that the fingerprint reads
`5C89 98F9 F241 7204 45D3  F28B 7039 6FED 9C63 4163`, then run the installer
again:

```bash title="macOS · Linux · WSL2 · BSD — import the key once"
curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import
gpg --fingerprint 70396FED9C634163
```

```powershell title="Windows · PowerShell — import the key once"
& "$env:ProgramFiles\Git\bin\bash.exe" -c 'curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import && gpg --fingerprint 70396FED9C634163'
```

On Windows, import through Git's `bash` as shown: `git verify-tag` reads the
keyring of the `gpg` that ships with Git for Windows. Installing
[cosign](https://docs.sigstore.dev/cosign/system_config/installation/) does
not replace the key import: with cosign on `PATH`, the installer checks the
signed release archive as well as the tag. A host without `gpg` can install
with `APOTHEM_VERIFY=checksum` and `APOTHEM_ALLOW_UNVERIFIED=1`, but that mode
does not verify the release (see
[The installer stops: checksum mode needs a second variable](#the-installer-stops-checksum-mode-needs-a-second-variable)).

### The installer stops: gpg not found

Install GnuPG, or on Windows Git for Windows, which ships the `gpg` that
`git verify-tag` runs. Then import the maintainer key as shown above and run
the installer again.

### The installer stops: the tag is not signed by the maintainer key

The message reads "Tag ... is signed by the key ..." and names the key that
signed it. The tag's signature is valid, but that key is not the one
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md#maintainer-signing-key)
publishes. Apothem release tags are signed only with that key, so treat this as
possible tampering: do not install, and report it through the channels in
SECURITY.md. A fork signed with its own key is expected to stop here.

### The installer stops: cosign could not confirm the release signature

Read the `cosign said:` text at the end of the message first.

- A network, proxy or trusted-root error means cosign could not reach
  Sigstore. Retry when you are online, upgrade cosign, or install with
  `APOTHEM_VERIFY=signature`, which checks the release tag against the
  maintainer key alone.
- A fork set through `APOTHEM_REPO` is expected to stop here: the installer
  accepts only Apothem's own release workflow.
- "expected GitHub Workflow SHA not found in certificate" means the
  certificate cosign verified was issued to a run on a different commit than
  the one the signed tag points at, so it does not tie `SHA256SUMS` to that
  commit. Do not install; report it through the channels in
  [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md).
- An identity or signature mismatch on Apothem's own releases means
  `SHA256SUMS` was not signed by Apothem's release workflow for this tag. Do
  not install; report it through the channels in
  [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md).

When the installer instead says it could not download the bundle, check your
connection; if the release publishes no bundle, install it with
`APOTHEM_VERIFY=signature`.

### The installer stops: the signed tag is not the release tag

The message reads "the signed tag object is not the vX.Y.Z release tag". The
tag carries the maintainer key's signature, but the object that was signed
names another tag, so a signed tag for a different release was re-pointed at
this name. Treat this as possible tampering: do not install, and report it
through the channels in
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md).
`APOTHEM_ALLOW_UNVERIFIED=1` does not bypass this check, but that variable
lets an unsigned tag, or one signed by another key, through, so the check
protects only tags that carry the maintainer key's signature.

### The installer stops: checksum mode needs a second variable

Checksum mode does not verify the release. SHA256SUMS comes from the same
release as the archive, so a match only shows the download isn't damaged;
anyone who can change the release's files can change both. For that reason
`APOTHEM_VERIFY=checksum` runs only when `APOTHEM_ALLOW_UNVERIFIED=1` is set
too. Set both if you accept that, or install `gpg` (and cosign) and run
without `APOTHEM_VERIFY=checksum`.

### The installer stops: the folder at APOTHEM_HOME is not an Apothem install

The installer does not replace a folder that holds something other than an
Apothem install. Move it aside, point `APOTHEM_HOME` at another folder, or
re-run with `--yes` (`-Yes` on PowerShell). With `--yes`, the installer moves
the whole folder, unchanged, into a new folder,
`<APOTHEM_HOME>.before-apothem-<time>`, beside it (it keeps its own name
inside), says where, and installs fresh. A git clone of another project counts
as such a folder. If both `<APOTHEM_HOME>.before-apothem-<time>` and the same
name with the installer's process ID added already exist, the installer stops
with "Could not move the existing ... aside; nothing was changed" before
anything moves; rename or remove one of them and re-run.

### The installer stops: APOTHEM_HOME is a symbolic link

The message reads "is a symbolic link" (on Windows, a symbolic link or a
junction). Replacing the folder would replace the link and not the folder it
leads to, so the installer refuses. Set `APOTHEM_HOME` to the folder the link
leads to, then re-run. An existing git clone behind a link is still updated
in place.

### The installer stops: the git clone holds local work

Replacing a git clone with a release archive needs `--yes`, and the installer
refuses even then while the clone holds local work it would lose: changes to
tracked files, stashes, commits that are not on a remote, or untracked files
in the clone's source tree. Commit and push that work, or move it elsewhere,
then re-run. The check also runs with `--dry-run`. When the clone has no
such work, `--yes` replaces it and keeps the clone's own tree at
`<APOTHEM_HOME>.before-apothem-<time>/<name>`, where `<name>` is the last part
of `APOTHEM_HOME`; the installer prints that path, and you delete the folder
once you no longer need it.

### The installer stops: the existing clone is set up in a way the update would trust

Before it fetches into an existing clone, the installer (and the update script)
checks how the clone is set up. `--dry-run` makes these checks too. "has
changes to tracked files" also appears when files are marked assume-unchanged
or skip-worktree, which hides their changes from git: run
`git update-index --no-assume-unchanged <file>` or
`git update-index --no-skip-worktree <file>`, then commit or stash the change.
"is not the work tree of its git clone" means git finds no work tree in
`APOTHEM_HOME`, as when the clone's git config sets `core.bare` to `true`: set
it to `false` so the clone checks out into `APOTHEM_HOME`. A `core.worktree`
setting, which would send the checkout to another folder, is reported as a
setting an update in place does not accept (below).

"own git config sets `<key>`, which an update in place does not accept in a
clone's own config" names a setting in the clone's `.git/config`, or in
`.git/config.worktree` when the clone has one. An update in place accepts only
these settings there (the section and the key compare without regard to case):

- the settings `git clone` and `git init` write for a full clone:
  `core.repositoryformatversion`, `core.filemode`, `core.bare`,
  `core.logallrefupdates`, `core.symlinks`, `core.ignorecase`,
  `core.precomposeunicode`, `core.longpaths`, `extensions.objectformat`,
  `extensions.refstorage` (only with the value `files` or `reftable`),
  `extensions.worktreeconfig`, `remote.origin.url`, `remote.origin.fetch` and
  `remote.origin.tagopt`;
- branch settings, `branch.<name>.<key>`, which git and editors add, except
  that `branch.<name>.remote` and `branch.<name>.pushremote` must be exactly
  `origin`;
- `user.name`, `user.email`, `maintenance.auto`, `maintenance.strategy`,
  `pull.rebase` and `pull.ff`.

Any other setting stops the update, because it could make git run a program,
read settings, hooks, attributes or objects from another place, or connect
somewhere else. A clone made with `--mirror`, `--sparse`,
`--recurse-submodules` or a remote not named `origin` stops here too, and so
does a partial clone, made with `--filter`: the message names
`remote.origin.promisor`, because git would fetch missing objects from the
remote on its own while it reads the clone. Clone again without `--filter`.
Remove the setting from the file the message names, for example
`git config --file ~/.apothem/.git/config --unset-all <key>`, then re-run.
`--unset-all` also removes a setting that is there more than once. For a
branch's `remote` or `pushremote`, set it to `origin` instead, for example
`git config --file ~/.apothem/.git/config branch.main.remote origin`. "own git
attributes name a filter or diff driver" names `.git/info/attributes`: remove
the `filter=` or `diff=` setting. git runs a filter while it reads files, and
`git diff` runs a diff driver's text conversion (`textconv`), so a driver your
own or the system's git config defines would run on the clone's files.

"which is not a plain file" names `.git/info/attributes`, `.git/config` or
`.git/config.worktree` when it is a folder, a named pipe or another special
file, or, on Windows, a link. git could read other text from such a file than
the check reads. Replace it with a plain file, or remove it, then re-run.

"has a setting whose name holds a line break" means a section name in the file
the message names holds a carriage return. git never writes one, and a reader
could take that name for two settings. Open the file in a text editor, remove
that section, then re-run.

"borrows objects from another repository" means the clone has an
`objects/info/alternates` or `objects/info/http-alternates` file, as a clone
made with `--reference` or `--shared` does. git would then read objects from
that other repository, under settings the installer does not check. Run
`git -C ~/.apothem repack -a -d` to copy the objects into the clone, remove the
file the message names, then re-run.

"keeps submodule repositories in ..." and "holds a submodule at ..." mean the
clone has a submodule, kept in the folder the first message names or recorded
in its index at the path the second one names. A release tree has none, and
git would run inside the submodule, whose own settings the installer does not
check. Remove the submodule and that folder from the clone, or move the clone
aside, then re-run. Replacing the clone with `--yes` makes this check too,
before `git status` looks for local work. The clone's git hooks never run
during an update.

### The installer stops: a .gitattributes file in the clone is untracked, changed or names a driver

git applies the `.gitattributes` files in the work tree while it compares and
checks out files, and such a file can make git run a program. Before any of
those commands, the installer and the update script stop on a `.gitattributes`
file that is not the committed one, in any folder of the clone and with any
mix of capital letters in its name, and on a git repository in the clone
that git does not track, since git would read the `.gitattributes` files in
it too. `--dry-run` and `--yes` make this check too. It does not read the
engine's own data folders (`backups`, `state`, `plans`, `memory`,
`contexts`, `learning` and `providers`), where no release writes, unless the
clone tracks files there.

- "has a .gitattributes file that git does not track, at ..." names a file git
  does not track, ignored files and files in untracked folders included.
  Remove it, then re-run.
- "has a changed .gitattributes file at ..." names a tracked file whose content
  differs from the committed copy, whose change is staged, or which is a link
  or a folder. If you made the change, put back the committed copy, for
  example with `git -C ~/.apothem checkout HEAD -- <path>`, then re-run.
- "has a .gitattributes file at ... that names a filter or diff driver
  (filter= or diff=)" names a tracked file whose committed copy, or the copy
  in the work tree, names one outside a comment, a macro (`[attr]` line) that
  names one included. git would run that driver, which your own or the
  system's git config may define, while it reads the clone. Remove the
  setting, commit that change, then re-run. A macro that only your own or the
  system's attributes file defines does not count: during the run git reads
  no attributes file outside the clone, so such a macro names no driver there.
- "has a .gitattributes file at ... whose committed copy git could not read"
  means the copy in the clone's git folder is missing or damaged, or its bytes
  do not match its ID, which git does not check as it reads them. The
  installer then cannot check what the file says, while git would still apply
  the copy in the work tree. Run `git -C ~/.apothem fsck` to see what is
  damaged, repair the clone or move it aside and install fresh, then re-run.
- "Could not run git to read the committed .gitattributes files in ..." comes
  from `install.ps1` and `update.ps1` only. In your PowerShell session `git`
  is a function or a script, for example a wrapper in your profile, and no
  git program is on `PATH` for the installer to read the files with. Add
  git's folder to `PATH`, so that `Get-Command git -CommandType Application`
  finds it, then re-run.
- "holds a git repository that git does not track, at ..." names a folder with
  a `.git` of its own. git lists nothing inside such a folder, so a
  `.gitattributes` file there goes unseen, yet git applies it to the files an
  update writes there. A release tree has none. Move the folder out of the
  clone, then re-run.

If you did not make the file or the change, someone else could write to the
clone: move it aside, install fresh, and make sure `APOTHEM_HOME` is a folder
only you can write.

### The installer stops: files under src that git does not track

The message reads "has files under src that git does not track, and the engine
could load them:" and lists each one (the first 20, then how many more). The
engine runs from the clone's `src` folder, so an extra file there could run as
part of it. Ignored files count, and so does a `.pyc` file beside the sources.
A folder named `Src` or `SRC` counts as `src`, since Windows and macOS find
it under that name.
An editable `pip install` of the clone writes `src/apothem.egg-info`, and a file
manager can write `.DS_Store` or `desktop.ini`. Move the files out of
`~/.apothem/src`, then re-run; nothing was changed. The check runs before the
fetch, in an update in place and in a dry run. Python's cache folders
(`__pycache__`) do not count: after the checkout, and before the engine first
runs from the clone, the update removes every `__pycache__` folder under `src`,
so no cached bytecode from before the update loads.

"Could not remove the Python cache folders (__pycache__) under ..." means that
removal failed, for example because a file in one of them belongs to another
user or, on Windows, is open in another program. The clone is already checked
out to the new release. Remove those folders yourself, then re-run.

### The installer stops: another run holds the lock

Each run of the install, update and uninstall scripts holds a lock beside
`APOTHEM_HOME` (`<APOTHEM_HOME>.lock`, so `~/.apothem.lock` by default) while
it runs; the `apothem install`, `apothem update` and `apothem uninstall`
commands do not take it. The message "Another Apothem install, update or
uninstall is running on ..." means a second run found it held. Wait for the
other run to finish, then re-run. If none is running, remove the lock the
message names, then re-run.

- "was left by an Apothem run that did not finish (process N is no longer
  running)" and "exists but names no running process" mean a run was killed
  before it could release the lock. Check that no Apothem install, update or
  uninstall is running, remove the lock, and re-run. The installer never
  removes it for you. On POSIX the lock is a folder (`rm -rf ~/.apothem.lock`);
  on Windows PowerShell it is a file that Windows deletes when its run ends.
- "is the lock file of an Apothem PowerShell run" comes from a POSIX script
  under Git Bash, MSYS2, Cygwin or WSL that found the file a PowerShell run
  holds. Windows removes that file when the run ends and lets no one remove it
  while the run is active. Wait for that run to finish. If no Apothem install,
  update or uninstall is running, remove the file, then re-run. On other
  systems the message reads "is a file where the Apothem lock folder belongs":
  remove the file if no run is active, then re-run.
- "was made by an Apothem run in another environment" means the lock folder
  names a process in another environment, such as WSL when the run is under
  Git Bash, Git Bash when it is under WSL or MSYS2, or another container.
  That process cannot be checked from here. Wait for that run to finish;
  remove the lock only if no Apothem install, update or uninstall is running
  anywhere.
- The POSIX scripts count a process that belongs to another user, such as a
  run under `sudo`, as running, so its lock reads as held. PowerShell cannot
  check the process ID of a lock folder made by the POSIX scripts (for example
  under Git Bash), so it reports that lock as held too.
- When `APOTHEM_HOME` is a symbolic link (or, on Windows, a junction), the
  POSIX and the PowerShell scripts take the lock beside the folder the link
  leads to, so a run through the link and a run through that folder stop each
  other; the message names that lock.
- "Could not create the lock ... Check that you can write to ..." means you
  cannot write to the folder the message names: the one that holds
  `APOTHEM_HOME` or, when `APOTHEM_HOME` is a link, the one that holds the
  folder it leads to. Every run
  needs to write there, an update in place, an uninstall and a dry run
  included.

### The installer stops: an earlier run left folders beside APOTHEM_HOME

The message reads "An earlier run was stopped part-way and left these
folders beside ..." and lists each folder with what it holds. Ctrl+C and a
termination signal are caught and the run cleans up; a forced kill or a
power loss during a swap is not, and can leave:

- `.apothem-old.<name>.*`: the earlier install that was being replaced, in its
  `home` folder. When that `home` folder holds a git clone and `APOTHEM_HOME`
  is in place (as it is once the new install has moved in), the line says
  instead that it holds the clone's tree, which that run was keeping: move it
  to a folder of your own if you still need it. When the `home` folder holds
  no Apothem install and `APOTHEM_HOME` is in place, the line says so: a folder
  appeared there while the run was moving the earlier install, the run put the
  install back and left that folder alone. Check what it holds before you
  remove it.
- `.apothem-extract.<name>.*` or `.apothem-clone.<name>.*`: the new source
  that was being installed. When the run had already moved entries of
  `APOTHEM_HOME` into it, the line names every one: engine data such as
  `backups` and `state`, and any other file or folder that was there.
- `<APOTHEM_HOME>.before-apothem-<time>`: listed only when `APOTHEM_HOME`
  itself is missing. It holds the earlier contents of `APOTHEM_HOME`, in a
  folder named after the last part of `APOTHEM_HOME`, or directly inside it
  for a folder an earlier installer made; the line says which.

`<name>` is the last part of `APOTHEM_HOME` (`.apothem` by default), so the
folders of another `APOTHEM_HOME` in the same parent folder, which a run on
that home may be using, are not listed. On Windows and macOS a `<name>` that
differs only in capital letters counts as this home's, because `APP` and
`app` name the same folder there by default. The rule follows the operating
system, not the file system: under WSL, even on a Windows drive, names that
differ in capitals are different homes, while on a case-sensitive macOS volume
or Windows folder they still count as one, so another home there whose name
differs only in capitals is listed too. A folder whose name has no `<name>` part was made by
an earlier installer that did not record the home; it is listed with a note
that it may belong to any Apothem home in that folder, and its line says the
entries were moved from the home it was made for. For such a folder made by
a clone install, the line names only the engine data it finds, so look inside
for anything else. Only folders count: a file or a link with such a name is
not listed. A folder the installer cannot read is listed as "could not be
read".

Nothing was changed and nothing is deleted. If `APOTHEM_HOME` is missing,
move the earlier install back to it first. Then move every entry the list
names as moved into a new source back into the home it came from (check
which home first for a folder with the note), remove the listed folders, and
re-run. The check runs for a fetched install, a dry run included; it does not
run for an install from your own checkout, nor for an update or an uninstall.

### The installer stops: another user owns the clone

The message reads "is owned by someone else, so git refuses to work in it
(git reports "dubious ownership")". git will not read a clone that another
user owns. Run the installer as the user who owns `APOTHEM_HOME`, take
ownership of the folder, or point `APOTHEM_HOME` at a folder you own, then
re-run. The installer does not add the folder to git's `safe.directory`
list. Any other failure of that first git command reads "git could not read
the clone at ..." followed by git's own first line of explanation.

### The installer warns: other users can change APOTHEM_HOME

The install and update scripts, dry runs included, warn when users other
than you can write to `APOTHEM_HOME` or the folder that holds it, or own
either, since they can then change the code the `apothem` command runs as
you; the runs that skip the check are listed below. The run goes on; the
warning names the folder, who can write to it or owns it, and the fix. The
warning starts with one of:

- "Other users can change the code Apothem runs as you", when they can write
  to `APOTHEM_HOME`, or when `APOTHEM_HOME` or the folder that holds it
  belongs to someone else (the message then says who owns which folder).
  When `APOTHEM_HOME` is a link, the message names the folder it leads to.
- "Other users can replace ...", when they can write to the folder that holds
  `APOTHEM_HOME` (or holds the link to it), and so rename or remove it.
- "A new ... would let", when `APOTHEM_HOME` does not exist yet and a new
  folder there would be open to others.

An install from a local checkout is not checked, whether `APOTHEM_SOURCE`
names it or you run that checkout's own `scripts/installer/install.sh` or
`install.ps1`. The update scripts skip the check only when `APOTHEM_SOURCE` is
set. If the warning names a group that you share on purpose with people you trust to
change the code, you can ignore it.

The check reads the permissions of `APOTHEM_HOME` and of the folder that
holds it, not of each file inside.

On Linux and macOS, the warning names "all users" or "the group" it found in
the folder's permission bits, and each user or group an access list (ACL)
lets write, which it reads with `getfacl` where that is installed. With an
access list, the group bits that `ls` shows are the list's mask, so where
`getfacl` lists the group's own entry (`group::`), that entry decides
whether the group is named; without `getfacl`, the group named may be one
the mask lets write but its own entry does not. The warning never names
you, the user root, or a group with your own user name (your own group). A
name that `getfacl` writes with escapes, such as a domain account's
`CORP\alice`, counts as the name it stands for. To fix it, run the command
the message gives (on Linux it also takes write access away from each user
and group the access list names):

```bash
chmod go-w "$HOME/.apothem"
```

Files made under the same settings can be writable too: `chmod -R go-w` on
the folder fixes those as well. If others need to write to the folder that
holds `APOTHEM_HOME`, as with `/tmp`, set its sticky bit with `chmod +t` so
they cannot rename or remove what you put there, or move `APOTHEM_HOME`. For
a new install, the warning reports your umask: run `umask 022` and run the
installer again. On WSL, keep `APOTHEM_HOME` in your Linux home, not under
`/mnt/c`, where every file looks writable by all users.

When the message says a user "owns" the folder, that user can change it
whatever its permissions say, and only root can make you its owner. A
folder root owns is fine. Move `APOTHEM_HOME` into a folder you own.

On Windows, the warning names each account or group that a permission entry
lets change the folder, as the folder's Security tab names it: Users,
Authenticated Users, Everyone, INTERACTIVE (everyone signed in at the
computer or over Remote Desktop, who can change what is made in
`C:\Users\Public`), Guests, or a group your organization or another program
made. It never names you, your own sign-in session, SYSTEM, Administrators,
TrustedInstaller, CREATOR OWNER or OWNER RIGHTS; the last two stand for
whoever makes or owns an item, and an owner who is someone else gets a
message of its own. When the folder belongs to another account, the message
says so and asks you to move `APOTHEM_HOME` into your user folder. When the
message adds "access that folders made at the root of a drive inherit from
the drive's default permissions", the folder sits at the root of a drive,
such as `C:\apothem`: Windows lets every user who signs in add and change
folders made there. The simplest fix is to move `APOTHEM_HOME` into your user
folder (`%USERPROFILE%`), as the default `~\.apothem` is. To keep the folder
where it is, turn off inheritance, give yourself full control, then remove
the groups the warning names. For a folder at the root of a drive, that is
Authenticated Users on Windows 10 and 11 and Users on Windows Server; the
commands below remove both:

```powershell
icacls "C:\apothem" /inheritance:d
icacls "C:\apothem" /grant:r "${env:USERNAME}:(OI)(CI)F"
icacls "C:\apothem" /remove:g *S-1-5-11 *S-1-5-32-545 *S-1-1-0 *S-1-5-4
```

Give yourself access before you remove the groups: the entry you remove can
be your only way to write to the folder. The `*S-...` names are the groups'
security IDs (Authenticated Users, Users, Everyone and INTERACTIVE), which
work in every Windows language. Remove any other name the warning gives on
an `icacls` line of its own, in quotes: a name `icacls` cannot find stops
the whole line, which then removes nothing and still prints "Successfully
processed 0 files". A name made of `S-` and numbers is the security ID of
an account Windows cannot look up, such as a deleted account or another
sign-in session: put `*` before it, and if `icacls` still removes nothing,
remove it in the folder's Properties > Security > Advanced. You can make
every change there too. When the warning is about the folder that holds
`APOTHEM_HOME`, make the change there, or move `APOTHEM_HOME`. A link or
junction at `APOTHEM_HOME` takes its permissions from that folder, so
others who can change the folder can delete the link and make their own.

`install.sh` and `update.sh` do not check under Git Bash, MSYS2 or Cygwin,
where the permission bits are made up from Windows permissions, so they give
no warning there. On Windows, run `install.ps1` or `update.ps1`, which read
the Windows permissions, to have the folder checked.

### The installer stops: the existing clone could not be updated

The installer fetches into an existing clone and checks the new tag before it
checks the clone out, so a failed check leaves the clone as it was. Two other
messages stop the update before the checkout. "Could not fetch" usually means a
local tag differs from the one on origin: delete it with
`git -C ~/.apothem tag -d <tag>` and re-run. "has changes to tracked files.
Commit or stash them, then re-run." means the clone has uncommitted changes to
files git tracks: commit or stash them, then re-run. A dry run does not check
for ordinary uncommitted changes, since it does not fetch into the clone, but
it stops with the same message when files are marked assume-unchanged or
skip-worktree (see the clone setup section above). "Could not check out"
means the checkout would still overwrite local changes. The installer never
discards local changes. For a non-release ref such as `main`, an existing
clone follows origin's copy of that branch.

### The installer or update script ends with exit code 2

The engine ended as partial. Either it left a file that holds Apothem's block
as it is because of its Apothem marker lines, and wrote the rest, or it
stopped after it had written something, for example when one tool failed
after an earlier one in an `APOTHEM_HARNESS=all` run. Its messages name the
file, or show the error that stopped it, and the script adds one line that
starts "The engine ended as partial (exit code 2)." The installer still runs
verify, places the `apothem` command and prints its banner, and the update
script still prints its last line. A piped PowerShell run
(`irm ... | iex`) leaves `$LASTEXITCODE` at `2` and your session open. A
one-shot
`pwsh -Command "irm ... | iex"` (or `powershell -c`) reports a partial run
only through `$LASTEXITCODE` and exits `0`: to get exit code `2` from the
process, end the command with `; exit $LASTEXITCODE`, or run the script by
path with `-File`. From PowerShell, bash or another POSIX shell, put that
command in single quotes. In double quotes the calling shell puts in its own
`$LASTEXITCODE` before the new process starts (a POSIX shell puts in an empty
string), so the process does not exit with the run's code. From cmd.exe,
double quotes are fine. A dry run writes nothing, so
it does not end as partial.
Fix what the messages name. For a file, keep your own text (see
[A file holds two blocks between Apothem's markers](#a-file-holds-two-blocks-between-apothems-markers)
and
[Apothem cannot tell its block from your text](#apothem-cannot-tell-its-block-from-your-text)),
then run `apothem update --harness <name>` again for each tool the run left
unfinished.
[When the engine leaves a file as it is](/docs/install/updating#when-the-engine-leaves-a-file-as-it-is)
describes the whole run.

### irm / iex blocked on Windows

If PowerShell execution policy blocks the installer:

```powershell
Set-ExecutionPolicy RemoteSigned -Scope CurrentUser
irm https://apothem.ahmedgad.com/install.ps1 | iex
```

### The installer ignored the checkout in my current folder

This is intended. A piped one-liner (`curl ... | sh`, `irm ... | iex`) never
uses a local tree, and never looks in the current folder or its parent folders:
it fetches and verifies the release. To install from a checkout, run that
checkout's own `scripts/installer/install.sh` (or `install.ps1`) by its path,
from any folder (for example `sh ~/src/apothem/scripts/installer/install.sh`),
or set `APOTHEM_SOURCE` to the checkout. Give the script a path with a folder
part: `sh scripts/installer/install.sh` or `sh ./scripts/installer/install.sh`
works, but `sh install.sh` with no folder part does not count as running from a
checkout, so the installer prints "Not using a checkout: to install from one,
run this script as ./install.sh or by its full path, or set APOTHEM_SOURCE." and
fetches and verifies the release instead. A script started through `sh -c` is
not treated as a checkout either, in shells that mark `-c` runs. dash does not
mark them, so under dash `sh -c "<script>" ./install.sh` started from a folder
named `scripts/installer` inside a source tree uses that tree: start script text
that way only from a folder you trust. In the same way, a copy of `install.sh`
that you save into another source tree's `scripts/installer` folder and run
there by path becomes that tree's own installer and installs it. Save a
downloaded script to an empty folder. `install.sh` follows a symlink to its real
file and uses the checkout that holds it. `install.ps1` does the opposite: it
refuses a checkout that it reaches through a symlink or junction, prints a
one-line note, and takes the fetched and verified path. Run it from the real
folder, or set `APOTHEM_SOURCE`. The installers, the `apothem` command, the npm
launcher and the hooks also keep the current folder off Python's module search
path, so a file named `click.py` in the folder you work in has no effect on
them. A `python -m apothem` command you type yourself does not: `-m` reads
modules from the current folder first, so run it only from a folder you trust.

### An old `apothem` command still looks at my current folder

Earlier releases wrote an `apothem` command shim that started Python in
a way that let the current folder shadow the engine's modules. Updating does
not rewrite that shim. Run the installer (`install.sh` or `install.ps1`) again
to replace it. The uninstallers remove both the old and the new shim.

### Git Bash: my `/c/...` PYTHONPATH entries are ignored

Under Git Bash the installers usually run a Windows Python, and a Windows
Python reads `PYTHONPATH` as `;`-separated Windows paths. The sh scripts and
the `apothem` shim they write keep only the drive and network paths of your
`PYTHONPATH` for that Python, so a POSIX-style entry such as `/c/Users/me/lib`
is dropped. Write the entry as a drive path, `C:\Users\me\lib` or
`C:/Users/me/lib`, and separate entries with `;`. A POSIX Python, such as
Cygwin's or MSYS2's own `python3`, reads `:`-separated paths that start with
`/`, and the scripts keep those for it.

## Runtime issues

### apothem install finds no harnesses

Run apothem doctor to read its Harness Status table, which has one row per
harness. A row marked `not installed` means Apothem found no install for that
harness. A row marked `needs --project` is a project-scope harness, which doctor
checks only when you pass `--project <path>`. If doctor reports
`No harness is installed yet`, ensure your harness is installed, then run
`apothem install --harness <name>`.

### apothem verify reports a failing adapter

Re-run apothem install to re-materialize the adapter. If the issue persists, check the
adapter-specific page under [Harness Adapters](/docs/harnesses). If the install
warned about a BEGIN marker with no END, or the failed row names a file that
holds one, re-running it does not help; see
[A file has an Apothem BEGIN marker with no END marker](#a-file-has-an-apothem-begin-marker-with-no-end-marker).
If the warning or the row says a file holds two or more whole blocks between
Apothem's markers, see
[A file holds two blocks between Apothem's markers](#a-file-holds-two-blocks-between-apothems-markers).
If it says Apothem cannot tell whether the marker lines in a file mark its
block or text of yours, see
[Apothem cannot tell its block from your text](#apothem-cannot-tell-its-block-from-your-text).

### A file has an Apothem BEGIN marker with no END marker

Apothem keeps its own text in a block that runs from a
`<!-- BEGIN APOTHEM MANAGED BLOCK -->` marker to the next
`<!-- END APOTHEM MANAGED BLOCK -->` marker. If the END marker is gone (an edit
by hand or a merge that dropped the line), or a BEGIN marker of yours sits
outside a whole block, nothing shows where Apothem's text stops and yours
starts. So Apothem never cuts the text after that marker:

- `apothem install` and `apothem update` keep it as it is, write Apothem's block
  apart from it, and print a warning that names the file and the marker's
  line, with a numbered step that changes that line (see below). The warning
  also says not to add the END marker back instead: with Apothem's block
  written apart from it, the file would then hold two Apothem blocks, which
  install and update leave as they are. A dry run reads the file before
  anything is written, so when the file holds no whole block yet, its warning
  says that if you add the END marker back instead, no line of yours may sit
  between the two markers, since the next run replaces or takes out every
  line between them, and not to add it back at all once an install or update
  has written Apothem's block apart from the marker. Until then, putting it
  back right below the old Apothem text, above your own lines, leaves one
  whole block, which the next update rewrites.
- `apothem uninstall` takes out Apothem's whole block, leaves the rest as it is,
  and names the file and the marker's line, with the same numbered step: an
  install keeps the marker as it is, and the tool still reads the text below
  it.
- `apothem verify` and `apothem doctor` fail and name the file and the
  marker's line, with the same numbered step, until the stray marker is
  changed; for a file the current install writes,
  `apothem status --profile` shows drift until then too. Running
  `apothem install` again does not clear it. Only the files Apothem keeps a
  block in for that harness count, so a marker in a file of your own does not
  fail them.

While an install record lists a file that holds no whole block but a marker
pair in code, such as a marker example you quote in a code block, install,
update and uninstall leave all of that file as it is: the pair may be Apothem's
block inside a code block of yours. Their warning, like the `apothem verify` note,
names that BEGIN marker first, then each pair, and the uninstall stays
unfinished (see
[Apothem cannot tell its block from your text](#apothem-cannot-tell-its-block-from-your-text)).
With no install record, a pair you quote in code is your text, and install and
update write Apothem's block apart from the stray marker. An END marker you
quote alone in code further down, with no marker pair after it, is different:
it closes that BEGIN marker, so an update replaces the lines between the two as
Apothem's block, and an uninstall removes them.

Apothem reads a marker only as a line of its own outside code, as a Markdown
viewer would, so a marker you quote in a sentence, in a fenced code block, or
in code indented four columns past its list item (or the margin) after a blank
line is not taken for one, and neither is a BEGIN and an END marker you quote
in two separate code blocks. A code fence you leave open to the end of the file
is read as text, however many there are, unless a BEGIN marker outside code
above it has its END marker in code and another marker pair follows them.
Markers inside an HTML block or a block quote, or after a list item whose text
goes on at the left margin, can still be read differently from a Markdown
viewer.

Every line number these warnings give counts lines as Apothem reads the file:
a line ends at CRLF, at LF, or at a CR on its own. In a file saved with CR
endings, or with one stray CR inside a line, count the lines the same way
before you change the lines a warning names.

To fix it, follow the numbered step in the warning, for example
"Fix A, if lines 77 to 148 are Apothem's block: A1. Change line 3: add a word
inside its comment." Line 3 is the stray BEGIN marker: the one with no END
marker before the next BEGIN marker, or none at all. Add a word just before
its closing `-->`, as in `<!-- BEGIN APOTHEM MANAGED BLOCK (example) -->`, and
the line no longer reads as a marker. That adds and removes no line, so
nothing else in the file reads differently, and the BEGIN line that opens
Apothem's current block stays as it is. The fix also changes every other BEGIN
marker line in the file, one you quote in a code block included, one step for
each, from the bottom of the file up (see
[Follow a numbered fix](#follow-a-numbered-fix)): a quoted BEGIN marker left as
it is could pair with an END marker below it once the uninstall takes
Apothem's block out. When the layout of the file
does not show that Apothem's block stays whole once those lines change (a
code block of yours that no line closes holds it, say), the fix changes every
BEGIN marker line in the file, the block's too, for example "Fix A: A1. Below
line 6, add a line of 3 backticks. A2. Change line 3: add a word inside its
comment. A3. Change line 2: add a word inside its comment. Apothem then reads
none of these lines as its markers, and the next update writes its block at
the end of the file." When the file ends inside a code block that no line
closes, as here, the fix first adds that code block's closing line below the
last line, so the block the next update writes there is no code. The old
Apothem text below a marker line you change, which repeats Apothem's rules,
is then yours to delete by hand. Do not add the END marker back
instead of changing the marker line: once an install or update has written
Apothem's block apart from it, the file would then hold two Apothem blocks
(see
[A file holds two blocks between Apothem's markers](#a-file-holds-two-blocks-between-apothems-markers)).
Once you change the marker line, an END marker below it pairs with nothing.
Then run `apothem update`, which writes Apothem's block back if the file no
longer holds one, and run `apothem verify` again. A BEGIN marker whose END
marker sits in code, with another marker pair after them, gets a different
warning; see
[Apothem cannot tell its block from your text](#apothem-cannot-tell-its-block-from-your-text).

### A file holds two blocks between Apothem's markers

Apothem writes one block per file. A file can still end up with two whole
blocks: an old block whose END marker you put back after an update had written
a fresh block below it, a marker pair of yours outside code (an example you
quote, say), or a block you pasted in a second time. Apothem then cannot tell
which one is its own:

- `apothem install` and `apothem update` leave the file as it is and print a
  warning that names each block by its lines, for example "holds 2 whole
  blocks between Apothem's markers (lines 1 to 32, and lines 36 to 67)". The
  run ends as partial: in place of its `✓` line it prints a `✗` line that
  names the file, its `--format json` `status` is `"partial"`, and it exits
  with code `2`, until you fix the file. In a dry run the warning says Apothem
  "would leave the file as it is".
- `apothem verify`, with or without `--profile`, and `apothem doctor` fail and
  name the file with each block (doctor's check is `harness.stray_begin`, and
  its message says the file holds "Apothem markers to fix by hand") until you
  fix the file; for a file the current install writes,
  `apothem status --profile` shows drift until then too.
- `apothem uninstall` takes out blocks that are exact copies of each other (a
  block pasted in twice, say). When a different block would be left, it
  leaves the file as it is, prints the same warning, which ends with "then run
  the uninstall again", and stays unfinished (exit code `2`) until you fix it
  (see
  [An uninstall that did not finish](/docs/cli-reference/uninstall#an-uninstall-that-did-not-finish)).
  With no install record, it leaves Claude Code's `CLAUDE.md` or a profile
  document that holds two blocks as it is too, and its warning names each
  block the same way. That warning says to run `apothem update`, then
  `apothem uninstall` again, after the fix, and it does not stop the
  uninstall. The uninstall run then names any marker lines of yours around
  Apothem's block before it takes the block out.

The warning then gives one numbered fix for each block, for the case that
it is Apothem's block, for example "Fix A, if lines 1 to 32 are Apothem's
block: A1. Change line 36: add a word inside its comment. Lines 1 to 32 are
then the one block in the file." (see
[Follow a numbered fix](#follow-a-numbered-fix)). A fix changes the BEGIN
marker line of every other block; an END marker with no BEGIN marker above
it pairs with nothing. A block whose case the layout of the file does not
show (one below a block that holds a code block, say) gets no fix of its
own, and one more fix, "in any other case", then changes every BEGIN marker
line in the file. Open the named file at the lines the warning gives:

1. Pick the fix for the block that holds Apothem's rules. In a file that
   starts with Apothem's frontmatter, that is the block right below it: an
   uninstall takes that frontmatter out only with the block right below it.
2. Do that fix's steps in the order given. Each step changes a BEGIN marker
   line in place, so the text below it stays: a marker pair of yours keeps
   your example, and the text of an older or pasted Apothem block, down to
   its END marker line, is then yours to delete by hand. Each fix holds for
   the next update as well as for an uninstall. Do not delete Apothem's block
   to keep a pair of yours: the next uninstall would then take out your pair as the one block
   left. Do not move a pair of yours into a code block either: once
   Apothem's own block is no longer whole (its END marker lost, say), a
   marker pair in code keeps install and update from writing Apothem's block
   while an install record lists the file (see
   [Apothem cannot tell its block from your text](#apothem-cannot-tell-its-block-from-your-text)).
3. Run `apothem update`, then `apothem verify` again. After an uninstall that
   did not finish, run `apothem uninstall` again instead.

A BEGIN marker above Apothem's block and an END marker below it make a second
block that shows only once Apothem's block is out. The uninstall's warning then
names Apothem's block and those two marker lines, for example "once the block
from line 5 to line 36 is out, the BEGIN marker at line 2 and the END marker at
line 39 make another", and says "Do not delete the block from line 5 to line
36": the next run would then read lines 2 to 39 as Apothem's block, and replace
or take out what is between them. Its one fix changes that BEGIN marker line
instead, keeping your own text, for example "Fix A, if lines 5 to 36 are
Apothem's block: A1. Change line 2: add a word inside its comment. Lines 5 to
36 are then the one block in the file."; then run the uninstall again. The END
marker below then pairs with nothing, so it can stay, as an example you quote
in a code block, say. Do not put both lines in one code block: it would hold
Apothem's block too. If that BEGIN marker is what is left of an older Apothem
block, the old Apothem text below it is then yours to delete by hand. An
`apothem update` does not fix such a file either, and `apothem verify` fails
until you fix it.

### Apothem cannot tell its block from your text

The warning names the file and says "Apothem cannot tell whether the marker
lines in this file mark its block or text of yours". You see it when a code
fence above Apothem's block was left open and a fence you added further down
closed it: the block then sits inside your code block. A Markdown viewer shows
those lines as code, and the same lines could be a marker pair you quote as an
example, so Apothem cannot tell whether they are its block or your text. The
same goes for a pair in indented code or indented under a paragraph, and for a
BEGIN marker outside code whose END marker sits in code while another marker
pair follows: either pair could be Apothem's block. A closing line inside
Apothem's own block can also close a code block of yours left open above it
(see below).

The warning names each marker pair in the file by the lines of its two markers
and says where they read, for example "The BEGIN marker at line 6 and the END
marker at line 38 sit inside a code block that opens at line 3." It also names
each BEGIN marker outside code that starts no marker pair, for example "The
BEGIN marker at line 1 starts no marker pair: its END marker is gone, or the
marker is yours." Then come numbered fixes, in the warnings of
`apothem install`, `apothem update` and `apothem uninstall`, the
`apothem verify` note and the fix `apothem doctor` prints, for example "Fix A:
A1. Change line 6: add a word inside its comment. Apothem then reads none of
these lines as its markers, and the next update writes its block at the end of
the file." A pair whose two marker lines both read outside code (one after a
BEGIN marker whose END marker sits in code) gets a fix of its own, for the
case that it is Apothem's block, where the layout of the file shows that it
then reads as the one whole block; the last fix, "in any other case" when
others come before it, changes every BEGIN marker line in the file. See
[Follow a numbered fix](#follow-a-numbered-fix) for how to read them.

While an install record lists the file (until an uninstall finishes; an
install ledger that cannot be read counts as one; a record made under another
spelling of the folder, such as your home reached through a link, counts too,
as it does for the uninstall, when the spelling you run under has an install
of its own still in place and the tool writes the
[shared folders in your home directory](/docs/cli-reference/install#folders-in-your-home-directory)),
`apothem install` and `apothem update` change nothing in it and print that
warning; in a dry run it says Apothem "would leave the file as it is". For a
BEGIN marker outside code whose END marker sits in code with another marker
pair after them, they do so with or without a record. Each such run ends as
partial: in place of its `✓` line it prints a `✗` line that names the file,
its `--format json` `status` is `"partial"`, and it exits with code `2`. The
warning says so: "Until you fix these marker lines as this text says, install
and update leave this file as it is and end as partial (exit code 2)." The
warning of a run that wrote the file, and so ends as a success, starts that
sentence "From the next run on, until you fix these marker lines". That
lasts as long as the marker lines stay as they are, a marker
example of yours in a code block included: such a pair may be Apothem's block
inside a code block of yours, so the warning adds that your example holds the
file back the same way until you change its BEGIN marker line, for example by
adding a word inside its comment, as in
`<!-- BEGIN APOTHEM MANAGED BLOCK (example) -->`. For a pair whose marker lines
read as part of the paragraph above them, it calls the pair "a marker example
of yours that reads as part of a paragraph". Nothing else ends it: the
uninstall does not finish while the pair is there either. A BEGIN marker outside
code that starts no pair does not change that, even when every marker pair in
the file is quoted in code below it: the marker may be what is left of
Apothem's block after its END marker was lost, but a pair in code may be
Apothem's block inside a code block of yours. The warning names such a BEGIN
marker first, and each fix changes it. The
`apothem verify` note and the fix `apothem doctor` prints give the same
sentence about ending as partial only where install and update would leave
the file as it is: with no install record, a marker pair you quote in code
does not hold the file back (see
below), unless the pair holds exactly the block the install writes. The note
and the fix do not check for that block, so for such a pair they leave that
sentence out; the next update leaves the file as it is, ends as partial and
says so.

Apothem closes a code block that a rule in your profile opens and never
closes, at the end of the block it writes, so the END marker of that block
never sits in code. A block an earlier release wrote from such a rule has no
closing line. With a marker pair of yours after it, install and update leave
the file as it is. No fix keeps that older block: a line of yours below it
closes the code block its rule opened, and once the next update replaced the
block, that line would open a code block over your text. The fix for the case
that the pair after it is Apothem's block changes the older block's BEGIN
marker line, for example "Fix A, if lines 8 to 10 are Apothem's block: A1.
Change line 1: add a word inside its comment.", and the last fix changes every
BEGIN marker line; the older block's text is then yours to delete by hand.

That closing line, or the closing line of a code block a rule in your profile
writes, can also close a code block of yours that opens above Apothem's block
and never closes, at the end of your notes, say. The block then reads as code
from its BEGIN marker on. The install or update that wrote it prints the
warning at once, without saying it left the file as it is, for example "The
BEGIN marker at line 6 sits inside a code block that opens at line 3, and the
END marker at line 44 is outside code." Its fix changes that BEGIN marker
line, as in "Fix A: A1. Change line 6: add a word inside its comment.": the
next update writes Apothem's block at the end of the file, below the line that
closes your code block, and the old block is yours to delete by hand. A dry
run reads the file before
anything is written, so it does not show that the block would read as code
once written. Deleting the block instead does not help: the next update writes
it again below the same open code block. An update that writes its block below
an older block that lost its END marker, where a rule left a code block open,
gets the same warning; it also names that older BEGIN marker, and each fix
changes it.

Until you fix the file, `apothem verify` fails and `apothem doctor` reports it
(as `harness.stray_begin`); for a file the current install writes,
`apothem status --profile` shows drift too. With no install record, verify and
doctor do not check `CLAUDE.md` or the profile document: only the record shows
that the install wrote those files. The OpenClaw verify still checks the rules
file in each workspace it finds, and fails without naming the file.

With an install record, `apothem uninstall` leaves the file as it is, removes
the rest of the install, and stays unfinished (exit code `2`, a second run
included) until you fix the file: the install record stays, so a later install
still leaves the file as it is, and the next uninstall names it again. Its
warning gives numbered fixes the same way and ends with "Then run the
uninstall again.", for example "Fix A: A1. Change line 6: add a word inside
its comment. Apothem then finds no block of its own in this file." Any marker
pair left in such a file keeps the uninstall unfinished, one of yours
included, so each fix changes the BEGIN marker line of every pair it does not
call Apothem's block. Its
`✗ <harness> uninstall did not finish:` line goes on "1 file(s) hold marker
lines Apothem cannot tell from your text, so Apothem left them as they are; fix
the marker lines each warning names, keeping your own text, then run apothem
uninstall again". With no install record, only a BEGIN marker outside code
whose END marker sits in code, with another marker pair after them, gets the
warning, and the uninstall stays unfinished (exit code `2`) for it and for the
paths no record shows (see
[An uninstall that did not finish](/docs/cli-reference/uninstall#an-uninstall-that-did-not-finish)).

Do every step of the fix you pick. If you delete only Apothem's block and leave
a BEGIN marker of yours above an END marker you quote in code, with no marker
pair after them, those two markers read as Apothem's block: the uninstall you
run again takes the lines between them out, and a later install or update
replaces them.

With no install record, a marker pair you quote in code is your text: the
install adds its block after it (in a rules file that Apothem writes with
frontmatter, that frontmatter and the block go at the top instead), unless the
pair holds exactly the block the install writes, and then it leaves the file
as it is and prints the warning. So if the install record is gone (the ledger
was deleted, say), delete Apothem's block from your code block by hand: a
later install treats it as your text.

To fix it, open the named file at the lines the warning gives. Decide which
case is true: whether the lines a fix names are Apothem's block, with
Apothem's rules between the markers, or an example of yours. Do the steps of
that fix, in the order given, and no other step (see
[Follow a numbered fix](#follow-a-numbered-fix)). Then run `apothem update`,
then `apothem verify` again. After an uninstall that did not finish, run
`apothem uninstall` again instead.

### Follow a numbered fix

The warnings for a file whose marker lines Apothem cannot place, for a file
with two or more whole blocks, for a BEGIN marker with no END marker, and for
Apothem's block that an uninstall with no install record leaves, give each
fix as numbered steps under a label that names its case, for example "Fix A,
if lines 6 to 38 are Apothem's block:", or "Fix A:" for a fix that holds
whichever lines are Apothem's. The steps of fix A are "A1.", "A2." and so on,
those of fix B "B1.", "B2.", in one paragraph, and the fix ends with what the
next run then does. Do the steps of one fix only.

Every line number in a step is the line's number in the file as it is when
the warning is printed, counted as Apothem counts lines (see
[A file has an Apothem BEGIN marker with no END marker](#a-file-has-an-apothem-begin-marker-with-no-end-marker)).
The steps run from the bottom of the file up, in the order given. Each step
is one of these, word for word, and ends with a period:

| Step | What to do |
| --- | --- |
| `Change line N: add a word inside its comment.` | Add a word to line N just before its closing `-->`, as in `<!-- BEGIN APOTHEM MANAGED BLOCK (example) -->`. The line stays where it is and no longer reads as a marker. |
| `Below line N, add a line of 3 backticks.` | Add a new line just below line N, the last line of the file, that holds that many backtick characters, or tilde characters for `tildes`, and nothing else. With `, indented 2 spaces` before the period, put that many spaces before them; without it, start the line at the left margin. |

Each `Change line` step changes a BEGIN marker line in place. Every Apothem
block, marker pair and stray marker starts at a BEGIN marker, and an END
marker pairs only with the BEGIN marker right above it, so an END marker with
no BEGIN marker above it marks nothing, and one you quote stays your text as
it is. A changed line is still an HTML comment on a line of its own: no line
moves, and a Markdown viewer reads every other line as before.

A fix that keeps a block changes every other BEGIN marker line in the file.
The warning gives it only where the layout of the file shows that the block
then reads as the one whole block: no code block of yours that runs to the end
of the file holds it, and no line from the first changed line down to the
block changes how its BEGIN marker reads. It ends "The next update then
replaces Apothem's block", "Lines 1 to 32 are then the one block in the
file", or, for an uninstall, "The uninstall run again then takes Apothem's
block out". A fix that keeps no block changes every BEGIN marker line in the
file and ends "Apothem then reads none of these lines as its markers, and the
next update writes its block at the end of the file", or, for an uninstall,
"Apothem then finds no block of its own in this file". Either way, any old
Apothem text below a line you change, with its END marker line, is then yours
to delete by hand.

A code block of yours that no line closes runs to the end of the file in a
Markdown viewer, but Apothem reads its opening line as text. A code block in
your profile's rules would close it, and the BEGIN marker of Apothem's block
would then read as code. So when your file ends inside such a code block, a
fix that leaves no Apothem block in the file first adds that code block's
closing line below the last line, as in "A1. Below line 7, add a line of 3
backticks.": the next install or update adds its block at the end of the
file, after it. No fix keeps a block that such a code block holds.

Apothem reads a code fence inside an HTML block, such as a comment that opens
with `<!--` and ends on a later line, as it reads any other code fence, and a
line of a list item's text that goes on at the left margin ends that item for
Apothem. A Markdown viewer does neither. When a line above the code block your
file ends in may start an HTML block (any line that starts with a tag counts,
except a link in angle brackets, a tag on a line right below a line of plain
text, and HTML in a code block), or a list item's text goes
on at the left margin above it and an indented line follows, that closing line
could start a code block in a viewer instead. That fix then gives no numbered steps: it says "Apothem cannot give
numbered steps for this fix" and names the line that opens the code block.
Edit the file by hand so that line opens no code block, or so that the code
block is closed where your viewer shows it ends; the next warning for the file
then gives numbered steps.

### Hooks not firing in Claude Code

Confirm Apothem is wired by checking ~/.claude/settings.json for the hook entries.
If the file is missing the hooks, run apothem install again.

### OpenCode does not load the Apothem rules

`apothem install`, `apothem update` and `apothem verify` print a note when a
file of yours in OpenCode's configuration folder keeps OpenCode 1 from loading
the `instructions` list Apothem writes in `opencode.json`:

- An `opencode.jsonc` with its own `instructions` list, even an empty one,
  replaces Apothem's list. Remove that key, or move its entries into the list
  in `opencode.json`, where installs keep the entries they did not write.
- A `config.json`, `opencode.json` or `opencode.jsonc` there that OpenCode 1
  cannot read or parse stops OpenCode 1 from loading any of its configuration.
  So does one whose top level is not an object, whose `instructions` value is
  not a list of text, or whose `{file:path}` names a file OpenCode 1 cannot
  read, and a folder with one of those names. Correct the file so it is one
  JSON object with only comments and trailing commas added, with `instructions`
  as a list of text, or move it out of the folder. When the note says the file
  breaks once OpenCode 1 puts in its `{env:NAME}` values, change that variable
  so its value holds no backslash, double quote or control character, for
  example a Windows path written with forward slashes. When the note says
  Apothem writes that `{env:NAME}` for an MCP server in your profile, an update
  writes back a reference removed from the file, so change the variable or, to
  keep it as it is, restate that server under
  `harnesses.opencode.mcp_servers.<name>` with the value saved in a file and
  written as a `{file:path}` that names it. When the note names a second
  problem with the file, fix that too. When it says Apothem cannot tell
  whether OpenCode 1 can read the file a `{file:path}` names, make sure that
  file can be read as well.

These notes are about OpenCode 1. OpenCode 2 reads both lists and reads no
`config.json`. It skips a file it cannot parse or whose top level is not an
object, which for `opencode.json` means it misses the rules too; a note says
what OpenCode 2 does with its file when that is known. The notes change no file
and no exit code. When install or update cannot parse `opencode.json` at all,
they stop with a `config.unparseable` error instead. See
[OpenCode](/docs/harnesses/opencode) for the details.
