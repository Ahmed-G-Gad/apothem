## Update the Claude Code plugin

Refresh the marketplace listing, then update the plugin from the `/plugin`
menu inside Claude Code:

```text title="Inside Claude Code"
/plugin marketplace update apothem
```

Open `/plugin`, select **apothem**, and choose the update action when a newer
plugin version is listed.

## npx always runs the current release

`npx @ahmed-g-gad/apothem` resolves the current published package on each
run, so there is nothing to update. When a stale npx cache serves an older
copy, pin the dist-tag explicitly:

```bash
npx @ahmed-g-gad/apothem@latest --version
```

## Update an installer-based setup

Re-run the installer — it is idempotent: it fetches an existing git clone,
checks the new release tag, and only then checks the clone out, and it updates
a release-archive install — or run the dedicated update script, which works on
a git clone:

```bash title="macOS · Linux · WSL2 · BSD"
bash scripts/installer/update.sh
```

```powershell title="Windows · PowerShell"
pwsh -NoProfile -File scripts/installer/update.ps1
```

The update script moves the source tree at `APOTHEM_HOME` (default
`~/.apothem`) to `APOTHEM_REF` — unset resolves the latest signed
`vMAJOR.MINOR.PATCH` release tag, a tag value pins it, and `main` selects the
moving branch only when `APOTHEM_ALLOW_UNVERIFIED=1` is also set. Without that
override, the update aborts before it checks anything out or re-materializes,
because a branch is not a signed release tag. It fetches the ref first and
verifies the tag's signature with `git verify-tag` before the checkout, so a
failed check leaves the clone at the version it was on. The signature must be
made by the maintainer key published in SECURITY.md, and the signed tag must
be the one named for the release; an unsigned or tampered tag, or one signed by
any other key, aborts unless `APOTHEM_ALLOW_UNVERIFIED=1` downgrades the abort
to a warning (that variable does not bypass the check that the signed tag is
the release tag). Because that variable lets an unsigned tag, or one signed by
another key, through, the check protects only tags that carry the maintainer
key's signature. With a non-release ref such as `main`, the clone follows
origin's copy of that branch. The checkout never discards local changes: a clone with
changes to tracked files stops the update, and you commit or stash them and
re-run. Before it fetches, the update also stops when files are marked
assume-unchanged or skip-worktree (git would not see their changes), when the
clone's work tree is not `APOTHEM_HOME`, when the clone holds a submodule,
when `.git/info/attributes` sets a `filter=`, or when the clone's
`.git/config` or `.git/config.worktree` holds a setting other than the ones
`git clone` and `git init` write there, branch settings, `user.name`,
`user.email`, `maintenance.auto`, `maintenance.strategy`, `pull.rebase` and
`pull.ff`. The message names the setting and the file it is in, and
[Troubleshooting](/docs/install/troubleshooting#the-installer-stops-the-existing-clone-is-set-up-in-a-way-the-update-would-trust)
lists the accepted settings. The clone's git hooks never run during the
update, and a clone of a project other than Apothem is not updated at all.
Each run holds a lock, `<APOTHEM_HOME>.lock`, for its whole length, so a
second install, update or uninstall on the same `APOTHEM_HOME` stops; see
[Troubleshooting](/docs/install/troubleshooting#the-installer-stops-another-run-holds-the-lock)
when a lock is left behind. A signed tag
whose maintainer public key is missing from the local keyring aborts with
key-import guidance pointing at the fingerprint published in
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md).
It then
re-materializes the harness named by `APOTHEM_HARNESS` by running
`apothem update` from the refreshed tree (the harness defaults per the
[installer environment variables](/docs/how-to/installer-environment-variables)
table). It requires a prior install: when
no tree exists at `APOTHEM_HOME` and `APOTHEM_SOURCE` is unset, it exits with
a message directing you to the installer first.

The update script works only on a git clone. An install made with cosign, or
with `APOTHEM_VERIFY=checksum`, places the release archive instead, so the
update script stops and tells you to re-run the installer with cosign and
`gpg` on `PATH`. That re-run swaps in the new release and keeps every file it
does not ship, including the engine's backups and install ledgers. Without
cosign, re-run the installer with `--yes` (`-Yes` on Windows): it switches the
archive install to a git clone checked against the maintainer key, and keeps
everything that is not part of the source tree, including the backups,
ledgers, plans and memory. `APOTHEM_VERIFY=checksum` also updates the archive
in place and needs `APOTHEM_ALLOW_UNVERIFIED=1`. Checksum mode does not verify
the release. SHA256SUMS comes from the same release as the archive, so a match
only shows the download isn't damaged; anyone who can change the release's
files can change both.

## Re-materialize harness output

After updating the engine or editing `~/.config/apothem/profile.yaml`,
re-derive the installed harness config. User-scope adapters do not need
`--project`; project-scope adapters do.

```bash
apothem update --harness claude-code
apothem update --harness cursor --project /path/to/project
apothem update --harness all --project /path/to/project
```

Run the same command with `--dry-run --json` when you need a machine-readable
preview with no filesystem writes.

## Current command boundary

`apothem update` updates harness output only. The CLI does not implement
`update --self`, `update --check`, or `update --apply`; update the engine
itself through the channel you installed with — the `/plugin` flow, a fresh
`npx` run, or the installer/update scripts above.

## Check the engine version

```bash
apothem --version

```
