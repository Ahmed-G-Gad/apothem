Apothem installs in under two minutes and works alongside your existing
harness configuration. Every path runs the same self-contained engine — the
source tree carries its vendored dependencies and runs from a checkout on
system Python 3.10 or newer (see
[the self-contained runtime](/docs/architecture/self-contained-runtime)).

**Two prerequisites are shared by every path:** system **Python 3.10 or newer**
on `PATH`, with the `click` and `rich` packages importable under it. The npm
shim (channel 2), the VS Code-family extension (channel 4), and the
command-line bootstraps (channels 5–7) additionally need **Node.js 18 or
newer** to run `npx`. Python 3.10 and Node.js 18 and 20 are past upstream end
of life; they remain supported and tested, but newer versions are preferred (see
[Prerequisites at a glance](#prerequisites-at-a-glance)). Each channel's own
section below repeats its exact prerequisites, one copy-ready command, and a
verification step.

## Choose a channel

Eight install channels are available. Pick by how you already work.

| # | Channel | Delivers | Prerequisites |
|---|---------|----------|---------------|
| 1 | [Claude Code plugin](#1-claude-code-plugin) | Full harness in Claude Code | Claude Code · Python 3.10+ |
| 2 | [npm shim (`npx`)](#2-npm-shim-npx) | Full harness, any tool | Node 18+ · Python 3.10+ |
| 3 | [One-shot installers](#3-one-shot-installers) | Full harness + an `apothem` command | Python 3.10+ (`git` for a network install) |
| 4 | [VS Code family extension](#4-vs-code-family-extension) | Full harness from the editor | VS Code · Node 18+ · Python 3.10+ |
| 5 | [Command-line bootstrap (extension host)](#5-command-line-bootstrap-extension-host) | Bootstrap that runs the engine | Its host tool · Node 18+ · Python 3.10+ |
| 6 | [Command-line bootstrap (`qwen-code` host)](#6-command-line-bootstrap-qwen-code-host) | Bootstrap that runs the engine | Its host tool · Node 18+ · Python 3.10+ |
| 7 | [Command-line bootstrap (plugin host)](#7-command-line-bootstrap-plugin-host) | Bootstrap that runs the engine | Its host tool · Node 18+ · Python 3.10+ |
| 8 | [Direct engine (`python -m apothem`)](#8-direct-engine-python--m-apothem) | Full harness from a checkout | Python 3.10+ (`click`, `rich`) |

<Callout title="Which channels deliver the full harness">
  The npm shim (2), the one-shot installers (3), and the direct engine (8)
  materialize the whole synced unit for any harness on their own. The three
  command-line extensions (5–7) install a small **bootstrap** that shells out
  to the engine (`npx @ahmed-g-gad/apothem install`) to materialize the full
  harness — they are the entry point, not the full delivery by themselves. The
  Claude Code plugin (1) carries the engine and runs it directly. The
  VS Code-family extension (4) carries no engine of its own: its commands run
  the engine through the npm shim by default.
</Callout>

Every path is idempotent: re-running is safe and converges to the same state.

## 1. Claude Code plugin

**Prerequisites:** Claude Code, and system Python 3.10+ on `PATH`.

The plugin path runs entirely inside Claude Code. It bundles the Apothem
engine with its slash commands, delegated workers, skills, rules, and hooks,
all runnable from the self-contained plugin tree:

```text title="Inside Claude Code"
/plugin marketplace add ahmed-g-gad/apothem
/plugin install apothem@apothem
```

After the install, the Apothem command set, the bundled delegated workers, the
skills, and the four [output styles](/docs/reference/output-styles) (pick one
with `/output-style` or from `/config`) are available in every Claude Code
session. The plugin ships each command as a skill, a `SKILL.md` with the
detail it loads on demand in a `references/` folder beside it, so Claude Code
invokes it with the plugin's prefix: `/apothem:plan-spec`,
`/apothem:security-audit`, and the rest. Two names are taken by Claude Code
itself: `/plan` enters plan mode and `/code-review` runs the bundled review, so
type `/apothem:plan` and `/apothem:code-review` for the Apothem commands. When
the Apothem engine installs into Claude Code instead of the plugin, the same
skills are written to `~/.claude/skills/` without a prefix, and a personal
`code-review` skill replaces the bundled `/code-review` (its `/review` alias
still runs the bundled one). Two names, `projectify` and `workflow`, are also
native skills; the native skill is the one the plugin and the engine install
ship, not a skill derived from the command. See
[Claude Code](/docs/harnesses/claude-code#command-skills-and-reference-files)
for how the commands are split, and [Slash commands](/docs/reference/commands)
for the full command catalog.

**Verify:** run `/plugin` inside Claude Code and confirm **apothem** is listed
as installed, or check the drift report from a terminal:

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 2. npm shim (`npx`)

**Prerequisites:** Node.js 18+ (for `npx`) and system Python 3.10+ on `PATH`.
The shim locates the interpreter and forwards every CLI command to the bundled
engine — nothing is placed permanently on your system. It tries `python3`,
`python`, then `py -3` in that order; set **`APOTHEM_PYTHON`** to an
interpreter path to try it first, which is what you need when Python is
installed but not on `PATH`, or when several versions are and you want a
specific one. The interpreter you name still has to pass the Python 3.10+
check; when it does not, the shim falls back to `python3`, `python`, then
`py -3`.

```bash title="npx"
npx @ahmed-g-gad/apothem install --harness claude-code
```

On a machine with no profile, this first `install` creates the starter profile
at `~/.config/apothem/profile.yaml` and says so. Its identity fields are
placeholders: personalize them (`npx @ahmed-g-gad/apothem profile edit`), then
rerun the command with `update` in place of `install` to apply them.

It also runs straight from the repository:

```bash title="npx from the repository"
npx github:ahmed-g-gad/apothem install --harness claude-code
```

Every command in the [CLI reference](/docs/cli-reference) works in this form;
substitute `npx @ahmed-g-gad/apothem` for `apothem`. This is also the install
path for OpenCode and every other tool that exposes no separate plugin or
extension registry — Apothem syncs those straight into their native config
directory (`npx @ahmed-g-gad/apothem install --harness opencode`).

**Verify:**

```bash title="Verify"
npx @ahmed-g-gad/apothem --version
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 3. One-shot installers

**Prerequisites:** system Python 3.10+ on `PATH` (the installer offers to add
the `click` / `rich` prerequisites for you). For a network install: `git`,
to find the latest release, and `gpg`, to check the signed release tag (Git for
Windows ships both). [cosign](https://docs.sigstore.dev/cosign/system_config/installation/)
is optional: with it, the installer also checks the signed release archive.

The installer scripts resolve the latest release, check it (see
[Trust model](#trust-model)), place the Apothem source tree at `~/.apothem`,
create a starter profile when none exists, materialize your first harness, and
verify the result, all in one run. The starter profile carries placeholder
identity fields: edit it, then run `apothem update --harness <name>` to apply
yours. Re-running is idempotent: a git clone is fetched, its new tag is
checked, and only then is the clone checked out to the resolved tag; a
release-archive install is updated in place; and the harness is
re-materialized. The verified install is the default and recommended path.

Import the maintainer signing key once first. Every network install checks
the release tag against it, with or without cosign, and stops when the key is
not in your keyring. Check that the fingerprint reads
`5C89 98F9 F241 7204 45D3  F28B 7039 6FED 9C63 4163`, the value
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md#maintainer-signing-key)
publishes. On Windows, `git verify-tag` reads the keyring of the `gpg` that
ships with Git for Windows, so the import runs through Git's own `bash`:

```bash title="macOS · Linux · WSL2 · BSD — import the key once"
curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import
gpg --fingerprint 70396FED9C634163
```

```powershell title="Windows · PowerShell — import the key once"
& "$env:ProgramFiles\Git\bin\bash.exe" -c 'curl -fsSL https://github.com/ahmed-g-gad.gpg | gpg --import && gpg --fingerprint 70396FED9C634163'
```

```bash title="macOS · Linux · WSL2 · BSD — latest signed tag, verified"
curl -fsSL https://apothem.ahmedgad.com/install.sh | bash
```

```powershell title="Windows · PowerShell — latest signed tag, verified"
irm https://apothem.ahmedgad.com/install.ps1 | iex
```

The same scripts ship in a checkout under `scripts/installer/` — `install`,
`uninstall`, and `update` in `.sh`, `.ps1`, and `.bat` forms — so you can run
them directly after cloning:

```bash title="From a checkout"
APOTHEM_HARNESS=claude-code sh scripts/installer/install.sh                                 # POSIX
$env:APOTHEM_HARNESS = 'claude-code'; pwsh -NoProfile -File scripts/installer/install.ps1   # Windows
```

A piped one-liner never uses a local tree: `curl ... | sh` and `irm ... | iex`
ignore the folder you run them from and its parent folders, and fetch and
verify the release. The installer uses a local tree only when you run the
checkout's own `scripts/installer/install.sh` (or `install.ps1`) by its path,
from any folder (for example `sh ~/src/apothem/scripts/installer/install.sh`),
or when `APOTHEM_SOURCE` names that tree. The engine and the `apothem` command
never import `click`, `rich` or `apothem` modules from the current folder.

Empty and relative entries in your own `PYTHONPATH` are not passed on to the
engine by any launcher (the installers, updaters, uninstallers, the POSIX and
Windows `apothem` shims, and the npm launcher). A kept entry must be a full
path: on Windows a drive path such as `C:\lib` or a network path, elsewhere a
path that starts with `/`. A rooted `\lib` or a drive-relative `C:lib` is
dropped. Under Git Bash, Windows-style entries are kept as such. The
installers' `git` commands that do not work on a clone do not read a
repository in the current folder.

### Trust model

With no `APOTHEM_REF` set, the installer resolves the highest
`vMAJOR.MINOR.PATCH` release and installs *that* — never the moving `main`
branch. It checks the release before any configuration is materialized, and
the check depends on whether `cosign` is on your `PATH`:

- **With cosign**, two checks must both pass. First, the release tag must
  carry a valid signature from the maintainer key, checked as in the next
  item, and the signed tag must be the one named for that release: a signed
  tag for another release, re-pointed at this name, is refused. Then the
  installer downloads the release's platform archive, its `SHA256SUMS` file
  and `SHA256SUMS.cosign.bundle`. cosign must confirm that Apothem's release
  workflow signed `SHA256SUMS` for that exact tag and, through its
  `--certificate-github-workflow-sha` check, that the certificate it verified
  was issued to a run on the commit the signed tag points at. The installer
  does not read the certificate itself. The archive's SHA-256 must then match
  the listed digest. The workflow runs for any tag that is pushed, so its
  signature alone is not enough; the tag signature shows the maintainer
  released that commit.
- **Without cosign**, or when `APOTHEM_HOME` already holds a git clone, the
  installer clones or updates the repository and checks the tag alone with
  `git verify-tag`. The signature must be valid *and* made by the
  maintainer key published in [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md), and the signed tag must be the one named for
  the release. A tag signed by any other key is refused,
  even when your keyring trusts that key. A signed git tag names its commit by
  a SHA-1 ID; with cosign, the installer also checks the archive's SHA-256.
  An existing clone is fetched and its new tag is checked *before* the clone
  is checked out. A failed check leaves the clone as it was, and a clone with
  changes to tracked files stops the update with a message to commit or stash
  them, instead of losing them. With a non-release ref such as `main`, an
  existing clone follows origin's copy of that branch.

The installer ignores the git environment variables that redirect git
(`GIT_DIR`, `GIT_WORK_TREE` and similar) and stops when `APOTHEM_REPO` starts
with `-`.

A failed check aborts the install before any configuration is written and
before the installer replaces `APOTHEM_HOME`. A
signed tag whose maintainer public key is not yet in the local keyring aborts
with key-import guidance instead: import the key as shown above, check its
fingerprint against the value published in [SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md), and re-run.

A re-run with cosign updates an earlier release-archive install. The new
source is checked and unpacked in a folder beside `~/.apothem` first, then
swapped in. Everything in `~/.apothem` that is not part of the source tree
carries over to the new install: the engine's rollback backups (`backups/`),
install ledgers (`state/`), plans, memory and its other data. If a step fails
or you interrupt the run, the earlier install is put back unchanged; if even
that fails, the message names where the earlier files are. These rules apply
when the installer replaces `~/.apothem`:

- A git clone is not replaced by a release archive without `--yes`. The files
  the clone does not track move into the new install, and the clone's own tree
  (its history and source) moves to `~/.apothem.before-apothem-<time>`; the
  installer says where, and you delete it once you no longer need it. Even
  with `--yes`, the installer refuses while the clone holds local
  work it would lose: changes, stashes, unpushed commits, or untracked files
  in its source tree. Commit and push that work, or move it elsewhere, then
  re-run. This check also runs with `--dry-run`. A `.git` file (a linked
  worktree) counts as a clone, and so does a `.git` folder.
- A git clone of anything other than Apothem is treated like any folder that
  holds no Apothem install (see below), never updated or replaced as a clone.
- An existing clone is updated in place only when git can see every change in
  it and nothing in its own setup runs code during the update. Before the
  fetch, the installer stops when files are marked assume-unchanged or
  skip-worktree, when the clone's work tree is not `APOTHEM_HOME`
  (`core.worktree`, or a `.git` file pointing at another clone), or when the
  clone's `.git/config` sets `gpg.program`, `gpg.openpgp.program`,
  `core.fsmonitor`, `core.hooksPath`, `include.*` or `includeIf.*`. The
  clone's git hooks never run during the update.
- A folder that holds only the engine's own data (`backups`, `state`, `plans`,
  `memory`, `contexts`, `learning`, `providers`) is updated without `--yes`,
  and that data is kept.
- A folder that holds no Apothem install is not touched without `--yes`. With
  `--yes`, the installer moves the whole folder, unchanged, to
  `~/.apothem.before-apothem-<time>`, says where, and installs fresh.
- A symbolic link at `APOTHEM_HOME` (on Windows, a symbolic link or a
  junction) is refused, because replacing it would replace the link and not
  the folder it leads to. Point `APOTHEM_HOME` at that folder and re-run. The
  exception is an existing git clone, which is updated in place.
- On Linux and macOS, a file or folder to carry over whose name has a space or
  another special character stops the install. Move it out of `APOTHEM_HOME`
  first.

`--dry-run` (`-DryRun` on Windows) fetches and checks the release in a
temporary folder, applies the same refusals as a real run, and leaves
`~/.apothem` unchanged. Pin a specific release with `APOTHEM_REF`:

```bash title="Pinned, verified install"
APOTHEM_REF=vMAJOR.MINOR.PATCH sh -c "$(curl -fsSL https://apothem.ahmedgad.com/install.sh)"
```

Replace `vMAJOR.MINOR.PATCH` with a tag from the
[releases page](https://github.com/ahmed-g-gad/apothem/releases). The oldest
release tag is a lightweight tag with no signature of its own, so the tag
check aborts on it even though its commit is signed; every later release tag
is annotated and signed. The
[SECURITY.md](https://github.com/ahmed-g-gad/apothem/blob/main/SECURITY.md)
release-signing section lists each tag and how to verify it.

Explicit overrides relax the default. `APOTHEM_ALLOW_UNVERIFIED=1` downgrades a
failed tag check on the clone path to a warning and proceeds, for air-gapped or
local use, or to install a release that predates tag signing. It never relaxes
the cosign path, so set `APOTHEM_VERIFY=signature` with it on a host that has
cosign. It also never relaxes the check that the signed tag is the one named
for the release. Because the override lets an unsigned tag, or one signed by
another key, through, that check protects only tags that carry the maintainer
key's signature. `APOTHEM_REF=main` checks out the moving branch without
verification only together with `APOTHEM_ALLOW_UNVERIFIED=1`. With
`APOTHEM_REF=main` alone, the installer fetches `main` into a staging folder
(into the existing clone, when `APOTHEM_HOME` is one), then aborts before it
checks anything out, replaces `APOTHEM_HOME` or materializes any
configuration, because a branch is not a signed release tag. A local checkout via `APOTHEM_SOURCE` fetches nothing and
skips verification.

Set `APOTHEM_VERIFY` to pick the check yourself. The default is `auto`:

| Value | What the installer checks |
| --- | --- |
| `auto` (default) | `release` when `cosign` is on `PATH` and `APOTHEM_HOME` is not a git clone, otherwise `signature` |
| `release` | The release tag's signature from the maintainer key and that the signed tag is the one named for the release, then cosign's check that the release workflow signed `SHA256SUMS` in a run on the tag's commit, then the archive's SHA-256. Stops if cosign or `gpg` is missing |
| `signature` | The release tag's GPG signature, which must come from the maintainer key, and that the signed tag is the one named for the release |
| `checksum` | The archive's SHA-256 against `SHA256SUMS` alone. Needs `APOTHEM_ALLOW_UNVERIFIED=1`, and warns before it downloads. Checksum mode does not verify the release. SHA256SUMS comes from the same release as the archive, so a match only shows the download isn't damaged; anyone who can change the release's files can change both. Use it only on a host with neither cosign nor `gpg`, and only when you accept that |

Every archive mode aborts on a digest mismatch before extracting anything.
Early releases name the bundle `SHA256SUMS.sig`, and the installer reads that
name when `SHA256SUMS.cosign.bundle` is absent.

The engine then runs directly from the placed tree. Every third-party
dependency except `click` and `rich` is vendored inside the source tree, and
the entry point puts that vendor directory on `sys.path` itself. The installer
prints the full path of the `apothem` shim it wrote. When it wrote no shim, it
prints a command that starts the engine with the current folder kept off
`sys.path`; copy that command from the banner.

Both scripts read the same configuration environment variables
(`APOTHEM_HOME`, `APOTHEM_REPO`, `APOTHEM_REF`, `APOTHEM_ALLOW_UNVERIFIED`,
`APOTHEM_VERIFY`, `APOTHEM_RELEASE_BASE`, `APOTHEM_SOURCE`, `APOTHEM_HARNESS`, `APOTHEM_PROFILE`,
`APOTHEM_SKIP_VERIFY`, `APOTHEM_AUTO_INSTALL_DEPS`, `APOTHEM_BIN_DIR`); see
[Installer environment variables](/docs/how-to/installer-environment-variables)
for the full table and
[Self-contained runtime](/docs/architecture/self-contained-runtime) for how the
`python -m` invocation model works.

**The `apothem` command.** After a successful install, the installer writes an
`apothem` shim that forwards to the bundled engine — POSIX into
`$HOME/.local/bin`, Windows into `%LOCALAPPDATA%\Microsoft\WindowsApps` (a user
directory already on the default Windows `PATH`). The installer never edits your
`PATH`. Once the directory is on `PATH` you run `apothem <command>` directly,
with no manual `PYTHONPATH`.

**Verify:**

```bash title="Verify"
apothem verify --harness claude-code

# or, before the shim is on PATH, from the bundled source:
PYTHONPATH="$HOME/.apothem/src" python -m apothem verify --harness claude-code
```

## 4. VS Code family extension

**Prerequisites:** VS Code, Node.js 18+, and system Python 3.10+ on `PATH`.

The **Apothem for VS Code** extension is on the
[Visual Studio Marketplace](https://marketplace.visualstudio.com/items?itemName=ahmed-g-gad.apothem-vscode)
as `ahmed-g-gad.apothem-vscode`: install it from the Extensions view or with
`code --install-extension ahmed-g-gad.apothem-vscode`. It also installs from an
`apothem.vsix` package: `code --install-extension apothem.vsix`, or the
editor's *Install from VSIX…* command. The release workflow signs the package and attaches it to each GitHub
Release. Releases published before the workflow packaged the extension carry
no `.vsix`; when the latest release lacks it, build the package from a checkout
with the vsce release locked in `tools/vsce/` (that vsce release needs
Node.js 22 or later):
run `npm ci --prefix tools/vsce --ignore-scripts`, then
`cd vscode-extension && ../tools/vsce/node_modules/.bin/vsce package --no-dependencies --out apothem.vsix`.
A copy installed from an earlier `apothem.vsix` carries the identifier
`ahmed-g-gad.apothem`; uninstall it (`code --uninstall-extension ahmed-g-gad.apothem`)
so the two copies do not both register the same commands. One extension covers the editors of the VS Code family. Its palette
commands (`Apothem: Install`, `Verify`,
`Update`, `Uninstall`, `Doctor`) run the same engine through the configured
runner (`npx @ahmed-g-gad/apothem@<extension version>` by default, so the
extension runs the engine version it shipped with; point the `apothem.runner`
user setting at a local checkout to run from source). Install, Verify, Update and Uninstall
ask which harness to act on, offering the editor's own harness first; `all` is
a choice, never the default. The `apothem.runner` setting is machine-scoped, so
a workspace cannot change it, and the extension runs only in a trusted
workspace.

**Verify:** run the **Apothem: Verify** command from the editor's command
palette, or from a terminal:

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

## 5. Command-line bootstrap (extension host)

**Prerequisites:** its host command-line tool, Node.js 18+, and system Python
3.10+ on `PATH`.

Install Apothem as an extension straight from the repository — the command
carries the exact host and harness slug:

```bash title="Install the extension"
gemini extensions install https://github.com/ahmed-g-gad/apothem
```

This extension is a **bootstrap**, not the full install on its own: it loads an
Apothem context file and adds a `/apothem` command that shells out to the engine
(`npx @ahmed-g-gad/apothem`). Materialize the full harness by running the
install through it:

```bash title="Materialize the full harness"
npx @ahmed-g-gad/apothem install --harness gemini-cli --project .
```

**Verify:**

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness gemini-cli --project .
```

## 7. Command-line bootstrap (plugin host)

**Prerequisites:** its host command-line tool, Node.js 18+, and system Python
3.10+ on `PATH`.

Add the repository as a plugin marketplace, then install the plugin — the
command carries the exact host and harness slug:

```bash title="Install the plugin"
codex plugin marketplace add ahmed-g-gad/apothem --sparse .agents/plugins --sparse plugins/apothem
codex plugin add apothem@apothem
```

The two `--sparse` paths fetch only the marketplace listing and the plugin,
not the whole repository; a full clone can run past the host's 30-second
clone limit on a slow disk, such as a Windows drive under WSL.

Like the channel-5 and channel-6 extensions, this is a **bootstrap** that shells
out to the engine. The plugin bundles one entry skill; its manifest is a root
`plugin.json`, and the
[plugin host's harness page](/docs/harnesses/codex#codex-plugin) describes the
layout and what the plugin leaves to the engine. Materialize the full harness by
running the install through it:

```bash title="Materialize the full harness"
npx @ahmed-g-gad/apothem install --harness codex
```

**Verify:**

```bash title="Verify"
npx @ahmed-g-gad/apothem verify --harness codex
```

## 8. Direct engine (`python -m apothem`)

**Prerequisites:** system Python 3.10+ with the `click` and `rich` packages
importable, plus a checkout of the repository. No Node.js required.

Run the engine straight from a clone. The entry point puts the vendored
dependencies (`src/apothem/_vendor`) on `sys.path`, so with `click` and `rich`
importable, `PYTHONPATH=src` is the whole setup:

```bash title="Direct engine"
git clone https://github.com/ahmed-g-gad/apothem
cd apothem
PYTHONPATH=src python -m apothem install --harness claude-code
```

As with the npm shim, a first `install` on a machine with no profile creates the
starter profile at `~/.config/apothem/profile.yaml` and continues.

**Verify:**

```bash title="Verify"
PYTHONPATH=src python -m apothem verify --harness claude-code
```

## Verify any install

Every channel above names its own verification command. The two general forms
are:

```bash title="Installer path"
PYTHONPATH="$HOME/.apothem/src" python -m apothem verify --harness claude-code
```

```bash title="npx path"
npx @ahmed-g-gad/apothem verify --harness claude-code
```

Replace the harness name with whichever adapter you installed; see the
[harness list](/docs/harnesses) for all supported names. To check every
installed adapter at once (its verify and its hook commands), run `doctor`
in place of `verify --harness NAME`, in whichever form you used above:
`apothem doctor`, `PYTHONPATH="$HOME/.apothem/src" python -m apothem doctor`, or
`npx @ahmed-g-gad/apothem doctor`. For the plugin path, run
`/plugin` inside Claude Code and confirm **apothem** is listed as installed.

## Prerequisites at a glance

- **Python 3.10 or later** — the paths that locate it do so by name, and the
  names differ by path. The npm shim tries `python3`, `python`, then `py -3`.
  The installers try `python3`, `python`, and the versioned names `python3.14`
  down to `python3.10`.
- **`click` and `rich` importable** under that interpreter — the two
  terminal-facing dependencies the engine does not vendor. The installers
  check both, name anything missing, and offer to install it for you — with
  your confirmation, or automatically with `--yes` (`-Yes` on PowerShell) or
  `APOTHEM_AUTO_INSTALL_DEPS=1`. On every other channel, a missing package
  stops the engine with an error (exit 1) that names the exact command for the
  interpreter it found, with the version constraints Apothem is tested
  against (`<interpreter> -m pip install "click==…" "rich>=…"`); with `--json` the
  same error arrives as a JSON envelope with code `runtime.dependency_missing`.
- **Node.js 18 or later** — only the paths that run `npx`: the npm shim (2),
  the VS Code-family extension (4), and the command-line bootstraps (5–7).
- **End-of-life runtimes.** Python 3.10 reached upstream end of life on
  2026-10-01, and Node.js 18 and 20 on 2025-04-30 and 2026-04-30. Apothem
  still supports them as its declared floors and tests each one in CI, but
  they no longer receive upstream security fixes, so prefer Python 3.11 or
  newer and Node.js 22 or newer. The
  [runtime-floor policy](/docs/governance/release-engineering-policy#runtime-floors)
  explains how a floor is raised.
- **Git and GnuPG** — installer path only, and only for the network form (the
  script finds the latest release and checks its signed tag with them, and,
  without cosign, clones the source; a local checkout needs neither).
- **Claude Code** — plugin path only. **VS Code** and each command-line
  bootstrap's own host tool are needed only for their own channel (4–7).
